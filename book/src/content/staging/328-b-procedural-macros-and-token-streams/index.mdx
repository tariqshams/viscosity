## A derive of your own

`#[derive(Debug)]` works on any struct you write, however many fields
it has and whatever their types. Say you want the same for a trait of
your own, a `describe()` method that prints a struct's name and each
field with its value. A `macro_rules!` macro could handle the simplest
structs; however, real structs have generics, attributes, `pub`,
comments and types with commas inside them, and writing a matcher for
all of that is a parser written in patterns. What you want is to write
the code generator in plain Rust, with loops, `match` and `Vec`, and
have the compiler run it for you. That is a **procedural macro**.

<Analogy title="a robot at a tailor's">
You hand the robot a paper pattern for a jacket. It reads the pattern,
measures each piece, and stitches a lining that fits exactly, then
hands you the jacket and lining together. A derive macro reads your
struct the same way and hands back the struct plus an `impl` that fits.
<span slot="breaks">The robot can try the jacket on a dummy; a macro
cannot try anything. It sees the struct's tokens only, before types
are known, so it cannot ask whether a field's type implements `Debug`
(the compiler checks that later, in the code it writes).</span>
</Analogy>

<Analogy title="a translator given one page">
A translator is handed one page and returns it in another language;
they never see the rest of the book. A procedural macro is handed
exactly the tokens of the item it is attached to, and returns tokens.
<span slot="breaks">A translator understands sentences. A macro gets
no sentences at all, only a flat run of words and brackets, and must
work out the structure itself (or ask the `syn` crate to).</span>
</Analogy>

## Tokens in, tokens out

A procedural macro is a public function with a special attribute, in a
crate of its own whose `Cargo.toml` says `[lib] proc-macro = true`.
It takes a **`TokenStream`** and returns one. The Reference describes a
token stream as "roughly equivalent to `Vec<TokenTree>`", where a
**token tree** is an identifier (`Ident`), a punctuation mark
(`Punct`), a literal (`Literal`), or a **group**: a bracketed run of
token trees, delimited by `( )`, `[ ]` or `{ }`<Cite id="rustref-procedural-macros" />.
They are the scanner's tokens of Part III, with the brackets already
matched up, and nothing more: "somewhere between tokens and the
AST", as the Little Book of Rust Macros puts it<Cite id="tlborm" />.

## Three kinds, one crate

<Figure takeaway="A proc-macro crate is compiled first, then run by the compiler while it expands your crate." caption="Building a crate that uses #[derive(Describe)]. The macro crate is a separate crate, compiled for the machine doing the build, and loaded into rustc.">
  <ProcMacroPipeline />
</Figure>

There are three kinds of procedural macro<Cite id="rustref-procedural-macros" />:
**function-like** (`show!(...)`, like `macro_rules!` but written in
Rust), **derive** (`#[derive(Describe)]`, which *adds* items after a
struct or enum), and **attribute** (`#[trace]`, which *replaces* the
item it is on). All three must live in the root of a `proc-macro`
crate, and cannot be used in the crate that defines them. They run
inside the compiler, with the compiler's own access to files and
input and output, so the Reference warns that they carry the same security
concerns as build scripts<Cite id="rustref-procedural-macros" />.

<Examples of="proc-macro">

```rust
#[proc_macro]
pub fn show(input: TokenStream)
    -> TokenStream {
    for tt in input.clone() {
        eprintln!("{tt:?}");
    }
    input
}
```

```rust
#[proc_macro_derive(Describe)]
pub fn describe(input: TokenStream)
    -> TokenStream {
    let ast = parse_macro_input!(
        input as DeriveInput);
    let name = &ast.ident;
    let Data::Struct(s) = &ast.data else {
        return syn::Error::new_spanned(
            name, "Describe needs a struct")
            .to_compile_error()
            .into();
    };
    let fields: Vec<_> = match &s.fields {
        Fields::Named(f) => f.named.iter()
            .map(|f| f.ident.clone())
            .collect(),
        _ => vec![],
    };
    quote! {
        impl #name {
            pub fn describe(&self)
                -> String {
                let mut s = String::from(
                    stringify!(#name));
                #(
                    s += &format!(
                        " {}={:?}",
                        stringify!(#fields),
                        self.#fields);
                )*
                s
            }
        }
    }
    .into()
}
```

```rust
#[proc_macro_attribute]
pub fn trace(_attr: TokenStream,
             item: TokenStream)
    -> TokenStream {
    let mut f = parse_macro_input!(
        item as syn::ItemFn);
    let name = f.sig.ident.to_string();
    let first: syn::Stmt =
        syn::parse_quote! {
            println!("-> {}", #name);
        };
    f.block.stmts.insert(0, first);
    quote!(#f).into()
}
```

</Examples>

The first is `show!`, the simplest possible macro: it walks its input
(a `TokenStream` iterates as token trees), prints each, and returns the
input unchanged. The second is the derive, using two crates almost
every procedural macro uses. **`syn`** parses a token stream "into a
syntax tree of Rust source code"<Cite id="syn-readme" />:
`parse_macro_input!` turns the input into a `DeriveInput`, from which
we take the type's name and, if it is a struct with named fields, the
fields' names. **`quote`** goes the other way: `quote! { ... }` is a
quasiquote, a template of Rust code in which `#name` interpolates a
value and `#( ... )*` repeats, "similar to `macro_rules!`"<Cite id="quote-readme" />.
The third is an attribute macro that parses a whole function, inserts a
`println!` as its first statement, and hands the function back.

With `#[derive(Describe)]` on `struct Point { x: f64, y: f64 }` and
`#[trace]` on an `area` function, the program printed
`Point x=1.5 y=-2.0`, then `-> area` and `6`.

A macro's errors appear in *someone else's* code. Two versions of the
"not a struct" case, as rustc 1.97 reported them for
`#[derive(Describe)] enum Shape` (trimmed):

```text
with panic!("Describe needs a struct"):
error: proc-macro derive panicked
3 | #[derive(Describe)]
  = help: message: Describe needs a struct
with syn::Error::new_spanned(name, ..):
error: Describe needs a struct
4 | enum Shape {
  |      ^^^^^
```

Both stop the build, but the second points at the user's own line,
because every token carries a **span**, its place in the source, and
`new_spanned` attaches the error to the span of the name.

Python's `dataclass` decorator does a similar job by inspecting the
class while the program runs<Cite id="python-dataclasses" />. Rust's
derive does it once, during compilation, from tokens, so the generated
code is type-checked like hand-written code and costs nothing at run
time; the price is a separate crate, and a slower build.

<Callout kind="definition">
A **procedural macro** is a Rust function, in a crate with
`proc-macro = true`, that the compiler runs during expansion: it takes
a `TokenStream` (and, for an attribute macro, a second one for the
attribute's arguments) and returns a `TokenStream` that replaces the
call or item, or, for a derive, is added after
it<Cite id="rustref-procedural-macros" /><Cite id="klabnik2026" />.
</Callout>

## What you learned

- A **procedural macro** is a Rust function in a `proc-macro` crate,
  run by the compiler: function-like, derive or attribute.
- It reads and writes a **token stream**: identifiers, punctuation,
  literals and bracketed groups, with no further structure.
- **`syn`** parses tokens into a syntax tree, **`quote!`** writes
  tokens from a template, and spanned errors point at the user's code.
