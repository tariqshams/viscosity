## Running it

*Fuzzing the Rust engine* built up to `scripts/fuzz.mjs`, a
generator that writes a valid program from a seed. Here is a run I did
for this chapter, on the current engine (release build, rustc 1.97,
node 22, on a shared cloud VM; wrapped):

```
$ node scripts/fuzz.mjs --count 300 --seed 5
  250/300 programs, 0 failing
  300/300 programs, 0 failing
fuzz: seed 5, 300 programs (138
  transformed, 178 may go out of bounds,
  11 with an early error), 0 failing,
  4.6 s
```

"Transformed" means the engine rewrote at least one collection, so the
compiled program really differs from the original; programs that "may
go out of bounds" are checked only with `--bounds check`, since
`--bounds assume` trusts a program not to.

Every program meets three **oracles**. **Behaviour**: the original and
the compiled program run in a fresh `vm` context of node (a separate set
of globals, so one program cannot disturb the next)<Cite id="node-vm" />,
and must print the same lines and throw the same error. **Parity**: the
TypeScript and Rust engines must give the same compiled code, explain
text and code frames, byte for byte (*TypeScript vs Rust: differential
tests*). **Early errors**: both must reject the programs that were
given one. The TypeScript engine runs inside the script; the Rust one is
reached through its CLI, one `viscosity build a.js b.js ... -o dir/`
per batch of 250 programs, so a process start is paid per batch, not
per program.

Each program's seed depends only on the campaign seed and its number,
which is why `--seed 5 --only 3` can rebuild program 3 alone. Here is
the mixing function from `fuzz.mjs` (rewrapped); the program it prints
for `(5, 3)` is the seed that `--seed 5 --only 3 --print` reports in
the program's first line:

`crates/cli/tests/fuzz.rs` runs 200 programs with seed 1 on every
`cargo test`; my run of it printed `fuzz: seed 1, 200 programs (85

## A failure to shrink

Today the fuzzer finds nothing, so to watch it fail I went back in
time: I put `fuzz.mjs` as it was at commit `c68daec` next to the
TypeScript engine from just before the commit that fixed the five bugs
(`10b4a63^`), and ran `--no-rust --count 300 --seed 5 --max-fail 5`. It
stopped after five failures (trimmed and wrapped):

FAIL program 31 ...: ts-crash

FAIL program 90 ...: behaviour-check,
  behaviour-assume
fuzz: seed 5, 91 programs (34

  5 failing, 2.0 s (TS only)

Program 90 had 20 lines, and somewhere in them was the lost store from

twenty; with `--reduce`, the fuzzer finds them itself.

## Delete, ask, keep or undo

<Analogy title="a string of fairy lights">
One dead bulb has put out a whole string of fairy lights. Rather than
test the fifty bulbs one at a time, you swap in good bulbs for half of
them: if the string lights up, the fault was in that half. Halve again,
and in a handful of tries you hold the bad bulb.
<span slot="breaks">A string of lights has one bad bulb; a program can
need two lines at once (a push and the store it spoils), which is why
the reducer does not stop at halves but keeps trying smaller and
smaller chunks.</span>
</Analogy>

<Analogy title="leaving ingredients out of a recipe">
A cake keeps upsetting your stomach, so you bake it again with half the
ingredients left out, and then with the other half, until you know which
one is to blame.
<span slot="breaks">Leave out the flour and you no longer have a cake at
all, so "it did not upset me" tells you nothing; a program with half its
lines deleted is often not a program either, which is why the reducer
throws away any try that does not parse.</span>
</Analogy>

The reducer is **line-based delta debugging**. It starts with chunks
of half the lines and tries deleting each chunk in turn; it keeps a
deletion if the program still fails in the same way, and otherwise puts
the lines back and moves on by one chunk. When a whole pass changes
nothing, it halves the chunk, down to single lines. Step through it on
an eight-line program whose failure needs lines 2 and 5:

<ReduceSteps client:visible />

"Fails in the same way" is a function inside `reduce` (trimmed):

```js
const stillFails = (lines) => {
  const code = lines.join('\n') + '\n';
  if (!prog.early && !parses(code))
    return false;
  // ... compile it, and run it ...
  return failuresOf(p, rust)
    .some((x) => x.kind === kind);
};
```

It joins the remaining lines back into a program; a try that acorn
cannot parse counts as "passes" (unless the program was *meant* to
contain an early error), which is the missing-flour rule; and the try
is a failure only if one of its failures has the same **kind** as the
original, such as `behaviour-check` or `ts-crash`. Each call costs a
compile and two runs, which is why big chunks come first.

<Callout kind="definition">
**Delta debugging** shrinks a failing input by deleting parts of it
while a test still reports the failure. The result is **1-minimal**
when deleting any single remaining part makes the failure go away.
`fuzz.mjs --reduce` deletes chunks of lines, halving the chunk size to
1, and counts a try as failing only if it parses and shows the **same
kind** of failure.
</Callout>

<Formal title="1-minimal">

```text
fails(P) ∧ ∀ l ∈ P : ¬ fails(P ∖ {l})
```

<span slot="read">The reduced program P still fails, and for every line
l in P, the program with l removed (P minus l) does not fail. It says
nothing about removing two lines at once, or about whether some other,
smaller program would fail too.</span>
</Formal>

## Same kind, not same meaning

The reducer keeps the *kind* of failure, not what the program meant,
and the two can drift apart. Here are three of the five, as the reducer
left them (wrapped; the first is shortened, since the last chapter showed
it whole):

<Examples of="fuzzing">

```js
function local1(m) { const ls = [];
  /* 64 pushes, a loop over b */
  ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
  t += ls[1].a; return t; }
console.log(local1(0), local1(1));
```

```js
let cells = [];
for (let i = 0; i < 64; i++)
  cells.push({ a: Math.sin(i) });
for (let i = 0; i < 5; i++)
  cells.push({ a: cells[i % cells.length]
    .a * cells[i % cells.length].a });
```

```js
const cells = [];
for (let i = 0; i < 70; i++)
  cells.push({ b: (i * 37) % 11 });
for (let i = 0; i < cells.length; i++) {
  const p = cells[(k++, i)]; s0 += p.b; }
```

</Examples>

The first is program 90, the lost store, intact; the reducer only
removed lines that had nothing to do with it. The second is program 31:
a push whose new record reads two other elements, and the old engine
crashed on it with `internal error: overlapping rewrites at 741-801`,
because it rewrote the whole object literal as one piece while also
rewriting the reads inside it. The third is program 12, and it is a
trap. Its `let k` and `s0` declarations were deleted, so the *original*
now throws `ReferenceError: k is not defined`. The compiled program
still differed, though: the old emitter copied the index `(k++, i)`
without its brackets and wrote `const p = k++, i;`, which is a
`SyntaxError` (`Missing initializer in const declaration`). A
ReferenceError against a SyntaxError is still a `behaviour-check`
failure, so the reduction was accepted. The bug survived the
shrinking; the program around it stopped making sense. Read a reduced
program before you trust it.

## What the five were

The engine's README lists them as bugs 11 to 15, each now with a
program of its own in the test corpus:

```
bug                     found as
rhs ran after the check behaviour
store into old column   behaviour
rewrite in push/array   ts-crash
rewrite in an index     ts-crash
(k++, 7) as an index    behaviour
```

All five were in both engines, because the port mirrors the reference
line for line, so the parity oracle, which compares the engines with
each other, was blind to every one of them; the behaviour oracle and
the TypeScript crash found them. After the fixes, the README records a
further 42,000 programs (seeds 5 to 7 and 101 to 103, with the
generator extended to the constructs that found the bugs) that found
nothing.

## Did coverage plateau?

When this chapter was first written, I measured the line coverage of
the TypeScript engine (core and frontend-js, without its two unused
parsers) at commit `c68daec`, with c8 10.1.3 and node's built-in
coverage:

<Figure caption="Lines of the engine run, out of 2,614. The fuzzer ran fewer lines than the hand-written programs, and ten times as many fuzz programs ran three more." takeaway="Line coverage flattened out early; the bugs were in combinations.">
  <CoverageBars />
</Figure>

The fuzzer covered *fewer* lines than the hand-written programs, yet
found what they missed, and ten times the programs added three lines.
Each of the five bugs needed a combination: a write whose right-hand
side pushes, an access inside a push. Line coverage says a line ran,
not what it ran with; that is one reason AFL counts edges and hit
counts, and a generator like this one finds new combinations only when
someone teaches it new constructs, as happened after the first finds.

## What you learned

- `fuzz.mjs` checks every program against three **oracles**:
  behaviour, parity and early errors.
- **Delta debugging** deletes chunks while the failure stays, halving
  the chunk to 1, which leaves a **1-minimal** program.
- The reducer keeps the failure's **kind**, not the program's meaning,
  so read the result before you trust it.
- Bugs that live in both engines are invisible to **parity**.
- **Line coverage** flattened out while the bugs hid in
  **combinations** of features.
