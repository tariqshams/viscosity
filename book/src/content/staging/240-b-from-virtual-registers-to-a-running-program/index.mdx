## As many registers as we like, until now

The last chapter's selector wrote `sumsq` with four virtual registers
and `fib` with seven, and a long program could use thousands; the
chip has 32 integer registers, several of them spoken for (`zero`,
`ra`, `sp` and the argument registers). Three stages remain: decide
where each virtual register lives, build each function's frame, and
turn the text into something that runs.

## Stages 4 and 5: intervals and linear scan

We use the allocator from chapter 234, **linear scan**, because it is
short and needs only each value's **live interval**: the first and
last line of the function that mention it. One subtlety comes from
loops: a value used inside a loop is needed on every trip, so its
interval is stretched to cover the whole loop, from the loop's label
to the jump back (a cruder picture than chapter 232's liveness, but a
safe one). Then the intervals are walked in order of their start,
each takes a free register, and when none is free, the one that ends
last is **spilled** to a stack slot.

<Analogy title="a small desk and a filing cabinet">
You can only keep a few folders open on your desk; the rest go in the
cabinet behind you. When a new folder arrives and the desk is full,
the sensible one to file away is the folder you will not need again
for the longest time, and fetching it back costs a trip.
<span slot="breaks">A person can look ahead and guess; linear scan
knows each value's whole interval in advance, because the program is
already written, and a value it files away is fetched back before
every single use, not once.</span>
</Analogy>

<ScanSteps client:visible />

Our allocator only hands out `s1` to `s11`, the callee-saved
registers (chapter 228). That is a deliberate simplification: values
in them survive every call without any extra code around the call, so
`fib(n - 1) + fib(n - 2)` keeps the first result safe while the second
call runs. The price is paid once per function instead, in the
prologue. A spilled value is loaded into `t0` or `t1` just before each
use and stored from `t2` just after each definition; those three
scratch registers are never handed out, so they are always free.

## Stage 6: the frame

Each function now knows which `s` registers it uses, how many spill
slots it needs, and whether it makes any calls. The psABI says that
`s0` to `s11` are preserved across calls<Cite id="riscv-psabi" />, so a
function that uses `s1` must save its caller's value first and put it
back at the end; a function that calls another overwrites `ra`, so it
must save that too; and the stack pointer must be "aligned to a
128-bit boundary upon procedure entry"<Cite id="riscv-psabi" />, 16
bytes, so the frame is rounded up to a multiple of 16. Here is the
frame of `main`, which calls two functions and keeps two values:

`j .Lsumsq_ret` that the selector wrote for `return s;`.

## Stage 7: running it

The output is ordinary RISC-V assembly, so we can run it two ways.
The first is a simulator: a program that executes machine
instructions one at a time, keeping the registers and memory in
ordinary variables, exactly as the hardware would. Ours is about
eighty lines and handles only the fifteen instructions our compiler
emits, with 64-bit registers held as JavaScript BigInts so that
overflow wraps as it does on RV64<Cite id="riscv-isa-unpriv" />;
`call print` is caught and printed instead of jumping anywhere.

<Analogy title="a flight simulator">
A pilot can practise on a machine that behaves like the aircraft:
the same controls, the same instruments, the same responses, with no
aircraft anywhere.
<span slot="breaks">A flight simulator approximates the physics; an
instruction-set simulator computes exactly the same results as the
chip, bit for bit, but (like ours) usually ignores timing, so it says
nothing about how fast the code would run.</span>
</Analogy>

<Callout kind="definition">
An **instruction-set simulator** is a program that runs machine code
for one processor by imitating it in software: it keeps the
registers, the program counter and memory in variables, and repeats
fetch, decode and execute one instruction at a time. It lets you run
and test code for a chip you do not have, and see its state after
every step.
</Callout>

The second way is the real toolchain. LLVM's assembler accepts our
output as it stands:

```text
$ llvm-mc -triple=riscv64 -mattr=+m \
    -filetype=obj sumsq.s -o sumsq.o
$ llvm-objdump -d -r sumsq.o
0000000000000000 <sumsq>:
 0: 13 01 01 fe  addi sp, sp, -0x20
 4: 23 3c 91 00  sd   s1, 0x18(sp)
 ...
20: 63 da 99 00  bge  s3, s1, 0x34
24: 33 8a 39 03  mul  s4, s3, s3
 ...
0000000000000050 <main>:
 ...
68: 97 00 00 00  auipc ra, 0x0
    R_RISCV_CALL_PLT  sumsq
6c: e7 80 00 00  jalr ra
```

Each instruction is four bytes, little-endian. The loop's `bge` was
resolved by the assembler (`63 da 99 00` already holds the distance to
`0x34`), but the two `call`s became `auipc` and `jalr` with an
`R_RISCV_CALL_PLT` relocation, a hole for the linker (chapter 238) to
fill with the distance to `sumsq` and to `print`<Cite id="riscv-psabi-relocations" />.
(Assembling the same file with `clang --target=riscv64 -c` leaves
even the local branches as relocations, `R_RISCV_BRANCH` and
`R_RISCV_JAL`, because with linker relaxation on, the linker may
later shrink code and move them<Cite id="riscv-psabi-relocations" />;
with `-mno-relax` it gives the same bytes as `llvm-mc`.)

The first is the smallest program the simulator can run: it starts at
`main`, puts 6 in `a0`, prints it, and `ret` jumps to the return
address it was started with, which ends the run. The second is the
check every allocator needs: squeeze it down to two registers and the
code gets slower (the listing in the stepper above), but must print
exactly the same. The third is the whole compiler, all seven stages
and the simulator, about five hundred short lines; it prints `sumsq`'s final
assembly and then runs a program with `sumsq` and `fib`. Change `REGS`
to `['s1']` and watch the spills pile up while the output stays put.

## How far from a real compiler?

Here is clang's `-O2` output for the same loop written in C (with one
LLVM option, `-replexitval=never`, that stops the middle end replacing
the whole loop with a formula, which the next chapter shows):

```text
sumsq:
  blez a0, .LBB0_4
  li   a2, 0
  li   a1, 0
.LBB0_2:
  mul  a3, a2, a2
  addi a2, a2, 1
  add  a1, a3, a1
  bne  a0, a2, .LBB0_2
  mv   a0, a1
  ret
.LBB0_4:
  li   a1, 0
  mv   a0, a1
  ret
```

Its loop is four instructions to our five, and it has no frame at all:
a function that makes no calls can keep everything in the
caller-saved `a` and `t` registers, which cost nothing to use. It has
also turned the loop round so that the test sits at the bottom,
after checking once at the top that the loop runs at all (a change
called **loop rotation**), which saves the `j` on every trip. Our compiler does neither, and has no
scheduler and no SSA optimisations; however, every stage is there, in
the right order, and the output is correct, which is the part that
cannot be added later.

## What you learned

- **Live intervals**, stretched over loops, feed **linear scan**,
  which gives each value a register or **spills** it to a stack slot,
  with scratch registers for the loads and stores.
- The **frame** saves exactly the callee-saved registers a function
  uses, and `ra` if it calls, rounded up to 16 bytes as the psABI
  requires; a two-rule **peephole** tidies the result.
- An **instruction-set simulator** runs the output in software;
  `llvm-mc` turns the same text into real object code, with
  relocations left for the linker.
- Compared with clang, the missing pieces are optimisations
  (caller-saved registers for leaf functions, loop rotation,
  scheduling), not stages.
