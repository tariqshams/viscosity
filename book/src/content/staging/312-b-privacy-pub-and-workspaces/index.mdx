## A table that guards itself

Here is drip-rs's hash table (`table.rs`, trimmed), the one from
*Finding things fast: hash tables*:

```rust
pub struct Table {
    count: usize,
    keys: Vec<Option<StrRef>>,
    values: Vec<Value>,
}
impl Table {
    pub fn new() -> Self { ... }
    fn grow(&mut self, cap: usize) { ... }
}
```

The struct is `pub`, and so is `new` (and `get`, `set` and the rest of
the API), but its three fields and `grow` have no `pub`, so they are
**private**: other modules can name `Table` and use its API, and that is
all. Try the rest
from outside `table`, and rustc 1.97 refuses each with its own code (a
private free function gives a third, E0603):

```text
error[E0624]: method `grow` is private
13 |     t.grow(16);
   |       ^^^^ private method
error[E0616]: field `count` of struct
  `Table` is private
14 | println!("{}", t.count);
   |                  ^^^^^ private field
```

Why bother? `count` must count live entries *and* tombstones, and the
two columns must stay the same length. If any module could write `t.count = 0`, or push onto
`keys` alone, the table could be broken from anywhere in the VM. With
private fields only `table.rs` can break it, so `table.rs` is all you
need to read to trust it. Outsiders cannot even build one with a struct
literal: `table::Table { count: 1, ... }` is E0451, "field `count` of
struct `Table` is private", so they must go through `new`.

<Analogy title="a shop counter and the stock room">
A shop sells through its counter: anyone can walk up and ask for what
is on the menu. The stock room behind it is private; staff go in and
out freely, but a customer who walks round the counter is stopped. The
counter is the `pub` API, the stock room is the private fields and
helpers, and the staff are the module itself and the modules inside it.
<span slot="breaks">A determined customer can still sneak into a stock
room; a Rust program that names a private item simply does not
compile, so there is no way round the counter at all (short of changing
the shop's own code).</span>
</Analogy>

## Private means "this module and below"

The exact rule, from the Rust Reference: a **private** item may be used
by the module it is in *and that module's descendants*; a **public**
item may be used from anywhere that can reach all of its ancestor
modules<Cite id="rustref-visibility" />.

<Figure takeaway="A private item is visible in its own module and every module inside it." caption="table's private method grow can be called in table and in table's child tests, and nowhere else. A pub method such as new can be called from all of them.">
  <PrivacyMap />
</Figure>

The first half is why a `tests` module inside `table.rs` can test
`grow`, which nothing else may call. The second half is why `pub` on
an item inside a *private* module does not make it reachable from
outside: if `mod gc` in `vm` is private, then `vm::gc::collect()` from
the root is E0603, "module `gc` is private", however `pub` `collect`
is. Two shortcuts round out the rules: every variant of a `pub enum` is
public, and so is every item of a `pub trait`<Cite id="rustref-visibility" />.
For the cases in between there is **`pub(crate)`**, visible anywhere in
this crate but not to other crates (neither drip-rs nor engine/rust
needs it).

<Callout kind="definition">
**Visibility** says where a name may be used. Items, struct fields and
methods are **private** by default: usable only in their own module and
its descendants. **`pub`** makes them usable wherever their parent
modules can be reached; **`pub(crate)`** limits that to the current
crate. **`pub use path;`** re-exports an item, giving it a second,
public path.
</Callout>

<Formal title="The privacy rule">

```text
private item i, defined in module m:
  usable in n  ⟺  n = m  or  n is inside m
pub item i, path m₁::m₂::…::i:
  usable in n  ⟺  every mₖ is usable in n
```

<span slot="read">A private item i defined in module m can be used in
module n exactly when n is m itself or a module somewhere inside m. A
public item can be used in n exactly when every module on the way to it
(m one, m two, and so on) can be used in n.</span>
</Formal>

<Examples of="visibility">

```rust
mod table {
    pub fn new_table() {}
    fn helper() {} // private
}
table::new_table(); // fine
table::helper();    // E0603
```

```rust
pub struct Particles {
    xs: Vec<f64>,  // private
    vxs: Vec<f64>, // private
}
```

```rust
// drip-rs's src/lib.rs
pub mod vm;
pub use vm::{Options, Outcome, Vm};
```

</Examples>

The first is visibility at its plainest. The second is this chapter's
exercise: the type is public but its two columns are not, so nobody
outside can push to one column and forget the other. The
third is a **re-export**: the VM really lives at `drip::vm::Vm`, and
`pub use` gives it a second, shorter public path, `drip::Vm`, which is
what drip-rs's `main.rs` (a separate binary crate in the same package)
and its tests use. Like a package's exports on npm, a crate's set of
`pub` paths is its public API, and changing it is what breaks other
people's code.

<OtherLanguages title="A counter nobody else can change">

```rust
mod tally {
    pub struct Tally { n: u32 }
    impl Tally {
        pub fn new() -> Tally {
            Tally { n: 0 }
        }
        pub fn add(&mut self) {
            self.n += 1;
        }
    }
}
```

```ts
export class Tally {
  #n = 0;   // private field
  add() { this.#n += 1; }
}
// not exported: private to this file
function helper() {}
```

</OtherLanguages>

TypeScript has two privacy tools, a module's `export` list and `#` on
class members (only the class's own methods may touch them). Rust has
one rule, about *modules*, not types: any code in `tally` may read `n`,
even outside `Tally`'s `impl`, while a sibling module may not, even in
the same file.

## Workspaces: several crates, one build

drip-rs is one package holding two crates, the `drip` library and the
`drip-rs` binary (from *Cargo, crates and packages*). The Rust
Viscosity is bigger: six packages, each with its own `Cargo.toml`,
built together as one **workspace**. Its root `Cargo.toml` holds no
code, only this (trimmed, and wrapped to fit):

```toml
[workspace]
members = ["crates/vir", "crates/core",
  "crates/frontend-js",
  "crates/frontend-python",
  "crates/cli", "crates/wasm"]

[workspace.dependencies]
viscosity-vir = { path = "crates/vir",
  version = "0.0.1" }
oxc_parser = "0.156"
```

A member then writes `viscosity-vir.workspace = true` under
`[dependencies]` instead of repeating the path or version, so every
crate agrees on one version of oxc. (A package called `viscosity-core`
is `viscosity_core` in Rust code, since `-` cannot appear in a path.)
Step through what depends on what:

<CrateSteps client:visible />

<Analogy title="a block of flats">
A block of flats has many front doors but one boiler, one bin store and
one post room. Each flat (crate) is its own home with its own key, yet
they share the services, so everyone gets the same hot water. A
workspace's crates share one `Cargo.lock` (the same version of every
dependency) and one `target/` folder (each dependency built once).
<span slot="breaks">Neighbours can walk into the shared post room; a
crate can only use another crate it lists as a dependency, and then
only that crate's `pub` items.</span>
</Analogy>

<Callout kind="definition">
A **workspace** is a set of packages built together from one root
`Cargo.toml` with a `[workspace]` table. Its members share one
`Cargo.lock` and one output folder, `target/`<Cite id="rust-book-workspaces" />,
and depend on each other with path dependencies. `cargo test
--workspace` tests every member; `cargo build -p viscosity-cli` builds
one.
</Callout>

<Examples of="workspace">

```toml
# Cargo.toml at the root
[workspace]
members = ["crates/core", "crates/fe"]
```

```toml
# crates/core/Cargo.toml
[dependencies]
viscosity-vir.workspace = true
```

```text
$ cargo test --workspace
$ cargo run -p viscosity-cli -- build x.js
```

</Examples>

The first is the smallest workspace: a root that lists two member
folders, each with its own `Cargo.toml`. The second is how engine/rust's
`core` asks for the IR crate, taking the path and version from the
root's `[workspace.dependencies]`. The third is the daily routine: test
every crate at once, or build and run just one, with `-p` naming the
package (everything after `--` goes to the program).

Crates may not depend on each other in a circle. In a scratch workspace
where `demo-core` and `demo-fe` each list the other, cargo 1.97 refuses
before compiling anything:

```text
error: cyclic package dependency: package
  `demo-core v0.1.0 (...)` depends on
  itself. Cycle: ...
```

<Callout kind="engine" label="Under the hood">
engine/rust's crate split turns *The plugin API*'s design into
something the compiler checks. `viscosity-core` does not depend on
`viscosity-frontend-js`, so its library code *cannot* mention oxc or
JavaScript syntax, only VIR and its own `LanguagePlugin` trait; the
README's claim that the analyses hold no JavaScript-specific code is
kept true by the dependency graph. Core's tests do need a real plugin,
so `frontend-js` is listed under `[dev-dependencies]`, which are built
only for tests; that breaks the cycle (moving the same line to
`[dependencies]` in the scratch workspace above gives the error shown).
The command-line tool and the WebAssembly build are each a thin crate
over the same core.
</Callout>

## What you learned

- Everything is **private** by default, fields and methods included.
  Private means "this module and its descendants"; `pub` opens an item
  to anyone who can reach its parents; `pub use` re-exports.
- Private fields let a type guard its invariants, like drip-rs's
  `Table`, because only its own module can break them.
- A **workspace** builds several crates together, with one
  `Cargo.lock` and one `target/`. engine/rust's split makes the plugin
  boundary a compile-time fact, and cargo refuses dependency cycles.
