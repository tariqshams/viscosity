## Two names, one string?

*References: two names, one object* began with a puzzle about two names
for one object. Here is the Rust version:

```rust
let a = String::from("fib");
let b = a;
println!("{a}");
```

In TypeScript, `const b = a` makes two arrows to one object, and the
garbage collector later works out when no arrows are left. Rust has no
collector, and the last chapter's rule says the text has exactly one
owner; so which of `a` and `b` would free it? rustc answers by rejecting
the program (its real output, trimmed to fit):

```text
error[E0382]: borrow of moved value: `a`
2 | let a = String::from("fib");
  |     - move occurs because `a` has
  |       type `String`, which does not
  |       implement the `Copy` trait
3 | let b = a;
  |         - value moved here
4 | println!("{a}");
  |            ^ value borrowed here
  |              after move
help: consider cloning the value if
the performance cost is acceptable
```

Read it from the top: `a` was **moved** into `b`, so `a` cannot be used
any more. ("Borrowed" is the subject of the next chapter; printing a
value borrows it.)

<Analogy title="handing over the car keys">
When you sell your car you hand the buyer the keys, and from then on
they drive it and you do not; the car itself stays exactly where it is
parked. A move is that hand-over: the small thing (the pointer, length
and capacity, like the keys) changes hands, and the big thing on the
heap does not move an inch.
<span slot="breaks">You could cut a spare key and drive off anyway;
Rust leaves no spare, and the compiler rejects any later use of the old
name.</span>
</Analogy>

## Watching a move

Step through it. On the left is `main`'s stack frame; on the right, the
heap. An arrow is drawn only from a value's one owner:

<OwnerSteps client:visible />

A move copies only the small part on the stack, 24 bytes for a `String`;
the heap text stays put, and nothing deep is ever copied unless you ask.
The old variable is then marked as moved, and since a moved-from
variable owns nothing, it is not dropped either, so the text is freed
exactly once<Cite id="rust-book-ownership" />.

<Callout kind="definition">
A **move** transfers ownership from one place to another: `let b = a;`,
passing `a` to a function, or returning a value from one. The bytes on
the stack are copied, the heap data is not, and the old place may not be
used again until it is given a new value. The compiler checks this, and
a use after a move is error E0382<Cite id="rust-error-codes" />.
</Callout>

## Copy and clone

The scalars from *Numbers, characters and booleans* behave differently.
`let m = n;` with an `i32` leaves both usable, because `i32` is a
**Copy** type: copying four bytes is cheap, and nothing on the heap needs
a single owner. All the integers, the floats, `bool` and `char` are
Copy<Cite id="rust-book-ownership" />. When you do want a second,
independent `String`, you ask for one with `clone`:

  <MoveCopyClone />
</Figure>

<Analogy title="a photocopier">
`clone` is a photocopier: you get a second, separate sheet, and writing
on one leaves the other alone. Copying costs paper and time in
proportion to the size of the document, which is why Rust makes you
press the button yourself rather than copying behind your back.
<span slot="breaks">A photocopy can be fainter than the original; a
clone is exactly equal to it, and for Copy types Rust presses the
button for you, because the "document" is a few bytes.</span>
</Analogy>

Compare `{ ...obj }` from *Copies: an object of your own*, which copied
only the top layer: a `String`'s `clone` copies the text too, and a
`Vec<String>`'s `clone` copies every string in it.

## Moving into and out of functions

Passing a value to a function moves it, exactly like `let`, and
returning a value moves it out to the caller:

<Examples of="move">

```rust
let a = String::from("fib");
let b = a;        // a moves into b
println!("{b}");  // fine: b owns it
```

```rust
fn eat(s: String) {
    println!("ate {s}");
} // s is dropped here

let name = String::from("drip");
eat(name);        // name moves into eat
```

```rust
fn make() -> String {
    String::from("vm")
}
let g = make();   // moved out to g
```

<Run id="moves" />

</Examples>

In the first, `b` becomes the owner and is used, which is fine; it is
only `a` that is finished. In the second, `eat` takes a `String`
parameter, so the call moves `name` into `s`, `eat` prints it and drops
it at its closing brace, and `name` is unusable afterwards. In the third
the string is built inside `make`, but returning it moves ownership out,
so it outlives the call and `g` owns it (the body is a tail expression,
from *Blocks, if and the tail expression*). The runnable one does all of
these and more; uncomment the last line to see E0382 for yourself.

Here is the classic mistake, calling the same function twice:

```rust
eat(name);
eat(name);        // broken
eat(name.clone());
eat(name);        // fixed: clone first
```

```text
error[E0382]: use of moved value: `name`
4 |     eat(name);
  |         ---- value moved here
5 |     eat(name);
  |         ^^^^ value used here after move
note: consider changing this parameter
type in function `eat` to borrow
instead if owning the value isn't
necessary
```

The note is the real fix: a function that only wants to *look* at a
string should borrow it, not own it, and the next chapter shows how.
The same error appears inside a loop, as "value moved here, in previous
iteration of loop", because the first time round moves the value and
the second time there is nothing left.

<OtherLanguages title="Give a value a second name">

```rust
let a = String::from("fib");
let b = a;  // a is now unusable
```

```ts
const a = ['f', 'i', 'b'];
const b = a; // two names, one array
```

```c
char *a = strdup("fib");
char *b = a; /* two pointers; free one
                and the other dangles */
```

```python
a = ["f", "i", "b"]
b = a  # two names, one list
```

</OtherLanguages>

TypeScript and Python both give one object two names and let the
collector or the counts sort it out later. C copies the pointer and
trusts you: free through one name and the other points at freed memory.
Rust copies the same bytes C does, but forbids the old name, so there is
never a second path to the text.

<Formal title="A move takes a name out of scope">

```text
Γ, a : String  ⊢  let b = a;
               ⊣  Γ, b : String
Γ, n : i32     ⊢  let m = n;
               ⊣  Γ, n : i32, m : i32
```

<span slot="read">Read ⊢ … ⊣ as "with these names available before the
statement, these are available after it". Moving a String takes a out of
the list and puts b in; copying an i32 leaves n in the list and adds m.
A later use of a finds a missing from the list, and that is E0382.</span>
</Formal>

This is the ledger of moves you kept in *A borrow checker in miniature*:
each move crossed a name off, and any later read of a crossed-off name
was an error. It is also the affine discipline from *Linear types and
effect systems*: a non-Copy value may be used *at most* once, then it is
gone (at most, not exactly, because a value that is never moved is
dropped in the usual way).

## What you learned

- `let b = a;`, passing `a` to a function and returning a value all
  **move** ownership. Only the stack part is copied; the heap data has
  one owner still.
- A moved-from variable is unusable (E0382), and it is not dropped, so
  nothing is ever freed twice.
- **Copy** types (integers, floats, `bool`, `char`) are copied instead.
  `clone()` makes an explicit deep copy with its own owner.
- Moves are the ledger of the borrow checker in miniature, and the
  "at most once" rule of affine types.
