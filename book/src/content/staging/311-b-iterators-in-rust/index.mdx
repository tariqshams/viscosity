## The same chain, a different machine

With the array methods of *Other ways to loop: map, filter, reduce and
while*, summing the positions of the live particles looks like this:

```js
const total = ps
  .filter((p) => p.alive)
  .map((p) => p.x)
  .reduce((a, b) => a + b, 0);
```

`filter` builds a whole new array, `map` builds another, and `reduce`
walks the second one. Here is the same thing in Rust, with the closures
of the last chapter:

```rust
let total: f64 = ps
    .iter()
    .filter(|p| p.alive)
    .map(|p| p.x)
    .sum();
```

It reads almost the same, but it builds no arrays at all. That is the
work of **iterators**, and this chapter is about how they do it.

<Analogy title="a ticket dispenser">
At a deli counter you pull a numbered ticket from a dispenser: one per
pull, in order, until the roll runs out. Nobody prints the whole roll
in advance and hands it to you; each pull produces one ticket. An
iterator is the dispenser, `next` is the pull, and an empty roll is
`None`.
<span slot="breaks">A dispenser's roll exists before anyone pulls; an
iterator over `0..1_000_000` makes each number only when asked, and an
adapter like `map` does not even look at the roll until someone pulls
from it.</span>
</Analogy>

## One method: next

An iterator is any value with a `next` method that hands out items one
at a time until it runs out. Its trait is tiny (trimmed from the
standard library):

```rust
trait Iterator {
    type Item;
    fn next(&mut self)
        -> Option<Self::Item>;
}
```

`Item` is the type it yields (an *associated type*: each iterator
picks it, as you will see in more depth later), and `next` returns
`Some(item)` or, at the end, `None`. It takes `&mut self` because
handing out an item moves the iterator on. Every other iterator method,
dozens of them, is built on `next`<Cite id="rust-std-iter" />. This is
the iterator protocol of *Iterators and generators*, with `Option`
standing in for `{ value, done }`.

```rust
let v = vec![10, 20, 30];
let mut it = v.iter();
it.next(); // Some(&10)
it.next(); // Some(&20)
it.next(); // Some(&30)
it.next(); // None
```

`v.iter()` makes an iterator that *borrows* `v` and hands out
references, `&10` and so on; it must be `let mut it`, because each
`next` changes where it is. Run it and the four lines print exactly as
the comments say (`Some(10)` shows without the `&`, since printing a
reference prints what it points at).

## What for really does

*Option and Result* promised to explain `for`. It is a shorthand for
this trait, and the Rust Reference spells out the expansion<Cite id="rustref-loop-expr" />:

<Formal title="A for loop, unfolded">

```text
for p in e { body }
  ≡
let mut it = IntoIterator::into_iter(e);
loop {
    match it.next() {
        Some(p) => { body }
        None => break,
    }
}
```

<span slot="read">A for loop over e is the same as: turn e into an
iterator with into_iter, then loop forever asking it for the next item;
if there is one, bind it to the pattern p and run the body; if there is
none, stop. (The symbol ≡ reads "means exactly the same as".)</span>
</Formal>

`into_iter` is where the three forms of `for` differ, because each
type decides what it hands out:

```rust
for x in &v { }     // x: &T, like v.iter()
for x in &mut v { } // x: &mut T
for x in v { }      // x: T, and v is gone
```

The last one *consumes* `v`: its `into_iter` takes `v` by value, which
is *Ownership*'s move, applied to a loop. Use `v` afterwards and rustc
1.97 says so, and suggests the fix:

```text
error[E0382]: borrow of moved value: `v`
3 | for x in v {
  |          - `v` moved due to this
  |            implicit call to
  |            `.into_iter()`
help: consider iterating over a slice
  of the `Vec<i32>`'s content to avoid
  moving into the `for` loop: &v
```

## Adapters, and laziness

Methods that take an iterator and return a new one are **adapters**.
Most of JavaScript's array methods have one, called on `xs.iter()`:

```text
JavaScript          Rust, on xs.iter()
xs.map(f)           .map(f)
xs.filter(f)        .filter(f)
xs.reduce(f, a)     .fold(a, f)
xs.find(f)          .find(f)
xs.some(f)          .any(f)
xs.every(f)         .all(f)
xs.entries()        .enumerate()
```

Rust adds some that JavaScript lacks, such as `.zip(ys)`, which walks
two sequences side by side, and `.take(n)`. Methods that pull items
until the end are **consumers**: `sum`, `count`, `fold`, `for_each`,
and `collect`, which builds a `Vec` (or a `HashMap`) from whatever comes
out, with the type written on the `let`.

The big difference is **laziness**. An adapter does nothing when you
call it; it only wraps the iterator in a new struct (a `Filter`, a
`Map`). Work starts when a consumer at the end calls `next`, and then
each item travels the whole chain before the next one
starts<Cite id="rust-book-iterators" />:

<Analogy title="an assembly line versus batch cooking">
Batch cooking is JavaScript's chain: chop *all* the onions into one
bowl, then fry the whole bowl, then plate everything. An assembly line
is Rust's: one item goes from station to station to the end before the
next one enters, so no bowl of half-done items ever exists.
<span slot="breaks">A real line keeps every station busy at once; an
iterator chain runs on one thread, one station at a time, and the
"line" only moves when the last station asks.</span>
</Analogy>

Forget the consumer and nothing happens at all. rustc warns
`unused Map that must be used`, with the note "iterators are lazy and
do nothing unless consumed"; and if you write `let ys: Vec<f64> =
xs.iter().map(...)`, the E0308 type error's help line says "consider
using `.collect()`".

<Callout kind="definition">
An **iterator** is a value whose type implements the `Iterator` trait:
an `Item` type and `fn next(&mut self) -> Option<Self::Item>`.
**Adapters** (`map`, `filter`, `zip`, `take`, ...) wrap an iterator in
another, lazily; **consumers** (`sum`, `count`, `collect`, `for`) call
`next` until `None`. Because each adapter is a small struct and its
closure is known, the chain compiles to about the same code as a
hand-written loop<Cite id="klabnik2026" />.
</Callout>

<Examples of="rust-iterator">

```rust
let n = (1..=10).filter(|x| x % 3 == 0)
    .count(); // 3: 3, 6 and 9
```

```rust
let names = ["a", "b"];
for (i, s) in names.iter().enumerate() {
    println!("{i}: {s}"); // 0: a, 1: b
}
```

```rust
// drip-rs's hash table (table.rs)
pub fn iter(&self) -> impl Iterator<
    Item = (StrRef, Value)> + '_ {
    self.keys.iter()
        .zip(&self.values)
        .filter_map(|(key, value)| {
            key.map(|k| (k, *value))
        })
}
```

</Examples>

The first counts the multiples of 3 from 1 to 10 (`1..=10` is itself
an iterator, including 10) without storing any of them. The second is
JavaScript's `entries()`: `enumerate` pairs each item with its index,
and the `for` pattern `(i, s)` unpacks the pair. The third is real. The
table of *Finding things fast: hash tables* stores its keys and values
as two columns, struct-of-arrays style; `zip` walks slot *i* of both
columns together, and `filter_map` (a filter and a map in one) skips
empty slots, whose key is `None`, while unpacking the full ones. The
`+ '_` says the returned iterator borrows the table (*Lifetime
annotations*). The collector traces a table with
`for (key, value) in self.iter()`, and `grow` re-inserts every entry
the same way.

<OtherLanguages title="Sum the doubled even numbers">

```rust
let xs = [1, 2, 3, 4];
let total: i32 = xs.iter()
    .filter(|x| *x % 2 == 0)
    .map(|x| x * 2)
    .sum(); // 12
```

```ts
const xs = [1, 2, 3, 4];
const total = xs
  .filter((x) => x % 2 === 0)
  .map((x) => x * 2)
  .reduce((a, b) => a + b, 0); // 12
```

</OtherLanguages>

Same answer, different work: TypeScript's version builds `[2, 4]` and
then `[4, 8]` before adding, while Rust's builds nothing and pulls each
number through. TypeScript does have lazy iterators (generators, from
*Iterators and generators*), but its array methods are eager; in Rust,
lazy is the default. Notice also `*x` in the filter: `iter()` hands out
`&i32`, and `filter` passes its closure a reference to *that*, a
`&&i32`; `*x` peels off one layer, and Rust's arithmetic accepts the
`&i32` that is left.

## What you learned

- An **iterator** has one required method,
  `next(&mut self) -> Option<Item>`; everything else is built on it.
- `for` calls `into_iter` and then `next` until `None`: `&v`, `&mut v`
  and `v` give `&T`, `&mut T` and `T`, and the last one moves `v`.
- **Adapters** such as `map`, `filter` and `zip` are **lazy** structs
  wrapped around each other; a **consumer** such as `sum` or `collect`
  pulls, and each item goes through every stage with no arrays in
  between.
