## Three checks

*Testing in Rust* used `assert!` and `assert_eq!` without stopping to
look at them. They are the whole vocabulary of a Rust test, and there
are only three:

- `assert!(cond)` panics if `cond` is false.
- `assert_eq!(a, b)` panics if `a != b`, and prints both.
- `assert_ne!(a, b)` panics if `a == b`, and prints both.

The `!` marks each one as a **macro** (code that writes code, as
`println!` is). drip-rs's string-interning test, from *String
interning*, uses two of them: the same text must give the same handle,
and different text a different one.

```rust
let a = heap.intern("hello");
let b = heap.intern_owned(
    String::from("hel") + "lo");
assert_eq!(a, b);
assert_ne!(a, heap.intern("world"));
```

`a` interns `"hello"` from a literal; `b` builds the same text at run
time and interns that; the `assert_eq!` checks that interning gave one
handle for both, and the `assert_ne!` that `"world"` got a different
one.

<Analogy title="a tripwire">
Each assertion is a wire stretched across the path your code takes:
"by here, this had better equal 2". Code that keeps its promises walks
over every wire without touching them; the moment something is wrong,
it trips the nearest wire, and the alarm says exactly which wire and
what was on each side of it.
<span slot="breaks">A tripwire catches only what crosses it; an
assertion checks only the one thing you wrote, so a bug that never
reaches a checked value goes unnoticed.</span>
</Analogy>

That is the whole reason to prefer `assert_eq!(a, b)` over
`assert!(a == b)`: both panic at the same time, but the plain `assert!`
can only say `assertion failed: a == b`, while `assert_eq!` shows the
two values, which is usually all you need to see the bug. Every assert
macro also takes a message after its checks, formatted like `println!`:
`assert!(n > 0, "n = {n} must be positive")` fails with
`n = 0 must be positive`<Cite id="rust-book-testing" />.

To compare, `assert_eq!` uses `==`, which needs the trait `PartialEq`;
to print, it uses `{:?}`, which needs `Debug` (both from *Traits*). Try
it on a struct with neither, and rustc 1.97 asks for both:

```text
error[E0369]: binary operation `==`
  cannot be applied to type `P`
help: consider annotating `P` with
  `#[derive(PartialEq)]`
error[E0277]: `P` doesn't implement
  `Debug`
help: consider annotating `P` with
  `#[derive(Debug)]`
```

That is why types meant for testing usually start with
`#[derive(Debug, PartialEq)]`, which writes both for you.

<Callout kind="definition">
The **assert macros** are `assert!(cond)`, `assert_eq!(left, right)`
and `assert_ne!(left, right)`. Each panics when its check fails, which
fails the test it is in (or stops the thread, in ordinary code); the
`eq` and `ne` forms print both values, which must implement `Debug`,
and compare them with `PartialEq`. An optional message, written as in
`println!`, is added to the panic<Cite id="rust-book-testing" />.
</Callout>

<Formal title="What assert_eq! means">

```text
assert_eq!(a, b, m)  ≈
  let (l, r) = (&a, &b);
  if !(*l == *r) {
      panic!(m, "left: {l:?}",
                "right: {r:?}")
  }
```

<span slot="read">assert_eq of a and b with message m works out a and b
once each, borrowing them as l and r; if l does not equal r, it panics
with the message followed by both values printed with Debug. The ≈
means "roughly": the real panic text is laid out as in the figure.</span>
</Formal>

<Examples of="assert-macros">

```rust
assert!(xs.is_empty());
```

```rust

```

## Tests that should panic, and tests that return Result

Some code is *supposed* to panic. drip-rs's arenas panic if you use a
handle to an object the collector freed, and a test checks exactly
that:

```rust
#[test]
#[should_panic(expected = "use after free")]
fn using_a_freed_handle_panics() {
    let mut arena = Arena::default();
    let a = arena.insert("x");
    arena.remove(a.index(), false);
    let _ = arena[a];
}
```

`#[should_panic]` flips the contract: the test passes only if the body
panics, and `expected = "..."` also requires the panic message to
contain that text, so a panic for some other reason does not count.
Both ways of getting it wrong are reported plainly by the harness:
`note: test did not panic as expected`, or `note: panic did not contain
expected string`, followed by the message it did get.

A test may also return `Result<(), E>` instead of nothing: `Ok(())` is
a pass, `Err(e)` a failure, and inside it the `?` of *Option and
Result* works, so a test of code that returns `Result` can read like the
code itself<Cite id="rust-book-testing" />.

<Analogy title="a smoke alarm">
An assertion in ordinary code, outside any test, is a smoke alarm in a
kitchen: it sits quietly through every normal meal and only goes off
when something is genuinely wrong, and when it does, everyone stops. A
`should_panic` test is the button on the alarm that you press on
purpose, to check that it does go off.
<span slot="breaks">A smoke alarm can be taken down and silenced; an
assertion in released code keeps running every time (only
`debug_assert!` is left out of optimised builds).</span>
</Analogy>

<OtherLanguages title="Checking values and expecting failure">

```rust
assert_eq!(max(&[3, 7, 2]), 7);
// and, on a test function:
#[should_panic(expected = "empty")]
```

```ts
expect(max([3, 7, 2])).toBe(7);
// and:
expect(() => max([])).toThrow('empty');
```

</OtherLanguages>

TypeScript's `expect` is a library function that builds a checker, and
a failure throws; `toThrow` wraps the call in a function so the library
can catch the exception. Rust's checks are macros that panic, and
expecting a panic is an attribute on the whole test, so a
`should_panic` test should contain only the call that ought to panic.

## Suites of hundreds of programs

The VM's corpus is a folder of Drip programs whose expected output is
written in their comments (*Differential testing at scale*). Wrapping
all of them in one `#[test]` would report a single `ok` or `FAILED` for
the lot, so drip-rs switches the standard harness off for that file in
`Cargo.toml`:

```toml
[[test]]
name = "corpus"
harness = false
```

`tests/corpus.rs` is then an ordinary program with its own `main`, and
cargo runs it and looks only at its exit code. That `main` lists the
`.drip` files, runs each through the VM, catches any panic with
`catch_unwind`, prints one line per program the way the standard
harness would, and calls `std::process::exit(1)` if any failed. On this
machine, `cargo test --test corpus -- programs/` ran 13 of them and
ended `corpus result: ok. 13 passed; 0 failed`; the full suite is 334
programs.

<Callout kind="engine" label="Under the hood">
engine/rust's `crates/cli/tests/parity.rs` is *Differential testing at
scale* across two languages: for every test program, with and without
`--bounds assume`, the Rust engine's output and explain text must equal
fixtures made by the TypeScript engine, byte for byte. Instead of
stopping at the first mismatch, it pushes each difference onto a `Vec`
with its first differing line, then asserts once:
`assert!(failures.is_empty(), "{} of {total} differ:\n{}", ...)`, so
one run reports every difference. Run with `--show-output` on this
machine, the test printed `parity: 190/190 (54 Python)`.
</Callout>

## What you learned

- **`assert!`**, **`assert_eq!`** and **`assert_ne!`** panic when their
  check fails; the last two print both values, so they need `Debug`
  and `PartialEq`. Each takes an optional message.
- **`#[should_panic(expected = "...")]`** passes only if the test panics
  with that text; a test returning `Result` fails on `Err` and may use
  `?`.
- `harness = false` lets a test file be its own program, as drip-rs's
  corpus runner is; engine/rust's parity test collects every difference
  before asserting once.
