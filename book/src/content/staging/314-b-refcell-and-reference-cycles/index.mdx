## Who owns the upvalue?

Here is a counter in Drip, close to the ones in *Capturing variables:
upvalues*:

```drip
fn makeCounter() {
  let n = 0;
  fn inc() { n = n + 1; }
  fn get() { return n; }
  inc();
  return get;
}
print makeCounter()(); # 1
```

`inc` and `get` both capture `n`, and `inc` changes it. In the
TypeScript VM, both closures hold a reference to one upvalue object,
and nobody asks which closure *owns* it: JavaScript's collector frees
it once nothing can reach it. In Rust, *Box, Rc and RefCell* gave us
`Rc` for "several owners", but an `Rc` only hands out shared access,
so `inc` could never change `n` through it. We need a way to mutate
something that several owners can see.

## RefCell: the borrowing rules, checked later

A **`RefCell<T>`** holds a value and a small borrow counter. Instead of
the compiler proving at build time that you never have a writer and a
reader at once, the `RefCell` *counts* them while the program runs:
`borrow()` hands out a reader, `borrow_mut()` a writer, and each call
first checks the rules of *Borrowing* against the counter. Each returns
a **guard**, a small value that gives its borrow back when it is
dropped. Step through one:

<BorrowFlag client:visible />

<Analogy title="a library book with a slip inside">
A reference book can be read by several people in the reading room at
once, but to take it home and write in the margins you need everyone
else to hand it back first. The librarian checks the slip inside the
cover each time someone asks, not once when the library was built.
<span slot="breaks">A librarian who finds the book out says "come back
later"; a `RefCell` that finds the rule broken stops the program with a
panic (unless you ask politely with `try_borrow_mut`, which returns an
error instead).</span>
</Analogy>

Because a `RefCell` lets you change its value through a shared `&`
reference, this is called **interior mutability**: from the outside
the cell looks unchanged, while its inside changes. Put one inside an
`Rc` and you have shared, mutable data, `Rc<RefCell<T>>`, the textbook
way to give one value several owners who may all change
it<Cite id="rust-book-smart-pointers" />.

<Run id="rc-share" />

That is the Drip counter in Rust: one upvalue in an
`Rc<RefCell<Upvalue>>`, captured by two closures. It prints
`owners: 3` (the original plus two closures), `get sees 2` after `inc`
has added 1 twice, and `owners: 1` once both closures are dropped.

<Callout kind="definition">
A **`RefCell<T>`** moves borrow checking from compile time to run time.
`borrow()` returns a shared guard (`Ref`) and `borrow_mut()` an
exclusive one (`RefMut`); each guard gives its borrow back when it is
dropped. Asking for a borrow that breaks the rules (a writer while
anyone else holds a borrow, or a reader while a writer does)
**panics**<Cite id="rust-std-cell" />. `Rc<RefCell<T>>` gives shared,
mutable data on one thread.
</Callout>

<Formal title="The check a RefCell makes">

```text
r = readers alive,  w = writer alive
borrow() ok      ⟺  ¬w
  and then r ← r + 1
borrow_mut() ok  ⟺  ¬w ∧ r = 0
  and then w ← true
otherwise: panic
```

<span slot="read">Let r be the number of reader guards alive and w say
whether a writer guard is alive. A borrow is allowed exactly when there
is no writer (¬ reads "not"), and adds a reader. A mutable borrow is
allowed exactly when there is no writer and (∧) no readers, and then a
writer is alive. Anything else panics.</span>
</Formal>

<Examples of="refcell">

```rust
let c = RefCell::new(5);
*c.borrow_mut() += 1;
println!("{}", c.borrow()); // 6
```

```rust
let up = Rc::new(RefCell::new(0.0));
let inc = Rc::clone(&up);
*inc.borrow_mut() += 1.0;
println!("{}", up.borrow()); // 1
```

```rust
fn heal(me: &RefCell<Instance>,
    other: &RefCell<Instance>) {
    let mut m = me.borrow_mut();
    let o = other.borrow();
    m.hp += o.hp / 2.0;
}
heal(&a, &b); // fine
heal(&a, &a); // panics
```

</Examples>

The first changes a number through a shared cell: `borrow_mut()`
gives a writer guard, `*` writes through it, and the guard is dropped
at the end of the statement, so the `borrow()` on the next line is
allowed. The second is the shared upvalue in four lines: `inc` and
`up` own the same cell, so the change made through one is seen through
the other. The third is where run-time checking bites. Drip happily
runs `a.heal(a)`, healing `a` from its own hit points, and here is a
VM's `heal` written with `RefCell`. `heal(&a, &b)` works, but
`heal(&a, &a)` asks for a reader of `a` while it holds a writer of `a`,
and rustc 1.97's program stops:

```text
thread 'main' panicked at
  src/main.rs:6:19:
RefCell already mutably borrowed
```

The compiler saw two parameters and no broken rule. The rule was broken
by *which objects were passed*, and in a VM the Drip program makes that
choice, so any VM code that holds a borrow while it touches another
object is one aliasing program away from a panic.

## Cycles never reach zero

Give each object a `field` that can hold another, and a `Drop` (code
that runs when a value is dropped) that prints. Then build a chain and
a cycle:

```rust
{
    let a = new("a");
    let b = new("b");
    a.borrow_mut().field =
        Some(Rc::clone(&b));
}
{
    let c = new("c");
    let d = new("d");
    c.borrow_mut().field =
        Some(Rc::clone(&d));
    d.borrow_mut().field =
        Some(Rc::clone(&c));
}
```

Run with rustc 1.97, the full program prints `free a`, `free b`,
`c has 2 owners` and `end of main`: the chain is freed, while `c` and
`d` never are. Step through the counts:

<CycleSteps client:visible />

<Analogy title="two people holding a door for each other">
Two polite people arrive at a door at once, and each says "after you";
each waits for the other to go first, so neither ever goes through. Two
`Rc`s that point at each other each wait for the other's count to fall
first, and neither ever does.
<span slot="breaks">People eventually laugh and one goes; an `Rc`
cycle never resolves itself, because nothing in reference counting
ever looks at the pair as a whole.</span>
</Analogy>

The standard library is blunt: a cycle between `Rc` pointers will
never be deallocated<Cite id="rust-std-rc" />, the problem *Cycle
collection and eliding counts* solved with a separate collector. The
Rust book adds that a leak is still memory *safe*: nothing dangles, the
memory is simply never given back<Cite id="klabnik2026" />. The usual
fix is **`Weak<T>`**, made with `Rc::downgrade(&rc)`: a pointer that
does not own, so it does not keep its value alive, and whose `upgrade()`
returns `Some(rc)` while the value exists and `None` after. Use it for
the edge that points "back up", such as a child's link to its parent.

<OtherLanguages title="Two objects that point at each other">

```rust
// leaks: neither count reaches 0
c.borrow_mut().field =
    Some(Rc::clone(&d));
d.borrow_mut().field =
    Some(Rc::clone(&c));
```

```ts
// fine: the collector frees both once
// nothing else can reach them
c.field = d;
d.field = c;
```

</OtherLanguages>

TypeScript's tracing collector (*Reclaiming memory: mark and sweep*)
asks "what can the roots reach?", so a cycle with no way in is garbage
like anything else. Reference counting only ever asks "how many
pointers are there?", and a cycle always has some. That is the price of
Rust freeing values at exact moments without a collector.

<Prompts ids={['cycle-leak', 'weak-what']} />

<Callout kind="engine" label="Under the hood">
A VM cannot use the `Weak` fix, because the *program* decides which
edges point back: `let a = new Node(); a.me = a;` is a one-line cycle,
and a recursive local function captures itself through an upvalue. So
drip-rs's `object.rs` opens by turning `Rc<RefCell<..>>` down: it
"would hand memory management to Rust instead of to our own garbage
collector". Its objects live in arenas instead, which the next chapter
builds; `Rc` appears only where ownership is simple, for frozen
bytecode chunks that never point back.
</Callout>

## What you learned

- A **`RefCell<T>`** checks the borrowing rules at run time:
  `borrow()` and `borrow_mut()` return guards, and breaking the rules
  **panics** (`RefCell already mutably borrowed`).
- **`Rc<RefCell<T>>`** gives a value several owners who may all change
  it, as a shared upvalue needs.
- **Cycles** of `Rc` never reach a count of 0, so they **leak**;
  `Weak` breaks a cycle when you know which edge points back.
- A VM's object graph is full of cycles the program chooses, which is
  why drip-rs gives its objects to its own collector.

Next: arenas and typed indices, where objects refer to each other by
number and cycles stop mattering.
