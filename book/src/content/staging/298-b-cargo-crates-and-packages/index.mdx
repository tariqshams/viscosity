## One file is easy; a project is not

You can compile a single Rust file by hand, with `rustc main.rs`, and
get a program called `main` beside it. Nobody works that way for long,
however: a real project has dozens of files, uses libraries other people
wrote, has tests, and needs two kinds of build (a quick one while you
work and a fast one to ship). In TypeScript you juggle `npm`, `tsc` and a
test runner for that; in Rust one tool does all of it.

<Analogy title="a general contractor">
When you build an extension you do not phone the bricklayer, the
plumber and the electrician yourself; you hire a contractor who knows
which trade comes next and who orders the materials. **Cargo** is that
contractor: you say "build", and it fetches the libraries you named,
calls the compiler in the right order and puts the results in one place.
<span slot="breaks">A contractor makes judgement calls on site; cargo
does exactly what its manifest file says, the same way every time, and
the compiler, not cargo, is the one that checks your code.</span>
</Analogy>

## Four commands

Step through a whole first session, from an empty folder to an
optimized program. The output is real (cargo 1.97, folder paths
trimmed):

<CargoSteps client:visible />

`cargo new` made a manifest and one source file. The manifest,
`Cargo.toml`, plays the part of `package.json`: a name, a version, an
edition and a list of dependencies<Cite id="rust-book-hello-cargo" />.

```toml
[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]
time = "0.1.12"
```

The first section names the package; `edition` picks a version of the
language's rules (cargo 1.97 writes 2024 for a new project, and this
book's runnable examples use 2021; nothing in the next chapters differs
between the two). The `[dependencies]` line asks for a library called
`time` from **crates.io**, Rust's public registry (as npm packages come
from the npm registry). The version `"0.1.12"` means "0.1.12 or any later
0.1 release, but not 0.2", because cargo assumes a change in the left-most
non-zero number may break your code<Cite id="cargo-specifying-deps" />.

The everyday commands, in the order you will use them:

<Examples of="cargo">

```text
$ cargo check
    Checking hello v0.1.0
error[E0308]: mismatched types
 --> src/main.rs:1:26
  |
1 | fn main() { let x: i32 = "a"; }
  |                          ^^^ expected
  |                    `i32`, found `&str`
```

```text
$ cargo run
    Finished `dev` profile [...]
     Running `target/debug/hello`
Hello, world!
```

```text
$ cargo build --release
   Compiling hello v0.1.0
    Finished `release` profile [optimized]
```

</Examples>

The first is the command you will type most: `cargo check` runs every
check the compiler has but skips making a program, so it is the fast
one, like `tsc --noEmit`; here it caught a string where a number was
promised. The second builds a **debug** program into `target/debug/`
and runs it; the lines starting with capitals are cargo's, and `Hello,
world!` is the program's own. The third turns the optimizer on and
writes to `target/release/`<Cite id="rust-book-hello-cargo" />. (Two
more you will meet soon: `cargo test` runs the `#[test]` functions, and
`cargo fmt` lays your code out in the standard style.)

<Callout kind="pitfall">
Debug builds are for working and release builds are for measuring. The
two differ in more than speed: the debug profile turns off optimization
and turns on checks such as integer overflow, which the release profile
turns off<Cite id="cargo-profiles" />. Every drip-rs number in the
previous chapter is a release number.
</Callout>

<Callout kind="definition">
**Cargo** is Rust's build tool and package manager. It reads the
manifest `Cargo.toml`, downloads the dependencies it lists (recording
their exact versions in `Cargo.lock`), runs `rustc`, and puts what it
builds under `target/`: `target/debug/` by default, `target/release/`
with `--release`.
</Callout>

## Crates: the pieces cargo builds

The compiler never looks at your whole project at once; it compiles one
**crate** at a time, starting from one file, the crate's **root**, and
following it to every file it names<Cite id="rust-book-packages-crates" />.
A crate comes in one of two kinds. A **binary crate** has a `main` and
becomes a program you can run. A **library crate** has no `main` and
becomes code that other crates use.

<Analogy title="a novel and a cookbook">
A novel is read from page one to the end, in order: it has a beginning,
like a binary crate's `main`. A cookbook has no beginning; you open it
at the recipe you need, the way other code calls the functions a library
crate offers. A **package** is the box set the publisher ships, with one
label on the box (one `Cargo.toml`).
<span slot="breaks">A box set may hold any number of novels and
cookbooks; a package may hold many binary crates but at most one library
crate.</span>
</Analogy>

The Rust Drip VM is a good example. Its `Cargo.toml` declares both kinds
in one package:

<Examples of="crate">

```rust
// src/main.rs: a binary crate
fn main() {
    println!("Hello, world!");
}
```

```rust
// src/lib.rs: a library crate
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}
```

```toml
# companion/rust/Cargo.toml
[lib]
name = "drip"
path = "src/lib.rs"

[[bin]]
name = "drip-rs"
path = "src/main.rs"
```

</Examples>

The first is the file `cargo new` writes: its root is `src/main.rs`, it
has a `main`, so it is a binary crate. The second is what `cargo new
--lib` writes instead (trimmed): no `main`, and `pub` (short for
*public*) lets other crates call `add`, like `export` in TypeScript. The
third is real: drip-rs names its library crate `drip`, holding the
scanner, compiler, VM and collector, and its binary crate `drip-rs`,
whose `main` reads a Drip file and hands it to the library.

Here is the mistake to expect, side by side with its fix:

```text
$ cargo new --lib mylib && cd mylib
$ cargo run
error: a bin target must be available
for `cargo run`
$ cargo test
test tests::it_works ... ok
```

A library has nothing to run, so `cargo run` refuses (the message says
there is no binary, which cargo calls a "bin target"); you exercise a
library through its tests, or from a binary crate that uses it.

<OtherLanguages title="Using a function from a library">

```rust
use drip::run;
// run(source, options) from the
// library crate `drip`
```

```ts
import { run } from 'drip';
// a function from an npm package
```

```python
from drip import run
# a function from a Python package
```

```c
#include "drip.h"
/* declares run(); the library is
   linked in by the build */
```

</OtherLanguages>

All four reach into a library by name. The genuine differences: in Rust
and TypeScript the library says which names are public (`pub`,
`export`), while Python lets you import almost anything; and in C the
header only *declares* the function, so the build has to link the
library's machine code in separately, which cargo does for you.

<Callout kind="definition">
A **crate** is the unit `rustc` compiles in one go, starting from its
root file. A **binary crate** has a `main` and becomes a program; a
**library crate** has no `main`, and other crates use its public items.
A **package** is one `Cargo.toml` with the crates it holds: any number
of binaries and at most one library<Cite id="rust-book-packages-crates" />.
</Callout>

## What you learned

- **Cargo** creates projects (`cargo new`), checks them quickly
  (`cargo check`), builds and runs them (`cargo build`, `cargo run`) and
  makes optimized builds (`--release`) in `target/release/`.
- `Cargo.toml` is the manifest; `[dependencies]` names libraries from
  crates.io, and `Cargo.lock` records their exact versions.
- A **crate** is one compilation unit: a binary (with `main`) or a
  library (without). A package holds at most one library and any number
  of binaries.
