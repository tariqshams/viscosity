## From a tree to a graph

The parser left you with an ESTree: a `ForStatement` node holding four
children, one each for the start, the test, the step and the body. That
tree mirrors how the code was *written*. The analyses ask questions
about how it *runs* (which values flow where, which loop reads which
field), and those questions need VIR, the SSA graph from the chapter
*VIR: Viscosity's IR*. The front end walks the tree once and builds that
graph, in `frontend-js/src/lower.ts`, about 600 lines.

<Analogy title="a recipe and a kitchen robot">
A recipe says "cream the butter and sugar, then fold in the flour"; a
kitchen robot needs "move arm to bowl 1, rotate 40 times, …". The recipe
groups words the way people think, while the robot's list orders actions
the way they happen. Lowering rewrites the first kind of text into the
second.
<span slot="breaks">A recipe step can be vague ("season to taste");
every JavaScript construct has an exact meaning, and when the lowering
does not model one exactly, it must say so (with `opaque`) rather than
guess.</span>
</Analogy>

<Analogy extra title="directions by landmarks and a sat-nav">
A friend says "go past the church, and if the bakery is open, cut
through the market". A sat-nav turns that into a numbered list of turns,
with every fork spelled out: at junction 3, if the market is open, go to
step 7, otherwise step 5.
<span slot="breaks">A sat-nav recomputes when you take a wrong turn;
lowering happens once, before anything runs, and must lay out every
path in advance, including the ones that loop back.</span>
</Analogy>

<Callout kind="definition">
**AST-to-IR translation** (lowering) walks a syntax tree and emits IR
instructions for each node: an expression returns the value that holds
its result, and a statement adds instructions and blocks. Control
structures such as loops become explicit blocks and branches, and
variables become SSA values or explicit memory.
</Callout>

## First, find out what every name means

Before emitting anything, `resolve.ts` walks the tree with a stack of
scopes, as your Drip resolver did in the chapter *Finding every name
before running: the resolver*. It maps every `Identifier` node to the
binding it refers to, and records some facts per binding:

```ts
interface JsBinding {
  name: string;
  kind: 'const' | 'let' | 'var'
    | 'param' | 'function' | /* … */;
  owner: Node;  // function that declares it
  usedIn: Set<Node>; // functions using it
  reassigned: boolean;
  assignedInTry: boolean;
  init: Node | null;
}
```

`usedIn` answers "is this captured?": if any function in the set is not
the owner, a closure reads or writes it. `assignedInTry` is set when an
assignment sits inside a `try` block, and `init` is the expression the
variable starts with.

## SSA value or binding?

Then comes the most important decision in the file. For each binding,
`lower.ts` picks one of two representations (simplified):

```ts
const simple = kind is const, let, var,
  param or catch;
if (simple && !capturedElsewhere
    && !b.assignedInTry
    && !isArrayInit(b.init))
  ssa.add(b);
```

An SSA variable is never stored anywhere: writing it records "`s` is now
`%8`", and reading it asks the builder (the on-the-fly algorithm of the
chapter *SSA on the fly*) for the current value, building phis at joins.
Everything else is a **binding**, with explicit `load` and `store`.
Here is the real VIR for a short program, trimmed:

```js
let s = 0;
let n = 0;
for (let i = 0; i < 3; i++) s = s + i;
const f = () => n;
```

```
b0:  %0 = const 0
     %1 = const 0
     store n, %1
     %3 = const 0
b1:  %7 = phi %0, %8      ; s
     %4 = phi %3, %11     ; i
b2:  %8 = binop + %7, %4
```

`s` and `i` vanished into values and phis, while `n`, read by the arrow
function, stays a binding with a real `store`: a closure may read it at
any time, long after any SSA value was current. Two rules look odd at
first. A variable assigned in a `try` is a binding, because the lowering
does not model the edges an exception can take, so an SSA value in the
`catch` could be the wrong one. And a variable initialised with an
array, such as `const ps = []`, is always a binding, so that every read
of a candidate collection shows up as a `load` the analyses can follow.

## Expressions return values

The heart of the file is `expr(e)`, one `switch` over ESTree node types;
each case lowers its children first and returns the `ValueId` of the
result. A `BinaryExpression` is one line:

```ts
case 'BinaryExpression':
  return fb.emit('binop',
    [expr(e.left), expr(e.right)],
    { operator: e.operator, src: src(e) });
```

Lower the left, then the right, then emit one `binop` that uses both,
and attach `src(e)`, the node's offsets, so emit can find this text
later. This is syntax-directed translation, as in the chapter
*Syntax-directed translation and attribute grammars*: each node's
translation is built from its children's.

<Formal title="Translating an expression">

```text
⟦n⟧        = emit const n
⟦x⟧        = current value of x  (SSA)
⟦e₁ op e₂⟧ = let a = ⟦e₁⟧, b = ⟦e₂⟧
             in emit binop op a, b
⟦e.f⟧      = emit field.get ⟦e⟧ .f
```

<span slot="read">The double brackets mean "the value that translating
this gives". A number emits a constant. A local name emits nothing: it
is whatever value the variable holds now. A binary expression translates
the left side, then the right, and emits one binop using both. A field
read translates the object and emits a field.get.</span>
</Formal>

<Examples of="ast-to-ir">

```
return a * 2 + 1;
  %1 = const 2
  %2 = binop * %0, %1
  %3 = const 1
  %4 = binop + %2, %3
  return %4
```

```
if (c) s = 1; else s = 2;
  b0: condbr %0, b1, b2
  b3: %4 = phi %2, %3
```

```
const ps = [{ x: 1 }];
ps[0].x++;
  %6 = index.get %4, %5
  %7 = field.get %6 .x
  %8 = unop + %7
  %9 = const 1
  %10 = binop + %8, %9
  field.set %6, %10 .x
```

</Examples>

In the first, the parameter `a` is `%0`, and the rule above produces
exactly this: `a * 2` first, because it is the left child of `+`. In
the second, a statement makes blocks: `condbr` splits, and the join
block gets a phi for `s`. The third is the interesting one. A compound
assignment goes through a helper, `readTarget`, which lowers the object
and index **once** and hands back a `get` and a `set` that share them,
just as JavaScript evaluates `ps[0]` once in `ps[0].x++`. The `unop +`
is JavaScript's conversion to a number: `x++` gives back the old value
*as a number*, even if `x` held the string `"5"`.

The runnable version lowers nested expressions the same way, numbering
values as it goes; try `['-', ['*', 'a', 'a'], 4]`.

## Loops become blocks

Statements add blocks. A `while` or `for` loop gets four, head, body,
continue and exit, which are also where `continue` and `break` jump to.
The interesting loop is `for (const p of ps)`. In JavaScript it runs the
iterator protocol<Cite id="mdn-for-of" />; however, when the right side
is a plain identifier, Viscosity lowers it to an index loop instead. For
arrays that visits the same elements in the same order (as long as
nobody replaces the built-in array iterator), and it makes element `i` an
ordinary `index.get` that the analyses already understand. Step through
it, with the real VIR:

<ForOfSteps client:visible />

If the right side is anything else, say `for (const p of make())`, the
test and the element both become `opaque` (VIR's honest unknown, from
the chapter *Records, collections and the honest unknown*), and no
analysis can claim to know what `p` is. The same goes for every
construct the lowering does not model: a class, a template literal,
destructuring. Each becomes one `opaque` instruction whose arguments are
every local variable its code mentions, so leaving something out of the
model can cost a speed-up but never correctness.

<Callout kind="engine" label="Under the hood">
The builder behind `fb.readVariable`, `fb.writeVariable` and `fb.seal`
is Braun and colleagues' SSA construction, which works during a single
walk of the tree: a block is sealed as soon as all its predecessors are
known<Cite id="braun2013" />. That is why the for-of lowering seals the
body right after the test, but the head only after the back edge
exists. The input is the standard ESTree node set<Cite id="estree" />,
so the same lowering runs on acorn's tree and on the book's hand-written
parser.
</Callout>

## What you learned

- **AST-to-IR translation** turns each expression into a value and each
  statement into instructions and blocks.
- Lowering **resolves scopes first**; `usedIn`, `assignedInTry` and
  `init` decide how each variable is represented.
- Uncaptured locals become **SSA values**; captured ones, ones assigned
  in `try`, and every variable initialised with an array become
  **bindings**.
- Compound assignments evaluate their target once (`readTarget`), and
  `for (const p of ps)` becomes an **index loop** with a phi.
