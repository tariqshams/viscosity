## A question the code cannot answer

*The cost model* gave Viscosity one rule that has nothing to do with
safety: below 64 elements, a new layout is not worth it. That rule needs
a number, and for most programs the analysis can count, because the
elements are pushed in a loop with a constant bound. Here it cannot:

```js
const ps = [];
function spawn(x) {
  ps.push({ x, vx: 1 });
}
for (let i = 0; i < 20; i++) spawn(i);
for (let f = 0; f < 100; f++) {
  for (let i = 0; i < ps.length; i++) {
    ps[i].x += ps[i].vx;
  }
}
console.log(ps[0].x);
```

The estimate in `core/src/analysis.ts` counts literal elements and
pushes in loops with constant trip counts, but only in the top-level
code: a push inside a function depends on how often the function is
called, so it gives up. `viscosity explain` says "size unknown
statically", so the threshold cannot apply, and Viscosity turns 20
elements into columns: safe, but pointless. You can read the 20 off
this program; a real program's count comes from a file, the network or
a user, and nobody can read it off the source.

<Analogy title="a tailor with a tape measure">
A tailor can guess your size from your height and age, or can measure
you; measuring takes a minute and gives the right answer, for you, on
the day you were measured.
<span slot="breaks">You will not grow into a different person by next
week; a program can be measured on a small input and then run on a huge
one.</span>
</Analogy>

<Analogy title="a shop ordering from last year's sales">
A shop orders this winter's stock from last winter's sales book rather
than from a hunch; if this winter turns out different, the shop has too
many umbrellas or too few, but it never sells anything it should not.
<span slot="breaks">A shop that misjudges loses money on every item;
Viscosity's worst case is a program exactly as fast as it was before
compiling.</span>
</Analogy>

## Run it, count, compile

Viscosity answers the question by running the program. The command is
`viscosity profile`, and its output goes back in with `--profile`. Step
through the loop, with every line of output taken from real runs of
the program above:

<PgoSteps client:visible />

<Callout kind="definition">
**Profile-guided optimisation (PGO)** is compiling with measurements
taken from real runs of the program, rather than only with what can be
worked out from the source. The measurements are the **profile**. The
usual loop is: instrument the program, run it on typical input, record,
and recompile with the record.
</Callout>

<Examples of="pgo">

```text
$ viscosity profile spawn.js -o p.json
$ cat p.json
{ "ps": { "maxLength": 20 } }
```

```text
$ viscosity explain spawn.js \
    --profile p.json
ps (line 1) {x, vx} → kept as array of
  objects
  · about 20 elements (measured): below
    the 64-element threshold, where the
    benefit is too small
```

```text
# the same program with 5000 calls:
ps (line 1) {x, vx} → struct of arrays
  · about 5000 elements (measured by
    profiling)
```

</Examples>

The first runs the program once and writes the profile (the real file
spreads it over several lines). The second compiles with it:
the measured 20 is below 64, so `ps` stays an array of objects, and the
report says the number was measured. The third is the same program with
the loop bound changed to 5000: profiled again, the measured size clears
the threshold and the verdict flips (the report's other lines are left
out here).

## Instrumentation

To count, `viscosity profile` builds a slightly different program. It
finds the collections the same way the compiler does (*Finding
collections*) and wraps the expression that creates each one. From
`cli/src/profile.ts`, slightly simplified:

```ts
const a = analyze(plugin.lower(src).module);
const edits = a.collections
  .map((c) => ({ start: c.init.src.start,
    end: c.init.src.end, name: c.name }))
  .sort((x, y) => y.start - x.start);
let out = src;
for (const e of edits) {
  const q = JSON.stringify(e.name);
  out = out.slice(0, e.start) +
    `__vsc_track(${q}, ` +
    out.slice(e.start, e.end) + ')' +
    out.slice(e.end);
}
return prelude + out;
```

Line by line: the program is lowered and analysed exactly as for
compiling; each collection contributes the start and end of its
creating expression and its name; the edits are sorted from the end of
the file backwards, so that inserting text never shifts the offsets of
edits still to come; and each edit wraps the expression in a call. The
prelude, put in front, defines the tracker and an exit hook:

```js
const __vsc_seen = [];
function __vsc_track(name, arr) {
  __vsc_seen.push([name, arr]);
  return arr;
}
process.on('exit', () => {
  const p = {};
  for (const [n, a] of __vsc_seen)
    p[n] = { maxLength: Math.max(
      p[n]?.maxLength ?? 0, a.length) };
  // ...write p to $VSC_PROFILE_OUT
});
```

`__vsc_track` returns the *same* array it was given; nothing is copied
or wrapped, so every `push`, every `===` and every `console.log` behaves
as before, because a profile of a program that behaves differently would
be a profile of the wrong program. The exit hook reads each tracked
array's length once, at the very end, and keeps the largest per name.
The instrumented copy runs once in a fresh Node process with its output
thrown away; nothing is timed, it only counts.

<Analogy title="a traffic counter across a road">
A council counts cars by laying a thin rubber tube across the road; each
wheel that rolls over it is counted, and the traffic carries on exactly
as before.
<span slot="breaks">Some drivers do slow down for the tube; good
instrumentation must change nothing a program can notice, and Viscosity's
only visible cost is a little extra time.</span>
</Analogy>

<Callout kind="definition">
**Instrumentation** is code added to a program to record what it does
while it runs: counts, sizes, branches taken, time spent. Good
instrumentation changes nothing the program can observe, and costs as
little as possible.
</Callout>

<Examples of="instrumentation">

```js
const ps = [];
// instrumented:
const ps = __vsc_track("ps", []);
```

```js
const grid = [{ h: 0 }, { h: 1 }];
// instrumented:
const grid = __vsc_track("grid",
  [{ h: 0 }, { h: 1 }]);
```

```text
viscosity: the profiled program failed
  (exit code 1)
```

</Examples>

The first is the real rewrite of our program's first line. The second
shows that the whole creating expression is wrapped, literal elements
and all, so the tracker sees the array the program will use. The third
is what you get if the program throws while being profiled: no profile
at all, because the sizes of half a run could mislead the planner. Try

## Where the number goes

The profile reaches exactly one place in the planner, from
`core/src/plan.ts`:

```ts
const measured =
  opts.profile?.[c.name]?.maxLength;
const size = measured ?? c.sizeEstimate;
if (size !== null && size < opts.minSize)
  // keep: "about N elements (measured)"
```

A measurement, when there is one, beats the estimate (`??` takes the
right side only when the left is missing, so a measured 0 still
counts). Look at *where* that line sits:

  <ProfileGate />
</Figure>

<Formal title="The size the threshold sees">

```text
size(c) = profile(c)   if c was measured
        = estimate(c)  otherwise
keep(c) ⟸ size(c) known ∧ size(c) < 64
```

<span slot="read">The size of collection c is its measured length if the
profile has one, and the static estimate otherwise; c is kept as objects
if (⟸, "it follows from") its size is known and less than 64.</span>
</Formal>

So a wrong profile can only pick between two programs already proven to
behave identically (*Proving it safe*), and the worst a stale profile
can do is choose the slower of two right answers. There are rough edges,
visible in the code: profiles are keyed by the variable's name, so two
collections both called `ps` share an entry; `viscosity profile` passes
the program no command-line arguments, so it must produce its typical
workload by itself; it cannot profile Python yet ("Python profiling is
not supported yet"); and the profile type has room for per-field read
counts that nothing records yet.

<Callout kind="engine" label="Under the hood">
A JIT does profile-guided optimisation all the time, during the same
run. V8 records feedback about the shapes and types each operation sees,
and its optimising compilers use it to generate specialised code; if an
assumption later breaks, the code is thrown away and execution
deoptimises<Cite id="v8-maglev" /> (*Speculation and deoptimization*).
That is the price of a profile that affects correctness: every
assumption needs a guard. Viscosity's profile is collected ahead of time
and only picks a size threshold, so its output needs no guard at all.
</Callout>

## What you learned

- **Profile-guided optimisation** compiles with measurements from a real
  run; Viscosity measures the one thing it cannot always compute, how big
  each collection gets.
- **Instrumentation** wraps each collection's creation in `__vsc_track`,
  which returns the same array, and an exit hook writes the lengths.
- In the planner, `measured ?? estimate`, read only after every safety
  check, so a bad profile costs speed, never correctness.
