## An order nobody asked for

Every IR in this part so far has been a list: three-address
instructions, one after another, grouped into basic blocks. A list
always says which instruction comes first, even when nothing needs it to:

```text
t1 = a * 2
t2 = b * 2
y  = x * c     ; only used in one arm
if (b) return t1 + t2
return y
```

The list says `t1` before `t2`, though either order gives the same
answer; and it computes `y` before the branch, though only one arm uses
it. Each optimisation then has to work out which of these orders are
real (an earlier pass wrote them down) and which are accidents of how the
source was written. What if the IR kept only the real ones?

<Analogy title="a recipe as a chart, not a list">
A cookbook lists its steps 1 to 8, yet you know you can chop the onions
while the water boils; only some steps truly wait for others (you cannot
drain pasta you have not cooked). Draw each step as a box, with an arrow
from every step to the steps that need its result, and the chart shows
exactly which orders are free.
<span slot="breaks">A kitchen has one cook and one stove, so in the end
someone still has to pick an order; the compiler, too, must turn its
chart back into a list before it can emit machine code.</span>
</Analogy>

<Callout kind="definition">
A **graph IR** stores a program as a graph whose nodes are operations and
whose edges say which operation uses which, rather than (or as well as)
as a list in a fixed order. The CFG of *IR, three-address code and
control-flow graphs* is already a graph,
of blocks; a graph IR goes further and makes the instructions themselves
the nodes.
</Callout>

## The sea of nodes

Cliff Click's design, worked out in his thesis on combining
optimisations<Cite id="clickthesis1995" /> and described with Michael
Paleczny in 1995<Cite id="clickpaleczny1995" />, goes all the way: every
instruction is a node, and there are no blocks to hold them. Two kinds of
edge remain. **Data edges** say which value feeds which; **control
edges** chain together the nodes that must happen in a set order (the
start, each branch, each return). A pure computation like `x * c` has
data edges but no control edge, so nothing ties it to a place: it
**floats**. The V8 team's description adds a third kind, **effect
edges**, which order memory loads and stores that have no data edge
between them<Cite id="v8-leaving-sea-of-nodes" />.

<Analogy extra title="a project board with only dependencies">
Picture a team's board where each task card lists only the cards it
waits for, with no dates at all. "Order the printing" waits for "finish
the poster"; "book the hall" waits for nothing, so it can happen any week
before the event. A scheduler reads the board and picks the dates.
<span slot="breaks">A real team can also run late or change its mind; a
node's place is decided once, by a fixed rule, and the rule must never
move it somewhere its inputs are not yet ready.</span>
</Analogy>

Eventually the floating nodes must be placed in blocks again. Click's
**global code motion** does it in two passes: schedule each node
**early**, in the first block where all its inputs exist, and then
**late**, in the nearest block that dominates all its uses; the node then
goes on the dominator-tree path between the two, in the shallowest loop,
and as late as possible<Cite id="click1995" /><Cite id="simple-son-gcm" />.
Step through it:

<SeaSteps client:visible />

<Formal title="Where global code motion puts a node">

```text
early(n) = deepest block of n's inputs
late(n)  = nearest common dominator
           of the blocks of n's uses
place(n) = on the path late → early,
           least loop depth, then latest
```

<span slot="read">The earliest block for n is the deepest (in the
dominator tree) of the blocks its inputs come from. The latest is the
nearest block that dominates every block that uses n. Walk up the
dominator tree from late to early, and choose the block with the smallest
loop depth; if several tie, the one nearest to late.</span>
</Formal>

<Callout kind="definition">
A **sea of nodes** is a graph IR in which only data dependencies,
control dependencies (and, in some designs, effect dependencies) order
the instructions. Pure nodes float free of any block until a scheduler,
such as global code motion, places them.
</Callout>

<Examples of="sea-of-nodes graph-ir">

```text
t1 = a * 2      ; two nodes, no edge
t2 = b * 2      ; between them: any order
```

```text
s = 0
loop: s = s + k * 2
; k * 2 uses only k, defined before the
; loop: least loop depth is outside it
```

```js
switch (c) {
  case 1: return a / b;
  case 2: return a / b + 1;
}
```

</Examples>

The first is the freedom a list hides: two nodes with no path between
them. The second is loop-invariant code motion for free: `k * 2` has no
input from inside the loop, so the "least loop depth" rule places it
before the loop. The third is a trap the V8 team describe: value
numbering merges the two divisions into one node, its uses are in two
different cases, so the nearest block dominating both is *before* the
switch, and `a / b` now runs even when `c` is 3; TurboFan's scheduler
had to learn to duplicate such nodes again<Cite id="v8-leaving-sea-of-nodes" />.

## Why V8 left the sea

TurboFan, V8's top-tier optimising compiler, was built on a sea of
nodes, an IR that by then had already been used for over ten years in
C2, the optimising compiler of the HotSpot Java virtual machine. In March 2025 the V8 team explained that,
for almost three years, they had been replacing it with a CFG-based IR
called **Turboshaft**; the whole JavaScript backend of TurboFan and all of
the WebAssembly pipeline used it by then<Cite id="v8-leaving-sea-of-nodes" />.
Their reasons, as they give them: in JavaScript almost every operation
can have side effects, so most nodes end up on the effect or control
chain anyway (their phrase is that the sea of nodes became "just CFG
where pure nodes are floating"); the graphs are hard for people to read;
keeping effect and control chains right by hand caused bugs; and
compiling was slow, which matters in a JIT. They report that compile time
halved after the switch<Cite id="v8-leaving-sea-of-nodes" />. That is one
team's experience with one language, not a verdict on the idea; however,
it shows that an IR is an engineering choice, judged by the programs it
has to compile.

## Continuations and A-normal form

Functional-language compilers have their own designs. In
**continuation-passing style** (CPS), no function returns: each one is
handed a callback, its *continuation*, saying what to do with the
result, so every intermediate value gets a name and the order of
evaluation is spelled out. **A-normal form** (ANF) keeps ordinary
returns but also names every intermediate value; Flanagan, Sabry, Duba
and Felleisen showed that a compiler can get the benefits of CPS from
this simpler form<Cite id="flanagan1993" />. ANF should look familiar: it

## MLIR: many small IRs

One IR for everything is a compromise; MLIR, from the LLVM project,
takes the opposite view. It is a framework of **dialects**, each a set
of operations and types under a namespace (`affine`, `arith`, `llvm`
and many more), and several dialects may live side by side in one
program; passes consume some and produce others<Cite id="mlir-langref" /><Cite id="lattner2021" />.
Its operations may also contain regions of blocks, so a loop can stay a
loop instead of becoming a tangle of branches. A program is
**progressively lowered**: rewritten a dialect at a time, from high-level
operations down to ones close to the machine<Cite id="mlir-langref" />.

<Examples of="mlir-dialects">

```text
%3 = toy.mul %2, %2 : tensor<3x2xf64>
```

```text
affine.for %i = 0 to 3 {
  affine.for %j = 0 to 2 {
    %a = affine.load %1[%i, %j]
    %m = arith.mulf %a, %a : f64
    affine.store %m, %0[%i, %j]
  }
}
toy.print %0 : memref<3x2xf64>
```

```text
%r = llvm.call @printf(%fmt, %v)
```

</Examples>

These come from the Toy tutorial, with types trimmed to fit. The first
multiplies two whole tensors in the `toy` dialect. The second is the
same multiply after partial lowering: two `affine` loops over buffers,
an `arith` multiply, and the `toy.print` still there, unlowered, in the
same function<Cite id="mlir-toy" />. The third is the last stage, in the
`llvm` dialect, where printing has become a call to C's `printf`. The
`affine` loops are *The polyhedral model* made into a
dialect, so loop transformations happen while the loops still exist.

<Callout kind="definition">
An **MLIR dialect** is a named set of operations, types and attributes
within MLIR. **Progressive lowering** translates a program through a
sequence of dialects, each step rewriting some operations into
lower-level ones, while other dialects may stay in place until their
turn.
</Callout>

## What you learned

- A **graph IR** keeps only the orders that matter: a node per
  operation, an edge per use.
- In a **sea of nodes**, data and control edges (and effect edges in
  TurboFan) order the nodes; pure nodes float until **global code
  motion** places them between early and late, in the shallowest loop.
- V8 replaced TurboFan's sea of nodes with Turboshaft, a CFG IR, citing
  readability, bugs and compile time for JavaScript.
- **CPS** names every intermediate and passes "what next" as a
  callback; **ANF** names every intermediate with ordinary returns.
- **MLIR dialects** let many small IRs coexist, and programs are
  **progressively lowered** through them.
