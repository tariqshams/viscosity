## Two keys, one slot

The last chapter ended on a collision: `"x"` is in slot 7, and
`"health"` hashes to slot 7 too. One fix hangs a little list off every
slot; the companion's `Table` does not, since a list per slot is one
more heap object to allocate and follow. Instead every entry lives in
the array itself, and a key whose slot is taken moves along.

<Analogy title="a car park with no reserved bays">
Your ticket says bay 7. If bay 7 is taken, you try bay 8, then 9,
wrapping round to bay 0 at the end of the row, until you find a free
one. Coming back later, you walk the same route from bay 7 and stop at
your car.
<span slot="breaks">A driver can see the whole row and pick any gap; the
table only ever looks at one slot at a time, in a fixed order, and a
lookup knows to give up when it reaches a bay that has never been
used.</span>
</Analogy>

## Linear probing

Lookups and inserts share one function, `Table.find`, which returns the
slot where the key *is*, or where it *should go* (from `vm/table.ts`,
with line breaks added to fit the page):

```ts
private static find(
  keys: (ObjString | null)[],
  values: Value[],
  key: ObjString): number {
  const mask = keys.length - 1;
  let index = key.hash & mask;
  let tombstone = -1;
  for (;;) {
    const k = keys[index];
    if (k === null) {
      if (values[index] === null)
        return tombstone !== -1
          ? tombstone : index;
      if (tombstone === -1)
        tombstone = index;
    } else if (k === key) {
      return index;
    }
    index = (index + 1) & mask;
  }
}
```

The first lines pick the starting slot, `hash & mask`, and `for (;;)`
loops until a `return`. A slot holding another key falls through to the
last line, which steps on (`& mask` wraps 8 back to 0); a slot holding
*our* key ends the search. A slot with no key is either truly empty
(value `null`), so our key is absent and we return where it should go,
or a **tombstone** (value `true`), which we remember and step past, for
reasons the next section explains.

Notice `k === key`: keys are compared as objects, not by their
characters. That is only right because equal strings are always the
same object in this VM, which is the job of *String interning*.

## Deleting without breaking the path

`health` sits in slot 2 *because* slots 7, 0 and 1 were full when it
arrived. Empty slot 1 by deleting `mass`, and a lookup for `health`
would stop there and report it missing. So `delete` leaves a marker
instead:

```ts
delete(key: ObjString): boolean {
  if (this.count === 0) return false;
  const i = Table.find(
    this.keys, this.values, key);
  if (this.keys[i] === null) return false;
  this.keys[i] = null;
  this.values[i] = TOMBSTONE;
  return true;
}
```

`TOMBSTONE` is the constant `true`. If `find` lands on a slot with no
key, there is nothing to delete; otherwise the key is cleared and the
value set to `true`: "something was here, keep going".
An insert of a new key reuses the *first* tombstone it passed, which is
why `find` remembers it; it cannot stop at the tombstone itself, because
only reaching a truly empty slot proves the key is not further along.

<Analogy title="a demolished house">
You find a friend's house by walking down the street from a number
worked out from their name. If one house on the way is knocked down
and the plot left bare, you might think the street ends there and turn
back; so the council puts up a sign on the plot: "a house was here,
keep walking".
<span slot="breaks">A real sign can be read from the pavement; the
table has to step onto the tombstone to see it. And the table can build
a new house on the plot, which is what reusing a tombstone does.</span>
</Analogy>

<Callout kind="definition">
With **open addressing**, every entry lives in the table's array itself;
a key whose slot is taken goes to another slot found by **probing**.
**Linear probing** tries the next slot, then the next, wrapping round. A
lookup stops at the key or at a truly empty slot. A deleted entry
becomes a **tombstone**, which probes step past, so keys stored beyond
it stay findable, and which an insert may reuse.
</Callout>

<Formal title="The probe sequence">

```text
pᵢ(k) = (slot(k) + i) mod m,  i = 0, 1, 2, …
stop at the first i where
  keys[pᵢ] = k            (found)
  or slot pᵢ is empty     (absent)
```

<span slot="read">The i-th slot tried for key k is its starting slot
plus i, wrapped round the capacity m. A lookup tries i = 0, then 1, then
2, and stops at the first slot that holds k or is truly empty;
tombstones are neither, so it goes on past them.</span>
</Formal>

```js

// 1 (mass), then 2 is free
```


## How full is too full?

Probing is quick while most slots are empty and slow when they are not,
and if no slot were ever truly empty, `find` would loop for ever. So `set` checks
the load *before* it does anything else:

```ts
set(key: ObjString, value: Value): boolean {
  if (this.count + 1 >
      this.keys.length * MAX_LOAD) {
    this.grow(this.keys.length < 8
      ? 8 : this.keys.length * 2);
  }
  const i = Table.find(
    this.keys, this.values, key);
  const isNew = this.keys[i] === null;
  if (isNew && this.values[i] === null)
    this.count++;
  this.keys[i] = key;
  this.values[i] = value;
  return isNew;
}
```

`MAX_LOAD` is `0.75`, and `count` counts live entries *and* tombstones,
since a tombstone fills a slot as far as probing is concerned; only
filling a truly empty slot adds to it. A new table has no slots at all,
so the very first `set` grows it to 8; after that it doubles. Because
the check comes before `find`, a `set` that would only overwrite an
existing key, or reuse a tombstone, can still trigger growth.

`grow` makes two new arrays of the new capacity, sets `count` to 0,
and walks the old `keys`: a slot with no key is skipped (`continue`),
and every live key is put through `find` on the *new* arrays and
stored there with its value, adding 1 to `count`. It cannot copy the
old arrays across, because the mask changes from 7 to 15 and every
key's starting slot may change; and since tombstones have no key,
growing also cleans the table up.

<Analogy title="a car park that closes at 75 per cent">
A car park puts up its FULL sign while a quarter of the bays are still
free, because the last few free bays take far longer to find than all
the others; the drivers circling for them would block everyone.
<span slot="breaks">A real car park cannot double in size overnight; the
table builds a brand new one twice as big and moves every car into
it.</span>
</Analogy>

<Callout kind="definition">
The **load factor** of a table is how full it is: occupied slots divided
by capacity. The companion table counts live entries and tombstones,
and before an insert that would take it past **0.75** it doubles its
capacity and re-inserts every live key. A lower limit wastes memory; a
higher one makes probe paths long.
</Callout>

<Formal title="When the table grows">

```text
α = count / capacity
grow first if count + 1 > ¾ × capacity
```

<span slot="read">The load factor, alpha, is count divided by capacity.
Before every set, if one more entry would push it above three quarters,
the table grows first.</span>
</Formal>

## What you learned

- **Open addressing** keeps every entry in the array. **Linear probing**
  steps to the next slot, wrapping with `& mask`, until it finds the key
  or a truly empty slot.
- `delete` leaves a **tombstone**, so probe paths stay unbroken; an
  insert reuses the first tombstone it passed.
- The **load factor** is count over capacity, tombstones included; the
  table doubles before it would pass 0.75, and re-inserts every live
  key, because the mask, and so every starting slot, changes.
