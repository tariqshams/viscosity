## A program that cannot change its mind

Every Drip program so far runs straight down the page: each statement
runs exactly once, in order, and then the program ends. You cannot print
"big" only when a number is big, and you cannot add up the numbers from
1 to 100 without writing a hundred lines. Real programs choose and
repeat, and this chapter teaches the interpreter both.

## Choosing: if and else

<Analogy title="points on a railway">
A train runs along one track until it reaches a set of points, where a
lever sends it left or right; which way depends on how the lever is set
at the moment the train arrives.
<span slot="breaks">A train always ends up somewhere; an `if` with no
`else` may take neither branch, and simply carry on with the next
statement.</span>
</Analogy>

Drip writes the condition without brackets and the body always in
braces: `if n > 3 { print "big"; }`. The interpreter's part is three
lines of `execute`:

```ts
case 'if':
  if (isTruthy(this.evaluate(s.condition)))
    return this.execute(s.then);
  if (s.else) return this.execute(s.else);
  return NORMAL;
```

It evaluates the condition, asks Drip's truthiness rule (so `0` and `""`
choose the `then` branch), and runs one branch or neither. Each branch
is a block, so it gets its own environment, exactly as in the last
chapter. There is no special node for `else if`: when the parser sees
`else if`, it parses the second `if` as the whole `else` branch, so a
chain of them is ifs nested inside elses.

<Callout kind="definition">
**Control flow** is the order in which a program's statements run, and
the parts of a language that change it: `if` chooses which statement
runs next, and loops send the program back to run statements again.
</Callout>

## Repeating: while, break and continue

`while` repeats its body while the condition is truthy, and each time
round the body gets a fresh environment:

```ts
case 'while':
  while (isTruthy(
      this.evaluate(s.condition))) {
    const c = this.executeBlock(s.body,
      new Environment(this.env));
    if (c === BREAK) break;
    if (c === RETURN) return c;
  }
  return NORMAL;
```

What is `c`? `break` and `continue` may sit deep inside the body (in an
`if`, in a block in an `if`), and they must stop work at every level on
the way out. So every `execute` hands back a small **completion** value
saying how the statement finished: `NORMAL`, `BREAK`, `CONTINUE` or
`RETURN`. The `break` statement just returns `BREAK`; `executeBlock`
stops its own list at the first statement that does not finish normally
and passes the value up. The loop then decides: `BREAK` ends it,
`CONTINUE` goes straight to the next test of the condition, and
`RETURN` (for functions, later) keeps travelling. Both statements apply
to the innermost loop, as in JavaScript<Cite id="mdn-break" /><Cite id="mdn-continue" />,
and outside a loop they are compile errors (`'break' outside a loop`).

## for, and rewriting one loop as another

Drip has one more loop, `for i in a..b { ... }`, which runs the body
with `i` set to `a`, `a + 1`, and so on while `i < b`. It looks like
something we could build out of parts we already have: a block, a
`let`, a `while` and a `+=`. Turning a construct into simpler ones like
that is called **desugaring** (the nicer spelling is the "sugar"), and
it is often done in the parser so that the back end has fewer kinds of
node to run.

<Analogy title="recipe shorthand">
A recipe says "make a white sauce", and an experienced cook expands that
into melt butter, stir in flour, add milk slowly; the short form is
easier to read and means exactly the long one.
<span slot="breaks">A cook can expand loosely; a desugaring must keep
*every* behaviour of the original, including the odd cases, or programs
quietly change meaning.</span>
</Analogy>

<Figure takeaway="A rewrite must keep every behaviour, and continue is the one that breaks this one." caption="A for loop and the while loop it seems to mean. The hidden end and k must not clash with your names, i must be fresh each time round, and a continue in the body would skip the k += 1 on the right, looping for ever.">
  <DesugarFor />
</Figure>

Look at the right-hand side carefully. `b` must be evaluated once, so it
needs a hidden variable; `i` is a fresh variable each time round
(assigning to it does not change which values come next), so the
counter has to be a different hidden `k`; and a `continue` in the body
jumps straight back to the test, *skipping* `k += 1`, so the loop never
ends. For these reasons the companion keeps a real `for` node and runs
it directly, in `forLoop`:

```ts
let i = start; // start and end: numbers
next = () => (i < end ? i++ : undefined);
for (let v = next(); v !== undefined;
     v = next()) {
  const loopEnv = new Environment(this.env);
  loopEnv.define(s.name.lexeme, v);
  // run the body; BREAK ends the loop
}
```

`start` and `end` are evaluated once, before the loop, and checked to be
numbers (`a range must start with a number, not a string`). Each value
gets its own `loopEnv`, which is how each time round has a fresh `i`,
the same choice JavaScript makes for `let` in a `for`<Cite id="mdn-for" />.

<Callout kind="definition">
**Desugaring** is rewriting a construct of a language in terms of
simpler constructs it already has, so that the rest of the
implementation needs to handle fewer kinds of node. In Drip, `else if`
is desugared into an `if` inside an `else`.
</Callout>

<Examples of="control-flow desugaring">

```text
if 0 { print "yes"; }   # yes: 0 is truthy
```

```text
for i in 0..3 { print i; }  # 0, 1, 2
for i in 3..0 { print i; }  # nothing
```

<Run id="loops" />

</Examples>

The first runs its body because `0` is truthy in Drip. In the second,
the range stops *before* `b`, so `0..3` gives three values and `3..0`
gives none at all. The runnable one adds up the numbers from 1 to 100
that are not multiples of 3: `continue` skips the multiples, and the
total is `3367`.

## && and || skip the right side

`&&` and `||` look like binary operators, but they cannot be, because a
binary node evaluates *both* children before it looks at the operator.
`false && x` already knows its answer after the left side, and so does
`true || x`; the right side should never run. The parser therefore gives
them their own node, `logical`, and the interpreter evaluates the right
side only when it is needed:

```ts
case 'logical': {
  const left = this.evaluate(e.left);
  if (e.operator.type === '||')
    return isTruthy(left) ? left
      : this.evaluate(e.right);
  return isTruthy(left)
    ? this.evaluate(e.right) : left;
}
```

The result is one of the operands, not always a boolean, which is also
how JavaScript's `||` behaves<Cite id="mdn-logical-or" />.

<Analogy title="a door with two checks">
A doorman checks your ticket first and your coat second; if you have no
ticket he sends you away without even looking at your coat.
<span slot="breaks">The doorman answers yes or no; Drip's `&&` and `||`
hand back one of the values they looked at, which may be a number or a
string.</span>
</Analogy>

<Callout kind="definition">
An operator **short-circuits** when it skips evaluating its right side
because the left side already decides the result: `&&` stops at a falsey
left side and `||` at a truthy one. Each produces the operand it stopped
at.
</Callout>

<Formal title="The two rules for &&">

```text
a ⇓ v    v falsey
─────────────────
   a && b ⇓ v

a ⇓ v    v truthy    b ⇓ w
──────────────────────────
       a && b ⇓ w
```

<span slot="read">Read ⇓ as "evaluates to". First rule: if a evaluates
to a falsey v, then a && b evaluates to v, and b is not mentioned above
the line at all, so it is never evaluated. Second rule: if a evaluates
to a truthy v and b evaluates to w, the whole expression is w. The
rules for || are the same with truthy and falsey swapped.</span>
</Formal>

<Examples of="short-circuit">

```text
print none || "default";  # default
```

```text
print 1 && 2;    # 2
print 0 || 5;    # 0: 0 is truthy
```

```text
print false && missing;   # false
```

</Examples>

`none` is falsey, so `||` moves on and returns `"default"`, the common
way to give a fallback value. `1 && 2` returns its right operand, `2`,
because the left was truthy; `0 || 5` returns `0`, because in Drip `0`
is truthy. The last line is the proof that the right side never runs:
`missing` was never defined, yet there is no runtime error.

## What you learned

- **Control flow** is which statement runs next: `if` picks a branch by
  truthiness, and `while` repeats with a fresh environment each time.
- `break` and `continue` travel outwards as a completion value until the
  innermost loop handles them.
- **Desugaring** rewrites a construct as simpler ones; `else if` is
  desugared, while `for` keeps its own node because the rewrite is
  easy to get wrong.
- `&&` and `||` **short-circuit**: they skip the right side when the left
  decides, and produce an operand.
