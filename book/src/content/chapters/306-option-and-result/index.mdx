## Where did the value go?

You have written this TypeScript many times:

```ts
const i = [4, 5, 6].indexOf(9);  // -1
const p = ps.find((p) => p.x > 100);
console.log(p.x); // crashes if none
```

That is two ways of saying "nothing here": `-1` and `undefined`. With
`strictNullChecks`, TypeScript flags the second, because `find` returns
`P | undefined`; however, `-1` is a perfectly good number, and nothing
stops you using it as an index. Rust takes the problem away at the
root: there is no `null` and no `undefined` at all. A value that might
be missing is an ordinary value of an enum you already know how to read.

<Analogy title="a parcel-locker slip">
When you collect a parcel from a locker bank, the machine prints a slip
first. The slip says either "box 7" or "nothing for you today". You
cannot open box 7 without reading the slip, and you cannot mistake
"nothing" for a box number, because it is not a number at all.
<span slot="breaks">A paper slip can be ignored or lost; Rust will not
let you ignore an `Option`, since it is a different type from the value
inside, and every use of it has to say what happens when it is
empty.</span>
</Analogy>

<Analogy title="a lost-property office">
Ask at a lost-property office about your umbrella and the clerk hands
you one of two things: the umbrella, or a card saying "not handed in".
They never hand you a random umbrella and hope you will not notice,
which is what `-1` does when it pretends to be an index.
<span slot="breaks">The clerk might add "try again tomorrow"; `None`
carries no reason at all. When you need to know *why* something is
missing, Rust uses a different enum, `Result`, which the next chapter is
about.</span>
</Analogy>

## Option: maybe a value

`Option` is an enum from the standard library, like the ones in *Enums
and match*. Simplified, its definition is:

```rust
enum Option<T> {
    None,
    Some(T),
}
```

The `<T>` says "some type, to be filled in": `Option<usize>` is maybe a
`usize`, `Option<&str>` is maybe a string slice. (The chapter *Generics
and trait bounds* is about those angle brackets; for now read them like
TypeScript's `Array<T>`.) `Option`, `Some` and `None` are so common that
every Rust file can use them without importing anything. Here is
`indexOf` done honestly; step through two calls:

The return type now says "maybe an index", and the caller cannot
pretend otherwise. Spot the difference: use the answer as a number, and
rustc 1.97 refuses (trimmed):

```rust
let i = find(&[4, 5], 5);
println!("{}", i + 1);  // ✗
```

```text
error[E0369]: cannot add `{integer}`
  to `Option<usize>`
12 |     println!("{}", i + 1);
   |                    - ^ - {integer}
   |                    |
   |                    Option<usize>
```

An `Option<usize>` is not a `usize`, so you have to read the slip first,
which the next section does.

<Callout kind="definition">
**`Option<T>`** is an enum with two variants: **`Some(value)`**, holding
a `T`, and **`None`**, holding nothing. A function that might have no
answer returns `Option<T>`, and the type system stops the caller from
using the `T` until it has checked which variant it got<Cite id="rust-book-enums" />.
</Callout>

<Examples of="option">

```rust
let xs = [4, 5, 6];
xs.get(1); // Some(5)
xs.get(9); // None
```

```rust
let words: Vec<&str> = vec![];
words.last(); // None
"drip".find('i'); // Some(2)
```

```rust
// from companion/rust/src/table.rs
keys: Vec<Option<StrRef>>, // None: empty
```

</Examples>

The first shows the standard library's own habit: `xs[9]` on a
three-element array would stop the program, while `xs.get(9)` asks
politely and answers `None`. In the second, `last` on an empty list has
nothing to give (`vec![]` makes an empty growable list, the `Vec` of a
later chapter), and `find` on a string answers with the byte position of
`'i'`, `Some(2)`. The third is real: the Rust Drip VM's hash table keeps
one key slot per entry, and a slot is either `Some(key)` or `None` for
empty, so "empty" can never be confused with a real key.

## Opening the slip

There are four everyday ways to get at what is inside, from the most
careful to the most blunt.

```rust
match find(&xs, 5) {
    Some(i) => println!("at {i}"),
    None => println!("absent"),
}
if let Some(i) = find(&xs, 6) {
    println!("6 is at {i}");
}
let i = find(&xs, 9).unwrap_or(0);
let j = find(&xs, 4).unwrap();
```

A `match` must cover both variants (leave out `None` and you get the
E0004 of *Enums and match*, "`None` not covered"). `if let`, from
*Patterns: the shapes match can see*, runs its block only for `Some`,
with `i` bound. `unwrap_or(0)` gives the value, or the default `0` when
there is none. And `unwrap()` gives the value or **panics**: it stops
the whole program with a message. Here is what `find(&xs, 9).unwrap()`
prints when it runs:

```text
thread 'main' panicked at f3.rs:11:30:
called `Option::unwrap()` on a `None`
value
```

So keep `unwrap` for places where `None` would be a bug in your own
program, such as a test, never for input a user could get wrong.

<OtherLanguages title="Maybe a particle">

```rust
fn first_fast(ps: &[f64])
    -> Option<f64> {
    for &v in ps {
        if v > 100.0 { return Some(v); }
    }
    None
}
let v = first_fast(&[3.0, 120.0]);
if let Some(v) = v { println!("{v}"); }
```

```ts
function firstFast(ps: number[])
    : number | undefined {
  for (const v of ps) {
    if (v > 100) return v;
  }
  return undefined;
}
const v = firstFast([3, 120]);
if (v !== undefined) console.log(v);
```

</OtherLanguages>

They read almost the same, and under `strictNullChecks` TypeScript also
makes you check before using `v`. The differences: in TypeScript the
check is narrowing on a union that includes `undefined`, and it is only
as strict as your compiler settings, while in Rust `Option` is an
ordinary enum, checked everywhere; and `Option` nests, so
`Option<Option<f64>>` can tell "no answer" apart from "the answer is
nothing", which `undefined | undefined` cannot.

## What Option costs

In memory, `Option` is the tagged union of *Sum types in memory*, with
one useful exception. The standard library guarantees that for some
types, such as references and `Box`, `Option<T>` is exactly the same
size as `T`: a reference is never null, so `None` can use the null bit
pattern, which the library calls the null pointer
optimization<Cite id="rust-std-option" /> (the niche of that chapter).

<Figure takeaway="Option of a reference is free; Option of a number needs a tag." caption="Sizes in bytes that rustc 1.97 printed on this machine. bool has spare bit patterns too, so Option<bool> fits in one byte, although that case is not one of the library's guarantees.">
  <OptionSizes />
</Figure>

<Formal title="Option adds one value">

```text
Option<T>  ≅  1 + T
|Option<bool>| = 1 + 2 = 3
```

<span slot="read">An Option of T is either the single value None (that
is the 1) or a Some holding any T, so it has one more possible value than T
itself: Option of bool has three, None, Some(false) and Some(true).
Whether that extra value needs extra bytes depends on whether T has a
bit pattern to spare.</span>
</Formal>

<Callout kind="engine" label="Under the hood">
The Rust Drip VM leans on `Option` where the TypeScript VM used `null`.
Returning from a call pops the running frame and then asks for the
caller with `self.frames.last()`, which is `None` when the script itself
has just returned; `pop_frame` (in `companion/rust/src/vm.rs`) returns
`Option<CallFrame>` for the same reason. A function's name is
`Option<StrRef>`, `None` for the top-level script and for anonymous
functions, which is how a stack trace knows to print `script` or
`anonymous fn`.
</Callout>

## What you learned

- **`Option<T>`** is `Some(value)` or `None`. It replaces `null`,
  `undefined` and magic values like `-1`, and it is a different type
  from `T`, so you cannot use it by accident.
- Get the value out with `match`, `if let`, `unwrap_or(default)`, or
  `unwrap()`, which panics on `None` and belongs where `None` is a bug.
- `Option<&T>` is the same size as `&T`; `Option<i32>` needs a tag.

Next: `Result`, for when you need to know *why* there is no value, and
the one-character operator that passes failures up the call stack.
