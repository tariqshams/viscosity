## Why 0.1 + 0.2 is not 0.3

In the testing chapter, `0.1 + 0.2` came out as `0.30000000000000004`,
and we needed `toBeCloseTo` to test it. That is not a bug in JavaScript;
it follows from how numbers are stored. The bitwise operators of the
last chapter worked on 32-bit integers, but those were temporary: every
ordinary JavaScript number is stored as a **float64**, a 64-bit pattern
in a format called IEEE 754 double precision<Cite id="mdn-number" />. It
works like scientific notation (6.02 × 10²³), but in binary: one bit for
the sign, 11 bits for the exponent (the power of 2) and 52 bits for the
digits.

<Figure takeaway="Every JavaScript number is 64 bits: sign, exponent, fraction." caption="The number 1 as a float64. Coloured cells are the bits that are on. The 11 exponent bits say “times 2 to the power 0”; the leading 1 of the number is implied, so the fraction bits are all zero.">
  <Float64Bits />
</Figure>

<Analogy title="a calculator with a short display">
On a calculator with eight digits, 1 ÷ 3 shows `0.3333333`, and
multiplying that by 3 gives `0.9999999`, not 1: the digits that did not
fit were dropped, and the small error shows up later.
<span slot="breaks">The calculator works in tens, so 0.1 fits on its
display exactly; a float64 works in twos, where 0.1 goes on forever
(like 1/3 in decimal), so even numbers that look simple to us are
slightly off.</span>
</Analogy>

<Analogy extra title="a ruler with marks">
A ruler can only show the lengths at its marks, so you write down the
nearest mark. Each float64 is one mark, and every result of a
calculation is moved to the nearest one.
<span slot="breaks">A real ruler's marks are evenly spaced; float64
marks are close together near 0 and spread out as numbers grow, until
above 2⁵³ they are 2 apart, and odd whole numbers fall between
them.</span>
</Analogy>

<Callout kind="definition">
A **float64** is a 64-bit (8-byte) floating-point number in the IEEE 754
double-precision format: a sign, an exponent and a fraction, so it can
hold very large and very small numbers, each to 15 to 17 significant
decimal digits. Every JavaScript number is one<Cite id="mdn-number" />.
</Callout>

<Formal title="What the 64 bits mean">

```text
value = (−1)ˢ × 1.f × 2^(e − 1023)
1:  s = 0,  e = 1023,  f = 0
```

<span slot="read">s is the sign bit (0 for positive), e is the 11-bit
exponent read as a whole number, and 1.f means a 1 followed by the 52
fraction bits as binary digits after the point. For the number 1, the
sign is 0, the exponent is 1023 (so the power is 1023 − 1023, which is
zero, and 2 to the power zero is one) and the fraction is all zeros.</span>
</Formal>

<Examples of="float64">

```js
0.1 + 0.2; // 0.30000000000000004
```

```js
2 ** 53 + 1 === 2 ** 53; // true
Number.MAX_SAFE_INTEGER; // 2 ** 53 - 1
```

```js
let total = 0;
for (let i = 0; i < 10; i++) {
  total = total + 0.1;
}
total; // 0.9999999999999999
```

</Examples>

The first is the famous one: neither `0.1` nor `0.2` can be stored
exactly, each is moved to the nearest mark, and the two tiny errors add
up to one that shows. The second is the other surprise: whole numbers
are exact only up to 2⁵³ − 1, which JavaScript names
`Number.MAX_SAFE_INTEGER`<Cite id="mdn-number" />; past that the marks
are 2 apart, so `2 ** 53 + 1` lands back on `2 ** 53`. The third is how
it bites in real code: adding ten prices of 0.1 does not give exactly
1, which is why programs that handle money usually count whole cents
instead.

<OtherLanguages>

```js
console.log(0.1 + 0.2);
// 0.30000000000000004
console.log(2 ** 53 + 1);
// 9007199254740992: not exact
```

```python
print(0.1 + 0.2)  # 0.30000000000000004
print(2**53 + 1)  # 9007199254740993
```

```java
System.out.println(0.1 + 0.2);
// 0.30000000000000004
long big = (1L << 53) + 1; // exact
```

```c
printf("%.17g\n", 0.1 + 0.2);
/* 0.30000000000000004 */
long long big = (1LL << 53) + 1;
```

</OtherLanguages>

All four agree on `0.1 + 0.2`, because Python's `float`, Java's
`double` and C's `double` are the very same float64 format. The real
difference is whole numbers: JavaScript has only the one number type,
so big integers run out of exact digits, while Python's `int` grows to
any size, and Java and C have separate integer types (`long`,
`long long`) that are exact up to about 9 × 10¹⁸. (JavaScript does have
a separate `BigInt` type for huge integers, written `123n`, which this
book does not need.)

## Raw bytes, and views onto them

Now that a number is 8 bytes, we can ask for bytes directly. An
`ArrayBuffer` is a block of raw bytes with no meaning attached; to read
or write it, you lay a **view** over it that says how to group the bytes
and what kind of number each group is.

<Analogy extra title="a strip of tiles and a stencil">
An `ArrayBuffer` is a strip of blank tiles. A typed array is a stencil
you lay over the strip: one stencil reads the tiles 8 at a time as
decimals, another 4 at a time as whole numbers. Two stencils over the
same strip see the same tiles.
<span slot="breaks">Tiles look the same however you group them; bytes
do not. The same 8 bytes read as a float64 and as two 32-bit integers
give numbers that look nothing alike, as the diagram below shows.</span>
</Analogy>

<Analogy extra title="seats sold in blocks">
A theatre sells one row of sixteen seats either as eight pairs or as
four blocks of four. The seats are the same; only the grouping changes,
and a change to seat 6 affects whichever block it belongs to.
<span slot="breaks">A seat is a seat however it is sold; a typed array
also decides what the bytes *mean* (a decimal, a whole number, signed or
not), so the grouping changes the values, not only the sizes.</span>
</Analogy>

<ByteViews client:visible />

```js
const buf = new ArrayBuffer(16);
const f64 = new Float64Array(buf);
const i32 = new Int32Array(buf);
console.log(f64.length, i32.length); // 2 4
```

Line 1 makes 16 bytes, all zero. Line 2 lays a `Float64Array` view over
them: 16 bytes in groups of 8 is two float64s, so `f64.length` is `2`.
Line 3 lays a second view over the *same* bytes, in groups of 4 as
32-bit integers, so `i32.length` is `4`; nothing is copied, and a write
through either view is seen by the other (aliasing, as in the chapter
on references). The diagram shows the bytes with the low byte first,
which is how most machines store them; typed arrays use whatever byte
order the machine natively has<Cite id="mdn-typedarray" />.

<Callout kind="definition">
An **ArrayBuffer** is a fixed-size block of raw bytes, initially all
zero; you cannot read it directly, only through a view<Cite id="mdn-arraybuffer" />.
A **typed array** (`Float64Array`, `Int32Array`, `Uint8Array`, …) is a
view that reads a buffer as numbers of one type and size<Cite id="mdn-typed-arrays" />:
its length is fixed, every element has the same type, and values are
converted to fit<Cite id="mdn-typedarray" />.
</Callout>

<Examples of="arraybuffer typed-array">

```js
const xs = new Float64Array(3);
xs;        // [0, 0, 0]
xs[1] = 2.5;
xs.length; // 3
```

```js
new Int32Array([3.7, -3.7]); // [3, -3]
new Uint8Array([256, 300]);  // [0, 44]
```

```js
const x = new Float64Array(3);
const vx = new Float64Array([2, 0, -1]);
for (let i = 0; i < 3; i++) {
  x[i] = x[i] + vx[i] * 0.5;
}
x; // [1, 0, -0.5]
```

</Examples>

The first skips the buffer: `new Float64Array(3)` makes its own 24-byte
buffer, filled with zeros, and you read and write it by index like any
array. The second shows the conversions: an `Int32Array` drops the
fraction, and a `Uint8Array` (one byte, no sign, 0 to 255) keeps only
the low 8 bits, so `256` becomes `0` and `300` becomes `44` (300 − 256).
The third is the payoff, the struct-of-arrays layout from the chapter on
arrays of objects: one column per field, here the positions `x` and speeds `vx` of
three particles, moved half a step.

<Figure takeaway="Columns are solid blocks of numbers; objects are reached through arrows." caption="The same three particles twice. Above, an array of arrows to separate objects. Below, one Float64Array per field: 3 × 8 = 24 bytes of numbers in a row, with nothing to follow.">
  <ColumnsLayout />
</Figure>

The fixed length is the usual surprise:

```js
const ys = new Float64Array(2);
ys.push(1);
// TypeError: ys.push is not a function
```

A typed array is a view over a buffer of a set size, so it has no
`push`; you create it at the size you need, then assign by index.

Try it: write through one view and read through the other, and watch
the conversions happen.

<Callout kind="engine" label="Under the hood">
One `Float64Array` per field is exactly the storage Viscosity generates.
The benchmark in this repository compares it with plain objects
(`engine/ts/packages/bench/results`, Node 22 on a shared cloud machine,
so treat the numbers as rough). Summing one field over a million
particles took about 1.1 ns per particle with `Float64Array` columns,
against about 8.9 ns with an array of objects. However, when the program
needed a real object for every one of those million particles, the
columns had to build them all, and came out over 30 times *slower* than
objects that already existed. Neither layout always wins, which is why
Viscosity has to analyse how your program uses its data before
choosing.
</Callout>

## What you learned

- Every JavaScript number is a **float64**: 64 bits, IEEE 754. So `0.1`
  is not exact, and whole numbers are exact only up to 2⁵³ − 1.
- An **ArrayBuffer** is raw bytes. A **typed array** is a fixed-length,
  single-type view of them that converts values to fit; two views of one
  buffer alias the same bytes.
- A `Float64Array` per field is the struct-of-arrays layout Viscosity
  generates.
