## What comes out

You met column storage in *Generating SoA storage*, where the JavaScript
emitter wrote one `Float64Array` per numeric field; this chapter goes
further, to the same plan carried out in Python, with Python's types
and Python's costs. Put `# @viscosity soa` on the line above a list, and `viscosity build`
turns this:

```py
ps = []
for i in range(1000):
    ps.append(P(float(i), 1.0))
for p in ps:
    p.x += p.vx
print(ps[3].x)
```

into this (the prelude it adds at the top comes later):

```py
ps = _Vsc_ps()
for i in range(1000):
    ps.append(float(i), 1.0)
for p in _vsc_iter(ps):
    ps.x[p] += ps.vx[p]
print(ps.x[_vsc_ix(ps, 3)])
```

Both print `4.0`. The records are gone: `ps` is now a container with
one column per field, `p` is now an index into those columns, and
`ps[3].x` became column `x`, slot 3, with a bounds check because the
analysis could not prove 3 is in range. It is the same plan the
JavaScript emitter carries out in *Generating SoA storage* and
*Rewriting field accesses and growing collections*, written in
Python's syntax and with Python's rules.

## The container

Here is the class the emitter generated for `ps`, from the real output
(its `_of` class method, which builds a container from a list literal,
is left out):

```py
class _Vsc_ps:
    __slots__ = ('n', 'x', 'vx')
    def __init__(self):
        self.n = 0
        self.x = _vsc_array('d')
        self.vx = _vsc_array('d')
    def append(self, v0, v1):
        self.x.append(v0)
        self.vx.append(v1)
        self.n += 1
    def __len__(self):
        return self.n
```

(In Python a class's methods take the instance as an explicit first
parameter, `self`, which plays the part of JavaScript's `this`, and
methods whose names begin and end with two underscores are hooks the
language calls itself: `__init__` when an instance is made, `__len__`
for `len(x)`.) `n` counts the elements; `__init__` makes one empty column per field
(`_vsc_array` is `array`, imported under a name your program cannot
clash with); `append` takes one value per column and adds each to its
own column; and `__len__` makes `len(ps)` keep working. `__slots__`
declares the container's attributes up front, so the container has no
per-instance dictionary<Cite id="python-datamodel" />, which has a
consequence for the generator: every attribute, `n` included, must be
listed, or `self.n = 0` raises `AttributeError`.

And the two helpers, wrapped to fit:

```py
def _vsc_ix(c, i):
    if -c.n <= i < c.n:
        return i
    raise IndexError(
        'list index out of range')

def _vsc_iter(c):
    i = 0
    while i < c.n:
        yield i
        i += 1
```

`_vsc_ix` is Python's indexing rule (as in *Lowering Python to VIR*,
an index must be an int, and here it must also be in range): negative
indexes count from the end and are fine, and anything past an end raises the same
`IndexError`, with the same message, that a list would. (It uses a
chained comparison, which Python itself is happy with; only Viscosity's
*reader* refuses them.) `_vsc_iter` is a **generator**, a function containing `yield` that
hands out one value each time a `for` loop asks for the next, so it
yields indexes
and re-reads `c.n` on every step, so a loop that appends while it
iterates sees the new elements, just as it would with a list.

## Python's array module

The typed columns are Python's own `array` type, part of the standard
library. `array('d')` holds C doubles, packed one after another, and
accepts only values that can be stored as one.

<Analogy title="an egg carton">
A list of floats is a row of labelled boxes, each holding a slip of
paper that says where its number is kept. An `array('d')` is an egg
carton: the numbers sit directly in the slots, packed side by side, with
no boxes at all, so the carton is far smaller. It also holds only eggs:
try to put a string in and it will not fit.
<span slot="breaks">An egg comes out of a carton as the same egg that
went in. A number comes out of an `array('d')` as a *new* Python float
built for the occasion, and an int that went in comes out as a float,
which is the whole story of this chapter.</span>
</Analogy>

<Analogy extra title="flat-pack furniture">
A warehouse that stores furniture flat-packed fits far more on its
shelves than a showroom that keeps every chair assembled. However,
every time a customer wants a chair from the warehouse, someone has to
assemble one before handing it over, while the showroom hands over the
chair that is already standing there.
<span slot="breaks">Assembling a chair takes minutes; building a float
takes nanoseconds. It only matters because a hot loop asks for one
millions of times, and because the "chair" is thrown away (left for the
garbage collector) as soon as the loop moves on.</span>
</Analogy>

<Examples of="python-array-module">

```py
>>> a = array('d', [1])
>>> a[0]
1.0
>>> a.itemsize
8
```

```py
>>> a.append('hi')
TypeError: must be real number, not str
>>> array('q', [2**63])
OverflowError: int too big to convert
```

```py
>>> xs = [2.5]
>>> xs[0] is xs[0]
True
>>> a = array('d', [2.5])
>>> a[0] is a[0]
False
```

</Examples>

All three are real output from Python 3.13, with the tracebacks
trimmed. In the first, the int `1` went in and the float `1.0` came
out, and each item takes 8 bytes (`itemsize`): that is why the planner
gives a typed column only to fields proven to hold floats, and every
other field gets a plain `list` column. The second is a spot the
difference with two failures: a string is refused outright, and a
64-bit integer column (type code `'q'`) is no way out for ints either,
because Python's ints are unbounded<Cite id="python-datamodel" /> and
`2**63` does not fit. The third is the one that decides the
measurement below: `is` asks "the very same object?", and reading a
list twice hands back the same float object both times, while reading
an `array('d')` twice builds two different float objects.

<Callout kind="definition">
Python's **array module** provides `array(typecode)`, a mutable
sequence that stores its items compactly as C values of one type, fixed
when it is created<Cite id="python-array" />. Type code `'d'` is a C
`double`, holding Python floats in 8 bytes each. Arrays index, slice
and `append` like lists, but storing a value of the wrong type is an
error, and every read builds a fresh Python object from the stored
value.
</Callout>

<Formal title="Bytes for n floats in CPython 3.13">

```text
list:       8n  (pointers)
          + 24n (one float object each)
array('d'): 8n  (the doubles themselves)
```

<span slot="read">A list of n distinct floats stores n pointers of 8
bytes each, and each points at its own float object of 24 bytes (what
sys.getsizeof(1.0) reports on this book's 64-bit machine), so about 32
bytes per number. An array of type d stores the n doubles directly, 8
bytes each, so about a quarter of that (both have a small fixed header
on top).</span>
</Formal>

## Why it is opt-in

Everything above works: the corpus programs print the same output and
raise the same exceptions as the originals. And yet, by default,
Viscosity keeps Python lists as objects, which *The architecture of
Viscosity and its plugin API* reported as a measured fact; here is the
measurement, and the reason for it in CPython's source:

<Figure takeaway="In CPython, columns save memory and cost time." caption="CPython 3.13, 100,000 elements, from this book's benchmark run (packages/bench/e2e-py/layouts.py, results/python-layouts-2026-10-31.json). The time is one update loop, x += vx * 0.016, written by hand for each layout.">
  <PyLayoutBars />
</Figure>

The update loop took 26.7 ns per element over dataclass objects, 43.3
over list columns and 72.7 over `array('d')` columns, while memory went
from 16.0 MB to 3.3 MB, about 4.9 times less. The reason is in
CPython's source: reading item `i` of an `array('d')` runs
`PyFloat_FromDouble` on the stored double<Cite id="cpython-arraymodule" />,
which creates a new float object every time (the chair being
assembled, the `False` in the third example). A dataclass object or a
list already holds float objects, so reading `p.x` hands one over.
CPython is an interpreter, and the cost of making objects dwarfs
anything a cache line can give back.

In JavaScript the same plan wins, because V8's optimising compiler
reads `Float64Array` elements as raw doubles (`FINDINGS.md`, section
6). Same IR, same analyses, same safety proofs; the measurement differs,
so the cost model's verdict differs. That is why a Python report says
`CPython: column access measured slower per element than objects (the
win is about 5x less memory)` and asks you to opt in, with
`# @viscosity soa` or `--python-auto`, when memory matters more than
time.

<Callout kind="pitfall">
The benchmark measures a hand-written loop, not Viscosity's output, and
the generated code also looks up `ps.x` on every access, which the
benchmark loop does not. No end-to-end Python result is committed yet;
`packages/bench/e2e-py/particles.py` is there for you to run on the
original and the compiled program.
</Callout>

## What you learned

- The Python emitter applies source **edits**: the list becomes a
  container, `append(P(...))` passes the arguments, element loops walk
  indexes, and field accesses become `ps.x[p]`, with `_vsc_ix` where a
  bound is not proven.
- The container uses `__slots__`, one column per field, a count `n`,
  and `__len__`.
- Python's **array module** stores C values compactly; `array('d')`
  holds floats only, an int comes back as a float, and every read
  builds a new float object.
- In CPython columns measured slower but used about 4.9 times less
  memory, so Python columns are opt-in.
