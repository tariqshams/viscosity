## Two hundred million questions

You met futures, `poll` and the waker in *Async Rust*, driven by the
crudest driver there is: a loop that polls, and if the answer is `Pending`, polls again at once.
For futures that are always nearly done, that works. Now give it a
future that waits 100 milliseconds for a timer on another thread. In a
release build with rustc 1.97 on a 4-core cloud machine, that loop
asked "are you done yet?" about 200 million times before the answer was
yes (between 176 and 267 million over eight runs, and about 7 million
in a debug build), with one CPU core
running flat out to learn nothing. We want a driver that asks once,
then sleeps until the future says it is worth asking again.

<Analogy title="a baby monitor">
You could stand by the cot all night asking "awake yet?". Instead you
go to bed with the monitor on; when it crackles, you get up and look.
The monitor is the waker, and getting up and looking is the poll.
<span slot="breaks">A monitor crackles at any noise, and sometimes the
baby is still asleep when you look; that happens to executors too (a
wake with nothing to do), which is why a woken future is polled and
may still answer Pending.</span>
</Analogy>

<Analogy extra title="an attendant at a launderette">
One attendant looks after forty machines. They do not walk the rows
opening doors; each machine beeps when its cycle ends, and the
attendant goes to whichever machine beeped and moves its washing on.
<span slot="breaks">The attendant only moves washing; the machines do
the washing on their own. In Rust, the work happens *during* the poll,
on the executor's own thread, which is why a poll must be quick.</span>
</Analogy>

## The executor's loop

<Callout kind="definition">
An **executor** is the code that runs futures to completion: it polls
each one, and when a future answers `Pending`, it waits until that
future's waker is called before polling it again. A **runtime** is an
executor plus what futures need to wait on: timers, network sockets and
files that report readiness, and ways to start new tasks<Cite id="async-book" />.
</Callout>

The standard library gives us the parts but no executor. A **`Waker`**
can be built from any type that implements the `Wake` trait, which has
one required method, `fn wake(self: Arc<Self>)`. A thread can sleep
with `thread::park()`, and another thread can wake it with
`unpark()` on its `Thread` handle<Cite id="rust-std-thread" />. Put
together, as the standard library's own documentation for `Wake`
does<Cite id="rust-std-future" />:

```rust
struct ThreadWaker(Thread);

impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) {
        self.0.unpark();
    }
}

fn block_on<F: Future>(f: F)
    -> F::Output {
    let mut f = pin!(f);
    let me = thread::current();
    let waker = Waker::from(
        Arc::new(ThreadWaker(me)));
    let mut cx =
        Context::from_waker(&waker);
    loop {
        match f.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => thread::park(),
        }
    }
}
```

Line by line: `ThreadWaker` wraps the handle of one thread, and waking
it means unparking that thread. `block_on` takes any future. `pin!`
fixes it in place on this stack frame (more on that below).
`thread::current()` is the thread calling `block_on`, the one that will
sleep. `Waker::from(Arc::new(...))` turns our type into a real waker,
and `Context::from_waker` wraps it for `poll`. Then the loop: poll once;
on `Ready`, return the value; on `Pending`, park, which sleeps until
someone calls `wake`. (If the wake comes before we park, `park` returns
at once, because an unpark is remembered; that is what keeps this from
missing a wake.)

## Why futures are pinned

`block_on` pins the future before polling it. Leave that out and rustc
1.97 refuses, with a hint (trimmed and wrapped):

```rust
let mut f = async { 1 };
let p = f.poll(&mut cx);
// error[E0599]: no method named `poll`
//   found for `async` block
// help: consider pinning the expression
//   let mut pinned = std::pin::pin!(f);
```

The reason is the state enum from the last chapter. An async fn may
keep a reference across an `.await` to one of its own local variables,
and both now live *inside the future*: the future points into itself.
If the future were moved to a new address, that inner reference would
point at the old one. `Pin` is the promise that, from the first poll
on, the future stays where it is, so such references stay
valid<Cite id="async-book" />. Most code never sees this: `pin!`,
`Box::pin` and `.await` take care of it.

## Many futures at once: Tokio

One `block_on` runs one future. Real programs want thousands, and want
the waiting itself to be cheap: a socket should wake its task when the
operating system says data has arrived, not because a helper thread
slept. That is a runtime's job. The most used one is **Tokio**, whose
README lists a multithreaded, work-stealing task scheduler, a reactor
built on the operating system's event queue (epoll, kqueue, IOCP) and
asynchronous sockets<Cite id="tokio-readme" />; the Rust book uses it
too<Cite id="klabnik2026" />.

<Examples of="executor">

```rust
// our own, from above
let n = block_on(async { 6 * 7 });
```

```rust
#[tokio::main]
async fn main() {
    let t = Instant::now();
    let (a, b) = tokio::join!(
        fetch("users", 300),
        fetch("posts", 200),
    );
    println!("{} in {:?}",
        a + b, t.elapsed());
}
```

```rust
let mut hs = Vec::new();
for i in 0..10_000u64 {
    hs.push(tokio::spawn(async move {
        sleep(ms(100)).await;
        i
    }));
}
for h in hs {
    sum += h.await.unwrap();
}
```

</Examples>

The first is ours: the simplest executor, for one future. The second
and third are trimmed from Tokio 1.54.1 programs built in a scratch
cargo project for this chapter (release build, rustc 1.97; `fetch` sleeps for the given
milliseconds with `tokio::time::sleep`, then returns the name's length,
and `ms` is short for `Duration::from_millis`). `#[tokio::main]` is a
macro that starts a runtime and calls `block_on` on your async `main`.
`tokio::join!` polls both futures in turn on one task, so the waits
overlap: it printed `posts done`, `users done`, `10 in 302.005458ms`,
the longer of the two waits rather than their sum. The third hands
10,000 futures to the scheduler as separate **tasks** with
`tokio::spawn`, each sleeping 100 ms, then awaits their handles; it
printed `49995000 in 109.193243ms`. Ten thousand waits overlapped on a
few worker threads, where ten thousand threads would have reserved
twenty gigabytes of stack.

<OtherLanguages title="Wait for two things at once">

```rust
let (a, b) = tokio::join!(
    fetch("users", 300),
    fetch("posts", 200),
);
```

```ts
const [a, b] = await Promise.all([
  fetch('users', 300),
  fetch('posts', 200),
]);
```

</OtherLanguages>

They read alike, but the difference from the last chapter shows here.
TypeScript's two calls have already started before `Promise.all` sees
them, and Node's built-in event loop runs them; Rust's two calls build
two paused futures, and `join!` is what polls them, inside whatever
runtime you chose.

One rule comes with every executor: **never block inside a future**.
`std::thread::sleep` is not an `.await`; it stops the whole thread,
and the executor with it. On Tokio's single-threaded runtime,
`join!(nap(200), nap(200))` with `std::thread::sleep` inside took
`400.385501ms`; with `tokio::time::sleep(...).await` it took
`201.334473ms`. The Async Book calls blocking a thread "very bad for
performance"<Cite id="async-book" />; slow work belongs on a thread of
its own (Tokio has `spawn_blocking` for that).

## What you learned

- An **executor** polls futures, and between polls it sleeps until a
  waker says a future can move; spinning instead wastes a whole core.
- A `block_on` is twenty lines of std: a `Wake` type that unparks a
  thread, a `Context`, and a loop of poll and `thread::park`; an
  executor for many tasks polls each in turn.
- Futures are **pinned** because they may point into themselves.
- **Tokio** is a runtime: `#[tokio::main]`, `join!` and `spawn` run
  many futures on a few threads, as long as no future blocks.
