## Three hops

To print a closure, the TypeScript VM of *Heap objects and lists in the
VM* follows references, `v.fn.name.chars`. drip-rs has no references
between objects: every object lives in an arena (*Arenas and typed
indices*), and where TypeScript holds an object, drip-rs holds a
`Gc<T>`, a typed slot number, so each hop is a trip to the heap:
`heap[c].function`, then `heap[function]`, then `heap.str(name)`.

<Analogy title="a cloakroom ticket">
At a theatre you hand in your coat and get a numbered ticket; you carry
the ticket all evening, not the coat, and you can copy the number onto
a napkin for a friend at no cost. Whenever anyone wants the coat, they
take the number to the counter, and the cloakroom, which owns every
coat on its rails, fetches it.
<span slot="breaks">If a cloakroom gave your peg to someone else after
you had left, an old ticket would fetch a stranger's coat; drip-rs has
exactly this risk after a collection, which is why its debug and stress
modes never reuse a freed slot, so a stale ticket fails loudly.</span>
</Analogy>

## One arena per kind, one alloc for all

The heap, from `gc.rs`, and an arena, from `object.rs` (trimmed):

```rust
pub struct Heap {
    pub strings: Arena<ObjString>,
    // ... eight more arenas
    interned: Table,
}

pub struct Arena<T> {
    slots: Vec<Option<T>>,
    free: Vec<u32>,
}
```

`insert` reuses a freed slot or pushes, and returns `Gc::new(index)`; a
freed slot is `None`. Objects carry no header: the arena says the type,
and mark bits live apart (*A garbage collector in Rust*).

<Figure takeaway="An arena is a Vec of optional slots; a handle is a slot number." caption="The closures arena after a collection freed slot 1. A Gc<ObjClosure> is just the number of its slot; insert takes slot 1 from the free list before it grows the Vec.">
  <ArenaSlots />
</Figure>

Where TypeScript has `newClosure`, `newClass` and so on, drip-rs has one
generic `alloc`, because every object type implements a trait naming its
arena (rewrapped, the collector's methods left out):

```rust
pub trait HeapObject: Sized {
    fn arena(heap: &Heap) -> &Arena<Self>;
    fn arena_mut(heap: &mut Heap)
        -> &mut Arena<Self>;
}

impl<T: HeapObject> Index<Gc<T>> for Heap {
    type Output = T;
    fn index(&self, handle: Gc<T>) -> &T {
        &T::arena(self)[handle]
    }
}
```

`a[b]` is shorthand for `*a.index(b)`<Cite id="rust-std-ops-index" />,
so one impl (and its `IndexMut` twin) serves every handle type, and
rustc makes a copy per type (*Generics and monomorphization*) in which
`T::arena` is just `&self.closures`: no tag is checked at run time. Step
through printing `add`, with the real slot numbers:

<HandleSteps client:visible />

<Callout kind="definition">
An **object handle** is a small `Copy` value that stands for a heap
object: in drip-rs a `Gc<T>`, the object's slot number in the arena for
`T`, read with `heap[handle]` and written with `heap[handle].field =
...`. Its type picks the arena at compile time; it owns nothing, so
anything can hold copies.
</Callout>

<Formal title="Typing heap[h]">

```text
h : Gc<T>    T : HeapObject
───────────────────────────
     heap[h] : T
```

<span slot="read">If h is a handle to a T, and T is a kind of heap
object, then heap of h is a T (borrowed from the heap): the type of the
handle alone decides which arena is read and what comes out.</span>
</Formal>

`heap[h]` borrows the *whole* heap, so reading one object while writing
another does not compile, even for two objects of the same kind:

<Examples of="object-handle">

```rust
let from = &self.heap[superclass].methods;
self.heap[subclass].methods.add_all(from);
// error[E0502]: cannot borrow
//   `self.heap` as mutable
let methods = self.heap[superclass]
    .methods.clone();
self.heap[subclass].methods
    .add_all(&methods);
```

</Examples>

This is `Inherit`, copying a superclass's methods into the subclass. The
first try holds `from`, a shared borrow of the heap, while
`heap[subclass]` asks for a mutable one, and rustc 1.97 refuses; the
real code clones first, once per class.

<More title="A heap to experiment with, and what a stale handle does">

A freed slot read through an old handle hits the `None` check, which
calls `use_after_free`, marked `#[cold]`, and panics with the type's
name from `std::any::type_name`, whose exact text the standard library
does not promise<Cite id="rust-std-type-name" />. `ObjString` overrides
the trait's `size` method to add its text's length, which the collector
uses to decide when to run.

## A list is a Vec behind a handle

In Drip, after `let ys = xs; push(ys, 30);` the list `xs` is longer too:
the assignment gives one list a second name. The TypeScript VM got that
sharing from JavaScript arrays. In drip-rs a list is
`ObjList { items: Vec<Value> }` in the `lists` arena, and a list value is
`Value::List(Gc<ObjList>)`, so `let ys = xs;` copies a handle and both
name one slot, whose 24-byte `Vec` owns a block of 16-byte elements.

<Figure takeaway="Two handles, one slot, one block of elements." caption="xs and ys hold the same Gc<ObjList>. The arena slot holds the Vec’s pointer, capacity and length; the elements are 16-byte Values in a block of their own, and a string element is one more handle.">
  <ListLayout />
</Figure>

For `[10, 20]` the compiler emits the elements, then `list 2`; the VM's
half (from `vm.rs`, rewrapped):

```rust
OpCode::List => {
    let n = self.read_byte() as usize;
    let start = self.stack.len() - n;
    let items =
        self.stack[start..].to_vec();
    let list =
        self.alloc(ObjList { items });
    self.stack.truncate(start);
    self.push(Value::List(list));
}
```

The order matters: `alloc` may collect first, while the new `Vec` is a
local the collector cannot see, so the elements must still be on the
stack, a root.

<ListBuildSteps client:visible />

<Callout kind="definition">
A **list in drip-rs's VM** is an `ObjList { items: Vec<Value> }` in the
heap's `lists` arena, reached through a `Gc<ObjList>` handle, so every
copy of the value shares one list; the collector marks every element of
every list it reaches.
</Callout>

<Examples of="rust-vm-list">

```text
let xs = [1];
xs[1] = 2;
# runtime error: index 1 is out of
#   range for a list of length 1
```

</Examples>

Both come from `check_index`, which checks in order that it has a list,
a number, a whole number and an index in range before turning it into a
`usize`; both VMs print the same message, trace line and exit code 70.
This is the common slip: `index.set` only replaces an element that
exists, and `push` adds one; `[1, 2]["0"]` fails the second check,
because a string is not a number even when it looks like one.

<More title="check_index, the cast it guards, and tracing a list">

The checks must come before `i as usize`, because a float-to-integer
`as` in Rust never fails: it rounds towards zero and saturates, and NaN
becomes 0<Cite id="rustref-numeric-cast" />, so `-1.0 as usize` is
silently 0. `pop` turns the `Option` from `Vec::pop` into `cannot pop
from an empty list`, and the standard library promises a push is cheap
on average but no particular growth factor<Cite id="rust-std-vec" />.

Tracing a list is one line of `gc.rs`,
`Gray::List(l) => self.lists[l].items.trace(marks)`, which marks each
element's object. A list that contains itself cannot trap the collector,
because a marked object is not pushed again, and printing has its own
guard: `let xs = []; push(xs, xs); print xs;` prints `[[...]]`. The heap
counts a list as `size_of::<ObjList>()`, 24 bytes, however long it is,
so a program with a few huge lists collects less often than its memory
use suggests.

## A string handle carries its hash

Interning (*String interning and globals by name*) makes equal strings
one object, so comparing them is one identity test. drip-rs keeps the
idea and changes the handle (from `object.rs`):

```rust
pub struct StrRef {
    pub handle: Gc<ObjString>,
    pub hash: u32,
}
```

The extra 4 bytes are free inside a 16-byte `Value`, and they let a
`Table`'s `get` and `set` take a key and nothing else. That matters
because tables live *inside* heap objects: if `set` had to read the
strings arena to hash a key, `self.heap[instance].fields.set(..)`, which
already borrows the heap mutably, could not compile.

<Figure takeaway="The hash rides in the handle, so a table never visits the heap." caption="A string value holds the handle and the hash. The ObjString keeps its text and the same hash; any table can start probing from the handle’s hash alone.">
  <StrRefShape />
</Figure>

Interning is the one place that compares characters. `Heap::intern`
hashes the text (FNV-1a, as in TypeScript<Cite id="lcn2-fnv" />), probes
`interned`, a `Table` of every live string used as a set, compares text
only when a hash matches, and allocates only when the string is new. It
calls `self.interned.find_string(&self.strings, chars, hash)`, borrowing
two fields at once, which rustc allows inside the heap's own method
because it can see they are different fields.

<Callout kind="definition">
A **string interner** maps each distinct string to one id: given some
characters, it either finds the id it handed out before or stores the
string and hands out a new one, so equal strings compare by id. In
drip-rs the interner is the heap's `interned` table, the id is a
`StrRef` (handle plus hash), and the collector deletes entries for
strings nothing else reaches.
</Callout>

<Examples of="string-interner">

```rust
let a = heap.intern("hello");
let b = heap.intern_owned(
    String::from("hel") + "lo");
assert_eq!(a, b);
assert_ne!(a, heap.intern("world"));
```

</Examples>

From `gc.rs`'s tests: text built at run time and text in the program
intern to the same `StrRef`, so `print "dr" + "ip" == "drip";` prints
`true` by comparing handles. `intern_owned` keeps the allocation `+`
just built; `intern`, lent a `&str`, must copy.

<More title="The interner's code, and the table: two columns, with tombstones">

From `gc.rs` (rewrapped):

```rust
pub fn intern(&mut self, chars: &str)
    -> StrRef {
    let hash = hash_string(chars);
    match self.interned.find_string(
        &self.strings, chars, hash) {
        Some(s) => s,
        None => self.add_string(
            chars.into(), hash),
    }
}
```

drip-rs's `Table` is the TypeScript one, struct of arrays and all:
`keys: Vec<Option<StrRef>>` and `values: Vec<Value>`. An empty slot is
`(None, Value::None)` and a deleted one `(None, Value::Bool(true))`, a
tombstone; `find` walks from `key.hash & mask`, remembering the first
tombstone it passes with `tombstone.get_or_insert(index)` so that `set`
can reuse it. The keys below really collide: by FNV-1a, `y`, `a`, `len`
and `key` all have `hash & 7 == 4`.

<TableSteps client:visible />

Why two columns in Rust? Measured here, `Option<StrRef>` is 12 bytes and
`Value` 16, while the pair `(Option<StrRef>, Value)` pads to 32; two
columns use 28 bytes a slot, and probing mostly reads only `keys`. The
interned table holds strings *weakly*: after a collection whose roots
never reach `"lost"`, interning `"lost"` again makes a new string.
`ObjString::chars` is a `Box<str>`, 16 bytes against `String`'s 24,
because an interned string never grows<Cite id="rust-std-string" />.
And interning moves work from comparing to creating: the `strings`
benchmark, whose loop builds and interns over a million strings, is
where drip-rs beat the TypeScript VM by only 1.26 times in the
2026-11-02 run, against 3.69 to 4.94 times on every other program.
