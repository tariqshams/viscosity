## Waiting for a value

Our running example, `sumsq`, adds up `i * i` for every `i` below `n`.
Ask clang for that function at `-O2` and there is a surprise: the
machine code has no loop in it at all, because the optimiser recognises
the sum and replaces it with a formula made of multiplies and shifts.
Real loops are rarely so obliging, so for the next few chapters we take
a close cousin of `sumsq` that no formula can replace, because it adds
up the squares of numbers that are only known when the program runs:

```drip
fn sumsq(xs) {
  let s = 0;
  for x in xs {
    s += x * x;
  }
  return s;
}
print sumsq([1, 2, 3, 4]); # 30
```

After instruction selection and register allocation, its loop looks
like this (`a0` points at the current number, `a1` at the end of the
list, and `a2` holds the sum; in machine code the numbers are 64-bit
integers, rather than Drip's floats):

```text
loop:
  ld   a3, 0(a0)      # x = *p
  mul  a3, a3, a3     # x = x * x
  add  a2, a3, a2     # s = s + x
  addi a0, a0, 8      # p = p + 8
  bne  a0, a1, loop   # again if p != end
```

Every line is correct, yet the machine spends much of its time idle. The reason is **latency** (*Caches, lines and locality*): an instruction's result
is not ready the moment it starts. A load has to reach the cache and come
back, and a multiply passes through several stages of the pipeline. The
`mul` on line 2 needs the value the `ld` fetches, so it has to wait; while
it waits, the CPU can do nothing else, because it starts instructions in
the order we wrote them.

To count cycles we will use a small, made-up machine for the rest of this
part: it starts at most one instruction per cycle, strictly in order; a
load or a multiply delivers its result 3 cycles after it starts; every
other instruction takes 1. Those two numbers are not invented: in LLVM's
model of SiFive's 7-series RISC-V cores, loads and integer multiplies both
have a latency of 3<Cite id="llvm-sifive7-sched" /> (that core can start
two instructions per cycle, which we leave out for now to keep the
counting easy).

A cycle in which nothing can start, because the next instruction is
waiting for an operand, is called a **stall**. Step through the loop and
watch where they fall:

The first order costs 9 cycles a trip, 4 of them stalls. The second is
what clang really produced for this loop at `-O2`: the same five
instructions, but with `addi` moved up to fill a gap, so a trip costs 8.
That move is the whole idea of this chapter.

<Callout kind="definition">
The **latency** of an instruction is the number of cycles from when it
starts to when an instruction that uses its result can start. A **stall**
is a cycle in which no instruction starts because the next one is waiting.
**Instruction scheduling** is reordering the instructions of a block,
without changing what the block computes, so that it finishes in fewer
cycles<Cite id="coopertorczon2022" />.
</Callout>

<Examples of="instruction-scheduling">

```text
ld   a3, 0(a0)
addi a3, a3, 1   # waits 2 cycles
li   a4, 5       # could fill the gap
```

```text
ld   a3, 0(a0)
li   a4, 5       # cycle 1: useful
addi a3, a3, 1   # cycle 3: one stall
```

```text
ld   a6, -32(a5)
ld   a7, -24(a5)
mul  a6, a6, a6
```

</Examples>

The first block wastes two cycles: `addi` needs `a3`, which arrives in
cycle 3, and `li a4, 5` (load the number 5 into `a4`), which needs
nothing, sits behind it. The second moves `li` into the gap; it now
starts in cycle 1, `addi` still starts in cycle 3, and the block finishes
a cycle sooner. The third is real: asked to compile the same loop for a
SiFive U74 core (`clang -O2 -mcpu=sifive-u74`), clang unrolled it eight
times and wove the copies together, so each `mul` starts a couple of
instructions after its load; these are the loop's first three lines.

Scheduling matters most on **in-order** cores like these; big
**out-of-order** cores also reorder instructions themselves, in
hardware, though only within a limited window.

## What may move, and what may not

Moving `addi a0` up was safe; moving it above the `ld` would not be,
because the `ld` reads `a0` and must see the old pointer, not the new one.
Before a scheduler can move anything it needs to know, for every pair of
instructions, whether their order matters. *Dependence analysis, interchange and fusion* met the three
kinds of dependence between statements in a loop; here are the same
three, between instructions in a block:

- a **true** dependence: B reads a register A writes (`ld a3` then
  `mul ... a3`). B must wait the full latency of A.
- an **anti** dependence: B writes a register A reads (`ld ... 0(a0)`
  then `addi a0`). B must not start before A, but need not wait longer.
- an **output** dependence: both write the same register; the second
  write must land last, or the wrong value is left behind.

Memory adds a fourth worry: a store and a load whose addresses might be
the same must keep their order, unless alias analysis (*Alias analysis and points-to*)
proves they never touch the same bytes. Finally, the branch at the end of
a block stays at the end.

We draw all of this as a graph. Each instruction is a node; an arrow from
A to B says "B must start at least this many cycles after A starts". The
arrows only ever point forwards, from earlier instructions to later ones,
so the graph can never loop back on itself:

<Analogy extra title="a cake and a mixing bowl">
The cake must bake for forty minutes before it can be iced: that is a
true dependence, with a delay. The icing can be made at any time, which
is why it is a separate node with no arrow into it. And if you have one
mixing bowl, you cannot start the icing in it until the batter has been
poured out: nothing flows from batter to icing, but the shared bowl
forces an order. That is an anti dependence.
<span slot="breaks">Fetch a second bowl and the anti dependence is gone.
Registers are like bowls, and fetching another is exactly what register
allocation decides not to do when registers run short; *List scheduling*
shows how scheduling and allocation pull against each other.</span>
</Analogy>

Socks before shoes, shirt before jacket; but socks and shirt can come in
either order. The rules form a graph with no loops (nobody needs shoes
on before socks), and any order that respects the arrows gets you
dressed.
<span slot="breaks">Getting dressed has no waiting: shoes can go on
the moment the socks are on. Our arrows carry delays as well as an
order.</span>
</Analogy>

<Callout kind="definition">
The **dependence DAG** (directed acyclic graph) of a block has one node
per instruction and an edge from A to B, labelled with a **delay**
d(A, B), whenever B must start at least that many cycles after A: the
latency of A for a true dependence, and 0 or 1 for an anti or output
dependence or a fixed order. The longest path through it, adding the
delays, is the **critical path**; no schedule can be shorter.
</Callout>

<Formal title="What a schedule must satisfy">

```text
S : instructions → cycles
for every edge A → B in the DAG:
    S(B) ≥ S(A) + d(A, B)
at most w instructions per cycle
length(S) ≥ longest path + 1
```

<span slot="read">A schedule S gives every instruction a start cycle.
For every arrow from A to B, B starts no earlier than A's start plus the
delay on the arrow. At most w instructions start in any one cycle (w is 1
on our toy machine). And whatever we do, the block takes at least the
critical path plus one cycle for the last instruction itself.</span>
</Formal>

<Examples of="dependence-dag">

```text
add t0, a0, a1
add t1, a2, a3   # no edge: unrelated
```

```text
mul a3, a3, a3
add a2, a3, a2   # true, delay 3
ld  a5, 0(a0)
addi a0, a0, 8   # anti, delay 0
li  a6, 1
li  a6, 2        # output, delay 1
```

<Run id="dag" />

</Examples>

The first pair share no registers, so either may go first and there is
no edge at all. The second block shows one edge of each kind, with the
delay our toy machine gives it. The runnable one builds the DAG of the
loop body the way a compiler does: it walks forwards, remembering, for
every register, which instruction last wrote it and which have read it
since. A read of a register that was written earlier gives a true edge;
a write gives an anti edge from every reader since the last write, and
an output edge from the last writer.

## What you learned

- **Latency** is how long a result takes to be ready; a **stall** is a
  cycle wasted waiting for one.
- **Instruction scheduling** reorders a block to fill those cycles,
  without changing what it computes.
- The **dependence DAG** records which instructions must wait for which,
  with a delay on every edge: true, anti, output, memory and branch order.
- The **critical path** is the longest path through it, and no schedule
  is shorter.
