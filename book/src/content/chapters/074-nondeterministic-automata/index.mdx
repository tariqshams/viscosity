## One machine for many rules

A real scanner does not have one rule; it has dozens. Drip's has a rule
for numbers, one for names, one for strings and one for each keyword and
operator, and at the start of every token it does not know which rule
will win. So imagine trying to build *one* DFA that recognises "`if`, or
any name": after reading `i` it must already be in a state that means
"this could still be the keyword, and it could also be a name", which is
a state neither of the two small machines had. Doing that by hand for
dozens of rules is a puzzle of its own, and it is exactly what this
chapter avoids.

The trick is to relax the rule that made a DFA deterministic. We allow a
state to have **several** arrows with the same label, and arrows marked
**ε** (epsilon, as in the last chapters: the empty string) that the
machine may follow *without reading anything*. Then "`if` or a name" is
easy to draw: a new start state with two ε-arrows, one into each small
machine.

<Analogy title="a search party">
A search party reaches a fork in the path and splits up, so that someone
walks down every branch at once; each group that hits a dead end simply
stops, and the search succeeds if any group finds the lost dog.
<span slot="breaks">Real groups get tired and the party runs out of
people; an NFA can follow any number of branches, and two groups that
arrive at the same spot merge into one, which is what keeps the
bookkeeping small.</span>
</Analogy>

<Analogy extra title="free connections on a train map">
On some city maps a dotted line joins two stations that are really one
interchange: you can walk between them without buying another ticket.
An ε-arrow is that dotted line; it moves you without using up any
input.
<span slot="breaks">Walking an interchange takes time; following an
ε-arrow costs nothing at all, and the machine follows every one it can,
all at once.</span>
</Analogy>

## Several arrows, and arrows that read nothing

Look at state 0 of the NFA: on `a` it has two arrows, one looping back
to 0 and one going to 1. The machine does not choose; we say it accepts
a string if **some** way of following the arrows ends in an accepting
state. For `bab`, the path 0, 0, 1, 2 does (loop on `b`, take the `a` to
1, then `b` to 2), so `bab` is accepted, even though the path that
loops all the way round ends in 0.

<Callout kind="definition">
A **nondeterministic finite automaton** (an **NFA**) is a finite
automaton in which a state may have any number of transitions for the
same character, including none, and may also have **ε-moves**:
transitions that are taken without reading a character. An NFA accepts
a string if at least one path from the start state, reading the whole
string (and taking any ε-moves along the way), ends in an accepting
state<Cite id="rabinscott1959" />.
</Callout>

<Formal title="What changes from a DFA">

```text
δ : Q × (Σ ∪ {ε}) → P(Q)
ε-closure(T) = T plus every state
   reachable from T by ε-moves alone
N accepts w  ⟺  δ*(q₀, w) ∩ F ≠ ∅
```

<span slot="read">The transition function now takes a state and either a
character or ε, and gives back a set of states (P(Q) is "the set of all
subsets of Q"), possibly empty. The ε-closure of a set T is T together
with everything you can reach from it by following ε-arrows only. N
accepts w exactly when the set of states you can be in after reading w
shares at least one state with F, the accepting states.</span>
</Formal>

## Running an NFA without guessing

"Some path works" sounds like the machine needs luck, or needs to try
every path one by one. It needs neither: instead of one current state,
keep the **set** of all states it could be in, like pins on a map, and
move every pin at each character. Step through the "keyword `if` or a
name" machine:

<NfaSetSteps client:visible />

Each step has two parts. First, **move**: for every pin, follow the
arrows labelled with the character just read (a pin with no such arrow
is dropped). Second, take the **ε-closure**: add every state reachable
from the pins by ε-arrows alone. At the end, accept if any pin is on an
accepting state. In code, with an NFA stored as a list of edges
`[from, label, to]` and `null` as the label for ε:

```js
function closure(nfa, set) {
  const out = new Set(set);
  const todo = [...set];
  while (todo.length > 0) {
    const q = todo.pop();
    for (const [p, c, r] of nfa.edges) {
      const eps = p === q && c === null;
      if (!eps || out.has(r)) continue;
      out.add(r);
      todo.push(r);
    }
  }
  return out;
}
```

`out` holds the answer and starts as a copy of the set; `todo` is a list
of states whose ε-arrows we have not followed yet. Each round takes one
state off `todo` and looks at every edge: `eps` is true for an ε-edge
that starts at `q`, and any other edge is skipped, as is one leading
somewhere already in `out` (which is what stops ε-cycles from looping
forever).
Any new state is added and put on `todo`, because *its* ε-arrows must
be followed too. When `todo` is empty, `out` is the closure.

The first is the NFA from the figure on `aab`: every `a` both keeps a
pin on 0 and puts one on 1, and the final `b` moves the pin on 1 to 2.
The second is the pattern `a?b` as an NFA; the ε-arrow is the "or
nothing" branch of `a|ε`, and it lets `b` alone through without reading
an `a`. The runnable one is the `if`-or-name machine from the stepper,
with real code; change the input words to see the sets change.

A common slip is to forget the closure at the very start:

```js
let set = new Set([nfa.start]); // wrong
let set = closure(nfa, [nfa.start]);
```

With the first line, the `if`-or-name machine begins with a pin on 0
only, and 0 has no arrow for `i`, so every word is rejected.

## Why bother, if DFAs are faster?

Simulating an NFA does more work per character than a DFA (it moves a
whole set of pins, not one), so why would a scanner use one? Because
NFAs are far easier to **build**: gluing two machines together is a
matter of adding a state and two ε-arrows, which is exactly what the
next chapter does for every operator of a regular expression. And they
cost nothing in power: Rabin and Scott proved that for every NFA there
is a DFA accepting the same language<Cite id="rabinscott1959" />. The
proof is the pins idea itself: make one DFA state for each *set* of
pins that can occur. That recipe, the subset construction, is also in
the next chapter.

<Callout kind="engine" label="Under the hood">
The price of that recipe is size: an NFA with n states has 2ⁿ possible
sets of pins, and for some languages the smallest DFA really does need
exponentially many states; the textbook example is "the n-th character
from the end is an a"<Cite id="hmu2006" />. Scanner rules are not like
that in practice, which is why tools such as lex turn their NFAs into
DFAs ahead of time<Cite id="aho2006" />, while some regex engines keep
simulating sets of states as you have just done, to avoid the blow-up.
</Callout>

## What you learned

- An **NFA** may have several arrows for one character, none at all,
  and **ε-moves** that read nothing; it accepts if some path ends in an
  accepting state.
- To run one without guessing, keep the **set of states** it could be
  in: move every pin on each character, then take the **ε-closure**;
  accept if any pin is on an accepting state.
- NFAs are easy to build and combine, and they recognise exactly the
  same languages as DFAs.
