## Two garbage collectors deep

Think back to the chapter *Reclaiming memory: mark and sweep*. Your Drip
VM is a TypeScript program, so it runs on V8, and V8 already has a
garbage collector<Cite id="v8-trash-talk" />; yet you still had to write
a second one over the VM's own list of objects, because only the VM knows
which Drip objects are still reachable (to V8, everything on that list
looks alive). That is two collectors stacked on top of each other, and
the bottom one is doing work you never asked for.

Then think back to *How JavaScript stores numbers and objects*: every
object carries a hidden header, and the engine decides how numbers are
stored. Viscosity, the compiler you finished in Part IX, exists because
JavaScript gives you no direct say over memory layout; it has to coax
the engine into a struct of arrays by way of typed arrays. Track B starts
again in a language where neither workaround is needed.

<Analogy title="a hotel versus a house of your own">
TypeScript is like staying in a hotel: the staff (the engine) clean your
room, decide where your luggage goes and tidy up after you leave, which
is lovely until you want the furniture somewhere else. Rust is like
owning the house: you decide where everything goes and nobody cleans up
after you; however, a strict inspector checks your plans before you
are allowed to move in, so the house never falls down.
<span slot="breaks">A real inspector checks a house once; the Rust
compiler checks your whole program every time you build it, and it
checks rules about memory, not about walls.</span>
</Analogy>

## What Rust is, and when it does its work

**Rust** is a language that is compiled ahead of time to machine code,
has no garbage collector, and still refuses to compile a program that
could read freed memory (outside code marked `unsafe`, which a later
chapter covers)<Cite id="klabnik2026" />. It manages that with a small
set of *ownership* rules, checked by the compiler, which are the heart
of this part of the book.

The biggest change from TypeScript is *when* the work happens. Step
through the same program going down both roads:

<BuildSteps client:visible />

V8 does a great deal while your program runs: it parses, interprets
bytecode with Ignition, watches for hot code and compiles
it<Cite id="v8-ignition" />. A Rust program did all of that before it
started, so all that is left at run time is your own code on the CPU.

<Analogy extra title="a banquet kitchen versus cooking to order">
A restaurant that cooks to order starts each dish when the ticket
arrives and gets faster at the popular ones as the night goes on; that is
V8, learning which functions are hot. A banquet kitchen preps and checks
every plate before the doors open, so service is only carrying plates
out; that is a Rust program.
<span slot="breaks">A banquet kitchen cannot change the menu once
guests arrive, and neither can Rust adapt its machine code to how the
program is used; V8 can, which is why a JIT sometimes wins.</span>
</Analogy>

<Callout kind="definition">
**Rust** is a compiled systems language. Its compiler, `rustc`, checks
types and memory-safety rules for the whole program, then produces
native machine code. The running program has no garbage collector and
no JIT: memory is freed at points the compiler works out in advance.
</Callout>

The costs are real, and you should hear them now. The compiler rejects
programs that TypeScript would happily run, and at first it will feel
like arguing with it; you wait for a full compile before every run; and
some designs that are easy with a collector (many objects all pointing
at each other) take more thought.

## Hello, Rust

Here is a complete Rust program:

```rust
fn main() {
    println!("Hello, Drip!");
}
```

Line 1 declares a function called `main` (`fn` is Rust's `function`),
which is where every Rust program starts; there is no top-level code as
in a JavaScript file. Line 2 prints a line of text, and plays the part of
`console.log`; the `!` marks `println!` as a **macro**, which is code
that writes code at compile time (a later chapter shows how), and every
statement ends with a semicolon. Inside the string, `{}` marks a gap
that `println!` fills with the next argument.

<Examples of="rust">

```rust
println!("{}", 2 + 3); // 5
```

```rust
let name = "drip";
let n = 35;
println!("{name}: fib({n})");
// drip: fib(35)
```

<Run id="hello" />

</Examples>

The first fills one gap with `2 + 3`, which is worked out before
printing, so it prints `5`. The second shows the other way to fill a
gap: a variable's name written inside the braces, `{name}`, prints that
variable (and `let` makes a variable, much like TypeScript's `const`,
which *Variables, types and mutability* explains). The runnable one mixes both
styles; change it and run it again.

Forget the `!` and the compiler tells you exactly that. Here is the
broken line and the fixed one, with rustc 1.97's real message (long
lines in this book are wrapped to fit your screen):

```rust
println("Hello, Drip!");  // broken
println!("Hello, Drip!"); // fixed
```

```text
error[E0423]: expected function, found
  macro `println`
2 |     println("Hello, Drip!");
  |     ^^^^^^^ not a function
help: use `!` to invoke the macro
```

Misspell `main` instead and the error says what is missing:
``error[E0601]: `main` function not found in crate``. Rust's messages
are long and specific, so read them to the end: the `help:` line often
holds the fix.

<OtherLanguages title="Hello, with a number in it">

```rust
fn main() {
    let n = 3;
    println!("n is {n}");
}
```

```ts
const n = 3;
console.log(`n is ${n}`);
```

```c
#include <stdio.h>
int main(void) {
    int n = 3;
    printf("n is %d\n", n);
    return 0;
}
```

```python
n = 3
print(f"n is {n}")
```

</OtherLanguages>

The real differences: TypeScript and Python run top-level code, while
Rust and C start in `main`; C must be told how to print each value
(`%d` for a whole number), while Rust's `{}` works it out from the type
at compile time and refuses to compile if a gap has no value; and only
Rust and C are compiled to machine code before they run.

<Prompts ids={['rs-main', 'rs-println-bang', 'rs-gap', 'rs-help-line']} />

<Callout kind="engine" label="Under the hood">
Viscosity rearranged arrays of objects into typed-array columns because
JavaScript hides layout. In Rust, a `Vec` of structs and a struct of
`Vec`s are both ordinary code you write, with no object headers in the
way, and the chapter *Struct of arrays in Rust by hand* builds one. The
Rust Drip VM goes further: its `src/lib.rs` starts with
`#![forbid(unsafe_code)]`, so the whole VM, collector included, is
checked by the compiler with no exceptions.
</Callout>

## What you learned

- **Rust** compiles to machine code ahead of time, with no garbage
  collector and no JIT, and the compiler checks memory safety before the
  program runs. The price is a stricter compiler and slower builds.
- In this book's run, the Rust port of the Drip VM was four to five
  times as fast as the TypeScript VM on most programs: one run, one
  port, one machine.
- Every program starts in `fn main()`; `println!` is a **macro**, and
  `{}` or `{name}` fills a gap in its text.

## One file is easy; a project is not

You can compile a single Rust file by hand, with `rustc main.rs`, and
get a program called `main` beside it. Nobody works that way for long,
however: a real project has dozens of files, uses libraries other people
wrote, has tests, and needs two kinds of build (a quick one while you
work and a fast one to ship). In TypeScript you juggle `npm`, `tsc` and a
test runner for that; in Rust one tool does all of it.

<Analogy title="a general contractor">
When you build an extension you do not phone the bricklayer, the
plumber and the electrician yourself; you hire a contractor who knows
which trade comes next and who orders the materials. **Cargo** is that
contractor: you say "build", and it fetches the libraries you named,
calls the compiler in the right order and puts the results in one place.
<span slot="breaks">A contractor makes judgement calls on site; cargo
does exactly what its manifest file says, the same way every time, and
the compiler, not cargo, is the one that checks your code.</span>
</Analogy>

## Four commands

Step through a whole first session, from an empty folder to an
optimised program. The output is real (cargo 1.97, folder paths
trimmed):

<CargoSteps client:visible />

`cargo new` made a manifest and one source file. The manifest,
`Cargo.toml`, plays the part of `package.json`: a name, a version, an
edition and a list of dependencies<Cite id="rust-book-hello-cargo" />.

```toml
[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]
time = "0.1.12"
```

The first section names the package; `edition` picks a version of the
language's rules (cargo 1.97 writes 2024 for a new project, and this
book's runnable examples use 2021; nothing in the next chapters differs
between the two). The `[dependencies]` line asks for a library called
`time` from **crates.io**, Rust's public registry (as npm packages come
from the npm registry). The version `"0.1.12"` means "0.1.12 or any later
0.1 release, but not 0.2", because cargo assumes a change in the left-most
non-zero number may break your code<Cite id="cargo-specifying-deps" />.

The everyday commands, in the order you will use them:

<Examples of="cargo">

```text
$ cargo check
    Checking hello v0.1.0
error[E0308]: mismatched types
 --> src/main.rs:1:26
  |
1 | fn main() { let x: i32 = "a"; }
  |                          ^^^ expected
  |                    `i32`, found `&str`
```

```text
$ cargo run
    Finished `dev` profile [...]
     Running `target/debug/hello`
Hello, world!
```

```text
$ cargo build --release
   Compiling hello v0.1.0
    Finished `release` profile [optimized]
```

</Examples>

The first is the command you will type most: `cargo check` runs every
check the compiler has but skips making a program, so it is the fast
one, like `tsc --noEmit`; here it caught a string where a number was
promised. The second builds a **debug** program into `target/debug/`
and runs it; the lines starting with capitals are cargo's, and `Hello,
world!` is the program's own. The third turns the optimiser on and
writes to `target/release/`<Cite id="rust-book-hello-cargo" />. (Two
more you will meet soon: `cargo test` runs the `#[test]` functions, and
`cargo fmt` lays your code out in the standard style.)

<Callout kind="pitfall">
Debug builds are for working and release builds are for measuring. The
two differ in more than speed: the debug profile turns off optimisation
and turns on checks such as integer overflow, which the release profile
turns off<Cite id="cargo-profiles" />. Every drip-rs number in the
previous chapter is a release number.
</Callout>

<Callout kind="definition">
**Cargo** is Rust's build tool and package manager. It reads the
manifest `Cargo.toml`, downloads the dependencies it lists (recording
their exact versions in `Cargo.lock`), runs `rustc`, and puts what it
builds under `target/`: `target/debug/` by default, `target/release/`
with `--release`.
</Callout>

## Crates: the pieces cargo builds

The compiler never looks at your whole project at once; it compiles one
**crate** at a time, starting from one file, the crate's **root**, and
following it to every file it names<Cite id="rust-book-packages-crates" />.
A crate comes in one of two kinds. A **binary crate** has a `main` and
becomes a program you can run. A **library crate** has no `main` and
becomes code that other crates use.

<Analogy extra title="a novel and a cookbook">
A novel is read from page one to the end, in order: it has a beginning,
like a binary crate's `main`. A cookbook has no beginning; you open it
at the recipe you need, the way other code calls the functions a library
crate offers. A **package** is the box set the publisher ships, with one
label on the box (one `Cargo.toml`).
<span slot="breaks">A box set may hold any number of novels and
cookbooks; a package may hold many binary crates but at most one library
crate.</span>
</Analogy>

The Rust Drip VM is a good example. Its `Cargo.toml` declares both kinds
in one package:

<Figure takeaway="One package can hold a library that does the work and a small program that uses it." caption="The drip-rs package in companion/rust. The binary crate is a short main that reads a file and calls the library; the integration tests are crates of their own that use the library too.">
  <CrateMap />
</Figure>

<Examples of="crate">

```rust
// src/main.rs: a binary crate
fn main() {
    println!("Hello, world!");
}
```

```rust
// src/lib.rs: a library crate
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}
```

```toml
# companion/rust/Cargo.toml
[lib]
name = "drip"
path = "src/lib.rs"

[[bin]]
name = "drip-rs"
path = "src/main.rs"
```

</Examples>

The first is the file `cargo new` writes: its root is `src/main.rs`, it
has a `main`, so it is a binary crate. The second is what `cargo new
--lib` writes instead (trimmed): no `main`, and `pub` (short for
*public*) lets other crates call `add`, like `export` in TypeScript. The
third is real: drip-rs names its library crate `drip`, holding the
scanner, compiler, VM and collector, and its binary crate `drip-rs`,
whose `main` reads a Drip file and hands it to the library.

Here is the mistake to expect, side by side with its fix:

```text
$ cargo new --lib mylib && cd mylib
$ cargo run
error: a bin target must be available
for `cargo run`
$ cargo test
test tests::it_works ... ok
```

A library has nothing to run, so `cargo run` refuses (the message says
there is no binary, which cargo calls a "bin target"); you exercise a
library through its tests, or from a binary crate that uses it.

<OtherLanguages title="Using a function from a library">

```rust
use drip::run;
// run(source, options) from the
// library crate `drip`
```

```ts
import { run } from 'drip';
// a function from an npm package
```

```python
from drip import run
# a function from a Python package
```

```c
#include "drip.h"
/* declares run(); the library is
   linked in by the build */
```

</OtherLanguages>

All four reach into a library by name. The genuine differences: in Rust
and TypeScript the library says which names are public (`pub`,
`export`), while Python lets you import almost anything; and in C the
header only *declares* the function, so the build has to link the
library's machine code in separately, which cargo does for you.

<Callout kind="definition">
A **crate** is the unit `rustc` compiles in one go, starting from its
root file. A **binary crate** has a `main` and becomes a program; a
**library crate** has no `main`, and other crates use its public items.
A **package** is one `Cargo.toml` with the crates it holds: any number
of binaries and at most one library<Cite id="rust-book-packages-crates" />.
</Callout>

## What you learned

- **Cargo** creates projects (`cargo new`), checks them quickly
  (`cargo check`), builds and runs them (`cargo build`, `cargo run`) and
  makes optimised builds (`--release`) in `target/release/`.
- `Cargo.toml` is the manifest; `[dependencies]` names libraries from
  crates.io, and `Cargo.lock` records their exact versions.
- A **crate** is one compilation unit: a binary (with `main`) or a
  library (without). A package holds at most one library and any number
  of binaries.
