## Two garbage collectors deep

In *Reclaiming memory: mark and sweep* you wrote a collector for the
Drip VM, although V8 already has one<Cite id="v8-trash-talk" />, because
only the VM knows which Drip objects are still reachable; two collectors
ended up stacked on top of each other. Viscosity, likewise, exists
because JavaScript gives you no say over memory layout (objects carry
hidden headers, and the engine decides where fields live). This part
starts again in a language where neither workaround is needed.

<Analogy title="a hotel versus a house of your own">
TypeScript is like staying in a hotel: the staff (the engine) clean your
room, decide where your luggage goes and tidy up after you leave, which
is lovely until you want the furniture somewhere else. Rust is like
owning the house: you decide where everything goes and nobody cleans up
after you; however, a strict inspector checks your plans before you
are allowed to move in, so the house never falls down.
<span slot="breaks">A real inspector checks a house once; the Rust
compiler checks your whole program every time you build it, and it
checks rules about memory, not about walls.</span>
</Analogy>

## What Rust is, and when it does its work

**Rust** is compiled ahead of time to machine code, has no garbage
collector, and still refuses to compile a program that could read freed
memory (outside code marked `unsafe`, which *unsafe and raw pointers*
covers)<Cite id="klabnik2026" />. It manages that with a small set of
*ownership* rules, checked by the compiler, which are the heart of this
part. The biggest change from TypeScript is *when* the work happens, so
step through the same program going down both roads:

<BuildSteps client:visible />

V8 parses, interprets with Ignition and compiles hot code while your
program runs<Cite id="v8-ignition" />; a Rust program did all of that
before it started.

<Callout kind="definition">
**Rust** is a compiled systems language. Its compiler, `rustc`, checks
types and memory-safety rules for the whole program, then produces
native machine code. The running program has no garbage collector and
no JIT: memory is freed at points the compiler works out in advance.
</Callout>

The costs are real: the compiler rejects programs TypeScript would run,
you wait for a compile before every run, and designs that are easy with
a collector (many objects pointing at each other) take more thought.

Every program starts in `fn main()` (`fn` is Rust's `function`); there is
no top-level code as in a JavaScript file. `let` makes a variable, much
like `const`. `println!` plays the part of `console.log`, and the `!`
marks it as a **macro**, code that writes code at compile time; its `{}`
is filled by the next argument and `{n}` by the variable `n`, so this
prints `fib(35) is slow` and `35 again`. Forget the `!` and rustc 1.97
stops with ``error[E0423]: expected function, found macro `println` ``,
and its `help:` line holds the fix: ``use `!` to invoke the macro``.

## Cargo, the contractor

A real project has many files, libraries, tests and two kinds of
build; in TypeScript you juggle `npm`, `tsc` and a test runner for that,
and in Rust one tool, **cargo**, does it all. Step through a first
session, from an empty folder to an optimised program (real output from
cargo 1.97, paths trimmed):

<CargoSteps client:visible />

`cargo new` made a manifest, `Cargo.toml`, which plays the part of
`package.json`<Cite id="rust-book-hello-cargo" />, and one source file,
`src/main.rs`:

<Examples of="cargo">

```toml
[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]
time = "0.1.12"
```

```text
$ cargo check
    Checking hello v0.1.0
error[E0308]: mismatched types
 --> src/main.rs:1:26
  |
1 | fn main() { let x: i32 = "a"; }
  |                          ^^^ expected
  |                    `i32`, found `&str`
```

</Examples>

`edition` picks a version of the language's rules (cargo 1.97 writes
2024; the runnable examples here use 2021, and nothing in this part
differs). The dependency asks for `time` from **crates.io**, Rust's
registry; `"0.1.12"` means "0.1.12 or any later 0.1 release, but not
0.2", since cargo assumes a change in the left-most non-zero number may
break you<Cite id="cargo-specifying-deps" />. `cargo check` runs every
check but makes no program (like `tsc --noEmit`), so it is the command
you will type most; `cargo run` builds a **debug** program in
`target/debug/` and runs it, and `cargo build --release` turns the
optimiser on and writes to `target/release/`.

<Callout kind="pitfall">
Debug builds are for working, release builds for measuring: the debug
profile turns off optimisation and turns on checks such as integer
overflow, which release turns off<Cite id="cargo-profiles" />.
</Callout>

<Callout kind="definition">
**Cargo** is Rust's build tool and package manager. It reads the
manifest `Cargo.toml`, downloads the dependencies it lists (recording
their exact versions in `Cargo.lock`), runs `rustc`, and puts what it
builds under `target/`: `target/debug/` by default, `target/release/`
with `--release`.
</Callout>

<Prompts ids={['cargo-check', 'cargo-release']} />

<Analogy extra title="a general contractor">
When you build an extension you do not phone the bricklayer, the
plumber and the electrician yourself; you hire a contractor who knows
which trade comes next and orders the materials. Cargo is that
contractor: you say "build", and it fetches the libraries you named,
calls the compiler in the right order and puts the results in one place.
<span slot="breaks">A contractor makes judgement calls on site; cargo
does exactly what its manifest says, the same way every time, and the
compiler, not cargo, is the one that checks your code.</span>
</Analogy>

## Crates: the pieces cargo builds

The compiler never looks at your whole project at once; it compiles one
**crate** at a time, starting from the crate's **root** file and
following it to every file it names<Cite id="rust-book-packages-crates" />.
A **binary crate** has a `main` and becomes a program; a **library
crate** has no `main` and becomes code other crates use. drip-rs has
both in one package:

<Figure takeaway="One package can hold a library that does the work and a small program that uses it." caption="The drip-rs package in companion/rust. The binary crate is a short main that reads a file and calls the library; the integration tests are crates of their own that use the library too.">
  <CrateMap />
</Figure>

<Examples of="crate">

```toml
# companion/rust/Cargo.toml (trimmed)
[lib]
name = "drip"
path = "src/lib.rs"

[[bin]]
name = "drip-rs"
path = "src/main.rs"
```

</Examples>

The library crate `drip` holds the scanner, compiler, VM and collector
(items marked `pub` are callable from other crates, like `export`); the
binary crate `drip-rs` is a `main` that reads a file and calls it. A
library has nothing to run, so after `cargo new --lib`, `cargo run`
refuses with
``error: a bin target must be available for `cargo run` ``; you exercise
a library through its tests, with `cargo test`.

<Callout kind="definition">
A **crate** is the unit `rustc` compiles in one go, starting from its
root file. A **binary crate** has a `main` and becomes a program; a
**library crate** has no `main`, and other crates use its public items.
A **package** is one `Cargo.toml` with the crates it holds: any number
of binaries and at most one library<Cite id="rust-book-packages-crates" />.
</Callout>

<Prompts ids={['crate-kinds']} />

<More title="More: hello in four languages, and a library crate">

```rust
// src/lib.rs, as `cargo new --lib`
// writes it (trimmed)
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}
```

That is a whole library crate: no `main`, and one public function.
Compare printing a number in four languages:

```c
#include <stdio.h>
int main(void) {
    int n = 3;
    printf("n is %d\n", n);
    return 0;
}
```

TypeScript and Python run top-level code, while Rust and C start in
`main`; C must be told how to print each value (`%d`), while Rust's `{}`
works it out from the type at compile time and refuses to compile if a
gap has no value. Misspell `main` and rustc says
``error[E0601]: `main` function not found in crate``.

</More>

<Analogy extra title="a banquet kitchen versus cooking to order">
A restaurant that cooks to order starts each dish when the ticket
arrives and gets faster at the popular ones as the night goes on; that is
V8, learning which functions are hot. A banquet kitchen preps and checks
every plate before the doors open, so service is only carrying plates
out; that is a Rust program.
<span slot="breaks">A banquet kitchen cannot change the menu once
guests arrive, and neither can Rust adapt its machine code to how the
program is used; V8 can, which is why a JIT sometimes wins.</span>
</Analogy>
