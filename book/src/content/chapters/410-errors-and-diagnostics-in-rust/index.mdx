## Five lines on stderr

```drip
class Oven {
  bake(n) { return self.heat(n); }
  heat(n) { return n * none; }
}
fn go() {
  return new Oven().bake(3);
}
go();
```

The script calls `go`, which calls `bake`, which calls `heat`, which
multiplies a number by `none`. drip-rs prints nothing on stdout, exits
with 70, and prints this on stderr:

```text
runtime error: cannot use '*' on a number
  and none
  at line 3 in fn heat
  at line 2 in fn bake
  at line 6 in fn go
  at line 8 in script
```

(The first line is wrapped for the page.) The message says what went
wrong, in Drip's own words; the `at` lines say where,
innermost call first: the multiply on line 3 inside `heat`, which was
called from line 2 inside `bake`, called from line 6 inside `go`,
called from line 8 of the script. That list is a **stack trace**, and
the TypeScript VM prints exactly the same bytes (so does the
tree-walker, from Part III). The question for a VM is how it still knows
lines 6 and 2, long after it ran those calls.

<Analogy title="sticky notes on a desk">
Writing a report, you need a number, so you stick a note on the desk,
"report, page 6", and open a spreadsheet; there you need a date, so a
second note goes on top, "spreadsheet, row 2", and you open the

notes from the top down.
<span slot="breaks">Your notes say where you *left*; for the task you
are doing right now there is no note yet, so you have to remember it

</Analogy>

<Analogy extra title="a parcel's tracking history">
A parcel's tracking page lists every depot it passed through, latest

<span slot="breaks">A parcel's history is kept forever; a VM's call

</Analogy>

## The trace, frame by frame

Every running call has a `CallFrame` (from *Functions and call frames in
Rust*) holding its closure, its chunk, its `ip` and its stack base, and
each chunk has a `lines` array with the source line of every byte. The
part of `Vm::runtime_error` that builds the trace, from `vm.rs`
(rewrapped):

```rust
let top = self.frames.len()
    .saturating_sub(1);
for (depth, frame) in
    self.frames.iter().enumerate().rev()
{
    let ip = if depth == top {
        self.ip
    } else {
        frame.ip
    };
    // `ip` is already past the failing
    // instruction.
    let line = frame.chunk.lines[ip - 1];
    // ...work out `place`: "fn heat",
    // "anonymous fn" or "script"...
    self.stderr.push(format!(
        "  at line {line} in {place}"));
}
```

`.rev()` walks the frames from the innermost out. For each one, `ip` is
the index of the *next* byte to run, so the byte that failed (or the
call that is still waiting) is at `ip - 1`, and `lines[ip - 1]` is its
source line. The one subtle line is the `if`: drip-rs keeps the running
frame's `ip` in a field of the `Vm` itself, `self.ip`, like a CPU
register (from *The VM loop in Rust*), and writes it back into the
frame only when that frame makes a call. So every outer frame's saved
`ip` is right, pointing just past its call, while the innermost frame's
copy is stale; the register is the truth for that one. `place` comes
from a `match` on the function's name: `Some(name)` gives `fn heat`, and
`None` gives `script` or `anonymous fn`, using a guard,
`None if function.is_script`.

<ErrorSteps client:visible />

Here is the spot the difference. In a scratch copy of drip-rs I changed
that `if` to plain `let ip = frame.ip;`, built it in debug mode, and ran
the oven program; it crashed instead of reporting (exit code 101, and
the path trimmed):

```text
thread 'main' panicked at
  src/vm.rs:270:42:
attempt to subtract with overflow
```

`heat` has made no calls, so its saved `ip` is still the 0 it started
with, and `0 - 1` on a `usize` overflows: a debug build checks that and
panics. (A release build would wrap round instead, and then the
indexing would panic.) With a stale but non-zero `ip`, it would quietly
print the wrong line, which is worse.

<Callout kind="definition">
A **stack trace** lists the calls that are running when an error
happens, innermost first, each with the line it was on. In drip-rs,
`runtime_error` writes the message, then one `at line N in place` line
per `CallFrame`: the innermost frame's line comes from the `ip`
register, every other frame's from the `ip` it saved when it made its
call, and each is `chunk.lines[ip - 1]`, because `ip` is already past
the instruction.
</Callout>

<Formal title="Which ip each frame uses">

```text
ipᵢ = self.ip     if i = top
ipᵢ = frameᵢ.ip   otherwise
lineᵢ = frameᵢ.chunk.lines[ipᵢ − 1]
```

<span slot="read">For frame number i, the ip to use is the register if
i is the top frame and the frame's own saved ip otherwise; its line is
the entry just before that ip in the frame's lines array.</span>
</Formal>

fn f(n) {

The first has no calls at all, so the trace is one line, the script's,
taken from the register. The second recurses until the 256-frame limit
(DRIP.md's rule, `FRAMES_MAX` in `vm.rs`): `call` refuses the next frame
with `stack overflow`, and the trace has 256 `at` lines, 255 for `f`,
all on line 2, and one for the script. The third, which you can run,
passes a named function into an anonymous one and prints `4`; remove
the `#` on its last line and it fails inside `half` with `cannot use
'/' on a string and a number`, and the trace reads `fn half`, then
`anonymous fn`, then `script`.

## Carrying the error out

A runtime error has to stop the program from deep inside the loop. The
TypeScript VM throws an exception: its `runtimeError` has the return
type `never` and ends with `throw`, and `interpret` catches it. drip-rs
has no exceptions; instead the error is a value, and from *Option and
Result* you know the shape:

```rust
pub struct RuntimeError;

type Run<T = ()> = Result<T, RuntimeError>;
```

`RuntimeError` is a **unit struct** (it carries nothing, because the
message and trace are already in `self.stderr` by the time one exists),
and every function that can fail returns `Run`, so an arm such as
`OpCode::Mul` writes `let (a, b) = self.pop_numbers("*")?;` and the `?`
returns the `Err` from `run` at once, up to `interpret`. There, a
`match` turns `Err(RuntimeError)` into exit code 70 after clearing the
stack, the frames, the chunk register and the open upvalues; the globals
stay, so the same `Vm` can run another program, as a REPL would.

<TwoPaths />

Compile errors take the other path in the diagram. The compiler pushes
each one as a `String` and carries on: syntax errors go into
`syntax_errors` through `error_at`, which in **panic mode** drops any
more until the parser reaches the next statement (from *A Pratt compiler
in Rust, part 2*); broken static rules go into `static_errors`. At the
end, `compile` reports the syntax errors if there are any and the static
ones only otherwise, as the TypeScript compiler does, so

```drip
let x = 1;
fn f() {
  break;
}
let z = ;
```

reports only `line 5: expected an expression, found ';'`, and exits
with 65; fix line 5 and the next run reports `line 3: 'break' outside a
loop`. Finally `main.rs` prints the lines and returns
`ExitCode::from(outcome.exit_code as u8)`<Cite id="rust-std-exitcode" />;
the `as u8` keeps the low byte of the `i32`<Cite id="rustref-numeric-cast" />,
which is the whole value for 0, 65 and 70.

## What you learned

- A **stack trace** is the message, then one `at` line per running
  call, innermost first.
- The innermost frame's line comes from the **`ip` register**; the
  others from the `ip` they **saved** when they called. Each line is
  `lines[ip - 1]`.
- A runtime error is a **value**: the unit struct `RuntimeError`,
  carried out of `run` by **`?`**, where the TypeScript VM throws.
- Compile errors collect in two `Vec`s; **static errors are reported
  only when there are no syntax errors**. Exit codes are 65 and 70.
