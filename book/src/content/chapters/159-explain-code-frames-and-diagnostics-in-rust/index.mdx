## Every decision, with a reason

*viscosity explain* promised a reason for every decision, and the Rust
engine has to keep that promise in exactly the same words, because the
parity test compares the two reports byte for byte. Here is a small
program, indented with tabs:

```js
const ps = [];
for (let i = 0; i < 99; i++)
	ps.push({ x: i });
const keep = [];
for (let i = 0; i < 99; i++) {
	if (ps[i].x > 3)
		keep.push(ps[i]);
}
const t = "🎉"; f(t, ps[2]);
function f() {}
```

and the Rust CLI's report on it (release build, rustc 1.97; long lines
wrapped):

```
ps (line 1) {x} → kept as array of objects
  · unsafe: line 7: an element is used by
    push
  · unsafe: line 9: an element is passed
    to a function call
keep (line 4) {} → kept as array of objects
  · unsafe: line 7: pushes something that
    is not a fresh object literal
```

The TypeScript CLI printed the same bytes.

<Analogy title="a referee's match report">
After a match the referee writes one line per team and, under it, a line
for each decision: the minute, the player, the reason. Nothing is left
out, and the wording follows a fixed form, so that anyone reading two
reports can compare them line by line.
<span slot="breaks">A referee writes from memory and may phrase things
freely; the report here is generated from the plan, in a fixed order,
and two engines must produce the same characters, down to the middle
dot.</span>
</Analogy>

<Analogy extra title="a finger on the page">
A note in the margin says "see line 7". A friend leaning over says "this
one, here", with a finger on the word. The report already had the margin
notes; frames add the finger.
<span slot="breaks">A finger is placed by someone who sees the page; the
carets are placed by counting characters, and a count can be wrong where
the page is drawn differently from how it is counted (an emoji drawn two
columns wide).</span>
</Analogy>

## One function, two outputs

In `crates/core/src/plan.rs`, `explain(p)` and `explain_with_frames(p,
source)` both call one private function, passing `None` or
`Some(source)`. Its body, rewrapped:

```rust
// fn explain_text(p: &Plan,
//     frames: Option<&str>) -> String
let mut lines = Vec::new();
for cp in &p.collections {
    let c = &cp.collection;
    let verdict = match cp.layout { … };
    lines.push(format!(
        "{} (line {}) {{{}}} → {verdict}",
        c.name, c.line,
        c.fields.join(", ")));
    let refused = !c.bailouts.is_empty()
        && cp.reasons.len()
            == c.bailouts.len();
    for (k, r) in cp.reasons.iter()
        .enumerate() {
        lines.push(format!("  · {r}"));
        let at = if refused {
            c.bailout_sites
                .get(&c.bailouts[k])
                .copied().flatten()
        } else { None };
        if let Some((src, at)) =
            frames.zip(at) {
            lines.push(code_frame(
                src, at, "    "));
        }
    }
}
lines.join("\n")
```

The verdict is a `match` on the layout, and `{{` and `}}` are literal
braces, so the header shows `{x}`. `refused` asks whether the collection was kept with
exactly one reason per bailout, which is what the safety rung of *The
cost model and thresholds in Rust* produces; only then is reason `k`
about bailout `k`. `Option::zip` gives `Some((src, at))` only when both
are `Some`: a source to quote and a place for this reason.

## Where a refusal happened

The places come from the analysis, where every bailout goes through one
small method on `Collection` (from `crates/core/src/analysis.rs`):

```rust
fn bail(&mut self, msg: String,
    at: Option<SourceRef>) {
    self.bailout_sites
        .entry(msg.clone())
        .or_insert(at);
    self.bailouts.push(msg);
}
```

`bailout_sites` is an `IndexMap` keyed by message, and
`entry(...).or_insert(at)` writes only when the key is new, so the
*first* place a message was found wins (`at` is `None` for bailouts with
no single place). The messages are later deduplicated, first of each
kept, so reason `k` finds its site by its message.

<Figure caption="Reason k of a refused collection is bailout k, and the bailout's message is the key to the place it was first found." takeaway="Matching positions, then a lookup by message, connect a reason to its source.">
  <SitesMap />
</Figure>

The site is a `SourceRef`: a start and an end (a **span**) and a line,
made once, when oxc's syntax node is lowered to a VIR instruction, so the
"line 7" in a reason and the frame under it cannot disagree.

<Callout kind="definition">
**explain in Rust** is `explain_text(p, None)`: per collection, in plan
order, a **header** (`name (line n) {fields} → verdict`) and one **`  · `**
line per reason. **`Collection::bail`** records each bailout's first
**site**, and `explain_with_frames` draws it under the matching
reason.
</Callout>

## What a diagnostic has

With `--frames`, the first refusal gets the line `7 | keep.push(ps[i]);`
and five carets under `ps[i]`. rustc's developer guide lists the parts
of an error message<Cite id="rustc-dev-guide-diagnostics" />: a
**level** such as `error`; an optional **code** such as `E0308`; a
**message** that makes sense on its own; and a window onto the code,
with the file, line and column where the **primary span** begins, the
code itself, and **labels** under the spans.

<Figure caption="Top: rustc 1.97 on a line that gives a string to an i32 (trimmed). Bottom: the Rust Viscosity CLI with --frames." takeaway="Viscosity’s frames have a message, a line, the code and a span; no level, code, file name or column.">
  <DiagnosticParts />
</Figure>

Viscosity's frame has the message, the line, the code and the carets,
but no level (a refusal to optimise is not an error), no code, no file
name and no column.

<Callout kind="definition">
A **diagnostic** is a compiler message tied to the source: a **message**
that makes sense on its own, plus a **span**, the stretch of source it is
about. A message without a span is only an error message.
</Callout>

<Examples of="diagnostic">

```
    5 | for (const p of ps) keep.push(p);
      | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

```
viscosity: Unexpected token (1:12)
```

</Examples>

The first is a refusal in a `for...of` loop: the element `p` was made by
the statement itself, so its `SourceRef` is the whole statement, and both
engines underline the whole line; correct, and nearly useless, since a
frame is only as good as its span. The second is the Rust CLI on `const
ps = [;`: a message and a position (line 1, column 12 from 0), but no
picture of the code.

## Bytes, units and code points

A Rust `SourceRef` holds UTF-8 byte offsets, since oxc's spans are
bytes; the TypeScript one holds UTF-16 offsets, since JavaScript strings
are indexed in 16-bit units (`🎉` is four bytes, two units, and one
character to you). So `ps` on line 9 starts at different offsets in the
two engines:

<Figure caption="Where ps starts on line 9 of the program, counted three ways." takeaway="Each engine slices in its own units and counts columns in a shared one.">

</Figure>

`code_frame` in `plan.rs` counts the characters before the span with
`chars()`, the TypeScript one with `Array.from`; both get 20. Each engine slices in
its own units and counts the column in a shared one. The pad before the
carets turns every character but a tab into a space, so the carets line
up however wide a tab is drawn. Step through it on line 7:

<More title="code_frame, line by line">
From `plan.rs`, rewrapped, with the last few lines (the line number, the
gutter and the final `format!`) left out:

```rust
let start = (at.start as usize)
    .min(source.len());
let s = source[..start]
    .rfind(is_line_break)
    .map_or(0, |i| i + source[i..]
        .chars().next()
        .map_or(1, char::len_utf8));
let e = source[start..]
    .find(is_line_break)
    .map_or(source.len(), |i| start + i);
let text = source[s..e]
    .trim_end_matches([' ', '\t']);
let before = &source[s..start];
let col = before.chars().count();
let end = (at.end as usize)
    .max(start).min(e);
let up_to =
    source[s..end].chars().count();
let width = up_to
    .min(text.chars().count())
    .saturating_sub(col)
    .max(1);
let pad: String = before.chars()
    .map(|c| if c == '\t' { '\t' }
        else { ' ' })
    .collect();
```

`s` is where the span's line starts: the last line break before `start`,
plus that break's length in bytes (U+2028 is three bytes, so
`char::len_utf8` is used instead of `+ 1`). `e` is where the line ends.
`is_line_break` is true for `\n`, `\r`, U+2028 and U+2029, the breaks
acorn counts lines by. A span across lines gets carets to the end of its
first line (`min(e)`), the width never runs past the trimmed text, and
`saturating_sub` and `max(1)` give an empty span one caret.

`scripts/gen_expected.mjs` writes a `.frames.txt` fixture for 14
programs with the TypeScript engine, and the parity test checks the Rust
output against every one; all 14 matched when I ran them. One,
`tests/extra/frames_columns.js`, was written to break exactly this: tabs,
accented letters and an emoji before a span, a CRLF line end, a U+2028
inside a line, and an element written across two lines.

One thing both engines still get wrong: a code point is not a screen
column. Many fonts draw an emoji two columns wide, so on line 9 the
carets start one column early wherever `🎉` is drawn double; getting it
right would need a table of character widths, which neither engine has.

<More title="Lines and columns for syntax errors">
A syntax error prints a column, and there the unit matters. For the
one-line file `const s = "🎉"; [;`, both CLIs print `viscosity:
Unexpected token (1:17)`. Count the characters before the last `;` and
you get 16; oxc's span says 19 (bytes); acorn, the parser behind the

CLI prints.

The JavaScript plugin records where every line starts, once per file, in
`LineIndex` (`crates/frontend-js/src/lines.rs`), counting the breaks
ECMAScript counts: `\n`, `\r\n` as one break, a lone `\r`, and U+2028
and U+2029.

<Figure caption="Five lines, separated by the four kinds of break JavaScript counts. The ; on line 5 is the error." takeaway="\r\n is one break; a lone \r, U+2028 and U+2029 are breaks too.">
  <LineBreaks />

```rust
pub fn line(&self, offset: u32) -> u32 {
    self.starts
        .partition_point(|&s| s <= offset)
        as u32
}
```

`partition_point` binary-searches the sorted line starts for how many
are at or before the offset, which is the 1-based line; `line_column`
adds the column as `encode_utf16().count()` of the slice from the line's
start. When the Rust chapters were first written, the port printed
`viscosity: SyntaxError: Unexpected token` with no position, because
`OxcDiagnostic`'s `Display` prints only its message, and the span lives
in its **labels**. Today `syntax_error` in
`crates/frontend-js/src/lib.rs` takes the first label's offset, turns it
into acorn's line and column with `LineIndex`, and appends `(line:col)`.

<Formal title="acorn’s column">

```text
col(p) = Σ { u16(c) : c on p's line,
                      before p }
u16(c) = 1 if c < U+10000, else 2
```

<span slot="read">The column of position p is the sum of u16 of c, over
every character c that comes before p on p's line. u16 of a character is
1 if its code point is below hexadecimal 10000, and 2 otherwise, because
UTF-16 needs a surrogate pair for it.</span>
</Formal>

The deep dive *Strings and Unicode* covers the encodings themselves.
</More>

## What you learned

- **`explain_text(p, frames)`** writes a **header** per collection and a
  **reason line** per reason, with a frame when `frames.zip(at)` is `Some`.
- `Collection::bail` keeps each message's **first site**.
- A **diagnostic** is a message plus a **span**, and a frame is only as
  precise as its span.
- Rust slices in **bytes**, TypeScript in **UTF-16 units**; both count
  columns in **code points**.
