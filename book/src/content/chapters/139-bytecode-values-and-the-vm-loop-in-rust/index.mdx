## Fifty-three numbers

The instruction set of *Bytecode as data, and a disassembler* is an
object of numbers in `chunk.ts`, `Op.Const` 0 up to `Op.Method` 52, plus
a table of names built from its keys: three things to keep in step by
hand. The stack machine of *A stack machine and its dispatch loop* is not
new here; what is new is how much of that bookkeeping Rust's types take
over.

<Analogy title="a café menu with numbered dishes">
The kitchen hears "number 20" and knows it means the toastie, because the
menu says so. Rust lets you print the menu once, as a type, and the
numbers come from where each dish sits on it: nobody types the 20.
<span slot="breaks">A café can renumber its menu on Monday and the regulars
adapt; renumbering the opcodes would make every chunk compiled before the
change mean something different, which is why both VMs keep the same
order.</span>
</Analogy>

<Analogy extra title="the buttons in a lift">
A lift in a ten-storey building has a button for every floor, and pressing
one is always safe. Ask the lift to go to "floor 54" by some other means,
though, and it has to check: there is no such floor. Encoding an opcode is
pressing a button; decoding a byte is the lift receiving a number it must
check.
<span slot="breaks">A lift with a bad request simply stays put; drip-rs
gets an `Option` back and decides for itself what a bad byte means (the
VM treats it as a bug and stops loudly).</span>
</Analogy>

## OpCode

drip-rs's `chunk.rs` (trimmed and rewrapped; `ALL` and `from_byte`
live in `impl OpCode`):

```rust
#[repr(u8)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum OpCode {
    Const,
    // ... 52 more, ending with Method
}
const ALL: [OpCode; 53] = [/* ... */];

pub fn from_byte(byte: u8)
    -> Option<OpCode> {
    OpCode::ALL.get(byte as usize).copied()
}
```

Variants are numbered from 0 in the order written<Cite id="rustref-enum" />,
following the TypeScript table, so both VMs write the same bytes.
`#[repr(u8)]` gives a data-less enum the size and alignment of a
`u8`<Cite id="rustref-type-layout" />, so encoding is a cast:
`self.emit(op as u8);`.

Decoding is the interesting half. `byte as OpCode` does not compile
(rustc 1.97: `error[E0605]: non-primitive cast: u8 as OpCode`), and could
not be right anyway, because most bytes are not opcodes:

<Figure takeaway="Only 53 of a byte's 256 values are opcodes." caption="Each variant casts to its byte with as u8. Going back, from_byte gives Some for 0 to 52 and None for everything else, and Option<OpCode> is still one byte.">
  <ByteSpace />
</Figure>

Reinterpreting the byte would need `unsafe`, which
`#![forbid(unsafe_code)]` rules out, so drip-rs indexes the table `ALL`;
a unit test checks `ALL[op as usize] == op` for every opcode, and the
disassembler's names come from the derived `Debug` text
(`JumpUnlessKeep` prints as `jump.unless.keep`).

<Callout kind="definition">
An **opcode enum** is an enum with one variant per instruction, none of
them carrying data, marked **`#[repr(u8)]`** so each value is stored as,
and casts with **`as u8`** to, the byte that encodes it. Variant order
fixes the numbering. Decoding goes the other way through a table, and
gives an `Option`.
</Callout>

<Examples of="opcode-enum">

```rust
OpCode::Add as u8      // 20
OpCode::from_byte(20)  // Some(Add)
OpCode::from_byte(53)  // None
// error[E0605]: non-primitive cast
let op = byte as OpCode;
```

</Examples>

`Add` is the twenty-first variant, so its byte is 20. Decoding a byte
past the last opcode is an ordinary `None`, not a crash; the last line is
the cast everyone tries first.

<More title="The chunk and the disassembler">

`Chunk` is the three arrays of *Bytecode as data, and a disassembler*,
typed: `code: Vec<u8>`, `lines: Vec<usize>` and `constants: Vec<Value>`.
Because `code` holds real bytes, `chunk.write(300, 1)` does not compile
("literal out of range for `u8`") rather than being a bug found later.
`debug.rs` prints the same text as `debug.ts`, column for column; step
through it:

It takes one extra parameter, `heap: &Heap`, because a string constant
is a handle, so printing `'hi'` means asking the heap for the text.
`padStart` becomes a format spec such as `{offset:04}`, and a `loop`'s
target is `offset + 3 - jump` because a `usize` cannot be negative.
To check the two disassemblers agree, I compiled each of the 344 corpus

## A value is a Copy enum of handles

In *Tagging values at run time* the TypeScript value type is
`null | boolean | number | Obj`, because JavaScript tags every value
behind the scenes. Rust keeps no hidden tags, so `value.rs` writes them
into an enum:

```rust
#[derive(Clone, Copy, Debug, PartialEq)]
pub enum Value {
    None,
    Bool(bool),
    Number(f64),
    String(StrRef),
    List(Gc<ObjList>),
    // ... six more Gc<..> variants
}
```

The objects are not inside: a `Gc<T>` is a typed `u32` index into the
heap's arena (*Arenas and typed indices*), and a `StrRef` is a string's
handle plus its hash. Ownership forced that: a `String(String)` variant
would make a `Value` own its text, and a string copied from a global
onto the stack would need two owners.

<Figure takeaway="Handles let many values share one object." caption="Left: two Values hold the same StrRef, so copying one copies 16 bytes and the text lives once in the heap. Right: if a Value owned its String, each copy would need its own clone of the text.">
  <HandlesShare />
</Figure>

A handle owns nothing, so `Value` derives `Copy`, and `push` and `pop`
copy 16 bytes (rustc 1.97, x86-64): an 8-byte payload, a tag, and
padding, since an `f64` must sit at a multiple of 8 and a size is a
multiple of the alignment<Cite id="rustref-type-layout" />:

<ValueLayoutSteps client:visible />

<Callout kind="definition">
A **value enum** gives a dynamically typed language's values a Rust type:
one variant per kind of value. Small values (none, booleans, numbers) are
stored right in the variant, and heap objects as handles. If every
payload is `Copy`, the enum can be `Copy`, so values move around the VM
without being moved or cloned.
</Callout>

<Formal title="The size of an enum">

```text
size = round_up(tag + largest payload,
                largest alignment)
     = round_up(1 + 8, 8) = 16
```

<span slot="read">An enum needs room for its tag and for its biggest
payload, rounded up to a multiple of the strictest alignment among its
payloads. For Value that is one byte of tag plus eight bytes of number,
nine, rounded up to the next multiple of eight, which is sixteen. This
is the layout rustc chose, read from its -Zprint-type-sizes report; the
Rust Reference leaves enum layout to the compiler<Cite id="rustref-enum" />.</span>
</Formal>

<Examples of="value-enum">

```rust
let a = Value::Number(3.0);
let b = a; // a copy: `a` still usable
assert!(a == b);

// does not compile:
#[derive(Clone, Copy)]
enum V { None, Str(String) }
// error[E0204]: the trait `Copy`
//   cannot be implemented for this type
```

</Examples>

`let b = a;` copies rather than moves (*Ownership: moves, copies and
clones*). The second half is the design ownership rules out: rustc
points at the `String` field, `this field does not implement Copy`.

<More title="Equality, printing, and numbers that print like JavaScript">

`derive(PartialEq)` gives exactly Drip's `==`: numbers compare as IEEE
doubles (`nan` is not equal to itself, `0` equals `-0`), handles compare
by index, which is right for strings too because they are interned
(*String interning and globals by name*), and values of different kinds
are never equal. `Option<Value>` is 16 bytes as well, because `None` is
stored as a tag value no variant uses; the hash inside `StrRef` rides in
bytes that `Number` needs anyway. NaN-boxing would halve a value to 8
bytes, and safe Rust could do it with `f64::to_bits`, but every read
would then need masks and shifts rather than a `match`; drip-rs keeps the
plain enum by choice (the deep dive *NaN-boxing and write
barriers in practice* goes further).

Printing is where handles cost something: the text of a string is in the
heap, so `value.format(&heap)` takes the heap. And Drip prints numbers
as JavaScript's `String(n)` does, which Rust's `{}` does not: `1e21`
prints as `1000000000000000000000` and `1.5e-7` as `0.00000015`. The
*digits* always agree, because both pick the shortest digits that read
back as the same double<Cite id="rust-std-flt2dec" /><Cite id="ecma262" />;
only the layout differs. So `format_number` takes the digits and exponent
from Rust's `{:e}` and lays them out by ECMAScript's rule, plain
decimals from 0.000001 up to (not including) 1e21 and exponent form
outside. Its test table holds 42 doubles written as raw bits, with what
Node 22 printed for each.

</More>

<Analogy extra title="a row of identical lockers">
Every locker in the row is the same size, so they line up neatly; a label
on the door says what is inside: nothing, a yes-or-no card, a number, or a
ticket for a parcel kept in the back room. Big things never go in a
locker; only their tickets do.
<span slot="breaks">A locker's label and its contents are separate, and
you could put the wrong thing behind a label; in Rust the label (the tag)
and the payload are written together, and the compiler never lets you
read a number out of a locker labelled "ticket".</span>
</Analogy>

## One exhaustive match

The top of `run` in `vm.rs` (rewrapped):

```rust
loop {
    let byte = self.read_byte();
    let op = OpCode::from_byte(byte).expect(
        "the compiler emits valid opcodes");
    match op {
        OpCode::Sub => {
            let (a, b) =
                self.pop_numbers("-")?;
            self.push(Value::Number(a - b));
        }
        // ... 52 more arms
    }
}
```

It is the TypeScript `switch` with two differences. The byte is decoded
first, and `expect` stops loudly if the compiler ever emitted a byte that
is no opcode. And there is no `default`: a Rust match must be
exhaustive<Cite id="klabnik2026" />, so an opcode with no arm stops the
VM compiling. Errors are returned, not thrown: `run` returns
`Result<(), RuntimeError>`, and `pop_numbers` returns `Err` when the
operands are not both numbers, which `?` passes straight out of `run`.
`print "hi" - 1;` prints `runtime error: cannot use '-' on a string and a
number`, `  at line 1 in script`, and exits with 70, like the TypeScript
VM.

<Callout kind="definition">
**Match-based dispatch**: the loop decodes each byte into an opcode enum
and runs one `match` over it, with one arm per instruction. Because the
match must be exhaustive, every opcode is guaranteed a handler at compile
time, and the only unchecked step left is decoding the byte.
</Callout>

<Examples of="match-dispatch">

```text
// the arm for False deleted (rustc 1.97):
error[E0004]: non-exhaustive patterns:
  `OpCode::False` not covered
```

</Examples>

Delete one arm from `run` and rustc names the opcode you forgot. Step
through the loop running
`print 1 + 2 * 3;`, whose chunk is the real fourteen bytes drip-rs
compiles it to:

<DispatchSteps client:visible />

<Formal title="Two arms as rules">

```text
code[ip] = True
──────────────────────────────
⟨ip, S⟩ → ⟨ip + 1, S · true⟩

code[ip] = Sub   S = S′ · a · b
      a, b numbers
──────────────────────────────
⟨ip, S⟩ → ⟨ip + 1, S′ · (a − b)⟩
```

<span slot="read">Read each rule from the top down. The first says: if
the byte at ip is True, a machine whose instruction pointer is ip and whose
stack is S steps to one whose instruction pointer is one further on and
whose stack has true pushed on top. The second says: if the byte is Sub,
and the stack is some S′ with a and then b on top, and both are numbers,
then the machine steps to the next instruction with a and b replaced by
a − b. Each arm of the match is one such rule; when no rule applies (b is
a string, say), the VM reports a runtime error.</span>
</Formal>

## The loop cannot hold the chunk

The TypeScript loop caches the running frame's `code` in a local and
calls `reload()` after every call and return. Try that in Rust:

```rust
fn run(&mut self) {
    let code = &self.code;
    for &b in code {
        self.push(b as f64);
    }
}
```

rustc 1.97 refuses with `error[E0502]: cannot borrow *self as mutable
because it is also borrowed as immutable`: `self.push` needs all of the
VM. It is right, too: in drip-rs the chunk belongs to a function in the
heap's arena, and allocating can grow that arena's `Vec` and move it. So
the running frame's state lives in fields of the `Vm`, which its comments
compare to a CPU's registers, `ip`, `chunk: Rc<Chunk>` and `slots`;
`read_byte` reads `self.chunk.code[self.ip]`, a borrow that ends with
the expression.

<Figure takeaway="One frozen chunk, three owners, no borrow of the heap." caption="While a function runs, its chunk is shared by three Rc pointers: the function's own, the call frame's, and the Vm's chunk register. ip and slots live in the Vm; the frame's ip is written back only when it makes a call.">
  <Registers />
</Figure>

The chunk is behind an `Rc` (*Box, Rc and RefCell*) because several
owners need it and cloning one only bumps a count; a finished chunk never
changes, so it needs no `RefCell`. `call` saves the caller's `ip` into
its frame and loads the callee's registers; returning loads the caller's
back.

<More title="A toy VM with registers">

The same design on a toy VM, small enough to change: try moving the
borrow back into a local and read rustc's error. In the committed
benchmark run (`results/drip-rs-bench-2026-11-02.md`, a shared cloud
VM), `fib` took 406 ms in drip-rs against 1,906 ms in the TypeScript VM.
