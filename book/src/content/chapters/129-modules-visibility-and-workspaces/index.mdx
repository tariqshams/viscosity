## Nine lines, nine files

Here is the top of drip-rs's `src/lib.rs`, the root of its library
crate (trimmed):

```rust
pub mod chunk;
pub mod compiler;
pub mod gc;
pub mod scanner;
pub mod vm;
// ... and four more
```

In TypeScript each file is a module just by existing, and
`import { scan } from './scanner.js'` finds it by its path on disk
(*Modules: import and export*). Rust works the other way round: the
compiler starts at one file, the **crate root** (`src/lib.rs` for a
library, `src/main.rs` for a program), and compiles only the files that
the root, or a module below it, asks for. `mod scanner;` says "there is
a module called `scanner`, and its code is in `scanner.rs` beside me";
delete that line and `scanner.rs` is ignored, however much code is in
it. (The `pub` in front lets code outside use it, as we will see.)

<Analogy title="a family tree drawn from the top">
A JavaScript project is like a pile of letters that mention each other
by address. A Rust crate is a family tree drawn from the oldest
ancestor down: the root names its children, each child names its own,
and anyone not drawn on the tree is not in the family, however close
they live.
<span slot="breaks">Real families have two parents and cousins who
marry; a module has exactly one parent, so the module tree is a true
tree with no loops.</span>
</Analogy>

<Figure takeaway="A file is part of the crate only if a mod line names it." caption="drip-rs's lib.rs names nine modules, and each line pulls in the file of that name. A file that no mod line names (notes.rs here is imaginary) is never compiled.">

</Figure>

Ask for a file that is not there and rustc 1.97 says E0583, "file not
found for module `scanner`", with the help line 'create file
"scanner.rs" or "scanner/mod.rs"'. A module can also be written
**inline**, with its body in braces: every Rust exercise in this book
wraps its tests in `mod tests { use super::*; ... }`.

## Paths and use

Every item in the tree has an address built from the names on the way
to it, joined by `::`. A **path** may start in three places:
`crate::` starts at the root (like `/` in a file path), `super::` at
the parent of the current module (like `..`), and `self::`, or nothing
at all, in the current module. Step through some real paths:

<PathSteps client:visible />

Writing `crate::scanner::Token` everywhere would be tiring, so **`use`**
makes a short name for a path, the way `import` does; drip-rs's
compiler opens with lines such as `use crate::scanner::{Scanner,
Token};`, where the braces bring in several names at once. A `use`
covers only the module it is written in, not its children or its
parent, so each module (each file, usually) has its own
list<Cite id="rust-book-modules" />.

<Examples of="rust-module">

```rust
mod geom {
    pub fn area(w: f64, h: f64) -> f64 {
        w * h
    }
}
mod report {
    use crate::geom::area;
    pub fn show() {
        println!("{}", area(2.0, 3.0));
    }
}
```

</Examples>

`geom` and `report` are inline modules, both children of the crate
root. `report` reaches `area` through `use crate::geom::area;`, a path
from the root, and `report::show()` prints `6`. Remove the `use` and
`area` is E0425, "cannot find function `area` in this scope", whose
help line offers the `use`; write `use geom::area;` instead and it is
E0432, "unresolved import `geom`", because a path without `crate::`
starts in the current module, and `report` has no child called `geom`.
A Rust path means the same thing in every file of the crate, where a
TypeScript import path is relative to the importing file.

<Callout kind="definition">
A **module** is a named scope in a crate's module tree, declared with
**`mod name { ... }`** (inline) or **`mod name;`** (its body is read
from `name.rs`, or `name/mod.rs`, beside the declaring file). Items are
reached by **paths**: `crate::a::b` from the root, `super::x` from the
parent, `self::y` from here. **`use path;`** binds the last name of a
path as a shortcut in the current module<Cite id="klabnik2026" />.
</Callout>

## Private unless it says otherwise

Here is drip-rs's hash table (`table.rs`, trimmed):

```rust
pub struct Table {
    count: usize,
    keys: Vec<Option<StrRef>>,
    values: Vec<Value>,
}
```

The struct is `pub`, and so are `new`, `get`, `set` and the rest of its
API; its three fields, and its `grow` method, are not, so they are
**private**. From another module, `t.count` is E0616, "field `count`
of struct `Table` is private", `t.grow(16)` is E0624, "method `grow`
is private", and a private free function is E0603. Why bother? `count`
must count live entries *and* tombstones, and the two columns must stay
the same length; with private fields only `table.rs` can break that, so
`table.rs` is all you need to read to trust it.

The exact rule: a private item may be used by the module it is in *and
that module's descendants*; a public item may be used from anywhere
that can reach all of its ancestor modules<Cite id="rustref-visibility" />.

<Figure takeaway="A private item is visible in its own module and every module inside it." caption="table's private method grow can be called in table and in table's child tests, and nowhere else. A pub method such as new can be called from all of them.">
  <PrivacyMap />
</Figure>

The first half is why a `tests` module inside `table.rs` can test
`grow`; the second half is why `pub` on an item inside a *private*
module does not make it reachable from outside. TypeScript has two
privacy tools, a file's `export` list and `#` on class members; Rust has
one rule, about *modules*, not types.

<Callout kind="definition">
**Visibility** says where a name may be used. Items, struct fields and
methods are **private** by default: usable only in their own module and
its descendants. **`pub`** makes them usable wherever their parent
modules can be reached; **`pub(crate)`** limits that to the current
crate. **`pub use path;`** re-exports an item, giving it a second,
public path.
</Callout>

<Examples of="visibility">

```rust
// drip-rs's src/lib.rs
pub mod vm;
pub use vm::{Options, Outcome, Vm};
```

</Examples>

The VM really lives at `drip::vm::Vm`; `pub use` gives it a second,
shorter public path, `drip::Vm`, which is what drip-rs's `main.rs` (a
separate binary crate in the same package) and its tests use. A crate's
set of `pub` paths is its public API, like a package's exports, and
changing it is what breaks other people's code.

## Workspaces: several crates, one build

drip-rs is one package. The Rust Viscosity is six, each with its own
`Cargo.toml`, built together as one **workspace**, whose root
`Cargo.toml` holds no code:

<Examples of="workspace">

```toml
[workspace]
members = ["crates/vir", "crates/core",
  "crates/frontend-js", "crates/cli",
  # ... two more
]
[workspace.dependencies]
viscosity-vir = { path = "crates/vir",
  version = "0.0.2" }
```

</Examples>

`members` lists the package folders. `[workspace.dependencies]` states
each shared dependency once, and a member then writes
`viscosity-vir.workspace = true` under its own `[dependencies]`, so
every crate agrees on one version (of oxc, too). `cargo test
--workspace` tests every member, and `cargo run -p viscosity-cli`
builds and runs one. (A package called `viscosity-core` is
`viscosity_core` in Rust code, since `-` cannot appear in a path.) Step
through what depends on what:

<CrateSteps client:visible />

<Callout kind="definition">
A **workspace** is a set of packages built together from one root
`Cargo.toml` with a `[workspace]` table. Its members share one
`Cargo.lock` and one output folder, `target/`<Cite id="rust-book-workspaces" />,
and depend on each other with path dependencies, which may not form a
cycle.
</Callout>

The split turns the plugin design of *The architecture of Viscosity
and its plugin API* into something the compiler checks:
`viscosity-core` does not depend on `viscosity-frontend-js`, so its
library code *cannot* mention oxc or JavaScript syntax, only VIR and
its own `LanguagePlugin` trait. Core's tests do need a real plugin, so
`frontend-js` is listed under `[dev-dependencies]`, built only for
tests, where cargo accepts the loop back to core; list two crates under
each other's `[dependencies]`, however, and cargo 1.97 refuses before
compiling anything, with "cyclic package dependency".

## What you learned

- A crate is a **module tree** rooted at `crate`. `mod name;` pulls in
  `name.rs`; a file no `mod` line names is not compiled.
- **Paths** start from `crate::`, `super::` or the current module;
  **`use`** makes a short name in the current module only.
- Everything is **private** by default, fields included: usable in its
  own module and its descendants. `pub` opens it to anyone who can
  reach its parents, and `pub use` re-exports.
- A **workspace** builds several crates with one `Cargo.lock` and one
  `target/`; engine/rust's split makes the plugin boundary a
  compile-time fact.
