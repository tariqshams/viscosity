## A reference with nothing behind it

In TypeScript you never ask how long an object will last: if `word`
still points at a string, the garbage collector keeps that string
alive. Rust has no collector, so when an owner goes out of scope its
value is dropped at once, and any reference still pointing at it would
point at freed memory; such a reference is **dangling**, and reading
through one is how C programs crash (or, worse, quietly read somebody
else's data). Here is the smallest program that would make one:

```rust
let r;
{
    let text = String::from("let x");
    r = &text[0..3];
}
println!("r is {r}");
```

`r` becomes a slice of `text`; the inner block ends, so `text` is
dropped; then `r` is read. rustc 1.97 refuses (wrapped to fit):

```text
error[E0597]: `text` does not live long
  enough
5 | r = &text[0..3];
  |      ^^^^ borrowed value does not
  |           live long enough
6 | }
  | - `text` dropped here while still
  |   borrowed
7 | println!("r is {r}");
  |                 - borrow later used here
```

Read it as three places: where the borrow was **made**, where the owner
**died**, and where the borrow was **still needed**. Every lifetime
error you meet is some arrangement of those three.

<Analogy title="a cloakroom ticket">
You leave your coat at a theatre's cloakroom and get a numbered ticket.
The ticket is small and you can carry it anywhere, but it is only worth
something while the cloakroom is open. A reference is the ticket, the
value is the coat, and the owner's scope is the opening hours; Rust
checks every ticket against the opening hours before the show starts.
<span slot="breaks">A real cloakroom might stay open late, or you might
get lucky; Rust never guesses, so it rejects the program if there is
any path on which the ticket could be used after closing.</span>
</Analogy>

<Callout kind="definition">
A **lifetime** is the stretch of a program during which a reference
must stay valid: from where the reference is made to the last place it
is used. The borrow checker gives every reference a lifetime and checks
that it fits inside the life of the value it points at, from that
value's creation to its drop<Cite id="rust-book-lifetimes" />. Lifetimes
exist only while compiling; at run time a `&str` is still only an
address and a length.
</Callout>

Two things follow. First, a borrow ends at its **last use**, not at the
closing brace: in *Vec and HashMap*, printing `first` before the `push`
made the same lines compile, because the shared borrow was over before
the mutable one began. Second, a function cannot hand back a borrow of
its own local:

<Examples of="lifetime">

```rust
fn make() -> &String {
    let s = String::from("hi");
    &s // s is dropped right here
}
```

</Examples>

`s` lives only until `make` returns, so the reference would point at
nothing. rustc stops at the signature with E0106, "missing lifetime
specifier", noting that the return type "contains a borrowed value, but
there is no value for it to be borrowed from", and its help line says
what you almost certainly want: "return an owned value", that is,
`fn make() -> String` with `s` as the last line. TypeScript never meets
this, because the collector keeps `s` alive for as long as the caller
holds it; C compiles the equivalent and returns a pointer into a stack
frame that is gone.

## Naming a lifetime

Inside a function body the compiler works out every lifetime by itself.
It needs your help at the *edges*: a reference stored in a struct, or
handed back from a function, travels where one body cannot show. Here
is drip-rs's token, whose `lexeme` is a slice of the source text rather
than a copy:

```rust
pub struct Token<'src> {
    pub kind: TokenKind,
    pub lexeme: &'src str,
    pub line: usize,
}
```

Write `lexeme: &str` with no `'src`, as you would in a TypeScript
interface, and rustc says E0106 and suggests `struct Token<'a>`. The
question is fair: a `Token` points into somebody else's text, so whose,
and for how long? `'src` (read it "tick src") is a **lifetime
parameter**, declared in angle brackets like the type parameters of
*Generics and monomorphization*; it names "however long the borrowed
source stays valid", so a `Token<'src>` can never outlive the text it
points into. The scanner says the same with `impl<'src> Scanner<'src>`
and `fn scan_token(&mut self) -> Token<'src>`: borrow the scanner for a
moment, and hand back a token valid for as long as the *source* is.

Now a function with two inputs, which returns the longer string:

<Examples of="lifetime-annotation">

```rust
fn longer<'a>(a: &'a str, b: &'a str)
    -> &'a str {
    if a.len() >= b.len() { a } else { b }
}
```

</Examples>

Without the ticks rustc asks, in E0106's help line, because the
signature "does not say whether it is borrowed from `a` or `b`". The
answer could be either, so the honest signature uses one name for all
three. Read it as: "there is some stretch `'a` during which both `a`
and `b` are valid, and the result is valid for that stretch". At each
call `'a` works out as the overlap of the two inputs' lives, so the
result may not be used after the shorter-lived input is gone, even if
`longer` happened to return the other one:

<Figure takeaway="With one name for both inputs, the result lives only as long as the shorter-lived input." caption="a lives to the end of main and b only inside a block, so 'a is the overlap. Using the result after b's block ends is E0597, even if it happened to be a.">
  <LongerBars />
</Figure>

<Callout kind="definition">
A **lifetime annotation** names a lifetime with an apostrophe, such as
`'a` or `'src`. It is declared as a parameter (`struct Token<'src>`,
`impl<'src>`, `fn f<'a>`) and attached to references (`&'a str`) or to
types that hold them (`Token<'a>`). Giving several references the same
name says they must all be valid over that stretch. Annotations change
no lifetime; they let the compiler check each caller against the
signature alone<Cite id="rust-book-lifetimes" />.
</Callout>

## When you may leave them out

*Slices, String and &str* had you write `fn first_word(s: &str) ->
&str` with no ticks at all. That works because of three **elision
rules**, which fill in lifetimes when the answer is
obvious<Cite id="rustref-lifetime-elision" />: each reference parameter
gets its own lifetime; if there is exactly one input lifetime, every
output gets it; and in a method with `&self` or `&mut self`, every
output gets *self's* lifetime. If an output is still unnamed after
that, you get E0106, as `longer` did; the compiler never reads the body
to decide.

<ElisionSteps client:visible />

The third rule is why a scanner must be explicit. Written the short
way, `fn next_word(&mut self) -> Option<&str>` ties each word to the
mutable borrow of the splitter `w`, so holding two words at once (which a
compiler does all the time with its `previous` and `current` tokens) is
E0499, "cannot borrow `w` as mutable more than once at a time".
drip-rs's `-> Token<'src>` says the token borrows the *source* instead,
so the scanner is free again the moment `scan_token` returns.

One lifetime is built in: **`'static`**, "valid for the whole run of
the program". String literals have it, because their text is stored in
the program itself, so drip-rs can put a made-up `"self"` token into a
`Token<'src>`. If a help line suggests `'static`, ask whether the
reference really should live that long; usually the fix is an owner
that lives longer<Cite id="rust-book-lifetimes" />.

## What you learned

- A **lifetime** is the stretch of code where a reference must stay
  valid, from where it is made to its **last use**; the borrow checker
  makes it fit inside the life of the value borrowed (E0597 otherwise).
- A function cannot return a borrow of its own local (E0106); return an
  owned value instead.
- A **lifetime annotation** such as `'src` names a lifetime, on structs
  that hold references (`Token<'src>`), their impls, and functions whose
  result borrows from an input. One shared name means "valid while all
  of these are"; annotations describe, and never extend, a life.
- Three **elision rules** fill in the obvious cases; rule 3 ties a
  method's result to `self`, which is wrong for a scanner. `'static`
  lasts the whole run.
