## Two right answers

One of the programs written for the port,
`tests/extra/unicode_offsets.js`, starts like this (first line cut):

```js
// Ünïcödé before the collection: …
const label = 'héllo wörld 😀';
const ps = [];
```

I parsed it with both parsers. acorn, the TypeScript engine's parser,
says the statement `const ps = [];` runs from offset 116 to 130. oxc,
the Rust engine's, says 126 to 140. Ten apart, and both correct. And
the parity test checks that both engines rewrite this file identically.
This chapter is about how both can be true.

## oxc

oxc, the Oxidation Compiler, is "a collection of high-performance tools
for JavaScript and TypeScript written in Rust": a parser, a linter, a
formatter, a transformer, a minifier<Cite id="oxc-project" />. The port
uses its parser and AST crates, version 0.156. The parser has "three
inputs (a memory arena, a source string, and a SourceType) and one
return struct"<Cite id="oxc-parser-docs" />. Here is the call in
`crates/frontend-js/src/lib.rs`, trimmed:

```rust
let allocator = Allocator::default();
let options = ParseOptions {
    preserve_parens: false,
    ..ParseOptions::default()
};
let ret = Parser::new(&allocator, source,
        SourceType::mjs())
    .with_options(options)
    .parse();
if let Some(e) =
    ret.diagnostics.errors().next() {
    return Err(CompileError(
        format!("SyntaxError: {e}")));
}
let program = ret.program;
```

Line it up with chapter 92's acorn adapter. `SourceType::mjs()` is
acorn's `sourceType: 'module'`. `preserve_parens: false` matches
acorn's default of not keeping parentheses as nodes. And errors come
back as data in `ret`, not as an exception, so the plugin turns the
first one into a `CompileError`.

<Callout kind="definition">
**oxc** (the Oxidation Compiler) is a JavaScript and TypeScript
toolchain written in Rust. Its parser takes an `Allocator`, the source
and a `SourceType`, and returns a `ParserReturn` holding the `Program`
(with its comments) and a list of syntax errors. The tree is a set of Rust
types, allocated in the arena, with spans in UTF-8 byte
offsets<Cite id="oxc-parser-docs" />.
</Callout>

## A tree in an arena

ESTree (chapter 92) is plain objects with a `type` string. oxc's tree is
Rust types: a `Statement` enum, an `Expression` enum with dozens of
variants, and a struct per node kind. One variant, from `oxc_ast`:

```rust
pub enum Expression<'a> {
    // ...
    BinaryExpression(
        Box<'a, BinaryExpression<'a>>),
    // ...
}
```

That `Box` is not std's. It is oxc's arena box: a pointer to a node in
the `Allocator`. On this machine an `Expression` is 16 bytes, a tag and
that pointer. The kinds are split finer than ESTree's, too: `ps[i].x`
is a `StaticMemberExpression` whose object is a
`ComputedMemberExpression`, where ESTree has one `MemberExpression`
with a `computed` flag. Chapter 173 maps them back.

<Callout kind="intuition">
A bump arena is a notepad. Each new node is written on the next free
line; nothing is ever erased on its own. When you're done, you throw
the whole pad away.
</Callout>

`'a` is chapter 133's lifetime, and here it names the arena. Every node
borrows the allocator, so no node can outlive it. Step through what that
means for the plugin:

<OxcSteps client:visible />

oxc's documentation spells out the deal. Objects in the arena "are
never Dropped"; the memory is "released in bulk when the allocator is
dropped". To keep that from leaking, the arena refuses, at compile
time, any type that implements `Drop`, such as a `std::vec::Vec`. That
is why oxc ships arena versions of `Box`, `Vec`, `String` and
`HashMap`<Cite id="oxc-allocator-docs" />.

For the port this settles a design question. The TypeScript engine keeps
ESTree nodes alive inside the VIR, in `SourceRef.node`. The Rust tree
dies when `lower` returns, so the VIR keeps a `NodeRef` index into a
side table of facts instead (chapter 173). Spans survive: an oxc `Span`
is two `u32`s with no lifetime.

## Bytes and code units

Now the two offsets. A JavaScript string is a sequence of UTF-16 code
units, and acorn's "character offsets" count those. A Rust `String` is
UTF-8 bytes, and oxc's spans count bytes. Before `const ps`, the file
has accented letters (one code unit, two bytes each) and two 😀 (two
code units, four bytes each). Measured on the same file:

```
             acorn       oxc
             (UTF-16)    (UTF-8)
const ps     116         126
ps[i].x      247         258
ps[3].name   290         305
```

Each engine splices its own string with its own offsets. The TypeScript
emitter does `out.slice(0, e.start) + e.text + out.slice(e.end)`. The
Rust one, from `emit.rs`:

```rust
out.replace_range(
    e.start as usize..e.end as usize,
    &e.text);
```

`slice` counts code units and `replace_range` counts bytes, so both cut
before the same `p` of `ps[i].x`. The fixture shows the result: the
same `s += ps.x[i]; // ✓ — done` line from both engines.

The danger is mixing the two. Hand acorn's 116..130 to the Rust string
and you get `"ld 😀';\ncons"`. Land inside a character and Rust panics,
because a string slice must start and end on a character
boundary<Cite id="rust-std-str" />. When the port does need a
JavaScript-style offset, `lines::utf16_offset` converts.

<Run id="three-lengths" />

Line numbers need care too, because oxc reports none. The plugin counts
them itself in `lines.rs`, at the same breaks acorn counts: `\n`,
`\r\n`, a lone `\r`, U+2028 and U+2029.
`tests/extra/annotation_line_breaks.js` puts a U+2028 between two
declarations to check it.

<Callout kind="pitfall">
oxc's parser doesn't report every syntax error. Its documentation says
the list "is not comprehensive": more expensive checks are left to its
semantic analyzer<Cite id="oxc-parser-docs" />, which the port doesn't
run. I gave twelve small programs with early errors to acorn and
to the Rust engine's `compile`. acorn rejected eleven (the twelfth, assigning to a `const`, is a
run-time error). oxc's parser rejected one, a top-level `return`. So
`let a = 1; let a = 2;` is a `SyntaxError` in the TypeScript engine,
and the Rust engine compiles it. No fixture covers this, because every
parity program is valid JavaScript.
</Callout>

<Prompts ids={['oxc-semantic']} />

<Callout kind="engine" label="Under the hood">
The arena is one reason oxc is fast. Allocating a node is a pointer
bump, and freeing a tree of thousands of nodes is returning a few
chunks; oxc's own docs list the arena first among its parser's
performance techniques, ahead of `u32` spans<Cite id="oxc-parser-docs" />.
The same docs advise reusing one `Allocator` and calling `reset` between
jobs, rather than making a new one each time<Cite id="oxc-allocator-docs" />.
The port makes a fresh one per `lower`, which is fine for a compiler
that parses a file or two per run.
</Callout>

## What you learned

- **oxc** is a Rust toolchain for JavaScript. Its parser takes an
  arena, the source and a `SourceType`, and returns the tree with its
  errors as data.
- The tree lives in a bump **arena**: `'a` ties every node to the
  `Allocator`, nodes are never dropped one by one, and the whole arena is
  freed at once. So the port keeps spans and facts, not the tree.
- oxc spans count **UTF-8 bytes**, acorn's offsets **UTF-16 code
  units**. Each engine slices its own string with its own offsets, so
  both cut at the same characters.
- Line numbers are counted by the plugin at every ECMAScript line
  break.
- oxc's parser leaves some early errors to a semantic pass the port
  doesn't run.
