## Meaning, one rule at a time

Since the chapter *Running expressions: a tree that computes*, our
interpreter has worked out what Drip programs mean by walking their trees, with one `case` for each kind of
node; that works, however it hides a pattern worth pulling into the
light. The grammar has a small number of productions, every node of a
parse tree is there because of exactly one of them, and the meaning of
a node only ever depended on the meanings of its children. So what if we
wrote the meaning down *next to the grammar*, one small rule per
production, and let a program do the walking? Take
`3 * (4 + 5)`: we would like its value, `27`, and we might also like
its translation into postfix code, `3 4 5 + *` (the order a stack
machine wants, operands first and the operator after them). Both
should come out of the same grammar, with no new parser.

<Analogy title="a phrasebook with a rule per pattern">
Picture a phrasebook that, instead of whole sentences, lists sentence
*patterns* with a note on each: "for *the X of Y*, write *Y's X*".
Translating a sentence means spotting which pattern it fits, translating
its parts, and joining them the way the note says.
<span slot="breaks">Human language is full of idioms and context, so a
note per pattern is never enough; here it is, because each rule sees only
its own parts, and the grammar guarantees every phrase fits exactly one
pattern.</span>
</Analogy>

## Rules attached to productions

Here is a small expression grammar, layered (as in the chapter *Precedence and associativity*) so
that `*` binds tighter than `+`, with a **semantic rule** beside each production
saying how to compute a value called `val`:

```text
E → E₁ + T     E.val = E₁.val + T.val
E → T          E.val = T.val
T → T₁ * F     T.val = T₁.val × F.val
T → F          T.val = F.val
F → ( E )      F.val = E.val
F → num        F.val = num.lexval
```

Read the first line as "an E can be an E, a plus and a T; when it is,
its `val` is the left part's `val` plus the right part's". The small
`₁` only tells the two `E`s apart (they are the same nonterminal in
different places), and `num.lexval` is the number the scanner read
(the literal of the chapter *Numbers and strings*). The `+` and the brackets carry no value: they
only decided which production was used.

<Callout kind="definition">
**Syntax-directed translation** is translating (or evaluating) a program
by attaching rules to the productions of its grammar, so that the result
for each node of the parse tree is computed from the results for its
parts. Each node gets **attributes** (named values, such as `val`), and
each production gets **semantic rules** that say how to compute them.
Sometimes the rules are written as actions placed inside the production
instead, to run when the parser reaches that point<Cite id="aho2006" />.
</Callout>

<Examples of="syntax-directed-translation">

```text
E → E₁ + T     E.code = E₁.code
                 ++ T.code ++ "+"
F → num        F.code = num.lexeme
```

```text
exp: exp '+' exp  { $$ = $1 + $3; }
```

```js
function parseNumber() {
  const t = advance();
  return { kind: 'literal',
           value: t.literal };
}
```

</Examples>

The first changes the rules and keeps the grammar: `code` is a string,
`++` joins strings, and the translation of a sum is the left part's
code, then the right part's, then `+`. On `3 * (4 + 5)` it produces
`3 4 5 + *` (try it below). The second is the yacc rule from the chapter *Parser generators and
PEGs*,
which is the same idea in a parser generator's notation: `$$` is the
attribute of the whole and `$1`, `$3` are the parts'. The third is the
realistic one, and you have already written it: in a recursive-descent
parser each function returns a node built from what the functions it
called returned, which makes building a syntax tree itself a
syntax-directed translation, with "the tree for this part" as the
attribute.

## Synthesised attributes

Every rule so far has the same shape: a parent's attribute is made from
its children's. To work them out, a node must wait until all its children
have their values, then run its own rule; in other words, visit the
children first.

<Analogy extra title="labelling boxes in a removals van">
Packing for a move, you weigh each small box, write the weight on it,
and pack small boxes into bigger ones; each bigger box's label is the
sum of the labels inside it plus the box itself, so the label on the
outermost crate is the weight of everything.
<span slot="breaks">A box's label is always a sum; a semantic rule can
be any calculation (a product, a string join, a new tree node), and
different kinds of box (different productions) can use different
rules.</span>
</Analogy>

Step through `3 * (4 + 5)` and watch each `val` appear only after its
children have theirs:

<AnnotateSteps client:visible />

A parse tree with the attributes written on it is called an
**annotated parse tree**.

<Callout kind="definition">
A **synthesised attribute** is one whose value at a node is computed
only from attribute values at that node's children (and at the node
itself). A definition that uses only synthesised attributes can be
evaluated in any order that visits children before parents, such as a
post-order walk, or during bottom-up parsing, at each reduce<Cite id="knuth1968" />.
</Callout>

<Formal title="The shape of a synthesised attribute">

```text
production   A → X₁ X₂ … Xₙ
rule         A.s = f(X₁.a, X₂.a, …, Xₙ.a)
```

<span slot="read">For a production where A is made of the parts X1 up to
Xn, the attribute s of A is some function f of the attributes of those
parts. Nothing from above A, and nothing beside it, is allowed in: the
information only flows upwards.</span>
</Formal>

<Examples of="synthesized-attribute">

```text
F → num   F.val = 7
on 7: val is 7
```

```text
E → E₁ + T   E.n = E₁.n + T.n
F → num      F.n = 1
on 1 + 2 + 3: n is 3
```

```text
E → E₁ + T
  E.const = E₁.const && T.const
F → num   F.const = true
F → id    F.const = false
```

</Examples>

The first is the smallest: a one-node tree, whose `val` is the number.
The second keeps the same grammar but counts numbers instead (the
copying rules, such as `E.n = T.n`, are left out to save room): `n` is
3 for `1 + 2 + 3`, and the attribute has nothing to do with arithmetic.
The third is realistic, the first question a compiler's optimiser asks
about an expression: is it made only of constants, so it can be worked
out once, before the program runs? A name (`id`) is not constant, and
a sum is constant only if both sides are.

The order matters when you write the evaluator. Here is the whole of
one in JavaScript: the rules are a table of functions, one per
production, and `synth` evaluates the children first and then runs the
node's rule on their values; the same tree is translated twice, with
two tables.

<Run id="two-translations" />

A spot the difference, with that same evaluator: leave out the copying
rule for `T → F`, and the walk reaches a node it has no rule for:

```text
rules['T→F'] missing

function
```

Copy rules look like they do nothing, which is why they are the ones
that go missing; every production needs a rule.

<Callout kind="engine" label="Under the hood">
Donald Knuth's 1968 paper gave these ideas their names: attributes
attached to the nodes of a parse tree, with functions tied to each
production, and the split between values that come up from the children
and values that come down from above<Cite id="knuth1968" />. Bottom-up
parsers use the synthesised half at full speed: an LR parser keeps a
stack of values beside its stack of states, and at each reduce it runs
the production's rule on the top values and pushes the result, which is
what yacc's `$$` is.
</Callout>

## What you learned

- **Syntax-directed translation** attaches a **semantic rule** to each
  production, so a node's result is built from its parts' results.
- The same grammar can carry many translations: a value, postfix code,
  a syntax tree.
- A **synthesised attribute** is computed from the children; evaluate
  children first, as a post-order walk or an LR parser's reduces do.

Next: values that flow *down* the tree, from parents and left siblings,
and the attribute grammars that combine both directions.
