## Four programs, four refusals

The analyses have done their work; someone still has to decide, and say
why. Here are the first reason lines the Rust CLI printed (release
build, rustc 1.97) for four small programs, each kept as an array of
objects for a different reason:

```
unsafe: line 6: an element is used by push
opt-in mode: not annotated
no field is provably numeric, so there are
  no typed columns to gain
no loop reads or writes its fields, so a
  new layout cannot pay off
```

(The programs push an element into another array, use `--mode opt-in`,
store only strings, and read one field outside any loop.) All four come from `plan_one` in `crates/core/src/plan.rs`, the port of
*The cost model*'s planner, where the order of the tests matters as much
as the tests.

<Analogy title="a pilot's pre-flight checklist">
Before take-off a pilot works down a printed checklist in a fixed
order: fuel, controls, instruments, weather. The first item that fails
stops the flight, and the reason is written in the log; a plane that
passes every item flies, and the log records what was checked.
<span slot="breaks">A pilot who finds a problem gets it fixed and starts
the list again; the planner never fixes anything, it only writes down
the first reason and moves on to the next collection.</span>
</Analogy>

## From continue to return

The TypeScript `plan()` is one loop over the collections, and each
refusal in it is `out.push(keep(...)); continue;`. The port keeps the
loop but moves its body into a function of its own:

```rust
pub fn plan(a: &Analysis, opts: PlanOptions)
    -> Plan {
    let mut out = Vec::new();
    for c in &a.collections {
        out.push(plan_one(a, c, &opts));
    }
    Plan { collections: out, options: opts }
}
```

`plan` owns the options and lends `plan_one` a shared `&opts`; inside
`plan_one`, every refusal is an early `return`, "this collection is
decided; stop here":

<Figure caption="The same planner in both engines, condensed: a refusal ends one turn of the TypeScript loop with continue, and ends the call to plan_one with return." takeaway="An early return in a function per item is the Rust shape of push-and-continue.">
  <ContinueReturn />
</Figure>

Every rung builds its answer with one closure, defined at the top of
`plan_one` (rewrapped):

```rust
let keep = |reasons: Vec<String>|
    CollectionPlan {
        collection: c.clone(),
        layout: Layout::Aos,
        block_size: 0,
        reasons,
    };
```

The closure borrows `c` and builds the plan for "leave it alone" with
the reasons it is handed (the reference's `keep` takes `...reasons`,
which Rust closures can't, so the port passes one `Vec<String>`). And
where the TypeScript plan holds
`collection: c`, a reference to the analysis's own object, the Rust plan
holds `c.clone()`: a `CollectionPlan` that borrowed from the `Analysis`
would need a lifetime tying the two together, while a copy lets the plan
live on its own.

## Safety first, one reason each

The first rung is the only one that can produce more than one reason:

```rust
if !c.bailouts.is_empty() {
    return keep(c.bailouts.iter()
        .map(|b| format!("unsafe: {b}"))
        .collect());
}
```

`map` turns each bailout into an `unsafe: ` reason, and `collect`
gathers them into the `Vec<String>` that `keep` wants. So a collection
with three bailouts gets exactly three reasons, in order, which
`explain --frames` relies on when it pairs reason *k* with bailout *k*'s
place in the source. It comes first because nothing else is worth
saying about a rewrite that could change what the program prints.

The annotation rungs come next: an `aosoa(N)` annotation has its block
size checked (only powers of two from 2 to 65536
pass<Cite id="rust-std-is-power-of-two" />), and then any annotation
returns at once, `aos` keeping the collection and `soa` or `aosoa(N)`
transforming it. That return happens before the cost rungs, so an
annotated collection is transformed even when it looks too small to pay
off, which is the point of annotating it. Then come opt-in mode and
Python without `--python-auto`, and then the questions of cost: with no
field proven numeric there are no `Float64Array` columns to gain, and
with no loop table of depth 1 or more no loop would get faster.

<Callout kind="definition">
The **cost model in Rust** is `plan_one` in `plan.rs`, called by `plan`
once per collection: a **ladder of early returns**, each built by the
**`keep` closure**. Safety comes first, with **one `unsafe:` reason per
bailout**; then annotations, which skip the cost rungs; then opt-in mode
and Python; then the cost rungs (**some field numeric**, **some loop of
depth ≥ 1**, and the **size threshold**). A collection that passes every
rung becomes `Layout::Soa`, with reasons from `describe`.
</Callout>

<Examples of="rust-cost-model">

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
const keep = [];
for (let i = 0; i < ps.length; i++)
  if (ps[i].x > 3) keep.push(ps[i]);
console.log(ps, keep.length);
// unsafe: the array is passed to a
//   method call at line 7
// unsafe: line 6: an element is used
//   by push
```

</Examples>

The comment holds the Rust CLI's reasons for `ps`, the same bytes the
TypeScript CLI prints. The cost rungs would pass, but there are two
problems, so two reasons, in the order the analysis found them:
`console.log(ps, ...)` hands the whole array to a method call, and
`keep.push(ps[i])` lets an element escape into another array. The first
rung returns with both.

## The last rung: is it big enough?

A layout change has fixed costs (a container class, a copy when the
array grows), so the planner leaves small collections alone. This
program pushes inside an `if`, so only every fourth trip adds an
element:

```js
const ps = [];
for (let i = 0; i < 100; i++)
  if (i % 4 === 0) ps.push({ x: i });
for (let i = 0; i < ps.length; i++)
  ps[i].x += 1;
```

By default `ps` is transformed (`at most 100 elements`); with `--min-size
200` it is kept (`at most 100 elements: below the 200-element threshold,
...`); and with a profile from `viscosity profile`, which measured 25,
it is kept too (`about 25 elements (measured): below the 64-element
threshold, ...`). Both CLIs printed the same bytes here. From `plan.rs`,
rewrapped:

```rust
let measured = opts.profile.as_ref()
    .and_then(|p| p.get(&c.name))
    .copied();
let size = measured.or(c.size_estimate);
if let Some(size) = size {
    if size < opts.min_size {
        return keep(vec![format!(
            "{} {} elements{}: below the …",
            if measured.is_none()
                && c.size_is_upper_bound
            { "at most" } else { "about" },
            js_number(size),
            if measured.is_some()
            { " (measured)" } else { "" },
            js_number(opts.min_size)
        )]);
    }
}
```

`opts.profile` is an `Option<HashMap<String, f64>>`: `as_ref()` borrows
what is inside rather than moving it out, `and_then` runs the lookup only
when there is a map, and `copied` turns the `Option<&f64>` from `get`
into an `Option<f64>`. `measured.or(c.size_estimate)` keeps the first
value if there is one, and only otherwise takes the
second<Cite id="rust-std-option-or" />, so a measurement always wins,
raising a size as readily as lowering it. `if let Some(size) = size`
then runs the comparison only when there *is* a size, which makes the
unknown case explicit: no size, no refusal. `js_number` prints `100`
rather than Rust's `100.0`.

<SizeRungSteps client:visible />

A maximum is used as if it were the size, so "at most 100" passes 64
although this program holds 25: better to transform a collection that
might be big than miss one that is. A maximum *below* the threshold is a
safe refusal, and an unknown size passes, since it may well be large.

<More title="More: a NaN threshold, and a sentence the fixtures never saw">

The comparison is a plain `f64` `<`, and every comparison with `NaN` is
false, so a `min_size` of `NaN` would make the rung silently stop
refusing anything. Both CLIs once let `--min-size abc` through as
`Number("abc")`, which is `NaN`; now both refuse it before planning,
with the same first line, `viscosity: --min-size must be a non-negative
number`, followed by the usage text.

When the port was first written, the profiled line read `about 25
(measured) elements: below`: the format string put " (measured)" before
"elements", while the reference writes `${size} elements${...}`. Nothing
caught it, because no parity fixture compiled a program with
`--profile`, and the fuzzer passed no profile either. Parity holds only
for what is tested: there are now four profile fixtures, checked by
`profiled_output_equals_typescript_output` in `parity.rs`, and the
fuzzer gives every batch a random profile.

<Formal title="The size rung">

```text
size = measured ?? estimate
keep  ⇔  size ≠ none ∧ size < min_size
```

<span slot="read">The size is the measured one if there is one,
otherwise the estimate (which may itself be missing). The collection is
kept exactly when there is a size and it is less than the threshold; in
every other case the rung lets it through.</span>
</Formal>

</More>

## What you learned

- `plan` calls **`plan_one`** once per collection; each refusal is an
  **early `return`**, built by the **`keep` closure**, and plans hold a
  **clone** of their collection.
- **Safety is the first rung**, with **one reason per bailout**;
  **annotations** skip the cost rungs, but never safety.
- The size is **`measured.or(estimate)`**, and **`if let Some(size)`**
  lets an **unknown** size pass; a maximum is treated as the size.
