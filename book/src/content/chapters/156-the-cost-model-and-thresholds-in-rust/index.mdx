## Four programs, four refusals

The analyses have done their work: for every collection the Rust engine
now knows whether the rewrite is safe, which fields are numbers, which
loops touch which fields, and roughly how big it will be (*Access
patterns in Rust*). Someone still has to decide, and say why. Here are
the first reason lines the Rust CLI printed (I ran `viscosity explain`
here, release build, rustc 1.97) for four small programs, each kept as
an array of objects for a different reason:

```
unsafe: line 6: an element is used by push
opt-in mode: not annotated
no field is provably numeric, so there are
  no typed columns to gain
no loop reads or writes its fields, so a
  new layout cannot pay off
```

The first program pushes an element of `ps` into another array, the
second was compiled with `--mode opt-in`, the third stores only strings,
and the fourth reads one field once, outside any loop. All four
sentences come from one function, `plan_one` in
`crates/core/src/plan.rs`, which ports the planner of *The cost model*.
It is short enough to read top to bottom, and the order of its tests
turns out to matter as much as the tests themselves.

<Analogy title="a pilot's pre-flight checklist">
Before take-off a pilot works down a printed checklist in a fixed
order: fuel, controls, instruments, weather. The first item that fails
stops the flight, and the reason is written in the log; a plane that
passes every item flies, and the log records what was checked.
<span slot="breaks">A pilot who finds a problem gets it fixed and starts
the list again; the planner never fixes anything, it only writes down
the first reason and moves on to the next collection.</span>
</Analogy>

<Analogy extra title="passport control">
An officer checks your passport, then your visa, then asks why you are
travelling, always in that order, and stops at the first problem. A
diplomatic pass lets you skip the questions about your trip, but never
the check that the passport is genuine.
<span slot="breaks">An officer can use judgement and wave someone
through; every rung of the planner is a plain test on the analysis's
facts, and two runs on the same program always give the same answer, in
the same words.</span>
</Analogy>

The diplomatic pass is the annotation: a `// @viscosity soa` comment
skips the cost questions, but never the safety one. Step down the

## From continue to return

The TypeScript `plan()` is one loop over the collections, and each
refusal in it is `out.push(keep(...)); continue;`. The port keeps the
loop but moves its body into a function of its own:

```rust
pub fn plan(a: &Analysis, opts: PlanOptions)
    -> Plan {
    let mut out = Vec::new();
    for c in &a.collections {
        out.push(plan_one(a, c, &opts));
    }
    Plan { collections: out, options: opts }
}
```

`plan` takes the options by value (so the finished `Plan` can own them)
and lends `plan_one` a shared reference to them, `&opts`, once per
collection. Inside `plan_one`, every refusal becomes an early `return`,
which is the Rust way to say "this collection is decided; stop here":

<Figure caption="The same planner in both engines, condensed: a refusal ends one turn of the TypeScript loop with continue, and ends the call to plan_one with return." takeaway="An early return in a function per item is the Rust shape of push-and-continue.">
  <ContinueReturn />
</Figure>

Every rung builds its answer with one closure, defined at the top of
`plan_one` (rewrapped):

```rust
let keep = |reasons: Vec<String>|
    CollectionPlan {
        collection: c.clone(),
        layout: Layout::Aos,
        block_size: 0,
        reasons,
    };
```

A **closure** is a small unnamed function that can use the variables
around it (*Iterators and closures in Rust*); this one borrows `c` and
builds the plan for "leave it alone": layout `Aos`, no block size, and
whatever reasons it is handed (`reasons,` is shorthand for `reasons:
reasons`). The reference's `keep` takes its reasons as `...reasons`, a
list of any length; Rust closures can't do that, so the port passes one
`Vec<String>`. There is a second difference: the TypeScript plan holds
`collection: c`, a reference to the analysis's own object, while the
Rust plan holds `c.clone()`, a copy. A `CollectionPlan` that borrowed
from the `Analysis` would need a lifetime tying the two together; a
copy lets the plan live on its own, at the price of copying each
collection's facts once.

## Safety first, one reason each

The first rung is the only one that can produce more than one reason:

```rust
if !c.bailouts.is_empty() {
    return keep(c.bailouts.iter()
        .map(|b| format!("unsafe: {b}"))
        .collect());
}
```

`iter()` walks the bailout messages, `map` turns each into an `unsafe:
` reason, and `collect` gathers them into the `Vec<String>` that `keep`
wants (Rust works out the type from `keep`'s parameter). So a collection
with three bailouts gets exactly three reasons, in order. That
one-to-one match is relied on later: `viscosity explain --frames` (in
*Code frames in Rust*) pairs reason *k* with bailout *k*'s place in the
source. And it comes first because no other answer is worth giving
about a rewrite that could change what the program prints: an
annotation, a size or a loop doesn't matter if the layout change could
be seen.

The annotation rungs come next. An `aosoa(N)` annotation has its block
size checked (only powers of two from 2 to 65536 are
accepted<Cite id="rust-std-is-power-of-two" />, for reasons *AoSoA and
hot/cold in Rust* and *Block sizes and typed columns in Rust*
explain), and then any annotation returns at
once: `aos` keeps the collection, and `soa` or `aosoa(N)` transforms it
with the reason `annotated @viscosity soa at line 1` followed by the
usual description. That return happens before the cost rungs, so an
annotated collection is transformed even when it looks too small to
pay off, which is the point of annotating it. After that come opt-in
mode (`opt-in mode: not annotated`) and Python without
`--python-auto`, and then the first two questions of cost (strings
elided with `…`):

```rust
if c.numeric_fields.is_empty() {
    return keep(vec![
        "no field is … to gain".into()]);
}
if !c.loops.iter().any(|l| l.depth > 0) {
    return keep(vec![
        "no loop reads … pay off".into()]);
}
```

With no field proven numeric, every column would be a plain array, and
there are no `Float64Array` columns to gain. With no loop table of depth
1 or more (the depth-0 table holds accesses outside every loop), no loop
would get faster. `.into()` turns the `&str` literal into the `String`
the `Vec` holds. The last rung, the size threshold, is the subject of
the next chapter, *Sizes and thresholds in Rust*; a collection that
passes it too becomes `Layout::Soa`.

<Formal title="The ladder as a first match">

```text
plan(c) = Aos(unsafe: b₁, …, unsafe: bₙ)
                         if n > 0
        = follow(ann)    if annotated
        = Aos(rᵢ)        if rung i refuses
        = Soa(describe(c))   otherwise
```

<span slot="read">The plan of a collection c is decided by the first
line whose condition holds, read from the top: if c has n bailouts b1 to
bn, keep it with one unsafe reason per bailout; otherwise, if it is
annotated, follow the annotation; otherwise, if some later rung i
refuses, keep it with that rung's reason; and only if nothing refuses,
store it as a struct of arrays, with the description of what it
gains.</span>
</Formal>

<Examples of="rust-cost-model">

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ name: 'p' + i });
for (let i = 0; i < ps.length; i++)
  ps[i].name += '!';
// no field is provably numeric, …
```

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
console.log(ps[3].x);
// no loop reads or writes its fields, …
```

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
const keep = [];
for (let i = 0; i < ps.length; i++)
  if (ps[i].x > 3) keep.push(ps[i]);
console.log(ps, keep.length);
// unsafe: the array is passed to a
//   method call at line 7
// unsafe: line 6: an element is used
//   by push
```

</Examples>

The comments are the Rust CLI's reasons, the same bytes the TypeScript
CLI prints. The first program is safe and has a hot loop, but its only
field holds strings, so it stops at the numeric rung. The second has a
numeric field, but its one read is outside every loop, so it stops one
rung later. The third has two problems, and gets two reasons in the order the analysis found
them: `console.log(ps, ...)` hands the whole array to a function the
compiler can't see into, and `keep.push(ps[i])` lets an element escape
into another array.

<Callout kind="definition">
The **cost model in Rust** is `plan_one` in `plan.rs`, called by `plan`
once per collection: a **ladder of early returns**, each built by the
**`keep` closure**. Safety comes first, with **one `unsafe:` reason per
bailout**; then annotations, which skip the cost rungs; then opt-in mode
and Python; then the cost rungs (**some field numeric**, **some loop of
depth ≥ 1**, and the size threshold). A collection that passes every
rung becomes `Layout::Soa`, with reasons from `describe`.
</Callout>

## What you learned

- `plan` calls **`plan_one`** once per collection; each refusal is an
  **early `return`** where the reference writes `push` and `continue`.
- The **`keep` closure** builds a kept plan from a `Vec<String>` of
  reasons; plans hold a **clone** of their collection, so they don't
  borrow from the analysis.
- **Safety is the first rung**, with **one reason per bailout**, which
  `--frames` relies on. **Annotations** come next and skip the cost
  rungs, but never safety.
- The cost rungs refuse a collection with **no numeric field** or **no
  loop of depth ≥ 1**, and then, in the next chapter, one that is too
  small.

## One collection, three verdicts

*The cost model in Rust* walked down the planner's ladder to its last
rung: is the collection big enough to be worth changing? A layout
change has fixed costs (a container class, a copy when the array
grows), and on a few dozen elements they can outweigh the gain, so the
planner leaves small collections alone. This program pushes inside an
`if`, so only every fourth trip adds an element:

```js
const ps = [];
for (let i = 0; i < 100; i++)
  if (i % 4 === 0) ps.push({ x: i });
for (let i = 0; i < ps.length; i++)
  ps[i].x += 1;
```

Here is what the Rust CLI decided about it with the default options,
with a higher threshold, and with a profile written by `viscosity
profile` (I ran all three here; the reason lines are wrapped, and the
TypeScript CLI printed the same bytes each time):

```
$ viscosity explain l1.js
  · at most 100 elements
$ viscosity explain l1.js --min-size 200
  · at most 100 elements: below the
    200-element threshold, where …
$ viscosity explain l1.js --profile p.json
  · about 25 elements (measured): below
    the 64-element threshold, where …
```

The first is transformed, the other two are kept, and every word of
those lines comes from about fifteen lines of `plan_one` in
`crates/core/src/plan.rs`.

<Analogy title="a forecast and a thermometer">
A forecast says "up to 30 degrees tomorrow"; a thermometer on the wall
says 18. When you have the reading, you go by the reading; when you
only have the forecast, you plan for its top end; and with neither, you
take a coat and sunglasses both.
<span slot="breaks">A forecast is a probability and can be wrong in
either direction; the analysis's "at most" is a real bound (the program
can never hold more), so only the low side is uncertain.</span>
</Analogy>

<Analogy extra title="a free-delivery minimum">
A shop delivers for free on orders of 20 pounds or more. Under the
minimum it isn't worth sending the van; over it, it is; and if the till
can't read the total, the shop sends the van anyway rather than lose
the customer.
<span slot="breaks">A shop loses only a delivery charge when it guesses
wrong; when the planner guesses wrong, the program still prints exactly
the same output, only a little slower or faster, because the change was
proven safe on an earlier rung.</span>
</Analogy>

## The rung

From `plan.rs`, rewrapped, with the long message cut short:

```rust
let measured = opts.profile.as_ref()
    .and_then(|p| p.get(&c.name))
    .copied();
let size = measured.or(c.size_estimate);
if let Some(size) = size {
    if size < opts.min_size {
        return keep(vec![format!(
            "{} {} elements{}: below the …",
            if measured.is_none()
                && c.size_is_upper_bound
            { "at most" } else { "about" },
            js_number(size),
            if measured.is_some()
            { " (measured)" } else { "" },
            js_number(opts.min_size)
        )]);
    }
}
```

The first three lines look the collection up in the profile, if there
is one. `opts.profile` is an `Option<HashMap<String, f64>>`;
`as_ref()` borrows what is inside rather than moving it out;
`and_then` runs the lookup only when there is a map, and `get` returns
`Option<&f64>`; `copied` turns that into an `Option<f64>`. So
`measured` is `Some(25.0)` when the profile has `ps`, and `None`
otherwise.

`measured.or(c.size_estimate)` keeps the first value if there is one,
and only otherwise takes the second<Cite id="rust-std-option-or" />, so
a measurement always wins over the estimate. `if let Some(size) = size`
then runs the comparison only when there *is* a size, which makes the
unknown case explicit: no size, no refusal. The four placeholders of
`format!` fill in the word ("at most" only for an estimate that is a
maximum), the size, the " (measured)" note and the threshold, and
`js_number` prints a number the way JavaScript would, `100` rather than
Rust's `100.0`, which keeps the text byte-identical to the reference's.

## Four kinds of size

Each kind of size meets the threshold in its own way, and each choice
is a bet. A **measured** size is a fact about one real run, so it is
used as it is, and always worded "about". An **estimate** is used as the
size. A **maximum** is used as if it were the size: "at most 100"
passes a threshold of 64, although this program holds 25, because the
planner would rather transform a collection that might be big than miss
one that is. A maximum *below* the threshold is a safe refusal, since
the real size can only be smaller. And an **unknown** size passes,
because a collection the analysis can't count (pushes inside a
function, a loop with no constant bound) may well be large.

<Formal title="The size rung">

```text
size = measured ?? estimate
keep  ⇔  size ≠ none ∧ size < min_size
```

<span slot="read">The size is the measured one if there is one,
otherwise the estimate (which may itself be missing). The collection is
kept exactly when there is a size and it is less than the threshold; in
every other case the rung lets it through.</span>
</Formal>

<Examples of="rust-cost-model">

```
small: at most 40 (estimate), min 64
  · at most 40 elements: below the
    64-element threshold, …
```

```
evens: at most 100, measured 50
  · about 50 elements (measured): below
    the 64-element threshold, …
```

```
small with a profile of 1000
  · about 1000 elements (measured by
    profiling)
```

</Examples>

All three come from the test program `tests/extra/upper_bound.js`
and its profile `tests/profiles/extra_upper_bound.json`, run through
the Rust CLI. In the first, `small` pushes on one trip in three of a
loop of 40, so the estimate is "at most 40", and a maximum below 64 is
kept. In the second, `evens` is "at most 100" by estimate and would
pass, but the profile says 50, which wins and is below 64. The third is
`small` again with the profile, which (hand-written for the test)
claims 1000 elements: a measurement can raise a size as well as lower
it, and the collection is transformed, with `describe` adding "(measured
by profiling)" to the size line.

## When the threshold disappears

The comparison is a plain `f64` `<`, and that has one odd consequence,
in both engines. Every comparison with `NaN` (the "not a number" value
of floating point, *How JavaScript stores numbers and objects*) is
false, so a `min_size` of `NaN` makes `size < opts.min_size` false for
every size, and the rung silently stops refusing anything. Both CLIs
once let `--min-size abc` through as `Number("abc")`, which is `NaN`.
Now both refuse it before planning, with the same words (the Rust check
is in `crates/cli/src/main.rs`):

```
$ viscosity explain l1.js --min-size abc
viscosity: --min-size must be a
non-negative number
```

A blank value is refused too, because JavaScript's `Number("")` is `0`,
not `NaN`. Only a program that calls the library directly can still
pass `NaN`. The default comes from `impl Default for PlanOptions`,
written by hand: auto mode, `min_size: 64.0`, bounds checks on, no
annotations, no profile, and no `python_auto`.

## A sentence the fixtures never saw

When the Rust chapters were first written, the profiled line in Rust
read `about 25 (measured) elements: below`. The format string was
`"{} {}{} elements: below …"`, so the third placeholder, " (measured)",
landed before the word "elements", while the TypeScript reference
writes `${size} elements${...}`: the same decision, worded differently.
Nothing caught it, because the 186 parity fixtures of that day compiled
every program with the default options and with `--bounds assume`, never
with `--profile`, and the fuzzer passed no profile either. Parity holds
only for what is tested. The fix moved the placeholder and added the
missing tests: four profiles in `engine/rust/tests/profiles`, checked
through both the library and the CLI's `--profile` by
`profiled_output_equals_typescript_output` in `parity.rs` (beside the
190 parity pairs, not among them), and a random profile for each batch
of the fuzzer. A run of 300 programs with seed 1 here ended `fuzz: seed 1, 300 programs (134
transformed, 174 may go out of bounds, 20 with an early error), 0
failing`.

<Callout kind="definition">
The **size rung** of `plan_one` takes the **measured** size from the
profile if there is one, else the **estimate** (`measured.or(...)`). A
known size **below `min_size`** keeps the collection, with "at most"
only for an unmeasured maximum and " (measured)" for a measurement; an
**unknown** size passes. A collection that passes becomes
`Layout::Soa`, and `describe` lists its loops, columns, size and bounds
proofs.
</Callout>

## What you learned

- The size is **`measured.or(estimate)`**: a profile's measurement wins,
  in either direction.
- **`if let Some(size)`** makes an **unknown** size pass; a **maximum**
  is treated as the size, and a maximum below the threshold is a safe
  refusal.
- A **`NaN`** threshold makes every `<` false, so both CLIs refuse
  `--min-size` values that aren't non-negative numbers.
- Byte parity covers **only what the fixtures exercise**: the measured
  threshold message once differed between the engines, and profile
  fixtures and fuzzed profiles now check it.
