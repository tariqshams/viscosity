## One byte, two ways

Every instruction the Drip VM runs starts by reading a byte, and drip-rs
does it like this (from `vm.rs`):

```rust
fn read_byte(&mut self) -> u8 {
    let byte = self.chunk.code[self.ip];
    self.ip += 1;
    byte
}
```

`code[self.ip]` compares `ip` with the length of `code` first, every
time, and panics if it is past the end; a VM written in C reads through a
pointer and checks nothing. Rust can read the C way too: slices have a method,
`get_unchecked`, that skips the check. drip-rs chose not to use it, and
one line at the top of its `lib.rs` makes that permanent:
`#![forbid(unsafe_code)]`.

<Analogy title="a staff-only door">
Safe Rust is a building where every door checks your badge. `unsafe` is
a staff-only door: behind it a few extra rooms open, and in those rooms
nobody checks badges for you. You sign the logbook on the way in (a
`SAFETY` comment), and whatever happens in there is on you.
<span slot="breaks">Behind a real staff door the ordinary rules may be
relaxed too; behind `unsafe`, every other check (types, borrows) still
runs exactly as before. Only the few extra rooms are new.</span>
</Analogy>

## Calling an unsafe function

`get_unchecked` is an **`unsafe fn`**: a function whose callers must keep
a promise the compiler cannot check, here that the index is less than
the length<Cite id="rust-std-slice-get-unchecked" />. Called outside an
`unsafe` block it is rustc 1.97's error E0133, `call to unsafe function
... is unsafe and requires unsafe function or block`. Step through four
ways to read one element, and what each costs:

<UncheckedSteps client:visible />

<Examples of="unsafe">

```rust
let xs = [10, 20, 30];
// SAFETY: 1 < xs.len() == 3.
let v = unsafe { *xs.get_unchecked(1) };

/// # Safety
/// The caller must make sure that
/// `i < xs.len()`.
unsafe fn at_unchecked(xs: &[f64],
    i: usize) -> f64 {
    // SAFETY: the caller promised it.
    unsafe { *xs.get_unchecked(i) }
}
```

</Examples>

The first part is the smallest use: one unsafe call, the `*` copying the
value out of the reference `get_unchecked` returns, and a `SAFETY`
comment saying why the promise holds, so `v` is 20. The second is an
`unsafe fn` of your own: a `# Safety` doc section says what callers must
promise, and the body's `unsafe` block has its own `SAFETY` comment, the
habit the Rust book recommends<Cite id="klabnik2026" />.

<Callout kind="definition">
An **`unsafe` block** marks code in which you may use a few extra
operations whose rules the compiler cannot check; everything else in it
is checked as usual. An **`unsafe fn`** is one whose callers must keep a
promise, so calling it needs `unsafe` too. A **`// SAFETY:`** comment
says what the promise is and why it holds<Cite id="klabnik2026" />.
</Callout>

## What unsafe unlocks, and what it does not

The Rust book lists five things only `unsafe` allows: dereference a raw
pointer, call an `unsafe` function or method, read or write a mutable
`static`, implement an `unsafe` trait, and read the fields of a
`union`<Cite id="klabnik2026" /> (the Reference adds a few rarer
ones<Cite id="rustref-unsafety" />). What `unsafe` does **not** do is
switch anything off: take `&v[0]`, then `v.push(4)`, then use the
reference, all inside `unsafe { }`, and rustc 1.97 warns `unnecessary
unsafe block` and then rejects the program with the ordinary E0502
borrow error.

The promise is narrow, but real: break it, and the result is **undefined
behaviour**. That is not a panic; the compiler optimises on the
assumption that it never happens, so anything at all may follow,
including nothing visible<Cite id="rustref-ub" />. Reading index 3 of a
three-element array with `get_unchecked`, a rustc 1.97 debug build
stopped with `unsafe precondition(s) violated`; that check is optional
and gone from release builds. The tool for finding such bugs is **Miri**, an
interpreter for Rust that runs your program or tests slowly and checks
every memory access<Cite id="miri-readme" />; it only checks the runs you
give it, so a clean run proves nothing<Cite id="klabnik2026" />.

## Safe on the outside

<Figure takeaway="Callers see only a safe function; its own check makes the unsafe line's promise true." caption="The usual shape of unsafe code: a safe function whose check proves the SAFETY comment, around an unsafe block of one line.">
  <SafeShell />
</Figure>

The usual shape is the figure's: a small, safe function whose own check
makes the promise true, so no caller can make it misbehave. Such a function is
called **sound**. Soundness depends on *safe* code too, as the
Rustonomicon points out with exactly this kind of function: change the
check from `i >= xs.len()` to `i > xs.len()`, a change in no `unsafe`
block at all, and `at(&xs, 3)` reads past the end<Cite id="nomicon-working-with-unsafe" />.
That is how `Vec`, slices and `String` are built: safe methods over a
little audited `unsafe` code inside the standard library.

`#![forbid(unsafe_code)]` turns the `unsafe_code` lint to its strictest
level for the whole crate: any `unsafe` block is an error (`usage of an
unsafe block`), and unlike `deny`, a later `#[allow(unsafe_code)]`
cannot undo it (rustc 1.97 answers E0453, `allow(unsafe_code)
incompatible with previous forbid`). It cost drip-rs no pointers between
heap objects, since the arenas and `Gc<T>` handles of *Arenas and typed
indices* replaced them; the cost is the checks, in `read_byte` and in
every `heap[handle]`. To put a number on it, I copied drip-rs into
a scratch folder, removed the `forbid`, replaced five checked reads with
`get_unchecked` (in `read_byte`, `read_constant`, `peek` and the arena's
two index methods), and timed both release builds (rustc 1.97) on five
corpus benchmarks, seven alternating runs each, twice, on a shared cloud
VM: the unchecked build's fastest run was 4 to 18 percent quicker, and
its median was quicker on every program. What drip-rs bought is just as
concrete: with its `debug_gc` option on, a freed slot is never
reused, so a collector that missed a root panics on use instead of
quietly reading whatever moved in.

<More title="The measurement, run by run">

Checks that never fail are cheap, because the branch predictor learns
that the index is always in bounds, but they are not free. Fastest of
seven runs, checked / unchecked, in milliseconds; both builds
printed the same output for every program.

```text

fib            402 / 380   403 / 373
method_calls   164 / 157   168 / 152
fields         186 / 167   186 / 162
instantiation  146 / 130   140 / 129

```

The shared VM is noisy (`fib`'s slowest checked run was 530 ms), which is
why the fastest and the middle runs are the ones to compare, and why two

## An address without promises

A Rust reference, `&T`, is an address plus a set of promises the
compiler checks: it is never null, it points at a live, correctly
aligned `T`, and the borrowing rules hold for as long as it lives. A
**raw pointer** is the same address with every one of those promises
taken off.

<Figure takeaway="A reference is an address the compiler vouches for; a raw pointer is an address nobody vouches for." caption="What each kind of pointer promises. Making a raw pointer is safe; everything after that is your job.">
  <RefVsRaw />
</Figure>

<Examples of="raw-pointer">

```rust
let mut n = 41;
let r: *const i32 = &raw const n;
let w: *mut i32 = &raw mut n;
let z: *const i32 = std::ptr::null();
let p = [1.5, 2.5, 4.0].as_ptr();
println!("{}", unsafe { *r }); // 41
```

</Examples>

The first five lines make raw pointers, all in safe code: `&raw const n`
and `&raw mut n` take `n`'s address without making a reference,
`std::ptr::null()` is address 0, and `as_ptr` gives a slice's first
element's address. A
`*const` and a `*mut` to the same variable exist side by side, which
`&n` and `&mut n` never could. Reading through one is the unsafe part:
without the block it is E0133 again, `dereference of raw pointer is
unsafe`, with rustc 1.97's note that "raw pointers may be null, dangling
or unaligned"; inside it the last line prints `41`.

<Callout kind="definition">
A **raw pointer** is `*const T` (read through it) or `*mut T` (read and
write through it): an address with no safety or liveness guarantees. It
may be null, dangling or misaligned. You make one with `&raw const` or
`&raw mut` (or `as_ptr`); making, copying and comparing them is safe,
and **dereferencing** one is an unsafe operation<Cite id="rustref-raw-pointer" />.
</Callout>

## Walking a buffer

`p.add(i)` moves a pointer on by `i` *elements*, not bytes, so on a
pointer to `f64` it adds `8 × i` to the address. For a pointer to the
start of `len` elements, `add` may go as far as one past the end (a
pointer you may compare but not read), and a read must stay strictly
inside, which is why `for i in 0..len { *p.add(i) }` is fine and
`0..=len` is not. Step through reading an array, first safely and then
through a pointer:

## What you learned

- An **`unsafe` block** unlocks five extra operations, such as calling an
  **`unsafe fn`**; it switches no checks off. Breaking its promise is
  **undefined behaviour**, which Miri and debug builds catch only
  sometimes.
- Keep `unsafe` inside a small safe function whose own check makes the
  promise true; drip-rs's `#![forbid(unsafe_code)]` rules it out.
- A **raw pointer** is an address without a reference's promises; making
  one is safe, reading through it needs `unsafe`.
