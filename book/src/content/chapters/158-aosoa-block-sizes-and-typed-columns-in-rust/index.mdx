## Blocks of four

A struct of arrays puts each field in its own array, so a loop over `x`
and `vx` reads two arrays that may sit far apart in memory. *When SoA
loses: materialization and AoSoA* described the middle way, an **array
of structs of arrays** (AoSoA): small blocks of elements, and inside
each block the values of one field side by side. Viscosity builds it
only when you ask, with an annotation, because *AoSoA code generation*
measured that V8 rarely rewards it. Here is a request:

```js
// @viscosity aosoa(4)
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, y: 2 * i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
```

`viscosity explain` (I ran the release build here, rustc 1.97) answers
`ps (line 2) {x, y, vx} → AoSoA, blocks of 4`. This chapter reads how
the Rust emitter lays that out and writes the arithmetic that finds a
field; the next one, *Block sizes and typed columns in Rust*, reads the
rules about which block sizes are allowed, and the port's other split,
by type.

<Analogy title="egg boxes on a shelf">
Three hens lay one egg a day each, and you pack them in boxes that
hold four days: a row for the first hen's four eggs, a row for the
second's, a row for the third's. To find hen 2's egg from day 13, you
count whole boxes (13 ÷ 4 = 3 boxes along), go to her row, and step to
place 1 in it.
<span slot="breaks">A shelf of boxes is fixed; the array grows, by
copying into one twice as long. That moves nothing, because an egg's
place depends only on its day and its hen, never on how many boxes
there are.</span>
</Analogy>

<Analogy extra title="a week of eight days">
With seven-day weeks, "which week and which weekday is day 45?" needs
a division. If weeks had eight days and you wrote day numbers in base
8, the answer would be the digits themselves: `55` in base 8 is week
5, day 5.
<span slot="breaks">Nobody counts days in base 8; a computer counts
everything in base 2, which is why blocks of 2, 4, 8 or 16 make the
digits do the work, and blocks of 6 don't.</span>
</Analogy>

## The slot of a field

With `F` fields and blocks of `B` elements, one `Float64Array` named
`data` holds everything. Block number `i / B` (rounded down) starts at
slot `(i / B) * F * B`. Inside it, field `k` has its own run of `B`
slots starting at `k * B`, and element `i` sits at lane `i % B` of that
run. Step through it for the program above, where `F = 3` and `B = 4`:

<AosoaSteps client:visible />

When `B` is 2 to the power `sh`, dividing by `B` and rounding down is
shifting `i` right by `sh` bits, and the remainder is the low `sh` bits,
which `i & (B - 1)` keeps: in binary, the block and the lane are simply
two parts of the same number.

<Figure caption="Element 13 with blocks of 4: the top bits are the block, the bottom two bits the lane. Blocks of 6 have no such split." takeaway="A power-of-two block size makes the block and the lane two pieces of the index's bits.">
  <ShiftMask />
</Figure>

<Formal title="The AoSoA slot">

```text
B = 2^sh,  B ≥ 2
slot(i, k) = (i >> sh) · F·B
           + k · B
           + (i & (B − 1))
```

<span slot="read">The block size B is 2 to the power sh, and at least
2. Field k of element i is at: i shifted right by sh (the block number)
times F times B (the slots in one block), plus k times B (where field
k's run starts inside the block), plus i with all but its low sh bits
cleared (the lane).</span>
</Formal>

For the program above, the emitter writes this `push` (from the
release CLI's output, reformatted):

```js
push(v0, v1, v2) {
  const n = this.length;
  if (n === this.cap) this.grow();
  const b = (n >> 2) * 12 + (n & 3);
  this.data[b + 0] = v0;
  this.data[b + 4] = v1;
  this.data[b + 8] = v2;
  return (this.length = n + 1);
}
```

`b` is the slot of field 0 of the new element `n`, so the three values
go to `b + 0`, `b + 4` and `b + 8`, one run of four further each. The
constructor rounds the capacity up to whole blocks
(`Math.ceil(cap / 4) * 4`), so the last block's runs always fit, and
`grow()` copies the old array into the front of one twice as long with
`set`; since a slot depends only on `i` and `k`, never on the capacity,
growing moves nothing. And the loop body `ps[i].x += ps[i].vx` becomes
(wrapped):

```js
ps.data[((i) >> 2) * 12 + 0 + ((i) & 3)]
  += ps.data[((i) >> 2) * 12 + 8
    + ((i) & 3)];
```

## The arithmetic in Rust

`emit.rs` builds that text in a closure, `slot`, which every rewritten
access calls. Its AoSoA half (rewrapped):

```rust
let sh = log2_exact(b)
    .expect("checked by container_class");
let bf = b as f64;
let (stride, off, mask) = (
    js_number(nf * bf),
    js_number(k as f64 * bf),
    js_number(bf - 1.0),
);
let at = if simple_idx {
    format!("(({idx}) >> {sh}) * {stride} \
        + {off} + (({idx}) & {mask})")
} else {
    need_aosoa = true;
    format!("__vsc_aosoa({idx}, {sh}, \
        {stride}, {off}, {mask})")
};
format!("{arr}.data[{at}]")
```

The three constants are computed as `f64` and printed by `js_number`,
which formats a number the way JavaScript prints it, so the text is
byte for byte what the TypeScript reference computes with its doubles.
The inline form writes the index twice, so it is used only for a
**simple** index (an identifier or a literal, already proven or assumed
in bounds), which is safe to repeat. Anything else, such as a call to
`__vsc_bc`, must run exactly once, so it is passed to a helper instead,
`__vsc_aosoa(i, sh, stride, off, mask)`, and `need_aosoa` makes sure the
helper is added to the prelude. The shift comes from a one-line
function:

```rust
fn log2_exact(b: u64) -> Option<u32> {
    b.is_power_of_two()
        .then(|| b.trailing_zeros())
}
```

`is_power_of_two` is true when exactly one bit of `b` is set, and
`trailing_zeros` counts the zero bits below it, which is the
shift<Cite id="rust-std-is-power-of-two" />: `8` is `0b1000`, so
`Some(3)`, and `6` is `0b110`, so `None`. `bool::then` runs the closure
only when the test is true. The reference computes the same thing as
`Math.log2(b)`, checked with `Number.isInteger`.

<Examples of="rust-aosoa">

```js
const b = (n >> 2) * 12 + (n & 3);
// push: field 0 of new element n
```

```js
ps.data[((i) >> 2) * 12 + 8
  + ((i) & 3)]
// vx (k = 2) of a proven index i
```

```js
ps.data[__vsc_aosoa(
  __vsc_bc(ps, 10, 'y', false),
  2, 12, 4, 3)]
// y (k = 1) of ps[10], not proven
```

</Examples>

All three are from the Rust CLI's output for the program above, with
`console.log(ps[10].y)` added at the end. The first is the push: block
`n >> 2`, lane `n & 3`, field 0. The second is the inline form for a
proven index: stride 12, offset `2 × 4 = 8` for `vx`, mask 3. The third
is a constant index outside any loop, which isn't proven, so the index
is a `__vsc_bc` call, and the arithmetic moves into `__vsc_aosoa` with
shift 2, stride 12, offset 4 and mask 3; node prints `20` for both the
original and the compiled program.

<Callout kind="definition">
**AoSoA in Rust** stores a collection of `F` numeric fields in one
`Float64Array`, `data`, in **blocks** of `B = 2^sh` elements, field-major
inside each block, and puts field `k` of element `i` at **`(i >> sh) *
F·B + k·B + (i & (B − 1))`**. The `slot` closure in `emit.rs` writes
that inline for a **simple** index, and through **`__vsc_aosoa`** for
any other; `log2_exact` gives `sh` with `is_power_of_two` and
`trailing_zeros`.
</Callout>

<Prompts ids={['ao-simple', 'ao-log2', 'ao-js-number', 'ao-shift-why']} />

<Callout kind="engine" label="Under the hood">
ISPC builds this layout into its language: an `soa<8>` type stores 8
values of each field in turn, and indexing it does the same block, lane
and offset arithmetic<Cite id="ispcdocs" />. There the block matches the
SIMD lanes, so one load fills a register. JavaScript has no such loads,
which is why Viscosity keeps AoSoA behind an annotation. (And
JavaScript's `>>` takes its shift count modulo 32<Cite id="ecma262-signed-right-shift" />,
which the next chapter shows matters for huge blocks.)
</Callout>

## What you learned

- AoSoA puts field `k` of element `i` at **`(i >> sh) * F·B + k·B +
  (i & (B − 1))`**, in one `Float64Array`, and growing moves nothing.
- A **power of two** turns division and remainder into a **shift** and
  a **mask**; `log2_exact` is `is_power_of_two` then `trailing_zeros`.
- The `slot` closure inlines the arithmetic for a **simple** index and
  calls **`__vsc_aosoa`** otherwise, so an index with effects runs once;
  `js_number` keeps the constants byte-identical to the reference's.

## Four is fine, six is not

*AoSoA in Rust* showed that the emitter finds an AoSoA
slot with a shift and a mask, which only works when the block size is a
power of two. So something has to refuse the others. Put `aosoa(6)`
above the `{x, y, vx}` program of that chapter, and the Rust CLI says
(I ran it here, release build, rustc 1.97; wrapped):

```
ps (line 2) {x, y, vx} → kept as array
  of objects
  · annotated aosoa(6), but the block
    size must be a power of two (2, 4, 8,
    16, ...)
```

The same happens for `aosoa(0)`, `aosoa(1)`, `aosoa(3)`, `aosoa(x)`
and `aosoa()`, while `aosoa(4)`, `aosoa(65536)` and a bare `aosoa`
(which means blocks of 8) are accepted; the TypeScript CLI printed the
same bytes for every one of them. This chapter reads where that rule
lives, why it also has an upper end, and then the port's other split of
a record's fields.

<Analogy title="a prescription checked twice">
A doctor writes a dose, the pharmacist checks it against the safe
range before filling it, and the label printer refuses a dose it cannot
print. The patient should only ever meet the first refusal; the later
checks are there so that a slip upstream shows up as a refusal, never
as the wrong pills.
<span slot="breaks">A pharmacist can phone the doctor and agree a
different dose; the planner never adjusts what was written, it refuses
it and says why, quoting the annotation as you wrote it.</span>
</Analogy>

<Analogy extra title="sorting laundry by fabric">
You can sort a wash by fabric (wool here, cotton there) or by how often
you wear things. Sorting by fabric is easy to get right, because the
label tells you; sorting by use needs a record of what you wore.
<span slot="breaks">You can re-sort the laundry every week; a column's
kind is fixed when the program is compiled, from a proof about every
value the field could ever hold.</span>
</Analogy>

## The rungs that refuse

The rule is two rungs of `plan_one` in `crates/core/src/plan.rs`, run
only for an `aosoa` annotation, right after the safety rung of *The
cost model in Rust*. Step through them on six annotations:

<BlockRungSteps client:visible />

The parser (`parse_annotation`, in `crates/frontend-js/src/lib.rs`)
hands the planner two fields: `block_text`, whatever was written
between the brackets (`None` if there were no brackets), and
`block_size`, that text as a number when it is made only of digits. The
`match` turns the pair into `b`, an `Option<u64>`. If something was
written but it isn't a whole number, `b` is `None`; otherwise it is the
number, or 8 when nothing was written. Then `is_some_and(|b| b >
MAX_BLOCK_SIZE)` is true only for a number above the limit, and
`!b.is_some_and(|b| b >= 2 && b.is_power_of_two())` is true for `None`
and for every number that isn't a power of two from 2 up. `1` needs
the `b >= 2`, because 1 is 2⁰ and so `1.is_power_of_two()` is
true<Cite id="rust-std-is-power-of-two" />.

<Formal title="Accepted block sizes">

```text
accept(B) ⇔ B = 2^s for some
            whole s with 1 ≤ s ≤ 16
```

<span slot="read">A block size B is accepted exactly when it is 2 to
the power s for a whole number s from 1 to 16: that is 2, 4, 8, and so
on up to 65536, and nothing else.</span>
</Formal>

The same rule is checked twice more, downstream. `container_class` in
`emit.rs` returns `CompileError("AoSoA block size must be a power of
two")` if `log2_exact` gives `None`, and the `slot` closure then calls
`log2_exact(b).expect("checked by container_class")`. Because the
planner refuses first, neither can fire for a program the CLI compiles;
they are there so that a mistake in one place shows up as an error
rather than as wrong arithmetic in your program.

## Why there is an upper limit

When the Rust chapters were first written, there was no rule at the
top end, in either engine. Both accepted `aosoa(1073741824)`, which is
2³⁰. The constructor then asked for `new Float64Array(2³¹ * 3)`, and
node stopped with `RangeError: Array buffer allocation failed` for a
program whose original runs fine. From 2³² up the arithmetic would have
been wrong as well, because JavaScript takes the count of a shift
modulo 32<Cite id="ecma262-signed-right-shift" />, so `i >> 32` is `i`.
And at 2⁶⁴ the two engines disagreed: the port parses the digits as an
`f64` and converts with `as u64`, which saturates at the largest `u64`
(the comment in `parse_annotation` says so), and refused the result,
while the reference accepted it. One limit closes all three holes, and
both engines now have it, checked before the power-of-two rule (from
`plan.rs`, rewrapped):

```rust
/// The largest AoSoA block size (2^16).
/// Larger blocks gain nothing, cost a
/// lot of memory per block, and break the
/// shift arithmetic from 2^32 up.
pub const MAX_BLOCK_SIZE: u64 = 65536;
```

so the old annotation now gets `annotated aosoa(1073741824), but the
block size must be at most 65536`. The test program
`tests/extra/aosoa_block_sizes.js` holds these cases, and the parity
test compares both engines on it.

<Examples of="rust-aosoa">

```
// @viscosity aosoa(3)
  · annotated aosoa(3), but the block
    size must be a power of two …
```

```
// @viscosity aosoa(131072)
  · annotated aosoa(131072), but the
    block size must be at most 65536
```

```
// @viscosity aosoa(4)  on {x, name}
  · annotated aosoa, but fields name
    may hold non-numbers
```

</Examples>

All three are the Rust CLI's reasons for a two- or three-field program
with a loop. Three isn't a power of two. 131072 is 2¹⁷, a power of
two but over the limit, and the limit is checked first. And the third
is one more AoSoA rung: every field shares the one `Float64Array`
`data`, so a record with a string field has nowhere to keep it, and the
planner refuses with the names of the fields that may hold something
else.

## Hot and cold, by type

*Hot/cold splitting* described splitting a record into **hot** fields,
used by the busy loops, and **cold** ones, so the busy loops read less
memory. The port has a split too, but it is by **type**, not by heat.
`describe` in `plan.rs` partitions the fields (rewrapped):

```rust
let (typed, generic): (Vec<&str>,
    Vec<&str>) = c.fields.iter()
    .map(String::as_str)
    .partition(|f| {
        c.numeric_fields.contains(*f)
    });
```

`partition` walks an iterator once and splits it into two collections,
those for which the closure is true and those for which it is false.
`container_class` makes the same split when it writes the constructor:
`new Float64Array(cap)` for each field proven always a number, `[]` for
the rest. The corpus program `mixed_columns.js` has records `{ id, hp,
x, tag }`, and explain says (wrapped):

```
  · typed Float64Array columns for hp, x;
    plain array columns for id, tag (may
    hold non-numbers)
```

<Figure caption="The columns of mixed_columns.js: the busy loop touches hp, x and tag, but only the numeric fields get typed arrays." takeaway="Viscosity chooses a column's kind by type, never by how often it is used.">
  <TypedPlain />
</Figure>

`tag` is read in the hottest loop and still gets a plain column, and a
numeric field that no loop touched would still get a typed one. So the
honest name for this split is "typed and plain", not "hot and cold".
What would a real split by heat need? The access tables of *Access
patterns in Rust* already record, for each loop, which fields it
touches together (*Hot/cold splitting* called this **field
affinity**), but
nothing in `plan.rs` reads them for grouping. And since every field
already has a column of its own, grouping would only matter where
fields share storage: in AoSoA's blocks, which today put every field in
every block.

<Callout kind="definition">
The **block-size rungs** of `plan_one` accept an `aosoa(B)` annotation
only when **`B` is a power of two from 2 to 65536** (`MAX_BLOCK_SIZE`)
and every field is numeric, refusing anything else with a reason that
quotes what was written; `emit.rs` checks the power of two again. The
port's **typed/plain split** gives each field a `Float64Array` column
when it is proven always a number and a plain array otherwise, chosen
by type alone.
</Callout>

## What you learned

- The planner refuses an `aosoa` block size that is **not a power of
  two**, is **below 2**, is **above 65536**, or was written but is **not
  a whole number**; a bare `aosoa` means **8**.
- The rule is checked **three times** (planner, `container_class`,
  `slot`), so a slip upstream becomes an error, not wrong arithmetic.
- The upper limit closed three holes at once: an allocation failure,
  shift counts taken **modulo 32**, and the engines disagreeing at 2⁶⁴.
- Viscosity's "hot/cold" split is **by type**: typed columns for proven
  numbers, **plain** columns for everything else.
