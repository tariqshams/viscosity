## Blocks of four

*SoA code generation in Rust* gave each field its own column, which may
sit far from the others. *AoSoA and hot/cold splitting* described the
middle way, an **array of
structs of arrays** (AoSoA): small blocks of elements, and inside each
block the values of one field side by side. Viscosity builds it only
when you ask, because V8 rarely rewards it, and here is a request:

```js
// @viscosity aosoa(4)
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, y: 2 * i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
```

The Rust CLI (release build, rustc 1.97) answers `ps (line 2) {x, y,
vx} → AoSoA, blocks of 4`.

<Analogy title="egg boxes on a shelf">
Three hens lay one egg a day each, and you pack them in boxes that hold
four days: a row for the first hen's four eggs, a row for the second's,
a row for the third's. To find hen 2's egg from day 13, you count whole
boxes (13 ÷ 4 = 3 boxes along), go to her row, and step to place 1 in it.
<span slot="breaks">A shelf of boxes is fixed; the array grows, by
copying into one twice as long. That moves nothing, because an egg's
place depends only on its day and its hen, never on how many boxes
there are.</span>
</Analogy>

<Analogy extra title="a week of eight days">
With seven-day weeks, "which week and which weekday is day 45?" needs a
division. If weeks had eight days and you wrote day numbers in base 8,
the answer would be the digits themselves: `55` in base 8 is week 5,
day 5.
<span slot="breaks">Nobody counts days in base 8; a computer counts
everything in base 2, which is why blocks of 2, 4, 8 or 16 make the
digits do the work, and blocks of 6 don't.</span>
</Analogy>

## The slot of a field

With `F` fields and blocks of `B` elements, one `Float64Array` named
`data` holds everything. Block `i / B` (rounded down) starts at slot
`(i / B) * F * B`; inside it, field `k` has its own run of `B` slots
starting at `k * B`, and element `i` sits at lane `i % B` of that run.
Step through it for the program above, where `F = 3` and `B = 4`:

<AosoaSteps client:visible />

When `B` is 2 to the power `sh`, `i / B` rounded down is `i >> sh`,
and the remainder is the low bits, `i & (B - 1)`.

<Figure caption="Element 13 with blocks of 4: the top bits are the block, the bottom two bits the lane. Blocks of 6 have no such split." takeaway="A power-of-two block size makes the block and the lane two pieces of the index's bits.">
  <ShiftMask />
</Figure>

<Formal title="The AoSoA slot">

```text
B = 2^sh,  B ≥ 2
slot(i, k) = (i >> sh) · F·B
           + k · B
           + (i & (B − 1))
```

<span slot="read">The block size B is 2 to the power sh, and at least
2. Field k of element i is at: i shifted right by sh (the block number)
times F times B (the slots in one block), plus k times B (where field
k's run starts inside the block), plus i with all but its low sh bits
cleared (the lane).</span>
</Formal>

The container's `grow()` copies `data` into the front of an array twice
as long, and since a slot depends only on `i` and `k`, never on the
capacity, growing moves nothing.

<Prompts ids={['ao-slot', 'ao-grow']} />

<More title="The push the emitter writes">
From the release CLI's output for the program above, reformatted:

```js
push(v0, v1, v2) {
  const n = this.length;
  if (n === this.cap) this.grow();
  const b = (n >> 2) * 12 + (n & 3);
  this.data[b + 0] = v0;
  this.data[b + 4] = v1;
  this.data[b + 8] = v2;
  return (this.length = n + 1);
}
```

`b` is the slot of field 0 of the new element `n`, so the three values
go to `b + 0`, `b + 4` and `b + 8`, one run of four further each. The
constructor rounds the capacity up to whole blocks (`Math.ceil(cap / 4)
* 4`), so the last block's runs always fit.

This small program fills a vector the way the container fills `data`,
and prints one block per line, so you can see the runs of each field.

## The arithmetic in Rust

`emit.rs` builds that text in a closure, `slot`, which every rewritten
access calls. Its AoSoA half (from
`crates/frontend-js/src/emit.rs`, rewrapped):

```rust
let sh = log2_exact(b)
    .expect("checked by container_class");
let bf = b as f64;
let (stride, off, mask) = (
    js_number(nf * bf),
    js_number(k as f64 * bf),
    js_number(bf - 1.0),
);
let at = if simple_idx {
    format!("(({idx}) >> {sh}) * {stride} \
        + {off} + (({idx}) & {mask})")
} else {
    need_aosoa = true;
    format!("__vsc_aosoa({idx}, {sh}, \
        {stride}, {off}, {mask})")
};
format!("{arr}.data[{at}]")
```

The constants are printed by `js_number`, JavaScript's number
formatting, so the text matches the TypeScript reference byte for byte.
The inline form writes the index twice, so it is used only for a **simple**
index (an identifier or a literal, already proven or assumed in bounds),
which is safe to repeat; anything else, such as a call to `__vsc_bc`,
must run exactly once, so it goes to a helper instead,
`__vsc_aosoa(i, sh, stride, off, mask)`, and `need_aosoa` adds that
helper to the prelude. The shift comes from a one-line function:

```rust
fn log2_exact(b: u64) -> Option<u32> {
    b.is_power_of_two()
        .then(|| b.trailing_zeros())
}
```

`is_power_of_two` is true when exactly one bit is set, and
`trailing_zeros` counts the zero bits below it, which is the
shift<Cite id="rust-std-is-power-of-two" />: `8` (`0b1000`) gives
`Some(3)`, and `6` gives `None`.

<Examples of="rust-aosoa">

```js
ps.data[((i) >> 2) * 12 + 8
  + ((i) & 3)]
// vx (k = 2) of a proven index i
```

```js
ps.data[__vsc_aosoa(
  __vsc_bc(ps, 10, 'y', false),
  2, 12, 4, 3)]
// y (k = 1) of ps[10], not proven
```

</Examples>

Both come from the Rust CLI's output for the program above, with
`console.log(ps[10].y)` added. The first is from the loop body: `i` is
proven in bounds, so it can be written twice, with stride 12 (three
fields times four lanes), offset `2 × 4 = 8` for `vx` and mask 3. The
second is a constant index that is not proven, so it becomes a
`__vsc_bc` call (which throws the original's `TypeError` when out of
range), and since that call must run once, the arithmetic moves into
`__vsc_aosoa`; node prints `20` for both programs.

<Callout kind="definition">
**AoSoA in Rust** stores a collection of `F` numeric fields in one
`Float64Array`, `data`, in **blocks** of `B = 2^sh` elements, field-major
inside each block, and puts field `k` of element `i` at **`(i >> sh) *
F·B + k·B + (i & (B − 1))`**. The `slot` closure in `emit.rs` writes that
inline for a **simple** index and through **`__vsc_aosoa`** for any
other; `log2_exact` gives `sh` with `is_power_of_two` and
`trailing_zeros`.
</Callout>

## Four is fine, six is not

A shift and a mask only work for a power of two, so something has to
refuse the others. Put `aosoa(6)` over the same program, and the Rust
CLI keeps the array of objects, saying `annotated aosoa(6), but the
block size must be a power of two (2, 4, 8, 16, ...)`. The rule is two
rungs of `plan_one` in `crates/core/src/plan.rs`, run only for an
`aosoa` annotation, right after the safety rung of *The cost model and
thresholds in Rust*. Step through them on six annotations:

<BlockRungSteps client:visible />

A `match` turns what was written between the brackets into `b:
Option<u64>`: `None` when the text is not a whole number, 8 when there
were no brackets. The first rung refuses a `b` above `MAX_BLOCK_SIZE`
(65536); the second refuses `None` and every number that is not a power
of two from 2 up (`1` needs the `b >= 2`, because 1 is 2⁰). Both quote
the annotation as written, byte for byte as the TypeScript CLI does,
and `container_class` and `slot` check the power of two again, so a slip
upstream becomes an error rather than wrong arithmetic.

<Prompts ids={['ao-refuse-1', 'ao-text-none']} />

<More title="Why there is an upper limit">
When the Rust chapters were first written there was no rule at the top
end, in either engine. Both accepted `aosoa(1073741824)`, which is 2³⁰;
the constructor then asked for `new Float64Array(2³¹ * 3)`, and node
stopped with `RangeError: Array buffer allocation failed` for a program
whose original runs fine. From 2³² up the arithmetic would have been
wrong as well, because JavaScript takes the count of a shift modulo
32<Cite id="ecma262-signed-right-shift" />, so `i >> 32` is `i`. And at
2⁶⁴ the two engines disagreed: the port parses the digits as an `f64`
and converts with `as u64`, which saturates, and refused the result,
while the reference accepted it. One limit closes all three holes, and
both engines now have it, checked before the power-of-two rule (from
`plan.rs`, rewrapped):

```rust
/// The largest AoSoA block size (2^16).
/// Larger blocks gain nothing, cost a
/// lot of memory per block, and break the
/// shift arithmetic from 2^32 up.
pub const MAX_BLOCK_SIZE: u64 = 65536;
```

So the old annotation now gets `annotated aosoa(1073741824), but the
block size must be at most 65536`, and `tests/extra/aosoa_block_sizes.js`
holds these cases for the parity test.

<Formal title="Accepted block sizes">

```text
accept(B) ⇔ B = 2^s for some
            whole s with 1 ≤ s ≤ 16
```

<span slot="read">A block size B is accepted exactly when it is 2 to the
power s for a whole number s from 1 to 16: that is 2, 4, 8, and so on up
to 65536, and nothing else.</span>
</Formal>

One more AoSoA rung follows: every field shares the one `Float64Array`,
so a record with a string field has nowhere to keep it, and the planner
refuses with `annotated aosoa, but fields name may hold non-numbers`.

ISPC builds this layout into its language: an `soa<8>` type stores 8
values of each field in turn, and indexing it does the same block, lane
and offset arithmetic<Cite id="ispcdocs" />. There the block matches the
SIMD lanes, so one load fills a register; JavaScript has no such loads,
which is why Viscosity keeps AoSoA behind an annotation.
</More>

## Hot and cold, by type

*AoS vs SoA, measured* split a record into **hot** fields, used by the
busy loops, and **cold** ones. The port has a split too, but by
**type**, not by heat: `describe` in `plan.rs` partitions the fields
with `Iterator::partition` into those proven always a number and the
rest, and `container_class` writes `new Float64Array(cap)` for the first
kind and `[]` for the second. The corpus program `mixed_columns.js` has
records `{ id, hp, x, tag }`, and explain says (wrapped):

```
  · typed Float64Array columns for hp, x;
    plain array columns for id, tag (may
    hold non-numbers)
```

<Figure caption="The columns of mixed_columns.js: the busy loop touches hp, x and tag, but only the numeric fields get typed arrays." takeaway="Viscosity chooses a column's kind by type, never by how often it is used.">
  <TypedPlain />
</Figure>

`tag` is read in the hottest loop and still gets a plain column, so the
honest name is "typed and plain". A split by heat would read the
**field affinity** in the access tables of *Access patterns and bounds
proofs in Rust*, which nothing in `plan.rs` does yet.

<More title="What a split by heat would need">
The access tables already record, for each loop, which fields it
touches together; a planner would have to group fields by them. Since
every field already has a column of its own, grouping would only matter
where fields share storage: in AoSoA's blocks, which today put every
field in every block.
</More>

<More title="The partition in describe">

```rust
let (typed, generic): (Vec<&str>,
    Vec<&str>) = c.fields.iter()
    .map(String::as_str)
    .partition(|f| {
        c.numeric_fields.contains(*f)
    });
```

`partition` walks an iterator once and splits it into two collections:
the items for which the closure is true, and the rest.
</More>

## What you learned

- AoSoA puts field `k` of element `i` at **`(i >> sh) * F·B + k·B +
  (i & (B − 1))`**, in one `Float64Array`, and growing moves nothing.
- A **power of two** turns division and remainder into a **shift** and a
  **mask**; `log2_exact` is `is_power_of_two` then `trailing_zeros`.
- The `slot` closure inlines the arithmetic for a **simple** index and
  calls **`__vsc_aosoa`** otherwise, so an index with effects runs once.
- The planner accepts block sizes that are **powers of two from 2 to
  65536**, and quotes anything else back to you.
- Viscosity's column split is **by type**: typed columns for proven
  numbers, **plain** columns for everything else.
