## One line of physics

You met operators as trait calls (`a + b` is `Add::add(a, b)`) and
`#[derive]` in *Traits, trait objects and derive*, and values dropped
when their owner goes in *Ownership: moves, copies and clones*. This
chapter goes further: operators whose two sides have different types,
the assigning and indexing operators, the bounds a derive quietly adds,
and the `Drop` trait itself.

Viscosity's whole subject is particles, and the line we want to write
is the one from a physics book:

```rust
p.pos += p.vel * dt;
```

With only `Add` it does not compile: `p.vel * dt` multiplies a `V2` by
an `f64`, and `+=` is a different operator from `+`. Step through how
rustc reads the line, and which impls it goes looking for:

<Analogy title="a keyboard shortcut">
Ctrl+C means "copy" in every program, but each program decides what
copying a thing means: text in an editor, a file in a file manager. `+`
means "call `Add::add`" for every type, `+=` means "call
`AddAssign::add_assign`", and each type decides what they do by
implementing the trait.
<span slot="breaks">Programs can invent new shortcuts; Rust has a fixed
list of operators, each tied to one trait, and you cannot add a new
operator or redefine `+` for `i32`.</span>
</Analogy>

## The operator traits in full

<Formal title="What rustc writes for each operator">

```text
a + b   ⇝ Add::add(a, b)
a += b  ⇝ AddAssign::add_assign(&mut a, b)
-a      ⇝ Neg::neg(a)
a[i]    ⇝ *Index::index(&a, i)
a == b  ⇝ PartialEq::eq(&a, &b)
a < b   ⇝ PartialOrd::lt(&a, &b)
```

<span slot="read">Read ⇝ as "is compiled as". Plus passes both sides
by value; plus-equals borrows the left side mutably; indexing borrows
the container and then follows the reference it gets back (or uses
IndexMut when the place is assigned to or mutably borrowed); equality
and ordering borrow both sides, so comparing never moves
anything.</span>
</Formal>

<Callout kind="definition">
An **operator trait** is a trait in `std::ops` (or `std::cmp`) that
rustc calls for an operator: `Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`,
`Not` and the bitwise ones, their assigning forms `AddAssign` and so
on, `Index` and `IndexMut` for `a[i]`<Cite id="rust-std-ops-index" />,
and `PartialEq` and `PartialOrd` for `==` and `<`. The binary
arithmetic traits have a generic parameter `Rhs`, the type on the
right, which defaults to `Self`, and an associated type `Output`, the
type of the result; the assigning forms have `Rhs` but no `Output`,
because they change the left side in place<Cite id="rust-std-ops-add" /><Cite id="rust-book-advanced-traits" />.
</Callout>

<Examples of="operator-trait">

```rust
impl Mul<f64> for V2 {      // v * 2.0
    type Output = V2;
    fn mul(self, k: f64) -> V2 {
        V2 { x: self.x * k,
             y: self.y * k }
    }
}
```

```rust
impl AddAssign for V2 {     // a += b
    fn add_assign(&mut self, o: V2) {
        self.x += o.x;
        self.y += o.y;
    }
}
```

```rust
// companion/rust/src/gc.rs: heap[h]
impl<T: HeapObject> Index<Gc<T>> for Heap {
    type Output = T;
    fn index(&self, h: Gc<T>) -> &T {
        &T::arena(self)[h]
    }
}
```

</Examples>

The first picks a different right-hand side: `Mul<f64>` makes `v * 2.0`
legal, but not `2.0 * v`, because the *left* operand chooses the impl,
and that one would be `impl Mul<V2> for f64` (which you may write,
since `V2` is yours). The second has no `Output`: `+=` takes the left
side as `&mut self` and changes it, so the whole expression is `()`.
The third is drip-rs: the heap keeps one arena per kind of object, and
this impl lets the VM write `heap[h]` for a handle to any of them.
`index` returns a *reference* and rustc adds the `*`, so `heap[h]`
names the object in place instead of copying it out; its twin,
`IndexMut`, returns `&mut T` and is what `heap[h].field = x` calls.

## The bound that derive adds

A derive writes the impl you would have written, field by field; on a
generic type it also writes a bound you may not want. drip-rs's handle
type is an index plus a zero-size marker that remembers which kind of
object it points to:

```rust
#[derive(Clone, Copy)]
struct Gc<T> {
    index: u32,
    marker: PhantomData<T>,
}
```

That derive expands to `impl<T: Clone> Clone for Gc<T>`, with a bound
on `T`, because derive cannot see that no field holds a `T`. A
`Gc<Closure>` then has no `clone` when `Closure` is not `Clone`, and
rustc 1.97 says so, with a hint that names the cure (trimmed):

```text
error[E0599]: the method `clone` exists for
  struct `Gc<Closure>`, but its trait
  bounds were not satisfied
  = help: consider manually implementing
    the trait to avoid undesired bounds
```

So drip-rs writes them by hand, with no bound at all:

```rust
// companion/rust/src/object.rs
impl<T> Clone for Gc<T> {
    fn clone(&self) -> Self { *self }
}
impl<T> Copy for Gc<T> {}
```

<Prompts ids={['derive-bound']} />

<More title="More: when derive is the specification">

The same file writes `PartialEq`, `Eq` and `Debug` for `Gc<T>` by hand
for the same reason. Where there is no generic parameter, derive is
often the specification itself: drip-rs's `Value` enum derives
`PartialEq`, and the derived `==` compares two `Number`s with `f64`'s
own `==`, so `NaN` is not equal to itself, exactly as Drip
requires<Cite id="rust-book-derivable-traits" />.

</More>

## Drop: code that runs at the end

Some values own more than memory: a lock to release, a file to flush,
a string that only C's `free` may release. When a type needs to do
something at the moment it is dropped, it implements `Drop`:

```rust
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}
```

`Drop` has one method, `drop(&mut self)`, which rustc calls just
before the value's memory is reclaimed. Now give `Noisy` some company:
a `Pair` that owns two of them and has a `Drop` of its own, which
prints the names of its fields. Step through a `main` that makes a few,
and watch the order in which the lines appear:

<DropOrderSteps client:visible />

<Run id="drop-order" />

Four rules are at work, all from the Rust
Reference<Cite id="rust-reference-destructors" />. Locals are dropped
in reverse order of declaration, as you saw in *Ownership*. A value's
own `drop` runs *first*, while its fields are still whole (which is why
`Pair` can print them), and then its fields are dropped in the order
they are *declared*, the opposite of the rule for locals. `let _ =
Noisy("underscore")` binds nothing, because `_` is a pattern that
matches without taking ownership, so the new value has no owner and is
dropped at the end of that statement (while `let _ = x;` on an
existing variable leaves `x` exactly as it was); give it a name, even
`_u`, and it lives to the end of the block. And a
temporary, a value that is never given a name, such as the `Noisy` in
`let n = Noisy("t").0.len();`, is dropped at the end of the statement
that made it, so "drop t" prints before the next line runs (a rule
that matters for lock guards, as *Checkpoint: a concurrent file indexer
in Rust* will show).

<Analogy extra title="checking out of a hotel">
When you check out, you hand back the key and the room is cleaned; you
never ring for the cleaner yourself, and the hotel never cleans a room
you are still in. `drop` is the cleaning, and leaving is the end of the
owner's scope.
<span slot="breaks">A guest can leave early and ask for the bill; in
Rust you leave early with `drop(x)`, which moves the value away, never
by asking the room to clean itself with `x.drop()`.</span>
</Analogy>

What you may not do is call the method yourself:

```text
error[E0040]: explicit use of destructor
  method
help: consider using `drop` function
```

If `x.drop()` were allowed, `x` would still be owned afterwards and
would be dropped *again* at the end of its scope. `std::mem::drop`
(in the prelude, so plain `drop`) avoids that by taking ownership; its
source says it "is not magic; it is literally defined as `pub fn
drop<T>(_x: T) {}`", so the value is dropped when that empty function
returns, and `x` is moved and cannot be used again.

<Callout kind="definition">
The **`Drop` trait** has one method, `fn drop(&mut self)`, which rustc
calls automatically when a value goes out of scope, is overwritten by
an assignment, or is moved into a function that lets it go, such as
`std::mem::drop`. A value's own `drop` runs before its fields are
dropped; fields are dropped in declaration order and locals in reverse
order of declaration. Calling `drop` as a method is error E0040, a
type with a `Drop` impl cannot be `Copy` (E0184), and you cannot move
a field out of such a value (E0509)<Cite id="rust-reference-destructors" />.
</Callout>

<Examples of="drop-trait">

```rust
struct Timer(&'static str, Instant);
impl Drop for Timer {
    fn drop(&mut self) {
        eprintln!("{}: {:?}", self.0,
                  self.1.elapsed());
    }
}
let _t = Timer("parse", Instant::now());
```

```rust
#[derive(Clone, Copy)]
struct H(u32);
impl Drop for H { fn drop(&mut self) {} }
// error[E0184]: the trait `Copy` cannot be
//   implemented for this type; the type
//   has a destructor
```

</Examples>

The first is a **guard**, a value whose only job is its `drop`: `_t`
lives to the end of the block, so the time it prints covers the whole
block, however it is left (the end, `return` or `?`). A
`MutexGuard` (in *Sharing and sending between threads*) is the same
idea, releasing a lock instead of printing a time. The second is why
`Copy` and `Drop` exclude each other: a copy is made by copying bits,
so two values would both run the same `drop`, and the one resource
would be released twice.

<More title="More: moving out, panics, forget, and what drop cannot do">

The same worry as `Copy` stops you taking a value apart:

```rust
struct Pair { left: String, right: String }
impl Drop for Pair { fn drop(&mut self) {} }
fn take(p: Pair) -> String { p.left }
// error[E0509]: cannot move out of type
//   `Pair`, which implements the `Drop`
//   trait
```

`Pair::drop` still runs when `p` goes, and it may read both fields, so
rustc will not let you take `left` away first. Clone it, or use
`std::mem::take(&mut p.left)` (with `mut p`), which leaves an empty
`String` in its place.

When a thread panics, Rust *unwinds* by default: it leaves each
function in turn, and drops every value those functions own on the
way, exactly as if each scope had ended. So guards run even on a
panic, which is what lets a `Mutex` notice that its holder panicked
and mark itself poisoned. (A program built with `panic = "abort"`
skips this and stops at once.)

`std::mem::forget(x)` does the opposite of `drop`: it takes ownership
and never runs `x`'s destructor. It is safe to call, because leaking
memory is not undefined behaviour, which in turn means unsafe code may
never *rely* on a `drop` running; that rule shapes the design of every
safe wrapper (*Safety invariants and safe wrappers*).

Finally, `drop` takes `&mut self`, not `self`: it cannot move the
fields out or stop them being dropped afterwards. To hand a field on
from inside `drop`, store it in an `Option` and `take()` it.

</More>

## What you learned

- `Rhs` (default `Self`) picks an operator's right-hand type, the left
  operand picks the impl, and `Output` is the result; `+=` borrows the
  left side mutably, and `a[i]` is `*Index::index(&a, i)`.
- On a generic type, `#[derive]` adds `T: Trait` bounds; when no field
  holds a `T`, write the impl by hand.
- **`Drop`** runs a value's own `drop`, then its fields in declaration
  order; locals go in reverse order, `let _ =` and temporaries at the
  end of the statement. Write `drop(x)`, never `x.drop()`.
