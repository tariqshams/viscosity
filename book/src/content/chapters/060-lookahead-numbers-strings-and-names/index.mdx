## One character is not always enough

The scanner from *Tokens and a scanner* reads one character and lets a
`switch` decide what it begins, and for `(` or `;` that is the whole
story. Three lines of Drip show where it stops being enough:

```
if (a <= 4.25) { print "hi"; }
let iffy = total;
```

A `<` might be the whole token or the first half of `<=`; `4.25` and
`"hi"` are many characters long and carry a value; and `iffy` starts
with the keyword `if` without being it. All three are settled by the
same two habits: glance ahead before committing, and always take the
biggest bite.

<Analogy title="for, or forest?">
You are reading and reach the letters "for". Is that the word *for*, or
the start of *forest*? You glance at the next letter before you decide,
without moving your eyes on; glancing is free, and it tells you how to
read what you already have.
<span slot="breaks">You can glance as far ahead as you like, and back
again. Drip's scanner looks at most two characters past `current`, and
never back.</span>
</Analogy>

## Peek and match

`peek`, which you have met, is the glance. Its partner `match` glances
and then consumes the character, but only if it is the one expected: at
the end of the source, or when the next character is not the one
wanted, it returns `false` and changes nothing, and only on a match does
it move `current` on and return `true`.

<Figure takeaway="peek looks; match looks and maybe moves; advance always moves." caption="Each call starts from the same place: the scanner has just read the < of <=, so current is 1. peek returns the = and leaves current alone. match('=') finds it, takes it and returns true. match('<') does not find a <, returns false and changes nothing. advance takes the = whatever it is.">
  <HelperTable />
</Figure>

With `match`, each two-character operator takes one line of the
`switch`:

```ts
case '<':
  add(match('=') ? '<=' : '<');
  break;
```

Comments need only `peek`: a `#` runs to the end of the line, and the
loop `while (peek() !== '\n' && !atEnd()) advance();` stops *before*
the newline, so the `'\n'` case still counts the line.

<Callout kind="definition">
**Lookahead** means examining characters after the current one without
consuming them. `peek()` looks one character ahead; `match(c)` looks,
and consumes only on a match; `peekNext()` looks two ahead.
</Callout>

<Examples of="lookahead">

```text
"<"   →  <          "<="  →  <=
"< =" →  <  =
"&&"  →  &&         "&"   →  error
```

</Examples>

On its own a `<` is `<`; followed by `=` it becomes one token `<=`; with
a space between them, `match('=')` sees the space, fails, and the two
come out separately. Drip has `&&` but no lone `&`, so when `match('&')`
fails there is nothing to fall back on, and the scanner makes an error
token.

<More title="match in full, and a pocket scanner to play with">

```ts
const match = (expected) => {
  if (atEnd()) return false;
  if (source[current] !== expected) {
    return false;
  }
  current++;
  return true;
};
```

A scanner of a few lines, with the same `peek` and `match`; run it,
then add inputs of your own at the bottom.

<Formal title="The three helpers">

```text
peek()    = source[current]     (or \0)
match(c)  = true, current + 1
              if source[current] = c
          = false, nothing moves
              otherwise
advance() = source[current], current + 1
```

<span slot="read">peek gives the character at current and changes
nothing (at the end it gives the stand-in \0). match of c gives true and
moves current on by one when the character at current is c, and
otherwise gives false and moves nothing. advance always gives the
character at current and always moves on.</span>
</Formal>

## Always the biggest bite

When the scanner sees `<=` it could make two tokens, `<` and `=`; it
does not, because `match` grabs the `=` whenever it can. The same rule
runs all through the scanner: a run of digits is one number, and
`fortune` is one identifier, not the keyword `for` followed by `tune`.

<MunchSteps client:visible />

<Callout kind="definition">
**Maximal munch** is the rule that a scanner always takes the longest
sequence of characters that forms a valid token, even when a shorter
token would also fit.
</Callout>

<Examples of="maximal-munch">

```js
let a = 1, b = 2;
a+++b; // a++ + b, so 3
```

</Examples>

This is JavaScript, whose specification states the rule in its own
words: source text is scanned left to right, "repeatedly taking the
longest possible sequence of code points as the next input
element"<Cite id="ecma262" />. So `a+++b` is cut as `a`, `++`, `+`,
`b`, which means `a++ + b`, which is 3, even though `a + ++b` would also
have made sense; in Drip, `!===` comes out as `!=` then `==` for the
same reason.

<More title="Maximal munch written as a formula, and JavaScript's / problem">

<Formal title="Maximal munch">

```text
next token = the longest prefix p
             of source[current ..)
             such that p is a token
```

<span slot="read">From the current position, look at every way the rest
of the source could begin with a valid token (a prefix is a piece taken
from the front), and take the longest one. For !=== the valid prefixes
are ! and !=, so it takes !=.</span>
</Formal>

Drip's scanner never needs to know what the parser is doing.
JavaScript's cannot be so independent: a `/` might be division or the
start of a regular expression like `/ab+/`, and no amount of lookahead
at the characters says which. So the JavaScript specification defines
several starting rules for its lexical grammar, and which one applies
depends on where the parser is in the syntax<Cite id="ecma262" />.

</More>

## Numbers: two characters ahead

<Callout kind="definition">
A **literal** is a value written directly in the source code: a number
such as `4.25` or a string such as `"hi"`. Its token records both the
lexeme (the characters) and the **literal value** they stand for, which
is what the running program will use.
</Callout>

A Drip number is digits, optionally followed by a dot and more digits.
The scanner knows one has started when the character it just read is a
digit:

```ts
if (isDigit(c)) {
  while (isDigit(peek())) advance();
  if (peek() === '.' &&
      isDigit(peekNext())) {
    advance(); // the '.'
    while (isDigit(peek())) advance();
  }
  const text = source.slice(start, current);
  add('number', Number(text));
}
```

Line 2 takes every further digit (maximal munch). Lines 3 and 4 are the
interesting test: at a `.`, one character of lookahead is not enough,
because in `4.25` the dot belongs to the number but in `p.x` it means
"get a property". So the scanner looks
*two* ahead and takes the dot only if a digit follows it. Line 9 hands
the lexeme to JavaScript's own `Number`, which turns `'4.25'` into a
64-bit float<Cite id="mdn-number" />: Drip gets its number format for
free from its host.

<Figure takeaway="The dot joins the number only if a digit follows it." caption="Three sources that start the same way. After the 4, peek() is the dot in every case, so peekNext() decides: a digit (4.25) means the dot and the digits join the number; anything else (a semicolon, a letter) means the number is just 4, and the dot is left for the next round.">
  <DotDecision />
</Figure>

<Examples of="literal">

```text
007    lexeme '007'    value 7
4.250  lexeme '4.250'  value 4.25
4.;    number 4, then .  ;
"hi"   lexeme "hi"     value hi
```

</Examples>

The first two show lexeme and value coming apart: the lexeme keeps
exactly what you wrote, while the value is the number itself (so `print
4.250;` shows `4.25`). In `4.;` no digit follows the dot, so the dot is
a token of its own. A string's lexeme keeps its quotes; its value leaves
them out.

A string's loop runs from `"` to the next `"`, turning escapes such as
`\n` into the characters they stand for, counting the newlines it passes
(Drip strings may span lines), and making the error token `unterminated
string` if the file ends first.

<More title="The string loop, line by line">

```ts
case '"': {
  const startLine = line;
  let value = '';
  while (peek() !== '"' && !atEnd()) {
    const ch = advance();
    if (ch === '\n') line++;
    if (ch === '\\' && !atEnd()) {
      value += ESCAPES[advance()];
    } else {
      value += ch;
    }
  }
  if (atEnd()) {
    error('unterminated string', startLine);
    break;
  }
  advance(); // the closing "
  add('string', value, startLine);
  break;
}
```

`ESCAPES` maps `n`, `t`, `"` and `\` to the characters they stand for.
Line 2 remembers where the string starts, which is where the token (or
its error) is reported; line 6 keeps every later token's line number
right; lines 7 and 8 take the character after a backslash at once, so in
`\"` the quote never reaches the test on line 4. (The real code in
`companion/ts/src/scanner.ts` also reports an unknown escape such as
`\q`.) Step through it on a string that spans two lines, and on one that
never ends:

## Names and keywords

An **identifier** starts with a letter or `_` and continues with
letters, digits or `_`. Keywords such as `let`, `if` and `while` are
spelled exactly like identifiers, so the scanner reads them with the
same loop, and only then asks a table:

```ts
} else if (isAlpha(c)) {
  while (isAlpha(peek()) ||
         isDigit(peek())) advance();
  const text = source.slice(start, current);
  add(KEYWORDS.get(text) ?? 'identifier');
}
```

`KEYWORDS` is a `Map` from each of Drip's twenty keywords to its own
token type (`'if'` to `'if'`, and so on); for any other word `get`
returns `undefined`, and `??` falls back to `'identifier'`. The order
matters: a scanner that recognised `if` as soon as it saw an `i` and an
`f` would cut `iffy` into the keyword `if` and a stray `fy`. Reading
the whole word first is maximal munch again.

<Figure takeaway="Read the whole word, then ask the table once." caption="Each whole word is looked up exactly once. if and while are in the table, so they get their own keyword types; iffy, format and total are not (even though iffy starts with if and format with for), so they become identifiers.">
  <KeywordLookup />
</Figure>

<Callout kind="definition">
An **identifier** is a name chosen by the programmer: in Drip, a letter
or `_` followed by any number of letters, digits and `_`. A **keyword**
is a word with a fixed meaning in the language, such as `if` or `let`;
every Drip keyword is **reserved**, so it cannot be used as a name. The
scanner finds keywords with a **reserved-word table**, a map from each
keyword's spelling to its token type, consulted after a whole word has
been scanned.
</Callout>

<Examples of="identifier keyword reserved-word-table">

```
let iff = 3;  # fine
let if = 3;
# line 1: expected a variable name
# after 'let', found 'if'
```

</Examples>

`iff` is not in the table, so it is an identifier and the first line is
an ordinary declaration. `if` is in the table, so the scanner makes an
`if` token; the parser needed a name after `let`, and says what it
found instead.

<More title="More names, and how JavaScript differs">

<Run id="names" />

A digit can never start a name, so `2x` is the number `2` and then the
identifier `x`; `-` is not allowed inside one, so `x-y` is a
subtraction; and case matters, so `Total` and `total` are two names.
`true`, `false` and `none` are keywords to the scanner, not values: the
parser turns the keyword `true` into the boolean, while `"true"` is a
four-letter string.

JavaScript is less tidy: its specification separates keywords from
reserved words, and `async` is a keyword that is not reserved, so `let
async = 1` is legal JavaScript<Cite id="ecma262-keywords" />. Drip keeps
every keyword reserved, so one table is enough.

<Analogy extra title="a guest list at the door">
A doorman reads the whole name on your ticket, "Annabel", before
checking the list; if he stopped at "Ann" and found an Ann on the list,
he would let in the wrong person.
<span slot="breaks">A guest list changes from night to night. Drip's
table is fixed when the language is designed, and every program sees
the same one.</span>
</Analogy>

</More>

## What you learned

- **Lookahead** examines characters without consuming them: `peek`
  looks, and `match` consumes only the expected character.
- **Maximal munch**: always take the longest token that fits, so `<=`
  is one token and `fortune` is one identifier.
- A **literal**'s token keeps its lexeme and its value; a number's dot
  is taken only if a digit follows it.
- **Identifiers** and **keywords** are scanned alike, then a
  **reserved-word table** decides, after the whole word is read.

That finishes Drip's scanner. Next: *Grammars and parse trees*, the
rules that say which sequences of these tokens make a program.
