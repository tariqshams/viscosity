## One character is not always enough

The last chapter's loop reads one character and lets a `switch` decide
what it begins, and for `(` or `;` that is the whole story. A `<` is
different: it might be the whole token, or the first half of `<=`, and
the character alone does not say which. The scanner has to glance at the
*next* character before it commits; however, it must glance without
consuming, because if the next character is a space or a number, that
belongs to the next token, not to this one.

<Analogy title="for, or forest?">
You are reading and reach the letters "for". Is that the word *for*, or
the start of *forest*? You glance at the next letter before you decide,
without moving your eyes on; glancing is free, and it tells you how to
read what you already have.
<span slot="breaks">You can glance as far ahead as you like, and back
again. Drip's scanner looks at most two characters past `current`, and
never back; the rest of the source stays unseen until it is reached.</span>
</Analogy>

<Analogy extra title="stepping stones">
Crossing a stream on stepping stones, you look at the next stone first;
if it is the one you want, you step onto it, and if it is not, you stay
where you are and choose differently.
<span slot="breaks">A wrong stone can still be stepped back from. The
scanner's `match` decides once, and a character it has stepped onto is
part of the token for good.</span>
</Analogy>

`peek`, from the last chapter, is the glance. The other helper is
`match`, which glances and then consumes the character, but only if it
is the one expected:

```ts
const match = (expected) => {
  if (atEnd()) return false;
  if (source[current] !== expected) {
    return false;
  }
  current++;
  return true;
};
```

Line 2 gives up at the end of the source, where there is nothing to
match. Lines 3 to 5 give up, changing nothing, when the next character
is not the one wanted. Only when it is does line 6 move `current` past
it, and line 7 report success. The figure lines up all three helpers on
the same state:

<Figure takeaway="peek looks; match looks and maybe moves; advance always moves." caption="Each call starts from the same place: the scanner has just read the < of <=, so current is 1. peek returns the = and leaves current alone. match('=') finds it, takes it and returns true. match('<') does not find a <, returns false and changes nothing. advance takes the = whatever it is.">
  <HelperTable />
</Figure>

With `match`, each of `!`, `=`, `<`, `>`, `+`, `-` and `.` takes one
line of the `switch` (`+` may become `+=`, and `.` may become `..`):

```ts
case '<':
  add(match('=') ? '<=' : '<');
  break;
```

If the next character is `=`, `match` takes it and the token is `<=`,
two characters long; otherwise nothing moves and the token is `<`. The
`? :` picks between the two types, and `add` slices whichever lexeme
the pointers now surround.

`&` and `|` use the same trick with a twist: Drip has `&&` and `||`
but no lone `&` or `|`, so when `match` fails there is no short token
to fall back on, and the scanner makes an error token instead:

```ts
case '&':
  if (match('&')) add('&&');
  else error(`unexpected character '&'`);
  break;
```

Comments need only `peek`. A `#` always starts a comment (Drip chose a
character that means nothing else, so no lookahead is needed to tell),
and the comment runs to the end of the line:

```ts
case '#':
  while (peek() !== '\n' && !atEnd()) {
    advance();
  }
  break;
```

The `while` eats every character up to (not including) the newline,
making no token. Notice that it uses `peek`, not `advance`, to test for
`'\n'`. That leaves the newline unread, so the next round of the main
loop handles it in the `'\n'` case, and `line` stays correct.

<Callout kind="definition">
**Lookahead** means examining characters after the current one without
consuming them. `peek()` looks one character ahead; `match(c)` looks,
and consumes only on a match. Drip also has `peekNext()`, which looks
two ahead, for numbers like `1.5` (coming up in the chapter on numbers
and strings); it is also what keeps `0..3` from being read as `0.`
and `.3`.
</Callout>

<Formal title="The three helpers">

```text
peek()    = source[current]     (or \0)
match(c)  = true, current + 1
              if source[current] = c
          = false, nothing moves
              otherwise
advance() = source[current], current + 1
```

<span slot="read">peek gives the character at current and changes
nothing (at the end it gives the stand-in \0). match of c gives true and
moves current on by one when the character at current is c, and
otherwise gives false and moves nothing. advance always gives the
character at current and always moves on.</span>
</Formal>

```text
"<"   →  <          "<="  →  <=
"< =" →  <  =
```

```text
"&&"        →  &&     "&"  →  error
"# half\n2"  →  2   (on line 2)
```

## Always the biggest bite

When the scanner sees `<=`, it could make two tokens, `<` and `=`. It
does not: `match` grabs the `=` whenever it can. The same rule runs all
through the scanner. A run of digits is one number, not several; and
`fortune` is one identifier, not the keyword `for` followed by `tune`.

<MunchSteps client:visible />

<Analogy extra title="a hungry guest at a buffet">
A hungry guest at a buffet takes the biggest portion that still fits on
the plate, every time. The scanner does the same: at each point, it
takes the longest piece of text that still forms a valid token.
<span slot="breaks">A guest can choose a smaller portion to leave room
for pudding. The scanner never does, even when a smaller token would
have suited the parser better; that is why `a+++b` (below) can surprise
people.</span>
</Analogy>

<Callout kind="definition">
**Maximal munch** is the rule that a scanner always takes the longest
sequence of characters that forms a valid token, even when a shorter
token would also fit.
</Callout>

<Formal title="Maximal munch">

```text
next token = the longest prefix p
             of source[current ..)
             such that p is a token
```

<span slot="read">From the current position, look at every way the rest
of the source could begin with a valid token (a prefix is a piece taken
from the front). Of all those prefixes, the scanner takes the longest
one as the next token. For !=== the valid prefixes are ! and !=, so it
takes !=.</span>
</Formal>

<Examples of="maximal-munch">

```text
"!==="    →  !=  ==
"<=<"     →  <=  <
```

```text
"fortune"  →  identifier fortune
"for tune" →  for  identifier tune
```

```js
let a = 1, b = 2;
a+++b; // a++ + b, so 3
```

</Examples>

In the first, taking the longest token each time gives `!=` and then
`==`, never `!` followed by `===` (Drip has no
`===`); and `<=<` is `<=` then `<`, because after `<=` the next round
starts fresh. The second shows the same rule on words: the scanner takes
every letter it can, so `fortune` is one name (a line from one of
Drip's test programs), and only a space makes the keyword `for`
appear. The third is JavaScript, whose spec states the same
rule in its own words: source text is scanned left to right,
"repeatedly taking the longest possible sequence of code points as the
next input element"<Cite id="ecma262" />. So `a+++b` is cut as `a`,
`++`, `+`, `b`, which means `a++ + b`: `a++` gives 1 (and makes `a` 2),
and 1 + 2 is 3, even though `a + ++b` would also have made sense.

<Prompts ids={['munch-what', 'orchid', 'bang-eq', 'a-plus']} />

<Callout kind="engine" label="Under the hood">
Drip's scanner never needs to know what the parser is doing.
JavaScript's cannot be so independent: a `/` might be division or the
start of a regular expression like `/ab+/`, and no amount of lookahead
at the characters says which. So the JavaScript spec defines several
starting rules for its lexical grammar, and which one applies depends
on where the parser is in the syntax<Cite id="ecma262" />. Drip's scanner
never needs to look further than two characters past `current`
(`peekNext` is as far as it goes), and never needs to ask the parser
anything.
</Callout>

## What you learned

- **Lookahead** examines characters ahead without consuming them:
  `peek` looks, and `match` consumes only when the next character is
  the expected one.
- `match` turns `<`, `>`, `=`, `!`, `+`, `-` and `.` into one- or
  two-character tokens in one line each; a lone `&` or `|` is an error.
- A `#` comment needs no lookahead to recognise.
- The comment loop stops *before* the newline, so the newline case can
  still count the line.
- **Maximal munch**: always take the longest token that fits, so `<=`
  is one token, `!===` is `!=` then `==`, and `fortune` is one
  identifier.

## Words with a value inside

Here are two lines of Drip:

```
let total = 4.25;
print "hello";
```

The scanner from the last two chapters handles `=` and `;` already, and
`let` and `total` get a chapter of their own next. This chapter is
about the other two tokens, `4.25` and `"hello"`, which are different
from everything so far in two ways: each is longer than one or two
characters, so it needs its own small loop; and each *carries a value*,
which the scanner must work out and keep in the token's `literal`
field. These loops are among the last pieces of Drip's scanner in
`companion/ts/src/scanner.ts`; the excerpts are lightly simplified to
fit a phone screen.

<Analogy title="a banknote and an IOU">
A banknote with "10" printed on it *is* ten pounds; you can spend it as
it is. A note saying "see drawer 3" is worth whatever happens to be in
drawer 3. A literal is the banknote: `4.25` is the number itself,
written out in the source, while a variable name like `total` is the
note pointing at a drawer.
<span slot="breaks">A banknote's value was decided by a bank. A
literal's value is decided by nothing but its own characters, read by
fixed rules, so the same characters always mean the same value.</span>
</Analogy>

<Callout kind="definition">
A **literal** is a value written directly in the source code: a number
such as `4.25` or a string such as `"hi"`. The scanner records both the
lexeme (the characters) and the **literal value** they stand for, which
is what the running program will use.
</Callout>

## Numbers

A Drip number is one or more digits, optionally followed by a dot and
more digits; so `7`, `007` and `4.25` are numbers. The scanner knows a
number has started when the character it just read is a digit:

```ts
if (isDigit(c)) {
  while (isDigit(peek())) advance();
  if (peek() === '.' &&
      isDigit(peekNext())) {
    advance(); // the '.'
    while (isDigit(peek())) advance();
  }
  const text = source.slice(start, current);
  add('number', Number(text));
}
```

Line 2 takes every further digit (maximal munch, from the last
chapter). Lines 3 and 4 are the interesting test. When the scanner
reaches a `.` after some digits, one character of lookahead is not
enough to decide: in `4.25` the dot is part of the number, but in `4.`
it is not, and in Drip a dot can also mean "get a property", as in
`point.x`. So the scanner looks *two* characters ahead, with `peekNext`,
and only takes the dot if a digit follows it. Lines 5 and 6 then take
the dot and the digits after it. Line 8 cuts out the lexeme, and line 9
hands it to `Number`, JavaScript's own converter, which turns `'4.25'`
into a 64-bit float<Cite id="mdn-number" />: Drip gets its number format
for free from its host language.

<Figure takeaway="The dot joins the number only if a digit follows it." caption="Three sources that start the same way. After the 4, peek() is the dot in every case, so peekNext() decides: a digit (4.25) means the dot and the digits join the number; anything else (a semicolon, a letter) means the number is just 4, and the dot is left for the next round.">
  <DotDecision />
</Figure>

<Formal title="The shape of a Drip number">

```text
number = digit digit* ( "." digit digit* )?
digit  = "0" | "1" | … | "9"
```

<span slot="read">A number is a digit followed by any number of further
digits (the star means "zero or more times"); then, optionally (the
question mark means "zero times or once"), a dot followed by at least
one digit. A digit is any one of the characters 0 to 9, where the
upright bar means "or". This little notation is a language for
describing words, and it gets its own chapters soon.</span>
</Formal>

<Examples of="literal">

```text
7      lexeme '7'      value 7
007    lexeme '007'    value 7
4.250  lexeme '4.250'  value 4.25
```

```text
4.;    →  number 4, then .  ;
p.x    →  identifier, ., identifier
1.2.3  →  1.2, then .  3
```

<Run id="numbers" />

</Examples>

The first shows lexeme and value coming apart: three different
spellings, and `Number` turns `007` into plain `7` and drops the
trailing zero of `4.250`, so the lexeme keeps exactly what you wrote
while the value is the number itself. The second shows the dot test at
work: in `4.` no digit follows the dot, so the number stops at `4` and
the dot becomes a token of its own; `p.x` starts with a letter, so no
number is involved at all; and in `1.2.3` the fraction is taken once,
so the number is `1.2` and the second dot is left over. The third runs
some literals through the real interpreter: notice that `print 4.250;`
shows `4.25`, because what `print` shows is the value, not the lexeme.

## Strings

A Drip string starts with `"` and runs to the next `"`, and it may run
across several lines. Inside it, a backslash starts an **escape**, a
two-character code for a character that would be awkward to type
directly: `\n` is a newline, `\t` a tab, `\"` a quote mark that does
*not* end the string, and `\\` one backslash. The scanner keeps them in
a small table:

```ts
const ESCAPES = {
  n: '\n', t: '\t', '"': '"', '\\': '\\',
};
```

and the case in the `switch` builds the value one character at a time:

```ts
case '"': {
  const startLine = line;
  let value = '';
  while (peek() !== '"' && !atEnd()) {
    const ch = advance();
    if (ch === '\n') line++;
    if (ch === '\\' && !atEnd()) {
      value += ESCAPES[advance()];
    } else {
      value += ch;
    }
  }
  if (atEnd()) {
    error('unterminated string', startLine);
    break;
  }
  advance(); // the closing "
  add('string', value, startLine);
  break;
}
```

<Analogy extra title="a quotation in a book">
When a book quotes someone, the words between the quote marks are
reproduced exactly as they were said, and the quote marks themselves
only show where the quotation starts and stops; nobody said the quote
marks.
<span slot="breaks">A book shows a quote inside a quote with single
marks inside double ones. Drip's trick is the escape `\"`, and it is
the scanner's job, not the reader's, to see that this quote mark is
part of the words.</span>
</Analogy>

Step through it on a string that spans two lines, and then on one that
never ends:

## What you learned

- A **literal** is a value written in the source. Its token keeps the
  lexeme (`'4.25'`) and the **literal value** (`4.25`).

## Three words that look alike

Here is a line of Drip:

```
let iffy = total;
```

Three of its tokens are words made of letters, and to the scanner's
loop they look exactly alike; however, they are not the same kind of
thing. `iffy` and `total` are names the programmer chose, and could have
been anything; `let` belongs to the language, and means the same in
every program ever written. Worse, `iffy` *starts* with `if`, which also
belongs to the language. The scanner has to read these words, tell
which are which, and never mistake the start of a name for a keyword.

## Names

<Analogy title="a label you write yourself">
You can write any label you like on a storage box with a marker pen:
"winter coats", "box 7", "misc_2". Drip does not care what your label
says, only that it is written with the allowed characters.
<span slot="breaks">On a box you may write anything at all, spaces and
dashes included. An identifier may only use letters, digits and `_`,
may not start with a digit, and may not be one of the language's own
words.</span>
</Analogy>

An identifier starts with a letter or an underscore, and continues
with letters, digits or underscores; so `total`, `_count2` and `x1` are
identifiers, while `2x` is not one (the scanner sees the digit first,
scans the number `2`, and then starts a fresh identifier `x`):

```ts
const isAlpha = (c: string) =>
  (c >= 'a' && c <= 'z') ||
  (c >= 'A' && c <= 'Z') || c === '_';

// in the scanner's switch:
} else if (isAlpha(c)) {
  while (isAlpha(peek()) ||
         isDigit(peek())) advance();
  const text = source.slice(start, current);
  add(KEYWORDS.get(text) ?? 'identifier');
}
```

Lines 1 to 3 define what may *start* a word: a lowercase letter, an
uppercase letter or `_` (comparing strings compares character codes, as
in *Strings up close*, so `c >= 'a' && c <= 'z'` means "a lowercase
letter"). In the `switch`, once the first character passes `isAlpha`,
the `while` takes every further letter, digit or underscore (maximal
munch again), `text` is the whole word, and the last line decides its
type, which is the subject of the next section.

<Callout kind="definition">
An **identifier** is a name chosen by the programmer: a variable,
function or class name. In Drip, it is a letter or `_` followed by any
number of letters, digits and `_`.
</Callout>

<Formal title="The shape of an identifier">

```text
identifier = alpha ( alpha | digit )*
alpha      = "a" … "z" | "A" … "Z" | "_"
```

<span slot="read">An identifier is one alpha character followed by any
number (the star: zero or more) of characters that are each an alpha
or a digit (the bar means "or"). An alpha is a lowercase letter, an
uppercase letter or the underscore. The same notation described numbers
in the last chapter.</span>
</Formal>

<Examples of="identifier">

```text
x   total   _count2   Particle
```

```text
2x   →  number 2, identifier x
x-y  →  identifier x, -, identifier y
```

## Keywords

Look at the last line of the scanner code again. `let`, `if` and `while`
are spelled exactly like identifiers, so the scanner reads them with the
same loop, and only then asks a table whether the word is special:

```ts
const KEYWORDS = new Map([
  'break', 'class', 'continue', 'else',
  'extends', 'false', 'fn', 'for', 'if',
  'in', 'init', 'let', 'new', 'none',
  'print', 'return', 'self', 'super',
  'true', 'while',
].map((k) => [k, k]));
```

Those are all twenty of Drip's keywords. The `.map` turns each word `k`
into the pair `[k, k]`, because each keyword maps to its own token
type, named after itself (from the chapter on tokens). One of them,
`init`, is a keyword only so that the name of the constructor method
can never be used for anything else. If the table has no entry for a word, `get` returns
`undefined`, and `??` (which picks its right-hand side only when the
left is `null` or `undefined`) falls back to `'identifier'`.

Some spaces in a car park are painted "staff only". They look exactly

The guest list is the point of the order. Why not spot `if` as soon as
the scanner has seen an `i` and an `f`? Because of maximal munch: in
`let iffy = 1;` a scanner that stopped at `if` would produce the keyword
`if` and then a stray `fy`. Reading the whole word first, then looking
it up once, gets `iffy` right:

<Callout kind="definition">
A **keyword** is a word with a fixed meaning in the language, such as
`if`, `while` or `let`. In Drip, every keyword is **reserved**: it
cannot be used as a name. The scanner finds keywords with a
**reserved-word table**, a map from each keyword's spelling to its token
type, consulted after a whole word has been scanned.
</Callout>

<Formal title="Choosing a word's type">

```text
type(w) = KEYWORDS(w)   if w is in KEYWORDS
        = identifier    otherwise
```

<span slot="read">For a whole word w, the token type is whatever the
keyword table gives for w when w is one of its keys, and identifier when
it is not. The lookup is on the complete word, never on a piece of
it.</span>
</Formal>

<Examples of="keyword reserved-word-table">

```text
if     →  'if'
iffy   →  identifier
```

```text
true   →  'true'   (a keyword)
"true" →  string    (a literal)
```

```
let if = 3;
# line 1: expected a variable name
# after 'let', found 'if'
# line 1: expected an expression,
# found '='
let iff = 3;  # fine
```

</Examples>

The first is the table at work: `if` is found and becomes the keyword
type `'if'`, while `iffy`, read whole, is not found and becomes a name.
The second shows that `true`, `false` and `none` are keywords to the
scanner, not values; the parser, a few chapters on, turns the keyword
`true` into the boolean value, while `"true"` in quotes is a string
literal with four letters in it. The third is a spot the difference:
because keywords are reserved, the scanner turns `if` into an `if`
token, the parser needed a name after `let`, and Drip says what it
found instead, `'if'` (the parser then starts afresh at that `if`, as if
it began an `if` statement, so the `=` draws a second complaint); one
more letter makes it an ordinary name.

<Callout kind="engine" label="Under the hood">
JavaScript's keywords are less tidy. Its specification separates
**keywords** (words with a job in the grammar) from **reserved words**
(words you cannot use as names): `if` and `while` are both, but `async`
is a keyword that is not reserved, so `let async = 1` is legal
JavaScript<Cite id="ecma262-keywords" />. Whether a word like `async`
acts as a keyword depends on where it appears, which a lookup table on
its own cannot know. Drip keeps every keyword reserved, so one table is
enough; and the scanner of Drip's VM in Part IV looks words up in this
same `KEYWORDS` table.
</Callout>

## What you learned

- An **identifier** is a letter or `_`, then letters, digits and `_`;
  a digit always starts a number instead.
- A **keyword** is scanned like an identifier, then found in a
  **reserved-word table**; reading the whole word first is maximal
  munch, which is why `iffy` is a name.
- Every Drip keyword is reserved, so it can never be a name; JavaScript
  has keywords, like `async`, that are not reserved.

That finishes Drip's scanner. Along the way we kept describing words
with little patterns ("a digit, then any number of digits", "a letter,
then letters or digits"). Those patterns are a small language of their
own, with a precise meaning and a theory behind them, and the next
chapter, *Regular expressions as a language*, starts there.
