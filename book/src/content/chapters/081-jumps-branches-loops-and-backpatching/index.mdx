## Bytecode has no inside

When the tree-walker ran an `if`, both branches were *inside* the `if`
node of the syntax tree, so choosing a branch meant choosing which child
to visit. Bytecode has no inside: a function's bytecode is one flat row
of bytes, and the dispatch loop does one thing, over and over, which is
to run the instruction at `ip` (the offset of the next byte to run) and
move on to the one after it. To skip a branch, or to go round a loop
again, something has to change `ip` itself.

<Analogy title="snakes and ladders">
The squares of a snakes-and-ladders board are numbered in one fixed
order, and normally your counter moves straight on. Land at the foot
of a ladder, though, and you jump forward to a square far ahead; land
on a snake's head and you slide back to an earlier one. The board never
changes shape, yet the path a counter takes through it can skip ahead
and go round again.
<span slot="breaks">A snake or ladder always fires when you land on
it; some jumps in the VM fire only when a condition is false. Also, a
ladder names the square it ends on, while a VM jump stores how *far*
to move, counted from the end of the jump instruction.</span>
</Analogy>

## Jumps

Drip's VM has five jump instructions (in `chunk.ts`): `jump` moves
forward, `jump.unless` pops a condition and moves forward if it is
falsey, `jump.unless.keep` and `jump.if.keep` serve `&&` and `||`, and
`loop` moves backward. Each carries a **two-byte distance**, stored
high byte first, so each jump is three bytes long, and the distance is
counted from the byte just *after* it, because by the time the VM has
read the operand, that is where `ip` points.

<Figure takeaway="A jump stores a distance, counted from the byte after the operand." caption="The bytes of if true { print 1; } else { print 2; }. jump.unless at offset 1 has the distance 0, 7 (that is 0 × 256 + 7). ip is 4 after the operand is read, so a jump lands at 4 + 7 = 11.">
  <JumpBytes />
</Figure>

From `vm.ts` (wrapped to fit):

```ts
const readShort = () => {
  frame.ip += 2;
  return (code[frame.ip - 2] << 8) |
    code[frame.ip - 1];
};
case Op.JumpUnless: {
  const off = readShort();
  if (isFalsey(this.pop()))
    frame.ip += off; break; }
case Op.Loop: {
  const off = readShort();
  frame.ip -= off; break; }
```

`readShort` moves `ip` past the operand and glues its bytes into one
number (the high byte times 256, plus the low byte). `jump.unless` pops
the condition and adds the distance only if the condition is falsey, so
a true condition falls through; `jump` adds it always, and `loop`
*subtracts* it always.

<Callout kind="definition">
A **jump** is an instruction that changes the instruction pointer, so
that execution continues somewhere other than the next instruction.
Drip's jumps carry a two-byte distance, counted from the byte after
the instruction: `jump` always moves forward by it, `jump.unless`
pops the condition and moves forward only if it is falsey, and `loop`
always moves backward.
</Callout>

<Examples of="jump">

```text
let x = 5;
if x > 3 { print "big"; }
else { print "small"; }

0006    2 load.global         2 'x'
0009    | const               3 '3'
0012    | gt
0013    | jump.unless        13 -> 23
0016    3 const               4 'big'
0019    | print
0020    4 jump               20 -> 27
0023    5 const               5 'small'
0026    | print
0027    6 none
```

</Examples>

The disassembler does the arithmetic and prints each jump as *where it
is* `->` *where it lands* (the real program has one statement per line,
and the two instructions that define `x` are left out). Offsets 6 to 12
leave `x > 3`, `true`, on the stack. At 13, `jump.unless` pops it; it is
true, so there is no jump, and the then-branch at 16 prints `big`. At
20, a plain `jump` to 27 skips the else-branch. Had `x` been 1,
`jump.unless` would land at 23, the else-branch, which runs on into 27
by itself. So an `if` with an `else` costs two jumps, one *into* the
else-branch and one *over* it.

A `while` adds a backward jump: a `jump.unless` after the condition
leaves the loop, and a `loop` at the end of the body sends `ip` back to
the condition. Step through `let n = 0; while n < 2 { n += 1; }`:

<More title="&& and ||: jumps that keep their value">

In Drip, `a && b` is `a` when `a` is falsey (and `b` is never
evaluated), otherwise `b`; `a || b` is `a` when `a` is truthy,
otherwise `b`. That is a jump over `b`, but the left value must *stay*
on the stack as the answer, so these use jumps that peek instead of
popping:

```text
print false && 1;
0000    1 false
0001    | jump.unless.keep    1 -> 8
0004    | pop
0005    | const               0 '1'
0008    | print
```

`false` is falsey, so `jump.unless.keep` jumps to the `print`, leaving
`false` to be printed; a truthy left side would fall through, be popped,
and `1` pushed instead. `||` is the mirror image, with `jump.if.keep`.

<Run id="short" />

CPython's bytecode is built from the same ideas: `JUMP_FORWARD` and
`JUMP_BACKWARD` move the bytecode counter by a distance, and
`POP_JUMP_IF_FALSE` pops the top of the stack and jumps if it is
false<Cite id="cpython-dis" />, just as `jump.unless` does.

</More>

## A jump to code that is not written yet

The compiler works in a single pass, so when it reaches the `{` after
`if x > 3` it must emit the `jump.unless` *now*, before the
then-branch, and the distance is the size of a then-branch that has not
been compiled yet. The answer is to write a placeholder, remember where
it is, and come back. From `compiler.ts`:

```ts
function emitJump(op: number): number {
  emit(op, 0xff, 0xff);
  return chunk().code.length - 2;
}
function patchJump(offset: number) {
  const jump = chunk().code.length
    - offset - 2;
  if (jump > 0xffff) staticError(previous,
    'too much code to jump over');
  chunk().code[offset] =
    (jump >> 8) & 0xff;
  chunk().code[offset + 1] = jump & 0xff;
}
```

`emitJump` writes the opcode and two placeholder bytes, `0xff 0xff`,
and returns the placeholder's position. `patchJump` is called when the
compiler reaches the target, which is always "here", `code.length`; at
run time `ip` will be at `offset + 2`, just past the operand, so the
distance is `code.length - offset - 2`, written high byte first. An
`if` calls `emitJump(Op.JumpUnless)` after its condition, compiles the
then-branch, and patches; with an `else`, it first emits the `jump`
over the else-branch, patches the first jump, compiles the else-branch
and patches the second.

<PatchSteps client:visible />

<Callout kind="definition">
**Backpatching** is emitting an instruction with a placeholder operand
and filling the operand in later, once the information it needs
(here, the target of a forward jump) is known. `emitJump` returns the
placeholder's position, and `patchJump` writes the distance from just
after the placeholder to the current end of the code.
</Callout>

A backward jump needs no patching: when the compiler writes `loop`, the
loop's start is already compiled, so `emitLoop(loopStart)` knows the
distance at once. `break` is the opposite case: a loop can contain any
number of them, all jumping to its end, so the compiler keeps a record
for each loop it is inside, with a `breaks` list of placeholders, and
patches every one when it reaches the loop's end. (Before its jump, a
`break` also emits a `pop` for each local declared in the loop, because
the jump skips the closing braces that would have popped them.)

<Examples of="backpatching">

```text
let i = 0;
while true {
  i += 1;
  if i == 3 { break; }
}

0006    2 true
0007    | jump.unless         7 -> 37
0028    | jump.unless        28 -> 34
0031    | jump               31 -> 37
0034    5 loop               34 -> 6
```

</Examples>

Only the jumps are listed. At 7 the compiler emitted the loop's exit
with a blank, not knowing the loop would end at 37. At 28 the `if`'s
`jump.unless` got a blank too, patched to 34 as soon as the `if`'s body
ended. The `break` at 31 is a `jump` with a blank, pushed onto the
loop's `breaks` list. At 34 the `loop` back to 6 was written whole,
since 6 was already known; then the compiler patched the exit and every
entry of `breaks` to 37, the first byte after the loop.

<More title="for loops, continue, and their hidden locals">

`for i in 0..3 { print i; }` needs somewhere to keep the counter and the
end value, so the compiler gives the loop two **hidden locals**, slots
with names a program can never write (they start with a space), plus
the visible `i` as a fresh local each time round:

<Figure takeaway="A for loop is a while loop with two hidden locals." caption="The real bytecode of for i in 0..3 { print i; }. iter.range only checks that both ends are numbers; the counter (slot 1) and end (slot 2) stay on the stack as hidden locals. inc.local adds 1 to the counter in place.">
  <ForLayout />
</Figure>

Each time round, `load.local 1` copies the counter into slot 3, which
becomes `i`; the body runs; a `pop` ends `i`'s life; `inc.local 1` adds
1 to the counter; and `loop` goes back to the test. A loop over a list
has the same shape, with `iter.list`, an index from 0 and `list.len` in
the test. A `continue` in a `while` loop jumps back to the condition,
which is already compiled, so it is a plain `loop`; in a `for` loop it
must reach the increment, which comes *after* the body, so it is
another list of blanks, patched as soon as the body ends. Using either
outside a loop is a compile error, `'break' outside a loop`.

<Run id="loops" />

Any compiler that emits forward jumps in one pass has to leave room for
the distance and fill it in later, whether it patches bytes as Drip
does or attaches labels that are resolved at the end.

</More>

## What you learned

- A **jump** changes `ip` by a two-byte distance counted from the byte
  after it; an `if` uses `jump.unless` (and a `jump` over any `else`),
  a `while` adds a `loop` back.
- **Backpatching**: `emitJump` writes a blank and `patchJump` fills it
  once the target is reached; backward jumps never need it, and
  `break`s wait in a list.
