## One loop, many kinds of thing

Since the Map and Set chapter, one loop has worked on almost everything:

```js
for (const x of [1, 2]) console.log(x);
for (const c of 'hi') console.log(c);
const s = new Set([7]);
for (const v of s) console.log(v);
```

An array, a string and a `Set` are stored in completely different ways,
yet `for...of` walks all three. It cannot know how each is built inside;
instead, each answers the same small question, "what is your next
value?", and the loop only ever asks that. Learn the question, and your
own objects (a range of numbers, a stream of tokens, the nodes of a
syntax tree) can answer it too.

## The iterator protocol

<Analogy title="a ticket dispenser">
At a deli counter you pull a ticket and get the next number. You never
see the roll inside, and when it runs out, the machine says so instead of
handing you a blank.
<span slot="breaks">A ticket roll is used up for everyone; each call to
`[Symbol.iterator]()` hands out a fresh iterator with its own position,
so two loops over one array never steal each other's values.</span>
</Analogy>

Step through what `for...of` does behind the scenes:

<NextSteps client:visible />

The key the loop uses, `Symbol.iterator`, is a **symbol**: a built-in key
that is not a string, so it can never clash with your own property names.
`[Symbol.iterator]()` reads or defines the method stored under it.

<Callout kind="definition">
The **iterator protocol** is an agreement between a loop and a value. An
**iterator** is an object with a `next()` method that returns
`{ value, done }`: `done: false` with the next value, or `done: true` when
there are no more. An **iterable** is an object with a
`[Symbol.iterator]()` method that returns a fresh iterator. `for...of`,
the spread `[...x]` and many built-ins accept any
iterable<Cite id="mdn-iteration-protocols" />.
</Callout>

(`[...x]` makes a new array of every value the iterable hands out, the
array cousin of `{ ...obj }`.)

<Examples of="iterator-protocol">

```js
const it = [10, 20][Symbol.iterator]();
it.next(); // { value: 10, done: false }
it.next(); // { value: 20, done: false }
it.next();
// { value: undefined, done: true }
```

```js
function countdown(n) {
  return {
    next() {
      if (n === 0) return { done: true };
      return { value: n--, done: false };
    },
    [Symbol.iterator]() { return this; },
  };
}
[...countdown(3)]; // [3, 2, 1]
```

```js
const m = new Map([['x', 1], ['y', 2]]);
for (const [k, v] of m) console.log(k, v);
// x 1, then y 2
```

</Examples>

The first calls `next()` by hand, exactly as the stepper did. The second
is an iterator written from scratch: `n` lives in a closure, `next()`
hands out `n` and lowers it (`n--` gives the old value, then subtracts
one), and `[Symbol.iterator]()` returns the object itself (`this`), so it
is iterable too and spread accepts it (a missing `value` counts as
`undefined`). The third shows that a `Map` hands out `[key, value]`
pairs, which `const [k, v]` unpacks into two names.

A plain object is *not* iterable:

```js
const o = { a: 1, b: 2 };
for (const k of o) {}
// TypeError: o is not iterable
for (const k of Object.keys(o)) {} // fine
```

Objects have no `[Symbol.iterator]` method; `Object.keys(o)` returns an
array, and an array is iterable.

<Formal title="What for...of means">

```text
for (const x of s) { B }
  ≈
const it = s[Symbol.iterator]();
let r = it.next();
while (!r.done) {
  const x = r.value; B
  r = it.next();
}
```

<span slot="read">A for...of loop over s behaves like this: get a fresh
iterator from s, ask it for a result, and while the result is not done,
put its value in x, run the body B, and ask again. (The ≈ reads "behaves
almost the same as": the real loop also tells the iterator when you leave
early with break, by calling its return() method, if it has one.)</span>
</Formal>

## Generators: functions that pause

Writing `countdown` by hand meant keeping state in a closure and building
`{ value, done }` objects. A **generator** writes the same thing as an
ordinary loop:

```js
function* countdown(n) {
  while (n > 0) yield n--;
}
[...countdown(3)]; // [3, 2, 1]
```

The `*` after `function` makes it a generator function, and `yield n--`
means "hand `n` out, then wait here until someone asks for the next one".

<Analogy extra title="a bookmark">
You read a chapter of a novel, put a bookmark in, and close it; tomorrow
you open it at the bookmark and carry on, remembering the story so far.
<span slot="breaks">A reader may skim ahead; a generator never runs
ahead of the requests. If no one calls `next()` again, the rest of the
body never runs at all.</span>
</Analogy>

<YieldSteps client:visible />

<Callout kind="definition">
A **generator function**, `function* f() { ... }`, does not run its body
when called; it returns a **generator** object, which is both an iterator
and iterable. Each `next()` runs the body until the next **`yield v`**,
which pauses it and hands out `{ value: v, done: false }`. When the body
ends, `next()` returns `{ done: true }` (with any `return` value as its
`value`, which `for...of` ignores)<Cite id="mdn-iterators-generators" />.
`yield` may only appear directly inside a generator function, not inside
a function nested in it<Cite id="mdn-yield" />.
</Callout>

<Examples of="generator yield">

```js
function* two() { yield 'a'; yield 'b'; }
for (const s of two()) console.log(s);
// a, then b
```

```js
function* evens(xs) {
  for (const x of xs) {
    if (x % 2 === 0) yield x;
  }
}
[...evens([1, 2, 3, 4])]; // [2, 4]
```

```js
function* nums(e) {
  if (e.kind === 'num') {
    yield e.value;
  } else {
    yield* nums(e.left);
    yield* nums(e.right);
  }
}
```

</Examples>

The first is the smallest generator: two `yield`s, so the loop runs
twice. The second filters, with a `yield` inside an `if` inside a loop,
which by hand would take careful bookkeeping. The third walks a syntax
tree from the tagged-unions chapter: `yield*` (with a star) hands out
*every* value of another iterable, here the recursive call on each child,
so `[...nums(tree)]` lists the tree's numbers from left to right.

<OtherLanguages>

```js
function* count(n) {
  for (let i = 0; i < n; i++) yield i;
}
for (const i of count(3)) console.log(i);
```

```python
def count(n):
    for i in range(n):
        yield i

for i in count(3):
    print(i)
```

```java
// no generators: a class keeps the state
class Count implements Iterator<Integer> {
    int i = 0, n;
    Count(int n) { this.n = n; }
    public boolean hasNext() {
        return i < n;
    }
    public Integer next() { return i++; }
}
```

```c
/* no generators: a struct holds the
   state, and a function steps it */
struct count { int i, n; };
int count_next(struct count *c, int *out) {
    if (c->i >= c->n) return 0;
    *out = c->i++;
    return 1;
}
```

</OtherLanguages>

Python's generators are nearly identical (any `def` containing `yield`
is one), though its iterators signal the end by raising a `StopIteration`
exception rather than returning `done: true`. Java has no `yield` for
this, so the state lives in a class, and it asks two questions,
`hasNext()` and `next()`, where JavaScript's one `next()` answers both.
In C, a `struct` holds the state and a function returns `0` at the end.

## Lazy sequences: values only when asked for

A generator computes nothing until someone asks, and that makes something
possible that no array can do: a sequence with no end.

```js
function* naturals() {
  let n = 0;
  while (true) yield n++;
}
```

`while (true)` looks like a bug, however the loop pauses at every
`yield`, so each `next()` does one turn and no more.

<Analogy extra title="a tap and a bucket">
An array is a bucket: all the water is drawn before you use any. A lazy
sequence is a tap: water flows only while you hold a glass under it, for
as long as you like.
<span slot="breaks">A tap runs on its own once opened; a lazy sequence
makes exactly one value per `next()`. And to see the values twice, you
need a fresh generator, which computes them all again.</span>
</Analogy>

<Callout kind="definition">
A **lazy sequence** produces each value only when it is asked for,
rather than all in advance, so it can be infinite, and work never asked
for is never done; an array holds every value at once<Cite id="mdn-generator" />.
</Callout>

<Examples of="lazy-sequence">

```js
const it = naturals();
it.next().value; // 0
it.next().value; // 1
```

```js
function* take(it, n) {
  if (n <= 0) return;
  for (const x of it) {
    yield x;
    if (--n === 0) return;
  }
}
[...take(naturals(), 3)]; // [0, 1, 2]
```

<Run id="lazy-order" />

</Examples>

The first asks for two values, so only two are ever made. The second
tames an infinite sequence: `take` passes values through,
counting down (`--n` subtracts one, then gives the new value), and
`return`s straight after the `n`th, so it never asks for one too many.
The matching mistake is `[...naturals()]`, which never finishes: spread
asks for *every* value, and an endless sequence has no last one. The
runnable one prints a line each
time a value is made and each time one is used: made, used, made, used,
rather than everything made first.

<Prompts ids={['lazy-what', 'infinite-safe']} />

<Callout kind="engine" label="Under the hood">
The bytecode compiler you will build later reads its tokens lazily: it
calls the scanner's `scanToken()` each time it wants one more (see
`book/companion/ts/src/vm/scanner.ts`), so the scanner never reads
further into the source than the compiler has got. It is the iterator
protocol in all but name.
</Callout>

## What you learned

- The **iterator protocol**: `next()` returns `{ value, done }`, and
  `[Symbol.iterator]()` makes an object iterable.
- A **generator**, `function*`, returns a paused generator object; each
  `next()` runs the body to the next **`yield`**, which hands out a value
  and pauses.
- A **lazy sequence** makes each value only when asked, so it can be
  infinite.
