## Where the core left off

You met type and shape inference in *Finding collections, and inferring
shapes*: one fact per SSA value, a two-level lattice ("number" above
"maybe not"), an optimistic fixpoint for loops, and record shapes that
must match exactly, field order included. That is all a `Float64Array`
column needs. This chapter goes further, in the direction a more
ambitious compiler (or a type checker such as TypeScript's) has to go:
facts that say *which* kinds a value may be, facts refined by the tests
the program itself makes, and shapes that can be combined instead of
rejected.

Here is a small program the two-level lattice handles badly:

```js
let x = c ? 1 : 'one';
if (typeof x === 'number') {
  total = total + x;   // x is a number here
} else {
  label = x + '!';     // and a string here
}
```

Inside the first branch, `x` is certainly a number, because the program
has just checked; however, an analysis with one fact per value says
"maybe not" for `x` everywhere, so `total` falls to "maybe not" too, and
it cannot even say that `label` is a string, since "maybe not a number"
covers strings, booleans and objects alike.

<Analogy title="the guest list at the door">
Outside a venue the crowd is mixed, but past the door where ages are
checked, everyone inside is old enough; nobody needs to look at the
guests again, because passing the door is the proof.
<span slot="breaks">A door checks each person as they pass, at the moment
they pass; an analysis learns the fact from the condition alone, ahead
of time, and the fact holds only as long as nothing can change the value
after the check.</span>
</Analogy>

## A lattice of kinds

The first step is a richer fact: the **set of kinds** a value may have,
drawn from `number`, `string`, `boolean`, `undefined`, `null` and
`object` (leaving out functions, symbols and bigints to keep the example
small). Sets ordered by inclusion form a lattice: the join is union, the
empty set (no value seen yet) is the optimistic start at the bottom,
and the set of every kind (nothing known) is the top.

<Figure takeaway="Join is union: from any two sets, go up to the smallest set that contains both." caption="The lattice for three kinds. The empty set (grey) is where an optimistic analysis starts, single kinds (green) are exact facts, pairs (amber) are unions, and the full set (red) says nothing.">
  <KindLattice />
</Figure>

Each operation then needs a rule from kinds to kinds, and the rule for
`+` is where JavaScript's own definition matters: if either side is a
string, the result is a string; otherwise, if either side is an object,
the object is first converted to a primitive (by its `valueOf` or
`toString`), which may give a number or a string; and otherwise the
result is a number (`true + 1` is `2`, `null + 1` is `1`, and
`undefined + 1` is `NaN`, which is still a number).

<Formal title="The rule for + on kinds">

```text
K(a + b) = ⋃ over x ∈ K(a), y ∈ K(b) of
  {string}          if x or y is string
  {number, string}  else, if x or y
                    is object
  {number}          otherwise
```

<span slot="read">The kinds of a + b are the union, over every pair of a
kind x of a and a kind y of b, of: string, if either is a string;
otherwise number or string, if either is an object; otherwise number.</span>
</Formal>

<Examples of="type-inference">

```js
// K(a) = {number}, K(b) = {number}
a + b      // {number}
```

```js
// K(x) = {number, string}
x + 1      // {number, string}
x + '!'    // {string}
```

<Run id="plusKinds" />

</Examples>

The first is the exact case. The second shows why the extra precision
pays: even when `x` is not known to be a number, `x + '!'` is known to
be a string. The runnable checks the rule against JavaScript itself,
including the two surprises: an array plus a number is a string
(`[] + 1` is `'1'`), while an object with a `valueOf` that returns a
number gives a number.

## Facts on the edges of a test

The second step uses the program's own tests. On the true edge of
`typeof x === 'number'`, `x`'s kinds can be intersected with
`{number}`; on the false edge, `number` can be removed. The catch is
that SSA gives `x` one fact everywhere, so there is nowhere to put a
different fact for each branch. The fix is to give the value a new name
on each edge, a copy placed at the start of the branch (often called a
**π-node**), whose fact is the refined one:

<NarrowSteps client:visible />

<Callout kind="definition">
**Narrowing** (or *refinement*) gives a value a smaller set of possible
types on the control-flow edges where a test guarantees it, such as the
two edges out of `typeof x === 'number'`. In an SSA-based analysis it
is done by inserting a copy of the value at the start of each branch, so
that each copy can carry its own fact; at the next φ the facts are
joined again.
</Callout>

TypeScript's checker does the same: its handbook shows a union narrowed
to a different type inside each branch of a `typeof` test, by the
control flow analysis that follows each path through the code, and it
also warns about a quirk any such analysis must respect: `typeof null`
is `'object'`, so the true edge of `typeof x === 'object'` keeps `null`
as well as objects<Cite id="ts-narrowing" />.

Narrowing is sound for an SSA value because the value can never change
after the test. A field is different:

```js
if (typeof p.x === 'number') {
  log(p);          // may set p.x = 'far'
  total += p.x;    // no longer proven
}
```

Between the test and the use, any call or store that might reach the
same object can undo the test, so a compiler may keep a field's
narrowed fact only across code that alias analysis (from *Alias
analysis and points-to*) proves cannot write that field.

## Shapes that merge

The core rejected a collection whose records had different shapes. A
type checker cannot afford to reject; instead it **joins** the shapes:
a field present in every record stays, with its kinds joined, and a
field present in only some becomes optional. TypeScript does this when
it infers the element type of an array of object literals; with tsc
6.0.2, `[{ x: 1, y: 0 }, { x: 1, y: 0, z: 2 }]` gets this type:

```ts
({ x: number; y: number; z?: undefined; }
 | { x: number; y: number; z: number; })[]
```

It keeps both shapes as a union, but writes the missing `z` into the
first as an optional field that can only be `undefined`, so that reading
`p.z` from any element type-checks and gives `number | undefined`.

A struct-of-arrays rewrite still has to demand equal shapes, and the
reason is what a column means: a `z` column for records that lack `z`
needs a separate "present" flag for each row, because `'z' in p`,
`Object.keys(p)` and `JSON.stringify(p)` all distinguish a missing
field from one holding `undefined`, and the rewritten program must
print exactly what the original did. Joined shapes are the right
answer for a checker, which only has to say what *may* be read; a
layout rewrite needs facts that hold for every record.

<More title="Shapes as a lattice">

Shapes ordered by "has at least these fields" also form a lattice, but
an infinite one, since there is no limit on field names; analyses keep
it finite by only ever using the field names that appear in the
program. A shape join is then: the fields common to both, each with its
kinds joined, plus the remaining fields marked optional. Order is a
separate question: TypeScript's object types ignore it, while V8's
hidden classes (from *Shapes, inline caches and elements kinds*) do
not, since `{x, y}` and `{y, x}` are reached by different transitions.

</More>

## What you learned

- **Sets of kinds** form a lattice whose join is union; it can say "a
  string" or "a number or a string" where a two-level lattice says
  only "maybe not".
- The rule for `+` follows JavaScript: a string on either side gives a
  string, an object may give a number or a string, anything else gives
  a number.
- **Narrowing** refines a value on the edges of a test, using a new
  name per edge; it is sound for SSA values, and for fields only where
  alias analysis rules out a write.
- Type checkers **join** shapes, making missing fields optional; a
  layout rewrite still needs equal shapes.
