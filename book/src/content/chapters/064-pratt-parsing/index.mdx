## A ladder with too many rungs

The parser of *Recursive descent, precedence and associativity* has one
function per precedence level. Count what happens when it parses the
lone number `7`: Drip has six levels of binary operators, then unary,
then calls, and every one of those functions is entered, finds no
operator of its own and hands back what the level below gave it. A new
operator means one more function, and one more call.

The real Drip parser, in `companion/ts/src/parser.ts`, reads
expressions with one small table of numbers and one loop instead. The
method is named after Vaughan Pratt, who described it in 1973 as "top
down operator precedence"<Cite id="pratt1973" />, and it builds the same
trees with far less code.

## Binding power

Look at the `2` in `1 + 2 * 3`. Both operators want it: the `+` as its
right operand, the `*` as its left one, and whichever wins decides the
shape of the tree.

<Analogy title="two magnets and a paperclip">
Put a paperclip between a weak magnet and a strong one, and it slides
to the strong one. In `1 + 2 * 3` the `2` is the paperclip, `+` is the
weak magnet and `*` the strong one, so `2 * 3` becomes one chunk before
the `+` gets anything.
<span slot="breaks">Two equal magnets would leave the paperclip stuck
halfway; in a parser a tie always goes to the operator on the left.</span>
</Analogy>

<Figure takeaway="Precedence becomes a table of numbers." caption="Drip’s binding powers. When two operators compete for the operand between them, the longer bar wins. The prefix row is for -x and !x.">
  <BpLadder />
</Figure>

<Callout kind="definition">
A **binding power** is a number attached to an operator that says how
strongly it holds the operands beside it. When two operators compete
for the same operand, the one with the higher binding power gets it; on
a tie, the one on the left gets it.
</Callout>

<Examples of="binding-power">

```text
x + 1 < n && ok
→ (&& (< (+ x 1) n) ok)
```

</Examples>

A realistic loop condition: the `1` goes to `+` (5) rather than `<`
(4), the `n` to `<` rather than `&&` (2), and `&&` ends up at the root,
worked out last, just as a person would read it. A token that is not in
the table, such as a number or a `;`, has no binding power at all,
which is how the parser will know an expression has ended; and adding
an operator to Drip is one more line in the table, not one more
function.

## The loop

Here is the code that runs these contests:

```ts
function pratt(minBp: number): Expr {
  let left = prefix();
  for (;;) {
    const bp = BP[peek().type];
    if (!bp || bp <= minBp) break;
    const op = advance();
    left = { kind: 'binary', left,
      operator: op, right: pratt(bp) };
  }
  return left;
}
```

Line 2 reads one operand (for now, think of `prefix()` as "read a number
or a name"). The loop peeks at the next token and looks up its power;
line 5 is the whole contest: if the token is not an operator, or its
power is not greater than `minBp`, stop. Otherwise take the operator and
build a node with everything so far on the left and, on the right,
whatever a fresh call `pratt(bp)` returns; then go round to see whether
a weaker operator wants the lot. `minBp` is a promise to the caller: "I
am the right operand of an operator this strong, so I only take stronger
ones"; the first call, `pratt(0)`, takes everything. Step through it on
`1 + 2 * 3 - 4`:

<PrattSteps client:visible />

The `*` node is built first, even though `+` came first in the text: the
call stack holds the unfinished `+` while the `*` finishes, and the
final `-` is turned away twice before the top call takes it.

<Callout kind="definition">
A **Pratt parser** parses expressions with one function and one loop
instead of one function per precedence level: it reads an operand, then
keeps taking operators whose binding power is greater than `minBp`,
parsing each one's right operand with a recursive call whose `minBp` is
that operator's own binding power.
</Callout>

<Examples of="pratt-parser">

```text
1 - 2 - 3  pratt(5) meets -: 5 <= 5,
           so (- (- 1 2) 3)
```

</Examples>

Left associativity falls out of that `<=`. The right operand of the
first `-` is parsed by `pratt(5)`, which meets the second `-`, also 5;
`5 <= 5` stops it, so it returns only `2`, and the outer loop takes the
second `-` itself: `(- (- 1 2) 3)`, which is `-4`. Change the test to
`<` and the chain would lean right.

<More title="Work these out, then run them; and the loop as equations">

`1 + 6 - 4` is `3`; brackets start a fresh `pratt(0)`, so `(1 + 2) * 3`
is `9`; `*` beats `==`, so `2 * 3 == 6` is `true`; and `8 / 4 / 2` leans
left, giving `1`.

<Run id="groupings" />

<Formal title="The loop as two equations">

```text
parse(m)   = loop(operand, m)
loop(L, m) = loop(L ∘ parse(bp(∘)), m)
               if bp(∘) > m
           = L   otherwise
```

<span slot="read">To parse with minimum power m, read an operand and
loop. In the loop, with L built so far and the next token an operator
(the small circle): if its power is greater than m, build L circle
"parse with the circle's power", and loop again with that as L;
otherwise the answer is L.</span>
</Formal>

The companion keeps the same ladder one higher (`*` is 7 there), because
it saves 1 for assignment; and the bytecode compiler of Part IV parses
expressions with the same loop and table, emitting bytecode instead of
nodes.

<Analogy extra title="a fairground ride with a height sign">
Each call is a ride with a "you must be this tall" sign set to `minBp`.
A taller operator gets on; a shorter one walks back out to the ride
before, whose sign is lower.
<span slot="breaks">A child who is turned away misses the ride; an
operator turned away by an inner call loses nothing, because the outer
call that takes it gets everything already built to its left.</span>
</Analogy>

</More>

## One token, two jobs

In `print 7 - -2;` the first `-` subtracts and the second negates.
Brackets do it too: the `(` in `(a + b) * 2` groups, while the `(` in
`f(a + b) * 2` calls a function. The parser tells them apart by one
fact: if it holds nothing yet, it is looking for the *start* of an
operand; if it already holds one, the next token can only *join* that
operand to something else.

<Analogy extra title="a shop door">
The same door is the way in from the street and the way out from the
shop; which, depends only on which side you are on.
<span slot="breaks">A door can be used both ways by different people at
once; a token is read once, from one side only, and some tokens (`*`,
`.`) have only one side that works at all.</span>
</Analogy>

<Figure takeaway="Where a token appears decides what it does." caption="Drip tokens with their two possible jobs. A blank box means the token cannot appear there; the number is the binding power of the infix job.">
  <TokenRoles />
</Figure>

<Callout kind="definition">
A token is in **prefix** position when it starts an operand, with
nothing on its left (`-x`, `!ok`, `(1 + 2)`, `7`). It is in **infix**
position when it follows a finished operand and joins it to what comes
next (`a - b`, `f(x)`, `xs[i]`, `p.x`). The same token can mean
different things in the two positions.
</Callout>

So `prefix()` is really a table of its own: for each token that can
start an operand, a function that parses one (a number, a name, a
bracketed group, a negation), and none for a token like `*`, which is
why `print * 2;` reports `expected an expression, found '*'`. Calls,
`.` and `[` are infix operators with the highest power of all. Pratt's
paper calls the two jobs a token's "null denotation" and "left
denotation"<Cite id="pratt1973" />.

<Examples of="prefix-infix">

```text
-f(2) * 3  →  (* (- (call f 2)) 3)
```

</Examples>

The first `-` has nothing on its left, so it is prefix: negate. Prefix
minus parses its operand with the prefix power (7 in our table), so the
operand's loop only takes stronger operators: the call's `(`, which
follows the finished operand `f`, is infix with power 8 and gets in,
while the `*` (6) is too weak, and is taken by the outer loop. So the
call is negated first, then multiplied.

<More title="The companion's two tables, and leaning right">

<Run id="two-jobs" />

The companion stores the prefix table as a `switch`:

```ts
function prefixRule(t: TokenType) {
  switch (t) {
    case '(': return grouping;
    case '[': return list;
    case '-': case '!': return unary;
    case 'identifier': return variable;
    // ...number, string, true, new, fn
    default: return null;
  }
}
```

The infix table is another `switch`: `(` builds a call node and reads
the arguments, `.` reads a property name, `[` reads an index, and every
other operator builds a binary node. Its loop is written the other way
round, `while (prec <= power of the next token)`, parsing a binary
operator's right side with its power plus one; "at least one more than
mine" is the same as "more than mine", so the trees are the same.

To make an operator group to the *right*, parse its right side with one
less than its own power, `pratt(bp - 1)`. Drip's assignment operators
are not in the table at all: the prefix rule for a name checks for `=`
and parses the value with `expression()`, which starts again from the
loosest level, so `a = b = 5` nests to the right; a flag, `canAssign`,
makes `a + 1 = 3` report `cannot assign to this expression`.

</More>

## What you learned

- A **binding power** says how tightly an operator holds its operands;
  the higher number wins a contested operand, and a tie goes left.
- A **Pratt parser** replaces the ladder with a table and one loop;
  `bp <= minBp` stops on equals, so chains lean left.
- A token is **prefix** when the parser holds no operand yet and
  **infix** after one; `-`, `(` and `[` have a job in each.
