## Two loops that look alike

You met lowering in *Lowering JavaScript to VIR*, where the JavaScript
plugin turned a syntax tree into VIR; this chapter goes further, to a
second language whose code can look like JavaScript and still mean
something else. Here are two loops, one in each language (`range(3)`
is Python's sequence 0, 1, 2):

```js
for (let i = 0; i < 3; i++) {
  console.log(i);
  i += 5;
}
```

```py
for i in range(3):
    print(i)
    i += 5
```

JavaScript prints `0` and stops: `i += 5` changed the loop variable to
5, `i++` made it 6, and the test `i < 3` failed. Python prints `0`,
`1` and `2`, because its `for` hands out the next value from
`range(3)` on every pass, whatever the body did to `i`. Same shape,
same words, different meaning. If the Python plugin lowered this loop
the way the JavaScript plugin lowers its `for`, every analysis after it
would reason about a loop that Python never runs, and nothing could
catch the mistake, because the analyses only ever see VIR.

<Analogy title="false friends">
Languages have *false friends*, words that look alike in two languages
but mean different things: the Spanish *embarazada* means pregnant, not
embarrassed. A translator who goes by spelling gets it wrong in a way
nobody reading only the translation can detect. Lowering is
translation, and Python and JavaScript have plenty of false friends.
<span slot="breaks">A false friend is one word, and a dictionary can
list them. Semantic differences are often whole behaviours (how a loop
takes its next value, when a default is computed), and nobody has a
complete list; the plugin found two of its own bugs only by running
both programs and comparing.</span>
</Analogy>

<Analogy extra title="a cup in a recipe">
A recipe that says "one cup of flour" means about 240 ml in an American
kitchen and 250 ml in an Australian one: the same words, a different
quantity, and a cake that is subtly wrong if you guess.
<span slot="breaks">Cups differ by a fixed amount you could convert.
Many semantic differences change *what happens* rather than how much:
Python's `(-1.0) ** 0.5` is a complex number, while JavaScript's is
`NaN`, and no conversion factor turns one into the other.</span>
</Analogy>

<Callout kind="definition">
**Semantic differences** are the places where two languages give
different meanings to code that looks the same: loops, numbers,
indexing, comparisons, defaults, scope. A front end for a
multi-language IR must lower each construct by what it *means* in its
own language, so that the shared analyses can trust the IR completely.
</Callout>

<Examples of="semantic-differences">

```text
print(1.0)       # Python: 1.0
console.log(1.0) // JS:     1
```

```text
7 / 2    # Python 3.5    JS 3.5
7 // 2   # Python 3      JS: no such
-7 // 2  # Python -4     operator
```

```text
(-1.0) ** 0.5
# Python: (6.123233995736766e-17+1j)
# JS:     NaN
```

</Examples>

The first is the smallest difference that matters to Viscosity: Python
keeps the int `1` and the float `1.0` apart and prints them
differently, while JavaScript has one kind of number, so `1.0` *is*
`1`. The second shows division: `/` gives a float in both languages,
but Python also has `//`, floor division, which keeps ints as ints and
rounds *down*, so `-7 // 2` is `-4`, not `-3`<Cite id="python-expressions" />.
The third is real: the corpus program `power_complex.py` takes square
roots of negative floats, which in Python gives a complex number
(here with a tiny rounding error in the real part) where JavaScript
gives `NaN`; how that bit the plugin is told below.

## A hidden counter

This is `counting()` from `lower.ts`, which lowers `for i in range(a, b)`,
trimmed to the lines that carry the meaning (`fb` is the shared SSA
builder):

```ts
const key = `range${s.start}`;
fb.writeVariable(key, fb.current.id, start);
// header: test the hidden counter
const i = fb.readVariable(key);
const cond = fb.emit('binop', [i, bound],
  { operator: '<', src: src(s) });
// body: copy the counter into i
write(target, fb.readVariable(key), target);
stmts(body);
// continue: bump the counter, not i
fb.writeVariable(key, cont.id,
  fb.emit('binop', [fb.readVariable(key),
    one], { operator: '+' }));
```

`start` and `bound` were computed once, before the loop, as Python
evaluates `range(a, b)` once. The counter is a variable of its own,
named after the loop's position in the file, so no Python name can
clash with it. Each pass copies the counter into the target, runs the
body, and then increments the *counter*, so whatever the body did to
`i` is overwritten next time: Python's meaning. Step through it:

<CounterSteps client:visible />

The hidden counter is *better* for the analyses, too: it is a clean
induction variable (from *Induction variables, the call graph and
inlining*),
so a bounds proof about it holds even when the body reassigns `i`. In
this program the body does `i += 50` and then indexes again:

```py
for i in range(len(ps)):
    ps[i].x += 1.0
    i += 50
    if i < len(ps):
        ps[i].x += 0.5
print(ps[60].x)
```

The report says `1 of 3 element accesses proven in bounds`: the first
`ps[i]` is proven, while the one after `i += 50` and the final
`ps[60]` get a check (`ps.x[_vsc_ix(ps, i)]` in the output), and the
compiled program prints `61.5`, exactly as the original does.

`for p in ps` goes the other way: it reads the length in the loop
header on *every* pass, because a Python list iterator notices elements
appended during the loop. The corpus file `append_while_iterating.py`
appends inside such a loop and checks that both versions agree.

## An int is not a float

Viscosity's typed column for Python, `array('d')`, holds C doubles. Put
the int `1` in and the float `1.0` comes out, so a later `print` would
show `1.0` where the original showed `1`. As such, the lowering keeps
the difference (each VIR `const` carries a note, `int` or `float`), and
the numeric inference in `core/src/analysis.ts` computes two facts
per value for Python: `n(v)`, "v is provably a float", and `I(v)`, "v
is provably an int". This is the float rule for an operation, as it is
(wrapped):

```ts
case 'binop': {
  const [a, b] = i.args;
  if (i.operator === '/')
    return nOrI(a) && nOrI(b);
  // ** with a non-integer exponent can
  // be complex: (-1.0) ** 0.5 is 1j.
  if (i.operator === '**')
    return n(a) && I(b);
  if (['+', '-', '*', '%', '//']
        .includes(i.operator!))
    return (n(a) && nOrI(b)) ||
           (I(a) && n(b));
  return false;
}
```

`nOrI(v)` means "a float or an int". `/` of two numbers is always a
float; a power is a float only for a float base and an int exponent;
the other five operators give a float when a float meets a float or an
int, on either side; anything else is not a float.

<Formal title="Two of the float rules">

```text
 n(a)   n(b) ∨ I(b)
────────────────────  ⊕ ∈ {+, −, ×, %, //}
     n(a ⊕ b)

 n(a) ∨ I(a)   n(b) ∨ I(b)
──────────────────────────
        n(a / b)
```

<span slot="read">If a is provably a float, and b is provably a float
or an int, then a combined with b by plus, minus, times, remainder or
floor division is provably a float (the real rule also allows the two
sides the other way round). If each side of a slash is provably a
float or an int, the quotient is provably a float.</span>
</Formal>

A field gets a typed column only if every value stored in it is
provably a float. In `ints_stay_ints.py` the field `count` holds `i`
and `weight` holds `i / 2`, and the report (with `--python-auto`, which
lets Viscosity give a Python list columns without an annotation) says
so: `typed array('d')
columns for weight; list columns for count (may hold non-floats)`.

The int fact has a second use: an index must be an int, because
`ps[1.5]` is a `TypeError` in Python. With `k = 1.5` and `ps[k].x`,
the report says `indexes the array with something that may not be an
int`, and the list is kept.

## Records are dataclass calls

JavaScript has object literals; Python's closest thing to a record is a
dataclass, a class whose `@dataclass` decorator generates an `__init__`
that stores each annotated field, in order<Cite id="python-dataclasses" />.
So the plugin first collects the module-level dataclasses whose bodies
are only annotated fields, then lowers `P(...)` to `record.new` with
the values in field order: positionals first, then keywords, then
defaults. In the corpus file `keywords_defaults.py`,
`Body(i * 1.0, y=1.5)` (with `m` defaulting to `2.0`) becomes a
record of `i * 1.0`, `1.5` and `2.0`. Keywords in a *different* order
from the fields, such as `P(y=1.0, x=v)`, are not lowered to a record
at all: Python evaluates arguments left to right, and moving them into
field order could change that order, so the plugin refuses rather than
guess. The report then says the list "appends something that is not a
fresh dataclass instance", and its note in brackets names both
conditions: a dataclass call is modelled only with its arguments in
field order and literal defaults.

<Callout kind="pitfall">
Defaults are a false friend, and the plugin once got them wrong (since
fixed). Python evaluates a field's default *once*, when the
class is defined, but the lowering copied the default's expression to
every call, so with `y: float = K` and a later `K = 3.0` the compiled
program stored `3.0` where Python stored `2.0`. Now only literal
defaults like `2.0` are modelled. A second one: the float rule once said float `**`
float is a float, but `(-1.0) ** 0.5` is complex, which an `array('d')`
refuses with a `TypeError`. Both are invisible to the shared core and
were caught only by comparing real runs; `nonliteral_default.py` and
`power_complex.py` keep them fixed.
</Callout>

<Prompts ids={['sd-dataclass', 'sd-kwargs']} />

Scope is the last difference: Python has no block scope (a loop
variable is still there after the loop), so the plugin collects names
per function, not per block.

<Callout kind="engine" label="Under the hood">
Notice where the knowledge lives. The tokenizer and parser know
Python's *spelling*; the lowering knows its *meaning* (the hidden
counter, the argument rules, the int and float notes); the core knows
only the few facts it cannot do without. Every bug above was in the
meaning layer, which is why the plugin's differential test,
`frontend-python/test/differential.test.ts`, runs both programs with
the real `python3` and compares their output and their exceptions.
</Callout>

## What you learned

- **Semantic differences** are where similar-looking code means
  different things; lowering must translate meaning, because the shared
  analyses trust VIR completely.
- `for i in range(...)` uses a hidden counter and a bound evaluated
  once; `for p in xs` re-reads the length on every pass.
- For Python, "numeric" means provably a **float**; ints are tracked
  separately, and an index must be an int.
- A dataclass call becomes `record.new` with fields in order; keywords
  out of order are refused, and only literal defaults are modelled.
