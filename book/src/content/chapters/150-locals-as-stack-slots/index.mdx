## Every name costs a search

In the chapter on globals, every use of a global variable became an
instruction like `load.global 2 'total'`: the operand picks a constant
holding the name, and at run time the VM hashes that name and searches
its globals table for it. That is fine for a handful of top-level
names; however, most of the variables a real program touches are
**locals** (the loop counter, the running total, the half-finished
answer), and they are used far more often:

```drip
{
  let total = 0;
  total = total + 5;
  print total;
}
```

Looked up by name, each of the three uses of `total` would hash
`"total"` and probe a table; however, the compiler can already see
which `let` each use refers to, so it should settle that once, at
compile time, and give the running program something cheaper than a
name.

## Locals come and go like a stack

Look at the order in which the locals of a nested block are created
and destroyed:

```drip
{
  let a = 1;
  {
    let b = 2;
  }
  let c = 3;
}
```

`a` is born on line 2; `b` is born on line 4 and dies at the brace
on line 5; `c` is born on line 6; and at the last brace `c` and `a`
die, `c` first. Because blocks nest (an inner block always ends
before the one around it), the local created **last** is always the
first destroyed, which is the rule of a stack: last in, first out.

<Analogy title="a pile of plates by the sink">
After a dinner party, plates pile up by the sink: each new plate goes
on top, and when you wash up you take from the top, so the last plate
put down is the first one washed. If you counted the plates from the
bottom as they went down (0, 1, 2), you could say "plate 1" and anyone
would know which one you meant, without writing names on the plates.
<span slot="breaks">With a real pile you can only reach the top plate;
the VM can read or change any slot by its number, whenever it likes.
The stack order only decides which slots exist at a given moment, not
which one you may touch.</span>
</Analogy>

<Analogy title="cars in a narrow driveway">
Cars park nose to tail in a long, narrow driveway with a wall at the
far end. The first car in is parked against the wall, and the last car
in has to be the first to leave, because it blocks everyone else.
Each car's spot can be named by counting from the wall: "the second
car".
<span slot="breaks">In a driveway the cars themselves force the
order; with locals it comes from the way blocks nest, and it is the
compiler, not physics, that keeps count.</span>
</Analogy>

The VM already has a stack, so the plan is to keep each local **in a
slot of that same stack**, and a second piece of luck makes this
almost free: when the VM runs `let a = 1;`, the initialiser leaves `1`
on top of the stack, and if `a` lives in *that* slot, no instruction
is needed to "define" `a` at all.

<Callout kind="definition">
A **stack slot** is a fixed position in the VM's value stack, counted
from where the current function's part of the stack begins. Each
local variable lives in one slot, from its `let` to the end of its
block, and instructions name the local by its slot number only:
`load.local 2` means "push a copy of slot 2". No variable name
survives into the running program.
</Callout>

<Formal title="What the two local instructions do">

```text
load.local i :   push(stack[base + i])
store.local i :  stack[base + i] := top
```

<span slot="read">load.local i pushes a copy of the value at stack
position base plus i; store.local i writes the top value into that
position and leaves it on top. Base is where the current function's
slots begin (0 for the script).</span>
</Formal>

## The smallest local, disassembled

Here is the companion's disassembler output for a block with one local:

```drip
{
  let a = 1;
  print a;
}
```

```text
== <script> ==
0000    2 const               0 '1'
0003    3 load.local          1
0005    | print
0006    4 pop
0007    | none
0008    | return
```

Offset 0, `const 0 '1'`, pushes constant number 0, which is `1`. It
lands in slot 1 (slot 0 holds the running script itself, as the
chapter on frames explains), and slot 1 is `a` from now on; nothing
else happens for the `let`. At offset 3, `load.local 1` pushes a copy
of slot 1 (its operand is the slot number, one byte), and `print`
pops and prints it. At offset 6, on line 4 (the closing brace), a
`pop` gives `a`'s slot back. `none` and `return` end every script.

Step through a longer program, with two blocks and an assignment,
and watch the slots:

<SlotRunSteps client:visible />

The VM's side is two lines of `vm.ts` (wrapped here to fit):

```ts
case Op.LoadLocal:
  this.push(stack[frame.slots +
    readByte()]); break;
case Op.StoreLocal:
  stack[frame.slots + readByte()] =
    this.peek(0); break;
```

`readByte()` reads the operand, and `frame.slots` is the *base* from
the formal box (0 for the script). `store.local` uses `peek(0)`,
which reads the top without popping it, because in Drip an
assignment is an expression whose value is the value assigned; when
it is a statement on its own, the compiler adds a `pop`. With a
one-byte operand a function has at most 256 slots, and the compiler
reports `too many local variables in one function` past that.

## Examples

<Examples of="stack-slot">

```text
{ let x = 10; let y = 20;
  print x + y; }

0006    4 load.local          1
0008    | load.local          2
0010    | add
0011    | print
0012    5 pop
0013    | pop
```

```text
{ let n = 4; n += 2; }

0003    3 load.local          1
0005    | const               1 '2'
0008    | add
0009    | store.local         1
0011    | pop
```

```text
{ let x = 2; let vx = 3;
  x += vx * 0.5; }

0006    4 load.local          1
0008    | load.local          2
0010    | const               2 '0.5'
0013    | mul
0014    | add
0015    | store.local         1
0017    | pop
```

</Examples>

(The source is squeezed onto one or two lines here; the line
numbers come from the real one-statement-per-line programs.) In the
first, `x` is slot 1 and `y` slot 2, because that is where their
initialisers' values landed; `x + y` reads both, and the closing
brace emits **two** pops, one per local. The second is `+=` on a
local: read slot 1, add 2, write it back with `store.local 1`, and
`pop` the leftover copy, so `n` is `6`. The third is a particle step,
the kind of update this book is about: read `x` (slot 1) and `vx`
(slot 2), multiply, add, write back to slot 1, so `x` becomes `3.5`.

A common slip is to use a local after its block has ended:

```drip
{
  let a = 1;
}
print a;
```

```text
0004    4 load.global         1 'a'
runtime error: undefined variable 'a'
  at line 4 in script
```

Outside the block no local `a` exists, so the compiler treats the
name as a global; there is no such global, and the program stops.
Moved inside the braces, `print a;` becomes `load.local 1` and
prints `1`.

<Callout kind="engine" label="Under the hood">
Real VMs split names from numbers in the same way. CPython's
`LOAD_GLOBAL` finds a global through a table of names, while its
`LOAD_FAST` pushes a local chosen by a plain index<Cite id="cpython-dis" />.
V8's Ignition interpreter goes a step further: it is a register
machine, whose instructions name their inputs and outputs as
numbered registers<Cite id="v8-ignition" />, which play much the role
that Drip's slots do.
</Callout>

## What you learned

- Locals are created and destroyed in last-in, first-out order, so
  each can live in a **stack slot**, a numbered position in the VM's
  own value stack.
- A `let` in a block emits no instruction of its own: the
  initialiser's value is already in the right slot.
- `load.local i` pushes a copy of slot `i`; `store.local i` writes the
  top of the stack into slot `i` and leaves it there.
- A block's closing brace emits one `pop` per local, and a freed slot
  is reused by the next local.
- A name used outside its block is no longer a local; it becomes a
  global lookup, and usually an `undefined variable` error.
