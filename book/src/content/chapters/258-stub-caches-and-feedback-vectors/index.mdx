## Two closures, one cache

You met inline caches, their states and the shared stub cache in
*Shapes, inline caches and elements kinds*, and feedback slots in *Tiers,
speculation and deoptimisation*. This chapter goes further, into where
that feedback is kept, and then into the other half of an array's
elements kind, holes. Start with a puzzle:

```js
function make() { return (o) => o.x; }
const f = make(), g = make();
for (let i = 0; i < 20; i++) f({ x: 1 });
for (let i = 0; i < 20; i++)
  g({ x: 1, y: 2 });
// %DebugPrint(f): slot #0
//   LoadProperty POLYMORPHIC
```

`f` and `g` are two different function objects, and each has only ever
seen one shape; yet `%DebugPrint(f)` (Node v22.23.4, V8 12.4) reports its
`o.x` as polymorphic. The shape that `g` saw is in `f`'s cache.

## One vector per function

Every slot number in a bytecode listing is an index into the function's
**feedback vector**, a heap object that holds the state of each of its
inline caches and feedback slots, together with bookkeeping for tiering:

```
// %DebugPrint(step), trimmed, for
// function step(p, dt) {
//   p.x += p.vx * dt;
//   return Math.abs(p.x); }
 - tiering state: TieringState::kNone
 - invocation count: 12
 - slot #0 LoadProperty MONOMORPHIC
 - slot #2 BinaryOp BinaryOp:Number
 - slot #3 BinaryOp BinaryOp:Number
 - slot #4 LoadProperty MONOMORPHIC
 - slot #6 SetNamedSloppy MONOMORPHIC
 - slot #8 LoadGlobalNotInsideTypeof
            MONOMORPHIC
 - slot #10 LoadProperty MONOMORPHIC
 - slot #12 Call MONOMORPHIC
```

There is a slot for each property load, arithmetic operation, store,
global read and call (the numbers jump by two where a slot takes two
entries), and above them a count of calls since the vector was made and
whether the function is marked for a higher tier.

<Analogy title="a logbook kept with the recipe">
A restaurant keeps one logbook clipped to each recipe card, and every
cook who makes the dish writes in it what the diners asked for. A new
cook starting on the dish reads the same logbook, and adds to it.
<span slot="breaks">A restaurant would start a logbook on the first
night; V8 waits until a function has been called several times, and does
not write down anything from those first calls at all.</span>
</Analogy>

The logbook is made late on purpose, because most functions run only a
handful of times and a vector for each would waste memory. In Node 22
it is allocated once a function has been called eight times (the default
of `--invocation-count-for-feedback-allocation`), and the calls before
that leave no trace:

<Callout kind="definition">
A **feedback vector** is the per-function object in which V8 keeps the
state of every inline cache and feedback slot in that function's
bytecode, along with its invocation count and tiering state. It is
allocated lazily, after a number of calls, and it belongs to the
function literal rather than to one function object: closures created
from the same literal share it<Cite id="v8-src-tiering-12-4" />.
</Callout>

That explains the puzzle. `f` and `g` were made by the same arrow
function in `make`, so `%DebugPrint` shows the same vector address for
both, and for a third closure `h = make()` made afterwards, which
inherits a polymorphic `o.x` before it has run once. The invocation count
says the same: 32, the forty calls of `f` and `g` together minus the
eight made before the vector existed.

<More title="More: what sharing means for real code">

A helper such as `getX(o)` has one vector however many places call it,
so if one caller passes particles and another passes points, the helper's
load is polymorphic for both, and the optimised code for either caller
inherits the wider case when the helper is inlined into it. A factory
that returns closures (`make` above, or a library that builds accessors
for you) has the same property: every closure from one factory shares
one set of caches. When a hot loop must see one shape, give it a function
of its own. And past four shapes the slot reads `MEGAMORPHIC`, meaning the
site has handed over to the stub cache shared by all megamorphic loads in
the engine<Cite id="v8-src-ic-12-4" />.

</More>

## An index with nothing in it

The elements kinds of *Shapes, inline caches and elements kinds* all
began with `PACKED_`. The other half of the name is about a question
every element load has to answer: is there really an
element at this index? In most languages the answer is always yes for an
index below the length; in JavaScript it is not:

```js
const xs = [0, , 2];  // a hole at 1
const ys = [];
ys[3] = 'x';          // holes at 0, 1, 2
```

`xs` has length 3, but nothing at index 1 (the empty space between the
commas); `ys` has length 4, and only index 3 holds anything. A hole is not
the same as storing `undefined`: `Object.hasOwn(xs, 1)` is `false`, the
array simply does not have an element 1, and reading `xs[1]` makes
JavaScript look further, at the object the array inherits from,
`Array.prototype`<Cite id="v8-elements-kinds" />.

<Analogy extra title="numbered lockers">
A row of lockers numbered 0 to 2, where locker 1 has never been assigned
to anyone. Ask for whatever is in locker 1 and the attendant does not hand
you an empty box; she goes to the office to ask whether anything for
locker 1 was left there, and only then tells you there is nothing.
<span slot="breaks">An unassigned locker is still a real, empty locker; a
hole is a marker that says "no element here", and the look-up it causes
goes through the prototype objects, which code can change.</span>
</Analogy>

<Analogy extra title="an egg box">
In a full egg box you can reach into any cup without looking. Once you
know some cups might be empty, you have to look before every grab, even
in the cups that are full.
<span slot="breaks">You can refill an egg box and forget it was ever
short; in V8 12.4 an array that has had a hole stays HOLEY even after
every hole is filled.</span>
</Analogy>

Usually nothing is on the prototypes and the read gives `undefined`, but

That is why holes are costly: for a packed array V8 knows every index
below the length has its own element, while for a holey one a read needs
extra checks and may have to search the prototype
chain<Cite id="v8-elements-kinds" />.

<Callout kind="definition">
A **holey array** has at least one index below its `length` with no
element of its own. Each basic kind has a holey variant
(`HOLEY_SMI_ELEMENTS`, `HOLEY_DOUBLE_ELEMENTS`, `HOLEY_ELEMENTS`), and
PACKED → HOLEY is one-way too: filling every hole later does not make the
array packed again<Cite id="v8-elements-kinds" />.
</Callout>

<Formal title="When an array is holey">

```text
holey(a) ⇔ at some time, ∃ i < a.length :
              ¬ hasOwn(a, i)
```

<span slot="read">An array a is holey if and only if (⇔), at some moment
in its life, there existed (∃) an index i below its length for which a
did not (¬) have an own element. "At some time" is the one-way part: the
condition only has to have been true once.</span>
</Formal>

<Examples of="holey-array">

```js
[0, , 2]   // HOLEY_SMI_ELEMENTS
```

```js
const h = new Array(3); // HOLEY_SMI
for (let i = 0; i < 3; i++) h[i] = i;
// still HOLEY_SMI_ELEMENTS
new Array(3).fill(0);   // HOLEY_SMI too
```

```js
// building n particles' x values:
const xs = [];
for (let i = 0; i < n; i++) xs.push(i);
// PACKED_SMI_ELEMENTS: push never
// skips an index
```

</Examples>

The first is the smallest hole, written directly. The second is the
common surprise: `new Array(3)` makes an array of length 3 with three
holes, and filling them in order does not make it packed. The V8 post
that describes the lattice adds a 2025 update saying `fill` is now an
exception to this rule<Cite id="v8-elements-kinds" />, but that is too
recent for Node 22, where `new Array(3).fill(0)` is still
`HOLEY_SMI_ELEMENTS` (checked with `%DebugPrint`). The third is the
habit to keep: start from `[]` and `push`, which always writes at the
current length, so no index is ever skipped.

Element loads see the difference too. Reading a hole once with
`--log-ic` gives a line that ends in a modifier the other loads in this
book never had:

```
KeyedLoadIC 2:29 0 1 1 .HOLES
```

(Node v22.23.4, V8 12.4, for `xs[1]` on `[0, , 2]`.) The cache records
that this load may meet holes, which is the extra checking of the
stepper, written down.

## What you learned

- A **feedback vector** holds a function's inline caches and feedback
  slots, its invocation count and its tiering state; in Node 22 it is
  made after eight calls, and closures of one function literal share it.
- A **hole** is an index below `length` with no element of its own; it is
  not `undefined`, and reading it continues along the prototype chain.
- Every basic kind has a **holey** variant, and PACKED → HOLEY is one-way;
  in V8 12.4 even `new Array(n).fill(v)` stays holey.
- Build arrays with literals or `push` to keep them packed, or use a
  typed array, which has no holes at all.
