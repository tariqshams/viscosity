## Has this already happened?

Look again at the Collatz graph from *IR, three-address code and
control-flow graphs*. Can b7, the join of the `if`, reuse the `n % 2`
computed in b2? Only if b2 has *certainly* run by then. Can it reuse
`3 * n` from b5? No: on the path through b6, b5 never ran. What matters
is whether you can get to b7 *without* the block.

<Analogy title="an island town with one bridge">
However you plan the trip into town, by the coast road or through the
hills, you cross the one bridge, so the bridge **dominates** the town. A
café you sometimes stop at on the way does not, because there is a
route that skips it.
<span slot="breaks">Bridges are permanent; whether a block dominates
another depends on the whole graph, so adding a single new edge (one new
route into town) can take away a block's dominance.</span>
</Analogy>

<Callout kind="definition">
In a CFG with entry block E, block A **dominates** block B if every path
from E to B passes through A. Every block dominates itself, and E
dominates every reachable block; A **strictly dominates** B if it
dominates B and A ≠ B. The strict dominators of a block always form a
chain, each dominating the next, so the closest one, its **immediate
dominator** idom(B), is enough: drawing an edge from idom(B) to B for
every block except the entry gives the **dominator tree**, and A
dominates B exactly when A is B or an ancestor of B in that tree.
</Callout>

<Examples of="dominator dominator-tree">

```text
idom: b1→b0  b2→b1  b4→b1
      b5→b2  b6→b2  b7→b2  b3→b7
```

</Examples>

This is what Viscosity's `dominators` returns for the Collatz graph:
each block's parent in the tree. b7's parent is b2, since either branch
can be skipped, so Dom(b7) is \{b0, b1, b2, b7\}. b4, the exit, hangs
off b1, not b2: when `n` starts at 1 the test fails at once and b4 runs
without b2, so running earlier is not dominating. And b3, the jump back
to the test, hangs below b7, so its CFG edge b3 → b1 goes to one of its
own ancestors; that is how loops are found.

## Computing the tree with two fingers

To reach B you must arrive from one of its predecessors, so a block
dominates B exactly when it is B itself or dominates *every*
predecessor of B; in tree terms, idom(B) is the nearest common ancestor
of B's predecessors. `dominators` in `packages/core/src/cfg.ts` computes
exactly that, by the iterative algorithm of Cooper, Harvey and Kennedy,
"A Simple, Fast Dominance Algorithm", storing only the tree (trimmed):

```ts
const intersect = (a, b) => {
  while (a !== b) {
    while (index.get(a) > index.get(b))
      a = idom.get(a);
    while (index.get(b) > index.get(a))
      b = idom.get(b);
  }
  return a;
};
// until nothing changes, for each block
// b in reverse postorder (not the entry):
let d = preds[0];
for (const p of preds.slice(1))
  d = intersect(p, d);
if (idom.get(b) !== d) {
  idom.set(b, d); changed = true;
}
```

`index` is each block's position in **reverse postorder** (a
depth-first search writes each block down once its successors are
done, and the list is reversed), so a block's idom always comes earlier
than the block. `intersect` puts a finger on each of two blocks and
moves whichever is later up to its idom, until the fingers meet at the
nearest block dominating both; the loop does that across a block's
predecessors (those with an idom so far, so unreachable blocks never
get one), and passes repeat until nothing changes. For Collatz the
order is `0 1 4 2 6 5 7 3`, and the second pass only confirms.

<More title="More: the dominator equation, sets that shrink, and a check by deletion">

<Formal title="The dominator equation">

```text
Dom(E) = { E }
Dom(B) = { B } ∪ ⋂ Dom(P)
               P ∈ pred(B)
```

<span slot="read">The entry is dominated only by itself. Any other
block B is dominated by itself together with (∪) the blocks that are in
the dominator set of every predecessor P of B (the big ⋂ reads "the
intersection over all P").</span>
</Formal>

Solved directly with sets, every non-entry set starts as "all blocks"
and is recomputed in reverse postorder until nothing changes; the sets
only shrink, and starting from "all" matters at a loop header, whose
back-edge predecessor has not been computed on the first pass (starting
it empty would wrongly empty the header's set, and a shrinking set can
never win the entry back). The fingers do the same intersection on the
tree, without building a single set.

A second way to say "A dominates B" makes a good check: deleting A from
the graph cuts B off from the entry.

## Finding the loops again

Almost every decision Viscosity makes is about a loop, where a program
spends its time; yet in VIR the word `for` is gone. Here is a function
with two loops, one inside the other:

```js
function sum(g) {
  let s = 0;
  for (let i = 0; i < g.length; i++)
    for (let k = 0; k < 3; k++)
      s += g[i].x;
  return s;
}
```

In its VIR, b1 is the test `i < g.length` and b3 is the `i++`, ending
with `br b1`; that arrow from b3 back up to b1 is all that is left of
the outer loop. What makes it special is dominance: b1 dominates b3,
since you cannot reach the end of a pass without passing the test, so
the arrow jumps back to a block you *certainly* passed on the way in.

<Callout kind="definition">
A **back edge** is a CFG edge `t → h` whose target `h` dominates its
source `t`. The **natural loop** of that back edge is `h` together with
every block that can reach `t` without passing through `h`; `h` is the
loop's **header** and `t` a **latch**. Every block in a natural loop is
dominated by its header, so the header is the only way in. Back edges
with the same header make one loop.
</Callout>

The definition says how to compute the loop: start with the header, add
the latch, then keep adding the predecessors of anything added,
skipping blocks already in. The header is in from the start, so it acts
as a fence and the walk never leaks out through the entrance. Here is
`naturalLoops` in `cfg.ts`, very slightly trimmed, run for every block
`b`:

```ts
for (const s of successors(f, b.id)) {
  if (!dominates(idom, s, b.id)) continue;
  let body = byHeader.get(s);
  if (!body)
    byHeader.set(s, (body = new Set([s])));
  const stack = [b.id];
  while (stack.length) {
    const x = stack.pop()!;
    if (body.has(x)) continue;
    body.add(x);
    for (const p of f.blocks[x].preds)
      stack.push(p);
  }
}
```

The first line lets only back edges through: a successor `s` that
dominates `b` (`dominates` walks up the tree from `b`, looking for
`s`). The body for header `s` starts as `{s}` the first time and is
reused after, which is how two latches merge. Then the walk: pop a
block, skip it if it is in, otherwise add it and push its predecessors.

<Examples of="natural-loop">

```text
header b1  depth 1
  body b1 b2 b3 b5 b6 b7 b8
header b5  depth 2
  body b5 b6 b7
```

</Examples>

This is what `naturalLoops` returns for `sum`. The outer back edge
b3 → b1 gives seven blocks; the inner one, b7 → b5 (`k++` back to
`k < 3`), gives three inside it. A loop's **depth** counts the loops
containing its header, and the innermost loop around a block is the
smallest containing it (`loopOf`): the read of `g[i].x` in b6 is charged
to the `k` loop, and `viscosity explain` reports that the loop at line 4
touches one field, `x`.

Right: the entry can jump to a or to b, so neither dominates the other; the edges between them form a cycle, but neither is a back edge.">

Not every cycle is a natural loop: on the right, the entry can jump to
`a` or to `b`, so neither dominates the other and neither edge is a back
edge, however "upward" it looks. Such a cycle is **irreducible**;
structured `for` and `while` loops never produce one.

<More title="More: two latches, the smallest loop, and other compilers">

A block with an edge to itself is the smallest loop there is, `{b1}`.
Two ways back to one header, from `a` and from `b` (the shape a
`continue` often makes), are two back edges whose walks overlap, so
they merge into one loop with two latches; LLVM does the
same<Cite id="llvm-loop-terminology" />, while Viscosity's own lowering
sends both through one shared block first. LLVM's loop information pass
computes the same nesting for its own optimisations<Cite id="llvm-passes" />,
and dominators are one of the classic analyses of a middle
end<Cite id="coopertorczon2022" />. Their other famous use, placing the
phis of SSA at the edges of each block's territory, is the deep dive
*Dominance frontiers and classic SSA construction*.
