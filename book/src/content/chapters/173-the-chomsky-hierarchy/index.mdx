## A family of four

You met grammars in *Grammars and parse trees* and finite automata in
*Finite automata*; this chapter puts them into one family, proves where
a language sits in it, and goes on to the machine that grammars need and
to the places where real languages step outside their grammars.

In 1959 Noam Chomsky described grammars by the shapes their rules may
take, and showed that each stricter shape describes a smaller class of
languages<Cite id="chomsky1959" />; the ladder he described is now called
the **Chomsky hierarchy**.

<Callout kind="definition">
The **Chomsky hierarchy** sorts grammars by the shape of their rules.
**Regular** grammars (type 3) give exactly the regular languages, the
ones regular expressions and finite automata describe. **Context-free**
grammars (type 2), whose heads are a single nonterminal, are the ones
parsers are written from; they need a *pushdown automaton*, a finite
automaton with a stack. **Context-sensitive** grammars (type 1) may look
at the symbols round a nonterminal, and **unrestricted** grammars
(type 0) may rewrite anything; the first need a *linear-bounded
automaton*, the second a *Turing machine* (a model of any
program)<Cite id="hmu2006" />.
</Callout>

<Formal title="The four rule shapes">

```text
type 3   A → a B   or   A → a
type 2   A → γ
type 1   α A β → α γ β   (γ ≠ ε)
type 0   α → β           (α ≠ ε)
```

<span slot="read">A and B are nonterminals, a is one terminal, and the
Greek letters stand for rows of symbols. Type 3: a nonterminal becomes a
terminal followed by at most one nonterminal. Type 2: a nonterminal
becomes any row, wherever it stands. Type 1: A may become gamma only when
it stands between alpha and beta, its context, and gamma is not empty.
Type 0: any nonempty row may become any row. (Books differ in small
details, such as where ε is allowed.)</span>
</Formal>

<Examples of="chomsky-hierarchy">

```text
type 3, a number's digits:
num → DIGIT num | DIGIT
```

```text
type 2, brackets nested to any depth:
p → "(" p ")" | ε
```

```text
beyond type 2:
let x = 1;  print x;   ✓
let x = 1;  print y;   ✗ y never declared
```

</Examples>

The first is regular: each rule adds one digit and moves on, which a
finite automaton follows with a single loop. The second is context-free:
the rule puts `p` in the *middle*, and a machine must count the open
brackets. The third, "use a name only after declaring it", has the shape
of a word written twice, which no context-free grammar can express (the
section "Past context-free" says why); so compilers check names in a
separate pass after parsing, as *The resolver* does for Drip.

## Proving a negative

The second example made a claim: that brackets need more than a finite
automaton. Suppose a colleague says they have found a regular expression
that matches exactly the balanced rows of `(` and `)`, and it passes a
hundred tests. That proves nothing (the hundred-and-first might fail),
and neither does "I tried and could not find one". We need an argument
that covers *every* regular expression at once; and since every regular
language has a DFA, it is enough to show that no DFA can do the job.

<Analogy title="a walk round a small town">
A town has only five junctions. Walk more than five blocks and you must
pass some junction twice, however you choose your route; and the stretch
between the two visits is a loop you could have left out, or walked
three times, and still finished in the same place.
<span slot="breaks">A walker can choose to repeat a junction; a DFA has
no choice at all, since each character decides its next state. And the
town only guarantees that *some* junction repeats, not which one, which
is why the argument has to work wherever the loop turns out to be.</span>
</Analogy>

## The pumping lemma

Take any DFA with `p` states that accepts every string of the form
`aⁿbⁿ` (some `a`s, then the same number of `b`s), and feed it `aᵖbᵖ`.
Step through it on a small machine:

<PumpSteps client:visible />

Reading the first `p` characters passes through `p + 1` states, so one
comes back; going round the loop between the two visits zero times or
twice changes only the number of `a`s, and the machine accepts a string
outside the language. No DFA escapes this, so `aⁿbⁿ` is not regular.
Written down once and for all, the argument is a theorem.

<Callout kind="definition">
The **pumping lemma for regular languages**: if `L` is regular, there is
a number `p` (the number of states of a DFA for `L` will do) such that
every string `w` in `L` of length at least `p` can be cut as `w = x y z`,
where `y` is not empty, `x y` has at most `p` characters, and
`x yᵏ z` is in `L` for every `k ≥ 0`. To prove a language is *not*
regular, show that for every `p` some long string cannot be cut that
way<Cite id="hmu2006" />.
</Callout>

<Formal title="The pumping lemma">

```text
L regular  ⇒  ∃p ≥ 1. ∀w ∈ L, |w| ≥ p.
  ∃x, y, z. w = xyz ∧ |xy| ≤ p
    ∧ y ≠ ε ∧ ∀k ≥ 0. x yᵏ z ∈ L
```

<span slot="read">If L is regular, then there exists a number p of at
least 1 such that, for every string w in L whose length is at least p,
there exist strings x, y and z with w equal to x y z, x y no longer than
p, y not empty, and, for every k from 0 upwards, x followed by k copies
of y followed by z still in L.</span>
</Formal>

<Examples of="regular-language">

```text
aⁿbⁿ:  w = aᵖbᵖ, y is all a's,
x yy z has more a's than b's:
not in L, so not regular
```

```text
balanced ( ): w = (ᵖ )ᵖ, y is all (,
x z has too few (   not regular
```

```text
(ab)*:  every long w pumps,
take y = "ab"   (and it is regular)
```

</Examples>

The first is the stepper's argument in one line. The second is the
colleague's brackets: the same string shape, with `(` for `a` and `)` for
`b`, so the same loop breaks them, and no regular expression, however
clever, matches balanced brackets. The third is a warning about which way
the lemma works. `(ab)*` pumps happily, and it *is* regular; however,
there are languages that are not regular and still pump, so a string that
pumps proves nothing. The lemma is a test that only ever says "no". (To
show that a language *is* regular, you build a regular expression or an
automaton for it.)

Here is the argument as a program, on the three-state machine from the
stepper, `A` to `X` on `a`, then `X` to `B` on `b`, with loops on `X` and
`B`. `loop` finds the first state that comes back in the trail, and the
loop is cut out and pumped:

<Run id="pump" />

`trail` records every state passed through; `loop` finds the first
position `j` whose state already appeared at an earlier `i`, and the
characters between them are `y`. It prints the cut `x = "a"`, `y = "a"`,
`z = "abbb"`, then `true` for `aabbb`, `aaaabbb` and `aaaaabbb`, none of
which has equal counts.

</More>

## A stack is the missing memory

What `aⁿbⁿ` needs is a memory that can grow: count the `a`s, then count
them off against the `b`s. A **pushdown automaton** is a finite automaton
with exactly that, a stack, and it is the machine of the context-free
level. Here it checks brackets with one state, pushing each `(` and
popping one for each `)`:

<PdaSteps client:visible />

<Callout kind="definition">
A **pushdown automaton** (PDA) is a finite automaton that also has a
stack, starting with a bottom marker. Each move depends on the current
state, the next input character (or none, for an ε-move) and the symbol
on top of the stack; it changes state, pops the top symbol and pushes a
row of symbols in its place. A PDA may be nondeterministic, like an NFA;
the languages that PDAs accept are exactly the context-free
languages<Cite id="hmu2006" />.
</Callout>

You have already written one. A recursive-descent parser is a pushdown
automaton whose stack is the call stack: each call to a rule's function
pushes a frame that remembers where to carry on in that rule, and each
return pops one, so nesting a thousand brackets deep uses a thousand
frames.

There is one difference from finite automata, and it matters for every
parser in this part. For finite automata, nondeterminism adds no power
(the subset construction of *From regular expressions to fast scanners*
removes it); for pushdown automata it does. Some context-free languages
need a PDA that guesses: for palindromes such as `abba` or `racecar`, a
PDA pushes the first half and pops it against the second, but nothing in
the input tells it where the middle is, so no deterministic PDA accepts
them<Cite id="hmu2006" />. The languages a *deterministic* PDA accepts are
the **deterministic context-free languages**, and they are exactly the
languages that the LR parsers of the coming chapters can parse: Knuth's
1965 paper showed that a language has an LR(k) grammar exactly when a
deterministic PDA accepts it, and that every such language then also has
an LR(1) grammar, with one token of lookahead<Cite id="knuth1965" />.

## Past context-free

Add one more count, `aⁿbⁿcⁿ`, and the stack is not enough. It can check
the `b`s against the `a`s, but popping the `a`s to do so throws away the
count that the `c`s need; and keeping it means not matching the `b`s.
The same goes for `w w`, any word written twice, which is the shape of
"declare a name, then use the same name": a stack gives back the first
copy in reverse order, never in the order needed. A second pumping lemma,
for context-free languages, turns that intuition into a proof for
both<Cite id="hmu2006" />.

<More title="The context-free pumping lemma, and a grammar for aⁿbⁿcⁿ">

A parse tree that is tall enough must repeat a nonterminal on some path
from the root, for the same pigeonhole reason as before (a grammar has
only so many nonterminals). The subtree between the two copies can be
repeated, and it pumps *two* places in the string at once, `u vᵏ x yᵏ z`.
Two places can keep two counts in step, as `aⁿbⁿ` needs, but not three:
in `aᵖbᵖcᵖ`, the piece `v x y` can be chosen at most `p` characters long,
so `v` and `y` cannot touch both the `a`s and the `c`s, and pumping
unbalances the counts<Cite id="hmu2006" />.

One level up, `aⁿbⁿcⁿ` has a grammar whose rules may look at their
neighbours:

```text
S  → a S B C  |  a B C
CB → BC
aB → ab    bB → bb
bC → bc    cC → cc
```

`S` lays down the `a`s with one `B` and one `C` for each; `CB → BC`
sorts every `B` before every `C`; and the last four rules turn each `B`
into `b` and each `C` into `c`, but only when the right letter stands to
their left, so the result is always in order. No rule makes a row
shorter, which is the mark of the context-sensitive level.

</More>

<Prompts ids={['anbncn']} />

<More title="Intersections, and which questions a program can answer">

Two facts follow that every parser writer meets sooner or later. The
first is that context-free languages are not closed under intersection:
`aⁱbⁱcʲ` (equal `a`s and `b`s) and `aʲbⁱcⁱ` (equal `b`s and `c`s) are
both context-free, yet the strings in both are exactly `aⁿbⁿcⁿ`. As
such, "this grammar, and also that rule" can leave the context-free level,
however simple each part is. The second is kinder: a context-free
language intersected with a *regular* one is always context-free, so a
regular restriction (say, "the file ends with a newline") can be added to
a context-free grammar without leaving the level<Cite id="hmu2006" />.

The levels also differ in which questions a program can answer about
them. The table sums up the standard results<Cite id="hmu2006" />:

```text
question            reg  CF   CS   type 0
is w in L?          yes  yes  yes  no
is L empty?         yes  yes  no   no
same language?      yes  no   no   no
```

"Yes" means an algorithm always answers; "no" means none can. Two
regular languages can be compared by minimising both DFAs and checking
that the results are the same machine (*Minimal DFAs and scanner
generators*); two context-free grammars cannot be compared at all in
general, so no tool can check, for every pair, whether a rewritten
grammar still describes the language the old one did (which is one
reason compilers keep large test suites of real programs). Whether a
context-free grammar is ambiguous cannot be decided either.

</More>

## Where real languages step outside

<Figure takeaway="Each band holds languages the band inside it cannot describe; parsers live in the deterministic band." caption="The hierarchy with the deterministic context-free languages (dashed) drawn in.   <LanguageMap />
</Figure>

Most of what a context-free grammar cannot say is checked after
parsing; however, some languages need context while they are still
reading their tokens, and each smuggles it in its own way.

<Examples of="chomsky-hierarchy">

```c
typedef int T;
T * x;      // declares x, a pointer
int a, b;
a * b;      // multiplies
```

```js
let x = a / b / c;    // two divisions
let r = /b/.test(s);  // a regex literal
```

```python
if ready:
    go()       # INDENT before go
stop()         # DEDENT before stop
```

</Examples>

In C, `T * x;` declares `x` if an earlier `typedef` made `T` a type, and
multiplies otherwise; GNU C's scanner looks each name up in the symbol
table and returns `TYPENAME` rather than `IDENTIFIER` for type names, so
the parser's input already carries the context<Cite id="bison-manual" />.
In JavaScript, `/` starts a division or a regular expression literal; the
specification gives its scanner several *goal symbols*, `InputElementDiv`
and `InputElementRegExp` among them, and the syntactic context says
which one applies<Cite id="ecma262" />. Python's scanner keeps a stack of
indentation levels: a deeper line pushes a level and produces `INDENT`,
a shallower one pops levels, one `DEDENT` each<Cite id="python-lexical" />.
That stack is a pushdown automaton hiding inside the scanner, turning
indentation into tokens a grammar can treat like `{` and `}`.

## What you learned

- The **Chomsky hierarchy**: regular ⊂ context-free ⊂ context-sensitive
  ⊂ unrestricted, recognised by finite automata, pushdown automata,
  linear-bounded automata and Turing machines; programming-language syntax
  is context-free, and rules such as "declare before use" are checked
  after parsing.
- The **pumping lemma** proves a language is not regular: a long enough
  string makes a DFA repeat a state, and the loop between the repeats can
  be pumped. It never proves a language is regular.
- A **pushdown automaton** is a finite automaton with a stack, and PDAs
  accept exactly the context-free languages; a recursive-descent parser is
  one, with the call stack as its stack.
- Deterministic PDAs accept fewer languages; those **deterministic
  context-free languages** are exactly the ones with LR(1) grammars.
- `aⁿbⁿcⁿ` is not context-free, context-free languages are not closed
  under intersection, and equivalence and ambiguity of grammars cannot be
  decided.
- C, JavaScript and Python each feed context to their scanners (a symbol
  table, a goal symbol, a stack of indentation levels) so that the parser
  can stay context-free.
