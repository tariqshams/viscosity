## Waste you can see from close up

Compile this one-line function with clang for RISC-V and no optimisation
(`-O0`):

```text
long sq(long x) {
  long y = x * x;
  return y;
}
```

and the middle of what comes out is this (real output, prologue and
epilogue left out):

```text
sd   a0, -24(s0)    # store x in its slot
ld   a0, -24(s0)    # load x back
mul  a0, a0, a0
sd   a0, -32(s0)    # store y in its slot
ld   a0, -32(s0)    # load y back
```

The first two lines store `a0` in memory and immediately load it back
into `a0`, which already holds that very value; the same happens on the
last two lines. You do not need to know anything about the rest of the
program to see that each `ld` is wasted: two neighbouring lines are
enough. That observation is the whole of **peephole optimisation**, named
by McKeeman in 1965 as a final step of compilation that discards
redundant instructions by looking at a few at a
time<Cite id="mckeeman1965" />.

<Analogy title="proofreading through a slot">
Cut a slot in a card, two words wide, and slide it along a page of text.
You will not follow the story, but you will spot "the the", a doubled
space, a full stop before a comma, and fix each one on the spot.
<span slot="breaks">A proofreader knows what the words mean; a peephole
optimiser only knows its list of patterns, and some fixes that look
safe through the slot are wrong because of something outside it, so
every rule must check its conditions.</span>
</Analogy>

<Analogy title="a note to yourself">
Writing a phone number on a sticky note and then at once reading it back
off the note is wasted effort: you still remember it. Skip the reading.
<span slot="breaks">You cannot throw the note away, though, because
someone else may read it later. In the same way the peephole drops the
load but keeps the store, since only code far outside the window could
say whether anyone reads that slot again.</span>
</Analogy>

## Windows and rules

A peephole optimiser slides a small **window** (two or three
instructions) over the code. At each position it checks a list of
**rules**, each a pattern with a replacement and a side condition; when a
rule matches, it rewrites the window and checks the same position again,
because the rewrite may have lined up a new match. It keeps going until a
whole pass changes nothing. Step through one such pass:

Notice that rule 1 only fires when the register and the address are both
the same. A load of the same slot into a *different* register is not a
no-op; at best it becomes a copy, `mv a1, a0`, and that is a different
rule. Notice too what the window could not do: the store is still there.

<Callout kind="definition">
A **peephole optimiser** slides a small **window** of neighbouring
instructions over generated code, and wherever the window matches a
**rule** (a pattern, a replacement and the conditions under which the
replacement means the same thing), it rewrites it; it repeats until no
rule matches<Cite id="mckeeman1965" />.
</Callout>

<Examples of="peephole">

```text
addi a0, a0, 0      →  (deleted)
j    next           →  (deleted)
next:                  next:
```

```text
beq  a0, a1, skip   →  bne a0, a1, far
j    far               skip:
skip:
```

```text
x * 8   →  slli a0, a0, 3
x * 9   →  slli a1, a0, 3
           add  a0, a1, a0
```

</Examples>

The first two are no-ops: adding 0 changes nothing (the RISC-V
manual defines `mv rd, rs` as exactly `addi rd, rs, 0`, so a move of a
register to itself is the same no-op<Cite id="riscv-isa-unpriv" />), and
a jump to the very next line goes where the program was going anyway.
The second is a branch over a jump: "if equal, skip the jump to `far`"
is the same as "if not equal, go to `far`", one instruction instead of
two (with a side condition: a branch reaches only about 4 KiB either
way, against 1 MiB for a jump, so `far` must be close
enough<Cite id="riscv-psabi" />). The third is real clang output at `-O2`: RISC-V has no
multiply-by-a-constant instruction, and a shift left by 3 multiplies by
8 more cheaply than `mul`; for 9, clang shifts and then adds the original
back (8x + x), a little strength reduction done on machine instructions.

In a real compiler these rules live next to the description of the
machine. GCC, for example, lets each target define its own peephole
patterns, and runs its `peephole2` pass after register allocation but
before scheduling<Cite id="gcc-md-peephole" />, because allocation
creates new patterns (a copy between two registers that ended up the
same) and scheduling should see the cleaned-up code.

## Searching for the shortest program

Every rule above was written by a person who noticed a pattern. A
**superoptimiser** turns that round: given a short sequence of
instructions, it searches for the shortest sequence that computes the
same thing. Massalin's superoptimiser enumerated programs of increasing
length and took the first one that agreed with the target, using a fast
probabilistic test to throw out wrong candidates before any careful
check<Cite id="massalin1987" />; to keep the search small, it limited
itself to between 10 and 15 opcodes, and reached programs of about 12
instructions<Cite id="stoke2013" />.

Here is the flavour of what such a search finds. The sign function,
`sgn(x)`, is -1 for a negative number, 0 for zero and 1 for a positive
one. The obvious code uses two branches; clang `-O2` instead emits three
instructions with no branch at all:

```text
srai a1, a0, 63    # -1 if x < 0, else 0
snez a0, a0        # 1 if x != 0, else 0
or   a0, a1, a0    # combine
```

`srai` shifts right by 63 and copies the sign bit into every bit, giving
all ones (-1) for a negative number and 0 otherwise; `snez` sets 1 if
`x` is not zero; and `or` combines them: -1 | 1 is -1, 0 | 0 is 0, and
0 | 1 is 1. Short, correct and far from obvious, which is the kind of
sequence a search turns up and a person might not:

<Analogy title="making change with fewest coins">
To pay 30p in the fewest coins, try every single coin, then every pair,
then every three; the first combination that adds up to 30p is the
answer, and nothing shorter can exist because you already tried it all.
<span slot="breaks">Checking a pile of coins is one addition. Checking
that two programs agree means agreeing on every possible input, which is
why a superoptimiser tests a few inputs first and only proves the rare
survivor.</span>
</Analogy>

<Analogy title="a combination lock">
With a three-digit bike lock you can always open it by trying 000, 001,
002 and onwards; it is slow, but it is certain.
<span slot="breaks">A lock tells you at once when it opens. A candidate
program can pass every test and still be wrong on some input nobody
tried, so a test pass is only a hint, never the answer.</span>
</Analogy>

<Callout kind="definition">
**Superoptimisation** searches a space of instruction sequences for the
shortest (or cheapest) one that is equivalent to a given sequence:
candidates are filtered by running them on test inputs, and a survivor is
accepted only once it has been checked or proved equal on all
inputs<Cite id="massalin1987" />.
</Callout>

<Formal title="What the search looks for">

```text
given target T, find P with
  ∀ x. P(x) = T(x)
  and cost(P) as small as possible
filter:  P(x) = T(x) for x in tests
```

<span slot="read">Given a target sequence T, find a program P such that
for every input x, P of x equals T of x, and whose cost (its length, or
its running time) is as small as possible. In practice, first keep only
the candidates that agree with T on a handful of test inputs, then prove
"for all x" for the few that pass.</span>
</Formal>

<Examples of="superoptimization">

```text
-(x + 1)   →  not a0, a0
(~x is -x - 1, the same thing)
```

```text
sgn(x)  →  srai a1, a0, 63
           snez a0, a0
           or   a0, a1, a0
```

</Examples>

The first is the smallest case: "add one, then negate" is two
instructions, but in two's complement `not` alone computes the same
value, and a search over one-instruction programs finds it. The second
is the sign function from above. The runnable one checks that three-line
sequence in JavaScript on 64-bit integers (`BigInt`), including the
largest and smallest values, where a careless trick would go wrong.

Modern superoptimisers scale this up in two directions. **STOKE** replaces
the orderly enumeration with a random search: it makes millions of small
random changes to a program, guided by a cost that rewards being correct
on tests and being fast, and can then verify the
result<Cite id="stoke2013" />. **Souper** works on LLVM's IR rather than
machine code, and uses an SMT solver (a program that proves or refutes
logical statements) to find missing peephole optimisations; several of
the patterns it found were then written by hand into LLVM and Microsoft's
compiler<Cite id="souper2017" />. In other words, the search is often
used to *discover* peephole rules, which people then check and add to
the ordinary, fast optimiser.

## What you learned

- A **peephole optimiser** slides a small **window** over finished code
  and rewrites patterns by **rules**, repeating until nothing matches.
- A rule must check its conditions, and a window cannot see far: it can
  drop a reloaded value, but not decide that a store is dead.
- A **superoptimiser** searches for the shortest equivalent sequence,
  filtering candidates with tests and proving the survivors.
- STOKE searches at random over x86-64 code; Souper searches LLVM IR with
  a solver, and its finds become ordinary peephole rules.
