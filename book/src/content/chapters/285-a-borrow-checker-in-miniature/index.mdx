## A bug with no error message

You met ownership and moves in *Ownership: moves, copies and clones*,
the borrowing rules and the errors that enforce them in *Borrowing and
the borrowing rules*, and lifetimes in *Lifetimes*; this chapter goes
further, to the algorithm a compiler uses to check those rules, by
building a small one. Here is a short C++ program that keeps a pointer (a reference, in C++'s
words) to the first element of a growable array, adds an element, and
reads through the pointer:

```cpp
std::vector<int> v = {1, 2};
int& first = v[0];
v.push_back(3);
std::printf("%d\n", first);
```

It compiles without a word of complaint; however, when the array has no
room for a third element, `push_back` moves the elements to a bigger
block of memory and frees the old one, so `first` now points into freed
memory. Built with AddressSanitizer (a checking mode of the compiler)
and run here, it stops with:

```text
ERROR: AddressSanitizer:
  heap-use-after-free
READ of size 4 ... in main inv.cpp:7
freed by thread T0 here: ...
  std::__new_allocator<int>::deallocate
```

Without that mode, the program prints whatever happens to be in the
freed block. JavaScript cannot have this bug, because a garbage
collector (as in *Reclaiming memory: mark and sweep*) keeps the old
block alive while anything can reach it; Rust has no garbage collector,
so it rules the bug out before the program runs, refusing the Rust
version with E0502. The part of the compiler that does it is the
**borrow checker**.

## A language small enough to check

The rules to enforce are the ones you already know<Cite id="rust-book-ownership" />:
a move makes the old name unusable, and at any moment a value may have
any number of shared (`&`) borrows or exactly one mutable (`&mut`)
borrow, never both<Cite id="rust-book-borrowing" />. The question here
is how a program can check them.

<Analogy title="a whiteboard in a meeting room">
Any number of people may read the whiteboard at once. Someone who wants
to write on it asks everyone else to look away first, because a reader
halfway through a sentence that is being rubbed out reads nonsense; and
nobody may carry the board out of the room, or wipe it clean, while
anyone is still reading or writing.
<span slot="breaks">In the room you can see who is looking; a borrow
checker must work it out from the program text alone, before anything
runs, for every way the program could go.</span>
</Analogy>

To build a checker we need a language small enough to see whole, so
here is **Lend**, with one statement per line:

```text
let v = new      # v owns a fresh value
let r = &v       # r borrows v, to read
let m = &mut v   # m borrows v, to change
let w = v        # move: w is the owner now
use r            # read r (or read v)
v = new          # give v a fresh value
```

A `let w = r` copies `r` when it is a shared reference (any number of
readers is fine) and moves it when it is `&mut` (two copies would be two
writers).

## The checker's ledger

The checker reads the program once, top to bottom, without running it,
and keeps a **ledger** of two things: the set of names whose value has
been moved away, and the list of **loans** that are out (which name is
borrowed, and whether shared or mutable). Every line touches a name in
one of four ways: it **reads** it (`use v`, or a new `&v`), it borrows
it **mutably** (`&mut v`), it **moves** it, or it **assigns** to it.
Before letting the line through, the checker looks the name up in the
ledger, and the whole rule fits in a table:

<Callout kind="definition">
A **borrow checking algorithm** walks a program before it runs, keeping
a ledger of moved names and of the **loans** in force (each a place,
such as `v`, and a kind, shared or mutable). Each statement is turned
into **accesses** of places (read, mutable borrow, move or assign); an
access to a moved name is an error, and an access that meets a loan of
the same place is an error unless both are reads. A legal borrow adds a
loan; a move adds the name to the moved set; an assignment takes it
out.
</Callout>

<Formal title="When an access is legal">

```text
legal(P, p, a) ⇔ p ∉ moved(P)  (a ≠ asgn)
  ∧ ∀ℓ ∈ loans(P). ℓ.place = p ⇒
        a = read ∧ ℓ.kind = shr
```

<span slot="read">An access a to the place p at point P is legal when
(unless a is an assignment) p has not been moved by then, and for every
loan ℓ in force at P, if ℓ borrows the same place p, then the access is
a read and the loan is shared.</span>
</Formal>

<Examples of="borrow-checking-algorithm">

```text
let v = new
let a = &v
let b = &v    # ok: readers share
use a
```

```text
let v = new
let a = &mut v
let b = &mut v  # E0499
```

```text
let x = new
let r = &x
x = new         # E0506
```

```text
let s = new
let r = &s
let t = s       # E0505
```

</Examples>

In the first, `a` and `b` are both shared loans of `v`, and a read
beside a shared loan is the one legal overlap. In the second the
second `&mut v` meets a mutable loan: rustc says "cannot borrow `v` as
mutable more than once at a time"<Cite id="rust-error-codes" />. In the
third, assigning to `x` would change the value under `r`'s feet:
"cannot assign to `x` because it is borrowed". In the fourth, moving
`s` would leave `r` borrowing nothing: "cannot move out of `s` because
it is borrowed". Each comment is the code rustc 1.97 gives the same
program written in Rust, run here. (The table folds two of rustc's
codes into one: a new `&v` beside a mutable loan is E0502, while a
plain use of `v` there is E0503, "cannot use `v` because it was mutably
borrowed".) The whole checker is about sixty
lines; run it, then edit the three programs at the bottom (add a line,
swap two) and watch the verdicts change:

## How rustc does it

rustc does not check your source text; the borrow checker runs on
**MIR** (the mid-level IR), a control-flow graph (as in *IR, three-address code and control-flow
graphs*) of small
statements, because MIR is far simpler than the syntax tree and its
graph is what lifetimes are built from<Cite id="rustc-dev-guide-borrowck" />.
For `let r = &x; let y = *r; x = 6;`, `rustc --emit=mir` prints
(trimmed):

```text
bb0: {
    _2 = &_1;
    _3 = copy (*_2);
    _1 = const 6_i32;
```

`_1` is `x` and `_2` is `r`, so the first line is a borrow, which makes
a loan of `_1`. The NLL RFC describes the same ledger we built, more
precisely<Cite id="rfc2094-nll" />: a loan is a region, a kind (shared
or mutable) and a path such as `x` or `(*x).foo`; the loans in force at
each point are found by a forward dataflow analysis (as in *Dataflow, fixpoints and
constant propagation*); and
each statement becomes **accesses** that are *deep* or *shallow* and
*reads* or *writes*, where `&x` is a deep read, `&mut x` and a move are
deep writes, and `x = ...` is a shallow write. An access is an error
unless it and the loan are both reads, which is our table. Paths are
what make the real thing bigger: borrowing `p.a` does not stop you
writing `p.b`.

## The catch: our loans never end

Try `let v = new`, `let r = &v`, `use r`, `let m = &mut v` in the
checker above: it reports E0502 on the last line, because once a loan
is in the ledger nothing takes it out. The same program in Rust
compiles, since `r` is never used after line 3. A loan should end when
its reference is finished with, and working out exactly when that is
takes *Non-lexical lifetimes and region inference*.

## What you learned

- The **borrow checking algorithm** keeps a ledger of moved names and
  **loans**, turns each statement into accesses, and reports a conflict
  unless both sides are reads.
- rustc does this on **MIR**, with deep and shallow reads and writes,
  and the error codes E0382, E0499, E0502, E0505 and E0506.
