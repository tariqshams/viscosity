## Two variables, one name

At the end of the last chapter, every Drip variable lived in one table:
the globals. `let` wrote a name into it, and using the name read it back.
That works until someone writes a block:

```js
let a = "global";
{
  let a = "block";
  print a;
}
print a;
```

Drip, like JavaScript, has block scope (chapter 11), so this should print
`block` and then `global`. The inner `a` is a *different variable* that
happens to share a name, and it should vanish at the closing `}`. With
one table, the second `let` simply overwrites the first, and the program
prints `block` twice. The outer `a` is lost for good.

One table per program is not enough. You need one table per *block*,
and a way for the tables to find each other.

## Environments

<Callout kind="intuition">
Think of a stack of notepads, one per block you are inside. Each new pad
is tied by a string to the pad that was open when it was made. To write
a new name, you always use the pad in front of you. To find a name, you
check that pad, and if it isn't there, you follow the string to the next
pad, and the next.
</Callout>

That picture is a small class. Here is the heart of `Environment` from
the companion's `runtime.ts`, slightly simplified:

```ts
class Environment {
  values = new Map<string, Value>();
  enclosing: Environment | null;
  constructor(
    enclosing: Environment | null = null,
  ) {
    this.enclosing = enclosing;
  }
  define(name: string, v: Value) {
    this.values.set(name, v);
  }
}
```

The `Map` (chapter 15) holds this block's names and their runtime values.
`enclosing` is a reference to the parent environment, or `null` for the
globals, which have no parent. `define` only ever touches *this* table:
it is what `let` calls. If the name is already here, it is replaced,
which is fine at the top level, where Drip lets you redefine a global.
(Declaring the same name twice in one *block* is rejected before the
program runs, by a pass you'll write in chapter 87.)

<Callout kind="definition">
An **environment** is a table from names to values, plus a reference to
an **enclosing** (parent) environment. The interpreter always has one
**current** environment. `let` **defines** a name in the current
environment and never looks anywhere else.
</Callout>

## Looking a name up

Reading a variable is where the parent arrow earns its keep:

```ts
get(name: string): Value {
  if (this.values.has(name)) {
    return this.values.get(name)!;
  }
  if (this.enclosing) {
    return this.enclosing.get(name);
  }
  throw new RuntimeError(
    `Undefined variable '${name}'.`);
}
```

Check here. If that fails, ask the parent, which checks *its* table and
asks *its* parent: a recursive walk (chapter 17) along a chain of
references. Only when the walk falls off the end, past the globals, is
the name truly undefined, and that is a runtime error. (The real `get`
takes the name's token rather than a string, so the error can say which
line it came from.)

<Callout kind="definition">
The **scope chain** is the line of environments from the current one,
through each parent, to the globals. Looking a name up walks the chain
and stops at the **first** environment that has it. If none does, the
lookup fails with a runtime error. When an inner environment defines a
name that an outer one also has, the inner variable **shadows** the
outer one: inside that block, the outer variable can't be reached by
name at all.
</Callout>

Because each block's environment is made while the interpreter is inside
the enclosing block, the chain always mirrors how the blocks are nested
in the source text. It is chapter 11's rooms with one-way glass, built
out of `Map`s and arrows. MDN describes JavaScript's own scopes the same
way, as a chain of outer scopes that inner code can see<Cite id="mdn-closures" />.

## Assigning: walk, then write

`n = 2` must change an *existing* variable, wherever it lives. So
`assign` walks the chain just like `get`, and writes into the first
table that already has the name:

```ts
assign(name: string, v: Value) {
  if (this.values.has(name)) {
    this.values.set(name, v);
    return;
  }
  if (this.enclosing) {
    this.enclosing.assign(name, v);
    return;
  }
  throw new RuntimeError(
    `Undefined variable '${name}'.`);
}
```

Notice that `assign` never creates a variable. Assigning to a name that
nobody declared is an error, not a quiet new global.

<Callout kind="pitfall">
`let` and `=` look alike but do opposite things to the chain. Inside a
block, `n = 2;` walks outward and changes the outer `n`. `let n = 2;`
makes a new `n` right here, which shadows the outer one and disappears
at the `}`. The outer `n` is untouched.
</Callout>

```js
let n = 1;
{ n = 2; }
print n; // 2
{ let n = 3; }
print n; // still 2
```

## Entering and leaving a block

The interpreter keeps the current environment in a field, `this.env`.
A block statement makes a fresh environment whose parent is the current
one, and runs its statements inside it:

```ts
case 'block':
  this.executeBlock(s.statements,
    new Environment(this.env));
  return;
```

```ts
executeBlock(stmts: Stmt[],
             env: Environment) {
  const previous = this.env;
  try {
    this.env = env;
    for (const s of stmts) {
      this.execute(s);
    }
  } finally {
    this.env = previous;
  }
}
```

Leaving the block is just switching back to `previous`. The block's own
environment isn't destroyed by hand: once nothing refers to it, it is
garbage like any other unreachable object.

Why `finally`? Because a block doesn't always end at its `}`. A runtime
error halfway through throws straight out of `execute`. Without the
`finally`, `this.env` would be left pointing at the dead inner
environment. In chapter 85 you'll see a second, more everyday reason:
`return`.

<Callout kind="engine" label="Under the hood">
Every variable read here is a `Map` lookup, repeated once per
environment on the way up the chain. A variable used inside five
nested blocks but declared at the top costs six lookups, every time
the line runs. Chapter 87 fixes the worst of this: a resolver works
out *before* running how many hops up each variable lives, and the
interpreter jumps straight there with `getAt(distance, name)`. That
is why the companion's `interpreter.ts` reads variables through a
`lookUp` helper instead of calling `get` directly. The bytecode VM of
chapter 110 goes further and keeps local variables in numbered stack
slots, with no names left at run time at all. This design of an
environment as a table with a parent link follows *Crafting
Interpreters*, which Drip is based on<Cite id="nystrom2021" />.
</Callout>

## What you learned

- An **environment** is a table from names to values with a reference
  to its **enclosing** environment. The globals have no parent.
- `let` **defines** in the current environment only.
- `get` and `assign` walk the **scope chain** outward and stop at the
  first match. Falling off the end is a runtime error.
- An inner variable **shadows** an outer one with the same name, until
  its block ends.
- Each block runs in a fresh environment, and `executeBlock` restores
  the previous one in `finally`, even if something is thrown.
