## Many ways to fail

The `drip-rs` binary fails in four ways, and says which with its exit
code: 64 if you call it wrongly, 66 if it cannot read the file, 65 for
a compile error and 70 for a runtime error, the same codes as the
TypeScript `drip` command. A test runner or a shell script can tell
those apart without reading a word of the message.

Inside a program the same question comes up at every layer. A function
returning `Result<f64, String>` works until a caller needs to *do*
something different for different failures (retry when a file is busy,
underline a compile error in an editor, exit with 65 rather than 70);
then a `String` is a dead end, because the only way to find out what
happened is to read the text.

<Analogy title="a note or a form">
A `String` error is a handwritten note saying what went wrong; an error
enum is a printed form with tick boxes, and room under each box for the
details. Anyone can read the note, but only the forms can be sorted
into piles without reading them.
<span slot="breaks">A clerk can still sort notes by reading them
carefully; a program that sorts by searching message text breaks the
day someone rewords a message, and nothing warns it.</span>
</Analogy>

## One enum for the crate

Give each kind of failure a variant, holding whatever detail that kind
has. Here is one for a command-line tool that reads a number from a
file:

<Examples of="error-enum">

```rust
#[derive(Debug)]
enum CliError {
    Usage,
    Io(io::Error),
    Num(ParseIntError),
}
fn exit_code(e: &CliError) -> u8 {
    match e {
        CliError::Usage => 64,
        CliError::Io(_) => 66,
        CliError::Num(_) => 65,
    }
}
```

</Examples>

`Usage` carries nothing, because the kind is the whole story; `Io`
holds the standard library's `std::io::Error` (with its own message,
such as "No such file or directory"), and `Num` holds the
`ParseIntError` from a failed `parse`. A caller now gets one error
type, and `exit_code` turns each kind into a number with one `match`,
searching no text. This is a TypeScript discriminated union with the
details inside each variant, and with the compiler checking every
`match`, which is the strongest reason to prefer it:

<ExitSteps client:visible />

Add a `Timeout` variant, and every `match` that does not handle it
stops compiling; for `exit_code`, rustc 1.97 says E0004,
"non-exhaustive patterns: `&CliError::Timeout` not covered". With
`String` errors, the code that should treat the new failure differently
would compile and quietly do the wrong thing. (A `_ =>` arm switches
the check off for that `match`, so use one only when "everything else"
really means every future variant too.)

<Callout kind="definition">
An **error enum** is a single enum that lists every way a crate's (or a
module's) operations can fail, one variant per kind, each holding that
kind's details. Its functions return `Result<T, ThatEnum>`, so callers
handle one error type and can match on its variants; it usually also
implements `Display`, for a message, and the standard
`std::error::Error` trait<Cite id="klabnik2026" />.
</Callout>

## Teaching ? to convert

Here is the tool's reading function, written with `?` alone:

```rust
fn min_size(path: &Path)
    -> Result<u32, CliError> {
    let s = fs::read_to_string(path)?;
    let n = s.trim().parse::<u32>()?;
    Ok(n)
}
```

`read_to_string` fails with an `io::Error`, not a `CliError`, and
`parse` with a `ParseIntError`. This is the detail *Option, Result and
the ? operator* mentioned in passing: on an `Err`, `?` first passes the
error through `From::from`, converting it into the function's own
error type, and *then* returns it<Cite id="rustref-try-propagation" />.
So you tell Rust once how each conversion goes, and every `?` in the
crate uses it:

<Examples of="from-trait">

```rust
impl From<io::Error> for CliError {
    fn from(e: io::Error) -> Self {
        CliError::Io(e)
    }
}
```

</Examples>

The whole impl is one function, `from`, that takes an `io::Error` by
value and wraps it in the `Io` variant, keeping the original inside;
the same five lines with `ParseIntError` and `Num` cover the second
`?`. Step through one conversion:

<FromSteps client:visible />

Leave out the `ParseIntError` impl and the second `?` stops compiling,
with a message that names the missing piece:

```text
error[E0277]: `?` couldn't convert the
  error to `CliError`
  the trait `From<ParseIntError>` is not
  implemented for `CliError`
```

The fix is the impl, or, for a one-off, a `map_err` before the `?`
(`map_err` converts the error inside a `Result` with a closure, and
leaves an `Ok` alone). In TypeScript you would wrap a low-level error
at each `catch`, by hand (`throw new CliError('io', { cause: e })`);
Rust writes the rule once, as a trait impl, and refuses to compile
where no rule exists.

<Callout kind="definition">
**`From<T>`** is the standard trait for converting a `T` into `Self`,
through one function, `fn from(value: T) -> Self`. The **`?`
operator** calls `From::from` on every error it returns early, so one
`impl From<SourceError> for MyError` per source error lets `?` work on
all of them. Implementing `From` also gives you the matching `Into` for
free, so `io_err.into()` works wherever a `CliError` is
expected<Cite id="rust-std-from" />.
</Callout>

You have used the trait since *Ownership: moves, copies and clones*:
`String::from("fib")` is the standard library's `impl From<&str> for
String`, and `?` uses impls like it as well:

## Two real designs

Neither of this book's Rust projects has an error enum for its whole
library, and why is instructive. drip-rs's compiler collects its
messages into a `Vec<String>` as it recovers and carries on, and its VM
error is `pub struct RuntimeError;`, a struct with no fields, because
(in its doc comment's words) "Its message and stack trace are already
on stderr by the time one of these exists"; it only has to stop the run
loop through `?`, and `main` then turns the outcome into exit code 65 or
70<Cite id="rust-std-exitcode" />. engine/rust's compile error is a
newtype, `pub struct CompileError(pub String);`, because every caller
prints the message and gives up; its command line has a two-variant
enum, `Usage` and `Other`, because `main` prints the help text after a
`Usage` error only, and `impl From<String> for CliError` lifts its
helpers' `String` errors into it with a bare `?`. An error enum earns
its keep when callers want different things: a test that expects a
runtime error and must not accept a compile error, or an editor that
underlines compile errors at their line.

## What you learned

- An **error enum** gives a crate one error type with a variant per
  kind of failure, so callers match instead of parsing messages; adding
  a variant makes every `match` that misses it fail to compile (E0004).
- **`From<T>`** converts a `T` into `Self` with one function, `from`,
  and gives you `Into` for free. **`?`** passes every early-returned
  error through `From::from`, so one impl per source error is all the
  plumbing an error enum needs; a missing impl is E0277.
- drip-rs keeps only the kind (exit codes 64, 65, 66 and 70);
  engine/rust's `CompileError` is one `String`. Choose by what callers
  need to tell apart.
