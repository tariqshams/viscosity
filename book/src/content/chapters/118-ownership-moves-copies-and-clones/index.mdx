## Who frees the memory?

Something has to give heap memory back. In C you call `free`, and
calling it too early or twice causes bugs that are hard to trace; in
TypeScript the engine's collector traces everything reachable from the
roots, as yours did in *Reclaiming memory: mark and sweep*. Rust has a
third answer, and the rest of this part is built on it:

```rust
fn main() {
    let s = String::from("fib");
    println!("{s}");
} // s is freed here
```

`String::from` asks the heap for room and copies `fib` into it
(`String` is Rust's growable text, from *Slices, String and &str*).
Nobody calls `free` and no collector runs; the memory is given back at
the closing brace, at a point the compiler worked out in advance.

<Analogy title="the deed to a house">
A house has exactly one deed, and whoever holds the deed is responsible
for the house. When the holder leaves town for good, the house is
cleared and the land handed back. Nobody has to go round checking which
houses are empty, because every house has someone whose leaving says
when.
<span slot="breaks">A real deed can be shared by joint owners; a Rust
value has one owner, full stop, and sharing needs tools from later
chapters (`Rc` in *Box, Rc and RefCell*).</span>
</Analogy>

## One owner, and drop

The rules are three<Cite id="rust-book-ownership" />: each value has an
**owner**; there is only one owner at a time; and when the owner goes
out of scope, the value is **dropped**. A `String` comes in two parts:
its variable's stack slot holds a pointer, a length and a capacity (24
bytes on a 64-bit machine), and the text lives on the heap; owning the
slot means owning the text. Ownership nests, so the arrows form a tree:

</Figure>

"Goes out of scope" means reaching the closing brace of the block that
declared the owner. Step through two scopes and a reassignment:

Variables in one scope are dropped in **reverse** order of declaration;
assigning to a `mut` variable drops its old value first; and `drop(x)`
drops early, because it is an ordinary function that takes the value and
does nothing with it<Cite id="rust-reference-destructors" />.

`drop b`, `main ends`, `drop d2`, `drop a`.

<Callout kind="definition">
**Ownership**: every value has exactly one owning variable (or is owned
by a value that is, as the strings in a `Vec` are). **Drop**: when the
owner goes out of scope, the value is destroyed and its heap memory
freed, along with everything it owns; variables in a scope are dropped
in reverse order of declaration<Cite id="rust-reference-destructors" />.
</Callout>

## Two names, one string?

In TypeScript, `const b = a` makes two arrows to one object. Rust's rule
says the text has one owner, so which of `a` and `b` would free it?
rustc answers by rejecting any later use of `a` (real output, trimmed):

```rust
let a = String::from("fib");
let b = a;
println!("{a}");
```

```text
error[E0382]: borrow of moved value: `a`
2 | let a = String::from("fib");
  |     - move occurs because `a` has
  |       type `String`, which does not
  |       implement the `Copy` trait
3 | let b = a;
  |         - value moved here
4 | println!("{a}");
  |            ^ value borrowed here
  |              after move
```

`a` was **moved** into `b` ("borrowed" is the subject of *Borrowing and
the borrowing rules*; printing a value borrows it). Step through it: an
arrow is drawn only from a value's one owner.

<OwnerSteps client:visible />

A move copies only the 24 bytes on the stack; the heap text stays put,
and since the moved-from variable owns nothing, it is not dropped, so the
text is freed exactly once<Cite id="rust-book-ownership" />. The scalars
behave differently: `let m = n;` with an `i32` leaves both usable,
because the integers, floats, `bool` and `char` are **Copy** types, and
duplicating a few bytes is cheap. When you do want a second, independent
`String`, you ask for one with `clone()`, which copies the text (unlike
`{ ...obj }`, it is a deep copy):

<Figure takeaway="A move hands over the heap data; a Copy type is duplicated; clone makes a second heap copy with its own owner." caption="The three outcomes. Only clone does work proportional to the size of the text.">
  <MoveCopyClone />
</Figure>

Passing a value to a function moves it exactly as `let` does, and
returning one moves it out to the caller:

<Examples of="move">

```rust
fn eat(s: String) {
    println!("ate {s}");
} // s is dropped here

let name = String::from("drip");
eat(name.clone()); // a copy moves in
eat(name);         // name moves in
// eat(name);      // E0382: moved
```

</Examples>

`eat` takes a `String`, so each call moves its argument into `s`, and
`eat` drops it at its closing brace. The first call hands over a clone,
so `name` still owns its text; the second hands over `name` itself, so
a third call would be "use of moved value: `name`". rustc's note on that
error is the real fix: a function that only wants to *look* at a string
should borrow it, which is the next chapter. (A function that builds a
`String` and returns it moves it to the caller, so it outlives the
call.)

<Callout kind="definition">
A **move** transfers ownership: `let b = a;`, passing `a` to a function,
or returning a value. The stack bytes are copied, the heap data is not,
and the old place may not be used again until it is given a new value;
a use after a move is error E0382<Cite id="rust-error-codes" />. **Copy**
types are duplicated instead, and `clone()` makes an explicit deep copy.
</Callout>

<More title="More: moves in a runnable program, loops, and other languages">

<Run id="moves" />

Uncomment the last line to see E0382 for yourself. Inside a loop the
same error says "value moved here, in previous iteration of loop": the
first time round moves the value, and the second finds nothing left.

```c
char *a = strdup("fib");
char *b = a; /* two pointers; free one
                and the other dangles */
```

C copies the same bytes a Rust move does, but keeps both names, so
freeing through one leaves the other pointing at freed memory; Rust
forbids the old name, so there is never a second path to the text.
Compared with a tracing collector (work at run time, but any object may
point at any other) and with reference counting (prompt, but every
pointer copy pays), ownership is what you get when the count is always
exactly one: the owner's closing brace *is* the moment the count would
reach zero, and the compiler knows where it is. A non-Copy value may be
moved at most once, which type theory calls an *affine* discipline; the
deep dive *Linear types and effect systems* goes further.

The Rust Drip VM still has a garbage collector
(`companion/rust/src/gc.rs`), because Drip programs share objects
freely; its objects live in arenas, and Drip values refer to them by
small typed handles. Ownership handles everything else: the stack, the
frames, the chunks and the heap's own storage, all freed when the `Vm`
is dropped.

</More>

<Analogy extra title="handing over the car keys">
When you sell your car you hand the buyer the keys, and from then on
they drive it and you do not; the car itself stays exactly where it is
parked. A move is that hand-over: the small thing (the pointer, length
and capacity, like the keys) changes hands, and the big thing on the
heap does not move an inch.
<span slot="breaks">You could cut a spare key and drive off anyway;
Rust leaves no spare, and the compiler rejects any later use of the old
name.</span>
</Analogy>

## What you learned

- Each value has one **owner**, and is **dropped** at the owner's
  closing brace, in reverse order of declaration.
- `let`, calls and returns **move** non-Copy values; Copy types are
  duplicated, and `clone()` copies on request.
