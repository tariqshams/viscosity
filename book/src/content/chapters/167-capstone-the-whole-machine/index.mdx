## Where you are

The book has asked one question all along: can a compiler quietly
rearrange an array of objects into columns, prove that nothing changes,
and make the loop faster? You now have the answer as a tool you
understand all the way down, built twice, in two languages, and shipped.

<Analogy title="an apprentice's second chair">
An apprentice builds a chair with the master watching, then builds the
same chair again, alone, in a harder wood. The second chair is no more
useful than the first; it is the proof that the apprentice knows why
every joint sits where it does.
<span slot="breaks">A chair is finished when it stands. Viscosity is
never quite finished: the second build turned up bugs in the first, and
both keep changing, with tests holding them together.</span>
</Analogy>

<Analogy extra title="an apprentice's masterpiece">
In the old craft guilds an apprentice finished by making one piece that
used every skill they had learned, judged as a whole; that is where the
word "masterpiece" comes from.
<span slot="breaks">A masterpiece was judged finished. This capstone
comes with a list of what is *not* finished, and that list is part of the
work.</span>
</Analogy>

instead<Cite id="makor2022" />, and SSA and dataflow are what those
proofs are made of.

<Prompts ids={['cap-what', 'cap-links']} />

Every implementation is checked against another. drip-rs runs the corpus
the TypeScript VM runs; the Rust engine reproduces every stored output of
the TypeScript engine byte for byte, and the fuzzer keeps generating
programs to compare them on; and every compiled program is run against
its original. That chain is what makes "the same machine, in Rust" a
claim you can test rather than a hope.

<Formal title="The two promises every check tests">

```text
∀ p ∈ Programs:  out(p) = out(compile(p))
∀ p ∈ Corpus, b ∈ {check, assume}:
    TS(p, b) = Rust(p, b)
```

<span slot="read">For every program p, running the compiled program
prints exactly what running the original prints (the upside-down A reads
"for every"). And for every corpus program and both bounds modes, the
TypeScript engine and the Rust engine produce the same code and the same
explain text.</span>
</Formal>

## What mastery looks like

<Callout kind="definition">
**Mastery**, as this book means it, is being able to build the thing
again yourself: to start from an empty folder and get back to a working
version, knowing why each piece is there and how you would check it. It
is not remembering every line; it is knowing which questions to ask, and
which test would answer each one.
</Callout>

<Examples of="mastery">

```
for (let i = 0; i < 10; i++) ps.push(...)
→ about 10 elements: below the
  64-element threshold, where the
  benefit is too small
```

```
console.log(s, qs[0].hp);
→ qs: no loop reads or writes its
  fields, so a new layout cannot pay off
```

</Examples>

The first is a prediction you can make before running anything: change
the first loop of the program above to ten elements, and `ps` falls under
the planner's default threshold of 64, so it is kept, in those words (I
ran the Rust CLI on it to check). The second changes the last line:
`qs[0].hp` reads a number, so no element escapes any more, yet `qs` is
still kept, for a different reason, because no loop touches its fields.
Before you believe any change to the machine, run both engines' test
suites (`cargo test --workspace` passed all 77 of its tests when I ran
it).

## What is still open

An honest capstone lists what is not done; some items are chores, and
some are research.

- **No changelog.** The npm packages are at 0.0.2 and the crates at
  0.0.1, but the commit history is the only record of what changed.
- **The port has gaps.** It refuses TypeScript input, its syntax errors
  are worded by oxc rather than acorn, and neither engine profiles Python.
- **The cost model cannot see the engine.** The same compiled heat gained
  <Num k="heatNode" /> on V8 and <Num k="heatBun" /> on JavaScriptCore;
  the likely cause, V8 keeping a double field in a separate box on the
  heap<Cite id="v8-react-cliff" />, is still a hypothesis.
- **Many ordinary programs are refused**: sorting, classes used as
  records, varying shapes, exported arrays (the deep dive *The research
  frontier* sorts them into chores and research).
- **Every version emits source code.** WebAssembly runs the compiler,
  not its output.

<Prompts ids={['m-chore']} />

<More title="Twenty-two bugs, and where to go from here">
`engine/rust/README.md` numbers twenty-two bugs: ten in the TypeScript
reference found while porting, five found by the fuzzer in both engines,
and seven found while writing this book. Several were soundness bugs,
where a compiled program would have behaved differently from its
original; every one is fixed, and has a test that keeps it fixed.

If you want to keep going, the repository's `CONTRIBUTING.md` says what a
change needs: differential tests for every transform, committed numbers
for every performance claim, and a clean run of the chapter checker.

- **Confirm or refute the heat hypothesis**, with a trace of heat's
  objects on V8 (the deep dive *Watching the engine work*).
- **Teach the cost model about engines**: run the matrix on more
  machines, and see whether a per-engine threshold would have predicted
  Bun's results.
- **Add a language.** The plugin trait is the whole contract, and the
  deep dive *A second language: why plugins pay off* starts the Python
  plugin from it.
- **Grow the subset.** Pick one refusal, prove it safe, and let the
  fuzzer tell you whether you were right.

One of the extra exercises below is Viscosity in miniature, done at run
time the way the research does it<Cite id="kloibhofer2023" />: check the
shape, bail out if anything is off, otherwise build columns.
</More>

## What you learned

- The book is a **Prelude**, a **30-day Core** and the **Deep dives**;
  the Core built Drip three times and Viscosity twice, and shipped it.
- Every implementation is **checked against another**: the shared corpus,
  byte-identical fixtures, the fuzzer, and original-against-compiled runs.
- One program passes through **parse, lower, analyse, plan, emit and
  explain**, and each line of its report traces back to a chapter.
- What is **open** is written down, and **mastery** is being able to
  build it again and to say how you would know it works.

That is the end of the Core, and I want to thank you for reading it. It
began with a question about where an array of objects sits in memory,
and every chapter since has been one step towards answering it with a
tool you understand all the way down; the code is in the repository, the
numbers are in its results files, and the rough edges are listed above.
Fifteen minutes at a time, you built the whole machine; now it is yours,
and the deep dives are there whenever you want to go further.
