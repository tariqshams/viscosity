## Two trees for one line

What is `1 + 2 * 3`? You learned the answer at school: 7, because
multiplication happens first. The tokens alone do not say that, though;
both of these trees fit them:

<Figure takeaway="Multiplication must end up deeper in the tree than addition." caption="Two ways to group the tokens 1 + 2 * 3. In a tree, deeper operations happen first. Drip, like JavaScript and school arithmetic, builds the left one.">
  <TwoTrees which="prec" />
</Figure>

This is the ambiguity from "Ambiguity and the Chomsky hierarchy": the
grammar `expr → expr "+" expr | expr "*" expr | NUMBER` allows both
trees. We need a grammar that allows only the left one.

<Analogy title="packing for a move">
You pack small things into boxes first, and only then load the boxes
into the van; nobody puts a single spoon in the van and then builds a
box round it. Multiplication is the boxes and addition is the van: each
product is packed and sealed before the sum loads it.
<span slot="breaks">Packing is a choice you could make differently;
precedence is a fixed rule of the language, and brackets are the only
way to ask for another order.</span>
</Analogy>

<Analogy title="superglue and tape">
Stick 1 and 2 together with tape and 2 and 3 with superglue, then pull:
the tape gives first, and the glued pair stays one piece. `*` holds its
neighbours more strongly than `+` does, so `2 * 3` stays together.
<span slot="breaks">Glue is about force; precedence is only about
grouping, and says nothing about which operation is harder or slower to
work out.</span>
</Analogy>

<Callout kind="definition">
**Precedence** says which operators bind tighter. In Drip, as in
arithmetic, `*`, `/` and `%` bind tighter than `+` and `-`, which bind
tighter than the comparisons, which bind tighter than `==` and `!=`; an
operator that binds tighter ends up deeper in the tree, so it is worked
out first.
</Callout>

<Examples of="precedence">

```text
1 + 2 * 3   →   (+ 1 (* 2 3))
```

```text
2 * 3 + 4   →   (+ (* 2 3) 4)
(1 + 2) * 3 →   (* (group (+ 1 2)) 3)
```

```text
-x * 2 < 4 == true
→ (== (< (* (- x) 2) 4) true)
```

</Examples>

In the first, the product is the right child of the sum. In the second
the `*` comes first in the source and is still the deeper node, and
brackets override precedence, putting the sum inside. The third is a
realistic condition with four levels: unary minus binds tightest, then
`*`, then `<`, and `==` is the root, worked out last.

## A grammar with levels

To build precedence into the grammar, give each level its own rule,
loosest first, and let each rule build its operands from the next,
tighter one:

<Formal title="Drip’s expression grammar, from equality down">

```text
equality   → comparison
               ( ( "==" | "!=" )
                 comparison )*
comparison → term
               ( ( "<" | "<=" | ">" | ">=" )
                 term )*
term       → factor
               ( ( "+" | "-" ) factor )*
factor     → unary
               ( ( "*" | "/" | "%" )
                 unary )*
unary      → ( "!" | "-" ) unary | call
primary    → NUMBER | STRING | "true"
           | "false" | "none" | IDENT
           | "(" expression ")" | ...
```

<span slot="read">An equality is a comparison, followed by zero or more
pairs of an equality operator and another comparison. A comparison is a
term, followed by zero or more pairs of a comparison operator and a
term. A term is a factor, followed by zero or more pairs of a plus or
minus and a factor. A factor is a unary, followed by zero or more pairs
of a times, divide or remainder sign and a unary. A unary is a not sign
or a minus sign followed by another unary, or else a call. A primary is
a number, a string, true, false, none, a name, a whole expression in
brackets, or one of a few more forms you will meet later.</span>
</Formal>

Above `equality`, Drip's grammar has three looser levels, `assignment`, then `or` (with `||`) and `and`
(with `&&`), and `call` sits between `unary` and `primary`. Our parser
writes the six levels shown, taking `call` as plain `primary`; `||` and
`&&` have exactly the same shape, and assignment comes back at the end.

So `term` can only join *finished* factors: when it meets the `+` in
`1 + 2 * 3`, the `2 * 3` on its right is one factor, built as a unit,
and there is no way to build the other tree. The lower a rule sits in
the list, the tighter its operators bind. The last rule, `primary`, is
the base case: a single literal, or a whole expression in brackets,
which starts again from the loosest level; that is why brackets can
override precedence.

## One function per level

Turned into recursive descent, each level is the same shape: get one
operand from the level below, then loop while the next token is one of
this level's operators. Tokens are plain strings here, and `i` is the
index of the next one:

```js
const at = (...ops) =>
  ops.includes(ts[i]);
const next = () => ts[i++];

function term() {
  let left = factor();
  while (at('+', '-')) {
    const op = next();
    const right = factor();
    left = bin(left, op, right);
  }
  return left;
}
```

`at` peeks: is the next token one of these? `next` takes it. `term`
gets a factor, and then, as long as the next token is `+` or `-`, takes
the operator, gets another factor, and replaces `left` with a binary
node joining the two (`bin` makes that node). `factor` is the same
function one level down, with `*`, `/` and `%` and calls to `unary`. `unary`
checks for `!` or `-`; if it finds one, it takes it and calls *itself*
for the operand (so `- - 1` and `!!x` work), and otherwise hands over to
`primary`, which takes one token and returns a literal (or, for `(`,
calls `expression` and then expects `)`). Watch
the levels call each other on `1 + 2 * 3`:

## Which way does a chain lean?

Precedence does not settle `1 - 2 - 3`: both operators are on the same
level, and the two groupings give different answers.

<Figure takeaway="Same-level operators group to the left." caption="1 - 2 - 3 grouped two ways. Drip, like arithmetic, groups to the left, so the first subtraction is deeper and happens first.">
  <TwoTrees which="assoc" />
</Figure>

<Analogy title="paying from a wallet">
You have 10 coins, pay 2 for a coffee and then 3 for a sandwich: you
have 5 left. Nobody works out "2 minus 3" first; each payment comes out
of whatever is left after the one before.
<span slot="breaks">Money has a natural order in time; a program's
operators only have the order the language's rules give them, which is
why some operators can be defined to lean the other way.</span>
</Analogy>

<Analogy title="wrapping a parcel in layers">
Wrap a present in one sheet of paper, then wrap that whole parcel in a
second sheet, then the result in a third. The first sheet ends up
innermost, and each new sheet goes round everything so far.
<span slot="breaks">A parcel is unwrapped from the outside in; a tree is
worked out from the inside out, so the innermost (first) subtraction is
done first.</span>
</Analogy>

The loop in `term` does exactly that wrapping. After `1 - 2`, `left`
holds the node `(- 1 2)`; the loop goes round again, sees the second
`-`, and builds a new node with that *whole* subtraction on its left.
Each pass wraps the tree so far, so the chain leans left.

<Callout kind="definition">
**Associativity** says how a chain of operators on the same precedence
level groups. Drip's binary operators are **left-associative**:
`a - b - c` means `(a - b) - c`. Assignment is the exception, and is
**right-associative**: `a = b = 1` means `a = (b = 1)`.
</Callout>

<Examples of="associativity">

```text
1 - 2 - 3  →  (- (- 1 2) 3)    is -4
```

```text
8 / 2 / 2  →  (/ (/ 8 2) 2)    is 2
1 < 2 < 3  →  (< (< 1 2) 3)
```

```text
a = b = 1  →  (= a (= b 1))
```

</Examples>

In the first, the left grouping gives `-1 - 3`, which is `-4` (the
other would give `2`). The second shows the same for division (`4 / 2`
is `2`; the other way, `8`) and for comparisons, which lean left too.
The third leans right: assignment stores `1` in `b`, and that value is
then stored in `a`, so the rightmost one must happen first.

<Formal title="Left and right associativity as trees">

```text
a ∘ b ∘ c  =  (a ∘ b) ∘ c    left
a ∘ b ∘ c  =  a ∘ (b ∘ c)    right
```

<span slot="read">Here the small circle stands for any one binary
operator. If the operator is left-associative, a chain a, operator, b,
operator, c means: first combine a and b, then combine that result with
c. If it is right-associative, it means: first combine b and c, then
combine a with that result.</span>
</Formal>

## Why a loop, and not a rule that starts with itself

The grammar in the chapter "Grammars" wrote this level as
`expr → expr "+" item`, which says "left-associative" very clearly. Why
not code that directly?

```js
function term() {
  const left = term(); // ✗
  // ...
}
// RangeError: Maximum call stack
//   size exceeded
```

The first thing `term()` would do is call `term()`, with the same token
still next, for ever, until the call stack runs out. A rule whose body
starts with its own name is **left-recursive**, and cannot be coded
directly in recursive descent; so the grammar uses `*` and the code a
loop, which gives the same left-leaning trees ("LL(1) tables and
rewriting grammars" shows how to rewrite any such rule). Recursing on
the *right* instead, `return bin(left, op, term())`, does stop, but it
makes the chain lean right, which is correct for assignment and wrong
for `-`.

<Prompts ids={['left-recursion']} />

<Callout kind="engine" label="Under the hood">
JavaScript's specification layers its operators the same way. It
defines an `AdditiveExpression` as a `MultiplicativeExpression`, or an
`AdditiveExpression` followed by `+` or `-` and a
`MultiplicativeExpression`<Cite id="ecma262-operators" />. That
self-reference on the left is exactly the left recursion you just met:
in a grammar it means left-associative, and in a hand-written parser it
becomes a loop. The companion parses Drip's expressions with the method
of "Pratt parsing", which builds the same trees from a table.
</Callout>

## What you learned

- **Precedence**: one grammar rule per level, loosest first, each built
  from the next. Tighter operators end up deeper, so they happen first;
  brackets restart at the top.
- Each level becomes a function: one operand from the level below, then
  a loop over this level's operators.
- **Associativity**: the loop wraps the tree so far, so `a - b - c`
  leans left; recursing on the right makes a chain lean right, as
  assignment does.
- A left-recursive rule cannot be coded directly: the function would
  call itself for ever.
