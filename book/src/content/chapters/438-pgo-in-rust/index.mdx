## A size the analysis can't count

*Access patterns in Rust* showed that a push inside a function makes a
collection's size unknown, because the analysis doesn't count calls.
*Profile-guided optimization* answered that in the TypeScript engine by
running the program once and measuring. The Rust binary takes the same
commands. Here is a program whose 20 elements are pushed inside a
function:

```js
const ps = [];
function spawn(x) {
    ps.push({ x, vx: 1 });
}
for (let i = 0; i < 20; i++) spawn(i);
for (let f = 0; f < 100; f++) {
    for (let i = 0; i < ps.length; i++) {
        ps[i].x += ps[i].vx;
    }
}
console.log(ps[0].x);
```

and a real session with it (release build, rustc 1.97, Node 22.23;
long lines wrapped, and the first report trimmed):

```
$ viscosity explain spawn.js
ps (line 1) {x, vx} → struct of arrays
  · size unknown statically
$ viscosity profile spawn.js -o p.json
$ cat p.json
{
  "ps": {
    "maxLength": 20
  }
}
$ viscosity explain spawn.js \
    --profile p.json
ps (line 1) {x, vx} → kept as array of
  objects
  · about 20 elements (measured): below
    the 64-element threshold, where the
    benefit is too small
```

The decision flips, as it should, and every line matches the TypeScript
CLI's. The JSON file is byte-identical to the one the TypeScript CLI
writes too, and the reason is the most interesting thing in
`crates/cli/src/profile.rs`.

<Analogy title="a clicker at the stadium gate">

The Rust engine doesn't run JavaScript itself either. It hands Node a
copy of the program with a clicker in it.
<span slot="breaks">A clicker counts people as they pass; the profile

## Writing a program that counts

`instrument` in `profile.rs` turns the source into a program that
records its own sizes. It starts the way the compiler does,
`JsPlugin.lower(source)` and then `analyze`, so it finds exactly the
collections the planner will later ask about (a syntax error becomes
the `Err` string the CLI prints, through `map_err(...)?`). For each
collection it takes the byte span of its initialiser, such as `[]`,
into a list of `(start, end, name)` edits, and then (rewrapped):

```rust
edits.sort_by_key(|e|
    std::cmp::Reverse(e.0));
let mut out = source.to_string();
for (start, end, name) in edits {
    let (start, end) =
        (start as usize, end as usize);
    let quoted = serde_json::
        to_string(name)
        .expect("strings serialize");
    let wrapped = format!(
        "__vsc_track({quoted}, {})",
        &out[start..end]);
    out.replace_range(start..end,
        &wrapped);
}
Ok(format!("{PRELUDE}{out}"))
```

The edits are sorted by start, **last first** (`Reverse` flips the
order of a sort key), so replacing one span never moves the offsets of
the spans still to come, the same idea as the emitter's edits in *SoA
code generation in Rust*. `replace_range` edits the `String` in place,
and the offsets are UTF-8 bytes from oxc, which is what a `String` is
indexed by. The name is quoted with `serde_json`, so it is always a
valid JavaScript string literal, and the wrapper keeps the original
initialiser as its second argument.

The `PRELUDE` that goes in front is a Rust `&str` holding JavaScript,
the TypeScript CLI's prelude character for character:

```js
const __vsc_seen = [];
function __vsc_track(name, arr) {
  __vsc_seen.push([name, arr]);
  return arr;
}
process.on('exit', () => {
  const p = {};
  for (const [n, a] of __vsc_seen)
    p[n] = { maxLength: Math.max(
      p[n]?.maxLength ?? 0, a.length) };
  require('node:fs').writeFileSync(
    process.env.VSC_PROFILE_OUT,
    JSON.stringify(p, null, 2));
});
```

(reformatted: the real prelude is seven lines). `__vsc_track` remembers
each array under its name and hands it straight back, so the program
runs exactly as before. When the process exits, the hook takes, for
each name, the largest length of any array tracked under it, and writes
the result as JSON with two-space indentation to the file named by the
environment variable `VSC_PROFILE_OUT`. So in both engines the JSON is
written by Node, with the same code; Rust never formats it, which is
why the two files are identical.

## Running node from Rust

`profile(file)` writes the instrumented program to a temporary
directory and runs it (rewrapped):

```rust
let status = Command::new("node")
    .arg(&inst)
    .env("VSC_PROFILE_OUT", &out)
    .stdin(Stdio::null())
    .stdout(Stdio::null())
    .status()
    .map_err(|e| format!("could not run \
        node (profiling needs Node.js on \
        the PATH): {e}"))?;
```

`std::process::Command` builds a child process step by step: the
program, its argument (the file `instrumented.cjs`), one environment
variable, an empty stdin and a discarded stdout (stderr still shows, so
you see the program's errors). `.status()` runs it, waits for it to
finish, and returns its exit status, or an `Err` if `node` couldn't be
started at all, which `map_err` turns into a helpful message. Then
`if !status.success()` turns a non-zero exit into an error too, "the
profiled program failed (exit code 1)", because a partial run's sizes
could mislead the planner; `status.code()` is `None` when the process
was killed by a signal rather than exiting, and that gets a message of
its own. Only then does `profile` read the file the hook wrote, with
`fs::read_to_string`, and return it. The
TypeScript CLI runs `process.execPath`, the very Node running it; the
Rust binary has no Node of its own, so it looks `node` up on the
`PATH`:

```
$ PATH=/nowhere viscosity profile spawn.js
viscosity: could not run node (profiling
needs Node.js on the PATH): No such file
or directory (os error 2)
```

The temporary directory is owned by a small guard value:

```rust
struct TempDir(std::path::PathBuf);

impl Drop for TempDir {
    fn drop(&mut self) {
        let _ = fs::remove_dir_all(&self.0);
    }
}
```

`Drop` runs when the value goes out of scope, on every way out of
`profile`: the normal return, an early `return Err(...)`, and every
`?`. So the directory is removed whether node succeeded, failed, or
never started, without a single clean-up line at each exit. Step through
the whole round trip:

<Formal title="What a profile records">

```text
profile(n) = max { a.length at exit
                   | a tracked as n }
```

<span slot="read">The profile's number for a name n is the largest
length, read when the program exits, of all the arrays that were
tracked under the name n.</span>
</Formal>

<Callout kind="definition">
**PGO in Rust** starts with `viscosity profile`: `instrument` finds the
candidate collections as the compiler does, **wraps each initialiser**
in `__vsc_track(...)` with edits applied **last first**, and prepends a
JavaScript **prelude** shared with the TypeScript CLI; `profile` runs
the result with **`node`** through `std::process::Command`, with a
**`Drop` guard** removing its temporary directory, and returns the JSON
that the program's exit hook wrote, so the file is **byte-identical** in
both engines.
</Callout>

## What you learned

- **`instrument`** finds collections the way the compiler does and wraps
  each initialiser in `__vsc_track(...)`, applying edits **last first**
  so the byte offsets stay valid.
- The JSON is written by **Node**, from a prelude copied from the
  TypeScript CLI, so it is **byte-identical**; Rust only starts `node`
  with **`std::process::Command`** and checks its exit status.
- A **`Drop`** guard removes the temporary directory on every way out of
  `profile`, `?` included.
