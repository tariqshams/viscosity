## One function, any type

You wrote generic functions in TypeScript (*Generics: types with
blanks*), and Rust's look almost the same:

```rust
fn first<T>(xs: &[T]) -> Option<&T> {
    xs.get(0)
}
```

`<T>` declares a **type parameter**: `first` works for a slice of any
`T`, and returns a borrowed `T` if there is one. Call it with `&[1, 2]`
and `T` is `i32`; with `&["a", "b"]`, `T` is `&str`; the compiler works
it out from the arguments. Two things differ from TypeScript, and they
are this chapter: what the body is allowed to *do* with a `T`, and what
the compiler *makes* of the function afterwards.

<Analogy title="a form letter">
A form letter reads "Dear ___, your order of ___ has shipped". It is
written and checked once, and then filled in for each customer. A
generic function is a form letter whose blanks are *types*.
<span slot="breaks">A form letter's blanks can be filled with any
words; a type parameter can be filled only with a type, and (with a
bound) only with a type that has passed a test first.</span>
</Analogy>

`Option<T>`, `Result<T, E>`, `Vec<T>` and `HashMap<K, V>` are all
generic types, and your own structs, enums and impl blocks can have
type parameters too:

<Examples of="rust-generics">

```rust
struct Pair<T> { a: T, b: T }
impl<T> Pair<T> {
    fn first(&self) -> &T { &self.a }
}
let p = Pair { a: 2.5, b: 4.0 };
p.first(); // &2.5
```

</Examples>

`struct Pair<T>` says both fields share one type, whatever it is.
`impl<T> Pair<T>` reads "for every `T`, here are methods of
`Pair<T>`" (the first `<T>` declares the name, the second uses it), and
`first` hands back a borrow of `a` without knowing anything about it.
`p` is a `Pair<f64>`, worked out from the two numbers. drip-rs's heap
handle is the same idea put to work: `pub struct Gc<T>` holds only a
`u32` index at run time, and the `T` keeps a handle to a closure from
ever being used to look up a class.

<Callout kind="definition">
**Generics** in Rust are type parameters, written in angle brackets on a
function (`fn first<T>`), a struct or enum (`struct Pair<T>`), or an
impl block (`impl<T> Pair<T>`). Each use fills them with concrete types,
written out or worked out by the compiler, and the body is checked once,
so that it is correct for every type it may be filled
with<Cite id="rust-book-generics" />.
</Callout>

## Bounds: what T can do

Now a generic function that compares:

```rust
fn top<T>(xs: &[T]) -> Option<&T> {
    let mut best = xs.get(0)?;
    for x in xs {
        if x > best { best = x; }
    }
    Some(best)
}
```

rustc 1.97 refuses it, and its help line is the fix:

```text
error[E0369]: binary operation `>` cannot
  be applied to type `&T`
help: consider restricting type parameter
  `T` with trait `PartialOrd`
1 | fn top<T: std::cmp::PartialOrd>(...
```

A body that works for *every* `T` may only do what every type can do,
and not every type can be compared. So you promise that this `T` can,
with `fn top<T: PartialOrd>`: the body may now use `>` (the standard
trait behind `<` and `>`), and every caller must pass a type that
implements it, or get E0277 at the call, "can't compare `P` with `P`".
Step through both checks:

<BoundSteps client:visible />

<Examples of="trait-bound">

```rust
fn report<T>(a: T, b: T) -> T
where
    T: PartialOrd + Display,
{
    let big = if a > b { a } else { b };
    println!("largest: {big}");
    big
}
```

</Examples>

`report` needs two promises, joined with `+`: `PartialOrd`, so it may
write `a > b`, and `Display` (from `std::fmt`), so it may print the
winner with `{big}`. The `where` clause holds them after the signature,
where long bounds read better than inside the angle brackets.
`report(3, 7)` prints `largest: 7` and returns `7`. For a single
parameter there is a short form: `fn show(p: &impl Plugin)` means the
same as `fn show<P: Plugin>(p: &P)`<Cite id="rust-book-traits" />.

<Callout kind="definition">
A **trait bound** such as `T: PartialOrd` restricts a type parameter to
types that implement the trait. It lets the generic body use that
trait's methods and operators, and makes every caller supply such a
type<Cite id="rustref-trait-bounds" />. `T: A + B` asks for both, and a
**`where`** clause holds longer bounds.
</Callout>

<Figure takeaway="A generic body may do exactly what its bounds promise." caption="With no bound, a T can only be moved, borrowed and stored. Each bound adds the operations of one trait.">
  <BoundPowers />
</Figure>

TypeScript is looser here: the unbounded `top<T>` passes `tsc
--strict`, so `top([{}, {}])` type-checks and compares two objects by
turning them into strings. Its constraints (`T extends ...`) describe
a *shape*; Rust's bounds name *traits*, and nothing else may be used in
the body.

## What runs: one copy per type

After `tsc`, a generic TypeScript function is one JavaScript function
with its types erased (*Interfaces, erasure and typeof*), serving
numbers, strings and everything else. Rust does the opposite. Take a
`Layout` trait with a method `slot(i, f)` that says where element `i`'s
field `f` lives in a flat buffer, implemented by an `Aos` and a `Soa`,
and a function that sums one field through it:

```rust
fn total<L: Layout>(l: &L, buf: &[f64],
    n: usize, f: usize) -> f64 {
    let mut s = 0.0;
    for i in 0..n {
        s += buf[l.slot(i, f)];
    }
    s
}
```

Call it with an `&Aos` and an `&Soa`, and a `total_dyn` (the same body
with `l: &dyn Layout`) with both as well; compile with rustc 1.97 and
`-C symbol-mangling-version=v0`, so that symbol names show their type
parameters, and list the functions with `nm -C`:

<Examples of="monomorphization">

```text
g3::total::<g3::Aos>
g3::total::<g3::Soa>
g3::total_dyn
<g3::Aos as g3::Layout>::slot
<g3::Soa as g3::Layout>::slot
```

</Examples>

Two `total`s, one per type, and a single `total_dyn`. Inside
`total::<Aos>` the call `l.slot(i, f)` can only ever reach `Aos::slot`,
so it is a direct call the optimiser may inline; `total_dyn` has one
copy, whose call loads a function pointer from whichever vtable it is
handed. (The program is in the dropdown below; listing symbols needs a
terminal, so try `nm -C` on your own machine.) Step through what each
copy does:

<MonoSteps client:visible />

<Callout kind="definition">
**Monomorphization** is how Rust compiles generic code: for each set of
concrete types a generic item is used with, it generates a separate,
ordinary copy with those types filled in<Cite id="rust-book-generics" />.
The copies call trait methods directly, so generic code runs like code
written by hand for each type; the price is compile time and binary
size<Cite id="rustc-dev-guide-monomorph" />. A thousand calls with
`i32` share one copy.
</Callout>

You have seen this trade from the engine's side: V8 has to *discover*
that a call site is monomorphic by watching it run (*Shapes, inline
caches and elements kinds*), and keeps a check in case a new shape
arrives, while a call inside `total::<Aos>` is monomorphic by
construction, known before the program runs.

<Figure takeaway="Generics: a copy per type and direct calls. dyn: one copy and a table." caption="The same Layout trait reached two ways. Neither is always better; this book has not timed them against each other, so it makes no speed claim here.">
  <TwoWays />
</Figure>

So choose by the job. `dyn` gives one copy and lets one `Vec` hold many
types, at the cost of an indirect call: a list of GC roots, or anything
chosen while the program runs. Generics give each type its own direct
copy: a hot loop over one known type. The Rust port of Viscosity's
pipeline is `pub fn compile<P: LanguagePlugin>(...)`, and its command
line calls `compile(&src, &PyPlugin, opts)` for `.py` files and
`compile(&src, &JsPlugin, opts)` otherwise, so rustc makes one
`compile` per plugin. (The deep dive *Generics: specialisation or
erasure* compares this with Java's erasure and C++'s templates.)

## What you learned

- **Generics** put type parameters on functions, structs, enums and
  impl blocks; the compiler usually works out the types at each call.
- A generic body may only do what its bounds allow. A **trait bound**
  like `T: PartialOrd` lets it use `>`, and makes every caller supply a
  type that implements the trait (E0277 otherwise). Combine bounds with
  `+`, and move long ones to `where`.
- **Monomorphization** makes one copy of a generic item per concrete
  type: `nm` showed `total::<Aos>` and `total::<Soa>`. Each copy calls
  directly; `dyn` has one copy and an indirect call.

says how long a reference is valid.
