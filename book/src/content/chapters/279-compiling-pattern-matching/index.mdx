## Three questions, asked once each

In chapter 30 you wrote a `switch` on a tagged union's `kind`, and
TypeScript checked that every kind had a case. Languages such as Rust,
OCaml, Haskell, Swift and Java 21 go further, with a `match` that looks
inside values. Here is a Rust function on a pair of optional bytes
(`Option` is a tagged union of `Some(value)` and `None`):

```rust
fn f(a: Option<u8>, b: Option<u8>) -> u8 {
  match (a, b) {
    (Some(x), Some(y)) => x ^ y,
    (None, _) => 0,
    (_, None) => 1,
  }
}
```

The arms are tried from the top, and the first one that fits wins; `_`
matches anything, and `x` and `y` match anything and name it. Read
literally, that is three questions: "are both `Some`?", then "is `a`
`None`?", then "is `b` `None`?". Asked in that order, `a`'s tag can be
tested three times. However, once you know `a` is `None` the answer is
already 0, and once you know `a` is `Some`, only `b` is left to look at;
a good compiler asks about `a` once and `b` at most once.

<Analogy title="a phone menu">
"Press 1 for bookings, 2 for billing"; then, inside billing, "press 1
to pay, 2 to dispute". Each question is asked once, and each answer
takes you down one branch until you reach the right person.
<span slot="breaks">A phone menu is designed by hand, in any order the
company likes; a compiler builds its tree from the arms, and must give
the same answer as trying them top to bottom.</span>
</Analogy>

<Callout kind="definition">
A **decision tree** for a match is a tree whose inner nodes each test
the constructor (the tag) of one part of the value, with one branch per
possible constructor, and whose leaves each name the arm to run (or
report that no arm fits). Following it from the root tests each part of
the value at most once<Cite id="maranget2008" />.
</Callout>

## Building the tree: specialisation

Write the arms as rows of a table, one column per thing being matched,
and the compiler can work on that table mechanically. The rule that
drives it is called **specialisation**: once we know column 1 holds
constructor `c`, a row that starts with `c(q…)` keeps its sub-patterns
`q…` in place of `c`, a row that starts with `_` keeps one `_` for each
of `c`'s fields, and a row that starts with any other constructor is
dropped, because it can no longer match. The algorithm then repeats:

1. No rows left: no arm fits this value, so this leaf reports a
   **missing case**.
2. The first row is all wildcards: it matches, so this leaf is its arm
   (later rows lose, since the first match wins).
3. Otherwise test a column: one branch per constructor of its type, and
   in each branch, specialise the rows and start again.

<Analogy title="sorting the post">
A sorting office does not hold each letter against every address on
its list. It reads the country once and sends the letter to that
country's bin, and the people at that bin read only the city; each bin
holds only the rules that can still apply.
<span slot="breaks">Every letter has the same fields in the same order;
patterns can look at different parts of the value in different
branches, which is why the compiler's choice of column matters (picking
well keeps the tree small).</span>
</Analogy>

<Callout kind="definition">
**Match compilation** turns the rows of a match into a decision tree
by repeatedly choosing a column to test and **specialising** the rows
for each constructor of that column's type, until each branch either
reaches a row of wildcards (that arm) or runs out of rows (a missing
case).
</Callout>

<Formal title="Specialising a row by constructor c">

```text
S(c, [c(q₁…qₖ), p₂…pₙ]) = [q₁…qₖ, p₂…pₙ]
S(c, [_,        p₂…pₙ]) = [_₁…_ₖ, p₂…pₙ]
S(c, [d(…),     p₂…pₙ]) = no row    (d ≠ c)
```

<span slot="read">Specialising a row by c, where c has k fields: a row
starting with c of q1 to qk is replaced by q1 to qk followed by the rest
of the row. A row starting with a wildcard is replaced by k wildcards
followed by the rest. A row starting with a different constructor d is
dropped.</span>
</Formal>

The first is the decision tree as plain JavaScript: three lines, each
tag read once. The second is what rustc really built, the `switchInt`
lines of its MIR for `f` (drawn in the figure): the same tree as ours,
plus an `unreachable` block for tag values that cannot occur. The third is Java 21's pattern `switch` on a sealed interface:
`javac` emits a call to a library method, `typeSwitch`, which returns the
index of the first case label that fits<Cite id="openjdk-switchbootstraps" />,
and a `lookupswitch` (a jump table) on that index; the `default` throws
a `MatchException`, which can only happen if, say, the sealed interface
gained a class after this code was compiled<Cite id="openjdk-matchexception" />.

## Proving nothing is missed

The tree gives two checks for free. If some branch runs out of rows,
there is a value no arm matches, and the path to that leaf is an
example of it; and if some arm is in no leaf at all, it can never run.
Real compilers phrase both as one question, "is this pattern useful
after the ones above it?", and answer it with the same specialisation
step, without building the whole tree<Cite id="maranget2007" />. Rust's
checker is inspired by that work<Cite id="rustc-usefulness" />.

<Analogy title="a jigsaw with a missing piece">
When a jigsaw is nearly done, you can see the shape of the hole, and so
you know exactly which piece to look for.
<span slot="breaks">A jigsaw has a fixed number of pieces; a type like
`u8` has 256 values and a string has endless ones, so a match on them
usually needs a `_` arm, and the checker reasons about groups of values,
not one value at a time.</span>
</Analogy>

<Callout kind="definition">
**Exhaustiveness checking** proves that every value of the matched type
fits some arm, and when one does not, reports an example (a
**witness**). The same analysis finds **redundant** arms, which no value
can reach because earlier arms cover everything they match. Rust uses
it both to report errors and because a `match` must produce a value
for every input<Cite id="rustc-dev-guide-exhaustiveness" />.
</Callout>

<Examples of="exhaustiveness-checking">

```text
error[E0004]: non-exhaustive patterns:
  `&Sh::Re(_, _)` not covered
```

```text
warning: unreachable pattern
3 |   (None, _) => 0,
  |   --------- matches all the
  |             relevant values
4 |   (None, None) => 2,
  |   ^^^^^^^^^^^^ no value can reach this
```

```ts
type Sh = { k: 'sq' } | { k: 're' };
function f(s: Sh) {
  if (s.k === 'sq') return 1;
  const n: never = s; // error
}
```

</Examples>

The first is rustc's error (wrapped to fit) for a `match` on a
three-variant enum that forgot the variant `Re`: the witness is exactly
the missing piece. The second is rustc's warning when `(None, None)`
comes after `(None, _)`: specialised by `None`, the second row is
already all wildcards, so the third never gets a leaf. The third is
chapter 30's TypeScript trick: after the `if`, narrowing leaves `s` with
type `{ k: 're' }`, which cannot be stored in a `never`, and the error
names the forgotten kind: `Type '{ k: "re"; }' is not assignable to
type 'never'`.

<Callout kind="engine" label="Under the hood">
Decision trees never test anything twice, but in bad cases they can
grow very large, because a row with `_` is copied into every branch.
The other classic design, a **backtracking automaton**, keeps the code
small but may test a part of the value more than once; Maranget's paper
on good decision trees chooses the column to test with heuristics so
that trees stay small and fast<Cite id="maranget2008" />. Exhaustiveness
in full generality is also hard: Rust's own source notes that it is
NP-complete<Cite id="rustc-usefulness" />, although real matches are
small enough that it never matters.
</Callout>

## What you learned

- A **decision tree** tests the tag of each part of the value at most
  once and ends in a leaf naming the arm.
- **Match compilation** builds it from rows of patterns by choosing a
  column and **specialising** the rows for each constructor.
- **Exhaustiveness checking** finds values no arm covers (with a
  witness) and arms no value reaches; rustc reports both.
