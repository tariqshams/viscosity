## Who calls whom

Inlining one call is a local decision; deciding *which* calls to inline
in a whole program is not. Inline `clamp` into `move`, and `move` grows,
which changes whether `move` is worth inlining into its own callers.
Inline `fact` into itself, and a new call to `fact` appears in the copy,
forever. Before deciding anything, a compiler draws a map:

<Analogy title="a phone tree">
A school's phone tree says who rings whom when school is closed: the
head rings three teachers, each teacher rings five parents. From it you
can see who will hear the news and in what order, without ringing
anybody.
<span slot="breaks">A phone tree is a tree; a call graph can have
cycles (two functions that call each other), and edges that say only
"may call", since a function calls different things on different
runs.</span>
</Analogy>

<Analogy title="a cookbook's cross-references">
Recipes say "see the pastry on page 12", and the pastry says "see the
glaze on page 30". Following the cross-references tells you every page
a dish depends on, and if two pages ever refer to each other, you will
go round in circles.
<span slot="breaks">A cookbook's cross-references are printed and
fixed. In JavaScript, a call like `g(x)` refers to whatever `g` holds
when it runs, which may not be known until then.</span>
</Analogy>

<Callout kind="definition">
A **call graph** has one node per function and an edge `f → g` when
`f` contains a call that may reach `g`. A cycle in it is recursion
(direct, `f → f`, or mutual, `f → g → f`). A call whose target cannot
be pinned down gets an edge to "unknown", which must be treated as
possibly any function.
</Callout>

<Formal title="Call graph and recursion">

```text
CG = (F, E),  E = { (f, g) : f may call g }
f is recursive  ⟺  f →⁺ f
```

<span slot="read">The call graph is a pair: the set F of functions, and
the set E of pairs (f, g) such that f may call g. A function f is
recursive exactly when there is a path of one or more edges (the little
plus sign) from f back to itself.</span>
</Formal>

## Why JavaScript makes the map hard

In C, `clamp(x)` names one function, fixed when the program is linked.
In JavaScript, a call names a *value*:

<Examples of="call-graph">

```js
function sq(v) { return v * v; }
sq(3);   // edge: caller → sq
```

```js
const f = cond ? sq : cube;
f(3);    // edges: → sq, → cube
xs.map(g); // map → g: from inside map
```

```js
o.area();
// whichever area the prototype chain
// of o finds at run time: unknown
// unless o's shape is known
```

</Examples>

The first is the easy case: a declared function, called by name. The
second shows two ways the callee becomes a value: chosen at run time,
or handed to another function (a callback), which calls it from code
the caller never sees. The third is a method call, whose target depends
on the object's prototype chain. An optimizing JIT copes by *watching*:
type feedback tells it which function a call site has actually called
so far, so it can inline that one, guarded by a check, and deoptimize
if the guess is ever wrong. A tool that compiles ahead of time, like
Viscosity, has to *prove* it instead.

Viscosity proves a small, exact piece of the call graph. A **known
function** is one declared once whose name is never used for anything
but a direct call: not passed as a value, not called as a method, not
reassigned. For those, it can list every call site. Simplified from
`analysis.ts`:

```ts
for (const l of loads.get(f.declaredAs)) {
  for (const u of usesOf(l.id)) {
    const i = u.inst;
    if (i && i.op === 'call' &&
        i.args[0] === l.id &&
        i.note !== 'method') sites.push(i);
    else ok = false;
  }
}
if (ok) callSites.set(f, sites);
```

With every call site known, its numeric inference can say a parameter
is a number when every call passes one, and its layout analysis can
follow a collection into a known function, but only if every call site
passes that same collection. When `total` is called with two different
arrays, it stops (real output, wrapped):

```text
a (line 2) {x} → kept as array of objects
  · unsafe: line 10: passed to total(),
    which is also called with other values
```

Inlining `total` at each call would have given each array its own copy;
Viscosity does not inline, so it keeps both as they are.

## Deciding what to inline

With the map drawn, an inliner needs rules. The common ones:

- **Small callees** are inlined almost always: the copy is not much
  bigger than the call it replaces.
- **Functions called once** (and not visible outside the program) are
  inlined, after which the original can be deleted, so the program gets
  smaller.
- **A growth budget** caps how much bigger a function, or the whole
  program, may get.
- **Hot call sites** (in loops, or seen often at run time) are worth
  more than cold ones.
- **Cycles are not chased**: a recursive call is inlined a few levels at
  most, much like unrolling a loop.

And the order matters. Inliners work **bottom-up**, leaves first: inline
`clamp` into `move` before deciding about `move`, so that every function
is already as optimized as it will get when its callers look at it.

<Callout kind="engine" label="Under the hood">
GCC's inliner, `ipa-inline.cc`, describes exactly these heuristics: an
early pass that runs over the call graph in topological order, so that
callees have already been optimized when they are inlined, and allows
small growth for leaf functions; then a whole-program pass that inlines
small functions greedily, ordered by an estimate of "badness", while
the limits allow, uses a special recursive inliner for recursive calls
("with results similar to loop unrolling"), and inlines functions called
once that are not exported<Cite id="gcc-ipa-inline" />. LLVM documents
its `inline` pass as bottom-up<Cite id="llvm-passes" />. V8's team has
written about the price of getting the budget wrong: the Octane
benchmark rewarded aggressive inlining, and heuristics tuned to it
caused regressions in real code through higher compile time and memory
use<Cite id="v8-retiring-octane" />.
</Callout>

## What you learned

- A **call graph** has a node per function and an edge for each call
  that may happen; recursion is a cycle.
- In JavaScript, callees are values (callbacks, methods, reassigned
  names), so edges can point to "unknown"; a JIT guesses from feedback
  and guards the guess, while Viscosity proves a small exact part (known
  functions and all their call sites).
- Inliners use budgets, prefer small, once-called and hot callees, never
  chase cycles, and work bottom-up so callees are optimized first.
