## Which x is this?

Here are four lines of three-address code:

```js
x = a + 1;
x = x * 2;
y = x + 3;
x = 0;
```

To know anything about the `x` in line 3, an optimiser must first work
out *which* assignment it is (line 2, by scanning backwards), and with
branches and loops that scan becomes a search over the CFG, repeated by
every analysis. So we stop letting one name stand for several values:
every assignment makes a fresh version, and every use names the latest.

<StraightSteps client:visible />

The result is `x1 = a0 + 1; x2 = x1 * 2; y1 = x2 + 3; x3 = 0;`, and line
3 now says `x2`, which has exactly one definition, so there is nothing
to scan.

<Callout kind="definition">
A program is in **static single assignment form** (**SSA**) when every
variable is assigned in exactly one place in the program text, so each
use refers to exactly one definition. "Static" means *in the text*: an
assignment inside a loop runs many times, but it is written once, so it
defines one SSA name.
</Callout>

<Examples of="ssa">

```text
func f(%0):         // let t = a;
  b0:               // let u = t * 2;
    %0 = param      // return u + t;
    %1 = const 2
    %2 = binop * %0, %1
    %3 = binop + %2, %0
    return %3
```

</Examples>

This function has no variable names at all, because in VIR an SSA
value *is* the instruction that defines it: `%2` means "the result of
instruction 2", written once. `t` is only another name for `%0`, and so
the questions become look-ups: `%1` is the constant 2 at every use,
because nothing can reassign it. Not every variable fits. A local that
a closure captures can be changed by another function at a moment this
CFG cannot see, so VIR keeps it as a **binding**, with `load` and
`store`; and SSA renames variables, not memory, so `p.x = 1; p.x = 2;`
stays two `field.set` instructions.

## Where paths meet

Branches break the "latest version" rule: in
`if (x1 > 5) { x2 = x1 * 2; } else { x3 = 0; }`, no single name can go
in the `y = ? + 3` after it, because the answer depends on which way the
program went. SSA's answer is a new kind of instruction at
the start of the join, `x4 = φ(x2, x3)` (φ is the Greek letter phi):
"x2 if we came from the left, x3 if we came from the right".

<RenameSteps client:visible />

<Callout kind="definition">
A **phi node** (φ) sits at the start of a block and has **one operand
per predecessor**, in predecessor order. When control enters the block
along the edge from its k-th predecessor, the phi takes the value of
operand k; all of a block's phis take their values at once, as control
crosses the edge. Phis are not machine instructions: before code
generation, a compiler replaces them with copies at the ends of the
predecessor blocks.
</Callout>

<Examples of="phi-node">

```text
func sum(%0):   // let s = 0;
  b1:  ; preds b0 b3
    %6 = phi %1, %7
    %3 = phi %2, %10
    %5 = binop < %3, %0
    condbr %5, b2, b4
  b2:  ; preds b1
    %7 = binop + %6, %3
    br b3
  b3:  ; preds b2
    %10 = binop + %8, %9
    br b1
```

</Examples>

This is the real VIR, trimmed, for
`for (let i = 0; i < n; i++) s = s + i;`. The loop header b1 is a join,
where the way in from b0 meets the back edge from b3, so each variable
the loop changes gets a phi, with operands in `; preds` order: `%6` is
`s`, `%1` from b0 and the new `s`, `%7`, from b3; `%3` is `i`, `%2` on
the way in and `%10` round the back edge. `%10` is defined *further
down*, which is fine: the phi only reads it on arrival from b3, after b3
has run.

<Figure takeaway="A loop phi takes its first value from the entry edge and every later value from the back edge." caption="The header b1 of sum. On the first arrival, from b0, the phis take %1 and %2, the two zeros. Every later arrival comes along the back edge from b3 and takes %7 (the new s) and %10 (the new i).">

</Figure>

<More title="More: why all the phis of a block act at once">

A loop that swaps two variables each time round has, at its header,
`p2 = φ(p0, q2)` and `q2 = φ(q0, p2)`. Along the back edge, `p2` must
get the *old* `q2` and `q2` the *old* `p2`; if the phis ran one after
the other, the second would read the first one's new value and the swap
would be lost. That is also why leaving SSA is not as simple as it
looks: the copies `p2 = q2; q2 = p2;` at the end of the predecessor
have exactly that bug, and a compiler must order them carefully or use
a spare temporary (the deep dive *Parallel copies and the swap problem*).

## Building SSA while lowering

VIR's builder, like *One pass from source to bytecode*, emits
instructions while it walks the syntax tree, and the IR comes out in SSA
directly. The method is Braun and colleagues'<Cite id="braun2013" />, in
`packages/core/src/builder.ts`: treat "what is `x` here?" as a question
a block can answer, or pass on to the blocks before it.

<Analogy title="a whiteboard in every room">
Each room in a building has a whiteboard. When you set the thermostat in
a room, you write the setting on that room's board. To find the setting
in a room with a blank board, you ask in the room you came from; if
people arrive from two rooms that give different answers, the room
needs a rule, "it depends on which door you came through".
<span slot="breaks">People forget to update whiteboards; the builder
writes every assignment down the moment it lowers it, and also writes
the answer to every question it had to ask, so the next reader in that
room finds it at once.</span>
</Analogy>

Each block keeps a table (`defs`, a `Map` per block from variable to
value id). `writeVariable(v, block, value)` records an assignment there,
and emits nothing; `readVariable(v, block)` looks there first, and only
if the block has no entry does `readVariableRecursive` ask (simplified):

```ts
if (!this.sealed.has(block)) {
  val = incompletePhi(v, block);
} else if (b.preds.length === 1) {
  val = this.readVariable(v, b.preds[0]);
} else if (b.preds.length === 0) {
  val = undefinedConst();
} else {
  const phi = this.newPhi(block);
  this.writeVariable(v, block, phi.id);
  val = this.addPhiOperands(v, phi);
}
this.writeVariable(v, block, val);
```

With **one predecessor**, the answer is whatever `v` is there; with
**none**, `v` is `undefined`; with **several**, make a phi, record it
*first*, then read `v` in every predecessor for its operands (recording
first means a search that comes back round a loop finds the phi and
stops). The last line caches the answer.

<Figure takeaway="A block with no answer asks its predecessors; where they disagree, it makes a phi." caption="Reading x in b3 of a small if/else. b3’s table has no x, so it asks b1 and b2, gets %2 and %3, and makes %4 = φ(%2, %3), the phi in the real VIR, which it records as its answer.">
  <AskPreds />
</Figure>

The first case is for loops. When the builder lowers a loop test, it
has not lowered the body, so the back edge does not exist yet. A block
is **sealed** once all its predecessors are known; reading a variable
in an unsealed block makes an empty **incomplete phi** and remembers it,
and `seal(block)` later calls `addPhiOperands` on each one. The front
end seals a loop header right after it emits the back edge
(`fb.br(head.id); fb.seal(head.id);`). Step through the real `sum`; a
dashed block is unsealed:

<BraunSteps client:visible />

The header asked "what is `n`?" before it could know that the loop
never changes `n`, so once sealed its phi was `%4 = φ(%0, %4)`, which
is `%0` whichever edge you take. A phi whose operands are all one value,
apart from the phi itself, is **trivial**, and `tryRemoveTrivialPhi`
replaces every use of it with that value, deletes it, and retries every
phi that used it, since removing one can make another trivial. (That is
why the listing of `sum` jumps from `%3` to `%5`.)

<Callout kind="definition">
**On-the-fly SSA construction** (Braun et al.) builds SSA while
lowering: each block records its own definitions; a read with no local
definition asks the predecessors, passing the question on through a
single predecessor and making a phi (recorded before its operands are
read) where there are several. A block whose predecessors are not all
known is **unsealed**, and reads there make incomplete phis that sealing
completes. A **trivial** phi, whose operands are one value or itself, is
replaced by that value.
</Callout>

<Examples of="on-the-fly-ssa">

```text
// let x = 1; let y = 5;
// if (c) { x = 2; } return x + y;
  b3:  ; preds b1 b2
    %17 = phi %16, %14
    %19 = binop + %17, %15
    return %19
```

</Examples>

Reading `x` at the join b3, whose table is empty, makes a phi and asks
both predecessors: b1 wrote `x = 2` (`%16`); b2, the empty else, asks
its one predecessor b0, which wrote `x = 1` (`%14`). They differ, so
`%17` stays. Reading `y` makes `%18` and gets `%15` from both sides, so
`%18` is trivial and removed: the listing jumps from `%17` to `%19`.

<More title="More: the code for trivial phis, Maglev's answer to loops, and the classic construction">

```ts
let same = null;
for (const op of phi.args) {
  if (op === same || op === phi.id)
    continue;
  if (same !== null) return phi.id;
  same = op;
}
```

The loop skips operands equal to the value already found or to the phi
itself, and the moment it meets a *second* different value the phi
really merges and is kept. Try the test on a few phis:

V8's Maglev builds SSA from Ignition bytecode in one forward pass, and
meets the loop problem too; it runs a prepass that finds which
variables each loop assigns, so it can create those loop phis before the
body and fill in the back-edge input at the end<Cite id="v8-maglev" />.
VIR's builder needs no prepass; it may create a few phis it does not
need, and deletes them as trivial. The classic alternative builds a
finished CFG first and then places phis using dominance; the deep dive
*Dominance frontiers and classic SSA construction* teaches it, after
*Dominators and natural loops* has introduced dominance.
