## The analysis that stops at the door

Last chapter's points-to analysis looked at one function's statements.
Real programs are mostly calls, and an analysis that looks at one
function at a time (an **intraprocedural** analysis, "inside one
procedure") has to treat each call as a closed door: whatever goes in
might be stored anywhere, and whatever comes out might be anything.
Take the smallest function there is:

```js
function id(p) { return p; }
const a = id({ n: 1 });  // call site s1
const b = id({ n: 2 });  // call site s2
```

Behind a closed door, `a` and `b` each point at "something unknown",
so every question about them is answered "may alias", and every object
passed in counts as lost. An **interprocedural** analysis opens the
door: it follows the argument into `id`, sees that `id` hands it
straight back, and concludes that `a` is the first object and `b` the
second.

<Analogy title="tracing a pipe through the walls">
A plumber who stops at every wall has to assume the pipe behind it
could go anywhere, and so cannot promise that the kitchen tap is safe
to turn on. One who opens the panels and follows the pipe through each
room can say exactly which taps it feeds.
<span slot="breaks">A pipe goes through a wall once; a function is
entered from many places, and the hard part (the rest of this chapter)
is remembering which entrance you came in by.</span>
</Analogy>

The trick is to see a call as nothing more than copies. Calling
`r = f(x)` copies the argument into the parameter and, on the way out,
the return value into `r`, so the same inclusion rules from the last
chapter apply:

<Formal title="A call as two copies">

```text
r = f(x)  at site s:
  pts(x) ⊆ pts(param of f)
  pts(return of f) ⊆ pts(r)
```

<span slot="read">At a call site s where r is assigned f of x: the set
of things x may point at is included in the set of f's parameter, and
the set of things f may return is included in the set of r.</span>
</Formal>

<Callout kind="definition">
**Interprocedural analysis** follows facts across function boundaries:
from arguments into parameters, and from return values back to the
callers, along the edges of the call graph (chapter 93). It sees more
than an intraprocedural analysis, which must assume the worst at every
call, without copying function bodies the way inlining does.
</Callout>

In JavaScript there is a twist. Which function a call reaches depends
on which function *value* the callee holds, and that is itself a
points-to question: in `g(x)`, the targets are whatever function objects
`pts(g)` contains. So the call graph and the points-to sets have to be
built together, each new edge adding facts and each new fact perhaps
adding edges. Doop, which the next chapter meets, computes exactly this,
"on the fly"<Cite id="bravenboer2009" />.

## The price of a single shelf

Follow the copies for `id` and something goes wrong. Both calls copy
into the same parameter `p`, so `pts(p) = {o1, o2}`; the return copies
all of `p` to both callers, so `a` and `b` both end up with
`{o1, o2}`, and the analysis says they may alias. They never do.

<Figure takeaway="Merging all callers lets facts enter at one call and leave at another, which no real run can do." caption="Real paths (green) return to the call site they came from. A context-insensitive analysis also follows the red one: in at s2, out to a.">
  <PathsPic />
</Figure>

The analysis has followed a path that enters `id` at `s2` and leaves to
`s1`'s result, which no run can take: a call always returns to the
place it came from. This kind of analysis, which keeps one set of facts
per function whatever the caller, is called **context-insensitive**,
and its false answers come from these impossible paths.

<Analogy extra title="one lost-property shelf for a whole hotel">
A small hotel keeps everything guests leave behind on one shelf. When
the guest from room 4 asks for her umbrella, the desk can only say
"one of these", because nobody wrote down which room each thing came
from. A shelf per room fixes it.
<span slot="breaks">A hotel has a fixed number of rooms; the number of
ways a function can be reached (chains of callers, recursion) can grow
without limit, so the analysis has to decide how many "rooms" it can
afford.</span>
</Analogy>

## Remembering who called

A **context** is a label that tells calls to the same function apart.
The best-known choice comes from Sharir and Pnueli's "call-string
approach": label each fact with the chain of call sites that led
there<Cite id="sharirpnueli1981" />. Since recursion makes those chains
endless, analyses keep only the last **k** sites (a "k-call-site"
analysis); with `k = 1`, `id` is analysed once for `s1` and
once for `s2`. Step through both versions:

<ContextSteps client:visible />

<Analogy extra title="a translator who notes the sender">
A translator works for two clients. If replies are handed back without
noting who asked, the answers get mixed up; writing the sender's name
on each message keeps every reply going to the person who asked. The
name on the message is the context.
<span slot="breaks">A name identifies a person forever; a call string
cut to k sites can make two different chains of callers look the
same, and then their facts mix again.</span>
</Analogy>

<Callout kind="definition">
**Context sensitivity** analyses a function separately for each kind of
caller, so facts from one caller never flow back to another. The
context is usually the last k call sites (**call-string** sensitivity)
or, for methods, the allocation site of the receiver object (**object
sensitivity**). A **context-insensitive** analysis keeps one set of
facts per function.
</Callout>

<Formal title="k-limited call strings">

```text
pts(v, c)       v's set in context c
call at site s in context c:
  callee context = first k of (s · c)
```

<span slot="read">Every variable now has one set per context c. When a
function running in context c makes a call at site s, the callee runs
in the context made by putting s in front of c and keeping only the
first k sites.</span>
</Formal>

<Examples of="interprocedural-analysis context-sensitivity">

```js
id({ n: 1 });  // s1: id in context [s1]
id({ n: 2 });  // s2: id in context [s2]
```

```js
function wrap(q) { return id(q); } // s3
wrap({ n: 1 });  // id in [s3, s1]
wrap({ n: 2 });  // id in [s3, s2]
// k = 1: both are [s3]: merged again
```

```js
function put(b, v) { b.set(v); } // s4
put(box1, o1);
put(box2, o2);
// call sites: set is always [s4];
// objects: set runs for box1, box2
```

</Examples>

The first is the case from the stepper: one site of context separates
the two calls. The second shows the limit of k: `id` is now always
called from the same site, `s3` inside `wrap`, so with `k = 1` both
calls look alike and the false alias returns; `k = 2` separates them,
at the price of more contexts. The third is why object-oriented code
uses **object sensitivity**, from Milanova, Rountev and Ryder: it
analyses a method separately for each receiver object (`box1`, `box2`)
rather than each call site<Cite id="milanova2005" />. The same idea
can be pictured as **cloning**: make a copy of the function for every
context and run a plain context-insensitive analysis on the bigger
program; Whaley and Lam made that practical for large Java programs by
storing the facts compactly in binary decision diagrams<Cite id="whaleylam2004" />.

## What you learned

- **Interprocedural analysis** follows facts across calls by treating a
  call as copies: argument to parameter, return value to result.
- In JavaScript the call graph needs points-to sets (callees are
  values), so the two are built together.
- A **context-insensitive** analysis merges every caller and follows
  impossible paths (in at one call, out at another), producing false
  aliases.
- **Context sensitivity** keeps facts apart per caller: by the last k
  call sites (**call strings**), by receiver object (**object
  sensitivity**), or, equivalently, by cloning functions per context.
- More context is more precise and more expensive; when k is too small,
  a wrapper merges the callers again.

## Read it once, use it everywhere

Context sensitivity keeps callers apart by analysing a function again
for each context, and in a big program the number of contexts can be
enormous: every chain of k call sites that can reach a function is one
more copy of its facts. There is another way, and it was the second of
Sharir and Pnueli's two approaches, the "functional approach": analyse
each function once, and record not an answer but a *rule* that turns
what comes in into what goes out<Cite id="sharirpnueli1981" />. Then
each call applies the rule to its own arguments.

For `id`, the rule is a single sentence: "the result points at whatever
the parameter points at". At `a = id(o1)` that gives `{o1}`, at
`b = id(o2)` it gives `{o2}`: the precision of a context-sensitive
analysis, while `id` was read only once.

<Analogy title="the allergy label on a recipe">
A recipe card can carry a label like "contains whatever nuts you put
in the filling". The cook reads the label instead of the whole recipe,
and the label gives the right answer for every filling, because it
says how the answer depends on the input.
<span slot="breaks">A cook can always check the recipe if the label is
unclear; an analysis that uses a summary has thrown the body away, so
the summary must be safe for every possible input, and when it cannot
be precise, it has to say the worst.</span>
</Analogy>

<Figure takeaway="A summary is computed once per function and read at every call." caption="Each function's body is analysed once and boiled down to what happens to its parameter; callers use only the summary.">
  <SummaryPic />
</Figure>

<Callout kind="definition">
A **function summary** records, once per function, what the function
does with what flows into it: which parameters may be returned, stored
somewhere lasting, or passed on, and which fields it reads and writes.
At every call site the analysis applies the summary to that call's own
arguments, instead of re-reading the body.
</Callout>

<Formal title="Applying a summary">

```text
S_f : facts about the parameters
        → facts about the result
r = f(x):  facts(r) = S_f(facts(x))
```

<span slot="read">The summary of f, written S_f, is a function from
facts about f's parameters to facts about its result (and effects). At
a call where r is assigned f of x, the facts about r are what you get
by applying the summary to the facts about x at that call.</span>
</Formal>

<Examples of="function-summary">

```js
function id(p) { return p; }
// summary: result ⊇ pts(p)
```

```js
function setX(o, v) { o.x = v; }
// summary: for each obj in pts(o),
//   pts(obj.x) ⊇ pts(v); returns none
```

```text
$ go build -gcflags='-m -l' .
./main.go:23:11: p does not escape
./main.go:28:33: &P{...} does not escape
```

</Examples>

The first is `id` again: its summary needs no context at all, because
it is a rule about the parameter. The second records a side effect: a
call `setX(a, b)` means "a's objects get b's objects in their field
x", which is the store rule from two chapters back, applied at the
call. The third is real: Go's compiler (go1.24.7, with `-l` turning
inlining off) analyses `func read(p *P) float64 { return p.x }` once,
concludes "p does not escape", and at the call `read(&P{7, 8})` uses
that summary to decide the new `P` can live on the stack. Go's own
source calls these summaries "parameter tags", "used at static call
sites to improve escape analysis of function arguments"<Cite id="go-escape" />.

Recursion needs one more step: to summarise `f`, you may need `f`'s
own summary. The answer is the usual one: start every summary at
"does nothing", recompute them all, and repeat until none changes, a
fixpoint over summaries instead of over sets.

## An analysis as a page of rules

By now every analysis in this part has the same shape: some facts read
off the program, some rules of the form "if this and that, then this
other thing", and a loop that applies the rules until nothing new
appears. Real points-to analyses have dozens of such rules (fields,
arrays, casts, calls, contexts), and the hand-written loops become the
hardest part to get right. **Datalog** is a small logic language whose
whole job is exactly that loop: you write the facts and the rules, and
an engine finds the fixpoint.

<Analogy extra title="a family tree and the word “ancestor”">
Write down who is whose parent, then two rules: a parent is an
ancestor, and a parent of an ancestor is an ancestor. Anyone can now
find every ancestor by applying the rules again and again until no new
names turn up; nobody needs to write a search procedure.
<span slot="breaks">A family tree only goes back in time, so it never
loops; program facts often form cycles (a = b, b = a), and the rules
still stop because no rule ever invents a new name, so there are only
so many facts to find.</span>
</Analogy>

A **fact** is a row in a table, such as `New(a, o1)` ("a is assigned a
new object from site o1") or `Assign(a, c)` ("c = a"). A **rule** has
a head, `:-` (read "if"), and a body; variables shared between body
parts must match, which joins the tables. Here are the two rules that
compute points-to sets for copies, evaluated step by step:

<DatalogSteps client:visible />

That is Andersen's analysis from two chapters back, in two lines. Doop,
a points-to framework for Java by Bravenboer and Smaragdakis, is
written this way from end to end, including context sensitivity and
building the call graph on the fly<Cite id="bravenboer2009" />. Here is
its copy rule, quoted from its source<Cite id="doop-micro" />:

```text
VarPointsTo(?heap, ?to) :-
   Assign(?from, ?to),
   VarPointsTo(?heap, ?from).
```

It reads: the variable `?to` may point at `?heap` if there is an
assignment from `?from` to `?to` and `?from` may point at `?heap`.
Doop's other rules add a `Reachable(?method)` condition, so that only
methods the call graph has reached contribute facts, and a rule that
derives `Reachable` and `CallGraphEdge` from the points-to sets of
receivers: the call graph and the sets grow together, as the last
chapter said they must.

<Callout kind="definition">
In a **Datalog analysis**, the program is turned into facts (rows of
relations such as `Assign` and `New`), the analysis is written as
rules `head :- body`, and an engine derives every fact the rules allow,
repeating until a round adds nothing (the least fixpoint). Because
rules never invent new values, there are finitely many possible facts,
so evaluation always stops.
</Callout>

<Formal title="Reading a rule">

```text
H(x, z) :- A(x, y), B(y, z).
∀ x, y, z :  A(x, y) ∧ B(y, z) ⇒ H(x, z)
```

<span slot="read">The rule says: for all x, y and z, if A holds for x
and y, and (the wedge ∧) B holds for y and z, then H holds for x and z.
The shared y is the join: an A row and a B row combine only when they
agree on y.</span>
</Formal>

<Examples of="datalog-analysis">

```text
Path(x, y) :- Edge(x, y).
Path(x, z) :- Edge(x, y), Path(y, z).
```

```text
Pts(v, h)  :- New(v, h).
Pts(t, h)  :- Assign(f, t), Pts(f, h).
```

```text
Pts(c, t, h) :- Assign(f, t, c),
                Pts(c, f, h).
```

</Examples>

The first is a version of the warm-up in Doop's own Datalog
tutorial<Cite id="doop-micro" />: paths in a graph, from edges. The second is the analysis in the stepper. The third
shows how context sensitivity looks in Datalog: one more column, `c`,
the context, carried through each rule, so facts from different
contexts never join. Engines then make it fast: Soufflé, which is
"frequently used as a domain-specific language for analysis problems",
compiles the rules to parallel C++<Cite id="souffle-readme" />, and
Whaley and Lam's bddbddb compiled Datalog to binary decision diagrams
to handle huge numbers of contexts<Cite id="whaleylam2004" />. Run the

## What you learned

- A **function summary** is computed once per function and applied at
  every call to that call's own arguments, which gives context-sensitive
  precision without re-reading the body (Sharir and Pnueli's functional
  approach; Go's "parameter tags").
- Recursive functions are summarised by iterating all summaries to a
  fixpoint.
- A **Datalog analysis** writes facts as table rows and the analysis as
  rules; shared variables join tables, and evaluation repeats until a
  round adds nothing. It always stops, since rules invent no new values.
- Doop writes a whole context-sensitive points-to analysis for Java this
  way, and engines like Soufflé compile the rules to fast code.
