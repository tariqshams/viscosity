## Where the core left off

You met points-to sets in *Alias analysis and points-to*, and in
*Escape analysis across functions* you followed them through calls,
kept a function's callers apart with contexts of the last k call sites
(Sharir and Pnueli's call-string approach<Cite id="sharirpnueli1981" />),
recorded function summaries, and wrote the analysis as Datalog rules
that an engine runs to a fixpoint. This chapter goes further in three
directions: contexts for the objects a function creates, what contexts
cost, and how a Datalog engine finds the fixpoint without redoing its
work every round.

Start with a problem that call contexts alone cannot solve. Points-to
analyses name each object by the place in the code that creates it (its
**allocation site**), because a program can create endless objects but
has only so many `new` expressions. That works well until the creating
happens inside a helper:

```js
function box() {
  return { v: null }; // site h
}
const a = box();   // call site s1
const b = box();   // call site s2
a.v = x;
b.v = y;
```

Every object `box` makes is "the object from site h", so `a` and `b`
point at the same abstract object, both stores land in its one field,
and reading `a.v` gives "`x`'s object or `y`'s object". Analysing `box`
separately for `s1` and `s2` does not help: in both contexts it returns
the same `h`.

<Analogy title="parcels named after the factory">
A courier who labels every parcel only with the factory it came from
cannot tell your parcel from your neighbour's when both came from the
same factory; adding the order number that asked for each one (which
customer, which order) separates them again.
<span slot="breaks">An order number is unique forever; a context cut to
k call sites is not, so two different chains of callers can end up with
the same label and their objects merge once more.</span>
</Analogy>

## Contexts for the heap

The fix is to give objects contexts too: name an object by its
allocation site *and* the context the allocating function was running
in. `box` runs in `[s1]` for `a` and in `[s2]` for `b`, so there are now
two abstract objects, `h@[s1]` and `h@[s2]`, each with its own field.
Step through it, including the wrapper that undoes it:

<HeapSteps client:visible />

<Callout kind="definition">
A **heap context** is the context attached to an abstract object: the
object is named by its allocation site together with (a prefix of) the
context of the function that allocated it. An analysis with heap
contexts is sometimes said to use **heap cloning**, since each
allocation site is copied once per context. Without heap contexts,
context sensitivity separates a function's variables but not the
objects it creates.
</Callout>

The last step of the stepper is the same lesson as call strings: a
wrapper spends one site of context, so a factory behind a factory needs
two. The same is true of object sensitivity (Milanova, Rountev and
Ryder's choice of the receiver object as the context<Cite id="milanova2005" />),
where the receiver is itself an abstract object named by its site and
its own heap context; as such, the precision of the method contexts
depends on the precision of the heap.

## What a context costs

Every context is one more copy of a function's facts, and the copies
multiply. If `main` calls `parse` from two sites, `parse` calls `node`
from two sites, and `node` calls `box` from two sites, there are two
call strings ending at `box` of length one, four of length two, and
eight of length three:

<Formal title="How many contexts">

```text
contexts(f) ≤ min(paths to f,  sites^k)
```

<span slot="read">The number of contexts a function f is analysed in is
at most the number of distinct chains of call sites that reach it,
and at most the number of call sites raised to the power k.</span>
</Formal>

<Examples of="context-sensitivity">

```js
// k = 0: box has 1 context
// k = 1: 2   ([s5], [s6])
// k = 2: 4   ([s5, s3], [s5, s4], ...)
// k = 3: 8, and k = 4 is still 8
```

<Run id="contextCount" />

</Examples>

The comments are what the runnable prints, and the last line is the
interesting one: once k is longer than the deepest chain of calls,
more context adds nothing, because there are no more call sites to
tell apart. With recursion there is no deepest chain, which is why k
has to be a fixed limit. Each context also multiplies the facts inside
it (every variable has a set per context, and with heap contexts every
object is several objects), so precision is paid for twice. The
everyday answer is to spend context only where it pays, for instance
giving heap objects a shorter context than method calls, since every
level added to the heap multiplies the objects as well.

<More title="Very many contexts, stored compactly">

Whaley and Lam showed that very large numbers of contexts can still be
handled for big Java programs: they clone each method once per context
and store the resulting facts as binary decision diagrams, a compact
encoding of huge sets in which facts that share structure are stored
once, and their bddbddb system compiles Datalog rules into operations
on those diagrams<Cite id="whaleylam2004" />.

</More>

## Contexts as a column

In Datalog, a context is one more column. The copy rule from the core
gains a context `c`, carried through so that facts from different
contexts never join, and a heap context `hc` sits next to the
allocation site:

```text
Pts(c, t, h, hc) :- Assign(f, t, c),
                    Pts(c, f, h, hc).
Pts(c, v, h, c)  :- New(v, h, c).
Ctx(g, [s, c1])  :- Call(s, f, g),
                    Ctx(f, [c1, c2]).
```

The first rule is the core's copy rule with contexts. The second gives
a new object the context its allocation ran in (a heap context of the
same length as the method's; a shorter one would keep only part of
`c`). The third builds contexts: when `f`, running in context
`[c1, c2]`, calls `g` at site `s`, then `g` runs in `[s, c1]`, which is
k = 2 call strings, the oldest site falling off. Doop, the Datalog
points-to framework for Java by Bravenboer and Smaragdakis, computes
contexts in rules of this kind while it builds the call graph on the
fly<Cite id="bravenboer2009" />, and Soufflé, the engine Doop's current
rules are written for<Cite id="doop-micro" />, supports the `[s, c1]`
notation directly, since its language "has terms known as
records"<Cite id="souffle-readme" />.

Records change one guarantee. Plain Datalog always stops, because rules
only rearrange values already in the facts, so there are finitely many
facts to find. A record is a *new* value, and a rule that builds
`[s, c]` with no limit could build `[s, [s, [s, c]]]` for ever around a
recursive call. The third rule stops only because it throws away `c2`:
**k-limiting is what keeps a context-sensitive Datalog analysis
finite**.

## Never join the same facts twice

The simplest engine, and the one the core wrote, evaluates rules
**naively**: each round
matches every rule against every known fact, keeps what is new, and
stops when a round adds nothing. That finds the right answer, but every
round re-derives every fact found in earlier rounds. The fix rests on
one observation: a match that uses only old facts was already made in
an earlier round, so a round only needs the matches that use at least
one fact that was *new* in the round before (the **delta**).

<SemiNaiveSteps client:visible />

<Callout kind="definition">
**Semi-naive evaluation** runs Datalog rules in rounds, but in each
round after the first it makes only the matches that use at least one
fact derived in the previous round. For a rule with several derived
atoms, it evaluates one version per atom: that atom matched against
the new facts, the atoms before it against the facts older than the
last round, and the atoms after it against all facts. Each match is
then made exactly once, in the round after its newest fact appeared.
</Callout>

On a chain of 100 nodes both strategies take 100 rounds to find the
4,950 path facts; naive evaluation makes 333,300 matches, semi-naive
makes 4,950, one per fact. The split into "before", "this one" and
"after" matters for rules like `Path(x, z) :- Path(x, y), Path(y, z)`,
where both atoms can match new facts in the same round: matching both
against all facts (with only one of them forced to be new) counts some
matches twice, and on a chain of five nodes gives 18 matches instead
of 14.

<More title="Negation, and why rules come in layers">

Real analyses also need "not": a value reaches a use if it is assigned
and **not** overwritten in between. A rule with `!Killed(x)` in its body
can only be applied once `Killed` is complete, since a fact added to
`Killed` later would make an earlier conclusion false, and a fixpoint
that grows only can never take a fact back. Engines therefore sort the
rules into **strata** (layers): every relation used under a "not" must
be finished in an earlier layer, and a program where a relation depends
negatively on itself (`P(x) :- Q(x), !P(x)`) has no such layering and is
rejected. Within each layer, evaluation is the semi-naive loop above.

</More>

## What you learned

- Naming objects by allocation site alone merges what a factory makes
  for different callers; a **heap context** (site plus the allocating
  function's context) separates them, and a wrapper again costs one
  site of context.
- Contexts multiply: up to sites^k per function, capped by the number
  of real call chains, and every context multiplies the facts inside
  it, so analyses spend context where it pays.
- In Datalog a context is an extra column, and building new contexts
  needs records; **k-limiting** is what keeps such rules finite.
- **Semi-naive evaluation** joins only with last round's new facts,
  making each match once instead of repeating all of them every round.
