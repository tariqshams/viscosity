## Two ways to ship Rust

Chapter 119 packed the TypeScript CLI for npm: one JavaScript bundle,
`dist/viscosity.mjs`, that runs on any computer with Node 18. Easy,
because JavaScript is the same everywhere. The Rust engine is faster
(chapter 192), but a compiled Rust program is not the same everywhere.
`cargo build --release` gave me a 2,785,400-byte ELF executable for
x86-64 Linux, linked against glibc. A Mac can't run it, and neither can
an ARM laptop.

Tools written in Rust, Go or C++ solve this in one of two ways, and
you have used both without noticing. Look in this book's own
`node_modules`. The bundler esbuild 0.27.7 lists 26
`optionalDependencies`, `@esbuild/darwin-arm64` to `@esbuild/win32-x64`,
and each of those packages declares the `os` and `cpu` it runs on.
npm compares them with the machine and skips the rest. Here only
`@esbuild/linux-x64` was installed: one 11,120,788-byte
binary<Cite id="npm-package-json-platform" />.

<Run id="pick-native" />

The other way is to compile once to WebAssembly and let the JavaScript
engine run it. wasm-bindgen's guide offers its Node target "perhaps as
an alternative to a native module"<Cite id="wasm-bindgen-guide" />.

<Callout kind="intuition">
Travelling abroad, you can pack a plug adapter for every country you
might visit, or bring a device that runs on the batteries sold
everywhere. The adapters give full power, but you need the right one.
The batteries work anywhere, at a little less power.
</Callout>

<Callout kind="definition">
**Native binaries vs WebAssembly**: a native build is compiled for one
operating system and CPU, so it is the fastest and can use threads and
files, but you ship (and build, and test) one per platform. A `.wasm`
is one file for every platform, run by the host's JavaScript engine.
It is slower, and on `wasm32-unknown-unknown` the standard library can't
reach the host: `std::fs` returns errors and `std::thread::spawn`
panics<Cite id="rustc-wasm32-unknown-unknown" />.
</Callout>

## One package, two kinds of glue

`@viscosity/wasm` takes the second road. Chapter 189's build left two
folders, `dist/node` (CommonJS glue that loads synchronously) and
`dist/web` (an ES module with `init()`). The `package.json` decides who
gets which, with an `exports` map. Trimmed:

```json
"exports": {
  ".": {
    "node": {
      "types": "./dist/node/….d.ts",
      "default": "./dist/node/….js"
    },
    "browser": {
      "types": "./dist/web/….d.ts",
      "default": "./dist/web/….js"
    },
    "types": "./dist/web/….d.ts",
    "default": "./dist/web/….js"
  },
  "./web": …, "./node": …,
  "./viscosity_wasm_bg.wasm": …
}
```

Each key is a **condition**. Node sets `"node"` and either `"import"`
or `"require"`; a bundler building for the web uses `"browser"`. Key
order is significant: the first key whose condition is active wins,
`"default"` always matches and so comes last, and a nested object that
matches nothing falls back to its parent's next
key<Cite id="node-packages-exports" />. TypeScript reads the same map
and always matches `"types"`<Cite id="ts-modules-reference" />. Step
through five importers:

## What is in the box

Packed at commit `288e497`, the package is 13 files, 997 KiB, and
2,840 KiB once unpacked. Most of it is two copies of the same module:
`dist/node/viscosity_wasm_bg.wasm` (1,373,454 bytes) and
`dist/web/viscosity_wasm_bg.wasm` (1,373,390). Each glue file loads the
module sitting next to it, so sharing one would mean editing
generated code. The build doesn't, and the price is 1.4 MB of disk.

There is no `bin`. `@viscosity/cli` installs a `viscosity` command;
`@viscosity/wasm` is a library, for programs that want to call
`compile` themselves: an editor plugin, a bundler plugin, this book.

The third big file is `THIRD_PARTY_LICENSES.txt`, 130,597 bytes. The
TypeScript CLI has one too, because its bundle contains acorn and
sucrase. The `.wasm` is the same situation, larger. It *statically
links* 71 third-party Rust crates: oxc's parser, `indexmap`,
`rustc-hash`, the ICU4X Unicode crates, wasm-bindgen itself. Their code
is inside the file you hand out, so their licence notices must go with
it. `build.mjs` asks `cargo tree` which crates are linked for
`wasm32-unknown-unknown` (proc macros, which run only at build time,
are left out), finds each crate's licence files through
`cargo metadata`, and writes every distinct text once. One snag: oxc's
crates are published without their licence file. The package carries
copies of oxc's own files in `licenses/`, and the script uses them as a
fallback for any `oxc` crate.

## Installed like a stranger would

Chapter 119 found three bugs by installing the TypeScript CLI in an
empty folder. `smoke.mjs` does that for this package, every time: `npm
pack`, install the tarball into a fresh directory, then compile every
corpus program through the installed package, 40 JavaScript and 20
Python, in three ways, and compare `code` and `explain` with what the
TypeScript CLI prints. Finally it type-checks a small consumer under
both the Node and the browser conditions. My run, at commit
`288e497` (repeated with the same results after the version became
0.0.1), trimmed:

```
packed viscosity-wasm-0.0.1.tgz:
  13 files, 997 KiB (2840 KiB unpacked)
✓ nodejs target, require():
  {"programs":60,"mismatches":0}
✓ nodejs target, import:
  {"programs":60,"mismatches":0}
✓ web target, init(bytes):
  {"programs":60,"mismatches":0}
✓ types (node, nodenext)
✓ types (browser, bundler)
```

The web variant runs in Node too, by passing the `.wasm` bytes to
`init()` instead of a URL. When this chapter was written the package
wasn't published, but like the CLI, everything up to `npm publish` had
been walked. On 2026-11-02 both went to npm (chapter 198), so
`npm install @viscosity/wasm` works now.

<Callout kind="engine" label="Under the hood">
The build itself relies on a WebAssembly package. Binaryen is written
in C++ and publishes native releases for five platforms, plus a Node
build: "A port of `wasm-opt` to JavaScript+WebAssembly … on any
platform that Node.js runs on"<Cite id="binaryen-readme" />. The npm
`binaryen` package that `build.mjs` finds is that port. Its
`bin/wasm-opt` is one 11 MB file: a JavaScript loader with the module
embedded in it. That's why `npm install` was enough on the build machine,
whatever it was. The cost showed in chapter 189: about 25 seconds for
each `-O3` run.
</Callout>

## What you learned

- **Native** builds are fastest but per platform. esbuild ships 26
  packages, and npm installs the one whose `os` and `cpu` match.
- A **.wasm** is one file for every platform, run by the JS engine,
  without threads or files on `wasm32-unknown-unknown`.
- An **exports map** is tried in key order: first active condition
  wins, `"default"` last, nested misses fall through.
- A statically linked `.wasm` must carry its crates' **licences**:
  71 of them here.
- `smoke.mjs` installs the tarball and checks 60 programs three ways
  against the TS CLI.
