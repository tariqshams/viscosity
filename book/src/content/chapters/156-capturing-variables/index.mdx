## The counter, on the VM

Here is the counter from the chapter "Closures in Drip":

```text
fn counter() {
  let n = 0;
  fn count() { n += 1; return n; }
  return count;
}
let a = counter();
print a();   # 1
```

The tree-walker kept `n` in a heap environment that `count` referred
to. The VM has no environments: `n` is a
**stack slot** (the chapter "Locals as stack slots"), and `return` cuts
the stack back to the frame's start, so the very next call writes over
it (the chapter "Frames: calling and returning in the VM"). So `count`
cannot remember `n`'s slot: by the time `a()` runs, that slot is
someone else's.

## A ticket instead of a slot

What `count` needs is a small object of its own that knows where `n`
is right now.

<Analogy title="a cloakroom ticket">
At a party you hand in your coat and get a numbered ticket; you carry
the small ticket, not the coat, and the ticket leads to the coat
wherever it happens to be.
<span slot="breaks">A cloakroom gives each guest their own ticket; two
closures that need one variable get the *same* ticket, so a change made
through one is seen through the other.</span>
</Analogy>

<Analogy extra title="a link to a shared document">
Two colleagues who each print a report hold two copies, and a correction
on one never reaches the other; two who each hold a link to one online
document see every edit at once, because there is only one document.
<span slot="breaks">A link points at one server for ever; what an
upvalue points at can move (to the heap, next chapter), and the upvalue
follows it.</span>
</Analogy>

That object is an **upvalue** (a value from "up there", in an
enclosing function); each closure carries one per outside variable it
uses: `count` says "my upvalue 0", and the upvalue
knows where the value is. Step through the counter (its return is the next chapter's

## Finding upvalues while compiling

The compiler knows the locals of every function it is compiling, so it
can find captured variables before the program runs. When a name is not a local of the current function,
`namedVariable` tries `resolveUpvalue` before treating it as a global:

```ts
function resolveUpvalue(c, name) {
  if (!c.enclosing) return -1;
  const local =
    resolveLocal(c.enclosing, name);
  if (local !== -1) {
    c.enclosing.locals[local]
      .isCaptured = true;
    return addUpvalue(c, local, true, name);
  }
  const up =
    resolveUpvalue(c.enclosing, name);
  if (up !== -1)
    return addUpvalue(c, up, false, name);
  return -1;
}
```

(Types left out.) If the name is a local of the function *directly* around this one, the
upvalue captures its slot (`isLocal` is `true`) and marks it
`isCaptured`, for the next chapter. Otherwise it asks one level further
out, by calling itself; if an outer function has the variable, the
enclosing function gets an upvalue of its own, and this one copies
*that* (`isLocal` is `false`). `addUpvalue` adds `{ index, isLocal }`
to the list unless it is already there, and returns its position.

When the function is finished, `fnRest` writes the list into the
bytecode as pairs of bytes after `closure`, and the disassembler prints
each pair on a line of its own:

```text
== counter ==
0000    2 const               0 '0'
0003    3 closure             1 fn count
0006    |   local 1
== count ==
0000    3 load.upvalue        0
0002    | const               0 '1'
0005    | add
0006    | store.upvalue       0
```

`local 1` means "capture slot 1 of the running frame", which is `n`;
inside `count`, `n += 1` takes the four steps a local would, with
"upvalue 0" in place of a slot number.

<Examples of="upvalue">

```text
fn adder(k) {
  return fn (x) { return x + k; };
}
print adder(2)(5);   # 7
```

```text
fn outer() {
  let x = 1;
  fn middle() {
    fn inner() { return x; }
    return inner;
  }
  return middle;
}
```

```text
== outer ==
0003    6 closure             1 fn middle
0006    |   local 1
== middle ==
0000    4 closure             0 fn inner
0003    |   upvalue 0
```

</Examples>

In the first, the anonymous function uses `adder`'s parameter `k`
(slot 1), so it gets the pair `local 1`, and `x + k` compiles to
`load.local 1` (its own) and `load.upvalue 0` (borrowed). In the second only `inner` uses `x`, but `inner` is made after
`outer` may have returned, so `middle` must carry `x` for it; the third
shows how: `outer` gives `middle` the pair `local 1`, and `middle` gives
`inner` the pair `upvalue 0` ("copy my own upvalue 0"), although its own
body never mentions `x`.

<Callout kind="definition">
An **upvalue** is a closure's handle on a variable declared in an
enclosing function. The compiler resolves upvalues while compiling and
emits one `(isLocal, index)` pair per upvalue after `closure`: when
`isLocal` is true, capture slot `index` of the running frame; when it is
false, reuse upvalue `index` of the running closure. The body reaches
them with `load.upvalue` and `store.upvalue`.
</Callout>

<Formal title="Where a name resolves">

```text
resolve(f, x) =
  local i     if x is local i of f
  upvalue j   if resolve(parent(f), x) is
              local i or upvalue i, and
              j = add(f, that pair)
  global x    otherwise
```

<span slot="read">If x is f's local number i, it is that local.
Otherwise ask the function around f; if it answers with a local or an
upvalue numbered i, that pair becomes f's upvalue j (added, or found
already there). If no function has x, it is a global.</span>
</Formal>

## Open: pointing into the stack

At run time the `closure` instruction makes the closure, pushes it, and
then reads the pairs:

```ts
for (let i = 0;
     i < closure.upvalues.length; i++) {
  const isLocal = readByte();
  const index = readByte();
  closure.upvalues[i] = isLocal
    ? this.captureUpvalue(
        frame.slots + index)
    : frame.closure.upvalues[index];
}
```

`frame.slots + index` turns "slot 1 of this frame" into a position in
the stack array; a non-local pair copies the running closure's
upvalue. An upvalue (`ObjUpvalue`) has three fields:
`slot`, `closed` and `nextOpen`. While `counter` is still running, `n`
really is in its slot, so the upvalue records that slot and
`load.upvalue` reads `stack[u.slot]`; an upvalue in this state is
**open**.

Two closures made in one call must share `n`, so the VM keeps every
open upvalue on one linked list, `openUpvalues`, sorted by slot with the
highest first, and `captureUpvalue` looks there before it makes a new
one. The stepper shows its body, exactly as in `vm.ts`: the loop walks
past every upvalue for a higher slot, remembering the one before
(`prev`); if it stops on one for exactly this slot, that one is shared;
otherwise a new upvalue is linked in at that spot, which keeps the list
sorted without ever sorting it.

<Examples of="open-upvalue">

```text
fn outer() {
  let x = 1;
  fn show() { print x; }
  x = 2;
  show();   # 2
}
```

<Run id="share" />

```text
0012    |   local 3
0014    |   local 1
0016    |   local 2
```

</Examples>

In the first, `show` runs while `outer` is still running, so its
upvalue is open: `x = 2` is a plain `store.local 1`, and `show` reads
that slot and prints `2`. In the
runnable one, `get` and `set` both have the pair `local 1`, so they
share one upvalue, and `set` changes what `get` sees. The third is the
pairs of `fn g() { return c + a + b; }`, over locals in slots 1, 2 and
3: they follow the order of use, and each new
upvalue goes to its sorted place, as in the stepper.

<Callout kind="definition">
An **open upvalue** is an upvalue whose variable is still on the stack:
its `slot` is the variable's stack index, and reads and writes go
straight to `stack[slot]`. The VM keeps open upvalues on one list,
sorted by slot, highest first, and a second capture of the same slot
reuses the open upvalue, so closures share one variable.
</Callout>

## What you learned

- A slot is reused once its call returns, so a closure reaches an
  outside variable through an **upvalue**.
- The compiler writes one pair per upvalue after `closure`: `local i`
  captures slot `i` of the running frame; `upvalue i` reuses the
  running closure's upvalue `i`, passing a variable down.
- An **open upvalue** points at a live stack slot; open upvalues sit on
  one sorted list, and a second capture of a slot shares the first.
