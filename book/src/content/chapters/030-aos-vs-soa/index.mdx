## Same data, four ways

For three chapters you’ve heard that layout matters. Now we measure it.
This book’s repository has a benchmark harness that stores the same
particles (`x`, `y`, `vx`, `vy`, `mass`, `health`) in several ways and
runs the same loops over each:

```js
// aos: an array of objects
ps[i].x

// aos-packed: one Float64Array, 6 per item
f[i * 6 + 0]

// soa: one Float64Array per field
x[i]

// aosoa8: blocks of 8, SoA inside a block
f[blk * 48 + 0 * 8 + lane]
```

All four hold identical numbers. Only where those numbers sit in memory
changes.

<Callout kind="intuition">
Think of a filing cabinet of student records. AoS files one folder per
student, with every detail inside. SoA keeps one long list per detail: all
names on one list, all grades on another. To average the grades, the
lists win: you read one list top to bottom. To print one student’s full
record, the folders win: everything is in one place.
</Callout>

## What each loop actually loads

The loop we care about most is `update-xy`: `x += vx * dt` and
`y += vy * dt` for every particle. It needs four of the six fields. Step
through what each layout drags into the cache to get them:

<LayoutSteps client:visible />

<Callout kind="definition">
**AoS vs SoA** is the trade-off between keeping each record’s fields
together (array of structs) and keeping each field’s values together
(struct of arrays). AoS suits code that uses whole records; SoA suits code
that uses a few fields of many records. **AoSoA** (array of structs of
arrays) is the hybrid: fixed-size blocks of records, with SoA inside each
block.
</Callout>

<BenchBars suite="sum-one-field" n={100000} title="Summing one field (mass)" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa', 'aosoa8']} caption="One field out of six: SoA loads only what it uses." />

Notice that **packed AoS** already captures a big part of the win. It
keeps AoS order but drops the object headers, the pointers and the boxed
numbers from chapter 29. So part of SoA’s advantage is simply *typed
storage*, and part is *locality*: SoA goes further only because it also
stops loading the unused fields.

Random order is where object arrays suffer most. The `random-x` suite reads
`x` and `vx` at shuffled indexes, so the prefetcher can’t help, and
every object is a pointer to chase:

<BenchBars suite="random-x" n={1000000} title="Reading x and vx in shuffled order" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa', 'aosoa8']} caption="Without a predictable order, the pointer hop to each object dominates. AoSoA pays for its index arithmetic here." />

## The loss: materialization

Sometimes the code really does want an object. Maybe it pushes particles
into a list, or hands them to a library. With SoA there *is* no object, so
it has to be built:

```js
function get(s, i) {
  return {
    x: s.x[i], y: s.y[i],
    vx: s.vx[i], vy: s.vy[i],
  };
}
```

<Run id="materialize" />

Every call allocates a fresh object, so `get(s, 0) === get(s, 0)` is
`false`. That’s the identity problem from chapter 4: an optimizer must
never let a program notice. And it costs time. The `materialize` suite
builds an array holding one real object per element:

<BenchBars suite="materialize" n={100000} title="Building one real object per element" highlight={['soa']} layouts={['aos', 'soa', 'aosoa8']} caption="AoS just copies references it already has. SoA must allocate every object." />

<Callout kind="definition">
**Materialization** is rebuilding a whole object from its columns. It
costs an allocation per object, and the new object has a new identity.
Materializing objects that are *kept* can wipe out every gain SoA made.
</Callout>

There’s a twist. The `get-objects` suite hands each element to a small
function that wants an object, but doesn’t keep it. There, in this book’s
run, SoA did **not** lose: V8 inlined the function and removed the
temporary object altogether. Whether materializing costs anything depends
on whether the object *escapes*, which is exactly the question
Viscosity’s escape analysis must answer. A TypeScript experiment by Zap
found the same shape: SoA wins on reading a few fields and loses when
whole objects must be rebuilt<Cite id="ziap2025" />.

## Small collections and AoSoA

With only 1,000 particles, everything fits in cache, and the picture
shrinks:

<BenchBars suite="update-xy" n={1000} title="Moving 1,000 particles" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa', 'aosoa8']} caption="Small data already fits in cache: the gains shrink, and AoSoA’s index arithmetic costs more than it saves." />

AoSoA is a compromise with its own trade-offs. Inside a block, each field
is contiguous: 8 doubles is exactly one cache line, and a natural fit for
SIMD lanes. ISPC builds this into the language as `soa<8>`, keeping
ordinary `pts[i].x` syntax while storing blocks<Cite id="ispcdocs" /><Cite id="pharrmark2012" />,
and its performance guide recommends it when vector loads
matter<Cite id="ispc-perfguide" />. But every random access must work out
a block and a lane, a division and a remainder. In plain JavaScript,
without SIMD, that arithmetic is pure cost.

## Hot/cold splitting

You don’t have to move every field. If a loop touches `x`, `y`, `vx` and
`vy` every frame but `name` and `health` almost never, move just the
busy fields into columns:

```js
const hot = {
  x: new Float64Array(n),
  y: new Float64Array(n),
  vx: new Float64Array(n),
  vy: new Float64Array(n),
};
const cold = [{ name: 'a', health: 100 }];
```

<Callout kind="definition">
A **hot/cold split** separates fields that are used often (hot) from
fields that are used rarely (cold), so hot loops only stream through hot
data.
</Callout>

<Callout kind="engine" label="Under the hood">
Choosing a layout means weighing everything above: how many elements,
which fields each loop touches, whether access is sequential, and whether
objects escape. Mike Acton’s 2014 talk on data-oriented design puts it
bluntly: “If you have different data, you have a different
problem”<Cite id="acton2014" />. Research on JavaScript arrays makes this decision at run
time: a JIT watches an array of objects and switches it to columnar
storage automatically<Cite id="makor2022" />, then generates specialized
code paths for the transformed arrays<Cite id="kloibhofer2023" />.
Viscosity makes the same decision ahead of time, as a compiler pass, with
a cost model fed by exactly these measurements.
</Callout>

## What you learned

- **AoS vs SoA** is a trade-off. SoA won in this book’s run when a loop
  touched a few fields of many elements, and in shuffled access.
- **Packed AoS** captures part of the win, by dropping headers, pointers
  and boxed numbers; SoA adds locality on top.
- **Materialization** (rebuilding objects from columns) is SoA’s weakness:
  it allocates, and it creates new identities. If the object doesn’t
  escape, the engine may remove it.
- Small collections barely benefit: the data already fits in cache.
- **AoSoA** stores blocks of SoA: cache- and SIMD-friendly inside a block,
  but random access pays for index arithmetic.
- A **hot/cold split** moves only the busy fields into columns.
