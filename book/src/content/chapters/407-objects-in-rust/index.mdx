## Fields in a table

```drip
class Point {}
let p = new Point();
p.x = 3;
p.y = 4;
print p.x; # 3
print p;   # Point { x: 3, y: 4 }
```

A Drip instance is a bag of fields that you can add to at any time, and
the chapter *Objects and method calls in the VM* put that bag in the
TypeScript VM as a hash table on each instance. drip-rs does the same,
from `object.rs` (comments trimmed):

```rust
pub struct ObjClass {
    pub name: StrRef,
    pub methods: Table,
}

pub struct ObjInstance {
    pub class: Gc<ObjClass>,
    pub fields: Table,
    pub field_order: Vec<StrRef>,
}
```

The TypeScript field is called `klass`, because `class` is a reserved
word in JavaScript; in Rust `class` is not a keyword<Cite id="rustref-keywords" />,
so drip-rs uses the plain word. `Table` is the hash table from the
chapter *Strings and interning in Rust*, keyed by `StrRef`: field names
are interned strings whose handle carries the hash, so looking up `x`
never visits the string arena. And `field_order` is the names in the
order they were first set, which is how an instance prints
(`Point { x: 3, y: 4 }`); a hash table on its own has no useful order.
The table and the `Vec` are plain Rust values inside the instance,
owned by it and freed with it when sweep drops the object (the chapter
*Ownership*).

<Analogy title="a luggage tag on a notebook">
The tag says which class the instance came from. The notebook has one
line per field, and you may add a line whenever you like; its first
page lists the fields in the order you started them. Everyone holding

<span slot="breaks">A notebook's lines are in the order written; the

</Analogy>

## Making an instance

`class` allocates an `ObjClass` with its name and an empty method table,
and pushes `Value::Class(handle)`. `new Point()` compiles to loading the
class, the arguments, and `new 0`; from `Vm::new_instance` (trimmed and
rewrapped):

```rust
let Value::Class(class) =
    self.peek(arg_count)
else { /* 'new' needs a class, not ... */ };
let instance = self.alloc(ObjInstance {
    class,
    fields: Table::new(),
    field_order: Vec::new(),
});
self.set_peek(arg_count,
    Value::Instance(instance));
// ...then call init, if the class has one
```

The `let ... else` (the chapter *Patterns in depth*) opens the value
under the arguments and reports the runtime error if it is not a class.
`alloc` may collect first, and the new instance holds `class`; that is
safe because the class is still on the stack in that slot, the rule
from *A garbage collector in Rust*. Only then does `set_peek` overwrite
the slot with the instance, which is where an `init` will find `self`
(the next chapter). Calling a class without `new`, as `Point()`, is the
runtime error `cannot call a class: use 'new Point(...)'`.

## Get and set

`get.prop` checks that `peek(0)` is an instance (or it is
`cannot read 'x' of a number`), then looks the name up:
`self.heap[instance].fields.get(name)` returns an `Option<Value>`, a
copy, so the borrow of the heap ends at once and `self.set_peek(0, value)`
can replace the instance with the field. A field that is missing falls
through to the class's methods, which is the next chapter; with no
method either, it is `Point has no property 'z'`. Fields are checked
first, so a field shadows a method of the same name. `set.prop`, from
`vm.rs` (rewrapped):

```rust
let name = self.read_string();
let Value::Instance(instance) = self.peek(1)
else { /* cannot set 'x' on ... */ };
let value = self.peek(0);
let object = &mut self.heap[instance];
if object.fields.set(name, value) {
    object.field_order.push(name);
}
// Leave the value as the
// assignment's result.
self.pop();
self.set_peek(0, value);
```

`Table::set` returns `true` when the key is new, and only then does the
name join `field_order`, so overwriting `p.x` later leaves it where it
was. `object` borrows one instance mutably for both writes, and its
borrow ends before `self.pop()`.

<InstanceSteps client:visible />

Here is the spot the difference. The TypeScript arm reads its operands
as it goes; a Rust toy that does the same in one line fails (rustc 1.97,
trimmed):

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
7 | self.insts[i].fields
  | ---------- first mutable borrow
8 |     .insert(self.read_byte() as u32, v);
  |      ------ ^^^^ second mutable borrow
```

The receiver, the field table, is borrowed mutably first, and then the
argument wants `&mut self` too, to move `ip` on. drip-rs reads the name
and the value into locals before it touches the table, the same habit
as `patch_jump` in *Branches and loops in Rust*: finish reading, then
borrow to write.

<Callout kind="definition">
In drip-rs, an **instance** is an `ObjInstance` in the heap's instance
arena: a `Gc<ObjClass>` handle to its class, a **field table** (a
`Table` from interned names to values) and `field_order`, the names in
the order they were first set. `Value::Instance(handle)` refers to it.
`get.prop` reads a field with one lookup, falling back to the class's
methods; `set.prop` adds or overwrites one. Both check that the receiver
is an instance first.
</Callout>

<Formal title="Reading a property">

```text
o.n = fields(o)[n]        if n ∈ fields(o)
    = bound(o, m)         else if
      where m = methods(class(o))[n]
    = error "C has no property 'n'"
                          otherwise
```

<span slot="read">Reading the property n of an instance o gives the
field named n if o has one; otherwise, if o's class has a method named
n, it gives that method bound to o; otherwise it is the runtime error
naming the class C. The order of the lines is the rule that fields
shadow methods.</span>
</Formal>

The first, after the program at the top, overwrites `x`: `fields.set`
returns `false`, so `field_order` is unchanged and `x` still prints
first. The second stores a function in a field and calls it with
`b.f()`; the call compiles to `invoke`, which checks the fields before
the methods, so the field is found and called. The third is the shape
this whole book is about: a list of records, each updated in a loop, so
every `p.x += p.vx` is a `get.prop`, an add and a `set.prop` on an
instance in the arena.

<Callout kind="engine" label="Under the hood">
To the collector, an instance is its class and its table: `blacken`
traces `instance.class` and `instance.fields`, which marks every key and
value (the names in `field_order` are keys of the table, so they are
marked already). Its size for pacing is `size_of::<ObjInstance>()`, 88
bytes (measured with rustc 1.97 on x86-64 Linux), which leaves out the
table's and the list's buffers, so a wide instance counts for less than
it holds. In this book's benchmark run (`drip-rs-bench-2026-11-02.md`),
`instantiation` took 140 ms on drip-rs and 623 ms on the TypeScript VM,
and `fields`, which reads and writes fields in a loop, 193 ms and 712 ms.
</Callout>

## What you learned

- An **instance** is an `ObjInstance`: a class handle, a **field
  table** it owns, keyed by interned names, and the names in the order
  they were first set.
- **`new`** allocates the instance while the class is still on the
  stack, then `set_peek` puts the instance in the class's slot.
- `get.prop` **copies** the field's value out, so the heap borrow ends
  at once; fields shadow methods.
- `set.prop` **reads its operands first**, then borrows the instance:
  the TypeScript habit in one line is E0499 in Rust.
