## Two kinds of variable

Here is what `drip-rs --disassemble` prints for two locals in a block,
`{ let a = 1; let b = 2; print a + b; }` on five lines (the closing
`none`, `return` left off):

```text
0000    2 const               0 '1'
0003    3 const               1 '2'
0006    4 load.local          1
0008    | load.local          2
0010    | add
0011    | print
0012    5 pop
0013    | pop
```

The TypeScript VM prints the same bytes, as *Locals as stack slots*
built them: the locals are bare slot numbers, 1 and 2, and their names
appear nowhere, while a global is an interned name looked up in a table
every time (*String interning and globals by name*). Nothing about the
design changes in Rust. What changes is how the compiler holds on to
things while it works: a local's name, a scope's depth, and the place
in the code where a jump's distance must be written later.

<Analogy title="a hotel register and a theatre ticket">
At a hotel, reception finds you by looking your name up in the
register every time; at a theatre, your ticket says row F, seat 12, and
you walk straight there. Globals are hotel guests; locals hold theatre
tickets.
<span slot="breaks">A theatre prints its seat numbers once, for good; a
local's slot is worked out by the compiler for each function, and the
same slot is handed to a different local once a block has ended.</span>
</Analogy>

<Figure takeaway="A global costs a table probe; a local costs an addition." caption="load.global reads a constant index, finds the interned name, and probes the globals table. load.local adds its operand to the frame’s base and reads the stack.">

</Figure>

<More title="Globals: three match arms">

The VM keeps globals in `globals: Table`, a field of the `Vm` and a
garbage-collection root beside the stack. `identifier_constant(name)`
interns the name and adds it to the constant pool, without looking for
an earlier copy. Two of the three arms (rewrapped):

```rust
OpCode::DefineGlobal => {
    let name = self.read_string();
    self.globals.set(name, self.peek(0));
    self.pop();
}
OpCode::StoreGlobal => {
    let name = self.read_string();
    if self.globals
        .set(name, self.peek(0))
    {
        self.globals.delete(name);
        // "undefined variable 'm'"
    }
}
```

`set` returns `true` when the name was new, a mistake for an
assignment, so `store.global` deletes it again: `m = 1;` prints
`runtime error: undefined variable 'm'`. `load.global` gets an `Option`
from `globals.get(name)` where TypeScript got `undefined`.

</More>

## Locals: a Vec the compiler keeps

The TypeScript compiler records a `name: string`, a `depth: number`
(`-1` while the initialiser is compiled) and `isCaptured` for each
local. drip-rs records:

```rust
struct Local<'src> {
    name: &'src str,
    depth: Option<usize>,
    is_captured: bool,
}
```

`name` is a slice of the source, borrowed for `'src`, so no name is
copied; `depth` is `None` where TypeScript used `-1`, so the compiler
cannot forget to check, because there is no number to compare until the
`Option` is opened<Cite id="rust-std-option" />. A local's index in the
`Vec` is its stack slot, and resolving a name searches from the end, so
the innermost variable with that name wins (rewrapped, the error
shortened):

```rust
let (slot, local) = locals.iter()
    .enumerate().rev()
    .find(|(_, l)|
        l.name == name.lexeme)?;
if local.depth.is_none() {
    // "cannot read 'a' in its own
    // initialiser"
}
Some(slot)
```

The `?` returns `None` when no local has the name, and the compiler then
tries a captured variable, and finally a global. Step through two nested
blocks being compiled:

<LocalsSteps client:visible />

<Callout kind="definition">
**Compile-time locals in drip-rs** are a `Vec<Local>` in each
`FunctionState`. A local's index in that `Vec` is its stack slot (slot
0 is reserved for the function being run, or `self` in a method). Each
`Local` holds its name as a `&str` into the source, its scope depth as
`Option<usize>` (`None` until initialised), and whether a closure
captures it. Declaring a local emits nothing: its initialiser's value is
already in the right slot.
</Callout>

<Formal title="Which slot a name means">

```text
slot(x) = max { i | locals[i].name = x }
```

<span slot="read">The slot of a name x is the largest index i whose
local is called x: the most recently declared, innermost one. If no
local is called x, there is no slot, and x is looked for further
out.</span>
</Formal>

<Examples of="rust-locals">

```drip
let a = 1;
{
  let a = a + 1;
}
# line 3: cannot read 'a' in its own
#   initialiser
```

</Examples>

This surprises people. The inner `a` is declared, with depth `None`,
before its initialiser is compiled, so the search from the end finds
the unfinished inner `a` first, not the global, and drip-rs reports a
compile error (exit 65) just as the TypeScript VM does; `let b = a + 1;`
would work.

Ending a scope pops the locals deeper than the scope, emitting `pop` or
`close.upvalue` for each. The TypeScript `endScope` keeps the current
function in a local and emits while it loops. In Rust, keeping
`let state = self.state();` across `self.emit_op(...)` fails with
E0499, `cannot borrow *self as mutable more than once at a time`:
`state` is a `&mut` into `self.functions`, and `emit_op` needs all of
`self`. So drip-rs reads the one fact it needs (`is_captured` of the
last local), pops, lets `state` go, and only then emits.

<More title="end_scope in full, and a duplicate declaration">

From `compiler.rs` (rewrapped, comments left out):

```rust
loop {
    let state = self.state();
    let depth = state.scope_depth;
    let captured =
        match state.locals.last() {
        Some(local) if local.depth
            .is_some_and(|d| d > depth) => {
            local.is_captured
        }
        _ => break,
    };
    state.locals.pop();
    self.emit_op(if captured {
        OpCode::CloseUpvalue
    } else { OpCode::Pop });
}
```

`declare_variable` has the same habit: it first computes a plain `bool`
with `state.locals.iter().rev().take_while(..).any(..)`, and only then
reports `line 3: 'a' is already declared in this scope` for two `let a`
in one block. At run time none of this is left: `load.local` adds
`self.slots` to its operand and reads the stack.

## A hole in the code, remembered as a number

For `let i = 0; while i < 3 { print i; i += 1; }`, drip-rs emits (columns
narrowed):

```text
0013    | jump.unless    13 -> 34
0016    3 load.global     4 'i'
  ... the body ...
0031    5 loop           31 -> 6
0034    | none
```

When the compiler writes the `jump.unless`, the body is not compiled
yet, so nobody knows the loop ends at 34; *Jumps: branches, loops and
backpatching* wrote a placeholder, remembered where, and filled it in
later. drip-rs does the same, and Rust decides two details: what the
"remember where" may be, and the order the patch works in (from
`compiler.rs`, signatures rewrapped):

```rust
fn emit_jump(&mut self, op: OpCode)
    -> usize {
    self.emit_op(op);
    self.emit(0xff);
    self.emit(0xff);
    self.chunk().code.len() - 2
}

fn patch_jump(&mut self, offset: usize) {
    let jump = self.chunk().code.len()
        - offset - 2;
    if jump > u16::MAX as usize {
        self.static_error(self.previous,
            "too much code to jump over");
    }
    let code = &mut self.chunk().code;
    code[offset] = (jump >> 8) as u8;
    code[offset + 1] = jump as u8;
}
```

`emit_jump` returns where its first placeholder byte is, as a `usize`.
The caller keeps it in a local, and a number borrows nothing; a
`&mut u8` into the code would lock the chunk until the patch, and the
body could not be compiled. `patch_jump` measures from the end of the
operand (`offset + 2`, where the VM's `ip` will stand) to the end of the
code, reports a distance that does not fit in a `u16` as a static
error, and writes it high byte first, since the VM's `read_short`
rebuilds `(high << 8) | low`; `jump as u8` keeps the low 8 bits, as
TypeScript's `& 0xff` did<Cite id="rustref-numeric-cast" />.

The order of the middle lines matters. Take `code` first and report
afterwards, and rustc 1.97 refuses with E0499 again: `code` reaches into
`self` through `chunk()`, and `static_error` needs `&mut self` to push
its message. So drip-rs reports first, while nothing is borrowed, and
only then takes hold of the code, the read-first habit of *A Pratt
compiler in Rust*. Step through the loop being compiled:

<JumpSteps client:visible />

<Callout kind="definition">
**Backpatching a jump in drip-rs**: `emit_jump` writes the opcode and
two placeholder bytes and returns their position as a `usize`, which the
caller keeps while the skipped code compiles. `patch_jump(offset)` then
works out the distance from the end of the operand to the end of the
code, reports a static error if it does not fit in 16 bits, and only
then borrows the code to write the two bytes, high byte first.
</Callout>

<Figure caption="Both jumps are measured from the byte after their operand, where the VM stands when it adds or subtracts." takeaway="Forward: len minus (at + 2). Backward: (len + 2) minus the start.">
  <JumpMath />
</Figure>

<Formal title="Where a jump lands">

```text
forward:  jump = len − (at + 2)
          (at + 2) + jump = len
backward: offset = (len₁ + 2) − start
          (len₁ + 2) − offset = start
```

<span slot="read">For a forward jump whose operand starts at "at", the
distance is the code's length minus the place just after the operand, so
when the VM, standing there, adds it, it arrives at the first
instruction after the skipped code. For a loop, len₁ is the length just
after the loop opcode; the VM stands two bytes further on, and
subtracting the offset takes it back to the start.</span>
</Formal>

<Examples of="patch-jump">

```text
if x > 3 { ... } else { ... }
0013    | jump.unless    13 -> 23
0016    3 const           4 'big'
0020    4 jump           20 -> 27
0023    5 const           5 'small'
```

</Examples>

An `if` with an `else` has two holes open at once. The `jump.unless`
whose operand is at 14 is patched when the `else` is reached, with the
code 23 bytes long: 23 − 14 − 2 = 7, stored as `00 07`, and the VM,
standing at 16, lands on 23. The `jump` at 20, which skips the
else-branch, is patched after it, to 27.

<More title="Loops, break and continue">

A loop's last jump goes back to code already compiled, so it needs no
hole: `emit_loop(loop_start)` emits `loop`, then the offset
`code.len() - loop_start + 2`, where the `+ 2` counts its own operand,
not yet written. In the listing, after the `loop` opcode at 31 the
length is 32, so the offset is 32 − 6 + 2 = 28, and the VM, at 34 after
the operand, lands on 34 − 28 = 6. Each `break` emits a `jump` and pushes
its `usize` onto the loop's `breaks`, patched once the loop is done. A
`continue` in a `while` jumps back with `emit_loop`
(`continue_target: Some(loop_start)`); in a `for` it must skip forwards
past the body, so the target is `None` and its jumps wait on a list, an
`Option` doing the job TypeScript gave to `-1`. In the VM, `Loop` does
`self.ip -= offset`, `usize` arithmetic: a bad offset would panic in a
debug build and wrap in a release build<Cite id="rustref-int-overflow" />,
and the next read, `self.chunk.code[self.ip]`, is bounds-checked either
way, so a compiler bug is a clean panic, not nonsense output.
