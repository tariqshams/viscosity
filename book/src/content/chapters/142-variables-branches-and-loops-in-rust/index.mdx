## Two kinds of variable

Here is what drip-rs's disassembler prints for a global, the program
`let n = 1; n = n + 1; print n;` written on three lines:

```text
0000    1 const               0 '1'
0003    | define.global       1 'n'
0006    2 load.global         3 'n'
0009    | const               4 '1'
0012    | add
0013    | store.global        2 'n'
0016    | pop
0017    3 load.global         5 'n'
0020    | print
```

and for two locals in a block, `{ let a = 1; let b = 2; print a + b; }`
on five lines:

```text
0000    2 const               0 '1'
0003    3 const               1 '2'
0006    4 load.local          1
0008    | load.local          2
0010    | add
0011    | print
0012    5 pop
0013    | pop
```

(Each listing's closing `none`, `return` is left off.) The TypeScript
VM prints both byte for byte the same, as *Globals by name* and *Locals
as stack slots* built them. The global is looked up by its name every
time; the locals are bare slot numbers, 1 and 2, and their names appear
nowhere.

<Analogy title="a hotel register and a theatre ticket">
At a hotel, reception finds you by looking your name up in the
register every time; at a theatre, your ticket says row F, seat 12, and
you walk straight there. Globals are hotel guests; locals hold theatre
tickets.
<span slot="breaks">A theatre prints its seat numbers once, for good; a
local's slot is worked out by the compiler for each function, and the
same slot is handed to a different local once a block has ended.</span>
</Analogy>

## Globals: names in a table

A global's name goes into the constant pool as an interned string; in
`src/compiler.rs`, `identifier_constant(name)` is two lines,
`let s = self.intern(name);` and
`self.make_constant(Value::String(s))`. It does not look for an earlier
copy, which is why the first listing has four constants that are all
`'n'` (the same `StrRef` four times). The VM keeps the globals in
`globals: Table`, a field of the `Vm`, and three arms of the dispatch
loop use it (rewrapped, comments left out):

```rust
OpCode::DefineGlobal => {
    let name = self.read_string();
    self.globals.set(name, self.peek(0));
    self.pop();
}
OpCode::StoreGlobal => {
    let name = self.read_string();
    if self.globals
        .set(name, self.peek(0))
    {
        self.globals.delete(name);
        // "undefined variable 'm'"
    }
}
```

`define.global` overwrites happily, which is why a second `let` of the
same global is allowed. `store.global` uses `set`'s return value: `true`
means the name was new, a mistake for an assignment, so it deletes the
entry again and reports `undefined variable 'm'`. `load.global` gets an
`Option` from `self.globals.get(name)` where TypeScript got `undefined`.
The globals table is also a garbage-collection root, beside the stack.

## Locals: a Vec the compiler keeps

Locals never reach a table: the compiler works out each one's stack
slot while it compiles, so at run time a local is an index. The
TypeScript compiler records a `name: string`, a `depth: number` (with
`-1` while the initialiser is compiled) and `isCaptured` for each local;
drip-rs records:

```rust
struct Local<'src> {
    name: &'src str,
    depth: Option<usize>,
    is_captured: bool,
}
```

`name` is a slice of the source, borrowed for `'src` (*A Pratt
compiler in Rust, part 2*), so no name is copied; and `depth` is `None`
where TypeScript used `-1`, so the compiler cannot forget to check,
because there is no number to compare until the `Option` is
opened<Cite id="rust-std-option" />.

<Analogy extra title="a seating plan drawn before the lesson">
A teacher draws a seating plan before class, one name per desk; during
the lesson she just says "desk two, please", and the plan goes in the
bin when term ends.
<span slot="breaks">Pupils move desks when they like; a local's slot
never changes while its block runs, and the compiler's plan is thrown
away when the function is finished, not at the end of term.</span>
</Analogy>

Resolving a name searches the locals from the end, so the innermost
variable with that name, the one that shadows the others, wins (from
`compiler.rs`, rewrapped, the message's `format!` shortened):

```rust
fn resolve_local(&mut self, level: usize,
    name: Token<'src>) -> Option<usize> {
    let locals =
        &self.functions[level].locals;
    let (slot, local) = locals.iter()
        .enumerate().rev()
        .find(|(_, l)|
            l.name == name.lexeme)?;
    if local.depth.is_none() {
        // static error: "cannot read 'a'
        // in its own initialiser"
    }
    Some(slot)
}
```

The `?` (from *Option and Result*) returns `None` when no local has
the name, and `named_variable`
then tries a captured variable, and finally a global. Reporting the
error needs `&mut self`, which is allowed because `local` is not used
after `is_none()`: the borrow of `self.functions` has already ended.

<Callout kind="definition">
**Compile-time locals in drip-rs** are a `Vec<Local>` in each
`FunctionState`. A local's index in that `Vec` is its stack slot (slot
0 is reserved for the function being run, or `self` in a method). Each
`Local` holds its name as a `&str` into the source, its scope depth as
`Option<usize>` (`None` until initialised), and whether a closure
captures it. Declaring a local emits nothing: its initialiser's value is
already in the right slot.
</Callout>

<Formal title="Which slot a name means">

```text
slot(x) = max { i | locals[i].name = x }
```

<span slot="read">The slot of a name x is the largest index i whose
local is called x: the most recently declared, innermost one. If no
local is called x, there is no slot, and x is looked for further
out.</span>
</Formal>

## Hold the function, lose the compiler

The TypeScript `endScope` keeps the current function in a local and
emits while it loops. Written that way in Rust, keeping
`let state = self.state();` across a call to `self.emit_op(...)`, rustc
1.97 refuses with E0499, "cannot borrow `*self` as mutable more than
once at a time": `state` is a `&mut` into `self.functions`, used
again after the call, and `emit_op` needs all of `self`. drip-rs reads
the one fact it needs, pops, and lets `state` go before it emits (from
`compiler.rs`, rewrapped, comments left out):

```rust
loop {
    let state = self.state();
    let depth = state.scope_depth;
    let captured =
        match state.locals.last() {
        Some(local) if local.depth
            .is_some_and(|d| d > depth) => {
            local.is_captured
        }
        _ => break,
    };
    state.locals.pop();
    self.emit_op(if captured {
        OpCode::CloseUpvalue
    } else { OpCode::Pop });
}
```

`declare_variable` has the same habit: it first computes
`let duplicate = state.locals.iter().rev().take_while(..).any(..);`, a
plain `bool`, and only then reports `'a' is already declared in this
scope`.


The first breaks a static rule: `declare_variable` finds an `a` at the
same depth, and nothing runs (exit code 65); at the top level it would
be fine, as a second `let` of a global replaces it. The second surprises
people: the inner `a` is declared (depth `None`) before its initialiser
is compiled, so `a + 1` finds the unfinished inner `a`, not the global;
`let b = a + 1;` works. The third mixes globals and locals.

<Prompts ids={['rl-end-scope', 'rl-declare']} />

<Callout kind="engine" label="Under the hood">
At run time none of this is left. `load.local` adds the frame's base,
`self.slots`, to its operand and reads `self.stack` there: one addition
and one indexed read. `load.global` hashes nothing (the `StrRef` brings
its hash), but it still probes a table. The `Vec<Local>` is dropped with
its `FunctionState` when the function is finished, so local names never
reach the heap at all.
</Callout>

## What you learned

- A **global** is an interned name in the constant pool and an entry in
  the VM's `globals` table; `store.global` on a new name deletes it
  again and reports `undefined variable`.
- **Compile-time locals** are a `Vec<Local<'src>>`: the index is the
  stack slot, the name borrows the source, and `depth: Option<usize>`
  replaces TypeScript's `-1`.
- `resolve_local` searches from the end and uses `?` to fall through to
  captured variables and globals.
- Don't hold `self.state()` across a call that needs `&mut self`: read
  what you need into a local, finish with the borrow, then **emit or
  report** (E0499 otherwise).

## A blank in the middle of the code

Here is the bytecode drip-rs makes for the loop
`let i = 0; while i < 3 { print i; i += 1; }`, from `drip-rs
--disassemble` with the columns narrowed to fit (the TypeScript VM
prints the same bytes):

```text
0006    2 load.global     2 'i'
0009    | const           3 '3'
0012    | lt
0013    | jump.unless    13 -> 34
0016    3 load.global     4 'i'
  ... the body ...
0031    5 loop           31 -> 6
0034    | none
```

The `jump.unless` at 13 says "if the condition is false, skip to 34";
however, when the compiler writes that instruction, the body has not
been compiled yet, so nobody knows that the loop ends at 34. The
chapter *Backpatching: if, for, break and continue* solved this in
TypeScript: write a placeholder, remember where it is, and fill it in
later. drip-rs does the same; Rust changes two details, which are what
the "remember where" note may be, and the order the patch works in.

<Analogy title="a coat-check ticket">
You hand your coat over and get a numbered ticket, so your hands are
free all evening, and the number finds the coat when you come back.
Holding the coat yourself would also "remember" it, but you could carry
nothing else. A `usize` offset is the ticket; a `&mut` reference into
the code would be holding the coat, and the borrow checker would not let
the compiler touch the chunk again until it let go.
<span slot="breaks">A cloakroom never moves your coat to a different
hook; an offset into a `Vec` only stays right because the compiler
always appends to the code and never removes bytes from the middle.</span>
</Analogy>

<Analogy extra title="“see page __” in a report">
Writing a report, you type "the results are on page __" before the
results exist, and fill in the number once you know it. The blank is as
wide as the number will be, so filling it in never moves the rest of
the page.
<span slot="breaks">A page number can grow to three digits if it needs
to; the blank in a jump is always two bytes, so a jump of more than
65,535 bytes cannot be written at all, and drip-rs reports it as an
error instead.</span>
</Analogy>

## Leaving the hole

From `compiler.rs` (the signature rewrapped to fit):

```rust
fn emit_jump(&mut self, op: OpCode)
    -> usize {
    self.emit_op(op);
    self.emit(0xff);
    self.emit(0xff);
    self.chunk().code.len() - 2
}
```

The first three lines write the opcode and two placeholder bytes. The
last line is the function's value (no `return` needed, as *Functions
and expressions* showed): the length minus two, which is the position
of the first placeholder. TypeScript's `emitJump` returned a `number`;
this returns a `usize`, Rust's type for positions in a `Vec`. The caller
keeps it in a local (`let exit_jump = self.emit_jump(...)`), and a plain
number borrows nothing, so the whole body can be compiled before the
compiler comes back.

## Filling it in

```rust
fn patch_jump(&mut self, offset: usize) {
    let jump = self.chunk().code.len()
        - offset - 2;
    if jump > u16::MAX as usize {
        self.static_error(self.previous,
            "too much code to jump over");
    }
    let code = &mut self.chunk().code;
    code[offset] = (jump >> 8) as u8;
    code[offset + 1] = jump as u8;
}
```

Line by line: `jump` is the distance from the end of the operand
(`offset + 2`, where the VM's `ip` will be) to the end of the code,
where the next instruction will go. If it does not fit in a `u16`, it
is a **static error** (one drip-rs prints only when there are no syntax
errors; it is pushed onto a `Vec` and compiling carries on). Then `code` borrows the bytes
once, for both writes: `(jump >> 8) as u8` is the high byte, and
`jump as u8` keeps only the low 8 bits, which is what TypeScript's
`& 0xff` did<Cite id="rustref-numeric-cast" />. The high byte goes first
because the VM's `read_short`, from the chapter *The VM loop in Rust*,
rebuilds the number as `(high << 8) | low`.

The order of the middle lines matters. Here is the spot the difference:
in a small copy of `patch_jump`, take `code` first and report
afterwards, and rustc 1.97 refuses (trimmed):

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
7  | let code = &mut self.chunk().code;
   |                 ---- first borrow
10 |     self.static_error("too much...");
   |     ^^^^ second mutable borrow
12 | code[offset] = (jump >> 8) as u8;
   | ---- first borrow later used here
```

`code` reaches into `self` through `chunk()`, and `static_error` takes
`&mut self` to push its message. Rust's rule from the chapter
*Borrowing* (one `&mut` at a time) forbids both being alive at once, so
drip-rs reports first, while nothing is borrowed, and only then takes
hold of the code. It is the read-first habit from *A Pratt compiler in
Rust, part 2*: finish everything that needs all of `self` before
borrowing a piece of it.

<Callout kind="definition">
**Backpatching a jump in drip-rs**: `emit_jump` writes the opcode and
two placeholder bytes and returns their position as a `usize`, which the
caller keeps while the skipped code compiles. `patch_jump(offset)` then
works out the distance from the end of the operand to the end of the
code, reports a static error if it does not fit in 16 bits, and only
then borrows the code to write the two bytes, high byte first.
</Callout>

<Formal title="Where a jump lands">

```text
forward:  jump = len − (at + 2)
          (at + 2) + jump = len
backward: offset = (len₁ + 2) − start
          (len₁ + 2) − offset = start
```

<span slot="read">For a forward jump whose operand starts at "at", the
distance is the code's length minus the place just after the operand, so
when the VM, standing there, adds it, it arrives at the first
instruction after the skipped code. For a loop, len₁ is the length just
after the loop opcode; the VM stands two bytes further on, and
subtracting the offset takes it back to the start.</span>
</Formal>

## Loops, and the jumps that go back

A loop's last jump goes backwards, to a place already compiled, so it
needs no hole (rewrapped):

```rust
fn emit_loop(&mut self, loop_start: usize) {
    self.emit_op(OpCode::Loop);
    let offset = self.chunk().code.len()
        - loop_start + 2;
    if offset > u16::MAX as usize {
        self.static_error(self.previous,
            "loop body too large");
    }
    let line = self.previous.line;
    self.emit_short_at(line, offset);
}
```

The `+ 2` counts the two operand bytes not yet written: in the listing, `loop` is at 31, so after the opcode the length is 32, the
offset is 32 − 6 + 2 = 28, and the VM, with `ip` at 34 after the operand,
lands on 34 − 28 = 6. On the VM side each jump is a three-line arm of
the `match` in `vm.rs`: `Jump` reads the offset with `read_short` and
does `self.ip += offset`, `JumpUnless` does the same only if the value
it pops is falsey (so neither path needs a `pop` afterwards), and
`Loop` does `self.ip -= offset`. The variants that `&&` and `||` use,
`jump.unless.keep` and `jump.if.keep`, only peek, because the value they
jump with is the expression's answer.

<Examples of="patch-jump">

```rust
// a jump over nothing at all
let at = c.emit_jump(OpCode::Jump);
c.patch_jump(at); // operand 00 00
```

```text
if x > 3 { ... } else { ... }
0013    | jump.unless    13 -> 23
0016    3 const           4 'big'
0020    4 jump           20 -> 27
0023    5 const           5 'small'
```

```rust
// break, in while_statement
let lp = self.state().loops.pop()
    .expect("a loop");
for b in lp.breaks {
    self.patch_jump(b);
}
```

</Examples>

The first is the smallest case: patched at once, the distance is
`len − (at + 2) = 0`, so it lands on the very next instruction. The
second, an `if` with an `else`, has two holes open at once: the
`jump.unless` at 13 is patched (to 23) when the `else` is reached, and
the `jump` at 20, which skips the else-branch, after it (to 27). The
third is `break`: each one emits a `jump` and pushes its `usize` onto
the loop's `breaks`, and `while_statement` patches them all once the
loop is finished. A `continue`
in a `while` needs no hole, since it jumps back with `emit_loop`; the
loop records that as `continue_target: Some(loop_start)`. In a `for`,
`continue` must skip forwards past the body, so the target is `None`
there and its jumps go on a `continues` list instead, an `Option` doing
the job TypeScript gave to `-1`.

<Callout kind="engine" label="Under the hood">
`self.ip -= offset` is `usize` arithmetic: if a bad offset took `ip`
below zero, a debug build would panic on the overflow and a release
build would wrap around to a huge number<Cite id="rustref-int-overflow" />.
Neither reads the wrong memory, because the next byte is read with
`self.chunk.code[self.ip]`, and indexing a `Vec` out of bounds panics;
a compiler bug shows up as a clean panic, not as nonsense output.
</Callout>

## What you learned

- **`emit_jump`** writes the opcode and `0xff 0xff` and returns the
  operand's position as a `usize`, a number that borrows nothing.
- **`patch_jump`** works out `len − offset − 2`, checks it fits in a
  `u16`, and writes it high byte first with `as u8`.
- **Report before you borrow**: `static_error` needs all of `self`.
- **`emit_loop`** adds 2 for its own operand; `break` jumps wait in a
  `Vec<usize>` until the loop ends.
