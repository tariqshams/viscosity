## A long pause, cut up

The Drip collector stops the program, marks everything, sweeps and
carries on. Marking costs time in proportion to the live data, so on a
heap of a few gigabytes one stop can last long enough to drop frames
in an animation or time out a request. Generations make the *common*
collection short, but the old generation must still be marked
sometime. There are two ways to stop that from being one long pause,
and V8's post on its collector names them
precisely<Cite id="v8-trash-talk" />:

- **Incremental**: the program's own thread does a small slice of
  marking now and then, and runs the program in between. The total
  work is the same (a little more, in fact), but it is spread out.
- **Concurrent**: other threads mark while the program's thread keeps
  running, all the time.

(**Parallel** is a third word, and a different thing: several threads
share the work while the program is stopped. It shortens a pause but
does not remove it.)

<Analogy title="painting a shop while it stays open">
Closing a shop for a day to repaint it is simple. Repainting one wall
each evening, or having a painter work in the stockroom while
customers shop, keeps it open; however, customers now move the shelves
while the painter works, and the painter must be told.
<span slot="breaks">A customer moving a shelf is easy to spot. A
program moving a pointer is invisible to the marker unless the program
itself reports it, through a barrier, on every store.</span>
</Analogy>

<Analogy extra title="counting a crowd that keeps moving">
Counting people at a festival is easy if everyone freezes; it is still
possible while they wander, as long as anyone who crosses from an
uncounted field into a counted one is stopped at the gate and counted.
<span slot="breaks">People do not appear out of nothing; a program
allocates new objects all through marking, and the collector must
decide what colour they are born.</span>
</Analogy>

<Callout kind="definition">
An **incremental** collector interleaves short slices of collection
work with the program's own work on the same thread. A **concurrent**
collector does collection work on other threads at the same time as the
program runs. Both let the program (the **mutator**, in collector
language: the code that changes the object graph) run while marking is
unfinished, so both need a barrier to keep marking correct.
</Callout>

## How a live object gets lost

Step back through the runnable example, or the stepper in the chapter
"Mark-compact and the write barrier", and look at what the program had
to do to hide C. Two things, both of them:

1. it stored a pointer to the white object C into a black object A,
   which the marker will never scan again; **and**
2. it destroyed every path to C that started at a grey object (B's
   pointer), so the marker could not find C another way.

Either alone is harmless: without the first, C is unreachable and
freeing it is right; without the second, the marker still reaches C
through B. So a barrier only has to break *one* of the two, and the two
classic barriers are exactly the two choices.

<Formal title="Two invariants">

```text
strong: black(a) ∧ a → b  ⇒  ¬white(b)
weak:   black(a) ∧ a → b ∧ white(b)
        ⇒ some grey g ⇝ b through whites
```

<span slot="read">The strong invariant: a black object never points
directly at a white one. The weak invariant allows that, but only if
the white object can still be reached from some grey object, along a
path of white objects. Either is enough for "nothing grey left" to mean
"every white object is garbage".</span>
</Formal>

**Dijkstra's barrier** breaks the first condition. Edsger Dijkstra,
Leslie Lamport and three colleagues described in 1978 a collector that
runs on its own processor beside the program<Cite id="dijkstra1978" />;
its barrier shades (makes grey) the object whose pointer a store
writes into a field, so a black
object can never come to point at a white one. This is the **strong**
invariant, and it is V8's: its post calls its barrier "Dijkstra-style"
and the invariant "the strong tri-color invariant"<Cite id="v8-concurrent-marking" />.
It is also called an **insertion** or **incremental update** barrier,
since it reacts to the pointer being inserted.

## Snapshot at the beginning

**Yuasa's barrier** breaks the second condition instead. Taiichi
Yuasa's 1990 collector, for ordinary machines with no special hardware,
shades the value a store is about to *overwrite*<Cite id="yuasa1990" />.
Then no pointer can vanish from the graph without its target being
shaded first, so every object that was reachable when marking began
stays findable. The collector marks a **snapshot** of the graph as it
was at the start; anything that dies during marking is kept until next
time (**floating garbage**), and objects allocated during marking are
made black, since they were not in the snapshot and cannot be garbage
yet.

<Analogy extra title="a photograph of the guests">
At the start of the evening you photograph every guest, and nobody in
the photo is asked to leave until the evening ends, even if they go
home early. Anyone arriving later is let in without question.
<span slot="breaks">A photograph is taken in an instant. The
collector cannot copy the whole graph at once; it gets the same
effect lazily, by saving each old pointer at the moment it is about to
be overwritten.</span>
</Analogy>

<SatbSteps client:visible />

<Callout kind="definition">
A **snapshot-at-the-beginning** (SATB) collector marks every object
that was reachable when marking started. Its **deletion barrier**
(Yuasa's) shades the old value of a pointer field before the field is
overwritten, which keeps the weak invariant; objects allocated during
marking are black. The cost is **floating garbage**: objects that die
during marking survive until the next cycle.
</Callout>

<Formal title="What SATB guarantees">

```text
Live(t₀) ⊆ Marked(t_end)
```

<span slot="read">Every object live at the start time t₀ is marked by
the time marking ends. Objects that became garbage in between may be
marked too: the guarantee is "at least the snapshot", not
"exactly the live objects at the end".</span>
</Formal>

<Examples of="snapshot-at-the-beginning">

```text
writePointer(slot, ptr):   // Go
  shade(*slot)
  if current stack is grey:
    shade(ptr)
  *slot = ptr
```

```cpp
// G1, before a reference store
// (write_ref_field_pre): enqueue the
// field's old value on the SATB queue
```

```text
let x = [1];   # live at t₀
x = none;      # dies during marking
# SATB: [1] is marked anyway
```

</Examples>

The first is Go's barrier, from the comment in its runtime's
`mbarrier.go`: a "hybrid barrier that combines a Yuasa-style deletion
barrier" with a Dijkstra insertion barrier, where the insertion half
is needed only while the current goroutine's stack is still grey; Go
also marks new objects black<Cite id="go-runtime-gc" />. The second is
OpenJDK 21's G1, whose pre-barrier puts the field's old value on a
per-thread SATB queue while marking is active<Cite id="hotspot-card-table" />.
The third is floating garbage in Drip: the list was in the snapshot,
so it survives this cycle and is freed by the next.

Barriers on several threads bring one more subtlety, from the chapter
"Threads, memory models and atomics": the barrier's check and the
store can be reordered. Both V8 and Go removed a check on the *owner's*
colour for exactly this reason, rather than pay for a memory
fence<Cite id="v8-concurrent-marking" /><Cite id="go-runtime-gc" />.

## What you learned

- **Incremental** collection slices marking between the program's
  work; **concurrent** collection marks on other threads; parallel
  collection only shares a pause.
- A live object is lost only if the program both stores it into a black
  object and removes every grey path to it.
- **Dijkstra's** insertion barrier shades the stored value (the strong
  invariant: V8); **Yuasa's** deletion barrier shades the overwritten
  value, giving **snapshot-at-the-beginning** (the weak invariant: G1,
  and half of Go's hybrid).
