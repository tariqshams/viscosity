## Tiles of data

AoSoA (from *When SoA loses: materialization and AoSoA*) cuts an array
into tiles of a fixed number of elements, and inside each tile stores the
fields as small columns; finding "field `y` of element 10" then turns on
one number, the size of the tile. Viscosity never picks AoSoA on its own:
you ask for it with the annotation from *Telling Viscosity more:
annotations and profiles*. This is the corpus program `aosoa.js`,
wrapped, without the lines that print results:

```js
// @viscosity aosoa(8)
const ps = [];
for (let i = 0; i < 1003; i++)
  ps.push({ x: i, y: -i, z: i / 2 });
for (let r = 0; r < 2; r++) {
  for (let i = 0; i < ps.length; i++) {
    const p = ps[i];
    p.x += p.z;
    p.y -= 1;
  }
}
```

and `viscosity explain` opens its report with
`ps (line 3) {x, y, z} → AoSoA, blocks of 8`.

## Blocks and lanes

<Analogy title="a binder of timetable pages">
A bus timetable is printed 8 buses to a page, with a row for times, a
row for stops and a row for destinations. To find bus 10's stop you turn
to page 1 (counting from 0), go to the "stop" row and read across to
column 2; each row is a neat run of one kind of fact.
<span slot="breaks">A printer can choose any number of buses per page;
the compiler insists on a power of two, and there is no paper: the pages
are glued end to end into one long strip of memory.</span>
</Analogy>

Every field of every element goes into one `Float64Array`, called
`data`. Step through finding `y` of element 10, with three fields in
blocks of 8:

<AosoaIndexSteps client:visible />

The **block** is the tile an element lives in (`i >> 3`, its number
shifted right three bits), and the **lane** is its place inside that
block (`i & 7`, its last three bits). JavaScript applies `>>` and `&` to
32-bit integers<Cite id="mdn-bitwise-and" /> (plenty for an index), and
for a power of two, dropping the low bits *is* dividing and rounding
down, and keeping them *is* the remainder.

<Callout kind="definition">
The **block size** B of an AoSoA layout is how many elements one block
holds. With F fields, a block is F × B slots: B values of field 0, then B
of field 1, and so on, so field k of element i is at slot
`(i >> s) * F*B + k*B + (i & (B-1))`, where `s = log2(B)`. Viscosity
requires B to be a power of two from 2 to 65,536, so that the block and
the lane are a shift and a mask rather than a division and a remainder.
</Callout>

<Examples of="block-size">

```js
// aosoa(8), F = 3: the compiled p.y -= 1
ps.data[((p) >> 3) * 24 + 8
  + ((p) & 7)] -= 1;
```

</Examples>

This is a line Viscosity emits for `aosoa.js`. `p` now holds an index (as
in *Rewriting field accesses and growing collections*); `(p) >> 3` is its
block, and a block is `F*B = 24` slots, so the product is where that
block starts; `y` is field 1, so `k*B = 8` skips the block's eight `x`
values; and `(p) & 7` is the lane. For element 10 that is
`24 + 8 + 2 = 34`. Every number but `p` is worked out at compile time and
written in as a constant.

Because a block is one `Float64Array` indexed with shifts, Viscosity
refuses what it cannot index that way: `aosoa(6)` keeps the objects with
`annotated aosoa(6), but the block size must be a power of two (2, 4, 8,
16, ...)`, and a field that may hold a string keeps them with
`annotated aosoa, but fields name may hold non-numbers`. The block size
is a dial: all the way down it gives packed AoS, and up to the length of
the array it gives SoA.

<More title="More: the generated container, the index helper, and a store by hand">

Here is the class `frontend-js/src/emit.ts` writes for `aosoa.js`,
reformatted, without its `static of` method:

```js
class __Vsc_ps {
  constructor(cap = 16) {
    this.length = 0;
    this.cap = Math.ceil(cap / 8) * 8;
    this.data =
      new Float64Array(this.cap * 3);
  }
  push(v0, v1, v2) {
    const n = this.length;
    if (n === this.cap) this.grow();
    const b = (n >> 3) * 24 + (n & 7);
    this.data[b + 0] = v0;
    this.data[b + 8] = v1;
    this.data[b + 16] = v2;
    return (this.length = n + 1);
  }
  // grow() { ...one bigger array... }
}
```

The constructor rounds the capacity up to whole blocks. `push` works out
`b`, the slot of field 0, once, then adds `k * 8` for the others.
`grow()` is simpler than SoA's: a block never moves when the array gets
longer, so it makes one array twice the size and copies the old one into
its start with a single `set`.

The formula uses the index twice, which is harmless for a name like `p`.
However, the last line of `aosoa.js` reads `ps[1002].z`, not proven in
bounds, so its index is wrapped in a bounds check, and running that twice
would be wasteful; for any index that is not a plain name or literal, the
emitter calls a helper that takes the index once:

```js
ps.data[__vsc_aosoa(
  __vsc_bc(ps, 1002, 'z', false),
  3, 24, 16, 7)]
```

Its arguments are the index, shift, stride, the field's offset (16, for
`z`) and mask. Both versions of `aosoa.js` print `1505503 501 14 -10`.

<Formal title="Where field k of element i lives">

```text
slot(i, k) = ⌊i / B⌋·F·B + k·B + (i mod B)

B = 2^s  ⟹  ⌊i / B⌋ = i >> s
            i mod B = i & (B − 1)
```

<span slot="read">The slot is the block number (i divided by B, rounded
down) times the F times B slots a block takes, plus k times B to skip the
block's earlier fields, plus the lane (the remainder of i divided by B).
When B is two to the power s, the block number is i shifted right s bits,
and the lane is i with all but its lowest s bits masked off.</span>
</Formal>

<Analogy extra title="house numbers on streets of exactly 100">
If every street had exactly 100 houses, house 347 would be street 3,
house 47, read off the digits with no dividing. A computer counts in
binary, so with 8 per block, element 10 (`1010` in binary) is block `1`
and lane `010`, which is 2.
<span slot="breaks">Real streets never have exactly 100 houses; and with
6 per block there are no digits to read off, so you must divide, which
is why Viscosity refuses 6.</span>
</Analogy>

</More>

Try the real compiler: change 8 to 4 or 6, delete the annotation
(Viscosity then picks plain SoA), or add `id: 'a'` to the record.

## Is it worth it?

<BenchBars suite="update-xy" n={100000} title="Moving 100,000 particles" highlight={['aosoa8']} layouts={['aos', 'soa', 'aosoa8']} caption="AoSoA beats objects here, but not plain SoA." />

In the committed run (`results/baseline-node-2026-10-31.md`), moving
100,000 particles took 3.15 ns per element with blocks of 8 and 1.72 with
plain SoA; reading 1,000 particles in shuffled order, AoSoA was the
slowest of all, at 9.63 ns against 2.94 for objects. And those `aosoa8`
kernels walk block by block, with no shift or mask in the inner loop;
Viscosity's emitted code does the arithmetic on every access, so it
cannot beat those bars. That is why *The cost model* never chooses
AoSoA: in V8 it was rarely better than SoA.

<Prompts ids={['ao-why-not-auto']} />

<More title="More: the shuffled-order run, and AoSoA in ISPC">

<BenchBars suite="random-x" n={1000} title="Reading x and vx of 1,000 particles in shuffled order" highlight={['aosoa8']} layouts={['aos', 'soa', 'aosoa8']} caption="At a small size with random access, AoSoA was the slowest of the three." />

ISPC builds this layout into its language: `soa<8> Point pts[...]` stores
8 `x` values, then 8 `y`, and `pts[10].x` reads the third `x` of the
second block, which is the same formula<Cite id="ispcdocs" /><Cite id="pharrmark2012" />.
There a block of 8 matches the SIMD lanes, and contiguous data allows
vector loads and stores<Cite id="ispc-perfguide" />. JavaScript has no
SIMD API, so in Viscosity's output the tiles must pay for a shift, a mask
and a multiply per access through the cache alone.

</More>

## The fields nobody reads

A game keeps entities `{ x, y, vx, vy, health, name }` in an array of
objects, and every frame a loop moves every entity, using `x`, `y`, `vx`
and `vy`; the name is printed only when an entity dies. Yet V8 keeps an
object's fields together, right after its
header<Cite id="v8-fast-properties" />, and the cache moves memory in
whole 64-byte lines<Cite id="slotin-amh-cache-lines" />, so the movement
loop drags `health` and a pointer to `name` through the cache for every
entity, and never looks at them. *AoS vs SoA, measured* named the fix, a
**hot/cold split**: the busy fields in one place, the rest in another,
both indexed by the same `i` (and code that wants a whole entity pays by
looking in two places).

## Which fields go together?

"Hot" is a matter of counting. For each field, count how often the
program touches it; for each *pair* of fields, count how often one loop
uses both; and weight each loop by how many times it runs, since a loop
that runs once a game should count for less than one that runs every
frame.

<AffinitySteps client:visible />

<Callout kind="definition">
**Field affinity** measures which fields are used together. A simple
score for a pair of fields is the total run count of the loops that use
both. Fields with high affinity belong in the same group, and a field's
**hotness** (the run count of the loops that use it at all) decides
whether its group is hot or cold.
</Callout>

<Examples of="field-affinity">

```js
// move ×1000: x, y, vx, vy
// damage ×100: x, health
aff('x', 'vx')     // 1000
aff('x', 'health') // 100
aff('vx', 'name')  // 0: never together
```

</Examples>

The first two lines list two loops with their run counts and the fields
each uses. `x` and `vx` are used together only by `move`, so their
affinity is its 1,000 runs; `x` and `health` only by `damage`, so 100;
and no loop uses `vx` with `name`, so their affinity is 0. A grouping
that follows these numbers puts `x, y, vx, vy` together, leaves `health`
lukewarm and `name` cold. `viscosity explain` already prints the raw
data: each `loop at line N ... touches 4 of 6 fields (vy, y, vx, x)` line
is one loop's field list.

<Formal title="Hotness and affinity">

```text
hot(f)    = Σ { runs(L) : f ∈ fields(L) }
aff(f, g) = Σ { runs(L) : f, g ∈ fields(L) }
```

<span slot="read">The hotness of field f is the sum (Σ) of runs(L) over
every loop L whose fields include f. The affinity of f and g is the same
sum, taken only over loops that use both f and g.</span>
</Formal>

A toolbox has a lift-out tray on top and a deep drawer below. The hammer
and screwdriver you use every day go in the tray; the pipe wrench you
need twice a year goes in the drawer.
<span slot="breaks">You can see at a glance which tools you use; a
compiler has to count, and a tool used rarely but always together with
the hammer would belong in the tray anyway.</span>
</Analogy>

</More>

## What Viscosity does

Viscosity does not build a hot struct and a cold struct; it gives every
field its own column, the finest split there is, so a `move` loop over
its columns never reads `name`, whatever its affinity. What it *does*
decide per field is the representation, and that split is by *type*, not
by heat: a field proved always numeric gets a `Float64Array`, any other
field a plain array, even one read in the hottest loop (in
`mixed_columns.js`, `tag` holds `null` or an object, so it gets a plain
column although the main loop reads it). Affinity would matter if fields
shared storage, as in packed AoS or AoSoA blocks; nothing in Viscosity
groups fields by affinity today. Try the policy: make `id` a number, and
it gets a typed column too.

## What you learned

- AoSoA tiles the data, and the **block size** B fixes the layout: field
  k of element i is at `(i >> s) * F*B + k*B + (i & (B-1))`, with B a
  power of two and every field a proven number.
- In V8 AoSoA rarely beat SoA, so it is opt-in only.
- A **hot/cold split** keeps rarely used fields out of a hot loop's cache
  lines; **field affinity** counts the runs of the loops that use a pair.
- Viscosity gives every field its own column, and chooses typed or plain
  by type, not by heat.
