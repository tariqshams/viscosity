## Four numbers that belong together

A particle has a position and a velocity: four numbers. With the tools
so far you would keep them in a tuple (values grouped in brackets):

```rust
let p = (0.0, 0.0, 3.0, 4.0);
let speed_x = p.2; // which one was vx?
```

The numbers travel together, but nothing says which is which; `p.2`
means "the third one", and a reader has to remember that the third one
is the horizontal speed. In TypeScript you solved this in *Objects:
things with named parts*, by giving every part a name. Rust has the same
idea, with one difference that runs through this whole chapter: you
declare the shape first, and every value is built from it.

<Analogy title="a printed form">
A passport application is printed with labelled boxes: surname, date of
birth, place of birth. Every copy has the same boxes in the same places,
the office will not accept one with a box missing, and you cannot add a
box of your own in the margin. The printed blank form is the **struct
definition**; each filled-in copy is one **value** of the struct.
<span slot="breaks">A paper form can be photocopied, so two people can
hold the same answers; a Rust struct value has one owner, and handing it
over moves it (as *Moves, copies and clones* showed for strings) unless the
type says it may be copied.</span>
</Analogy>

<Analogy extra title="a bento box">
A bento box is moulded with compartments: one for rice, one for fish,
one for pickles. Whatever lunch you pack, it has exactly those
compartments, and you reach into one by name ("the rice"). Every box from
the same mould is the same size, so a stack of them fits neatly on a
shelf.
<span slot="breaks">You can leave a compartment of a lunch box empty;
a struct must have something in every field (when "nothing" is a real
possibility, the field's type says so, as the chapter *Option and
Result* shows).</span>
</Analogy>

## Defining and building a struct

Here is the particle as a Rust struct:

```rust
struct Particle {
    x: f64,
    y: f64,
    vx: f64,
    vy: f64,
}
```

`struct Particle` names a new type, and the braces list its **fields**,
each with a name and a type (`f64` is the 64-bit floating-point number
from *Numbers, characters and booleans*). This defines no value yet,
only the shape every `Particle` will have. Step through one particle's
life:

<FieldSteps client:visible />

<Callout kind="definition">
A **struct** is a named record type: a fixed list of **fields**, each
with a name and a type. A **struct expression**, `Name { field: value,
... }`, builds a value of it and must give every field. `value.field`
reads one field; writing to a field needs the whole value to be bound
with `let mut`<Cite id="rust-book-structs" />.
</Callout>

<Examples of="struct">

```rust
struct Point { x: f64, y: f64 }
let p = Point { x: 1.0, y: 2.0 };
println!("{}", p.x + p.y); // 3
```

```rust
let (x, y) = (5.0, 6.0);
let a = Point { x, y };
let b = Point { y: 0.0, ..a };
println!("{} {}", b.x, b.y); // 5 0
```

```rust
// from companion/rust/src/vm.rs
struct CallFrame {
    closure: Gc<ObjClosure>,
    chunk: Rc<Chunk>,
    ip: usize,
    slots: usize,
}
```

</Examples>

The first is the smallest struct there is: two fields, one value built
with both, and two fields read with a dot and added, so it prints `3`.
The second shows two shortcuts. `Point { x, y }` is **field init
shorthand**: when a variable has the same name as the field, `x` alone
means `x: x`. `Point { y: 0.0, ..a }` is **struct update syntax**: give
the fields you want to change, then `..a` (last) to take every other
field from `a`; so `b` has `a`'s `x`, `5`, and its own `y`, `0`. The
third is real: the Rust Drip VM keeps one `CallFrame` per call in
progress, holding the closure being run, its bytecode, the index of the
next byte to run (`ip`) and where its stack slots start: the call frame
of Part IV, with a fixed shape.

Two errors catch everyone in their first week, so here they are as
pairs, each with rustc 1.97's real message (trimmed, and wrapped to fit
your screen). Leaving out a field:

```rust
let p = Point { x: 1.0 };           // ✗
let p = Point { x: 1.0, y: 0.0 };   // ✓
```

```text
error[E0063]: missing field `y` in
  initializer of `Point`
7 |     let p = Point { x: 1.0 };
  |             ^^^^^ missing `y`
```

and changing a field without `mut`:

```rust
let p = Point { x: 1.0, y: 2.0 };   // ✗
let mut p = Point { x: 1.0, y: 2.0 };
p.x = 5.0;                          // ✓
```

```text
error[E0594]: cannot assign to `p.x`, as
  `p` is not declared as mutable
8 |     p.x = 5.0;
  |     ^^^^^^^^^ cannot assign
help: consider changing this to be mutable
```

Mutability belongs to the binding, so `let mut p` makes all of `p`
changeable; no single field can be marked `mut`<Cite id="rust-book-structs" />.

## Three shapes of struct

Rust has two more kinds of struct, and the Rust Drip code uses both.
A **tuple struct** has fields with no names, only positions, and is
handy for wrapping one value in a type of its own; a **unit struct** has
no fields at all, and exists only as a name (the chapter *Traits* gives
them work to do).

```rust
struct Meters(f64);   // tuple struct
struct Origin;        // unit struct
let m = Meters(2.5);
println!("{}", m.0);  // 2.5
let o = Origin;
```

`m.0` reads the first field by position. The point of `Meters` is that
it is a *different type* from `f64`, so a function that asks for
`Meters` will not accept a plain number of seconds by mistake (the idea
of *Branded types: same shape, different meaning*, without the trick).

A struct moves like a `String` does: `let q = p;` hands the particle to
`q`, and `p` becomes unusable, as the diagram's last step showed. To
print a whole struct with `{:?}`, put `#[derive(Debug)]` above it, which
asks the compiler to write the printing code (the chapter *Traits*
explains `derive`).

## Passing structs to functions

A struct is an ordinary value, so functions can take one and hand one
back. A function that only reads a struct borrows it with `&`, exactly
as in the chapter *Borrowing*, so the caller keeps it:

```rust
fn speed(p: &Particle) -> f64 {
    (p.vx * p.vx + p.vy * p.vy).sqrt()
}
println!("{}", speed(&p)); // 5
```

For the particle from the diagram, `speed(&p)` lends `p`; inside, `p.vx`
reads through the borrow with the same dot, and the answer is the square
root of 3² + 4², which is `5`. Afterwards `p` is still yours. Try it:

<Run id="particle" />

<OtherLanguages title="A record type and one value of it">

```rust
struct Particle { x: f64, y: f64 }
let p = Particle { x: 0.0, y: 4.0 };
```

```ts
interface Particle { x: number; y: number }
const p: Particle = { x: 0, y: 4 };
```

</OtherLanguages>

They look alike, but the TypeScript interface is only a promise to the
type checker: it is erased before the program runs (*Interfaces, erasure
and typeof*), and the engine has to discover the object's shape for
itself (*Shapes in depth*). The Rust struct *is* the type at run time: a
value can only be built from it, by name, with every field, and the
compiler knows its size and the place of every field before the program
starts.

## Structs in memory

A struct is a **product** of its fields: one `Particle` is one `x`
*and* one `y` *and* one `vx` *and* one `vy`, all present at once. The
chapter *Sum types in memory* met the other kind, a value that is one
thing *or* another; the chapter *Enums and match* builds those in
Rust.

<Formal title="A struct is a product of its fields">

```text
struct P { a: A, b: B }
P  ≅  A × B
|P| = |A| × |B|
```

<span slot="read">A struct with a field of type A and a field of type
B holds one A together with one B, which mathematicians write A × B.
So the number of different values P can have is the number of A values
times the number of B values: a struct of two bools has 2 × 2 = 4
possible values.</span>
</Formal>

How the fields sit in memory matters for this book. Rust's default
layout promises little about a struct on its own (the fields do not
overlap, and each starts at an offset its type allows, but the compiler
may reorder them); what it does promise is that an array of `T` puts
element `n` exactly `n × size_of::<T>()` bytes from the
start<Cite id="rustref-type-layout" />. So `[Particle; 3]` is an array of
structs in the most literal sense:

<Figure takeaway="Rust stores structs inline; JavaScript stores references to objects." caption="On this machine a Particle is 32 bytes (four 8-byte f64s), and [Particle; 1000] is exactly 32,000 bytes. A JavaScript array of particle objects holds references, and each object lives somewhere else.">
  <InlineArray />
</Figure>

The fields sit inline, one particle after another, with no pointer to
follow; a JavaScript array of objects holds references to objects that
live elsewhere, which is what made pointer chasing slow in *Prefetching
and pointer chasing*.

## What you learned

- A **struct** is a named record with typed fields. Build it with every
  field, read and write fields with a dot, and change it only through a
  `let mut` binding; field init shorthand and `..other` save typing.
- Tuple structs (`Meters(f64)`) name fields by position; unit structs
  have none. Structs move, like `String`s, and functions that only read
  one borrow it with `&`.
- Unlike a TypeScript interface, a struct is the real type at run time,
  with a fixed size and shape.
- A struct is a product of its fields, and an array of structs stores
  them inline, back to back.
