## The same line, two answers

Here is a Drip program to think hard about:

```text
let x = "global";
{
  fn show() { print x; }
  show();
  let x = "block";
  show();
}
```

When `show` is declared the only `x` it can see is the global one, and
lexical scope promises that *where* a line is written decides what its
names mean, so both calls should print `global`. With lookups that
search the chain of environments at the moment they run, however, the
second call prints `block`: `show` captured the block's environment,
and `let x = "block"` adds an `x` to that very environment, so the
second search finds it one step earlier. Searching answers "which `x`
is visible right now?", when the question should be "which `x` did this
line mean when it was written?"; and nothing about that answer depends
on running the program.

<Analogy title="directions written on a note">
Someone writes "the café two streets north" on a sticky note, looking at
the map today. Tomorrow a new café opens one street north, but the note
still means the one it was written about; follow the note rather than
asking "which café is nearest now?", and you end up where the writer
meant.
<span slot="breaks">A note can go out of date if the café closes; the
resolver's notes cannot, because a Drip declaration never moves once
the program is written.</span>
</Analogy>

## Decide once, before running

So Drip gets one more stage between parsing and running. The
**resolver** walks the whole tree once, keeping a stack of scopes, one
for each block, function body or loop it is inside; each scope is a
`Map` from a name to a flag saying whether its declaration is done. There are no values anywhere, because the resolver never runs a
line. For each variable it meets, it searches from the innermost scope
outwards and records how many scopes it stepped out:

```ts
for (let i = scopes.length - 1;
     i >= 0; i--) {
  const done = scopes[i]
    .get(name.lexeme);
  if (done !== undefined) {
    if (!done) report(name, ...);
    locals.set(expr,
      scopes.length - 1 - i);
    return;
  }
}
```

`locals` is a `Map` whose keys are the syntax-tree nodes themselves;
object keys are compared by identity<Cite id="mdn-map" />, so two `x`
nodes get separate entries even though they spell the same name. A name
found in no scope gets no entry: it must be a global. (The `report`
fires when a variable is read while still being declared.)

<Callout kind="definition">
The **resolver** is a pass over the syntax tree, run after parsing and
before running, that works out which declaration each variable use
refers to. It keeps a stack of scopes that mirrors the environments the
interpreter will make, and for each use of a local variable it records
how far out its declaration is; names it cannot find in any scope are
treated as globals and get no entry.
</Callout>

Someone draws up the wedding seating plan before any guest arrives, so
on the day each guest walks straight to their table.
<span slot="breaks">A seating plan names a table; the resolver writes a
*distance* ("two environments out from wherever you are"), because the
same function's body runs in a different environment on every
call.</span>
</Analogy>

## From distance to environment

The interpreter's lookup changes from "search the chain" to "hop
exactly `d` parents up, then look": if `locals` has an entry `d` for
the node, it calls `this.env.getAt(d, name)`, which follows `d` parent
links; otherwise it reads the globals, and stops with `undefined
variable` if the name is not there either. Assignment has a matching
`assignAt`.

<Callout kind="definition">
A variable's **scope depth** (or distance) is the number of environments
between the one current where it is used and the one where it is
declared: 0 for the innermost, 1 for its parent, and so on. The resolver
computes it once, from the source; the interpreter uses it on every
lookup to go straight to the right environment.
</Callout>

<Examples of="resolver scope-depth">

```text
fn outer() {
  let a = 1;
  {
    let b = 2;
    fn inner() { print a + b; }
    inner();
  }
}
outer(); # 3
```

</Examples>

Walking `inner`'s body, the resolver's scopes are, from the inside out,
`inner`'s, the block's (holding `b`) and `outer`'s (holding `a`), so it
records 1 for `b` and 2 for `a`; at run time the environments line up
the same way:

<Figure caption="When inner runs, the current environment is its call's. b is 1 hop up, in the block; a is 2 hops up, in outer's call. The resolver counted the same steps through its scopes." takeaway="One scope in the resolver for each environment at run time.">
  <HopsFigure />
</Figure>

This only works because the two sides agree on every level: every place
the resolver begins a scope must be a place where the interpreter makes
an environment, and the other way round. That means a block (one
scope), a function call (one, holding the parameters *and* the body's
own variables) and a `for` loop (two: the loop variable's and the
body's). If one side ever added a level the other did not, every
distance past it would be off by one, and lookups would quietly read
the wrong variable. And the program from the start now prints `global`
twice: no scope held an `x` when the resolver walked `show`, so that
node has no entry, and both calls read the global.

<Formal title="Scope depth">

```text
scopes s₀ … sₖ, with sₖ innermost
depth(x) = k − i, for the largest i
           with x declared in sᵢ
no such i  ⟹  x is a global
```

<span slot="read">With the scopes numbered from 0 on the outside to k on
the inside, the depth of a use of x is k minus the number of the
innermost scope that declares x. If no scope declares it, x is treated
as a global (the arrow reads "means").</span>
</Formal>

## Errors before running

The resolver already walks every line, including branches a given run
never reaches, so it can check rules on the way. Here is a mistake in a
branch that hardly ever runs:

```text
fn check(x) {
  if x > 1000000 {
    let n = n + 1;
  }
  print "ok";
}
check(5);
# line 3: cannot read 'n' in its
#   own initialiser
```

Found by running, it would print `ok` every day until the first big
number, perhaps years later; found by the resolver, nothing runs.

<Callout kind="definition">
**Static analysis** means learning facts about a program from its source
or its syntax tree, without running it. Its results hold for every
possible run, including branches that a particular run never reaches.
The resolver is a small static analysis; the mistakes it finds are
**compile errors**, reported before the program starts, so nothing
runs.
</Callout>

<Analogy extra title="a spell-checker">
A spell-checker underlines a misspelt word the moment you type it, in a
paragraph nobody may read for weeks.
<span slot="breaks">A spell-checker only suggests, and you can send the
email anyway; a Drip compile error is final.</span>
</Analogy>

Drip's static rules are few: no second `let` of a name in one local
scope; no reading a local in its own initialiser (the ready flag);
`return` only inside a function; `break` and `continue` only inside a
loop; and `self` and `super` only inside methods (classes add three
more). For the middle ones the resolver remembers what it is inside
with two plain variables, `currentFunction` and `loopDepth`; entering a
function resets `loopDepth` to 0, because a `break` in a function
declared inside a loop would run in a different call from the loop. It
reports every mistake as `line N: message` and keeps walking, so you see
them all, in source order; and it runs only if the parser found no
syntax errors, since a half-built tree would give nonsense. Step
through a program with three mistakes:

<Examples of="static-analysis">

```text
fn h(a) {
  let a = 2;
}
# line 2: 'a' is already declared
#   in this scope
```

</Examples>

A function's parameters and its body's `let`s share one environment, so
they share one scope, and redeclaring a parameter is an error (globals
are not tracked, so redeclaring one is allowed).

What static analysis cannot know, in a dynamically typed language, is
what a name will *hold*: `"a" + 1`, a wrong argument count and an
undefined global all stay runtime errors. TypeScript's type checker is
a much bigger static analysis that catches the first, because its
source does say what each name holds.

<More title="The loop check in code, and a runnable list of mistakes">

```ts
case 'break':
case 'continue':
  if (loopDepth === 0)
    report(s.keyword,
      `'${s.kind}' outside a loop`);
  return;
case 'return':
  if (currentFunction === 'none')
    report(s.keyword,
      "'return' outside a function");
```

Compile errors exit with code 65, runtime errors with 70. The bytecode
compiler checks the same rules in a single pass while it generates
code, and the test corpus pins every message and line, so both report
the same errors byte for byte; it turns each local into a numbered slot
rather than a distance, in *Locals as stack slots*.

## What you learned

- The **resolver** walks the program once before it runs, and records
  each local use's **scope depth**; globals get no entry.
- The interpreter hops exactly that many parents, which needs one
  resolver scope per runtime environment.
- As **static analysis**, it also checks Drip's rules, reporting every
  compile error before anything runs; what a name will hold is left to
  run time.
