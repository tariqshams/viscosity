## A ladder with too many rungs

In "Precedence and associativity" you parsed expressions with one
function per precedence level, each calling the next, tighter one for
its operands. It works, and it reads exactly like the grammar; however,
count what happens when it parses the lone number `7`. Drip has six
levels of binary operators, then unary, then calls, and every one of
those functions is entered, finds no operator of its own and hands back
what the level below gave it, before anyone looks at the `7`. And a new
operator means a new rung: one more function, and one more call.

The real Drip parser, in `companion/ts/src/parser.ts`, reads expressions
with one small table of numbers and one loop instead. The method is
named after Vaughan Pratt, who described it in 1973 as "top down
operator precedence"<Cite id="pratt1973" />, and it builds exactly the
same trees as the ladder, with far less code.

## Binding power

Look at the `2` in `1 + 2 * 3`. Both operators want it: the `+` as its
right operand, the `*` as its left one. Whichever wins decides the shape
of the tree, so the parser needs a rule for settling the contest.

<Analogy title="two magnets and a paperclip">
Put a paperclip between a weak magnet and a strong one, and it slides
to the strong one. In `1 + 2 * 3` the `2` is the paperclip, `+` is the
weak magnet and `*` the strong one, so `2 * 3` becomes one chunk before
the `+` gets anything.
<span slot="breaks">Two equal magnets would leave the paperclip stuck
halfway; in a parser a tie always goes to the operator on the left, by
a rule we will see shortly.</span>
</Analogy>

<Analogy title="an auction with two bidders">
An item goes to whoever bids more, and each operator bids for the
operand beside it with a number printed on a card: `*` always bids 6
and `+` always bids 5, so `*` wins every contest between them.
<span slot="breaks">At an auction people raise their bids as they go;
here the bids are fixed in a table before parsing starts, so the same
contest always ends the same way.</span>
</Analogy>

That bid is called the operator's binding power, and Drip's whole
precedence ladder becomes a table of them:

This chapter uses the numbers in the figure. The companion keeps the
same ladder one higher, because it saves 1 for assignment:

```ts
export const INFIX_PREC = {
  '*': Prec.FACTOR, // 7
  '+': Prec.TERM,   // 6
  '<': Prec.COMPARISON, // 5
  // ...and every other operator
};
```

Looking up `INFIX_PREC['*']` gives `7`. A token that is not in the
table, such as a number or a `;`, has no binding power at all, which is
how the parser will know an expression has ended; and adding an
operator to Drip is one more line here, not one more function.

<Callout kind="definition">
A **binding power** is a number attached to an operator that says how
strongly it holds the operands beside it. When two operators compete
for the same operand, the one with the higher binding power gets it; on
a tie, the one on the left gets it.
</Callout>

<Formal title="Who gets the middle operand">

```text
a ∘₁ b ∘₂ c  groups as
  a ∘₁ (b ∘₂ c)   if bp(∘₂) > bp(∘₁)
  (a ∘₁ b) ∘₂ c   otherwise
```

<span slot="read">In a row a, operator one, b, operator two, c, the
middle operand b goes to the right-hand operator when its binding
power is strictly greater than the left-hand one's; otherwise, ties
included, it goes to the left-hand operator.</span>
</Formal>

<Examples of="binding-power">

```text
1 + 2 * 3   →  (+ 1 (* 2 3))
```

```text
2 * 3 + 4   →  (+ (* 2 3) 4)
a < b == c  →  (== (< a b) c)
```

```text
x + 1 < n && ok
→ (&& (< (+ x 1) n) ok)
```

</Examples>

In the first, `*` (6) outbids `+` (5) for the `2`. In the second the
stronger operator is on the left, so it keeps the `3`, and `<` (4)
beats `==` (3) the same way, which is why `a < b == c` needs no
brackets. The third is a realistic loop condition: the `1` goes to `+`
rather than `<`, the `n` to `<` rather than `&&` (2), and `&&` ends up
at the root, worked out last, just as a person would read it.

## The loop

Here is the code that runs these contests, in the form we will trace:

```ts
function pratt(minBp: number): Expr {
  let left = prefix();
  for (;;) {
    const bp = BP[peek().type];
    if (!bp || bp <= minBp) break;
    const op = advance();
    left = { kind: 'binary', left,
      operator: op, right: pratt(bp) };
  }
  return left;
}
```

Line 2 reads one operand (for now, think of `prefix()` as "read a
number or a name"; the next chapter shows what else it does). The loop
then peeks at the next token without taking it and looks up its power.
Line 5 is the whole contest: if the token is not an operator, or its
power is not greater than `minBp`, stop. Otherwise take the operator and
build a node with everything so far on the left and, on the right,
whatever a fresh call `pratt(bp)` returns; that node becomes `left`, and
the loop goes round to see whether a weaker operator wants the lot.

`minBp` is a promise to the caller: "I am the right operand of an
operator this strong, so I only take stronger ones." The first call,
`pratt(0)`, has no operator waiting, so it takes everything.

<Analogy title="a fairground ride with a height sign">
Each call is a ride with a "you must be this tall" sign set to `minBp`.
A taller operator gets on; a shorter one walks back out to the ride
before, whose sign is lower. The first ride, `pratt(0)`, has its sign
on the floor, so every operator gets on somewhere.
<span slot="breaks">A child who is turned away misses the ride; an
operator turned away by an inner call loses nothing, because the outer
call that takes it gets everything already built to its left.</span>
</Analogy>

<Analogy title="a snowball rolling downhill">
A snowball picks up a layer on every turn, and each layer wraps the
whole ball so far. `left` grows the same way, and it stops rolling
where the slope flattens: at the first operator too weak for this call.
<span slot="breaks">Snow is snow; here each layer's right side may be a
whole tree, built by a separate, nested call before it is wrapped
on.</span>
</Analogy>

The `*` node is built first, even though `+` came first in the text:

<Callout kind="definition">
A **Pratt parser** parses expressions with one function and one loop
instead of one function per precedence level: it reads an operand, then
keeps taking operators whose binding power is greater than `minBp`,
parsing each one's right operand with a recursive call whose `minBp` is
that operator's own binding power.
</Callout>

<Formal title="The loop as two equations">

```text
parse(m)   = loop(operand, m)
loop(L, m) = loop(L ∘ parse(bp(∘)), m)
               if bp(∘) > m
           = L   otherwise
```

<span slot="read">To parse with minimum power m, read an operand and
loop. In the loop, with L built so far and the next token an operator
(the small circle): if its power is greater than m, build L circle
"parse with the circle's power", and loop again with that as L;
otherwise the answer is L.</span>
</Formal>

## Equal stops, so chains lean left

Left associativity falls out of that `<=`. In `1 - 2 - 3`, the right
operand of the first `-` is parsed by `pratt(5)`, which meets the second
`-`, also 5; `5 <= 5` stops it, so it returns only `2`, and the outer
loop takes the second `-` itself: `(- (- 1 2) 3)`, which is `-4`.

<Examples of="pratt-parser">

```text
7          pratt(0) reads 7; no operator
```

```text
1 - 2 - 3  pratt(5) meets -: 5 <= 5,
           so (- (- 1 2) 3)
```

<Run id="groupings" />

</Examples>

The first is the smallest case: one call, one operand, and a peek at the
end of the input, which has no power (compare eight functions on the
ladder). The second is the tie rule. The runnable one is real Drip; work
each line out before you run it: `1 + 6 - 4` is `3`; `1 - 2 - 3` is
`-4`; `-2 * 3` is `-6`; brackets start a fresh `pratt(0)`, so
`(1 + 2) * 3` is `9`; `*` beats `==`, so `2 * 3 == 6` is `true`; and
`8 / 4 / 2` leans left, giving `1`.

A common slip is two operands with no operator between them, or an
operator with nothing after it:

```text
print 1 2;
# line 1: expected ';' after the
#   value, found '2'
print 1 +;
# line 1: expected an expression,
#   found ';'
print 1 + 2;  # 3
```

(Drip prints each message on one line.) In the first, the `2` has no
power, so the expression ends after `1` and `print` wants its `;`. In
the second, the loop takes the `+` and calls `pratt(5)`, which finds a
`;` where an operand should start.

## What you learned

- A **binding power** says how tightly an operator holds its operands.
  The higher number wins a contested operand; a tie goes to the left.
- A **Pratt parser** replaces the ladder of precedence functions with
  a table and one loop: read an operand, then keep taking operators
  whose power is greater than `minBp`, each with a recursive call for
  its right side.
- `bp <= minBp` stops on equals, which makes chains
  **left-associative**; a token with no power ends the expression.
