## All the pieces, joined

Since chapter 225 we have built a back end one piece at a time: the instruction set, the calling convention, code shapes,
instruction selection, register allocation, scheduling, peephole
clean-ups and the assembler. Each was shown on its own, on a
fragment. That leaves a fair question: do the pieces actually fit
together? This chapter and the next answer it by building **one**
compiler, about five hundred short lines of JavaScript, that takes
Drip source text and produces RISC-V assembly which LLVM's assembler
accepts and a small simulator runs. (To be plain about it: this is a
teaching back end, chosen to be short rather than fast; Viscosity has
no native back end at all, because it compiles JavaScript to
JavaScript.)

<Analogy title="a newspaper going to press">
A story passes from the reporter to an editor, to a sub-editor who
fits it to the page, to the typesetter, and finally to the press;
each person does one job and hands on something the next can use.
<span slot="breaks">A newspaper's stages all work on the same story in
roughly the same form; a compiler's stages change what the program is
made of (text, then tokens, then a tree, then instructions), and a
stage may reject the program outright, which no sub-editor can.</span>
</Analogy>

<Analogy extra title="building a house">
An architect's drawing becomes a list of materials, then a schedule
of trades, then work on site: the plan gets more concrete at every
step, until bricks are laid.
<span slot="breaks">A house is built once; a compiler runs the same
stages on every program it is given, so each stage must work for any
input, not only the one in front of it.</span>
</Analogy>

<Callout kind="definition">
A **native pipeline** is the full sequence of stages that turns source
text into machine code for a real processor: scanning, parsing,
(optionally) optimising, instruction selection over virtual registers,
register allocation with spilling, laying out each function's frame
according to the ABI, assembling, and linking. Each stage takes the
previous one's output, and each can be studied, tested and replaced on
its own.
</Callout>

## The language it accepts

A whole compiler for all of Drip would need a garbage collector,
strings, lists, classes and closures, which is a book of its own. So
we choose a subset, and say exactly what it is:

- **Numbers** are whole numbers, held as 64-bit integers (as typed
  Drip, chapter 192, could prove for programs like `sumsq`), and only
  `+`, `-` (also as a prefix) and `*` are allowed. Drip's `/` gives
  `3.5` for `7 / 2` while RISC-V's integer `div` gives 3, so `/` and
  `%` are left out rather than computed wrongly.
- **Statements**: `let`, assignment with `=`, `+=` and `-=`, `if`
  with `else` and `else if`, `while`, `return`, `print`, and calls.
- **Comparisons** (`<`, `<=`, `>`, `>=`, `==`, `!=`) only as the
  condition of an `if` or a `while`, never as values.
- **Functions** with up to eight parameters, the number of argument
  registers (chapter 228), calling each other and themselves.
- **Not included**: floats, strings, booleans as values, `none`,
  `&&` and `||`, `for`, lists, classes and closures. A function that
  ends without `return` returns 0 here, where Drip would give `none`.

<Formal title="The subset's grammar">

```text
program → ( fnDecl | stmt )*
fnDecl  → "fn" ID "(" params? ")" block
stmt    → "let" ID "=" expr ";"
        | ID ( "=" | "+=" | "-=" ) expr ";"
        | ifStmt
        | "while" test block
        | ( "return" | "print" ) expr ";"
        | expr ";"
ifStmt  → "if" test block
          ( "else" ( ifStmt | block ) )?
test    → expr ( "<" | "<=" | ">" | ">="
               | "==" | "!=" ) expr
expr    → term ( ( "+" | "-" ) term )*
term    → unary ( "*" unary )*
unary   → "-" unary | NUM | ID
        | ID "(" args? ")" | "(" expr ")"
```

<span slot="read">A program is any mix of function declarations and
statements. Each line says what one rule may be made of: the bar means
"or", the star means "any number of", and the question mark means
"optional". Comparisons only appear in test, which only appears after
if and while; that is how the grammar keeps them out of values.</span>
</Formal>

Every program in the subset is an ordinary Drip program, and prints
the same thing under the Drip interpreter, as long as its numbers stay
well within range and no function runs off its end. Here is a mistake the subset
catches, next to its fix:

```text
print 7 / 2;
# compiler: expected ';', found '/'
print 7 - 2;
# 5
```

The scanner happily makes a `/` token, but the parser's `term` rule
only knows `*`, so after reading `7` as a whole expression it expects
the `;` and finds `/` instead.

## Stages 1 and 2: from text to trees

These are Part III's scanner and parser, made small. The scanner is
one regular expression, which matches numbers, words, the two-character
operators and then any other single character:

```js
const re = /\d+|\w+|[<>=!+-]=|\S/g;
return src.replace(/#.*/g, '')
  .match(re) ?? [];
```

The parser is recursive descent, one function per grammar rule, and
it builds trees out of arrays, so `s += i * i;` becomes
`['set', 's', ['+', ['var', 's'], ['*', ['var', 'i'], ['var', 'i']]]]`
(the `+=` is desugared to `s = s + ...` on the spot). The statements
at the top level are gathered into a function called `main`, so from
here on the program is a list of functions.

## Stage 3: instruction selection

The selector walks each function's tree and covers it with **tiles**,
small tree patterns that each become one or a few RISC-V instructions
(chapter 232), choosing the bigger tile where one matches:

<Figure takeaway="Each tree pattern has its own short instruction sequence; constants that fit in 12 bits ride along inside addi, and a comparison becomes a single branch." caption="The tiles of the chapter's selector. d is a fresh virtual register, and no is the label to jump to when a test fails.">
  <TilesFigure />
</Figure>

The results go into **virtual registers**, `v0`, `v1` and so on, as
many as needed; mapping them onto real ones is the next chapter's job.
Every variable gets one virtual register for its whole life (we skip
SSA here; chapter 234 showed how a compiler leaves it anyway). The
convention from chapter 228 is already visible: parameters arrive in
`a0` to `a7`, a call puts its arguments there, and results come back in
`a0`. A test jumps to the false branch when it **fails**, which is why
`i < n` becomes `bge`, "branch if greater or equal". RISC-V's
conditional branches are `beq`, `bne`, `blt` and `bge` (with unsigned
forms), and the manual notes that `bgt` and `ble` are made by
reversing the operands of `blt` and `bge`<Cite id="riscv-isa-unpriv" />;
so `a > b` fails exactly when `b >= a`, and the selector emits
`bge b, a, no` (LLVM's assembler expands its own `bgt` the same way).

<Examples of="native-pipeline">

```text
print 1 + 2;
tokens: print 1 + 2 ;
tree:   ['print', ['+', ['num', 1],
                        ['num', 2]]]
main:
  li   v0, 1
  addi v1, v0, 2
  mv   a0, v1
  call print
  li   a0, 0
```

```text
sumsq:
  mv   v0, a0          # n
  li   v1, 0           # s
  li   v2, 0           # i
.Lsumsq0:
  bge  v2, v0, .Lsumsq1
  mul  v3, v2, v2
  add  v1, v1, v3
  addi v2, v2, 1
  j    .Lsumsq0
.Lsumsq1:
  mv   a0, v1
  j    .Lsumsq_ret
```

<Run id="front" />

</Examples>

The first is the smallest program there is: `1 + 2` matches the
`addi` tile because 2 fits in 12 bits, so only 1 needs a register;
`print` is a call like any other, with its argument in `a0`, and
`main` ends by putting 0 in `a0`, its return value. The second is the
running example, and it is nearly the listing chapter 225 promised:
the loop test is one `bge`, `s += i * i` is a `mul` and an `add`
straight into `s`'s register (the selector writes the result of an
assignment directly into the variable, with no extra copy), and
`i += 1` is one `addi`. The jump to `.Lsumsq_ret` goes to the
function's exit, which the next stage writes. The third runs stages 1
to 3 on `sumsq` and on a recursive `fib`; change the Drip text and see
what the selector makes of it.

## What you learned

- A **native pipeline** runs scanning, parsing, instruction selection,
  register allocation, frame layout, assembly and linking in order,
  each stage handing the next a more concrete program.
- Our compiler accepts a stated **subset** of Drip: whole numbers,
  `+ - *`, tests only in `if` and `while`, functions of up to eight
  parameters; anything else is rejected rather than compiled wrongly.
- The selector covers trees with **tiles**, writes into **virtual
  registers**, follows the calling convention, and turns each test
  into one branch taken when the test fails.
