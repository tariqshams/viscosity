## Two leads from the profile

*Profiling the Rust VM* left two leads. In fib, the two lines of
`read_byte` were 11.4% of all instructions, and every one of those
reads is **bounds-checked**: before Rust reads `self.chunk.code[self.ip]`
it compares `self.ip` with the length of `code` and panics if it is too
big, which is what makes safe Rust safe. In `strings.drip`,
`format_number` was 48.2% of all instructions. Each lead suggests a
change, and the rule for this chapter is the one the last chapter
earned: make one change at a time in a scratch copy, run the corpus and
the stress-GC suite (a faster wrong answer is worthless), count the
instructions with callgrind, time it in fresh processes, and keep the
change only if the time, not just the count, improves. None of the
changes below is in the companion code; they were measured here, on
2026-11-02, and the copies thrown away.

## What get_unchecked promises

Rust's slices have a method that skips the check:
`get_unchecked(i)` returns the element at `i` without comparing `i`
with the length, and it is an `unsafe` function, because if `i` is out
of range the behaviour is **undefined**<Cite id="rust-std-slice-get-unchecked" />.
Undefined behaviour is not "it panics" or "it reads garbage"; it means
the language makes no promise at all, and the optimiser may transform
the program on the assumption that it cannot happen<Cite id="rustref-ub" />.
Calling it needs an `unsafe` block, which is you telling the compiler
"I have checked this myself".

<Examples of="unchecked-indexing">

```text
let v = vec![10, 20, 30];
v[5]
// thread 'main' panicked at ix.rs:6:21:
// index out of bounds: the len is 3 but
//   the index is 5
```

```text
v.get(1)  // Some(20)
v.get(5)  // None
```

<Run id="unchecked" />

</Examples>

The first is the checked index failing: a panic with a message that
names the length and the index (rustc 1.97's real output, from a
three-line program, wrapped). The second is the checked index that does
not panic: `get` returns an `Option`, `None` when out of range, so the
caller decides. The third, which you can run, reads a byte three ways,
including the unchecked way, with the `SAFETY` comment Rust programmers
write above every `unsafe` block to say why it holds.

drip-rs cannot do this at all. Its `lib.rs` says

```rust
#![forbid(unsafe_code)]
```

and when I added an unchecked `read_byte` to a scratch copy without
removing that line, the build stopped with rustc's
``error: usage of an `unsafe` block``. So the experiment deleted the
`forbid` and changed only `read_byte` (rewrapped):

```rust
fn read_byte(&mut self) -> u8 {
    let ip = self.ip;
    // SAFETY: every chunk ends with
    // `return`, so ip < code.len().
    let byte = unsafe {
        *self.chunk.code
            .get_unchecked(ip)
    };
    self.ip += 1;
    byte
}
```

The safety argument is real: the compiler's `emit_return` ends every
function with `return`, and every jump lands inside the chunk. But it is
an argument about the *compiler*, so a compiler bug would turn into
undefined behaviour in the VM instead of a clean panic.

<Callout kind="definition">
**Unchecked indexing** reads an element without comparing its index
with the length: in Rust, `unsafe { *v.get_unchecked(i) }`. The caller
promises that `i < v.len()`; if the promise is broken the behaviour is
undefined. The checked forms are `v[i]`, which panics when out of
range, and `v.get(i)`, which returns `None`.
</Callout>

<Formal title="Checked and unchecked reads">

```text
v[i]  = *(p + i)   if i < len(v)
      = panic      otherwise
get_unchecked(v, i) = *(p + i)
      requires i < len(v)
```

<span slot="read">Reading v at i through the index operator loads the
element at address p plus i when i is less than the length, and panics
otherwise. get_unchecked loads it with no test, and it is only defined
when i really is less than the length.</span>
</Formal>

## What the measurements said

<CheckSteps client:visible />

The unchecked `read_byte` did what it promised in instructions: fib went
from 5,551,649,854 to 5,107,553,155, 8.0% fewer. In time it bought
nothing. Over 15 fresh runs each, alternating, the committed build's
best was 398 ms and median 427 ms, and the unchecked build's best 406
ms and median 439 ms: no faster, within this machine's noise. The
reason is the diagram above: the check is a comparison and a branch
that the CPU predicts correctly every single time, and a modern CPU runs
such instructions alongside the others, so removing them barely changes
how long each byte takes. That is the trap the traffic survey warned
about in the last chapter, met in practice, and it is why drip-rs keeps
its `forbid`.

The committed design shows what a real win looks like. The README
records that keeping the running frame's `ip` and chunk in fields of the
`Vm` (the "registers") made fib about 1.4 times faster when it was
added. I measured the reverse: a copy whose `read_byte` and
`read_constant` reach the chunk through the frame, the closure and the
function in the heap on every read ran fib in 11,011,220,718
instructions, almost twice as many, with a best of 842 ms and a median
of 889 ms, about 2.1 times slower. Taking work out of the loop beats
taking checks out of it.

The second lead paid off too. `format_number` turns every number into
text by asking Rust for `{:e}` (scientific notation) and then laying the
digits out the way JavaScript would, which allocates several `String`s
per number. Most numbers a Drip program prints are small whole numbers,
so I added a fast path before the general one:

```rust
if n.fract() == 0.0
    && n.abs() < 9007199254740992.0
{
    return (n as i64).to_string();
}
```

Below 2^53 (that long constant) every whole number is exact in an
`f64`, `as i64` converts it exactly, and JavaScript prints it as plain
digits, so the output is byte for byte the same; the copy passed the
corpus, the stress-GC suite and every benchmark's output. On
`strings.drip` the instructions fell from 3,573,697,000 to
1,989,310,781, 44% fewer, and this time the time followed: every one of
the 15 runs was faster than every committed run, best 176 ms against
308 ms, about 1.75 times as fast. It is a safe, five-line change that
the profile found; it is not in the companion code yet, so the
benchmark tables in the next chapter do not include it.

<Callout kind="engine" label="Under the hood">
When a check does cost time, safe Rust has ways to make the compiler
remove it for you. Iterating with `for x in xs` or `.iter()` needs no
index, so there is nothing to check<Cite id="rust-std-iter" />; and
reading a fixed-size piece once, such as two operand bytes with
`<[u8; 2]>::try_from(&code[ip..ip + 2])`, turns two checks into one
range check up front<Cite id="rust-std-array-tryfrom-slice" />. After
such a check the optimiser can often prove later indexes are in range
and drop their checks itself, with no `unsafe` written anywhere.
</Callout>

## What you learned

- A **bounds check** compares an index with the length; `v[i]` panics
  and `v.get(i)` returns `None` when it fails.
- **Unchecked indexing**, `get_unchecked`, skips the check and makes an
  out-of-range read **undefined behaviour**; drip-rs forbids it with
  `#![forbid(unsafe_code)]`.
- Measured here: unchecked `read_byte` saved **8% of instructions and
  no time**; removing the chunk register cost **2.1×**; a whole-number
  fast path made `strings.drip` **1.75×** faster.
- Keep a change only when the **time** improves beyond the noise and
  the corpus still passes.
