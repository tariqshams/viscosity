## The same listing

*VIR: records, collections and opaque values* printed functions with
`printFunc`; the Rust `vir` crate has a `print_func`. I lowered
`function sum(n)`, which adds `i` to `t` in a loop from 0 to `n`, with
both engines here and compared the two listings with `diff`, which found
no difference at all. Here is the loop header, block `b1`, from either
engine:

```
  b1:  ; preds b0 b3
    %6 = phi %1, %7
    %3 = phi %2, %10
    %5 = binop < %3, %0
    condbr %5, b2, b4
```

`%3` is `i` and `%6` is `t`, each a **phi**. Same blocks, same phis,
same numbers, so the analyses read the same graph in both engines; the
data structures behind the text differ, however, and the difference is
**ownership**.

## Who owns an instruction?

In TypeScript (`vir.ts`), a block's `insts` is an `Inst[]` of its
instruction objects, and the module's `values` is a second `Inst[]`
holding the very same objects, by id. Two references to one object cost nothing in JavaScript. In Rust a
value has exactly one owner (*Ownership: moves, copies and clones*), so
the port has to pick one, and it picks the module (from
`crates/vir/src/lib.rs`, doc comments left out):

```rust
pub struct Block {
    pub id: BlockId,
    pub insts: Vec<ValueId>,
    pub term: Terminator,
    pub preds: Vec<BlockId>,
}
```

and `Module` has `pub values: Vec<Inst>`, next to its functions and
bindings. Every instruction of every function lives in `values`, its id
is its position there, and a block is a list of ids:

<ArenaSteps client:visible />

<Callout kind="definition">
An **IR arena** stores the nodes of an intermediate representation in
`Vec`s owned by one container, here the `Module`, and refers to them by
**typed ids**: `ValueId`, `BlockId`, `FuncId` and `BindingId`, each a
`u32` wrapped in its own struct. A node's id is its index in its arena,
ids never move, and a reference between nodes is an id rather than a
pointer.
</Callout>

<Examples of="ir-arena">

```rust
for &v in &f.block(BlockId(1)).insts {
    let i = m.inst(v);
    println!("{v:?} = {:?}", i.op);
}
```

</Examples>

This walks block `b1` of `sum`: `f.block(BlockId(1))` borrows the
block; the `&v` pattern copies each `ValueId` out of its list (a 4-byte
`Copy` type, so no borrow is kept); `m.inst(v)` is
`&m.values[v.index()]`, with nothing searched; and the loop prints the
two phis and the comparison in block order. Because ids are plain
numbers, any number of analyses can hold them while reading `&Module`.

A removed trivial phi keeps its slot in `values` (marked `opaque`, with
the note `removed-trivial-phi`); only its block forgets it, and walks
go through blocks. TypeScript's `type ValueId = number` and `type
BlockId = number` mix silently; the Rust ids are separate newtypes, so
`m.inst(BlockId(1))` is `error[E0308]: mismatched types`, the idea of
*Arenas and typed indices* applied to an IR.

The crate writes the newtype once, as a `macro_rules!` template (a code
stamp that the deep dive *Macros: declarative and procedural* explains),
and stamps it out four times. Simplified:

```rust
macro_rules! id_type {
    ($name:ident, $prefix:literal) => {
        #[derive(Copy, Clone, PartialEq,
            Eq, PartialOrd, Ord, Hash)]
        pub struct $name(pub u32);
        // + index(), and a Debug that
        // prints "%3", "b1", "f0", ...
    };
}
id_type!(ValueId, "%");
id_type!(BlockId, "b");
```

Run this, then uncomment the marked line to see the E0308:

<Run id="typed-vir" />

A TypeScript `Inst` carries every possible payload as an optional field
(`value?`, `field?`, `binding?` and more), and code that knows the op
asserts that the right one is there, as in `m.bindings[i.binding!]`.
The Rust `Op` is an enum whose 22 variants each carry their own data,
such as `Op::LoadBinding { binding }` and `Op::FieldGet { field }`, so a
`match` hands you the binding with nothing to assert; `op.name()` still
returns the TypeScript spelling, such as `"index.get"`, because
`explain` quotes it. A binding's owner is `Option<FuncId>` where
TypeScript used `-1`, and a use is `Use::Inst(ValueId)` or `Use::Term {
func, block }`, ids again where TypeScript stored object references.

Numbers in the output go through `vir::js_number`, which takes the
shortest digits that read back as the same number from Rust's
`{:e}`<Cite id="rust-std-flt2dec" /> and places the point where
ECMAScript's `String(x)` does<Cite id="ecma262" />. Given a minimum
size of `1e21`, both engines print `below the 1e+21-element threshold`,
where Rust's `{}` would have written twenty-two digits.

</More>

## A cast nobody checks

*The architecture of Viscosity and its plugin API* gave every language
plugin two halves: `lower` turns source into VIR, and `emit` rewrites
the source from the plan, receiving the same `LoweredModule` that
`lower` returned. The JavaScript plugin needs more than that base type
holds (the ESTree program and the scope resolution), so its `lower`
returns a bigger object and its `emit` casts it back (from
`frontend-js/src/index.ts`, rewrapped):

```ts
emit(_source: string,
     lowered: LoweredModule,
     plan: Plan): string {
  const l = lowered as JsLowered;
  return emitJs(l.js, l.program,
                l.resolution, plan);
},
```

`as` is a promise to the type checker, not a check: I handed the
JavaScript plugin's `emit` what the Python plugin's `lower` returned for
`xs = []`, `tsc --strict` accepted it, and it returned `undefined`.

<Analogy extra title="a dry cleaner's ticket">
Each dry cleaner prints its own tickets, and the counter only hands
over clothes for a ticket it printed; take one shop's ticket to another
and you are turned away, rather than handed a stranger's coat.
<span slot="breaks">The shop checks at the counter, when you are
already standing there; Rust checks before the program ever runs, so a
mismatched ticket is a build error.</span>
</Analogy>

## The trait

Here is the Rust version, from `crates/core/src/plugin.rs` (doc
comments shortened, rewrapped):

```rust
pub trait LanguagePlugin {
    /// carried from lower to emit
    type Extra;

    fn id(&self) -> &'static str;
    fn extensions(&self)
        -> &'static [&'static str];
    fn lower(&self, source: &str) -> Result<
        LoweredModule<Self::Extra>,
        CompileError,
    >;
    fn emit(
        &self,
        source: &str,
        lowered:
            &LoweredModule<Self::Extra>,
        plan: &Plan,
    ) -> Result<String, CompileError>;
}
```

`type Extra;` is an **associated type** (*Closures, iterators and
associated types*): a type that each implementation chooses, the way
each iterator chooses its `Item`. `LoweredModule` is generic over it,
holding the VIR `module`, the `annotations` found in the source, and
`extra: X`, the plugin's private data, the part TypeScript smuggled
through the cast. `JsPlugin` sets `type Extra = JsExtra` (facts about
the syntax nodes behind instructions, and a map of bindings), and the
Python plugin, `PyPlugin`, has its own (the deep dive *The Python plugin
in Rust* reads it).

<Figure takeaway="The core reads the module; the plugin's own data goes around it." caption="compile hands the module and annotations to the core and passes extra straight from lower to emit. Nothing that compile returns mentions Extra.">
  <ExtraRoute />
</Figure>

<Callout kind="definition">
**LanguagePlugin** is the Rust trait a Viscosity front-end implements:
`id`, `extensions`, `lower` and `emit`, plus an **associated type**
`Extra` for the data that `lower` passes to `emit`. Because `emit` takes
`&LoweredModule<Self::Extra>`, it only accepts what its own plugin's
`lower` produced. Errors are `Result`s with a `CompileError` instead of
exceptions.
</Callout>

<Examples of="plugin-trait">

```rust
let l = PyPlugin.lower(py)?;
JsPlugin.emit(py, &l, &p)?;
// error[E0308]: mismatched types
//   expected `&LoweredModule<JsExtra>`,
//   found `&LoweredModule<PyExtra>`
```

</Examples>

This is the TypeScript mix-up again. The first line lowers the Python
source `py` into `l`, a `LoweredModule<PyExtra>`; the second hands it
to the JavaScript plugin's `emit`, declared with
`&LoweredModule<Self::Extra>`, where `Self::Extra` is `JsExtra`. So
rustc 1.97, compiling against the real crates, stops with the error
shown (trimmed) before anything runs, and the real `JsPlugin::emit`
reads `lowered.extra.nodes` with nothing to cast.

The pipeline is generic, `compile<P: LanguagePlugin>(source, plugin,
opts)`: lower, analyse, plan, emit, explain. Rust compiles one copy per
plugin (**monomorphization**), and nothing in the `CompileResult` it
returns mentions `Extra`, which is dropped before `compile` returns.

## Why not dyn?

*Traits, trait objects and derive* kept two plugins in one `Vec<&dyn
Plugin>`, a list of **trait objects**. Try that with the real trait:

<DispatchSteps client:visible />

The trait is dyn compatible (it breaks none of the Rust Reference's
rules<Cite id="rustref-dyn-compatibility" />), but a trait object has to
name every associated type, which is what E0191
says<Cite id="rustc-e0191" />, and `dyn LanguagePlugin<Extra = JsExtra>`
and `dyn LanguagePlugin<Extra = PyExtra>` are different types. Code that
calls `lower` through the table<Cite id="rust-reference-trait-object" />
must know the type it gets back. So the port branches *before* the
generic call
(from `run_language` in `crates/wasm/src/lib.rs`, where `compile` is
imported as `compile_with_plugin`, shortened here to `compile`):

```rust
let r = match language {
    "javascript" | "js" =>
        compile(source, &JsPlugin, opts),
    "python" | "py" =>
        compile(source, &PyPlugin, opts),
    _ => return Err(/* ... */),
};
```

Both arms have the type `Result<CompileResult, CompileError>`, so the
`match` has one type; the CLI does the same on the file's extension.

## What you learned

- The Rust **IR arena** gives instructions one owner,
  `Module::values`, and blocks list **typed ids**, which never move.
- **LanguagePlugin** has `id`, `extensions`, `lower` and `emit`, and an
  **associated type** `Extra` that carries each plugin's own data from
  `lower` to `emit`. Passing one plugin's output to another is E0308.
- `&dyn LanguagePlugin` is E0191; to pick a plugin at run time, branch
  first and call the generic `compile` in each arm.
