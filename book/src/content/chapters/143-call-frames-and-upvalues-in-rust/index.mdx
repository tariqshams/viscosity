## A frame you are not allowed to hold

In *Frames: calling and returning* the TypeScript VM's loop keeps the
running frame in a local, `let frame = this.frames[this.frames.length -
1]`, so `frame.ip++` moves the frame itself on, and `reload()` re-points
it after a call. Here is that shape in a toy Rust VM:

```rust
let frame = self.frames.last_mut().unwrap();
frame.ip += 1;
self.call(0); // pushes onto self.frames
frame.ip += 1;
```

rustc 1.97 refuses with `error[E0499]: cannot borrow *self as mutable
more than once at a time`. `call` pushes onto the very `Vec` that `frame`
points into, and a push may move every element to a bigger
buffer<Cite id="rust-std-vec" />, so the borrow checker is right. *Bytecode,
values and the VM loop in Rust* gave drip-rs's way out: the running
frame's `ip`, chunk and stack base live in fields of the `Vm`, its
registers; here are the frames behind them.

<Analogy title="a cupboard of paused board games">
The game you are playing is open on the table, and your eyes keep your
place in it. Every paused game is in its box with a note saying where
you stopped. To start a new game you first write the note for the one on
the table; when you finish it, you take the top box out and read its
note. The open game's box has a note too, but it is out of date until
you pause again.
<span slot="breaks">A paused board game cannot change while it waits;
a paused frame's variables can, because a closure the callee holds may
write to them through an upvalue.</span>
</Analogy>

<Analogy extra title="a phone call on hold">
Talking to one caller, you put them on hold to take another, after
jotting down where you had got to. The conversation you are in lives in
your head; the jotted notes are for the calls waiting.
<span slot="breaks">A caller on hold may hang up; a paused frame always

</Analogy>

## The frames are a Vec

From `vm.rs` (comments trimmed):

```rust
struct CallFrame {
    closure: Gc<ObjClosure>,
    chunk: Rc<Chunk>,
    ip: usize,
    slots: usize,
}
```

Unlike TypeScript's `{ closure, ip, slots }`, the closure is a handle,
and the chunk is an `Rc` clone, so 20 recursive frames share one chunk
for the price of a count<Cite id="rust-std-rc" />. A frame's `ip` means
something only while the frame is paused under a call.

<Figure caption="TypeScript keeps a live reference to the running frame; drip-rs copies its ip, chunk and base into the VM and writes ip back only when it makes a call." takeaway="The running frame’s own ip field is out of date by design.">
  <HoldOrCopy />
</Figure>

After its two checks (the argument count, then 256 frames at most,
which gives `stack overflow`), `call` saves, pushes and loads
(rewrapped):

```rust
if let Some(caller) =
    self.frames.last_mut()
{
    caller.ip = self.ip;
}
let chunk =
    Rc::clone(&self.heap[function].chunk);
let slots =
    self.stack.len() - arg_count - 1;
self.frames.push(CallFrame { closure,
    chunk: Rc::clone(&chunk),
    ip: 0, slots });
self.ip = 0;
self.chunk = chunk;
self.slots = slots;
```

Writing the register `ip` into the caller's frame is the moment that
field becomes correct (`caller` borrows `self.frames` while `self.ip` is
read, two different fields, so rustc allows it). `slots` points at the
callee itself, one below its arguments, as in TypeScript. Because `call`
loads the registers, the `Call` arm of the loop is one line with no
`reload`. Returning is the mirror: `pop_frame` pops the finished frame,
uses `self.frames.last()?` to return `None` when there is no caller (the
script has finished), and loads the caller's three saved values back;
the `Return` arm then does `self.stack.truncate(frame.slots)` and pushes
the result.

<FrameSteps client:visible />

<Callout kind="definition">
drip-rs's **frame stack** is `frames: Vec<CallFrame>`, one entry per call
in progress, innermost last. A frame holds its closure's handle, an `Rc`
clone of its chunk, a saved `ip`, and `slots`, the stack index of its
slot 0. The running frame is `frames.last()`, but its live `ip`, chunk
and base are in the VM's registers: `call` saves the caller's `ip` and
loads the callee, and `pop_frame` loads the caller back.
</Callout>

<Examples of="frame-stack">

```text
runtime error: cannot negate a string
  at line 2 in fn f
  at line 5 in fn g
  at line 7 in script
```

</Examples>

This is drip-rs running `g`, which calls `f("hi")`, where `f` does
`return -x;`. `runtime_error` walks the frames innermost first, and each
line needs the line of the instruction that was running,
`chunk.lines[ip - 1]`. For `g` and the script, the frame's own `ip` is
right, saved when they made their calls; for `f`, the top frame, that
field still says 0, so the code reads the register instead,
`let ip = if depth == top { self.ip } else { frame.ip };`.

<More title="Natives, roots, and a recursive run">

A native such as `len` is called without a frame. A natural design would
store a function pointer, `fn(&[Value]) -> Value`<Cite id="rustref-fn-pointer" />;
drip-rs keeps an enum, `Native::{Clock, Len, Push, Pop, Str}`, and
matches on it in `call_native`, which can then use the whole VM (to
describe a value in an error, or to intern the string `str` makes). The
arguments stay on the stack while it runs, so a collection cannot free
them. The frames are also roots: `VmRoots` traces each frame's
`closure`, while the `Rc<Chunk>` needs no tracing, because Rust frees
the bytes when the last clone goes. In the committed benchmark run,
`fib`, almost nothing but calls and returns, took 406 ms on drip-rs and
1,906 ms on the TypeScript VM.

## An upvalue is an enum behind a handle

```drip
fn make_counter() {
  let n = 0;
  fn count() { n += 1; return n; }
  return count;
}
let c = make_counter();
print c(); # 1
print c(); # 2
```

By the time `c()` runs, `make_counter`'s frame and slots are gone, yet
`count` still reads and writes `n`. *Upvalues: capturing and closing*
answered this with an upvalue that points at the slot while it exists
and holds the variable afterwards; the TypeScript object has `slot`
(`-1` once closed), `closed` and `nextOpen`, three fields for two states.
drip-rs (from `object.rs`, comments shortened):

```rust
pub enum ObjUpvalue {
    Open(usize),   // still on the stack
    Closed(Value), // the upvalue holds it
}
```

The enum makes the states exclusive: an open upvalue has no stale
`closed` value, and a closed one no slot. `LoadUpvalue` is a `match`,
`Open(slot) => self.stack[slot]` or `Closed(value) => value`, after two
lookups, the running closure and then its upvalue's handle.

<Callout kind="definition">
In drip-rs, an **upvalue handle** is a `Gc<ObjUpvalue>`: a slot number in
the heap's upvalue arena. The object behind it is
`ObjUpvalue::Open(slot)` while the variable is still on the stack, and
`ObjUpvalue::Closed(value)` after its scope ends. Closures hold handles,
never values, so closures that capture the same variable share one
handle, and closing it, which overwrites the object in its arena slot,
is seen by all of them.
</Callout>

The VM must find an existing upvalue for a slot, so that two closures
over `n` share it, and close the right ones when a scope ends.
TypeScript links the open upvalues highest slot first; drip-rs keeps
their handles in a `Vec`, lowest first, so its end matches the top of
the stack:

<Figure caption="Two orders for the same list: TypeScript links highest slot first, drip-rs keeps a Vec lowest first, so both reach the top of the stack at once." takeaway="The end of the Vec is the top of the stack.">
  <OpenList />
</Figure>

`capture_upvalue(slot)` walks back from the end: an upvalue for this
very slot is returned as it is (that is the sharing), one for a lower
slot means the new one belongs just after it, and a fresh `Open(slot)`
is inserted there. `close_upvalues(last)` pops while the last open
upvalue's slot is at or above `last`, doing
`self.heap[upvalue] = ObjUpvalue::Closed(self.stack[slot]);`, at
`Return` with the frame's base and at `close.upvalue` as a captured
local's block ends. The assignment replaces the object in its arena slot
but keeps the handle, so every closure holding it now reads `Closed`.

<Analogy extra title="a parcel-locker code">
A delivery company texts you a code. While your parcel is still on the
van, the code means "van 7"; once the van is unloaded it means "locker
12"; you, your flatmate and your neighbour can all hold the same code,
and whoever uses it finds the parcel wherever it is now.
<span slot="breaks">A parcel is collected once and then it is gone; an
upvalue can be read and written as often as you like, by every closure
holding its handle, for as long as any of them is alive.</span>
</Analogy>

The TypeScript `Closure` case allocates the closure first, with `null`s,
and then fills each entry with `captureUpvalue`. In Rust that order is
E0499 again: capturing needs all of `self`, because it may allocate,
while the half-built closure is still borrowed. So `Vm::closure`
captures every upvalue into a local `Vec` first and allocates
`ObjClosure { function, upvalues }` only when the list is complete, which
also leaves `Vec<Gc<ObjUpvalue>>` with no `null`s. It is safe although
`alloc` may collect and the local is invisible to the collector: every
handle in it is either in `open_upvalues`, a root, or in the enclosing
closure, which the running frame keeps alive.

<Examples of="upvalue-handle">

```drip
let fs = [];
for i in 0..3 {
  push(fs, fn () { return i; });
}
for f in fs { print f(); } # 0 1 2
```

</Examples>

`i` is a fresh local each time round, so each pass's closure captures
its own `Open` upvalue, and the `close.upvalue` at the end of the pass
makes it `Closed(0)`, `Closed(1)`, `Closed(2)`; drip-rs prints 0, 1 and
2, as the TypeScript VM does.

<More title="capture_upvalue in full, sharing, and how long the list gets">

From `vm.rs`, rewrapped:

```rust
fn capture_upvalue(&mut self, slot: usize)
    -> Gc<ObjUpvalue> {
    let mut i = self.open_upvalues.len();
    while i > 0 {
        let existing =
            self.open_upvalues[i - 1];
        let existing_slot =
            self.open_slot(existing);
        if existing_slot == slot {
            return existing;
        }
        if existing_slot < slot {
            break;
        }
        i -= 1;
    }
    let created =
        self.alloc(ObjUpvalue::Open(slot));
    self.open_upvalues.insert(i, created);
    created
}
```

`Vec::insert` shifts every later element, so it costs time in
proportion to the length<Cite id="rust-std-vec-insert" />; but the list
holds only captured variables of scopes still running, and with a
counter added to a scratch copy of drip-rs, all 344 corpus files never
made it longer than 3, apart from a test that captures 100 variables at

## What you learned

- The **frame stack** is a `Vec<CallFrame>`; the running frame's state
  is in registers, so its own `ip` is out of date.
- An **upvalue handle** names an `Open` or `Closed` enum in the arena;
  the open ones are a sorted `Vec`, and capturing comes before
  allocating.
