## A frame you are not allowed to hold

The chapter *Frames: calling and returning in the VM* gave the
TypeScript VM one small object per call in progress, and its loop keeps
the running one in a local variable (trimmed):

```ts
let frame =
  this.frames[this.frames.length - 1];
// ... case Op.Call:
this.callValue(...);
reload(); // frame = the new top
```

`frame` refers to the object inside the array, so `frame.ip++` moves
the frame itself on, and `reload()` re-points it after a call. Here is
the same shape in a toy Rust VM, and what rustc 1.97 says (trimmed):

```rust
let frame = self.frames.last_mut().unwrap();
frame.ip += 1;
self.call(0); // pushes onto self.frames
frame.ip += 1;
```

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
6 | let frame = self.frames.last_mut()...
  |             ----------- first borrow
8 | self.call(0);
  | ^^^^ second mutable borrow occurs here
```

`call` pushes onto `self.frames`, the very `Vec` that `frame` points
into, and a push may move every element to a bigger
buffer<Cite id="rust-std-vec" />; the borrow checker is right to refuse
(the rule is the one from the chapter *Borrowing*: one `&mut` at a
time<Cite id="klabnik2026" />). The chapter *The VM loop in Rust* showed
drip-rs's way out: the running frame's `ip`, chunk and stack base live
in fields of the `Vm` itself, its **registers**. This chapter is about
the frames behind them.

<Analogy title="a cupboard of paused board games">
The game you are playing is open on the table, and your eyes keep your
place in it. Every paused game is in its box with a note saying where
you stopped. To start a new game you first write the note for the one on
the table; when you finish it, you take the top box out and read its
note. The open game's box has a note too, but it is out of date until
you pause again.
<span slot="breaks">A paused board game cannot change while it waits;
a paused frame's variables can, because a closure the callee holds may
write to them (the next chapter, *Capturing variables in Rust*, shows
how).</span>
</Analogy>

<Analogy extra title="a phone call on hold">
Talking to one caller, you put them on hold to take another, after

## The frames are a Vec

From `vm.rs` (comments trimmed):

```rust
struct CallFrame {
    closure: Gc<ObjClosure>,
    chunk: Rc<Chunk>,
    ip: usize,
    slots: usize,
}
```

Compared with TypeScript's `{ closure, ip, slots }` there are three
differences. The closure is a handle (the chapter *Heap objects in an
arena*), not a reference. The frame carries its function's chunk as an
**`Rc` clone**, so when `fib` has called itself 20 deep, 20 frames share
one chunk and each clone only adds one to a count<Cite id="rust-std-rc" />.
And `ip` in a frame means something only while the frame is paused
under a call. `Vm::new` reserves room with
`Vec::with_capacity(FRAMES_MAX)`, and `self.stack.len()` plays the part
of TypeScript's `sp`.

## Call: save, push, load

From `call`, after its two checks (the argument count, then
`self.frames.len() == FRAMES_MAX`, which is 256 and gives the runtime
error `stack overflow`), rewrapped:

```rust
// Save the caller's ip, then load
// the callee into the registers.
if let Some(caller) =
    self.frames.last_mut()
{
    caller.ip = self.ip;
}
let chunk =
    Rc::clone(&self.heap[function].chunk);
let slots =
    self.stack.len() - arg_count - 1;
self.frames.push(CallFrame {
    closure, chunk: Rc::clone(&chunk),
    ip: 0, slots });
self.ip = 0;
self.chunk = chunk;
self.slots = slots;
Ok(())
```

The first block writes the register `ip` into the caller's frame, which
is the moment that field becomes correct; `caller` borrows
`self.frames` while `self.ip` is read, which is fine because they are
different fields. (The script's own call has no caller, so `last_mut()`
gives `None` and nothing is saved.) `chunk` is a new `Rc` handle to the
callee's bytecode. `slots` points at the callee itself, one below its
arguments, because slot 0 of every frame holds the function being
called (or `self`, in a method). Then the frame is pushed and the three
registers are loaded. Because `call` does the loading, the `Call` arm of
the loop is one line, `self.call_value(self.peek(arg_count), arg_count)?;`,
with no `reload`.

<Callout kind="definition">
drip-rs's **frame stack** is `frames: Vec<CallFrame>`, one entry per call
in progress, innermost last. A frame holds its closure's handle, an `Rc`
clone of its chunk, a saved `ip`, and `slots`, the stack index of its
slot 0. The running frame is `frames.last()`, but its live `ip`, chunk
and base are in the VM's registers: `call` saves the caller's `ip` and
loads the callee, and `pop_frame` loads the caller back.
</Callout>

<Formal title="A call and a return, on the stack">

```text
call:   slots = len − argc − 1
        frames ← frames + [frame]
return: stack ← stack[0 .. slots] + [r]
        frames ← frames − last
```

<span slot="read">A call's base is the length of the stack minus its
arguments minus one, the slot of the callee itself, and a new frame goes
on the end of the list. A return keeps the stack up to (not including)
that base, puts the result r after it, and takes the last frame off the
list.</span>
</Formal>

## Return: pop, load, truncate

```rust
fn pop_frame(&mut self)
    -> Option<CallFrame> {
    let frame = self.frames.pop()
        .expect("a frame is running");
    let caller = self.frames.last()?;
    self.ip = caller.ip;
    self.chunk = Rc::clone(&caller.chunk);
    self.slots = caller.slots;
    Some(frame)
}
```

`pop` takes the finished frame out of the `Vec` by value. `?` on the
`Option` (the chapter *Option and Result*) returns `None` at once when
there is no caller left, which is how the loop learns that the script
has finished, where TypeScript checks `frames.length === 0`. Otherwise
the caller's three saved values go back into the registers. The
`Return` arm then does `self.stack.truncate(frame.slots)`, dropping the
callee and all its arguments and locals in one step, and pushes the
result; when `frame` goes out of scope, its `Rc` clone goes with it.

<Examples of="frame-stack">

```text
fn hi() { print "hi"; }   hi();
stack: [script, hi]    slots = 2 − 0 − 1 = 1
```

```text
runtime error: area() takes 2 arguments
  but got 1
  at line 4 in script
```

```text
runtime error: cannot negate a string
  at line 2 in fn f
  at line 5 in fn g
  at line 7 in script
```

</Examples>

The first is the smallest call: no arguments, so the new frame's slot 0
is `hi` itself, at stack index 1. The second (one line, wrapped here) is
`call`'s first check, from `print area(3);` with `fn area(w, h)`: the
error comes before any frame is pushed, so the trace has only the
script. The third is a realistic trace, from `g` calling `f("hi")` and
`f` doing `return -x;`. `runtime_error` walks the frames innermost
first, and for each it needs the line of the instruction that was
running, `chunk.lines[ip - 1]`. For `g` and the script, the frame's own
`ip` is right, saved when they made their calls; for `f`, the top frame,
that field still says 0, so the code reads the register instead:

```rust
let ip = if depth == top { self.ip }
    else { frame.ip };
```

A native, such as `len`, is called without a frame at all. A natural
design would store a function pointer, a value of type
`fn(&[Value]) -> Value`<Cite id="rustref-fn-pointer" />; drip-rs keeps
an enum, `Native::{Clock, Len, Push, Pop, Str}`, and matches on it in
`call_native`, which can then use the whole VM (to describe a value in
an error, or to intern the string `str` makes). The arguments stay on
the stack while it runs, so a collection it causes cannot free them,
and afterwards one `truncate` drops them with the callee.

## What you learned

- drip-rs keeps **a `Vec` of call frames**; each `CallFrame` has a
  closure handle, an `Rc<Chunk>` clone, a saved `ip` and `slots`.
- The loop cannot hold `&mut CallFrame` across a call, so the running
  frame's state lives in **registers**: `call` saves and loads,
  `pop_frame` loads the caller back.
- The running frame's own `ip` field is **out of date**; the stack
  trace reads the register for the top frame.
- `pop_frame` returns **`Option<CallFrame>`**: `None` means the script
  has finished.

## A counter that outlives its frame

```drip
fn make_counter() {
  let n = 0;
  fn count() { n += 1; return n; }
  return count;
}
let c = make_counter();
print c(); # 1
print c(); # 2
```

`n` is a local of `make_counter`, in a stack slot, and by the time
`c()` runs that frame and its slots are gone; yet `count` still reads
and writes `n`. The chapter *Capturing variables:
upvalues* answered this for the TypeScript VM with an **upvalue**: an
object that points at the variable's stack slot while the slot exists,
and holds the variable itself afterwards. drip-rs prints `1` and `2`,
as the TypeScript VM does; what changes is how an upvalue is written
down, and how the VM tracks the ones still pointing into the stack.

<Analogy title="a parcel-locker code">
A delivery company texts you a code. While your parcel is still on the
van, the code means "van 7"; once the van is unloaded it means "locker
12"; you, your flatmate and your neighbour can all hold the same code,
and whoever uses it finds the parcel wherever it is now.
<span slot="breaks">A parcel is collected once and then it is gone; an
upvalue can be read and written as often as you like, by every closure
holding its handle, for as long as any of them is alive.</span>
</Analogy>

<Analogy extra title="a shared document link">
You and two colleagues have the same link to a document. When the file
moves from your laptop to the office server, the link is updated in one
place, and all three copies of it still open the same file.
<span slot="breaks">A moved file can leave a broken link behind; an
upvalue handle cannot dangle, because the garbage collector keeps the
upvalue alive while any closure refers to it (the chapter *A garbage
collector in Rust* shows how).</span>
</Analogy>

## Two states, one enum

The TypeScript upvalue, from `object.ts`, and drip-rs's, from
`object.rs` (both trimmed, comments shortened):

```ts
interface ObjUpvalue extends ObjHeader {
  slot: number; // -1 once closed
  closed: Value;
  nextOpen: ObjUpvalue | null;
}
```

```rust
pub enum ObjUpvalue {
    Open(usize),   // still on the stack
    Closed(Value), // the upvalue holds it
}
```

The TypeScript object has three fields for two states, and the rule
"`closed` means something only when `slot` is -1" lives in your head.
The enum (the chapter *Enums and match*) makes the states exclusive: an
open upvalue has no stale `closed` value, and a closed one has no slot.
Reading one is a `match`, from the `LoadUpvalue` arm:

```rust
let value = match self.heap[upvalue] {
    ObjUpvalue::Open(slot) =>
        self.stack[slot],
    ObjUpvalue::Closed(value) => value,
};
```

Here `upvalue` came from
`self.heap[self.closure_register()].upvalues[index]`: the running
closure first, then its upvalue, two lookups where a
TypeScript closure holds the object directly. `StoreUpvalue` matches on
`&mut self.heap[upvalue]` instead and writes either into
`self.stack[*slot]` or into the `Closed` value itself.

<Callout kind="definition">
In drip-rs, an **upvalue handle** is a `Gc<ObjUpvalue>`: a slot number in
the heap's upvalue arena. The object behind it is
`ObjUpvalue::Open(slot)` while the variable is still on the stack, and
`ObjUpvalue::Closed(value)` after its scope ends. Closures hold handles,
never values, so closures that capture the same variable share one
handle, and closing it, which overwrites the object in its arena slot,
is seen by all of them.
</Callout>

## The open list is a Vec

The VM must find an existing upvalue for a slot, so that two closures
over `n` share it, and it must close the right ones when a scope ends.
TypeScript links the open upvalues through `nextOpen`, highest slot
first; drip-rs keeps their handles in a `Vec`, sorted lowest first, so
the end of the `Vec` matches the top of the stack:

<Figure caption="Two orders for the same list: TypeScript links highest slot first, drip-rs keeps a Vec lowest first, so both reach the top of the stack at once." takeaway="The end of the Vec is the top of the stack.">
  <OpenList />
</Figure>

From `vm.rs`, rewrapped to fit:

```rust
fn capture_upvalue(&mut self, slot: usize)
    -> Gc<ObjUpvalue> {
    let mut i = self.open_upvalues.len();
    while i > 0 {
        let existing =
            self.open_upvalues[i - 1];
        let existing_slot =
            self.open_slot(existing);
        if existing_slot == slot {
            return existing;
        }
        if existing_slot < slot {
            break;
        }
        i -= 1;
    }
    let created =
        self.alloc(ObjUpvalue::Open(slot));
    self.open_upvalues.insert(i, created);
    created
}
```

It walks back from the end: an upvalue for this very slot is returned
as it is (that is the sharing), and one for a lower slot means the new
one belongs just after it, so the loop stops. Otherwise a fresh
`Open(slot)` is allocated and inserted at `i`, which keeps the order.
(`open_slot` reads an open upvalue's slot; a `Closed` one in this list
would be a VM bug, so it panics with `unreachable!`.)

`close_upvalues(last)` is the other half. While the last open upvalue's
slot is at or above `last`, it does
`self.heap[upvalue] = ObjUpvalue::Closed(self.stack[slot]);` and pops
it from the list. It runs at `Return`, with the frame's base, and at
`close.upvalue`, which the compiler emits for a captured local as its
block ends. The assignment replaces the whole object in its arena slot
but keeps the handle, so every closure holding it now reads `Closed`.

## Capture first, then allocate

The TypeScript `Closure` case allocates the closure first, with an array
of `null`s, pushes it so the collector can see it, and then fills each
entry with `captureUpvalue`. In a toy Rust VM, that order is refused
(rustc 1.97, trimmed):

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
8  | let c = self.closures.last_mut()...
   |         ------------- first borrow
10 | c.upvalues.push(self.capture(s));
   | ----------      ^^^^ second borrow
```

`capture` needs all of `self`, because it may allocate, while `c` still
borrows the closure. So drip-rs reverses the order, from `Vm::closure`
(rewrapped):

```rust
let mut upvalues =
    Vec::with_capacity(count);
for _ in 0..count {
    let is_local = self.read_byte() == 1;
    let index = self.read_byte() as usize;
    upvalues.push(if is_local {
        self.capture_upvalue(
            self.slots + index)
    } else {
        self.heap[self.closure_register()]
            .upvalues[index]
    });
}
let closure = self.alloc(
    ObjClosure { function, upvalues });
```

Each pair of operand bytes says where the variable is: a local of the
running frame (capture it) or one of the running closure's own upvalues
(share its handle). Only when the list is complete is the closure
allocated, which also makes the type simpler: `Vec<Gc<ObjUpvalue>>`,
with no `null`s. Is it safe, given that `alloc` may collect and the
local `upvalues` is invisible to the collector? The comment in `vm.rs`
gives the argument: every handle in it is either in `open_upvalues`,
which is a root, or in the enclosing closure, which the running frame
keeps alive.

<Examples of="upvalue-handle">

```drip
fn outer() {
  let x = 1;
  fn get() { return x; }
  x = 2;
  print get(); # 2
}
```

<Run id="shared" />

```drip
let fs = [];
for i in 0..3 {
  push(fs, fn () { return i; });
}
for f in fs { print f(); } # 0 1 2
```

</Examples>

In the first (called as `outer();`), the upvalue is still `Open` when
`get` runs, so it reads the slot, which already holds 2: a closure
captures the variable, not a copy. In the second, `inc` and `get` are
made in the same frame and both capture `n`, so `capture_upvalue` finds
the existing handle the second time and they share it; two calls to
`inc` and `get` sees 2. The third is the realistic case from the
chapter *Closing upvalues: a fresh variable every pass*: `i` is a fresh
local each time round, and the `close.upvalue` at the end of each pass
closes that pass's upvalue, so the three closures print 0, 1 and 2.

## What you learned

- drip-rs's **`ObjUpvalue`** is an enum: `Open(slot)` while the variable
  is on the stack, `Closed(value)` once its scope ends.
- Closures hold **upvalue handles**; closing overwrites the object in
  its arena slot, so every closure sharing the handle sees the change.
- The **open upvalues** are a `Vec` of handles sorted by slot: capture
  searches from the end, close pops from the end.
- drip-rs **captures every upvalue before allocating the closure**: the
  borrow checker forbids the other order, and every handle is already
  reachable from a root.
