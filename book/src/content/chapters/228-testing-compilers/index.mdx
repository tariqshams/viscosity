## The worst kind of bug

When your code has a bug, you read your code. When the compiler has a
bug, your code is fine and the program still does the wrong thing, and
nothing in your source points at the cause. Viscosity rewrites your
arrays into columns; if the rewritten program ever prints something
different, or fails differently, Viscosity is broken, however fast it is.

So we test it, and at once hit the hard part. A test needs an
**oracle**, something that says what the right answer is, and for a
compiler the "answer" is a whole program's behaviour; writing it out by
hand for thousands of programs would be slow and error-prone. The
research on compiler testing treats the choice of oracle as one of its
central questions<Cite id="chen2020survey" />, and there are four good
answers.

<Figure takeaway="You rarely need the right answer if you have something it must equal." caption="Four oracles. Golden: compare with an output stored earlier. Differential: two implementations must agree. Metamorphic: a change that must not change the output. Round trip: an operation and its inverse must give back the input.">
  <OracleKinds />
</Figure>

A **unit test** checks one small piece against an answer you know, such
as the mini parser's test that `2 ** 3 ** 2` groups to the right. A
**golden test** stores a whole output once (checked by a person) and
compares every later run against it; the Drip corpus does this with its
`# expect:` comments, and the Rust port's parity fixtures are golden
files generated from the TypeScript engine. The other two need no
stored answer at all.

## Two programs that must agree

<Analogy title="checking a translation without the language">
You can check a translated set of directions without speaking either
language: hand the original to one person and the translation to
another, ask both to follow them, and see whether they end up at the
same door.
<span slot="breaks">Both walkers could take the same wrong turn, and you
would never know; two implementations can share a bug, which is why
agreement is strong evidence, never a proof.</span>
</Analogy>

<Analogy extra title="two clocks in the house">
If the kitchen clock and the bedroom clock disagree, at least one of
them is wrong, even though you do not know the time.
<span slot="breaks">Clocks drift a little and you shrug; programs must
agree exactly, and a single different character in the output counts as
a failure.</span>
</Analogy>

<Callout kind="definition">
**Differential testing** runs two implementations of the same thing on
many inputs and compares the results; every difference is a bug in one
of them, and no expected outputs are needed<Cite id="mckeeman1998" />.
For a compiler the two are usually the program before and after
compiling, two compilers, or two versions of one compiler.
</Callout>

<Formal title="What a compiler must preserve">

```text
∀ x.  run(P, x) = run(C(P), x)
```

<span slot="read">For every input x (∀ reads "for every"), running the
program P on x gives the same outcome, the same output and the same
error, as running C(P), the compiled program. A differential test checks
this for many inputs and many programs, never for all of them.</span>
</Formal>

Viscosity's test corpus is a folder of small JavaScript programs, each
built to probe one case (an escape, a shape mismatch, an out-of-bounds
read), with a first line saying what Viscosity should decide, such as
`// viscosity: ps=soa`. The test, from
`frontend-js/test/differential.test.ts`, simplified:

```ts
const r = compile(src, jsPlugin());
expect(got(r.plan)).toEqual(want(src));
const before = runIsolated(src);
const after = runIsolated(r.code);
expect(after).toEqual(before);
```

The first `expect` checks the decisions against the header; the second
runs both versions with `runIsolated`, which gives each a brand-new Node
VM context (its own globals, so neither run can see the other's leftovers)
and records every `console.log` line *and* the uncaught error, if any, as
`'TypeError: ' + message`. Step through one corpus program:

The last step is a real experiment, not a test in the repository:
compiled with `--bounds assume`, that file prints `0` where the original
threw a `TypeError`, and only comparing errors as well as output catches
it. The header check catches the opposite failure, because a compiler
that never transforms anything passes every behaviour test.

<Examples of="differential-testing">

```js
// a fast sort against a slow, obvious one
fast([3, 1, 2]);   // [1, 2, 3]
slow([3, 1, 2]);   // [1, 2, 3]: agree
```

```ts
// acorn against the hand-written parser
const a = compile(src,
  jsPlugin({ parser: 'acorn' }));
const m = compile(src,
  jsPlugin({ parser: 'mini' }));
expect(m.code).toBe(a.code);
```

```text
TS engine   → code + explain  ┐ byte for
Rust engine → code + explain  ┘ byte
```

</Examples>

The first is the idea at its smallest: a fast sort is checked against a
slow one too simple to be wrong. The second is
`mini-parser.test.ts`: for every corpus and benchmark program, Viscosity
compiled with acorn and with its own small parser must give
byte-identical code and explanations. The third is the parity guarantee
of the Rust port, whose README counts 95 programs, each compiled in two
bounds modes, 190 pairs that all match; and the Drip companion does the
same with its two interpreters, requiring the tree-walker and the VM to
print the same, byte for byte, on every corpus program.

## Changing the input on purpose

A **metamorphic test** needs only one implementation: change the input
in a way that must not change the answer, and check that it does not.
Sorting a list and sorting its reverse must give the same result;
renaming every variable must not change what a program prints. Le,
Afshari and Su made this a powerful compiler test: run a program on an
input, delete some of the code that did not execute on that input, and
the new program must still behave the same on it. In about eleven
months this gave them 147 confirmed, unique bug reports against GCC and
LLVM alone<Cite id="le2014emi" />.

## Round trips

There is one more trick, made for front ends. Parse a program, print the
tree back to source, and parse that: you must get the same tree, and any
difference means the parser or the printer lost something (a missing
pair of brackets is the classic).

<Callout kind="definition">
**Round-trip testing** checks that a pair of opposite operations undo
each other: parse → print → parse gives the same tree, encode → decode
gives the same value. Like differential testing, it needs only the
input, not an expected output.
</Callout>

<Examples of="round-trip-testing">

```js
const v = { x: 1, y: [2, 3] };
JSON.parse(JSON.stringify(v)); // same data
```

```js
show(['*', ['+', 1, 2], 3]);
// '(1 + 2) * 3'; without brackets,
// '1 + 2 * 3' parses as 1 + (2 * 3)
```

```ts
const src = 'const a = [1, 2, 3];\n' +
  '// a comment\n' +
  'console.log(a.length);\n';
expect(compile(src, jsPlugin()).code)
  .toBe(src);
```

</Examples>

The first is the everyday round trip: JSON out and back in again gives
the same data. The second is the bug it is famous for catching: a
printer that leaves out brackets turns `(1 + 2) * 3` into `1 + 2 * 3`,
and parsing that back gives a different tree. The third is Viscosity's
own version. It never prints a whole tree (it edits only the parts of
the source it changes), so its round trip is the identity: a program
with nothing to transform must come back byte for byte, comment
included.

Try all three ideas on a sort: a differential check against a slow sort,
a metamorphic check with a shuffled input, and a JSON round trip.

## What you learned

- Testing a compiler is mostly the **oracle problem**: knowing the right
  answer. Unit and golden tests store it; the others avoid needing it.
- **Differential testing** compares two implementations. Viscosity
  compares each program before and after compiling, output *and*
  errors, in fresh VM contexts, and checks its decisions too.
- Two parsers, two engines and two interpreters that must agree byte for
  byte are all differential tests.
- **Metamorphic** tests change the input in a way that must not change
  the answer; **round-trip testing** checks that opposite operations
  undo each other.
