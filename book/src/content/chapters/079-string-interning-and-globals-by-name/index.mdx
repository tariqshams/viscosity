## Two strings, one object

*Hash tables* left a loose thread: `Table.find` compares keys with
`k === key`, and Drip's `==` is no better, since `valuesEqual(a, b)` is
`a === b`. For objects, `===` asks "is this the same object?", not "are
these the same characters?". Yet this prints `true`:

```text
let a = "ab";
let b = "a" + "b";
print a == b;
```

`a` holds a literal, made by the compiler; `b` is built while the
program runs, by `add`, which joins two strings into a new object. So
how can they be the same object? Because `copyString`, which makes
every string object, does not always allocate.

<Analogy title="the badge desk at a conference">
Before printing a name badge, the clerk looks through the box of
badges already printed; if one says "Ada Lovelace", you get that one.
As such, everyone called Ada Lovelace wears the very same badge, and
checking whether two people have the same name is as quick as checking
whether they are wearing the same badge.
<span slot="breaks">Two real people cannot wear one badge at once; a
string object can be pointed at from any number of places at the same
time, because nothing in Drip can change a string's characters.</span>
</Analogy>

## Interning

Here is the real `copyString`, from `vm/heap.ts`:

```ts
copyString(chars: string): ObjString {
  const hash = hashString(chars);
  const interned =
    this.strings.findString(chars, hash);
  if (interned) return interned;
  const s = this.allocate<ObjString>({
    type: 'string', chars, hash,
    isMarked: false, next: null });
  this.push(s);
  this.strings.set(s, null);
  this.pop();
  return s;
}
```

It hashes the characters with FNV-1a, then asks `heap.strings`, a
`Table` used as a *set* (its keys are every string the VM has made, its
values all `null`), whether a string with those characters exists; if
so, it returns that object and allocates nothing. Only a string never
seen before is allocated and added to the set (`push` and `pop` keep it
safe from the garbage collector meanwhile). Every string in the VM
comes through here, literals, names, joins and the results of `str`,
so there is never more than one object with the same characters.

<InternSteps client:visible />

<Callout kind="definition">
**Interning** keeps exactly one copy of each distinct string. Every
request for a string first looks in a table of the strings that exist,
the **intern table** (here `heap.strings`), and gets the existing object
if there is one. Because equal strings are then always the same object,
comparing strings becomes comparing **identity**: one `===` on two
references, however long the strings are.
</Callout>

<Examples of="interning">

```text
print "ab" == "a" + "b"; # true
```

</Examples>

The compiler interned `"ab"` when it met the literal. At run time `add`
joins `"a"` and `"b"` and calls `copyString("ab")`, which hashes the
characters, finds the literal's object in the intern table and returns
it, so both sides of `==` are one reference and `===` says `true`.
Without interning, two objects holding `'ab'` would be two objects, and
`===` would say `false`.

<TwoCompares />

<More title="findString, the one place characters are compared">

`Table.find` compares keys by identity, which `copyString` cannot use:
it is holding characters, not an object. So the table has a second
lookup, `findString`, which probes exactly like `find` but tests each
key with `k.hash === hash && k.chars === chars`. Comparing two numbers
is cheap and rules out almost every wrong string, so the characters are
compared only when the hashes match, and by then it is nearly always
the right string.

<Run id="intern-vm" />

Interning is everywhere: Python interns the names in its programs, so a
dictionary lookup can compare pointers instead of
strings<Cite id="python-sys-intern" />, and Java interns every string
literal<Cite id="openjdk-string-intern" />. The companion VM interns
every string it makes, which is simpler than choosing, and is what
makes `===` correct for every Drip value.

</More>

Interning moves work around; it does not remove it. Every new string,
every join and every `str(...)` is hashed in full and looked up before
it exists; the companion's `strings` benchmark does little else, and in
the run of 2 November 2026 it took 383 ms on the VM and 365 ms on the
tree-walker. In return, `==` on strings is one comparison, and every
lookup of a name (globals, fields, methods) is by identity. One more
duty: if the intern table kept every string alive, no string could ever
be freed, so it holds strings **weakly**, and during a collection
(*Reclaiming memory: mark and sweep*) each entry whose string nothing
else reached becomes a tombstone before the sweep frees it.

## Globals by name

Now the VM can give `total` in `let total = 10;` somewhere to live:
the tree-walker kept a `Map` from names to values, and the VM keeps one
`Table`, `vm.globals`, keyed by interned name strings. An instruction
cannot carry a string, only bytes after its opcode, so the compiler
puts the *name* in the constant pool (with `copyString`, so every
mention of `total` is one object) and gives its index as a two-byte
operand. The VM side, from `vm/vm.ts`:

```ts
case Op.LoadGlobal: {
  const name = readString();
  const v = this.globals.get(name);
  if (v === undefined)
    this.runtimeError(
      `undefined variable '${name.chars}'`);
  this.push(v!);
  break;
}
case Op.DefineGlobal:
  this.globals.set(readString(),
    this.peek(0));
  this.sp--;
  break;
```

`load.global` pushes the value stored under the name, or stops with
Drip's runtime error. `define.global` *peeks* at the value, stores it,
and only then drops it, so the value is always somewhere a garbage
collection would find it; a second top-level `let` replaces the first.

Assigning to an undefined name must be an error, and the obvious code
looks the name up, checks, then stores: two lookups. `store.global`
does one:

```ts
case Op.StoreGlobal: {
  const name = readString();
  if (this.globals.set(name,
      this.peek(0))) {
    this.globals.delete(name);
    this.runtimeError(
      `undefined variable '${name.chars}'`);
  }
  break;
}
```

`Table.set` returns `true` when the key was *new*, which in a correct
program never happens here, so a correct assignment costs one `set`; a
mistaken one has just created a variable that should not exist, so it
deletes it again and reports the error. There is no pop, because an
assignment is an expression (`print a = 3;` needs the value).

<GlobalSteps client:visible />

<Callout kind="definition">
The VM's **global table** is one hash table (`vm.globals`) mapping
interned name strings to values. `define.global` stores the value on
top of the stack under a name and pops it; `load.global` pushes the
value stored under a name, or reports `undefined variable`;
`store.global` overwrites an *existing* name and leaves the value on
the stack. Each takes one operand: the two-byte constant index of the
name.
</Callout>

<Examples of="global-table">

```text
0000    1 const               0 '1'
0003    | define.global       1 'a'
0006    2 load.global         2 'a'
0009    | print
0010    3 load.global         4 'a'
0013    | const               5 '2'
0016    | add
0017    | store.global        3 'a'
0020    | pop
```

</Examples>

This is the companion disassembler's listing for `let a = 1; print a;
a = a + 2;`, one statement per line. Line 1 pushes `1` and
`define.global` stores it under constant 1, the name `a`. Line 2 loads
`a` by name and prints it. Line 3 loads `a`, adds `2`, and
`store.global` writes the sum back, leaving it on the stack for `pop`.
Every instruction with a constant is three bytes (the offsets go up by
3), and each mention of `a` adds a pool entry, but all hold the same
interned string.

<NameToValue />

<More title="Found late, on purpose, and what it costs">

A global is looked up by name *when the instruction runs*, not when it
is compiled, so a function can mention a global that does not exist
yet, as long as it exists by the time the function is called; that is
also what lets two top-level functions call each other.

<Run id="late-global" />

The natives are globals in the same table, so `print len;` prints
`native fn len`, and a top-level `let len = 3;` replaces it. Every
global access is a hash-table lookup at run time, and it shows: in the
companion's benchmark run of 2 November 2026 the VM lost to the
tree-walker on `fields` (712 ms against 530 ms), which reads globals and
their fields millions of times, each a lookup in one of the VM's own
tables written in JavaScript, where the tree-walker uses the engine's
built-in `Map`. CPython's `LOAD_GLOBAL` also names a global by an index
into a table of names, while locals use another instruction with a
plain index<Cite id="cpython-dis" />. Drip is about to make the same
split.

</More>

## What you learned

- **Interning** keeps one object per distinct string, so equal strings
  are identical and Drip's `==` is one `===`; new strings pay a hash
  and a lookup, and the intern table holds them weakly.
- The **global table** maps interned names to values; the instructions
  name a global by a constant index, and `store.global` sets first and
  undoes a new key.
