## Two arrays that look the same

To JavaScript, these hold the same kind of thing. `typeof` says
`'number'` for every element of both:

```js
const a = [1, 2, 3];
const b = [1, 2, 3.5];
```

V8 sees two different arrays. Chapter 22 showed that it stores small
integers as Smis and other numbers as doubles. If V8 knows an array
holds only Smis, it can optimize operations on it for exactly that
case<Cite id="v8-elements-kinds" />. One stray `3.5` changes how the
whole array is stored, and what the optimizing compiler may assume.

V8 keeps elements, the values at integer indices, apart from an object's
named properties<Cite id="v8-fast-properties" />. And for each array it
tracks what kind of elements it holds<Cite id="v8-elements-kinds" />.

## Three kinds, one way down

<Callout kind="intuition">
Think of a pantry with three shelves. The top one takes only identical
jars, the middle one any can, the bottom one anything at all. Things only
ever move down: once you've put a cardboard box on the bottom shelf with
everything else, nobody carries the jars back up, even if the box is
eaten.
</Callout>

There are three basic kinds. **SMI** means every element is a small
integer. **DOUBLE** means every element is a number, stored as a raw
64-bit double. **ELEMENTS** means anything goes: each slot is an ordinary
tagged value. Each new value can push the array to a more general kind.

```
 - elements kind: PACKED_DOUBLE_ELEMENTS
 - elements kind: PACKED_ELEMENTS
 - elements kind: HOLEY_ELEMENTS
```

The same output shows where the kind lives. It is part of the array's
map, the shape of chapter 63, and the change to a holey kind is listed as
a map transition (addresses shortened):

```
 - map: 0x… <Map[32](PACKED_SMI_ELEMENTS)>
 …
   (transition to HOLEY_SMI_ELEMENTS)
```

It also names the backing store: a `FixedArray` for Smis and general
values, a `FixedDoubleArray` once the array went DOUBLE.

<Callout kind="definition">
An array's **elements kind** records what its indexed elements can hold.
The basic kinds are **SMI** (small integers), **DOUBLE** (any number,
stored as untagged doubles<Cite id="v8-src-elements-kind" />) and
**ELEMENTS** (any value). Kinds form a
**lattice**, and an array only ever moves to a more general kind: SMI →
DOUBLE → ELEMENTS<Cite id="v8-elements-kinds" />. V8 records the kind in
the array's map.
</Callout>

<Callout kind="pitfall">
Some numbers that look harmless are not Smis. `-0`, `NaN` and `Infinity`
are doubles, so pushing one onto an array of small integers moves it to
DOUBLE<Cite id="v8-elements-kinds" />. So does a large integer like
`2 ** 31`, which is too big for a Smi in this Node build (checked with
`%DebugPrint`).
</Callout>

## Holes

Every kind comes in two flavours: **PACKED** and **HOLEY**. A hole is
an index below the length with nothing in it:

```js
const xs = [0, , 2];  // a hole at 1
const ys = [];
ys[3] = 'x';          // holes at 0, 1, 2
```

A hole is not the same as storing `undefined`. Reading one makes
JavaScript look further, at the object the array inherits from,
`Array.prototype`. Usually nothing is there and you get `undefined`. But
try this:

That is why holes are costly. For a packed array, V8 knows every index
below the length has its own element. For a holey one, a read needs
extra checks and may have to search the prototype chain<Cite id="v8-elements-kinds" />.

<Callout kind="definition">
A **holey array** has at least one index below its `length` with no
element of its own. Each basic kind has a holey variant
(`HOLEY_SMI_ELEMENTS`, `HOLEY_DOUBLE_ELEMENTS`, `HOLEY_ELEMENTS`), and
PACKED → HOLEY is one-way too: filling every hole later doesn't make the
array packed again<Cite id="v8-elements-kinds" />.
</Callout>

`new Array(3)` starts holey, because its three slots are empty. Filling
them with integers leaves it `HOLEY_SMI_ELEMENTS` (V8 12.4 again). The
post that describes the lattice adds a 2025 update: `fill` is now an
exception to this rule<Cite id="v8-elements-kinds" />, a change too
recent for Node 22. Starting from `[]` and pushing never makes a hole.

## Kinds meet inline caches

Elements kinds matter most to optimized code. An element load like
`xs[i]` has an inline cache (chapter 64), and it remembers the kinds it
has seen. A helper called with arrays of Smis, of doubles and of strings
sees three kinds. Its loads become polymorphic and must check which case
they are in every time<Cite id="v8-elements-kinds" />. One kind per call
site keeps them monomorphic.

<Callout kind="engine" label="Under the hood">
The V8 post that explains the lattice dates from 2017 and counts 21
different elements kinds; this chapter covers the six common ones<Cite id="v8-elements-kinds" />.
Typed arrays have specialized kinds of their own<Cite id="v8-elements-kinds" />:
`%DebugPrint` reports `FLOAT64ELEMENTS` for a `Float64Array`. That is
one more reason Viscosity's struct-of-arrays columns are `Float64Array`s.
A column's kind is fixed: it can't fall from SMI to DOUBLE halfway
through a loop, and it can never become holey.
</Callout>

## What you learned

- Every array has an **elements kind**: **SMI**, **DOUBLE** or
  **ELEMENTS**, each **PACKED** or **HOLEY**.
- The kinds form a **lattice**, and an array only moves to more general
  kinds. Overwriting a double with an integer doesn't move it back.
- `-0`, `NaN`, `Infinity` and large integers are doubles, not Smis.
- A **holey array** has empty indices. Reading a hole can reach the
  prototype chain, so holey arrays need extra checks. Build arrays with
  literals or `push`.
- The kind lives in the array's **map**, and element loads' inline caches
  see it: one kind per call site keeps them monomorphic.
