## A call that makes garbage

In the chapter "Objects and method calls in the VM", `get.prop` on a
method made a **bound method**, a small heap object holding the
instance and the method together, because Drip says that `o.m` on its
own is a value you can store and call later. So the plain reading of
`c.m(2)` is "read `c.m` (make a bound method), then call it". The
compiler does not do that, as the disassembler shows (the method is
called `m` here only so that the lines fit the page):

```text
0030    6 load.global         9 'c'
0033    | const              11 '2'
0036    | invoke             10 'm' (1 args)
0040    | pop
0041    7 load.global        12 'c'
0044    | get.prop           13 'm'
0047    | const              14 '3'
0050    | call                1
```

Line 6 is `c.m(2);` and line 7 is `(c.m)(3);`, which means exactly the
same thing; the brackets stop
the compiler seeing a call straight after the property, so it falls
back to the literal reading: `get.prop` allocates a bound method, and
`call` unpacks it again at once. That bound method is garbage as soon as
`call` has unpacked it, which in a loop of a million calls is a million
objects for the collector.

## One instruction: invoke

When `dot` in the compiler has parsed `.name` and the next token is
`(`, it compiles the arguments and emits one instruction carrying both
the name and the argument count:

```ts
} else if (match('(')) {
  const argc = argumentList();
  emitConstantOp(name.line, Op.Invoke, k);
  emitAt(name.line, argc);
}
```

The receiver is pushed first and the arguments above it, so when
`invoke` runs, the receiver is already in the slot that will become the
method's slot 0, `self`. Here is `invoke` in `vm.ts`, shortened where
marked:

```ts
const receiver = this.peek(argCount);
// (an error unless it is an instance)
const field = receiver.fields.get(name);
if (field !== undefined) {
  this.stack[this.sp - argCount - 1] =
    field;
  return this.callValue(field, argCount);
}
const method =
  receiver.klass.methods.get(name);
if (method === undefined) return ...;
this.call(method as ObjClosure, argCount);
```

It looks in the instance's fields first; a field holding a function
shadows a method of the same name, so the field replaces the receiver
in the callee's slot and is called like any value. Otherwise it finds
the method in the class's table and calls it straight away: no bound
method, nothing to unpack, and the frame is the same one `call` would
have built. Step through both routes:

Did it pay off? In runs I did for this book, I built a copy of the
companion whose compiler never emits `invoke` (so every `o.m()` becomes
`get.prop` and `call`) and timed the `method_calls` benchmark against
the real one, alternating the two, nine runs each. The best run with
`invoke` took 704 ms and the best without it 932 ms; and where the real
VM never needed a single collection, the copy ran 48 of them and freed
1,570,728 bound methods. The chapter "Measuring and speeding up the VM"
puts this next to the other changes measured the same way.

<Callout kind="definition">
**Method invocation**, in the VM, is the single instruction `invoke
name argc`, emitted when a property access is immediately called. It
looks the name up in the receiver's fields, then in its class's
methods, and calls what it finds with the receiver already in slot 0.
It means exactly what `get.prop` followed by `call` means, without
allocating a bound method.
</Callout>

<Formal title="Invoke means read, then call">

```text
o.m(a1, …, an)  ≡  (o.m)(a1, …, an)
  invoke m n    ≡  get.prop m; call n
```

<span slot="read">Calling o.m with arguments a1 to an gives the same
result as first reading o.m and then calling that with the same
arguments. In bytecode: one invoke of m with n arguments does what a
get.prop of m followed by a call with n arguments does; the only
difference is the bound method the second one allocates.</span>
</Formal>

<Run id="field-wins" />

That program is why the field check exists: after `a.m = f;`, the
instance has a field named `m`, so `a.m()` must call `f`, exactly as
`(a.m)()` would, and it prints `field`.

## Inheritance by copying

The tree-walker found an inherited method by walking up the chain of
superclasses on every lookup. The VM does that walk once, when the
subclass is made: `inherit` copies the superclass's whole method table
into the new class.

```ts
// Copy-down inheritance: the methods are
// copied once, now.
(this.peek(0) as ObjClass).methods.addAll(
  (superclass as ObjClass).methods);
this.sp--;
```

(From the `inherit` case, wrapped; before it, the instruction checks
that the superclass really is a class.) It runs before the subclass's
own `method` instructions, so an overriding method simply overwrites
the copied entry, and every later lookup is a single probe in one
table.

This is only correct because a Drip class can never gain or lose
methods after its declaration; if it could, the copies would go stale.

`super` needs one more piece. When a class extends another, the
compiler opens a scope around the class body and declares a local named
`super` holding the superclass; methods that say `super` capture it as
an upvalue (the chapter "Capturing variables: upvalues"), and it is
closed when the class declaration ends. Here is
`class B extends A { m() { return super.m() + "B"; } }`:

```text
== <script> ==
0022    | load.global         7 'A'
0025    | load.global         8 'B'
0028    | inherit
0029    | load.global         9 'B'
0032    5 closure            11 fn m
0035    |   local 1
0037    | method             10 'm'
0040    6 pop
0041    | close.upvalue
== m ==
0000    5 load.local          0
0002    | load.upvalue        0
0004    | invoke.super        0 'm' (0 args)
```

`load.global 'A'` leaves the superclass in slot 1, the hidden `super`
local; `inherit` copies its methods into `B` and pops `B`; `B`'s
method `m` captures slot 1 (`local 1`); and after the class body, the `pop`
drops `B` and `close.upvalue` closes `super` into the upvalue. Inside
it, `super.m()` pushes `self`, then the superclass through the
upvalue, and `invoke.super 'm'` looks `m` up in *that* class's table
and calls it, with `self` already in place, allocating nothing. (Reading
`super.m` without calling it compiles to `get.super`, which makes a
bound method, as `get.prop` does.)

<Examples of="method-invocation">

```text
t.flip().value();
# invoke 'flip', then invoke 'value'
```

```text
let f = c.add;   # get.prop: a bound method
f(4);            # call: unpacked
```

```text
super.init(on);
# load.local 0, load.local 1,
# load.upvalue 0, invoke.super 'init'
```

</Examples>

The first is from the `method_calls` benchmark: `flip` returns `self`,
and the chained call becomes two `invoke` instructions, the second one
finding its receiver where the first left its result. The second is the
case `invoke` cannot cover: the method is stored as a value, so the
bound method really has to exist, and `call` unpacks it later. The
third is a subclass's `init` calling its parent's: `self`, the argument
and the superclass go on the stack, and `invoke.super` calls the
parent's `init` on the same instance.

## What you learned

- `o.m(args)` compiles to **`invoke m n`**, which calls the method with
  the receiver already in slot 0 and allocates no bound method;
  `(o.m)(args)` and `let f = o.m;` still take the long way.
- `invoke` checks fields before methods, so it means exactly what
  reading and then calling would.
- `inherit` copies the superclass's methods down once; overrides are
  added after, so they win, and every lookup is one probe.
- `super` is a hidden local captured as an upvalue; `invoke.super` and
  `get.super` start the lookup at that class.
