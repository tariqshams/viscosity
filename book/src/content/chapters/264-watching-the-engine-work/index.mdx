## Make the engine talk

The chapters from *The V8 pipeline* to *Mark-compact and the write
barrier* described V8's tiers, shapes, elements kinds, deoptimisation
and garbage collector. You do not have to take any of it on trust: V8
has flags that print what it is doing, and Node passes them through.
Every output in this chapter is real, from this book's machine, trimmed
only to fit your phone.

<Analogy title="a car's diagnostic port">
A modern car has a socket under the dashboard; plug a reader into it
and the car's own computer tells you what it decided and why ("misfire
on cylinder 2", "fuel mix adjusted"), things you could never see by
driving.
<span slot="breaks">A car's fault codes follow a published standard
and mean the same thing for years; V8's output is private to its
developers and can change in any release, so every reading must be
labelled with the version that produced it.</span>
</Analogy>

<Analogy extra title="a chess player thinking aloud">
Some chess players, streaming a game, say their reasoning as they go:
"his bishop is pinned, so I'll take the pawn; no, wait, that loses the
knight". You learn more from that commentary than from the moves alone.
<span slot="breaks">The player picks what to say for an audience; V8
prints everything a flag covers, tersely, in its own shorthand, and the
printing itself takes time, so never benchmark with tracing on.</span>
</Analogy>

<Callout kind="pitfall" label="These flags are V8's, not yours">
They are defined inside V8 for its own developers, in one file per V8
version<Cite id="v8-flag-definitions" />. They are not part of
JavaScript or of Node's stable interface, and names, output formats and
defaults can change in any release. Everything below was run on
**Node v22.23.4, V8 12.4.254.21**. Addresses (`0x…`) differ on every
run. Run `node --v8-options` to see what your own version offers.
</Callout>

<Callout kind="definition">
**Engine tracing** means running a program with an engine's diagnostic
flags so that the engine reports its own decisions as it makes them.
In V8 these include `--print-bytecode` (Ignition bytecode),
`--trace-opt` (functions marked and compiled by the optimising tiers),
`--trace-deopt` (every deoptimisation, with its kind, reason and
bytecode offset), `--trace-generalization` (hidden-class fields
becoming more general) and `--trace-gc` (one line per garbage
collection)<Cite id="v8-flag-definitions" />. Their output is for
diagnosis, not for parsing in production: it varies between versions.
</Callout>

## Bytecode

Ignition is a register machine with an accumulator (one special
register that most instructions read and write)<Cite id="v8-ignition" />.
Ask for one function's bytecode, using the filter so that you do not get
Node's own thousands of functions as well:

```text
$ node --print-bytecode \
    --print-bytecode-filter=add bc.js
```

For `function add(a, b) { return a + b; }`:

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[generated bytecode for function:
 add (0x… <SharedFunctionInfo add>)]
Bytecode length: 6
Parameter count 3
Register count 0
 @ 0 : 0b 04     Ldar a1
 @ 2 : 3b 03 00  Add a0, [0]
 @ 5 : ae        Return
```

`Ldar a1` loads the second argument into the accumulator. `Add a0, [0]`
adds the first argument to it, and `[0]` is a **feedback slot**: where
this `+` records the types it sees (*Speculation and
deoptimisation*)<Cite id="v8-ignition-handlers" />. `Return` hands back
whatever is in the accumulator. The `@ 2` on the `Add` line is its
offset, its position in bytes from the start of the bytecode; remember
it.

## Optimising, and giving up

This program makes `add` hot with integers, then hands it a double:

```js
function add(a, b) {
  return a + b;
}
for (let i = 0; i < 1e5; i++) add(i, 1);
add(0.5, 1); // a double!
```

```text
$ node --trace-opt --trace-deopt opt.js
```

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[marking … <JSFunction add …> for
 optimization to TURBOFAN, …,
 reason: hot and stable]
[compiling method … <JSFunction …>
 (target TURBOFAN) OSR, …]
[completed optimizing … add …
 (target TURBOFAN)]
[bailout (kind: deopt-eager, reason:
 Insufficient type feedback for call):
 … <JSFunction (sfi = …)>, …
 bytecode offset 41, …]
[bailout (kind: deopt-eager, reason:
 not a Smi): … <JSFunction add …>,
 … bytecode offset 2, …]
```

`add` is "hot and stable", so TurboFan compiles it, concurrently, on
another thread. The nameless function is the top-level script; its
loop is still running when it gets hot, so V8 uses **on-stack
replacement** (OSR)<Cite id="v8-flag-definitions" />: it switches the
loop over to optimised code in the middle of running it. You will not
see Maglev here: in this Node build, `--v8-options` lists it as off by
default.

Then two bailouts. The script's optimised code reaches the call
`add(0.5, 1)`, which had never run, so it had no feedback to go on. And
`add` itself fails its small-integer check at bytecode offset 2: the
`Add` above. Here is that last line in full, read part by part:

<Formal title="The shape of a bailout line">

```text
line   ::= "[bailout (kind: " kind
           ", reason: " reason "): "
           … "bytecode offset " n … "]"
kind   ::= "deopt-eager" | …
```

<span slot="read">A bailout line is the text "[bailout (kind: ", then a
kind, then ", reason: " and a reason, then "): ", then other details,
somewhere among which is "bytecode offset " followed by a number, and a
closing bracket. A kind is deopt-eager, or the name of the other kind
V8 12.4 defines, the lazy one. This is the grammar the exercise's regular expression
matches; like the output itself, it is only true for this
version<Cite id="v8-deopt-kinds" />.</span>
</Formal>

## Three programs, three traces

Run each of these with `--trace-deopt` and see what V8 says. Try to
predict each one before reading its output:

<Examples of="engine-tracing">

```js
function sq(x) { return x * x; }
for (let i = 0; i < 1e5; i++) sq(i);
// [bailout (kind: deopt-eager,
//   reason: overflow): … sq …
//   bytecode offset 2, …]
```

```js
// …the same loop, then:
sq('3');
// [bailout (kind: deopt-eager, reason:
//   not a Number or Oddball): … sq …]
```

```js
const x = new Float64Array(1e5);
const vx = new Float64Array(1e5);
function step(dt) {
  for (let i = 0; i < 1e5; i++)
    x[i] += vx[i] * dt;
}
for (let t = 0; t < 100; t++) step(0.5);
// (no bailout lines at all)
```

</Examples>

The first is the surprise: `sq` only ever sees integers, yet it
deoptimises. The reason is `overflow`. The optimised code guessed that
`x * x` stays a small integer, because every result so far had been
one; on this build a Smi holds up to 2<sup>31</sup> − 1
(`%DebugPrint(2 ** 31 - 1)`, from the next chapter, prints `Smi`), and 46341 × 46341 is the
first square past that. (A loop that stopped at 46340 printed no
overflow bailout; one that reached 46341 did.) V8 then compiles `sq`
again with what it has learned. The second hands `sq` a string,
and the reason changes to "not a Number or Oddball" (an *oddball*, in V8's own
naming, is a special value such as `undefined`, `null` or `true`:
`%DebugPrint(null)` labels it `[Oddball]`)<Cite id="v8-deopt-kinds" />: the multiply can no longer assume
numbers at all. The third is the struct-of-arrays loop from Part II.
With `--trace-opt` it shows `step` being compiled by TurboFan through
OSR; with `--trace-deopt` it prints nothing, because two
`Float64Array`s of doubles never surprise the optimised code. When you
check your own hot loops, silence is the answer you want.

## Garbage collection

Keep three million small objects alive and watch the collector:

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[…]   24 ms: Scavenge 4.4 (5.1) ->
  3.9 (6.1) MB, … 1.03 / 0.00 ms …
  allocation failure;
[…]  214 ms: Mark-Compact 53.7 (86.2)
  -> 41.0 (74.2) MB, … 44.16 / 0.00
  ms … GC in old space requested
[…]  577 ms: Scavenge 166.9 (185.5)
  -> 166.9 (201.5) MB, … 32.16 / 0.00
  ms … allocation failure;
3000000
[…]  617 ms: Mark-Compact 205.6
  (235.1) -> 3.6 (36.9) MB, …
```

Each line gives the time since start, the collector, the size of the
objects before and after (with the heap's memory size in brackets), the
time it took, and the reason<Cite id="v8-gc-tracer" />. Scavenges are
young-generation collections, mark-compacts whole-heap ones (*V8's
garbage collector*). At 577 ms a scavenge freed nothing: every object
was still in `keep`. Once the script had finished, the last
mark-compact found almost everything dead. This is also the flag behind
*Escape analysis in V8*: counting scavenges with
`--trace-gc | grep -c Scavenge` is how that chapter showed the
temporary objects had vanished.

## What you learned

- **Engine tracing**: V8's `--print-bytecode` (with a filter),
  `--trace-opt`, `--trace-deopt` and `--trace-gc` report its decisions
  as it makes them.
- A bytecode listing shows each instruction's **offset** and its
  **feedback slots**.
- A deopt line gives the **kind** (eager or lazy), the **reason**, the
  function, the tier and the **bytecode offset**, which you can match to
  the `--print-bytecode` listing.
- Even integer code can deoptimise, on **overflow**; a loop over typed
  arrays of doubles should print no bailouts at all.
- All of it is **V8-internal** and version-specific: label your output
  with the version, and expect it to change.

## A question the trace cannot answer

The previous chapter's flags report decisions as V8 makes them: this
function was optimised, that guess failed, the young generation was
collected. Sometimes, though, the question is about one object, right
now: what shape does it have? Is it in dictionary mode? Are its numbers
boxed? *Shapes in depth* and *Elements kinds* told you these things
exist; this chapter shows you how to look at them directly.

V8 has a set of internal runtime functions, and with one flag it lets
your source call some of them by name, with a `%` in front.

<Analogy title="a television's service menu">
Many televisions have a hidden service menu, opened by pressing a
secret sequence of buttons on the remote, that shows the engineer
readings no viewer ever sees: panel hours, voltages, calibration
values.
<span slot="breaks">A service menu belongs to one model and stays the
same for its life; V8's natives belong to one version of V8 and can
change or disappear in the next, so a program that relies on them is
tied to that version.</span>
</Analogy>

<Analogy extra title="an X-ray">
A doctor who wants to know how a bone has healed does not ask the
patient how it feels; an X-ray shows the inside directly.
<span slot="breaks">An X-ray only looks; some natives also act, for
example by telling V8 to optimise a function on its next call, so they
can change what the engine does, not only show it.</span>
</Analogy>

## Turning it on

Without the flag, `%` at the start of a statement is not JavaScript at
all, and the program does not even start. Here is the spot-the-difference
pair, run on Node v22.23.4:

```text
$ node e.js
%DebugPrint(p);
^
SyntaxError: Unexpected token '%'

$ node --allow-natives-syntax e.js
DebugPrint: 0x…: [JS_OBJECT_TYPE]
 - map: 0x… <Map[32](HOLEY_ELEMENTS)>
```

The file is the same two lines both times (`const p = { x: 1 };` and
`%DebugPrint(p);`); only the flag differs. `--allow-natives-syntax` is
defined in V8's flag file<Cite id="v8-flag-definitions" />, and the
functions it unlocks are listed in V8's `runtime.h`, where
`DebugPrint`, `HasFastProperties`, `HaveSameMap`,
`GetOptimizationStatus`, `PrepareFunctionForOptimization` and
`OptimizeFunctionOnNextCall` sit in the group meant for
testing<Cite id="v8-runtime-h" />.

<Callout kind="definition">
**Natives syntax** is V8's `%Name(args)` syntax for calling its internal
runtime functions directly from JavaScript, enabled only by
`--allow-natives-syntax`. Functions such as `%DebugPrint` (print an
object's map, fields and elements) and `%HasFastProperties` are meant
for V8's own tests: they are not JavaScript, and they can change or
disappear between versions<Cite id="v8-runtime-h" />.
</Callout>

`%DebugPrint(o)` prints what V8 knows about one value. Here it is for an

line by line:

For an array, the same function shows the elements kind changing as
you go (real output, Node v22.23.4, trimmed to the `map` line):

```js
const a = [1, 2, 3];
%DebugPrint(a); // PACKED_SMI_ELEMENTS
a.push(1.5);
%DebugPrint(a); // PACKED_DOUBLE_ELEMENTS
a[10] = 1;
%DebugPrint(a); // HOLEY_DOUBLE_ELEMENTS
```

Three small integers make a packed array of Smis. Pushing `1.5` moves
the whole array to doubles, still packed. Writing to index 10 of an
array of length 4 leaves holes at 4 to 9, so it becomes holey; each
step is one of the one-way moves from *Elements kinds*, now seen from
inside.

## Asking yes-or-no questions

`%DebugPrint` prints a great deal. For a test, you usually want one
answer, and some natives return a plain value you can `console.log`
or check with an `if`:

<Examples of="natives-syntax">

```js
const p = { x: 1, y: 2 };
%HasFastProperties(p); // true
delete p.x;
%HasFastProperties(p); // false
```

```js
const q = { x: 1, y: 2 };
const r = { x: 3, y: 4 };
%HaveSameMap(q, r);        // true
r.z = 5;
%HaveSameMap(q, r);        // false
%HaveSameMap(q, { y: 1, x: 2 }); // false
```

```js
function add(a, b) { return a + b; }
%PrepareFunctionForOptimization(add);
add(1, 2); add(3, 4);
%OptimizeFunctionOnNextCall(add);
add(5, 6);
%GetOptimizationStatus(add); // 0b1010001
```

</Examples>

The first shows dictionary mode: a fresh object literal has fast
properties, laid out by its map, and `delete` drops it into a
dictionary (a hash table), as *Slack tracking and dictionary mode*
described. The second
checks shapes: two objects built the same way share a map, adding `z`
to one moves it to a new map, and an object with the same fields in the
other order has a different map too, because maps record the order in
which properties were added. The third makes V8 optimise `add` on
demand rather than waiting for it to get hot:
`%PrepareFunctionForOptimization` readies the function (as its name
says), two calls give it something to learn from, and
`%OptimizeFunctionOnNextCall` makes the next call run optimised code,
which the status shows. Each
output was printed by running the line on Node v22.23.4.

## Decoding an optimisation status

`%GetOptimizationStatus` returns a number in which each bit means one
fact about the function, and V8's `runtime.h` names every
bit<Cite id="v8-runtime-h" />. Printed in binary with
`.toString(2)`, `add`'s status was `10000001` before the forced
optimisation and `1010001` after it (and `10000001` again after
`add(0.5, 1)` made it deoptimise):

<Figure takeaway="Each bit of the status is one fact about the function." caption="Two statuses of add, decoded with the bit names from V8 12.4’s runtime.h.">
  <StatusBits />
</Figure>

<Formal title="Reading bit k of a status">

```text
bit(s, k) = ⌊ s ÷ 2ᵏ ⌋ mod 2
          = (s >> k) & 1
```

<span slot="read">Bit k of a status s is s divided by 2 to the k,
rounded down, then the remainder when divided by 2; in JavaScript that
is s shifted right by k places, and-ed with 1. For 1010001 in binary,
bit 6 is 1 (TurboFanned) and bit 7 is 0 (not interpreted).</span>
</Formal>

## A field that changes kind

The repository's findings (FINDINGS.md, section 4) used a tracing flag,
`--trace-generalization`, to explain why a TypeScript-style class was
slow. It belongs here because it is about one object's fields. You can
reproduce it: a class with a field declaration, filled with doubles.
Node prints many lines for its own code, so keep only yours:

```js
class P {
  x;
  constructor(x) { this.x = x; }
}
const ps = [];
for (let i = 0; i < 10; i++) {
  ps.push(new P(i + 0.5));
}
```

```text
$ node --trace-generalization gen.js \
    | grep gen.js
[generalizing]x:h{Any;const}->
 t{Any;mutable} (uninitialized field)
 [new ~P+16 at …/gen.js:3]
```

The field starts as a heap-object field (it holds `undefined` before
the constructor runs), and storing a number generalises it to a generic
*tagged* field, so every double is boxed; the `const` from the
`%DebugPrint` stepper becomes `mutable` at the same moment. Without the
`x;` line, no such line appears for `x`.

<Prompts ids={['generalization']} />

<Callout kind="engine" label="Under the hood">
V8 lists these functions in the group meant for
testing<Cite id="v8-runtime-h" />, and that is the right way to use them
in your work too: a small test that says "these two objects
share a map" or "this function is optimized" checks a performance
assumption the way an ordinary test checks a result. Viscosity's
claims can be checked like this, since its output is ordinary
JavaScript. Keep them out of anything you ship: they are not
JavaScript, no other engine understands them, and they belong to one
V8 version.
</Callout>

## What you learned

- **Natives syntax**, `%Name(args)`, calls V8's internal runtime
  functions from JavaScript; without `--allow-natives-syntax` it is a
  `SyntaxError`.
- `%DebugPrint` shows an object's **map**, its fields (a **Smi** in
  place, a double as a **HeapNumber**) and an array's **elements
  kind**.
- `%HasFastProperties` and `%HaveSameMap` answer yes-or-no questions
  about dictionary mode and shapes.
- `%GetOptimizationStatus` returns a bit set, named in `runtime.h`;
  `%OptimizeFunctionOnNextCall` forces optimisation for a test.
- All of them are V8 test functions, for one version: use them to check
  assumptions, never in shipped code.
