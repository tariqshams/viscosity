## Three ways to run the same program

The book has now built Drip three times: a **tree-walker** in
TypeScript (Part III), which runs a program by walking its syntax tree;
a **bytecode VM** in TypeScript (Part IV), which compiles the program to
bytecode first and runs that; and **drip-rs**, the same VM ported to
Rust, function for function. All three pass the same corpus, so they
compute the same answers. This chapter asks how fast they compute them,
and the honest answer has a surprise in it.

The programs are the ten in `corpus/benchmark`, each a few dozen lines
that exercise one thing hard: `fib` (recursive calls), `closures`,
`method_calls`, `fields` (reading and writing fields), `instantiation`
(making objects), `trees` (building and walking a tree of objects),
`particles`, `sieve`, `sort` and `strings`. On 2026-11-02 the
TypeScript script `scripts/bench.mjs` timed both TypeScript
implementations on Node 22.23.4, and then `scripts/bench.sh` timed
drip-rs on the same machine a few seconds later, and wrote one table
with all three (`results/drip-rs-bench-2026-11-02.md`). Every time is
the best of three runs, each in a fresh process, with compiling the
program included, so it is what a person running `drip program.drip`
would wait for.

routes (all traffic lights) barely care what you ride.

## The results

<ThreeWaySteps client:visible />

Step through the diagram; it reads every number from the two committed
JSON files. In the first step you see the times; the rest are
**speed-ups**, old time divided by new time, so 2× means "twice as
fast" and anything under 1× means slower. Three things stand out.

drip-rs is faster than both TypeScript implementations on every
program: from 1.26 to 4.94 times the TypeScript VM's speed, with a
geometric mean of 3.94, and 3.98 against the tree-walker. Its speed-up
over the TypeScript VM varies little, because the two VMs run the same
bytecode with the same instructions; only `strings` stands apart, and
*Profiling the Rust VM* showed why: there drip-rs spends half its time
formatting numbers in library code, not in the dispatch loop.

The TypeScript VM, on the other hand, is **not** reliably faster than
the tree-walker. It wins on six programs, by at most 1.30 times
(`method_calls`), and loses on four: `fields` (0.74), `instantiation`
(0.69), `strings` (0.95) and `trees` (0.80). The geometric mean over the
ten is 1.01: on these programs, on this day, compiling to bytecode in
TypeScript bought nothing on average.

A **geometric mean** is the right summary for speed-ups: multiply the
ten ratios and take the tenth root. It treats "twice as fast" and "half
as fast" as equal and opposite, which the ordinary average does not
(the average of 2 and 0.5 is 1.25, which would call a wash a win).

<Callout kind="definition">
An **implementation comparison** runs the same programs, with the same
inputs and the same expected output, on two or more implementations of
one language, on the same machine, measured the same way, and reports
each program's speed-up (old time divided by new time) and their
geometric mean. It is only meaningful when every implementation passes
the same tests, so that all of them are doing the same work.
</Callout>

<Formal title="Speed-up and its summary">

```text
speedup(p) = t_old(p) / t_new(p)
geomean = (Πₚ speedup(p))^(1/n)
```

<span slot="read">The speed-up on program p is the old time over the
new time. The summary over n programs is the n-th root of the product
of all the speed-ups, so a 2× and a 0.5× cancel out exactly.</span>
</Formal>



## Why the TypeScript VM loses

A bytecode VM is supposed to win by doing less work per step than a
tree-walker. To see why that did not happen in TypeScript, I profiled
both TypeScript implementations with V8's own sampling profiler,
`node --cpu-prof src/cli.ts --vm ../corpus/benchmark/instantiation.drip`
(and the same without `--vm`, and for `trees` and `fields`), and grouped
the samples by source file:

<WhereVmTime />

The difference is in what each implementation builds by hand. The
tree-walker stores an instance's fields in a JavaScript `Map` and lets
V8's garbage collector free everything, so both of those jobs are done
by V8's own code, written in C++. The TypeScript VM, being a model of a
real VM, builds both itself: its own hash table (`table.ts`, with
open addressing and tombstones from *Finding things fast: hash tables*)
and its own mark-and-sweep collector (`heap.ts`), written in TypeScript
and running *on top of* V8's collector, which still has to free the
JavaScript objects underneath. On `instantiation`, the VM's own table
(16% of samples, much of it `Table.grow` as new instances' tables
expand), its own collector (10%) and V8's collector (13%) add up to 39%
of the run; on `trees`, 43%. The tree-walker's `Map`s and V8's collector
take 30 to 31%.

`fields` needs no allocation at all (two objects, half a million loop
turns), and there the cost is per instruction: the statement
`a.x += a.vx;` is eight VM instructions (`load.global a`, `dup`,
`get.prop x`, `load.global a`, `get.prop vx`, `add`, `set.prop x`,
`pop`), and five of them are probes in the VM's hand-written table;
the VM's loop and table take 85% of the samples against the
tree-walker's 75% for its loop and `Map` lookups. drip-rs runs the same
eight instructions, but each is a few machine instructions of compiled
Rust, which is where its 3.69× comes from. In short, the TypeScript VM
models the *design* of a fast VM faithfully, and the design only pays
once it is compiled to machine code, which is what the port to Rust
did.

<Callout kind="engine" label="Under the hood">
These are end-to-end times of short programs, so they include starting
Node or the Rust binary and compiling the Drip program, and the Node
numbers include V8 warming up its compiler on the interpreter's own
code. A long-running server would see V8 at full speed, and smaller
gaps between the two TypeScript implementations, or larger ones; the
results file says what was measured, and nothing here should be read as
a claim about other programs or machines. The noise is real too: a run
can vary by tens of percent on this shared machine, which is why the
tables report the best of three, and why a 0.95 for `strings` is best
read as "about the same".
</Callout>

## What you learned

- Compare implementations on the **same programs**, the **same
  machine** and the **same measurement**, and only once they pass the
  **same tests**.
- Summarise speed-ups with a **geometric mean**: drip-rs is 3.94×
  the TypeScript VM and 3.98× the tree-walker; the TypeScript VM is
  **1.01×** the tree-walker.
- The TypeScript VM **loses** on `fields`, `instantiation`, `strings`
  and `trees`: it rebuilds a hash table and a collector in TypeScript
  that the tree-walker gets from V8.
- The VM's design pays off **once compiled**: the same bytecode in Rust
  runs 1.26 to 4.94 times as fast.
