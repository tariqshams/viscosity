## Two classes that look the same

Here are two TypeScript classes for a particle. Read them carefully:

```ts
class P {
  x: number;
  constructor(x: number) {
    this.x = x;
  }
}

class K {
  declare x: number;
  constructor(x: number) {
    this.x = x;
  }
}
```

They hold the same data and run the same constructor; the only
difference is the word `declare` on the second line. Yet in this book's
benchmark, moving particles made from the first class was several times
slower than moving particles made from the second. The last chapter
showed what numbers and objects look like inside V8: small integers as
Smis in the slot, other numbers as HeapNumber boxes, and a header at the
front of every object. This chapter adds the last piece, which is how V8
decides to store each *field*, and with it the whole explanation.

## A field remembers what it has held

V8 does not treat every field as "could be anything". It watches the
values stored into each field, records what kind they have been, and
picks the cheapest storage that fits all of them; a field that has only
ever held small integers can keep them as Smis, and a field that has
only ever held numbers can keep a double that is updated in place. When a value arrives that
does not fit, the field is widened to something more general, and in
general it does not go back<Cite id="v8-react-cliff" />.

<Analogy title="a labelled kitchen drawer">
A drawer labelled "teaspoons" lets you grab one without looking. The day
someone drops a whisk in, the label becomes "spoons and whisks"; after
the first ladle, it says "utensils", and now you have to look at
whatever you pull out. Nobody ever writes the narrower label back on.
<span slot="breaks">A drawer's label is a guess you could check by
opening it; V8's record is a promise it relies on when it generates
machine code, so when a value breaks it, the code built on the old label
has to be thrown away and rebuilt, which costs time on its own.</span>
</Analogy>

<Analogy title="a spreadsheet column's format">
Format a spreadsheet column as "number" and every cell is stored as a
number, so summing it is quick. Type a word into one cell, and the
column becomes "general": each cell might now be text, and the
spreadsheet has to check every cell before using it.
<span slot="breaks">A spreadsheet changes one column for one sheet; V8
records the field's kind in the hidden class, which is shared by every
object of that shape, so one odd value can slow down a million
objects at once.</span>
</Analogy>

<Callout kind="definition">
A **field representation** is how the engine has decided to store one
field, recorded in the object's hidden class. The V8 blog describes the
**Smi** and **Double** representations, and a field moving to a more
general one when it receives a value that does not fit<Cite id="v8-react-cliff" />;
V8's own trace output, below, also shows **heap object** (h) and
**tagged** (t, anything at all). A field with the Double representation
keeps its value in a box that only its object can see, so V8 can
update it in place; a Tagged field keeps numbers as ordinary immutable
HeapNumbers<Cite id="v8-react-cliff" />.
</Callout>

<Formal title="Widening: the smallest rung that fits">

```text
Smi ⊑ Double ⊑ Tagged    HeapObject ⊑ Tagged
rep' = rep ⊔ kind(v)
Smi ⊔ Double = Double
Double ⊔ HeapObject = Tagged
```

<span slot="read">The symbol ⊑ is read "is below, or equal to, on the
ladder": Smi is below Double, Double is below Tagged, and a heap object
is below Tagged. Storing a value v into a field changes its
representation to rep ⊔ kind(v), read "rep joined with the kind of v",
which means the lowest rung that is at or above both. So a Smi field
that receives a fraction becomes Double, and a Double field that
receives undefined (or any other heap object) has to jump all the way to
Tagged.</span>
</Formal>

<Examples of="field-representation">

```js
const o = { n: 1 }; // n: Smi
o.n = 2;            // still Smi
```

```js
o.n = 1.5;  // widens to Double
o.n = 7;    // stays Double
```

```js
const t = { start: null };
// start: heap object (null)
t.start = performance.now();
// a double arrives: Tagged
```

</Examples>

The first is the easy case: `n` has only ever held small integers, so it
stays a Smi, and updates are written straight into the slot. In the
second, `1.5` does not fit a Smi, so the field moves up one rung to
Double; storing `7` afterwards does not move it back (`7` is stored as
the double 7.0), because a field only moves up. The third is the one to
remember. `null` is not a number, so `start` begins as a heap-object
field; then `performance.now()` returns a fraction of a millisecond, a
double, and the only rung above both is Tagged. From then on every new
time stored in `start` is a fresh HeapNumber. The V8 team's advice is
exactly this: do not start numeric fields as `null`<Cite id="v8-react-cliff" />.

## Back to the two classes

In modern JavaScript, `x;` inside a class body is a real **class
field**. Fields are added before the constructor's body runs, and a
field without a starting value starts as `undefined`<Cite id="mdn-class-fields" />.
You can watch it happen:

<Run id="field-undefined" />

The constructor prints `before: undefined` and `has x? true`: the field
already exists, holding `undefined`, before the line `this.x = x` has
run; after the constructor, `p.x` is `0.5`. TypeScript turns
`x: number;` into exactly that kind of field when the target is ES2022
or later<Cite id="ts-use-define" />. Writing `declare x: number;`
instead emits nothing at all, so there is no field until the constructor
first stores a number<Cite id="ts-37-declare" />. Here is the difference
side by side, as it reaches the engine:

```js
// what class P becomes
class P {
  x; // starts as undefined
  constructor(x) { this.x = x; }
}
// what class K becomes
class K {
  constructor(x) { this.x = x; }
}
```

Now put the ladder to work: in `P`, the first value `x` ever holds is
`undefined` (a heap object), and the second is a double, so the field
jumps to Tagged; in `K`, the first value is a double, so the field is
Double. Step through both:

This is not guesswork. Running the benchmark with V8's
`--trace-generalization` flag printed this line for class `P`:

```text
x:h{Any;const}->t{Any;mutable}
```

Read it as "field `x` went from `h` (the heap-object representation,
because of the `undefined`) to `t` (Tagged)". Here is what that costs:

<BenchBars suite="update-xy" n={1000000} title="Moving particles: x += vx, y += vy" highlight={['aos-class']} layouts={['aos', 'aos-class', 'aos-ctor']} caption="The class with TypeScript field declarations is the slow one: every update allocates a new HeapNumber." />

In this book's benchmark run, the class with field declarations was
about 3 times slower than the object literal and the constructor-only
class at 100,000 particles, and 5 to 7 times slower at 1,000 and at
1,000,000. The object literal and the constructor-only class were about
equal, which tells you the slowdown is not about classes; it is about
the field's first value.

<Callout kind="pitfall">
The fix is to make sure a number field's first value is a number: use
`declare` for fields the constructor always sets, or assign them only in
the constructor, and never start a numeric field as `null` or
`undefined`. Better still, do not depend on it at all: struct-of-arrays
columns, in the next chapter, sidestep the whole question.
</Callout>

<Callout kind="engine" label="Under the hood">
A `Float64Array` has no per-element representation to widen: it stores
raw 64-bit doubles side by side, with no tags and no boxes<Cite id="mdn-typed-arrays" />,
and V8's pointer compression post recommends Float64 typed arrays for
number-crunching code<Cite id="v8-pointer-compression" />. That is why
Viscosity's columns are `Float64Array`s: whatever the source declared, a
column of doubles stays a column of doubles. It also means a
TypeScript-aware Viscosity pass can fix the slow class for free, since
the compiler reads the field's declared `number` type before any of it
reaches the engine.
</Callout>

## What you learned

- A **field representation** is how V8 stores one field (Smi, Double,
  heap object or Tagged), recorded in the hidden class.
- A field only **widens**: to the lowest rung that fits every value it
  has held. Smi plus a fraction is Double; a number plus a heap object
  is Tagged.
- A Double field can be updated in place; a Tagged field keeps numbers
  as immutable HeapNumbers, so every update allocates.
- A TypeScript field declaration (`x: number;`) becomes a real class
  field that starts as `undefined`, which made this book's class several
  times slower; `declare`, or constructor-only fields, avoid it.
