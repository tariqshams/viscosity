## The same string twice

In the TypeScript VM, `heap.copyString('hi')` hands back the same object
every time it is given `hi` (the chapter *String interning*), which is
why comparing two strings there is one identity test. drip-rs keeps the
idea and changes the handle. A string value is a `StrRef`, from
`src/object.rs` (comments left out):

```rust
pub struct StrRef {
    pub handle: Gc<ObjString>,
    pub hash: u32,
}

pub struct ObjString {
    pub chars: Box<str>,
    pub hash: u32,
}
```

The hash is stored twice: in the object, and in every handle to it. The
handle's extra 4 bytes are free, because a `Value` is 16 bytes whatever
it holds (the chapter *Values in Rust* measured it), and this chapter is
about what they buy. `chars` is a `Box<str>` rather than a `String` (the owned string of
*Slices and strings*): an
interned string never grows, so it needs no capacity, and on rustc 1.97
here `Box<str>` is 16 bytes where `String` is 24.

</Figure>

<Analogy title="a library card with the shelf number printed on it">
If every library card has the book's shelf number printed on it, the
librarian can file and find cards by that number without ever walking
into the stacks; only when two cards share a shelf number does anyone go
and compare the books themselves.
<span slot="breaks">Shelf numbers are chosen; a hash is computed, and
two different strings can share one, which is why interning still
compares the characters when hashes match.</span>
</Analogy>

## A table that never sees the heap

The table's methods, in `src/table.rs`, take a key and nothing else:

```rust
pub fn get(&self, key: StrRef)
    -> Option<Value>
pub fn set(&mut self, key: StrRef,
    value: Value) -> bool
```

The hash comes from the key, and two keys are equal exactly when their
handles are, because strings are interned. That matters because tables
live *inside* heap objects: every instance has `fields: Table`, every
class `methods: Table`. Suppose, as a design experiment, that `set` had
to read the strings arena to hash a key:

```rust
let strings = &self.heap.strings;
self.heap[instance].fields
    .set(strings, name, value);
// error[E0502]: cannot borrow `self.heap`
//   as mutable because it is also
//   borrowed as immutable
```

`heap[instance]` borrows the whole heap mutably (the chapter *Heap
objects in an arena*), and the strings arena is part of it. Carrying
the hash in the handle removes the need, so the real `SetProp` writes
the field with `object.fields.set(name, value)`.

## The interner

Interning is the one place that compares characters. From `src/gc.rs`
(rewrapped):

```rust
pub fn intern(&mut self, chars: &str)
    -> StrRef {
    let hash = hash_string(chars);
    match self.interned.find_string(
        &self.strings, chars, hash) {
        Some(s) => s,
        None => self.add_string(
            chars.into(), hash),
    }
}
```

`interned` is a `Table` whose keys are every live string. `find_string`
probes it by hash, and only when a key's hash matches does it compare
the text, read from the strings arena it was handed; borrowing
`self.interned` and `self.strings` together is fine, because inside the
heap's own method rustc can see they are different fields. `add_string`
allocates the `ObjString` and records it with
`self.interned.set(s, Value::None)`: the table is used as a set, and
the value means nothing. The TypeScript `copyString` pushes the new
string as a temporary root while it does this; drip-rs need not,
because the heap never collects on its own.

<Analogy extra title="a phone that will not save a contact twice">
Type a name into some phones and, before saving a new contact, they
offer the one you already have with exactly that name; so the whole
phone has one entry per name, and anything that refers to "Ada" means
the same entry.
<span slot="breaks">A phone may keep "Ada" and "ada" as two people, as
the interner does; but a phone never deletes a contact by itself, while
drip-rs's collector drops interned strings that nothing else uses.</span>
</Analogy>

The VM has a second door, `intern_owned(String)`, for a string it has
just built, such as the result of `+` in `Vm::add`, which joins with
`[self.heap.str(a), self.heap.str(b)].concat()`. Handing over the
`String` lets the heap keep that very allocation: `into_boxed_str` only
reallocates to drop spare capacity<Cite id="rust-std-string" />, and
`concat` reserves exactly the joined length. `intern` has to copy,
because it was only lent a `&str`.

<Examples of="string-interner">

```rust
let a = heap.intern("hello");
let b = heap.intern_owned(
    String::from("hel") + "lo");
assert_eq!(a, b);
assert_ne!(a, heap.intern("world"));
```

```drip
print "dr" + "ip" == "drip";   # true
print str(42) == "42";         # true
```

```rust
let lost = heap.intern("lost");
heap.collect(&[&class]);
assert_ne!(heap.intern("lost"), lost);
```

</Examples>

The first is from `gc.rs`'s own tests: text built at run time and text
written in the program intern to the same `StrRef`, and different text
to a different one. The second shows it from Drip: `+` builds `drip`
and interns it, so `==` compares two handles and prints `true`, and
`str(42)` interns its result too. The third is also from the tests
(trimmed): the interned table holds strings *weakly*, so after a
collection whose roots never reach `"lost"`, the table has forgotten it,
and interning `"lost"` again makes a new string.

<Callout kind="definition">
A **string interner** maps each distinct string to one id: given some
characters, it either finds the id it handed out before or stores the
string and hands out a new one, so equal strings compare by id. In
drip-rs the interner is the heap's `interned` table, the id is a
`StrRef` (handle plus hash), and the collector deletes entries for
strings nothing else reaches.
</Callout>

<Formal title="What interning promises">

```text
intern(s) = intern(t)  ⇔  s = t
```

<span slot="read">Interning two strings gives the same handle exactly
when the two strings have the same characters, so comparing handles is
the same as comparing text.</span>
</Formal>

The hash is FNV-1a<Cite id="lcn2-fnv" />, as in TypeScript
(rewrapped):

```rust
pub fn hash_string(s: &str) -> u32 {
    let mut hash: u32 = 2_166_136_261;
    for byte in s.bytes() {
        hash ^= u32::from(byte);
        hash = hash
            .wrapping_mul(16_777_619);
    }
    hash
}
```

`wrapping_mul` is TypeScript's `Math.imul`, a multiply that keeps the low
32 bits. One difference: drip-rs hashes UTF-8 bytes and TypeScript
UTF-16 code units, so the two agree only on ASCII; nothing a program can
print depends on a hash.

## Two columns, with tombstones

The table itself is the TypeScript one, struct of arrays and all:

```rust
pub struct Table {
    count: usize,
    keys: Vec<Option<StrRef>>,
    values: Vec<Value>,
}
const TOMBSTONE: Value = Value::Bool(true);
```

An empty slot is `(None, Value::None)` and a deleted one
`(None, Value::Bool(true))`, a **tombstone**, exactly the TypeScript
encoding with `None` for `null`; `count` includes tombstones, because
they lengthen probes too. `find` walks from `key.hash & mask`, remembering
the first tombstone it passes with `tombstone.get_or_insert(index)`, so
that `set` reuses it. The keys below really collide: by FNV-1a, `y`,
`a`, `len` and `key` all have `hash & 7 == 4`.

<TableSteps client:visible />

Why two columns in Rust? A `Vec` of pairs would not allocate per entry
either, but a pair pads: measured here, `Option<StrRef>` is 12 bytes and
`Value` 16, while `(Option<StrRef>, Value)` is 32. Two columns use 28
bytes a slot, and probing mostly reads only the denser `keys`.

<Callout kind="engine" label="Under the hood">
Interning moves work from comparing to creating. Every string the VM
makes, every `+` and every `str()`, is hashed and looked up once; after
that, `==` between strings, global lookups and field lookups compare
handles, never characters. The `strings` benchmark, whose loop builds
and interns over a million strings with `+` and `str`, is where that
creation cost lives: in the 2026-11-02 run drip-rs beat the TypeScript
VM by only 1.26 times there, against 3.7 to 4.9 times on every other
program (*Profiling the Rust VM* looks at where the time goes).
</Callout>

## What you learned

- A **`StrRef`** is a string handle plus the string's hash, and costs
  nothing extra inside a 16-byte `Value`.
- Keys carry their hash and are interned, so a **table never needs the
  heap**, which lets tables live inside heap objects without borrow
  conflicts.
- The **string interner** is the heap's `interned` table: `intern`
  hashes, probes, compares characters only on a hash match, and
  allocates only for a new string; the table holds strings weakly.
- drip-rs's table is the TypeScript one: two columns, `(None,
  Value::None)` empty, `(None, Value::Bool(true))` a **tombstone**.
