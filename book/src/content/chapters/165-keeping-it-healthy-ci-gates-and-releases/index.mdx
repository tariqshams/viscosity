## It worked on my machine

On 31 October 2026, the commit that added the fuzzer was pushed to
GitHub, and a fresh machine there ran the engine's Rust tests. One failed
(from the job's log, trimmed and wrapped):

```
test a_fixed_seed_fuzz_run_finds_nothing
  ... FAILED
Error [ERR_MODULE_NOT_FOUND]: Cannot find
  package 'acorn' imported from
  .../frontend-js/src/index.ts
```

`fuzz.rs` runs `fuzz.mjs`, which loads the TypeScript engine, which
imports acorn. Where the test was written, `engine/ts/node_modules` was
already full; the fresh machine had only what the repository said to
install. One added step, `npm ci` in `engine/ts`, fixed it. A check that only ever runs where its
inputs are already present cannot tell you that they are missing.

<Analogy title="a recipe in someone else's kitchen">
A recipe you have only ever cooked in your own kitchen hides what you
never wrote down: the spice that is always in your cupboard, the oven
that runs hot. Hand it to a new cook in an empty kitchen every morning,
and the missing lines show up on the first day.
<span slot="breaks">A new cook improvises when something is missing; a
CI machine does exactly what the workflow says and stops at the first
step that fails, which is what makes the gap visible rather than
papered over.</span>
</Analogy>

`npm ci`, the install command for automated machines, has the same
character. A **lockfile** (`package-lock.json`) records the exact version
of every package to install, and while `npm install` quietly updates it
when it disagrees with `package.json`, `npm ci` "will exit with an
error, instead of updating the package lock"<Cite id="npm-ci-docs" />;
it caught five workspace packages missing from this repository's
lockfile that nobody had noticed.

## The workflow

**Continuous integration** (CI) means that every change is built and
checked, automatically, on a machine set up from scratch. This
repository describes its CI in `.github/workflows/ci.yml`, which GitHub
Actions runs on a fresh virtual machine, a **runner**, for every job.
Step through a push:

<CiSteps client:visible />

<Callout kind="definition">
**Continuous integration** runs every check on every change, on a
**fresh machine** that has only what the repository says to install. A
change is healthy when every **gate** (every check that can fail the
run) passes there. It catches what passes on your machine only because
of something your machine has.
</Callout>

<Examples of="continuous-integration">

```yaml
on:
  push:
  pull_request:
concurrency:
  group: >-
    ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

</Examples>

`on` runs the workflow on every push and pull request. `concurrency` is
a **concurrency group**: runs with the same group string (the workflow
and the branch) never run side by side, and with `cancel-in-progress:
true` a newer run cancels the one still going<Cite id="gha-concurrency" />,
since only the latest commit's result matters. That is not rare here: of the 62 runs GitHub
listed for the repository between 31 October and 2 November, 19 were
cancelled by a newer push. The workflow's five jobs (`engine-ts`,
`engine-rust`, `drip`, `book` and `website`) run side by side, so one red
job never hides the others.

<More title="The five jobs">

```
job          what it runs
engine-ts    npm ci, tsc --noEmit, vitest,
             npm pack + install the CLI
engine-rust  npm ci (TS reference), fmt,
             cargo test, clippy -D warnings,
             wasm32 build, cargo package
drip         vitest; cargo test --release,
             clippy (book/companion)
book         check_chapters, vitest, build,
             link check, Playwright smoke
website      npm ci, build, link check
```

All run on `ubuntu-latest`, and the workflow sets `permissions:
contents: read`, so a job can read the repository but not change it.
</More>

<Prompts ids={['ci-def', 'ci-concurrency']} />

Two caches save downloading and compiling everything on every push,
keyed so that they can never serve something stale. `actions/setup-node` keeps npm's download cache under a key built
from a hash of each `package-lock.json`<Cite id="setup-node-readme" />:
the same lockfile gives the same key and a hit, and a changed one a new
key and a miss. `Swatinem/rust-cache` keeps the compiled *dependencies*,
under a key that includes the rustc version, and deliberately not the
workspace's own crates<Cite id="rust-cache-readme" />, so Viscosity
itself is compiled afresh on every run.

## The gates

Steps in a job run in order, and the first that fails ends the job, the
later ones shown as skipped. Each step that can fail the job is a
**gate**, and every gate exists because of a particular kind of mistake.
Step through seven mistakes and the gate that stops each:

<GateSteps client:visible />

The `engine-rust` job runs five. **Format**: `cargo fmt --all --check`
exits with 1 if rustfmt would change a file<Cite id="rustfmt-readme" />,
and comes first because it takes seconds. **Test**: `cargo test
--workspace`, 77 tests in 14 binaries when I ran it (all passing),
holding most of this Part together: parity (`parity: 190/190 (54
Python)`), the differentials, early errors, the multi-file CLI,
profiles, and a 200-program fuzz run. **Clippy**: `cargo
clippy --workspace --all-targets -- -D warnings` turns every lint
warning into an error<Cite id="clippy-readme" />. **WebAssembly**: the
engine must still build for `wasm32-unknown-unknown`. **Package**:
`cargo package --workspace --no-verify --allow-dirty` proves every crate
can still be packaged for crates.io.

<Figure caption="What each job checks directly (filled) and what it relies on (ring): parity reads the TypeScript engine’s output, and the book’s checker and smoke test run Drip and both engines." takeaway="No single job protects everything; together they cover every part.">
  <GateMap />
</Figure>

A mistake gets through only if **every** gate misses it, and a gate
catches only what it was written to look for: the five bugs of *TypeScript against Rust: differential tests, fuzzing and
shrinking* passed every gate until a fuzzer was added.

<Prompts ids={['gt-skip', 'gt-new-kind']} />

Clippy with `-D warnings`, on a small file written to trip it (trimmed):

```

3 |     if v.len() == 0 {
  |        ^^^^^^^^^^^^ help: using
```

A diagnostic in the full sense of *explain, code frames and diagnostics
in Rust*: a level, a message, a position, the code, and a label.

The parity fixtures in `tests/expected/` are the TypeScript engine's
output, committed, so the Rust half of parity needs no TypeScript to
run. The price is a rule: after changing the reference, run `node
scripts/gen_expected.mjs`, then `cargo test`, and commit both. A test,
`fixtures_match_the_programs_exactly`, fails with `run node
scripts/gen_expected.mjs; missing [...], stale [...]` when the fixture
folder and the program list disagree.

The `book` job runs the chapter checker (frontmatter, concept order,
citations, code widths, the time budget, and every exercise), the unit
tests, the reference merge, the Astro build, a link check, and a smoke
test that opens the built site in Chromium at 440 by 956 pixels and
uses it, the Playground on both engines included. On 1 November it
caught two pages that did not fit a phone. `engine-ts` packs
`@viscosity/cli` the way npm publishes it and installs the tarball in an
empty folder, so it tests what a user would download.

<Analogy extra title="security at an airport">
Before a flight you pass several checks: a person compares your face
with your passport, a scanner looks inside your bag, an arch looks for
metal. Each catches things the others cannot.
<span slot="breaks">Security staff notice odd behaviour nobody wrote a
rule for; a gate catches only what it was written to look for.</span>
</Analogy>

## Releasing

<Analogy extra title="a ferry leaving">
Up to the moment a ferry sails you can fix anything on board. Once it
has sailed, whatever was on it is on the other shore for good, and the
only remedy is the next ferry; so the crew walks the same checklist on
the quay every time.
<span slot="breaks">A ferry can turn back. A published version cannot:
crates.io and npm both refuse to let a version number be used
twice.</span>
</Analogy>

Viscosity ships the six Rust crates to crates.io, and `@viscosity/cli`
and `@viscosity/wasm` to npm.

<Callout kind="definition">
A **release process** is the repeatable set of steps that turns one
commit into published, versioned packages: choose the version number,
record what changed (a **changelog**), build each package, check it as a
user would get it, and then **publish** it to its registry. Publishing
is the one step that cannot be undone: a crates.io version "can never be
overwritten, and the code cannot be deleted"<Cite id="cargo-publishing-guide" />,
and an npm name and version can never be used again<Cite id="npm-publish-docs" />.
</Callout>

<ReleaseSteps client:visible />

The version lives in three files: `[workspace.package] version` in
`engine/rust/Cargo.toml`, which all six crates inherit<Cite id="cargo-workspaces" />,
and the two `package.json` files. Internal crate dependencies carry a
version beside their path, because crates.io accepts no path-only
dependencies<Cite id="cargo-specifying-deps" />. `scripts/release.sh`
is the whole procedure: it checks the tokens (without printing them), a
clean git tree, that the three versions agree and that its crate list
is in dependency order, runs both test suites, and only then publishes.
The heart of it (rewrapped):

```bash
for crate in "${CRATES[@]}"; do
  if crate_published "$crate"; then
    step "$crate $VERSION is already" \
      "on crates.io; skipping"
    continue
  fi
  step "cargo publish -p $crate"
  (cd "$RUST" && cargo publish -p "$crate")
  wait_for_index "$crate"
done
```

<Examples of="release-process">

```
$ scripts/release.sh --dry-run
release.sh: .../cli/package.json is
  0.0.3 but the crates are 0.0.2
```

</Examples>

That is the first check, as it would speak if one `package.json` were
bumped and the workspace not: nothing is built or uploaded. In the loop,
`CRATES` lists `viscosity-vir` first, because each crate needs its
dependencies on crates.io already; `crate_published` skips a version the
crates.io API already has; and `wait_for_index` polls the index, because
cargo's own wait gives up after 60 seconds. A step that can be repeated without harm, as
this whole loop can, is **idempotent**. Here is how it went on
2026-11-02:

<PublishSteps client:visible />

The npm packages went out at 0.0.1 with `--npm-only`, and the crates
with `--crates-only`; crates.io answered the sixth crate, `viscosity-wasm`,
with HTTP 429, a limit on how quickly one account may create *new* crate
names, and because the loop asks before it uploads, the same command
about ten minutes later skipped the five and published the sixth. That
evening the version moved to 0.0.2 in all three files, and the npm
packages were published again (the CLI gained a README, and both carry a
corrected dataclass message); the crates were not, so crates.io still
serves 0.0.1, and `cargo install viscosity-cli` prints `viscosity
0.0.1`.

<Prompts ids={['publish-permanent', 'skip-published']} />

<More title="Packaging the crates, and Cargo's caret rule">
The first `cargo package` here found two problems, both fixed since:
`viscosity-core` failed with "all dependencies must have a version
requirement specified when packaging. dependency `viscosity-vir` does
not specify a version" (the fix is a version beside the path), and
`crates/vir` shipped without its LICENSE text. Before the first upload,
`cargo package -p viscosity-core` on its own also failed to verify ("no
matching package named `viscosity-vir` found"), because verification
looks on crates.io; `--workspace` packs `viscosity-vir` first and
verifies against it, which is why the dry run uses it. Both npm packages
are scoped, which npm treats as private unless
`"publishConfig": { "access": "public" }` says
otherwise<Cite id="npm-publish-docs" />.

<Figure caption="What three caret requirements accept. The range always ends where the left-most non-zero part would change; for 0.0.1 that leaves only 0.0.1 itself." takeaway="Under Cargo's caret rule, every 0.0.z release is incompatible with the last.">
  <CaretRanges />
</Figure>

Cargo's default requirement is the caret, so `viscosity-core = "0.0.1"`
means `>=0.0.1, <0.0.2`<Cite id="cargo-specifying-deps" />. There is no
changelog yet: the commit history is the only record of what changed.
</More>

## What you learned

- **Continuous integration** runs every gate on every push, on a **fresh
  runner**; a concurrency group cancels superseded runs, and caches are
  keyed by a **hash** of their inputs.
- A job's first failing **gate** skips the rest; a mistake gets through
  only if every gate misses it.
- A **release process** ends in a permanent publish; `release.sh`
  checks, tests, then publishes the crates in **dependency order**,
  skipping what is there, so a re-run is safe.
- 0.0.1 went to both registries on 2026-11-02; the npm packages are now
  at 0.0.2, the crates still at 0.0.1.
