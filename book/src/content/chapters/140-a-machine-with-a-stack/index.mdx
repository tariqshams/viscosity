## Where do the half-finished answers go?

The tree-walker never had to think about this. To evaluate `1 + 2 * 3`
it called itself for `2 * 3`, and the `6` came back as a return value,
held in a JavaScript variable until the `+` needed it; the host
language's call stack quietly kept every half-finished answer for it.

Bytecode has no recursion to lean on. `const 1, const 2, const 3, mul,
add` is a flat list, and while the machine works out `2 * 3`, the `1`
has to wait *somewhere*; then the `6` has to wait somewhere until `add`
runs. The answer is a stack that the VM keeps for itself, with the
newest value always on top.

<Analogy title="a pile of plates">
In a canteen, clean plates are stacked in a pile, and you only ever
touch the top one: put a plate on, take a plate off. An instruction
like `mul` is a cook who takes the top two plates, combines what is on
them, and puts one plate back. Nobody needs to know *where* any plate
is, only that the one they want is on top.
<span slot="breaks">A real pile only lets you see the top plate; the VM
can look at the second or third value down without moving anything (and
later, in *Locals as stack slots*, reach a value directly by its
position), which no canteen allows.</span>
</Analogy>

<Analogy extra title="a calculator with an Enter key">
Some old scientific calculators had no `=` key. To work out
`(1 + 2) × 3` you typed `1`, Enter, `2`, `+`, `3`, `×`: each number
went onto a little stack inside the calculator, and each operation took
its inputs from the top of that stack and left its answer there.
<span slot="breaks">Those calculators held only four values; Drip's
stack has room for 65,536, because it also holds every running
function's local variables, as the chapter *Frames: calling and
returning in the VM* shows.</span>
</Analogy>

## The stack is one array

Drip's stack is a big array made once, at full size, plus a number,
`sp` (the **stack pointer**), which is the index of the next free slot.
These are the real lines from `companion/ts/src/vm/vm.ts`, rewrapped to
fit the page:

```ts
readonly stack: Value[] =
  new Array(STACK_MAX).fill(null);
sp = 0;

push(v: Value) {
  this.stack[this.sp++] = v;
}
pop(): Value {
  return this.stack[--this.sp];
}
peek(distance: number): Value {
  return this.stack[this.sp - 1 - distance];
}
```

`STACK_MAX` is 65,536 (`FRAMES_MAX * 256`, room for 256 slots in each
of 256 nested calls), and `fill(null)` puts `null` in every slot, so
the array is complete before the program runs. `push` writes the value
into slot `sp` and *then* adds one to `sp` (that is what `sp++` after
the name means); `pop` takes one from `sp` *first* (`--sp`, before the
name) and reads that slot, which is the top. `peek(0)` reads the top
without removing it, `peek(1)` the value under it, and so on. Nothing is
allocated or freed per value; only `sp` moves, and the slots above it
are simply ignored until something is pushed there again.

<Callout kind="definition">
A **stack machine** is a VM whose instructions take their inputs from
the top of a value stack and push their results back onto it. Because
the inputs are always "the top few values", most instructions do not
need to say where their inputs are, so most need no operands at all.
</Callout>

<Formal title="Stack effects">

```text
const k :      → constants[k]
add     : a b  → a + b
print   : v    →
```

<span slot="read">Each line says what an instruction needs on top of the
stack (left of the arrow, with the top value written last) and what it
leaves there instead (right of the arrow). const needs nothing and
leaves a constant; add needs two values, a and then b on top, and
leaves their sum; print needs one value and leaves nothing.</span>
</Formal>

<Examples of="stack-machine">

```text
print 1 + 2;
const '1'  →  [1]
const '2'  →  [1, 2]
add        →  [3]
print      →  []
```

```text
print (1 + 2) * 3;
const '1'  →  [1]
const '2'  →  [1, 2]
add        →  [3]
const '3'  →  [3, 3]
mul        →  [9]
```

```text
print price * qty + 1;
load.global 'price' → [4]
load.global 'qty'   → [4, 3]
mul                 → [12]
const '1'           → [12, 1]
add                 → [13]
```

</Examples>

Each line is one instruction and the stack after it, with the top on
the right (the script's own slot 0 is left out). In the first, two
values go on, `add` turns them into one, and `print` takes it away,
leaving the stack as it was: every statement does that. The second shows
that brackets change the order of the instructions, not the machine:
the sum is finished before the `3` is pushed, so the stack never holds
more than two values, where `1 + 2 * 3` needed three. The third is the
line from *Why bytecode?* with `price` set to 4 and `qty` to 3:
`load.global` pushes a variable's value exactly as `const` pushes a
constant's, so to the stack a variable is just another way of getting a
value onto the top.

## The instruction pointer

The VM also needs to know where it is in the code, and that is one
number too. Inside `run`, three small helpers read the code and move it
(rewrapped to fit):

```ts
const readByte = () => code[frame.ip++];
const readShort = () => {
  frame.ip += 2;
  return (code[frame.ip - 2] << 8)
    | code[frame.ip - 1];
};
const readConstant = () =>
  constants[readShort()];
```

`ip` always holds the index of the *next* byte to read, and every read
moves it on, so reading an instruction's operands also steps over them.
`readByte` reads one byte, for the opcode itself or a one-byte operand.
`readShort` reads a two-byte operand: it moves `ip` on by two first, then
rebuilds the number from the two bytes it has just passed (the high
byte shifted left by eight binary places, which multiplies it by 256,
combined with the low byte). `readConstant` reads a two-byte constant
number and looks the value up in the pool. So after a `const`, `ip` has
moved by three and lands exactly on the next opcode. (`ip` lives in
`frame` because every running function will get its own, in *Frames:
calling and returning in the VM*; for now there is one frame, the
script's.) Step through the VM running `print 1 + 2 * 3;`, watching
`ip` and the stack together:

<Analogy extra title="a finger on the page">
Reading a recipe aloud to someone who is cooking, you keep a finger on
the line you have reached, and move it down as you read; if a line
says "see the sauce on page 40", the finger jumps there. The finger is
`ip`: it marks where reading will continue, and it moves as a side
effect of reading.
<span slot="breaks">Your finger moves a whole line at a time; `ip`
moves a byte at a time, so an instruction with two operand bytes moves
it three places, and a finger that landed on an operand would read
nonsense.</span>
</Analogy>

<Callout kind="definition">
The **instruction pointer** (`ip`) is the position in the bytecode of
the next byte to run. Reading an opcode or an operand moves it on, so an
instruction finishes with `ip` pointing at the instruction after it.
Jump instructions change it on purpose.
</Callout>

<Examples of="instruction-pointer">

```text
print 7;
ip: 0 → 3 → 4 → 5 → 6
```

```text
{ let a = 2; print a + 1; }
ip: 0 → 3 → 5 → 8 → 9 → 10 → ...
```

```text
0013    | jump.unless        13 -> 20
ip after reading it: 16
if the condition is false: 16 + 4 = 20
```

</Examples>

The first shows `ip` at the start of each instruction of `print 7;`:
`const` takes it from 0 to 3, `print`, `none` and `return` one byte each.
The second is the block from *Reading bytecode back: a disassembler*: `load.local`,
with its one-byte operand, moves `ip` by two (from 3 to 5), between
two `const`s that move it by three. The third is the one place where
`ip` does not simply move on: after reading `jump.unless` and its
operand `ip` is 16, and if the condition is false the instruction adds
the distance, 4, to `ip`, so the next instruction run is the one at 20.
That is all a jump is, which the chapter *Branches and loops in
bytecode* builds on.

<Callout kind="engine" label="Under the hood">
V8's interpreter keeps the same two pieces of state in each running
function's stack frame: a pointer to the bytecode array being run, and
the offset of the current bytecode in it<Cite id="v8-sparkplug" />,
which is its version of `ip`. Its values live differently, though:
Ignition is a register machine, whose instructions name the registers
they read and write, with a special accumulator register as the
unwritten input and output of many of them, where Drip's always use the
top of a stack<Cite id="v8-ignition" />. The chapter *The dispatch
loop* compares the two.
</Callout>

## What you learned

- A **stack machine** keeps in-between values on a stack: each
  instruction pops its inputs and pushes its result, so most need no
  operands.
- Drip's stack is one array made at full size and `sp`, the next free
  slot; `push` writes and moves `sp` up, `pop` moves it down and reads,
  and `peek` looks without moving it.
- The **instruction pointer** is the index of the next byte; reading
  operands moves it past them (`readShort` by two), and jumps move it on
  purpose.
