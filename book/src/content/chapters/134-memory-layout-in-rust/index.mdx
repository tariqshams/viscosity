## How big is a particle?

In *How JavaScript stores numbers and objects* you had to piece
together what an object with six number fields really costs (a header,
a hidden class pointer, perhaps a boxed number per field), because
JavaScript has no expression that answers "how many bytes is this?".
Rust has one:

```rust
use std::mem::size_of;

struct Particle {
    x: f64, y: f64,
    vx: f64, vy: f64,
    mass: f64, health: f64,
}

fn main() {
    let n = size_of::<Particle>();
    println!("{n}"); // 48
}
```

The `use` line brings `size_of` in from the standard library's `mem`
(memory) module. The struct is the book's particle: six `f64`s, the
8-byte float JavaScript uses for every number. `size_of::<Particle>()`
asks for the size of the *type* (`::<...>`, the "turbofish", is how a
type is handed to a generic function), and it prints `48`: six times
8, with nothing added. No header, no hidden class, no boxes.

That number connects to *Cache lines and locality*: memory moves in
64-byte **cache lines**, so a particle fits one and a third times into
a line, and a loop that reads only `x` still drags all 48 bytes of
each particle through the cache.

## size_of: the distance to the next one

<Analogy title="train carriages on a platform">
To plan a platform, a station measures from the front of one
carriage to the front of the next, couplings included, because that is
what eight carriages in a row really take. `size_of` is that
front-to-front distance: the room one value takes in a row of them.
<span slot="breaks">Carriages in a real train can differ in length;
every element of a Rust array has exactly the same type and so exactly
the same size, which the compiler knows before the program ever
runs.</span>
</Analogy>

<Analogy extra title="a sheet of stamps">
To know how many stamps fit on a sheet, you measure from one
perforated edge to the next, white border and all, not only the
picture. A type's size counts its "border" too: unused bytes inside
it are part of every copy.
<span slot="breaks">Every stamp has a border, but many Rust types have
no unused bytes at all (`Particle` has none); and unlike a stamp, a
type can have size 0 and take no room whatever.</span>
</Analogy>

Here is what is inside some everyday Rust values, drawn to scale:

```rust
size_of::<Vec<f64>>()  // 24: + capacity
size_of::<Box<f64>>()  // 8: one address
```

<Run id="sizes" />

</Examples>

The first block is plain numbers, whose sizes the Rust Reference
fixes<Cite id="rustref-type-layout" />: a `char` is four bytes (enough
for any Unicode character) and the empty tuple `()` takes none. The
second is where guesses go wrong. A reference is one address, 8 bytes
on a 64-bit machine, whatever it points at; a slice reference adds a
length (the pair *Slices and strings* drew), which is how `xs.len()`
works without touching the data; a `Vec<f64>` adds a capacity, 24
bytes however many million numbers it holds, since those live on the
heap; a `String` is the same three words, being a `Vec` of UTF-8
bytes; and a `Box<f64>` is one address. The runnable one prints a
table (the third column, alignment, is the next section); here it
printed `Vec<f64>` as `24 8` and `Particle` as `48 8`, and `64 / 48`
rounds down to one whole particle per line.

One line deserves a second look. `Option<&f64>` is 8 bytes, like
`&f64`, because a reference is never address 0, so 0 can mean
`None`<Cite id="rust-std-option" />; `Option<f64>` is 16, because
every bit pattern of an `f64` is some number, so `None` needs a tag of
its own. That spare pattern is the **niche** of *Sum types in
memory*.

A common slip is to forget the two colons:

```rust
let n = size_of<f64>();
// error: comparison operators cannot
//        be chained
// help: use `::<...>` instead of `<...>`
let n = size_of::<f64>(); // 8
```

Without `::`, rustc 1.97 reads `size_of < f64 > ()` as two
comparisons in a row, and says so (trimmed above); its help line gives
the fix.

<Callout kind="definition">
**`std::mem::size_of::<T>()`** returns the size of the type `T` in
bytes: the distance from one `T` to the next in an array, including
any unused bytes inside `T`<Cite id="rust-std-size-of" />. It is worked
out by the compiler, so calling it costs nothing when the program runs.
</Callout>

<Formal title="Sizes of arrays">

```text
size([T; n]) = n × size(T)
size(T) = k × align(T), for some whole k ≥ 0
```

<span slot="read">An array of n values of type T takes n times the
size of one T, with nothing between them. And a type's size is always a
whole number of times its alignment (the next section), with 0 counting
as a multiple of anything.</span>
</Formal>

let you ask. TypeScript can only give the size of a typed-array slot;
where a plain `number` lives is the engine's choice. Python 3.13 says
24, because every float is a full object, with a reference count and
a type pointer in front of its 8 bytes.

## Alignment: where a value may start

`size_of::<(u8, u32)>()` is 8, not 5. To see why, you need the second
fact the table printed: **alignment**.

<Analogy extra title="booking a sports hall">
A sports hall takes half-hour bookings at any half hour, but the big
two-hour sessions may only start on the even hours (2, 4, 6), so the
courts can be set up the same way each time. A value is the same: a
`u8` may start at any address, a `u32` only at a multiple of 4, an
`f64` only at a multiple of 8.
<span slot="breaks">The hall's rule is a convenience for the staff;
the computer's rule comes from how its memory hardware fetches words,
and in Rust it is not a preference at all: a value at a wrong address
is a broken promise, as *Unsafe Rust* explains.</span>
</Analogy>

<Analogy extra title="lorry bays in a car park">
In a car park painted with a lorry bay every eight metres, a motorbike
can park anywhere, but a lorry only fits where a bay begins. Park a
motorbike at the start, and the lorry behind it cannot squeeze in right
after; it goes to the next painted line, and the tarmac in between is
left empty.
<span slot="breaks">A car park can be repainted on a whim; the
alignments of Rust's types are fixed by the target machine and the
compiler, and differ only between machines (an `f64` is aligned to 4
on many 32-bit ones).</span>
</Analogy>

Step through where each type may start, ending with the `(u8, u32)`
puzzle:

<AlignSteps client:visible />

The CPU wants this because it fetches memory in aligned chunks: an
aligned `f64` always lies inside one chunk (and one cache line, as 64
is a multiple of 8), while a misaligned one could straddle two, and
some CPUs refuse such loads outright.

<Examples of="alignment">

```rust
align_of::<u8>()    // 1: anywhere
align_of::<u16>()   // 2: even addresses
align_of::<f64>()   // 8
```

```rust
align_of::<(u8, u32)>()   // 4
align_of::<[f64; 4]>()    // 8
align_of::<Particle>()    // 8
```

```rust
let xs = [1.5f64, 2.5, 3.5];
for x in &xs {
    println!("{:p}", x);
}
// 0x7ffdbd4808b0
// 0x7ffdbd4808b8
// 0x7ffdbd4808c0
```

</Examples>

The first block is this x86-64 machine; the Reference says
alignments are platform-specific, usually equal to the size but not
always<Cite id="rustref-type-layout" />. The second shows the rule
for compound types: a tuple, array or struct is aligned like its most
demanding field. The third prints each element's address with `{:p}`:
in hexadecimal they go up by 8 and end in `0` or `8`, so each is a
multiple of 8. (The numbers change from run to run; the pattern does
not.)

Alignments belong to the target, too. Compiled for
`wasm32-unknown-unknown`, `size_of::<&f64>()` returned 4, since
WebAssembly's linear memory (*WebAssembly as a target*) has 32-bit
addresses, while `align_of::<f64>()` stayed 8.

<Callout kind="definition">
A type's **alignment** (`std::mem::align_of::<T>()`) is a power of
two, at least 1, and a value of that type may only be stored at an
address that is a multiple of it. A compound type's alignment is at
least the largest alignment of its fields, and its size is always a
multiple of its alignment<Cite id="rustref-type-layout" />.
</Callout>

<Formal title="The alignment rule">

```text
addr(v) mod align(T) = 0
align(S) ≥ max { align(F) : F a field of S }
```

<span slot="read">The address of any value v of type T leaves no
remainder when divided by T's alignment. And a struct S is aligned at
least as strictly as the most strictly aligned of its fields.</span>
</Formal>

## What you learned

- **`size_of::<T>()`** gives a type's size in bytes: the distance from
  one value to the next in an array. It costs nothing at run time.
- A reference is one address; a slice reference adds a length; a `Vec`
  or `String` adds a capacity: 8, 16 and 24 bytes on a 64-bit machine.
- **Alignment** says which addresses a type may start at: a multiple of
  `align_of::<T>()`, a power of two. Compound types take their fields'
  largest alignment.
- `Option<&T>` costs nothing extra, `Option<f64>` costs 8 more bytes:
  a niche, from *Sum types in memory*.

## Five bytes in eight

*Memory layout in Rust* ended on a puzzle: a `(u8, u32)` holds one
byte and four bytes, five in all, yet `size_of` says 8. You already
know half the answer, since the `u32` has alignment 4 and so may not
start at address 1; this chapter is the other half, the bytes that
fill the gap, and the attribute that lets you decide the layout
yourself.

<Analogy title="chapters that start on a right-hand page">
Many printed books start every chapter on a right-hand page, so when a
chapter ends on a right-hand page, the printer leaves the next page
blank. Nothing is printed there; it exists only so the next chapter
starts where it must. Those blank pages are padding: a `u32` "starts on
a right-hand page" (a multiple of 4), so the three bytes after a `u8`
are left blank.
<span slot="breaks">A printer does it for looks, and keeps the
chapters in the author's order; the compiler does it because the
hardware wants aligned values, and (unless you say otherwise) it may
move fields around to need fewer blank pages.</span>
</Analogy>

<Analogy extra title="a wedding hall with tables of eight">
A family of eight must sit at one table, together. If one guest has
already sat down at table one, the family goes to table two, and seven
chairs at table one stay empty. The hall is also booked in whole
tables, so a party of seventeen pays for twenty-four chairs.
<span slot="breaks">Latecomers could fill empty chairs; padding bytes
are never used for anything, and safe Rust cannot even read what is in
them.</span>
</Analogy>

The second picture has both kinds of padding in it. Step through the
compiler laying out a `u8`, an `f64` and another `u8`:

<PadSteps client:visible />

The first gap (the seven empty chairs) puts the `f64` at a multiple of
8. The second, at the end, is the hall booked in whole tables: the
struct's size must be a multiple of its alignment, so that in an array
the *next* struct's `f64` is aligned too.

<Examples of="padding">

```text
`TokC`: 12 bytes, alignment: 4 bytes
```

```rust
// size_of::<C3>() 24, a@0 b@8 c@16
```

```text
    discriminant: 1 bytes
    variant `Number`: 15 bytes
        padding: 7 bytes
        field `.0`: 8 bytes, alignment: 8

        padding: 3 bytes
        field `.0`: 8 bytes, alignment: 4
    variant `Bool`: 1 bytes
```

</Examples>

<Figure takeaway="A Value is a tag byte, padding up to its payload's alignment, and the payload; the biggest payload sets the size." caption="drip-rs's Value, drawn from that report: 16 bytes, aligned to 8. Five of its eleven variants shown; the other handles sit like List's.">
  <ValueLayout />
</Figure>

The first is rustc's own report for a token-like struct marked
`#[repr(C)]` (`kind: u8, start: u32, len: u16`), printed by the
nightly-only flag `-Zprint-type-sizes`, which the book ran with rustc
1.97: one byte of `kind`, three of padding so `start` lands on 4, two
of `len`, and two more at the end to reach 12, a multiple of 4. The
second is the diagram's struct, twice. With `#[repr(C)]` it is 24
bytes, of which 14 are padding; without it, rustc 1.97 put `b` first
and packed `a` and `c` behind it, and `offset_of!` reported 16 bytes
(the token struct, likewise, shrank from 12 to 8). The third is the
real thing, drip-rs's `Value`, drawn below: the tag-and-payload layout
of *Sum types in memory*, with a one-byte tag and each variant's
payload at its own alignment after it. A `Number`'s `f64` needs
offset 8, so seven bytes of padding come first; a `String` holds a
`StrRef` (a 4-byte handle and a 4-byte hash, aligned to 4) at offset 4,
filling bytes 4 to 11; a `Bool` sits right after the tag. The biggest
variant ends at byte 16, and 16 is a multiple of 8, so that is the
size. That is also why drip-rs can store each string's hash inside the
value for free: those bytes were there anyway.

<Callout kind="definition">
**Padding** is bytes the compiler leaves unused inside a type: before
a field, so that it starts at a multiple of its alignment, and at the
end, so that the size is a multiple of the type's alignment and the
next element of an array is aligned too<Cite id="rustref-type-layout" />.
</Callout>

<Formal title="The repr(C) layout rule">

```text
off₁ = 0
offᵢ = up(offᵢ₋₁ + sizeᵢ₋₁, alignᵢ)
A    = max(align₁ … alignₙ)
size = up(offₙ + sizeₙ, A)
up(n, a) = ⌈n / a⌉ × a
```

<span slot="read">The first field goes at offset 0. Each later field
goes at the end of the one before it, rounded up to the next multiple
of its own alignment. The struct's alignment A is the largest field
alignment, and its size is the end of the last field rounded up to a
multiple of A. "up of n and a" means the first multiple of a that is
at least n: the align_up of the last chapter's exercise.</span>
</Formal>

## Choosing a layout: repr

Rust's default layout, the one with no attribute, promises very
little: each field is aligned and fields do not overlap, and that is
all, so the order you write is not the order you get, and it may
change between compiler versions<Cite id="rustref-type-layout" />. That
freedom is what let rustc shrink `R3`. However, sometimes another
program reads your bytes: a C library expecting a C struct, a
WebAssembly host reading linear memory, a file format with fixed
offsets. Then you need a promise, and `#[repr(...)]` is how you ask
for one.

<Analogy extra title="a printed form">
A tax office's printed form puts every box at a fixed spot, so a
scanning machine can find "date of birth" without reading the rest.
Your own notes on the same facts can be arranged however is neatest.
`#[repr(C)]` is the printed form; the default representation is your
notes.
<span slot="breaks">A form's layout helps people too; `repr(C)` only
helps other programs, and fixing the offsets does not make a Rust
`String` field mean anything to C.</span>
</Analogy>

<Analogy extra title="shipping containers">
Containers have their corner fittings in exactly the same places, so
any crane in any port can lift any of them; the contents are each
shipper's business. A `repr` is that standard for a type's outside:
offsets and sizes others can rely on.
<span slot="breaks">Every container is the same size; each `repr(C)`
struct has its own layout, computed by a rule, and both sides must
apply the same rule to the same fields.</span>
</Analogy>

<Examples of="repr">

```rust
#[repr(C)]
struct TokC {
    kind: u8, start: u32, len: u16,
}
// 12 bytes, in this order, always
```

```rust
#[repr(u8)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum OpCode {
    Const,
    None,
    True,
    // ...
}
```

```rust
#[repr(align(64))]
struct Line { x: f64 }
// size_of 64, align_of 64

#[repr(C, packed)]
struct K3 { a: u8, b: f64, c: u8 }
// size_of 10, align_of 1
```

</Examples>

The first fixes `TokC`'s layout to C's rule, declaration order with
the padding from the formula: 12 bytes, and the same 12 bytes a C
compiler would produce, which is the point. The second is from
drip-rs's `chunk.rs` (trimmed): on an enum whose variants carry no
data, `#[repr(u8)]` makes the tag exactly one `u8`, so each opcode is
the byte that encodes it and writing one into a chunk is `op as u8`,
which costs nothing; the numbering is declaration order, matching the
TypeScript VM's opcode table. The third shows the two modifiers:
`align(64)` raises a type's alignment, so each `Line` starts its own
cache line (useful when two threads would otherwise fight over one
line), and `packed` removes the padding, leaving fields misaligned.

That last one has a sharp edge, and rustc guards it:

```rust
let k = K3 { a: 1, b: 2.5, c: 3 };
let r = &k.b;
// error[E0793]: reference to field of
//   packed struct is unaligned
// = note: creating a misaligned
//   reference is undefined behavior
let b = k.b; // fine: a copy, 2.5
```

A reference promises an aligned value, and `k.b` sits at offset 1, so
rustc 1.97 refuses to make one (the message above is its own, trimmed);
copying the field out into a local, as the last line does, is allowed,
because the compiler then reads it byte by byte.

<Callout kind="definition">
A **`#[repr(...)]`** attribute chooses a type's **representation**,
which decides its layout. The default (`Rust`) guarantees only aligned,
non-overlapping fields. `repr(C)` lays fields out in declaration order
by C's rule, so the layout is fixed. A primitive representation such
as `repr(u8)` makes a field-less enum exactly that integer type.
`align(N)` raises the alignment to N; `packed` lowers it, removing
padding<Cite id="rustref-type-layout" />.
</Callout>

<OtherLanguages title="The same 24-byte struct">

```rust
#[repr(C)]
struct C3 { a: u8, b: f64, c: u8 }
// size_of::<C3>() == 24
```

```c
struct C3 {
    uint8_t a; double b; uint8_t c;

/* sizeof(struct C3) == 24 (gcc 13) */
```

```ts
// No structs in memory; lay it out by
// hand in an ArrayBuffer, as Part II did:
const buf = new ArrayBuffer(24);
const v = new DataView(buf);
v.setUint8(0, 1);          // a

v.setUint8(16, 3);         // c
```

</OtherLanguages>

Rust with `repr(C)` and C agree byte for byte, which is what lets the
two share memory. TypeScript has no structs in memory at all; to get
the same bytes you choose the offsets yourself in an `ArrayBuffer`, as
*Memory is one long array* did, and nothing checks your arithmetic.

## What you learned

- **Padding** fills the gap before a misaligned field and the gap
  after the last one, so the size is a multiple of the alignment.
- The default representation may **reorder** fields to need less
  padding (16 bytes rather than 24), but promises no order.
- **`#[repr(C)]`** fixes declaration order by C's rule;
  **`#[repr(u8)]`** makes an enum one byte; `align` and `packed` raise
  or lower alignment, and a reference to a packed field is error E0793.
- drip-rs's `Value` is a tag, padding and a payload: 16 bytes.
