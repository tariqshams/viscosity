## How big is a particle?

In *How JavaScript stores numbers, objects and fields* you had to piece
together what an object with six number fields really costs, because
JavaScript cannot answer "how many bytes is this?". Rust can:

<Examples of="size-of">

```rust
use std::mem::size_of;

struct Particle {
    x: f64, y: f64,
    vx: f64, vy: f64,
    mass: f64, health: f64,
}

size_of::<Particle>()  // 48
size_of::<&f64>()      // 8: one address
size_of::<&[f64]>()    // 16: + length
size_of::<Vec<f64>>()  // 24: + capacity
size_of::<Option<&f64>>() // 8
size_of::<Option<f64>>()  // 16
```

</Examples>

Every number is what rustc 1.97 printed on x86-64 Linux. `size_of::<T>()`
asks for the size of a *type* (`::<...>`, the "turbofish", hands a type
to a generic function). The particle is six 8-byte `f64`s and nothing
else: 48 bytes, no header, no boxes, so with 64-byte cache lines a loop
that reads only `x` still drags all 48 bytes of each particle through
the cache. A reference is one address; a slice reference adds a length,
which is how `xs.len()` works without touching the data; a `Vec<f64>`
(and a `String`) adds a capacity, 24 bytes however many million numbers
it holds, since those live on the heap. The last two lines differ for a
good reason: a reference is never address 0, so 0 can mean `None` for
free<Cite id="rust-std-option" />, while every bit pattern of an `f64` is
some number, so `Option<f64>` needs a tag of its own (that spare pattern,
a *niche*, is the subject of the deep dive *Sum types in memory*).

<Analogy title="train carriages on a platform">
To plan a platform, a station measures from the front of one carriage to
the front of the next, couplings included, because that is what eight
carriages in a row really take. `size_of` is that front-to-front
distance: the room one value takes in a row of them, gaps and all.
<span slot="breaks">Carriages can differ in length; every element of a
Rust array has the same type and so the same size, known before the
program runs.</span>
</Analogy>

<Figure takeaway="Plain numbers are their own bytes; references and collections are a few machine words that point at the data." caption="Sizes in bytes on x86-64 Linux, from size_of with rustc 1.97. A slice reference is an address and a length; a Vec adds a capacity. Option<&f64> needs no tag, because an address is never 0.">
  <SizeBars />
</Figure>

<Callout kind="definition">
**`std::mem::size_of::<T>()`** returns the size of the type `T` in bytes:
the distance from one `T` to the next in an array, including any unused
bytes inside `T`<Cite id="rust-std-size-of" />. It is worked out by the
compiler, so calling it costs nothing when the program runs.
</Callout>

<More title="Run it, and the same question in other languages">

<Run id="sizes" />

C answers `sizeof(double)` with 8, as Rust does. TypeScript can only
report the size of a typed-array slot (`Float64Array.BYTES_PER_ELEMENT`
is 8); where a plain `number` lives is the engine's choice. Python 3.13's
`sys.getsizeof(1.5)` says 24, because every float is a full object with a
reference count and a type pointer in front of its 8 bytes.

</More>

## Alignment: where a value may start

`size_of::<(u8, u32)>()` is 8, not 5. The reason is **alignment**: a
`u8` may start at any address, but a `u32` only at a multiple of 4 and an
`f64` only at a multiple of 8, because the CPU fetches memory in aligned
chunks and a misaligned value could straddle two. Step through where each type may
start, ending with the `(u8, u32)` puzzle:

<AlignSteps client:visible />

<Examples of="alignment">

```rust
align_of::<u8>()        // 1: anywhere
align_of::<f64>()       // 8
align_of::<(u8, u32)>() // 4
align_of::<Particle>()  // 8
let xs = [1.5f64, 2.5, 3.5];
for x in &xs { println!("{:p}", x); }
// 0x7ffdbd4808b0
// 0x7ffdbd4808b8
// 0x7ffdbd4808c0
```

</Examples>

The first two lines are this x86-64 machine (alignments are
platform-specific<Cite id="rustref-type-layout" />); the next two show
that a tuple, array or struct is aligned like its most demanding field.
The loop prints each element's address with `{:p}`: they go up by 8 and
end in `0` or `8` in hexadecimal, each a multiple of 8.

<Callout kind="definition">
A type's **alignment** (`std::mem::align_of::<T>()`) is a power of two,
at least 1, and a value of that type may only be stored at an address
that is a multiple of it. A compound type's alignment is at least the
largest alignment of its fields, and its size is always a multiple of
its alignment<Cite id="rustref-type-layout" />.
</Callout>

## Padding: the bytes in between

So a `(u8, u32)` is one byte, three empty bytes so the `u32` lands on
4, and the `u32`. Those empty bytes are **padding**. Step through the
compiler laying out a `u8`, an `f64` and another `u8` in declaration
order:

<PadSteps client:visible />

The first gap (seven bytes) puts the `f64` at a multiple of 8. The
second, at the end, is there because the struct's size must be a
multiple of its alignment, so that in an array the *next* struct's `f64`
is aligned too.

<Examples of="padding">

```rust
struct R3 { a: u8, b: f64, c: u8 }
#[repr(C)]
struct C3 { a: u8, b: f64, c: u8 }
// size_of::<R3>() 16, b@0 a@8 c@9
// size_of::<C3>() 24, a@0 b@8 c@16
```

</Examples>

These are the same three fields twice, measured with `size_of` and
`offset_of!` under rustc 1.97. `C3` keeps the written order, as in the
diagram: 24 bytes, 14 of them padding. `R3`, with no attribute, is 16,
because rustc put `b` first and packed `a` and `c` behind it. Rust's default
layout promises very little: each field is aligned and fields do not
overlap, and that is all, so the order you write is not the order you
get, and it may change between compiler versions<Cite id="rustref-type-layout" />.

<Callout kind="definition">
**Padding** is bytes the compiler leaves unused inside a type: before a
field, so that it starts at a multiple of its alignment, and at the end,
so that the size is a multiple of the type's alignment and the next
element of an array is aligned too<Cite id="rustref-type-layout" />.
</Callout>

<Formal title="The repr(C) layout rule">

```text
off₁ = 0
offᵢ = up(offᵢ₋₁ + sizeᵢ₋₁, alignᵢ)
A    = max(align₁ … alignₙ)
size = up(offₙ + sizeₙ, A)
up(n, a) = ⌈n / a⌉ × a
```

<span slot="read">The first field goes at offset 0. Each later field goes
at the end of the one before it, rounded up to the next multiple of its
own alignment. The struct's alignment A is the largest field alignment,
and its size is the end of the last field rounded up to a multiple of A.
"up of n and a" means the first multiple of a that is at least n.</span>
</Formal>

drip-rs's `Value`, the tag-and-payload enum of *Tagging values at run
time*, measures 16 bytes, aligned to 8: a one-byte tag, then each
variant's payload at its own alignment, so a `Number`'s `f64` sits at
offset 8 after seven bytes of padding, and a cache line holds four
`Value`s.

<Figure takeaway="A Value is a tag byte, padding up to its payload's alignment, and the payload; the biggest payload sets the size." caption="drip-rs's Value, drawn from rustc's -Zprint-type-sizes report: 16 bytes, aligned to 8. Five of its eleven variants shown; the other handles sit like List's.">

## Choosing a layout: repr

When another program reads your bytes (a C library, a file format with
fixed offsets), you need a promise, and `#[repr(...)]` asks for one.

<Examples of="repr">

```rust
#[repr(C)]
struct TokC {
    kind: u8, start: u32, len: u16,
}
// 12 bytes, in this order, always

// adapted from drip-rs, src/chunk.rs
#[repr(u8)]
pub enum OpCode {
    Const,
    None,
    True,
    // ...
}
```

</Examples>

`#[repr(C)]` fixes `TokC`'s layout to C's rule in the formal box above:
declaration order, `kind` at 0, three bytes of padding, `start` at 4,
`len` at 8, and two bytes of end padding to reach 12, the same 12 bytes a
C compiler would produce (without the attribute the same fields took 8). On an enum whose variants carry no data, `#[repr(u8)]`
makes the tag exactly one `u8`, so in drip-rs each opcode *is* the byte
that encodes it, and writing one into a chunk is `op as u8`, which costs
nothing.

<Callout kind="definition">
A **`#[repr(...)]`** attribute chooses a type's **representation**, which
decides its layout. The default (`Rust`) guarantees only aligned,
non-overlapping fields. `repr(C)` lays fields out in declaration order by
C's rule, so the layout is fixed. A primitive representation such as
`repr(u8)` makes a field-less enum exactly that integer type. `align(N)`
raises the alignment to N; `packed` lowers it, removing
padding<Cite id="rustref-type-layout" />.
</Callout>

<More title="align and packed, and drip-rs's hash table, laid out">

Two modifiers complete the set. `#[repr(align(64))]` raises a type's
alignment: a `struct Line { x: f64 }` with it is 64 bytes and starts its
own cache line. `#[repr(C, packed)]` removes padding: a packed `C3` is 10
bytes, aligned to 1. Packed fields are misaligned, so `&k.b` is refused
with E0793, `reference to field of packed struct is unaligned`; copying
the field out, `let b = k.b;`, is allowed.

drip-rs's hash table keeps its keys and values in two `Vec`s, `keys:
Vec<Option<StrRef>>` and `values: Vec<Value>`. A key is 12 bytes (an
8-byte `StrRef` and a 4-byte tag, since every `u32` handle is valid and
there is no niche) and a value 16, so the two columns cost 28 bytes per
slot, while one `Vec<(Option<StrRef>, Value)>` would cost 32, rounded up
to the pair's alignment of 8 (all three sizes measured with rustc 1.97).
Probing past occupied slots reads only the 12-byte keys, five to a cache
line: *AoS vs SoA, measured* again, chosen by hand.

</More>

## What you learned

- **`size_of::<T>()`** is the distance from one value to the next: a
  reference is 8 bytes, a slice reference 16, a `Vec` 24.
- **Alignment** says which addresses a type may start at; **padding**
  fills the gaps so every field, and the next element, is aligned.
- The default representation may reorder fields; **`#[repr(C)]`** fixes
  C's order, `#[repr(u8)]` makes a field-less enum one byte.
