## Which arrays are tables?

A program is full of arrays, and only some of them are what *AoS vs
SoA, measured* called an array of structs, a table whose elements are
all records with the same fields; those are the only ones a column
layout can help, so the first job of Viscosity's analyses is to find
them, to work out what each column may hold, and to say, for each array
it passes over, why.

<Analogy title="a librarian and a set of encyclopaedias">
A librarian wants to move a shelf of encyclopaedias into a cabinet
with one drawer per volume. First she checks that it really is one
set: the same series and the same format all the way along, no volume
out on a long loan, and nobody planning to swap the whole shelf for a
different set tomorrow.
<span slot="breaks">She can see the shelf and judge it at a glance;
Viscosity cannot see the array at all, only the code that builds and
uses it, so it has to reason from every line that touches the array
instead of looking at it.</span>
</Analogy>

<Callout kind="definition">
**Collection discovery** finds the variables that hold an array of
same-shaped records: a `const` or `let` given a fresh array literal,
filled only with fresh object literals of one shape, and never given a
different value. Each one found becomes a **collection**; anything that
breaks the rules adds a **bailout** reason to it, and a collection with
any reason is left exactly as it is.
</Callout>

All of it runs on VIR, in `packages/core/src/analysis.ts` (so it works
for the Python front-end too), and *Lowering JavaScript to VIR* made it
easy on purpose: a variable initialised with an array literal is always
a binding, so every read of it is an explicit `load`.

## Candidates, then a worklist

The first pass files each `storeBinding` and `loadBinding` under its
binding. Then, trimmed from `analysis.ts`:

```ts
for (const binding of m.bindings) {
  if (binding.kind !== 'const'
    && binding.kind !== 'let') continue;
  const st = stores.get(binding.id) ?? [];
  const arrayStores = st.filter((x) =>
    ['array.empty', 'array.new']
      .includes(inst(x.args[0]).op));
  if (arrayStores.length === 0) continue;
  // … make collection c from that array …
  if (st.length > 1)
    bail(c, /* reassigned */);
}
```

<Examples of="collection-discovery">

```text
const ps = [];  … ps.push({ x: i });
ps (line 1) {x} → kept as array of
  objects
  · no loop reads or writes its fields,
    so a new layout cannot pay off

var ps = [];  … (the same program)
No arrays of objects found.
```

</Examples>

A binding that is not a `const` or `let` is skipped; one never given an
`array.empty` (`[]`) or `array.new` (`[a, b]`, of object literals) is
skipped too; the rest become candidates, and **any** second store is a
bailout, since the name may not always hold this array. The example (a
program, then the real `viscosity explain` output) shows both sides:
with `const`, `ps` is found (then kept, by the cost model's decision);
with `var`, which can be declared twice and used before its line, the
same table is never a candidate.

A load can also be passed to a function, where the parameter becomes
another name for the same array, so discovery is a small **dataflow
problem** (as in *Dataflow, fixpoints and constant propagation*): each
value either refers to the collection or does not, and the fact starts
at the loads and flows forward along **def-use edges**, from each value
to the instructions that use it. VIR is in SSA form, so every value
already has its list of uses, and no sets need carrying between blocks.

Every load of ps refers to it; both calls of step pass ps, so the parameter qs (%0) refers to it too, and its uses inside step are checked like any other.">

A worklist starts with every load and pops one at a time, and each use
of the popped value must be one Viscosity knows how to rewrite:
`ps.length`; `ps.push(r)` of one fresh object literal; `ps[i]`, whose
element is checked later; or a call of a known function whose every
call passes this same collection (the parameter then joins the
worklist). Anything else, such as `ps.map(...)`, is a bailout with a
reason. Step through it, with real VIR:

Refs(c) is the smallest set where:

<span slot="read">Refs of c, the values that refer to collection c, is
the smallest set with two properties: every load of c is in it; and
whenever a value in it is passed as argument k to a known function
(declared once, only ever called directly), and every call of that
function passes c in position k, then that function's parameter k is
in it as well. "Smallest" means nothing else gets in, which is exactly
what a worklist computes.</span>
</Formal>

## Is this field always a number?

A `Float64Array` column needs a fact no JavaScript program states: that
the field only ever holds **numbers** (a `Float64Array` quietly turns
`'far'` into `NaN`). Viscosity cannot ask, and it does not trust
TypeScript annotations either, since they are erased before the code
runs<Cite id="ts-basics" />; so it deduces the fact from the code.

<Callout kind="definition">
**Type inference** deduces the types of values from how they are made
and used, without annotations. In a dynamic language it is done per
value, at each point in the program. Viscosity's version answers one
question per value: is it provably a number?
</Callout>

In SSA every assignment makes a new value, each with its own fact, so
the facts are **flow-sensitive**: one name can have a different fact at
different points. Where paths meet, a phi joins its inputs into a
**union**, "a number *or* a string"; and since Viscosity's facts form a
lattice of only two levels, *number* above *maybe not* (all a
`Float64Array` needs), any union that is not all numbers is *maybe
not*.

<Figure takeaway="Each SSA value has its own fact; a phi joins them." caption="x is 1 on one path and 'one' on the other. x1 and x2 each have an exact fact; the phi x3 can be either, a union. Viscosity's lattice has only two levels, so the union is recorded as “maybe not a number”.">
  <UnionMerge />
</Figure>

Each value's fact comes from a small rule. Trimmed from
`analysis.ts`, where `n(v)` reads the current fact for `v`:

<Examples of="type-inference">

```ts
switch (i.op) {
  case 'const':
    return typeof i.value === 'number';
  case 'binop':
    return ARITH.has(i.operator!)
      && n(i.args[0]) && n(i.args[1]);
  case 'phi': return i.args.every(n);
  case 'param':  // every caller passes one
    return sites.every((s) =>
      n(s.args[i.index! + 1]));
  default: return false;
}
```

</Examples>

A constant is a number if its `typeof` says so; arithmetic counts only
when both sides are numbers (`1 + '1'` is `'11'`); a phi needs *every*
input to be one, which is the join; a parameter of a known function
needs every call site to pass one; and anything else is not a number.

## The loop problem

In a loop, the phi at the top depends on the addition at the bottom,
which depends on the phi; where do you start? Step through both answers:

<LatticeSteps client:visible />

<Callout kind="definition">
An **optimistic** analysis starts every value that may sit on a cycle
at the best answer ("number") and knocks down what a rule contradicts,
round after round, until nothing changes (a fixpoint). A
**pessimistic** one starts at the worst answer and adds only what it can
prove, so on a cycle it never starts: each value waits for the other.
</Callout>

Facts only fall and are finite, so the rounds end; even so, the code
stops after 1000 rounds and, if unsettled, throws away every guess (it
**fails closed**).

shows one variable observed with a different type at each point, and a
union where paths re-merge<Cite id="ts-narrowing" />. Languages designed
for inference can go much further and find every type with no
annotations at all, which the deep dive *Hindley–Milner type inference*
builds; the deep dive *Type and shape inference* takes Viscosity's
version further.

## Shapes from object literals

The other fact is the shape. Each object literal becomes a `record.new`
carrying its field list; the first list Viscosity meets becomes the
collection's shape, and every other one must be **equal** to it, order
included:

```ts
if (c.fields.length === 0)
  c.fields = [...r.fields!];
else if (JSON.stringify(c.fields)
    !== JSON.stringify(r.fields))
  bail(c, `${where}: records with ` +
    'different fields or field order');
```

<Callout kind="definition">
**Shape inference** deduces an object's layout (its fields and their
order) statically, from the code that creates the objects. Viscosity's
rule for combining the shapes of a collection is the strictest possible:
they must all be equal.
</Callout>

<Examples of="shape-inference">

```js
ps.push({ x: i, y: 0 });       // {x, y}
ps.push({ x: 1, y: 0, z: 2 }); // {x, y, z}
ps.push({ y: 1, x: i });       // {y, x}
```

</Examples>

Each push makes a `record.new` with the field list in its comment, and
no two lists are equal (the second has an extra field; the third has
the first one's fields in another order), so any two of these pushes in
one program make explain report "records with different fields or field
order". Why should order matter for the same data? Viscosity's rewritten
`push` is positional, taking each column's value from a fixed slot; and
JavaScript itself can tell the two apart (`Object.keys`,
`JSON.stringify`), as can V8, which gives them different hidden
classes<Cite id="v8-fast-properties" />.

<Prompts ids={['si-order']} />

<More title="Run it, and the other half of the shape check">

<Run id="order" />

Every record must also be **used exactly once**, by the push itself:

```js
const r = { x: i };
ps.push(r);
if (i === 5) r.x = 500; // refused
```

Here the `record.new` has two uses, the push and the `field.set`; after
a layout change there would be no object `r` any more, only a slot in a
column, so the write would go nowhere. In the language of *Alias
analysis and points-to*, `r` and `ps[5]` must alias, and Viscosity
refuses any record that has a second name; *Record shapes* comes back to
this rule.

V8 learns similar facts by watching rather than proving: its type
feedback records which shapes and number representations each operation
has seen, its optimising tiers specialise on that, and deoptimisation is
the way back when a guess turns out wrong<Cite id="v8-maglev" />.
Viscosity runs before the program and has no way back, so a guess has
to become a proof, which is why one string or one reordered literal is
enough to change its decision.

Try it: swap the field order in the push, push the same object twice,
add a `ps.filter(...)` call, or add `ps = [];` at the end (after changing
`const` to `let`), and read the reasons:

## What you learned

- **Collection discovery** finds `const`/`let` names given a fresh
  array literal and never reassigned, then follows "refers to this
  collection" from the loads along def-use edges, accepting only a few
  uses.
- **Type inference** gives each SSA value a fact (flow-sensitive, joined
  at phis); Viscosity's two-level lattice is "number" or "maybe not",
  solved by an **optimistic** fixpoint that fails closed.
- **Shape inference** takes the literals' field lists, which must be
  equal, order included.

Next: *Record shapes*, which turns the field lists and facts into
columns, and asks whether a shape can change after creation.
