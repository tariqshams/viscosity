## Three typos, one run

Say you have written twenty lines of Drip, and three of them have a
typo. One parser stops at the first and tells you about it. You fix it,
run again, meet the second, fix that, run again. Another parser tells
you all three at once. A third tells you about the three, and then
about forty more that are not really there, because it got lost after
the first.

You want the second parser. This chapter is about how to be it.

## What a syntax error is

<Callout kind="intuition">
Read “the cat sat on.” and you stop, because the sentence promised
something after “on” and delivered a full stop. You know exactly where
it broke: at the full stop, which is where you noticed. A parser is the
same kind of reader, and its rule book is the grammar.
</Callout>

In the Drip parser, every place where the grammar *requires* a
particular token goes through `consume`:

```ts
function consume(t, what) {
  if (check(t)) advance();
  else expected(what, t === ';'
    ? previous : current);
}
// e.g. at the end of a print statement:
consume(';', "';' after the value");
```

If the token is there, `consume` takes it. If not, `expected` builds
the message `expected <what>, found <token>` and reports it; it does
not throw (more on that below). For `print 1 +;` Drip says:

```
line 1: expected an expression, found ';'
```

and for `print 1 +` with nothing after it, the same with
`found end of file`. The format is `line N: message` (`errors.ts`), and
the token found is named as `';'`, `'print'`, `a string` or
`end of file`. The line is where the parser *noticed*, with one kind
exception: a missing `;` is reported on the line of the token before
it, where the `;` belongs, not at the first token of the next line.

<Callout kind="definition">
A **syntax error** is source code that breaks the grammar: at some
point the parser needs a certain kind of token and finds another. The
parser reports it with the line, the token where it noticed, and what it
expected. Nothing has run yet: syntax errors are found before the
program starts.
</Callout>

## Don't stop at the first

Reporting one error is easy: throw, and let the whole parse fail.
Reporting *several* is harder, because after an error the parser is in
the middle of something it no longer understands. If it carried on
from exactly where it stopped, it might treat the rest of a broken
statement as the start of a new one, and report errors that are only
echoes of the first. Those are called **cascading** errors, and they
send people hunting for problems that do not exist.

<Callout kind="intuition">
A pianist who loses their place does not keep playing the wrong notes
and hope. They skip ahead to the start of the next bar, where they know
exactly where they are, and carry on from there.
</Callout>

<Callout kind="definition">
**Error recovery** is what a parser does after a syntax error so that
it can keep parsing and report later errors too. It has two goals that
pull against each other: find as many **real** errors as possible, and
report no **cascading** ones.
</Callout>

## Panic mode

Drip uses the oldest and simplest strategy, with one flag. Every error
goes through `errorAt`, and `declaration()`, the function that parses
one statement, checks the flag when the statement is done:

```ts
// simplified from parser.ts
function errorAt(token, message) {
  if (panicMode) return; // an echo
  panicMode = true;
  reporter.error(token.line, message);
}
function declaration(): Stmt {
  let s: Stmt;
  if (match('let')) s = letDeclaration();
  // … class, fn
  else s = statement();
  if (panicMode) synchronize();
  return s;
}
```

The first error in a statement is reported and sets `panicMode`; any
more errors in the same statement are dropped, because they are
probably echoes. The parser does not stop: a failed `consume` reports
and carries on, building a tree that will never run. When the statement
is done, `synchronize()` clears the flag and throws tokens away until a
new statement probably starts: just after a `;`, just before a keyword
that begins a statement (`class`, `fn`, `let`, `for`, `if`, `while`,
`print`, `return`, `break`, `continue`, the set `STATEMENT_STARTS`), or
at the `}` that closes the block it is in. Braces opened while skipping
are skipped whole. Step through it on a four-line program with two
mistakes:

<Callout kind="definition">
**Panic mode** is error recovery by skipping. On an error the parser
abandons the current statement, discards tokens until it reaches a
**synchronization point** (a token after which the grammar is likely to
make sense again), and resumes normal parsing there.
</Callout>

The price is visible in the step-through: `x = 2;` was skipped
without being checked. If it had contained a mistake, that mistake
would only show up on the next run. Panic mode accepts that, because a
missed error costs you one more run, while a fake error costs you
confusion.

Some errors cost nothing at all. When the parser reads `a + b = 3;`, it
parses `a + b`, sees the `=`, and reports
`cannot assign to this expression`. That sets `panicMode` too, but the
parser is not lost: it carries on, takes the `;`, and `synchronize()`
stops at once, because the previous token is a `;`. Nothing is skipped.

## A syntax error stops everything

What happens to the statements that parsed fine? They are never run.
Here is the top of `run` in `companion/ts/src/drip.ts`:

```ts
const reporter = makeReporter();
const program = parse(scan(source),
  reporter);
if (reporter.errors.length)
  return { stdout,
    stderr: reporter.errors,
    exitCode: 65 };
// … resolve, and only then run
```

The scanner turns a mistake such as an unterminated string into an
error token, which the parser reports along with its own errors, so
both end up in `reporter.errors`. If anything went wrong, Drip prints the errors and stops
with exit code 65, the code its test suite uses for “this program is
not valid Drip”. Half a program is never run.

## What you learned

- A **syntax error** is a token the grammar did not allow. Drip reports
  the line, the token where it noticed, and what it expected.
- **Error recovery** lets a parser report several real errors in one
  run, without **cascading** errors that are only echoes.
- In **panic mode**, the parser reports only the first error of a
  statement, then skips tokens to a **synchronization point** (after a
  `;`, before a statement keyword, or at the `}` closing the block).
- Every statement takes at least one token before it synchronizes, so
  the parser can never get stuck.
- Some errors, like `cannot assign to this expression`, leave the
  parser in a known place, so nothing is skipped.
- If any error was reported, Drip runs nothing and exits with code 65.
