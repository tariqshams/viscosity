## A tree nobody needs

In the tree-walker, `print 1 + 2 * 3 - 4;` became a list of every token,
then a syntax tree, then a walk. Compiling that tree to bytecode would
mean building the whole tree, walking it once to write the bytes, and
throwing it away. Drip's bytecode compiler skips the middle: it parses
and writes bytes in the same breath, so the tree never exists.

## One token at a time

The compiler does not even ask for all the tokens at once: its scanner
hands out one token per `scanToken()` call (a test checks they are
exactly the tree-walker's tokens), and the compiler keeps two, `current`,
the lookahead it has not used yet, and `previous`, the one just
consumed. This is the real `advance`, from `vm/compiler.ts`:

```ts
function advance() {
  previous = current;
  for (;;) {
    current = scanner.scanToken();
    if (current.type !== 'error') break;
    errorAt(current, current.lexeme);
  }
}
```

A scanning problem comes back as an `'error'` token whose lexeme is the
message, so `advance` reports it and asks again.

<Callout kind="definition">
A **single-pass compiler** reads the source once, from start to end,
and produces its output during that one reading, without first building
a complete in-between form such as a syntax tree. It is quick and needs
little memory, but every decision must be made with only what it has
read so far.
</Callout>

<Examples of="single-pass-compiler">

```text
print 1 + 2;

0000    1 const               0 '1'
0003    | const               1 '2'
0006    | add
0007    | print
```

</Examples>

Four instructions, in the order the tokens were read. Notice what it
does *not* do: work out `1 + 2` itself, which a compiler holding the
whole tree could easily do (*constant folding*), so the VM adds the same
two numbers every time it runs this line.

<More title="Errors in one pass, and brackets">

```text
print 1 +;
print 2;

line 1: expected an expression, found ';'
```

The compiler had already written bytes for `print 1 +` when it met the
`;`, so it reports the error (in the tree-walker's exact words) and
throws the chunk away; nothing runs, not even `print 2`.

```text
print -(1 + 2) * 3;

0006    | add
0007    | neg
0008    | const               2 '3'
0011    | mul
```

`add` comes before `neg`, because the sum must finish before the minus
applies to it: brackets change the order of the bytes and emit none.

</More>

## Emit

Writing bytes is three small functions in `compiler.ts`, rewrapped:

```ts
function emitAt(line: number,
                ...bytes: number[]) {
  const c = chunk();
  for (const b of bytes) c.write(b, line);
}
const emit = (...bytes: number[]) =>
  emitAt(previous.line, ...bytes);
const emitConstantOp = (line: number,
    op: number, k: number) =>
  emitAt(line, op, (k >> 8) & 0xff,
    k & 0xff);
```

`emitAt` appends bytes to the current function's chunk, each tagged with
`line`; `emit` tags them with the line of `previous`, the token just
consumed; `emitConstantOp` writes an opcode and a two-byte constant
number, high byte first. Every rule writes code through these three.

<Analogy extra title="a till roll">
At a shop till, each item you scan prints one more line at the bottom of
the receipt, straight away, in the order you scanned it; nothing is ever
printed in the middle of the roll. The receipt is the chunk, scanning an
item is reading a token, and printing a line is emitting.
<span slot="breaks">The till prints exactly one line per item; the
compiler may read a token and emit nothing yet (a `+` waits for its
right operand), or emit several instructions for one token.</span>
</Analogy>

<Callout kind="definition">
To **emit** an instruction is to append its bytes to the end of the
chunk being compiled, each tagged with a source line. Emitting only
ever appends, so the order of the emit calls *is* the order in which the
VM will run the instructions.
</Callout>

<Examples of="emit">

```text
print 1;
print 2 +
  -"a";

0004    2 const               1 '2'
0007    3 const               2 'a'
0010    | neg
0011    2 add
0012    3 print
```

</Examples>

The line tags are chosen with care: `add` is emitted *after* its right
operand, while the compiler is already on line 3, but the rule for `+`
uses `emitAt(op.line, ...)`, the line of the `+` token, so an error in
the addition points at line 2, where the `+` is; `print` gets line 3,
the line of the `;` just consumed.

## Pratt rules that write bytes

The compiler parses expressions with the loop of *Pratt parsing*: the
same functions, in the same order, as the tree-walker's parser, except
that every rule emits code instead of returning a node. Here is the
part of `infix` for the plain binary operators, exactly as in the file:

```ts
default:
  parsePrecedence(INFIX_PREC[op.type]! + 1);
  emitAt(op.line, BINARY_OPS[op.type]!);
```

`INFIX_PREC` gives each operator its precedence and `BINARY_OPS` its
opcode. The rule compiles its right operand *first* and emits its own
opcode *after* (the left operand was emitted before the rule was
called): the children-first order of *Why bytecode*, falling out of the
order of two lines. The `+ 1` asks for strictly tighter operators, so
equal ones group to the left. Prefix rules work the same way: a number
emits `const` at once, a minus compiles its operand and then emits
`neg`. Watch the rules compile `print 1 + 2 * 3 - 4;`:

## An instruction for every comparison

Drip's VM has an opcode for each of the six comparisons, although
`a >= b` could be "not `a < b`". The reason is `NaN` (the result of
`0 / 0`): under IEEE 754 every `<`, `<=`, `>` and `>=` with `NaN` is
false (*How JavaScript stores numbers, objects and fields*):

```text
print 0 / 0 >= 1;    # false
print !(0 / 0 < 1);  # true
```

Compiling one as the other would make the VM disagree with the
tree-walker, which running the same programs on both engines (the
differential testing of *Edge cases and differential testing*) would
catch.

<More title="More expressions on the VM, and statements">

<Run id="exprs-vm" />

`print` emits its expression, then `print`; an expression statement
such as `1 + 2;` emits its expression, then `pop`, so the unused value
does not stay on the stack.

</More>

## What you learned

- A **single-pass compiler** parses and generates code in the same
  reading of the source; Drip's never builds a syntax tree, and pulls
  one token at a time, keeping only `previous` and `current`.
- To **emit** is to append bytes to the chunk, tagged with a line (the
  previous token's, or the operator's for binary operators); emission
  order is execution order.
- Pratt rules emit their operands first and their opcode last, so the
  bytes come out children-first without a tree.
- Each comparison has its own opcode, because with `NaN`, "not less
  than" is not "greater than or equal".
