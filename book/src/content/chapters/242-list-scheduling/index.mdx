## Too many orders to try

The last chapter turned a block into a dependence DAG: which instructions
must wait for which, and for how many cycles. Any order that respects the
arrows is correct, so the question now is which of those orders is
fastest. For our five-instruction loop body we could list them all, but
the number of orders grows like a factorial: 30 instructions can be put in
order in about 2.6 × 10³² ways, and a block of 30 instructions is nothing
unusual once a loop has been unrolled. Finding the very best order is a
hard problem in the same family as colouring a graph, and so, as with
register allocation, compilers use a fast greedy method that is nearly
always good enough<Cite id="coopertorczon2022" />.

That method is **list scheduling**. It pretends to be the machine: it
walks forwards one cycle at a time, and in each cycle it looks at the
instructions that could start right now and picks one.

<Analogy title="a chef at the pass">
A chef in a busy kitchen keeps glancing at the order tickets. Of the
dishes whose ingredients are ready, she starts the one with the longest
cooking still ahead of it (the roast before the salad), because that is
the one that will hold up the table if it starts late.
<span slot="breaks">A chef can rethink the whole evening; list scheduling
never takes a decision back. Once it has started an instruction in a
cycle, that is final, which is what makes it fast and also why it is not
always perfect.</span>
</Analogy>

<Analogy extra title="a building site">
The plumber cannot start until the walls are up, and the plaster must dry
before the painter comes. Each morning the foreman looks at the jobs whose
earlier jobs are done and sends the crew to the one at the head of the
longest remaining chain, so that the whole house is finished soonest.
<span slot="breaks">A foreman can hire extra crew on a busy day. A CPU
has a fixed number of instructions it can start per cycle (one, on our
toy machine), and no amount of urgency changes that.</span>
</Analogy>

## The ready list and the priority

Two ideas make the method work. An instruction is **ready** in cycle c
when every instruction it depends on has started and its delay has
passed; the set of ready instructions is the **ready list**, which is
where the method gets its name. And when more than one is ready, we pick
the one with the highest **priority**. The usual priority is the
instruction's **height**: the longest chain of delays from it to the end
of the block. An instruction with a long chain behind it is on (or near)
the critical path, so delaying it delays everything.

Eight cycles instead of fourteen: the second load slips into the first
load's wait, and the two multiplies overlap. Gibbons and Muchnick built
exactly this kind of scheduler, over a dependence graph, for a pipelined
machine, choosing among ready instructions with a few simple rules rather
than searching ahead<Cite id="gibbonsmuchnick1986" />.

<Callout kind="definition">
**List scheduling** builds a schedule one cycle at a time. In each cycle
c it forms the **ready list**: the unscheduled instructions all of whose
predecessors A have started with S(A) + d(A, B) ≤ c. It starts the
highest-priority ready instructions, up to the machine's width; if none
is ready, the cycle is a stall. The usual **priority** is the **height**,
the longest path of delays from the instruction to the end of the block,
with ties broken by, for example, the number of successors or the
original order.
</Callout>

<Formal title="Height and the ready list">

```text
h(i) = 0   if i has no successors
h(i) = max over edges i → j of d(i,j) + h(j)

R(c) = { j unscheduled :
         every edge a → j has
         a scheduled and S(a) + d(a,j) ≤ c }
in cycle c, start the j in R(c) with
the largest h(j)
```

<span slot="read">The height of an instruction with nothing after it is
zero; otherwise it is the largest, over every arrow out of it, of that
arrow's delay plus the height at its far end. In cycle c, the ready list
holds every unscheduled instruction whose predecessors have all started
and whose delays have passed by c; we start the one with the greatest
height.</span>
</Formal>

Heights are computed from the bottom of the block upwards, because each
one needs the heights of the instructions after it; you can do it in a
single backwards pass. Change the edges below and watch the heights move:

<Examples of="list-scheduling">

```text
ld   a3, 0(a0)    h = 3
li   a4, 5        h = 0
addi a3, a3, 1    h = 0
cycle 0: ld, 1: li, 2: stall, 3: addi
```

```text
loop body (h): ld 7, mul 4, add 1,
               addi 1, bne 0
cycles: ld 0, addi 1, (stall),
        mul 3, (stalls), add 6, bne 7
```

scheduling reaches 8 cycles, the critical-path bound, so for this block

## Scheduling pulls against register allocation

There is a catch, and the timelines below show it. In the original order
the two loaded values are alive one after the other, so one register
would hold both. In the faster schedule they are alive at the same time:

<Figure takeaway="Overlapping work means more values alive at once." caption="Lifetime of the two squared values, x0 and x1, in each order. The list schedule is almost twice as fast, but from cycle 1 to cycle 6 it needs two registers where the original order needed one.">

</Figure>

The number of values alive at one point is called the **register
pressure**. Every overlap a scheduler creates raises it; on a big loop the
pressure can pass the number of registers there are, and then the
allocator must spill (chapter 239), adding loads and stores that cost
more than the stalls we saved.

<Analogy extra title="a desk with limited space">
Working on several jobs at once is faster than finishing one before
starting the next, but every half-done job takes desk space. Start too
many, and papers go into a drawer (spilled), and fetching them back
costs time.
<span slot="breaks">You can always buy a bigger desk. A RISC-V core has
32 integer registers, fixed by the instruction set, and some of those are
reserved by the calling convention.</span>
</Analogy>

So which goes first? If we schedule **before** allocation, the scheduler
is free (values have their own names, so there are no false anti or
output dependences), but it may push pressure too high. If we allocate
**first**, the allocator reuses registers, and every reuse adds an anti
or output edge that pins instructions in place: had both trips used `a3`,
the second `ld a3` could not have moved above the first trip's `add`.
This is a **phase-ordering problem**: each pass makes the other's job
harder. Real compilers compromise. LLVM's default machine scheduler is a
list scheduler that runs before register allocation and tracks register
pressure as it goes, holding back when the pressure gets too high; it
can then run a second, post-allocation scheduler over the final
code<Cite id="llvm-machinescheduler" />.

## What you learned

- **List scheduling** walks forward cycle by cycle, keeps a **ready
  list**, and starts the highest-priority ready instruction.
- The usual priority is the **height**, the longest chain of delays to
  the end of the block, computed in one backwards pass.
- It is greedy and never takes a decision back, yet it often reaches the
  critical-path bound.
- Overlapping work raises **register pressure**; scheduling and
  allocation pull against each other, and compilers schedule before
  allocation while watching pressure, then again after.
