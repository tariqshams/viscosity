## A string goes in, a 7 comes out

Here is a complete program in Drip, the small language you are about to
build:

```
print 1 + 2 * 3;
```

Run it and you see `7`; however, the program that runs it receives no
sum and not even the word `print`, only a string of sixteen characters.
Somewhere between that row of characters and the `7`, something has to
notice that `print` is one word, that `2 * 3` happens before the `+`,
and that the answer should be shown; nobody sensible does all of that in
one go, so the work is split into stages.

## The pipeline

<PipelineSteps client:visible />

Each stage is an ordinary function that takes the previous stage's
output and returns something more organised. Here is the heart of
Drip's `run`, simplified from `companion/ts/src/drip.ts`:

```ts
const tokens = scan(source);
const program = parse(tokens, reporter);
const locals = resolve(program, reporter);
interp.interpret(program, locals);
```

The **scanner** turns the source string into **tokens**, the words of
the program; the **parser** turns the tokens into a **syntax tree**, the
tagged-union tree of *Tagged unions: the shape of every syntax tree*;
the resolver works out which variable each name refers to (*The
resolver* builds it); and the interpreter walks the tree and does what
it says. The `reporter` collects error messages, and `run` stops after
parsing if it holds one, which is why a program with a syntax error on
its last line prints nothing at all.

<Callout kind="definition">
A **compiler pipeline** is a chain of stages where each stage's output
is the next stage's input. For Drip: **source** (a string) → the scanner
→ **tokens** → the parser → a **syntax tree** → then either an
interpreter, which produces **output**, or a compiler, which produces
another form of the program, sometimes by way of an **intermediate
representation** (an **IR**: a form designed for the compiler's own use
rather than for people).
</Callout>

<Examples of="compiler-pipeline">

```text
"print 7;"
→ print  7  ;  eof
→ Print(Number 7)
→ 7
```

</Examples>

Eight characters become four tokens (the last, `eof`, marks the end),
the tokens become a tree with one `Print` node holding the number 7,
and walking the tree prints `7`. *Checkpoint: JSON and its scanner* built
the same shape with two stages, a scanner and a parser,
where the tree *is* the answer.

<Formal title="A pipeline is functions applied in turn">

```text
scan      : string  → Token[]
parse     : Token[] → Tree
interpret : Tree    → output
run(src) = interpret(parse(scan(src)))
```

<span slot="read">Each stage takes the previous one's output; running a
program is the stages applied one inside another, innermost first,
which mathematicians write run = interpret ∘ parse ∘ scan.</span>
</Formal>

<Analogy extra title="an assembly line">
A car moves down a line, and each station does one job and passes it on,
knowing only what arrives and what it must hand over.
<span slot="breaks">In a language implementation each stage hands on
something of a *different kind*, and the earlier form is usually thrown

## Front end and back end

The pipeline cuts in two. The **front end** reads the program and works
out what it says, so it cares about the source language (the scanner
must know that `fn` is a Drip word); the **back end** makes it happen,
so it cares about the target (a tree-walker, a bytecode machine, a real
processor). Whatever sits between them, a tree or an IR, can be shared.

  <HubFigure />
</Figure>

<Callout kind="definition">
The **front end** of a language implementation turns source text into a
structured form (tokens, then a tree or IR) and reports errors in the
source; it depends on the **source language**. The **back end** turns
that structure into the result (output, bytecode or code); it depends on
the **target**. Production compilers often add a **middle end** of
analysis and improvement passes between the two<Cite id="coopertorczon2022" />.
</Callout>

<Examples of="front-end-back-end">

```text
JavaScript ─┐           ┌─ emit JS
            ├─ VIR, plan┤
Python ─────┘           └─ emit Python
```

</Examples>

This is Viscosity's own repository: a front end for JavaScript and
another for a subset of Python both lower their programs into the same
IR, called VIR, so the analysis and layout planning in the middle is
written once, and each language gets a small emitter at the end.

## Two ways to finish the journey

The tree says that `2 * 3` comes first and that the answer should be
printed, but it has computed nothing; there are two ways to finish.

<Analogy title="an interpreter and a translator">
To get a speech in Japanese to an English audience, an **interpreter**
stands beside the speaker and says each sentence in English as it is
spoken. A **translator** takes the whole speech home and comes back with
an English text, which someone else reads out later, as often as they
like.
<span slot="breaks">A human translator may reword freely; a compiler may
change *how* the program does its work, but never *what* it does, for
any input at all.</span>
</Analogy>

<TwoRoutesSteps client:visible />

The compiler visits the tree in the same order the interpreter does;
where the interpreter computes `2 * 3`, the compiler writes down `mul`.

<Callout kind="definition">
An **interpreter** is a program that runs another program directly,
producing its output. A **compiler** is a program that translates a
program into another form (machine code, **bytecode** or source code)
without running it. A **bytecode VM** combines them: compile to bytecode
(a list of simple instructions), then interpret the bytecode.
</Callout>

<Examples of="interpreter compiler">

```text
interpreter:  1 + 2  →  3
compiler:     1 + 2  →  push 1
                        push 2
                        add
tsc app.ts   → app.js    (compiles)
node app.js  → output    (runs it)
```

</Examples>

The interpreter answers `3` at once; the compiler answers nothing, and
writes three instructions that *would* compute `3` on a machine that
keeps numbers on a stack. `tsc` translates TypeScript into JavaScript
and runs neither; Node runs the result afterwards, perhaps many times.

<Formal title="What each one promises">

```text
interp(P, input) = output
compile(P)       = P′
run(P′, input)   = interp(P, input)
```

<span slot="read">An interpreter takes a program and its input. A
compiler takes only the program and gives a new program P′; the promise
every correct compiler keeps is that for every input, running P′ gives
the output interpreting P would.</span>
</Formal>

## Why compile, and who does which

Compiling pays for **reading once**: a tree-walker pays for the walk
every time a loop goes round, while compiled instructions have already
been worked out. It can target something **faster**, such as machine
code; and sometimes the target is **the only thing that can run**: a
browser runs JavaScript, not TypeScript, and Viscosity's output is
JavaScript for the same reason. Interpreting starts at once, is far
simpler to write (the clearest way to pin down what a language means),
and points every error at the line you wrote, which is why building
Drip starts there.

<Figure takeaway="Real systems mix the two." caption="Four systems from this book. Orange steps compile (translate without running); blue steps interpret (run). Drip's tree-walker only interprets and tsc only compiles; Drip's VM and V8 do both, one after the other.">
  <WhoRunsWhat />
</Figure>

Drip's VM compiles source into bytecode and then runs an interpreter
loop over it. V8 compiles each function to bytecode, which its
interpreter, Ignition, runs, and compiles hot code *again* into machine
code<Cite id="v8-ignition" />. Viscosity is a **source-to-source**
compiler, JavaScript in and JavaScript out, rewriting arrays of objects
into typed-array columns where that is safe<Cite id="makor2022" />, and
then handing the result to an engine like V8.

## What you learned

- A **compiler pipeline** passes a program through stages: source →
  tokens → tree → output or another form; each stage has one job.
- The **front end** depends on the source language, the **back end** on
  the target; a shared IR turns M × N translators into M + N.
- An **interpreter** runs a program; a **compiler** translates it
  without running it, keeping its meaning for every input; a bytecode VM
  and V8 do both.
