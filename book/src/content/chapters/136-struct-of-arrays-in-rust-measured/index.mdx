## The same particles, a new language

In *Generating SoA storage*, Viscosity turned an array of particle
objects into `Float64Array` columns. In Rust you write the columns
yourself, but look first at what you start from: a six-`f64` `Particle`
is 48 bytes, and a `Vec<Particle>` keeps them back to back, with no
object headers, pointers or boxed numbers. The array of structs starts
out good; what it still wastes is the fields a loop does not touch:

## Columns by hand

<Analogy title="a filing cabinet">
One folder per person, holding all their details, is an array of
structs; one drawer per question ("everyone's weight", "everyone's
height"), each drawer in the same order of people, is a struct of
arrays. To answer "what does everyone weigh?" you open one drawer and
read straight down it.
<span slot="breaks">A clerk can hand over one whole folder; with drawers
there is only a fresh card copied from each drawer, which is what a
`get` method must return.</span>
</Analogy>

<Figure takeaway="Particle i is index i of every column; push must write all of them." caption="A Particles struct of six Vec<f64> columns. The highlighted index is one particle; the dashed cells are what one push adds.">
  <ColumnIndex />
</Figure>

<Examples of="rust-soa">

```rust
struct Particles {
    x: Vec<f64>, y: Vec<f64>,
    vx: Vec<f64>, vy: Vec<f64>,
    mass: Vec<f64>, health: Vec<f64>,
}

impl Particles {
    fn push(&mut self, p: Particle) {
        self.x.push(p.x);
        self.y.push(p.y);
        // ...and vx, vy, mass, health
    }
    fn step(&mut self, dt: f64) {
        for i in 0..self.x.len() {
            self.x[i] += self.vx[i] * dt;
            self.y[i] += self.vy[i] * dt;
        }
    }
}
```

</Examples>

Particle `i` is index `i` of every column, and `push` appends each field
to its own column, so all six grow together. `step` is the `update-xy` loop
of *AoS vs SoA, measured*: it reads `vx[i]` and `vy[i]` and moves `x[i]`
and `y[i]`, and never touches `mass` or `health`, so their columns are
never fetched. `self.x[i] += self.vx[i] * dt` borrows `self.x` mutably
and `self.vx` for reading at once, which is fine, because they are
different fields; a `&self` method such as `self.vx_at(i)` called inside
a loop over `self.x.iter_mut()` is not, since it borrows the *whole* of
`self` (rustc 1.97 reports E0502).

<More title="What Rust does not check, and get">

Nothing makes `push` write *every* column: forget one and it compiles,
then the first `step` panics with an index out of bounds, so make the
fields private to their module and test `push`. And `get(i)` must build
and return a `Particle` by value, the materialisation of *Identity and
materialization*, since there is no `Particle` in memory to lend.

</More>

<Callout kind="definition">
A **struct of arrays** in Rust is a struct with one `Vec` per field, such
as `x: Vec<f64>`, where element `i` is made of index `i` of every column.
Its methods must keep one **invariant** (a fact that must stay true
between calls): every column has the same length. Each `Vec` grows by
itself, with amortised constant-time `push`<Cite id="rust-std-vec" />.
</Callout>

## A number from the wrong build

Time the loop with `cargo run` and the columns are *slower*; however,
Cargo printed ``Finished `dev` profile [unoptimized + debuginfo]``. It
builds with a **profile**, a named set of compiler settings: `dev` by
default, `release` with `--release`, and `bench` (which inherits from
`release`) for `cargo bench`<Cite id="cargo-profiles" />:

## The loop that vanished

Now build for release and time a sum of a million `f64`s, done 100 times,
once plainly and once with its input and output wrapped in `black_box`.
Step through what four builds of it printed:

<OptSteps client:visible />

A hundred million additions in under 210 ns did not happen: the result
was dropped, so the optimiser deleted the calls (the dead code
elimination of *Benchmarking honestly*). **`std::hint::black_box`** is
the fix.

<Examples of="black-box">

```rust
use std::hint::black_box;
for _ in 0..100 {
    black_box(sum(black_box(&xs)));
}
```

</Examples>

`black_box` returns its argument unchanged, but the compiler must assume
the value could be used in any way at all: wrapping the input stops it
reasoning about `xs`, and wrapping the result stops it throwing the sum
away<Cite id="rust-std-black-box" />. With both, the release build took
74 to 75 ms, the real cost of the work.

<Callout kind="definition">
**`black_box(x)`** (in `std::hint`) is an identity function the compiler
must treat as opaque, so work feeding into it cannot be removed and
values coming out of it cannot be predicted. It is **best-effort**: the
documentation says it can generally be relied on for benchmarking, but
never for correctness<Cite id="rust-std-black-box" />.
</Callout>

## The measured result

A fuller harness (release build, three loops, each warmed up and timed in
31 samples of about 20 million particle updates, keeping the median; the
whole run three times on the shared VM) found no win at a thousand
particles (48 KB, which stays in cache), and at a million SoA about 1.7
times faster for `update-xy` and 2.6 for summing one field. Most of what
Viscosity wins in JavaScript is getting away from objects, and a Rust
struct was never an object in that sense; what remains, in both
languages, is not fetching the fields you do not use.

## Is that difference real? Criterion

The ranges above came from repeating everything and eyeballing the
spread. The Rust world's usual tool for doing that with statistics is the
crate **criterion**, run by `cargo bench` on stable Rust (the built-in
`#[bench]` attribute is nightly-only<Cite id="cargo-bench-docs" />).

<Examples of="criterion">

```toml
# Cargo.toml
[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "sum"
harness = false
```

```text
sum 1000  time: [665.89 ns 672.29 ns
                 679.35 ns]
```

</Examples>

Criterion is a **dev-dependency** (never shipped), and `harness = false`
tells Cargo that `benches/sum.rs` brings its own `main` (criterion's
macros write it). The output is what `cargo bench` (cargo 1.97,
criterion 0.5.1) printed for a sum of 1,000 `f64`s: the time per call as
an interval, low, estimate and high. Step through how criterion gets
there:

<CriterionSteps client:visible />

One call is too short for the clock, so sample *k* runs *k* × *d* calls,
and the time per call is the **slope** of the line through the samples;
resampling them a hundred thousand times (a **bootstrap**) gives the
interval. Run again, criterion reports a change only if a test says it is
unlikely to be chance (p below 0.05) *and* it exceeds a 1 percent noise
threshold<Cite id="criterion-analysis" />.
I ran it on unchanged code eight times in a row on the shared VM: six
runs found no change or one within the noise, run 7 said `Performance has
regressed` (+4.7 percent) and run 8 `Performance has improved` (−3.2
percent). The cause was the VM's other tenants, not the code; on such a
machine a 5 percent difference is a rumour until the whole comparison has
been repeated.

<Callout kind="definition">
**Criterion** is a statistical benchmarking crate for stable Rust. It
warms the code up, takes many samples of growing size, estimates the
time per iteration as the slope of a fitted line, gives a bootstrap
**confidence interval** for it, flags outliers with Tukey's fences, and
compares each run with the last one saved<Cite id="criterion-analysis" />.
</Callout>

<More title="The bench file, Tukey's fences, a bootstrap by hand, and how the book's Rust projects time themselves">

```rust
// benches/sum.rs
fn bench(c: &mut Criterion) {
    let xs: Vec<f64> = (0..1000)
        .map(|i| i as f64).collect();
    c.bench_function("sum 1000", |b| {
        b.iter(|| sum(black_box(&xs)))
    });
}
criterion_group!(benches, bench);
criterion_main!(benches);
```

`bench_function` names the benchmark, and `b.iter` runs the closure as
many times as criterion asks, passing each result through `black_box`
itself, so only the input needs hiding.

Criterion counts outliers with Tukey's fences: a sample more than 1.5
interquartile ranges (the width of the middle half of the data) outside
the middle half is a mild outlier, beyond 3 a severe one, and both are
reported, not dropped.

<Figure takeaway="Outliers are judged against the middle half of the data, and reported rather than thrown away." caption="Tukey's fences on some illustrative timings: one sample beyond the 1.5 IQR fence (mild), one beyond 3 IQR (severe).">
  <Fences />
</Figure>

The program below does a bootstrap by hand, on the mean of twelve
timings; it prints a mean of 676.2 ns and a 95 percent interval of 665.8
to 689.4, wider on the high side because of the two slow samples.

<Run id="bootstrap" />

Neither of the book's Rust projects uses criterion. drip-rs's
`scripts/bench.sh` builds with `--release`, runs each benchmark program
in a fresh process and keeps the best wall-clock time; the output is
printed, a side effect the optimiser must keep, so no `black_box` is
needed (its committed results put `fib` at 406 ms against the TypeScript
VM's 1906). engine/rust's `compile_speed` example times 500 warm calls
with `Instant`, passing each result to `black_box`, and reports median
and minimum; even so, its committed file shows `ledger`'s fastest compile
at 74, 73, then 109 µs in three rounds on the shared VM.

</More>

## What you learned

- A **`Vec<Particle>`** is already flat; a Rust **struct of arrays**
  (one `Vec<f64>` per field, all the same length) saves the fields a loop
  skips: 1.7 to 2.6 times faster at a million particles, no faster at a
  thousand.
- Time only **release builds**, and wrap inputs and results in
  **`black_box`** so the work is not deleted.
- **Criterion** gives an interval and a change test; on a shared machine,
  repeat before believing a few percent.
