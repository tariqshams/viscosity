## The same particles, a new language

In *Generating SoA storage*, Viscosity turned `const ps = []` into a
generated class whose fields were columns, `this.x = new
Float64Array(cap)` and one more per field. No compiler does that for
you in Rust; however, Rust lets you write the columns yourself in about
twenty lines, and its type system keeps them pleasant to use. First,
look at what you start from.

```rust
#[derive(Clone, Copy)]
struct Particle {
    x: f64, y: f64,
    vx: f64, vy: f64,
    mass: f64, health: f64,
}
let ps: Vec<Particle> = vec![p; n];
```

*Memory layout in Rust* measured a `Particle` at 48 bytes with no
padding, and a `Vec<Particle>` keeps them back to back in one buffer:
no object headers, no pointer per element, no boxed numbers. That is
much closer to Part II's packed `Float64Array` layout than to a
JavaScript array of objects, so in Rust the array of structs starts out
good. What it still wastes is the fields a loop does not touch:

## Columns by hand

<Analogy title="a filing cabinet">
One folder per person, holding all their details, is an array of
structs; one drawer per question ("everyone's weight", "everyone's
height"), each drawer in the same order of people, is a struct of
arrays. To answer "what does everyone weigh?" you open one drawer and
read straight down it.
<span slot="breaks">A clerk can pull one folder out and hand it over
whole; with drawers there is no folder to hand over, only a fresh
summary card copied from each drawer, which is exactly what `get` will
return.</span>
</Analogy>

<Analogy extra title="a teacher's mark book">
A mark book keeps one column per subject, with the pupils in the same
order down every column, so averaging the maths marks means running a
finger down one column. If one pupil is added to the maths column and
forgotten in the others, every name below them is now beside the wrong
marks.
<span slot="breaks">A teacher would spot the misaligned row at a
glance; Rust will not, as the next section shows, and a missed
column only fails when some index runs off its end.</span>
</Analogy>

<Figure takeaway="Particle i is index i of every column; push must write all of them." caption="A Particles struct of six Vec<f64> columns. The highlighted index is one particle; the dashed cells are what one push adds.">
  <ColumnIndex />
</Figure>

```rust
struct Particles {
    x: Vec<f64>, y: Vec<f64>,
    vx: Vec<f64>, vy: Vec<f64>,
    mass: Vec<f64>, health: Vec<f64>,
}

impl Particles {
    fn push(&mut self, p: Particle) {
        self.x.push(p.x);
        self.y.push(p.y);
        // ...and vx, vy, mass, health
    }

    fn step(&mut self, dt: f64) {
        for i in 0..self.x.len() {
            self.x[i] += self.vx[i] * dt;
            self.y[i] += self.vy[i] * dt;
        }
    }
}
```

The struct has one `Vec<f64>` per field, and particle `i` is index
`i` of every column. `push` takes a `Particle` apart and appends each
field to its own column, so all six grow together. `step` is the
`update-xy` loop of *AoS vs SoA, measured*: for each index it reads `vx[i]` and `vy[i]`, and
moves `x[i]` and `y[i]`; it never touches `mass` or `health`, so their
columns are never fetched.

```rust
let mut s = Xs { x: vec![], vx: vec![] };
s.x.push(1.0);
s.vx.push(0.5); // both columns: len 1
```

```rust

```

The first is the smallest struct of arrays there is: two columns, one
particle, pushed into both, so both have length 1. The second shows
why columns suit iterators (from *Iterators in Rust*):
summing every mass is one pass over one `Vec`, and `zip` walks the
`x` column mutably and the `vx` column for reading side by side, with
no indices, so there is nothing to bounds-check. The runnable one
builds a million particles both ways and times `update-xy` on each;
the section after next explains why its numbers need care.

<Callout kind="definition">
A **struct of arrays** in Rust is a struct with one `Vec` per field,
such as `x: Vec<f64>`, where element `i` is made of index `i` of every
column. Its methods must keep one **invariant** (a fact that must stay
true between calls): every column has the same length. Each `Vec`
grows by itself, with amortised constant-time `push`<Cite id="rust-std-vec" />.
</Callout>

<Formal title="One particle, many columns">

```text
pᵢ = (xᵢ, yᵢ, vxᵢ, vyᵢ, massᵢ, healthᵢ)
len(x) = len(y) = … = len(health) = n
```

<span slot="read">Particle i is the tuple of the i-th entries of the
six columns. And all six columns have the same length n, the number of
particles; every method must keep that equation true.</span>
</Formal>

<OtherLanguages title="Two columns, one step">

```rust
for i in 0..s.x.len() {
    s.x[i] += s.vx[i] * dt;
}
```

```ts
// what Viscosity generates, simplified
for (let i = 0; i < ps.n; i++)
  ps.x[i] += ps.vx[i] * dt;
```

```c
for (size_t i = 0; i < s.n; i++)
    s.x[i] += s.vx[i] * dt;
```

```python
for i in range(len(s.x)):
    s.x[i] += s.vx[i] * dt
```

</OtherLanguages>

All four loops have the same shape, and that is the point of the
layout: the code reads like the array-of-structs version with the
index moved. The differences are in the columns themselves. Rust's
`Vec<f64>` and C's `double *` hold raw doubles; the TypeScript one is a
`Float64Array`, which Viscosity must grow by hand; and in Python the
columns are plain lists unless, as in *Emitting Python with column
storage*, you use `array('d')`.

## What Rust checks, and what it doesn't

Two things work in your favour. First, `self.x[i] += self.vx[i] * dt`
borrows `self.x` mutably and `self.vx` for reading in one statement,
and that is fine: they are different fields, so the borrow checker sees
two separate borrows. Calling a method instead is not:

```rust
for (i, x) in self.x.iter_mut()
    .enumerate() {
    *x += self.vx_at(i) * dt;
}
// error[E0502]: cannot borrow `*self` as
//   immutable because it is also
//   borrowed as mutable
*x += self.vx[i] * dt; // fine
```

`self.vx_at(i)` borrows the *whole* of `self`, including the `x` column
the loop is already changing, so rustc 1.97 refuses it with the error
above (trimmed); naming the field directly borrows only `vx`. Second,
if the fields are private to their module (*Privacy, pub and
workspaces*), nobody outside can push to only one column.

One thing Rust does not check: nothing makes `push` write *every*
column. Forget `self.vx.push(p.vx)` and it compiles; then the first
`step` panics with an index out of bounds, because `vx` is empty. In Part
VIII, Viscosity generated `push` itself; here, tests do that job.
And getting a particle back is materialisation (*Identity and
materialization*): `get(i)` builds a `Particle` from the columns and
returns it by value, since there is no `Particle` in memory to lend a
`&Particle` to, so changing the copy changes nothing in the columns.

## Measuring it

Read the runnable example's output with suspicion. In the page it runs
on the Rust Playground as a *debug* build, with no optimisation. On
this book's machine (a shared cloud VM, rustc 1.97) the debug build
made SoA *slower*, about 20 ns per particle against 4 to 9 for AoS in
three runs, because every `s.x[i]` paid for an unoptimised bounds
check; built with `-O`, the same program printed about 1.3 ns for SoA
against 2.4 for AoS, three times out of three. The program wraps the
data in `std::hint::black_box`, which stops the optimiser from
deleting work whose result it can see is unused<Cite id="rust-std-black-box" />;
*Measuring Rust performance* explains both pitfalls properly.

For this chapter I also ran a fuller harness: release build, three
loops, each warmed up and then timed in 31 samples of about 20 million
particle updates, keeping the median; the whole run three times, in
nanoseconds per particle (ranges across the runs):

```text
n = 1,000          AoS        SoA
  update-xy        0.38–0.41  0.41–0.54
  sum-one-field    0.65–0.71  0.65–0.66
  read-all         1.10–1.11  1.08–1.12
n = 1,000,000
  update-xy        2.35–2.37  1.28–1.33
  sum-one-field    2.00–2.03  0.72–0.76
  read-all         2.51–2.67  1.77–1.85
```

With a thousand particles (48 KB, which stays in cache) there was no
win, and `update-xy` was if anything a little slower as columns. With
a million, SoA was about 1.8 times faster for `update-xy` and 2.7 for
summing one field, and it came out ahead even reading all six fields,
which this chapter cannot fully explain, so do not lean on that row.
Now the same loop in JavaScript, from this book's Node run:

## What you learned

- A **`Vec<Particle>`** is already flat: structs back to back, no
  headers or pointers. Its waste is the fields a loop skips.
- A Rust **struct of arrays** has one `Vec<f64>` per field; keep the
  columns the same length, and the fields private.
- Borrowing two different fields at once is fine; a method call
  borrows all of `self` (E0502). `get` returns a rebuilt copy.
- In this chapter's release runs SoA was 1.8 to 2.7 times faster at a
  million particles and no faster at a thousand.

## A number from the wrong build

You port a hot loop to Rust, time it with `cargo run`, and it is slower
than your JavaScript. Before you blame Rust, look at the line Cargo
printed just before your program started:

```text
Finished `dev` profile [unoptimized +
  debuginfo] target(s) in 0.09s
```

You measured the build made for debugging. *Benchmarking honestly*
warned that a JIT needs warming up before its numbers mean anything;
Rust has no JIT, but it has an equally large trap of its own, and a
second one that runs the other way.

<Analogy title="a car on the test track">
A debug build is a car on the test track with a sensor on every bolt
and a speed limiter fitted: perfect for finding faults, useless for lap
times. A release build takes the sensors off.
<span slot="breaks">Taking sensors off a car does not change where it
goes; a release build can also behave differently, since integer
overflow, for example, panics in one and wraps in the other.</span>
</Analogy>

<Analogy extra title="a dance rehearsal">
In rehearsal the teacher stops the music at every slip and the steps
are taken at half speed, so each mistake is easy to see; on the night
the piece runs at full speed with no stops. Nobody times the
rehearsal and calls it the length of the show.
<span slot="breaks">A rehearsal is slower in a steady way; a debug
build is slower by different factors in different code (about 5
times for this chapter's sum, 10 for drip-rs's `fib`, 15 for the
columns in *Struct of arrays in Rust by hand*), so you cannot divide by a constant to correct it.</span>
</Analogy>

## Debug and release

Cargo builds with a **profile**, a named set of compiler settings.
`cargo build`, `cargo run` and `cargo test` use `dev`; adding
`--release` uses `release`; and `cargo bench` uses `bench`, which
inherits from `release`<Cite id="cargo-profiles" />:

<Examples of="release-build">

```text
  debuginfo]

```


<Run id="overflow-play" />

</Examples>

The first shows the two commands and the line each prints, which is
the quickest way to know which build you are timing. How much it
matters: for this chapter I built drip-rs both ways (rustc 1.97, the
book's shared cloud VM) and ran `fib.drip` three times each; the debug
build took 4.3 to 4.7 seconds and the release build 0.45 to 0.64, ten
times faster. The second is how drip-rs asks for even more: `lto =
true` (link-time optimisation) and `codegen-units = 1` let the
optimiser see the whole program at once, at the price of slower
builds. The third, the runnable one, shows that the two builds also
*behave* differently: integer overflow panics in a debug build and
wraps around in a release build<Cite id="rustref-int-overflow" />.
In the page it runs as a debug build and stops with `attempt to add
with overflow`; built with `-O` on the same machine it printed
`255 + 1 = 0`.

<Callout kind="definition">
A **release build** (`cargo build --release`) compiles with the
`release` profile: `opt-level = 3`, with debug assertions and overflow
checks off. Only release builds (or `cargo bench`, which inherits from
release) give timings that say anything about speed; the default `dev`
profile does no optimisation, for fast builds and easy debugging<Cite id="cargo-profiles" />.
</Callout>

## The loop that vanished

Now build for release and time a sum of a million `f64`s, done 100
times, once plainly and once with every input and output wrapped in
`black_box`. Step through what four builds of it printed:

<OptSteps client:visible />

A hundred million additions in under 200 ns is about half a million
additions per nanosecond; they did not happen. `sum` has no side
effects and its result was dropped, so the optimiser deleted the calls:
the dead code elimination *Benchmarking honestly* caught a JIT doing,
here in a compiler with all the time it likes to look for it.
**`std::hint::black_box`** is the fix: it returns its argument
unchanged, but the compiler must assume the value could be used in any
way at all. Wrapping the input stops the compiler reasoning about `xs`;
wrapping the result stops it throwing the sum away<Cite id="rust-std-black-box" />.

<Examples of="black-box">

```rust
use std::hint::black_box;
let n = black_box(1_000_000);
// the compiler may not assume n's value
```

```rust
for _ in 0..100 {
    black_box(sum(black_box(&xs)));
}
```

<Run id="bb-play" />

</Examples>

The first hides a constant: without `black_box`, the compiler could
work out anything that depends on `n` before the program runs. The
second is the benchmark loop from the diagram, with both ends hidden.
The runnable one is the whole program; run in the page (a debug build)
the two lines come out within a few tens of percent of each other,
which is exactly the misleading part, and in a release build the
`plain` line drops to nanoseconds.

<Callout kind="definition">
**`black_box(x)`** (in `std::hint`) is an identity function the
compiler must treat as opaque, so work feeding into it cannot be
removed and values coming out of it cannot be predicted. It is
**best-effort**: the documentation says it can generally be relied on
for benchmarking, but never for correctness<Cite id="rust-std-black-box" />.
</Callout>

<Formal title="An identity the optimiser cannot see through">

```text
black_box : T → T
black_box(x) = x
```

<span slot="read">black_box takes a value of any type T and gives back
a value of the same type; in fact it gives back x itself. As a function
it does nothing; what it changes is what the compiler is allowed to
assume about x, before and after.</span>
</Formal>

`black_box` hides values; it does not stop the compiler being clever
with the code between them. A loop adding up `i * i` for every `i`
below a black-boxed million still took 1 to 2 ns per call in a
release build here, so the loop must have been replaced by a formula
(about a million multiplications cannot fit in 2 ns). Benchmark work
shaped like the real thing.

<OtherLanguages title="Keep the result alive">

```rust
let t = Instant::now();
black_box(sum(black_box(&xs)));
let d = t.elapsed();
```

```ts
// A JIT may also delete unused work;
// keep the result and use it.
const t = performance.now();
const r = sum(xs);
const d = performance.now() - t;
console.log(r);
```

```c
/* gcc -O2 may delete an unused loop */
volatile double sink;
sink = sum(xs, n);
```

```python
t = time.perf_counter()
r = sum(xs)  # CPython runs it all
d = time.perf_counter() - t
```

</OtherLanguages>

The problem is not Rust's alone. An optimising JIT can remove work
whose result nobody uses, so a JavaScript benchmark keeps and prints
its result; C programmers write to a `volatile` variable, which the
compiler must treat as watched from outside; CPython does no such
optimisation, so a plain timing runs everything (slowly). Rust's
`black_box` is the standard, named way to say "assume this matters".

<Callout kind="engine" label="Under the hood">

compile was 74, 73, then 109 µs in three rounds. The next chapter adds
statistics to judge such differences.
</Callout>

## Is that difference real?

*Measuring Rust performance* got the build and the optimiser out of
the way, and its exercise collected one time per run. Now suppose you
change a function and the median goes from 665 ns to 690. Did you make
it slower, or did another program on the machine wake up?
*Noisy numbers: the median, p95 and a fresh process* answered with a
median and a careful eye; the Rust world's usual answer is a crate
that does the statistics for you.

<Analogy title="an opinion poll">
A poll does not ask every voter; it asks a thousand, and reports
"42 percent, give or take 3". The "give or take" is the honest part: a
second poll might say 44, and that alone would not mean anyone changed
their mind. Criterion reports a benchmark the same way: an estimate and
a margin.
<span slot="breaks">A poll's margin comes from asking different
people; criterion asks the same code again and again, and its spread
comes from the machine (other programs, caches, the CPU's clock), so
the "true value" itself drifts from hour to hour.</span>
</Analogy>

<Analogy extra title="weighing yourself a hundred times">
Step on a bathroom scale a hundred times and the readings wobble by a
few hundred grams; once or twice you forgot to take off your coat.
You would report the typical reading, flag the coat readings, and not
believe a 200-gram "loss" between two mornings.
<span slot="breaks">A coat is easy to spot; a benchmark's "coat" (a
background task) is invisible, and it can make a whole run slower, not
just one reading, which is how a quiet hour can look like an
improvement.</span>
</Analogy>

## Setting it up

Stable Rust's `cargo bench` runs whatever is in a crate's `benches/`
folder, but the built-in `#[bench]` attribute is nightly-only, so the
Cargo book points to crates such as **criterion** for stable
Rust<Cite id="cargo-bench-docs" />. The book's Run button cannot run
it (it compiles single files with no crates, in debug mode), so for
this chapter I ran it with cargo 1.97, which fetched criterion 0.5.1
from crates.io.

<Examples of="criterion">

```toml
# Cargo.toml
[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "sum"
harness = false
```

```rust
// benches/sum.rs
use criterion::{criterion_group,
    criterion_main, Criterion};
use crit::sum;
use std::hint::black_box;

fn bench(c: &mut Criterion) {
    let xs: Vec<f64> = (0..1000)
        .map(|i| i as f64)
        .collect();
    c.bench_function("sum 1000", |b| {
        b.iter(|| sum(black_box(&xs)))
    });
}
criterion_group!(benches, bench);
criterion_main!(benches);
```

```text
$ cargo bench
Finished `bench` profile [optimized]
sum 1000   time: [658.64 ns 665.74 ns
                  672.99 ns]
```

</Examples>

The first adds criterion as a **dev-dependency** (used only by tests
and benchmarks, never shipped) and declares one benchmark, `sum`, with
`harness = false`, which tells Cargo that the file brings its own
`main` instead of using the built-in test harness. The second is that
file. `sum` comes from the crate being measured (here called `crit`);
`bench` builds a thousand numbers once, then `bench_function` names the
benchmark, and `b.iter` runs the closure as many times as criterion
asks, passing each result through `black_box` itself, so only the
input needs hiding. The last two lines generate that `main`. The third
is what `cargo bench` printed on this book's VM: it built with the

## What criterion does

Step through one benchmark as criterion measures it:

<CriterionSteps client:visible />

The key move is the slope. One call to `sum` takes well under a
microsecond, too short for the clock to time on its own, so criterion
never times one call: sample *k* runs *k* × *d* calls, and the time per
call is the slope of the line through all the samples. To put a margin
on that slope it uses the **bootstrap**: pick 100 samples at random
from the 100 it has (some twice, some not at all), fit a line, and
repeat a hundred thousand times; the middle 95 percent of those slopes
is the interval it prints<Cite id="criterion-analysis" />. The
runnable example does a bootstrap by hand, on the mean of twelve
timings:

<Run id="bootstrap" />

It prints a mean of 676.2 ns and a 95 percent interval of 665.8 to
689.4, wider on the high side because of the two slow samples.

<Callout kind="definition">
**Criterion** is a statistical benchmarking crate for stable Rust. It
warms the code up, takes many samples of growing size, estimates the
time per iteration as the slope of a fitted line, gives a bootstrap
**confidence interval** for it, flags outliers with Tukey's fences, and
compares each run with the last one saved<Cite id="criterion-analysis" />.
</Callout>

<Formal title="Slope and fences">

```text
tₖ ≈ β × (k × d),   k = 1 … 100
IQR = Q3 − Q1
mild:   x outside [Q1 − 1.5·IQR,
                   Q3 + 1.5·IQR]
severe: x outside [Q1 − 3·IQR,
                   Q3 + 3·IQR]
```

<span slot="read">The total time of sample k is about β times its
number of calls, k times d; β, the slope, is the time per call. A
sample is a mild outlier if it lies more than one and a half
interquartile ranges below the first quartile or above the third, and
a severe one beyond three. The interquartile range is the distance
between the first and third quartiles, the middle half of the
data.</span>
</Formal>

## The run that improved nothing

Criterion saves each run's samples and compares the next run with
them, using a statistical test; it reports a change only if the test
says it is unlikely to be chance (p below 0.05) *and* the change is
bigger than its noise threshold, 1 percent by default<Cite id="criterion-analysis" />.
I ran the same benchmark, on the same code, eight times in a row. Six
runs said `No change in performance detected` or `Change within noise
threshold`. Two did not:

```text
run 6  change: [-4.93% -3.24% -1.49%]
       (p = 0.00 < 0.05)
       Performance has improved.
run 8  change: [+2.15% +4.25% +6.68%]
       (p = 0.00 < 0.05)
       Performance has regressed.
```

Neither was false, in a narrow sense: the timings really did differ
between those runs. However, the cause was the shared VM's other
tenants, not the code, which had not changed at all. Criterion's own
guide warns that small, deterministic benchmarks are this sensitive,
and that the noise threshold exists for exactly this<Cite id="criterion-analysis" />;
on a machine like this one, 1 percent is too small. The lesson
survives any tool: alternate the two versions you compare, repeat the
whole comparison, and treat a single 5 percent difference on a shared
machine as a rumour.

## What you learned

- **Criterion** runs on stable Rust through `cargo bench`: a
  dev-dependency, and a `[[bench]]` with `harness = false`.
- It fits a line through samples of growing size; the **slope** is
  the time per call, and a **bootstrap** gives its interval.
- Outliers are counted with **Tukey's fences** (1.5 and 3 IQR), and
  reported, not dropped.
- It compares runs with a test and a 1 percent noise threshold; on a
  shared VM, unchanged code was reported as 3 percent faster, then 4
  percent slower.
