## Two strings, one object

The last chapter left a loose thread: `Table.find` compares keys with
`k === key`. The VM's `eq` instruction is no better; here is all of
Drip's `==`, from `vm/object.ts`:

```ts
export const valuesEqual =
  (a: Value, b: Value): boolean => a === b;
```

For objects, `===` asks "is this the same object?", not "are these the
same characters?" (the chapter on references showed the difference).
Yet this prints `true`:

```text
let a = "ab";
let b = "a" + "b";
print a == b;
```

`a` holds a literal, made by the compiler. `b` is built while the
program runs, by `add`, and the chapter on heap objects said that
joining two strings makes a new string object. So how can `a` and `b` be
the same object? Because that "new" was not the whole truth:
`copyString`, which makes every string object, does not always
allocate.

## Interning

<Analogy title="the badge desk at a conference">
Before printing a name badge, the clerk looks through the box of
badges already printed; if one says "Ada Lovelace", you get that one.
As such, everyone called Ada Lovelace wears the very same badge, and
checking whether two people have the same name is as quick as checking
whether they are wearing the same badge.
<span slot="breaks">Two real people cannot wear one badge at once; a
string object can be pointed at from any number of places at the same
time, because nothing in Drip can change a string's characters.</span>
</Analogy>

<Analogy title="songs in a music library">
Add a song to five playlists and your music app does not store the file
five times: each playlist holds a reference to the one file in the
library.
<span slot="breaks">The app keeps a file even when no playlist uses it;
the VM's string table lets a string go once nothing else refers to it,
as the end of this chapter explains. And the app matches songs by file,
while interning matches by exact characters.</span>
</Analogy>

Here is the real `copyString`, from `vm/heap.ts` (line breaks added to
fit the page):

```ts
copyString(chars: string): ObjString {
  const hash = hashString(chars);
  const interned =
    this.strings.findString(chars, hash);
  if (interned) return interned;
  const s = this.allocate<ObjString>({
    type: 'string', chars, hash,
    isMarked: false, next: null });
  this.push(s);
  this.strings.set(s, null);
  this.pop();
  return s;
}
```

Line 2 hashes the characters with the FNV-1a of *Finding things
fast*. Lines 3 and 4 ask `heap.strings`, a `Table` used as a *set*
(its keys are every string the VM has made, and its values are all
`null`), whether a string with those characters already exists; if
so, line 5 returns that object, and nothing is allocated. Only a string
never seen before reaches line 6, which allocates it, and lines 9 to
11 add it to the set, so the next request finds it. (`push` and `pop`
keep `s` on a list of roots while it is being added, so the garbage
collector of *Reclaiming memory* cannot free it halfway.)

Every string in the VM comes through here: literals, names,
concatenations, and the results of `str`. So there is never more than
one object with the same characters.

<InternSteps client:visible />

Notice the first step: the name of the variable `a` and the literal
`"a"` on line 2 are the same object, because when the compiler asked
for `"a"` the second time, `copyString` found the first.

<Callout kind="definition">
**Interning** keeps exactly one copy of each distinct string. Every
request for a string first looks in a table of the strings that exist,
the **intern table** (here `heap.strings`), and gets the existing object
if there is one. Because equal strings are then always the same object,
comparing strings becomes comparing **identity**: one `===` on two
references, however long the strings are.
</Callout>

<Formal title="What interning guarantees">

```text
intern(s) is intern(t)  ⟺  s = t
a == b  ⟺  a is b       (a, b strings)
```

<span slot="read">The object you get for the characters s is the very
same object as the one for t exactly when s and t are the same
characters. So for two strings in the VM, being equal and being the
same object are one and the same thing (the double arrow reads
"exactly when").</span>
</Formal>

<Examples of="interning">

```text
print "ab" == "a" + "b"; # true
```

```js
// without interning: two objects
const s = { chars: 'ab' };
const t = { chars: 'a' + 'b' };
s === t; // false
```

The first is the whole story in one line: the literal and the joined
string are one object, so `eq`'s `===` says `true`. The second is the
spot-the-difference: two JavaScript objects holding the same characters
are still two objects, and `===` says `false`, which is what Drip's
`==` would say for strings if `copyString` always allocated. The
runnable one builds a string in a loop and compares it with a literal;
change a letter and see `false`.

## Finding a string by its characters

There is a catch. `Table.find` compares keys by identity, which is
exactly what `copyString` cannot do yet: it is holding characters, not
an object. So the table has a second lookup, the only place in the VM
that compares a string's characters (from `vm/table.ts`):

```ts
findString(chars: string, hash: number):
    ObjString | null {
  if (this.count === 0) return null;
  const mask = this.keys.length - 1;
  let index = hash & mask;
  for (;;) {
    const k = this.keys[index];
    if (k === null) {
      if (this.values[index] === null)
        return null;
    } else if (k.hash === hash &&
        k.chars === chars) {
      return k;
    }
    index = (index + 1) & mask;
  }
}
```

The probing is the same as `find`'s; only the test differs.
`k.hash === hash` compares two numbers, which is cheap and rules out
almost every wrong string. Only when the hashes match are the characters
compared (`k.chars === chars`, which JavaScript does letter by letter),
and by then it is nearly always the right string. A tombstone (no key,
value not `null`) is stepped over, as before.

## What it costs, what it buys

Interning moves work around; it does not remove it.

**Making a string costs more.** Every new string, including every
concatenation and every `str(...)`, is hashed in full and looked up
before it exists. The book's `strings` benchmark does little else: each
of its 240,000 rounds builds six strings with `+` and `str`, about 1.4
million hashes and lookups, although after the first few hundred
rounds nearly all of them are already in the table. In this book's
benchmark run of 2 November 2026 it took 383 ms on the VM and 365 ms on
the tree-walker, which builds plain JavaScript strings and lets the
engine compare them; the VM was slightly *slower*, because the work it
saves elsewhere is paid back here.

**Using a string costs less.** `==` on strings is one comparison, and
every global variable lookup (*Globals by name*), field access and
method call finds a name in a table by identity too. Most programs make
a name once and use it many times, so this is usually a good trade. It
also saves memory: a thousand mentions of `"name"` are one object.

The intern table has one more duty. If it kept every string alive, no
string could ever be freed. So it holds strings **weakly**: during a
collection, after everything reachable is marked, `removeWhite` turns
each entry whose string nothing else reached into a tombstone, just
before the sweep frees it (*Reclaiming memory* shows the whole
collector).

<Callout kind="engine" label="Under the hood">
Interning is everywhere. Python's `sys.intern` enters a string in a
table of interned strings; its documentation says the names in Python
programs are interned automatically, and that with interned keys a
dictionary's key comparisons, after hashing, can be a pointer compare
instead of a string compare<Cite id="python-sys-intern" />. Java
interns every string literal, and `s.intern() == t.intern()` holds
exactly when `s` and `t` have equal contents<Cite id="openjdk-string-intern" />.
The companion VM interns every string it makes, which is simpler than
choosing, and is what makes `===` correct for every Drip value.
</Callout>

## What you learned

- **Interning** keeps one object per distinct string, so equal strings
  are identical and Drip's `==` is a single `===`.
- `copyString` hashes the characters and asks the intern table first;
  it allocates only for a string it has never seen.
- `findString` is the one place characters are compared, and only after
  the hashes match.
- The trade: every new string pays a hash and a lookup (the `strings`
  benchmark shows the bill), so that every later comparison and name
  lookup is one reference check.
- The intern table holds strings weakly: unreachable strings leave it
  before they are freed.
