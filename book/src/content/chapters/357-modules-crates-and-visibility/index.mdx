## Nine lines, nine files

Here is the top of drip-rs's `src/lib.rs`, the root of the `drip`
library crate (from *Cargo, crates and packages*):

```rust
pub mod chunk;
pub mod compiler;
pub mod debug;
pub mod gc;
pub mod object;
pub mod scanner;
pub mod table;
pub mod value;
pub mod vm;
```

In *Modules: import and export*, each JavaScript file was a module just
by existing, and `import { scan } from './scanner.js'` found it by its
path on disk. Rust works the other way round: the compiler starts at
one file, the **crate root** (`src/lib.rs` for a library, `src/main.rs`
for a program), and only compiles the files that root, or a module
below it, asks for. `mod scanner;` says "there is a module called
`scanner`, and its code is in `scanner.rs` next to me"; delete that
line and `scanner.rs` is ignored, however much code is in it. (The
`pub` in front lets code outside this module use it; the next chapter
is all about `pub`, so for now read it as "others may use this".)

<Analogy title="a family tree drawn from the top">
A JavaScript project is like a pile of letters that mention each other
by address. A Rust crate is a family tree drawn from the oldest
ancestor down: the root names its children, each child names its own,
and anyone not drawn on the tree is simply not in the family, however
close they live.
<span slot="breaks">Real families have two parents and cousins who
marry; a module has exactly one parent, so the module tree is a true
tree with no loops.</span>
</Analogy>

Ask for a file that is not there and rustc 1.97 tells you where it
looked:

```text
error[E0583]: file not found for module
  `scanner`
= help: to create the module `scanner`,
  create file "scanner.rs" or
  "scanner/mod.rs"
```

A module can also be written **inline**, with its body in braces right
where it is declared. You have met one at the bottom of every Rust
exercise: the tests are wrapped in `mod tests { use super::*; ... }`.
Inline or in a file, the result is the same: one more node in the
**module tree**, a tree of named scopes rooted at `crate`.

## Paths: an address for every item

Every function, struct, enum or module in the tree has an address
built from the names on the way to it, joined by `::`. A **path** may
start in three places:

- `crate::` starts at the root, like `/` at the start of a file path;
- `super::` starts at the parent of the current module, like `..`;
- `self::` (or nothing at all) starts in the current module.

<Analogy title="a postal address">
"Flat 2, 14 Mill Lane, Leeds, UK" names one front door by going from
the biggest area down to the smallest. `crate::scanner::Token` does the
same, from the crate down to one struct. `super::` is "the house next
door's street", worked out from where you are standing.
<span slot="breaks">A letter can be addressed from anywhere in the
world to anywhere; a Rust path can only be followed if every module on
the way lets you through, which is what the next chapter's `pub`
decides.</span>
</Analogy>

Writing `crate::scanner::Token` everywhere would be tiring, so **`use`**
makes a short name for a path, the way `import` does. drip-rs's
compiler opens with:

```rust
use crate::chunk::{Chunk, OpCode};
use crate::gc::{Heap, Trace};
use crate::scanner::{Scanner, Token};
```

Braces bring several names from one module at once; `use a::b as c;`
renames on the way in; and `use a::*;` (the **glob**) brings in every
public name, which is handy in tests and risky elsewhere, because you
can no longer see where a name came from. A `use` covers only the
module it is written in, not its children or its parent, so each
module (each file, usually) has its own list<Cite id="rust-book-modules" />.

<Callout kind="definition">
A **module** is a named scope in a crate's module tree, declared with
**`mod name { ... }`** (inline) or **`mod name;`** (its body is read
from `name.rs`, or `name/mod.rs`, beside the declaring file). Items are
reached by **paths**: `crate::a::b` from the root, `super::x` from the
parent, `self::y` from here. **`use path;`** binds the last name of a
path as a shortcut in the current module<Cite id="klabnik2026" />.
</Callout>

<Formal title="How a path is followed">

```text
crate::p  from m  →  p from the root
super::p  from m  →  p from parent(m)
self::p   from m  →  p from m
a::p      from m  →  p from child a of m
a         in m    →  the item named a
```

<span slot="read">To follow a path from module m: crate:: jumps to the
root, super:: to m's parent, and self:: stays in m. Otherwise the first
name a must be a child of m (or a name a use brought into m), and we
carry on from there; the last name is the item itself.</span>
</Formal>

<Examples of="rust-module">

```rust
mod geom {
    pub fn area(w: f64, h: f64) -> f64 {
        w * h
    }
}
fn main() {
    println!("{}", geom::area(2.0, 3.0));
}
```

```rust
// src/lib.rs: mod vm;   src/vm.rs:
use crate::compiler::compile;
use crate::gc::Heap;
pub struct Vm { /* ... */ }
```

</Examples>

The first is the smallest module there is: `geom` is inline, and
`main`, at the root, reaches `area` by the path `geom::area` (relative,
since `geom` is a child of the root), printing `6`. The second is the
shape of every file in drip-rs: one `mod vm;` line in `lib.rs`, then
`vm.rs` starts with its own `use` lines, which reach across the tree
with `crate::`. The runnable one has a `scanner` module with a nested
`tests` module that calls its parent's function through `super::`, and
a `compiler` module that `use`s it; change the paths and watch the
errors.

The two errors you will meet most are a missing `use` and a `use`
that starts in the wrong place:

```rust
mod report {
    pub fn show() {
        area(2.0, 3.0); // E0425
    }
}
mod report2 {
    use geom::area; // E0432
}
```

```text
error[E0425]: cannot find function `area`
  in this scope
help: consider importing this function:
  use crate::geom::area;
error[E0432]: unresolved import `geom`
help: a similar path exists:
  crate::geom::area
```

In the first, `area` lives in `geom`, and nothing brought it into
`report`. In the second, a `use` path that does not start with
`crate::` starts in the current module, and `report2` has no child
called `geom`. Both help lines give the fix.

<OtherLanguages title="Using a function from another module">

```rust
// src/lib.rs
mod scanner;
mod compiler;
// src/compiler.rs
use crate::scanner::scan;
```

```ts
// compiler.ts
import { scan } from './scanner.js';
// scanner.ts is a module because it
// is a file; nothing declares it
```

</OtherLanguages>

TypeScript finds modules by file path, relative to the importing file,
and every file is a module whether anyone imports it or not. Rust finds
them by their place in one tree that the crate root declares, so
`crate::scanner::scan` means the same thing in every file of the crate;
and a Rust crate is compiled as one unit (the compilation unit of
*Modules and separate compilation*), while each TypeScript file can be
handled on its own.

## What you learned

- A crate is a **module tree** rooted at `crate`. `mod name;` pulls in
  `name.rs` (or `name/mod.rs`); a file no `mod` line names is not
  compiled. `mod name { ... }` declares one inline.
- **Paths** name items: `crate::` from the root, `super::` from the
  parent, `self::` (or nothing) from here.
- **`use`** makes a short name for a path in the current module only;
  braces, `as` and `*` bring in several, rename, or bring in all.
