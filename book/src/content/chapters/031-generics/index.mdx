## The same function, three times

What is the type of a function that returns the first item of a list?
If we write `first(xs: number[]): number | undefined`, it works only for
lists of numbers. For a list of strings we would need a second copy with
`string` in it, and a third for particles, even though the body (`return
xs[0];`) is the same every time, because it never looks at the items at
all. We want to write the function once and still have the checker know,
at every call, what kind of item comes back.

<Analogy title="a crumble recipe">
A recipe says “fruit crumble: take 500 g of the fruit of your choice”.
Make it with apples and you get apple crumble; with plums, plum crumble.
The recipe is written once, with a blank, and whatever fruit goes in is
the fruit that comes out.
<span slot="breaks">A cook can mix apples and plums in one dish; a type
parameter is filled with one type for each call (though that type may
itself be a union, such as `number | string`).</span>
</Analogy>

<Analogy title="a cloakroom">
You hand in a coat and get a ticket; later the ticket gets you back
*your* coat. The cloakroom does not care what you hand in, but whatever
kind of thing went in is the kind of thing that comes back out.
<span slot="breaks">The cloakroom really looks at your coat; the type
parameter is only a name the checker uses. It is erased before the code
runs, so the function itself can never ask what `T` was.</span>
</Analogy>

## A blank called T

```ts
function first<T>(xs: T[]): T | undefined {
  return xs[0];
}
const a = first([1, 2]);
// a: number | undefined
const b = first(['x']);
// b: string | undefined
```

`<T>` after the name declares a blank called `T` (any name works, but a
single capital letter is the custom). The parameter `xs: T[]` says “a
list of T”, and the result `T | undefined` says “one T, or nothing, for
an empty list”: the union from two chapters ago. At each call the
checker fills the blank in from the argument, so `a` is labelled
`number | undefined` and `b` is labelled `string | undefined`, all from
one definition.

<Callout kind="definition">
A **generic** function or type has a **type parameter**, such as `T`,
written in angle brackets, which is filled in with a real type each time
it is used<Cite id="ts-generics" />. Filling it in is called
**instantiating** it. `first<T>` is a generic function; `Array<T>` and
`Map<K, V>` are generic types.
</Callout>

<Formal title="The type of first">

```text
first : ∀T. T[] → T | undefined
first([1, 2]) : number | undefined
```

<span slot="read">The symbol ∀ reads “for every”: for every type T,
first takes a list of T and gives back a T or undefined. In the call on
the second line, T is number, so the result is a number or
undefined.</span>
</Formal>

<Examples of="generic">

```ts
function last<T>(xs: T[]): T | undefined {
  return xs[xs.length - 1];
}
last(['a', 'b']); // 'b', a string
```

```ts
const m = first([1, 'a']);
// m: string | number | undefined
const n = first<number>(['x']);
// error: Type 'string' is not
// assignable to type 'number'.
```

```ts
const v = first(scores);
if (v !== undefined) {
  console.log(v.toFixed(1));
}
```

</Examples>

The first is a twin of `first` that reads the last slot (`xs.length -
1`, from chapter 3); called on strings, its result is
`string | undefined`. The second shows two things: a list holding both
numbers and strings fills `T` with the union `string | number`, and you
may also fill the blank by hand, `first<number>(...)`, in which case the
checker holds the argument to it and rejects a list of strings. The
third, with `scores` a list of numbers, puts it together: `first` returns
`number | undefined`, the `!== undefined` check narrows it to `number`,
and only then may we call `toFixed`.

## Generic types

Types can have blanks too. You have been using one all along:
`number[]` is a short way of writing `Array<number>`, the generic type
`Array<T>` with `number` in the blank, and the unions chapter's
`new Map<string, number>()` filled both blanks of `Map<K, V>` (the key
type and the value type). You can write your own with `type`:

```ts
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; error: string };

const r: Result<number> =
  { ok: true, value: 42 };
const s: Result<string> =
  { ok: false, error: 'not found' };
```

`Result<T>` is last chapter's tagged union with a blank in it: a result
that worked holds a `value` of type `T`, and one that failed holds an
`error` message. `Result<number>` is a result whose value is a number;
`Result<string>`, one whose value is a string. Writing
`{ ok: true, value: 'x' }` as a `Result<number>` is an error, because the
blank was filled with `number`.

<OtherLanguages>

```ts
function first<T>(xs: T[]): T | undefined {
  return xs[0];
}
```

```js
// no types, so nothing to fill in
function first(xs) {
  return xs[0];
}
```

```python
def first[T](xs: list[T]) -> T | None:
    return xs[0] if xs else None
```

```java
static <T> T first(List<T> xs) {
    return xs.isEmpty() ? null : xs.get(0);
}
```

```c
/* no generics: void * means "a pointer
   to anything", and the type is lost */
void *first(void **xs, size_t n) {
    return n > 0 ? xs[0] : NULL;
}
```

</OtherLanguages>

Python (from version 3.12) writes the blank in square brackets after the
name, and as before nothing enforces it unless you run a checker. Java
puts `<T>` before the result type, and, like TypeScript, erases it: at
run time a `List<String>` and a `List<Integer>` are the same kind of
object. Java's blanks must be filled with objects, not plain numbers,
which is why it writes `List<Integer>` rather than `List<int>`. C has no
generics at all; the usual trick is `void *` (a pointer to anything),
which works but throws the type away, so the compiler can no longer
catch a mix-up.

## How the checker fills in T

You rarely write `first<number>(...)` by hand, because the checker works
`T` out from the arguments, a step called **type inference**. It is at
its most useful with callbacks: once `T` is known from one argument, the
callback's parameter gets its type for free. Step through a call:

<InferSteps client:visible />

The first argument, `[3, 8, 12]`, has to match `xs: T[]`, so `T` is
`number`; the callback's parameter is `x: T`, so `n` is a number without
any label, and `n > 5` is allowed; and the result `T | undefined` makes
`big` a `number | undefined`. The same inference catches a mistake:

```ts
firstWhere([3, 8], (n) => n.toUpperCase());
// error: Property 'toUpperCase' does not
// exist on type 'number'.
```

Here `T` is `number` again, so `n` is a number, and numbers have no
`toUpperCase`. Generics have much more to them (limiting what `T` may
be, giving a blank a default, letting several blanks depend on each
other), and TypeScript III covers them in depth.

<Callout kind="engine" label="Under the hood">
Like every other type, a type parameter is erased: `first<T>` becomes
`function first(xs) { return xs[0]; }`, one function for every caller,
which is why the body can never ask what `T` was<Cite id="ts-generics" />.
Viscosity leans on generic types throughout: in
`engine/ts/packages/core/src/analysis.ts`, for instance,

## What you learned

- A **generic** function like `first<T>` has a **type parameter** that
  each call fills in, so one definition keeps the real type for every
  caller.
- Types can be generic too: `Array<T>` (written `T[]`), `Map<K, V>`, and
  your own, such as `Result<T>`.
- The checker usually **infers** `T` from the arguments, and then knows
  the types inside your callbacks. `T` is erased before the code runs.
