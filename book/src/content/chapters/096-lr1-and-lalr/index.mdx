## Each item remembers what may follow

The last chapter ended with SLR asking the wrong question. In state 2
of the assignment grammar it reduced `R → L` under `=`, because *some*
`R` somewhere can be followed by `=`; but the `L` in state 2 starts a
statement, and an `R` made from it can only be followed by the end of
the input. Here is the grammar again:

```text
S → P
P → L = R      P → R
L → * R        L → id
R → L
```

The cure is to stop asking about the grammar as a whole and let every
item carry the answer for its own situation.

<Analogy title="a parcel with a delivery label">
A sorting office handles thousands of identical brown boxes; what tells
them apart is the label on each, which says where it is going. Two
boxes with the same contents but different labels go to different
places.
<span slot="breaks">A parcel's label is written once, by the sender;
an item's lookahead is worked out by the parser generator, and the same
rule gets a different label each time it is reached from a different
place.</span>
</Analogy>

<Callout kind="definition">
An **LR(1) item** is a pair `[A → α · β, a]`: an LR(0) item (its
**core**) and a terminal `a`, its **lookahead**. It means "we are this
far through `A → α β`, and once it is finished, the next token will be
`a`". A complete item `[A → α ·, a]` allows the reduction only when the
next token is `a`. An **LR(1) parser** (also called *canonical LR*)
uses the automaton built from these items.
</Callout>

Closure now has to work out lookaheads. For an item
`[A → α · B β, a]`, the new items for `B` get every token that can come
right after that `B`: the first token of `β`, or, if `β` is empty (or
can vanish entirely), `a` itself. The FIRST sets of "FIRST and FOLLOW" do exactly
this job. Step through state 0:

<Lr1ClosureSteps client:visible />

<Formal title="LR(1) closure">

```text
[A → α · B β, a] in closure(I),
B → γ in G,  b ∈ FIRST(β a)
──────────────────────────────
  [B → · γ, b] in closure(I)
```

<span slot="read">If the closure holds an item with the dot before B
and lookahead a, and the grammar has a rule B goes to gamma, then for
every token b that can start beta followed by a, the closure also holds
B goes to dot gamma with lookahead b. goto is unchanged: it moves the
dot and keeps each item's lookahead.</span>
</Formal>

<Examples of="lr1">

```text
[R → L ·, $]   reduce only before $
[R → L ·, =]   reduce only before =
same core, two different items
```

```text
[P → · L = R, $] gives [L → · id, =]
[P → · R, $]     gives [R → · L, $]
then [L → · id, $]
```

```text
expression grammar with *:
LR(0) automaton  12 states
LR(1) automaton  22 states
```

</Examples>

The first shows what the lookahead adds: the two items have the same
core, and differ only in which token permits the reduction, so a state
holding just the first one reduces under `$` and nowhere else. The
second is the step-through in two lines: an `L` that starts `L = R` is
followed by `=`, while an `L` reached through `R` gets `$`. The third
is the price, counted by building both automata for the expression
grammar: LR(1) splits states whenever the same core turns up with
different lookaheads (an `F` inside brackets is followed by `)`, one at
the top level by `$`), and for a real programming language the growth is
large: Bison's manual says that state-merging methods often need an
order of magnitude fewer states than canonical LR<Cite id="bison-manual" />.

## LALR: merge what looks the same

Look at the LR(1) states of the assignment grammar and you find pairs
that are twins except for their lookaheads: the state after `*` at the
top level and the one after `*` on the right of `=` both have the core
`L → * · R`, `R → · L`, `L → · * R`, `L → · id`. Merging every such pair
(keeping one state, with the lookaheads of both) gives exactly as many
states as the LR(0) automaton, and usually keeps LR(1)'s precision.

<Analogy title="two classes in one room">
A school has two small classes doing the same lesson, so it puts them in
one room; the register for the room lists the pupils of both. Nothing
is lost, as long as nobody needed to know which class a pupil came from.
<span slot="breaks">Pupils keep their own names, so the school can sort
them out again; a merged state keeps only the combined set of
lookaheads, and which context each token came from is gone for
good.</span>
</Analogy>

<Callout kind="definition">
The **core** of an LR(1) state is its set of LR(0) items, with the
lookaheads ignored. An **LALR** (*look-ahead LR*) parser merges all
LR(1) states with the same core into one, whose items carry the union
of their lookaheads. It has as many states as the LR(0) automaton, and
it parses every LR(1) grammar whose merged table still has no
conflicts.
</Callout>

<Examples of="lalr">

```text
[L → * R ·, =]  and  [L → * R ·, $]
merge into  L → * R ·  on { = $ }
assignment grammar: 14 states → 10
```

```text
expression grammar: 22 → 12 states,
no conflicts, same table as SLR
```

```text
P → a A d | b B d | a B e | b A e
A → c        B → c
LR(1): fine.  LALR: reduce/reduce
```

</Examples>

The first is merging doing its job: both states reduce `L → * R`, and
the merged state does so on either token, which is right in both
contexts, so the assignment grammar is LALR(1) with ten states and no
conflict. The second shows that for everyday grammars LALR and SLR
often agree; LALR's extra precision only shows in grammars like the
assignment one. The third is the case to remember, and the figure shows
why: after `a c` the parser must reduce to `A` before `d` and to `B`
before `e`; after `b c` it is the other way round. Each LR(1) state is
fine on its own, but they have the same core, and merging them puts
both reductions under both tokens.

<Figure takeaway="Merging can create a reduce/reduce conflict that LR(1) did not have." caption="The two LR(1) states after a c and after b c have the same core, so LALR merges them, and the union of their lookaheads puts both reductions under d and under e.">
  <MergeConflict />
</Figure>

Merging can only ever cause this kind of conflict. A shift depends on
the core alone, so if a merged state had a shift/reduce conflict, one of
the original LR(1) states would have had the same shift beside the same
reduction already; but two reductions can meet for the first time when
their lookaheads are pooled. Frank DeRemer invented LALR in his 1969
thesis, as a way to get LR(1)'s power at LR(0)'s
size<Cite id="deremer1969" />, and the trade has held up: yacc and Bison
both build LALR(1) tables, and the dragon book treats canonical LR and
LALR together, as its "more powerful LR parsers"<Cite id="aho2006" />.

## Conflicts in a real parser generator

Bison, the GNU version of yacc, builds LALR(1) tables by default ("for
historical reasons", its manual says) and offers IELR(1) and canonical
LR(1) as options. Give it the ambiguous grammar `exp → exp + exp |
exp - exp | exp * exp | exp / exp | NUM`, and it warns:

```text
calc.y: warning:
  16 shift/reduce conflicts
State 8 conflicts: 4 shift/reduce
State 9 conflicts: 4 shift/reduce
State 10 conflicts: 4 shift/reduce
State 11 conflicts: 4 shift/reduce
```

The second part comes from its report file, which lists every state and
the conflicts in it: one state for each operator, holding a finished
`exp op exp`, and in each a conflict under all four operators that might
come next. A conflict is not fatal: Bison settles a
shift/reduce conflict by shifting, and a reduce/reduce conflict by the
rule that comes first in the grammar, though its manual warns that this
is "very risky to rely on". The intended fix for operators is a
precedence declaration, where later lines bind
tighter<Cite id="bison-manual" />:

```text
%left '+' '-'
%left '*' '/'
```

Each rule takes the precedence of its last terminal, so `exp '+' exp`
has `+`'s level. On a shift/reduce conflict Bison compares the rule
with the next token: if the token's level is higher it shifts, if the
rule's is higher it reduces, and on a tie `%left` reduces (grouping to
the left) while `%right` shifts. With `exp + exp` on the stack and `*`
next, `*` is higher, so it shifts; with `+` next, it is a tie and `+` is
left-associative, so it reduces. Try it:

<Run id="precedence" />

The classic shift/reduce conflict outside arithmetic is the
**dangling else**: in `if a then if b then x else y`, does the `else`
belong to the inner or the outer `if`? Shifting, Bison's default, gives
it to the inner one, which its manual calls the established
convention<Cite id="bison-manual" />. Drip side-steps the
question in its grammar: an `if` must be followed by a block in braces,
`if c { ... } else { ... }`, so every `else` has exactly one `if` it can
belong to.

## What you learned

- An **LR(1) item** adds a lookahead to an LR(0) item; closure gives new
  items the lookaheads in `FIRST(β a)`, and a reduction happens only on
  its own lookahead. LR(1) is the most precise of the three, and the
  largest.
- **LALR** merges LR(1) states with the same core and unites their
  lookaheads: LR(0)'s size, nearly LR(1)'s power. Merging can create
  reduce/reduce conflicts, never new shift/reduce ones.
- Bison builds LALR tables by default, reports conflicts per state,
  shifts on a shift/reduce conflict unless **precedence declarations**
  say otherwise, and settles reduce/reduce by rule order.
