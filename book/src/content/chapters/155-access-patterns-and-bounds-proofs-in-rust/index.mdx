## What the planner needs to know

The Rust engine has found the collections and proved that nothing can
see their layout change. Would a new layout pay off? The planner needs
the facts of *Access patterns* and *Proving it safe*:

```js
const ps = [];
for (let i = 0; i < 500; i++)
  ps.push({ x: i, y: 0, vx: 1, vy: 2 });
for (let i = 0; i < ps.length; i++) {
  ps[i].x += ps[i].vx;
  ps[i].y += ps[i].vy;
}
let s = 0;
for (let i = 1; i < ps.length; i++)
  s += ps[i - 1].x;
console.log(s, ps[0].y);
```

and the end of what `viscosity explain` says about it (Rust CLI,
release build, rustc 1.97; the TypeScript CLI printed the same; lines
wrapped):

```
  · loop at line 4 in <module>() touches 4
    of 4 fields (vy, y, vx, x)
  · loop at line 9 in <module>() touches 1
    of 4 fields (x)
  · about 500 elements
  · 4 of 6 element accesses proven in
    bounds
```

All three facts come from one function in `analysis.rs`,
`bounds_loops_and_sizes`.

## One table per loop

Each field read or write on an element is filed under the loop it
happens in, in a plain struct (from `analysis.rs`, doc comments left
out):

```rust
pub struct LoopAccess {
    pub func: String,
    pub line: u32,
    pub depth: u32,
    pub reads: IndexSet<String>,
    pub writes: IndexSet<String>,
    pub trips: Option<f64>,
}
```

`depth` is 1 for an outermost loop (0 outside loops), and `trips` is the
loop's constant trip count, if any. An **`IndexSet`** remembers the order
things were first added, as a JavaScript `Set` does<Cite id="indexmap-docs" />.
The heart of the filing loop (rewrapped):

```rust
let l = loop_of(loops, ai.block);
let la = by_loop
    .entry((f, l.map(|l| l.header)))
    .or_insert_with(|| { /* new table */ });
match a.kind {
    AccessKind::Read => la
        .reads.insert(a.field.clone()),
    AccessKind::Write => la
        .writes.insert(a.field.clone()),
};
```

`loop_of` returns the innermost natural loop around the access, or
`None`. The key is a tuple, `(FuncId, Option<BlockId>)`, where the
TypeScript builds a string such as `` `${f.id}:${l.header}` ``, because a
JavaScript `Map` compares object keys by identity; Rust's tuple compares
by value, and `None` is a real key. `or_insert_with` runs its closure
only the first time a key is seen, and either way `entry` hands back
`&mut LoopAccess` for the `match` to fill. The tables are then sorted by
line with the stable `sort_by_key`<Cite id="rust-std-slice-sort-by-key" />.

<TableSteps client:visible />

Why `(vy, y, vx, x)`? Fields keep the order the pass *visits* them,
which is the order the collection pass's worklist found the element
reads, last load first, in both engines.

<More title="More: the size estimate, and three programs">

The analysis counts the elements of the array literal and, for each
`push`, multiplies the trip counts of every loop around it; a trip count
is known only for `for (let i = 0; i < N; i++)` with a constant `N`. A
push that may not run on every trip (one inside an `if`, which does not
dominate every way out of its loop) makes the size only a maximum, and
a push inside a function other than the top-level code makes it
unknown. Two lines store the result:

```rust
c.size_estimate = known.then_some(size);
c.size_is_upper_bound = known && upper;
```

`bool::then_some` gives `Some(size)` when `known` is true and `None`
otherwise, so an unknown size cannot be mistaken for zero.

## Four questions

An unproven element read becomes `ps.x[__vsc_bc(ps, i, 'x', false)]`, a
check on every access (*Rewriting field accesses and growing
collections*), in exactly the loops Viscosity wants to speed up.

<Analogy title="climbing a ladder in the dark">
You can climb a ladder you cannot see without ever grabbing air, if you
keep three rules: start on a rung you know is there, only ever move up
one rung, and before each move feel that there is a rung above. Nobody
has to count the rungs for you; the rules alone keep you on the ladder.
<span slot="breaks">A ladder can't change while you climb; an array
can grow during the loop. That is fine, because the guard rereads
`ps.length` on every trip, and a collection Viscosity transforms can
only use `.length` and `.push`, so it never gets shorter.</span>
</Analogy>

The proof asks four questions of each element read (each `index.get` in
VIR), and an access is proven only if all four say yes:

1. Is the index the phi at the header of some loop that contains the
   access? (Any enclosing loop counts, not only the innermost.)
2. Is that phi a **counting phi**: it starts at a non-negative whole
   number and steps by `+ 1`?
3. Does that loop's header test `index < c.length`, for this same
   collection (one conjunct of an `&&` is enough)?
4. Does the true edge of that test **dominate** the access, so that the
   access can only be reached after the test said yes?

<Callout kind="definition">
The **access-pattern pass in Rust** is `bounds_loops_and_sizes` in
`analysis.rs`. It files each field access into **one `LoopAccess` per
loop**, keyed by `(FuncId, Option<BlockId>)` in an `IndexMap`; estimates
the **size** as an `Option<f64>`; and marks an
element read `c[i]` **proven in bounds** when `i` is a **counting phi**
of a loop around it, that loop's header tests **`i < c.length`**, and
the test's **true edge dominates** the read.
</Callout>

<Examples of="rust-access-pass">

```js
for (let i = 0; i < ps.length; i++)
  for (let j = i + 1;
      j < i + 8 && j < ps.length; j++)
    ps[i].x += ps[j].x;
// 2 of 2 element accesses proven
```

</Examples>

`ps` holds 100 pushed records (left out), and the comment is the Rust
CLI's verdict. `ps[j]` is proven although `j` starts at `i + 1`, because
question 2 only asks for a non-negative integer start, which `i + 1` is;
the guard is split into its conjuncts, and `j < ps.length` is the test
question 3 wants; and the body is reached only through its true edge.
`ps[i]` is proven through the *outer* loop, since any enclosing loop
counts. In the opening program, by contrast, `ps[i - 1]` (a subtraction, not the
phi) and `ps[0]` (outside every loop) are not proven: 4 of 6.

## The counting phi, and its cycle

In SSA, a loop variable becomes a phi at the loop header: `i = φ(0, i +
1)` means "0 when we arrive from before the loop, `i + 1` when we come
back round". The test for question 2, `is_counting_phi`, rewrapped, with
the step test shortened to a comment:

```rust
for (s0, s1) in [(0, 1), (1, 0)] {
    let start = self.inst(phi.args[s0]);
    let step = self.inst(phi.args[s1]);
    // continue unless step is phi + 1
    let start_ok = if zero_start {
        start.op == Op::Const(
            Const::Number(0.0))
    } else {
        self.non_neg_int(start,
            &mut HashSet::default())
    };
    if start_ok { return true; }
}
```

A phi's operands are listed in the order of the header's predecessor
blocks, which says nothing about which one is the start, so the loop
tries both orders: `[(0, 1), (1, 0)]` is an array of two tuples. The
`zero_start` flag serves two callers: trip counts need a start of
exactly `0`, while bounds only need a non-negative integer, which is the
job of `non_neg_int`. Its first lines (rewrapped; the `+`, `*` and unary
`+` arms left out):

```rust
if !seen.insert(v.id) {
    return true;
}
match &v.op {
    Op::Const(Const::Number(x)) => x
        .is_finite()
        && x.trunc() == *x
        && *x >= 0.0,
    Op::Phi => v.args.iter().all(
        |&a| self.non_neg_int(
            self.inst(a), seen)),
    _ => false,
}
```

`HashSet::insert` returns `false` when the value was already in the
set<Cite id="rust-std-hashset-insert" />, so one call both records the
visit and asks "have I been here?". A start like `j = i + 1` leads to
`i`, which is `φ(0, i + 1)`, which leads to `i` again. Answering `true`
on the second visit is an optimistic assumption ("suppose `i` is fine")
that the rest of the cycle must earn, here with `0` and `1`; `false`
would also end the walk, but then no start mentioning a loop variable
could pass.

<More title="More: the guard, and two phases for the borrow checker">

`conjuncts` flattens `a && b && c` into a list, and one conjunct must be
a `<` whose left side is the index and whose right side is a `.length`
read of a load of this same collection. Each answer is pushed into a
local `Vec<bool>` (`proven.push(guarded && idom.dominates(then,
gi.block))`), and only after the loop over all reads are the answers
stored, with `iter_mut().zip(proven)`. The first loop calls `&self`
methods such as `is_counting_phi`, which borrow all of `self`, so it
can't also hold a mutable borrow of a collection's element reads: read
everything, then write. The TypeScript sets `ig.boundsProven = true`
inside its loop, which JavaScript allows.

The proof is cautious, and the port keeps every caution: `i <= ps.length`
is not proven (rightly: on the last trip the read throws), `i < 100` is
not proven even when `ps` holds 100 elements, because the test must read
`ps.length`, and `i += 2` is not, because the step must be `+ 1`.

</More>

## What you learned

- Field accesses go into **one `LoopAccess` per loop**, keyed by a
  **tuple** in an **`IndexMap`**, fields in **visit order**.
- An element read is **proven in bounds** when its index is a
  **counting phi** of a loop around it, the header tests **`index <
  c.length`**, and that test's true edge **dominates** the read.
- `is_counting_phi` tries **both orders**; `non_neg_int`'s **`seen`**
  set carries the walk round a phi's cycle exactly once.
