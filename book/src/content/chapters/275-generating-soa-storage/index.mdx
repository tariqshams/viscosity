## Where do the columns live?

The planner has said `soa` for this program, and now the compiler has
to make it true:

```js
const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
```

Nothing in JavaScript is a "struct of arrays"; there are objects, plain
arrays and typed arrays, and the compiler has to build the new layout
out of those. This is code generation in the sense of *Emitting
JavaScript*: the plan is a decision, and now somebody has to write the
code that carries it out. Viscosity's answer is to write a small class
at the top of your file and to replace the empty array with one of its
objects, `const ps = new __Vsc_ps();`. Everything about the new layout
lives inside that class.

## One array per field

Start with what the class holds: one array per field, instead of one
object per element.

<Analogy title="a register and a spreadsheet">
A paper visitors' book has one row per visitor, with their name, time and
reason written across it. A spreadsheet of the same visits keeps one
column per question, every name in column A and every arrival time in
column B, and visitor 7 is row 7 of every column. To add a visitor you
write one cell in each column, on the same row.
<span slot="breaks">A spreadsheet will happily let you sort one column on
its own; do that to Viscosity's columns and every record is scrambled,
because the shared row number is the only thing holding a record
together.</span>
</Analogy>

<Analogy title="a chest of drawers">
You can pack each day's outfit in its own bag, or keep all the socks in
one drawer and all the shirts in another; Monday's outfit is then "the
first sock, the first shirt". If all you want this morning is socks, you
open one drawer and never touch the shirts.
<span slot="breaks">Socks in a drawer are in no particular order, and any
pair will do; column `x` must keep element 7's `x` in slot 7, exactly,
and slot 8 belongs to element 8.</span>
</Analogy>

<Figure caption="The same three records, as objects and as columns. Element i is index i of every column, and nothing else ties a record together." takeaway="A record stops being an object and becomes an index.">
  <Columns />
</Figure>

<Callout kind="definition">
**Column storage** keeps one array per field: every `x` together, every
`vx` together, with element `i`'s fields at index `i` of each column.
Viscosity uses a `Float64Array` column for a field it has proved is
always a number, and a plain JavaScript array for any other field.
</Callout>

<Formal title="An element, as a row across columns">

```text
ps[i]  ≅  ( x[i], vx[i] )     0 ≤ i < length
```

<span slot="read">Element i of the original array corresponds to (≅,
"stands for the same thing as") the pair made of slot i of column x and
slot i of column vx, for every i from 0 up to, but not including, the
length.</span>
</Formal>

Why two kinds of column? A `Float64Array` stores raw 64-bit doubles side
by side, with no object per value<Cite id="mdn-typed-arrays" />, which is
the whole point; however, it stores only numbers, and anything else you
write into it is converted:

<Run id="typedcol" />

Line by line: a new `Float64Array(4)` is four zeros; `2.5` and `-0` are
stored exactly (`Object.is` tells `-0` from `0`); the string `'7'`
comes back as the number `7`, and `'abc'` as `NaN`; a write past the end
is silently dropped; and a plain array takes anything and grows. So a
typed column is correct only for a field the numeric analysis from
*Record shapes* has proved is always a number.

<Examples of="column-storage">

```js
ps.push({ x: i, vx: 1 });
// x and vx are numbers: two
// Float64Array columns, ps.x and ps.vx
```

```js
es.push({ id: 'e' + i, hp: 100, x: i,
  tag: i % 3 ? null : { boss: true } });
// hp, x: Float64Array; id, tag: plain
```

```js
const pts = [{ x: 1, y: 2 },
  { x: 3, y: 4 }, { x: -0, y: NaN }];
// → __Vsc_pts.of(1, 2, 3, 4, -0, NaN)
```

</Examples>

The first is the particle shape: both fields are numbers in every push,
so both get typed columns. The second is the corpus file
`mixed_columns.js`: `id` is a string and `tag` is `null` or an object,
so explain reports "typed Float64Array columns for hp, x; plain array
columns for id, tag (may hold non-numbers)", and the constructor makes
`this.id = []; this.tag = [];`. The third, `literal_init.js`, shows that
the awkward doubles survive: after compiling, `Object.is(pts[2].x, -0)`
and `Number.isNaN(pts[2].y)` still print `true`, because a
`Float64Array` holds any IEEE 754 double exactly.

## The container class

The columns need somewhere to live, along with the count of elements and
the one method most programs call, `push`.

<Analogy title="a filing cabinet with a tally on top">
The cabinet has one drawer per kind of paper, and a card on top saying
how many files are in it and how many fit. Filing a new case means
putting its papers in the same position in every drawer and then
updating the card; when the drawers are full, you buy a bigger cabinet.
<span slot="breaks">A clerk can file papers in any order; the container's
`push` always writes slot `length` and nothing else, so the drawers can
never get out of step.</span>
</Analogy>

Here is the class Viscosity emits for `ps`, with records `{ x, vx }`.
The compiler writes each member on one long line; the stepper reflows it
to fit, with nothing else changed. Step through it:

<ContainerSteps client:visible />

<Callout kind="definition">
An **SoA container** is the object that holds a collection's columns,
with `length` (elements in use), `cap` (slots per column) and the
methods the program still needs: `push`, which takes one value per field
and returns the new length, `grow`, and `of` for array literals.
Viscosity generates one container class per transformed collection,
named `__Vsc_` plus the collection's name.
</Callout>

<Examples of="soa-container">

```js
const ps = [];
// → const ps = new __Vsc_ps();
```

```js
n = ps.push({ x: i, vx: 2 });
// → n = ps.push(i, 2);
//   n is still the new length: 100
```

```js
ps.push({ length: i, cap: 1, 'a-b': 2 });
// columns: ps.f0_, ps.f1_, ps.f2_
// ps[i].length → ps.f0_[i]
```

</Examples>

The first is creation, the one edit every transformed collection gets.
In the second, the program keeps the value `push` returns; after 100
pushes both versions print `100`, because the generated `push` returns
`this.length` just as `Array.prototype.push` does. The third is the
awkward case. The container already has members called `length`, `cap`
and `push`, so a field with one of those names would overwrite them, and
`'a-b'` is not a name you can write after a dot at all. The emitter
therefore renames any field that is reserved (`length`, `push`, `grow`,
`of`, `constructor`, `prototype`, `get`, `cap`, `data`) or is not a
plain identifier to `f`, its position and `_`. The program's
`ps[i].length` becomes `ps.f0_[i]`, while `ps.length` stays the element
count. And if a real field is already called `f0_` (records
`{ length: i, f0_: 2 }`, the corpus file `renamed_column_clash.js`), the
renamed column takes one more `_`, `f0__`, until the name is free.

## Watching it grow

The columns are fixed-size `Float64Array`s, so the container has to make
room itself. Step through the first seventeen pushes of
`for (let i = 0; i < N; i++) ps.push(i, 1)`:

<GrowSteps client:visible />

The check `n === this.cap` runs on every push and is almost always false,
so a push is two stores and an addition; the copying happens only on the
17th push, the 33rd, the 65th and so on, and only for typed columns, since
a plain array lengthens by itself. *Growing collections* shows why
doubling makes that cheap on average.

<Callout kind="engine" label="Under the hood">
ISPC does the same job inside a compiler for C-like code. Declaring
`soa<8> Point pts[...]`, for `struct Point { float x, y, z; }`, stores the
array as if each block were `struct { uniform float x[8], y[8], z[8]; }`
<Cite id="ispcdocs" />: a generated container, as here, but with the
columns cut into blocks of eight (Viscosity's blocked version is *AoSoA
code generation*). One difference matters for JavaScript: Viscosity can
use a typed column only when it has proved the field is a number,
because a JavaScript field has no declared type.
</Callout>

## What you learned

- **Column storage** keeps one array per field; element `i` is index `i`
  of every column. Provably numeric fields get a `Float64Array`, the
  rest a plain array.
- The **SoA container** is a generated class: `length`, `cap`, one
  column per field, `push` (one value per field, returns the new
  length), `grow` and `of`.
- Fields whose names clash with the container's own members, or are not
  plain identifiers, are renamed `f0_`, `f1_`, … (with an extra `_`
  if needed), invisibly to the program.
