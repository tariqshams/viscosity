## One file in, one file out

Seven parts have handed you the pieces: arrays of objects, parsers,
IRs, SSA form, dataflow, alias and escape analysis, a native back end
and differential tests. Part VIII puts them together into
**Viscosity**, the compiler in this repository's `engine/ts` folder, and
the first question to ask of any machine is what goes in and what comes
out. In goes a plain particle program:

```js
const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
console.log(ps[3].x);
```

and what comes out, a new JavaScript file whose last lines are these (a
generated class `__Vsc_ps` with one `Float64Array` per field sits above
them, along with a small bounds-check helper):

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 1000; i++)
  ps.push(i, 1);
for (let i = 0; i < ps.length; i++)
  ps.x[i] += ps.vx[i];
console.log(ps.x[__vsc_bc(ps, 3, 'x',
  false)]);
```

(The last line is split here to fit.) Every `ps[i].x` became a column
access `ps.x[i]`, the struct-of-arrays change from the chapter *AoS vs
SoA, measured*; this chapter is about what happened in between.

## Four steps, two owners

The top of the compiler is surprisingly small. The function `compile`,
in `packages/core/src/index.ts`, is the whole pipeline, and this is the
part that matters:

```ts
function compile(source, plugin, opts) {
  const lowered = plugin.lower(source);
  const analysis =
    analyze(lowered.module);
  const p = plan(analysis, opts);
  const code =
    plugin.emit(source, lowered, p);
  return { code, plan: p, analysis,
    explain: explain(p) };
}
```

(Trimmed: the real one also fills in default options.) Line 2 hands
the text to a
**plugin**, the part that knows one language, which parses it and
**lowers** it to VIR, Viscosity's IR. Line 3 runs the **analyses** on
that VIR, and line 5 turns their facts into a **plan**: one layout per
collection. Line 6 gives the plan back to the same plugin, which
**emits** new source text; the last line returns that text, the plan,
the analysis and a readable explanation of every decision.

<Analogy title="a hospital laboratory">
On each ward, a nurse who speaks the patient's language takes a blood
sample and labels the tube in the hospital's standard form. The central
laboratory never meets a patient: it reads the tubes, runs the same tests
for every ward and sends back a result sheet. Then the ward nurse, who
knows the patient, acts on the sheet. The wards are the plugins, the
labelled tube is VIR, and the laboratory is the core.
<span slot="breaks">A laboratory can send back a result that nobody acts
on; Viscosity's plan is always carried out, and when the core is unsure it
plans to change nothing at all.</span>
</Analogy>

<Analogy extra title="a removal company re-packing a kitchen">
A local crew reads the labels on your boxes, in whatever language you
wrote them, and phones head office with a list ("40 forks, all the same
size"). Head office decides how they should be packed without ever seeing
your kitchen, and the crew re-packs to that plan, leaving everything it
was not told about exactly where it was.
<span slot="breaks">Real removers move everything; Viscosity's crew
touches only the few characters the plan names, and the rest of your
file is copied through byte for byte.</span>
</Analogy>

Step through one program, and watch the label above each stage: two of
the steps belong to the language plugin, and the rest to the core.

<Callout kind="definition">
The **Viscosity pipeline** is `lower → analyze → plan → emit`. A
language plugin **lowers** source code to **VIR**, Viscosity's IR. The
analyses and the **layout planner** work on VIR alone and choose a
layout for each collection (`aos`, `soa` or `aosoa`). The same plugin
then **emits** new source code by applying the plan. Only lowering and
emitting know the language.
</Callout>

This is the front-end and back-end split from the chapter *From source
text to a running program*, with a twist: the plugin does both ends, and
the middle (the SSA, dataflow and escape analysis of Part VI) is
shared.

<Formal title="The pipeline as function composition">

```text
lower   : Source → Lowered
analyze : VIR → Analysis
plan    : Analysis → Plan
emit    : Source × Lowered × Plan → Source

compile(s) = emit(s, L,
                  plan(analyze(L.module)))
  where L = lower(s)
```

<span slot="read">Each step is a function from one kind of thing to
another (× means "together with"): emit takes the source, the lowered
module and the plan, and gives back source. To compile s, lower it once
and call the result L; feed L's module to analyze, the facts to plan,
and everything to emit. The output has the same type as the input:
source.</span>
</Formal>

<Prompts ids={['arch-four', 'arch-owners', 'arch-why-split']} />

Notice that emit does *not* print the program back out of VIR: it
replaces only the ranges of your text that the plan requires, using the
pointer back to the source that each VIR instruction keeps, so your
comments, formatting and unrelated lines come through as you wrote
them.

Every program goes through all four steps, whatever the verdict; here
is what `viscosity explain` prints for three of them (wrapped to fit).

<Examples of="viscosity-pipeline">

```js
let total = 0;
for (let i = 0; i < 10; i++) total += i;
// explain: No arrays of objects found.
```

```js
const ps = [];
for (let i = 0; i < 10; i++)
  ps.push({ x: i, vx: 1 });
for (const p of ps) p.x += p.vx;
// ps (line 1) {x, vx} → kept as array
//   of objects
//   · about 10 elements: below the
//     64-element threshold, where the
//     benefit is too small
```

```js
// the particle program, as above
// ps (line 1) {x, vx} → struct of arrays
//   · loop at line 4 … touches 2 of 2
//   · about 1000 elements
//   · 2 of 3 element accesses proven
//     in bounds
```

</Examples>

In the first, lowering finds no array of records, so the plan is empty
and emit returns your file unchanged. In the second, the analyses find a
collection, `ps`, but the planner's cost rule (at least 64 elements by
default) says a new layout cannot pay for itself. In the third, every
check passes and the plan says struct of arrays; "2 of 3" is because
`ps[3]` is not proven in bounds, which is why the output wraps it in the
`__vsc_bc` check.

## Output that is source code

The input was JavaScript, and so is the output: you can read it, diff it,
commit it, and run it on any engine.

<Callout kind="definition">
A **source-to-source compiler** (sometimes called a *transpiler*) is a
compiler whose output is source code in a high-level language, often the
same language it reads. That output is then run or compiled by an
ordinary tool. Viscosity reads JavaScript, TypeScript or Python and
writes JavaScript or Python.
</Callout>

<Examples of="source-to-source">

```ts
interface P { x: number; vx: number }
const ps: P[] = [];
// out (the interface line is now blank):
const ps = new __Vsc_ps();
```

```py
# @viscosity soa
ps = []
# out: ps = _Vsc_ps()
```

</Examples>

The first is real output for a TypeScript file: the plugin strips the
types first (as in the chapter *Interfaces, erasure and typeof*), so the
output is plain JavaScript. The second is the Python plugin, writing
Python with a generated `_Vsc_ps` class. The runnable one does the
change by hand and prints the same answer twice; change the numbers and
check that both halves still agree.

## Ahead of time, or inside the engine

Viscosity is not the first system to turn arrays of JavaScript objects
into columns. As the chapter *Columnar arrays at run time: the research*
described, Makor and colleagues did it *while the program runs*, inside a
JavaScript engine built on Truffle and Graal<Cite id="makor2022" /><Cite id="wurthinger2013" />,
and a follow-up generated specialised loop code for the converted
arrays<Cite id="kloibhofer2023" />.

<Figure caption="The same idea in two places. Viscosity changes the program before it runs; the run-time approach changes the engine." takeaway="Ahead of time works with any engine but must prove safety from the code alone.">
  <WhenItHappens />
</Figure>

The trade is real in both directions. A run-time transformation sees the
actual values and can speculate, then back out with deoptimisation if a
guess fails (as in the chapter *Speculation and deoptimization*);
however, it only helps programs on that one engine. Viscosity's
output runs anywhere, adds no work at start-up and can be read by a
person; in exchange it gets one look at the code, with no values and no
way to back out. As such, every decision must be *proved* from the text
alone, and when a proof fails the collection stays exactly as it was.

## What you learned

- The **Viscosity pipeline** is `lower → analyze → plan → emit`, in one
  short `compile` function.
- **Lower** and **emit** belong to a language plugin; **analyze** and
  **plan** belong to the core and see only VIR.
- Emit edits the *original text* range by range, so untouched code
  survives exactly.
- Viscosity is a **source-to-source compiler**: JavaScript in,
  JavaScript out, runnable on any engine.
- Working ahead of time trades run-time values and deoptimisation for
  portability and readable output, so every decision must be proved.
