## One function, many sizes

Here is the smallest useful generic function, in TypeScript:

```ts
function first<T>(xs: T[]): T {
  return xs[0];
}
```

TypeScript checks it once and then **erases** the types (chapter 28):
the JavaScript that runs is `function first(xs) { return xs[0]; }`,
and that is fine, because in a JavaScript engine every value already
fits one slot. Now picture compiling `first` to RISC-V. For an array of
32-bit integers, `xs[0]` is a 4-byte load into an integer register; for
64-bit floats, an 8-byte load into a float register; for a 24-byte
struct, three loads and a copy to memory. There is no single sequence
of instructions for "return element 0 of a T", and last chapter's
dictionaries only supply operations, not sizes. Real compilers take one
of two roads, and Go found a third.

## Specialisation: a copy per type

The first road is to treat the generic function as a template and stamp
out a fresh, ordinary copy for each type it is used with, with the type
filled in. Each copy knows its type exactly, so it uses the right
loads and registers, calls methods directly, and can inline them.

<Analogy title="a tailor">
A tailor cuts a new suit for each customer, from their own
measurements: every suit fits perfectly, and each one costs cloth and
time.
<span slot="breaks">A tailor can turn a customer away; a compiler must
make a copy for every type the program uses, even a hundred copies that
come out nearly the same.</span>
</Analogy>

<Analogy title="a stamp and ink pad">
One rubber stamp, pressed onto each envelope, leaves a separate print
on every one; the stamp is written once, the prints are many.
<span slot="breaks">Every print of a stamp is the same; each copy of a
generic function is changed by its type, so the copies differ, and the
compiler only makes those the program actually uses.</span>
</Analogy>

<Callout kind="definition">
**Generic specialisation** (also **monomorphisation**) compiles a
generic function or type by making a separate copy for each set of type
arguments the program uses, with the types substituted in. Calls go to
the matching copy; there is no run-time cost for being generic, but the
code grows with the number of types.
</Callout>

The Rust compiler's guide says it plainly: rustc "stamps out a
different copy of the code of a generic function for each concrete type
needed", which gives fast programs at the cost of compile time and
binary size<Cite id="rustc-dev-guide-monomorph" />. C++ templates work
the same way, and Swift does it as an optimisation whenever the
generic's definition is visible<Cite id="swift-optimization-tips" />.
Here is the evidence, from the trait `Area` of chapter 296 with two
types:

<Examples of="generic-specialization">

```rust
#[inline(never)]
pub fn gen<T: Area>(x: &T) -> f64 {
    x.area() + 1.0
}
// called as gen(&sq) and gen(&ci)
```

```text
$ nm -C l.o     # rustc 1.97 -O
T l::gen::<l::Ci>
T l::gen::<l::Sq>
```

```text
l::gen::<l::Sq>:     # x86-64
  movsd (%rdi), %xmm0   # load x.0
  mulsd %xmm0, %xmm0    # area, inlined
  addsd .LCPI1_0(%rip), %xmm0  # + 1.0
  retq
```

</Examples>

The first is the source: one generic `gen`, used with `Sq` and `Ci`
(`#[inline(never)]` stops rustc from dissolving it into its callers).
The second lists the object file's symbols, with names decoded by
`nm -C`: two separate functions, one per type. The third is the body of
the `Sq` copy (real output, trimmed): it loads the square's side, squares
it and adds one, with no call at all, because `Sq::area` was inlined.
Compare last chapter's `&dyn Area` version, which had to call
`*24(%rsi)` through the vtable.

## Erasure: one copy, one shape of value

The second road makes the *values* uniform instead of the code. If
every value the generic code handles is one pointer-sized word, then
`first` really is one sequence of instructions: load a word, return a
word. Objects already are pointers; the job is to make everything else
look like one.

<Analogy title="shipping containers">
A port's cranes handle any cargo because it all arrives in containers
of a few standard sizes; the cranes never need to know what is inside.
<span slot="breaks">A container's contents can be anything; a generic
Java method still needs a cast to use what it took out, and that cast
is checked at run time.</span>
</Analogy>

<Callout kind="definition">
**Generic erasure** compiles one copy of a generic function for all
types, by giving every value the generic code handles a **uniform
representation** (usually one word: a pointer, or a tagged small
integer). The type arguments are checked at compile time and then
discarded; where the code needs a specific type back, the compiler
inserts a conversion or a cast.
</Callout>

Java erases generics to `Object`, and javac has a whole pass for it,
which its source describes as translating "Generic Java to conventional
Java"<Cite id="javac-transtypes" />. OCaml chose a uniform value from
the start: its manual says a value is either an unboxed integer or a
pointer to a block in the heap<Cite id="ocaml-manual-value" /> (the value
itself says which it is, rather like V8's small integers in chapter
57).

<Examples of="generic-erasure">

```java
static <T> T first(List<T> xs) {
  return xs.get(0);
}
```

```text
static <T> T first(java.util.List<T>);
  2: invokeinterface // List.get:(I)
                     //   Ljava/lang/Object;
  7: areturn
```

```text
static int c(List<String> xs) // .length()
  2: invokeinterface // List.get -> Object
  7: checkcast   // class java/lang/String
 10: invokevirtual // String.length:()I
```

</Examples>

The first is the Java source. The second is its bytecode from
`javap -c` (real, trimmed): `List.get` returns `Object`, whatever `T`
is, and the method returns that reference unchanged with `areturn`; a
single copy serves every `T`. The third is a caller that knows
`T = String`: javac inserts `checkcast String` after `get`, a run-time
check that the `Object` really is a `String`, before calling `length`.
The types were real at compile time and are gone at run time.

## Boxing: making a number fit

An `int` is 32 bits of raw number, not a pointer, so it cannot travel
through erased code as it is. The cure is **boxing**: allocate a small
heap object holding the number and pass a pointer to it; unboxing reads
the number back out.

<Analogy title="a cloakroom ticket">
The cloakroom takes your coat, whatever its size, and hands you a
small numbered ticket; everyone's ticket fits the same pocket, and the
ticket brings the coat back.
<span slot="breaks">A cloakroom stores each coat once; a program may
box the same number again and again, making a new box (and new garbage)
each time, unless the language keeps a cache of common boxes.</span>
</Analogy>

<Callout kind="definition">
**Boxing** stores a value that does not fit the uniform representation
(a raw integer or float) in a heap object, and uses a pointer to that
object instead; **unboxing** reads the value back. It costs an
allocation, an extra memory load on every use, and the object's header.
</Callout>

<Examples of="boxing">

```java
static int sum(List<Integer> xs) {
  xs.add(7);
  return xs.get(0) + 1;
}
```

```text
 1: bipush 7
 3: invokestatic // Integer.valueOf:(I)
                 //   Ljava/lang/Integer;
 6: invokeinterface // List.add:(Object)Z
14: invokeinterface // List.get -> Object
19: checkcast  // class java/lang/Integer
22: invokevirtual // Integer.intValue:()I
```

```js
// V8, chapter 57:
let n = 7;    // a Smi: fits, no box
let t = 4.2;  // a HeapNumber: boxed
```

</Examples>

The first is innocent-looking Java. Its bytecode, the second, shows
boxing on the way in (`7` becomes an `Integer` object through
`Integer.valueOf`) and unboxing on the way out (`checkcast`, then
`intValue` to get the raw number back for `+ 1`). The third is the same
problem inside a JavaScript engine, from chapter 57: V8 tags small
integers to fit a pointer-sized slot, while `4.2` does not fit and is
boxed as a HeapNumber.

## The trade, and Go's middle road

<Formal title="How many copies?">

```text
copies of a generic f:
specialise:  |{ τ : f<τ> is used }|
erase:       1
by shape:    |{ shape(τ) : f<τ> is used }|
```

<span slot="read">The bars around a set mean "how many". With
specialisation, a generic f is compiled once for
every type τ the program uses it with. With erasure, once in all. Go's
way, once for every distinct shape among those types, where all pointer
types share one shape.</span>
</Formal>

Specialisation buys speed with code size and compile time; erasure
buys one small copy with boxes and casts. Go 1.18 chose between them:
types of the same **gcshape** (the same underlying type, or any pointer
type) share one copy, and each call passes a dictionary describing the
real type arguments<Cite id="go-generics-dictionaries" />. Compiling
`First[T any](xs []T) T` with Go 1.24 for `int`, `float64`, `*A` and
`*B` produced exactly three bodies, `First[go.shape.int]`,
`First[go.shape.float64]` and one `First[go.shape.*uint8]` shared by
both pointer types: dictionary passing from chapter 296, used for
generics.

## What you learned

- **Specialisation** makes one copy of a generic per type: exact,
  inlinable code, paid for in code size and compile time (Rust, C++).
- **Erasure** makes one copy for all types by giving values a uniform
  one-word representation, with casts where a type comes back (Java,
  OCaml, and TypeScript at the type level).
- **Boxing** puts a raw value in a heap object so it fits that word,
  at the price of allocation and pointer chasing; Go's shapes sit
  between the two roads.
