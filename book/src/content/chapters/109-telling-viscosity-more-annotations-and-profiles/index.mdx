## You know something it doesn't

The cost model guesses from what the code looks like, and sometimes you
know better: the test data has 10 particles but production has two
million; or you are chasing a bug and want `ps` left as you wrote it; or
the array is filled inside a function, so it cannot be counted. Viscosity gives you two ways to tell it
more: a comment that names the layout you want, and a measured run that
tells the cost model how big each collection really gets.

<Analogy title="a sticker on a removal box">
The removal crew decides how to load the van, but a box marked "fragile"
or "this way up" is handled the way the sticker says; however, no sticker
makes the crew carry a box down a staircase that has given way, and if
you never hire a crew, the sticker does no harm at all.
<span slot="breaks">A crew reads a sticker wherever it is on the box;
Viscosity reads an annotation only in one exact place (the line above, or
the end of the same line), and a sticker in the wrong place is ignored
without a word.</span>
</Analogy>

## Three words in a comment

There are three annotations, one per layout: `// @viscosity aos` keeps
the objects, `// @viscosity soa` asks for a struct of arrays, and
`// @viscosity aosoa(8)` asks for AoSoA in blocks of 8. The JavaScript
plugin finds them with one regular expression in
`frontend-js/src/index.ts`:

```js
/@viscosity\s+(aosoa|soa|aos)\b
  (?:\(([^)]*)\))?/
```

(One line in the source, split here.) It matches `@viscosity`, spaces,
one of the three names (`aosoa` first, so it is tried before its prefix
`aos`), a word boundary `\b` (so `soap` is not `soa`), and optionally any
text in brackets, which the planner judges later; it is case-sensitive.

Which declaration a comment reaches is decided from its line alone: a
comment **alone on its line** annotates the declarations on the *next*
line, and a **trailing** comment (code before it on the same line)
annotates only its own line. Step through a file with four comments that
look like annotations:

<AnnotationSteps client:visible />

<Callout kind="definition">
An **annotation** is a comment (or other marker) that gives the compiler
extra instructions without changing what the program means. A Viscosity
annotation names a layout for one collection; a program with annotations
is still ordinary JavaScript, and runs the same with or without
Viscosity.
</Callout>

<Examples of="annotation">

```js
// @viscosity soa
const pts = [{ x: 1, y: 2 },
  { x: 3, y: 4 }, { x: 5, y: 6 }];
for (let i = 0; i < pts.length; i++)
  pts[i].x += pts[i].y;
```

</Examples>

Line 1 is alone on its line, so it reaches `pts` on line 2; lines 2
and 3 make three records, which the cost model alone would refuse (far
below its 64-element threshold); lines 4 and 5 loop over them, reading
and writing two fields. `viscosity explain` says:

```text
pts (line 2) {x, y} → struct of arrays
  · annotated @viscosity soa at line 1
  · about 3 elements
```

The size is reported but no longer decides anything. Change `soa` to
`SoA` and explain says `kept as array of objects` with the threshold
reason: the pattern did not match, so the comment is only a comment, and
there is no warning (a blank line before the declaration fails in the
same silent way). So check that explain names your annotation.

## What an annotation cannot do

On the planner's ladder from *The cost model*, an annotation sits below
safety and above every cost rule:

<Figure caption="An annotation skips the cost rules beneath it, and can never reach past safety above it." takeaway="Annotations overrule guesses, not proofs.">
  <WhereItSits />
</Figure>

`soa` skips every cost rule (even the numeric one: a string field gets
a plain-array column), and `aos` stops a transform outright. `aosoa(N)`
has conditions, because a block is one `Float64Array` indexed with
shifts: N a power of two up to 65536 (8 when left out), and every field
provably numeric; otherwise the collection is kept with a reason. Above
all of this sits safety: annotate `ps` with `soa` and also write
`console.log(ps)`, and explain still says
`unsafe: the array is passed to a method call at line 7`. An annotation
tells the cost model what to think; it cannot make an observable change
invisible.

Try it: this program becomes SoA; add `// @viscosity aos` above
`const ps` and watch the explanation and the compiled code change.

<More title="More: opt-in mode, the pattern by hand, and other compilers' hints">

With `--mode opt-in`, only annotated collections are transformed; every
other one is kept with `opt-in mode: not annotated`. That suits adopting
Viscosity a little at a time, or a team that wants every layout change to
show in code review. (Python is already close to opt-in: its planner
keeps lists unless you annotate them, for the reason *The cost model*
gave.)

Run the annotation pattern on a few comments, including `SoA`, `soap`
and `aosoa(x)`:

<Run id="pattern" />

Compilers have long taken hints this way. Clang accepts
`#pragma clang loop vectorize(enable)` before a loop, overruling its
vectorizer's cost model for that one loop<Cite id="llvm-vectorizers" />;
Intel's ISPC puts the layout in the type, so `soa<8> Point pts[...]`
stores an array eight elements at a time, field by field, while code
still writes `pts[10].x`<Cite id="ispcdocs" />. Viscosity's hint names a
layout, like ISPC's, and sits on one declaration, like a pragma; but it
lives in a comment, so every JavaScript engine reads the program as
before.

</More>

## A question the code cannot answer

The threshold needs a number, and usually the analysis can count, since
elements are pushed in a loop with a constant bound. Here it cannot:

```js
const ps = [];
function spawn(x) {
  ps.push({ x, vx: 1 });
}
for (let i = 0; i < 20; i++) spawn(i);
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
```

The size estimate counts literal elements and pushes in top-level loops
with constant trip counts; a push inside a function depends on how often
it is called, so the estimate gives up (`size unknown statically`), and
Viscosity turns 20 elements into columns: safe, but pointless. A real
program's count comes from a file or a user, so Viscosity runs the
program and counts:

<PgoSteps client:visible />

<Callout kind="definition">
**Profile-guided optimisation (PGO)** is compiling with measurements
taken from real runs of the program, rather than only with what can be
worked out from the source. The measurements are the **profile**; the
usual loop is to instrument the program, run it on typical input, record,
and recompile with the record.
</Callout>

<Examples of="pgo">

```text
$ viscosity profile spawn.js -o p.json
$ viscosity explain spawn.js \
    --profile p.json
ps (line 1) {x, vx} → kept as array of
  objects
  · about 20 elements (measured): below
    the 64-element threshold, where the
    benefit is too small
```

</Examples>

The first command runs the program once and writes
`{ "ps": { "maxLength": 20 } }` to `p.json`; the second compiles with
it, and the measured 20 keeps `ps` as objects. With the loop bound
changed to 5000 and a fresh profile, the verdict flips to
`struct of arrays`.

## Counting without changing anything

To count, `viscosity profile` (in `cli/src/profile.ts`) builds a slightly
different program: it finds the collections exactly as the compiler
does, and wraps the expression that creates each one in a call to a
tracker, which a short prelude defines:

<Examples of="instrumentation">

```js
function __vsc_track(name, arr) {
  __vsc_seen.push([name, arr]);
  return arr;
}
const ps = __vsc_track("ps", []);
```

</Examples>

The tracker returns the *same* array, not a copy, so every `push`,
`===` and `console.log` behaves as before (a profile of a program that
behaves differently would profile the wrong program); the last line is
the real rewrite of `const ps = [];`. An exit hook in the prelude reads
each tracked array's length once, at the end, and writes the largest per
name. If the run throws there is no profile at all, because half a run's
sizes could mislead the planner.

<Callout kind="definition">
**Instrumentation** is code added to a program to record what it does
while it runs: counts, sizes, branches taken, time spent. Good
instrumentation changes nothing the program can observe, and costs as
little as possible.
</Callout>

## Where the number goes

The profile reaches exactly one place in the planner, in
`core/src/plan.ts`:

```ts
const measured =
  opts.profile?.[c.name]?.maxLength;
const size = measured ?? c.sizeEstimate;
if (size !== null && size < opts.minSize)
  // keep: "about N elements (measured)"
```

A measurement beats the estimate (`??` keeps a measured 0), and what
matters most is *where* that line sits:

<Figure caption="The planner's checks for an unannotated collection, in order. Any yes keeps the objects, with that reason." takeaway="A profile can only move the last rung, after every safety check has passed.">
  <ProfileGate />
</Figure>

So a wrong profile can only choose between two programs already proven to
behave identically (*Proving it safe*); the worst a stale one can do is
pick the slower of two right answers. That is the opposite of a JIT,
which profiles during the same run and speculates on what it saw, so
every assumption needs a guard and a way to deoptimise<Cite id="v8-maglev" />
(*Tiers, speculation and deoptimisation*).

## What you learned

- An **annotation** (`@viscosity aos`, `soa`, `aosoa(N)`) reaches the
  next line, or its own when trailing; it overrules guesses, never proofs.
- **Profile-guided optimisation** compiles with measurements from a real
  run, gathered by **instrumentation** that returns the same array.
- A measured size is read only after every safety check, so a bad
  profile costs speed, never correctness.
