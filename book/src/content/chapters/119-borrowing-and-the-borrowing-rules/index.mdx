## Lending, not giving

Ownership left an awkward rule: pass a `String` to a function and it
moves in, so this fails with E0382, "borrow of moved value: `name`":

```rust
fn count(s: String) -> usize {
    s.len()
}
let name = String::from("drip");
let n = count(name);
println!("{name} has {n} bytes");
```

rustc's note says what to do: "consider changing this parameter type
in function `count` to borrow instead". In TypeScript, passing an object
passes an arrow and the caller keeps its own; Rust can pass an arrow
too, and it keeps track of who holds one.

<Analogy title="lending a friend a book">
You lend a friend a book. They can read it, but it is still yours, and
when they are done it comes back; they do not get to give it away or
throw it out, because it was never theirs to throw.
<span slot="breaks">A friend might keep the book for months; a Rust
borrow is checked by the compiler to end before the owner is finished
with the value, so the book always comes back in time.</span>
</Analogy>

## Two kinds of loan

Write `s: &String` and call `count(&name)`, and `name` stays usable:
`&name` makes a **reference** without moving anything, and when `s` goes
away nothing is dropped, because `s` never owned
anything<Cite id="rust-book-borrowing" />. A plain `&` may only read; to
change a borrowed value you need a **mutable reference**, `&mut`, and
`*` to follow it to the value. Step through both, across a call:

<RefSteps client:visible />

<Examples of="borrow">

```rust
fn bump(n: &mut i32) {
    *n += 1;
}
let mut hits = 0;
bump(&mut hits);
bump(&mut hits);
println!("{hits}"); // 2
```

</Examples>

`*n += 1` writes through the reference into `main`'s variable (method
calls such as `s.len()` follow references for you, so you rarely write
`*` there). The owner says `let mut`, the caller `&mut hits` and the
parameter `&mut i32`, so unlike in TypeScript, you can see at the call
that a function may change your value. Each missing piece is a compile error:
`n: &i32` gives E0594, "cannot assign to `*n`, which is behind a `&`
reference", and `let hits = 0` gives E0596, "cannot borrow `hits` as
mutable".

<Figure takeaway="Owners can do anything; borrowers can read, and a mutable borrower can also change, but no borrower can move or drop the value." caption="The three ways to hold a value, and what each may do.">
  <RefKinds />
</Figure>

<Callout kind="definition">
A **reference** is an address you can follow to a value someone else
owns, and making one is **borrowing**. A **shared reference** `&T` can
only read; a **mutable reference** `&mut T`, made with `&mut x` from a
`let mut` variable, can also write, through `*r`. No reference can move
or drop the value it borrows, and Rust guarantees a reference always
points at a valid value<Cite id="rust-book-borrowing" />.
</Callout>

## A pointer into a growing list

Here is a bug every C programmer has written once:

```rust
let mut xs = vec![1, 2, 3];
let first = &xs[0];
xs.push(4);
println!("{first}");
```

`first` points into the `Vec`'s heap buffer, and if the buffer is full,
`push` moves the elements to a bigger one and frees the old one, so
`first` would dangle. C compiles this; rustc 1.97 refuses it:

```text
error[E0502]: cannot borrow `xs` as
  mutable because it is also borrowed
  as immutable
3 |     let first = &xs[0];
  |                  -- immutable borrow
  |                     occurs here
4 |     xs.push(4);
  |     ^^^^^^^^^^ mutable borrow
  |                occurs here
5 |     println!("{first}");
  |                ----- immutable borrow
  |                      later used here
```

The rule behind it is short: at any moment, a value may have *either*
any number of shared references, *or* exactly one mutable reference,
never both<Cite id="rust-book-borrowing" />. Step through it; the bars
underneath show how long each borrow lives:

<BorrowSteps client:visible />

The surprise is where the bars stop. A borrow does not last until the
closing brace; it ends at its **last use**, so a writer may start
straight after the readers are finished (how rustc works out "last use"
is the deep dive *Non-lexical lifetimes and region inference*).

<Figure takeaway="Reading next to readers is the only overlap allowed; everything else is a compile error." caption="What a program may do while an earlier borrow of s is still live (will be used again). Each cross is the error rustc 1.97 reports.">
  <ConflictGrid />
</Figure>

<Examples of="shared-vs-mutable">

```rust
let mut xs = vec![1, 2, 3];
let first = xs[0]; // a copy, not a borrow
xs.push(4);
println!("{first}"); // 1
let r = &xs;
println!("{}", r.len()); // r's last use
let w = &mut xs;         // so this is fine
w.push(5);
```

</Examples>

The first fix copies the number out (an `i32` is Copy), so nothing is
borrowed across the `push`; the second is the reorder that fixes most
borrow errors: `r` is finished before `w` starts.

<Callout kind="definition">
The **borrowing rule** (shared versus mutable): at any point in the
program, a value may have *either* any number of live shared references
`&T`, *or* exactly one live mutable reference `&mut T`, and never both.
A borrow is live from where it is made to the last place it is used.
</Callout>

## The borrow checker

The part of rustc that enforces the rule is the **borrow checker**. Its
errors share one three-point shape: where the first borrow started,
where the clashing access happened, and where the first borrow was still
needed; the fix is to stop those marks overlapping.

</Examples>

Run it: `a` reads `s`, `w` writes it, and `a` is used again after `w`
was made, so rustc reports E0502 with all three marks. The `^^^^` marks
the clash, but the real problem is often the third mark, the later use;
move the `println!` above `let w` and it compiles. Its relatives have the same
shape: two live writers is E0499, "cannot borrow `n` as mutable more
than once at a time"; moving a value while it is borrowed is E0505,
"cannot move out of `s` because it is borrowed"; and keeping a reference
past its value's block is E0597, "`s` does not live long enough", the
other half of the rules: a reference must always point at a live value.

<Callout kind="definition">
The **borrow checker** is a static analysis inside the Rust compiler. It
works out where every borrow starts and where it is last used, and
rejects any program in which a value is written, moved or dropped while
another borrow of it is live, or in which a reference outlives its
value. It runs at compile time, so the program it accepts has nothing
left to check while it runs<Cite id="rust-error-codes" />.
</Callout>

<Prompts ids={['e0502-fix', 'e0597-why']} />

<More title="More: what the rule buys the optimiser, and the VM">

<Run id="borrow-len" />

At run time a reference is an address, eight bytes, like a C pointer;
all the checking happened before. rustc's real checker works on its MIR,
with liveness deciding when a loan ends<Cite id="rustc-dev-guide-borrowck" />,
and the deep dive *A borrow checker in miniature* builds a small one.
The rule also pays the optimiser: the Rust Reference lists breaking it
as undefined behaviour (while a `&mut T` is live, no other pointer may
touch that memory, and memory behind a live `&T` must not
change)<Cite id="rustref-ub" />, so the compiler may assume it, which is
the very fact *Alias analysis and points-to* had to work hard (and often
fail) to prove for JavaScript. The same rule means two threads can never
write one value at once<Cite id="klabnik2026" />. The Rust Drip VM leans
on it in `vm.rs`: before it collects garbage it builds a `VmRoots` value
holding shared borrows of its stack, frames and globals, so the
collector can read every root while nothing can change them.

</More>

<Analogy extra title="a whiteboard in a meeting">
Any number of people can read a whiteboard at once. When someone picks
up the pen to rewrite it, everyone else has to stop reading until they
put the pen down, or they will copy half of the old version and half of
the new one into their notes.
<span slot="breaks">In a meeting, people agree to wait out of
politeness; in Rust, the compiler proves before the program runs that
nobody reads while the pen is up, so there is no waiting at run
time at all.</span>
</Analogy>

## What you learned

- `&T` lends for reading and `&mut T` for changing; neither may move or
  drop the value.
- **Many readers or one writer**, never both; a borrow lives until its
  **last use**, and the **borrow checker** proves it at compile time.
