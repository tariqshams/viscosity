## Where you started

This was the first program in the book:

```js
function double(n) {
  return n * 2;
}
```

That chapter promised that everything later would be built from one
idea: name a piece of work, then build bigger work out of named pieces.
Since then those pieces have become a JSON parser, scanners and
automata, recursive-descent, Pratt and LR parsers, a type checker with
inference, a tree-walking interpreter, a bytecode compiler and virtual
machine with a garbage collector, a RISC-V back end, an SSA
intermediate representation with a stack of analyses, and an optimiser
that changes how a program's data sits in memory, for two languages,
published for anyone to install.

<Analogy title="an apprentice's masterpiece">
In the old craft guilds an apprentice finished by making one piece (a
chair, a lock, a cabinet) that used every skill they had learned, and
it was judged as a whole; that is where the word "masterpiece" comes
from. The point was not the chair, but showing that the skills fit
together in one pair of hands.
<span slot="breaks">A masterpiece was judged finished. This capstone
comes with a list of what is *not* finished, and that list is part of
the work: knowing exactly which parts are solid is the skill being
shown.</span>
</Analogy>

<Analogy title="walking through a house you built">
When the last wall is up, you walk from room to room and see why the
foundations were dug where they were, why that wall carries the floor
above, why the pipes run where they run. Each early decision makes
sense only now.
<span slot="breaks">A house is finished when the roof is on. A compiler
keeps changing, and the parts here were built to be pulled apart and
rebuilt (Track B rebuilds two of them in another language), which no
builder plans for a house.</span>
</Analogy>

## One program, all the way down

Here is a particle simulation. Run it through the real compiler, then
read the report with the whole book in mind:

<Playground client:visible title="The whole pipeline" initial={`const ps = [];
for (let i = 0; i < 10000; i++) {
  ps.push({ x: i, y: 0,
    vx: 1, vy: 0.5, m: 1 });
}
for (let t = 0; t < 100; t++) {
  for (let i = 0; i < ps.length; i++) {
    ps[i].x += ps[i].vx;
    ps[i].y += ps[i].vy;
  }
}
let s = 0;
for (const p of ps) s += p.x;
console.log(s);`} />

The CLI says the same thing about it:

```text
ps (line 1) {x, y, vx, vy, m} → struct
  of arrays
  · loop at line 7 in <module>() touches
    4 of 5 fields (vy, y, vx, x)
  · loop at line 13 in <module>() touches
    1 of 5 fields (x)
  · typed Float64Array columns for all 5
    fields
  · about 10000 elements
  · 5 of 5 element accesses proven in
    bounds
```

To get there, acorn parsed the source into an ESTree (*Parsing real
JavaScript*); the front end lowered it to VIR in SSA form (*Lowering
JavaScript to VIR*, built on *SSA form* and *Building SSA*);
*Finding collections* found `ps`; *Record shapes* saw five fields in a
stable order; *Access patterns* found the two hot loops; *Proving it
safe* found no escape and proved every index in bounds; *The cost
model* liked 10,000 elements; and *Generating SoA storage*, *Rewriting
field accesses* and *Growing collections* replaced the objects with a
container of five `Float64Array`s that doubles its capacity as it
grows. Every line of the report was written by the planner as it
decided (*viscosity explain*), and behind all of it,
*Differential testing at scale* runs every corpus program both ways and
compares the output.

same five proofs, columns of `array('d')` instead of `Float64Array`,
and again the same output from both versions (`50995000.0`, a float,
because Python kept the floats as floats).

## What it measured

Two numbers summarise the building parts of Track A: how much the
bytecode VM beat the tree-walker, and how much Viscosity sped up whole
programs. Both come from committed result files, from runs on a shared
cloud machine:

<TrackAResults caption="The VM won on six programs, by at most 1.3×, and lost on four. Viscosity won big where a hot loop reads a few fields of a large array, and little on nbody and boids." />

Read the losses as carefully as the wins. The VM was slower than the
tree-walker on four programs (`fields`, `instantiation`, `strings` and
`trees`), and *Measuring and speeding up the VM* found why: both
engines are JavaScript that V8 compiles, so the tree-walker was never
the slow, naive interpreter the textbook argument assumes, and the VM
rebuilds in JavaScript (its own hash tables, its own collector on top
of V8's) what the tree-walker borrows from V8. Viscosity's smallest
wins came on `nbody`, where every body reads every field of the others,
and on `boids`; and in the benchmark matrix some of the same compiled
programs gained far less, or nothing, on Bun's engine than on Node's. The
cost model chose struct of arrays for all of them alike: it cannot yet
tell them apart.

## What is not done

An honest capstone lists the unfinished parts:

- **No WebAssembly back end** (*WebAssembly as a target*). Viscosity
  emits JavaScript and Python; WebAssembly runs the *compiler*, not its
  output.
- **Many ordinary programs are refused** (*The research frontier*):
  sorting, classes, destructuring, varying shapes, exported arrays.
  Some of those are chores; some are research.
- **The cost model is a heuristic**, with a 64-element threshold and
  measurements from one machine, and its verdicts already differ
  between engines.
- **Python is partial**: no profiling, no AoSoA, no end-to-end timing
  committed, and a refused file's reason never reaches the report.

Shipping, at least, is done: version 0.0.1 is on npm as `@viscosity/cli`
and `@viscosity/wasm`, and on crates.io as six crates
(*Shipping Viscosity*).

## What comes next

Track A has one more part. **Part X, Implementing language features**,
turns from building one compiler to how real languages implement what
their programmers take for granted: objects and dynamic dispatch,
traits, generics, closures, exceptions, pattern matching, generators
and `async`, Unicode strings, modules, macros, reference counting, a
borrow checker in miniature, threads and memory models, and modern
garbage collectors. Each of them is a lowering, the same kind of
translation you have now done three times.

Then **Track B** rebuilds the two biggest things you made, in a language
where memory layout is yours to control: Part XI teaches Rust itself
(ownership and borrowing as pictures, structs, enums and `match`,
traits, lifetimes, arenas, struct-of-arrays by hand); Part XII rebuilds
Drip's VM as `drip-rs`; Part XIII ports Viscosity, parsing with oxc and
making the same decisions as the TypeScript engine; and Part XIV builds
the command-line tool, the release and the final benchmark matrix.

"The same decisions" is checkable, because Track A left a contract
behind. For every corpus and benchmark program, in both bounds modes,
the TypeScript engine's compiled code and explain report are stored as
files in `engine/rust/tests/expected`, and the Rust port has to
reproduce them byte for byte.

<Callout kind="engine" label="Under the hood">
The Rust port already exists, and Track B is the story of how it was
built. Its workspace has six crates (`vir`, `core`, `frontend-js`,
`frontend-python`, a `cli` that builds the `viscosity` binary, and
`wasm`, which wraps the compiler for the browser), and its parity test
matches all 190 stored fixture pairs (95 programs, both bounds modes)
byte for byte, as does the WebAssembly build. In the benchmark matrix
(`matrix-2026-10-31.md`, section (b)), the Rust CLI compiled the
40-program corpus 10.9 times faster than the TypeScript CLI, start-up
included, and inside Node, as WebAssembly, each compile was 5.26 times
faster. The Playground's **TS / Rust** switch runs exactly that build.
</Callout>

## What you learned

- Track A taught **JavaScript and TypeScript**, how **machines** run
  code, the full theory of **front ends** around Drip, a **bytecode VM**,
  **real engines**, the whole **middle end**, a native **RISC-V** back
  end, and **Viscosity**, for two languages.
- One program passes through a dozen chapters on its way to SoA, and
  every step can be named.
- The **measurements** include losses: the VM on four programs, small
  wins where every field is read, gains that depend on the engine.
- What is unfinished is known: no WebAssembly back end, refused
  programs, a heuristic cost model, a partial Python.
- **Part X** implements language features; **Track B** rebuilds the VM
  and the compiler in Rust, checked byte for byte against Track A.
