## The CPU and its registers

The **CPU** (the processor) runs a program by repeating three steps for
each instruction: **fetch** it from memory, **decode** what it asks
for, and **execute** it<Cite id="slotin-amh-pipelining" />. It keeps the
values it is working on in **registers**, a few tiny storage slots
inside the CPU itself and the fastest storage there
is<Cite id="slotin-amh-hierarchy" /><Cite id="apple-wwdc25-cpu" />.

<CpuSteps client:visible />

<Examples of="cpu register">

```text
loop:
  load r1, [r2]    ; r1 = xs[i]
  add  r0, r0, r1  ; s = s + r1
  add  r2, r2, 8   ; address of next
```

</Examples>

The instructions are made up, but their shape is real: a good compiler
keeps `s` in `r0` and the address of `xs[i]` in `r2`, so each turn makes
one trip to memory (the `load`), and that trip is the slow part.

## A ladder of caches

A read that goes all the way to main memory is, on the chips Apple
describes, about fifty times slower than the fast
path<Cite id="apple-wwdc25-cpu" />, so CPUs keep copies of recently used
data close by, in several caches.

<Analogy title="an office with three stores">
You keep a desk drawer for what you are using now, a shelf for this
week's work, and a storeroom down the hall for the month; the warehouse
across town has everything. You look in the drawer first, then the
shelf, then the storeroom, and only then make the trip across town.
<span slot="breaks">The caches hold copies, so one value can be in all
three at once; and each cache fills itself, from what the program has
recently read, without being asked.</span>
</Analogy>

</Figure>

<Callout kind="definition">
A **CPU cache** is a small, fast memory between the CPU and main memory
that keeps copies of recently used data; the hardware checks it on
every read. Modern CPUs have a **cache hierarchy**: **L1**, smallest and
fastest, inside each core; then **L2** and **L3**, bigger and slower;
then main memory<Cite id="slotin-amh-hierarchy" />. **Latency** is how
long one access takes: roughly 2 nanoseconds for L1 and 100 for main
memory on those 2021 figures<Cite id="slotin-amh-hierarchy" />.
</Callout>

<CacheTrip client:visible />

When the data is already in a cache, the read is a **hit**; when it is
not, it is a **cache miss**, and the CPU looks further down, leaving
copies on the way back.

<Examples of="cpu-cache cache-hierarchy latency cache-miss">

```js
// 9 hits at 2 ns, 1 miss at 100 ns
(9 * 2 + 1 * 100) / 10;  // 11.8 ns
// 1,000,000 particles × 6 float64s
1000000 * 6 * 8;  // 48 MB: beyond L3
```

</Examples>

A 90% hit rate still costs nearly six times the all-hit 2 ns, because
one miss costs as much as fifty hits. That solves the puzzle: a
thousand particles (48 KB) fit in the caches, so nearly every read hits;
a million come to 48 MB, so the loop keeps missing.

<Formal title="The average cost of a read">

```text
t̄ = h · t_hit + (1 − h) · t_miss
```

<span slot="read">The average time of a read is the hit rate h times
the cost of a hit, plus the miss rate, one minus h, times the cost of a
miss.</span>
</Formal>

## Memory moves in lines

Caches do not move single values. They move a **cache line**, a fixed
block of neighbouring bytes: 64 bytes on most mainstream
processors<Cite id="slotin-amh-cache-lines" />, the size Linux assumes
for 64-bit x86<Cite id="linux-x86-kconfig-cpu" /> (some chips, such as
Apple's, also use 128<Cite id="apple-wwdc25-cpu" />; this book uses 64).
Asking for one byte fetches its whole line.

<Examples of="cache-line">

```js
Math.floor(200 / 64); // 3: line 3
200 % 64;             // 8: its byte 8
200 >> 6;             // 3, by bits
```

</Examples>

Because 64 is 2⁶, the hardware splits an address with a shift instead
of a division (*Bits and bytes*). One consequence surprises everyone
once: eight float64s fill a line, so touching every 8th element of a big
`Float64Array` still fetches every line, and is nowhere near eight
times faster<Cite id="slotin-amh-cache-lines" />.

## Stride and spatial locality

So count the lines a loop touches, not the values it reads; that
depends on the distance from one read to the next.

<StrideSteps client:visible />

<Callout kind="definition">
The **stride** of a loop is the distance in memory between consecutive
accesses. Small strides share lines; from 64 bytes up, every read pays
for a line of its own. **Spatial locality** is using data near data you
just used, so it arrives in lines already
fetched<Cite id="slotin-amh-locality" />; a loop along a typed array
uses every byte of every line.
</Callout>

<Examples of="stride spatial-locality">

```js
// grid of w columns, row by row
for (let r = 0; r < h; r++)  // stride 8
  for (let c = 0; c < w; c++)
    s += g[r * w + c];
for (let c = 0; c < w; c++)  // stride 8w
  for (let r = 0; r < h; r++)
    s += g[r * w + c];
```

</Examples>

Images and maps are grids stored row after row, so cell `(r, c)` is at
`r * w + c`. Both loops add the same numbers; the first has stride 8,
eight reads to a line, while the second jumps a whole row each step, so
on a big grid every read costs its own line.

## Reuse, and how fast bytes can flow

<FuseSteps client:visible />

<Callout kind="definition">
**Temporal locality** is using the *same* data again soon, while it is
still in a cache<Cite id="slotin-amh-locality" />; "soon" means before
more data than the cache holds has passed through. **Bandwidth** is how
many bytes per second can flow from memory to the CPU when many
accesses overlap: roughly ten gigabytes per second from main memory on
the 2021 figures<Cite id="slotin-amh-hierarchy" />. A loop streaming
through a big array cannot finish faster than its bytes can flow.
</Callout>

<Examples of="temporal-locality bandwidth">

```js
for (const v of xs) { a += v; b += v * v; }
// a million float64s at ~10 GB/s:
1000000 * 8 / 10e9;   // 0.0008 s
// mass from 6-field records:
1000000 * 48 / 10e9;  // 0.0048 s
```

</Examples>

The fused loop uses each value twice while its line is cached, where
two loops over a big array fetch it twice. The sums are floors: a
million masses in a `Float64Array` take at least 0.8 ms to stream, and
inside 48-byte records, which drag five unused fields along, six times
as long.

## What you learned

- The **CPU** works in **registers**; the **cache hierarchy** trades
  size for **latency**, and a few **cache misses** dominate.
- Memory moves in 64-byte **cache lines**: count lines, not reads.
- **Stride** sets **spatial locality**; **temporal locality** is reuse
  while cached; **bandwidth** is a streaming loop's floor.
