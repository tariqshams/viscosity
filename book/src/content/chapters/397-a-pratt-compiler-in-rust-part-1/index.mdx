## The table you already wrote

In *One pass from source to bytecode*, the TypeScript compiler parsed
expressions with a Pratt parser, and the parser was driven by a table:
for every kind of token, the table says what the token does when it
**starts** an expression (its prefix rule), and how tightly it binds
when it **continues** one (its precedence, used by its infix rule).
Here are two rows of the TypeScript version, from `vm/compiler.ts`:

```ts
case '(': return grouping;
case '-': case '!': return unary;
```

`prefixRule` answers with a closure, which reaches `previous`, the
chunk and the rest of the compiler's variables because it was written
inside `compile`. In drip-rs the compiler's state is a struct passed
around as `&mut self` (*A Pratt compiler in Rust, part 2* shows why), so
a function stored in a table cannot quietly reach it; this chapter is
about what the table becomes instead.

<Analogy title="a phrasebook with one page per word">
Picture a phrasebook with one page per word, each answering the same
three questions: can this word start a sentence, and how; can it carry
on a sentence somebody else started; and how hard does it pull its
neighbours towards itself. You never think about grammar; you look the
word up and do what the page says.
<span slot="breaks">Real phrasebooks are full of "it depends on
context"; the parser's table is looked up with the token's kind and
nothing else, and the instructions on a page may send you straight back
to the start of the book to parse a smaller expression.</span>
</Analogy>

## Three matches make one table

drip-rs answers each of a row's three questions with a `match` on the
token's kind. The first is how tightly a
token binds as an infix operator, from `src/compiler.rs` (rewrapped, and
with three arms left out):

```rust
fn infix_precedence(kind: TokenKind)
    -> u8 {
    use TokenKind as T;
    match kind {
        T::LeftParen | T::LeftBracket
            | T::Dot => PREC_CALL,
        T::Star | T::Slash | T::Percent
            => PREC_FACTOR,
        T::Plus | T::Minus => PREC_TERM,
        // ...comparison, equality, &&
        T::OrOr => PREC_OR,
        _ => PREC_NONE,
    }
}
```

The precedences are plain `u8` constants, weakest first, the numbers of
TypeScript's `Prec`: `PREC_NONE` is 0, `PREC_ASSIGNMENT` 1, up to
`PREC_CALL` at 9. The `_` arm gives every other token 0, lower than any
expression asks for, which is what makes a `;` or a `)` end one. (Rust could also make precedence an enum that
derives `Ord`, which orders the variants by position<Cite id="rust-std-ord" />;
drip-rs keeps numbers, because the parser adds one to them.)

The second question is what a token does at the start of an
expression, and here the answer is not a function but a *name* for one
(rewrapped):

```rust
#[derive(Clone, Copy)]
enum Prefix {
    Grouping, List, Unary, Number, String,
    Literal(OpCode), Variable, SelfKw,
    Super, New, Fn,
}
```

`prefix_rule(kind)` maps each token to `Some(Prefix::...)`, `-` and `!`
to `Unary`, `true` to `Literal(OpCode::True)`, and everything else to
`None`. The third question, what code to run, is answered by two
methods, `prefix(&mut self, prefix, can_assign)` and `infix(&mut self,
op, can_assign)`, each a `match` with one arm per kind; the `Unary` arm
parses its operand at `PREC_UNARY` and then emits `neg` or `not`.

## Why a name and not a function

Rust *can* store functions in a table: a type like
`fn(&mut Compiler, bool)` is a **function pointer**, the address of
some function with that signature, where which function is decided at
run time<Cite id="rustref-fn-pointer" />. A cell could then be
`Option<fn(&mut Compiler, bool)>`, and because a function pointer is
never null, `None` costs nothing<Cite id="rust-std-fn-primitive" />;
it is 8 bytes either way (the extra exercise builds a table like that).
drip-rs chose the enum instead, and measured on rustc 1.97 here,
`Option<Prefix>` is a single byte. A `Prefix` is `Copy`, it can carry
data (`Literal` holds the opcode to emit, so `true`, `false` and `none`
share one arm), and the `match` in `prefix` must have an arm for every
variant, or the crate does not compile
(*Enums and match*).

<Analogy extra title="an order ticket in a kitchen">
The waiter does not cook; she writes "soup" on a ticket and clips it to
the rail, and the cook, who has the whole kitchen to hand, reads the
ticket and makes the soup. The ticket is small, it can be passed around
or kept for later, and it needs no kitchen of its own.
<span slot="breaks">Tickets in a kitchen wait in a queue; a `Prefix`
is acted on at once, on the same call stack, by the only cook there is,
and the cook can write new tickets for itself halfway through a dish.</span>
</Analogy>

Keeping one for later really happens: a statement starting `fn (` is
an anonymous function, but `declaration` only knows that after it has
consumed `fn`, so it calls `expression_statement_from(Some(Prefix::Fn))`
to resume the expression with its prefix already chosen.

## The heart of the parser

Two methods run the table. `parse_precedence(precedence)` advances
past one token and asks `prefix_rule` about it; with no rule it reports
`expected an expression, found ...`, and otherwise it hands over to
`continue_expression` (rewrapped, its error report shortened to a
comment):

```rust
fn continue_expression(&mut self,
    precedence: u8, prefix: Prefix) {
    let can_assign =
        precedence <= PREC_ASSIGNMENT;
    self.prefix(prefix, can_assign);
    while precedence <= infix_precedence(
        self.current.kind)
    {
        self.advance();
        self.infix(self.previous,
            can_assign);
    }
    if can_assign
        && self.match_assign_op()
    {
        // "cannot assign to this
        // expression"
    }
}
```

It runs the prefix code (which emits the left operand), then absorbs infix operators while the next token binds at
least as tightly as `precedence`. `can_assign` is true only at the
loosest level, so in `a + b = 1` the `=` is still there after `a + b`,
and the last line reports it. Step through `-1 + 2 * 3`:

For a binary operator, the default arm of `infix` parses the right
operand one level tighter than the operator itself (rewrapped):

```rust
kind => {
    // Left-associative: the right side may
    // only hold tighter operators.
    self.parse_precedence(
        infix_precedence(kind) + 1);
    self.emit_op_at(op.line,
        binary_op(kind));
}
```

That `+ 1` is why `8 - 3 - 2` means `(8 - 3) - 2`: the second `-` has
the same precedence as the first, so it may not join the right operand
(which wants something tighter) and is left for the outer loop.

<Callout kind="definition">
A **parse-rule table** maps each token kind to a prefix parse function
(what it does at the start of an expression), an infix parse function
(what it does after a complete operand) and an infix precedence; any of
these may be absent. In drip-rs the table is three matches on
`TokenKind`: `prefix_rule` returns an `Option<Prefix>` naming the prefix
function, `infix_precedence` returns a `u8` (0 for none), and the
methods `prefix` and `infix` run the code.
</Callout>

<Formal title="The Pratt loop">

```text
parse(p) = prefix(t₁);
           while p ≤ prec(next):
             infix(next)
infix(op) = parse(prec(op) + 1); emit op
```

<span slot="read">To parse at minimum precedence p, run the prefix rule
of the first token; then, as long as the next token's precedence is at
least p, run its infix rule. A binary operator's infix rule parses its
right side at one more than its own precedence, then emits the
operator.</span>
</Formal>

<Examples of="parse-rule-table">

```text
print -1 + 2 * 3;     # 5
const '1'  neg
const '2'  const '3'  mul  add
```

```text
print 8 - 3 - 2;      # 3
const '8'  const '3'  sub
const '2'  sub
```

```text
print 1 + ;
line 1: expected an expression,
  found ';'
```

</Examples>

The first is the walk-through above, its bytecode (from
`--disassemble`, operands trimmed) in the order the stack needs it, so
the answer is `(-1) + 6`, which is 5. In the second, the first `sub` is
emitted before the `2` is loaded: `8 - 3` first, then `5 - 2`. The third
is the table saying no: `prefix_rule(Semicolon)` is `None`, so the
parser reports the token it found (wrapped here); the exit code is 65,
and the TypeScript VM prints the same line.

## What you learned

- drip-rs's **parse-rule table** is three matches on `TokenKind`:
  `prefix_rule` (an `Option<Prefix>`), `infix_precedence` (a `u8`, 0
  meaning "never continues") and the `prefix` and `infix` methods that
  run the code.
- A cell holds a one-byte **`Prefix`** that names a parse function, not
  a closure; the code runs with `&mut self`, and the name can be kept,
  as `Some(Prefix::Fn)` is.
- `continue_expression` runs the prefix rule, then infix rules while the
  next token binds at least as tightly as `precedence`.
- A binary operator parses its right side at its precedence **+ 1**,
  which makes `8 - 3 - 2` group from the left.
