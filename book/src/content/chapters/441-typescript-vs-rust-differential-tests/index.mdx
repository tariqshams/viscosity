## Two bugs nobody's tests saw

While this Part was being written, two differences between the engines
turned up by hand. The chapter *The cost model in Rust* noticed that,
given a profile, the Rust planner wrote "about 20 (measured) elements"
where the TypeScript one wrote "about 20 elements (measured)". And the
chapter *PGO in Rust* fed both CLIs a hand-edited profile:

```json
{ "ps": { "maxLength": "20" } }
```

The Rust CLI skipped the entry, since `"20"` is a string, and
transformed `ps`; the TypeScript CLI compared `"20" < 64` the
JavaScript way (which turns the string into a number), got `true`, and
kept `ps` as objects. Same program, different decisions, and yet at the
time `cargo test` passed everything. That is not a contradiction:
every test compares against *something*, on *some* inputs, and neither
bug was in any test's inputs. (Both are fixed now.)

<Analogy title="smoke alarms and gas detectors">
A smoke alarm does not smell gas, and a gas detector does not see
smoke. You do not fix that by buying a better smoke alarm; you put a
few different detectors in the house, and you know which one covers
which danger in which room.
<span slot="breaks">A detector either works or it does not; a test
layer also has *inputs*, so even the right kind of detector misses a
danger that never happens in the rooms it is placed in.</span>
</Analogy>

## Five oracles

An **oracle** is whatever a test trusts to give the right answer.
Here there are two: the original program (run it and see what it
prints) and the TypeScript engine (the reference, whose output is
saved as fixtures). Every layer compares an engine with one of them:

```text
layer         oracle         inputs
parity        TS fixtures    95 programs
node diff     the original   68 JS
python3 diff  the original   27 Python
wasm          TS fixtures    95 programs
fuzzer        TS + original  random JS
```

Read the table one row at a time, asking two questions of each layer:
what does it trust, and what does it feed in?

**Parity** (`parity.rs`, from the chapter *Round-trip tests across
engines*) compares code and explain text with the TypeScript output,
byte for byte, for every program in both bounds modes, plus 14
`--frames` fixtures and 4 `--profile` fixtures. Its oracle is the
reference, so it catches **divergence** (the two engines disagreeing),
and nothing else: if both engines are wrong in the same way, parity
passes, because it has nothing outside the two engines to compare with.

**The node differential** (`differential.rs`) runs each original and
compiled JavaScript program in an isolated context and compares
everything printed and thrown. Its oracle is the source program
itself, so it catches **miscompiles** (a compiled program that behaves
differently), even ones both engines share; however, it sees only its
68 programs, it compiles them only with bounds checks on, and a
difference in explain text never changes what a program prints, so
explain is invisible to it. **The python3 differential** does the same
for the 27 Python programs, comparing standard output and the last
line of standard error (the exception), so a difference earlier in
standard error, such as a warning, would pass.

**The wasm check** runs the same fixtures through the WebAssembly
build. I loaded the module this book serves in Node and ran all six
suites through `compileLanguage`: 190 of 190. It is the parity oracle on
a different target, so it catches whatever changes with the target;
its API takes no profile and returns no frames, so it cannot check
either.

**The fuzzer** (`scripts/fuzz.mjs`) generates random programs in the
part of JavaScript Viscosity cares about and checks each against both
oracles: the TypeScript output against the original under node, and
the Rust output against the TypeScript output (code, explain, frames,
and explain with a random profile). My run of its default, 300 programs
with seed 1, took 5.9 seconds: 134 of them were transformed, and 20 had
an early error inserted, which both engines must reject.

The first is what `cargo test` prints today: all 190 fixture pairs

divergence, a change of wording with the same decision, which only a
layer that compares text, and runs with a profile, can see. The third
is from the fuzzer's `failuresOf` (trimmed and rewrapped): when either
engine fails on a program, it reports a failure only if exactly one of
them failed. `!a.error` turns "has an error message" into `true` or
`false`, so two errors with different wording count as agreement,
because oxc and acorn word their messages differently.

<Callout kind="definition">
**Engine parity** is two engines making identical decisions, held in
place by tests against different **oracles**: the reference engine's
output (for divergence), the source program's own behaviour (for
miscompiles), and both at once on generated inputs. A test catches
only what differs from its oracle, on its inputs, under its options.
</Callout>

<Formal title="What one test checks">

```text
pass(x)  ⇔  obs(E(x))  ≈  obs(O(x))
blind:   E(x) = O(x) ≠ right(x)
```

<span slot="read">A test with engine E, oracle O, an observation obs
(the text, or what the program prints) and an equality ≈ (bytes, or
"both have an error") passes on input x when what it observes of E's
answer equals what it observes of the oracle's. It is blind whenever E
and O give the same wrong answer, and to every x it never tries.</span>
</Formal>

Put the two hand-found bugs through that rule. For parity, E is the
Rust engine, O the TypeScript fixtures, obs the explain text and ≈
"the same bytes"; the wording bug made the two texts differ, so parity
*could* have failed, but only on an input x compiled with a profile, and
no x in its set had one. For the node differential, obs is what the
program prints, and a change of wording prints nothing different, so
it could never fail, whatever its inputs. Two different reasons for
silence: the wrong inputs, and the wrong observation.

## Who could have seen it?

Step through seven cases (two of them hypothetical, and marked so).
For each, the lit layers are those whose oracle and inputs could
notice it:

<OracleSteps client:visible />

The first two are opposites. The line deleted from the Rust builder
was a Rust-only change on a corpus program, so parity and the node
differential both failed at once. The fuzzer's five finds (the chapter
*SoA code generation in Rust* covered the write-order ones) were all
in *both* engines, because the port mirrors the reference; parity
cannot see a bug both share, so every one was found by a different
oracle: the behaviour check, or the rule that the TypeScript engine
must not crash on a valid program ("internal error: overlapping
rewrites"). A port that copies its reference makes cross-engine checks
blind to shared bugs; only an oracle outside both engines finds those.

<Analogy title="checking a translation">
Two people translate the same letter; comparing their translations
catches a slip either one made alone, but if both misread the same
smudged word, they agree perfectly and are both wrong. To catch that,
you have to ask the person who wrote the letter.
<span slot="breaks">The letter writer can always be asked; a program's
behaviour is only observed on the inputs and options a test actually
runs, which is exactly where the two hand-found bugs hid.</span>
</Analogy>

## Inputs, options, and what counts as equal

Both hand-found bugs needed `--profile`, and at the time no fixture was
compiled with one, the fuzzer never passed one, and the wasm API still
cannot take one: an option no layer sets is untested in every layer,
however good the layers are. The second bug needed more, a profile no
profiling run would ever write, because `viscosity profile` always
writes numbers. The profile file is an input too, and every profile a
test could have used came from the profiler, so the string `"20"` was
outside every layer's reach: a layer finds only what its inputs can
produce, which is why the fix added hand-written odd profiles rather
than more profiled runs.

Then there is what counts as equal.
Parity says bytes; the differential says printed output and the error
message; the python3 test says standard output and the last line of
standard error; the fuzzer says bytes for output and presence for
errors. Each looser rule hides something, and each stricter one would
fail on differences nobody cares about.

<Prompts ids={['ep-option', 'ep-input', 'ep-equal']} />

The fixes followed from the map, and the engines have them now: four
profile fixtures and a random profile in every fuzzer batch;
`profile_cli.rs`, which feeds odd profiles to both CLIs; and
`early_errors.rs`, which checks that both engines reject 108 invalid
programs and accept 77 valid ones close to them. One gap is left: the
fuzzer generates JavaScript only. The Python plugin had one ad hoc run
of 800 random programs when it was ported (its commit message says
so), but there is no committed Python fuzzer.

<Callout kind="engine" label="Under the hood">
The fuzzer is cheap because two of its three engines run in the same
process: the TypeScript compiler and Node's `vm` module are both
JavaScript. The Rust engine is reached through its CLI, one
`viscosity build a.js b.js ... -o dir/` call per batch of 250 files, so
the cost is a few process starts per batch rather than per program.
The README puts the campaign at about 50,000 programs: the five bugs
turned up in roughly the first 8,000, and 42,000 more after the fixes
found nothing. The chapter *Fuzzing the Rust engine* goes further.
</Callout>

## What you learned

- Each layer has an **oracle**: the TS fixtures (parity, wasm), the
  original program (node and python3 differentials), or both (fuzzer).
- **Parity** catches divergence and is blind to shared bugs; the
  **differentials** catch miscompiles, but only on their inputs.
- A bug hides where **no layer** feeds its input or option, or where
  the **equality rule** is loose (errors by presence).
