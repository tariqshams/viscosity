## A frame you are not allowed to hold

The chapter *Frames: calling and returning in the VM* gave the
TypeScript VM one small object per call in progress, and its loop keeps
the running one in a local variable (trimmed):

```ts
let frame =
  this.frames[this.frames.length - 1];
// ... case Op.Call:
this.callValue(...);
reload(); // frame = the new top
```

`frame` refers to the object inside the array, so `frame.ip++` moves
the frame itself on, and `reload()` re-points it after a call. Here is
the same shape in a toy Rust VM, and what rustc 1.97 says (trimmed):

```rust
let frame = self.frames.last_mut().unwrap();
frame.ip += 1;
self.call(0); // pushes onto self.frames
frame.ip += 1;
```

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
6 | let frame = self.frames.last_mut()...
  |             ----------- first borrow
8 | self.call(0);
  | ^^^^ second mutable borrow occurs here
```

`call` pushes onto `self.frames`, the very `Vec` that `frame` points
into, and a push may move every element to a bigger
buffer<Cite id="rust-std-vec" />; the borrow checker is right to refuse
(the rule is the one from the chapter *Borrowing*: one `&mut` at a
time<Cite id="klabnik2026" />). The chapter *The VM loop in Rust* showed
drip-rs's way out: the running frame's `ip`, chunk and stack base live
in fields of the `Vm` itself, its **registers**. This chapter is about
the frames behind them.

<Analogy title="a cupboard of paused board games">

<span slot="breaks">A paused board game cannot change while it waits;

## The frames are a Vec

From `vm.rs` (comments trimmed):

```rust
struct CallFrame {
    closure: Gc<ObjClosure>,
    chunk: Rc<Chunk>,
    ip: usize,
    slots: usize,
}
```

Compared with TypeScript's `{ closure, ip, slots }` there are three
differences. The closure is a handle (the chapter *Heap objects in an
arena*), not a reference. The frame carries its function's chunk as an
**`Rc` clone**, so when `fib` has called itself 20 deep, 20 frames share
one chunk and each clone only adds one to a count<Cite id="rust-std-rc" />.
And `ip` in a frame means something only while the frame is paused
under a call. `Vm::new` reserves room with
`Vec::with_capacity(FRAMES_MAX)`, and `self.stack.len()` plays the part
of TypeScript's `sp`.

## Call: save, push, load

From `call`, after its two checks (the argument count, then
`self.frames.len() == FRAMES_MAX`, which is 256 and gives the runtime
error `stack overflow`), rewrapped:

```rust
// Save the caller's ip, then load
// the callee into the registers.
if let Some(caller) =
    self.frames.last_mut()
{
    caller.ip = self.ip;
}
let chunk =
    Rc::clone(&self.heap[function].chunk);
let slots =
    self.stack.len() - arg_count - 1;
self.frames.push(CallFrame {
    closure, chunk: Rc::clone(&chunk),
    ip: 0, slots });
self.ip = 0;
self.chunk = chunk;
self.slots = slots;
Ok(())
```

The first block writes the register `ip` into the caller's frame, which
is the moment that field becomes correct; `caller` borrows
`self.frames` while `self.ip` is read, which is fine because they are
different fields. (The script's own call has no caller, so `last_mut()`
gives `None` and nothing is saved.) `chunk` is a new `Rc` handle to the
callee's bytecode. `slots` points at the callee itself, one below its
arguments, because slot 0 of every frame holds the function being
called (or `self`, in a method). Then the frame is pushed and the three
registers are loaded. Because `call` does the loading, the `Call` arm of
the loop is one line, `self.call_value(self.peek(arg_count), arg_count)?;`,
with no `reload`.

<FrameSteps client:visible />

<Callout kind="definition">
drip-rs's **frame stack** is `frames: Vec<CallFrame>`, one entry per call
in progress, innermost last. A frame holds its closure's handle, an `Rc`
clone of its chunk, a saved `ip`, and `slots`, the stack index of its
slot 0. The running frame is `frames.last()`, but its live `ip`, chunk
and base are in the VM's registers: `call` saves the caller's `ip` and
loads the callee, and `pop_frame` loads the caller back.
</Callout>

<Formal title="A call and a return, on the stack">

```text
call:   slots = len − argc − 1
        frames ← frames + [frame]
return: stack ← stack[0 .. slots] + [r]
        frames ← frames − last
```

<span slot="read">A call's base is the length of the stack minus its
arguments minus one, the slot of the callee itself, and a new frame goes
on the end of the list. A return keeps the stack up to (not including)
that base, puts the result r after it, and takes the last frame off the
list.</span>
</Formal>

## Return: pop, load, truncate

```rust
fn pop_frame(&mut self)
    -> Option<CallFrame> {
    let frame = self.frames.pop()
        .expect("a frame is running");
    let caller = self.frames.last()?;
    self.ip = caller.ip;
    self.chunk = Rc::clone(&caller.chunk);
    self.slots = caller.slots;
    Some(frame)
}
```

`pop` takes the finished frame out of the `Vec` by value. `?` on the
`Option` (the chapter *Option and Result*) returns `None` at once when
there is no caller left, which is how the loop learns that the script
has finished, where TypeScript checks `frames.length === 0`. Otherwise
the caller's three saved values go back into the registers. The
`Return` arm then does `self.stack.truncate(frame.slots)`, dropping the
callee and all its arguments and locals in one step, and pushes the
result; when `frame` goes out of scope, its `Rc` clone goes with it.

<Examples of="frame-stack">

```text
fn hi() { print "hi"; }   hi();
stack: [script, hi]    slots = 2 − 0 − 1 = 1
```

```text
runtime error: area() takes 2 arguments
  but got 1
  at line 4 in script
```

```text
runtime error: cannot negate a string
  at line 2 in fn f
  at line 5 in fn g
  at line 7 in script
```

</Examples>

The first is the smallest call: no arguments, so the new frame's slot 0
is `hi` itself, at stack index 1. The second (one line, wrapped here) is
`call`'s first check, from `print area(3);` with `fn area(w, h)`: the
error comes before any frame is pushed, so the trace has only the
script. The third is a realistic trace, from `g` calling `f("hi")` and
`f` doing `return -x;`. `runtime_error` walks the frames innermost
first, and for each it needs the line of the instruction that was
running, `chunk.lines[ip - 1]`. For `g` and the script, the frame's own
`ip` is right, saved when they made their calls; for `f`, the top frame,
that field still says 0, so the code reads the register instead:

```rust
let ip = if depth == top { self.ip }
    else { frame.ip };
```

A native, such as `len`, is called without a frame at all. A natural
design would store a function pointer, a value of type
`fn(&[Value]) -> Value`<Cite id="rustref-fn-pointer" />; drip-rs keeps
an enum, `Native::{Clock, Len, Push, Pop, Str}`, and matches on it in
`call_native`, which can then use the whole VM (to describe a value in
an error, or to intern the string `str` makes). The arguments stay on
the stack while it runs, so a collection it causes cannot free them,
and afterwards one `truncate` drops them with the callee.

## What you learned

- drip-rs keeps **a `Vec` of call frames**; each `CallFrame` has a
  closure handle, an `Rc<Chunk>` clone, a saved `ip` and `slots`.
- The loop cannot hold `&mut CallFrame` across a call, so the running
  frame's state lives in **registers**: `call` saves and loads,
  `pop_frame` loads the caller back.
- The running frame's own `ip` field is **out of date**; the stack
  trace reads the register for the top frame.
- `pop_frame` returns **`Option<CallFrame>`**: `None` means the script
  has finished.
