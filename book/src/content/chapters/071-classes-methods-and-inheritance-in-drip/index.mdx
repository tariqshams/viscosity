## Data that knows what to do

Real programs keep wanting data and behaviour together: a particle with
its position *and* a way to move. Here is a Drip class, shaped like
those in *Classes: a blueprint for objects*:

```text
class Cake {
  init(flavour) {
    self.flavour = flavour;
  }
  taste() {
    print "Mmm, " + self.flavour;
  }
}
let c = new Cake("lemon");
c.taste();  # Mmm, lemon
print c;    # Cake { flavour: "lemon" }
```

The set-up method is `init` (a keyword) and the object a method works
on is `self`; underneath there are only two maps and two tricks we
already have.

<Analogy title="a cookie cutter">
One cutter, many cookies: every cookie gets the cutter's shape, and each
can be iced differently. The cutter is the class; each cookie is an
instance, and its icing is its own data.
<span slot="breaks">A cookie's shape is fixed once it is cut; a Drip
instance can gain a new field at any moment, and its methods are not
copied into it at all, but looked up on the class every time they are
used.</span>
</Analogy>

## Classes, instances and fields

The `class` statement makes each method an ordinary `DripFunction`
capturing the class's environment, puts them in a `Map`, and defines a
`DripClass` (name, superclass, map). `new Cake("lemon")` checks the name
holds a class, makes a `DripInstance` with no fields, and calls `init`
on it through `callFunction` (so its arity is checked); the value of
`new` is the instance, whatever `init` does.

<NewSteps client:visible />

An instance is its class plus a second `Map`, of fields. Fields are
never declared: assigning to one creates it, which is how `init` builds
an instance up. Reading checks the fields first, then the class:

```ts
get(name: Token): Value {
  const v = this.fields.get(name.lexeme);
  if (v !== undefined) return v;
  const m = this.klass.findMethod(
    name.lexeme);
  if (m) return m.bind(this);
  throw new RuntimeError(name,
    `${this.klass.name} has no ` +
    `property '${name.lexeme}'`);
}
```

So a field can hide a method of the same name, and only instances have
properties.

<Figure caption="Each instance has its own map of fields and a pointer to its class. The class holds the methods, once, for every instance. A property read checks the fields first, then the class." takeaway="Fields live on the instance; methods live on the class.">
  <InstanceFigure />
</Figure>

<Callout kind="definition">
A **Drip class** is a runtime value holding a name, an optional
superclass and a map from method names to functions. `new C(args)`
makes an instance, which holds its class and a map of fields, calls
`init` on it if the class has one, and gives back the instance. A
**field** is a piece of data stored on one instance under a name:
`obj.name = value` creates or replaces it, and reading `obj.name`
returns the field if there is one, otherwise the class's method of that
name, otherwise it is a runtime error.
</Callout>

<Examples of="drip-class field">

```text
class Box {}
let b = new Box();
print b;      # Box {}
b.size = 3;
b.size += 1;
print b;      # Box { size: 4 }
```

</Examples>

`Box` has no methods and no `init`, so `new Box()` takes no arguments
and gives an instance with no fields; assigning `b.size` creates a
field, and `+=` reads it and writes it back.

<More title="new in code, a runnable example, and how engines do better">


A class with no `init` given arguments stops with `Box has no init, so

## Methods that keep their self

In JavaScript, a method read off an object and called later without the
dot loses `this`, which is decided by the dot in each
call<Cite id="mdn-this" /> (*Methods and this*). Drip does not lose
`self`, and not by a special rule: `self` is an ordinary variable. The resolver wraps a class's
methods in one extra scope that declares `self`, so inside a method
`self` is one scope out (and `self` in a plain function is a compile
error). The resolver's rule, one scope per runtime environment, then
demands an environment one step out holding `self`, and `bind` makes it
every time a method is read off an instance:

```ts
bind(instance: DripInstance) {
  const env = new Environment(
    this.closure);
  env.define('self', instance);
  return new DripFunction(this.decl,
    env, this.isInitializer);
}
```

When the new function value is called, the call's environment hangs off
the small one as always, so `self` is exactly one hop up.

<Figure caption="While resolving taste, self is one scope out, in the class scope. When c.taste() runs, the interpreter must have a matching environment one step out, holding self." takeaway="self is found by distance, like any variable.">
  <SelfScopes />
</Figure>

<BindSteps client:visible />

<Callout kind="definition">
A **bound method** is a method together with the instance it was read
from. Drip makes one in `bind`: a new environment whose only variable is
`self`, holding the instance, wrapped around the method's captured
environment, and a new function value that captures it. The binding
happens when the method is *read* (`c.taste`), not when it is called,
so `self` travels with the value wherever it goes.
</Callout>

<Examples of="bound-method">

```text
let f = c.taste;  # bound to c
f();              # Mmm, lemon
print c.taste == c.taste; # false
```

</Examples>

With the `Cake` from the start, `f` keeps `c` with no dot in sight.
Every read binds again, so two reads are two different values (and
every method read allocates two objects). A bound `init` always returns
the `self` from its bind environment, which is why `return value;` in
`init` is a compile error.

<Analogy extra title="a TV remote paired with one TV">
A remote paired with the living-room TV works whoever presses it; you
can hand it to a guest, and the living-room TV still answers.
<span slot="breaks">Drip pairs again on every read, so `c.taste` read
twice gives two different function values.</span>
</Analogy>

## Inheritance and super

`class Dog extends Animal` gives `Dog` a superclass, which must be a
class (checked when the statement runs; `class A extends A {}` is a
compile error). Finding a method becomes a walk up the chain:

```ts
findMethod(name: string) {
  return this.methods.get(name)
    ?? this.superclass?.findMethod(name);
}
```

That is the whole of inheritance in the interpreter: a subclass
overrides a method by reusing its name, and `init` is inherited like
any other.

<Figure caption="A method lookup starts at the instance's class and walks up the superclass links until a class has the method. If no class has it, the read is an error." takeaway="Inheritance is a walk up the superclass chain.">
  <ChainFigure />
</Figure>

<Callout kind="definition">
**Inheritance** lets a class reuse another class's methods. In `class B
extends A`, `A` is the **superclass** of `B`; looking a method up checks
the class's own methods first and then walks the superclass chain, so a
subclass **overrides** a method by defining one with the same name.
</Callout>

<Examples of="inheritance">

```text
class A { hi() { print "A"; } }
class B extends A {}
new B().hi(); # A
```

</Examples>

`B` has no methods of its own, so `findMethod('hi')` misses in `B`,
asks `A`, and finds it one class up.

`super.m()` means "the `m` above the class this method was *written*
in, called on the same `self`". The tempting shortcut, the superclass of
`self`'s class, breaks with three levels:

```text
class A { m() { print "A.m"; } }
class B extends A {
  m() { print "B.m"; super.m(); }
}
class C extends B {}
new C().m(); # B.m, then A.m
```

`B`'s `m` runs with `self` a `C`, whose superclass is `B`, so the
shortcut would call `B`'s `m` until `stack overflow`. The right answer,
`A`, depends on where the method was written, which is lexical scope:
so a subclass's methods capture one more environment, holding `super`,
with a matching resolver scope around the `self` scope. `super` is then
found by scope depth, with `self` one environment closer.

<SuperSteps client:visible />

<Callout kind="definition">
**`super.name`** finds the method `name` starting from the superclass of
the class the current method was *written in*, and binds it to the
current `self`. Drip stores that superclass in an environment made when
the subclass is declared, so `super` is found by scope depth, like any
variable. Using `super` outside a method, or in a class that does not
extend another, is a compile error.
</Callout>

<Examples of="super">

```text
class S { init(a) { self.a = a; } }
class T extends S {
  init(a, b) {
    super.init(a);
    self.b = b;
  }
}
print new T(1, 2); # T { a: 1, b: 2 }
```

</Examples>

`T`'s `init` runs `S`'s on the same instance, then adds its own
field.

<More title="The super environment in code, and a runnable example">

```ts
let env = this.env;
if (superclass) {
  env = new Environment(env);
  env.define('super', superclass);
}
// ... each method captures env ...
```

`superMethod` reads `super` at the recorded distance `d` and `self` at
`d - 1`, calls `findMethod` on the superclass, and binds the result (or
stops with `S has no method 'm'`). JavaScript walks a *prototype chain*
the same way (*Overriding and the prototype chain*); the bytecode VM
instead copies the superclass's methods into the subclass's table once,
when it is declared, so a lookup never walks a chain.

## What you learned

- A **class** is a name, a superclass and a map of methods; an instance
  is its class plus a map of **fields**, read before the methods.
- Reading a method **binds** it, so a **bound method** keeps its `self`.
- **Inheritance** is a walk up the superclass chain; **`super`** is
  found by scope, fixed where the method was written.

That is the whole of Drip as a tree-walker. Next: *Why bytecode*, and
why walking a tree is slow.
