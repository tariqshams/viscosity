## A working VM, and a blank file

In Part IV you built a bytecode VM for Drip in TypeScript; it lives in
`companion/ts/src/vm`, about 2,000 lines across nine files, and it runs
every program in the book's test corpus. This part rebuilds it in Rust.
The result already exists (it is called **drip-rs**, and it lives in
`companion/rust`), so rather than invent it from nothing, these chapters
walk through it file by file, next to the TypeScript you already know.

The goal is easiest to state as a test: for every corpus program, drip-rs
must print the same output, the same error messages, the same stack
traces and the same exit code as the TypeScript VM. Not "close"; the same
bytes. Most of the port is translation, however one part is not, and it
shapes everything else, so this chapter is about that part.

<Analogy title="moving house to another country">
Most of your things go straight into boxes and come out the same at the
other end; a few need a plug adapter; and one thing, the wiring you ran
through every wall yourself, has to be redone to the new country's rules.
For drip-rs, the boxes are the scanner and the compiler, and the wiring
is the web of references between heap objects.
<span slot="breaks">A house move is done once and then forgotten; here
the old house keeps standing next door, and every program must behave
identically in both, for as long as the book exists.</span>
</Analogy>

<Analogy title="a band covering a song note for note">
A tribute band may play different guitars through different amplifiers,
but the audience should not be able to tell the recording from the cover.
drip-rs is free to arrange its insides however Rust likes, as long as
what comes out of the speakers is identical.
<span slot="breaks">A cover that is a little off is still a fine night
out; a VM that prints `1e21` where the other prints `1e+21` simply fails
its tests.</span>
</Analogy>

The port keeps the TypeScript VM's shape: one Rust module per TypeScript
file, in pipeline order (source text in at the top, output out of the

`lib.rs` declares the modules, under `#![forbid(unsafe_code)]`, which

no dependencies, so drip-rs is the standard library and nothing else.

<Callout kind="definition">
**drip-rs** is the Rust implementation of Drip's bytecode VM, in
`book/companion/rust`. It is a library crate, `drip`, plus a binary,
`drip-rs`. It ports the TypeScript VM module by module, uses only `std`

must match byte for byte.

## Objects that point at each other

In TypeScript, a closure object holds its function, an instance holds its
class, and a class holds a table of closures; any object can point at any
other, cycles are normal, and JavaScript's own collector sorts it out.
Rust's first offer for shared, changeable objects is the one from the
chapter *Box, Rc and RefCell*, `Rc<RefCell<T>>`, and for a VM it is wrong
in three ways: reference counting would decide when objects die, leaving
the mark-and-sweep collector of *Reclaiming memory: mark and sweep* with
nothing to do; a cycle of `Rc`s never reaches a count of zero, so it
leaks<Cite id="klabnik2026" />; and every `borrow_mut()` is a check made
at run time, on the hottest paths of the interpreter.

So drip-rs does what the chapter *Arenas and typed indices* showed. Each
kind of object lives in its own `Arena<T>`, a `Vec` of slots owned by the
`Heap` (nine arenas, one per kind), and a reference to an object is a
`Gc<T>`. From `object.rs` (comment rewrapped):

```rust
pub struct Gc<T> {
    index: u32,
    // `fn() -> T` makes the handle Copy,
    // Send and Sync whatever `T` is.
    marker: PhantomData<fn() -> T>,
}
```

A `Gc<T>` is a slot number and nothing more (the `PhantomData` takes no
space; it only records `T`, so a closure handle cannot look up a class),
and `heap[handle]` reads the object.

Pass the wrong kind of handle, `h.inst(c)` with a `ClassRef`, and rustc

<Callout kind="definition">
In drip-rs every heap object lives in an **arena** owned by the `Heap`. A
**`Gc<T>`** is a typed `u32` index into the arena for `T`: `Copy`, 4
bytes, and unusable for any other kind of object. Only the heap owns
objects, and the garbage collector, not reference counting, decides when
they die.
</Callout>

## Roots are passed in

The TypeScript heap starts a collection by itself, inside `allocate`, and
to find the roots it calls back into the VM, which registered itself with
`this.heap.vm = this`. In Rust the VM owns the heap, so a heap method that
also borrowed the whole VM would need `&mut` to part of something already
lent out, which the chapter *Borrowing* forbids:

```text
error[E0502]: cannot borrow `self.heap`
  as mutable because it is also
  borrowed as immutable
```

So drip-rs turns it round: allocating never collects. The VM asks
`heap.should_collect()`, and if the answer is yes, it borrows the fields
that hold roots one by one and hands them over (from `vm.rs`):

```rust
pub fn collect_garbage(&mut self) {
    let roots = VmRoots {
        stack: &self.stack,
        frames: &self.frames,
        globals: &self.globals,
        open_upvalues: &self.open_upvalues,
        init_string: self.init_string,
    };
    self.heap.collect(&[&roots]);
}
```

Borrowing `self.stack` and `self.heap` at once is fine, because they are
different fields and the borrow checker tracks each separately.
`collect` takes `&[&dyn Trace]`, a list of things that can mark what they
reach, so the compiler can pass in its half-built functions the same way.

## The one Rc

There is exactly one `Rc` in drip-rs, in the field
`pub chunk: Rc<Chunk>` of `ObjFunction`. When the compiler finishes a
function it freezes the chunk with `Rc::new`, and nothing changes it
again. The VM keeps the running function's chunk in a field of its own
(the README calls such fields **registers**) and reads bytes with
`self.chunk.code[self.ip]`. A plain `&Chunk` would point into the heap
and keep the heap borrowed while the VM pushes values and allocates; an
`Rc` clone is the VM's own pointer to the same chunk, so the heap stays
free, and because the chunk never changes it needs no `RefCell`. The
README reports that these registers made `fib` about 1.4 times faster;
the chapter *The VM loop in Rust* looks at why.

## The same bytes

How do you know the port is right? The answer from *Differential testing
at scale* is to run one corpus through both and compare. drip-rs's
`tests/corpus.rs` runs the 334 corpus programs that are not benchmarks
and checks each against the expectations written in its comments, with a
Rust port of `check()` from the TypeScript runner. Two real lines:

```drip
print (1 + 2) * (3 + 4); # expect: 21
let count = 3;
print "count: " + count;
```

The first is from `operators/grouping.drip`; the third line of the
second program, from `strings/add_a_number.drip`, carries the comment
`# expect runtime error: cannot add a string and a number`, so the
checker wants that message, a trace pointing at that line, and exit
code 70. `cargo test` also runs 165 of the programs with a collection
before every allocation (`tests/stress_gc.rs`), which makes a forgotten
root fail at once, and `scripts/compare_with_ts.mjs` runs both VMs on all
344 programs, benchmarks included, and on thousands of randomly broken
ones, comparing stdout, stderr and exit codes; when I ran it, 343 were
compared (one reads the clock, so its output differs on every run) and
none differed.

<Formal title="What “the same bytes” means">

```text
∀ p ∈ Corpus:
  run_rs(p) = run_ts(p)
run(p) = (stdout, stderr, exit code)
```

<span slot="read">For every program p in the corpus, running p on drip-rs
gives exactly the same result as running it on the TypeScript VM, where a
result is three things together: everything printed to standard output,
everything printed to standard error, and the exit code.</span>
</Formal>

<Callout kind="engine" label="Under the hood">
"The same bytes" reaches into odd corners: numbers must print as the
TypeScript VM prints them (`1e+21`, `-0`, `nan`), so `value.rs`
reimplements that layout; and where the TypeScript heap poisons freed
objects, drip-rs never reuses a freed arena slot in its debug and stress
modes, so a stale handle panics rather than reading some other object.
</Callout>

## What you learned

- **drip-rs** is a module-by-module port of the TypeScript VM: `std`
  only, `#![forbid(unsafe_code)]`, tested against the same corpus.
- Heap objects live in **arenas** owned by the heap; references are
  **`Gc<T>`** handles, typed `u32` indices, so cycles cost nothing and
  the collector decides when objects die.
- The heap cannot reach the VM that owns it, so **roots are passed in**:
  the VM borrows its root fields and calls `collect(&[&roots])`.
- Compiled chunks never change, so they are frozen in **`Rc<Chunk>`**,
  the crate's only `Rc`.
- "Correct" means the same stdout, stderr and exit code as the
  TypeScript VM, on every corpus program.
