## Same data, different answer

*Finding collections* found the variables that hold an array and only
ever receive object literals. Here is one from the differential
corpus, `shape_mismatch.js`, trimmed:

```js
const ps = [];
for (let i = 0; i < 100; i++) {
  if (i % 2) ps.push({ x: i, y: 1 });
  else ps.push({ y: 1, x: i });
}
```

Every element has an `x` and a `y`, all numbers; Viscosity refuses
anyway:

```text
ps (line 2) {y, x} → kept as array of
  objects
  · unsafe: line 4: records with
    different fields or field order
    ({x, y} vs {y, x})
```

(Real `viscosity explain` output, wrapped to fit, as everywhere in
this chapter.) To see why, we need to be precise about what a shape
is, and what it takes for one to stay put.

## A shape is two lists

<Analogy title="a printed form">
Every copy of a printed form has the same boxes in the same places,
which is what lets a clerk read a whole stack of them quickly; and each
box says what may go in it, "digits only" or "anything".
<span slot="breaks">A clerk can still read a form on which someone
wrote the boxes in a different order; Viscosity cannot, because it
copies each record's values into columns by position, without reading
the labels again.</span>
</Analogy>

Viscosity's `Collection` record keeps both halves: `fields`, the names
in order, and `numericFields`, the fields that get `Float64Array`
columns. Here is the shape of `es` from `mixed_columns.js`:

<Figure takeaway="A shape is the fields in order, plus a column type for each." caption="Three of the 300 records of es, and the four columns they become. hp and x only ever hold numbers, so they get Float64Array columns; id and tag hold strings, objects and null, so they get plain arrays.">
  <ShapeColumns />
</Figure>

<Callout kind="definition">
A **record shape** is what every element of a collection has in
common: its **fields, in order**, and for each field a **column
type**. A field that provably only ever holds numbers gets a
`Float64Array` column; any other field gets a plain array column. A
collection has a shape only if all its object literals agree on the
fields.
</Callout>

<Examples of="record-shape">

```text
ps.push({ x: i, y: 0 }); ps[i].y += ps[i].x;
· typed Float64Array columns for all
  2 fields
```

```text
… and ps.push({ x: 5, y: 'far' });
· typed Float64Array columns for x;
  plain array columns for y (may hold
  non-numbers)
```

```text
mixed_columns.js: es.push({ id: 'e' + i,
  hp: 100, x: i, tag: … });
· typed Float64Array columns for hp, x;
  plain array columns for id, tag (may
  hold non-numbers)
```

</Examples>

In the first, both fields only ever hold numbers, so the shape is
`{x: number, y: number}`. In the second, one extra push puts `'far'` in
`y`: the field list is unchanged, so the shape still unifies, but `y`
falls to "anything". The third is the figure's: two typed columns, two
plain ones, and still a struct of arrays.

## Unifying the literals

Each object literal is a `record.new` instruction in VIR, carrying its
field names. The first one Viscosity meets sets the shape; every later
one must match it exactly. Step through it:

<ShapeSteps client:visible />

Here is the real check, `setShape`, slightly simplified:

```ts
const setShape = (c, r, where) => {
  if (c.fields.length === 0)
    c.fields = [...r.fields];
  else if (JSON.stringify(c.fields)
           !== JSON.stringify(r.fields))
    bail(c, where + ': records with ' +
      'different fields or field order');
  if (usesOf(r.id).length !== 1)
    bail(c, where + ': the new record ' +
      'is also referenced elsewhere');
};
```

If the collection has no fields yet, the record's field list becomes
the shape. Otherwise both lists are turned into strings such as
`["x","y"]` and compared, so a missing field, an extra one or a
different order all fail; the last two lines are the aliasing rule
from *Finding collections*. ("The first one it meets" is the last in
the source, since the worklist takes the last load first, which is why
`shape_mismatch.js` reports `{y, x}` and blames line 4.) The order
really matters, because the rewritten
`push` is positional: the emitter turns `ps.push({ x: a, y: b })` into
`ps.push(a, b)`, and slot `k` goes into column `k`.

In the terms of *Type and shape inference*, this is shape inference
with the simplest possible join: equal shapes join to themselves, and
different shapes join to "no shape at all", a bailout.

## What the columns may hold

The second list, the column types, comes from the numeric analysis of
*Type and shape inference*. For each column, the facts form a lattice
with two points, "always a number" above "maybe anything", and each
column starts **optimistic**, at "always a number", falling as soon as
one value that may flow into it is not provably a number. Two kinds of
value flow into a column `ps.f`: slot `k` of every literal, and the
right-hand side of every `ps[i].f = v`. Simplified:

```ts
for (const f of c.fields) {
  const k = c.fields.indexOf(f);
  let ok = colNumeric.get(key(c, f));
  for (const r of literalsOf(c))
    if (!num.get(r.args[k])) ok = false;
  for (const v of storesInto(c, f))
    if (!num.get(v)) ok = false;
  update(key(c, f), ok); // sets changed
}
```

For each field at position `k`, `ok` starts at the column's current
fact; a literal whose slot `k`, or a stored value, is not known to be a
number knocks it down; and `update` stores it and, if it changed,
sends the outer loop round again,
because other values (such as a later `s += ps[i].x`) depend on this
one. The loop stops when a whole round changes nothing: a fixpoint.

<Formal title="The column type of a field">

```text
L = { num, any },   num ⊐ any
type(c.f) = ⊓ { type(v) | v flows into c.f }
start: type(c.f) = num, then fall
```

<span slot="read">The lattice L has two elements, num ("always a
number") above any ("maybe anything"). The type of field f of
collection c is the meet (the lower of, written ⊓) of the types of all
the values that flow into it: one value that may be anything drags the
whole column down to any. The analysis starts every column at num and
lets facts only fall, so it finds the greatest fixpoint, the most
hopeful answer every flow agrees with (the optimistic style of *Sparse
conditional constant propagation*).</span>
</Formal>

A field that falls is not a reason to give up; it only means a
`Float64Array` would be wrong for it, because a typed array converts
whatever you store into a number<Cite id="mdn-typed-arrays" />:

<Run id="coerce" />

One more rule makes this trustworthy. Facts only fall, so the loop
must end; Viscosity does not bet on that, though. It stops after 1000
rounds, and if the facts were still changing, it **fails closed**,
setting every fact to "maybe anything". An unfinished
optimistic analysis still holds guesses nobody has disproved yet, and
those are not proofs.

## Shapes that stay put

A shape computed from the literals describes the elements *when they
are made*. JavaScript objects can change after that: gain a property,
lose one, or be changed through a second reference. If any of that
could happen, the columns would describe something that no longer
exists.

<Analogy title="a printed seating plan">
A seating plan for a dinner is only useful if nobody brings an extra
chair, takes one away, or swaps seats with a friend after it has been
printed.
<span slot="breaks">At a dinner, a guest who swaps seats is still one
person in one chair; in a program, a second reference to a record is
the same record in two places at once, which no plan of separate seats
can describe.</span>
</Analogy>

<Callout kind="definition">
**Shape stability** is whether a shape can change after the object is
created. Viscosity needs every element's shape to be stable, and it
proves it by allowing only two things to be done to an element: read
a field the shape has, and write a field the shape has (on records
that have no other reference).
</Callout>

<Examples of="shape-stability">

```text
const r = { x: i }; ps.push(r);
if (i === 5) r.x = 500;
· unsafe: line 6: the new record is also
  referenced elsewhere, so it could be
  aliased
```

```text
ps[i].z = 1;   (records are {x, y})
· unsafe: line 5: adds a new property .z
  to an element
```

```text
delete ps[i].y;
· unsafe: the array is used by code
  Viscosity doesn't model (delete) at
  line 5
```

</Examples>

Each way of changing a shape meets a different rule. In the first
(from `record_shared.js`), `r` is a second name for an element, so a
write through it could change the element behind the collection's
back. The second would add a property with no column (reading one is
refused too: "reads .z, which the records don't have"). The third
removes one; `delete` is not modelled, so it becomes an `opaque`
instruction, and an unmodelled use is always a refusal.

<Prompts ids={['ss-what', 'ss-oneuse', 'ss-addprop']} />

<Callout kind="engine" label="Under the hood">
V8 meets unstable shapes all the time and copes with them while the
program runs: adding a property moves the object to a new hidden class
along a transition, and code specialised for the old shape stops
matching<Cite id="bynensmeurer2018" />. That works because V8 can
change its mind later. Viscosity chooses one layout before the program
starts and can never change it, so a shape that *might* change is
treated as one that *will*.
</Callout>

## What you learned

- A **record shape** is an ordered field list plus a column type per
  field: `Float64Array` for provably numeric fields, a plain array for
  the rest.
- Shapes unify only if every object literal has the same fields **in
  the same order**, because the rewritten `push` is positional; two
  different shapes join to a bailout.
- A column type is a two-point lattice, solved **optimistically**: it
  falls when any literal slot or field store may not be a number, which
  makes the column plain but does not stop the transform. If the
  fixpoint does not converge in 1000 rounds, it **fails closed**.
- **Shape stability** means the shape cannot change after creation.
  Viscosity proves it by allowing only reads and writes of known
  fields, on records that have no other reference.
