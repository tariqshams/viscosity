## A tree that contains itself

*Syntax trees and a tree printer* built expressions out of nodes, where an
addition node holds two smaller expressions; in TypeScript nobody thinks
twice about `{ kind: 'add'; l: Expr; r: Expr }`. Write it as a Rust enum,
`enum Expr { Num(f64), Add(Expr, Expr) }`, and rustc 1.97 refuses:

```text
error[E0072]: recursive type `Expr` has
  infinite size
help: insert some indirection (e.g., a
  `Box`, `Rc`, or `&`) to break the cycle
```

Rust stores an enum's fields *inside* it and must know every type's size
before the program runs, so an `Expr` holding two `Expr`s would contain
itself forever; TypeScript's fields hold *references*, never the objects.
Rust needs **indirection**: a field holding a pointer to the child.

<Analogy title="nesting dolls versus a note">
A set of nesting dolls has each doll inside the next; ask for a doll that
contains a doll *of its own size* and no set could ever be made. Now let
each doll hold a slip of paper saying which shelf the next doll is on:
every doll is the same small size, and the chain can be as long as you
like.
<span slot="breaks">A slip of paper can point at any doll, even one
already pointed at; a `Box` is the *only* pointer to its doll, so two
nodes can never share a child (that takes an `Rc`).</span>
</Analogy>

## Box: one owner, on the heap

A **`Box<T>`** is that slip of paper: `Box::new(v)` moves `v` to the heap
and gives you a pointer that owns it. All of *Ownership: moves, copies
and clones* still holds: moving the box moves ownership, and dropping
the box drops the value and frees its memory. It costs one heap
allocation and nothing else, with no counting and no check when you use
it<Cite id="rust-book-smart-pointers" />.

<Examples of="box">

```rust
enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}
let e = Expr::Mul(
    Box::new(Expr::Num(2.0)),
    Box::new(Expr::Num(3.0)),
);
```

</Examples>

Each `Add` or `Mul` now holds two pointers (8 bytes each on a 64-bit
machine) plus the tag saying which variant it is, so the size is fixed
(`size_of::<Expr>()` prints 24 under rustc 1.97 on x86-64). `e` is the
tree for `2 * 3`, each child a heap allocation of its own, and when `e`
goes out of scope the whole tree is freed. (drip-rs keeps a Drip string's
characters in a `Box<str>`: a `String` that can never grow.)

<Figure takeaway="Each Box owns exactly one child, so dropping the root frees the whole tree." caption="The tree for (1 + 2) * 3. The root is in a local variable; every child is a separate heap allocation owned by one Box in its parent.">
  <BoxTree />
</Figure>

<Callout kind="definition">
A **`Box<T>`** is a pointer to a `T` on the heap that **owns** it:
exactly one box per value, moving the box moves ownership, and dropping
it drops the `T` and frees the memory. A `Box` has a fixed size whatever
`T` is, which makes recursive types possible, and it holds a trait object
(`Box<dyn Trait>`) as an owned value<Cite id="rust-book-smart-pointers" />.
</Callout>

## Rc: several owners, counted

A tree suits `Box` because each node has one parent. Bytecode is not like
that: in drip-rs one compiled function's `Chunk` is needed by every call
frame running it (a recursive function has many) and by the VM's "current
chunk" register, and it must live exactly as long as the last of them
needs it. That is **`Rc<T>`**, short for *reference counted*:
`Rc::new(v)` puts `v` on the heap next to a **strong count** of 1;
`Rc::clone(&r)` copies the pointer, not `v`, and adds 1; dropping an `Rc`
subtracts 1, and at 0 the value is dropped<Cite id="rust-std-rc" />.

<RcSteps client:visible />

<Examples of="rc">

```rust
// drip-rs, src/vm.rs, starting a call
let chunk = Rc::clone(
    &self.heap[function].chunk);
self.frames.push(CallFrame {
    closure,
    chunk: Rc::clone(&chunk),
    ip: 0, slots });
self.chunk = chunk;
```

</Examples>

This is real (wrapped to fit). The function object owns an `Rc<Chunk>`;
the first line clones it, the second clone goes into the new call frame,
and the last line moves the first clone into the VM's register, so the
bytecode is shared three ways and copied never. There is a catch: write `a.value += 1.0` through an `Rc`, and
rustc 1.97 stops with E0594, `cannot assign to data in an Rc`. With
several owners alive, the many-readers-or-one-writer rule of *Borrowing
and the borrowing rules* means an `Rc` can only hand out shared access.
That is fine for a chunk, which is frozen once compiled.

<Callout kind="definition">
An **`Rc<T>`** is a pointer to a heap value with several owners. The
value carries a **strong count**: `Rc::clone` adds 1, dropping an `Rc`
subtracts 1, and the value is dropped when the count reaches 0. Through
an `Rc` you can only read. `Rc` is for one thread only (its count is not
updated atomically)<Cite id="rust-std-rc" />.
</Callout>

<More title="Rc against TypeScript's shared objects, and a runnable count">

## RefCell: the borrowing rules, checked later

Some shared data must change. In Drip, `fn makeCounter() { let n = 0;
fn inc() { n = n + 1; } fn get() { return n; } ... }` gives two closures
one captured `n`, and `inc` changes it. A **`RefCell<T>`** makes that
possible: it holds a value and a small borrow counter, and instead of the
compiler proving at build time that you never have a writer and a reader
at once, it *counts* them while the program runs. `borrow()` hands out a
reader and `borrow_mut()` a writer, each first checking the rules
against the counter, and each returns a **guard** that gives its borrow
back when it is dropped:

<BorrowFlag client:visible />

Because it lets you change its value through a shared `&`, this is called
**interior mutability**; put one inside an `Rc` and `Rc<RefCell<T>>` is
shared data that several owners may all change<Cite id="rust-book-smart-pointers" />.

<More title="The Drip counter in Rust, runnable">

One upvalue in an `Rc<RefCell<..>>`, captured by two closures: the
program prints `owners: 3`, then `get sees 2` after `inc` has added 1
twice, then `owners: 1` once both closures are dropped.

<Run id="rc-share" />

</More>

<Callout kind="definition">
A **`RefCell<T>`** moves borrow checking from compile time to run time.
`borrow()` returns a shared guard (`Ref`) and `borrow_mut()` an exclusive
one (`RefMut`); each guard gives its borrow back when dropped. Asking for
a borrow that breaks the rules (a writer while anyone else holds a
borrow, or a reader while a writer does) **panics**<Cite id="rust-std-cell" />.
</Callout>

<Examples of="refcell">

```rust
fn heal(me: &RefCell<Instance>,
    other: &RefCell<Instance>) {
    let mut m = me.borrow_mut();
    let o = other.borrow();
    m.hp += o.hp / 2.0;
}
heal(&a, &b); // fine
heal(&a, &a); // panics
```

</Examples>

Drip happily runs `a.heal(a)`, and here is a VM's `heal` built on
`RefCell`. `heal(&a, &b)` takes a writer of `a` and a reader of `b`, which
is fine; `heal(&a, &a)` asks for a reader of `a` while it holds a writer
of `a`, and under rustc 1.97 the program stops with `RefCell already
mutably borrowed`. The compiler saw two parameters and no broken rule:
the rule was broken by *which objects were passed*, and in a VM the Drip
program makes that choice.

## Cycles never reach zero

Make objects whose `field` can hold an `Rc` to another, and link `c` to
`d` and `d` to `c`. When the variables go out of scope each count falls
to 1, not 0, because the other object still points at it, so neither is
ever freed; the standard library is blunt that such a cycle will never
be deallocated<Cite id="rust-std-rc" /> (it is still memory *safe*:
nothing dangles, the memory is simply never given back<Cite id="klabnik2026" />).
Step through it:

<CycleSteps client:visible />

The usual fix is **`Weak<T>`**, made with `Rc::downgrade(&rc)`: a pointer
that does not own, used for the edge that points "back up". A VM cannot
use it, because the *program* decides which edges point back: `let a =
new Node(); a.me = a;` is a one-line cycle. So drip-rs's `object.rs` opens by
turning `Rc<RefCell<..>>` down, since it "would hand memory management to
Rust instead of to our own garbage collector"; its objects live in
arenas instead, and `Rc` appears only for frozen chunks that never point
back.

## What you learned

- **`Box<T>`**: one owner on the heap, a fixed size, so recursive types
  work. **`Rc<T>`**: several owners and a strong count, read-only.
- **`RefCell<T>`** checks the borrowing rules at run time and panics when
  they break; `Rc<RefCell<T>>` is shared, mutable data.
- `Rc` cycles leak, which is why drip-rs gives its objects to its own
  collector.
