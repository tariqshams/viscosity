## Fields in a table

```drip
class Point {}
let p = new Point();
p.x = 3;
p.y = 4;
print p.x; # 3
print p;   # Point { x: 3, y: 4 }
```

A Drip instance is a bag of fields that you can add to at any time, and
the chapter *Objects and method calls in the VM* put that bag in the
TypeScript VM as a hash table on each instance. drip-rs does the same,
from `object.rs` (comments trimmed):

```rust
pub struct ObjClass {
    pub name: StrRef,
    pub methods: Table,
}

pub struct ObjInstance {
    pub class: Gc<ObjClass>,
    pub fields: Table,
    pub field_order: Vec<StrRef>,
}
```

The TypeScript field is called `klass`, because `class` is a reserved
word in JavaScript; in Rust `class` is not a keyword<Cite id="rustref-keywords" />,
so drip-rs uses the plain word. `Table` is the hash table from the
chapter *Strings and interning in Rust*, keyed by `StrRef`: field names
are interned strings whose handle carries the hash, so looking up `x`
never visits the string arena. And `field_order` is the names in the
order they were first set, which is how an instance prints
(`Point { x: 3, y: 4 }`); a hash table on its own has no useful order.
The table and the `Vec` are plain Rust values inside the instance,
owned by it and freed with it when sweep drops the object (the chapter
*Ownership*).

<Analogy title="a luggage tag on a notebook">
The tag says which class the instance came from. The notebook has one
line per field, and you may add a line whenever you like; its first
page lists the fields in the order you started them. Everyone holding
the instance's number opens the same notebook.
<span slot="breaks">A notebook's lines are in the order written; the
table's slots are in hash order, which is why the separate list of
names is needed to print the fields in a sensible order.</span>
</Analogy>

Each guest card names the room type (the class) and has blanks the desk

<span slot="breaks">A hotel card has a fixed set of printed blanks; a

## Making an instance

`class` allocates an `ObjClass` with its name and an empty method table,
and pushes `Value::Class(handle)`. `new Point()` compiles to loading the
class, the arguments, and `new 0`; from `Vm::new_instance` (trimmed and
rewrapped):

```rust
let Value::Class(class) =
    self.peek(arg_count)
else { /* 'new' needs a class, not ... */ };
let instance = self.alloc(ObjInstance {
    class,
    fields: Table::new(),
    field_order: Vec::new(),
});
self.set_peek(arg_count,
    Value::Instance(instance));
// ...then call init, if the class has one
```

The `let ... else` (the chapter *Patterns in depth*) opens the value
under the arguments and reports the runtime error if it is not a class.
`alloc` may collect first, and the new instance holds `class`; that is
safe because the class is still on the stack in that slot, the rule
from *A garbage collector in Rust*. Only then does `set_peek` overwrite
the slot with the instance, which is where an `init` will find `self`
(the next chapter). Calling a class without `new`, as `Point()`, is the
runtime error `cannot call a class: use 'new Point(...)'`.

## Get and set

`get.prop` checks that `peek(0)` is an instance (or it is
`cannot read 'x' of a number`), then looks the name up:
`self.heap[instance].fields.get(name)` returns an `Option<Value>`, a
copy, so the borrow of the heap ends at once and `self.set_peek(0, value)`
can replace the instance with the field. A field that is missing falls
through to the class's methods, which is the next chapter; with no
method either, it is `Point has no property 'z'`. Fields are checked
first, so a field shadows a method of the same name. `set.prop`, from
`vm.rs` (rewrapped):

```rust
let name = self.read_string();
let Value::Instance(instance) = self.peek(1)
else { /* cannot set 'x' on ... */ };
let value = self.peek(0);
let object = &mut self.heap[instance];
if object.fields.set(name, value) {
    object.field_order.push(name);
}
// Leave the value as the
// assignment's result.
self.pop();
self.set_peek(0, value);
```

`Table::set` returns `true` when the key is new, and only then does the
name join `field_order`, so overwriting `p.x` later leaves it where it
was. `object` borrows one instance mutably for both writes, and its
borrow ends before `self.pop()`.

<InstanceSteps client:visible />

Here is the spot the difference. The TypeScript arm reads its operands
as it goes; a Rust toy that does the same in one line fails (rustc 1.97,
trimmed):

```text
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
7 | self.insts[i].fields
  | ---------- first mutable borrow
8 |     .insert(self.read_byte() as u32, v);
  |      ------ ^^^^ second mutable borrow
```

The receiver, the field table, is borrowed mutably first, and then the
argument wants `&mut self` too, to move `ip` on. drip-rs reads the name
and the value into locals before it touches the table, the same habit
as `patch_jump` in *Branches and loops in Rust*: finish reading, then
borrow to write.

<Callout kind="definition">
In drip-rs, an **instance** is an `ObjInstance` in the heap's instance
arena: a `Gc<ObjClass>` handle to its class, a **field table** (a
`Table` from interned names to values) and `field_order`, the names in
the order they were first set. `Value::Instance(handle)` refers to it.
`get.prop` reads a field with one lookup, falling back to the class's
methods; `set.prop` adds or overwrites one. Both check that the receiver
is an instance first.
</Callout>

<Formal title="Reading a property">

```text
o.n = fields(o)[n]        if n ∈ fields(o)
    = bound(o, m)         else if
      where m = methods(class(o))[n]
    = error "C has no property 'n'"
                          otherwise
```

<span slot="read">Reading the property n of an instance o gives the
field named n if o has one; otherwise, if o's class has a method named
n, it gives that method bound to o; otherwise it is the runtime error
naming the class C. The order of the lines is the rule that fields
shadow methods.</span>
</Formal>

## What you learned

- An **instance** is an `ObjInstance`: a class handle, a **field
  table** it owns, keyed by interned names, and the names in the order
  they were first set.
- **`new`** allocates the instance while the class is still on the
  stack, then `set_peek` puts the instance in the class's slot.
- `get.prop` **copies** the field's value out, so the heap borrow ends
  at once; fields shadow methods.
- `set.prop` **reads its operands first**, then borrows the instance:
  the TypeScript habit in one line is E0499 in Rust.

## The cake, one more time

```drip
class Cake {
  init(f) { self.f = f; }
  taste() { print "Mmm, " + self.f; }
}
let c = new Cake("lemon");
c.taste();
let t = c.taste;
t();
print t; # fn taste
```

It prints `Mmm, lemon` twice, then `fn taste`, exactly like the
TypeScript VM. `drip-rs --disassemble` shows the split from the chapter
*Invoking methods, and inheritance in the VM*: `c.taste()` is one
`invoke 'taste' (0 args)`, while `let t = c.taste;` is
`get.prop 'taste'`, which has to build a **bound method**, a value that
remembers both the method and the instance it was read from, so that a
later `t()` knows what `self` is. That object, and the `init` behind
`new Cake("lemon")`, are this chapter.

## A bound method is two handles

<Analogy title="a remote already paired with one television">
Pressing a button (calling the method) works on that set (the
receiver), whoever holds the remote and wherever they carry it.
<span slot="breaks">Pairing a remote is done once; drip-rs makes a new
bound method every time a method is read from an instance, so
`c.taste == c.taste` is `false`: two reads, two objects.</span>
</Analogy>

<Analogy extra title="a letter in a stamped, addressed envelope">
The letter is the method, the address on the envelope is the receiver;
whoever posts it, it reaches the same house.
<span slot="breaks">A posted letter is used up; a bound method can be
called any number of times, and each call gets the same receiver.</span>
</Analogy>

The TypeScript object is `{ type: 'bound', receiver, method }`. The Rust
one, from `object.rs`:

```rust
/// A method together with the instance it
/// was looked up on.
pub struct ObjBoundMethod {
    pub receiver: Value,
    pub method: Gc<ObjClosure>,
}
```

It lives in its own arena, `heap.bound_methods`, and a value refers to
it as `Value::BoundMethod(Gc<ObjBoundMethod>)`. The receiver is kept as
a `Value`, which is exactly what a call will write back onto the stack,
and the collector traces both fields. `get.prop` makes one when the
instance has no field of that name (the chapter *Objects in Rust*), from
`vm.rs` (rewrapped):

```rust
let class = self.heap[instance].class;
let Some(method) =
    self.heap[class].methods.get(name)
else { return Err(self.no_property(...)); };
let receiver = self.peek(0);
let bound = self.alloc(ObjBoundMethod {
    receiver,
    method: as_closure(method),
});
self.set_peek(0, Value::BoundMethod(bound));
```

Two details. The method table stores `Value`s, so `as_closure` opens the
`Value::Closure` with a `match` and calls `unreachable!` on anything
else, where TypeScript wrote `method as ObjClosure`, a promise the type
checker takes on trust. And the order matters: `alloc` may collect, so
the receiver stays on the stack, a root, until the bound method exists,
and only then does `set_peek` overwrite it with the handle.

## Calling it: copy two fields out

`call_value`'s arm for a bound method, from `vm.rs` (rewrapped):

```rust
Value::BoundMethod(bound) => {
    let ObjBoundMethod { receiver, method }
        = self.heap[bound];
    // The receiver goes in slot 0, where
    // the method finds `self`.
    self.set_peek(arg_count, receiver);
    self.call(method, arg_count)
}
```

Here is the spot the difference. The tempting line is
`let b = self.heap[bound];`, and on a toy with a `Vec<Bound>` rustc
1.97 says (trimmed):

```text
error[E0507]: cannot move out of index
  of `Vec<Bound>`
4 |     let b = bounds[0];
  |             ^^^^^^^^^ move occurs
  value has type `Bound`, which does not
  implement the `Copy` trait
```

Indexing gives a *place* (a location, not a value), and `let b = place`
would move the object out of the arena and leave a
hole<Cite id="rust-std-ops-index" />. The destructuring pattern instead
binds each field by value: `Value` and `Gc<T>` are both `Copy`, so each
field is copied and the object stays put (the chapter *Ownership*
explains moves and copies). TypeScript's `callee.receiver` is a plain
reference read, so the question never comes up there. Then
`set_peek(arg_count, receiver)` overwrites the callee's own slot, which
`call` turns into the new frame's slot 0; inside the method, `self`
compiles to `load.local 0`, so it is the receiver.

<BoundSteps client:visible />

<Callout kind="definition">
A **bound method in drip-rs** is an `ObjBoundMethod`, holding a
`receiver: Value` and a `method: Gc<ObjClosure>`, in the heap's
`bound_methods` arena, with a `Value::BoundMethod` handle to it.
`get.prop` makes one when a property read finds a method: it allocates
while the receiver is still on the stack, then overwrites the receiver
with the handle. Calling one copies both fields out with a destructuring
pattern, puts the receiver in the callee's slot, and calls the closure.
</Callout>

<Formal title="What a bound method and new mean">

```text
bound(r, m)(a₁, …, aₙ)
  = m(a₁, …, aₙ)   with slot 0 = r
new C(a₁, …, aₙ)
  = o              after C.init(a₁, …, aₙ)
                   runs with slot 0 = o
```

<span slot="read">Calling a bound method made from the receiver r and
the method m is calling m with the same arguments, except that slot 0,
where self lives, holds r. And new C with some arguments makes a fresh
instance o, runs C's init with those arguments and o in slot 0 (if C has
an init), and produces o.</span>
</Formal>

## Initialisers

`new` is `Vm::new_instance`. The chapter *Objects in Rust* showed its
first half: allocate the instance while the class is still in its slot,
then overwrite that slot with it. The second half (rewrapped):

```rust
match self.heap[class].methods
    .get(self.init_string) {
    Some(init) => self.call(
        as_closure(init), arg_count),
    None if arg_count != 0 => {
        // "Cake has no init, so it takes no
        // arguments, but got 2"
    }
    None => Ok(()),
}
```

`init_string` is `"init"`, interned once in `Vm::new` and listed in
`VmRoots`, so the lookup allocates nothing and the string cannot be
collected. `get` returns a copied `Option<Value>`, so the borrow of the
class ends before `call` needs `&mut self`. TypeScript's two `if`s
become one `match` with a guard, which says in one place what happens
in all three cases. The compiler's half: `method()` picks
`FunctionKind::Initializer` when the name is the keyword `init` (an
enum variant where TypeScript compared the string `'initializer'`), and
then `emit_return` ends every initialiser with `load.local 0` and
`return`, so `new` always produces the instance (rewrapped):

```rust
if self.state().kind
    == FunctionKind::Initializer {
    // An initializer returns `self`, which
    // is in slot 0.
    let line = self.previous.line;
    self.emit_op_byte_at(line,
        OpCode::LoadLocal, 0);
} else {
    self.emit_op(OpCode::None);
}
```

## What you learned

- A **bound method** in drip-rs is `ObjBoundMethod { receiver, method }`
  in an arena, reached through `Value::BoundMethod`.
- `get.prop` **allocates before it overwrites** the receiver, so the
  receiver is a root if a collection runs.
- Indexing the heap gives a place: **destructure** it to copy the `Copy`
  fields out; `let b = self.heap[bound];` would be a move (E0507).
- Calling a bound method or running `init` **uses the callee's slot** as
  slot 0, `self`; `FunctionKind::Initializer` makes every `init` return
  slot 0.

## Two classes, one copy

Here is the smallest program that needs inheritance, with an override
and a call through `super`:

```drip
class A {
  hi() { print "A.hi"; }
  me() { print "A.me"; }
}
class B extends A {
  hi() { print "B.hi"; super.hi(); }
}
new B().hi();
new B().me();
```

drip-rs prints `B.hi`, `A.hi` and `A.me`: B's own `hi` runs and calls
A's through `super`, and `me`, which B never wrote, is found anyway.
How was settled in *Invoking methods, and inheritance in the VM*: when
B is declared, every method of A is **copied down** into B's own table,
so a lookup on B never looks anywhere else. This is the part of
`drip-rs --disassemble` that declares B:

```text
0022    5 class               7 'B'
0025    | define.global       8 'B'
0028    | load.global         9 'A'
0031    | load.global        10 'B'
0034    | inherit
0035    | load.global        11 'B'
0038    6 closure            13 fn hi
0041    |   local 1
0043    | method             12 'hi'
0046    7 pop
0047    | close.upvalue
```

`class` makes an empty B and `define.global` names it; A is loaded (it
stays in that slot as a hidden local called `super`), B goes on top,
and `inherit` copies A's methods into B. Then the body runs as usual:
`closure` makes B's `hi`, capturing local 1 (the `super` slot), and
`method` puts it in B's table; at the end `close.upvalue` saves `super`
for the methods that captured it. The TypeScript VM's disassembler
prints the same listing, byte for byte; the Rust differs in one line of
the VM and in how the compiler tracks the class it is in.

<Analogy title="photocopying a recipe binder">
When you move out, you photocopy your parent's recipe binder and write
your own versions over a few pages. From then on you open only your
binder; you never phone home to ask.
<span slot="breaks">If your parent later adds a recipe, your copy does
not have it. That would be a bug for a language where classes can grow;
it is safe in Drip only because a class can never gain a method after
its declaration.</span>
</Analogy>

<Analogy extra title="setting up a new phone">
A new phone copies the contacts from the old one on the first day, and

<span slot="breaks">Contacts keep changing on both phones; Drip's

## The line that will not compile

In the TypeScript VM, `inherit` is one statement:

```ts
(this.peek(0) as ObjClass).methods
  .addAll((superclass as ObjClass).methods);
```

It reads A's table and writes B's at once. Write that in Rust, against a toy heap that implements `Index` and
`IndexMut` (the traits behind `heap[handle]`, from *Heap objects in an
arena*), and rustc 1.97 refuses it (trimmed and
rewrapped):

```rust
let from = &h[sup].methods;
h[sub].methods.extend(from);
```

```text
error[E0502]: cannot borrow `*h` as
  mutable because it is also borrowed
  as immutable
12 | let from = &h[sup].methods;
   |             - immutable borrow
13 | h[sub].methods.extend(from);
   | ^ mutable borrow occurs here
```

`h[sub]` on the left of a write is `*h.index_mut(sub)`, and `index_mut`
takes `&mut self`, the **whole** heap, not one slot<Cite id="rust-std-ops-index" />. The borrow checker
(from *Borrowing*) only sees "a shared borrow of `h` is alive, and now
someone wants a mutable one"; it has no idea that `sub` and `sup` are
different numbers, so it must assume they could be the same slot.

<BorrowSplit />

drip-rs's arm, from `vm.rs` (the error message trimmed, and rewrapped):

```rust
OpCode::Inherit => {
    let Value::Class(superclass) =
        self.peek(1)
        else {
        // "a class can only extend a
        // class, not ..."
        return Err(/* ... */);
    };
    let subclass = as_class(self.peek(0));
    // Copy-down inheritance: methods are
    // copied once, now.
    let methods = self.heap[superclass]
        .methods.clone();
    self.heap[subclass].methods
        .add_all(&methods);
    self.pop();
}
```

The `let ... else` (from *Patterns in depth*) opens the superclass,
and anything else is the program's mistake, reported as a runtime
error. The subclass goes through `as_class`, which is `unreachable!`
for a non-class, because the compiler put B there itself. Then
`clone()` copies A's `Table` (it derives `Clone`) into the local
`methods`, and the shared borrow ends at that semicolon; only then
does `add_all` borrow the heap mutably to write into B, and `pop`
removes B, leaving `super`.

<Prompts ids={['cd-e0502', 'cd-clone', 'cd-check']} />

The copy is Rust memory, not a Drip object: it never goes through
`Heap::alloc`, so it cannot start a collection. It is dropped at the
end of the arm, and it happens once per class, never once per call.

<Callout kind="definition">
**Copy-down inheritance** copies every entry of the superclass's
methods table into the subclass's table once, when the class is
declared and before the subclass's own methods are added, so overrides
win; a lookup is then one probe in the subclass's own table. In drip-rs
`inherit` clones the superclass's `Table` first, then adds it to the
subclass. It is correct because a Drip class cannot gain methods later.
</Callout>

<Formal title="Copy-down as a table union">

```text
methods(B) = methods(A) ◁ own(B)
lookup(B, m) = methods(B)[m]
```

<span slot="read">B's table is A's table with B's own methods laid over
it: where both have a name, B's entry wins (the triangle points at the
side that loses). Looking m up on B is one lookup in B's table.</span>
</Formal>

<Examples of="method-copy-down">

```drip
class A { me() { print "A.me"; } }
class B extends A {}
new B().me(); # A.me
```

```drip
class A { f() { return "A"; } }
class B extends A {}
class C extends B {
  f() { return "C+" + super.f(); }
}
print new C().f(); # C+A
```

<Run id="shapes" />

</Examples>

In the first, B's table after `inherit` holds A's `me` and nothing
else, so `new B().me()` finds it in one probe. In the second, B gets
A's `f` when it is declared, and C later gets B's whole table, which
already holds A's `f`; the copy is transitive with no extra code, and
C's own `f` then overwrites it. Inside C's `f`, `super` is B, and `super.f()` finds A's
`f` in B's table and prints `C+A`. The third, which you can run, is the
realistic shape: `Rect`'s `init` calls `super.init("rect")`, and
`describe`, which only `Shape` wrote, calls `self.area()`, which only
`Rect` wrote; it prints `rect 12`.

## super in the compiler

The TypeScript compiler keeps nested classes in a linked list of
`{ enclosing, hasSuperclass }` records and holds the current one in a
variable, `cc`, so that it can set `cc.hasSuperclass = true` later.
drip-rs keeps a stack, `classes: Vec<ClassState>`, beside its stack of
`FunctionState`s (from *A Pratt compiler in Rust, part 2*). Holding a
`&mut ClassState` across the calls in between would lock up `self`, the
E0499 of *Globals by name and locals by slot, in Rust*, so the compiler
reaches back in when it needs to; from `class_declaration` (rewrapped):

```rust
self.begin_scope();
self.add_local("super", superclass);
self.mark_initialized();
self.named_variable(class_name, false);
self.emit_op_at(superclass.line,
    OpCode::Inherit);
self.classes.last_mut()
    .expect("a class")
    .has_superclass = true;
```

`add_local` wants a `&'src str`, a name borrowed from the source, and
is handed `"super"`, a `&'static str`; that is allowed, because
`'static` lives at least as long as `'src` (the chapter *Lifetimes*).
`super_expression` uses the same trick, `Token::synthetic("super",
line)`, to load the hidden local, as TypeScript's `synthetic('super')`
does. Its checks give the same compile errors as the TypeScript
compiler; for `class A2 extends A2 {}` on line 2, `super.m()` in a
class with no `extends` on line 4 and `print super.x;` on line 6
(wrapped):

```text
line 2: a class cannot extend itself
line 4: cannot use 'super' in a class
  that does not extend another
line 6: cannot use 'super' outside a
  method
```

At run time, `get.super` pops the superclass and makes a bound method
(from *Method calls and init in Rust*), and `invoke.super` calls the
method at once; a missing one is `A has no method 'nope'`, the same
runtime error in both VMs.

<Callout kind="engine" label="Under the hood">
Copy-down trades memory for speed: every subclass carries a copy of
everything it inherits, and no lookup walks a chain. It depends on
classes being closed once declared; a language that lets you add
methods to a class later (JavaScript, Python) must look along the chain
at call time, or cache the answer and drop the cache when a class
changes. The corpus's `inheritance/` folder holds 19 programs, and
drip-rs passes all of them, under the stress collector too.
</Callout>

## What you learned

- `inherit` **copies the superclass's methods down** into the
  subclass, once, before the subclass's own `method` instructions run,
  so overrides win.
- Reading `heap[sup]` while writing `heap[sub]` is **E0502**: indexing
  borrows the whole heap. drip-rs **clones the table first**, and the
  clone is Rust memory, so it **cannot start a collection**.
- The compiler keeps a **`Vec<ClassState>`** and reaches back in with
  `last_mut()`, rather than holding a reference.
