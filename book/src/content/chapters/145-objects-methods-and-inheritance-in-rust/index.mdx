## Fields in a table

```drip
class Point {}
let p = new Point();
p.x = 3;
p.y = 4;
print p;   # Point { x: 3, y: 4 }
```

*Classes and method calls in the VM* gave each TypeScript instance a hash
table of fields. The design carries over; what Rust changes is how the VM
may touch an object while it also reads the stack and the code. A class is `ObjClass { name, methods: Table }`, and an instance,
from `object.rs` (comments trimmed):

```rust
pub struct ObjInstance {
    pub class: Gc<ObjClass>,
    pub fields: Table,
    pub field_order: Vec<StrRef>,
}
```

The TypeScript field is `klass`, because `class` is reserved in
JavaScript; in Rust it is not a keyword<Cite id="rustref-keywords" />.
`Table` is keyed by `StrRef`, interned names that carry their hash, so
looking up `x` never visits the string arena. `field_order` is the names
in the order first set, which is how an instance prints; a hash table on
its own has no useful order.

<Analogy title="a luggage tag on a notebook">
The tag says which class the instance came from. The notebook has one
line per field, and you may add a line whenever you like; its first
page lists the fields in the order you started them. Everyone holding
the instance's number opens the same notebook.
<span slot="breaks">A notebook's lines are in the order written; the
table's slots are in hash order, which is why the separate list of
names is needed to print the fields in a sensible order.</span>
</Analogy>

`get.prop` copies the field out, `self.heap[instance].fields.get(name)`
being an `Option<Value>`, so the heap borrow ends at once; a missing
field falls through to the class's methods, so fields shadow methods.
`set.prop` (from `vm.rs`, the error trimmed):

```rust
let name = self.read_string();
let Value::Instance(instance) =
    self.peek(1) else { /* error */ };
let value = self.peek(0);
let object = &mut self.heap[instance];
if object.fields.set(name, value) {
    object.field_order.push(name);
}
```

`Table::set` returns `true` for a new key, and only then does the name
join `field_order`. Everything is read into locals *before* `object`
borrows the instance: a one-liner in the TypeScript style,
`self.heap[i].fields.set(self.read_string(), v)`, is E0499 in rustc
1.97, because the table is borrowed mutably as the receiver and then
`read_string` wants `&mut self` to move `ip` on.

<Callout kind="definition">
In drip-rs, an **instance** is an `ObjInstance` in the heap's instance
arena: a `Gc<ObjClass>` handle to its class, a **field table** (a
`Table` from interned names to values) and `field_order`, the names in
the order they were first set. `get.prop` reads a field with one lookup,
falling back to the class's methods; `set.prop` adds or overwrites one.
</Callout>

<Examples of="rust-instances">

```drip
p.x = 5;
print p; # Point { x: 5, y: 4 }
```

</Examples>

After the program above, this overwrites `x`: `fields.set` returns
`false`, so `field_order` is unchanged and `x` still prints first, in
drip-rs and the TypeScript VM alike.

<More title="Making an instance, and a list of records">

`new Point()` runs `Vm::new_instance`, which opens the class with
`let Value::Class(class) = self.peek(arg_count) else { ... }`, allocates
`ObjInstance { class, fields: Table::new(), field_order: Vec::new() }`,
and only then overwrites the class's stack slot with the instance. The
order is the rule of *A garbage collector in Rust*: `alloc` may collect,
and the instance holds `class`, so the class must still be on the stack.
That slot becomes slot 0 of `init`. To the collector an instance is its
class and its table; its pacing size is `size_of::<ObjInstance>()`, 88
bytes (rustc 1.97, x86-64), which leaves out the buffers. This program

## A bound method is two handles

```drip
class Cake {
  init(f) { self.f = f; }
  taste() { print "Mmm, " + self.f; }
}
let c = new Cake("lemon");
let t = c.taste;
t(); # Mmm, lemon
```

`c.taste()` compiles to one `invoke`, which allocates nothing; but
`let t = c.taste;` is a `get.prop` that must build a **bound method**, a
value remembering both the method and the instance, so that a later
`t()` knows what `self` is (*Classes and method calls in the VM*).

<Figure caption="c.taste() goes straight to the method; c.taste on its own makes a bound method, which a later call unpacks into slot 0." takeaway="Only reading a method without calling it allocates.">
  <TwoPaths />
</Figure>

```rust
pub struct ObjBoundMethod {
    pub receiver: Value,
    pub method: Gc<ObjClosure>,
}
```

It lives in `heap.bound_methods`. `get.prop` reads the method from the
class's table, allocates `ObjBoundMethod { receiver, method }` while the
receiver is still on the stack (a root, in case `alloc` collects), and
only then overwrites the receiver with `Value::BoundMethod(bound)`.
Calling one, in `call_value` (rewrapped):

```rust
Value::BoundMethod(bound) => {
    let ObjBoundMethod { receiver, method }
        = self.heap[bound];
    self.set_peek(arg_count, receiver);
    self.call(method, arg_count)
}
```

The tempting line is `let b = self.heap[bound];`, and rustc 1.97
refuses: `error[E0507]: cannot move out of index of Vec<Bound>` (on a
toy), `which does not implement the Copy trait`. Indexing gives a
*place*, and binding the whole struct would move the object out of the
arena<Cite id="rust-std-ops-index" />; the pattern binds each field
instead, and `Value` and `Gc<T>` are both `Copy`, so each is copied and
the object stays put. Then the receiver overwrites the callee's slot,
which `call` turns into slot 0, where `self` lives.

<Analogy extra title="a remote already paired with one television">
Pressing a button (calling the method) works on that set (the
receiver), whoever holds the remote and wherever they carry it.
<span slot="breaks">Pairing a remote is done once; drip-rs makes a new
bound method every time a method is read from an instance, so
`c.taste == c.taste` is `false`: two reads, two objects.</span>
</Analogy>

<Callout kind="definition">
A **bound method in drip-rs** is an `ObjBoundMethod`, holding a
`receiver: Value` and a `method: Gc<ObjClosure>`, in the heap's
`bound_methods` arena, with a `Value::BoundMethod` handle to it.
`get.prop` makes one when a property read finds a method; calling one
copies both fields out with a destructuring pattern, puts the receiver
in the callee's slot, and calls the closure.
</Callout>

<Examples of="rust-bound-method">

```drip
print t;                  # fn taste
print c.taste == c.taste; # false
```

</Examples>

Every read of `c.taste` makes a new `ObjBoundMethod`, and objects
compare by handle, so two reads are two different values, in both VMs.

<More title="Initialisers in the compiler and the VM">

After allocating the instance, `new_instance` matches on
`self.heap[class].methods.get(self.init_string)`: `Some(init)` calls it,
`None if arg_count != 0` is the runtime error `Cake has no init, so it
takes no arguments, but got 2`, and `None` is fine. `init_string` is
`"init"`, interned once and listed in `VmRoots`. In the compiler,
`FunctionKind::Initializer` (an enum where TypeScript compared the
string `'initializer'`) makes `emit_return` end every `init` with
`load.local 0`, so `new` always produces the instance, and makes
`return 1;` inside `init` the compile error `'init' cannot return a
value`.

## Copying methods down, once

*Classes and method calls in the VM* settled inheritance by copy-down:
when `class B extends A` is declared, every method of A is copied into
B's own table, so a lookup on B never looks anywhere else. The compiler
loads A (which stays in its slot as a hidden local, `super`), then B,
then emits `inherit`, before B's own `method` instructions, so overrides
win. The `Inherit` arm is the borrow problem met in *Heap objects in an
arena*: reading A's table while writing B's would hold a shared and a
mutable borrow of the whole heap at once, because `heap[sub]` on the
left of a write is `*heap.index_mut(sub)`, which takes `&mut self`, and
the borrow checker cannot know `sub` and `sup` are different slots. So
drip-rs clones first (rewrapped, the error trimmed):

```rust
OpCode::Inherit => {
    let Value::Class(superclass) =
        self.peek(1) else { /* error */ };
    let subclass = as_class(self.peek(0));
    let methods = self.heap[superclass]
        .methods.clone();
    self.heap[subclass].methods
        .add_all(&methods);
    self.pop();
}
```

The superclass is the program's value, so a non-class is a runtime
error, while `as_class` is `unreachable!` for a non-class, because the
compiler put B there itself. The clone is Rust memory, not a Drip
object: it never goes through `Heap::alloc`, so it cannot start a
collection, and it happens once per class, never per call.

<InheritSteps client:visible />

<Callout kind="definition">
**Copy-down inheritance** copies every entry of the superclass's
methods table into the subclass's table once, when the class is
declared and before the subclass's own methods are added, so overrides
win; a lookup is then one probe in the subclass's own table. In drip-rs
`inherit` clones the superclass's `Table` first, then adds it to the
subclass. It is correct because a Drip class cannot gain methods later.
</Callout>

<Examples of="method-copy-down">

```drip
class A { f() { return "A"; } }
class B extends A {}
class C extends B {
  f() { return "C+" + super.f(); }
}
print new C().f(); # C+A
```

</Examples>

B gets A's `f` when it is declared, and C later gets B's whole table,
which already holds A's `f`: the copy is transitive with no extra code,
and C's own `f` then overwrites it. Inside C's `f`, `super` is B, and
`super.f()` finds A's `f` in B's table, so drip-rs prints `C+A`.

<More title="Why the one-line version fails, and super in the compiler">

<BorrowSplit />

The TypeScript compiler keeps nested classes in a linked list and holds
the current one in a variable to set `hasSuperclass` later; drip-rs
keeps `classes: Vec<ClassState>` and reaches back in with
`self.classes.last_mut().expect("a class").has_superclass = true;`,
because holding a `&mut ClassState` across the calls in between would
lock up `self`. The hidden local is added with `self.add_local("super",
superclass)`, a `&'static str` where a `&'src str` is wanted, which is
allowed because `'static` outlives `'src` (*Lifetimes*). The compile
errors are the TypeScript compiler's: `a class cannot extend itself`,
`cannot use 'super' in a class that does not extend another`, `cannot
use 'super' outside a method`. Copy-down depends on classes being closed
once declared; a language that lets you add methods later (JavaScript,
Python) must look along the chain at call time, or cache and
invalidate.

## What you learned

- An **instance** is a class handle, a field table and `field_order`;
  read into locals before borrowing it to write.
- A **bound method** is two `Copy` handles, destructured out of the
  arena, never moved.
- **Copy-down** clones the superclass's table once, then adds it.
