## A column that grows

In *Rewriting field accesses and growing collections* you grew a
`Float64Array` column by hand: keep a length and a capacity, and when
they meet, allocate a bigger array and copy across. Rust's `Vec` does
that bookkeeping for you:

```rust
let mut xs: Vec<f64> = Vec::new();
xs.push(1.5);
xs.push(2.5);
println!("{} {}", xs.len(), xs[0]); // 2 1.5
```

`Vec<f64>` reads "a vector of `f64`". Unlike a TypeScript array, every
element has the same type, so the elements sit side by side in memory;
a `Vec<f64>` is laid out like a `Float64Array` that can grow.

<Analogy title="a row of theatre seats">
A `Vec` is a ticket stub for a row of seats. The stub, in your pocket
(the stack), says where the row starts, how many seats your group has
taken and how many are reserved; the seats themselves are in the hall
(the heap). When the group outgrows the row, the usher finds a longer
row elsewhere and moves everyone, and your stub is updated; however,
anyone still holding an old seat number is now pointing at an empty
chair.
<span slot="breaks">An usher would tell the people holding old seat
numbers; a computer does not, which is exactly why Rust refuses to let
anyone hold an old seat number (a reference into the `Vec`) across a
move.</span>
</Analogy>

## Length, capacity, buffer

A `Vec` value is three words: a pointer to a heap buffer, a length and
a capacity, and the buffer is one contiguous block<Cite id="rust-std-vec" />.
Step through some pushes:

<VecSteps client:visible />

The capacities in the diagram are real (rustc 1.97 on this machine
gave 4, 4, 4, 4, 8, 8, 8, 8, 16 for nine pushes), but the documentation
promises no growth strategy, only that `push` takes amortised constant
time and that `Vec::with_capacity(n)` makes room for at least `n`
elements<Cite id="rust-std-vec" />.

<Callout kind="definition">
A **`Vec<T>`** is Rust's growable array. It owns a contiguous heap
buffer of `T`s and records its **length** (elements in use) and
**capacity** (room allocated). `push` appends, reallocating and moving
the elements when the length would pass the capacity.
</Callout>

<Examples of="vec">

```rust
let mut v = vec![1.5, 2.5, 4.0];
v[0] = 9.0;
let last = v.pop();  // Some(4.0)
let gone = v.get(5); // None
let bad = v[5];      // panics
```

</Examples>

The `vec!` macro builds a `Vec` with elements already in it (an empty
one is `Vec::new()`). Indexing reads and writes like an array, so `v`
becomes `[9.0, 2.5, 4.0]`. `pop` takes the last element off and returns
an `Option`, since the `Vec` might be empty, which leaves `[9.0, 2.5]`.
`get` is the polite way to read an index: `None` when it is out of
range. The last line is the impolite way; rather than read whatever
memory lies past the end, Rust stops the program with `index out of
bounds: the len is 2 but the index is 5` (TypeScript would hand back
`undefined` and carry on).

## The rule that pays its way

Here is a program every Rust programmer writes once. It looks harmless,
and rustc 1.97 refuses it:

```rust
let mut v = vec![1.0, 2.0];
let first = &v[0];
v.push(3.0);
println!("{}", first); // ✗
```

```text
error[E0502]: cannot borrow `v` as
  mutable because it is also borrowed
  as immutable
3 | let first = &v[0];
  |              - immutable borrow
4 | v.push(3.0);
  | ^^^^^^^^^^^ mutable borrow
5 | println!("{}", first);
  |                ----- later used here
```

It is the shared-or-mutable rule of *Borrowing and the borrowing
rules*, and the diagram's last steps showed why it matters: if this
`push` hit the capacity, the elements would move and `first` would
point into freed memory. JavaScript never hands you a pointer into an
array's storage; C hands you one and does not check; Rust hands you
one, and checks.

A loop over a `Vec` makes the same three choices a method makes about
`self`:

</Figure>

A function that only reads should take a slice, `&[f64]`, which a
`&Vec<f64>` turns into by itself.

## Counting with names

Viscosity's analysis wants to know which fields a loop touches, and how
often. In TypeScript you reached for a `Map`; in Rust it is
`HashMap<K, V>`, imported with `use std::collections::HashMap;`.

`m.insert(k, v)` adds a key and its value, or replaces the value and
returns the old one as `Some(old)`. `m.get(k)` returns an `Option<&V>`:
`None` for a missing key, otherwise a borrowed look at a value the map
keeps. Counting, however, needs "if the key is new, start at zero;
either way, add one", and that is the **entry API**:

<EntrySteps client:visible />

`entry(f)` finds the slot for `f`; `or_insert(0)` puts in `0` only if
the slot was empty, and either way returns a mutable reference to the
value, which `*... += 1` follows and changes<Cite id="rust-book-hashmaps" />.

<Callout kind="definition">
A **`HashMap<K, V>`** is Rust's hash table. It owns its keys and its
values. `insert` adds or replaces, `get` returns `Option<&V>`, and
`entry(k).or_insert(v)` returns a mutable reference to the value for
`k`, inserting `v` first if there was none. Its iteration order is
arbitrary, and can change from run to run<Cite id="rust-std-hashmap" />.
</Callout>

<Examples of="hashmap">

```rust
let used = ["x", "vx", "x", "y", "x"];
let mut n = HashMap::new();
for f in used {
    *n.entry(f).or_insert(0) += 1;
}
n.get("x");        // Some(3)
n.get("mass");     // None
n.insert("y", 10); // Some(1)
```

</Examples>

The first `x` finds no entry, so `or_insert(0)` adds one and `+= 1`
makes it 1; the next two `x`s find it and add to it, so `get("x")` is
`Some(3)`. A field never read has no entry, so `get("mass")` is `None`,
not `0`, and `insert` on an existing key replaces the count and hands
back the old one. TypeScript's `n.set(f, (n.get(f) ?? 0) + 1)` looks
the key up twice; `entry` looks it up once.

<Run id="map-play" />

Two differences from a JavaScript `Map` remain. The map **owns its
keys**: insert a `String` and it moves in, so using it afterwards is
E0382 (rustc suggests `k.clone()`). And the **order** is not promised:

<Figure takeaway="A HashMap's order changes between runs; a JavaScript Map's never does." caption="Real output of one program run three times with rustc 1.97. The default hasher is randomly seeded each run, so keys land in different slots.">
  <OrderRuns />
</Figure>

A JavaScript `Map` iterates in insertion order<Cite id="mdn-map" />; a
`HashMap` promises nothing. That matters here: the Rust port of
Viscosity must make the same decisions as the TypeScript one, so where
order reaches the output it uses `IndexMap` (from the `indexmap`
crate), a hash map that remembers insertion order; its SSA builder
fills phis in that order because, as a comment in `builder.rs` says,
it "decides value numbering and the order of instructions".

<Prompts ids={['map-get', 'map-entry', 'map-own', 'map-order']} />

<More title="Under the hood: SwissTable, and drip-rs's own table">
std's `HashMap` is a Rust port of Google's SwissTable, and by default it
hashes keys with SipHash 1-3, randomly seeded, to resist attackers who
choose keys that collide<Cite id="rust-std-hashmap" />. drip-rs does
not use it for Drip's globals and fields: its `table.rs` is the table
of *Hash tables* ported, with linear probing, tombstones, and storage
as a struct of arrays, `keys: Vec<Option<StrRef>>` beside
`values: Vec<Value>`. Its keys are interned strings (*String interning
and globals by name*) whose handle carries the hash, so a lookup never
runs a hash function at all.
</More>

## What you learned

- A **`Vec<T>`** owns a contiguous heap buffer of `T`s, with a length
  and a capacity; `push` grows it. `v[i]` panics out of range and
  `v.get(i)` returns an `Option`.
- You cannot `push` while a reference into the `Vec` is alive, because
  the buffer might move. Loop over `&v` to read, `&mut v` to change,
  `v` to use it up.
- A **`HashMap<K, V>`** owns its keys and values; `get` returns
  `Option<&V>`, and `*m.entry(k).or_insert(0) += 1` counts in one
  lookup. Its order is arbitrary; use `IndexMap`, or sort, when order
  reaches the output.
