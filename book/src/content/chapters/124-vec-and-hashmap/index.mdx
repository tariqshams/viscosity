## A column that grows

In *Growing collections* you taught Viscosity to grow a `Float64Array`
column by hand: keep a length and a capacity, and when they meet,
allocate a bigger array and copy everything across. Rust's standard
library does that bookkeeping for you:

```rust
let mut xs: Vec<f64> = Vec::new();
xs.push(1.5);
xs.push(2.5);
println!("{} {}", xs.len(), xs[0]);
// 2 1.5
```

`Vec<f64>` reads "a vector of `f64`". Unlike a JavaScript array, every
element has the same type, so the elements sit side by side in memory
with nothing in between: a `Vec<f64>` is laid out like a `Float64Array`
that can grow.

<Analogy title="a row of theatre seats">
A `Vec` is a ticket stub for a row of seats. The stub, in your pocket
(the stack), says where the row starts, how many seats your group has
taken and how many are reserved. The seats themselves are in the hall
(the heap). When the group outgrows the row, the usher finds a longer
row elsewhere and moves everyone; your stub is updated, but anyone still
holding an old seat number is now pointing at an empty chair.
<span slot="breaks">An usher would tell the people holding old seat
numbers; a computer does not, which is exactly why Rust refuses to let
anyone hold an old seat number (a reference into the `Vec`) across a
move.</span>
</Analogy>

<Analogy extra title="a train and its platform">
A train adds carriages at the back, one at a time, and every carriage is
the same size. While the platform is long enough nothing else changes;
when it is not, the whole train moves to a longer platform, which takes
a while, but happens rarely, because each new platform is about twice
as long as the last.
<span slot="breaks">A real train moves under its own power; a `Vec`'s
move is a copy of every element into fresh memory, and the old memory is
freed at once.</span>
</Analogy>

## Length, capacity, buffer

The standard library documents the picture exactly: a `Vec` value is a
pointer to a heap buffer, a length and a capacity, and the buffer is one
contiguous block<Cite id="rust-std-vec" />. Step through some pushes:

<VecSteps client:visible />

The capacities in that diagram are real: on this machine, with Rust
1.97, pushing nine `f64`s one at a time gave capacities 4, 4, 4, 4, 8,
8, 8, 8, 16. Do not build on those numbers, however: the documentation
promises no particular growth strategy, only that `push` takes amortised
constant time (the doubling argument of *Growing collections*). What it
does promise is that `Vec::with_capacity(n)` makes room for at least `n`
elements, and that a `Vec` never shrinks by itself<Cite id="rust-std-vec" />.

<Callout kind="definition">
A **`Vec<T>`** is Rust's growable array. It owns a contiguous heap
buffer of `T`s and records its **length** (elements in use) and
**capacity** (room allocated). `push` appends, reallocating and moving
the elements when the length would pass the capacity. When the `Vec` is
dropped, its elements are dropped and the buffer is freed.
</Callout>

<Formal title="What a Vec keeps true">

```text
v = (ptr, len, cap)       len ≤ cap
v[i] is an element  ⟺  0 ≤ i < len
n pushes from empty: O(n) total work
```

<span slot="read">A Vec is three numbers: where its buffer is, how many
elements are in use, and how many fit; the length is never more than the
capacity. v[i] is a real element exactly when i is at least 0 and below
the length. Because the capacity grows by a factor each time, n pushes
cost work proportional to n in total, so each push is constant time on
average ("amortised").</span>
</Formal>

<Examples of="vec">

```rust
let mut v = Vec::new();
v.push(10);
v.push(20);
println!("{:?}", v); // [10, 20]
```

```rust
let mut xs = vec![1.5, 2.5, 4.0];
xs[0] = 9.0;
let last = xs.pop();  // Some(4.0)
xs.get(5);            // None
```

```rust
// from companion/rust/src/chunk.rs
pub struct Chunk {
    pub code: Vec<u8>,
    pub lines: Vec<usize>,
    pub constants: Vec<Value>,
}
```

</Examples>

The first lets Rust work out the element type from the first push (an
`i32`), and `{:?}` prints the whole `Vec`; `v.len()` would now be `2`. The second uses the `vec!`
macro to build one with elements already in it; indexing reads and
writes like an array, `pop` takes the last element off and returns an
`Option`, since the `Vec` might be empty, and `get` is the polite
reading of an index from *Option and Result*. The third is the Rust Drip
compiler's bytecode: three `Vec`s growing in step, one byte of code, one
line number and, now and then, one constant at a time.

## The rule that pays its way

Here is a program that every Rust programmer writes once. It looks
harmless; rustc 1.97 refuses it:

```rust
let mut v = vec![1.0, 2.0];
let first = &v[0];
v.push(3.0);
println!("{}", first); // ✗
```

```text
error[E0502]: cannot borrow `v` as mutable
  because it is also borrowed as immutable
3 |     let first = &v[0];
  |                  - immutable borrow
  |                    occurs here
4 |     v.push(3.0);
  |     ^^^^^^^^^^^ mutable borrow
  |                 occurs here
5 |     println!("{}", first);
  |                    ----- immutable
  |              borrow later used here
```

It is the shared-or-mutable rule from *The borrowing rules*, and the diagram's
last steps showed why it matters here: if this `push` hit the capacity,
the elements would move to a new buffer and `first` would point into
freed memory. Print `first` *before* the push, and the borrow has ended
in time, so the same lines compile. JavaScript never hands you a pointer
into an array's storage, so it cannot have this bug; C hands you one and
does not check, so it has it all the time; Rust hands you one, and
checks.

Reading past the end is the other mistake, and Rust stops the program
rather than reading whatever memory is there:

```text
thread 'main' (32218) panicked at
h3.rs:12:22:
index out of bounds: the len is 1 but
the index is 5
```

## Looping

A loop over a `Vec` makes the same three choices a method makes about
`self`:

<Figure takeaway="Loop over &v to read, &mut v to change, v to use it up." caption="The three loops. The third moves the elements out, so v cannot be used after it; rustc's help for that mistake suggests writing &v.">
  <LoopForms />
</Figure>

A function that only reads should take a slice, `&[f64]`, rather than
`&Vec<f64>`: a `&Vec<f64>` turns into a slice automatically, and the
function then also works on arrays and on parts of a `Vec`. Try all of
it:

<Run id="vec-play" />

<OtherLanguages title="A growable list of numbers">

```rust
let mut xs: Vec<f64> = vec![1.0, 2.0];
xs.push(3.0);
for x in &mut xs { *x *= 2.0; }
println!("{:?}", xs.get(9)); // None
println!("{}", xs[9]);       // panics
```

```ts
const xs: number[] = [1, 2];
xs.push(3);
for (let i = 0; i < xs.length; i++)
  xs[i] *= 2;
console.log(xs[9]); // undefined
xs.push('four' as any); // allowed
```

</OtherLanguages>

They look alike, and both grow with `push`. The differences: a
TypeScript array can be talked into holding anything (the engine then
stores references, as *How JavaScript stores numbers and objects*
showed), while a `Vec<f64>` holds only `f64`s, stored as raw 8-byte
numbers; an out-of-range read gives `undefined` in TypeScript and a
panic (or `None` from `get`) in Rust; and only Rust stops you holding a
reference into the array while it grows.

<Prompts ids={['vec-loops', 'vec-slice-param']} />

<Callout kind="engine" label="Under the hood">
`Vec` is everywhere in drip-rs. The VM's value stack is a `Vec<Value>`,
created with `Vec::with_capacity` so that it rarely needs to grow, and
`push`, `pop` and `peek` are `Vec`'s own `push`, `pop` and indexing; its
call frames are a `Vec<CallFrame>`. Each kind of heap object lives in
its own `Vec`, addressed by index, which the chapter *Arenas and typed
indices* turns into a pattern.
</Callout>

## What you learned

- A **`Vec<T>`** owns a contiguous heap buffer of `T`s, with a length and
  a capacity; `push` grows it, and only amortised constant-time growth
  is promised.
- `v[i]` panics when out of range; `v.get(i)` returns an `Option`.
- You cannot `push` while a reference into the `Vec` is alive, because
  the buffer might move.
- Loop over `&v` to read, `&mut v` to change, `v` to use it up; take
  `&[T]` in functions that only read.

## Counting with names

Viscosity's analysis wants to know which fields a loop touches, and how
often: `x` three times, `vx` once, `y` once. In TypeScript you reached
for a `Map` (*Map and Set*); in Rust it is `HashMap<K, V>`, a map from
keys of type `K` to values of type `V`, built on the hash table you
wrote in *Finding things fast: hash tables*. It is not imported
automatically, so a file that uses it starts with
`use std::collections::HashMap;`.

<Analogy title="a cloakroom">
At a cloakroom you hand over your coat and get a tag; later the tag
gets you your coat back. The cloakroom now holds the coat (you do not
have it any more), and asking with a tag nobody issued gets you a polite
"no coat here", not someone else's coat.
<span slot="breaks">A cloakroom hangs coats in the order they arrive,
and you could walk along the rail; a `HashMap` puts each entry wherever
its key's hash says, so walking through it gives an order that can change
from one run of the program to the next.</span>
</Analogy>

<Analogy extra title="pigeonholes in a staff room">
A staff room has a wall of pigeonholes. Instead of searching every hole
for a teacher's post, there is a rule that turns a name into a hole
number at once (say, from the first letters), so finding the post takes
the same short time however many teachers there are.
<span slot="breaks">Two names can share a hole under that rule, and
then someone has to look a little further; the hash table handles such
collisions for you, and its rule (the hash function) is deliberately
unpredictable, to stop an attacker filling one hole on purpose.</span>
</Analogy>

## Insert, get, entry

```rust
let mut ages: HashMap<String, u32> =
    HashMap::new();
ages.insert(String::from("ada"), 36);
println!("{:?}", ages.get("ada"));
// Some(36)
println!("{:?}", ages.get("alan"));
// None
```

`insert` adds a key and its value, or replaces the value if the key is
already there (and returns the old one, as an `Option`). `get` returns
an `Option<&V>`, because the key may be missing: you get a borrowed look
at the value, which the map keeps. `contains_key`, `remove` and `len`
do what their names say. Counting, however, needs something more:
"if the key is new, start at zero; either way, add one". That is the
**entry API**; step through it:

<EntrySteps client:visible />

`entry(f)` finds the slot for `f`; `or_insert(0)` puts in `0` only if
the slot was empty, and either way returns a mutable reference to the
value, which `*... += 1` follows and changes<Cite id="rust-book-hashmaps" />.

<Callout kind="definition">
A **`HashMap<K, V>`** is Rust's hash table. It owns its keys and its
values. `insert` adds or replaces, `get` returns `Option<&V>`, and
`entry(k).or_insert(v)` returns a mutable reference to the value for
`k`, inserting `v` first if there was none. Its iteration order is
arbitrary, and can change from run to run<Cite id="rust-std-hashmap" />.
</Callout>

<Formal title="A map is a partial function">

```text
m : K ⇀ V
get(m, k) = Some(m(k))  if k ∈ dom(m)
          = None        otherwise
insert(m, k, v) = m[k ↦ v]
```

<span slot="read">A map m from K to V is a partial function: it gives a
value for some keys (its domain, dom(m)) and none for the rest. get of k
is Some of the value when k is in the domain, and None otherwise.
Inserting v under k gives the same map, except that k now leads to v
(the arrow ↦ reads "maps to").</span>
</Formal>

<Examples of="hashmap">

```rust
let mut m = HashMap::new();
m.insert("x", 1);
m.insert("x", 2);   // replaces: Some(1)
m.len();            // 1
```

```rust
let used = ["x", "vx", "x", "y", "x"];
let mut n = HashMap::new();
for f in used {
    *n.entry(f).or_insert(0) += 1;
}
n.get("x");  // Some(3)
```

```rust
// engine/rust/crates/core/src/builder.rs
defs: HashMap<BlockId, HashMap<K, ValueId>>,
```

</Examples>

The first shows that a key appears at most once: the second `insert`
replaces the value and hands back the old one, so the map still has one
entry. The second is the field count, with the counting line from the
diagram. The third is real: the Rust port of Viscosity builds SSA form
(Part VI), and for each block it keeps a map from each variable to the
value that currently defines it, a map of maps.

## The map owns its keys

Insert a `String` key and it moves into the map, exactly as passing it
to a function would. Spot the difference:

```rust
let k = String::from("x");
m.insert(k, 1);
println!("{}", k);          // ✗
m.insert(k.clone(), 1);     // ✓ a copy
```

```text
error[E0382]: borrow of moved value: `k`
5 |     m.insert(k, 1);
  |              - value moved here
6 |     println!("{}", k);
  |                    ^ value borrowed here
  |                      after move
help: consider cloning the value if the
  performance cost is acceptable
```

Inserting a `&str` key instead stores only the borrow, which is fine as
long as the strings outlive the map (the chapter *Lifetimes* is about
exactly that). Reading a missing key with `m["mass"]` panics with `no
entry found for key`, so prefer `get` unless absence is a bug.

## Order is not promised

Print the whole field-count map three times, from three runs of the same
program, and you get three orders:

<Figure takeaway="A HashMap's order changes between runs; a JavaScript Map's never does." caption="Real output of one program run three times with rustc 1.97. The default hasher is randomly seeded each run, so keys land in different slots.">
  <OrderRuns />
</Figure>

<OtherLanguages title="Counting with a map">

```rust
let mut n: HashMap<&str, i32> =
    HashMap::new();
for f in ["x", "vx", "x"] {
    *n.entry(f).or_insert(0) += 1;
}
println!("{:?}", n.get("x")); // Some(2)
```

```ts
const n = new Map<string, number>();
for (const f of ['x', 'vx', 'x']) {
  n.set(f, (n.get(f) ?? 0) + 1);
}
console.log(n.get('x')); // 2
```

</OtherLanguages>

The two read alike, with three real differences. A JavaScript `Map`
iterates in insertion order<Cite id="mdn-map" />; a `HashMap` promises
nothing. TypeScript's `get` returns `number | undefined`, where Rust's
returns `Option<&i32>`. And the TypeScript version looks the key up
twice (`get`, then `set`), while `entry` looks it up once.

The order matters for this book. The Rust port of Viscosity must make
the same decisions as the TypeScript one, message for message, so where
order reaches the output it uses `IndexMap`, from the `indexmap` crate,
a hash map that remembers insertion order. A comment in
`engine/rust/crates/core/src/builder.rs` says why: the incomplete phis
of SSA construction are filled in insertion order, which "decides value
numbering and the order of instructions, exactly as in the TS
reference".

<Prompts ids={['map-order', 'map-indexmap']} />

<Callout kind="engine" label="Under the hood">
std's `HashMap` is a Rust port of Google's SwissTable, using quadratic
probing and SIMD lookups, and by default it hashes keys with SipHash
1-3, randomly seeded, to resist attackers who choose keys that
collide<Cite id="rust-std-hashmap" />. drip-rs does not use it for
Drip's globals and fields: its `table.rs` is the table of *Finding
things fast: hash tables* ported, with linear probing, tombstones, and
storage as a struct of arrays, `keys: Vec<Option<StrRef>>` beside
`values: Vec<Value>`. Its keys are interned strings (*String
interning*) whose handle carries the hash, so the table never runs a
hash function during a lookup at all.
</Callout>

## What you learned

- A **`HashMap<K, V>`** owns its keys and values; `insert` adds or
  replaces, and `get` returns `Option<&V>`.
- `*m.entry(k).or_insert(0) += 1` is the counting idiom: one lookup,
  and a mutable reference to the value.
- Inserting a `String` key moves it into the map.
- Iteration order is arbitrary and changes between runs; use `IndexMap`
  (or sort) when order reaches the output.
