## Every `ps[i].x` has to change

*Generating SoA storage* built the container, but the program does not
know about it yet: every line that touches `ps` must now create the
container, push into it, and read element 7's `x` from the `x` column;
and nothing else may change, because the output is code that a person
will read, diff and debug.

<Analogy title="correcting a printed contract">
You do not retype a forty-page contract to change six words; you strike
them out in pen and write the new ones above, and every other word stays
exactly where it was. If your list of changes says "page 12, line 4",
start from the last page and work towards the first, and the page and
line numbers in the list stay right as you go.
<span slot="breaks">A pen correction can be as messy as you like, and a
person will still read it; a compiler's edits must never overlap, and two
edits on the same words would be a bug, not a judgment call.</span>
</Analogy>

## Edits, not reprinting

While it walks the plan, the emitter in `frontend-js/src/emit.ts`
collects **edits**, each a range of the original text and its
replacement, and then applies them all at once (trimmed):

```js
edits.sort((x, y) => y.start - x.start);
let out = source;
let lastStart = Infinity;
for (const e of edits) {
  if (e.end > lastStart) throw new Error(
    'internal error: overlapping rewrites');
  out = out.slice(0, e.start) + e.text
    + out.slice(e.end);
  lastStart = e.start;
}
```

Line 1 sorts by `start`, largest first, and lines 7 and 8 splice each
edit in. Working from the end backwards, an edit only ever shifts text
that is already done, so every `start` and `end` still points at the
right characters; and an edit that reaches past the previous one's start
would mean the compiler tried to rewrite the same text twice, so it stops
with an internal error rather than guess. Step through a small program:

<RewriteSteps client:visible />

<Callout kind="definition">
**Access rewriting** replaces every use of a transformed collection with
the matching use of its container: `a[i].f` becomes `a.f[i]`, an element
variable becomes an index, and creation and `push` change to match.
Viscosity does it as text edits on the original source, so everything it
does not rewrite comes out byte for byte the same.
</Callout>

There are five kinds of rewrite: creation (`[]` becomes
`new __Vsc_ps()`), push (`push({ x: a, vx: b })` becomes `push(a, b)`),
direct access (`ps[i].x` becomes `ps.x[i]`), element variables and for-of
loops. One program shows them all; this is the real output of
`viscosity build`:

<Examples of="access-rewriting">

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 1000; i++)
  ps.push(i, 0.5);
for (let i = 0; i < ps.length; i++) {
  const p = i;
  ps.x[p] += ps.vx[p];
}
let s = 0;
for (let p = 0; p < ps.length; p++)
  s += ps.x[p];
console.log(s, ps.x[__vsc_bc(ps, 3,
  'x', false)]);
```

</Examples>

Line 1 was `const ps = [];` and line 3 was `ps.push({ x: i, vx: 0.5 })`:
the record literal is taken apart into one argument per field. Line 5 was
`const p = ps[i];`, and is the clever one: `p` used to hold a reference to
an object, and now holds a number, the index, so line 6 (`p.x += p.vx`)
reads and writes the columns at that index; the `+=` itself is left alone,
because a typed-array element is as good a target for `+=` as a property.
Lines 9 and 10 were `for (const p of ps) s += p.x;`, now a counting loop
(`let`, because `p` changes), stopping at the container's `length`. The
last line was `console.log(s, ps[3].x)`, and the index `3` is wrapped in
a bounds check, which the next section explains.

This is correct only because of *Proving it safe*: a `p` that holds `5`
would break `p === q` or `console.log(p)`, so the analysis proved every
use of `p` is a field read or write (anything else is a bailout).

## Keeping the errors the same

In the original, `ps[100]` on a 100-element array is `undefined`, and
`ps[100].x` throws a `TypeError`. After the rewrite, `ps.x[100]` reads a
`Float64Array`, which never throws; worse, the column has spare slots
(the next section explains why), so it quietly returns `0`. So every
access is checked unless the analysis proved it in bounds, and the proof
is a simple pattern: the index is the loop's counter, and the condition
is `i < ps.length`. Any other index goes through a helper the emitter
adds to the file:

<BoundsSteps client:visible />

`i >>> 0 === i` holds only for whole numbers from 0 up (it reads `i` as
an unsigned 32-bit integer<Cite id="mdn-unsigned-right-shift" />), and
the index must then be below the *length*. Otherwise the helper throws
the error the original would have thrown, in V8's wording (the
specification leaves the message to the engine<Cite id="ecma262" />, and
Viscosity's differential tests run in Node and compare errors exactly).

<Prompts ids={['rw-bc']} />

<More title="More: a slip in a loop condition, error messages, late stores, and ISPC">

A small slip in a loop condition shows the rule at work:

```js
for (let i = 0; i < ps.length; i++)
  s += ps[i].a;
// → s += ps.a[i];   (proven)
for (let i = 0; i <= ps.length; i++)
  s += ps[i].a;
// → s += ps.a[__vsc_bc(ps, i, 'a',
//        false)];
```

With `<` the counter never reaches the length, so the access is left
bare; with `<=` nothing is proven, every access pays for the check, and
the last trip throws exactly as the original does. The run below shows
the same messages before and after; `--bounds assume` drops the checks,
for programs you trust never to go out of range.

<Run id="messages" />

A compound update such as `ps[k].x += 1` passes `false` (a read), because
the original fails on the read first. A write whose right-hand side runs
code, as in `ps[3].x = (more(), 77)` where `more()` pushes, needs more
care: a plain `ps.x[3] = …` fetches the column before `more()` runs, so
if the container grows the store lands in the old, discarded column. The
emitter writes `__vsc_set(ps, 'x', __vsc_bk(ps, 3), (more(), 77), 'x')`
instead: check the index without throwing yet, run the right-hand side,
and only then throw, or store into the column as it is now (the corpus
file `write_rhs_grows.js`).

ISPC makes the same rewrite inside the compiler: for an `soa<8>` array
you keep writing `pts[10].x`, and the generated code finds the block and
the slot<Cite id="ispcdocs" />. Viscosity does it in the source, so you
can read exactly what will run.

<Formal title="The rewrite rules">

```text
⟦ a[i].f ⟧         =  a.f[ ⟦i⟧ ]
⟦ const p = a[i] ⟧ =  const p = ⟦i⟧
⟦ p.f ⟧            =  a.f[p]
⟦ a.push({f: v…}) ⟧ = a.push(⟦v⟧, …)
```

<span slot="read">The double brackets ⟦ ⟧ mean "the rewrite of". The
rewrite of a[i].f is a.f indexed by the rewrite of i (the index may
itself contain an access to rewrite). A variable set from a[i] is set
from the index instead, and p.f, for such a p, becomes a.f[p]. A push of
a record literal becomes a push of its rewritten values, in field
order.</span>
</Formal>

</More>

## Capacity and length

A `Float64Array` made with `new Float64Array(16)` has 16 slots for ever:
its length is fixed when it is made, it starts out full of
zeros<Cite id="mdn-typedarray" />, and it has no `push`. So the container
keeps two numbers, `cap`, how many slots each column has, and `length`,
how many of them hold real elements. Step through a column filling up (it
starts at 4 to stay small; Viscosity's starts at 16):

<CapacitySteps client:visible />

<Callout kind="definition">
A collection's **capacity** is the number of slots it has allocated; its
**length** is the number in use. The slots from `length` up to
`capacity` are spare: they exist in memory, but they are not elements.
When a push finds `length === capacity`, the collection **grows**: it
allocates bigger storage and copies the old elements into it.
</Callout>

<Examples of="capacity">

```js
// after 17 pushes of (i, 1):
// ps.length 17, ps.cap 32
// ps.x[20] is 0: a spare slot
```

</Examples>

The container started with room for 16; the 17th push found every slot
used and grew it to 32, so now 17 slots hold elements and slots 17 to 31
hold zeros that no element owns. That is exactly why the bounds check
compares an index with `length`, never with the capacity: a bare
`ps.x[20]` would quietly read one of those zeros.

The generated `push` checks `n === this.cap` and, if so, calls `grow()`,
which doubles `cap` and, for each typed column, makes a new
`Float64Array` of that size, copies the old values into its start with
`set`<Cite id="mdn-typedarray-set" />, and swaps it in (the garbage
collector reclaims the old one). Plain-array columns are left alone: a
plain array lengthens by itself.

## Why doubling

Growing could add a fixed number of slots, say 16, each time, which
sounds thriftier. Count the copies instead:

<Figure caption="Copies made while pushing 400 elements, from capacity 16. Adding 16 slots curves up; doubling is a low staircase that never crosses the dashed line 2n." takeaway="Doubling: fewer than two copies per push, however long the list gets.">
  <CopyCurve />
</Figure>

When doubling, each grow copies more values than all the earlier grows
put together (16, then 32, then 64), so the total is always less than the
final capacity, which is less than twice the length. Adding 16 copies 16,
32, 48, 64 and so on, a sum that grows with the *square* of the length.

<Callout kind="definition">
**Amortised growth** spreads the cost of the rare, expensive grows over
all the cheap pushes. With doubling, n pushes copy fewer than 2n values
in total, so one push costs a constant amount *on average*, even though
an unlucky push copies everything. Growing by a constant amount instead
makes n pushes cost time proportional to n².
</Callout>

<Examples of="amortized-growth">

```js
// pushes   doubling   adding 16
//   1000       1008       31248
//  10000      16368     3120000
// 100000     131056   312450000
```

</Examples>

These are real counts (the run in the dropdown below), from a starting
capacity of 16: at 100,000 pushes, doubling has copied 1.3 values per
push and adding 16 over 3,000, and the gap keeps widening, because one
grows like n and the other like n².

<Formal title="Doubling, summed">

```text
copies(n) = 16 + 32 + … + 2ᵏ·16
          < 2ᵏ⁺¹·16 ≤ 2n
```

<span slot="read">The copies made while pushing n elements are 16, then
32, and so on up to the last grow, 2 to the k times 16, which is less
than n. Each power of two is bigger than all the ones before it put
together, so the sum is less than the next power, 2 to the k + 1 times
16, which is at most 2n. Divided by n: fewer than two copies per
push.</span>
</Formal>

A car park has 100 spaces and, at the moment, 63 cars. The spaces are

## What you learned

- **Access rewriting** turns `a[i].f` into `a.f[i]` as edits applied back
  to front; element variables become indexes, and for-of becomes a
  counting loop, which the safety analysis makes correct.
- Accesses not proven in bounds go through `__vsc_bc`, which throws the
  same `TypeError` as the original.
- A container has a **capacity** and a **length**; spare slots hold
  zeros, so checks compare with length.
- **Amortised growth**: doubling copies fewer than 2n values for n pushes;
  growing by a constant is quadratic.
