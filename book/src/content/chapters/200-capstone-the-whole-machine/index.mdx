## Where Track B started

Chapter 121's first program was three lines:

```rust
fn main() {
    println!("Hello, Drip!");
}
```

That chapter's argument was about memory. Viscosity exists because
JavaScript gives you no say over layout, so it has to trick the engine
into a struct of arrays; Rust lets you decide, with a strict inspector
checking the plans. Eighty chapters later, both of the book's large
programs exist in both languages.

<Callout kind="intuition">
A carpenter's apprentice builds a chair with the master watching, then
builds the same chair again alone, in a harder wood. The second chair
isn't more useful than the first. It's the proof that the apprentice
knows why every joint is where it is.
</Callout>

## What you built

**Drip, three times.** A tree-walking interpreter in TypeScript (Part
III), a bytecode VM in TypeScript (Part IV), and `drip-rs`, the same VM
design in Rust (Part X): typed arena handles instead of pointers, a
mark-sweep collector with explicit roots, `#![forbid(unsafe_code)]`,
and the shared corpus as its judge.

**Viscosity, twice.** The TypeScript reference (Parts VII and VIII),
and its Rust port (Part XI): VIR in arenas, the plugin trait, oxc for
parsing, the SSA builder and dataflow framework, the analyses, the
cost model, the code generators for SoA and AoSoA, `explain` with code
frames, and PGO.

**Two languages.** The JavaScript plugin and the Python plugin both
lower to the same VIR, so the analyses and the planner never see
syntax. Both exist in both engines.

**Three ways to run it.** A native CLI (chapter 197), the same engine
as WebAssembly in an npm package (189, 190), and that WebAssembly
inside this book's Playground (191).

Every one of these is checked against another. drip-rs runs the corpus
the TypeScript VM runs. The Rust engine reproduces every stored output
of the TypeScript engine byte for byte, and the fuzzer keeps generating
programs to compare them on. The compiled programs are run against
their originals. That chain of checks is what makes "the same machine,
in Rust" a claim you can test rather than a hope.

Read the stages against the book. oxc parsed it (chapter 172) and the
plugin lowered it to VIR in SSA form, where line 6's `for…of` became a
phi, a length check, an `index.get`, two `field.get`s and a
`field.set` (173, 176). The analyses saw only VIR: they found two
collections (178), three numeric fields each (179), and an escape for
`qs` when `qs[0]` was passed to `console.log` (180). They found the
two loops over `ps` and their fields (181), and proved both of its
indexes in bounds. The cost model wrote its reasons as it decided (182),
the emitter turned `ps` into three `Float64Array` columns (183), and
`explain --frames` put carets under `qs[0]` (185). Both programs print
`509500 { x: 0, vx: 1, hp: 3 }`. The TypeScript CLI prints the same
report, byte for byte.

Run it yourself, on the Rust engine compiled to WebAssembly (the toggle
switches to TypeScript, and the decisions don't change):

## What is still open

An honest capstone lists what isn't done. Some items are chores; some
are research.

- **The release is 0.0.1, with no changelog** (chapter 198). When
  this chapter was written nothing was published. On 2026-11-02 the
  npm packages went out, then the six crates, so
  `cargo install viscosity-cli` works now. The commit history is still
  the only record of what changed.
- **The Rust port has gaps.** It rejects TypeScript input (the reference
  strips types with sucrase, and copying sucrase's exact output is out
  of scope), and its syntax errors are worded by oxc, not acorn. Neither
  engine profiles Python programs.
- **The cost model can't see the engine.** It decides from size and
  access patterns, with a 64-element threshold, and the matrix showed
  the same output gaining a lot on V8 and nothing on JSC for heat. Why
  is still a hypothesis without an engine trace (chapter 199).
- **Many ordinary programs are refused**, as chapter 118 listed: sorting,
  classes as records, varying shapes, exported arrays. Hot/cold
  splitting is by type only.
- **Every version emits source code.** There is no WebAssembly back end
  for the compiled programs (chapter 117); WebAssembly runs the
  compiler, not its output.
- **Drip's VMs share a limit**: 256 constants per chunk, which is why
  `string_equality` runs only on the tree-walker.

## Going further

If you want to keep going, each of these starts from code you have read:

- **Confirm or refute the heat hypothesis.** Take an engine trace of
  heat's objects on V8 (chapter 72 shows how to watch the engine work),
  and see whether its fields really are boxed doubles.
- **Teach the cost model about engines.** Run the matrix on more
  machines and engines, and see whether a per-engine threshold would
  have predicted Bun's results.
- **Add a third language.** The plugin trait (chapter 171) is the whole
  contract. The Python plugin shows what the minimum looks like.
- **Grow the subset.** Pick one refusal from chapter 118, make the
  analysis prove it safe, and let the fuzzer tell you whether you were
  right (`node scripts/fuzz.mjs --count 20000`).
- **Fix the small things**: the wasm smoke test in CI, a changelog, a
  Python fuzzer (chapter 188).

<Callout kind="engine" label="Under the hood">
Building a language twice, simply and then fast, and the second time in a
lower-level language, is the shape this book borrowed from *Crafting
Interpreters*<Cite id="nystrom2021" />. Track B took it one step
further, to an optimizing compiler, and added a rule that book didn't
need: the second implementation must agree with the first on every
output, not just every result. Holding to it, porting and then
fuzzing turned up fifteen bugs, listed in `engine/rust/README.md` and
fixed in both engines. Five were soundness bugs, where the compiled
program would have behaved differently from the original.
</Callout>

## What you learned

- The book built **Drip three times** and **Viscosity twice**, for two
  languages, and runs the Rust engine natively, in Node and in the
  browser.
- Every implementation is **checked against another**: the shared
  corpus, byte-identical fixtures, the fuzzer, and original-versus-compiled
  runs.
- One program passes through **parse, lower, analyze, plan, emit and
  explain**, and each line of its output can be traced to a chapter.
- What is **open** is known and written down: no changelog, the
  port's gaps, an engine-blind cost model, refused programs, no
  WebAssembly output.
- **Mastery** is being able to build it again, and to say how you would
  know it works.

That is the end of the book. It started from a question about where an
array of objects sits in memory, and every chapter since has been one
step towards being able to answer it with a tool you understand all the
way down. The code is in the repository, the numbers are in its result
files, and the rough edges are listed above. Fifteen minutes at a time,
you built the whole machine.
