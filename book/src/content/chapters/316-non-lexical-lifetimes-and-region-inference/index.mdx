## Loans that last too long

The checker from the last chapter never ends a loan, so it rejects
this harmless program, where `r` is finished with before `m` is made:

```text
let v = new
let r = &v
use r
let m = &mut v   # our checker: E0502
use m
```

Before NLL (proposed in 2017), rustc worked almost like that: a
reference stored in a variable kept its loan until the end of that
variable's **lexical** scope (the block it was declared in, a fact you
can read off the text), so code like this had to be wrapped in extra
braces to make the borrow end sooner<Cite id="rfc2094-nll" />. The fix,
**non-lexical lifetimes** (NLL), ends a loan where the reference is
last used<Cite id="rust-book-borrowing" />, and rustc 1.97 compiles the
Rust version of the program above without complaint.

<Analogy title="a hired car">
Under the lexical rule you hire a car for the whole week, even though
you only drive it on Monday; nobody else can hire it until Sunday night.
Under NLL the hire ends when you drop the keys back, so the car is free
again on Tuesday morning.
<span slot="breaks">A hire company knows when you return the keys
because it sees you do it; the compiler has to predict the last use
from the text, for every path, before the program runs.</span>
</Analogy>

<Analogy title="a library book">
A lexical loan is a book you must keep until the end of term, read or
not; a non-lexical one goes back the moment you have read the last page
you will ever need, so the next student can take it out.
<span slot="breaks">A student may change their mind and want the book
again; a reference whose last use has passed is never read again, which
is exactly what makes ending the loan safe.</span>
</Analogy>

## Liveness says where a loan ends

The question "may this reference still be used?" is one you have
answered before: it is **liveness** (chapter 204). A variable is live
at a point if the value it holds there may be used later, on some
path<Cite id="rfc2094-nll" />, and liveness is a backward dataflow
analysis over the control-flow graph, so it handles branches and loops
for free. NLL gives each reference a **region**: the set of points
where it is live. A loan is in force exactly at the points of its
reference's region, and the ledger from last chapter is checked only
against the loans in force at each point.

<Callout kind="definition">
**Non-lexical lifetimes** make the lifetime of a borrow a set of points
in the control-flow graph (where its reference may still be used)
rather than a block of the source text. A loan is in force only at
those points, so it ends after the last use of its reference on each
path, even in the middle of a block.
</Callout>

<Examples of="non-lexical-lifetimes">

```rust
let first = &v[0];
println!("{first}");  // last use
v.push(3);            // ok
```

```rust
let mut p = &a;
if c {
    println!("{p}");  // p dead below
    p = &b;
}
println!("{p}");
```

```rust
match map.get_mut(&k) {
    Some(x) => *x += 1,
    None => { map.insert(k, 0); }
}
```

</Examples>

The first is the push example from last chapter with two lines
swapped: `first` is last used before the push, so its loan has ended
and rustc accepts it. The second is the NLL RFC's own example: inside
the `if`, `p` is dead between its use and its reassignment, because the
value it holds there (`&a`) is never read again, even though the name
`p` is; so the loan of `a` does not hold on that stretch. In the third,
the reference `x` is live only on the `Some` path, so on the `None`
path the map is no longer borrowed and `insert` is allowed; the RFC
lists this as problem case #2, which lexical lifetimes
rejected<Cite id="rfc2094-nll" />.

## Copies stretch a region

Liveness alone is not enough, because a loan can travel. Here `r` is
last used on line 3, where it is copied into `r2`, but the loan it holds
lives on inside `r2`:

```text
error[E0506]: cannot assign to `x`
  because it is borrowed
3 |  let r = &x;
  |          -- `x` is borrowed here
4 |  let r2 = r;
5 |  x = 6;
  |  ^^^^^ `x` is assigned to here but
  |        it was already borrowed
6 |  println!("{r2}");
  |             -- borrow later used here
```

So every copy `let r2 = r` at point P adds an **outlives constraint**,
written `'r: 'r2 @ P`: the region of `r` must contain every point of
the region of `r2` that can be reached from P. **Region inference**
finds regions that satisfy all of these at once, and the method is the
one from chapter 196: start each region at its live points, apply every
constraint, and repeat until a whole pass changes nothing. The RFC
describes exactly this fixpoint, with each region starting empty and
growing "until they are big enough to satisfy all
constraints"<Cite id="rfc2094-nll" />; in rustc, the regions in a
function body become inference variables, a second type check over MIR
collects the constraints, and a solver propagates
them<Cite id="rustc-dev-guide-region-inference" />.

<RegionSteps client:visible />

<Callout kind="definition">
**Region inference** computes, for every borrow and every reference,
the smallest set of program points where it must be valid. It collects
two kinds of constraint (a region contains each point where its
reference is live, and `'a: 'b @ P` wherever a reference flows from a
place of region `'a` into one of region `'b`) and solves them by
growing the sets to a fixpoint.
</Callout>

<Formal title="Region constraints">

```text
(L : {P}) @ P      if L is live at P
('a : 'b) @ P      for a copy at P
'a ⊇ { Q ∈ 'b | Q reachable from P }
```

<span slot="read">The first rule says that if lifetime L is live at
point P, then L must contain P. The second says a copy at P makes 'a
outlive 'b from P on. The third says what that means: 'a contains every
point Q of 'b that can be reached from P.</span>
</Formal>

<Examples of="region-inference">

```text
let r = &x     # 'r ⊇ live(r)
let r2 = r     # 'r : 'r2 @ here
```

```text
let a = &x
let b = a      # 'a : 'b
let c = b      # 'b : 'c, so 'a ⊇ 'c
```

```rust
fn first<'a>(xs: &'a [i32]) -> &'a i32 {
    &xs[0]
}
```

</Examples>

In the first, `r`'s region is where `r` is live plus, through the
constraint, wherever `r2` is live afterwards. The second is the chain
in the step-through: constraints compose, which is why one pass is not
enough. The third has a named region, `'a`, in a function signature:
inside the body it stands for "some points in the caller", and the
returned reference must outlive it, so the caller's borrow of `xs`
lasts as long as the result is used.

## Where NLL stops

Some safe programs are still refused. This one returns a reference out
of one branch and inserts in the other (RFC problem case #3):

```rust
match map.get_mut(&k) {
    Some(v) => v,
    None => {
        map.insert(k, String::new());
        map.get_mut(&k).unwrap()
    }
}
```

rustc 1.97 says `error[E0499]: cannot borrow *map as mutable more than
once at a time`, because returning `v` forces the loan's region to
cover the caller's `'r`, and region constraints say *that* a loan flows
into `'r` but not *on which path*. Issues like this were deferred from
NLL to **Polonius**, a new formulation of the borrow checker in terms
of facts and rules, like the Datalog of the chapter on function summaries, for which this example
is the motivating case<Cite id="polonius-update-2023" />.

## What you learned

- **Non-lexical lifetimes** end a loan at the last use of its
  reference, found by **liveness** over the control-flow graph.
- A **region** is a set of program points; copies add **outlives
  constraints** `'a: 'b @ P`.
- **Region inference** solves the constraints by growing sets to a
  **fixpoint**; what NLL still rejects is the target of Polonius.
