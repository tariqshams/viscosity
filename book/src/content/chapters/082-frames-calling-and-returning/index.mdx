## A loop cannot call itself

In the tree-walker, a Drip call was a chain of TypeScript calls, so
*where to go back to* and *what each caller was in the middle of* lived
in TypeScript's own frames, on the host's call stack (*Return, the host
stack and closures*). The VM is one `for (;;)` loop reading bytes. When
`f` calls `sq`, the loop must remember where it was in `f`, read `sq`'s
bytecode instead, and later carry on in `f` from the byte after the
call; and if `sq` calls something else, remember *that* too. Since the
loop never calls itself, all of this has to be data the VM keeps.

First, the compiler. A function body is compiled by a fresh, nested
function compiler into the bytecode of a new function object, whose
`locals` array has slot 0 reserved; each parameter is declared as an
ordinary local, so parameters take slots 1, 2, and so on. The finished
function becomes a *constant* of the code around it, pushed at run time
by `closure` (*Upvalues: capturing and closing* explains the name).

<Analogy title="bookmarks in a pile of books">
You are reading a novel when a footnote says "see the atlas, page 40".
You put a bookmark in the novel and open the atlas, which in turn says
"see the dictionary"; another bookmark, another book. When you finish
in the dictionary, you go back to the most recently bookmarked book,
the atlas, exactly where you left it, and later to the novel.
<span slot="breaks">Each book is in the pile once; with recursion the
same function can have many frames at the same time, each with its own
bookmark in the same bytecode. And you could pick any book up; the VM
only ever runs the newest frame.</span>
</Analogy>

## Call frames

Each call the VM is in the middle of has a record in `vm.ts`:

```ts
interface CallFrame {
  closure: ObjClosure;
  ip: number;
  slots: number;
}
```

`closure` is the function being run, `ip` is this call's own bookmark
in that function's bytecode, and `slots` is the stack index where its
slots begin. The VM keeps the frames in an array, newest last, and runs
the newest.

<Figure takeaway="Every call in progress has its own ip." caption="The deepest moment of print f(3), where f calls sq. Three frames exist; each ip points into a different function's bytecode, at the next instruction that call will run.">
  <FramesFigure />
</Figure>

`call n` finds the callee `n` places below the top of the stack and
hands it to `callValue`, which checks what kind of value it is; a Drip
function ends up here (the arity message shortened to `ARITY_MSG`):

```ts
private call(closure: ObjClosure,
    argCount: number): void {
  const fn = closure.fn;
  if (argCount !== fn.arity)
    this.runtimeError(ARITY_MSG);
  if (this.frames.length === FRAMES_MAX)
    this.runtimeError('stack overflow');
  this.frames.push({ closure, ip: 0,
    slots: this.sp - argCount - 1 });
}
```

That is the whole call: two checks and one record pushed. The dispatch
loop then runs `reload()`, which refreshes its cached `frame`, `code`
and `constants` from the newest frame, so the next byte it reads is the
callee's first. `return` undoes it, popping the frame, so the caller
carries on from its own saved `ip`; when the script itself returns, the
frames array is empty and the program is over. A native function such
as `len` gets no frame at all: `callValue` runs it at once and pushes
its result.

<Callout kind="definition">
A **call frame** is the VM's record of one call that has started but
not yet returned: which function is running, its own instruction
pointer, and where its slots begin on the value stack. The frames
live in an array, newest last; a call pushes one and a return pops
one, and the VM always runs the newest.
</Callout>

The companion disassembler lists the script, then `add`'s own bytecode
(the real program puts `return` on its own line; the script's first two
instructions, which push the function and store it in the global `add`,
are left out). The script pushes the callee, then the two arguments,
then runs `call 2`, which checks that `add` takes 2 and pushes a frame
with `ip` 0 in `add`'s bytecode. Inside, `a` and `b` are only slots 1
and 2; `add` adds them, and `return` pops the frame and leaves `3`
where the callee was, so the script's own `ip`, saved at 17, runs
`print`.

<More title="Stack traces, and a trace three calls deep">

Because frames are data, `runtimeError` can walk them, newest first,
and print one `at` line for each: the line of byte `ip - 1` (each `ip`
has already moved past its instruction, which for a waiting caller is
its `call`) and the function's name. A recursion with no way out stops
when a new call would make more than 256 frames, with `runtime error:
stack overflow` and 256 `at` lines; that limit, `FRAMES_MAX`, is the
VM's own choice, not the host's. The runnable one stops with `c() takes 0 arguments but got 2` and four `at`
lines, `fn c`, `fn b`, `fn a` and `script`: the arity check fails
*before* a frame for the new call is pushed, so the innermost line is
the call inside `c`.

<Run id="trace" />

This is the call stack<Cite id="mdn-call-stack" /> made explicit:
one entry per call in progress, added when a function is called and
removed when it returns, with a fixed limit beyond which the program
stops. The tree-walker borrowed its host's call stack for the calls
themselves; the VM keeps the whole thing as data, in one array.

</More>

## The frame pointer: one stack, many windows

In the tree-walker, calling `add(1, 2)` made a fresh environment and
copied each argument into it under its parameter's name. Now look at
the VM's stack at the moment `call 2` runs:

```text
index:  0       1        2   3
value:  script  fn add   1   2
```

Inside `add`, slot 0 is the function, slot 1 is `a` and slot 2 is `b`;
so if `add`'s slot 0 is *declared* to be index 1, the argument `1` is
already sitting in slot 1 and `2` in slot 2. Nothing is copied, renamed
or allocated: the call records that one number, as
`slots: this.sp - argCount - 1`, and `load.local` reads
`stack[frame.slots + readByte()]`, so the same bytes of a function work
for every call of it, each through its own window.

<Callout kind="definition">
A frame's **frame pointer** (`slots` in Drip's VM) is the stack index
of its slot 0. Every local of that call is found relative to it:
slot *i* lives at `stack[slots + i]`. Because `call` sets it to the
callee's own position, the callee and its arguments become slots 0,
1, 2, and so on, of the new frame without being moved.
</Callout>

<Figure takeaway="One instruction, a different cell in every call." caption="Inside fib(2), which has called fib(1). load.local 1 means 'my n'; the frame pointers, 1 and 3, turn it into stack index 2 in one call and 4 in the other.">

Returning cuts the stack back to the window (from `vm.ts`):

```ts
case Op.Return: {
  const result = this.pop();
  this.closeUpvalues(frame.slots);
  this.frames.pop();
  if (this.frames.length === 0) {
    this.sp = 0;
    return;
  }
  this.sp = frame.slots;
  this.push(result);
  reload();
  break;
}
```

`frame` is still the frame that is finishing. Setting `sp` to its
`slots` throws away the callee, its arguments, its locals and any
temporaries in one assignment, and the result is pushed exactly where
the callee was (`closeUpvalues` rescues captured locals first, as
*Upvalues: capturing and closing* explains). For a method, slot 0 holds
the receiver rather than the function: the compiler names that local
`self`, and the VM writes the receiver over the callee's position
before it pushes the frame (for `new P(4)`, the new instance replaces
the class the same way, before `init` runs).

<Examples of="frame-pointer">

```text
print f(3), where f(y) calls sq(y):
f:  slots = 3 − 1 − 1 = 1, y at 2
sq: slots = 5 − 1 − 1 = 3, x at 4
```

</Examples>

When `print f(3)` calls `f`, the stack holds `script`, `fn f` and `3`,
so `f`'s window starts at 3 − 1 − 1 = 1, with `y` at index 2. When `sq`
is called the stack holds five values (`script`, `fn f`, `3`, `fn sq`,
`3`), so `sq`'s window starts at 3, and its `x` at index 4 is the copy
of `y` that `f` pushed. When `sq` returns, `sp` drops to 3 and its
result sits where `fn sq` was.

## What you learned

- A **call frame** records the running function, its own `ip` and
  where its slots begin; `call` checks arity and depth and pushes one,
  `return` pops it.
- The **frame pointer** is the index of a call's slot 0, `sp − argc −
  1`, so arguments are already in place; `return` sets `sp` back to it.
