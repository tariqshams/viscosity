## Too many ways to say one thing

Viscosity wants to turn your arrays of objects into struct-of-arrays
storage, the layout that won in *AoS vs SoA, measured*; however, before
it can, it has to answer questions about your program, such as which
fields of a particle are read, whether a particle is handed to code we
cannot see, and which loops are hot. Try answering the first question
by reading source. Every one of these lines adds `vx` to `x`:

```js
p.x += p.vx;
p.x = p.x + p.vx;
p["x"] = p["x"] + p.vx;
const { vx } = p; p.x += vx;
```

An analysis over source text, or even over the syntax tree, needs a
case for every spelling, and again for every new question; so compilers
translate the program once into a form with far fewer cases, and ask
every question there.

<Analogy title="a bank statement">
Your receipts come in every shape: printed, handwritten, emailed, a
photo of a till slip. To answer "how much did I spend on food this
month?" from the receipts you would need to understand each format;
your bank statement lists every payment in the same columns, so the
same question becomes one pass down a list.
<span slot="breaks">A statement throws away detail (what you actually
bought). An IR may not lose anything that changes what the program
does; where it cannot describe something, it says so out loud, as we
will see with `opaque`.</span>
</Analogy>

Step through one small function in four forms, and watch what each
makes easy and what it hides:

<FourForms client:visible />

In the IR, each instruction does one small thing and names its result
(`%2`), and the control flow, which the tree only implied, is written
down as jumps between labelled blocks.

<Callout kind="definition">
An **intermediate representation** (**IR**) is the form a compiler
keeps a program in while it analyses and transforms it, between the
source language and the target. A good IR is **explicit** (values have
names and control flow is spelled out), **small** (few kinds of
instruction, so each analysis has few cases) and independent of how the
source happened to be written. Translating into a lower-level form like
this, with fewer kinds of construct and more explicit steps, is called
**lowering**.
</Callout>

<Examples of="ir lowering">

```text
func m(%0):        // p.x += p.vx;
  b0:
    %0 = param
    %1 = field.get %0 .x
    %2 = field.get %0 .vx
    %3 = binop + %1, %2
    field.set %0, %3 .x
    return
```

</Examples>

This is real VIR, Viscosity's IR, for `function m(p) { p.x += p.vx; }`,
printed by `printFunc` in `packages/core/src/vir.ts`. The parameter `p`
is the value `%0`, and the compound `+=` became two field reads, one
addition and one field write; `p.x = p.x + p.vx` lowers to the same
four lines, so the spelling is erased, and "which fields are read?" is
answered by looking for `field.get`. Real differences are kept, though:
`x++` gets an extra `unop +` (convert to a number), because with
`x = "5"` it gives `6` where `x += 1` gives `"51"`; and anything not
modelled, like `delete o.x`, becomes `opaque`, which tells every
analysis "this might do anything with its inputs".

<More title="More: the lowering code, and ++ against += running">

From `packages/frontend-js/src/lower.ts`, trimmed:

```ts
case 'AssignmentExpression': {
  const t = readTarget(e.left, e);
  const op = e.operator.slice(0, -1);
  const v = fb.emit('binop',
    [t.get(), expr(e.right)],
    { operator: op });
  t.set(v);
  return v;
}
```

`readTarget` works out what is assigned to (a variable or a field) and
returns a `get` and a `set`; `slice(0, -1)` turns `"+="` into `"+"`;
`fb.emit` writes one `binop`, and `t.set(v)` writes the result back.
After this, no later pass ever sees `+=`.

<Run id="plus-plus" />

VIR's `Op` union names records, fields, indexing and `push` as
instructions of their own, because Viscosity cares about arrays of
objects, and nothing in it says "JavaScript": each language's front end
lowers to VIR, and every analysis after that sees only VIR. V8 makes a
similar split: Sparkplug turns Ignition bytecode into machine code in
one pass with no IR of its own<Cite id="v8-sparkplug" />, which is why
it compiles fast and optimises little, while the analyses of a
compiler's middle end run on an IR<Cite id="coopertorczon2022" />.
Viscosity's idea itself comes from research done inside an optimising
JIT<Cite id="makor2022" />.

</More>

## One operation per line

Drip's VM ran `1 + 2 * 3` as push, push, push, multiply, add, and the
`6` never had a name; but an optimiser wants to say "the product is the
constant 6" or "nobody uses this result", and each sentence needs to
*point at* the product. Three-address code names every value:

```text
t1 = 2 * 3
t2 = 1 + t1
```

Lowering an expression is the tree-walker's recursion, except that it
emits instructions rather than computing values, children first,
because an instruction needs names for its inputs:

<TacSteps client:visible />

<Callout kind="definition">
**Three-address code** is an IR whose instructions each perform one
operation on at most two operands and put the result in a named
destination, `x = y op z` (two inputs and an output: three addresses).
Copies, one-operand operations, jumps and conditional jumps complete
the set. A **temporary** is a name the compiler creates for an
intermediate value, the result of one instruction; in VIR every value
is one, written `%n` and unique in the whole module.
</Callout>

<Examples of="three-address-code temporary">

```text
func f(%0):            // let t = a;
  b0:                  // let u = t * 2;
    %0 = param         // return u + t;
    %1 = const 2
    %2 = binop * %0, %1
    %3 = binop + %2, %0
    return %3
```

</Examples>

Your variables have disappeared. `let t = a` produced no instruction at
all, because the front end only remembers that `t` now means `%0`, so
when the code reads `t` it gets `%0`. The literal `2` *is* an
instruction, `%1 = const 2`, because constants are values and get names
too. Because inputs are names, "who uses `%0`?" is a lookup:
`buildUses` files every instruction under each of its `args`, which
here gives `%2` and `%3`.

## Basic blocks and the graph between them

Here is a classic loop: halve `n` if it is even, otherwise triple it
and add one, until it reaches 1.

```js
function g(n) {
  while (n > 1) {
    if (n % 2) n = 3 * n + 1;
    else n = n / 2;
  }
  return n;
}
```

As one flat list with jumps, "what can run just before this line?"
means searching the whole list; so compilers cut code into straight
runs and draw the jumps between them as arrows.

<Callout kind="definition">
A **basic block** is a maximal sequence of instructions with one entry
and one exit: control enters only at the first instruction and leaves
only after the last, so if the first runs, they all run, in order. A
**control-flow graph** (**CFG**) has a node for each block and an edge
A → B whenever B can run immediately after A; B is a **successor** of
A, A is a **predecessor** of B, one block is the **entry**, a block is
**reachable** if some path leads to it from the entry, and a cycle is a
loop.
</Callout>

Viscosity's lowering builds the blocks directly as it walks the tree
(an `if` makes a block per branch and one where they meet), and VIR's
types make "one exit per block" impossible to get wrong:

```ts
interface Block {
  id: BlockId;
  insts: Inst[];
  term: Terminator;
  preds: BlockId[];
}
type Terminator =
  | { kind: 'br'; target: BlockId }
  | { kind: 'condbr'; cond: ValueId;
      then: BlockId; else: BlockId }
  | { kind: 'return';
      value: ValueId | null }
  | { kind: 'throw'; value: ValueId }
  | { kind: 'unreachable' };
```

The instructions in `insts` never jump; exactly one **terminator** in
`term` can (`br` to `target`, `condbr` to `then` or `else`, or leave the
function). So `successors` in `cfg.ts` is one expression on `term`, and
when the builder sets a terminator, `terminate` pushes the block onto
each successor's `preds`. Step through it for `g`:

<PredSteps client:visible />

<Examples of="basic-block cfg">

```text
b1:  ; preds b0 b3
    %10 = binop > %8, %9
    condbr %10, b2, b4
b2:  ; preds b1
    %12 = binop % %8, %11
    condbr %12, b5, b6
b3:  ; preds b7
    br b1
b7:  ; preds b5 b6
    br b3
```

</Examples>

These are four of the eight blocks of the real VIR for `g`, trimmed
(the `phi` lines are left out for now), with each block's predecessors
in a `; preds` comment. b1 is the loop test, and it has two
predecessors: b0, the way in, and b3, the end of each pass. b2 tests
the parity and branches to b5 or b6, the two arms of the `if`, which
both jump to b7, where they meet; b7 jumps on to b3, which jumps back to
the test: that ring is a cycle, and so a loop. (b3 and b7 hold only a
`br`; the lowering always makes them, which keeps it mechanical.)

<More title="More: unreachable blocks, and finding blocks in a flat list">

Code after a `return` is lowered into a fresh block that no terminator
points at, so no path from the entry reaches it, and a compiler can
drop it. (The entry has no predecessors either, and a block whose
predecessors are all unreachable is unreachable too, so the safe test
is a search from the entry.)

A compiler that starts from flat code (bytecode, or machine code read
back from a file) must find the blocks itself. It marks the
**leaders**, where a block must start: the first instruction, every
jump target, and every instruction straight after a jump or a `return`.
Each block runs from one leader up to, but not including, the next. A
call in the middle of a block does not end it, because the call comes
back to the next instruction. Here is `g` as a flat list, with leaders
0, 2, 4, 7 and 9:

```text
0  t1 = n > 1
1  ifnot t1 goto 9
2  t2 = n % 2
3  ifnot t2 goto 7
4  t3 = 3 * n
5  n = t3 + 1
6  goto 0
7  n = n / 2
8  goto 0
9  return n
```

Running it for `n = 6` and counting each line shows the "all or
nothing" promise: every line of a block runs exactly as often as its
leader.
