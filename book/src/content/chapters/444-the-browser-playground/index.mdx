This one starts on the Rust engine. Edit the program and watch the
status line under the output:

The decisions should begin `ps (line 1) {x, vx} → struct of arrays`,
followed by the loop, the typed columns and the bounds proof. Press

because syntax errors come from two different parsers, oxc and acorn,
each wording them its own way.

<Callout kind="definition">
A **playground** is the compiler running in a web page: the reader
edits a program and sees the compiler's output, here the decisions,
the compiled code and a check that both versions print the same thing.
The book's `Playground` component has two engines, the TypeScript
bundle and the Rust engine as WebAssembly, switched with the **TS /
Rust** toggle or the `engine` prop.
</Callout>

The first is the smallest use, in a chapter's MDX: `client:visible`
tells the site to start the component's JavaScript only when it
scrolls into view, and `initial` is the program in the editor; it
starts on the TypeScript engine, so no `.wasm` is downloaded unless the
reader presses **Rust**. The second starts on the Rust engine, as the
one above does, which is meant only for chapters about the Rust port,
since it costs every reader the download. The third hides the toggle,
for a chapter where switching engines would only distract.

## Only when asked

The `.wasm` is 1.4 MB, so pages that never use it must not pay for it.
The chapter *Compiling the engine to WebAssembly* showed `build.mjs
--book` copying the web glue into `book/src/vendor` and the module into
`book/public/wasm`; files in `public/` are served as they are, never
bundled. The loading happens in a **worker**, a script running on a
background thread, apart from the page, which talks to the page only
by messages (`postMessage` on one side, `onmessage` on the
other)<Cite id="mdn-web-workers" />:

<Analogy title="the pizza oven">
A café keeps a wood-fired oven in the back and lights it only when the
first customer orders pizza; everyone else gets sandwiches made at the
counter, at once, with no oven involved.
<span slot="breaks">A lit oven warms up slowly and stays lit; the
engine is ready as soon as one download and one compile of the module
finish, and the café's oven never has to be thrown out and replaced,
which, as we will see, the worker sometimes does.</span>
</Analogy>

`play.worker.ts` loads the engine like this (rewrapped, with the
module's URL, built from the site's base path, shortened to `URL`):

```ts
let rust: Promise<Wasm> | null = null;
const loadRust = () => (rust ??=
  import('../../vendor/viscosity_wasm.js')
    .then(async (m) => {
      await m.default({
        module_or_path: URL });
      return m;
    })
    .catch((err) => {
      rust = null; throw err;
    }));
```

The first line holds the loading promise, `null` until a reader asks.
`??=` means "assign only if it is still null", so the first request
stores the promise and every later request awaits the same one,
instead of downloading again. `import(...)` with brackets is a dynamic
import, which fetches the glue only when this line runs; `m.default`
is the glue's `init()`, which fetches and instantiates the module.
The `.catch` sets the promise back to `null` after a failed download,
so the next request tries again instead of reusing a rejection
forever. The TypeScript engine, by contrast, is imported into the page
itself and called synchronously.

## One ticket per keystroke

Every edit compiles, and a Rust compile is a round trip to the worker,
so a reply can arrive after a newer edit, or after the reader has
switched to the TypeScript engine. Each compile therefore takes a
ticket (trimmed: the types are left out):

```ts
const ticket = ++latest.current;
const show = (r, error, note) => {
  if (ticket !== latest.current)
    return; // a newer edit or
            // engine switch won
  setRes(r); setErr(error);
  setStatus(note);
};
```

`latest` is a counter that survives between renders; `++` makes a new
ticket for this compile, and `show`, the only way a result reaches the
screen, checks that no newer compile has started since. Both engines
share the counter, so a late Rust reply cannot overwrite a newer
TypeScript result either.

<Analogy extra title="numbered tickets at a deli counter">
At a deli counter you take a numbered ticket, and the display shows
only the number being served now; if you wandered off and took a new
ticket, your old number is skipped when it comes up.
<span slot="breaks">At the deli, the skipped order is never made; here
the old compile still runs to the end in the worker, and only its
result is thrown away, so tickets save the screen from confusion but
do not save any work.</span>
</Analogy>

<Formal title="The ticket rule">

```text
on compile:  latest := latest + 1
             tᵢ := latest
on reply i:  show rᵢ  ⇔  tᵢ = latest
```

<span slot="read">Each compile adds one to latest and keeps that value
as its ticket. When a reply comes back, its result is shown if and only
if its ticket still equals latest, that is, if no compile has started
since it did.</span>
</Formal>

## When Rust panics

The Rust engine should not panic (the chapter *Fuzzing the Rust
engine* hunts for inputs that make it, and its finds are fixed), but
the playground must survive one anyway. In native Rust a panic
*unwinds*: Rust walks back up the stack and cleans up each function's
data on the way<Cite id="klabnik2026" />, and `catch_unwind` can stop
an unwinding panic and hand you an `Err`<Cite id="rust-std-catch-unwind" />.
Watch the clean-up release a `RefCell`'s borrow:

<Run id="unwind" />

It prints `caught: true`, then `free again: true`, then `[1, 2]`: the
closure borrowed `seen` mutably, pushed 2 and panicked, and on the way
out the borrow guard `v` was dropped, so the `RefCell` is free.

WebAssembly built by cargo does not unwind. By default, Rust panics
there compile with `panic=abort`, "which aborts the WebAssembly
instance on panic"<Cite id="wasm-pack-book" />, and from JavaScript
the abort is a **trap**, thrown as a `WebAssembly.RuntimeError`<Cite id="mdn-wasm-runtimeerror" />.
The instance is still there afterwards, in whatever state the panic
left it. I tried it for this chapter with a small crate built like the
engine (rustc 1.97, wasm-bindgen 0.2.106, Node 22): `remember(s)`
borrows a thread-local `RefCell<Vec<String>>`, pushes `s`, and panics
on `"boom"`; `busy()` asks whether the `RefCell` is still borrowed;
`shout(s)` uppercases a string and touches nothing else:

```text
a -> 1
boom -> RuntimeError: unreachable
busy -> true
still here -> STILL HERE
c -> RuntimeError: unreachable
```

No destructor ran, so the borrow guard was never dropped: the
`RefCell` stays mutably borrowed forever, and every later call that
touches it panics on borrowing<Cite id="rust-std-cell" />, which traps
again. An unrelated function still works, which is worse, because the
instance looks alive. So the worker reports a trap as fatal (rewrapped):

```ts
post({ id,
  error: (err as Error).message
    ?? String(err),
  fatal: err instanceof
    WebAssembly.RuntimeError });
```

On a fatal reply the page calls `terminate()` on the
worker<Cite id="mdn-web-workers" /> and forgets it; requests still
queued on it get an error at once, so none waits forever, and the next
compile starts a new worker, with a new instance and new memory.

<Callout kind="engine" label="Under the hood">
`scripts/smoke.mjs` checks all this in a real browser (Playwright), on

no `.wasm` may be requested; after pressing **Rust**, exactly one
request, for `/wasm/viscosity_wasm_bg.wasm`. The compiled code and the

engine's output must print the same as the original, switching back to
TS must work, and there must be no console errors. It also checks that
the toggle buttons are at least 44 pixels high and wide, and that the
whole Playground fits a 440-pixel-wide screen. Each Run both gets a
fresh worker of its own, stopped after 10 seconds, so a program that
loops forever cannot hang the page.
</Callout>

## What you learned

- A **playground** runs the real compiler in the page; the Rust engine
  is fetched only when a reader picks it, into a **worker**, through
  one memoised loading promise that resets on failure.
- Each compile takes a **ticket**, and a reply is shown only if its
  ticket is still the latest, whichever engine it came from.
- A Rust panic in WebAssembly is a **trap**: nothing unwinds, state can
  stay broken, so the worker is replaced.
