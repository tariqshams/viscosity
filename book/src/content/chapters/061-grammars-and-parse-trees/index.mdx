## Right words, wrong order

Give Drip's scanner this line:

```
print + ; 3 (
```

It does not complain, because every token is spelled correctly;
however, the line means nothing, like "sat the on cat mat the". The
problem is in how the tokens are arranged, so we need rules about
**order**, written precisely enough for a program to check.

## Rules with blanks

<Analogy title="a form with blanks">
A greetings card company prints cards from templates: "Dear ___, happy
___!", where the first blank says *a name* under it and the second says
*an occasion*. A separate sheet lists what may go in each blank: a name
is "Ada" or "Alan"; an occasion is "birthday" or "anniversary". Any card
you can fill in from those sheets is allowed, and nothing else is.
<span slot="breaks">A real blank takes whatever you write in it; a
grammar's blank only takes what its own rules allow, and those rules may
contain more blanks, even blanks of the same kind.</span>
</Analogy>

Here is a grammar for a small piece of Drip, print statements that add
numbers, with brackets allowed; read each arrow as "can be made of":

```text
stmt → "print" expr ";"
expr → expr "+" item
expr → item
item → NUMBER
item → "(" expr ")"
```

Words in quotes are exact tokens; `NUMBER` stands for any number token;
and the bare words `stmt`, `expr` and `item` are the blanks, each the
name of some rules. Step through how one rule is read:

<ReadRuleSteps client:visible />

<Callout kind="definition">
A **grammar** is a set of rules that says which rows of tokens are valid
programs. Each rule is a **production rule**: one name (its *head*), an
arrow, and a *body*, the row of symbols the head may be replaced by. A
**terminal** is a symbol that stands for a token, such as `"print"` or
`NUMBER`; it is never replaced. A **nonterminal** is the name of one or
more rules, a blank to be filled in; one of them, the **start symbol**
(here `stmt`), is where every program begins.
</Callout>

<Examples of="grammar production-rule terminal nonterminal">

```text
item → "(" expr ")"
terminals: "(" and ")"
nonterminals: item, expr
```

</Examples>

This is one production rule, with head `item` and a body of three
symbols. The brackets are in quotes, so they are terminals, each meaning
one bracket token; `item` and `expr` have rules of their own, so they
are nonterminals.

`expr` appears on both sides of `expr → expr "+" item`, and `item →
"(" expr ")"` puts a whole `expr` inside brackets; so five rules allow
`print ((1) + 2) + 3;` and endlessly many more. This is recursion, and
like any recursion it needs a base case: `expr → item` and `item →
NUMBER` are the ways out. It is also what lets a grammar check that
every `(` has its `)` at any depth, which no flat pattern can.

<More title="Fill in the blanks yourself, and a grammar that writes sentences">

Each button uses one rule on the underlined nonterminal; you are done
when only terminals are left.

<DerivePlay client:visible />

A program can do the same, choosing rules at random. `rules` maps each
nonterminal to its list of bodies; `make(sym)` writes out a terminal,
or picks a body and calls itself on each symbol; past `depth` 3 it
always takes the first body, the way out, so every sentence finishes.

<Run id="randomSentences" />

<Formal title="A grammar as four things">

```text
G = (N, Σ, P, S)
every rule in P:  A → α
  where A ∈ N  and  α ∈ (N ∪ Σ)*
S ∈ N
```

<span slot="read">A grammar G is four things: N, the nonterminals; Σ
(sigma), the terminals; P, the production rules; and S, the start
symbol. Every rule has the form "A is made of α", where A is one
nonterminal (∈ reads "is a member of") and α is a row of zero or more
symbols, each a nonterminal or a terminal (∪ reads "together with").
Because every head is a single nonterminal, it may be replaced the same
way wherever it stands; grammars like this are called context-free, and
they are what JavaScript's specification uses<Cite id="ecma262-grammar"
/>.</span>
</Formal>

<Analogy extra title="a cookbook with sub-recipes">
A cookbook says "a sandwich is bread, a filling, then bread", and on
another page "a filling is cheese, or ham and tomato". The printed words
(bread, cheese) are things you use; the recipe names only tell you which
page to turn to.
<span slot="breaks">A cookbook tells you how to *make* one thing; a
grammar is more like a judge, deciding whether a row of tokens you
already have could have been made by its recipes.</span>
</Analogy>

</More>

## BNF and its shorthands

The standard way to write rules is **BNF** (Backus–Naur form). Its
extended form adds four shorthands, and with them the five rules
become three:

```text
stmt → "print" expr ";"
expr → item ( "+" item )*
item → NUMBER | "(" expr ")"
```

`|` means "or"; `( )` groups symbols into one piece; `*` after a piece
means "zero or more times"; and `?` means "optional". The star has
replaced the rule that mentioned itself, and both grammars allow
exactly the same rows.

<Callout kind="definition">
**BNF** is the standard notation for grammars: each production rule is
a nonterminal, an arrow (or `::=`), and a row of terminals and
nonterminals. *Extended* BNF (EBNF) adds `|` for alternatives, `( )`
for grouping, `*` for "zero or more" and `?` for "optional"; each
unfolds back into plain rules, so they add readability, not power.
</Callout>

<Examples of="bnf">

```text
call → IDENT "(" args? ")"
args → expr ( "," expr )*
```

</Examples>

This is the shape of every function call: a name, a bracket,
*optionally* some arguments, and a closing bracket, where the arguments
are one `expr` followed by zero or more `, expr` pairs. So `f()` and
`f(x, y, z)` fit, while `f(x,)` does not, because each comma brings an
`expr` with it.

<More title="How the shorthands unfold, and Drip's statements on one page">

<ShorthandSteps client:visible />

With the shorthands, the statements of Drip fit in a few lines (the full
grammar also has `while`, `for`, `return`, classes and more, and
`expression` has rules of its own):

```text
program     → declaration* EOF
declaration → fnDecl | letDecl
            | statement
letDecl     → "let" IDENT
              ( "=" expression )? ";"
statement   → printStmt | ifStmt
            | block | exprStmt
printStmt   → "print" expression ";"
ifStmt      → "if" expression block
              ( "else" ( ifStmt | block ) )?
block       → "{" declaration* "}"
exprStmt    → expression ";"
```

<Figure takeaway="Loops of rules let statements nest to any depth." caption="Which rules use which: an arrow from one rule to another means the second appears in the first one's body. The dashed arrows close the loops: a block holds declarations, which can be statements, which can be blocks; an if statement's branches are blocks, so they can hold anything; and after else an if statement can name itself.">
  <DripGrammarMap />
</Figure>

Older books write `<stmt> ::= "print" <expr> ";"`, and JavaScript's
specification writes `PrintStatement : print Expression ;` with a small
"opt" where we write `?`<Cite id="ecma262-grammar" />; all three are
read the same way.

<Analogy extra title="a knitting pattern">
"*knit 2, purl 2; repeat from * to end of row" saves writing the
stitches forty times, and anyone who knows the shorthand can expand it
back into every single stitch.
<span slot="breaks">"To the end of the row" depends on how long the row
is; a grammar's repeat has no outside limit, and the tokens alone
decide.</span>
</Analogy>

</More>

## Derivations: showing that it fits

To *show* that `print 1 + 2;` fits, start from the start symbol and
rewrite one nonterminal at a time, until only tokens are left; if they
are the tokens you were given, that is the proof.

<Analogy extra title="showing your working in algebra">
To simplify `2(x + 3) - x` you write a line for each move, so a reader
can check every line on its own.
<span slot="breaks">In algebra you choose any move that helps; in a
derivation the only move is "replace one nonterminal by one of its rule
bodies", and the lines usually get longer.</span>
</Analogy>

<Examples of="derivation">

```text
stmt
⇒ print expr ;            stmt → …
⇒ print expr + item ;     expr → expr + item
⇒ print item + item ;     expr → item
⇒ print NUMBER + item ;   item → NUMBER
⇒ print NUMBER + NUMBER ; item → NUMBER
```

</Examples>

Read `⇒` as "becomes in one step"; the rule used is on the right. Each
line is a **sentential form**, which may still hold nonterminals, and
the last, with only terminals, is a **sentence**. On the third line we
rewrote the leftmost of two nonterminals; doing that every time gives a
**leftmost derivation**, and always taking the rightmost gives a
**rightmost** one.

<Callout kind="definition">
A **derivation** is a list of sentential forms that begins with the
start symbol, where each form comes from the one before by replacing
exactly **one** nonterminal with the body of one of its rules. A row of
tokens fits the grammar exactly when some derivation ends with it.
</Callout>

<More title="A rightmost derivation in code, and the formal notation">

`rightmost` keeps the form as an array; each step walks back from the
end to the rightmost nonterminal (`form[i] in rules`), and splices in

<Run id="rightmost" />

<Formal title="One step, many steps, and the language">

```text
α A β  ⇒  α γ β      if  A → γ is a rule
S  ⇒*  w             in zero or more steps
L(G) = { w ∈ Σ* | S ⇒* w }
```

<span slot="read">If A is made of γ is a rule, then any row alpha, A,
beta becomes alpha, gamma, beta in one step, leaving the symbols round
A alone. The arrow with a star means "in zero or more steps". The
language of the grammar G is the set of all rows w of terminals that
the start symbol S becomes in zero or more steps.</span>
</Formal>

</More>

## Parse trees

The two derivations look different, yet they drew the same tree; and
the tree is what a compiler wants, because it shows what is added to
what.

<Callout kind="definition">
A **parse tree** has the start symbol at its root. Each inner node is a
nonterminal, and its children, from left to right, are the symbols of
the body of the rule used on it. Each leaf is a terminal (or `ε`, the
empty row, for an empty body). Reading the leaves from left to right
gives the tree's **yield**: the sentence it derives.
</Callout>

<Examples of="parse-tree">

```text
stmt ┬ print
     ├ expr ┬ expr ── item ── NUMBER
     │      ├ +
     │      └ item ── NUMBER
     └ ;
```

</Examples>

This is the tree of `print 1 + 2;`, drawn sideways. The inner `expr`
with its single child `item` is the step `expr ⇒ item`, and the `+`
sits between the two `item`s, which is how the tree says "these two are
added". A tree records which rule was used on which nonterminal and
forgets the order of the steps, so one tree stands for many derivations,
but for exactly one leftmost derivation<Cite id="aho2006" />.

<Figure takeaway="Read the leaves left to right and you get the sentence back." caption="The parse tree of print (1 + 2) + 3; under the adding grammar, with each NUMBER leaf shown by its lexeme. The dashed lines drop every leaf to the bottom row: in order, they spell the sentence.">

## Ambiguity: two trees, two meanings

The grammar most people write first for arithmetic is short: `expr →
expr "-" expr | expr "+" expr | expr "*" expr | NUMBER`. `1 - 2 - 3`
fits it; the trouble is *how*. Step through two leftmost derivations,
both following the rules exactly:

<AmbigSteps client:visible />

<Callout kind="definition">
A grammar is **ambiguous** when at least one sentence has two (or more)
different parse trees; equivalently, two different leftmost
derivations.
</Callout>

<Examples of="ambiguity">

```text
expr → expr "-" expr | NUMBER
1 - 2 - 3:  (1 - 2) - 3  = -4
       or   1 - (2 - 3)  =  2
```

</Examples>

One operator, two ways to chain it, and two answers; a grammar that
allows both trees has not decided what the program means. Ambiguity
belongs to the grammar, not to the sentences: a grammar with one
nonterminal per level of operator describes the same rows with one tree
each, and *Recursive descent, precedence and associativity* builds it.

<More title="The dangling else, and where grammars sit in a larger family">

The most famous ambiguity is `if (a) if (b) s1 else s2`, under a
C-style grammar where a bracketed condition is followed by a single
statement: the rules allow the `else` to belong to either `if`.

<Figure takeaway="The rules allow the else to belong to either if." caption="The tokens of if (a) if (b) s1 else s2 (brackets left out), grouped two ways. Top: the else belongs to the inner, nearest if, so s2 runs when a is true and b is false. Bottom: it belongs to the outer if, so s2 runs when a is false.">
  <DanglingElse />
</Figure>

JavaScript's specification keeps the short rules and adds that the
`else` goes with the nearest `if`<Cite id="ecma262-if" />; a grammar
can be rewritten with "matched" and "unmatched" statements, at the cost
of doubling the rules<Cite id="aho2006" />; and Drip requires braces
round every branch, so the braces show which `if` an `else` belongs to.

each operator as the root and combining every tree of the left part

Some sets of sentences have no unambiguous grammar at all, and no
program can decide, for every grammar, whether it is
ambiguous<Cite id="hmu2006" />; the grammars of programming languages
are designed to avoid both problems. The deep dive *The Chomsky

<Analogy extra title="a newspaper headline">
"Squad helps dog bite victim" can be read two ways. Every word is right,
and so is their order; what is missing is which words group together.
<span slot="breaks">A reader picks the sensible meaning without
noticing; a parser has no common sense, so a grammar must leave it no
choice to make.</span>
</Analogy>

## What you learned

- A **grammar** is a set of **production rules**; **terminals** are
  tokens and **nonterminals** are blanks. A rule that mentions itself
  gives endlessly many programs, and needs a way out.
- **BNF** writes rules as `head → body`; `|`, `( )`, `?` and `*` are
  shorthands that unfold into plain rules.
- A **derivation** replaces one nonterminal per step; a **parse tree**
  records which rule was used where, and its leaves spell the sentence.
- A grammar is **ambiguous** when one sentence has two parse trees.
