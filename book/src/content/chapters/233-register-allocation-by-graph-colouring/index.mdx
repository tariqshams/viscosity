## Colouring a map

The last chapter left `sumsq` as eight virtual registers and a graph
saying which of them may not share. **Register allocation** is the
stage that decides which real register each virtual register gets
(and, when there are not enough, which values must wait in memory
instead, the subject of the next chapter). With the interference
graph in hand, its question becomes a famous puzzle: give every node
one of k colours, the k registers, so that no edge joins two nodes of
the same colour.

<Analogy title="colouring a map">
On a map of countries, neighbours must have different colours so that
you can see the border. With few countries and plenty of crayons it
is easy; the puzzle is doing it with as few crayons as possible.
<span slot="breaks">Any flat map can be coloured with four crayons (a
famous theorem); an interference graph is not a flat map, and a
function can need any number of registers, so "four is always
enough" has no counterpart here.</span>
</Analogy>

<Analogy title="timetabling exams">
A school puts two exams in the same time slot only if no pupil sits
both. Draw a dot per exam and a line between two exams that share a
pupil, and choosing time slots is colouring the dots: each slot is a
colour, and joined dots need different slots.
<span slot="breaks">A school can always add another day; a processor
has a fixed number of registers, and when the colours run out the
allocator must change the program (by spilling) rather than add a
colour.</span>
</Analogy>

<Callout kind="definition">
**Register allocation** maps the virtual registers of a function to
the machine's physical registers, so that two values that interfere
never get the same one; values that cannot be given a register are
kept in memory. **Graph colouring** assigns each node of a graph one
of k colours so that the two ends of every edge differ; a graph that
can be coloured this way is **k-colourable**. Colouring the
interference graph with k = the number of registers gives a register
allocation.
</Callout>

<Formal title="A k-colouring">

```text
c : V → {1, …, k}
for every edge {u, v} ∈ E:  c(u) ≠ c(v)
```

<span slot="read">A colouring c gives each node in the set of nodes V
a colour from 1 to k. It is a proper colouring if, for every edge
between nodes u and v in the set of edges E, the colour of u differs
from the colour of v.</span>
</Formal>

The bad news is that deciding whether a graph can be coloured with k
colours is one of the classic hard problems of computer science: for
k of 3 or more, no fast method is known that always gets it right,
and most people who study it believe none exists. The good news is
that interference graphs from real programs are rarely the hard
cases, and the method below, Chaitin's, colours them quickly
<Cite id="chaitin1982" />.

## Few neighbours, no problem

Here is the observation everything rests on. Suppose a node `v` has
fewer than k neighbours. Take it out of the graph, colour the rest
somehow, and then put it back: its neighbours use at most k − 1
colours between them, so at least one of the k colours is free for
`v`. In other words, a node of degree less than k (its **degree** is
its number of neighbours) can always be coloured *last*, so we can
set it aside and worry about the smaller graph.

Better still, removing `v` lowers the degree of each of its
neighbours, which may push some of them below k too. So **simplify**:
repeatedly remove a node of degree less than k and push it on a
stack, until the graph is empty. Then **select**: pop the nodes off
the stack one at a time, in the reverse order, and give each the
lowest colour that none of its already-coloured neighbours has. Every
node is popped into a graph where, when it was pushed, it had fewer
than k neighbours, so a colour is always free. Step through it on
`sumsq` with four registers:

<Formal title="Why simplify is safe">

```text
deg(v) < k  ⟹
  (G is k-colourable ⟺ G − v is
                        k-colourable)
```

<span slot="read">If node v has fewer than k neighbours, then the
whole graph G can be coloured with k colours exactly when the graph
without v, written G − v, can be: any colouring of G − v leaves a
colour free for v, and any colouring of G already colours G − v.</span>
</Formal>

<Callout kind="definition">
**Simplify and select** is Chaitin's colouring method. *Simplify*
repeatedly removes a node with fewer than k neighbours from the
interference graph and pushes it on a stack. *Select* pops the nodes
in reverse order and gives each the lowest colour not used by its
coloured neighbours. If simplify reaches a graph in which every node
has k or more neighbours, it is **stuck**, and some value must be
treated specially: Chaitin spills one to memory; Briggs, Cooper and
Torczon push one anyway and hope.
</Callout>

## When simplify gets stuck

With three registers, `sumsq` gets stuck after removing `s0` and
`i0`: the six nodes left all have three or more neighbours. That is
real, since `n`, `s1`, `i1` and `t` are all alive at once and three
registers cannot hold four values, so something will have to wait in
memory. But being stuck does not always mean failing. Here is a
square of four values with two registers:

<Figure takeaway="Stuck is a warning, not a verdict." caption="Left: a cycle a–b–c–d with k = 2. Every node has two neighbours, which is not fewer than 2, so simplify cannot remove anything. Right: pushing a anyway and carrying on still succeeds, because a's two neighbours, b and d, end up with the same register.">
  <OptimismFigure />
</Figure>

Chaitin's allocator, stuck, would spill a value here, although two
registers are enough. Briggs, Cooper and Torczon's improvement,
**optimistic colouring**, is to push the stuck node anyway (choosing
it the way Chaitin would choose a spill) and carry on simplifying;
only if select later finds no free colour for it is the value really
spilled<Cite id="briggs1994" />. The rule "degree less than k" is a
guarantee that a colour will be free; a node with k or more
neighbours may still find one, when some of its neighbours share.

<Examples of="register-allocation graph-coloring simplify-select">

```text
a–b, b–c, c–a, k = 2
  every degree is 2: stuck
  select finds no colour: spill one
```

```text
a–b–c–d–a, k = 2
  stuck, push a anyway (optimism)
  a r1, b r2, c r1, d r2: it fits
```

```text
sumsq, k = 4 (r1–r4)
  push s0 i0 t s1 n i1 s2 i2
  pop: i2 r1, s2 r2, i1 r1, n r3,
       s1 r2, t r4, i0 r1, s0 r2
```

</Examples>

colours, a triangle: every pair interferes, so three registers are

<Callout kind="engine" label="Under the hood">
A real allocator has more to respect than the graph. Some values must
be in particular registers: arguments and results in `a0` and `a1`,
by the calling convention, so those nodes are **precoloured**, joined
to the graph with their colour fixed in advance. Values live across a
call interfere with every caller-saved register, which the call may
destroy, so they are pushed towards the callee-saved ones. Textbook
colouring allocators handle both by adding precoloured nodes and
edges, then running the same simplify and select
<Cite id="coopertorczon2022" />. LLVM's default allocator, the greedy
one, is not a colouring allocator at all, but it asks the same
question (do these two live ranges overlap?) one live range at a time
<Cite id="llvm-codegen" />; the chapter on linear scan comes back to
it. Viscosity
allocates no registers; V8 does that for the JavaScript it emits.
</Callout>

## What you learned

- **Register allocation** gives each virtual register a physical one,
  so that interfering values differ; it is **graph colouring** of the
  interference graph with k colours, k being the number of registers.
- A node with fewer than k neighbours can always be coloured last;
  **simplify** removes such nodes onto a stack, and **select** pops
  them and gives each the lowest free colour.
- When simplify is stuck, Chaitin spills; Briggs's **optimistic**
  version pushes a node anyway and spills only if select finds no
  colour.
- With four registers, `sumsq` colours with no spill, and by luck all
  its copies become copies of a register to itself.
