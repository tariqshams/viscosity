## Knowing the moment an object dies

You met a reference count as a Rust type in *Box, Rc and RefCell*,
where `Rc::clone` added one and a drop took one away; this chapter goes
further, to reference counting as the way a whole language runtime
manages memory, and what it costs. Your Drip VM's collector (from
*Reclaiming memory: mark and sweep*) finds garbage by searching: now and then it stops the program, marks everything it can
reach from the roots, and sweeps away the rest. Between collections,
dead objects sit in memory, and nobody knows exactly when they will go.
There is another way, nearly as old (George Collins described it for
Lisp lists in 1960<Cite id="collins1960" />): have each object keep a
count of the references that point at it, update the count whenever a
reference is made or lost, and free the object the instant its count
reaches zero. CPython, Swift, Objective-C, Rust's `Rc` and `Arc`, and
C++'s `shared_ptr` all work this way.

<Analogy title="last one out turns off the lights">
An office has a rule: whoever leaves last switches off the lights. Each
person arriving adds one to the people inside, each person leaving
takes one away, and the person who brings it to zero does the job, at
once, without anyone touring the building at night to check.
<span slot="breaks">People know when they arrive and leave; in a
program every copy of a reference, every overwrite and every variable
going out of scope must be counted, and it is the compiler that inserts
those updates for you.</span>
</Analogy>

<Analogy extra title="a balloon held by strings">
Each reference is a string tied to a balloon; while anyone holds a
string, the balloon stays. Let go of the last string and it floats
away, and anything tied only to it floats away with it.
<span slot="breaks">Two balloons tied only to each other, with nobody
holding either, still float away in real life; under reference
counting each still has one string attached, so neither is ever
freed. That is the cycle problem, and the subject of *Cycle
collection and eliding counts*.</span>
</Analogy>

<Callout kind="definition">
**Reference counting** stores in every heap object a count of the
references to it. Making a new reference (storing a pointer into a
variable, a field or an argument) **increments** the count; losing one
(overwriting it, or the variable going out of scope) **decrements**
it. When a count reaches zero the object is freed immediately, and
every reference it held is decremented in turn, which may free more
objects.
</Callout>

<Formal title="The invariant and the rule">

```text
rc(o) = |{ r : r is a reference to o }|

dec(o): rc(o) := rc(o) − 1
        if rc(o) = 0:
          for each reference c in o: dec(c)
          free(o)
```

<span slot="read">The count of an object o is the number of references
that point at o, from variables or from other objects. Decrementing o
lowers that number by one; if it reaches zero, o is unreachable, so
each object o points at is decremented in turn (a recursive step that
can free a whole structure), and then o's memory is freed.</span>
</Formal>

<Examples of="reference-counting">

```text
# Python 3.13
x = object()
sys.getrefcount(x)   # 2
y = x
sys.getrefcount(x)   # 3
del y
sys.getrefcount(x)   # 2
a = N(); a = None    # prints "freed a"
```

```rust
struct N(&'static str, Option<Rc<N>>);
impl Drop for N {   // runs when freed
  fn drop(&mut self) {
    println!("free {}", self.0);
  }
}
let c = Rc::new(N("c", None));
let b = Rc::new(N("b", Some(c)));
let a = Rc::new(N("a", Some(b)));
drop(a); // free a, free b, free c
```

```text
// C++: int call(const shared_ptr<int>& p)
//        { return peek(p); }  // copies p
// clang++ 18 -O2, trimmed:
lock incl  8(%rax)    // count += 1
call ...
lock xaddl %ecx, 8(%rbx)  // count -= 1
```

</Examples>

The first is real Python 3.13 output. `sys.getrefcount` reports one
more than you might expect, because passing `x` to it makes a
temporary reference<Cite id="python-sys-getrefcount" />; `y = x` adds
one and `del y` takes it away. On the last line `N` is a class whose
`__del__` method prints a message when an object is freed: setting `a`
to `None` drops the only reference and the message appears at once,
before the next line runs, where a tracing collector would print it
whenever it next happened to run. The second is the cascade, in Rust: `a` holds the only `Rc` to `b`,
and `b` the only one to `c`, so dropping `a` takes its count to zero,
and freeing it drops the `Rc` it held, which takes `b` to zero, and so
on down the list (rustc 1.97 printed the three lines in that order,
with no collector involved)<Cite id="rust-std-rc" />. The third is
the price: passing a C++ `shared_ptr` by value copies it, and clang's
code for the copy is a `lock`-prefixed increment, and for the
destruction a `lock`-prefixed exchange-and-add, because the count may
be shared between threads (libstdc++ checks a flag first, and uses
plain instructions while the program has only one thread). Locked instructions make every core agree on
the value, and they cost more than ordinary ones; Rust offers
`Rc`, whose counts are plain, non-atomic, and `Arc` for sharing across
threads, and makes the compiler refuse to send an `Rc` to another
thread<Cite id="rust-std-rc" />.

Here is the order of the two updates, in a few lines you can change:

<Run id="assign" />

`set` stores an object in a variable as a compiler's inserted code
would: it increments the new value's count *first*, then decrements the
old one. Run it: `b = A`, then `a = null`, leave A alive with count 1,
and `b = null` frees it. The last two lines assign a variable to
itself, `c = c`; with the order reversed, the decrement would reach
zero and free C before the increment could save it, so try swapping
the two halves of `set` and watch C die.

Swift calls the whole scheme Automatic Reference Counting (ARC): the
compiler, not the programmer, inserts the increments and decrements
(Swift's `retain` and `release`) for every class instance, and
"automatically frees up the memory used by class instances when those
instances are no longer needed"<Cite id="swift-arc" />.

## What you learned

- **Reference counting** keeps a count of references in each object's
  header; new references increment it, lost ones decrement it, and an
  object is freed the moment its count reaches zero.
- Freeing an object decrements everything it points to, so one
  assignment can free a whole structure.
- The costs: a memory write on every copy of a pointer, atomic
  instructions when threads share counts (`shared_ptr`, `Arc`), and
  cycles that never reach zero.

Next, *Cycle collection and eliding counts*: finding the cycles that
counting misses, and removing the count updates a compiler can prove it
