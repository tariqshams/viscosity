## Where shapes strain

The previous chapter showed the good case: a thousand particles built the
same way share one map, and each one holds only its values. However, the
scheme has two weak spots. First, V8 must decide how much room to give an
object *before* its properties arrive, without knowing how many will
come. Second, every new key moves an object to a new shape, so an object
whose keys keep changing creates shape after shape that nothing else will
ever share. V8 answers the first with slack tracking and the second with
dictionary mode.

## Room to grow: slack tracking

Objects made by a constructor get extra room at first. In 2020 the V8 team
described **slack tracking**: a new object gets spare in-object space,
starting from the properties the compiler expects plus eight, and after
seven constructions V8 shrinks the shape to what was actually
used<Cite id="v8-slack-tracking" />. You can watch it:

```js
function P(x, y) { this.x = x; this.y = y; }
%DebugPrint(new P(1, 2));
for (let i = 0; i < 10; i++) new P(i, i);
%DebugPrint(new P(3, 4));
```

```
// Node v22.23.4, V8 12.4, trimmed
// the first object
 - instance size: 104
 - inobject properties: 10
 - unused property fields: 8
 - construction counter: 6
// after eleven more
 - instance size: 40
 - inobject properties: 2
 - unused property fields: 0
 - construction counter: 0
```

Line 1 is a constructor that sets two fields; line 2 prints the first
object; line 3 makes ten more; line 4 prints a twelfth. The first had ten
slots (two expected, plus eight) and was 104 bytes; by the twelfth, the
map had been trimmed to two slots and 40 bytes, and the construction
counter, which counts down while V8 is still watching, had reached zero.

## When V8 gives up: dictionary mode

If a program keeps adding and removing properties, keeping a shape for
every combination costs more than it saves. So V8 can switch an object to
**slow properties**: a self-contained hash table that holds names and
values together<Cite id="v8-fast-properties" />, which is how every Drip
instance stores its fields.

<Analogy title="a seating chart and a pinboard">
A wedding seating chart is printed once, and every guest finds their seat
by its number; it is quick to read, but moving one guest means reprinting
it. A pinboard of name cards is slower to search, but anyone can pin or
unpin a card at any time.
<span slot="breaks">Nobody reprints a seating chart for one guest; V8
would happily make a new shape for one change, and switches to the
"pinboard" only when the changes themselves (like `delete`) make shapes a
bad deal.</span>
</Analogy>

<Analogy title="a cabinet and a shoebox">
A filing cabinet has labelled drawers in a fixed order, so you reach for
the third drawer without reading labels; a shoebox of labelled envelopes
takes any number of envelopes, in any order, but you read the labels to
find one.
<span slot="breaks">A shoebox can be sorted back into a cabinet in an
afternoon; in my test on V8 12.4, an object that had gone into dictionary
mode was still a dictionary a million reads later.</span>
</Analogy>

<Callout kind="definition">
An object in **dictionary mode** stores its named properties in its own
hash table instead of using a shared shape. Adding and removing properties
is cheap, but reads are slower, and the inline caches of a later chapter
do not work on it<Cite id="v8-fast-properties" />. V8's source says a map
is used either for dictionary-mode objects or for fast ones, never
both<Cite id="v8-src-map-12-4" />.
</Callout>

<Examples of="dictionary-mode">

```js
const p = { x: 1, y: 2, z: 3 };
p.z = undefined;
%HasFastProperties(p); // true
delete p.z;
%HasFastProperties(p); // false
```

```js
let last = true;
for (let n = 1; n <= 40; n++) {
  const o = {};
  for (let i = 0; i < n; i++)
    o['k' + i] = i;
  const f = %HasFastProperties(o);
  if (f !== last) console.log(n, f);
  last = f;
}
// prints: 20 false
```

```js
// a lookup table whose keys come and go
const seen = new Map();
seen.set('ada', 1);
seen.delete('ada');
// no shapes to break: Map is built
// for keys that change
```

</Examples>

The first is the spot-the-difference pair in one object: setting `p.z` to
`undefined` changes a value and keeps the shape, while `delete p.z`
removes the key and sends `p` into dictionary mode (in my tests on V8
12.4, deleting the last-added property did the same, as did deleting the
first). The second builds objects with 1, 2, 3, … computed keys and
prints when the answer changes: at 20 properties added this way, the
object turned into a dictionary in this version (do not memorize the
number; it is an engine detail). The third is the realistic answer for
data whose keys really do change, such as a set of names seen so far: a
`Map`, which is made for exactly that and has no shapes to lose.

<Callout kind="pitfall">
`delete obj.prop` is fine for a lookup table you add and remove keys from;
for an object with a fixed set of fields, such as a particle, set the
field to `undefined` (or keep a flag) instead, and use a `Map` for data
whose keys change.
</Callout>

<Callout kind="engine" label="Under the hood">
You have met this cliff already: in the chapter on making the VM fast,
the Drip VM's biggest measured speed-up came from making its debug-only
"poisoning" of freed objects, which deleted their properties, really
debug-only, because those deletes pushed objects into V8's dictionary
mode. Dictionary objects also give an optimizing tier nothing to rely on:
Maglev's fast `o.x` is a check of one shape plus a load at a fixed
offset<Cite id="v8-maglev" />, and a dictionary has no fixed offsets.
</Callout>

## What you learned

- **Slack tracking** gives a constructor's first objects spare in-object
  room (expected plus eight), then trims the map to what was used.
- **Dictionary mode** replaces the shared shape with a per-object hash
  table: cheap to change, slower to read, and invisible to inline caches.
- In V8 12.4, `delete` and many computed keys trigger it; for fixed
  fields set `undefined`, and for changing keys use a `Map`.
