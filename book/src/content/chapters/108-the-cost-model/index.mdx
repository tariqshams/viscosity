## Safe is not the same as worth it

Here is a small program that sums the `x` of two points:

```js
const pts = [{ x: 1, y: 2 },
  { x: 3, y: 4 }];
let sx = 0;
for (let i = 0; i < pts.length; i++)
  sx += pts[i].x;
console.log(sx);
```

Every check from *Proving it safe* passes: the records have one stable
shape, both fields are numbers, the loop only reads `x`, and nothing can
observe the layout. Viscosity could turn `pts` into two `Float64Array`
columns; however, this is what it says instead (wrapped to fit the page,
as all explain output in this chapter is):

```text
pts (line 1) {x, y} → kept as array
  of objects
  · about 2 elements: below the
    64-element threshold, where the
    benefit is too small
```

A layout change is not free: it adds a generated class, rewrites every
access and is harder to follow in a debugger, and for two points nothing
would ever pay that back.

<Analogy title="reorganising a kitchen">
Moving the spices next to the cooker is worth it for the jar you reach
for twenty times a day, and not worth it for the box of birthday candles
you open once a year. Before you move anything, you make a rough guess
of how often you will use it, and that guess is all a cost model is.
<span slot="breaks">You know your own habits; Viscosity never watches the
program run (unless you give it a profile), so it guesses from what the
code looks like: how big the array seems to be and whether a loop
touches it.</span>
</Analogy>

<Analogy extra title="a sat nav choosing a route">
A sat nav picks the motorway over the back roads from things it can see
on the map (distance, road type, speed limits), it is sometimes wrong
because of traffic it could not know about, and you can always tell it
"avoid motorways" and it will obey.
<span slot="breaks">A sat nav adds up minutes along every route and
compares the totals; Viscosity's model adds nothing up, it asks a few
yes-or-no questions in a fixed order and stops at the first "yes".</span>
</Analogy>

<Callout kind="definition">
A **cost model** is the part of a compiler that estimates whether a
transformation will pay off, so that it makes only the changes that are
safe *and* worth it. It works from facts the compiler can see in the
code (sizes, loops, types) or has measured, and its estimates can be
wrong.
</Callout>

You have met cost models before. *The call graph* showed inliners
working to a growth budget, because copying a body is a cost, and
*Loop unrolling and vectorisation* weighed what unrolling saves against
what it costs in code size and registers. Viscosity's is the same idea
applied to data layout.

## The ladder

The planner, `plan()` in `core/src/plan.ts`, decides one collection at
a time. It asks a fixed series of questions, and the first one answered
"yes" decides; the first few are about permission, and the rest are the
cost model proper. Step through them:

<PlanLadder client:visible />

Here it is as code, `plan()` rewritten as one chain of `if`s (`keep`
records `aos` with a reason, and `size` is the profiled length if there
is one, else the estimate):

```ts
if (c.bailouts.length) keep('unsafe: …');
else if (ann) use(ann.layout);
else if (opts.mode === 'opt-in')
  keep('opt-in mode: not annotated');
else if (python && !opts.pythonAuto)
  keep('CPython: …');
else if (c.numericFields.size === 0)
  keep('no field is provably numeric…');
else if (!c.loops.some((l) => l.depth > 0))
  keep('no loop reads or writes…');
else if (size !== null
         && size < opts.minSize)
  keep(`about ${size} elements: …`);
else use('soa');
```

Line 1 is safety: any bailout from *What Viscosity refuses to touch*
keeps the collection, and nothing below can change that. Line 2 is an
annotation (the next chapter, *Opting in with @viscosity*), which skips
every rule after it. Lines 3 to 6 are choices of the user and the
language; lines 7 to 13 are the three cost rules; the last line is what
is left.

<Formal title="The planner as a function">

```text
plan(c) =
  aos     if bailouts(c) ≠ ∅
  ann(c)  else if c is annotated
  aos     else if numeric(c) = ∅
  aos     else if loops(c) = ∅
  aos     else if size(c) < minSize
  soa     otherwise
```

<span slot="read">The plan for c is aos if its set of bailouts is not
empty (≠ ∅ reads "is not the empty set"); else the annotation, if there
is one; else aos if no field is numeric, no loop touches a field, or c
is smaller than minSize; else soa. Rows are tried from the top, and the
first true one wins (the opt-in and Python rows are left out).</span>
</Formal>

## Three rules, and where they came from

**Is any field provably numeric?** If not, every column would be a
plain JavaScript array. Part of SoA's measured advantage comes from
typed storage: in this book's benchmark run, a packed `Float64Array`
that keeps each record's fields together was already 2.1× faster than
objects on the particle loop at 100,000 elements (`FINDINGS.md`,
section 5). Plain-array columns get none of that, so the rule says no.

**Does a loop read or write a field?** A layout pays off only through
work that is repeated. A collection whose fields are touched once, or
never, is kept.

**Is it big enough?** Here is the measured basis: the same `x += vx`
loop from *AoS vs SoA, measured*, at two sizes.

  caption="At 1,000 elements the data already fits in cache, and SoA's lead is modest." />

<BenchBars suite="update-xy" n={100000} title="The same loop, 100,000 elements"
  highlight={['soa']} layouts={['aos', 'soa']}
  caption="At 100,000 elements the array of objects slows down per element; SoA barely changes." />

In this run SoA was 1.7× faster at 1,000 elements and 3.8× at 100,000
(`results/baseline-node-2026-10-31.md`): the win grows with size, as
the cache stops hiding the waste in each object. The benchmark never
measured below 1,000 elements, however, so the default threshold of 64
is not read off a chart; it is a cautious judgment (64 records of two
doubles are sixteen 64-byte cache lines), and `--min-size` changes it.

Each rule stops a different program; here are three, each with the
reason the real `viscosity explain` prints.

<Examples of="cost-model">

```js
const ws = [];
for (let i = 0; i < 500; i++)
  ws.push({ w: 'w' + i });
// kept: no field is provably numeric
```

```js
const ws = [];
for (let i = 0; i < 500; i++)
  ws.push({ n: i });
console.log(ws[9].n);
// kept: no loop reads or writes its fields
```

```js
const ps = [];
for (let i = 0; i < 40; i++)
  if (i % 2) ps.push({ x: i });
// (and a loop summing ps[i].x)
// kept: at most 40 elements: below …
```

</Examples>

In the first, the only field is a string, so the numeric rule stops it
(even with a loop reading `w` 500 times). In the second, `n` is a
number, but its only read, `ws[9].n`, is outside any loop. The third
reaches the size rule, and says "at most" because its `push` sits under
an `if`; the next section explains that 40.

## Guessing the size

The planner needs a size before the program has run. The analysis
counts the literal elements, then adds each `push`, multiplied by the
**trip count** (how many times a loop's body runs) of every loop around
it, when that loop is a plain counting loop with a constant bound like
`i < 1000`. A push inside nested loops of 20 and 30 trips counts 600.

<Formal title="The static size estimate">

```text
size = L + Σ   ∏   trips(ℓ)
          p∈P ℓ∋p
```

<span slot="read">The size is the number of literal elements L, plus,
for each push p in the set of pushes P, the product (∏) of the trip
counts of every loop ℓ that contains p (ℓ ∋ p reads "ℓ contains p"). A
push in no loop multiplies nothing, so it counts once.</span>
</Formal>

Three things can bend that number. A `push` under an `if` might not run
every time, so the count is only a maximum, and explain says "at most".
A loop whose bound is not a constant makes the size unknown. And a
`push` inside a function makes it unknown too, because the analysis
does not count how often the function is called. Step through five
programs:

<SizeSteps client:visible />

An unknown size *passes* the size rule. The planner is optimistic: when
it cannot tell, it assumes the collection may be large. In the last
program of the stepper (`spawn(10)` pushing ten points) that guess is
wrong, and measuring fixes it. `viscosity profile` runs the original
program with a little counting added, and writes down how long each
collection grew; *Profile-guided optimization* builds it. Fed back in,
the measured length replaces the estimate. After `viscosity profile
spawn.js -o prof.json`, the command `viscosity explain spawn.js --profile
prof.json` keeps `ps`, with the reason "about 10 elements (measured):
below the 64-element threshold".

## What the model leaves out

This is a simple model, and it does not look at

- **how hot a loop is**: any loop counts, even one that runs once, or
  lives in a function nobody calls (the analysis records trip counts,
  but the planner does not use them);
- **how many fields a loop touches**: explain prints "touches 1 of 2
  fields", and SoA gains most when a loop uses few of many fields, but
  the planner does not weigh it;
- **the costs SoA adds**: bounds checks and the generated code do not
  enter the model;
- **AoSoA**: the planner never chooses it on its own, only an annotation
  can;
- **the engine**: the thresholds come from Node on one machine.

The end-to-end results show why that matters. In the benchmark
matrix (`results/matrix-2026-10-31.md`) all five programs were
transformed and all got faster on Node, from 1.2× (`nbody`) to 4.37×
(`particles`); on Bun, `heat` gained 1.02× and `nbody` came out at
0.97×, within the noise the matrix warns about. Nothing in the model could have
told a gain of a fifth from a fourfold one, or seen that the engine
matters.

## What you learned

- A **cost model** estimates whether a safe change will pay off.
- The planner's rules run in order, first "yes" wins: unsafe, annotated,
  opt-in, Python, no numeric field, no loop, too small; else **soa**.
- SoA's measured lead grows with size; the threshold of 64 is a
  cautious judgment, changed with `--min-size`.
- The **size estimate** is literals plus pushes times constant trip
  counts; it can be a maximum or unknown, and a **profile** replaces it.
- The model ignores how hot a loop is, how many fields it uses and what
  SoA adds: simple, and explainable, on purpose.
