## The fields nobody reads

A game keeps its entities in an array of objects:

```js
const es = [];
es.push({
  x: 0, y: 0, vx: 1, vy: 0,
  health: 100, name: 'goblin',
});
```

Every frame a loop moves every entity, using `x`, `y`, `vx` and `vy`;
the name is printed only when an entity dies. Yet V8 keeps an object's
fields together, right after its header<Cite id="v8-fast-properties" />,
and the cache moves memory in whole 64-byte
lines<Cite id="slotin-amh-cache-lines" /> (*Cache lines and locality*),
so the movement loop drags `health` and a pointer to `name` through the
cache for every entity, and never looks at them.

<Analogy title="a toolbox with a tray">
A toolbox has a lift-out tray on top and a deep drawer below. The hammer
and screwdriver you use every day go in the tray; the pipe wrench you
need twice a year goes in the drawer. You keep the wrench; you just stop
lifting it every time you reach for the hammer.
<span slot="breaks">You can see at a glance which tools you use; a
compiler has to count, and a tool used rarely but always together with
the hammer would belong in the tray anyway.</span>
</Analogy>

*AoS vs SoA, measured* named the fix: a **hot/cold split**, which puts
the busy fields in one place and the rest in another, both indexed by
the same `i`:

```js
const hot = {
  x: [0], y: [0], vx: [1], vy: [0],
};
const cold = [
  { health: 100, name: 'goblin' },
];
for (let i = 0; i < n; i++)
  hot.x[i] += hot.vx[i];
```

`hot` keeps one array per busy field, and `cold` keeps the rarely used
fields of entity `i` in `cold[i]`; the loop at the end touches only
`hot`, so the cache lines it pulls in hold nothing else. The price is on
the cold side: code that wants a whole entity (to print it when it
dies, say) has to look in two places and stitch the halves together by
`i`. Here is what one cache line carries for the movement loop under
three layouts:

## Which fields go together?

"Hot" is a matter of counting. For each field, count how often the
program touches it; for each *pair* of fields, count how often one loop
uses both; and weight each loop by how many times it runs.

<Analogy extra title="a wedding seating plan">
To seat a wedding, you notice who talks to whom, and how much: the two
friends who chat all evening share a table, and the cousin who says one
"hello" to the bride's colleague does not need to sit next to them.
<span slot="breaks">Guests can be moved during the meal; a layout is
fixed before the program runs, so the counts must be good guesses
in advance.</span>
</Analogy>

<AffinitySteps client:visible />

<Callout kind="definition">
**Field affinity** measures which fields are used together. A simple
score for a pair of fields is the total run count of the loops that use
both. Fields with high affinity belong in the same group, and a field's
**hotness** (the run count of the loops that use it at all) decides
whether its group is hot or cold.
</Callout>

<Formal title="Hotness and affinity">

```text
hot(f)    = Σ { runs(L) : f ∈ fields(L) }
aff(f, g) = Σ { runs(L) : f, g ∈ fields(L) }
```

<span slot="read">The hotness of field f is the sum (Σ) of runs(L) over
every loop L whose fields include f. The affinity of f and g is the same
sum, taken only over loops that use both f and g.</span>
</Formal>

<Examples of="field-affinity">

```js
// move ×1000 uses x, vx
// draw ×1000 uses x, vx
aff('x', 'vx') // 1000 + 1000 = 2000
```

```js
// move ×1000: x, y, vx, vy
// damage ×100: x, health
aff('x', 'health') // 100
aff('vx', 'name')  // 0: never together
```

```text
es (line 1) {x, y, vx, vy, health,
  name} → struct of arrays
  · loop at line 6 in <module>()
    touches 4 of 6 fields (vy, y, vx, x)
  · loop at line 11 in <module>()
    touches 2 of 6 fields (health, x)
  · loop at line 14 in <module>()
    touches 1 of 6 fields (health)
```

</Examples>

In the first, both loops use the pair, so both runs count. In the
second, only `damage` uses `x` with `health`, so their affinity is its
100 runs, and `vx` with `name` is 0 because no loop uses both. The third
is real: `viscosity explain` on a 500-entity version of our game, where
the move loop sits inside a 1000-frame loop, the damage check inside a
100-round loop, and a final count of the dead runs once. Each "touches"
line is a loop's field list, exactly the raw data the formula needs;
multiply in each loop's runs (1000, 100 and 1, times 500 entities) and
you have every hotness and affinity. Run the counting yourself:

## What Viscosity does

Viscosity does not build a hot struct and a cold struct; it gives every
field its own column, the finest split there is, so a `move` loop over
its columns never reads `name`, whatever its affinity. What Viscosity
*does* decide per field is the representation. The corpus program
`mixed_columns.js` puts strings, numbers, `null` and objects in four
fields (`id`, `hp`, `x` and `tag`), and later writes `es[4].id = 42`.
Its report says, among other lines,

```text
· typed Float64Array columns for hp, x;
  plain array columns for id, tag (may
  hold non-numbers)
```

and the generated constructor, reformatted, is below. It starts the
length at 0 and the capacity at 16, makes a 16-slot `Float64Array` for
each numeric field, and an empty plain array for each other field (a
plain array grows by itself, so `grow()` only replaces the typed ones):

```js
constructor(cap = 16) {
  this.length = 0;
  this.cap = cap;
  this.hp = new Float64Array(cap);
  this.x = new Float64Array(cap);
  this.id = [];
  this.tag = [];
}
```

The numeric analysis from *Record shapes* proved `hp` and `x` are always
numbers, so they get columns of raw doubles<Cite id="mdn-typed-arrays" />;
`id` holds strings and later a number, and `tag` holds `null` or an
object, so they get plain arrays, which store any value.

Notice that this split is by *type*, not by heat. `tag` is read in the
hottest loop, yet it is a plain column, because a `Float64Array` cannot
hold an object; and a numeric field that is hardly ever read still gets
a typed column. The analysis even records each loop's trip count
(`trips` in `core/src/analysis.ts`), and the planner's profile option
has an unused slot for per-field read counts; however, nothing groups fields by
affinity today. Try the policy: make `id` a number, and it gets a typed
column too.

<Callout kind="engine" label="Under the hood">
Affinity matters when fields share storage. In packed AoS, and in the
blocks of *AoSoA code generation*, all of a record's fields sit in one
array, so the grouping of fields decides what each cache line carries.
A layout that put hot fields into one AoSoA array and kept cold ones in
plain columns would need exactly this chapter's counts; Viscosity
sidesteps the question by giving each field a column.
</Callout>

## What you learned

- A **hot/cold split** moves rarely used fields out of a hot loop's way;
  code that wants a whole record pays by looking in two places.
- **Field affinity** of a pair is the total runs of the loops that use
  both; **hotness** is the same count for one field.
- SoA is the finest split: each field its own column. Viscosity's real
  per-field decision is **typed or plain**, by type, not by heat.
