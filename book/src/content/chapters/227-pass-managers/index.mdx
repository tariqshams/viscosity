## Many passes, one program

Every optimisation in this part needs something worked out first:
constant propagation wants def-use lists, dead code elimination wants
liveness, loop-invariant code motion wants dominators and loops. Put a
dozen of them in a row and two problems appear at once. If each one
works out its own dominator tree, the same tree is built a dozen times;
and if they share one, then the moment a pass deletes a block, the
shared tree is *wrong*, and every pass after it makes decisions on facts
that are no longer true, which is exactly how a compiler miscompiles.

<Analogy title="one bowl of chopped onions">
A busy kitchen has many cooks who all need chopped onions, so rather
than each cook chopping their own, one bowl sits on the counter for
everyone. However, if someone tips sugar into that bowl, the next cook
must be told it is no good, and a fresh bowl must be made.
<span slot="breaks">A cook can taste the onions and notice the sugar; a
compiler cannot tell a stale dominator tree from a fresh one by looking
at it, so whoever changed the program has to say so.</span>
</Analogy>

<Analogy title="a printed street map">
A town prints a street map once and everyone uses it. Repainting a
house changes nothing on the map; digging up a road and building a new
one does, and until the map is reprinted it sends people the wrong way.
<span slot="breaks">A street map can be patched with a sticker; many
compiler analyses can only be thrown away and rebuilt, although some
(LLVM's dominator tree, for one) can be updated in place by a careful
pass.</span>
</Analogy>

The map is the picture to keep: some changes (rewriting the instructions
inside a block) leave the "streets" (the blocks and edges) alone, so the
analyses that depend only on the streets survive them.

<Callout kind="definition">
A **compiler pass** is one analysis or one transformation over the IR.
An **analysis pass** reads the IR and produces facts, like a dominator
tree; a **transformation pass** changes the IR, like dead code
elimination. LLVM's own catalogue describes its passes in three kinds,
analysis, transform and utility, and warns that even that list is
incomplete<Cite id="llvm-passes" />.
</Callout>

<Examples of="compiler-pass">

```text
dominators   reads the CFG, makes a tree
```

```text
dce          deletes unused instructions
simplifycfg  merges and removes blocks
```

```text
viscosity: lower → analyze → plan → emit
```

</Examples>

The first is an analysis: it changes nothing and produces a fact other
passes ask for. The second pair are transformations, and they differ in
what they touch: dead code elimination removes instructions but leaves
the blocks, while a CFG simplifier changes blocks and edges. The third
is Viscosity's whole compiler, four steps, which this chapter comes back
to.

## Order matters

Passes feed each other. Constant propagation can turn `if (n > 0)` into
`if (true)`, which makes the other arm dead, which gives dead code
elimination something to delete; inlining a call can expose constants
that constant propagation could not see before. Run them in a different
order and you get a different (often worse) program, and no single order
is best for every program; this is called the **phase-ordering
problem**, and real pipelines live with it by running cheap clean-up
passes several times. LLVM even notes that *how* passes are grouped can
change the result: running all loop passes on one loop before moving to
the next "may cause a later loop to be able to be optimized more" than
running each pass over every loop in turn<Cite id="llvmnewpm" />. In its
`opt` tool you write the order and the nesting yourself:

```text
opt -passes='function(sccp,dce)' a.ll
```

## Caching, then invalidating

A pass manager solves both problems from the top of the chapter. Passes
do not compute analyses themselves; they ask the manager, which returns
a cached result if it holds a valid one and otherwise computes, stores
and returns it. After a transformation it throws away whatever the
change may have made wrong. Step through four passes:

<PassSteps client:visible />

Only the pass knows what it changed, so in LLVM's new pass manager every
pass returns a `PreservedAnalyses` value, and the manager invalidates
everything not in it<Cite id="llvmnewpm" />:

```cpp
// changed nothing at all
return PreservedAnalyses::all();
// changed instructions, not blocks/edges
PreservedAnalyses PA;
PA.preserveSet<CFGAnalyses>();
return PA;
```

The first says "every cached fact is still true". The second is the map
analogy in code: the instructions changed, so def-use facts are gone,
but analyses that only care about the CFG, such as the dominator tree,
survive. A pass can also return `none()`, or update an analysis as it
goes (there is a `DomTreeUpdater` for exactly that) and then preserve it;
and much of the manager's complexity, its documentation admits, comes
from trying to invalidate as little as possible, because recomputing
costs compile time<Cite id="llvmnewpm" />.

<Callout kind="definition">
A **pass manager** is the scheduler that runs passes in order and
supplies them with analyses, computing each one at most once while it
stays valid. **Analysis invalidation** is throwing away cached facts
after a transformation that may have made them wrong: a pass reports
which analyses it **preserved**, and everything else is invalidated.
</Callout>

<Formal title="Which cached results survive a pass">

```text
keep(A) ⇔ A ∈ preserved(P)
          ∧ ∀ D ∈ deps(A). keep(D)
```

<span slot="read">After pass P, a cached analysis A is kept if and only
if P said it preserved A and, for every analysis D that A was built from,
D is kept too. (The ∀ reads "for every"; ∧ reads "and".) The second half
matters: a loop analysis built from a dominator tree that has been
thrown away cannot be trusted either.</span>
</Formal>

<Examples of="pass-manager analysis-invalidation">

```text
licm   asks for loops: miss, computed
unroll asks for loops: hit, reused
```

```text
constprop: preserves CFG analyses
  → uses dropped; dominators kept
```

```text
simplifycfg deletes a block:
  preserves none → everything dropped
```

</Examples>

The first is the cache at work: the second request costs nothing. The
second is the common middle case, an instruction-only change. The third
is the safe answer for a pass that changed the CFG and kept nothing up
to date. LLVM also nests managers: the IR comes in levels, module, then
(optionally) call-graph SCC, then function, then loop, each with its own
analysis manager, and an *adaptor* runs, say, a function pass over every
function of a module<Cite id="llvmnewpm" />. Try a tiny cache:

## Viscosity's pipeline, honestly

Here is the whole of Viscosity's `compile`, simplified, from
`packages/core/src/index.ts`:

```ts
const lowered = plugin.lower(source);
const analysis = analyze(lowered.module);
const p = plan(analysis, opts);
const code = plugin.emit(source,
  lowered, p);
```

Viscosity has **no pass manager**. It runs this one fixed sequence, and
it gets away with it because nothing after `lower` changes the IR: the
analyses only read it, and `emit` edits the original source text rather
than the IR. Inside `analyze`, though, numbered stages run in an order
written by hand:

<Figure takeaway="A fixed order, safe only because nothing changes the IR." caption="Viscosity's pipeline. Inside analyze, stage 2 meets array indexes before stage 3 knows which values are numbers, so it writes the checks down and stage 3's end does them.">
  <ViscosityPipeline />
</Figure>

```ts
// stage 2, walking the uses
indexChecks.push({ c, i });
// after stage 3, numeric inference
for (const { c, i } of indexChecks)
  if (!isNumberLater(i.args[1]))
    bail(c, 'indexes the array with' +
      ' something that may not be' +
      ' a number');
```

And there is one small cache already: bounds checks and loop access
patterns both need each function's dominators and natural loops, so a
helper, `info(f)`, computes them once and keeps them in a `Map` that is
never cleared. That is correct here, because the IR never changes while
`analyze` runs; put a transformation between two stages and the same
cache becomes a bug. Asking for analyses through a manager would fix
both at once: `safety` would ask for `numeric`, so the order would follow
by itself, and each transform would declare what it keeps.

<Callout kind="engine" label="Under the hood">
LLVM's new pass manager is the realistic model: analysis managers that
cache results per IR unit, passes that return `PreservedAnalyses`, and
adaptors that run inner passes inside an outer pipeline. Its own
documentation says the middle end uses the new manager while the
target-specific code generator still uses the legacy one<Cite id="llvmnewpm" />.
Viscosity's single `analyze` is the stage before all that: correct
because nothing changes the IR, with its order written by hand.
</Callout>

## What you learned

- A **compiler pass** is one analysis or transformation; optimisers are
  many small ones, and their **order** changes the result.
- A **pass manager** runs passes and caches the analyses they ask for,
  computing each at most once while it stays valid.
- **Analysis invalidation** throws away cached facts after a change.
  Each pass reports what it **preserved** (all, none, or a set such as
  the CFG analyses), and an analysis built from a dropped one is dropped
  too.
- Viscosity runs a fixed pipeline, lower → analyze → plan → emit, with
  no pass manager; that is safe only because nothing changes the IR.
