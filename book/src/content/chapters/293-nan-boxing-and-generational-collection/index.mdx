You met both ideas in *Measuring and speeding up the VM*: NaN-boxing,
which fits every value into one 8-byte double by hiding the non-numbers
inside NaN bit patterns, and the generational heap, which collects young
objects often and needs a write barrier to remember old objects that
point at young ones. *JavaScriptCore and SpiderMonkey* then showed two
real engines choosing opposite NaN encodings. This chapter goes further
on both: first the bet about pointer sizes that every 64-bit NaN-boxing
engine makes, and then what a write barrier would really cost the
companion VM, instruction by instruction, measured on its own
benchmarks. The chapters after it build the collectors themselves.

## A pointer has to fit

The teaching scheme of *Measuring and speeding up the VM* kept a 32-bit index in the low word; a
real engine written in C keeps a real pointer, and a pointer on a 64-bit
machine is, in principle, 64 bits. The trick only works because, in
practice, it is far smaller. On x86-64 with the usual 4-level page
tables, a virtual address has 48 significant bits, the top 16 must copy
bit 47, and user programs only ever get the lower half, so every
user-space pointer fits in **47 bits**. SpiderMonkey's 64-bit layout
(called PUNBOX64) relies on exactly that: it puts a 17-bit tag in bits
63 to 47 and the pointer in the 47 bits below, and its own allocator
makes sure every pointer it stores fits<Cite id="spidermonkey-value" />.

<Analogy title="a footpath over a low bridge">
A town runs a footpath across the top of a low road bridge, using the
space a tall vehicle would need, and that works only because the road
is signed for nothing taller than the bridge; the whole design rests on
the promise that no tall lorry will ever come along.
<span slot="breaks">A road sign is read by every driver, and a warning
bar stops the ones who miss it. The 47-bit promise is checked nowhere at run time: it holds
because the operating system and the engine's allocator agree to keep
memory low, and a pointer that broke it would silently corrupt the
tag.</span>
</Analogy>

The tall lorry exists. Newer x86 processors support **5-level paging**,
which gives user space 56 bits of address, and a 56-bit pointer would
run straight into the tag field. The Linux kernel's documentation says
plainly that "at least some JIT compilers use higher bits in pointers
to encode their information", that such pointers collide with valid
5-level addresses, and that for this reason the kernel does not hand
out addresses above 47 bits unless a program asks for them with a high
hint to `mmap`. SpiderMonkey's header makes the matching promise from
its side: large addresses are opt-in, "and we simply don't use
them"<Cite id="spidermonkey-value" />.

## Reading a SpiderMonkey Value

The tags are chosen so that the common questions cost one instruction.
Doubles are stored as themselves, and every non-double tag has its top
bit set, so any 64-bit pattern up to `0xfff80000ffffffff` (the largest
pattern that is still a double, a NaN produced by hardware included) is
a double, and anything above is boxed: the test "is this a double?" is
one unsigned compare<Cite id="spidermonkey-value" />. Above that line,
the tag says what the rest holds; an int32 has the tag `0x1fff2` and an
object the tag `0x1fffc`, which, shifted up by 47, puts `fff9` and
`fffe` at the top of the word. Values are easiest to try out with a
**BigInt**, JavaScript's integer of any size (written `5n`), whose
`<<`, `>>`, `&` and `|` work on all 64 bits at once:

```js
const v = new DataView(
  new ArrayBuffer(8));
v.setFloat64(0, 1.5);
v.getBigUint64(0).toString(16);
// '3ff8000000000000': a double
(0x1fffcn << 47n | 0x7f1234567890n)
  .toString(16);
// 'fffe7f1234567890': an object
```

The first three lines store `1.5` and read the same 8 bytes back as one
unsigned 64-bit BigInt, which is below the line, so a double. The last
builds an object Value by hand: the object tag shifted to bit 47, and an
address (a typical one for a 64-bit Linux heap) in the 47 bits below.
<More title="Unboxing a pointer, and why it is an XOR">

To get the pointer back, SpiderMonkey does not mask the tag off but
XORs the Value with the tag it expects: on an object Value that clears
the top bits exactly, while on a Value of any other type it leaves some
high bits set, so a wrongly speculated access (the Spectre attacks)
gets an unusable address rather than a real one<Cite id="spidermonkey-value" />.
That one instruction on every object access is the price *JavaScriptCore
and SpiderMonkey* weighed against JavaScriptCore's raw pointers.

</More>

The tag has one more user: the garbage collector. Because every Value
says whether it holds a pointer, the marker can scan a stack slot or an
object's field and know at once whether to follow it, with no separate
map of where the pointers are. V8 makes a different bargain: its values
are tagged pointers and Smis, and pointer compression shrinks each one
to 32 bits, which cut the V8 heap by up to 43%; NaN-boxed values can
never be smaller than the 8 bytes of a double<Cite id="v8-pointer-compression" />.

## Where the companion would need a barrier

The companion's collector has one generation and needs no barrier. To
make it generational, every instruction that stores a reference into a
heap object must run one, and finding them all is harder than it looks,
because some stores do not look like stores. Reading `vm.ts` and the
natives, the full list is:

```text
set.prop       o.f = v
index.set      xs[i] = v
push           push(xs, v)   (a native)
store.upvalue  only when closed
close.upvalue  stack value → upvalue
method         a method into a class
inherit        copies methods down
```

The first three are the obvious ones. `store.upvalue` writes into the
heap only once the upvalue is closed; while it is open, it writes a
stack slot, which is a root. `close.upvalue` (and `return`, which
closes upvalues too) is the hidden one: it copies a value off the stack
into an upvalue object that may have been allocated long ago and
promoted, so it can create an old-to-young pointer without any
assignment in the Drip program. `method` and `inherit` fill a class's
method table, which is only safe to skip if classes are always young
when it happens. The stores that need nothing are as instructive:
`store.local` and `store.global` write the stack and the globals table,
which a minor collection scans as roots anyway, and the stores that
fill a brand-new list or bound method write into an object
that is young by construction. (A new closure is young too, but
capturing its upvalues can allocate, and a collection in between would
promote it; skipping a barrier is only safe when nothing can allocate
between the allocation and the store.)

## What the barrier costs

To see what a barrier would do, I added a counter at each of those
sites in a copy of the companion and ran its benchmarks, calling an
object *old* once it had survived a collection (so one survival
promotes). Each row counts the stores that would run the barrier, how
many stored an object rather than a number or `none`, and how many of
those wrote a young object into an old one:

```text
program        checks  objects  old→young
instantiation 1200002   400002          0
closures       320004        4          0
sort          1832669  1632669     184681
trees          651272   323592          0
```

Nearly every check is wasted. In `instantiation` two stores in three
write numbers, and the object stores go into records allocated moments
before, so they are young; `closures` stores almost no objects at all;
`trees` builds each tree from new nodes, so again nothing old is
written. Only `sort` creates old-to-young pointers, and many of them:
it pushes fresh records into a list that a collection has promoted, and
then quicksort swaps them around inside it. However, in all 184,681 of
those stores, only **4** distinct objects needed remembering (the list
being filled at the moment each of the four collections ran), because
an object only needs to be in the remembered set once.

That is why barriers usually keep a **remembered bit** in each object:
the first old-to-young store into an object sets it and adds the object
to the remembered set, and every later one sees the bit and stops. The
next minor collection scans the set, promotes the survivors and clears
the bits. Step through it:

`store` is the barrier: it counts every check, returns at once for a
number, returns for a young owner or an old value, and only for an old
owner and a young value looks at the bit. `minor` promotes every young
object (in this toy, everything survives, because the list holds it all)
and clears the bits. Five thousand fresh objects stored into an old
list make 5,000 old-to-young stores but only 5 entries, one per minor
collection, and the 5,000 number stores afterwards are checked and
cost nothing else. V8's Scavenger keeps its remembered sets per page of
memory, as slot sets, rather than per object, for the same reason: the
set must stay small while the stores it records are
many<Cite id="v8-orinoco-scavenger" />.

## What you learned

- A 64-bit NaN-boxing engine bets that pointers fit in **47 bits**;
  5-level paging breaks the bet, so Linux and SpiderMonkey keep large
  addresses opt-in.
- SpiderMonkey's tags make "is it a double?" one unsigned compare, and
  an object pointer one mask away; every Value also tells the collector
  whether it holds a pointer.
- A generational companion would need barriers at seven instructions,
  including the hidden **close.upvalue**; locals, globals and fresh
  objects need none.
- Measured, almost every barrier check finds nothing to record, and a
  **remembered bit** keeps the remembered set to one entry per object.
