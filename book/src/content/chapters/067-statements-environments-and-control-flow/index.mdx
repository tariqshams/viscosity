## A calculator with no memory

The evaluator from the last chapter can work out `(1 + 2) * 3`, and
then it forgets; it cannot keep a running total, it cannot give a name
to a result, and it cannot even show you an answer unless something
prints it. Real programs *do* things, one after another, and they
remember what they did. In Drip, the parts that do things are
**statements**, and this chapter teaches the interpreter to run them.

## A program is a list

The parser does not return one tree for a whole program; it returns an
array of trees, one per statement, in the order they were written.
Running the program is a loop over that array, and this is `interpret`
from `companion/ts/src/interpreter.ts` (the `locals` argument comes from
the resolver, a later chapter, so ignore it for now):

```ts
interpret(statements: Stmt[],
          locals: Locals): void {
  // ...
  for (const s of statements)
    this.execute(s);
}
```

<Analogy title="a numbered recipe">
Step 4 can use the onion you chopped in step 2, but not one you will
only chop in step 6; and if the pan catches fire at step 5, you stop
there, with steps 1 to 4 done and steps 6 and 7 never started.
<span slot="breaks">A cook can do two steps at once, or skip one that
looks pointless; the interpreter does exactly one statement at a time,
in written order, and skips nothing.</span>
</Analogy>

<Callout kind="definition">
In Drip, a **program is a list of statements**. The interpreter runs
them one at a time, top to bottom; each runs to completion before the
next starts, and a runtime error stops the list where it is, so earlier
output stays and later statements never run.
</Callout>

## Statements make things happen

Here are the three statements of this chapter, from `execute` (the real
one also reports how each statement finished, which loops will need in
a later chapter):

```ts
case 'expression':
  this.evaluate(s.expression); // dropped
  return NORMAL;
case 'print':
  this.out(stringify(
    this.evaluate(s.expression)));
  return NORMAL;
case 'let':
  this.env.define(s.name.lexeme,
    s.initializer
      ? this.evaluate(s.initializer)
      : null);
  return NORMAL;
```

`evaluate` hands back a value, but no statement does: a statement is
worth running only for what it *changes*. `print` changes the world
outside the program, by adding a line of output; `let` changes the
program's memory, by adding a variable (`none`, held as `null`, when
there is no `=`). An **expression statement** evaluates its expression
and drops the value, so `1 + 2;` is legal Drip that does nothing you can
see<Cite id="mdn-expression-statement" />. It exists for expressions
that change something while they are evaluated, like an assignment.

<Figure takeaway="A statement is run for what it changes, not for a value." caption="The three statements of this chapter and where each one leaves its mark: print on the output, let on the table of variables, and an expression statement nowhere, unless its expression changes something itself.">
  <StatementEffects />
</Figure>

<Analogy extra title="a receipt printer and a till drawer">
Ringing up a sale works out a total, but nobody cares about the number
inside the machine; what matters is what it leaves behind, a printed
receipt and more money in the drawer. Those leftovers are the side
effects.
<span slot="breaks">A shop wants the total too; an expression statement
genuinely throws its value away, and only the leftovers survive.</span>
</Analogy>

<Callout kind="definition">
A **side effect** is a change that running code makes to the world
beyond producing a value: printing output, or creating or changing a
variable. Statements exist for their side effects, and an expression
statement keeps only the side effects of its expression.
</Callout>

<Examples of="program-as-list side-effect">

```text
print 1;
print 2;    # 1, then 2
```

```text
1 + 2;      # legal; prints nothing
```

```text
let n = 0;
n += 5;     # the change is the point
print n;    # 5
```

</Examples>

The first prints `1` and then `2`, because the list runs in order. The
second is a whole program with no visible effect: the sum is worked out
and dropped. The third is how real programs use expression statements:
`n += 5;` is an assignment whose value (`5`) is dropped, but whose side
effect, `n` changing, is what the next line prints.

## A table of globals

Where does `let` put its variable? At the top level of a program, in one
table of names and values that the whole program shares, the
interpreter's `globals`, a `Map` from name strings to runtime values.
Using a variable looks its name up there, and assigning overwrites an
entry that must already exist; simplified from `lookUp` and `assign`:

```ts
case 'variable': {
  const v = globals.values.get(name);
  if (v === undefined)
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  return v;
}
case 'assign': {
  const v = this.evaluate(e.value);
  if (!globals.values.has(name))
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  globals.values.set(name, v);
  return v;
}
```

(`name` is `e.name.lexeme`; `undefined` is safe as "missing", because
no Drip value is held as `undefined`.) Notice that the assignment
*returns* the value: assignment is an expression with a side effect,
which is why `print a = 3;` prints `3`. For `x += e`, the companion
reads the old value of `x` once, adds the value of `e` with the ordinary
`+` rules, and stores the sum. Step through a program and watch the
table and the output change:

<Analogy extra title="the whiteboard in a shared kitchen">
Anyone in the house can write "milk: 2" on the board, read it, or rub
out the 2 and write 3; there is one board, and everyone sees the same

<span slot="breaks">If you look for "eggs" on a real board and it is not
there, you shrug; Drip stops with a runtime error, because a missing
name is far more likely a typo than a plan.</span>

<Callout kind="definition">
A **global variable** is one declared at the top level of a program,
outside any block. It lives in one table shared by the whole program,
from the moment its `let` runs until the program ends. At the top level
`let` always defines, replacing an old variable of the same name, while
reading or assigning a name needs it to exist already.
</Callout>

<Examples of="global-variable">

```text
let a = 1;
print a;    # 1
```

```text
print b;    # error: undefined variable 'b'
let b = 2;
```

</Examples>

The first defines `a` and then finds it. The second is a
spot-the-difference with the first: the same two lines in the other
order stop with `runtime error: undefined variable 'b'`, because the
table is filled in as the program runs, and when the `print` runs no
`let` has added `b` yet. The runnable one keeps a total across lines,
uses `+=`, prints the value of an assignment, and then replaces `total`
with a second top-level `let`, which Drip allows for globals.

## What you learned

- A Drip **program is a list of statements**, run in order; a runtime
  error stops the list, and earlier output stays.
- Statements run for their **side effects**: `print` writes output and
  `let` creates a variable; an expression statement drops its value.
- **Global variables** live in one table: `let` defines, a name looks

## Two variables, one name

At the end of the last chapter every Drip variable lived in one table,
the globals, and that works until someone writes a block:

```text
let a = "global";
{
  let a = "block";
  print a;
}
print a;
```

Drip, like JavaScript<Cite id="mdn-block" />, has block scope, so this
should print `block` and then `global`: the inner `a` is a *different
variable* that happens to share a name, and it should vanish at the
closing `}`. With one table, however, the second `let` overwrites the
first, the program prints `block` twice, and the outer `a` is lost for
good. One table per program is not enough; we need one table per
*block*, and a way for the tables to find each other.

## Environments

<Analogy title="sticky notes on nested folders">
Each folder in a filing cabinet has a sticky note on its cover listing a
few names and numbers, and every folder sits inside a bigger folder. To
add a name you write on the note in your hand; to find one, you read
that note first, and if it is not there you look at the note on the
folder around it, and so on outwards.
<span slot="breaks">You can open any folder in the cabinet; the
interpreter only ever looks outwards from where it is, never into a
folder nested deeper or beside it.</span>
</Analogy>

That picture is a small class. The companion's `runtime.ts` keeps
exactly this data in its `Environment`:

```ts
class Environment {
  values = new Map<string, Value>();
  enclosing: Environment | null;
  constructor(enclosing:
      Environment | null = null) {
    this.enclosing = enclosing;
  }
  define(name: string, value: Value) {
    this.values.set(name, value);
  }
}
```

The `Map` holds this block's names and their runtime values;
`enclosing` is a reference to the parent environment, or `null` for the
globals, which have no parent. `define` only ever touches *this* table,
and it is what `let` calls.

<Callout kind="definition">
An **environment** is a table from names to values, plus a reference to
an **enclosing** (parent) environment. The interpreter always has one
**current** environment, and `let` **defines** a name in the current
environment without looking anywhere else.
</Callout>

## Looking a name up

Reading a variable is where the parent arrow earns its keep. Here is a
lookup that walks the chain (we will meet the companion's faster
version in a moment):

```ts
get(name: string): Value {
  if (this.values.has(name))
    return this.values.get(name)!;
  if (this.enclosing)
    return this.enclosing.get(name);
  throw new RuntimeError(/* token */,
    `undefined variable '${name}'`);
}
```

Check here; on a miss, ask the parent, which checks *its* table and asks
*its* parent, a recursive walk along a chain of references. Only when
the walk falls off the end, past the globals, is the name truly
undefined. `assign` walks the same way and overwrites the first table
that has the name, so it never creates a variable. Step through the
program and watch where each `let` writes and which boxes each lookup
checks:

<EnvSteps client:visible />

<Formal title="Looking a name up">

```text
look(E, x) = E.values(x)    if x in E
look(E, x) = look(P, x)     if not, and
                            E's parent is P
look(E, x) = error          otherwise
```

<span slot="read">To look up the name x starting at environment E: if E
has x, the answer is its value there; if not, and E has a parent P, the
answer is whatever looking x up from P gives; and if E has no parent,
x is undefined, which is an error.</span>
</Formal>

<Callout kind="definition">
The **scope chain** is the line of environments from the current one,
through each parent, to the globals. A lookup walks it and stops at the
**first** environment that has the name; if none does, it is a runtime
error. When an inner environment defines a name that an outer one also
has, the inner variable **shadows** the outer one: inside that block,
the outer variable cannot be reached by name at all.
</Callout>

<Figure takeaway="The lookup stops at the first match, so the nearer a hides the farther one." caption="Inside the inner block, a lookup of a starts at the current environment and stops there; the global a is still alive, only hidden. A lookup of b finds nothing nearby and walks out to the globals.">
  <ShadowPicture />
</Figure>

<Analogy extra title="a nickname at home">
At home your family calls you "Bee", and anyone saying "Bee" there means
you, even though your aunt across town is also called Bee; the nearer
Bee wins, and the farther one is untouched.
<span slot="breaks">Your aunt can still be reached by her full name; a
shadowed Drip variable cannot be reached at all from inside the block,
because Drip has no "full name" for it.</span>
</Analogy>

<Examples of="environment scope-chain shadowing">

```text
let n = 1;
{ print n; }   # 1: found one level up
```

```text
let n = 1;
{ n = 2; }     # assign walks out
{ let n = 3; } # a new n, gone at }
print n;       # 2
```

<Run id="shadow" />

</Examples>

In the first, the block's own table is empty, so the lookup walks one
step out and finds the global `n`. The second shows that `let` and `=`
do opposite things to the chain: `n = 2;` walks outwards and changes the
global, while `let n = 3;` makes a new `n` that shadows it and vanishes
at the `}`, so the last line prints `2`. The runnable one has three
levels and an assignment that lands in the middle one.

A common slip is to use the outer value to start the inner one:

```text
let a = 1;
{ let a = a + 1; }
# line 2: cannot read 'a' in its own
# initialiser
{ let b = a + 1; print b; }   # 2
```

Drip refuses the first block before anything runs (a compile error, so
exit code 65), because the inner `a` already exists, unset, while its
own initialiser runs; giving it a different name works. Declaring the
same name twice in one block (`{ let x = 1; let x = 2; }`) is refused
the same way, with `'x' is already declared in this scope`, while at the
top level a second `let` replaces a global. A pass called the resolver
checks these rules, and has its own chapter.

## Entering and leaving a block

The interpreter keeps the current environment in a field, `this.env`. A
block statement makes a fresh environment whose parent is the current
one, and runs its statements inside it:

```ts
case 'block':
  return this.executeBlock(s.statements,
    new Environment(this.env));
```

```ts
executeBlock(statements: Stmt[],
             env: Environment) {
  const previous = this.env;
  this.env = env;
  try {
    for (const s of statements) { /*...*/ }
  } finally {
    this.env = previous;
  }
}
```

Leaving the block means switching back to `previous`; nobody destroys
the block's environment by hand, because once nothing refers to it, it
is garbage like any other unreachable object. The `finally` is there
because a block does not always end at its `}`: a runtime error halfway
through throws straight out, and without the `finally` the interpreter
would be left inside the dead block's environment.

<Prompts ids={['block-new-env', 'finally-why']} />

<Callout kind="engine" label="Under the hood">
The walking `get` costs one `Map` lookup per environment on the way up,
every time the line runs. The companion does better: its `Environment`
has `getAt(distance, name)` and `assignAt` instead of `get` and
`assign`, because the resolver works out *before* running how many hops
up each local variable lives, and the interpreter jumps straight there.
It finds the same variable as the walk, only faster. JavaScript's own
scopes form the same chain of outer scopes that inner code can
see<Cite id="mdn-closures" />.
</Callout>

## What you learned

- An **environment** is a table from names to values with a reference
  to its **enclosing** environment; the globals have no parent, and
  `let` defines in the current one only.
- Lookups and assignments walk the **scope chain** outwards and stop at
  the first match; falling off the end is a runtime error.
- An inner variable **shadows** an outer one with the same name until
  its block ends.
- Each block runs in a fresh environment, and `executeBlock` puts the
  old one back in `finally`.

## A program that cannot change its mind

Every Drip program so far runs straight down the page: each statement
runs exactly once, in order, and then the program ends. You cannot print
"big" only when a number is big, and you cannot add up the numbers from
1 to 100 without writing a hundred lines. Real programs choose and
repeat, and this chapter teaches the interpreter both.

## Choosing: if and else

<Analogy title="points on a railway">
A train runs along one track until it reaches a set of points, where a
lever sends it left or right; which way depends on how the lever is set
at the moment the train arrives.
<span slot="breaks">A train always ends up somewhere; an `if` with no
`else` may take neither branch, and simply carry on with the next
statement.</span>
</Analogy>

Drip writes the condition without brackets and the body always in
braces: `if n > 3 { print "big"; }`. The interpreter's part is three
lines of `execute`:

```ts
case 'if':
  if (isTruthy(this.evaluate(s.condition)))
    return this.execute(s.then);
  if (s.else) return this.execute(s.else);
  return NORMAL;
```

It evaluates the condition, asks Drip's truthiness rule (so `0` and `""`
choose the `then` branch), and runs one branch or neither. Each branch
is a block, so it gets its own environment, exactly as in the last
chapter. There is no special node for `else if`: when the parser sees
`else if`, it parses the second `if` as the whole `else` branch, so a
chain of them is ifs nested inside elses.

<Callout kind="definition">
**Control flow** is the order in which a program's statements run, and
the parts of a language that change it: `if` chooses which statement
runs next, and loops send the program back to run statements again.
</Callout>

<Prompts ids={['if-truthy', 'else-if-nested']} />

## Repeating: while, break and continue

`while` repeats its body while the condition is truthy, and each time
round the body gets a fresh environment:

```ts
case 'while':
  while (isTruthy(
      this.evaluate(s.condition))) {
    const c = this.executeBlock(s.body,
      new Environment(this.env));
    if (c === BREAK) break;
    if (c === RETURN) return c;
  }
  return NORMAL;
```

What is `c`? `break` and `continue` may sit deep inside the body (in an
`if`, in a block in an `if`), and they must stop work at every level on
the way out. So every `execute` hands back a small **completion** value
saying how the statement finished: `NORMAL`, `BREAK`, `CONTINUE` or
`RETURN`. The `break` statement just returns `BREAK`; `executeBlock`
stops its own list at the first statement that does not finish normally
and passes the value up. The loop then decides: `BREAK` ends it,
`CONTINUE` goes straight to the next test of the condition, and
`RETURN` (for functions, later) keeps travelling. Both statements apply
to the innermost loop, as in JavaScript<Cite id="mdn-break" /><Cite id="mdn-continue" />,
and outside a loop they are compile errors (`'break' outside a loop`).

## for, and rewriting one loop as another

Drip has one more loop, `for i in a..b { ... }`, which runs the body
with `i` set to `a`, `a + 1`, and so on while `i < b`. It looks like
something we could build out of parts we already have: a block, a
`let`, a `while` and a `+=`. Turning a construct into simpler ones like
that is called **desugaring** (the nicer spelling is the "sugar"), and
it is often done in the parser so that the back end has fewer kinds of
node to run.

<Analogy extra title="recipe shorthand">
A recipe says "make a white sauce", and an experienced cook expands that
into melt butter, stir in flour, add milk slowly; the short form is
easier to read and means exactly the long one.
<span slot="breaks">A cook can expand loosely; a desugaring must keep
*every* behaviour of the original, including the odd cases, or programs
quietly change meaning.</span>
</Analogy>

<Figure takeaway="A rewrite must keep every behaviour, and continue is the one that breaks this one." caption="A for loop and the while loop it seems to mean. The hidden end and k must not clash with your names, i must be fresh each time round, and a continue in the body would skip the k += 1 on the right, looping for ever.">
  <DesugarFor />
</Figure>

Look at the right-hand side carefully. `b` must be evaluated once, so it
needs a hidden variable; `i` is a fresh variable each time round
(assigning to it does not change which values come next), so the
counter has to be a different hidden `k`; and a `continue` in the body
jumps straight back to the test, *skipping* `k += 1`, so the loop never
ends. For these reasons the companion keeps a real `for` node and runs
it directly, in `forLoop`:

```ts
let i = start; // start and end: numbers
next = () => (i < end ? i++ : undefined);
for (let v = next(); v !== undefined;
     v = next()) {
  const loopEnv = new Environment(this.env);
  loopEnv.define(s.name.lexeme, v);
  // run the body; BREAK ends the loop
}
```

`start` and `end` are evaluated once, before the loop, and checked to be
numbers (`a range must start with a number, not a string`). Each value
gets its own `loopEnv`, which is how each time round has a fresh `i`,
the same choice JavaScript makes for `let` in a `for`<Cite id="mdn-for" />.

<Callout kind="definition">
**Desugaring** is rewriting a construct of a language in terms of
simpler constructs it already has, so that the rest of the
implementation needs to handle fewer kinds of node. In Drip, `else if`
is desugared into an `if` inside an `else`.
</Callout>

<Examples of="control-flow desugaring">

```text
if 0 { print "yes"; }   # yes: 0 is truthy
```

```text
for i in 0..3 { print i; }  # 0, 1, 2
for i in 3..0 { print i; }  # nothing
```

<Run id="loops" />

</Examples>

The first runs its body because `0` is truthy in Drip. In the second,
the range stops *before* `b`, so `0..3` gives three values and `3..0`
gives none at all. The runnable one adds up the numbers from 1 to 100
that are not multiples of 3: `continue` skips the multiples, and the
total is `3367`.

## && and || skip the right side

`&&` and `||` look like binary operators, but they cannot be, because a
binary node evaluates *both* children before it looks at the operator.
`false && x` already knows its answer after the left side, and so does
`true || x`; the right side should never run. The parser therefore gives
them their own node, `logical`, and the interpreter evaluates the right
side only when it is needed:

```ts
case 'logical': {
  const left = this.evaluate(e.left);
  if (e.operator.type === '||')
    return isTruthy(left) ? left
      : this.evaluate(e.right);
  return isTruthy(left)
    ? this.evaluate(e.right) : left;
}
```

The result is one of the operands, not always a boolean, which is also
how JavaScript's `||` behaves<Cite id="mdn-logical-or" />.

<Analogy extra title="a door with two checks">
A doorman checks your ticket first and your coat second; if you have no
ticket he sends you away without even looking at your coat.
<span slot="breaks">The doorman answers yes or no; Drip's `&&` and `||`
hand back one of the values they looked at, which may be a number or a
string.</span>
</Analogy>

<Callout kind="definition">
An operator **short-circuits** when it skips evaluating its right side
because the left side already decides the result: `&&` stops at a falsey
left side and `||` at a truthy one. Each produces the operand it stopped
at.
</Callout>

<Formal title="The two rules for &&">

```text
a ⇓ v    v falsey
─────────────────
   a && b ⇓ v

a ⇓ v    v truthy    b ⇓ w
──────────────────────────
       a && b ⇓ w
```

<span slot="read">Read ⇓ as "evaluates to". First rule: if a evaluates
to a falsey v, then a && b evaluates to v, and b is not mentioned above
the line at all, so it is never evaluated. Second rule: if a evaluates
to a truthy v and b evaluates to w, the whole expression is w. The
rules for || are the same with truthy and falsey swapped.</span>
</Formal>

<Examples of="short-circuit">

```text
print none || "default";  # default
```

```text
print 1 && 2;    # 2
print 0 || 5;    # 0: 0 is truthy
```

```text
print false && missing;   # false
```

</Examples>

`none` is falsey, so `||` moves on and returns `"default"`, the common
way to give a fallback value. `1 && 2` returns its right operand, `2`,
because the left was truthy; `0 || 5` returns `0`, because in Drip `0`
is truthy. The last line is the proof that the right side never runs:
`missing` was never defined, yet there is no runtime error.

## What you learned

- **Control flow** is which statement runs next: `if` picks a branch by
  truthiness, and `while` repeats with a fresh environment each time.
- `break` and `continue` travel outwards as a completion value until the
  innermost loop handles them.
- **Desugaring** rewrites a construct as simpler ones; `else if` is
  desugared, while `for` keeps its own node because the rewrite is
  easy to get wrong.
- `&&` and `||` **short-circuit**: they skip the right side when the left
  decides, and produce an operand.
