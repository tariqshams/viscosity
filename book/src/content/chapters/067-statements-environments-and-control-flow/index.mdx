## A calculator with no memory

The evaluator of *Running expressions: a tree that computes* can work
out `(1 + 2) * 3`, and then it forgets; it cannot keep a total, name a
result, choose, or repeat.

## Statements, side effects and globals

The parser hands over an array of statement trees, one per statement,
and running the program is a loop, `for (const s of statements)
this.execute(s);`. Here are three cases of `execute`, from
`companion/ts/src/interpreter.ts`:

```ts
case 'expression':
  this.evaluate(s.expression); // dropped
  return NORMAL;
case 'print':
  this.out(stringify(
    this.evaluate(s.expression)));
  return NORMAL;
case 'let':
  this.env.define(s.name.lexeme,
    s.initializer
      ? this.evaluate(s.initializer)
      : null);
  return NORMAL;
```

No statement hands back a value: a statement is worth running only for
what it *changes*. `print` adds a line of output, `let` adds a variable,
and an expression statement drops its value, so `1 + 2;` is legal Drip
that does nothing you can see<Cite id="mdn-expression-statement" />.

<Figure takeaway="A statement is run for what it changes, not for a value." caption="The three statements and where each one leaves its mark: print on the output, let on the table of variables, and an expression statement nowhere, unless its expression changes something itself.">
  <StatementEffects />
</Figure>

<Callout kind="definition">
In Drip, a **program is a list of statements**, run one at a time, top
to bottom; a runtime error stops the list where it is. A **side effect**
is a change that running code makes beyond producing a value, such as
printing or changing a variable. A **global variable** is declared at
the top level and lives in one table shared by the whole program; `let`
defines a name, while reading or assigning one needs it to exist.
</Callout>

<Examples of="program-as-list side-effect global-variable">

```text
let n = 0;
n += 5;     # the change is the point
print n;    # 5
print m;    # error: undefined variable 'm'
print 1;    # never runs
```

</Examples>

`n += 5;` is an expression statement: the assignment's value is
dropped, but its side effect, `n` changing, is what the next line
prints. `m` was never defined, so the fourth line stops the program,
after `5` has been printed and before `print 1;` runs. Step through a program and watch the table and the
output change:

<More title="Lookup and assignment in the globals, and a running total">

Simplified from `lookUp` and `assign` (`undefined` is safe as "missing",
because no Drip value is held as `undefined`):

```ts
case 'variable': {
  const v = globals.values.get(name);
  if (v === undefined)
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  return v;
}
case 'assign': {
  const v = this.evaluate(e.value);
  if (!globals.values.has(name))
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  globals.values.set(name, v);
  return v;
}
```

The assignment *returns* its value, which is why `print a = 3;` prints
`3`; and at the top level a second `let` replaces a global.

## Environments: a table per block

One table is not enough once someone writes a block. In `let a = 1; {
let a = 2; print a; } print a;` the inner `a` is a *different variable*
that happens to share a name, because Drip, like JavaScript<Cite
id="mdn-block" />, has block scope; the program must print `2` then `1`.
With one table the second `let` would overwrite the first.

<Analogy title="sticky notes on nested folders">
Each folder in a filing cabinet has a sticky note on its cover listing a
few names and numbers, and every folder sits inside a bigger folder. To
add a name you write on the note in your hand; to find one, you read
that note first, and if it is not there you look at the note on the
folder around it, and so on outwards.
<span slot="breaks">You can open any folder in the cabinet; the
interpreter only ever looks outwards from where it is, never into a
folder nested deeper or beside it.</span>
</Analogy>

So each block gets a table of its own, with a reference to the table
around it. `define` writes only in the current table; `get` checks the
current table, then asks the parent, and so on out to the globals, and
`assign` walks the same way. Step through a program and watch where each
`let` writes and which tables each lookup checks:

<EnvSteps client:visible />

<Callout kind="definition">
An **environment** is a table from names to values, plus a reference to
an **enclosing** (parent) environment; the globals have none. The
**scope chain** is the line of environments from the current one,
through each parent, to the globals; a lookup walks it and stops at the
**first** environment that has the name. When an inner environment
defines a name an outer one also has, the inner variable **shadows** the
outer one: inside that block, the outer one cannot be reached by name.
</Callout>

<Examples of="environment scope-chain shadowing">

```text
let n = 1;
{ n = 2; }     # assign walks out
{ let n = 3; } # a new n, gone at }
print n;       # 2
```

</Examples>

`let` and `=` do opposite things to the chain. `n = 2;` finds no `n` in
its block's table, walks out and changes the global; `let n = 3;` makes
a new `n` that shadows the global and vanishes at the `}`. So the last
line prints `2`.

<Figure takeaway="The lookup stops at the first match, so the nearer a hides the farther one." caption="Inside the inner block, a lookup of a starts at the current environment and stops there; the global a is still alive, only hidden. A lookup of b finds nothing nearby and walks out to the globals.">
  <ShadowPicture />
</Figure>

<More title="The Environment class, entering a block, and what the resolver adds">

```ts
class Environment {
  values = new Map<string, Value>();
  enclosing: Environment | null;
  constructor(enclosing:
      Environment | null = null) {
    this.enclosing = enclosing;
  }
  define(name: string, value: Value) {
    this.values.set(name, value);
  }
}
```

A block statement runs `executeBlock(s.statements, new
Environment(this.env))`, which saves the current environment, switches
to the new one, runs the statements, and switches back in a `finally`,
so that a runtime error thrown halfway through does not leave the
interpreter inside a dead block's environment. Nobody destroys the old
environment by hand: once nothing refers to it, it is garbage.

<Run id="shadow" />

Drip also refuses `{ let a = a + 1; }` before anything runs (`cannot
read 'a' in its own initialiser`), and two `let`s of one name in the
same block; *The resolver* checks these rules, and works out before
running how many hops up each local lives, so the companion's `getAt`
jumps straight there. JavaScript's scopes form the same chain of outer
scopes<Cite id="mdn-closures" />.

<Analogy extra title="a nickname at home">
At home your family calls you "Bee", even though your aunt across town
is also called Bee; the nearer Bee wins, and the farther one is
untouched.
<span slot="breaks">Your aunt can still be reached by her full name; a
shadowed Drip variable cannot be reached at all from inside the block.</span>
</Analogy>

## Choosing and repeating

`if` evaluates its condition, asks Drip's truthiness rule (so `0`
chooses the `then` branch), and runs one branch or neither; each branch
is a block, so it gets its own environment. `while` repeats its body,
in a fresh environment each time, while the condition is truthy. A
`break` may sit deep inside the body, so every `execute` hands back a
*completion* value (`NORMAL`, `BREAK`, `CONTINUE` or `RETURN`); a
statement list stops at the first that is not `NORMAL` and passes it up,
and the loop ends on `BREAK` or moves to the next test on `CONTINUE`<Cite id="mdn-break" /><Cite
id="mdn-continue" />.

<LoopSteps client:visible />

`for i in a..b { ... }` runs the body with `i` set to `a`, `a + 1`, and
so on while `i < b`. It looks like something we could rewrite as a
`let` and a `while`, which is called **desugaring**; however, the
rewrite is easy to get wrong:

<Figure takeaway="A rewrite must keep every behaviour, and continue is the one that breaks this one." caption="A for loop and the while loop it seems to mean. The hidden end and k must not clash with your names, i must be fresh each time round, and a continue in the body would skip the k += 1 on the right, looping for ever.">
  <DesugarFor />
</Figure>

So the companion keeps a real `for` node, giving each value its own
environment (as JavaScript does for `let` in a `for`<Cite id="mdn-for"
/>); it does desugar `else if` into an `if` inside an `else`.

<Callout kind="definition">
**Control flow** is the order in which a program's statements run, and
the parts of a language that change it: `if` chooses which statement
runs next, and loops send the program back to run statements again.
**Desugaring** is rewriting a construct in terms of simpler constructs
the language already has, so the rest of the implementation handles
fewer kinds of node.
</Callout>

<Examples of="control-flow desugaring">

```text
for i in 0..4 {
  if i == 1 { continue; }
  if i == 3 { break; }
  print i;     # 0, then 2
}
```

</Examples>

At `0` neither `if` fires, so `0` is printed. At `1` the `continue`
returns `CONTINUE` out of its `if`, the body stops, and the loop moves
on; `2` is printed; at `3` the `break` travels out the same way and ends
the loop. Desugared into a `while` with `k += 1` at the end of the body,
that `continue` would have skipped the increment and looped for ever.

<More title="The if case, and a loop to run">

```ts
case 'if':
  if (isTruthy(this.evaluate(s.condition)))
    return this.execute(s.then);
  if (s.else) return this.execute(s.else);
  return NORMAL;
```

## && and || skip the right side

`&&` and `||` cannot be ordinary binary nodes, because a binary node
evaluates *both* children before it looks at its operator, and `false
&& x` already knows its answer. So they get their own node, `logical`,
which evaluates the left side, and the right side only when the left
does not decide.

<Callout kind="definition">
An operator **short-circuits** when it skips evaluating its right side
because the left side already decides the result: `&&` stops at a falsey
left side and `||` at a truthy one. Each produces the operand it stopped
at, not always a boolean, as in JavaScript<Cite id="mdn-logical-or" />.
</Callout>

<Examples of="short-circuit">

```text
print none || "default";  # default
print false && missing;   # false
```

</Examples>

`none` is falsey, so `||` moves on and returns `"default"`, the usual
way to give a fallback. In the second, `missing` was never defined, yet
there is no runtime error: the right side never runs.

<More title="The logical case">

```ts
case 'logical': {
  const left = this.evaluate(e.left);
  if (e.operator.type === '||')
    return isTruthy(left) ? left
      : this.evaluate(e.right);
  return isTruthy(left)
    ? this.evaluate(e.right) : left;
}
```

</More>

## What you learned

- A **program is a list of statements**, run in order for their **side
  effects**; **globals** live in one table.
- An **environment** is a table with a parent; lookups walk the **scope
  chain** to the first match, so inner names **shadow** outer ones.
- **Control flow**: `if` picks by truthiness, loops repeat, and `break`
  travels out as a completion value. **Desugaring** must keep every
  behaviour, which is why `for` keeps its own node.
- `&&` and `||` **short-circuit**.
