## SSA without a second pass

Building SSA put a finished CFG into SSA in two passes: place the phis
using dominance frontiers, then rename everything by walking the
dominator tree. A compiler that works that way needs the whole CFG, its
dominator tree and its frontiers first. VIR's builder has none of
those: like the single-pass compiler of Compiling expressions, it emits
instructions while it walks the syntax tree, and the IR comes out in
SSA form directly, with no version that has ordinary, reassignable
variables. The trick, from Braun and colleagues<Cite id="braun2013" />,
is to treat "what is the value of `x` here?" as a question a block can
answer, or pass on to the blocks before it.

## Each block keeps a notepad

<Analogy title="a whiteboard in every room">
Each room in a building has a whiteboard. When you set the thermostat in
a room, you write the new setting on that room's board. To find the
setting in a room with a blank board, you ask in the room you came
from; if people arrive from two rooms that give different answers, the
room needs a rule, "it depends on which door you came through".
<span slot="breaks">People forget to update whiteboards; the builder
writes every assignment down the moment it lowers it, and it also writes
the answer to every question it had to ask, so the next reader in that
room finds it at once.</span>
</Analogy>

Inside one block, SSA is a table: writing `x` records which value it now
holds, and reading looks it up. From `packages/core/src/builder.ts`:

```ts
writeVariable(v, block, value) {
  let m = this.defs.get(block);
  if (!m) this.defs.set(block,
    (m = new Map()));
  m.set(v, value);
}
readVariable(v, block) {
  const local =
    this.defs.get(block)?.get(v);
  if (local !== undefined) return local;
  return this.readVariableRecursive(
    v, block);
}
```

`v` is any key the front end chooses for a variable, and `defs` maps
each block to its own table (a `Map` from variable to value id).
`writeVariable` records the value in the block's table (creating the
table the first time), and `readVariable` looks there first. An assignment never
emits an instruction; it only writes into the table, which is why
`function f(x) { x = 2; return x; }` lowers to nothing more than
`%1 = const 2` and `return %1`.

## Asking the predecessors

When a block has no entry for `v`, `readVariableRecursive` asks the
blocks that lead to it. Simplified:

```ts
if (!this.sealed.has(block)) {
  val = incompletePhi(v, block);
} else if (b.preds.length === 1) {
  val = this.readVariable(
    v, b.preds[0]);
} else if (b.preds.length === 0) {
  val = undefinedConst();
} else {
  const phi = this.newPhi(block);
  this.writeVariable(v, block, phi.id);
  val = this.addPhiOperands(v, phi);
}
this.writeVariable(v, block, val);
```

Leave the first case for the next section. With **one predecessor**, the
answer is whatever `v` is there. With **no predecessors**, the variable
was read before any write, so it is `undefined`. With **several**, make a
phi, record it *first*, then read `v` in every predecessor to get its
operands; recording it first matters in loops, because if the search
comes back round to this block it finds the phi and stops, rather than
asking forever. The last line caches the answer, so the next read in
this block is a plain look-up.

<Formal title="Reading a variable">

```text
read(v, B) = def(v, B)     if B wrote v
           = read(v, P)    if pred(B) = {P}
           = φ(read(v, P₁), …, read(v, Pₙ))
                           otherwise
```

<span slot="read">To read v in block B: if B itself wrote v, the answer
is that value. Otherwise, if B has exactly one predecessor P, the answer
is whatever v is in P. Otherwise B has several predecessors P₁ to Pₙ,
and the answer is a phi whose operands are the reads of v in each of
them, in order (and if they all agree, the phi is not needed, as we will
see).</span>
</Formal>

## Loops: promise now, pay later

<Analogy title="a wedding planner with replies still coming in">
A planner is seating guests while invitations are still going out. For a
table whose guests are not all confirmed, she puts a "reserved" card and
a note to finish it once the last reply arrives.
<span slot="breaks">A planner can wait for replies before seating
anyone; the builder cannot wait, because the loop body it has not
lowered yet will itself read the variables, so the "reserved" phi has to
be usable as a value straight away.</span>
</Analogy>

A loop header is entered from before the loop *and* from the end of the
body; however, when the builder lowers the loop test, it has not lowered
the body yet, so the back edge does not exist and the header's list of
predecessors is incomplete. Braun and colleagues call a block **sealed**
once all its predecessors are known<Cite id="braun2013" />. Reading a
variable in an unsealed block creates an empty, **incomplete phi** and
remembers it, and sealing the block fills in every incomplete phi:

```ts
seal(block) {
  const inc = this.incomplete.get(block);
  if (inc) {
    for (const [v, phi] of inc)
      this.addPhiOperands(v, phi);
    this.incomplete.delete(block);
  }
  this.sealed.add(block);
}
```

The front end decides when. For a loop, `lower.ts` seals the header
right after it emits the back edge:

```ts
fb.br(head.id); // the back edge
fb.seal(head.id);
```

## Trivial phis

Look again at the step where the header asked "what is `n`?" and got a
phi, because it could not yet know that the loop never changes `n`.
Once sealed, the phi was `%4 = φ(%0, %4)`: whichever edge you take, it is
`%0`. A phi whose operands are all one value, apart from the phi
itself, is **trivial**:

```ts
let same = null;
for (const op of phi.args) {
  if (op === same || op === phi.id)
    continue;
  if (same !== null) return phi.id;
  same = op; // first other value
}
// replace every use of phi with same,
// then retry phis that used this phi
```

The loop skips operands equal to the value already found, or to the phi
itself; the moment it meets a *second* different value, the phi really
merges and is kept. Otherwise `tryRemoveTrivialPhi` rewires every use of
the phi (including branch conditions, returns and the definition tables)
to `same`, deletes the phi, and retries every phi that used it, since
removing one phi can make another trivial.

<Examples of="on-the-fly-ssa">

```text
x = 2      →   %1 = const 2
              (table: x → %1)
```

```text
b3: read x, preds disagree
    →  %4 = phi %2, %3
```

```text
b3: read y, preds agree
    %5 = φ(%2, %2)  →  removed
```

</Examples>

The first is the simplest case: an assignment emits only the value's own
instruction and writes the table. The second is a join where the
predecessors disagree, so the phi stays, as in the figure above. The
third is from real VIR for
`let x = 1; let y = 5; if (c) { x = 2; } return x + y;`: reading `y` at
the join made `%5 = φ(%2, %2)`, both edges agree, so it was replaced by
`%2`, and the listing jumps from `%4` to `%6`:

```text
  b3:  ; preds b1 b2
    %4 = phi %3, %1
    %6 = binop + %4, %2
    return %6
```

In the module's list of values, instruction 5 is left behind as a dead
entry noted `removed-trivial-phi`. Try the test on a few phis:

<Callout kind="pitfall">
Do not confuse "trivial" with "useless". `%3 = φ(%2, %10)`, the loop
counter, has two different operands and is kept even if nothing read
`i` after the loop; and `φ(%0, %4)` is removed even though the variable
is used everywhere, because it always means `%0`.
</Callout>

<Callout kind="engine" label="Under the hood">
Compared with placing phis at dominance frontiers<Cite id="cytron1991" />,
this method needs no dominator tree and works while the IR is still
being made, which suits a front end that lowers straight from a syntax
tree. V8's Maglev meets the loop problem too, while building SSA from
Ignition bytecode in one forward pass, and answers it differently: a
prepass finds which variables are assigned inside each loop, so Maglev
can create those loop phis before it processes the body, and fill in
the back-edge input at the end<Cite id="v8-maglev" />. VIR's builder
needs no prepass; it may create a few phis it does not need, and then
deletes them as trivial.
</Callout>

## What you learned

- **On-the-fly SSA construction** keeps a table of definitions per
  block; assignments only write into it.
- `readVariable` looks locally, then asks predecessors: one predecessor
  passes the question on; several make a phi, recorded first so loops
  terminate.
- An **unsealed** block (a loop header, before its back edge) gets
  **incomplete phis**, and `seal` fills them in.
- A **trivial phi** chooses only one value (or itself); it is replaced,
  and phis that used it are retried.
