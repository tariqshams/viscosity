## Spot the bug

```js
const a = { x: 0, y: 0, vx: 1, vy: 2 };
const b = { x: 5, y: 1, vx: 0, vy: 1 };
const c = { x: 2, y: 7, vX: 3, vy: 0 };

function move(p) {
  p.x = p.x + p.vx;
}
move(c); // c.x becomes NaN
```

`c` was typed with `vX` instead of `vx`, so `c.vx` is `undefined`, and
`2 + undefined` is `NaN` (JavaScript's "not a number"). Nothing warned
you. With a thousand particles written by hand, typos like this are
certain. And `move` floats around on its own, separate from the data it
works on.

You want a single blueprint that every particle is built from, with the
code that works on particles kept right next to it.

<Callout kind="intuition">
A class is a cookie cutter. Every cookie pressed out with it has the same
outline. Each cookie can still have its own icing: the same properties,
with different values.
</Callout>

## class, constructor and new

```js
class Particle {
  constructor(x, vx) {
    this.x = x;
    this.vx = vx;
  }
}

const p = new Particle(3, 1);
console.log(p.x, p.vx); // 3 1
console.log(p);
// Particle { x: 3, vx: 1 }
```

`new Particle(3, 1)` builds a particle. Step through what it does:

<Callout kind="definition">
A **class** is a blueprint for objects of the same kind<Cite id="mdn-classes" />.
Its **constructor** is the function that sets up each new object.
**`new`** creates a fresh empty object, runs the constructor with `this`
meaning that object, and returns it. The result is an **instance** of the
class. Every `new` makes a separate instance, with its own properties.
</Callout>

## Methods and this

Functions written inside the class body, next to the constructor, are
**methods**. Here is `move`, now living with the data:

```js
class Particle {
  constructor(x, vx) {
    this.x = x;
    this.vx = vx;
  }
  move() {
    this.x = this.x + this.vx;
  }
}

const p = new Particle(0, 2);
const q = new Particle(10, -1);
p.move();
q.move();
console.log(p.x, q.x); // 2 9
```

There's one `move`, and two particles. How does `move` know which one to
change? It doesn't take a parameter. It uses `this`.

<Callout kind="intuition">
`this` works like the word "me". The sentence "move me forward" is the
same sentence whoever says it, but it moves whoever is speaking. In
`p.move()`, `p` is speaking.
</Callout>

<ThisSteps client:visible />

<Callout kind="definition">
A **method** is a function stored on an object or a class. Methods written
in a class body are stored once, with the class, and shared by every
instance<Cite id="mdn-using-classes" />. Inside a method, **`this`** is
the object the method was called on: in `p.move()`, the object before the
dot<Cite id="mdn-this" />. It is decided freshly by each call.
</Callout>

Compare that with last chapter. What a function can *see* is decided by
where it is **written**. What `this` means is decided by how it is
**called**.

## Losing this

Since `this` comes from the dot, a method called without a dot has no
object to use:

```js
const m = p.move;
m();
// a TypeError: inside move,
// this is undefined
```

`m` is the same function, but `m()` has nothing before a dot, so inside it
`this` is `undefined`. (Class code always runs in JavaScript's *strict
mode*, which is what makes it `undefined` rather than something
stranger<Cite id="mdn-classes" />.) The exact error message differs from
browser to browser.

This bites most often with callbacks. Passing `p.move` passes only the
function, not `p`:

```js
function twice(f) {
  f();
  f();
}

twice(p.move);         // TypeError
twice(() => p.move()); // works
```

The arrow function keeps the dot: when `twice` calls it, it calls
`p.move()` properly, with `p` before the dot.

<Callout kind="pitfall">
`p.move` (no parentheses) is just the function. It doesn't remember `p`.
To hand a method to someone else, wrap it: `() => p.move()`.
</Callout>

## Which class made it? instanceof

```js
console.log(p instanceof Particle); // true

const fake = { x: 0, vx: 2 };
console.log(fake instanceof Particle);
// false
```

`fake` has exactly the same properties, but it wasn't made by
`new Particle`, and `instanceof` can tell.

<Callout kind="definition">
**`a instanceof C`** is `true` when the object `a` was made by the class
`C` (precisely: when the object holding `C`'s shared methods is in the
chain of objects that `a` borrows methods from<Cite id="mdn-instanceof" />). It checks where an object came from, not
what it contains.
</Callout>

<Prompts ids={['instanceof-what']} />

<Callout kind="engine" label="Under the hood">
Every `new Particle(...)` adds `x` and then `vx`, in the same order, through
the same constructor. Remember shapes from chapter 3: engines give objects
that have the same properties, added in the same order, one shared hidden
shape, and then they know where `x` sits in every one of them without
searching<Cite id="bynensmeurer2018" />. A class is the simplest way to make
thousands of objects that share a shape.

That is also good news for Viscosity. An array whose elements all came from
`new Particle(...)` is the ideal candidate for a struct of arrays: every
record has the same fields. It's a strong hint, not a promise, though.
Nothing stops code from later writing `p.color = 'red'` on one particle, so
in chapter 97 Viscosity checks whether a shape can change after the
objects are made. And in chapter 43, you'll implement classes, instances
and `this` yourself, inside your own interpreter.
</Callout>

## What you learned

- A **class** is a blueprint. Its **constructor** sets up each object.
- **`new`** makes an empty object, runs the constructor with `this` set to
  it, and returns it: an **instance**.
- **Methods** live in the class body and are shared by all instances.
- Inside a method, **`this`** is the object before the dot in the call. A
  method called without a dot loses its `this`, so wrap it:
  `() => p.move()`.
- **`instanceof`** checks which class made an object.
- Objects from one constructor tend to share one shape, which helps
  engines and Viscosity alike.
