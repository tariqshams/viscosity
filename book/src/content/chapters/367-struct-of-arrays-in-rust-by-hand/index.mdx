## The same particles, a new language

In *Generating SoA storage*, Viscosity turned `const ps = []` into a
generated class whose fields were columns, `this.x = new
Float64Array(cap)` and one more per field. No compiler does that for
you in Rust; however, Rust lets you write the columns yourself in about
twenty lines, and its type system keeps them pleasant to use. First,
look at what you start from.

```rust
#[derive(Clone, Copy)]
struct Particle {
    x: f64, y: f64,
    vx: f64, vy: f64,
    mass: f64, health: f64,
}
let ps: Vec<Particle> = vec![p; n];
```

*Memory layout in Rust* measured a `Particle` at 48 bytes with no
padding, and a `Vec<Particle>` keeps them back to back in one buffer:
no object headers, no pointer per element, no boxed numbers. That is
much closer to Part II's packed `Float64Array` layout than to a
JavaScript array of objects, so in Rust the array of structs starts out
good. What it still wastes is the fields a loop does not touch:

## Columns by hand

<Analogy title="a filing cabinet">
One folder per person, holding all their details, is an array of
structs; one drawer per question ("everyone's weight", "everyone's
height"), each drawer in the same order of people, is a struct of
arrays. To answer "what does everyone weigh?" you open one drawer and
read straight down it.
<span slot="breaks">A clerk can pull one folder out and hand it over
whole; with drawers there is no folder to hand over, only a fresh
summary card copied from each drawer, which is exactly what `get` will
return.</span>
</Analogy>

<Analogy title="a teacher's mark book">
A mark book keeps one column per subject, with the pupils in the same
order down every column, so averaging the maths marks means running a
finger down one column. If one pupil is added to the maths column and
forgotten in the others, every name below them is now beside the wrong
marks.
<span slot="breaks">A teacher would spot the misaligned row at a
glance; Rust will not, as the section after next shows, and a missed
column only fails when some index runs off its end.</span>
</Analogy>

<Figure takeaway="Particle i is index i of every column; push must write all of them." caption="A Particles struct of six Vec<f64> columns. The highlighted index is one particle; the dashed cells are what one push adds.">

</Figure>

```rust
struct Particles {
    x: Vec<f64>, y: Vec<f64>,
    vx: Vec<f64>, vy: Vec<f64>,
    mass: Vec<f64>, health: Vec<f64>,
}

impl Particles {
    fn push(&mut self, p: Particle) {
        self.x.push(p.x);
        self.y.push(p.y);
        // ...and vx, vy, mass, health
    }

    fn step(&mut self, dt: f64) {
        for i in 0..self.x.len() {
            self.x[i] += self.vx[i] * dt;
            self.y[i] += self.vy[i] * dt;
        }
    }
}
```

The struct has one `Vec<f64>` per field, and particle `i` is index
`i` of every column. `push` takes a `Particle` apart and appends each
field to its own column, so all six grow together. `step` is the
`update-xy` loop of *AoS vs SoA, measured*: for each index it reads `vx[i]` and `vy[i]`, and
moves `x[i]` and `y[i]`; it never touches `mass` or `health`, so their
columns are never fetched.

The first is the smallest struct of arrays there is: two columns, one
particle, pushed into both, so both have length 1. The second shows
why columns suit iterators (from *Iterators and closures in Rust*):
summing every mass is one pass over one `Vec`, and `zip` walks the
`x` column mutably and the `vx` column for reading side by side, with
no indices, so there is nothing to bounds-check. The runnable one
builds a million particles both ways and times `update-xy` on each;
the section after next explains why its numbers need care.

<Callout kind="definition">
A **struct of arrays** in Rust is a struct with one `Vec` per field,
such as `x: Vec<f64>`, where element `i` is made of index `i` of every
column. Its methods must keep one **invariant** (a fact that must stay
true between calls): every column has the same length. Each `Vec`
grows by itself, with amortized constant-time `push`<Cite id="rust-std-vec" />.
</Callout>

<Formal title="One particle, many columns">

```text
pᵢ = (xᵢ, yᵢ, vxᵢ, vyᵢ, massᵢ, healthᵢ)
len(x) = len(y) = … = len(health) = n
```

<span slot="read">Particle i is the tuple of the i-th entries of the
six columns. And all six columns have the same length n, the number of
particles; every method must keep that equation true.</span>
</Formal>

All four loops have the same shape, and that is the point of the
layout: the code reads like the array-of-structs version with the
index moved. The differences are in the columns themselves. Rust's
`Vec<f64>` and C's `double *` hold raw doubles; the TypeScript one is a
`Float64Array`, which Viscosity must grow by hand; and in Python the
columns are plain lists unless, as in *Emitting Python with column
storage*, you use `array('d')`.

## What Rust checks, and what it doesn't

Two things work in your favour. First, `self.x[i] += self.vx[i] * dt`
borrows `self.x` mutably and `self.vx` for reading in one statement,
and that is fine: they are different fields, so the borrow checker sees
two separate borrows. Calling a method instead is not:

```rust
for (i, x) in self.x.iter_mut()
    .enumerate() {
    *x += self.vx_at(i) * dt;
}
// error[E0502]: cannot borrow `*self` as
//   immutable because it is also
//   borrowed as mutable
*x += self.vx[i] * dt; // fine
```

`self.vx_at(i)` borrows the *whole* of `self`, including the `x` column
the loop is already changing, so rustc 1.97 refuses it with the error
above (trimmed); naming the field directly borrows only `vx`. Second,
if the fields are private to their module (*Modules, crates and
visibility*), nobody outside can push to only one column.

One thing Rust does not check: nothing makes `push` write *every*
column. Forget `self.vx.push(p.vx)` and it compiles; then the first
`step` panics with an index out of bounds, because `vx` is empty. In Part
VIII, Viscosity generated `push` itself; here, tests do that job.
And getting a particle back is materialization (*Identity and
materialization*): `get(i)` builds a `Particle` from the columns and
returns it by value, since there is no `Particle` in memory to lend a
`&Particle` to, so changing the copy changes nothing in the columns.

## Measuring it

Read the runnable example's output with suspicion. In the page it runs
on the Rust Playground as a *debug* build, with no optimization. On
this book's machine (a shared cloud VM, rustc 1.97) the debug build
made SoA *slower*, about 20 ns per particle against 4 to 9 for AoS in
three runs, because every `s.x[i]` paid for an unoptimized bounds
check; built with `-O`, the same program printed about 1.3 ns for SoA
against 2.4 for AoS, three times out of three. The program wraps the
data in `std::hint::black_box`, which stops the optimizer from
deleting work whose result it can see is unused<Cite id="rust-std-black-box" />;
*Measuring Rust performance* explains both pitfalls properly.

For this chapter I also ran a fuller harness: release build, three
loops, each warmed up and then timed in 31 samples of about 20 million
particle updates, keeping the median; the whole run three times, in
nanoseconds per particle (ranges across the runs):

```text
n = 1,000          AoS        SoA
  update-xy        0.38–0.41  0.41–0.54
  sum-one-field    0.65–0.71  0.65–0.66
  read-all         1.10–1.11  1.08–1.12
n = 1,000,000
  update-xy        2.35–2.37  1.28–1.33
  sum-one-field    2.00–2.03  0.72–0.76
  read-all         2.51–2.67  1.77–1.85
```

With a thousand particles (48 KB, which stays in cache) there was no
win, and `update-xy` was if anything a little slower as columns. With
a million, SoA was about 1.8 times faster for `update-xy` and 2.7 for
summing one field, and it came out ahead even reading all six fields,
which this chapter cannot fully explain, so do not lean on that row.
Now the same loop in JavaScript, from this book's Node run:

## What you learned

- A **`Vec<Particle>`** is already flat: structs back to back, no
  headers or pointers. Its waste is the fields a loop skips.
- A Rust **struct of arrays** has one `Vec<f64>` per field; keep the
  columns the same length, and the fields private.
- Borrowing two different fields at once is fine; a method call
  borrows all of `self` (E0502). `get` returns a rebuilt copy.
- In this chapter's release runs SoA was 1.8 to 2.7 times faster at a
  million particles and no faster at a thousand.
