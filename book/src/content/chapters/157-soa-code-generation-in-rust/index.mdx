## From a plan to a program

The planner has decided that `ps` should become a struct of arrays
(*The cost model in Rust*). Now something has to write the program that
does it: a class to hold the columns, and a new spelling for every place
the program creates, grows or reads `ps`. In the TypeScript engine that
was *Generating SoA storage* and *Rewriting field accesses*; in Rust it
is `crates/frontend-js/src/emit.rs`. Here is a program:

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
console.log(ps[99].x);
```

and the end of what `viscosity build` wrote for it (I ran it here,
release build, rustc 1.97; node prints `100` for both versions):

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 100; i++)
  ps.push(i, 1);
for (let i = 0; i < ps.length; i++)
  ps.x[i] += ps.vx[i];
console.log(
  ps.x[__vsc_bc(ps, 99, 'x', false)]);
```

The last line is wrapped to fit; otherwise every character the program
didn't need to change is exactly where it was. Above it, the emitter put
a class, `__Vsc_ps`, and a helper, `__vsc_bc`. This chapter reads how it
writes all three, and how it picks names that can never collide with
the programmer's own. (What happens when a *write* goes out of bounds
is subtle enough for its own chapter, *The order of a field write in
Rust*.)

<Analogy title="relabelling a warehouse">
A warehouse that stored each customer's order on one shelf moves to one
aisle per product: all the screws together, all the bolts together. The
goods are the same, but every pick list has to be rewritten, from
"shelf 12, the screws" to "the screw aisle, slot 12", and nothing else
on the list may change.
<span slot="breaks">A picker who finds an old pick list can ask
someone; a compiled program can't, so the emitter must rewrite every
single access, which is why the analysis refused any collection with a
use it couldn't see.</span>
</Analogy>

<Analogy extra title="names a folder won't take">
Copy `report.txt` into a folder that already has one, and you get

## The container class

For each collection planned as SoA, `container_class` builds the class
with `format!` and `join`. Reformatted (it is six long lines in the
output), with `of` and `grow` shortened:

```js
class __Vsc_ps {
  constructor(cap = 16) {
    this.length = 0; this.cap = cap;
    this.x = new Float64Array(cap);
    this.vx = new Float64Array(cap);
  }
  static of(...v) { … }
  push(v0, v1) {
    const n = this.length;
    if (n === this.cap) this.grow();
    this.x[n] = v0; this.vx[n] = v1;
    return (this.length = n + 1);
  }
  grow() { … }
}
```

`length` is how many elements are in use and `cap` how many slots each
column has. Each numeric field gets a `Float64Array` column (a typed
array: a fixed-size block of 64-bit floats). `push` takes the values in
field order, grows the columns when they are full, writes slot `n` of
each, and returns the new length, as `Array.prototype.push` does.
`grow` doubles `cap`, makes new typed arrays and copies the old ones in
with `set`, which is the doubling of *Growing collections*. `of` builds
a container from an array literal's values, taking them two at a time
for two fields.

## Edits, back to front

The emitter does not print the program from its IR. It collects a list
of **edits**, each a byte range of the original source and the text
that replaces it, and leaves everything else alone, comments and
spacing included. The doc comment at the top of `emit.rs` lists the
shapes it rewrites (rearranged to fit):

```
const ps = [];
  → const ps = new __Vsc_ps();
ps.push({ x: a, y: b });
  → ps.push(a, b);
ps[i].x
  → ps.x[i]
const p = ps[i]; p.x
  → const p = i; ps.x[p]
for (const p of ps) p.x
  → for (let p = 0; p < ps.length; p++)
      ps.x[p]
```

As *Emitting JavaScript from Rust* showed, the edits are then sorted by
start, largest first, and applied with `String::replace_range`, so no
edit still waiting has moved, and an overlap is reported as `internal
error: overlapping rewrites` rather than written out. Step through the edits for the program
above:

## Names that never clash

Two collections can have the same name in different functions, so the
class name is numbered (from `emit_js`):

```rust
let mut cls = format!("__Vsc_{}", c.name);
let mut k = 2;
while class_names.contains(&cls) {
    cls = format!("__Vsc_{}_{k}", c.name);
    k += 1;
}
class_names.insert(cls.clone());
```

`class_names` is a `HashSet<String>` of names already used, so the
corpus program `same_name_collections.js` gets `__Vsc_ps` and
`__Vsc_ps_2`. Columns need more care, because they are properties of
the container: a field called `length` or `push` would overwrite the
container's own members. `column_name(field, i)` keeps a field's name
only if it is a plain ASCII identifier and not in the list `RESERVED`
(`length`, `push`, `grow`, `of`, `constructor`, `prototype`, `get`,
`cap`, `data`); otherwise field number `i` becomes `f{i}_`. Then
`column_names` makes the whole list unique: a renamed column gets `_`
appended until it differs from every field that kept its name and every
column before it. The corpus program `renamed_column_clash.js` has
fields `length` and `f0_`, and its constructor shows both rules:

```js
this.f0__ = new Float64Array(cap);
this.f0_ = new Float64Array(cap);
```

`length` (field 0) became `f0_`, which the real field `f0_` already
uses, so it became `f0__`. Explain still says `{length, f0_}`,
because columns are an internal detail.

## Reads that need a check

An element read that wasn't proven in bounds (*Proving an index in
bounds in Rust*) goes through a helper the emitter adds to the prelude
only when some access needs it (rewrapped, the message split in two):

```js
function __vsc_bc(c, i, f, w) {
  if (i >>> 0 === i && i < c.length)
    return i;
  throw new TypeError(w
    ? `Cannot set properties of undefined`
      + ` (setting '${f}')`
    : `Cannot read properties of undefined`
      + ` (reading '${f}')`);
}
```

`i >>> 0` converts `i` to an unsigned 32-bit integer, so `i >>> 0 ===
i` holds exactly for whole numbers from 0 to 2³² − 1 (not `-1`, `1.5`
or `'3'`),
and `i < c.length` checks the top end. In range, it returns the index
unchanged, so `ps.x[__vsc_bc(ps, 99, 'x', false)]` reads the same slot
as `ps.x[99]`; out of range, it throws the same `TypeError`, word for
word, that the original would have thrown reading `.x` of `undefined`.
The flag `w` picks the "setting" wording for writes.

<Formal title="Rewriting a field access">

```text
c[i].f  ⟶  c.col(f)[i]
            if i is proven in bounds
c[i].f  ⟶  c.col(f)[bc(c, i, f, w)]
            otherwise
```

<span slot="read">Reading or writing field f of element i of a
transformed collection c becomes indexing f's column with i, when i is
proven to be in bounds; otherwise the index first goes through the
bounds check bc, which returns i unchanged or throws the original's
error, with w saying whether it is a write.</span>
</Formal>

<Examples of="rust-soa-codegen">

```js
const ps = [{ x: 1, vx: 2 },
  { x: 3, vx: 4 }];
// → const ps = __Vsc_ps.of(1, 2, 3, 4);
```

```js
for (const p of ps) s += p.x;
// → for (let p = 0; p < ps.length;
//     p++) s += ps.x[p];
```

```js
const p = ps[i];
p.x *= 2;
// → const p = i;
//   ps.x[p] *= 2;
```

</Examples>

All three are real output of the Rust CLI (the first with `--min-size
0`, since two elements are below the threshold). An array literal
becomes a call to `of`, with the values in field order. A `for...of`
loop becomes a counting loop, and the loop variable now holds an index,
so every `p.x` becomes `ps.x[p]`. And a variable that held an element
now holds the element's index: `const p = ps[i]` becomes `const p = i`,
and `p.x` becomes `ps.x[p]`, which is how the hot loop of the benchmark
`particles.js` is compiled.

<Callout kind="definition">
**SoA emission in Rust** (`emit.rs`) writes one **container class** per
transformed collection, `__Vsc_name` (numbered `__Vsc_name_2`, ... on a
clash), with one **column** per field named by `column_names`
(`f{i}_` for reserved or non-identifier names, then made unique), and
rewrites the program as a list of **byte-range edits** applied **back to
front**, so that everything else is copied through unchanged. Accesses
not proven in bounds index through **`__vsc_bc`**, which throws the
original's `TypeError`.
</Callout>

## What you learned

- The **container class** holds `length`, `cap` and one column per
  field; `push` writes slot `n` of every column, and `grow` doubles.
- The emitter **splices edits** into the original text, **last first**,
  so no offset goes stale and untouched code is copied byte for byte.
- Class names are **numbered** on a clash; columns keep the field name
  unless it is **reserved** or not a plain identifier, then become
  `f{i}_`, extended with `_` until **unique**.
- Unproven accesses go through **`__vsc_bc`**, which returns the index
  or throws the original's error.

## A write that failed too early

*SoA code generation in Rust* showed how an unproven access gets a
bounds check, `ps.x[__vsc_bc(ps, i, 'x', true)]`. For reads that is the
whole story. For writes it is not, and the corpus program
`write_rhs_first.js` is there to show why: a fuzzer (*Testing
compilers*) wrote a program like it. Its middle part:

```js
try {
  for (let i = 0; i <= ps.length; i++)
    ps[i].x = ps[i].y;
} catch (e) {
  console.log('caught', e.message);
}
let t = 0;
try {
  ps[100].x = (t = 5);
} catch (e) {
  console.log('caught', e.message, t);
}
```

`ps` holds 100 elements, so both writes go out of bounds. Here is what
node prints for the original, and for the Rust emitter's output before
the fix (I reproduced that here, on a scratch copy of `engine/rust`
with the new branch switched off; lines wrapped):

```
original, and today's output:
  caught Cannot read properties of
    undefined (reading 'y')
  caught Cannot set properties of
    undefined (setting 'x') 5
before the fix:
  caught Cannot set properties of
    undefined (setting 'x')
  caught Cannot set properties of
    undefined (setting 'x') 0
```

The compiled program failed at the wrong moment: before the right-hand
side ran, so the wrong error was thrown and `t = 5` never happened.

<Analogy title="a waiter and a moved table">
A waiter takes your order and only walks to your table once the plate
is ready. If the table was moved while the food was cooking, he looks
for it again; he doesn't set the plate down where the table used to
be.
<span slot="breaks">A waiter can see the room; the compiled code can't
"look again" unless the emitter wrote it to fetch the column at the
moment of the store, which is exactly what the fix does.</span>
</Analogy>

<Analogy extra title="a cheque that bounces">
You write a cheque and hand it over; it bounces later, at the bank.
Everything you did before that still happened. A shop that refused the
cheque before you wrote it would change your afternoon, although the
payment fails either way.
<span slot="breaks">A bounced cheque can be paid later; a failed store
is final, and the only thing the compiled program must get right is
when it fails and with which message.</span>
</Analogy>

## Three steps, in order

For an assignment `a = b`, the specification evaluates the left-hand
side to a **reference** (here, "property `x` of the value `ps[100]`"),
then the right-hand side, and only then stores, with `PutValue`; and
it is `PutValue` that throws when the base is `undefined`<Cite id="ecma262-assignment-order" />.
Reading `ps[100]` gives `undefined` without complaint. So in the
original, `t = 5` runs, and then the store throws "Cannot set
properties of undefined". In the loop, the right side `ps[i].y` is read
first and throws its own error, "reading 'y'".

The rewritten left side `ps.x[__vsc_bc(ps, 100, 'x', true)]` is also
evaluated first, but now that *runs the check*, which threw before the
right side ran. The same order caused a quieter bug: evaluating
`ps.x[...]` also fetches the column, and if the right side pushes and
the container grows, `grow()` replaces `this.x`, so the store goes
into the old array, which nothing reads any more. Step through it on `ps[3].x = (more(),
77)`, where `more()` pushes:

E0499<Cite id="rustc-e0499" />. Run it and read the error:

## What the right side can do

The fix starts in the analysis (`crates/core/src/analysis.rs`). For
every field write it records what evaluating the rest of the assignment
can do, as an enum ordered from least to worst (doc comments left
out):

```rust
#[derive(Copy, Clone, PartialEq, Eq,
    PartialOrd, Ord, Debug)]
pub enum RhsEffect {
    Inert,
    MayThrow,
    Effects,
}
```

Deriving `PartialOrd` and `Ord` orders the variants as they are
written, so `Inert < MayThrow < Effects`, and the analysis can combine
the instructions of a right-hand side with `worst = worst.max(effect(x))`.

<Prompts ids={['cg-ord-derive']} />

Constants, variables and arithmetic on numbers are `Inert`; reading an
element that wasn't proven in bounds is `MayThrow`; a call, an
assignment such as `t = 5`, or anything the analysis doesn't model is
`Effects`. Two things are left out of the count: the element being
written to, and, for `+=` and friends, the read of the old value, which
JavaScript does first in both versions anyway.

The emitter then picks the late form only when the order can be
observed (from `emit_js`, rewrapped):

```rust
let typed = cp.layout == Layout::Aosoa
    || c.numeric_fields.contains(&a.field);
if let Some(op) = operator.filter(|&op| {
    write
        && ((op == "=" && !ok
            && a.rhs != RhsEffect::Inert)
            || (typed && a.rhs
                == RhsEffect::Effects))
}) {
```

`ok` means "proven in bounds, or `--bounds assume`". An unproven `=`
whose right side may throw or act needs its error after the right side.
A typed column (or AoSoA's `data`) can be replaced by `grow()`, but only
if the right side runs code. A plain column is an ordinary array that
grows in place, and an inert right side can't tell the difference, so
both keep the cheap `col[i] = rhs`.

<Formal title="When a write stores late">

```text
late ⇔ write ∧ ( (op is = ∧ ¬ok
                  ∧ rhs ≠ Inert)
               ∨ (typed ∧ rhs = Effects) )
```

<span slot="read">A field access is stored late exactly when it is a
write, and either it is a plain assignment whose index isn't proven
(and isn't assumed) and whose right side can do something, or its
column is a typed array and its right side runs code.</span>
</Formal>

## Storing late

The late form uses three helpers, which the emitter adds to the prelude
only when some write needs them (wrapped; `__vsc_seta` is the same for
AoSoA, computing the slot in `data`):

```js
let __vsc_k = 0;
function __vsc_bk(c, i) {
  return i >>> 0 === i && i < c.length
    ? i : NaN;
}
function __vsc_set(c, col, i, v, f) {
  if (i !== i) throw new TypeError(
    `Cannot set properties of undefined`
    + ` (setting '${f}')`);
  c[col][i] = v;
  return v;
}
```

`__vsc_bk` decides the bounds question first, as the original's
reference is evaluated first, but answers `NaN` instead of throwing.
Then the right side runs, as an argument. Then `__vsc_set` throws if the
index was `NaN` (`i !== i` is true only for `NaN`), and otherwise
fetches the column `c[col]` *now*, after any growth, and stores. It
returns `v`, because an assignment's value is its right side.

<Examples of="rust-soa-codegen">

```js
ps[100].x = (t = 5);
// → __vsc_set(ps, 'x', __vsc_bk(ps, 100),
//     (t = 5), 'x');
```

```js
ps[4].x += (more(), 1);
// → __vsc_set(ps, 'x', __vsc_k =
//     __vsc_bc(ps, 4, 'x', false),
//     ps.x[__vsc_k] + ((more(), 1)), 'x');
```

```js
qs[5].a = (grow(qs, 70), 9);
// → __vsc_seta(qs, __vsc_bk(qs, 5),
//     (grow(qs, 70), 9), 'a', 2, 8, 0, 3);
```

</Examples>

All three are real lines of the Rust CLI's output, wrapped. The first
is the plain case. The second is a compound write, which in the
original *reads* `ps[4].x` first, so it keeps `__vsc_bc` with `false`
(the "reading" wording) and saves the checked index in the scratch
variable `__vsc_k` for the late store. The third, from
`write_rhs_grows.js`, is an AoSoA collection whose right side pushes
70 elements; `__vsc_seta` gets the shift, stride, offset and mask of
*AoSoA in Rust*. That program prints `130 77 6` and `335 9
4 4` for the original and today's output, but `130 4 6` and `335 5 4 0`
for the old emitter's (both run here with node).

<Callout kind="definition">
A **late store** is the emitter's form for a field write whose order
could be observed: an unproven `=` whose right side may throw or act, or
a typed column whose right side runs code (the analysis records each
write's **`RhsEffect`**: `Inert`, `MayThrow` or `Effects`). The index is
checked before the right-hand side with **`__vsc_bk`**, and the store
happens after it with **`__vsc_set`** or **`__vsc_seta`**, which throws
the original's error or writes into the column as it is then.
</Callout>

## What you learned

- JavaScript evaluates a field write's **left reference first**, then
  the **right-hand side**, then **stores**; only the store throws on a
  missing element.
- The old rewrite ran the **check** and fetched the **column** too
  early, so it threw too soon and could store into a column that
  **`grow()`** had replaced.
- Each write's **`RhsEffect`** (`Inert < MayThrow < Effects`) decides
  whether the emitter **stores late**, through **`__vsc_bk`** and
  **`__vsc_set`**.
