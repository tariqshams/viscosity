## Five lines on stderr

```drip
class Oven {
  bake(n) { return self.heat(n); }
  heat(n) { return n * none; }
}
fn go() {
  return new Oven().bake(3);
}
go();
```

drip-rs prints nothing on stdout, exits with 70, and prints on stderr
(the first line wrapped here):

```text
runtime error: cannot use '*' on a number
  and none
  at line 3 in fn heat
  at line 2 in fn bake
  at line 6 in fn go
  at line 8 in script
```

The message says what went wrong; the `at` lines say where, innermost
call first. The TypeScript VM prints exactly the same bytes, and so does
the tree-walker. Two questions follow: how a VM still knows lines 6 and
2 long after it ran those calls, and how anyone knows three
implementations that share no code agree on every byte.

<Analogy title="one answer key for three exam papers">
Three students sit the same exam, and one answer key marks all three
papers. Nobody has to compare the students' working with each other;
each is checked against the key, and if all three match the key, they
match each other.
<span slot="breaks">An answer key is written by someone who knows the
answers. The corpus was written by people, too, and if a comment is
wrong, all three implementations are forced to be wrong the same way;
DRIP.md makes the corpus the source of truth for wording because
someone had to decide.</span>
</Analogy>

<Analogy extra title="sticky notes on a desk">
Writing a report, you need a number, so you stick a note on the desk,
"report, page 6", and open a spreadsheet; there you need a date, so a
second note goes on top, "spreadsheet, row 2", and you open the
calendar, where things go wrong. To explain how you got there, read the
notes from the top down.
<span slot="breaks">Your notes say where you *left*; for the task you
are doing right now there is no note yet, so you have to remember it
yourself. A VM has exactly that problem.</span>
</Analogy>

## The trace, frame by frame

*Call frames and upvalues in Rust* showed the one subtle line of
`Vm::runtime_error`: it walks `self.frames` innermost first, and for each
frame takes `ip` from the register `self.ip` if it is the top frame and
from the frame's saved `ip` otherwise, then reads
`frame.chunk.lines[ip - 1]`, because `ip` is already past the failing
instruction (or the waiting call). The place is a `match` on the
function's name: `Some(name)` gives `fn heat`, `None` gives `script` or
`anonymous fn`.

<ErrorSteps client:visible />

Here is the spot the difference. In a scratch copy of drip-rs I changed
that choice to plain `let ip = frame.ip;`, built it in debug mode, and
ran the oven program; it crashed with exit code 101 instead of
reporting:

```text
thread 'main' panicked at
  src/vm.rs:270:42:
attempt to subtract with overflow
```

`heat` has made no calls, so its saved `ip` is still the 0 it started
with, and `0 - 1` on a `usize` overflows, which a debug build checks.
With a stale but non-zero `ip` it would quietly print the wrong line,
which is worse.

<Callout kind="definition">
A **stack trace** lists the calls that are running when an error
happens, innermost first, each with the line it was on. In drip-rs,
`runtime_error` writes the message, then one `at line N in place` line
per `CallFrame`: the innermost frame's line comes from the `ip`
register, every other frame's from the `ip` it saved when it made its
call, and each is `chunk.lines[ip - 1]`, because `ip` is already past
the instruction.
</Callout>

<Examples of="runtime-stack-trace">

```drip
fn f(n) {
  return f(n + 1);
}
f(0);
# runtime error: stack overflow
#   at line 2 in fn f    (255 times)
#   at line 4 in script
```

</Examples>

`call` refuses the 257th frame with `stack overflow` (the limit is
DRIP.md's, `FRAMES_MAX` in `vm.rs`), so the trace has 256 `at` lines:
255 for `f`, every one on line 2 where its recursive call waits, then the
script. The error itself is a value, the unit struct `RuntimeError`
carried out of `run` by `?` (*Bytecode, values and the VM loop in
Rust*); it holds nothing because the message and trace are already in
`self.stderr`, and `interpret` turns it into exit code 70, clearing the
stack and frames but keeping the globals, so the same `Vm` could run
another program, as a REPL would.

<TwoPaths />

Compile errors take the other path. The compiler pushes each one as a
`String` and carries on, syntax errors into `syntax_errors` (with panic
mode dropping echoes until the next statement) and broken static rules
into `static_errors`, and reports the static ones only when there are no
syntax errors, as the TypeScript compiler does: a `break` outside a loop
on line 3 and `let z = ;` on line 5 report only `line 5: expected an
expression, found ';'`, exit 65. `main.rs` returns
`ExitCode::from(outcome.exit_code as u8)`<Cite id="rust-std-exitcode" />,
where `as u8` keeps the low byte<Cite id="rustref-numeric-cast" />, the
whole value for 0, 65 and 70.

<More title="An anonymous function in a trace, and what the CLIs disagree on">

This program passes a named function into an anonymous one and prints
`4`; remove the `#` on its last line and it fails inside `half`, and the
trace reads `fn half`, then `anonymous fn`, then `script`.

<Run id="anon" />

The two command lines agree on the codes (64 for bad usage, 65, 66 for a
file that cannot be read, 70) but not on every word: for a missing file
drip-rs prints Rust's own `No such file or directory (os error 2)` where
the TypeScript CLI prints Node's `ENOENT`. The corpus never tests that
line, so nothing caught it: a fair example of what a shared test suite
cannot see.

</More>

## One folder, three interpreters

The tree-walker, the TypeScript VM and drip-rs share hardly a line, so
nobody checks them against each other's code. Instead the behaviour is
written down once, as a folder, `book/companion/corpus`: 344 small Drip
programs in 25 folders (334 tests and 10 benchmarks), each saying in its
comments what it must do, and every implementation must prove it.

<CorpusFan />

<Examples of="shared-corpus">

```drip
let a = [1, 2];
let b = a;
push(b, 3);
print a; # expect: [1, 2, 3]
```

```drip
print 1 print 2;
# expect compile error: line 1:
#   expected ';' after the value,
#   found 'print'
```

</Examples>

The first four lines are from `lists/by_reference.drip`: `# expect:` is
one line of output, and here it checks that lists are shared, not
copied, because an implementation printing `[1, 2]` has copied a list
somewhere. The second is `compile/missing_semicolon.drip`, its comment
wrapped here (it really sits at the end of line 1): `# expect compile
error:` lists the compile errors exactly and in order, and means exit 65
with nothing run. The other two markers are `# expect runtime error:`,
the message (and exit 70), and `# expect trace:`, one per `at` line,
innermost first; without trace lines only the innermost `at` line is
checked, against the line the runtime-error comment is on. A multi-line
call reports the line of its `(`, DRIP.md's rule, which three
implementations had to agree on.

<Callout kind="definition">
A **shared corpus** is one set of test programs that every
implementation of a language must pass, with each program's expected
behaviour (its output, its compile errors, its runtime error and stack
trace, its exit code) written beside it, so that the tests belong to
the language rather than to any one implementation.
</Callout>

<Formal title="Passing the corpus">

```text
passes(I) ⇔ ∀p ∈ C. run(I, p) = expect(p)
passes(I) ∧ passes(J) ⇒ ∀p ∈ C.
    run(I, p) = run(J, p)
```

<span slot="read">An implementation I passes the corpus C when, for every
program p in C, what I does with p equals what p's comments expect. If I
and J both pass, they behave the same on every program in C (and the
corpus says nothing about programs outside it).</span>
</Formal>

On the Rust side, `tests/corpus.rs` is a port of the TypeScript runner's
`check()`, with its own `main` because `Cargo.toml` sets
`harness = false`<Cite id="cargo-targets" />, so it prints one line per
program rather than being one big test. It runs each program in-process
with `debug_gc` (freed slots are never reused, so a collector bug
panics), catches a panic so that it fails only that program, and compares
the exit code, the errors and trace, then stdout line by line.
`tests/stress_gc.rs` reruns the 165 programs of the ten folders that
allocate most with a collection before every allocation. On 2026-11-02
`cargo test` (cargo 1.97) printed `corpus result: ok. 334 passed; 0
failed` and `stress GC result: ok. 165 passed; 0 failed`.

<CheckSteps client:visible />

Passing the corpus says each implementation matches the comments, not
that they match each other on what the comments leave out, such as a
second error after the first. `scripts/compare_with_ts.mjs` checks that
directly: it runs drip-rs and the TypeScript VM on every program and
compares stdout, stderr and exit code byte for byte, then **mangles**
2,000 programs (dropping, replacing or inserting a token) and compares
again, which tests error recovery hardest. Run on 2026-11-02, it printed
`corpus: 343 programs compared, 0 differ` (the one program that prints
`clock()` is skipped) and `mangled: 2000 programs, 0 skipped (slow), 0
differ`.

<More title="Differential testing, and its blind spot">

Comparing two implementations with each other, rather than with a
written answer, is the differential testing of *Testing compilers:
differential, round-trip, fuzzing and shrinking*: it needs no answers
written in advance, so it can test thousands of programs nobody wrote.
Its blind spot is the corpus's, a shared mistake: if both VMs were wrong
the same way, every comparison would still say `0 differ`. That is why
the corpus is checked against DRIP.md by people, and the implementations
against the corpus by programs. The TypeScript side has its own fuzzer,
`test/fuzz.mjs`, which checks that the tree-walker's parser and resolver
report exactly the compile errors the VM's one-pass compiler does. Run
