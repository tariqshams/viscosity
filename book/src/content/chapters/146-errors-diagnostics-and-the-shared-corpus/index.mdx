## Five lines on stderr

```drip
class Oven {
  bake(n) { return self.heat(n); }
  heat(n) { return n * none; }
}
fn go() {
  return new Oven().bake(3);
}
go();
```

The script calls `go`, which calls `bake`, which calls `heat`, which
multiplies a number by `none`. drip-rs prints nothing on stdout, exits
with 70, and prints this on stderr:

```text
runtime error: cannot use '*' on a number
  and none
  at line 3 in fn heat
  at line 2 in fn bake
  at line 6 in fn go
  at line 8 in script
```

(The first line is wrapped for the page.) The message says what went
wrong, in Drip's own words; the `at` lines say where,
innermost call first: the multiply on line 3 inside `heat`, which was
called from line 2 inside `bake`, called from line 6 inside `go`,
called from line 8 of the script. That list is a **stack trace**, and
the TypeScript VM prints exactly the same bytes (so does the
tree-walker, from Part III). The question for a VM is how it still knows
lines 6 and 2, long after it ran those calls.

<Analogy title="sticky notes on a desk">
Writing a report, you need a number, so you stick a note on the desk,
"report, page 6", and open a spreadsheet; there you need a date, so a
second note goes on top, "spreadsheet, row 2", and you open the
calendar, where things go wrong. To explain how you got there, read the
notes from the top down.
<span slot="breaks">Your notes say where you *left*; for the task you
are doing right now there is no note yet, so you have to remember it
yourself. A VM has exactly that problem, as we will see.</span>
</Analogy>

<Analogy extra title="a parcel's tracking history">
A parcel's tracking page lists every depot it passed through, latest
first, so when it is lost you can see the last place anyone saw it and
the route that led there.
<span slot="breaks">A parcel's history is kept forever; a VM's call
frames disappear as each call returns, so the trace is only a picture
of the calls that are still running at the moment of the error.</span>
</Analogy>

## The trace, frame by frame

Every running call has a `CallFrame` (from *Functions and call frames in
Rust*) holding its closure, its chunk, its `ip` and its stack base, and
each chunk has a `lines` array with the source line of every byte. The
part of `Vm::runtime_error` that builds the trace, from `vm.rs`
(rewrapped):

```rust
let top = self.frames.len()
    .saturating_sub(1);
for (depth, frame) in
    self.frames.iter().enumerate().rev()
{
    let ip = if depth == top {
        self.ip
    } else {
        frame.ip
    };
    // `ip` is already past the failing
    // instruction.
    let line = frame.chunk.lines[ip - 1];
    // ...work out `place`: "fn heat",
    // "anonymous fn" or "script"...
    self.stderr.push(format!(
        "  at line {line} in {place}"));
}
```

`.rev()` walks the frames from the innermost out. For each one, `ip` is
the index of the *next* byte to run, so the byte that failed (or the
call that is still waiting) is at `ip - 1`, and `lines[ip - 1]` is its
source line. The one subtle line is the `if`: drip-rs keeps the running
frame's `ip` in a field of the `Vm` itself, `self.ip`, like a CPU
register (from *The VM loop in Rust*), and writes it back into the
frame only when that frame makes a call. So every outer frame's saved
`ip` is right, pointing just past its call, while the innermost frame's
copy is stale; the register is the truth for that one. `place` comes
from a `match` on the function's name: `Some(name)` gives `fn heat`, and
`None` gives `script` or `anonymous fn`, using a guard,
`None if function.is_script`.

<ErrorSteps client:visible />

Here is the spot the difference. In a scratch copy of drip-rs I changed
that `if` to plain `let ip = frame.ip;`, built it in debug mode, and ran
the oven program; it crashed instead of reporting (exit code 101, and
the path trimmed):

```text
thread 'main' panicked at
  src/vm.rs:270:42:
attempt to subtract with overflow
```

`heat` has made no calls, so its saved `ip` is still the 0 it started
with, and `0 - 1` on a `usize` overflows: a debug build checks that and
panics. (A release build would wrap round instead, and then the
indexing would panic.) With a stale but non-zero `ip`, it would quietly
print the wrong line, which is worse.

<Callout kind="definition">
A **stack trace** lists the calls that are running when an error
happens, innermost first, each with the line it was on. In drip-rs,
`runtime_error` writes the message, then one `at line N in place` line
per `CallFrame`: the innermost frame's line comes from the `ip`
register, every other frame's from the `ip` it saved when it made its
call, and each is `chunk.lines[ip - 1]`, because `ip` is already past
the instruction.
</Callout>

<Formal title="Which ip each frame uses">

```text
ipᵢ = self.ip     if i = top
ipᵢ = frameᵢ.ip   otherwise
lineᵢ = frameᵢ.chunk.lines[ipᵢ − 1]
```

<span slot="read">For frame number i, the ip to use is the register if
i is the top frame and the frame's own saved ip otherwise; its line is
the entry just before that ip in the frame's lines array.</span>
</Formal>

<Examples of="runtime-stack-trace">

```drip
let xs = [1, 2, 3];
print xs[3];
# runtime error: index 3 is out of
#   range for a list of length 3
#   at line 2 in script
```

```drip
fn f(n) {
  return f(n + 1);
}
f(0);
# runtime error: stack overflow
#   at line 2 in fn f    (255 times)
#   at line 4 in script
```

</Examples>

The first has no calls at all, so the trace is one line, the script's,
taken from the register. The second recurses until the 256-frame limit
(DRIP.md's rule, `FRAMES_MAX` in `vm.rs`): `call` refuses the next frame
with `stack overflow`, and the trace has 256 `at` lines, 255 for `f`,
all on line 2, and one for the script. The third, which you can run,
passes a named function into an anonymous one and prints `4`; remove
the `#` on its last line and it fails inside `half` with `cannot use
'/' on a string and a number`, and the trace reads `fn half`, then
`anonymous fn`, then `script`.

## Carrying the error out

A runtime error has to stop the program from deep inside the loop. The
TypeScript VM throws an exception: its `runtimeError` has the return
type `never` and ends with `throw`, and `interpret` catches it. drip-rs
has no exceptions; instead the error is a value, and from *Option and
Result* you know the shape:

```rust
pub struct RuntimeError;

type Run<T = ()> = Result<T, RuntimeError>;
```

`RuntimeError` is a **unit struct** (it carries nothing, because the
message and trace are already in `self.stderr` by the time one exists),
and every function that can fail returns `Run`, so an arm such as
`OpCode::Mul` writes `let (a, b) = self.pop_numbers("*")?;` and the `?`
returns the `Err` from `run` at once, up to `interpret`. There, a
`match` turns `Err(RuntimeError)` into exit code 70 after clearing the
stack, the frames, the chunk register and the open upvalues; the globals
stay, so the same `Vm` can run another program, as a REPL would.

<TwoPaths />

Compile errors take the other path in the diagram. The compiler pushes
each one as a `String` and carries on: syntax errors go into
`syntax_errors` through `error_at`, which in **panic mode** drops any
more until the parser reaches the next statement (from *A Pratt compiler
in Rust, part 2*); broken static rules go into `static_errors`. At the
end, `compile` reports the syntax errors if there are any and the static
ones only otherwise, as the TypeScript compiler does, so

```drip
let x = 1;
fn f() {
  break;
}
let z = ;
```

reports only `line 5: expected an expression, found ';'`, and exits
with 65; fix line 5 and the next run reports `line 3: 'break' outside a
loop`. Finally `main.rs` prints the lines and returns
`ExitCode::from(outcome.exit_code as u8)`<Cite id="rust-std-exitcode" />;
the `as u8` keeps the low byte of the `i32`<Cite id="rustref-numeric-cast" />,
which is the whole value for 0, 65 and 70.

<Prompts ids={['de-unit', 'de-question', 'de-reset', 'de-static']} />

<Callout kind="engine" label="Under the hood">
The two command lines agree on the codes (64 for bad usage, 65, 66 for
a file that cannot be read, 70) but not on every word: for a missing
file drip-rs prints Rust's own `No such file or directory (os error 2)`
where the TypeScript CLI prints Node's `ENOENT`. The corpus never tests
that line, so nothing caught it; it is a fair example of what a shared
test suite cannot see. On everything the corpus does test,
`scripts/compare_with_ts.mjs` found drip-rs's stdout, stderr and exit
code identical to the TypeScript VM's for all 343 programs it compared
on 2026-11-02.
</Callout>

## What you learned

- A **stack trace** is the message, then one `at` line per running
  call, innermost first.
- The innermost frame's line comes from the **`ip` register**; the
  others from the `ip` they **saved** when they called. Each line is
  `lines[ip - 1]`.
- A runtime error is a **value**: the unit struct `RuntimeError`,
  carried out of `run` by **`?`**, where the TypeScript VM throws.
- Compile errors collect in two `Vec`s; **static errors are reported
  only when there are no syntax errors**. Exit codes are 65 and 70.

## One folder, three interpreters

The book has built Drip three times: the tree-walker of Part III, the
TypeScript VM of Part IV, and now drip-rs. How do you know the three
agree? Not by reading them side by side; they share hardly a line. You
agree on the *behaviour* instead, write it down once, and make every
implementation prove it. In this book that agreement is a folder,
`book/companion/corpus`: 344 small Drip programs in 25 folders (334
tests and 10 benchmarks), each of which says in its own comments what it
should print. Here is `lists/by_reference.drip`, whole:

```drip
let a = [1, 2];
let b = a;
push(b, 3);
print a; # expect: [1, 2, 3]
fn fill(xs) {
  xs[0] = "changed";
}
fill(a);
print b[0]; # expect: changed
```

It checks that lists are shared, not copied: `b` is the same list as
`a`, so pushing through `b` shows up in `a`, and `fill` writing through
its parameter shows up in `b`. The two `# expect:` comments are the
whole test: the program must print exactly those two lines, in that
order, with nothing on stderr and exit code 0. Any implementation that
prints `[1, 2]` has copied a list somewhere it should not have.

<Analogy title="one answer key for three exam papers">
Three students sit the same exam, and one answer key marks all three
papers. Nobody has to compare the students' working with each other;
each is checked against the key, and if all three match the key, they
match each other.
<span slot="breaks">An answer key is written by someone who knows the
answers. The corpus was written by people, too, and if a comment is
wrong, all three implementations are forced to be wrong the same way.
DRIP.md says the corpus is the source of truth for wording for exactly
this reason: someone had to decide.</span>
</Analogy>

<Analogy extra title="a reference weight at a market">
A market keeps one certified kilogram, and every stallholder's scale is
checked against it; the scales can be of any make, as long as they
agree with the weight.
<span slot="breaks">A weight checks one number; the corpus checks 344
behaviours, and a scale that passes them all could still be wrong on a
program nobody wrote. That gap is what the fuzzers at the end of this
chapter go looking for.</span>
</Analogy>

## Four kinds of comment

A program says what it should do with four markers, all documented in
the corpus's `README.md`:

<Examples of="shared-corpus">

```drip
print 1 + 2; # expect: 3
```

```drip
print 1 print 2;
# expect compile error: line 1: expected
#   ';' after the value, found 'print'
```

```drip
fn f(a, b) { return a + b; }
f(
  1,
  "x"
);
# expect runtime error: cannot add a
#   number and a string  (on line 1)
# expect trace: at line 1 in fn f
# expect trace: at line 2 in script
```

<Run id="shared" />

</Examples>

The first is the commonest: `# expect:` is one line of output. The
second is `compile/missing_semicolon.drip` (its comment, which really
sits at the end of line 1, is wrapped here): `# expect compile error:`
lists the compile errors, exactly and in order, and means the program
must exit with 65 without running anything. The third is
`errors/call_spanning_lines.drip`, shortened: `# expect runtime error:`
gives the message and means exit 70, and the two `# expect trace:`
lines pin the whole stack trace, innermost first. Notice the second
trace line says line 2, where the call's `(` is, although the arguments
run on to line 5; that is DRIP.md's rule, and three implementations had
to agree on it. Without `trace` lines, only the innermost `at` line is
checked, against the line the runtime-error comment is on. The fourth is
`by_reference.drip` again, for you to run and change.

<Callout kind="definition">
A **shared corpus** is one set of test programs that every
implementation of a language must pass, with each program's expected
behaviour (its output, its compile errors, its runtime error and stack
trace, its exit code) written beside it, so that the tests belong to
the language rather than to any one implementation.
</Callout>

<Formal title="Passing the corpus">

```text
passes(I) ⇔ ∀p ∈ C. run(I, p) = expect(p)
passes(I) ∧ passes(J) ⇒ ∀p ∈ C.
    run(I, p) = run(J, p)
```

<span slot="read">An implementation I passes the corpus C when, for every
program p in C, what I does with p equals what p's comments expect. If I
and J both pass, they behave the same on every program in C (and the
corpus says nothing about programs outside it).</span>
</Formal>

## The Rust side: cargo test

`tests/corpus.rs` runs every program except the benchmarks; it is short,
because the work is in `tests/common/mod.rs`, a port of `check()` from
the TypeScript runner `test/corpus.ts`:

```rust
fn main() {
    let options = Options {
        debug_gc: true,
        ..Options::default()
    };
    common::run_suite("corpus",
        |t| !common::is_benchmark(t),
        options);
}
```

(rewrapped). It has its own `main` because `Cargo.toml` sets
`harness = false` for it<Cite id="cargo-targets" />: Rust's built-in
test runner would make one test of the whole folder, whereas this prints
one line per program, as the TypeScript runner does, and a failure says
which file. `run_suite` reads each program, runs it with `drip::run`
(in the same process, so no files or pipes are involved), wraps the run
in `catch_unwind` so that a panic fails only that program, and calls
`check`, which compares the exit code, then the compile errors or the
runtime error and its trace, then stdout line by line. `debug_gc` makes
the heap never reuse a freed slot, so a collector bug panics instead of
quietly reading another object. The expectations are found by hand,
with `str::find` and `strip_prefix`, because the crate has no
dependencies at all, not even a regex crate.

<CheckSteps client:visible />

`tests/stress_gc.rs` is the same runner with `stress_gc: true`: the
heap collects before **every** allocation and never reuses a slot, so a
value that is only on a Rust local, and not on any root, is freed at the
first chance, and the next read of it panics. It runs the 165 programs
in the ten folders that allocate most (`closures`, `classes`,
`inheritance`, `strings`, `functions`, `lists`, `methods`, `fields`,
`for` and `programs`). On 2026-11-02, `cargo test` printed
`corpus result: ok. 334 passed; 0 failed` and
`stress GC result: ok. 165 passed; 0 failed`, beside the 13 unit tests
in the modules and the 6 in `tests/vm.rs`.

## Byte for byte, and mangled programs

Passing the corpus says each implementation matches the comments; it
does not say they match each other on things the comments leave out,
such as a second error after the first. `scripts/compare_with_ts.mjs`
checks that directly: it runs drip-rs (as a process) and the TypeScript
VM (in Node) on every corpus program, benchmarks included, and compares
stdout, stderr and the exit code byte for byte. Then it **mangles**
2,000 programs, dropping a token, replacing one with a random piece of
Drip such as `fn` or `}`, or inserting one, and compares again. Mangled
programs are mostly broken, so this tests compile errors and error
recovery hardest; for instance, turning line 3 of `by_reference.drip`
into `push(b, 3) fn` makes both print the same two errors:

```text
line 3: expected ';' after the
  expression, found 'fn'
line 4: expected a function name
  after 'fn', found 'print'
```

When I ran `node scripts/compare_with_ts.mjs 2000` on 2026-11-02 it took
27 seconds and printed `corpus: 343 programs compared, 0 differ` (one
program reads the clock, so its output differs on every run and it is
skipped) and `mangled: 2000 programs, 0 skipped (slow), 0 differ`. The
TypeScript side has a fuzzer of its own, `test/fuzz.mjs`, which mangles
programs the same way and checks that the tree-walker's parser and
resolver report exactly the compile errors the VM's one-pass compiler
does; `node test/fuzz.mjs 2000` printed
`2000 mangled programs, 0 disagreements`.

<Prompts ids={['sc-mangle', 'sc-clock']} />

<Callout kind="engine" label="Under the hood">
Comparing two implementations with each other, rather than with a
written answer, is differential testing: generate many programs, run
them through two implementations, and investigate every difference. It
needs no answers written in advance, which is why it can test thousands
of programs nobody wrote. Its blind spot is the
same as the corpus's, a shared mistake: if both VMs were wrong the same
way, every comparison here would still say `0 differ`. That is why the
corpus is checked against DRIP.md by people, and the implementations
against the corpus by programs.
</Callout>

## What you learned

- The **shared corpus** is 344 programs whose comments say what they
  must do; all three implementations run it.
- Four markers: **`# expect:`**, **`# expect compile error:`**,
  **`# expect runtime error:`** and **`# expect trace:`**.
- drip-rs's suites bring their own `main` (**`harness = false`**) to

  allocation, so a missing root fails at once.

  for byte, on the corpus and on 2,000 mangled programs.
