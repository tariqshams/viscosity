## Saying no

Viscosity's differential corpus is a folder of 40 small programs, each
run twice, once as written and once compiled, and the two outputs must
match. Each file's first line, such as `// viscosity: ps=aos`, also
says which layout Viscosity must pick, and 18 of the 40 files are
there, at least in part, to make it *refuse*. A wrong refusal costs
some speed; a wrong acceptance changes what a program prints. So the
refusals are tested as carefully as the transformations.

<Analogy title="a bank teller and a signature">
A bank teller who cannot verify a signature does not cash the cheque.
It is not an accusation, since the cheque may be perfectly good; the
teller cannot prove it, and the cost of being wrong would fall
on someone else.
<span slot="breaks">A teller can ask for identification and try
again; Viscosity cannot ask you anything while it compiles, so it can
only refuse, and tell you why in its explain output.</span>
</Analogy>

<Analogy extra title="a pharmacist and an unclear prescription">
A pharmacist who cannot read a word on a prescription does not guess.
The doctor probably meant the right thing, but "probably" is not good
enough when the patient pays for a mistake; the prescription goes back
with a note saying exactly which word was unclear.
<span slot="breaks">The pharmacist's note goes to the doctor, who
fixes the prescription; Viscosity's note goes to you, and the fix,
such as keeping an index instead of an element, is a change you make
to your own code.</span>
</Analogy>

<Callout kind="definition">
A **bailout** is leaving a collection unchanged because its safety
cannot be proved. In Viscosity it is a reason string in the
collection's `bailouts` list, and `viscosity explain` prints it after
**`unsafe:`**. A bailout does not say that something is wrong; only
that something might be.
</Callout>

<Formal title="Prove, or guess and check">

```text
Viscosity:  prove safe(c)  ⇒ transform c
            otherwise      ⇒ keep c
V8:         assume P, run fast code,
            check P;  ¬P ⇒ deoptimize
```

<span slot="read">Viscosity transforms a collection only when it can
prove, before the program runs, that it is safe; otherwise it keeps
it, and that refusal is the bailout. An engine such as V8 works the
other way round: it assumes a fact P from what it has seen so far,
runs fast code that relies on P, checks P as it goes, and if P ever
turns out false, deoptimises, throwing the fast code away. Viscosity
has no "check as it goes", which is why it must prove.</span>
</Formal>

## Lesson 1: two names, one object

From `aliasing_identity.js`:

```js
const keep = [];
for (let i = 0; i < ps.length; i++)
  keep.push(ps[i]);
keep[0].x = 42;
console.log(ps[0].x, keep[0] === ps[0]);
```

```text
ps (line 2) {x} → kept as array of
  objects
  · unsafe: line 7: an element is
    compared or combined with "==="
  · unsafe: line 5: an element is used
    by push
```

The program builds a second array, `keep`, holding the very same
objects; writes `42` through it; and prints `42 true`, because there is
one object with two names (as *References: two names, one object*
showed). In a struct of arrays, an element is a row number, not an
object. To give `keep` an element, Viscosity would have to build one,
and a built object is a copy: writes to it are lost, and `===`
compares identity, so a fresh copy is never the same
object<Cite id="mdn-equality" />. Run what columns would have to fake:

<Run id="fake" />

*Identity and materialization* looks at what it would take to keep
identity anyway; here, Viscosity's answer is to refuse.

## Lesson 2: a name that outlives the line

Here is a spot the difference, from `closure_alias.js`, with the fix
next to it:

```js
// refused
const p = ps[3];
const f = () => p.x;

// accepted, same output
const k = 3;
const f = () => ps[k].x;
```

```text
· unsafe: line 4: an element is stored
  in another variable (p)
```

Both versions are followed by a loop that adds 1 to every `x`, and
then `console.log(f())`, which must print `4`, the value *after* the
loop. In the first, only a real object shared by `p` and `ps[3]` gives
that, and storing an element under another name is enough to stop
Viscosity (it does not follow `p` into the closure). The second keeps
the *index* instead of the element, so `f` reads the column at the
moment it runs. Try it: replace the two lines in the playground and
watch the verdict change.

<Playground client:visible title="Fix the refusal" initial={`const ps = [];

## Lesson 3: code it cannot see

<Examples of="bailout">

```text
escapes_log.js: console.log(ps[3]);
· unsafe: line 5: an element is passed
  to a method call
```

```text
map_method.js:
  ps.map((p) => p.x).slice(0, 3)
· unsafe: line 5: uses .map on the
  array (only .length and .push are
  supported)
· unsafe: the array is passed to a
  method call at line 5
```

```text
throw_from_loop.js: throw e;
  (where e = ps[0])
· unsafe: line 5: an element is
  returned or branched on in <module>()
```

</Examples>

`console.log` prints the object, `{ x: 4, y: 3 }`, keys and all. `map`
calls a function with every element and collects the results. The
third throws an element out of a loop, where any `catch` anywhere
could receive it. None of these can be rewritten into columns without
building objects, and in general a function or a `catch` Viscosity
cannot see into might do anything with what it is given; unknown code
counts as code that observes. That is escape analysis's rule, too.

## Lesson 4: shapes, names and types

Four more refusals come from facts the earlier chapters established:

```text
// shape_mismatch.js (Record shapes)
· unsafe: line 4: records with
  different fields or field order
  ({x, y} vs {y, x})
// reassigned.js: later, ps = [];
· unsafe: "ps" is reassigned (line 5),
  so it may not always hold this array
// string_index.js: const k = '5';
· unsafe: line 6: indexes the array with
  something that may not be a number
```

`reassigned.js` is the plainest: after `ps = []`, the name means a
different array, one built after Viscosity's rewrite was planned, so
every `ps[i]` would have to work on both. And `ps[k]` with a string
happens to work for `'5'`, but the same line with `'length'` reads a
property, so a string cannot be trusted as an index. (The corpus even
has `comma_field_name.js`, where a field called `'a,b'` must not be
mistaken for the two fields `a` and `b`.)

## Lesson 5: callers it cannot see

```text
// interproc_mixed.js: total(a), total(b)
· unsafe: line 10: passed to total(),
  which is also called with other values
// param_unknown.js:
//   export function nudge(dx) {...}
ps (line 2) {x} → kept as array of
  objects
  · no field is provably numeric, so
    there are no typed columns to gain
```

The second one is not a bailout at all; notice there is no `unsafe:`.
`nudge` is exported, so its callers are not all visible and `dx` might
be anything; `ps[i].x += dx` could then put a string in `x`, so `x`
gets no typed column, and with no typed column there is nothing to
gain. The same goes for `all_generic.js`, whose only field is a string,
and for `no_loops.js` and `small_auto.js`: safe, but not worth
changing. Those are the cost model's decisions, in the next chapter.

<Callout kind="engine" label="Under the hood">
Engines bail out too, but later. V8's optimising tiers speculate from
the feedback they have seen and, when a guess fails at run time,
deoptimise: they throw the optimised code away and carry on in a
slower tier<Cite id="v8-maglev" />. A bailout there costs time at the
moment it happens. Viscosity's bailouts happen before the program runs
and cannot be undone, so they last for the whole run; in exchange, the
decision is written down, with a reason you can read and act on.
</Callout>

## What you learned

- A **bailout** leaves a collection unchanged because safety cannot be
  proved; explain prints each one after `unsafe:`. Viscosity proves
  before it acts, where an engine guesses, checks and deoptimises.
- **Identity**: a second name (another array, a variable, a closure)
  or `===` needs real element objects, which columns do not have;
  keeping an index instead of an element often fixes it.
- **Unknown code**: calls, array methods and `throw` that Viscosity
  cannot see past might observe the elements, so they count as
  observing.
- **Shapes, names, types**: mismatched or shared literals, a
  reassigned binding, and indexes that may not be numbers.
- **Callers**: a known function must get the same collection at every
  call. Unknown callers can also make columns non-numeric, which is a
  cost decision, not a bailout.
