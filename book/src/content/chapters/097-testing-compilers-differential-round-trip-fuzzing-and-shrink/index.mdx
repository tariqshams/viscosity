## The worst kind of bug

When your code has a bug, you read your code; when the compiler has a
bug, your code is fine and the program still does the wrong thing, and
nothing in your source points at the cause. If a program Viscosity
rewrote ever prints something different, or fails differently,
Viscosity is broken, however fast it is.

So we test it, and at once hit the hard part: a test needs an
**oracle**, something that says what the right answer is, and for a
compiler the answer is a whole program's behaviour, which nobody wants
to write out by hand for thousands of programs. The research on compiler
testing treats the choice of oracle as one of its central
questions<Cite id="chen2020survey" />. A **unit test** checks one piece
against an answer you know; a **golden test** stores a whole output once
(checked by a person) and compares every later run with it, as the Drip
corpus does with its `# expect:` comments. The other kinds need no
stored answer at all:

## Two programs that must agree

<Analogy title="checking a translation without the language">
You can check a translated set of directions without speaking either
language: hand the original to one person and the translation to
another, ask both to follow them, and see whether they end up at the
same door.
<span slot="breaks">Both walkers could take the same wrong turn, and you
would never know; two implementations can share a bug, which is why
agreement is strong evidence, never a proof.</span>
</Analogy>

<Callout kind="definition">
**Differential testing** runs two implementations of the same thing on
many inputs and compares the results; every difference is a bug in one
of them, and no expected outputs are needed<Cite id="mckeeman1998" />.
For a compiler the two are usually the program before and after
compiling, two compilers, or two versions of one compiler.
</Callout>

Viscosity's corpus is a folder of small programs, each built to probe
one case (an escape, a shape mismatch, an out-of-bounds read), whose
first line says what Viscosity should decide, such as
`// viscosity: ps=soa`. The test in
`frontend-js/test/differential.test.ts`, simplified:

<Examples of="differential-testing">

```ts
const r = compile(src, jsPlugin());
expect(got(r.plan)).toEqual(want(src));
const before = runIsolated(src);
const after = runIsolated(r.code);
expect(after).toEqual(before);
```

</Examples>

The first `expect` checks the decisions against the header, because a
compiler that never transforms anything passes every behaviour test.
The next two lines run both versions with `runIsolated`, which gives
each a fresh Node VM context (its own globals, so neither run sees the
other's leftovers) and records every `console.log` line *and* the
uncaught error, if any, as `'TypeError: ' + message`; the last `expect`
says the two must be equal. Errors count as results: compiled with
`--bounds assume`, one corpus file prints `0` where the original threw a
`TypeError`, and only comparing errors catches it:

<More title="More: the repository's other differential tests, and metamorphic testing">

`mini-parser.test.ts` compiles every corpus and benchmark program with
acorn and with Viscosity's own small parser, and requires byte-identical
code and explanations. The Rust port's README counts 95 programs, each
compiled in two bounds modes, 190 fixture pairs that all match the
TypeScript engine; and the Drip companion requires its tree-walker and
VM to print the same, byte for byte, on every corpus program.

A **metamorphic test** needs only one implementation: change the input
in a way that must not change the answer (sort a list and its reverse;
rename every variable), and check that it does not. Le, Afshari and Su
ran a program on an input, deleted code that did not execute on that
input, and required the same behaviour; in about eleven months this gave
147 confirmed, unique bug reports against GCC and LLVM<Cite id="le2014emi" />.

<Formal title="What a compiler must preserve">

```text
∀ x.  run(P, x) = run(C(P), x)
```

<span slot="read">For every input x, running the program P on x gives
the same outcome (the same output and the same error) as running C(P),
the compiled program. A differential test checks this for many inputs
and programs, never for all of them.</span>
</Formal>

</More>

## Round trips

There is one more trick, made for front ends: parse a program, print the
tree back to source and parse that, and you must get the same tree; a
difference means the parser or the printer lost something (a missing
pair of brackets is the classic).

<Callout kind="definition">
**Round-trip testing** checks that a pair of opposite operations undo
each other: parse → print → parse gives the same tree, encode → decode
gives the same value. Like differential testing, it needs only the
input, not an expected output.
</Callout>

<Examples of="round-trip-testing">

```ts
const src = 'const a = [1, 2, 3];\n' +
  '// a comment\n' +
  'console.log(a.length);\n';
expect(compile(src, jsPlugin()).code)
  .toBe(src);
```

</Examples>

Viscosity never prints a whole tree (it edits only the parts of the
source it changes), so its round trip is the identity: a program with
nothing to transform, such as this one with no array of objects, must
come back byte for byte, comment included. A printer that dropped
brackets would turn `(1 + 2) * 3` into `1 + 2 * 3`, which parses back as
a different tree.

## The programs nobody thought of

The corpus is programs somebody imagined; the bugs that hurt are the
ones nobody did. When the repository's Viscosity fuzzer was first run,
about 8,000 random programs turned up five bugs, all in both engines;
in one, a field write `ps[i].x = rhs` checked the index *before*
evaluating `rhs`, while the original evaluates `rhs` first, so out of
bounds the two threw different errors.

<Callout kind="definition">
**Fuzzing** generates large numbers of random inputs (for a compiler,
random programs) to find bugs that no hand-written test covers. Paired
with differential testing as the oracle, it needs no expected outputs at
all.
</Callout>

Two things make a compiler fuzzer useful. The random choices come from
a generator started at a known **seed**, so the same seed always gives
the same program and a failure found at 3 a.m. can be made again at 9;
and the programs must be **valid**, with exactly one right behaviour. A
C program that reads uninitialised memory may legitimately do different
things under two correct compilers, so a disagreement on it proves
nothing; Csmith, the best-known C program generator, works hard to
avoid undefined behaviour<Cite id="csmith" /><Cite id="yang2011" />, and
YARPGen found more than 220 bugs in GCC, LLVM and the Intel C++ compiler
while avoiding it by construction<Cite id="livinskii2020" />.

## Shrinking what fails

A fuzzer's failures are big and noisy: a dozen lines, of which the bug
needs two. **Test-case reduction** finds the small version
automatically: remove part of the input, and keep the removal if the
failure is still there. C-Reduce does this for C, driven by an
*interestingness test*, a script that says whether a candidate still
shows the bug<Cite id="regehr2012" />; the repository's `--reduce` is
line-based, halving the chunk size each round, and keeps a removal only
if the candidate still parses and fails in the same way:

<ReduceSteps client:visible />

It ends with a **1-minimal** input: one that still fails, and stops
failing if any single line is removed (not necessarily the smallest
failing input there is).

<More title="More: translation validation">

Testing samples programs. **Translation validation** checks, each time
the compiler runs, that the program it produced is equivalent to the one
it was given; Necula built such a checker for the GNU C compiler's
optimiser<Cite id="necula2000" />. Viscosity has none; its differential
tests are the sampled version of the same question. Coverage-guided
fuzzing, which keeps the random inputs that reach new code, comes in
*TypeScript against Rust: differential tests, fuzzing and shrinking*.

</More>
