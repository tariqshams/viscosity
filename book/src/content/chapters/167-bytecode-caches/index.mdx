## The second visit

The previous chapter saved work by not parsing what is not called.
However, a page you visit every day ships the same script every day, and
every day V8 would parse and compile the same functions into the same
bytecode again. The work is identical each time; the obvious move is to
do it once and keep the answer.

<Analogy title="a café regular">
A regular orders the same thing every morning. The barista could take the
order from scratch each time, or keep it written on a card by the till;
as long as the regular does not change their mind, the card saves the
asking.
<span slot="breaks">A barista would notice a new face asking for "the
usual"; a cache cannot see what it is being used for, so somebody has to
check that it is being handed to the very same code it came from.</span>
</Analogy>

<Analogy extra title="a saved game">
Loading a saved game puts you straight back where you were, instead of
playing every level again to get there.
<span slot="breaks">A save from an older version of a game sometimes still
loads; a bytecode cache is only good for exactly the source and engine it
was made by, and anything else must be refused, or the wrong code
runs.</span>
</Analogy>

V8 can serialise compiled code (write it out as bytes), and a later
compile of the same script can rebuild the code from those bytes instead
of parsing and compiling<Cite id="v8-code-caching" />. Chrome uses this in
three steps<Cite id="v8-code-caching-devs" />:

<Figure caption="Chrome's code cache, as the V8 team described it in 2019 (updated 2020). The first visit stores the file, the second also stores its compiled code, and from the third the compile step is skipped." takeaway="A cached script skips parsing and compiling.">
  <CacheRuns />
</Figure>

Since Chrome 66 (2018) the cache is made *after* the script's top level
has run, so it also holds lazy functions that ran during
startup<Cite id="v8-improved-code-caching" />. Node exposes the same
machinery through `vm.Script`, whose `createCachedData()` makes the bytes
and whose `cachedData` option offers them back<Cite id="node-vm-cached-data" />:

```js
const vm = require('node:vm');
const src = `
function add(a, b) { return a + b; }
function sub(a, b) { return a - b; }
add(1, 2);`;
const s = new vm.Script(src);
const before = s.createCachedData();
s.runInThisContext();
const after = s.createCachedData();
console.log(before.length, after.length);
```

Line 1 loads Node's `vm` module; lines 2 to 5 are a tiny script with two
functions, of which only `add` is called; line 6 compiles it (both
functions lazily); line 7 takes a cache before running, line 8 runs the
script, and line 9 takes a cache again. Step through what happens, and
what happens when the cache is offered back:

<Callout kind="definition">
A **bytecode cache** (or **code cache**) stores a script's compiled
bytecode so that a later load of the *same* script can skip parsing and
compiling. It is only valid for exactly the source and the engine version
it was made by; a cache from one Node version, for example, is not reused
by another<Cite id="node-compile-cache" />.
</Callout>

<Prompts ids={['cache-what', 'cache-after-run']} />

<Formal title="When a cache may be used">

```text
use(cache, src) ⇔ src = cache.src
                ∧ engine = cache.engine
```

<span slot="read">A cache may be used for a source if and only if (⇔) the
source is exactly the one the cache was made from, and (∧) the engine is
the same one that made it. Both halves must hold; the rest of the chapter
shows that V8 checks the first one only roughly.</span>
</Formal>

<Examples of="bytecode-cache">

```
// the program above
Node v22.23.4, V8 12.4.254.21
528 672
// with node --no-lazy
824 824
```

```js
// offer the 672 bytes back
new vm.Script(src, { cachedData: after })
  .cachedDataRejected;        // false
new vm.Script(src + ' ',
  { cachedData: after })
  .cachedDataRejected;        // true
// same length, different code:
// a + b changed to a - b   →  false (!)
```

```
$ NODE_COMPILE_CACHE=cache \
  NODE_DEBUG_NATIVE=COMPILE_CACHE node m.js
[compile cache] ... was accepted
$ # edit m.js: a+b becomes a-b, run again
[compile cache] ... code hash mismatch
```

</Examples>

The first shows what goes into a cache: 528 bytes before running and 672
after, because by then `add` had been compiled and its bytecode came
along, while `sub` stayed lazy; with `--no-lazy`, which turns lazy
parsing off, everything is compiled up front and both caches are 824
bytes. The second offers the cache back: accepted for the identical
source, and rejected when one space is added. But in my test a change
that kept the length the same (`a + b` to `a - b`) was *accepted*, and
the script then ran the old `a + b` code: V8 12.4's own check is coarse,
and making sure a cache belongs to exactly this file is the job of
whoever stores it. The third shows Node doing that job: with its module
compile cache on, Node keeps caches on disk in a folder named after the
Node version<Cite id="node-compile-cache" />, and its debug output shows
it accepting the cache for an unchanged file, and rejecting it with "code
hash mismatch" after the same one-character edit.

<Callout kind="pitfall">
If you store caches yourself with `vm.Script`, store a hash of the source
text next to the bytes and compare it before offering them back; do not
rely on `cachedDataRejected` alone. In my Node 22 test, a same-length
edit got past it.
</Callout>

<Callout kind="engine" label="Under the hood">
The V8 team's own advice on caching for web developers starts with "do
nothing": the heuristics change between releases<Cite id="v8-code-caching-devs" />.
A cache holds bytecode, the starting point for every tier above the
interpreter; Sparkplug, for one, compiles from bytecode, so it benefits
from bytecode that was never recompiled<Cite id="v8-sparkplug" />.
</Callout>

## What you learned

- A **bytecode cache** stores compiled bytecode so the same script can
  skip parsing and compiling on a later load; Chrome makes one on the
  second visit and uses it from the third.
- Made after the top level runs, it also holds lazy functions that were
  called; functions never called stay out.
- A cache is only valid for exactly its source and engine; V8 12.4's own
  check can be fooled, so the embedder (Chrome, Node's compile cache)
  keys it by the real content.
