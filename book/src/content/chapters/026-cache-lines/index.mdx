## Fewer reads, same time?

Here is a strange experiment. Make a big `Float64Array`, then add 1 to
every element. Then do it again, but only to every 8th element:

```js
for (let i = 0; i < n; i += 1) xs[i] += 1;
for (let i = 0; i < n; i += 8) xs[i] += 1;
```

The second loop does one eighth of the work. You would expect it to take
one eighth of the time. Try it:

<Run id="every-eighth" />

If your machine behaves like most, the second loop is nowhere near eight
times faster. Something other than the number of reads is setting the
pace.

## Memory moves in blocks

<Callout kind="intuition">
The warehouse from chapter 25 doesn’t ship single screws. Ask for one
and it sends the whole box the screw came in. If the next thing you need
is in that box too, it’s already on your desk. If not, the rest of the
box was a wasted trip.
</Callout>

The box is called a **cache line**. On most processors it is 64 bytes
<Cite id="slotin-amh-cache-lines" />: Linux assumes 64-byte lines for
64-bit x86 and for 64-bit ARM<Cite id="linux-x86-kconfig-cpu" />. Some
chips use bigger lines; Apple describes its caches as using 64- or
128-byte lines<Cite id="apple-wwdc25-cpu" />. This book uses 64.

Eight `float64`s fill one line. So every eighth element of `xs` is in a
*different* line, and the second loop still has to fetch every line of
the array. Same lines, same trips to memory, nearly the same time.

Memory is divided into lines at fixed boundaries, so working out which
line an address is in is one division:

```js
const line = Math.floor(addr / 64);
// addresses 0..63 are line 0,
// 64..127 are line 1, and so on.
```

<Callout kind="definition">
A **cache line** is the block that caches move between levels: 64 bytes
on most mainstream processors. Asking for one byte fetches its whole
line<Cite id="slotin-amh-cache-lines" />. The line of address `a` is
`Math.floor(a / 64)`.
</Callout>

## Counting lines, not reads

Now go back to chapter 25’s loop, summing every `mass`, and count lines.
The objects here use a toy layout, one per line, to keep the picture
simple.

<LineSteps client:visible />

The objects need a new line for every particle, plus the lines holding
the pointers. The `Float64Array` needs one line per eight particles. That
is the right way to think about memory cost: count the lines a loop
touches, not the values it reads<Cite id="slotin-amh-cache-lines" />.

<Callout kind="definition">
**Spatial locality** means using data *near* data you just used, so it
arrives in lines you have already fetched. **Temporal locality** means
using the *same* data again soon, while it is still in a cache<Cite id="slotin-amh-locality" />.
A loop over a contiguous typed array has excellent spatial locality.
</Callout>

Temporal locality is about *when*. These two loops do the same sums:

```js
// two passes: xs is fetched twice
for (const v of xs) a += v;
for (const v of xs) b += v * v;

// one pass: each line is used for both
for (const v of xs) {
  a += v;
  b += v * v;
}
```

If `xs` is too big for the caches, the second pass of the first version
finds its early lines long gone and fetches everything again. The fused
loop uses each value while it is still hot.

## Stride

The gap, in bytes, from one read to the next is the loop’s **stride**.
Step through three layouts of the same masses:

<StrideSteps client:visible />

<Callout kind="definition">
The **stride** of a loop is the distance in memory between consecutive
accesses. For one field of a packed record with `k` fields of 8 bytes,
the stride is `8 × k` bytes. When the stride is small, many reads share
a line. Once it reaches 64 bytes, every read pays for a whole line.
</Callout>

Fetching unused bytes costs more than time spent waiting. It also uses
up **bandwidth**: how many bytes per second can flow from memory to the
CPU. A rough 2021 table puts main memory at around ten gigabytes per
second, and L1 several times higher<Cite id="slotin-amh-hierarchy" />.
A loop that streams through a big array is limited by that flow. If only
8 bytes of every 64 are useful, seven eighths of the flow is wasted.

<Prompts ids={['stride-what', 'stride-64', 'bandwidth-what']} />

This book’s benchmark measured exactly these three layouts:

<BenchBars suite="sum-one-field" n={100000} title="Sum every mass: three layouts"

The order matches the line counts. The packed buffer removes the objects
and pointers, but it still drags five unused fields through the cache
for every mass. The struct of arrays fetches nothing it doesn’t use.

<Callout kind="engine" label="Under the hood">
This is the heart of Viscosity. Your code says `ps[i].mass`, and as far
as the hardware is concerned that means “fetch the line holding this
particle, use 8 bytes of it”. Viscosity’s compiler rewrites the loop to
read `mass[i]` from a `Float64Array` instead: stride 8, every byte used.
Whether that is worth it depends on the loop. A loop that reads *every*
field of each particle uses whole lines either way, so the benefit
shrinks, and Part VIII’s cost model has to tell those cases apart.
</Callout>

## What you learned

- Memory moves in **cache lines**: 64-byte blocks on most mainstream
  processors. The line of address `a` is `Math.floor(a / 64)`.
- Count lines touched, not values read.
- **Spatial locality**: use data near what you just used. **Temporal
  locality**: use the same data again soon.
- **Stride** is the distance between consecutive accesses. Small strides
  share lines; strides of 64 bytes or more pay for a line every read.
- **Bandwidth** is how many bytes per second can flow. Unused bytes in a
  line waste it.
