## Two functions that never met

Change the running example a little, so that the square is worked out
by a function of its own:

```drip
fn sq(x) {
  return x * x;
}
fn sumsq(n) {
  let s = 0;
  let i = 0;
  while i < n {
    s += sq(i);
    i += 1;
  }
  return s;
}
print sumsq(4);   # 14
```

Now suppose `sq` lives in another file, compiled last week, perhaps by
a different compiler. When `sumsq` calls it, where should it put `i`
so that `sq` can find it? Where will the answer be? How does `sq` know
where to jump back to? Neither function can look inside the other, so
the only way this works is if both were compiled to the same set of
rules, agreed in advance.

<Analogy title="the changeover box in a relay race">
In a relay, the baton must pass from one runner to the next inside a
marked box on the track, in the right hand, at a run. Neither runner
needs to know how the other trains; they only both keep the rules of
the box.
<span slot="breaks">Relay runners can see each other and adjust; a
caller and a callee never meet, so a mistake (an argument in the wrong
register) is not noticed by anyone, and the program quietly computes
the wrong answer.</span>
</Analogy>

## The calling convention

For whole numbers and addresses, RISC-V's rules are
these<Cite id="riscv-psabi" />. The first eight arguments go in
registers `a0` to `a7`, in order; any more go on the stack, the ninth
at `0(sp)`, the tenth at `8(sp)` and so on, as the callee sees `sp` on
entry. The result comes back in `a0` (and `a1`, if it needs two
registers). And the address to come back to goes in `ra`, the return
address register: `call sq` jumps to `sq` and, in the same step,
stores the address of the instruction after the call in `ra` (the
assembler spells `call` as `auipc` plus `jalr`, the jump-and-link
instructions<Cite id="riscv-asm-manual" />), and `ret` is
`jalr x0, 0(ra)`, a jump to whatever `ra` holds. Step through one trip
round `sumsq`'s loop, as clang compiles it:

<CallSteps client:visible />

<Callout kind="definition">
A **calling convention** is the set of rules every function follows so
that separately compiled code can call each other: where the caller
puts the arguments, where the callee leaves the result, how the return
address is passed, what the stack must look like at the call, and
which registers each side may change. On RISC-V: arguments in `a0` to
`a7` and then on the stack, results in `a0` and `a1`, the return
address in `ra`<Cite id="riscv-psabi" />.
</Callout>

<Formal title="Where an integer argument goes (RV64)">

```text
arg k, 0 ≤ k ≤ 7:  a_k        (= x(10+k))
arg k, k ≥ 8:      mem[sp + 8·(k − 8)]
result:            a0 (and a1)
return address:    ra (= x1)
```

<span slot="read">Number the arguments from 0. Argument k, for k from
0 to 7, travels in register a-k, which is register 10 plus k. From the
ninth argument (k = 8) on, argument k is in memory at sp plus 8 times
(k minus 8), measured with sp as the callee finds it on entry. The
result comes back in a0, and in a1 as well if it is two registers
wide, and the return address arrives in ra, which is x1.</span>
</Formal>

<Examples of="calling-convention">

```text
sq:                    # long sq(long x)
    mul  a0, a0, a0    # x in a0, result a0
    ret
```

```text
f:          # long f(long a, long b, long c)
    mul  a1, a2, a1    # b * c
    add  a0, a1, a0    # a + b * c
    ret
```

```text
use9:      # return nine(1, 2, ..., 9);
    li   t0, 9
    li   a0, 1         # ... a1 to a6 ...
    li   a7, 8
    sd   t0, 0(sp)     # 9th argument
    call nine
nine:      # its 9th parameter:
    ld   a0, 0(sp)
    ret
```

</Examples>

All three are clang's `-O2` output for small C functions, trimmed
(the third omits `use9`'s frame set-up, which the next chapter
explains). In the first, `sq` reads its only argument from `a0`,
squares it, and leaves the answer in `a0`, which is also where the
argument was: the convention allows a callee to overwrite its argument
registers. In the second, `a` is in `a0`, `b` in `a1` and `c` in `a2`
by position, and the compiler is free to reuse `a1` for `b * c`
because the caller has no claim on it. The third shows the ninth
argument: `use9` fills `a0` to `a7` with 1 to 8 and stores 9 at
`0(sp)`, and `nine` finds it at exactly the same address, `0(sp)`,
because a call does not move `sp`.

Here is the same agreement played by hand in JavaScript, with one
shared object standing in for the registers: `sq` knows nothing about
its caller except that the argument is in `a0`, the answer must go in
`a0` and the way back is in `ra`.

## The ABI: everything else the two sides agree on

Registers for arguments are only part of the story. If `sumsq` passed
`sq` a record, both sides would also have to agree on how big each
field is, in what order the fields sit, and whether the record travels
in registers or in memory; and to be joined into one program, both
files must be in the same object-file format. All of that together is
the ABI.

<Analogy title="shipping containers">
A container loaded in one country goes onto a ship, a train and a
lorry built in others, because its size, corner fittings and weight
limits are standard; nobody unpacks it at the border.
<span slot="breaks">A container standard fixes only the outside of the
box; an ABI also fixes the inside (how each kind of value is laid out
in bytes), and breaking any part of it does not jam a crane, it makes
the program silently wrong.</span>
</Analogy>

<Callout kind="definition">
An **application binary interface** (**ABI**) is the full set of rules
that compiled code from different sources agrees on so it can work
together: the calling convention, the sizes, alignments and layouts of
data types, how records are passed and returned, the stack's
alignment, and the format of object files. RISC-V's is the psABI,
which covers the calling convention, the ELF object-file format, DWARF
debugging information and more; it names variants such as **LP64**
(integer registers only) and **LP64D** (doubles passed in
floating-point registers, the recommended default on RV64G)<Cite id="riscv-psabi" />.
</Callout>

In LP64 (the name means "longs and pointers are 64 bits"), a `char` is
1 byte, an `int` 4, and a `long` and a pointer 8 each<Cite id="riscv-psabi" />.
Records follow two rules that matter here: one no bigger than two
registers (16 bytes on RV64) travels in a pair of argument registers,
first 8 bytes in the lower-numbered one; anything bigger is copied to
memory by the caller and passed **by reference**, as its
address<Cite id="riscv-psabi" />:

<Figure takeaway="Small values go in registers; a record of up to 16 bytes goes in a register pair; anything bigger goes by its address." caption="Three arguments as RISC-V passes them on RV64. The 24-byte struct is copied into the caller's frame and only its address travels in a0.">
  <ArgsFigure />
</Figure>

<Examples of="abi">

```text
mk:     # struct P mk(long x)
        #   { return (struct P){ x, 1 }; }
    li   a1, 1         # second field
    ret                # first is already a0
```

```text
callq:  # sumq((struct Q){ x, 2, 3 })
    sd   a0, 0(sp)     # copy q into the
    li   a0, 2         # caller's frame
    sd   a0, 8(sp)
    li   a0, 3
    sd   a0, 16(sp)
    mv   a0, sp        # pass its address
    call sumq
```

```text
$ ld.lld m.o sq.o
ld.lld: error: sq.o: cannot link object
files with different floating-point ABI
from m.o
```

</Examples>

The first returns a two-field record (`struct P { long x, vx; }`, the
particle of the last chapter) in `a0` and `a1`: `x` arrived in `a0` and
can stay there, so the whole function is one `li` and a `ret`. The
second passes a three-field, 24-byte record: too big for a pair, so
`callq` writes the fields into its own stack frame and passes the
address `sp` in `a0` (frame set-up again omitted). The third is a
spot the difference at the scale of whole files: `sq.c` was compiled
with `-mabi=lp64d` and `m.c` with `-mabi=lp64`, so the two disagree on
where floating-point values travel, and LLVM's linker refuses to join
them with exactly that error; compiled with the same `-mabi`, they
link. Viscosity, as a source-to-source compiler, never has to keep
these rules, but any back end that emits machine code for a real
system must keep every one of them.

## What you learned

- A **calling convention** says where arguments, results and the return
  address go: on RISC-V, `a0` to `a7` and then the stack, results in
  `a0` and `a1`, and `ra`, set by `call` and used by `ret`.
- An **ABI** is the whole agreement compiled code relies on: the calling
  convention plus type sizes and layouts, how records are passed, stack
  alignment and the object-file format; RISC-V's is the psABI, with
  variants such as LP64 and LP64D.
- Records of up to two registers travel in a register pair; bigger ones
  are passed by reference.
