## A size the analysis can't count

*Access patterns in Rust* showed that a push inside a function makes a
collection's size unknown, because the analysis doesn't count calls.
*Profile-guided optimization* answered that in the TypeScript engine by
running the program once and measuring. The Rust binary takes the same
commands. Here is a program whose 20 elements are pushed inside a
function:

```js
const ps = [];
function spawn(x) {
    ps.push({ x, vx: 1 });
}
for (let i = 0; i < 20; i++) spawn(i);
for (let f = 0; f < 100; f++) {
    for (let i = 0; i < ps.length; i++) {
        ps[i].x += ps[i].vx;
    }
}
console.log(ps[0].x);
```

and a real session with it (release build, rustc 1.97, Node 22.23;
long lines wrapped, and the first report trimmed):

```
$ viscosity explain spawn.js
ps (line 1) {x, vx} → struct of arrays
  · size unknown statically
$ viscosity profile spawn.js -o p.json
$ cat p.json
{
  "ps": {
    "maxLength": 20
  }
}
$ viscosity explain spawn.js \
    --profile p.json
ps (line 1) {x, vx} → kept as array of
  objects
  · about 20 elements (measured): below
    the 64-element threshold, where the
    benefit is too small
```

The decision flips, as it should, and every line matches the TypeScript
CLI's. The JSON file is byte-identical to the one the TypeScript CLI
writes too, and the reason is the most interesting thing in
`crates/cli/src/profile.rs`.

## Writing a program that counts

`instrument` in `profile.rs` turns the source into a program that
records its own sizes. It starts the way the compiler does,
`JsPlugin.lower(source)` and then `analyze`, so it finds exactly the
collections the planner will later ask about (a syntax error becomes
the `Err` string the CLI prints, through `map_err(...)?`). For each
collection it takes the byte span of its initialiser, such as `[]`,
into a list of `(start, end, name)` edits, and then (rewrapped):

```rust
edits.sort_by_key(|e|
    std::cmp::Reverse(e.0));
let mut out = source.to_string();
for (start, end, name) in edits {
    let (start, end) =
        (start as usize, end as usize);
    let quoted = serde_json::
        to_string(name)
        .expect("strings serialize");
    let wrapped = format!(
        "__vsc_track({quoted}, {})",
        &out[start..end]);
    out.replace_range(start..end,
        &wrapped);
}
Ok(format!("{PRELUDE}{out}"))
```

The edits are sorted by start, **last first** (`Reverse` flips the
order of a sort key), so replacing one span never moves the offsets of
the spans still to come, the same idea as the emitter's edits in *SoA
code generation in Rust*. `replace_range` edits the `String` in place,
and the offsets are UTF-8 bytes from oxc, which is what a `String` is
indexed by. The name is quoted with `serde_json`, so it is always a
valid JavaScript string literal, and the wrapper keeps the original
initialiser as its second argument.

  <WrapOrder />
</Figure>

The `PRELUDE` that goes in front is a Rust `&str` holding JavaScript,
the TypeScript CLI's prelude character for character:

```js
const __vsc_seen = [];
function __vsc_track(name, arr) {
  __vsc_seen.push([name, arr]);
  return arr;
}
process.on('exit', () => {
  const p = {};
  for (const [n, a] of __vsc_seen)
    p[n] = { maxLength: Math.max(
      p[n]?.maxLength ?? 0, a.length) };
  require('node:fs').writeFileSync(
    process.env.VSC_PROFILE_OUT,
    JSON.stringify(p, null, 2));
});
```

(reformatted: the real prelude is seven lines). `__vsc_track` remembers
each array under its name and hands it straight back, so the program
runs exactly as before. When the process exits, the hook takes, for
each name, the largest length of any array tracked under it, and writes
the result as JSON with two-space indentation to the file named by the
environment variable `VSC_PROFILE_OUT`. So in both engines the JSON is
written by Node, with the same code; Rust never formats it, which is
why the two files are identical.

## Running node from Rust

`profile(file)` writes the instrumented program to a temporary
directory and runs it (rewrapped):

```rust
let status = Command::new("node")
    .arg(&inst)
    .env("VSC_PROFILE_OUT", &out)
    .stdin(Stdio::null())
    .stdout(Stdio::null())
    .status()
    .map_err(|e| format!("could not run \
        node (profiling needs Node.js on \
        the PATH): {e}"))?;
```

`std::process::Command` builds a child process step by step: the
program, its argument (the file `instrumented.cjs`), one environment
variable, an empty stdin and a discarded stdout (stderr still shows, so
you see the program's errors). `.status()` runs it, waits for it to
finish, and returns its exit status, or an `Err` if `node` couldn't be
started at all, which `map_err` turns into a helpful message. Then
`if !status.success()` turns a non-zero exit into an error too, "the
profiled program failed (exit code 1)", because a partial run's sizes
could mislead the planner; `status.code()` is `None` when the process
was killed by a signal rather than exiting, and that gets a message of
its own. Only then does `profile` read the file the hook wrote, with
`fs::read_to_string`, and return it. The
TypeScript CLI runs `process.execPath`, the very Node running it; the
Rust binary has no Node of its own, so it looks `node` up on the
`PATH`:

```
$ PATH=/nowhere viscosity profile spawn.js
viscosity: could not run node (profiling
needs Node.js on the PATH): No such file
or directory (os error 2)
```

The temporary directory is owned by a small guard value:

```rust
struct TempDir(std::path::PathBuf);

impl Drop for TempDir {
    fn drop(&mut self) {
        let _ = fs::remove_dir_all(&self.0);
    }
}
```

`Drop` runs when the value goes out of scope, on every way out of
`profile`: the normal return, an early `return Err(...)`, and every
`?`. So the directory is removed whether node succeeded, failed, or
never started, without a single clean-up line at each exit. Step through
the whole round trip:

5 a loop pushed.

**PGO in Rust** starts with `viscosity profile`: `instrument` finds the

JavaScript **prelude** shared with the TypeScript CLI; `profile` runs
the result with **`node`** through `std::process::Command`, with a
**`Drop` guard** removing its temporary directory, and returns the JSON
that the program's exit hook wrote, so the file is **byte-identical** in
both engines.
</Callout>

## What you learned

- **`instrument`** finds collections the way the compiler does and wraps
  each initialiser in `__vsc_track(...)`, applying edits **last first**
  so the byte offsets stay valid.
- The JSON is written by **Node**, from a prelude copied from the
  TypeScript CLI, so it is **byte-identical**; Rust only starts `node`
  with **`std::process::Command`** and checks its exit status.
- A **`Drop`** guard removes the temporary directory on every way out of
  `profile`, `?` included.

## A file anyone can edit

*PGO in Rust* ended with a JSON file that Node wrote. Nothing stops a
person from editing it, or writing one by hand, and then the planner
has to decide what to make of it. Here is a profile whose number has
been typed in quotes, and what both CLIs say about it (I ran them here,
release build, rustc 1.97):

```
$ cat bad.json
{"ps": {"maxLength": "20"}}
$ viscosity explain spawn.js \
    --profile bad.json
viscosity: the profile entry "ps" must be
an object whose maxLength is a
non-negative number
```

The TypeScript CLI prints the same line. It wasn't always so: when the
Rust chapters were first written, the Rust CLI skipped such an entry
(and transformed `ps`), while the TypeScript CLI compared `"20" < 64`
the way JavaScript does (as numbers, so true) and kept the array, so
the two engines made different decisions from one file
(`engine/rust/README.md` lists it as bug 21). Now both apply one rule,
with one wording. This chapter reads the Rust side of that rule, how
the planner uses what it reads, and what a profile can't tell it.

<Analogy title="a delivery note checked at the door">
A warehouse checks a delivery note line by line: every line must name
a product and a quantity written as a number. One line that says "a
few" and the whole note is sent back, with the line that was wrong.
<span slot="breaks">A warehouse might accept the good lines and query
the bad one; the CLI refuses the whole file, because a profile that is
half believed could steer the planner with numbers nobody meant.</span>
</Analogy>

<Analogy extra title="a high-water mark">
A harbour wall has a line showing the highest the tide reached. It
says nothing about when the tide was high, how often, or what it will
do next year.
<span slot="breaks">A high-water mark records the peak whenever it
happened; the profile reads each array's length once, at exit, which
is its peak only because a collection Viscosity can transform never
gets shorter.</span>
</Analogy>

## One rule, one wording

`read_profile` in `crates/cli/src/main.rs` reads the file, parses it
with `serde_json` into a `Value` (a tree of JSON values), and checks it
(rewrapped, with the error messages shortened to comments):

```rust
let obj = json.as_object()
    .ok_or(/* must be a JSON object */)?;
obj.iter()
    .map(|(name, v)| match v.as_object()
        .and_then(|e| e.get("maxLength"))
        .and_then(Value::as_f64) {
        Some(n) if n.is_finite()
            && n >= 0.0 =>
            Ok((name.clone(), n)),
        _ => Err(/* the profile entry … */),
    })
    .collect()
```

`as_object` gives `Some(map)` only for a JSON object, so a file that is
`[1]` stops at once with "the profile must be a JSON object". Then each
entry goes through a chain of `Option`s: is the value an object, does it
have a `maxLength`, is that a number (`as_f64` is `None` for the string
`"20"`)? A **match guard** (`if n.is_finite() && n >= 0.0`) then
refuses infinity, `NaN` and negative numbers. Other keys inside an
entry are ignored, and so are entries for names the program doesn't
have.

The last line does more than it looks. The `map` produces an iterator
of `Result<(String, f64), String>`, and `collect` is asked (by the
function's return type) for one `Result<HashMap<String, f64>, String>`.
Rust's `FromIterator` for `Result` does exactly that: it builds the map
while every item is `Ok`, and stops at the first `Err`, returning it.
So one bad entry refuses the whole file, and the message names that
entry. Step through it on three files:

<Formal title="A valid profile">

```text
valid(P) ⇔ P is an object ∧
  ∀ name ∈ P.
    P[name] is an object ∧
    P[name].maxLength ∈ [0, ∞)
```

<span slot="read">A profile P is valid exactly when it is an object,
and for every name in P, the entry for that name is an object whose
maxLength is a number from zero up, and not infinity.</span>
</Formal>

## Where the planner uses it

The checked map goes into `PlanOptions::profile` as a
`HashMap<String, f64>` of `maxLength` by name, and the size rung of
*Sizes and thresholds in Rust* looks the collection up by its name,
`opts.profile.as_ref().and_then(|p| p.get(&c.name))`. A hit wins over
the estimate, in either direction, and a measured size is worded "about
... (measured)" in a refusal and "(measured by profiling)" in a
transformed collection's reasons. Nothing else in the planner reads the
profile: it is consulted after every safety check, so it can only move
a collection across the size threshold, never make an unsafe rewrite
look safe.

```

```

```
{"ps": {"maxLength": 20, "note": "x"},
 "zz": {"maxLength": 3}}
```

Each is a profile file and the first line the Rust CLI printed for
`explain spawn.js --profile` with it (the TypeScript CLI printed the
same). In the first, `ps` is fine but `qs` is a bare number, and
collecting stops there. The second isn't an object at all. The third
is accepted: the extra key `"note"` is ignored, `zz` names no
collection of the program and is never looked up, and `ps` is kept as
"about 20 elements (measured)".

## What a profile can't say

The code is short enough to read its limits straight off it, and each
one below was checked here with the Rust CLI.

- **Keyed by name.** Give two functions each their own `ps`, one of
  1000 elements and one of 10, and the profile has one entry, `"ps": {
  "maxLength": 1000 }`; with it, explain reports "about 1000 elements
  (measured by profiling)" for both.
- **The length at exit.** The hook reads `a.length` once, at exit, and
  keeps the largest per name. Every tracked array also stays alive until
  then, because `__vsc_seen` holds it.
- **One run, no input.** The program gets no arguments and an empty
  stdin, so it measures one day of the program's life.
- **Scripts only.** The file is run as CommonJS, so a program with
  `import` fails ("Cannot use import statement outside a module"), and a
  program that throws is an error, "the profiled program failed (exit
  code 1)", even though its exit hook wrote the JSON.
- **JavaScript only.** `viscosity profile x.py` refuses, with the
  reference's words: "profile runs JavaScript programs only; Python
  profiling is not supported yet".

<Callout kind="definition">
**Reading a profile in Rust** is `read_profile` in the CLI: the file
must be a JSON **object** whose every entry is an object with a
**finite, non-negative `maxLength`**; the entries are checked with a
chain of `Option`s and a match guard, and **collected into one
`Result`**, which stops at the first bad entry and names it. The result
is a `HashMap<String, f64>` the planner looks collections up in **by
name**, and it can only change the size threshold's verdict.
</Callout>

## What you learned

- `read_profile` accepts only a JSON **object** of entries that are
  objects with a **finite, non-negative `maxLength`**, and both CLIs
  refuse anything else **with the same words**.
- Collecting an iterator of **`Result`s into one `Result`** stops at the
  first `Err`, so one bad entry refuses the whole file.
- The planner looks the profile up **by name**, after every safety
  check, so it can only move a collection across the size threshold.
- A profile is **keyed by name**, records the **length at exit** of
  **one run**, and needs a **CommonJS script** that exits cleanly;
  Python isn't profiled.
