## A size the analysis can't count

A push inside a function makes a collection's size unknown, because the
analysis does not count calls, and *Telling Viscosity more: annotations
and profiles* answered that in the TypeScript engine by running the
program once and measuring. The Rust binary takes the same commands.
Here is a program whose 20 elements are pushed inside a function:

```js
const ps = [];
function spawn(x) {
    ps.push({ x, vx: 1 });
}
for (let i = 0; i < 20; i++) spawn(i);
for (let f = 0; f < 100; f++) {
    for (let i = 0; i < ps.length; i++) {
        ps[i].x += ps[i].vx;
    }
}
console.log(ps[0].x);
```

and a session with it (release build, rustc 1.97, Node 22.23; the first
report trimmed to its verdict and size, long lines wrapped):

```
$ viscosity explain spawn.js
ps (line 1) {x, vx} → struct of arrays
  · size unknown statically
$ viscosity profile spawn.js -o p.json
$ viscosity explain spawn.js \
    --profile p.json
ps (line 1) {x, vx} → kept as array of
  objects
  · about 20 elements (measured): below
    the 64-element threshold, where the
    benefit is too small
```

The decision flips, as it should, and `p.json` (`"maxLength": 20` for
`ps`) is byte-identical to the file the TypeScript CLI writes.

## Writing a program that counts

`instrument` in `profile.rs` starts the way the compiler does,
`JsPlugin.lower(source)` and then `analyze`, so it finds exactly the
collections the planner will later ask about. For each one it takes the
byte span of its initialiser, such as `[]`, into a list of `(start, end,
name)` edits, and then (rewrapped):

```rust
edits.sort_by_key(|e|
    std::cmp::Reverse(e.0));
let mut out = source.to_string();
for (start, end, name) in edits {
    let (start, end) =
        (start as usize, end as usize);
    let quoted = serde_json::
        to_string(name)
        .expect("strings serialize");
    let wrapped = format!(
        "__vsc_track({quoted}, {})",
        &out[start..end]);
    out.replace_range(start..end,
        &wrapped);
}
Ok(format!("{PRELUDE}{out}"))
```

The edits are sorted by start, **last first** (`Reverse` flips the order
of a sort key), so replacing one span never moves the offsets of the
spans still to come. `replace_range` edits the `String` in place, at
oxc's UTF-8 byte offsets<Cite id="rust-std-string-replace-range" />, and
`serde_json` quotes the name as a valid JavaScript string.

</Figure>

The `PRELUDE` in front is a Rust `&str` holding JavaScript, the
TypeScript CLI's prelude character for character. `__vsc_track(name,
arr)` remembers each array under its name and hands it straight back, so
the program runs as before; a `process.on('exit', ...)` hook then takes,
for each name, the largest length of any array tracked under it, and
writes the result with `JSON.stringify(p, null, 2)` to the file named by
the environment variable `VSC_PROFILE_OUT`. So in both engines the JSON
is written by Node, with the same code, and Rust never formats it.

<Examples of="rust-pgo">

```js
const ps = __vsc_track("ps", []);
```

```js
const ps = __vsc_track("ps",
  [{ x: 1 }, { x: 2 }]);
```

</Examples>

The first is the instrumented `spawn.js` after the prelude: the later
pushes go into the very array that was tracked. The second wraps an
array literal whole, so its two elements are counted too.

## Running node, and tidying up

`profile(file)` writes the instrumented program into a temporary
directory and runs it with `std::process::Command::new("node")`, found on
the `PATH` (the TypeScript CLI runs the Node it is running in). A
non-zero exit is an error ("the profiled program failed (exit code 1)"),
because a partial run's sizes could mislead the planner.

The temporary directory is owned by a small guard value:

```rust
struct TempDir(std::path::PathBuf);

impl Drop for TempDir {
    fn drop(&mut self) {
        let _ = fs::remove_dir_all(&self.0);
    }
}
```

`Drop` runs when the value goes out of
scope<Cite id="rust-reference-destructors" />, on every way out of
`profile`, every `?` included, so the directory is removed whether node
succeeded, failed or never started. Step through the round trip:

<More title="The prelude, and the Command">
The prelude, reformatted (the real one is seven lines):

```js
const __vsc_seen = [];
function __vsc_track(name, arr) {
  __vsc_seen.push([name, arr]);
  return arr;
}
process.on('exit', () => {
  const p = {};
  for (const [n, a] of __vsc_seen)
    p[n] = { maxLength: Math.max(
      p[n]?.maxLength ?? 0, a.length) };
  require('node:fs').writeFileSync(
    process.env.VSC_PROFILE_OUT,
    JSON.stringify(p, null, 2));
});
```

And the call that runs it (rewrapped):

```rust
let status = Command::new("node")
    .arg(&inst)
    .env("VSC_PROFILE_OUT", &out)
    .stdin(Stdio::null())
    .stdout(Stdio::null())
    .status()
    .map_err(|e| format!("could not run \
        node (profiling needs Node.js on \
        the PATH): {e}"))?;
```

stderr is left alone, so you see the program's own errors.
`status.code()` is `None` when the process was killed by a signal rather
than exiting, and that gets a message of its own.

<Formal title="What a profile records">

```text
profile(n) = max { a.length at exit
                   | a tracked as n }
```

<span slot="read">The profile's number for a name n is the largest
length, read when the program exits, of all the arrays that were tracked
under the name n.</span>
</Formal>
</More>

<Callout kind="definition">
**PGO in Rust** starts with `viscosity profile`: `instrument` finds the
candidate collections as the compiler does, **wraps each initialiser** in
`__vsc_track(...)` with edits applied **last first**, and prepends a
JavaScript **prelude** shared with the TypeScript CLI; `profile` runs the
result with **`node`**, a **`Drop` guard** removing its temporary
directory. `--profile` then reads the file back through `read_profile`,
which accepts only an object of entries with a **finite, non-negative
`maxLength`**, and the planner looks collections up in it **by name**.
</Callout>

## Reading it back

Nothing stops a person from editing the file. Type the number in quotes,
`{"ps": {"maxLength": "20"}}`, and both CLIs say `viscosity: the profile
entry "ps" must be an object whose maxLength is a non-negative number`.
(Once, the two engines read such a file differently; now
`read_profile` in `crates/cli/src/main.rs` applies one rule, rewrapped,
messages shortened to comments:)

```rust
let obj = json.as_object()
    .ok_or(/* must be a JSON object */)?;
obj.iter()
    .map(|(name, v)| match v.as_object()
        .and_then(|e| e.get("maxLength"))
        .and_then(Value::as_f64) {
        Some(n) if n.is_finite()
            && n >= 0.0 =>
            Ok((name.clone(), n)),
        _ => Err(/* the profile entry … */),
    })
    .collect()
```

Each entry goes through a chain of `Option`s (is it an object, does it
have a `maxLength`, is that a number?), and a **match guard** refuses
infinity, `NaN` and negative numbers. The last line does more than it
looks: the `map` yields `Result<(String, f64), String>` items, and the
function's return type asks `collect` for one `Result<HashMap<String,
f64>, String>`. Rust's `FromIterator` for `Result` builds the map while
every item is `Ok` and stops at the first `Err`, returning it, so one
bad entry refuses the whole file and the message names it. Step through
it on three files:

<More title="What else a profile can't say, and what tests it">
Each limit below was checked with the Rust CLI.

- **The length at exit.** The hook reads `a.length` once, at exit, and
  keeps the largest per name; every tracked array stays alive until then,
  because `__vsc_seen` holds it.
- **One run, no input.** The program gets no arguments and an empty
  stdin, so it measures one day of the program's life.
- **Scripts only.** The file runs as CommonJS, so a program with
  `import` fails, and a program that throws is an error even though its
  exit hook wrote the JSON.
- **JavaScript only.** `viscosity profile x.py` refuses: "profile runs
  JavaScript programs only; Python profiling is not supported yet".

Before there were profile fixtures, the port printed "about 10
(measured) elements" where the reference wrote "about 10 elements
(measured)", and every test passed (`engine/rust/README.md` lists it as
bug 20). Now four profiles in `engine/rust/tests/profiles` go through
both the library and `--profile` in the parity test, `profile_cli.rs`
checks that both CLIs validate profile files identically and clean up
their temporary directories, and the fuzzer gives every batch a random
profile.
</More>

## What you learned

- **`instrument`** finds collections the way the compiler does and wraps
  each initialiser in `__vsc_track(...)`, applying edits **last first**.
- The JSON is written by **Node**, from a prelude copied from the
  TypeScript CLI, so it is **byte-identical**; a **`Drop`** guard removes
  the temporary directory on every way out.
- Collecting **`Result`s into one `Result`** stops at the first `Err`, so
  one bad entry refuses the whole file, with the same words in both CLIs.
- The planner looks the profile up **by name**, after every safety check.
