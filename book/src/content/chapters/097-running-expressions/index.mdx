## A tree is not an answer

After all the chapters on parsing, `print 1 + 2 * 3 - 4;` has become a
tidy tree, `(- (+ 1 (* 2 3)) 4)`; however, nobody who types that line
wants a tree, they want to see `3`. This chapter starts the back end of
the pipeline, which in our interpreter is one function that looks at a
node and works out what it is worth.

## Walking the tree

Precedence was settled when the tree was built (the `*` sits below the
`+`), and a node's value depends only on its children's values, so the
rule is "ask the children, then combine what they say".

<Analogy title="a company adding up its sales">
The boss is asked for the year's total and cannot answer alone, so she
asks her two managers; each manager asks their own team, and the people
at the bottom simply know their own number and say it. The answers flow
back up, each manager adding what they heard, until the boss has the
total, and nobody answers before everyone below them has.
<span slot="breaks">Managers can ask their teams at the same time; the
interpreter asks one child at a time, always the left one first, which
matters as soon as asking can print something or fail.</span>
</Analogy>

<Analogy title="brackets on a pocket calculator">
For `(2 × 3) + 1` you work out the inner bracket first, note the 6, and
use it in the outer sum.
<span slot="breaks">A person spots shortcuts (anything times zero is
zero, so why work out the rest?); the interpreter never does, and it
visits every node, even a lone `4`.</span>
</Analogy>

Step through the tree for `1 + 2 * 3 - 4` and watch the calls wait on
each other, then the values climb back up:

<EvalSteps client:visible />

Here is the heart of `evaluate` in `companion/ts/src/interpreter.ts`,
with the cases for later chapters left out:

```ts
evaluate(e: Expr): Value {
  switch (e.kind) {
    case 'literal':
      return e.value;
    case 'grouping':
      return this.evaluate(e.expression);
    case 'unary': {
      const right = this.evaluate(e.right);
      if (e.operator.type === '!')
        return !isTruthy(right);
      if (typeof right !== 'number')
        throw new RuntimeError(e.operator,
          'cannot negate ' +
          describe(right));
      return -right;
    }
    case 'binary': {
      const l = this.evaluate(e.left);
      const r = this.evaluate(e.right);
      return this.arithmetic(/* ... */);
    }
  }
}
```

There is one `case` per kind of node, and narrowing on `kind` tells
TypeScript which fields each case may touch. A **literal** already holds its value, put there by
the scanner, so it returns it. A **grouping** does nothing of its own:
the brackets did their work when they shaped the tree. A **unary** node
evaluates its one child and then applies `!` or `-`; a **binary** node
evaluates its left child, then its right child, and only then applies
the operator (`==` and `!=` are checked first; everything else goes to
`arithmetic`, which we read below).

<Callout kind="definition">
To **evaluate** an expression is to compute the value it stands for. A
**tree-walking interpreter** runs a program by visiting its syntax tree
directly: a recursive function evaluates a node's children, combines
their values, and returns the result.
</Callout>

<Formal title="Evaluating a sum">

```text
e₁ ⇓ v₁    e₂ ⇓ v₂    v₁, v₂ numbers
────────────────────────────────────
         e₁ + e₂ ⇓ v₁ + v₂
```

<span slot="read">The arrow ⇓ reads "evaluates to". Above the line are
the things that must be true first: e₁ evaluates to v₁, e₂ evaluates to
v₂, and both are numbers. Below the line is what follows: the sum
evaluates to the two values added: children first, as in the
code.</span>
</Formal>

<Examples of="evaluate tree-walking-interpreter">

```text
print 7;            # 7
```

```text
print (1 + 2) * 3;  # 9
print -(2 - 5);     # 3
```

```text
print 10 + 2 * 0.5; # 11
```

</Examples>

The first tree is one literal node, so `evaluate` returns `7`. In the second, the brackets make `+` the left child of `*`, so the
sum is finished first and the answer is `9`; the next line's unary minus
waits for its child, `2 - 5`, which is `-3`, and negates it. The third is a
particle at 10 moving at speed 2 for half a second: `2 * 0.5` is `1`, and
`10 + 1` is `11`.

## What a value looks like

While a Drip program runs, its values have to live somewhere, and since
the interpreter is written in TypeScript, the easiest home is a
TypeScript value. This is the `Value` type from `runtime.ts`:

```ts
type Value = null | boolean | number
  | string | DripList | DripFunction
  | NativeFunction | DripClass
  | DripInstance;
```

<Figure takeaway="Simple Drip values borrow the host's own values." caption="The left column is what you write in Drip; the right is what the interpreter holds. Lists, functions, classes and instances are objects of the interpreter's own classes, met in later chapters.">
  <ValueMap />
</Figure>

Borrowing the host's values means `+` on two Drip numbers *is* `+` on
two JavaScript numbers, so Drip numbers are 64-bit IEEE 754
doubles<Cite id="mdn-number" />. Only printing differs: `stringify` shows `null`
as `none`, `NaN` as `nan` and `Infinity` as `inf`.

<Callout kind="definition">
A **runtime value** is how a value of the language is held while the
program runs. Drip's tree-walker reuses JavaScript values for the simple
ones (`none` is `null`, and booleans, numbers and strings are
themselves), so a Drip value's type can be checked with `typeof`.
</Callout>

<Examples of="runtime-value">

```text
print none;    # none
```

```text
print 10 / 4;  # 2.5
print 1 / 0;   # inf
```

```text
print 0.1 + 0.2;  # 0.30000000000000004
print 3 == "3";   # false
```

</Examples>

`none` is held as `null` and printed by its Drip name. `10 / 4` is
`2.5`, because division never rounds down, and `1 / 0` is JavaScript's
`Infinity`, shown as `inf`. In the third, the sum is a double's nearest
answer, and `3 == "3"` is `false`: the companion's `isEqual` is `a === b`, so values of different
types are never equal.

## What counts as true

`!` needs to know whether a value is "true enough", and so will `if` and
`while` soon. Drip's rule fits on one line of `runtime.ts`:

```ts
const isTruthy = (v: Value): boolean =>
  v !== null && v !== false;
```

Only `none` and `false` are false, and every other value is true,
including `0`, the empty string and the empty list. That is a smaller
list than JavaScript's, where `0`, `-0`, `NaN`, `""`, `null` and
`undefined` all count as false too<Cite id="mdn-falsy" />.

<Callout kind="definition">
**Truthiness** is the rule that decides which values count as true
where a condition is expected. In Drip, `none` and `false` are
**falsey** and every other value is **truthy**.
</Callout>

<Examples of="truthiness">

```text
print !none;  # true
```

```text
print !0;     # false
print !"";    # false
```

```text
print !(3 > 4);  # true
```

</Examples>

`none` is falsey, so `!none` is `true`. `0` and `""` are truthy in Drip,
so negating them gives `false` (in JavaScript `!0` is `true`). The last
is the everyday case: a comparison makes a real boolean, and `!` flips
it. A common slip in the interpreter is writing `!right` instead of
`!isTruthy(right)`, which borrows JavaScript's rule.

## When the values make no sense together

Drip is dynamically typed, so nothing checks `"1" - 1` before the
program runs; instead, `arithmetic` checks just before it applies each
operator:

```ts
if (op === '+') {
  if (typeof l === 'number' &&
      typeof r === 'number') return l + r;
  if (typeof l === 'string' &&
      typeof r === 'string') return l + r;
  throw new RuntimeError(at, `cannot add `
    + `${describe(l)} and ${describe(r)}`);
}
```

The other operators need two numbers, checked the same way. In
JavaScript `'1' - 1` is `0`, because the string is quietly converted;
Drip refuses. `describe` names a type with its article (`a number`,
`none`), and `RuntimeError` extends `Error`<Cite id="mdn-error" /> with
the line of the operator's token. The runner catches it, prints it, and
exits with code 70:

<Run id="type-error" />

The first `print` showed `3`; the second stopped the program with
`runtime error: cannot use '-' on a string and a number` and
`at line 2 in script`, and the third never ran. The exit code is 70, not
a compile error's 65, because this was good Drip that went wrong only
while running.

<Callout kind="definition">
A **runtime error** is an error found while the program runs, such as an
operator given values of the wrong types. Drip prints
`runtime error:` and the message, then where it happened, stops the
program and exits with code 70. A syntax error, by contrast, is found
before anything runs.
</Callout>

<Examples of="runtime-error">

```text
print -"hi";
# cannot negate a string
```

```text
print 1 < "2";
# cannot compare a number and a string
# with '<'
```

```text
print 2 + " cups";      # error
print str(2) + " cups"; # 2 cups
```

</Examples>

Unary minus needs a number. The comparison names both types and the
operator, so you can see which side was wrong. The last pair is the
spot-the-difference you will meet most: the first line stops with
`cannot add a number and a string`; the second turns the number into a
string with the built-in `str`, so `+` joins two strings.

## What you learned

- To **evaluate** a tree, evaluate the children, then combine their
  values; values flow from the leaves up to the root.
- A **tree-walking interpreter** does that with one recursive function
  and one `case` per kind of node.
- Drip's **runtime values** borrow JavaScript's: `none` is `null`.
- **Truthiness**: only `none` and `false` are false; `0` and `""` are
  true.
- Operators check their operands as they run, and a mismatch is a
  **runtime error**: a message, a line, and exit code 70.
