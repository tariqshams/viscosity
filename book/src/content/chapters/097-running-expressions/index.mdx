## A tree is not an answer

After eight chapters of scanning and parsing, `1 + 2 * 3 - 4` has become
a beautiful tree: `(- (+ 1 (* 2 3)) 4)`. But nobody asked for a tree.
They asked for `3`. The parser is the front end of the pipeline. This
chapter starts the back end, and in a tree-walking interpreter the back
end is surprisingly small.

## Walking the tree

<Callout kind="intuition">
Picture a company asked for its total sales. The boss can't answer
alone, so she asks her two managers. Each manager asks their own team.
The people at the bottom just know their number and say it. Then the
answers flow back up, each manager adding up what they heard, until the
boss has the total. Nobody answers before everyone below them has.
</Callout>

That is the whole algorithm. A node's value depends only on its
children's values, so ask the children first, then combine:

<EvalSteps client:visible />

Here is the core of it, simplified from `evaluate` in
`companion/ts/src/interpreter.ts`:

```ts
function evaluate(e: Expr): Value {
  switch (e.kind) {
    case 'literal':
      return e.value;
    case 'grouping':
      return evaluate(e.expression);
    case 'unary': {
      const right = evaluate(e.right);
      if (e.operator.type === '!')
        return !isTruthy(right);
      return -num(e.operator, right);
    }
    case 'binary': {
      const l = evaluate(e.left);
      const r = evaluate(e.right);
      return binary(e.operator, l, r);
    }
  }
}
```

One `case` per kind of node, and TypeScript's narrowing on `kind` knows
which fields each case may touch. A grouping node does nothing of its
own: the parentheses already did their work when the tree was shaped.

<Callout kind="definition">
To **evaluate** an expression is to compute the value it stands for. A
**tree-walking interpreter** runs a program by walking its syntax tree
directly: a recursive function visits each node, evaluates its children,
and combines their values. No other form of the program is produced.
</Callout>

## What a value looks like

While a Drip program runs, its values have to live *somewhere*. The
interpreter is written in TypeScript, so the easiest home is a
TypeScript value:

```ts
// runtime.ts (functions, classes: later)
type Value = null | boolean | number
  | string | DripCallable | DripInstance;
```

```
Drip         in the interpreter
nil          null
true         true
12.5         the number 12.5
"hi"         the string 'hi'
```

Borrowing the host's values means `+` on two Drip numbers is just `+`
on two JavaScript numbers. `print` needs one small adjustment, made by
`stringify`: `null` must print as `nil`.

<Callout kind="definition">
A **runtime value** is the representation of a Drip value while the
program runs. Drip's tree-walker reuses JavaScript values: `nil` is
`null`, and booleans, numbers and strings are their JavaScript
counterparts. The Drip type of a value is therefore just its JavaScript
type, checked with `typeof`.
</Callout>

## What counts as true

`!` needs to know whether a value is “true enough”, and so will `if`
and `while` in chapter 100. Drip's rule fits on one line:

```ts
const isTruthy = (v: Value) =>
  v !== null && v !== false;
```

Only `nil` and `false` are false. Everything else, including `0` and
the empty string `""`, is true. That is *not* JavaScript's rule, where
`0` and `''` are also falsy. The example above shows it: `!0` printed
`false`, because `0` is truthy in Drip.

<Callout kind="definition">
**Truthiness** is the rule that decides which values count as true where
a condition is expected. In Drip, `nil` and `false` are **falsey** and
every other value is **truthy**.
</Callout>

## When the types are wrong

Drip is dynamically typed: nothing checks `"1" - 1` before the program
runs. So the interpreter checks while it runs, right before it applies
each operator:

```ts
case '+':
  if (typeof l === 'number' &&
      typeof r === 'number') return l + r;
  if (typeof l === 'string' &&
      typeof r === 'string') return l + r;
  throw new RuntimeError(op,
    'Operands must be two numbers or ' +
    'two strings.');
case '-':
  nums(op, l, r); // throws if not numbers
  return l - r;
```

Try `'1' - 1` in JavaScript and you get `0`: the string is quietly
converted. Drip refuses. `RuntimeError` carries the operator's token,
and the token knows its line, so the message can say where:

<Run id="type-error" />

The first `print` ran and printed `3`. The second stopped the program.
Drip prints the message, then `[line 2]`, and exits with code 70: not
65, because this program was perfectly valid Drip. It went wrong while
running.

<Callout kind="definition">
A **runtime error** is an error found while the program runs, such as
an operator applied to values of the wrong type. Drip reports the
message and the line of the operator's token, stops the program, and
exits with code 70. A syntax error, by contrast, is found before
anything runs.
</Callout>

<Callout kind="engine" label="Under the hood">
Because Drip numbers *are* JavaScript numbers, they are 64-bit IEEE 754
doubles, the format from chapters 34 and 57. So `print 0.1 + 0.2;`
prints `0.30000000000000004` in Drip, exactly as in JavaScript. The
price of walking the tree is just as concrete: every node costs a
function call and a `switch`, even a lone `4`. Chapter 106 measures that
overhead, and Part IV removes most of it with bytecode. Drip's design
follows Lox from *Crafting Interpreters*<Cite id="nystrom2021" />.
</Callout>

## What you learned

- To **evaluate** a tree, evaluate the children, then combine their
  values. Values flow from the leaves up to the root.
- A **tree-walking interpreter** does exactly that, with one recursive
  function and one `case` per kind of node.
- Drip's **runtime values** are JavaScript values: `nil` is `null`,
  and booleans, numbers and strings are themselves.
- **Truthiness** in Drip: only `nil` and `false` are false. `0` and
  `""` are true.
- Operators check their operand types as they run. A mismatch is a
  **runtime error**: a message, the line, and exit code 70.
