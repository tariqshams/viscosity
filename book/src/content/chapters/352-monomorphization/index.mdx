## What runs?

The last chapter's `top<T: PartialOrd>` was checked once and then called
with `i32`, `&str` and `f64` slices. In TypeScript you know what runs
afterwards (*Interfaces, erasure and typeof*): the types are erased, and
one JavaScript function serves numbers, strings and everything else. The
chapter *Generics: specialisation or erasure* showed that a compiler
has two honest choices here: one copy of the code that works on a
uniform representation of every value, or a separate copy for each type.
Rust takes the second, and this chapter shows you the copies.

<Analogy title="a print shop">
A print shop asked for wedding invitations does not print one card that
says "Dear guest" and let each guest pencil in a name; it prints a
separate card for every guest, with the name set in type, before the
day. The cards cost more to make and take more paper, but each one is
exactly right, and nobody has to fill anything in at the door.
<span slot="breaks">A print shop prints a card per *guest*; Rust makes
a copy per *type* that is actually used, however many calls there are,
so a thousand calls with `i32` share a single copy.</span>
</Analogy>

<Analogy title="tailored or one-size">
A one-size-fits-all coat with a drawstring fits everyone a little
loosely (that is erasure, where every value is boxed to the same shape);
a tailor cuts a coat for each customer, which takes longer and uses more
cloth, and fits each perfectly (that is a copy per type).
<span slot="breaks">A tailor measures by hand and may make mistakes;
the compiler's copies are made mechanically from one source, so they
cannot drift apart, and each was already checked against the bounds.</span>
</Analogy>

## The copies, found

Take the `Layout` trait from the chapter *Traits*, and two functions
that sum one field: one generic over the layout, one taking a trait
object.

```rust
fn total<L: Layout>(l: &L, buf: &[f64],
    n: usize, f: usize) -> f64 {
    let mut s = 0.0;
    for i in 0..n {
        s += buf[l.slot(i, f)];
    }
    s
}
```

`total_dyn` is the same body with `l: &dyn Layout`. Call each with an
`&Aos` and an `&Soa`, compile with rustc 1.97 and
`-C symbol-mangling-version=v0` (so symbol names show their type
parameters), and list the program's functions with `nm -C`:

```text
g3::total::<g3::Aos>
g3::total::<g3::Soa>
g3::total_dyn
<g3::Aos as g3::Layout>::slot
<g3::Soa as g3::Layout>::slot
```

Two `total`s, one per type; one `total_dyn`. (Run the program below to
see that all four calls agree; listing symbols needs a terminal, so try
`nm -C` on your own machine.) Step through what each copy does when it
calls `slot`:

<Callout kind="definition">
**Monomorphization** is how Rust compiles generic code: for each set of
concrete types a generic item is used with, it generates a separate,
ordinary copy with those types filled in<Cite id="rust-book-generics" />.
The copies call trait methods directly (static dispatch), so generic code
runs like code written by hand for each type, and the compiler may inline
those calls; the price is compile time and binary
size<Cite id="rustc-dev-guide-monomorph" />.
</Callout>

<Formal title="Stamping out copies">

```text
fn f<T: Tr>(…) { body }
used with T = U₁, …, Uₙ
  ⟹  f::<U₁>, …, f::<Uₙ>
f::<Uᵢ> = body[T := Uᵢ]
```

<span slot="read">If a generic function f with type parameter T is used
with the types U₁ up to Uₙ, the compiler produces n functions, one for
each; the copy for Uᵢ is the body with every T replaced by Uᵢ (the
notation [T := U] reads "with T replaced by U"). Calls of Tr's methods
in that copy then name Uᵢ's own methods.</span>
</Formal>

The first is the Rust book's own example: one generic `Option<T>`, used
with two types, becomes two concrete types, as if you had written an
`Option_i32` and an `Option_f64` by hand. The second is the pair found
above: one source function, two compiled ones, each calling a known
`slot`. The third is real and larger: the Rust port of Viscosity's
pipeline is `pub fn compile<P: LanguagePlugin>(source: &str, plugin: &P,
...)`, its command-line tool calls `compile(&src, &PyPlugin, opts)` for
`.py` files and `compile(&src, &JsPlugin, opts)` otherwise, and `nm -C`
on the built tool lists exactly those two copies.

## Monomorphic by construction

You have seen this trade from the engine's side. In *Inline caches* a
call site that has only ever seen one shape is *monomorphic*, and
Maglev turns such an access into one shape check and a plain load at a
fixed offset<Cite id="v8-maglev" />. V8 has to *discover* that a site is
monomorphic by watching it run, and must keep a check in case a new
shape arrives.

Inside `total::<Aos>`, the call `l.slot(i, f)` can only ever reach
`Aos::slot`. The site is monomorphic by construction, known before the
program runs, so there is nothing to check and nothing to deoptimize.
`total_dyn` is the other case: its one call site sees whatever vtable it
is handed, like a polymorphic site, and has no feedback to specialise
on, so it loads a function pointer and calls it<Cite id="rust-reference-trait-object" />.

```ts
// what tsc emits for top<T>
function top(xs) {
  let best = xs[0];
  for (const x of xs)
    if (x > best) best = x;
  return best;
}
```

</OtherLanguages>

TypeScript's output is one function with the types removed; every call
runs the same code, and the engine's inline caches learn the types as
it runs. Rust's output is a function per type (with names of rustc's
own choosing; the ones above are only for illustration), each knowing
exactly which `>` it calls. Java erases its generics too, and boxes
numbers to make them fit, as the chapter on specialisation and erasure
showed; C++ templates make copies, like Rust.

## Choosing

Generics give each type its own fast copy, at the cost of more machine
code and one more copy to compile for each type. `dyn` gives one copy
and lets one `Vec` hold many types, at the cost of an indirect call. A
plugin registry, a list of GC roots, or anything decided while the
program runs wants `dyn`; a hot loop over one known type wants generics.

The Rust port of Viscosity chose generics for `compile`, and for a
second reason as well: `dyn LanguagePlugin` is not even available as
written. The trait has an associated type, `Extra` (each plugin's
private data), and a trait object must name it, so
`Vec<&dyn LanguagePlugin>` fails with E0191, "the value of the
associated type `Extra` in `LanguagePlugin` must be
specified"<Cite id="rustc-e0191" />. The command-line tool picks the
plugin with an ordinary `if` on the file's extension instead, and each
branch calls its own copy. drip-rs uses both styles in one file:
`gc.rs` has `impl<T: Trace> Trace for Vec<T>` (every `Vec` of traceable
things is traceable, one copy per element type) and
`fn alloc<T: HeapObject>`, while `collect` takes `&[&dyn Trace]`.

## What you learned

- **Monomorphization** makes one copy of a generic item per concrete
  type it is used with: `nm` showed `total::<Aos>` and `total::<Soa>`,
  and `compile::<JsPlugin>` and `compile::<PyPlugin>` in Viscosity.
- Each copy's trait calls are direct and monomorphic by construction;
  a `dyn` call site takes whatever vtable it is given.
- Generics cost compile time and code size; `dyn` costs an indirect
  call. Use `dyn` for mixed collections and run-time choices, generics
  for hot code over known types.
