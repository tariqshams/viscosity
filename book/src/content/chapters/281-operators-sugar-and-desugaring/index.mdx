## A + for your own types

A game keeps positions and velocities as two-number vectors, and the
code is full of lines like this:

```js
const p2 = add(add(p, v), wind);
// what we would like to write:
// const p2 = p + v + wind;
```

Many languages allow the second form: a type you define can say what
`+`, `==` or `[]` mean for its values. Chapter 67 met **desugaring**,
rewriting one construct into another the compiler already handles
(Drip's `for` into a `while`); operators on your own types are the same
trick. The compiler rewrites `p + v` into a call of a function you
wrote, and from then on it is an ordinary call, which can be inlined,
specialised or dispatched like any other. What differs between
languages is *when* the function is chosen and *how* it is named.

<Analogy title="one job sheet, different trades">
A building site's job sheet says "join part A to part B". If the parts
are wood, the carpenter glues them; if they are steel, the welder
welds them. The sheet uses one word, and the material decides which
trade does the work.
<span slot="breaks">On a site someone decides on the day; C++ and Rust
decide while compiling, from the declared types, so at run time the
call is already fixed, and Python adds a twist no site has: if the
first trade declines, the second part's trade is asked.</span>
</Analogy>

<Analogy extra title="a universal remote's play button">
The same "play" button starts a DVD or a music stream: the remote
sends whichever command the chosen device understands.
<span slot="breaks">A remote looks only at the device you selected;
an operator looks at its operands' types, and in Python at both of
them, left first and then right.</span>
</Analogy>

<Callout kind="definition">
**Operator overloading** lets a program define what an operator means
for its own types. The compiler desugars each use into a call: in C++
of a function named `operator+`, chosen by overload resolution on the
operand types<Cite id="cxx-over-oper" />; in Rust of the method `add`
of the trait `std::ops::Add`<Cite id="rust-std-ops-add" />; in Python
of the special method `__add__` (or `__radd__`), found at run time
from the operands' types<Cite id="python-datamodel" />. Java, C and
JavaScript do not let programs overload operators.
</Callout>

<Formal title="The desugaring">

```text
C++, Rust (types known when compiling):
  ⟦a + b⟧ = add_T,U(⟦a⟧, ⟦b⟧)
      where a : T, b : U
Python (types known when running):
  ⟦a + b⟧ = r := type(a).__add__(a, b)
            if r is NotImplemented:
              r := type(b).__radd__(b, a)
            if r is NotImplemented:
              raise TypeError
```

<span slot="read">In C++ and Rust, a plus b becomes a call of the add
function chosen for the types T and U of the two operands, so the
choice is made once, while compiling. In Python it becomes a run-time
procedure: ask the left operand's type to add; if it answers "not
implemented", ask the right operand's type for the reflected add with
the operands swapped; if that also declines, raise a type
error.</span>
</Formal>

<Examples of="operator-overloading">

```text
// C++: V operator+(V a, V b); and ==
$ nm v.o | c++filt
T operator+(V, V)     (_Zpl1VS_)
T operator==(V, V)    (_Zeq1VS_)
// clang++ -O0, inside f(p, q) = p + q:
callq _Zpl1VS_
```

```text
// Rust: impl Add for V; f(p, q) = (p + q).x
// rustc --emit=mir, trimmed:
_3 = <V as Add>::add(copy _1, copy _2)
_0 = copy (_3.0: i32);
```

```python
class V:
    def __init__(s, x): s.x = x
    def __add__(s, o):
        if not isinstance(o, V):
            return NotImplemented
        return V(s.x + o.x)
# dis of a + b:  BINARY_OP 0 (+)
V(1) + 'a'   # TypeError: unsupported
# operand type(s) for +: 'V' and 'str'
```

</Examples>

The first is C++: `operator+` is an ordinary function with a mangled
name, `pl` being the Itanium ABI's code for `+` and `S_` a
back-reference to the first name already written, `1V`, so it is not
spelled out twice<Cite id="itanium-cxx-abi" />, and at
`-O0` the expression `p + q` is a plain call of it (at `-O1` clang
inlines it, and the call disappears into two additions). The second is
Rust's middle-level IR, MIR: the `+` has already become a call of the
`Add` trait's method for `V`, a static call chosen by type, which LLVM
can inline in the same way. The third is Python 3.13: the bytecode for
`a + b` is the one instruction `BINARY_OP`<Cite id="cpython-dis" />,
whatever the types, and the work happens at run time; `V.__add__`
returns the special value `NotImplemented` for a string, `str` cannot
add a `V` either, and the error is quoted exactly. Step through how
Python decides:

<DispatchSteps client:visible />

Python's data model spells out the order: `x + y` calls
`type(x).__add__(x, y)`, and the reflected `type(y).__radd__(y, x)` is
tried "only if the left operand does not support the corresponding
operation and the operands are of different
types"<Cite id="python-datamodel" />. (One refinement: if the right
operand's type is a *subclass* of the left's and overrides the
reflected method, it is asked first, so a subclass can change how its
parent's operators treat it.)

Java has no user-defined operators, yet even it desugars `+`: for
strings, `javap -c` on javac 21's output shows `s + n` compiled as an
`invokedynamic` call named `makeConcatWithConstants`, a call into the
Java library rather than any addition. A table of operator functions,
looked up by types while compiling, is all the C++-style choice needs:

<Run id="lower-ops" />

`lower` builds a key from the operator and the two operand types and
looks it up, first among the built-in operations and then among the
operator functions the program defined; it prints `add`, `call
_Zpl1VS_` and `call _Zeq1VS_`, and for `V + int`, which nobody
defined, it reports `no operator + V int`, the point at which a C++ compiler
reports that no `operator+` matches.

## Sugar that must not repeat itself

Compound assignment is sugar too: Drip's `x += e` means `x = x + e`
(and Python's `x += y` first tries a method `__iadd__`, falling back to
`__add__` and `__radd__`<Cite id="python-datamodel" />). Written out
naively, though, the target would be worked out twice. Run this, where
`pick()` counts how often it is called:

<Run id="plus-once" />

`xs[pick()] += 5` adds 5 to `xs[0]` and calls `pick` once, so it
prints `[15, 20]` and `1`; the hand-written `xs[pick()] = xs[pick()] +
5` calls `pick` twice more, and the count reaches 3. Drip's
specification says `x += e` evaluates its target once, and your VM's
compiler keeps that promise without any temporary variable, by
duplicating the list and the index already on the stack:

```ts
// companion/ts/src/vm/compiler.ts
// xs[i] += e, after xs and i are pushed:
if (op.type !== '=')
  emitAt(bracket.line,
    Op.Dup2, Op.IndexGet);
expression();
if (op.type !== '=')
  emitAt(op.line, compoundOp(op));
emitAt(bracket.line, Op.IndexSet);
```

`Dup2` copies the top two stack values (the list and the index), so
`IndexGet` can read the old element while a second copy waits for
`IndexSet`; the value of `e` is pushed and added (`compoundOp` picks
`Add` for `+=`), and `IndexSet` stores the sum. A desugaring is only
right if it keeps such details; the next chapter's `?.` needs the same
care, with temporaries.

## What you learned

- **Operator overloading** is desugaring: `a + b` on a user type
  becomes a call of a function the program wrote.
- C++ (`operator+`, mangled `_Zpl…`) and Rust (`Add::add`) choose that
  function from the types while compiling, so it can be inlined like
  any call.
- Python compiles every `+` to one `BINARY_OP` and chooses at run
  time: `__add__` on the left, then `__radd__` on the right, then
  `TypeError`.
