## Every decision, with a reason

A compiler that quietly rearranges your data is hard to trust unless it
tells you what it did and why. *viscosity explain* made that a promise
in the TypeScript engine: one header line per collection, then one line
per reason, every decision accounted for. The Rust engine has to keep
the promise in exactly the same words, because the parity test compares
the two reports byte for byte. Here is a small program:

```js
const ps = [];
for (let i = 0; i < 99; i++)
	ps.push({ x: i });
const keep = [];
for (let i = 0; i < 99; i++) {
	if (ps[i].x > 3)
		keep.push(ps[i]);
}
const t = "🎉"; f(t, ps[2]);
function f() {}
```

(it is indented with tabs, which the next chapter cares about) and the
Rust CLI's report on it (I ran `viscosity explain` here, release build,
rustc 1.97; long lines wrapped):

```
ps (line 1) {x} → kept as array of objects
  · unsafe: line 7: an element is used by
    push
  · unsafe: line 9: an element is passed
    to a function call
keep (line 4) {} → kept as array of objects
  · unsafe: line 7: pushes something that
    is not a fresh object literal
```

The TypeScript CLI printed the same bytes. This chapter reads the Rust
that writes those lines, and how each refusal remembers where in the
source it was found, which the next chapter, *Code frames in Rust*,
uses to point at the code.

<Analogy title="a referee's match report">
After a match the referee writes one line per team and, under it, a
line for each decision: the minute, the player, the reason. Nothing is
left out, and the wording follows a fixed form, so that anyone reading
two reports can compare them line by line.
<span slot="breaks">A referee writes from memory and may phrase things
freely; the report here is generated from the plan, in a fixed order,
and two engines must produce the same characters, down to the middle
dot.</span>
</Analogy>

<Analogy extra title="a marked exam paper">
A marked paper has the total at the top and a short note beside each
lost mark, written next to the line where the mistake is.
<span slot="breaks">A marker writes the note on the page itself; the
report keeps the message and the place apart (the place is only shown
with `--frames`), and a mark lost twice for the same reason is noted
once.</span>
</Analogy>

## One function, two outputs

`crates/core/src/plan.rs` has two public functions, `explain(p)` and
`explain_with_frames(p, source)`. Both call one private function, and
the only difference is an `Option<&str>`: `None` for the plain report,
`Some(source)` when frames were asked for. Here it is, rewrapped, with
the frame part left as a comment for the next chapter:

```rust
fn explain_text(p: &Plan,
    frames: Option<&str>) -> String
```

and its body:

```rust
let mut lines = Vec::new();
for cp in &p.collections {
    let c = &cp.collection;
    let verdict = match cp.layout {
        Layout::Aos => "kept as array \
            of objects".to_string(),
        Layout::Soa =>
            "struct of arrays".to_string(),
        Layout::Aosoa => format!(
            "AoSoA, blocks of {}",
            js_number(
                cp.block_size as f64)),
    };
    lines.push(format!(
        "{} (line {}) {{{}}} → {verdict}",
        c.name, c.line,
        c.fields.join(", ")));
    // one reason per bailout?
    let refused = !c.bailouts.is_empty()
        && cp.reasons.len()
            == c.bailouts.len();
    for (k, r) in cp.reasons.iter()
        .enumerate() {
        lines.push(format!("  · {r}"));
        // --frames: a code frame here
    }
}
lines.join("\n")
```

The verdict is a `match` on the layout, with `js_number` printing the
block size as JavaScript would (`8`, not `8.0`). In a format string
`{{` and `}}` stand for a literal brace, so `"{{{}}}"` is a brace, the
field list, and a brace: `{x}`, or `{}` when no field could be seen.
`refused` asks whether the collection was kept with exactly one reason
per bailout, which is what the safety rung of *The cost model in Rust*
produces; only then is reason `k` known to be about bailout `k`.
`enumerate` hands out each reason with its number `k`, and the lines
are joined with line breaks, with none at the end (the CLI adds one
when it prints). Step through it on the program above:

## Where a refusal happened

The places come from the analysis. Every bailout in `analysis.rs` goes
through one small method:

```rust
fn bail(&mut self, msg: String,
    at: Option<SourceRef>) {
    self.bailout_sites
        .entry(msg.clone())
        .or_insert(at);
    self.bailouts.push(msg);
}
```

`bailout_sites` is an `IndexMap<String, Option<SourceRef>>`, keyed by
message. `entry(...).or_insert(at)` writes `at` only when the key is
new, so the *first* place a message was found wins, and later ones
with the same words are ignored. `at` is an `Option` because some
bailouts have no single place ("no records are ever added" has `None`).
At the end of the analysis the messages are deduplicated, keeping the
first of each, by collecting them through an `IndexSet`:

```rust
let unique: IndexSet<String> =
    c.bailouts.drain(..).collect();
c.bailouts = unique.into_iter().collect();
```

`drain(..)` moves every message out of the vector, the `IndexSet`
keeps each once in first-seen order, and the vector is filled again.
So the planner sees each message once, writes it as `unsafe: ...`,
and reason `k` can look up `c.bailout_sites[&c.bailouts[k]]`.

The site is the span of the instruction the bailout is about: the
element `ps[i]` for an escape, the record literal for a shape mismatch,
`ps = []` for a reassignment. Sometimes that instruction isn't on the
line the message names. In the corpus program `string_index.js`, the
message is about the access `ps[k]` on line 6, but the site is on line
4, because the bailout's instruction is the index *value*: in SSA
(*SSA form*), `k` is the constant `'5'`, and its `SourceRef` is where
that constant was written (arguably the more useful place to point).

<Formal title="The shape of a report">

```text
report ::= block ( "\n" block )*
block  ::= header ( "\n" reason )*
header ::= name " (line " n ") {"
           fields "} → " verdict
reason ::= "  · " text
```

<span slot="read">A report is one block, then any number of further
blocks, each after a line break. A block is a header followed by any
number of reasons, each on its own line. A header is the collection's
name, its line in brackets, its fields in braces, an arrow and the
verdict; a reason is two spaces, a middle dot, a space and the reason's
text.</span>
</Formal>

All three are lines of the Rust CLI's reports from earlier chapters,
wrapped and shortened with `…`. The first is a transformed collection,
whose reasons come from `describe`: its loops, its columns, its size
and its bounds proofs. The second is an annotated one, whose verdict
prints the block size with `js_number`. The third is `string_index.js`,
refused, with one reason for its one bailout; with `--frames` it is the
one that points at line 4.

<Callout kind="definition">
**explain in Rust** is `plan::explain`, a call to `explain_text(p,
None)`: for each collection in plan order, a **header** (`name (line n)
{fields} → verdict`) and one **`  · `** line per reason. Each bailout's
first **site** is recorded by **`Collection::bail`** in
`bailout_sites`, keyed by message (`entry().or_insert`), and a kept
collection whose reasons are **exactly its bailouts** can match reason
`k` to that site, which `explain_with_frames` uses.
</Callout>

## What you learned

- **`explain_text(p, frames)`** serves both `explain` and
  `explain_with_frames`; the `Option` decides whether frames are added.
- A report is a **header** per collection and a **reason line** per
  reason, in plan order, joined with line breaks and with `{{`/`}}` for
  the literal braces.
- `Collection::bail` records each message's **first site**
  (`entry().or_insert`), and the messages are **deduplicated** through
  an `IndexSet`, so reason `k` of a refused collection finds bailout
  `k`'s place.
