## Four programs, four refusals

The analyses have done their work: for every collection the Rust engine
now knows whether the rewrite is safe, which fields are numbers, which
loops touch which fields, and roughly how big it will be (*Access
patterns in Rust*). Someone still has to decide, and say why. Here are
the first reason lines the Rust CLI printed (I ran `viscosity explain`
here, release build, rustc 1.97) for four small programs, each kept as
an array of objects for a different reason:

```
unsafe: line 6: an element is used by push
opt-in mode: not annotated
no field is provably numeric, so there are
  no typed columns to gain
no loop reads or writes its fields, so a
  new layout cannot pay off
```

The first program pushes an element of `ps` into another array, the
second was compiled with `--mode opt-in`, the third stores only strings,
and the fourth reads one field once, outside any loop. All four
sentences come from one function, `plan_one` in
`crates/core/src/plan.rs`, which ports the planner of *The cost model*.
It is short enough to read top to bottom, and the order of its tests
turns out to matter as much as the tests themselves.

<Analogy title="a pilot's pre-flight checklist">
Before take-off a pilot works down a printed checklist in a fixed
order: fuel, controls, instruments, weather. The first item that fails
stops the flight, and the reason is written in the log; a plane that
passes every item flies, and the log records what was checked.
<span slot="breaks">A pilot who finds a problem gets it fixed and starts
the list again; the planner never fixes anything, it only writes down
the first reason and moves on to the next collection.</span>
</Analogy>

<Analogy title="passport control">
An officer checks your passport, then your visa, then asks why you are
travelling, always in that order, and stops at the first problem. A
diplomatic pass lets you skip the questions about your trip, but never
the check that the passport is genuine.
<span slot="breaks">An officer can use judgement and wave someone
through; every rung of the planner is a plain test on the analysis's
facts, and two runs on the same program always give the same answer, in
the same words.</span>
</Analogy>

skips the cost questions, but never the safety one. Step down the

## From continue to return

The TypeScript `plan()` is one loop over the collections, and each
refusal in it is `out.push(keep(...)); continue;`. The port keeps the
loop but moves its body into a function of its own:

```rust
pub fn plan(a: &Analysis, opts: PlanOptions)
    -> Plan {
    let mut out = Vec::new();
    for c in &a.collections {
        out.push(plan_one(a, c, &opts));
    }
    Plan { collections: out, options: opts }
}
```

`plan` takes the options by value (so the finished `Plan` can own them)
and lends `plan_one` a shared reference to them, `&opts`, once per
collection. Inside `plan_one`, every refusal becomes an early `return`,
which is the Rust way to say "this collection is decided; stop here":

  <ContinueReturn />
</Figure>

Every rung builds its answer with one closure, defined at the top of
`plan_one` (rewrapped):

```rust
let keep = |reasons: Vec<String>|
    CollectionPlan {
        collection: c.clone(),
        layout: Layout::Aos,
        block_size: 0,
        reasons,
    };
```

A **closure** is a small unnamed function that can use the variables
around it (*Iterators and closures in Rust*); this one borrows `c` and
builds the plan for "leave it alone": layout `Aos`, no block size, and
whatever reasons it is handed (`reasons,` is shorthand for `reasons:
reasons`). The reference's `keep` takes its reasons as `...reasons`, a
list of any length; Rust closures can't do that, so the port passes one
`Vec<String>`. There is a second difference: the TypeScript plan holds
`collection: c`, a reference to the analysis's own object, while the
Rust plan holds `c.clone()`, a copy. A `CollectionPlan` that borrowed
from the `Analysis` would need a lifetime tying the two together; a
copy lets the plan live on its own, at the price of copying each
collection's facts once.

## Safety first, one reason each

The first rung is the only one that can produce more than one reason:

```rust
if !c.bailouts.is_empty() {
    return keep(c.bailouts.iter()
        .map(|b| format!("unsafe: {b}"))
        .collect());
}
```

`iter()` walks the bailout messages, `map` turns each into an `unsafe:
` reason, and `collect` gathers them into the `Vec<String>` that `keep`
wants (Rust works out the type from `keep`'s parameter). So a collection
with three bailouts gets exactly three reasons, in order. That
one-to-one match is relied on later: `viscosity explain --frames` (in
*Code frames in Rust*) pairs reason *k* with bailout *k*'s place in the
source. And it comes first because no other answer is worth giving
about a rewrite that could change what the program prints: an
annotation, a size or a loop doesn't matter if the layout change could
be seen.

The annotation rungs come next. An `aosoa(N)` annotation has its block
size checked (only powers of two from 2 to 65536 are
accepted<Cite id="rust-std-is-power-of-two" />, for reasons *AoSoA and
hot/cold in Rust* and *Block sizes and typed columns in Rust*
explain), and then any annotation returns at
once: `aos` keeps the collection, and `soa` or `aosoa(N)` transforms it
with the reason `annotated @viscosity soa at line 1` followed by the
usual description. That return happens before the cost rungs, so an
annotated collection is transformed even when it looks too small to
pay off, which is the point of annotating it. After that come opt-in
mode (`opt-in mode: not annotated`) and Python without
`--python-auto`, and then the first two questions of cost (strings
elided with `…`):

```rust
if c.numeric_fields.is_empty() {
    return keep(vec![
        "no field is … to gain".into()]);
}
if !c.loops.iter().any(|l| l.depth > 0) {
    return keep(vec![
        "no loop reads … pay off".into()]);
}
```

With no field proven numeric, every column would be a plain array, and
there are no `Float64Array` columns to gain. With no loop table of depth
1 or more (the depth-0 table holds accesses outside every loop), no loop
would get faster. `.into()` turns the `&str` literal into the `String`
the `Vec` holds. The last rung, the size threshold, is the subject of
the next chapter, *Sizes and thresholds in Rust*; a collection that
passes it too becomes `Layout::Soa`.

<Formal title="The ladder as a first match">

```text
plan(c) = Aos(unsafe: b₁, …, unsafe: bₙ)
                         if n > 0
        = follow(ann)    if annotated
        = Aos(rᵢ)        if rung i refuses
        = Soa(describe(c))   otherwise
```

<span slot="read">The plan of a collection c is decided by the first
line whose condition holds, read from the top: if c has n bailouts b1 to
bn, keep it with one unsafe reason per bailout; otherwise, if it is
annotated, follow the annotation; otherwise, if some later rung i
refuses, keep it with that rung's reason; and only if nothing refuses,
store it as a struct of arrays, with the description of what it
gains.</span>
</Formal>

<Examples of="rust-cost-model">

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ name: 'p' + i });
for (let i = 0; i < ps.length; i++)
  ps[i].name += '!';
// no field is provably numeric, …
```

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
console.log(ps[3].x);
// no loop reads or writes its fields, …
```

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
const keep = [];
for (let i = 0; i < ps.length; i++)
  if (ps[i].x > 3) keep.push(ps[i]);
console.log(ps, keep.length);
// unsafe: the array is passed to a
//   method call at line 7
// unsafe: line 6: an element is used
//   by push
```

</Examples>

The comments are the Rust CLI's reasons, the same bytes the TypeScript
CLI prints. The first program is safe and has a hot loop, but its only
field holds strings, so it stops at the numeric rung. The second has a
numeric field, but its one read is outside every loop, so it stops one
rung later. The third has two problems, and gets two reasons in the order the analysis found
them: `console.log(ps, ...)` hands the whole array to a function the
compiler can't see into, and `keep.push(ps[i])` lets an element escape
into another array.

<Callout kind="definition">
The **cost model in Rust** is `plan_one` in `plan.rs`, called by `plan`
once per collection: a **ladder of early returns**, each built by the
**`keep` closure**. Safety comes first, with **one `unsafe:` reason per
bailout**; then annotations, which skip the cost rungs; then opt-in mode
and Python; then the cost rungs (**some field numeric**, **some loop of
depth ≥ 1**, and the size threshold). A collection that passes every
rung becomes `Layout::Soa`, with reasons from `describe`.
</Callout>

## What you learned

- `plan` calls **`plan_one`** once per collection; each refusal is an
  **early `return`** where the reference writes `push` and `continue`.
- The **`keep` closure** builds a kept plan from a `Vec<String>` of
  reasons; plans hold a **clone** of their collection, so they don't
  borrow from the analysis.
- **Safety is the first rung**, with **one reason per bailout**, which
  `--frames` relies on. **Annotations** come next and skip the cost
  rungs, but never safety.
- The cost rungs refuse a collection with **no numeric field** or **no
  loop of depth ≥ 1**, and then, in the next chapter, one that is too
  small.
