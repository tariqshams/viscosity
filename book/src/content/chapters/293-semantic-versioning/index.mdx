## Three numbers on a label

The previous chapter shipped Viscosity: two npm packages and six Rust
crates, all labelled `0.0.1`. Suppose next month a bug is fixed, then
a new option is added, then an old option is removed. What should each
release be called, and what does a project that already depends on
`0.0.1` get when it next runs `npm install`?

npm works in **semantic versioning**: it requires versions that its
semver library can parse<Cite id="npm-package-json" />, and the rules
fit in a sentence: given MAJOR.MINOR.PATCH, bump MAJOR for incompatible
API changes, MINOR for backward compatible new features and PATCH for
backward compatible bug fixes, and reset the numbers to the right of
the one you bumped<Cite id="semver2" />.

<Analogy title="editions of a book">
A reprint that fixes typos is like a patch; a new edition that adds a
chapter but keeps every page number is like a minor release; a revised
edition that renumbers the chapters breaks everyone's references, which
is a major release.
<span slot="breaks">Publishers decide what counts as a new edition by
habit. Semver only means something against a *declared* public API:
until you say what your API is, nobody can tell a fix from a breaking
change, as the last section shows.</span>
</Analogy>

<Analogy title="a restaurant's menu">
Fixing a spelling mistake on the menu changes nothing for diners; adding
a dish gives them more choice and takes nothing away; taking a dish off
disappoints everyone who came for it.
<span slot="breaks">Diners can read the whole menu. Users of a library
often depend on things nobody listed (the exact wording of a message,
how fast a call is), and a change to those can break them although the
"menu" of documented functions never changed.</span>
</Analogy>

<Callout kind="definition">
**Semantic versioning** (semver) numbers releases MAJOR.MINOR.PATCH.
MAJOR changes when the **public API** breaks, MINOR when it gains
backward compatible features, PATCH for backward compatible fixes, and
the parts to the right of the bumped one reset to 0. Released versions
are immutable, 0.y.z promises nothing, and pre-release tags
(`1.0.0-beta.1`) sort before the release.
</Callout>

## Comparing versions

Three details catch people out. First, the parts are compared as
**numbers**, so `1.10.0` is newer than `1.9.0`, even though as strings
it sorts first. Second, a released version must never change: once a
name and version have been published on npm, that pair can never be
used again, even after unpublishing<Cite id="npm-publish-docs" />.
Third, major version zero is for initial development, and "anything MAY
change at any time"<Cite id="semver2" />.

<Formal title="Ordering versions, and a caret range">

```text
(a,b,c) < (x,y,z)  iff  a < x
   or (a = x and b < y)
   or (a = x and b = y and c < z)
^1.2.3 = [1.2.3, 2.0.0)
^0.1.0 = [0.1.0, 0.2.0)
^0.0.1 = [0.0.1, 0.0.2)
```

<span slot="read">Version a.b.c comes before x.y.z if its major part
is smaller; or the majors are equal and its minor is smaller; or both
are equal and its patch is smaller: the first part that differs
decides, as numbers. A caret range accepts everything from the given
version up to, but not including, the next version that changes the
leftmost non-zero part: below 2.0.0 for ^1.2.3, below 0.2.0 for ^0.1.0,
and below 0.0.2 for ^0.0.1, which is only 0.0.1 itself.</span>
</Formal>

A dependency in `package.json` names a *range* rather than one version,
and npm installs the newest release in it. The caret, `^`, is the
usual range, and it follows the zero rule: in 0.x the minor number is
treated as the breaking one, and in 0.0.x even the patch
is<Cite id="node-semver-ranges" />. Step through it:

The first walks the story from the top of the chapter through three
releases: a fix bumps the patch; a new option bumps the minor and
resets the patch (and 9 + 1 is 10, not "91"); removing an option breaks
anyone who used it, so the major goes up and everything to its right
resets. The second runs the numbers-not-strings trap: line 4 prints
`false`, because `'1.10.0' > '1.9.0'` compares character by character
and `'1'` sorts before `'9'`; `parse` splits each version at the dots
and turns the pieces into numbers, and the last line compares the minor
parts, 10 and 9, and prints `true`. The third is Viscosity's own
choice: a project depending on `^0.0.1` gets 0.0.1 and nothing newer.
Cargo reads `0.0.1` the same way, which the release notes in
`engine/rust/README.md` give as the reason for starting there: no
project that depends on it picks up a newer release without asking for
it.

## What is Viscosity's public API?

Semver starts with a demand: declare your public API, because the
numbers only mean something relative to it<Cite id="semver2" />. For a
library that is its exported functions; for Viscosity it is more:

- **The CLI**: its commands and options (the docs site's CLI reference
  is generated from `--help`, so the documentation cannot drift from
  it).
- **The plugin API** from *The plugin API*, if other people write
  plugins.
- **The explain text**, since *viscosity explain* argued that if people
  read the reports they are part of the interface, and scripts will
  search them.
- **The decisions.** A release that suddenly keeps a collection it used
  to transform makes someone's program slower without changing its
  output.

Is that last one a breaking change? The output is identical (the
differential tests check exactly that), so by semver's letter it is a
fix or a feature, but a user who measured a speed-up may disagree.
Deciding, and writing the decision down, is part of shipping. (One
small thing was fixed on the way: `viscosity --version` used to print a
hard-coded number, a second copy of the one in `package.json` that
would one day disagree with it; now it reads `package.json`, so there
is only one place the version lives.)

## What you learned

- **Semantic versioning**: MAJOR.MINOR.PATCH; bump one part for a
  breaking change, a feature or a fix, and reset the parts to its
  right.
- Versions compare **as numbers**, part by part; released versions are
  **immutable**; pre-releases sort before their release.
- **Caret ranges** accept everything up to the next change in the
  leftmost non-zero part, so `^0.1.0` means 0.1.x and `^0.0.1` means
  only 0.0.1, which is why Viscosity starts there.
- Versions are only meaningful against a declared **public API**, which
  for Viscosity includes its options, reports and decisions.
