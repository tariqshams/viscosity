## A guard fails mid-call

The previous chapter ended with three bailout lines, one per kind of
guess. Each of them happened in the *middle* of a call: some of the
function had already run, as fast machine code with values in machine
registers, and then a check said "this is not what I was compiled for".
The call cannot simply start again (it might already have changed
something), and it cannot stop with an error (the program did nothing
wrong). It has to *continue*, correctly, in code that handles every case.

<Analogy title="handing back from autopilot">
When an aircraft's autopilot meets something it was not set up for, it
disengages, and the pilot takes over at the exact position, height and
speed the plane is at, instead of returning to the runway to start the
flight again.
<span slot="breaks">A pilot can look out of the window to see where the
plane is; the interpreter cannot look at optimized code's registers and
make sense of them, so the optimized code must carry a written map of
where everything is at each point it might hand over.</span>
</Analogy>

<Analogy title="a supply teacher's notes">
A teacher who has to leave mid-lesson leaves notes: "we are on page 42,
question 3; the class has done questions 1 and 2". The supply teacher
picks up from exactly there, and the pupils never notice a gap.
<span slot="breaks">Notes can be incomplete, and the supply teacher can
improvise; V8's notes (the frame state) must say where every live value
is, and the interpreter resumes exactly at the recorded instruction,
with nothing left to guess.</span>
</Analogy>

Here is the real thing: warm `add` up with 100,000 integer calls, then
call `add('a', 'b')` (Node v22.23.4, `add` lines only, shortened with
`…`):

```
$ node --trace-opt --trace-deopt d2.js
[marking … add … to TURBOFAN, …
  reason: hot and stable]
[completed optimizing … add …
  (target TURBOFAN)]
[bailout (kind: deopt-eager,
  reason: not a Smi): begin.
  deoptimizing … add …,
  bytecode offset 2, …]
ab
```

The last line, `ab`, is the program's own output: the call that failed
the guard still returned the right answer. `--trace-deopt-verbose` shows
where it happened and what the deoptimizer built:

```
;;; deoptimize at <…/d2.js:2:12>
translating interpreted frame add
  => bytecode_offset=2, …
  <- "b" ; stack parameter
  <- "a" ; stack parameter
  <- "b" ; accumulator
```

Line 2, column 12 of the file is the `+`. To get back into Ignition, V8
needs to know, at that exact point, where every interpreter register's
value lives in the optimized code: in a machine register, on the stack,
or not computed at all. So optimized code carries that map with it:
Maglev attaches the interpreter's **frame state** to every node that can
deoptimize, and the deoptimizer uses it to fill in a fresh interpreter
frame, a mechanism TurboFan shares<Cite id="v8-maglev" />.

<Callout kind="definition">
**Deoptimization** leaves optimized code when an assumption fails, and
continues the same call in unoptimized code. The deoptimizer reads the
saved **frame state** for that point, rebuilds the interpreter frame from
the optimized code's registers and stack, and resumes at the same
bytecode. The result is the same as if the code had never been
optimized; only speed changes.
</Callout>

<Formal title="Deoptimization keeps meaning">

```text
fs(p) : optimized state → Ignition frame
deopt at p : frame ← fs(p)(state)
             resume Ignition at offset(p)
result(optimized run) = result(Ignition)
```

<span slot="read">For every point p in the optimized code that can
deoptimize, there is a frame state fs(p): a recipe that turns the
optimized code's registers and stack at p into an Ignition frame. When a
deopt happens at p, the deoptimizer builds that frame and Ignition
resumes at the bytecode offset recorded for p. The last line is the
promise all of this keeps: whatever happens, the program's result equals
what Ignition alone would have produced.</span>
</Formal>

```
[bailout (kind: deopt-eager,

```

```
// d5.js: 1e5 integer calls, a string
// call, 1e5 more, another string call
[marking … add … reason: hot and stable]
[completed optimizing … add …]
[bailout (… reason: not a Smi) … add]
[marking … add … reason: hot and stable]
[completed optimizing … add …]
// and no second bailout
```

</Examples>

The first is the simplest view: which function, why, and at which
bytecode. The second is the frame the deoptimizer built, and it lines up
with `add`'s bytecode from the chapter on Ignition: `Ldar a1` (offset 0)
had already loaded `b` into the accumulator, so Ignition resumes at offset
2, `Add a0, [0]`, which adds `"a"` to it and returns `"ab"`. The third is
the realistic one, the whole life of a function in a longer run: optimized,
deoptimized by the first string call, hot again, optimized again, and
then the second string call goes straight through, with no bailout.

## After the bailout

A deopt also cleans up. The optimized code is no longer valid, so it is
unlinked from the function, and the next call goes back to unoptimized
code<Cite id="v8-lazy-unlinking" />. The failed call finished in Ignition,
and on the way it updated the feedback to `Any`; when `add` got hot
again, the new code was compiled from that wider feedback, with no Smi
guess left to fail, which is why the third example shows no second
bailout. Getting this wrong is expensive: Crankshaft, V8's optimizing
compiler before TurboFan, too often reoptimized a function with the same
assumptions that had just failed, giving endless
optimization–deoptimization loops<Cite id="v8-leaving-sea-of-nodes" />.

<Callout kind="engine" label="Under the hood">
The cheaper compiling is, the cheaper a wrong guess. Maglev compiles
roughly ten times faster than TurboFan, so V8 can use it earlier: if the
feedback was not stable yet, deoptimizing and recompiling costs
little<Cite id="v8-maglev" />. (This Node 22 build does not enable Maglev,
which is why every trace here says TURBOFAN.) Viscosity has no such
safety net: it compiles before the program runs, with no deoptimizer to
fall back on, so it must prove every change safe.
</Callout>

## What you learned

- **Deoptimization** happens when a guard fails: the deoptimizer uses the
  saved **frame state** to rebuild an Ignition frame, and the call
  finishes in the interpreter with the same result.
- `--trace-deopt` names the reason and bytecode offset;
  `--trace-deopt-verbose` shows the rebuilt frame, down to the
  accumulator.
- After a deopt the code is unlinked and the feedback is wider, so the
  next optimization does not repeat the guess; repeating it is a
  **deoptimization loop**.
