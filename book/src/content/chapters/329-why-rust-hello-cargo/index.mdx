## Two garbage collectors deep

Think back to the chapter *Reclaiming memory: mark and sweep*. Your Drip
VM is a TypeScript program, so it runs on V8, and V8 already has a
garbage collector<Cite id="v8-trash-talk" />; yet you still had to write
a second one over the VM's own list of objects, because only the VM knows
which Drip objects are still reachable (to V8, everything on that list
looks alive). That is two collectors stacked on top of each other, and
the bottom one is doing work you never asked for.

Then think back to *How JavaScript stores numbers and objects*: every
object carries a hidden header, and the engine decides how numbers are
stored. Viscosity, the compiler you finished in Part IX, exists because
JavaScript gives you no direct say over memory layout; it has to coax
the engine into a struct of arrays by way of typed arrays. Track B starts
again in a language where neither workaround is needed.

<Analogy title="a hotel versus a house of your own">
TypeScript is like staying in a hotel: the staff (the engine) clean your
room, decide where your luggage goes and tidy up after you leave, which
is lovely until you want the furniture somewhere else. Rust is like
owning the house: you decide where everything goes and nobody cleans up
after you, however a strict inspector checks your plans before you are
allowed to move in, so the house never falls down.
<span slot="breaks">A real inspector checks a house once; the Rust
compiler checks your whole program every time you build it, and it
checks rules about memory, not about walls.</span>
</Analogy>

## What Rust is, and when it does its work

**Rust** is a language that is compiled ahead of time to machine code,
has no garbage collector, and still refuses to compile a program that
could read freed memory (outside code marked `unsafe`, which a later
chapter covers)<Cite id="klabnik2026" />. It manages that with a small
set of *ownership* rules, checked by the compiler, which are the heart
of this part of the book.

The biggest change from TypeScript is *when* the work happens. Step
through the same program going down both roads:

<BuildSteps client:visible />

V8 does a great deal while your program runs: it parses, interprets
bytecode with Ignition, watches for hot code and compiles
it<Cite id="v8-ignition" />. A Rust program did all of that before it
started, so all that is left at run time is your own code on the CPU.

<Analogy title="a banquet kitchen versus cooking to order">
A restaurant that cooks to order starts each dish when the ticket
arrives and gets faster at the popular ones as the night goes on; that is
V8, learning which functions are hot. A banquet kitchen preps and checks
every plate before the doors open, so service is only carrying plates
out; that is a Rust program.
<span slot="breaks">A banquet kitchen cannot change the menu once
guests arrive, and neither can Rust adapt its machine code to how the
program is used; V8 can, which is why a JIT sometimes wins.</span>
</Analogy>

<Callout kind="definition">
**Rust** is a compiled systems language. Its compiler, `rustc`, checks
types and memory-safety rules for the whole program, then produces
native machine code. The running program has no garbage collector and
no JIT: memory is freed at points the compiler works out in advance.
</Callout>

The costs are real, and you should hear them now. The compiler rejects
programs that TypeScript would happily run, and at first it will feel
like arguing with it; you wait for a full compile before every run; and
some designs that are easy with a collector (many objects all pointing
at each other) take more thought.

Read it with the care of *Benchmarking honestly*:

- **Both ran on the same shared cloud machine, on the same day,** each
  program in a fresh process, best of three runs for both VMs, so expect
  some noise.
- **This is one port, not "Rust versus JavaScript".** Different code,
  or a JIT that suits a program better, could change every bar.
- **The gain is not uniform.** Most programs ran four to five times as
  fast, but `strings` barely moved (1.26×), a reminder that a port speeds
  up some kinds of work far more than others.

## Hello, Rust

Here is a complete Rust program:

```rust
fn main() {
    println!("Hello, Drip!");
}
```

Line 1 declares a function called `main` (`fn` is Rust's `function`),
which is where every Rust program starts; there is no top-level code as
in a JavaScript file. Line 2 prints a line of text, and plays the part of
`console.log`; the `!` marks `println!` as a **macro**, which is code
that writes code at compile time (a later chapter shows how), and every
statement ends with a semicolon. Inside the string, `{}` marks a gap
that `println!` fills with the next argument.

<Examples of="rust">

```rust
println!("{}", 2 + 3); // 5
```

```rust
let name = "drip";
let n = 35;
println!("{name}: fib({n})");
// drip: fib(35)
```

<Run id="hello" />

</Examples>

The first fills one gap with `2 + 3`, which is worked out before
printing, so it prints `5`. The second shows the other way to fill a
gap: a variable's name written inside the braces, `{name}`, prints that
variable (and `let` makes a variable, much like TypeScript's `const`,
which *Variables, types and mutability* explains). The runnable one mixes both
styles; change it and run it again.

Forget the `!` and the compiler tells you exactly that. Here is the
broken line and the fixed one, with rustc 1.97's real message (long
lines in this book are wrapped to fit your screen):

```rust
println("Hello, Drip!");  // broken
println!("Hello, Drip!"); // fixed
```

```text
error[E0423]: expected function, found
  macro `println`
2 |     println("Hello, Drip!");
  |     ^^^^^^^ not a function
help: use `!` to invoke the macro
```

Misspell `main` instead and the error says what is missing:
``error[E0601]: `main` function not found in crate``. Rust's messages
are long and specific, so read them to the end: the `help:` line often
holds the fix.

<OtherLanguages title="Hello, with a number in it">

```rust
fn main() {
    let n = 3;
    println!("n is {n}");
}
```

```ts
const n = 3;
console.log(`n is ${n}`);
```

```c
#include <stdio.h>
int main(void) {
    int n = 3;
    printf("n is %d\n", n);
    return 0;
}
```

```python
n = 3
print(f"n is {n}")
```

</OtherLanguages>

The real differences: TypeScript and Python run top-level code, while
Rust and C start in `main`; C must be told how to print each value
(`%d` for a whole number), while Rust's `{}` works it out from the type
at compile time and refuses to compile if a gap has no value; and only
Rust and C are compiled to machine code before they run.

<Prompts ids={['rs-main', 'rs-println-bang', 'rs-gap', 'rs-help-line']} />

<Callout kind="engine" label="Under the hood">
Viscosity rearranged arrays of objects into typed-array columns because
JavaScript hides layout. In Rust, a `Vec` of structs and a struct of
`Vec`s are both ordinary code you write, with no object headers in the
way, and the chapter *Struct of arrays in Rust by hand* builds one. The
Rust Drip VM goes further: its `src/lib.rs` starts with
`#![forbid(unsafe_code)]`, so the whole VM, collector included, is
checked by the compiler with no exceptions.
</Callout>

## What you learned

- **Rust** compiles to machine code ahead of time, with no garbage
  collector and no JIT, and the compiler checks memory safety before the
  program runs. The price is a stricter compiler and slower builds.
- In this book's run, the Rust port of the Drip VM was four to five
  times as fast as the TypeScript VM on most programs: one run, one
  port, one machine.
- Every program starts in `fn main()`; `println!` is a **macro**, and
  `{}` or `{name}` fills a gap in its text.
