## A function that stops half-way

You wrote generators, functions with a `*` that hand out values one at
a time with `yield`, in *Iterators and generators*; this chapter goes
further, to how a compiler turns one into code that only calls and
returns. Here is the smallest useful one:

```js
function* count(n) {
  for (let i = 0; i < n; i++) yield i;
  return 'done';
}
const g = count(2);
g.next(); // { value: 0, done: false }
g.next(); // { value: 1, done: false }
g.next(); // { value: 'done', done: true }
```

Calling `count(2)` runs nothing; it returns a generator object, and each
`next()` runs the body until the next `yield`, which hands a value out
and pauses<Cite id="mdn-generator" />. Now think about what that means
for the machine. An ordinary call keeps its variables in a frame on the
call stack, and the frame is thrown away when the call returns; but the
first `next()` returns while `i` is still 0 and the loop is half done,
and the second `next()` must find `i` again and carry on from just after
the `yield`. Neither a stack frame nor a return address survives that.
A compiler has to keep two things somewhere longer-lived: the
variables, and *where it stopped*.

<Analogy title="a bookmark and a notepad">
You stop reading a novel at bedtime. The bookmark says where you
stopped, and your notepad holds who is who; tomorrow you open at the
bookmark and read on, without starting the book again.
<span slot="breaks">A bookmark can go on any page; a compiled generator
can only stop and restart at its `yield`s, the places the compiler
numbered in advance.</span>
</Analogy>

<Callout kind="definition">
A **resumable function** can stop part-way through, return to its
caller, and later continue from the same point with its local variables
as they were. A generator is one; it stops at each `yield`, and is
resumed by `next()`.
</Callout>

## Number the stops, switch on the number

The machine only knows how to call and return, so we rewrite the
generator into code that only calls and returns. Three steps do it:

1. Move every variable that must survive a `yield` into a **record**
   that outlives the call (here, variables captured by a closure, the
   way *Closure conversion and lambda lifting* turned closures into
   records).
2. Give the start, each `yield` and the end a **state number**, and keep
   the current number in the record as well.
3. Make `next()` a `switch` on the state number. Each `yield` becomes
   "set the state to the number of the code after me, then return the
   value"; the code after the `yield` becomes that state's `case`. A
   loop that contains a `yield` is cut into states too, with a jump
   (setting the state and going round again) instead of the loop.

You stop a board game half-way and leave everything on the table: the
pieces where they stood and a note saying "Ana's turn, she has rolled".

<span slot="breaks">A note on a game can say anything; a generator's

`switch`.</span>
</Analogy>

<Callout kind="definition">
**State-machine lowering** compiles a resumable function into an
ordinary one: its live variables move into a record that outlives each
call, every suspension point gets a **state number**, and the body
becomes a `switch` on the state, where each suspension saves the next
state and returns, and each `case` continues after one suspension.
</Callout>

<Formal title="Lowering the k-th yield">

```text
⟦ S₁; yield e; S₂ ⟧
  =  ⟦S₁⟧; st = k; return more(e);
     case k: ⟦S₂⟧
```

<span slot="read">To lower some code S1, then the k-th yield of e, then
more code S2: lower S1, then set the state to k and return e as a value
that is not done; the code S2 after the yield becomes case k of the
switch, so the next call to next() starts there.</span>
</Formal>

## The same machine, three times

You do not have to take this on trust: three real systems do exactly
this, and you can see it in their output.

<Examples of="state-machine-lowering resumable-function">

```text
// tsc 5.9 --target es5, count (trimmed)
switch (_a.label) {
  case 0: i = 0; _a.label = 1;
  case 1:
    if (!(i < n)) return [3, 4];
    return [4 /*yield*/, i];
  case 2: _a.sent(); _a.label = 3;
  case 3: i++; return [3, 1];
  case 4: return [2, 'done'];
}
```

```text
// node --print-bytecode, function* count
SwitchOnGeneratorState r0, [0], [2]
                   { 0: @20, 1: @62 }
SuspendGenerator r0, r0-r1, [1]
ResumeGenerator r0, r0-r1
```

```text
# python3.13 -m dis, def count(n)
RETURN_GENERATOR
YIELD_VALUE 0
RESUME 5
```

</Examples>

The first is TypeScript compiling `count` for old browsers that have no
generators: the body is a `switch` on `_a.label` (its state number),
and instead of returning a value it returns a small instruction to a
helper, `__generator`, from the `tslib` library: `[4, i]` means "yield
`i`, and add one to the label", `[3, 1]` means "jump to label 1", and
`[2, 'done']` means "return"<Cite id="tslib-generator" /> (the `/*break*/`
and `/*return*/` comments it adds are trimmed here, and short lines
joined). The second is V8: a
generator function starts with `SwitchOnGeneratorState`, a jump table
from state to resume point, and each `yield` is a `SuspendGenerator`,
which copies the function's registers into the generator object and
returns, paired with a `ResumeGenerator` that copies them
back<Cite id="v8-interpreter-generator" />. The third is CPython, where
`RETURN_GENERATOR` makes the generator object, with the function's
whole frame embedded inside it, and `YIELD_VALUE` returns to the caller
after saving the instruction pointer in that frame<Cite id="cpython-generators" />;
the generator's frame lives in a heap object, not on the stack.

<Prompts ids={['v8-saves', 'python-frame']} />

<Callout kind="engine" label="Under the hood">
The three differ in *what* goes in the record. CPython keeps the whole
frame, V8 copies its register file, and the TypeScript output keeps
only the variables the body declares, in the closure of the function it
passes to `__generator`. A compiler can go further and keep only the
variables that are live across some `yield` (the analysis of *Liveness*, put to a new use), so that the record is as small as
possible. *Lowering async/await* does this one more time, for `async` functions,
where the thing that calls `next()` is the promise machinery rather
than a `for...of` loop.
</Callout>

## What you learned

- A **resumable function** stops part-way and continues later with its
  variables intact, so its variables and its place cannot live in an
  ordinary stack frame.
- **State-machine lowering** moves the variables into a record, numbers
  the suspension points, and turns the body into a `switch` on the
  state; each `yield` saves the next state and returns.
- TypeScript's ES5 output, V8 (`SuspendGenerator`) and CPython
  (`YIELD_VALUE`) all build this machine, keeping different amounts of
  the frame.

Next, *Lowering async/await*: `async` and `await`, which are the same
machine driven by promises.
