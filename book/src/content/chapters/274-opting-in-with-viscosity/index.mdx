## You know something it doesn't

The cost model from the last chapter guesses from what the code looks
like, and sometimes you know better: the test data has 10 particles but
production has two million; or you are chasing a bug and want `ps` left
exactly as you wrote it; or the array is filled inside a function, so
the size is "unknown" (which passes), and you know it is tiny. In each
case the fix is one comment on the line above the declaration:

```js
// @viscosity aos
const ps = [];
```

<Analogy title="a sticker on a removal box">
The removal crew decides how to load the van, but a box marked "fragile"
or "open first" gets handled the way the sticker says; and if you never
hire a crew, the sticker does no harm at all.
<span slot="breaks">A crew reads a sticker wherever it is on the box;
Viscosity reads an annotation only in one exact place (the line above,
or the end of the same line), and a sticker in the wrong place is
ignored without a word.</span>
</Analogy>

<Analogy extra title="a do-not-disturb sign">
Housekeeping has its own plan for which rooms to clean, and the sign on
your door overrules that plan for your room; however, it does not stop
the fire alarm, which goes into every room whatever the sign says.
<span slot="breaks">A hotel guest can hang a sign for any reason;
Viscosity accepts only three words, and an `aosoa` sign it cannot honour
(a bad block size, a field that is not a number) is turned down, with a
reason, rather than followed.</span>
</Analogy>

The fire alarm in that picture is safety, and the plan is the cost
model: an annotation overrules the guess, never the proof.

## Three words

There are three annotations, one per layout:

```js
// @viscosity aos       keep objects
// @viscosity soa       struct of arrays
// @viscosity aosoa(8)  AoSoA, blocks of 8
```

The JavaScript plugin finds them with one regular expression, `ANN`
in `frontend-js/src/index.ts` (one line in the source, split here):

```js
/@viscosity\s+(aosoa|soa|aos)\b
  (?:\(([^)]*)\))?/
```

Read it left to right: the word `@viscosity`; one or more spaces (`\s+`);
one of the three layout names, captured as `m[1]` (`aosoa` is listed
first, so it is tried before its shorter prefix `aos`); a word boundary
(`\b`), so that `@viscosity soap` is not read as `soa`; and, optionally,
whatever sits in parentheses, captured as `m[2]`. The plugin accepts any
text there and lets the planner judge it later. Try it on a few comments:

<Callout kind="definition">
An **annotation** is a comment (or other marker) that gives the compiler
extra instructions without changing what the program means. A
Viscosity annotation names a layout for one collection; a program with
annotations is still ordinary JavaScript, and runs the same with or
without Viscosity.
</Callout>

<Formal title="The annotation, as a grammar">

```text
annotation ::= "@viscosity" space+ layout
               [ "(" text ")" ]
layout     ::= "aosoa" | "soa" | "aos"
```

<span slot="read">An annotation is the word @viscosity, then one or
more spaces, then a layout, then optionally some text in brackets
(square brackets in the rule mean "optional", and + means "one or
more"); a layout is one of the three words, spelled exactly in lower
case.</span>
</Formal>

## Which declaration?

A comment has no idea which variable it is about. While parsing, acorn
reports every comment with the line it ends on, and the plugin decides
from the line itself (trimmed slightly):

```ts
for (const cm of comments) {
  const m = ANN.exec(cm.value);
  if (!m) continue;
  const own = /^\s*(\/\/|\/\*|\*)/
    .test(srcLines[cm.line - 1] ?? '');
  for (const [jb, id] of bindingOf) {
    const line = jb.decl?.loc?.start.line;
    if (own ? line === cm.line + 1
            : line === cm.line)
      annotations.set(id, {
        layout: m[1], blockText: m[2],
        line: cm.line, blockSize: … });
  }
}
```

Lines 2 and 3 skip any comment that does not match. Lines 4 and 5 ask
whether the comment is **alone on its line**: does the line start, after
spaces, with `//`, `/*` or `*`? Line 6 walks every declared name, and
line 8 picks the target: a comment alone on its line annotates
declarations on the *next* line, and a trailing comment (code before it)
annotates only its *own* line. The record keeps the layout, the text in
brackets, the comment's line for explain, and `blockSize`, which is the
number when the text is all digits and `undefined` otherwise. Step
through a file with four comments that look like annotations:

```js
// @viscosity aos
const ps = [];

```

```js
const ps = []; // @viscosity aos

// → ps kept as told; qs is not
//   annotated, and becomes soa
```

```js
// @viscosity soa
const pts = [{ x: 1, y: 2 },
  { x: 3, y: 4 }, { x: 5, y: 6 }];
// → struct of arrays, "about 3
//   elements": the size rule is skipped
```

</Examples>

The first is the plain case: alone on line 1, it reaches `ps` on line 2,
which (filled with 1,000 particles and looped over) would otherwise have
become SoA. In the second the comment trails `ps` on line 1, so it
reaches only `ps`; `qs` on the next line goes down the ladder on its own
and is transformed. The third is the case the cost model would refuse,
three points, and the annotation wins (both programs also fill and loop
over their arrays; the verdicts are the real explain output).

The common mistake is a comment that looks right and does nothing:

```js
// @viscosity SoA
const ps = [{ x: 1 }, { x: 2 }];
// → kept: about 2 elements: below
//   the 64-element threshold
```

With `soa` in lower case the same program is annotated and transformed;
with `SoA` the pattern does not match, the comment is only a comment,
and the size rule keeps the array. There is no warning, and a blank line
between the comment and the declaration fails the same way. So check:
`viscosity explain` names every annotation that landed ("annotated
@viscosity … at line N").

## What an annotation can and can't do

On the planner's ladder from *The cost model*, an annotation sits on the
second rung: below safety, above every cost rule.

<Figure caption="An annotation skips the cost rules beneath it, and can never reach past safety above it." takeaway="Annotations overrule guesses, not proofs.">
  <WhereItSits />
</Figure>

**`aos` stops a transform.** This program becomes SoA. Add
`// @viscosity aos` on the line above `const ps`, then watch the
explanation and the compiled code change, and run both:

<Playground client:visible title="Stop the transform" initial={`const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
console.log(ps[7].x);`} />

**`soa` skips the cost rules**, all three: the size (as in the third
example), the loop rule and even the numeric rule, so an annotated
collection with only a string field gets a plain-array column for it.

**`aosoa(N)` has conditions**, checked in this order, because the whole
block is one `Float64Array` indexed with shifts (as *AoSoA code
generation* shows). N must be at most 65536; it must be a power of two
(2, 4, 8, …), and a missing `(N)` means 8; and every field must be
provably numeric. Each failure keeps the collection with a reason rather
than stopping the compile:

```text
annotated aosoa(6), but the block size
  must be a power of two (2, 4, 8, 16, ...)
annotated aosoa, but fields id may
  hold non-numbers
```

**Nothing overrides safety.** Annotate `ps` with `soa` and then write
`console.log(ps)`, and explain still says "unsafe: the array is passed
to a method call at line 7". An annotation tells the cost model what to
think; it cannot make an observable change invisible.

## Opt-in mode

By default Viscosity decides everything, and annotations adjust it. With
`--mode opt-in` it flips: only annotated collections are transformed. The
corpus file `opt_in_mode.js` has two identical arrays of 300 records, and
marks only the first with `// @viscosity soa`:

```text
marked (line 3) {v} → struct of arrays
  · annotated @viscosity soa at line 2
  …
unmarked (line 4) {v} → kept as array
  of objects
  · opt-in mode: not annotated
```

That suits adopting Viscosity a little at a time, or a team that wants
every layout change to show in the source and in code review. Python is
already close to opt-in: its planner keeps lists unless you annotate
them, for the reason *The cost model* gave.

<Callout kind="engine" label="Under the hood">
Compilers have long taken hints this way. Clang accepts
`#pragma clang loop vectorize(enable)` before a loop, and can be told a
vector width, overruling its vectorizer's cost model for that one
loop<Cite id="llvm-vectorizers" />. Intel's ISPC puts the layout in the
type: `soa<8> Point pts[...]` stores an array eight elements at a time,
field by field, while code still writes `pts[10].x`<Cite id="ispcdocs" />.
Viscosity sits between the two: its hint names a layout, like ISPC's,
and sits on one declaration, like a pragma on one loop; but it lives in
a comment, so every JavaScript engine and tool reads the program as
before.
</Callout>

## What you learned

- An **annotation** is a comment with instructions for the compiler:
  `@viscosity aos`, `soa` and `aosoa(N)`.
- Alone on its line, it reaches the next line; trailing, only its own
  line. Wrong case or a blank line, and it silently does nothing, so
  check with `viscosity explain`.
- It sits below safety and above the cost model: `aos` stops a
  transform, `soa` skips the cost rules, and nothing forces an unsafe
  change.
- `aosoa(N)` needs N a power of two up to 65536, and every field numeric.
- `--mode opt-in` transforms only annotated collections.
