## One file in, one file out

This part puts the pieces together into **Viscosity**, the compiler in
this repository's `engine/ts` folder; the first question to ask of any
machine is what goes in and what comes out. In goes a particle program:

```js
const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
for (let i = 0; i < ps.length; i++)
  ps[i].x += ps[i].vx;
console.log(ps[3].x);
```

and `viscosity build` writes a new JavaScript file whose last lines are
these (above them sit a generated class `__Vsc_ps`, with one
`Float64Array` per field, and a small bounds-check helper):

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 1000; i++)
  ps.push(i, 1);
for (let i = 0; i < ps.length; i++)
  ps.x[i] += ps.vx[i];
console.log(ps.x[__vsc_bc(ps, 3, 'x',
  false)]);
```

Every `ps[i].x` became a column access `ps.x[i]`, the struct-of-arrays
change of *AoS vs SoA, measured*; this chapter is about what happened in
between.

## Four steps, two owners

The function `compile`, in `packages/core/src/index.ts`, is the whole
pipeline:

<Examples of="viscosity-pipeline">

```ts
function compile(source, plugin, opts) {
  const lowered = plugin.lower(source);
  const analysis =
    analyze(lowered.module);
  const p = plan(analysis, opts);
  const code =
    plugin.emit(source, lowered, p);
  return { code, plan: p, analysis,
    explain: explain(p) };
}
```

</Examples>

(Trimmed: the real one also fills in default options.) Line 2 hands the
text to a **plugin**, the part that knows one language, which parses it
and **lowers** it to VIR, Viscosity's IR; line 3 runs the **analyses**
on that VIR, and line 5 turns their facts into a **plan**, one layout
per collection; line 6 gives the plan back to the same plugin, which
**emits** new source text; and the last lines return that text, the
plan, the analysis and a readable explanation of every decision (`viscosity explain` prints `ps (line 1) {x, vx} → struct of arrays`
and `2 of 3 element accesses proven in bounds`, which is why `ps[3]`
kept its check).

<Analogy title="a hospital laboratory">
On each ward, a nurse who speaks the patient's language takes a blood
sample and labels the tube in the hospital's standard form. The central
laboratory never meets a patient: it reads the tubes, runs the same tests
for every ward and sends back a result sheet, and the ward nurse, who
knows the patient, acts on it. The wards are the plugins, the labelled
tube is VIR, and the laboratory is the core.
<span slot="breaks">A laboratory can send back a result that nobody acts
on; Viscosity's plan is always carried out, and when the core is unsure
it plans to change nothing at all.</span>
</Analogy>

<PipelineSteps client:visible />

<Callout kind="definition">
The **Viscosity pipeline** is `lower → analyze → plan → emit`. A
language plugin **lowers** source code to **VIR**, Viscosity's IR; the
analyses and the **layout planner** work on VIR alone and choose a
layout for each collection; and the same plugin then **emits** new
source code by applying the plan. Only lowering and emitting know the
language.
</Callout>

This is the front-end and back-end split of *From source to a running
program: interpreters and compilers*, with a twist: the plugin does both
ends, and the middle is shared. Emit does *not* print the program back
out of VIR, either: it replaces only the ranges of your text that the
plan requires, using the pointer back to the source that each VIR
instruction keeps, so your comments, formatting and unrelated lines come
through as you wrote them.

<More title="More: the pipeline as function composition">

<Formal title="The pipeline as function composition">

```text
lower   : Source → Lowered
analyze : VIR → Analysis
plan    : Analysis → Plan
emit    : Source × Lowered × Plan → Source
```

<span slot="read">Each step is a function from one kind of thing to
another (× means "together with"): emit takes the source, the lowered
module and the plan, and gives back source, so the output has the same
type as the input.</span>
</Formal>

With ten particles instead of a thousand, `explain` keeps the objects:
`about 10 elements: below the 64-element threshold, where the benefit is
too small`. The packages follow the pipeline: `packages/core` holds VIR,
its builder, the analyses and the planner; `frontend-js` and
`frontend-python` are the two plugins; and `cli` wraps `compile` as
`viscosity build` and `viscosity explain`.

</More>

## Output that is source code

<Callout kind="definition">
A **source-to-source compiler** (sometimes called a *transpiler*) is a
compiler whose output is source code in a high-level language, often the
same language it reads; that output is then run or compiled by an
ordinary tool. Viscosity reads JavaScript, TypeScript or Python and
writes JavaScript or Python.
</Callout>

<Examples of="source-to-source">

```ts
interface P { x: number; vx: number }
const ps: P[] = [];
// out (the interface line is now blank):
const ps = new __Vsc_ps();
```

</Examples>

For a TypeScript file the plugin strips the types first (*Interfaces,
erasure and typeof*), so the output is plain JavaScript you can read,
diff and run on any engine. Researchers
have also turned arrays of JavaScript objects into columns *while the
program runs*, inside an engine built on Truffle and
Graal<Cite id="makor2022" /><Cite id="wurthinger2013" /><Cite id="kloibhofer2023" />:

<Figure caption="The same idea in two places. Viscosity changes the program before it runs; the run-time approach changes the engine." takeaway="Ahead of time works with any engine but must prove safety from the code alone.">
  <WhenItHappens />
</Figure>

A run-time transformation sees real values and can speculate, then back
out with deoptimisation; however, it helps only on that one engine.
Viscosity's output runs anywhere and adds no work at start-up, but it
gets one look at the code, with no values and no way to back out, so
every decision must be *proved* from the text, and when a proof fails
the collection stays exactly as it was.

## Two functions

This is the whole interface, from `packages/core/src/plugin.ts`
(comments shortened):

<Examples of="language-plugin">

```ts
interface LoweredModule {
  module: Module;
  annotations: Map<BindingId, Annotation>;
}
interface LanguagePlugin {
  id: string;      // 'javascript'
  extensions: string[];
  lower(source: string,
    filename?: string): LoweredModule;
  emit(source: string,
    lowered: LoweredModule,
    plan: Plan): string;
}
```

</Examples>

`lower` takes source text and gives back a VIR `Module` and any
`@viscosity` annotations it found in comments;
`emit` gets the source, the same `lowered` object and the plan, and
returns new source; `id` names the language and `extensions` lists the
file endings it handles. There is no `parse`: parsing happens inside
`lower`, with whatever parser the plugin likes, and the core only ever
receives VIR. The smallest correct plugin lowers everything to an empty
module and has `emit: (s) => s`: useless, but never wrong.

<Callout kind="definition">
A **language plugin** is the object a language front end gives
Viscosity: an `id`, the file `extensions` it handles, and two functions,
**`lower`**, which parses source and lowers it to VIR, and **`emit`**,
which rewrites that source according to a layout plan. Everything
between them (analysis, planning, explain) is shared by every language.
</Callout>

`emit` gets `lowered` back typed as a plain `LoweredModule`, but a
plugin may return a *bigger* object from `lower` (an interface promises
at least these fields): the JavaScript plugin adds its syntax tree, its
scope resolution and the JavaScript text it analysed, and the core
passes the whole object along without looking inside:

<Figure caption="lower returns one object. The core reads only its LoweredModule part; emit gets all of it back." takeaway="A plugin keeps private state across the core without the core knowing its type.">
  <PrivateParcel />
</Figure>

Syntax needs someone who knows the language; "which fields does this
loop touch?" has the same answer however the loop was spelled, so the
escape checks and bounds proofs are written once, on VIR:

## Layout strategies

The other way to extend Viscosity is *how* a collection is stored, and
the same file lists that too: `STRATEGIES`, three entries named `aos`,
`soa` and `aosoa`, each with a one-line description.

<Callout kind="definition">
A **layout strategy** is one way of storing a collection: `aos` leaves
the array of objects, `soa` uses one column per field, and `aosoa` uses
blocks of N elements, field-major inside each block. The planner chooses
a strategy per collection, and each plugin's `emit` knows how to write
it.
</Callout>

<Examples of="layout-strategy">

```js
ps[i].x    // aos: left as it was
ps.x[i]    // soa: column x, slot i
// aosoa(8), fields x and vx:
ps.data[((i) >> 3) * 16 + 0
  + ((i) & 7)]
```

</Examples>

These are the real accesses Viscosity writes for `ps[i].x`. Under `soa`,
field `x` has its own `Float64Array` and element `i` is slot `i`; under
`aosoa(8)` everything lives in one `Float64Array`, `data`, where `i >> 3`
is the block number (`i` divided by 8, rounded down), each block holds
16 numbers (8 `x`s, then 8 `vx`s), `+ 0` picks the `x` part and `i & 7`
is the position inside the block. Today the list is only names, though: each
emitter implements each layout (the Python one throws on `aosoa`).

<More title="More: the address formula, and computing it">

<Formal title="Where field k of element i lives">

```text
aos:    ps[i].f_k
soa:    col_k[i]
aosoa:  data[⌊i / B⌋·F·B + k·B + (i mod B)]
```

<span slot="read">With F fields numbered from 0 and blocks of B
elements: under aos it is a property of the i-th object; under soa it is
slot i of column k; under aosoa, element i is in block ⌊i / B⌋, each
block holds F·B numbers, field k's run starts k·B into the block, and
the element sits i mod B along that run.</span>
</Formal>

<Run id="addresses" />

Both plugins build VIR with the same `ModuleBuilder`, so both get SSA
from one implementation of the on-the-fly algorithm<Cite id="braun2013" />:
a plugin never writes a phi by hand.

</More>
