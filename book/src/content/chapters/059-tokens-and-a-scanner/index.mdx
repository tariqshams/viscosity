## Characters are too small

```
let speed = 10.5;
```

The parser's job is to recognise the shape of this line: a `let`, then
a name, then `=`, then a value, then `;`. Doing that one character at a
time, it would have to ask whether `l` starts `let` or a name like
`lemon`, and whether `1` is a number or the start of `10.5`; every rule
of the grammar would worry about spelling as well as shape. So the
scanner deals with spelling once and hands the parser whole words,
called **tokens**, as in *Checkpoint: JSON and its scanner*.

## What a token is

<TokenSteps client:visible />

In the companion code a token is a plain object, from
`companion/ts/src/token.ts`:

```ts
interface Token {
  type: TokenType;
  lexeme: string;
  literal: string | number | null;
  line: number;
}
```

<Callout kind="definition">
A **token** is one meaningful word of source code. Its **lexeme** is the
exact characters it was made from, such as `"10.5"`. Its **token type**
is its category: a number, an identifier, a keyword, the `+` operator.
For numbers and strings the scanner also stores the **literal**, the
value the characters stand for, such as the number `10.5`. (Textbooks
often call the type the token's *syntactic
category*<Cite id="coopertorczon2022" />.)
</Callout>

<Examples of="token lexeme">

```text
print x;  →  print   x   ;   eof
10.5    lexeme '10.5' (text), literal 10.5
"fast"  lexeme "fast" (6), literal fast (4)
```

</Examples>

Three words make three tokens, the space makes none, and the scanner
always adds `eof` (end of file), so a parser asking "what is next?" gets
a clear answer at the end. The number's lexeme is four characters of
text, while its literal is a number the interpreter can do arithmetic
with; a string's lexeme includes its quote marks, while its literal is
the text inside them, which is what `print` shows.

## Token types

Why a type, if the lexeme says everything? Because the parser thinks
in categories: its rule is "a `let` is followed by *any* name", and
thousands of different lexemes share the one type `identifier`.

<Callout kind="definition">
A **token type** is the category of a token. Drip's `TokenType` is a
union of string literal types (*TypeScript II: unions and narrowing*),
52 in all: one for each of its 27 punctuation marks and operators,
`identifier`, `string` and `number`, one for each of its 20 keywords,
`eof`, and `error`, for a piece of source the scanner could not use.
Spaces, newlines and `#` comments separate tokens but never become
tokens.
</Callout>

<Examples of="token-type">

```text
while n <= 10 {
'while'  identifier  '<='  number  '{'
```

</Examples>

For punctuation and keywords the type *is* the spelling (`<=` is one
token of type `'<='`, not `<` then `=`), and only names, numbers and
strings have a type that differs from their lexeme; a misspelt type
such as `'eqaul'` is rejected by TypeScript before the scanner ever
runs.

<More title="The whole TokenType union">

```ts
type TokenType =
  // punctuation and operators
  | '(' | ')' | '{' | '}' | '[' | ']'
  | ',' | '.' | '..' | ';' | '+' | '-'
  | '*' | '/' | '%' | '!' | '!=' | '='
  | '==' | '<' | '<=' | '>' | '>='
  | '&&' | '||' | '+=' | '-='
  // literals
  | 'identifier' | 'string' | 'number'
  // keywords
  | 'break' | 'class' | 'continue'
  | 'else' | 'extends' | 'false' | 'fn'
  | 'for' | 'if' | 'in' | 'init' | 'let'
  | 'new' | 'none' | 'print' | 'return'
  | 'self' | 'super' | 'true' | 'while'
  | 'error' | 'eof';
```

<Analogy extra title="a sentence marked up by a teacher">
A teacher underlines each word, writes a label under it (*noun*,
*number*) and notes the line in the margin: the spelling, the category
and the place.
<span slot="breaks">A teacher's label depends on meaning; a scanner
decides a token's category from its spelling alone.</span>
</Analogy>

</More>

## Where it came from

When something goes wrong much later, in a stage that never sees the
characters, the token is the only way to say *where*. A scanner walks
the source by **offset** (a character's index in the whole string,
newlines included), and people want a line instead, which comes from
counting the newlines passed:

<Figure takeaway="Count the newlines you pass." caption="The source let x;, an empty line, then print x +;. Every character, newlines included, has one offset in the whole string. The + at offset 16 comes after two newlines, so it is on line 3, and it is the ninth character of that line.">
  <OffsetGrid />
</Figure>

<Callout kind="definition">
A token's **source location** says where in the source it came from:
its line, and often its column (its position within the line, counting
from 1). Error messages use it to point at the problem. Drip's tokens
record only the line, because Drip's error messages name only the line.
</Callout>

<Examples of="source-location">

```text
let x;

print x +;
line 3: expected an expression,
found ';'
```

</Examples>

The parser expected a value after `+` and found the `;` token, so its
message takes the line from that token and quotes its lexeme. (Drip's
VM keeps a line number beside every byte of bytecode for the same
reason, so an error deep inside it can still name your line; and
Viscosity's IR gives every instruction a `SourceRef` with offsets and a
line.)

<More title="Try it, and the column formula">

`one` is never printed: the whole program is checked before any of it
runs.

<Run id="error-lines" />

<Formal title="From an offset to a line">

```text
line(o) = 1 + (newlines in source[0 .. o))
col(o)  = o − (offset after the last
               of those newlines) + 1
```

<span slot="read">The line of the character at offset o is one more
than the number of newlines before it; its column is how far it is past
the start of its line, plus one. For the + in the figure: two newlines,
line 3; line 3 starts at offset 8, so column 16 − 8 + 1 = 9.</span>
</Formal>

</More>

## Two fingers on a line of text

The scanner itself is one function, `scan(source: string): Token[]` in
`companion/ts/src/scanner.ts`, about a hundred lines long.

<Analogy title="two fingers on a line of text">
Run two fingers along a line of print. Your left finger marks where the
current word began; your right finger slides forward, letter by letter,
until the word ends. Everything between your fingers is the word: write
it down, move your left finger up to your right one, and start again.
<span slot="breaks">Fingers can jump back to reread. Drip's scanner
never moves backwards: once a character is behind the right finger, it
is never looked at again.</span>
</Analogy>

The fingers are two numbers, with helpers declared inside `scan` as
closures, so they all see `source`, `start` and `current` (simplified
here to fit):

```ts
let start = 0;   // where this token began
let current = 0; // the next char to read
let line = 1;
const atEnd = () =>
  current >= source.length;
const advance = () => source[current++];
const add = (type, literal = null) =>
  tokens.push({ type, literal, line,
    lexeme: source.slice(start, current) });
```

`advance` returns the character at `current` *and* moves past it
(`current++` gives the old value, then adds one); `add` cuts the lexeme
from `start` up to, not including, `current`. (A `peek` helper looks at
the next character without moving, returning `'\0'` at the end.)

<Figure takeaway="The lexeme is everything between the pointers." caption="Scanning x = 12;. The token being built started at offset 4 and current has moved to offset 6, the semicolon, which is not part of it. slice(4, 6) takes offsets 4 and 5: the lexeme 12.">
  <TwoPointers />
</Figure>

<Callout kind="definition">
A **scanner** (also called a *lexer*) is the first stage of a front end.
It reads source text character by character and produces a list of
tokens, skipping the characters that only separate them. Drip's keeps
two indexes into the text: `start`, the first character of the token
being built, and `current`, the next character to read.
</Callout>

Every round of the loop makes at most one token: move `start` up to
`current`, read one character, and let a `switch` decide what it
begins.

<ScanLoopSteps client:visible />

<Examples of="scanner">

```ts
while (!atEnd()) {
  start = current;
  const c = advance();
  switch (c) {
    case '(': case ')': case ';':
      add(c); break;
    case ' ': case '\t': break;
    case '\n': line++; break;
    default:
      error(`unexpected character '${c}'`);
  }
}
tokens.push({ type: 'eof', lexeme: '',
  literal: null, line });
```

</Examples>

A one-character token needs only `add(c)`, since its type is its own
spelling. Whitespace does nothing, so it makes no token, and a newline
only bumps `line`. The `default` case catches a character no case
wanted, such as `@`, and `error` adds a token of type `error` whose
lexeme is the message; scanning *carries on*, and the parser reports
that token when it reaches it, so every error comes out in source
order. After the loop, one `eof` token is pushed.

<More title="Try it: a scanner small enough to read in one go">

It knows brackets, braces and semicolons, skips spaces, counts lines and
reports anything else; change the inputs at the bottom.

<Run id="mini-scan" />

Drip's VM makes a different choice: its scanner hands out one token at a
time, whenever the compiler asks (`companion/ts/src/vm/scanner.ts`), so
the full list is never built. A list is easier to inspect and test; one
at a time saves memory on a long program. Either way, this is the part
a compiler textbook calls the *lexical
analyser*<Cite id="coopertorczon2022" />.

</More>

## What you learned

- A **token** is one meaningful word of source: its **lexeme** is the
  exact characters, its **token type** its category, and numbers and
  strings also carry a literal.
- A **source location** lets later stages report errors in the right
  place.
- A **scanner** keeps two pointers, `start` and `current`; each lexeme
  is `source.slice(start, current)`, whitespace makes no token, and an
  unknown character becomes an `error` token.
