## Push into a fixed box

Here is a program from Viscosity’s test corpus, `growth.js`. Nobody knows
how many elements `ps` will hold until the `while` loop has run:

```js
const ps = [];
let n = 0;
while (n < 5000) {
  ps.push({ a: n, b: n % 7 });
  n++;
}
```

Viscosity turns `ps` into a struct of arrays with two `Float64Array`
columns. But a `Float64Array` made with `new Float64Array(n)` has a fixed
length, and it starts out full of zeros<Cite id="mdn-typedarray" />.
There is no `push` on it. So how does the compiled program keep pushing?

<Callout kind="intuition">
A restaurant expecting an unknown number of guests doesn’t add one chair
each time someone walks in. It sets a table for 16. When that fills up, it
moves everyone to a table for 32. Moving is a hassle, but it happens
rarely, and most guests just sit down.
</Callout>

## Capacity and length

The container from chapter 216 keeps two numbers. `cap` is how many slots
each column has. `length` is how many of them hold real elements. Step
through a column filling up:

<CapacitySteps client:visible />

<Callout kind="definition">
A collection’s **capacity** is the number of slots it has allocated; its
**length** is the number in use. Slots from `length` up to `capacity` are
spare: they exist in memory, but they aren’t elements. When a push finds
`length === capacity`, the collection **grows**: it allocates bigger
storage and copies the old elements into it.
</Callout>

## The real container

Here is what Viscosity really generates for `growth.js`, reformatted to fit
the screen (the compiler writes each method on one line):

```js
class __Vsc_ps {
  constructor(cap = 16) {
    this.length = 0;
    this.cap = cap;
    this.a = new Float64Array(cap);
    this.b = new Float64Array(cap);
  }
  push(v0, v1) {
    const n = this.length;
    if (n === this.cap) this.grow();
    this.a[n] = v0;
    this.b[n] = v1;
    return (this.length = n + 1);
  }
  grow() {
    const cap = (this.cap *= 2);
    let t;
    t = new Float64Array(cap);
    t.set(this.a); this.a = t;
    t = new Float64Array(cap);
    t.set(this.b); this.b = t;
  }
}
```

The `push` in the loop becomes `ps.push(n, n % 7)`. `grow()` doubles
`cap`, and gives each column a new `Float64Array` of that size. `set`
copies every value of the old column into the start of the new
one<Cite id="mdn-typedarray-set" />. The old column has no references
left, so the garbage collector will reclaim it. And `push` returns the new
length, just as `Array.prototype.push` does, in case the program uses it.

Not every column is typed. When a field may hold strings or objects,
chapter 216’s container gives it a plain array column instead, and
`grow()` leaves that column alone. Writing `this.name[n] = v` at index
`length` simply appends to a plain array: the JavaScript engine grows it by
itself.

## Why doubling

Growing could add a fixed number of slots, say 16, each time. That sounds
thriftier. Count the copies instead:

<Run id="policies" />

With doubling, building 100,000 elements copies about 131,000 values in
all. Adding 16 at a time copies more than 312 million. The reason is
simple. When doubling, each grow copies 16 more values than all the
earlier grows put together: 16, then 32, then 64. So the total is
always less than the final capacity, which is less than twice the length.
Adding 16 instead copies 16, 32, 48, 64 and so on, a sum that grows with
the square of the length.

<Callout kind="definition">
**Amortized growth** spreads the cost of the rare, expensive grows over
all the cheap pushes. With doubling, n pushes copy fewer than 2n values
in total, so one push costs a constant amount *on average*, even though
an unlucky push copies everything. Growing by a constant amount instead
makes n pushes cost time proportional to n².
</Callout>

For `growth.js` itself, the counter below follows the container from
capacity 16: 9 grows, 8,176 values copied per column, and a final capacity
of 8,192 for 5,000 elements.

## What it costs

The book’s `construct` suite times building a whole collection of 6-field
particles from raw values:

<BenchBars suite="construct" n={100000} title="Building 100,000 particles" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa', 'aosoa8']} caption="Writing numbers into columns is far cheaper than allocating one object per element." />

Read it carefully. The harness knows `n` in advance, so its columns are
created at the right size and never grow. What the chart shows is that
filling columns avoids an allocation per element. Doubling adds fewer
than two copies per value on top, which is small next to an allocation,
but this run doesn’t time it separately.

<Callout kind="engine" label="Under the hood">
The spare slots are the subtle part. In the original program `ps[100].a`,
one past the end, throws a TypeError, because `ps[100]` is `undefined`.
After the rewrite the column may have 128 slots, and `ps.a[100]` would
quietly return 0. So when Viscosity can’t prove an index is in bounds, it
wraps it in a check that compares the index with the container’s
`length` and throws the same TypeError. The corpus program
`out_of_bounds.js` tests exactly that. Literal initializers get a capacity
too: `const ps = [{...}, {...}]` becomes `__Vsc_ps.of(...)`, which starts
at the number of records, or 16 if that is larger.
</Callout>

## What you learned

- A collection has a **capacity** (slots allocated) and a **length**
  (slots used). Spare slots are real memory, full of zeros, so bounds
  checks must compare with length.
- Viscosity’s container grows by **doubling** `cap` and copying each
  typed column with `set()`. Plain array columns grow by themselves.
- **Amortized growth**: with doubling, n pushes copy fewer than 2n values
  in total, so a push is cheap on average. Growing by a constant is
  quadratic.
- The `construct` benchmark shows filling columns beats allocating
  objects; it doesn’t measure growth, because its sizes are known.
