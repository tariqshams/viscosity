## Eighty lines

The last chapter described tokens. Now for the program that makes them.
In the companion code it is a single function, `scan`, in
`companion/ts/src/scanner.ts`: about eighty lines that take a string and
return an array of tokens.

```ts
function scan(
  source: string,
  reporter: Reporter,
): Token[]
```

The `reporter` is where it sends error messages. Everything else
happens inside. You met a small version of this loop in chapter 10. This
is the real thing.

<Callout kind="intuition">
Run two fingers along a line of text. Your left finger marks where the
current word began. Your right finger slides forward, letter by letter,
until the word ends. Everything between your fingers is the word. Write
it down, move your left finger up to your right one, and start again.
</Callout>

## The state and the helpers

The two fingers are two numbers. There is also a line counter, for the
source location:

```ts
let start = 0;   // where this token began
let current = 0; // the next char to read
let line = 1;
```

Around them sit a few tiny helper functions. They are closures, from
chapter 6: arrow functions declared inside `scan`, so they can all see
`source`, `start` and `current`. Here are the first three:

```ts
const atEnd = () =>
  current >= source.length;
const advance = () => source[current++];
const peek = () =>
  atEnd() ? '\0' : source[current];
```

`advance` reads a character *and* moves `current` past it. `peek` only
looks. At the end of the source it returns `'\0'`, a stand-in character
that none of the scanner's checks will match, so callers never have to
deal with `undefined`. When a token is complete, `add` cuts its lexeme out of the
source with `slice`, from `start` up to (not including) `current`:

```ts
const add = (type, literal = null) => {
  tokens.push({
    type,
    lexeme: source.slice(start, current),
    literal,
    line,
  });
};
```

(The real `add` also has type annotations. Here and below, the code is
simplified from `scanner.ts` to fit your screen.)

<Callout kind="definition">
A **scanner** (also called a *lexer*) is the first stage of a front end.
It reads source text character by character and produces a list of
tokens. Drip's keeps two indexes into the text: `start`, the first
character of the token being built, and `current`, the next character to
read.
</Callout>

## The loop

Every round of the loop makes at most one token. It moves `start` up to
`current`, reads one character, and lets a `switch` decide what that
character begins. Step through it on a short line:

<ScanLoopSteps client:visible />

The real loop has the same shape, with a case for every kind of
character:

```ts
while (!atEnd()) {
  start = current;
  const c = advance();
  switch (c) {
    case '(': case ')': case '{':
    // … the other one-character tokens
      add(c);
      break;
    case ' ': case '\r': case '\t':
      break;
    case '\n':
      line++;
      break;
    // … more cases
  }
}
tokens.push({ type: 'eof', lexeme: '',
  literal: null, line });
```

Notice `add(c)`. Because a punctuation token's type is its own spelling
(chapter 27), the character `c` *is* the type. Whitespace cases do
nothing, and a newline only bumps `line`. Neither makes a token.

## Lookahead

Some characters can't be decided alone. A `<` might be the whole token,
or the first half of `<=`. The scanner has to glance at the next
character before it commits.

<Callout kind="intuition">
You're reading and reach the letters "for". Is that the word *for*, or
the start of *forest*? You glance at the next letter before you decide,
without moving on. Glancing is free, and it tells you how to read what
you already have.
</Callout>

`peek` is one way to glance. The other is `match`, which glances and
then consumes the character, but only if it is the one expected:

```ts
const match = (expected) => {
  if (atEnd()) return false;
  if (source[current] !== expected) {
    return false;
  }
  current++;
  return true;
};
```

With it, each of `!`, `=`, `<` and `>` takes one line of the `switch`:

```ts
case '<':
  add(match('=') ? '<=' : '<');
  break;
```

Comments use the same trick. A `/` followed by another `/` starts a
comment, which runs to the end of the line:

```ts
case '/':
  if (match('/')) {
    while (peek() !== '\n' && !atEnd()) {
      advance();
    }
  } else {
    add('/');
  }
  break;
```

The comment loop uses `peek`, not `advance`, to test for `'\n'`. That
leaves the newline unread, so the next round of the main loop handles it
in the `'\n'` case and `line` stays correct.

<Callout kind="definition">
**Lookahead** means examining characters after the current one without
consuming them. `peek()` looks one character ahead. `match(c)` looks
and consumes only on a match. Drip also has `peekNext()`, which looks
two ahead, for numbers like `1.5` (chapter 29).
</Callout>

## Always the biggest bite

When the scanner sees `<=`, it could make two tokens, `<` and `=`. It
doesn't: `match` grabs the `=` whenever it can. The same rule runs all
through the scanner. A run of digits is one number, not several. And
`orchid` is one identifier, not the keyword `or` followed by `chid`.

<Callout kind="intuition">
A hungry eater at a buffet takes the biggest portion that still fits on
the plate. The scanner does the same: at each point, it takes the
longest piece of text that still forms a valid token.
</Callout>

One of the Lox tests feeds the scanner `!===`. Taking the longest token
each time gives `!=` and then `==`, never `!` followed by `===` or
anything else. Try it below. This is a pocket-sized scanner written
just for this page, with the same habits:

<Callout kind="definition">
**Maximal munch** is the rule that a scanner always takes the longest
sequence of characters that forms a valid token, even when a shorter
token would also fit.
</Callout>

JavaScript's spec states the same rule in its own words: source text is
scanned left to right, "repeatedly taking the longest possible sequence
of code points as the next input element"<Cite id="ecma262" />. That is
why `a+++b` in JavaScript means `a++ + b`.

When the `switch` finds nothing that fits, the `default` case reports
"Unexpected character." through the reporter, with the current line,
and carries on. One run can report every bad character, instead of
stopping at the first.

<Callout kind="engine" label="Under the hood">
Drip's scanner never needs to know what the parser is doing. JavaScript's
can't be so independent. A `/` might be division or the start of a
regular expression like `/ab+/`, and the characters alone don't say
which. So the spec defines several starting rules for its lexical
grammar, and which one applies depends on where the parser is in the
syntax<Cite id="ecma262" />. Drip's VM in Part IV makes a different
change: its scanner hands out one token at a time, when the compiler
asks, instead of building the whole list first (see
`companion/ts/src/vm/scanner.ts`). Both follow the same two-pointer
design as Lox's scanners<Cite id="nystrom2021" />.
</Callout>

## What you learned

- A **scanner** turns characters into tokens. Drip's keeps two
  pointers: `start`, where the token began, and `current`, the next
  character to read. Each token's lexeme is `source.slice(start, current)`.
- The main loop reads one character, and a `switch` decides what it
  begins. Whitespace and comments make no tokens, and `'\n'` bumps the
  line count.
- **Lookahead**: `peek` looks without consuming, and `match` consumes
  only when the next character is the expected one.
- **Maximal munch**: always take the longest token that fits, so `<=`
  is one token and `orchid` is one identifier.
