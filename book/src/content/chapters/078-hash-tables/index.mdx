## Finding a name without searching

From here on the VM looks things up by name all the time: globals,
fields, methods. Keep 500 globals in a plain list of `[name, value]`
pairs, and every `print total;` compares `"total"` with up to 500 names
before it prints anything. The tree-walker used a JavaScript `Map`; the
VM builds its own, in `vm/table.ts`, so you can see what a `Map` does
inside (and so the garbage collector, in *Reclaiming memory*, can walk
it and remove entries itself).

*Hashing: finding without searching* gave the picture: pigeonholes,
where the key itself says which hole to look in. That takes a way to
turn a key into a number and an array the number points into; this
chapter builds both, and the next handles two keys wanting one hole.

## A hash function

<Analogy title="a smoothie blender">
Put strawberries and a banana in, and you get a smoothie of one exact
colour; put the same fruit in again and you get the same colour again.
Swap the banana for a pear and the colour changes completely, and nobody
can look at the smoothie and tell you which fruit went in.
<span slot="breaks">A blender's result wobbles with how long you run it;
a hash function gives exactly the same number every time, on every
computer. Also, two different mixes can, rarely, come out the same; we
will meet that as a collision.</span>
</Analogy>

The companion VM uses **FNV-1a**, a hash named after Glenn Fowler,
Landon Curt Noll and Phong Vo, which is short, fast and spreads keys
well<Cite id="lcn2-fnv" />. Here it is from `vm/object.ts` (one line
break added to fit the page):

```ts
export function hashString(
  s: string): number {
  let h = 2166136261;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return h >>> 0;
}
```

`h` starts at a fixed number, the **offset basis** (`0x811c9dc5`).
Then, for each character, `h ^= s.charCodeAt(i)` mixes the character's
code into `h` with XOR (the bit operation from *Bits and bytes*), and
the next line multiplies by the **FNV prime**, `16777619`
(`0x01000193`), keeping only the low 32 bits; those are the values in
the reference code<Cite id="lcn2-fnv" />. Step through it for `"vx"`:

<FnvSteps client:visible />

Two JavaScript details matter, and both are easy to get wrong:

- **`Math.imul`, not `*`.** `h * 16777619` is an ordinary JavaScript
  multiply on doubles, and the product can be far past 2<sup>53</sup>,
  where doubles stop holding every whole number, so its low bits are
  rounded away. `Math.imul` multiplies as 32-bit integers and wraps
  round exactly, the way C does<Cite id="mdn-math-imul" />.
- **`>>> 0` at the end.** XOR and `Math.imul` give *signed* 32-bit
  results, which may be negative; `>>> 0` reads the same 32 bits as a
  number that never is<Cite id="mdn-unsigned-right-shift" />.

Here is the first mistake, caught on the one-letter key `"x"`:

```js
let h = 2166136261 ^ 120; // ^ 'x'
(h >>> 0) * 16777619 % 2 ** 32;
// 4245442696   wrong: off by one
Math.imul(h, 16777619) >>> 0;
// 4245442695   right
```

Line 1 XORs in the only character, `x` (code 120). Line 2 multiplies
with `*` and keeps 32 bits with `% 2 ** 32`, but the true product had
more digits than a double holds, so the last was rounded: one too big.
Line 4 is right. (The reference code hashes bytes; this one hashes the
UTF-16 code units of *Strings up close*, the same for ASCII names.)

<Callout kind="definition">
A **hash function** turns a key into a number, its **hash**. It must be
**deterministic**: equal keys always give equal hashes. A good one also
spreads different keys evenly over its range, so similar keys do not
bunch up. The companion VM hashes each string once, when the string
object is made, and keeps the result in the object's `hash` field.
</Callout>

<Formal title="FNV-1a, one character at a time">

```text
h₀     = 2166136261
hᵢ₊₁   = ((hᵢ ⊕ cᵢ) × 16777619) mod 2³²
hash(s) = hₙ      where n = length of s
s = t  ⟹  hash(s) = hash(t)
```

<span slot="read">Start from the offset basis. For each character code
c, XOR it in (the circled plus), multiply by the prime, and keep the
remainder after dividing by 2 to the 32, which is the low 32 bits. The
hash is the value after the last character. The last line is the rule
every hash function obeys: if two keys are equal, their hashes are
equal. It does not run backwards: equal hashes do not prove equal
keys.</span>
</Formal>

<Examples of="hash-function">

```js
hashString('x'); // 4245442695
```

```js
hashString('health'); // 1805184399
hashString('healti'); // 1788406780
```

</Examples>

## From a hash to a slot

An 8-slot table needs a number from 0 to 7, not one in the billions.
The companion keeps its capacity a power of two, so keeping the low
bits does it in one cheap step: `hash & 7` keeps the last three
bits<Cite id="mdn-bitwise-and" />, and `"x"`, whose hash ends in binary
`111`, goes to slot 7 (with 16 slots, `hash & 15`).

With more possible names than slots, two keys will sooner or later
want one slot (nine names in eight slots guarantee it). That is a
**collision**; a hash function can make it rare, never impossible.

<Analogy extra title="a post room with numbered trays">
A post room sorts letters into ten trays by a rule worked out from the
address, say the last digit of the house number. To find a letter for
number 37 you go straight to tray 7 and never look in the other nine.
<span slot="breaks">A tray can hold many letters; a slot in this table
holds one key, so when two keys want the same slot one of them must go
somewhere else, and the next chapter decides where.</span>
</Analogy>

first collision:

<Callout kind="definition">
A **hash table** is an array indexed by hashes: a key's hash, reduced
to the array's size (`hash & (capacity − 1)` here), says which slot to
look in, so finding a key takes about the same time however many keys
there are. Two keys that reduce to the same slot are a **collision**,
and every hash table needs a rule for them.
</Callout>

<Formal title="Which slot a key starts in">

```text
m = 2ᵇ          (the capacity)
slot(k) = hash(k) mod m
        = hash(k) & (m − 1)
```

<span slot="read">When the capacity m is 2 to the power b, the slot is
the remainder of the hash divided by m, and that is the same as keeping
its low b bits with AND m minus 1. For m = 8, that is AND 7.</span>
</Formal>

## The VM's table: two arrays

Here is the start of the `Table` class in `vm/table.ts`, and its `get`
(line breaks added to fit the page):

```ts
export class Table {
  count = 0; // live entries + tombstones
  keys: (ObjString | null)[] = [];
  values: Value[] = [];

  get(key: ObjString): Value | undefined {
    if (this.count === 0) return undefined;
    const i = Table.find(
      this.keys, this.values, key);
    return this.keys[i] === null
      ? undefined : this.values[i];
  }
```

Keys are string objects (`ObjString`) carrying their hash, so a lookup
never hashes again. `get` asks `find` for the slot
where the key *is* or *would be*; an empty slot means `undefined`, the
VM's "not here" (no Drip value is ever `undefined`), and otherwise the
answer is the value at the same position of the other array. With no
collisions `find` is only `key.hash & mask`; the next chapter writes the
rest, and explains the tombstones in the comment.

The table is two parallel arrays, `keys[]` and `values[]`, rather than
one array of `{ key, value }` objects: the struct of arrays from *AoS vs
SoA, measured*, inside the VM. With entry objects (the first version),
every slot was a heap object that a lookup followed a pointer to before
it could read the key. The comment in `table.ts` says the switch made
object-heavy programs measurably faster; the commit records no number.

<Examples of="hash-table">

```js
// set("x", 10), empty 8-slot table
keys[7] = 'x'; values[7] = 10;
```

```js
// get("z"): hash & 7 is 5, and
keys[5] === null // so: undefined
```


The first is a whole insert: `"x"` hashes to slot 7, so the key goes in
`keys[7]` and its value in `values[7]`. The second is a miss: slot 5,
where `"z"` would live, is empty, so one look says `z` is absent. The
third is real: the VM defines five native functions before your program
starts, leaving its globals table like this (a dot is an empty slot). `clock`, `len` and `pop` sit where their hashes say;
however, `push` wanted slot 5, which `clock` already had, and `str`
wanted slot 0, which `pop` had, so each moved one slot along: that is
the collision rule of the next chapter, already at work.

## What you learned

- A **hash function** turns a key into a number, and equal keys always
  get equal hashes. **FNV-1a** XORs in each character and multiplies by
  a prime; in JavaScript that needs `Math.imul` and a final `>>> 0`.
- `hash & (capacity − 1)` picks a slot, for a power-of-two capacity.
- A **hash table** goes straight to that slot instead of searching. Two
  keys wanting one slot is a **collision**, and cannot be avoided.
- The VM's `Table` keeps keys and values in two parallel arrays, so no
  entry object is allocated or followed per slot.

## Two keys, one slot

The last chapter ended on a collision: `"x"` is in slot 7, and
`"health"` hashes to slot 7 too. One fix hangs a little list off every
slot; the companion's `Table` does not, since a list per slot is one
more heap object to allocate and follow. Instead every entry lives in
the array itself, and a key whose slot is taken moves along.

<Analogy title="a car park with no reserved bays">
Your ticket says bay 7. If bay 7 is taken, you try bay 8, then 9,
wrapping round to bay 0 at the end of the row, until you find a free
one. Coming back later, you walk the same route from bay 7 and stop at
your car.
<span slot="breaks">A driver can see the whole row and pick any gap; the
table only ever looks at one slot at a time, in a fixed order, and a
lookup knows to give up when it reaches a bay that has never been
used.</span>
</Analogy>

## Linear probing

Lookups and inserts share one function, `Table.find`, which returns the
slot where the key *is*, or where it *should go* (from `vm/table.ts`,
with line breaks added to fit the page):

```ts
private static find(
  keys: (ObjString | null)[],
  values: Value[],
  key: ObjString): number {
  const mask = keys.length - 1;
  let index = key.hash & mask;
  let tombstone = -1;
  for (;;) {
    const k = keys[index];
    if (k === null) {
      if (values[index] === null)
        return tombstone !== -1
          ? tombstone : index;
      if (tombstone === -1)
        tombstone = index;
    } else if (k === key) {
      return index;
    }
    index = (index + 1) & mask;
  }
}
```

The first lines pick the starting slot, `hash & mask`, and `for (;;)`
loops until a `return`. A slot holding another key falls through to the
last line, which steps on (`& mask` wraps 8 back to 0); a slot holding
*our* key ends the search. A slot with no key is either truly empty
(value `null`), so our key is absent and we return where it should go,
or a **tombstone** (value `true`), which we remember and step past, for
reasons the next section explains.

Notice `k === key`: keys are compared as objects, not by their
characters. That is only right because equal strings are always the
same object in this VM, which is the job of *String interning*.

## Deleting without breaking the path

`health` sits in slot 2 *because* slots 7, 0 and 1 were full when it
arrived. Empty slot 1 by deleting `mass`, and a lookup for `health`
would stop there and report it missing. So `delete` leaves a marker
instead:

```ts
delete(key: ObjString): boolean {
  if (this.count === 0) return false;
  const i = Table.find(
    this.keys, this.values, key);
  if (this.keys[i] === null) return false;
  this.keys[i] = null;
  this.values[i] = TOMBSTONE;
  return true;
}
```

`TOMBSTONE` is the constant `true`. If `find` lands on a slot with no
key, there is nothing to delete; otherwise the key is cleared and the
value set to `true`: "something was here, keep going".
An insert of a new key reuses the *first* tombstone it passed, which is
why `find` remembers it; it cannot stop at the tombstone itself, because
only reaching a truly empty slot proves the key is not further along.

<Analogy extra title="a demolished house">
You find a friend's house by walking down the street from a number
worked out from their name. If one house on the way is knocked down
and the plot left bare, you might think the street ends there and turn
back; so the council puts up a sign on the plot: "a house was here,
keep walking".
<span slot="breaks">A real sign can be read from the pavement; the
table has to step onto the tombstone to see it. And the table can build
a new house on the plot, which is what reusing a tombstone does.</span>
</Analogy>

<Callout kind="definition">
With **open addressing**, every entry lives in the table's array itself;
a key whose slot is taken goes to another slot found by **probing**.
**Linear probing** tries the next slot, then the next, wrapping round. A
lookup stops at the key or at a truly empty slot. A deleted entry
becomes a **tombstone**, which probes step past, so keys stored beyond
it stay findable, and which an insert may reuse.
</Callout>

<Formal title="The probe sequence">

```text
pᵢ(k) = (slot(k) + i) mod m,  i = 0, 1, 2, …
stop at the first i where
  keys[pᵢ] = k            (found)
  or slot pᵢ is empty     (absent)
```

<span slot="read">The i-th slot tried for key k is its starting slot
plus i, wrapped round the capacity m. A lookup tries i = 0, then 1, then
2, and stops at the first slot that holds k or is truly empty;
tombstones are neither, so it goes on past them.</span>
</Formal>

<Examples of="open-addressing">

```js

// set("health"): 7 (x), 0 (vy),
// 1 (mass), then 2 is free
```

```js

// 7, 0, 1 (tombstone: go on), 2: found
```

## How full is too full?

Probing is quick while most slots are empty and slow when they are not,
and if no slot were ever truly empty, `find` would loop for ever. So `set` checks
the load *before* it does anything else:

```ts
set(key: ObjString, value: Value): boolean {
  if (this.count + 1 >
      this.keys.length * MAX_LOAD) {
    this.grow(this.keys.length < 8
      ? 8 : this.keys.length * 2);
  }
  const i = Table.find(
    this.keys, this.values, key);
  const isNew = this.keys[i] === null;
  if (isNew && this.values[i] === null)
    this.count++;
  this.keys[i] = key;
  this.values[i] = value;
  return isNew;
}
```

`MAX_LOAD` is `0.75`, and `count` counts live entries *and* tombstones,
since a tombstone fills a slot as far as probing is concerned; only
filling a truly empty slot adds to it. A new table has no slots at all,
so the very first `set` grows it to 8; after that it doubles. Because
the check comes before `find`, a `set` that would only overwrite an
existing key, or reuse a tombstone, can still trigger growth.

`grow` makes two new arrays of the new capacity, sets `count` to 0,
and walks the old `keys`: a slot with no key is skipped (`continue`),
and every live key is put through `find` on the *new* arrays and
stored there with its value, adding 1 to `count`. It cannot copy the
old arrays across, because the mask changes from 7 to 15 and every
key's starting slot may change; and since tombstones have no key,
growing also cleans the table up.

<Analogy extra title="a car park that closes at 75 per cent">
A car park puts up its FULL sign while a quarter of the bays are still
free, because the last few free bays take far longer to find than all

<span slot="breaks">A real car park cannot double in size overnight; the

<Callout kind="definition">
The **load factor** of a table is how full it is: occupied slots divided
by capacity. The companion table counts live entries and tombstones,
and before an insert that would take it past **0.75** it doubles its
capacity and re-inserts every live key. A lower limit wastes memory; a
higher one makes probe paths long.
</Callout>

<Formal title="When the table grows">

```text
α = count / capacity
grow first if count + 1 > ¾ × capacity
```

<span slot="read">The load factor, alpha, is count divided by capacity.
Before every set, if one more entry would push it above three quarters,
the table grows first.</span>
</Formal>

## What you learned

- **Open addressing** keeps every entry in the array. **Linear probing**
  steps to the next slot, wrapping with `& mask`, until it finds the key
  or a truly empty slot.
- `delete` leaves a **tombstone**, so probe paths stay unbroken; an
  insert reuses the first tombstone it passed.
- The **load factor** is count over capacity, tombstones included; the
  table doubles before it would pass 0.75, and re-inserts every live
  key, because the mask, and so every starting slot, changes.
