## Finding a name without searching

From here on the VM looks things up by name all the time: globals,
fields, methods. Keep 500 globals in a list of `[name, value]` pairs,
and every `print total;` compares `"total"` with up to 500 names. The
tree-walker used a JavaScript `Map`; the VM builds its own, in
`vm/table.ts`, so you can see what a `Map` does inside (and so the
garbage collector can walk it). *Hashing: finding without searching*
gave the picture: the key itself says where to look.

<Analogy title="a car park with numbered bays">
Your ticket is worked out from your number plate, and it says bay 7.
If bay 7 is taken, you try bay 8, then 9, wrapping round to bay 0 at
the end of the row, until you find a free one. Coming back later, you
work out the same bay from the same plate, walk the same route from
bay 7, and stop at your car.
<span slot="breaks">A driver can see the whole row and pick any gap; the
table only ever looks at one bay at a time, in a fixed order, and a
lookup knows to give up when it reaches a bay that has never been
used.</span>
</Analogy>

## A hash function

The companion VM uses **FNV-1a**, a hash named after Glenn Fowler,
Landon Curt Noll and Phong Vo, which is short, fast and spreads keys
well<Cite id="lcn2-fnv" />. Here it is from `vm/object.ts`:

```ts
export function hashString(
  s: string): number {
  let h = 2166136261;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 16777619);
  }
  return h >>> 0;
}
```

`h` starts at a fixed number, the offset basis; for each character it
XORs in the character's code, then multiplies by the FNV prime, keeping
the low 32 bits<Cite id="lcn2-fnv" />. `h * 16777619` would multiply
doubles, and a product past 2<sup>53</sup> loses its low bits, while
`Math.imul` multiplies as 32-bit integers and wraps round exactly<Cite id="mdn-math-imul" />;
`>>> 0` reads the signed result as a number that is never
negative<Cite id="mdn-unsigned-right-shift" />.

<FnvSteps client:visible />

<Callout kind="definition">
A **hash function** turns a key into a number, its **hash**. It must be
**deterministic**: equal keys always give equal hashes. A good one also
spreads different keys evenly over its range, so similar keys do not
bunch up. The companion VM hashes each string once, when the string
object is made, and keeps the result in the object's `hash` field.
</Callout>

<Examples of="hash-function">

```js
hashString('health'); // 1805184399
hashString('healti'); // 1788406780
```

</Examples>

The keys differ only in their last letter, yet the hashes differ from
the second digit on: the multiply spreads the change of the last XOR
through the whole number.

<More title="Formal FNV-1a, the rounding trap, and a runnable hash">

```text
h₀     = 2166136261
hᵢ₊₁   = ((hᵢ ⊕ cᵢ) × 16777619) mod 2³²
hash(s) = hₙ      where n = length of s
```

Start from the offset basis; for each character code c, XOR it in (the
circled plus), multiply by the prime, and keep the remainder after
dividing by 2 to the 32. Here is the `*` mistake, caught on the
one-letter key `"x"` (code 120):

```js
let h = 2166136261 ^ 120;
(h >>> 0) * 16777619 % 2 ** 32;
// 4245442696   wrong: off by one
Math.imul(h, 16777619) >>> 0;
// 4245442695   right
```

The true product had more digits than a double holds, so the last was
rounded. (The reference code hashes bytes; this one hashes UTF-16 code
units, the same for ASCII names.) The runnable one hashes the six

## From a hash to a slot

An 8-slot table needs a number from 0 to 7, not one in the billions.
The companion keeps its capacity a power of two, so `hash & 7` keeps the
last three bits<Cite id="mdn-bitwise-and" />, and `"x"`, whose hash ends
in binary `111`, goes to slot 7 (with 16 slots, `hash & 15`). With more
possible names than slots, two keys will sooner or later want one slot:
a **collision**, which a hash function can make rare, never impossible.

<PlaceSteps client:visible />

<Callout kind="definition">
A **hash table** is an array indexed by hashes: a key's hash, reduced
to the array's size (`hash & (capacity − 1)` here), says which slot to
look in, so finding a key takes about the same time however many keys
there are. Two keys that reduce to the same slot are a **collision**,
and every hash table needs a rule for them.
</Callout>

The companion's `Table` is two parallel arrays, `keys` (string objects,
which carry their hash) and `values`, rather than an array of
`{ key, value }` objects: the struct of arrays from *AoS vs SoA,
measured*, saving one heap object per slot.

<Examples of="hash-table">

```text
slot:  0   1   2 3 4   5     6    7
keys:  pop str . . len clock push .
```

</Examples>

This is the real globals table of a fresh companion VM, holding its
five native functions (a dot is an empty slot). `pop`, `len` and
`clock` sit where `hash & 7` says; `push` wanted slot 5, which `clock`
had, and `str` wanted slot 0, which `pop` had, so each moved one slot
along: the collision rule, already at work.

## Open addressing: moving along

Rather than hang a little list off every slot (one more heap object to
follow), the companion keeps every entry in the array itself, and a key
whose slot is taken moves along, like the car park. Lookups and inserts
share `Table.find`, which returns the slot where the key *is*, or where
it *should go*:

```ts
const mask = keys.length - 1;
let index = key.hash & mask;
let tombstone = -1;
for (;;) {
  const k = keys[index];
  if (k === null) {
    if (values[index] === null)
      return tombstone !== -1
        ? tombstone : index;
    if (tombstone === -1)
      tombstone = index;
  } else if (k === key) {
    return index;
  }
  index = (index + 1) & mask;
}
```

A slot holding another key steps on (`& mask` wraps 8 back to 0); a
slot holding *our* key ends the search (`k === key` compares objects,
which works because *String interning and globals by name* makes equal
strings one object). A slot with no key is either truly empty (value
`null`), so the key is absent, or a **tombstone** (value `true`), left
by `delete` to say "something was here, keep going", since a key that
probed past that slot would otherwise be lost. An insert reuses the
first tombstone it passed, once an empty slot proves the key is new.

<ProbeSteps client:visible />

<Callout kind="definition">
With **open addressing**, every entry lives in the table's array itself;
a key whose slot is taken goes to another slot found by **probing**.
**Linear probing** tries the next slot, then the next, wrapping round. A
lookup stops at the key or at a truly empty slot. A deleted entry
becomes a **tombstone**, which probes step past, so keys stored beyond
it stay findable, and which an insert may reuse.
</Callout>

<Examples of="open-addressing">

```text
keys: vy mass . . y . . x
set("health"): tries 7, 0, 1, puts 2
delete("mass"), get("health"):
  7, 0, 1 (tombstone, go on), 2 found
```

</Examples>

`health` hashes to slot 7, which `x` holds, so the insert tries 0 and 1
and lands in 2. After deleting `mass`, the lookup walks past the
tombstone in slot 1 to reach `health`; an empty slot 1 would have
stopped it.

## How full is too full?

Probing is quick while most slots are empty, slow when they are not,
and endless if none is. So `set` checks the load first; `MAX_LOAD` is
`0.75`, and `count` includes tombstones, which fill slots as far as
probing is concerned.

```ts
if (this.count + 1 >
    this.keys.length * MAX_LOAD) {
  this.grow(this.keys.length < 8
    ? 8 : this.keys.length * 2);
}
```

A new table has no slots, so the first `set` grows it to 8; after that
it doubles. `grow` puts every live key through `find` on two new
arrays; copying would be wrong, because the mask changes from 7 to 15
and so may every key's starting slot (and dropping tombstones cleans
the table up).

</Figure>

<Callout kind="definition">
The **load factor** of a table is how full it is: occupied slots divided
by capacity. The companion table counts live entries and tombstones,
and before an insert that would take it past **0.75** it doubles its
capacity and re-inserts every live key. A lower limit wastes memory; a
higher one makes probe paths long.
</Callout>

<Examples of="load-factor">

```text
globals: 5 natives in 8 slots
let a = 1;   6 of 8: 6 ≤ 6, fits
a = 2;       7 > 6: grows to 16
```

</Examples>

On a fresh VM, the first `let` makes six entries in eight slots, which
is exactly the limit of 6. The assignment then grows the table although
`a` is already in it: the load check runs before `find`, so it does not
yet know the key is old.

<More title="How CPython's dict does it">

CPython's `dict` is an open-addressing table too, and the comments in
its source spell out the same ideas. A deleted entry becomes a *dummy*
slot, which can never become unused again, or the probe paths would
lose their way. The table is resized when it is two-thirds full. And it
does not probe linearly: each next slot mixes in higher bits of the
hash, so keys whose low bits agree spread
apart<Cite id="cpython-dictobject" />.

</More>

## What you learned

- A **hash function** turns a key into a number, equal keys always
  getting equal hashes; a **hash table** reduces it to a slot.
- **Open addressing** keeps entries in the array and probes past taken
  slots and tombstones; the **load factor** limit makes it grow.
