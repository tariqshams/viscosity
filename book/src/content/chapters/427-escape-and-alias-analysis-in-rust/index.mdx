## A refusal, pointed at

A value **escapes** (in the sense of *Escape analysis*) when it reaches a
place the compiler cannot follow, and two names are **aliases** when they
reach the same object (see *Alias analysis*); either way, rewriting the
array into columns would break whoever holds the other name. Here is a
program that does three such things with elements of `ps`:

```js
const ps = [];
for (let i = 0; i < 99; i++)
  ps.push({ x: i });
const box = {};
box.k = ps[1];
ps[2][0] = 5;
const t = [];
t[ps[3]] = 1;
```

`viscosity explain` gives three refusals for `ps` (real Rust CLI output,
wrapped):

```
  · unsafe: line 8: an element is used
    as an index
  · unsafe: line 6: an element is
    written with an index store
  · unsafe: line 5: an element is
    stored into an object property
```

Lines 6 and 8 are both the same VIR instruction, `index.set` (store into
`a[i]`), and yet one reason says "written with an index store" and the
other "used as an index". The difference is *which operand* the element
is: in `ps[2][0] = 5` it is the thing being indexed, and in `t[ps[3]] = 1`
it is the index. (With `explain --frames`, an option in both engines'
CLIs, each refusal also shows its source line with carets under the code;
there is one below.)

## describe_use asks "which operand?" first

<Analogy title="a name in a photo caption">
"Ana is in this photo" could mean Ana took it or Ana is standing in it;
knowing the photo exists is not enough, you need to know her place in it.
`describe_use` asks the same of a value and an instruction.
<span slot="breaks">A photo has a handful of roles; an instruction's
operands are numbered, and the function has to check each position that
matters by its number.</span>
</Analogy>

The function takes a use *and* the value being described, and its first
`match` handles only the cases where the operand matters. Trimmed from
`analysis.rs` and rewrapped:

```rust
let i = match u {
    Use::Term { func, .. } => return
        format!("returned or branched \
            on in {}()", /* name */),
    Use::Inst(i) => self.inst(i),
};
match &i.op {
    Op::FieldSet { field }
        if i.args[0] == v => return
        format!("modified directly (its \
            .{field} is assigned) ..."),
    Op::IndexSet if i.args[0] == v =>
        return format!("written with an \
            index store at line {line}"),
    Op::IndexSet | Op::IndexGet
        if i.args[1] == v => return
        format!("used as an index ..."),
    _ => {}
}
// ...then a match by kind of instruction
```

A **use** is either an instruction that takes the value as an operand, or
a block's **terminator** (its last step: a branch, a `return` or a
`throw`). For a terminator there is one sentence, "returned or branched on
in f()". For an instruction, the guards (`if i.args[0] == v`) pick the
operand-specific case: `args[0]` is the object or array, `args[1]` the
index. Only if none matches does the second `match` describe the
instruction in general: a `field.set` where the value is not the object
is "stored into an object property", a store to a variable is "stored in
another variable (e)", and so on, down to "used by code Viscosity doesn't
model (...)" for anything opaque. (The TypeScript version takes `v` as
optional; in Rust it is always given.)

## What may be done, and nothing else

</Figure>

`element_uses` walks every use of every element (every `index.get` of the
collection). A `field.get` or `field.set` with the element as operand 0,
on a field the records have, is recorded as an access; anything else is an
escape. The message starts with the element's own line, so a repeat of
that line at the end is cut off, trimmed:

```rust
let why = self.describe_use(u, ig.inst);
let why = [" at line ", " near line "]
    .iter()
    .find_map(|p| why.strip_suffix(
        &format!("{p}{line}")))
    .unwrap_or(&why);
```

`find_map` tries each ending in turn and returns the first `strip_suffix`
that succeeds (`Some` text without it); if neither ends the sentence with
*this* line, `unwrap_or` keeps the sentence whole. The reference does it
with a regular expression, `/ (?:at|near) line N$/`; two `strip_suffix`
calls match the same strings without a regex crate.

<Callout kind="definition">
**The escape and alias passes in Rust** are the use checks of
`analysis.rs`. The array may only be read for `.length`, pushed fresh
records, indexed, or passed to a known function (followed into the
parameter). Each element may only have its fields read or written. Any
other use is a bailout, whose reason, from `describe_use`, depends on the
instruction and on which operand the value is, with the source site kept
for `--frames`.
</Callout>

<Formal title="The escape check">

```text
Arr  = {.length, push(fresh), [i],
        known call}
Elem = {.f read, .f = v}  (f a field)
safe(c) ⟺ ∀u ∈ uses(c): u ∈ Arr
       ∧ ∀e ∈ elems(c), ∀u ∈ uses(e):
           u ∈ Elem
```

<span slot="read">A collection c is safe to rewrite exactly when every use
of the array is one of the allowed array uses, and every use of every
element read from it is a read or write of one of the records' fields.
Nothing else is allowed, so there is no need to know where an escaping
value ends up.</span>
</Formal>

## Into known functions, and not elements

The collection pass follows the array into a **known function**'s
parameter (see *Collection discovery in Rust*), and the uses inside are
then checked like any others, so an element that leaves the function is
caught there; however, an *element* passed to a function is never
followed.

<Examples of="rust-escape-pass">

```
· unsafe: line 4: an element is passed
  to a function call
```

```
· unsafe: line 3: an element is stored
  in another variable (e)
```

```
· unsafe: line 5: an element is
  returned or branched on in step()
  5 |   return qs[0];
    |          ^^^^^
```

</Examples>

All three are real Rust CLI output, wrapped. The first is
`function bump(e) { e.x += 1; }` called as `bump(ps[0])`: following an
element would mean proving the callee only touches its fields, and
nothing in the pass does that, so the call itself is the escape. The
second is `const e = ps[0]; const f = () => e;`: a closure that captures
`e` turns it into a variable stored in memory (a binding with `load` and
`store`), a second home for the element. The third is a known function
`step(qs)` that updates `qs[i].y` in a loop and then `return qs[0]`,
shown with `--frames`: the array is followed into `step`, so the return
inside is caught, with carets under the element. Delete the `return` and
`ps` becomes a struct of arrays; add a second call `step([])`, and the
function is no longer called only with `ps`, so `ps` is refused with
"passed to step(), which is also called with other values".

## Aliases without points-to sets

<Analogy title="a library that lends only to named members">
A small library lends a book only to the member whose card is stamped;
if that member passes the book on to a friend, the library does not try
to track the friend, it simply stops lending that book.
<span slot="breaks">A real library could phone round and find the book.
Viscosity never tries: any second home for an element is a refusal, which
is safe and simple but turns away some programs that would have been
fine.</span>
</Analogy>

Viscosity keeps no **points-to sets** (lists of which objects each name
may reach, as the chapter *Alias analysis* describes). It needs none,
because SSA already says when two names are one value: in
`const e = ps[0]; e.x += 1;` the name `e` *is* the `index.get`, so its
field access is fine. Anything else that gives an element a second name
is refused, and a **phi** is the other way to get one. Here, after the
same three lines that build `ps`:

```js
let p = ps[0];
if (ps.length > 9) p = ps[9];
console.log(p.x);
```

Both elements reach `p` through a phi at the join, and a phi is a merge
the pass cannot see through, so both are refused (wrapped):

```
· unsafe: line 5: an element is merged
  with other values (a variable
  reassigned along different paths)
· unsafe: line 4: ... (as above) ...
  near line 5
```

A phi has no source position of its own, so `line_of` gives it the latest
line among the values it merges, here 5. For the element read on line 5
that repeat is cut; for the one on line 4 it is new information, so
"near line 5" stays.

<Callout kind="engine" label="Under the hood">
Each bailout records its site the first time its message is seen: the
escaping value's own span when it is a load of the array's name,
otherwise the using instruction's span, and element messages point at
the element's `index.get`. The frame counts columns in characters (code
points), so the UTF-8 byte offsets of Rust and the UTF-16 offsets of
TypeScript put the carets in the same place. Fourteen `.frames.txt`
fixtures, and the fuzzer's comparison of both engines' `--frames` text,
keep it that way.
</Callout>

## What you learned

- **The escape and alias passes in Rust** allow only `.length`, fresh
  pushes, indexing and known calls on the array, and only field access on
  elements; everything else is a refusal.
- `describe_use` checks **which operand** the value is before the kind of
  instruction: `e.k = 1` modifies `e`, `box.k = e` aliases it.
- Arrays are followed into **known functions**; elements never are.
- There are no points-to sets: SSA gives one value one name, and **phis**
  and stores into other places are refused.
