## When the answer is up the tree

In C (and Java) you can declare several variables at once, `int a, b, c;`,
and every name gets the type written once at the front. Write a grammar
for it and try to give each name its type with the last chapter's
synthesized attributes, and you get stuck: the leaf for `c` has no
children to ask, and the type sits in a different branch, to the left.

```text
D → T L        L.in = T.type
T → int        T.type = integer
L → L₁ , id    L₁.in = L.in
               addType(id, L.in)
L → id         addType(id, L.in)
```

The fix is to let information flow the other way. `T.type` is
synthesized as before (from `int`); the rule for `D` then hands it to
its *other* child as `L.in`, and each list node passes `in` down to the
list inside it, telling each name its type on the way (`addType` writes
the name and its type into a table).

<Analogy title="a family name">
A baby does not choose her surname, and nothing about her own children
decides it: it comes down from her parents, and she passes it on in
turn.
<span slot="breaks">A surname is passed on unchanged; an inherited
attribute can be changed on the way down (one more level of depth, one
more pair of array brackets), and a node may inherit from a sibling
through its parent's rule, which surnames do not do.</span>
</Analogy>

<Callout kind="definition">
An **inherited attribute** is one whose value at a node is defined by
the rule of the node's *parent*, from attributes of the parent and of
the node's siblings. It carries information down (and across) the tree,
where a synthesized attribute carries it up<Cite id="knuth1968" />.
</Callout>

<Formal title="The shape of an inherited attribute">

```text
production   A → X₁ X₂ … Xₙ
rule         Xᵢ.h = f(A.h, X₁.a, …, Xᵢ₋₁.a)
```

<span slot="read">For a production where A is made of X1 up to Xn, the
inherited attribute h of the i-th part is a function of what A
inherited and of the attributes of the parts to its left. This is the
common, tidy case, called L-attributed: nothing comes from the right.</span>
</Formal>

<Examples of="inherited-attribute attribute-grammar">

```text
S → A        A.depth = 0
A → ( A₁ )   A₁.depth = A.depth + 1
```

```text
1101.01 in binary is 13.25:
each digit's scale comes down,
its value goes up
```

</Examples>

The first is the smallest inherited attribute there is: how deep a
node is, which only its ancestors can tell it. The second is Knuth's own
example from the 1968 paper that named both kinds of
attribute<Cite id="knuth1968" />: a digit's worth depends on its
*position*, and the position is known only above it, so each digit
inherits a scale (a power of two) while values are synthesized back up.
The runnable version shows the realistic shape in code: `L` gets
`scale` as a parameter (inherited) and returns a value (synthesized);
`1` at scale 3 is worth 8, and the fraction `01` starts at scale −2,
because it has two digits, so its `1` is worth a quarter. (Knuth's
grammar gets that −2 from a synthesized length: the two directions
feed each other.) You have met a third, everyday inherited attribute
already: the resolver of chapter 110 carries the current scope *down*
into every block it visits.

## Attribute grammars

<Analogy title="a sorting office">
A parcel goes to the regional office, which writes "north" on it; the
local office adds a street; the van driver adds a door number. Each stage
uses what was written before it, and the driver could not start until
the earlier labels were on.
<span slot="breaks">Parcels go one way; in a tree, a value can go down
to a node, be used there, and the result come back up, so the order is
worked out from the rules rather than fixed in advance.</span>
</Analogy>

<Callout kind="definition">
An **attribute grammar** is a context-free grammar in which every
symbol has a set of attributes, each one synthesized or inherited, and
every production has semantic rules that define the synthesized
attributes of its head and the inherited attributes of its body, using
only other attributes of the symbols in that production. The value of
an attribute at a node is whatever those rules force it to
be<Cite id="knuth1968" />.
</Callout>

Because each rule names the values it reads, the rules for one tree
draw a **dependency graph**: an arrow from each value to every value
computed from it. Any order that follows the arrows (a *topological
order*) works. If the arrows ever go round in a circle, no order exists
and the grammar is **circular**; Knuth's paper gave a test that finds
whether *any* tree of a grammar could have a circle (a correction to it
followed in 1971)<Cite id="knuth1968" />. Most real attribute grammars
avoid the question by staying L-attributed, which can be evaluated in
one depth-first pass, left to right; in a recursive-descent parser that
means inherited attributes are **parameters** and synthesized ones are
**return values**<Cite id="aho2006" />.

## Type and width, by hand

Here is a grammar for array types such as `int[2][3]`, and rules that
compute both the type and the width in bytes (an `int` takes 4 here):

```text
T → B C          C.b = B.t; C.bw = B.w
                 T.t = C.t; T.w = C.w
B → int          B.t = int; B.w = 4
C → [ num ] C₁   C₁.b = C.b; C₁.bw = C.bw
                 C.t = array(num, C₁.t)
                 C.w = num × C₁.w
C → ε            C.t = C.b; C.w = C.bw
```

`b` and `bw` (the base type and its width) are inherited: they go down
the chain of `C`s. `t` and `w` are synthesized: they come back up, one
array layer per pair of brackets. (`ε` means "nothing": `C` may also
be empty.) Step through it:

The answer, `array(2, array(3, int))` and 24 bytes, says `int[2][3]`
is two rows of three ints, which is how C lays it out in memory: the
width is what a compiler needs to reserve space and to compute where
`x[i][j]` lives.

## What you learned

- An **inherited attribute** is defined by the parent's rule, from the
  parent and the siblings: information flowing down.
- An **attribute grammar** gives every symbol attributes and every
  production rules; the dependency graph fixes the order, and a cycle
  means no order exists.
- L-attributed grammars run in one pass: inherited values are
  parameters, synthesized values are return values.
