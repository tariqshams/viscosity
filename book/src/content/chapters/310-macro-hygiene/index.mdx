## A swap that swaps nothing

The last chapter's macros pasted code into the program; here is one
that also needs a variable of its own. Swapping two variables needs a
spare place to hold one value, so a C programmer writes:

```c
#define SWAP(a, b) \
  { int tmp = a; a = b; b = tmp; }

int tmp = 1, y = 2;
SWAP(tmp, y);
printf("%d %d\n", tmp, y);  // 1 2
```

Every use with other names works. This one, compiled with gcc 13 and
run, prints `1 2`: nothing was swapped, and the compiler said nothing.
`gcc -E` shows why: the expansion is `{ int tmp = tmp; tmp = y; y =
tmp; }`, and inside those braces every `tmp`, including the one the
*caller* wrote, now means the macro's new variable. Step through it,
and then through the fix:

<CaptureSteps client:visible />

This is **variable capture**, and it comes in two directions. Above,
a variable the macro declares captures a name the caller passed in.
The other way round, a name the macro *uses* can be captured by a
variable the caller declared: a macro whose template calls a helper
`len()` breaks if it is used in a block where the caller has written
`let len = 5;`. In both cases the scoping rules of chapter 11 are
obeyed perfectly; it is the pasting that put a name in a scope its
author never saw.

<Analogy title="two people called Sam">
A visiting engineer leaves a note at reception: "give the keys to
Sam". The engineer meant their own colleague Sam, but the office has a
Sam too, and the receptionist, reading the note in the office, hands
the keys to the wrong one.
<span slot="breaks">A receptionist could ask; a compiler cannot. It
can only make sure each name carries a note of who wrote it, so that
the visitor's "Sam" and the office's "Sam" are never the same
person.</span>
</Analogy>

<Analogy title="a quotation in an essay">
When an essay quotes someone saying "I was there", the "I" means the
person quoted, not the essay's author; the quotation marks keep the
two apart.
<span slot="breaks">Quotation marks are visible to every reader; the
marks a hygienic expander adds are invisible in the printed expansion,
which can look exactly like the broken one (as rustc's output below
shows).</span>
</Analogy>

## Fresh names, by hand and by the expander

The traditional fix is to give the macro's variable a name the caller
cannot have written. Lisp programmers call a function `gensym` that
returns a brand-new symbol; C programmers pick an ugly name such as
`_swap_tmp_` and hope. That cures the first direction (the macro's
variable can no longer catch the caller's), but not the second: a
fresh name for a variable the macro *declares* does nothing for a
helper the macro *calls*, which still has to be found by its ordinary
name in the caller's scope.

A **hygienic** expander does both automatically. It records, for every
identifier, where it came from: the caller's code, or a particular use
of a particular macro. Two identifiers refer to the same variable only
if they have the same name *and* the same origin; in effect, every
variable the template declares is renamed to a fresh name for each
expansion, while names the template only uses are looked up where the
macro was written. The idea and the name come from Kohlbecker,
Friedman, Felleisen and Duba's 1986 paper "Hygienic Macro
Expansion"<Cite id="kohlbecker1986" />, written for Scheme.

<Callout kind="definition">
**Variable capture** happens when macro expansion makes a name refer
to a different binding than the one its author meant. A macro system
is **hygienic** if expansion never causes capture: a binding written
in a macro's template binds only names from that template (and from
that one expansion), and a name the template uses refers to what it
meant where the macro was defined. Expanders implement it by marking
every identifier with its origin, which amounts to renaming the
template's variables apart for each expansion.
</Callout>

<Formal title="Hygiene as renaming">

```text
swap!(a, b)
  ⇒ let t′ = a; a = b; b = t′;
     where t′ is fresh:
     t′ ∉ names(a) ∪ names(b) ∪ names(ctx)
```

<span slot="read">Expanding swap with arguments a and b produces the
template with its own variable renamed to t-prime, a name that does
not appear in either argument or anywhere in the surrounding code.
Because the new name is fresh, no name from the caller can be captured
by it. This is the same renaming that chapter 118's substitution needs
to avoid capture, applied to macro templates.</span>
</Formal>

<Examples of="hygiene">

```text
// C, gcc 13: no hygiene
SWAP(tmp, y)  ⇒  { int tmp = tmp;
                   tmp = y; y = tmp; }
// prints 1 2
```

```rust
macro_rules! swap {
    ($a:ident, $b:ident) => {
        let tmp = $a; $a = $b; $b = tmp;
    };
}
let mut tmp = 1;
let mut y = 2;
swap!(tmp, y);
println!("{} {}", tmp, y); // 2 1
```

```text
macro_rules! make_x {
    () => { let x = 1; };
}
make_x!();
println!("{}", x);
error[E0425]: cannot find value `x`
help: an identifier with the same name
  is defined here, but is not accessible
  due to macro hygiene
```

</Examples>

The first is the C version again: `gcc -E`'s expansion, which pastes
text with no marks at all. The second is the same swap in Rust, and it
prints `2 1`, even though `rustc -Zunpretty=expanded` prints its
expansion as `let tmp = tmp; tmp = y; y = tmp;`, letter for letter the
broken C one; only the hygiene view in the figure shows that the
macro's `tmp` carries mark 7 and the caller's mark 0. The third is the
other side of the same rule, and real rustc 1.97 output (trimmed): a
variable *declared* inside a macro cannot be used by the caller,
because the caller's `x` and the macro's `x` have different origins.
The Rust reference calls this **mixed-site hygiene**: local variables
and labels are looked up where the macro was defined, other names
(functions, types) where it is called<Cite id="rustref-macros-by-example" />,
so a macro that calls a helper function is not hygienic in the second
direction, a trade-off Rust chose on purpose.

<Run id="capture" />

The example rebuilds the problem with the tree templates of the last
chapter. `SWAP` is the swap template, with holes `a` and `b` and a
variable of its own, `tmp`; `fill` pastes the caller's names into the
holes; and `run` is an interpreter of three lines for `do` (run each
part), `let` and `set` (both store a value in `vars`, which is all the
variables there are, so `let` cannot even make a new scope here). The
first call swaps `x` and `y` and prints `{ x: 2, y: 1, tmp: 1 }`: it
works, though the macro's `tmp` is left lying around. The second call
passes the caller's own `tmp`, and prints `{ tmp: 2, y: 2 }`: the
template's `tmp` and the caller's are the same entry, so the old value
of `tmp` is overwritten before it is copied into `y`. Change the
template's two `'tmp'` strings to `'tmp_1'` and run it again: that is
renaming by hand, and the exercise does it automatically.

## What you learned

- **Variable capture** is a macro's name and a caller's name meeting by
  accident: a template's variable catching an argument, or a caller's
  variable catching a name the template uses.
- **Fresh names** (`gensym`) fix the first direction by hand.
- A **hygienic** expander marks every identifier with where it was
  written, which renames each expansion's variables apart; Rust's
  `macro_rules!` is hygienic for local variables and labels, and C's
  preprocessor not at all.
