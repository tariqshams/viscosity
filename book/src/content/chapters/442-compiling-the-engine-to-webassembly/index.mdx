## Once by hand, then every time

In the chapter *Rust and WebAssembly* you ran two commands, `cargo
build` for the `wasm32-unknown-unknown` target and `wasm-bindgen
--target nodejs`, and the Rust engine compiled JavaScript from inside
Node. That was enough to check parity, but not enough to ship, for
three reasons: a browser needs different glue from Node (the
JavaScript that loads the module and converts strings in and out of
it); the file should be as small as it can be, because readers
download it; and the wasm-bindgen command-line tool must be exactly the
version the crate was built with (the chapter *The Rust workspace*
pinned it), or it refuses the file.

The Rust world has a standard tool for all of this, **wasm-pack**.
`wasm-pack build` "creates the files necessary for JavaScript
interoperability and for publishing a package to npm": it compiles the
crate, runs wasm-bindgen, and writes a `pkg` folder holding the
`.wasm`, the JavaScript wrapper, your README and a
`package.json`<Cite id="wasm-pack-book" />. For release builds it also
runs wasm-opt, an optimiser from the Binaryen
project<Cite id="wasm-pack-book" /><Cite id="binaryen-readme" />.

<Analogy title="a flat-pack wardrobe">
A flat-pack wardrobe comes with a kit: screws, a little key and a sheet
of pictures, and most people use the kit. If your wall is unusual, you
buy your own fixings, but you still do the same steps in the same
order, because the steps are what make a wardrobe.
<span slot="breaks">The kit's pictures never change; wasm-pack's steps
do change between versions, which is one more reason a project with an
unusual wall writes its steps down in its own script.</span>
</Analogy>

<Callout kind="definition">
**wasm-pack** builds an npm package from a Rust crate. `wasm-pack build`
compiles to WebAssembly, runs **wasm-bindgen** for one `--target`
(`bundler` by default, or `nodejs`, `web`, `no-modules`, `deno`),
optimises with **wasm-opt** in release builds, and writes `pkg/` with a
generated `package.json`<Cite id="wasm-pack-book" />.
</Callout>

<Examples of="wasm-pack">

```sh
wasm-pack build
```

```sh
wasm-pack build --target nodejs
```

```sh
node packages/wasm/build.mjs
```

</Examples>

The first is the whole tool in one word: a release build for the
default `bundler` target, written to `pkg/`. The second changes only
the glue, asking for CommonJS that Node can `require`; it is still one
target per run, so getting both a Node and a browser build would mean
running it twice into two folders and writing your own `package.json`
to join them. The third is what Viscosity actually runs: its own
script, which does both targets in one go.

## Why Viscosity builds by hand

Viscosity's package is built by `engine/rust/packages/wasm/build.mjs`,
140 lines of Node. The unusual wall is the one-target rule:
`@viscosity/wasm` wants a `nodejs` build and a `web` build in a single
package, and lets each environment pick its own (that is the chapter
*The npm package*). The script also writes the licence texts and, with
`--book`, copies the web build into this book. Its steps, as shell
commands (the real code calls `execFileSync` for each):

```sh
# 1. cargo
cargo build --release \
  --target wasm32-unknown-unknown \
  -p viscosity-wasm
# 2. the locked wasm-bindgen, twice
wasm-bindgen --target nodejs ...
wasm-bindgen --target web ...
# 3. if wasm-opt can be found
wasm-opt -O3 <features> f -o f
# 4. LICENSE, THIRD_PARTY_LICENSES.txt
# 5. --book: copy dist/web into the book
```

Step 3 is optional: with no wasm-opt, the build carries on and says
so, and the result works, only larger. Unless `$WASM_OPT` names one,
the wasm-opt it looks for first is an npm devDependency, so `npm
install` is all a contributor needs.

## What each step does to the file

For this chapter I rebuilt the current tree from an empty target
directory, with cargo 1.97, wasm-bindgen 0.2.106 and wasm-opt 132,
running the script's commands one at a time. Cargo took 46 seconds on
the shared machine and each wasm-opt run about 36; between steps I
walked the section headers of the `.wasm` to see where the bytes were.

<PipelineSteps client:visible />

A WebAssembly file is a list of numbered **sections**: types,
functions, exports, code, data, and **custom** sections that engines
may ignore (the name section, which maps function numbers to names for
stack traces, is one). Each section starts with its id, one byte, and
its size, written as a variable-length number in a format called
LEB128. The program below walks a 52-byte module the same way:

<Run id="sections" />

<Formal title="Reading a LEB128 number">

```text
bytes b₀ b₁ … bₙ, where bₙ < 128
value = Σₖ (bₖ mod 128) · 128ᵏ
```

<span slot="read">Each byte carries seven bits of the number, lowest
first; a byte of 128 or more (its top bit set) says another byte
follows, and the first byte below 128 is the last. The value is the
sum of each byte's low seven bits times 128 to the power of its
position.</span>
</Formal>

It prints five lines, one per section: `type: 5 bytes`, `function:
2 bytes`, `export: 5 bytes`, `code: 6 bytes` and `custom "name": 16
bytes`. The module is one function, `f`, that returns 42, so the type
section describes one signature (no parameters, one 32-bit result), the
function section says function 0 has that type, the export section
publishes it as `f`, and the code section holds its body, which is the
instruction "push the constant 42" and an end marker. The last section
is custom: it has a name of its own, `"name"`, and maps function 0 to
the word `answer`, which is what a debugger would show. That is the
same section wasm-opt removes from the engine, 257 KB of it.

Inside the program, `main` checks the four "magic" bytes `\0asm`,
skips the version, then loops: read the id byte, read the size with
`leb`, and jump `i` to the end of the section, so it never needs to
understand what is inside. The `leb` function is the formula above:
`x & 0x7f` keeps the low seven bits, `<< s` multiplies by 128 to the
power of the position (`s` grows by 7 each time), and `x & 0x80 == 0`
stops at the last byte. For a custom section it also reads the name,
which is a LEB128 length followed by that many bytes of UTF-8.

The second step explains something the chapter *Rust and WebAssembly*
left open: how does a command-line tool know that `compile` takes a
string and returns an `Output`? The `#[wasm_bindgen]` macro cannot
write that down as data, because it runs before the compiler has worked
out the types, so it emits code instead, one `__wbindgen_describe_`
function per export, which reports the types when run. The CLI contains
"a tiny and incomplete Wasm interpreter" for exactly this: it runs every
describe function, writes the glue, then deletes them
all<Cite id="wasm-bindgen-cli-descriptors" />.

## Two kinds of glue

The two wasm-bindgen runs produce the same `.wasm` (64 bytes apart) and
different JavaScript:

<Figure takeaway="One module, two loaders: Node reads the file and starts at once; a browser fetches it and waits." caption="The nodejs glue is CommonJS and reads the .wasm with readFileSync as soon as it is required. The web glue is an ES module whose init() fetches the .wasm; nothing works until that promise resolves.">
  <TwoGlues />
</Figure>

<Analogy extra title="two editions of one book">
A publisher prints one text as a hardback for libraries and a paperback
for train stations; the words are identical, and only the binding
differs, chosen for where the book will be read.
<span slot="breaks">Two editions of a book are separate printed
objects, but they are read the same way; the two glues are read
differently (one at once, one after an `await`), and the package ships
two copies of the module only because each glue looks for it next to
itself.</span>
</Analogy>

The `nodejs` target writes CommonJS that can be `require`d like any
Node module<Cite id="wasm-bindgen-guide" />. Near its end (rewrapped):

```js
const wasmBytes = require('fs')
  .readFileSync(wasmPath);
const wasmModule =
  new WebAssembly.Module(wasmBytes);
const wasm = exports.__wasm =
  new WebAssembly.Instance(
    wasmModule, imports).exports;
```

That is synchronous: `compile` works the moment `require` returns. A
browser cannot read files, so the `web` target writes an ES module with
an `init()` that you `await`; it fetches the `.wasm` (by default from
next to the glue) and instantiates it, streaming if it
can<Cite id="wasm-bindgen-guide" />:

```js
import init, { compile }
  from '@viscosity/wasm/web';
await init();
const { code, explain } = compile(src);
```

## Checking the tools

Step 2 begins with the check you will write below: it reads the
`wasm-bindgen` version from `Cargo.lock`, asks the CLI for its own
with `--version`, and stops with the exact `cargo install` command if
they differ. One more check is worth having for a committed binary:
my rebuild's web `.wasm` was byte-identical to the one in
`book/public/wasm`, so the file this book serves really is the engine
in this tree.

<Callout kind="engine" label="Under the hood">
The final module has 15 exports: `compile`, `compileWith`,
`compileLanguage`, the getters, setters and `free` of `Output`, the
memory, and wasm-bindgen's allocator, table and start functions. It
imports three functions from JavaScript: one throws an error, one makes
an `Error` object, and one sets up the table of JavaScript values.
Everything else, oxc's parser included, is Rust compiled into the code
section, 1,248,736 of its 1,373,422 bytes. `build.mjs` passes wasm-opt
the WebAssembly features rustc enables by default for this
target<Cite id="rustc-wasm32-unknown-unknown" />; I ran wasm-opt
without them too, and the same bytes came out, because the module
lists its features in its own `target_features` custom section.
</Callout>

## What you learned

- **wasm-pack** compiles, binds, optimises and packages a crate for
  npm, one target at a time; `build.mjs` does the same steps for two.
- Cargo's file carries **describe functions** for the CLI, which runs
  them, writes the glue and removes them; wasm-opt then drops the
  **name section** and shrinks the code, 386 KB in all, but only about
  6% once gzipped.
- The **nodejs** glue loads synchronously; the **web** glue needs
  `await init()`. The CLI must match `Cargo.lock` exactly.
