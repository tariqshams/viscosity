## You have been graded all along

In TypeScript a test is a call into a library (`test('...', () =>
expect(x).toBe(7))`, with Vitest or Jest providing both). Rust builds
testing into the compiler and cargo, and a test is an ordinary function
with a label on it; every Rust exercise since *Why Rust, and cargo* has
been checked this way, and the `todo!()` in each starter made it fail.

```rust
fn is_alpha(c: u8) -> bool {
    c.is_ascii_alphabetic() || c == b'_'
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn letters_and_underscore() {
        assert!(is_alpha(b'a'));
        assert!(is_alpha(b'_'));
        assert!(!is_alpha(b'7'));
    }
}
```

Lines 1 to 3 are the code under test, the scanner's "can this byte start
a name?" from *Tokens and a scanner*. `#[test]` is an **attribute** (a
note to the compiler above an item) marking a test, and `assert!(cond)`
panics if `cond` is false, so each line inside is one check. `#[cfg(test)]` compiles the module only when
building tests, so a normal build carries no test code; and because
`tests` is a child module, `use super::*` brings in its parent's items,
and the privacy rule of *Modules, visibility and workspaces* (a private
item is visible to its module's descendants) lets the test call private
helpers nothing else may call.

<Analogy title="a driving test">
The examiner hands you a route, and you drive it. Finish without a
serious fault and you pass; make one and the test stops there and then,
with the examiner's note saying what went wrong. A Rust test is the
route, each `assert!` is a point where the examiner is watching, and a
panic is the fault.
<span slot="breaks">An examiner can be lenient; a Rust test has no
judgement at all, and fails if anything panics, even code you did not
mean to test.</span>
</Analogy>

## Pass by returning, fail by panicking

That is the whole contract: a test **passes if it returns** and **fails
if it panics**. The test runner (the **harness**, a `main` function
cargo writes for you) runs each test on a thread of its own, and when a
test's thread dies of a panic it marks that test failed and carries on
with the rest<Cite id="rust-book-testing" />:

  <RunnerFlow />
</Figure>

Here are lines from a real run with rustc 1.97, where a second test calls
a function that still says `todo!()`:

```text
test tests::letters_and_underscore ... ok
test tests::max_picks_the_largest
  ... FAILED
thread 'tests::max_picks_the_largest'
  panicked at t1.rs:6:5:
not yet implemented
test result: FAILED. 1 passed; 1 failed;
```

Each test is named by its module path, the failure shows the panic's
message and line, and the run ends with a summary and a failing exit
code, so CI can tell. A word after `cargo test` runs only the tests whose
path contains it.

<Callout kind="definition">
A **unit test** is a function marked **`#[test]`**, usually inside a
`#[cfg(test)] mod tests` beside the code it tests. **`cargo test`**
compiles the crate in test mode, runs every test (in parallel threads by
default), and reports each as `ok` or `FAILED`; a test fails exactly when
it panics<Cite id="rust-book-testing" />.
</Callout>

<Examples of="cargo-test">

```rust
// drip-rs, src/object.rs
#[test]
fn hashes_with_fnv_1a() {
    assert_eq!(hash_string(""),
        2_166_136_261);
    assert_eq!(hash_string("a"),
        0xe40c292c);
}
```

</Examples>

This one is real, from drip-rs's `object.rs` (wrapped to fit). It pins
the string hash of *String interning and globals by name* to known
answers: the empty string hashes to FNV-1a's starting value, and `"a"`
to `0xe40c292c`. Change the hash and this test is where you find out;
its name reads as a sentence, so the failure explains itself.

## Integration tests

Files in a crate's `tests/` folder are **integration tests**. Each file is
compiled as a *separate crate* that depends on yours, so it sees only your
`pub` items, as a user would (drip-rs's `tests/vm.rs` starts with `use
drip::{Options, Vm};`); shared helpers go in `tests/common/mod.rs`, since
a `tests/common.rs` would be one more test crate<Cite id="rust-book-testing" />.

## Three checks

There are three assert macros: `assert!(cond)` panics if `cond` is
false, `assert_eq!(a, b)` if `a != b` and `assert_ne!(a, b)` if `a == b`,
the last two printing both values; each takes an optional message after
its checks, formatted like `println!`. Step through a check of the
array-of-structs slot formula (element `i`'s field `f`, with `nf` fields
each, lives at `i * nf + f`) written wrong on purpose:

<AssertSteps client:visible />

<Examples of="assert-macros">

```rust
fn slot(i: usize, f: usize, nf: usize)
    -> usize {
    f * nf + i // bug: i * nf + f
}
assert_eq!(slot(0, 0, 2), 0);
assert_ne!(slot(1, 0, 2), 0);
assert_eq!(slot(3, 1, 2), 7,
    "element 3, field 1");
```

</Examples>

`slot` returns `f * nf + i`, the bug. The first `assert_eq!` passes by
luck (both formulas give 0 for element 0, field 0), and the `assert_ne!`
passes because element 1 is not at slot 0 either way; the third compares
`slot(3, 1, 2)`, which is `1 * 2 + 3 = 5`, with 7, and panics, printing
your message and then `left: 5` and `right: 7`:

That is the reason to prefer `assert_eq!(a, b)` to `assert!(a == b)`:
both panic at the same moment, but `assert!` can only print `assertion
failed: a == b`. Comparing needs `PartialEq` and printing needs `Debug`;
on a struct with neither, rustc 1.97 reports E0369 and E0277 and
suggests deriving them, which is why test-facing types usually start
with `#[derive(Debug, PartialEq)]`.

<Callout kind="definition">
The **assert macros** are `assert!(cond)`, `assert_eq!(left, right)` and
`assert_ne!(left, right)`. Each panics when its check fails, which fails
the test it is in; the `eq` and `ne` forms compare with `PartialEq` and
print both values with `Debug`. An optional message, written as in
`println!`, is added to the panic<Cite id="rust-book-testing" />.
</Callout>

## Tests that should panic, and suites of hundreds

Some code is *supposed* to panic: drip-rs's arena panics on a handle to
a freed object, and `object.rs` tests that with `#[should_panic(expected = "use after free")]` on the test
function: the test now passes only if the body panics, *and* the
message contains that text, so a panic for some other reason (an index
out of range, say) fails it with `note: panic did not contain expected
string`.

The VM's corpus is 334 Drip programs with their expected output in
comments (*End to end: benchmarks and differential testing at scale*);
one `#[test]` around them all would report one `ok` or `FAILED` for the
lot, so drip-rs's `Cargo.toml` switches the harness off for that file:

```toml
[[test]]
name = "corpus"
harness = false
```

`tests/corpus.rs` is then an ordinary program with its own `main`, which
prints one line per program and exits with 1 if any failed; cargo looks
only at its exit code.

<More title="Tests that return Result, engine/rust's parity test, and TypeScript's toThrow">

A test may also return `Result<(), E>`: `Ok(())` passes, `Err(e)` fails,
and the `?` of *Option, Result and the ? operator* works inside it, so a
test of code that returns `Result` can read like the code itself.

engine/rust's `crates/cli/tests/parity.rs` compares the Rust engine's
output and explain text, for every fixture, with what the TypeScript
engine produced, byte for byte. Rather than stopping at the first
mismatch, it pushes each difference onto a `Vec` with its first
differing line and asserts once at the end, `assert!(failures.is_empty(),
...)`, so one run reports every difference. Run with `--show-output`, it
printed `parity: 190/190 (54 Python)`.

In TypeScript, `expect(() => max([])).toThrow('empty')` wraps the call in
a function so the library can catch the exception; in Rust, expecting a
panic is an attribute on the whole test, so a `should_panic` test should
contain only the call that ought to panic.

</More>

## What you learned

- A **`#[test]`** function passes if it returns and fails if it panics;
  unit tests may call private items, integration tests only `pub` ones.
- **`assert_eq!`** and **`assert_ne!`** print both values on failure, so
  they need `Debug` and `PartialEq`.
- `should_panic(expected = ...)` checks the panic's text; `harness =
  false` lets a test file be its own program.
