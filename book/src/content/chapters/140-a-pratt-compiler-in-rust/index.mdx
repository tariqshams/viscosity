## The table you already wrote

In *One pass from source to bytecode* the TypeScript compiler parsed
expressions with the Pratt parser of *Pratt parsing*, driven by a table:
for every kind of token, what it does when it **starts** an expression
(its prefix rule), and how tightly it binds when it **continues** one
(its precedence, used by its infix rule). `prefixRule` answers with a
closure written inside `compile`, which reaches every variable of the
compiler; helpers as closures over shared variables are what Rust will
not allow.

<Analogy title="a phrasebook with one page per word">
Picture a phrasebook with one page per word, each answering the same
three questions: can this word start a sentence, and how; can it carry
on a sentence somebody else started; and how hard does it pull its
neighbours towards itself. You never think about grammar; you look the
word up and do what the page says.
<span slot="breaks">Real phrasebooks are full of "it depends on
context"; the parser's table is looked up with the token's kind and
nothing else, and the instructions on a page may send you straight back
to the start of the book to parse a smaller expression.</span>
</Analogy>

## Three matches make one table

drip-rs answers each question with a `match` on the token's kind. How
tightly a token binds as an infix operator (from `compiler.rs`, trimmed
and rewrapped):

```rust
fn infix_precedence(kind: TokenKind)
    -> u8 {
    use TokenKind as T;
    match kind {
        T::Star | T::Slash | T::Percent
            => PREC_FACTOR,
        T::Plus | T::Minus => PREC_TERM,
        // ... calls, comparisons, && and ||
        _ => PREC_NONE,
    }
}
```

The precedences are plain `u8` constants, weakest first, the numbers of
TypeScript's `Prec`: `PREC_NONE` 0, `PREC_ASSIGNMENT` 1, up to `PREC_CALL`
9. The `_` arm gives every other token 0, lower than any expression asks
for, which is what makes a `;` or a `)` end one.

What a token does at the start of an expression is not a function but a
*name* for one, `enum Prefix { Grouping, Unary, Number, Literal(OpCode),
Variable, ... }` (eleven variants). `prefix_rule(kind)` maps `-` and `!`
to `Some(Prefix::Unary)`, `true` to `Some(Prefix::Literal(OpCode::True))`
and anything that cannot start an expression to `None`; the methods
`prefix(&mut self, prefix, can_assign)` and `infix` then run the code,
one `match` arm per kind.

Why a name? Rust *can* store functions: `fn(&mut Compiler, bool)` is a
function pointer type, and `Option` of one is 8
bytes<Cite id="rustref-fn-pointer" /><Cite id="rust-std-fn-primitive" />.
But `Option<Prefix>` is one byte (rustc 1.97), a `Prefix` can carry data
(`true`, `false` and `none` share the `Literal` arm), the `match` in
`prefix` must cover every variant, and a name can be kept: after
consuming `fn`, `declaration` may resume an anonymous function's
expression with `Some(Prefix::Fn)`.

<More title="Precedence as an Ord enum, and what the match compiles to">

Rust could make precedence an enum that derives `Ord`, which orders the
variants by position<Cite id="rust-std-ord" />; drip-rs keeps numbers,
because the parser adds one to them. rustc may compile a `match` on a
small enum to a jump table or a short chain of comparisons; no hashing is
involved either way. The TypeScript `prefixRule` builds a new closure each
time it is asked about a number, a string, a name or a literal, where
drip-rs returns a byte.

</More>

## The loop that runs the table

`parse_precedence(p)` advances past one token, asks `prefix_rule` about
it (reporting `expected an expression` when it is `None`), and hands over
(rewrapped, its error report shortened):

```rust
fn continue_expression(&mut self,
    precedence: u8, prefix: Prefix) {
    let can_assign =
        precedence <= PREC_ASSIGNMENT;
    self.prefix(prefix, can_assign);
    while precedence <= infix_precedence(
        self.current.kind)
    {
        self.advance();
        self.infix(self.previous,
            can_assign);
    }
    // ... report a leftover `=`
}
```

It emits the left operand, then absorbs infix operators while the next
token binds at least as tightly as `precedence`; `can_assign` is true
only at the loosest level, so the `=` of `a + b = 1;` is left over. A
binary operator's arm of `infix` parses its right operand one level
tighter, `self.parse_precedence(infix_precedence(kind) + 1)`, then emits
the operator; that `+ 1` is why `8 - 3 - 2` is `(8 - 3) - 2`, because
the second `-` may not join a right operand that wants something
tighter. Step through `-1 + 2 * 3`:

<Callout kind="definition">
A **parse-rule table** maps each token kind to a prefix parse function
(what it does at the start of an expression), an infix parse function
(what it does after a complete operand) and an infix precedence; any of
these may be absent. In drip-rs the table is three matches on
`TokenKind`: `prefix_rule` returns an `Option<Prefix>` naming the prefix
function, `infix_precedence` returns a `u8` (0 for none), and the
methods `prefix` and `infix` run the code.
</Callout>

<Formal title="The Pratt loop">

```text
parse(p) = prefix(t₁);
           while p ≤ prec(next):
             infix(next)
infix(op) = parse(prec(op) + 1); emit op
```

<span slot="read">To parse at minimum precedence p, run the prefix rule
of the first token; then, as long as the next token's precedence is at
least p, run its infix rule. A binary operator's infix rule parses its
right side at one more than its own precedence, then emits the
operator.</span>
</Formal>

<Examples of="parse-rule-table">

```text
print 8 - 3 - 2;      # 3
const '8'  const '3'  sub
const '2'  sub
print 1 + ;
line 1: expected an expression, found ';'
```

</Examples>

The bytecode (from `drip-rs --disassemble`, operands trimmed) emits the
first `sub` before the `2` is loaded: `8 - 3` first, then `5 - 2`. The
last two lines are the table saying no: `prefix_rule(Semicolon)` is
`None`, so the parser reports the token it found and exits with 65, the
same line the TypeScript VM prints.

## Closures that cannot share

The TypeScript `compile` keeps `current`, `previous`, `panicMode` and
the rest in local variables, and dozens of helpers, all closures, read
and write them and call each other in circles (`parsePrecedence` calls
`infix`, which calls `parsePrecedence`). The smallest piece of that in
Rust, two closures over one counter:

```rust
let mut pos = 0;
let mut advance = || pos += 1;
let peek = || pos;
advance();
```

rustc 1.97 refuses with `error[E0502]: cannot borrow pos as immutable
because it is also borrowed as mutable`. A closure that changes a
variable holds a mutable borrow of it for as long as the closure may
still be called (*Closures, iterators and associated
types*<Cite id="klabnik2026" />), and meanwhile nobody else may even read
it. So drip-rs gathers the state into one struct (trimmed):

```rust
struct Compiler<'src, 'a> {
    scanner: Scanner<'src>,
    current: Token<'src>,
    previous: Token<'src>,
    panic_mode: bool,
    // ... error lists, classes
    functions: Vec<FunctionState<'src>>,
    heap: &'a mut Heap,
    roots: &'a dyn Trace,
}
```

Every helper is a method on `&mut self`, which lends the same `&mut` to
the helpers it calls and gets it back when they return, so there is only
ever one user. `'src` is the source, which tokens and local names slice;
`'a` is what the caller lends, its `Heap` and its GC roots. Nested
functions are a `Vec`, innermost last, not an `enclosing` list.

<Figure takeaway="One struct holds everything; it borrows the source and the caller's heap." caption="The Compiler's fields. Tokens and local names point into the source ('src); heap and roots are lent by the caller ('a); functions is a stack, the innermost function last.">
  <CompilerShape />
</Figure>

<Callout kind="definition">
**Threading compiler state through `&mut self`** means putting all of
a compiler's changeable state in one struct and writing every parse and
emit helper as a method on `&mut self`. Each call lends the whole state
to the callee for the length of the call. It replaces closures over
shared variables, which the borrow checker does not allow.
</Callout>

<Analogy extra title="one workbench, handed along">
Picture a workshop with one bench, holding all the tools and the
half-built piece. Rather than everyone reaching across at once, the
bench is handed from worker to worker: whoever has it may use anything
on it, and asking a colleague for help means handing the whole bench
over and waiting until it comes back.
<span slot="breaks">Workers can cheat and grab; in Rust the hand-over
is proved at compile time, so nobody can touch the bench while it is
lent out, and it always comes back when the helper returns.</span>
</Analogy>

One habit shows up all over `compiler.rs`:

<Examples of="compiler-state">

```rust
fn emit(&mut self, byte: u8) {
    self.chunk().write(byte,
        self.previous.line);
} // error[E0503]

fn emit(&mut self, byte: u8) {
    let line = self.previous.line;
    self.emit_at(line, byte);
}
```

</Examples>

The first is the natural attempt. `self.chunk()` (the innermost
function's chunk) returns a `&mut Chunk` that borrows *all* of `self`,
and the borrow lasts until `write` is done, so reading `self.previous.line`
for the argument falls inside it: `cannot use self.previous.line because
it was mutably borrowed`. The second is drip-rs's real `emit`: copy the
`usize` into a local first, and only then borrow.

<More title="Levels instead of links, two error lists, and the roots">

The TypeScript compiler resolves a captured variable by walking the
`enclosing` list and changing entries on the way, which in Rust would
mean mutable borrows of several of them at once. drip-rs names a
function by its index, its *level*: `resolve_upvalue(level, name)` looks
in `self.functions[level - 1]` and recurses with the level below, and a
level borrows nothing. Each `FunctionState` has its own `chunk`, and
`end_function` moves it into the heap as an `Rc<Chunk>`, frozen from
then on.

Static rules (`return` outside a function) go into `static_errors`;
syntax errors go into `syntax_errors` and set `panic_mode` until the next
statement (*Syntax errors and panic mode*). With a syntax error, the
static rules are never reported: `return 1;` then `print ;` prints only
`line 2: expected an expression, found ';'`, and without the second line
you get `line 1: 'return' outside a function`. `compile` ends with
`errors.is_empty().then_some(function)`, where TypeScript returned
`null`.

At run time a `&mut` is one address, no dearer than the TypeScript
closures. The struct also keeps unfinished functions alive: before
allocating, the compiler runs
`self.heap.collect(&[self.roots, &self.functions])`, and `FunctionState`
implements `Trace`, marking its function and its chunk's constants.

  the methods that run the code.
