## A class, compiled

The tree-walker ran classes in the chapter "Records with behaviour:
classes in Drip". Here is a small one on the VM:

```text
class P {
  init(x) { self.x = x; }
  get() { return self.x; }
}
let p = new P(3);
print p.get();   # 3
print p;         # P { x: 3 }
```

The disassembler shows how the class itself is built, before any
instance exists:

```text
0000    1 class               0 'P'
0003    | define.global       1 'P'
0006    | load.global         2 'P'
0009    2 closure             4 fn init
0012    | method              3 'init'
0015    3 closure             6 fn get
0018    | method              5 'get'
0021    4 pop
```

`class 'P'` pushes a new, empty class, and `define.global` stores it
under its name. `load.global` pushes it again, so that each method can
be added to it: `closure` pushes the method's closure on top of the
class, and `method 'init'` stores that closure in the class's method
table under the name `init` and pops it, leaving the class for the next
method. The final `pop` drops the class once its body is done.

## Two tables

Both kinds of object are small (from `object.ts`): a class is a name and
a method table, and an instance is a pointer to its class, a field table
and the order its fields were first set, which is how `print` lists
them.

<Figure caption="An instance of P, and its class." takeaway="A class is a table of methods; an instance is its class plus a table of fields.">
  <ClassTablesFigure />
</Figure>

Both tables are the hash tables of the chapter "Finding things fast:
hash tables", keyed by interned strings (the chapter "String
interning"), so finding `"x"` compares one pointer rather than
characters.

Inside a method, `self` is not special at run time: it is slot 0. When
the compiler starts a method or an initialiser, `initCompiler` names
slot 0 `self` (in a plain function, slot 0 holds the function itself,
with an empty name no code can use), so `self.x` in `get` compiles to
`load.local 0`, then `get.prop 'x'`. `get.prop` checks the instance's
fields first and its class's methods second; a method found that way is
wrapped in a bound method (the chapter "Methods that keep their self"),
which the next chapter looks at closely. `set.prop` writes the field
table, and appends the name to `fieldOrder` the first time a field is
set:

```ts
if (instance.fields.set(name, this.peek(0)))
  instance.fieldOrder.push(name);
```

(One line in `vm.ts`, wrapped.) `Table.set` returns `true` only when
the key is new, so a field keeps its place in the printout however
often it is assigned.

## Making an instance

<Analogy title="a new starter’s first day">
On someone's first day, the office first sets up an empty desk with
their name on it, and then runs the onboarding checklist, which fills
the drawers; whatever the checklist says, at the end of the day what
the company has gained is the person at the desk, not the checklist.
<span slot="breaks">An office can skip the checklist and still have a
working employee; a class with no `init` gives you an instance with no
fields at all, and Drip then refuses any arguments, because there is
nothing to give them to.</span>
</Analogy>

<Analogy extra title="a cake box at the bakery">
You order a cake: someone takes a flat box, folds it into shape, puts
the cake in and hands it over the counter. Whatever happens inside, what
comes back to you is always the box.
<span slot="breaks">A bakery chooses which box to use; in Drip the
instance is made before `init` runs and is handed to it as `self`, and
`init` cannot hand back anything else, even if it wants to.</span>
</Analogy>

`new P(3)` compiles to `load.global 'P'`, `const 3` and `new 1`, so the
class sits in exactly the slot where a function would sit for an
ordinary call, with its arguments above it. Here is what `new` does,
from `vm.ts` (long lines wrapped, return type left out):

```ts
private newInstance(argCount: number) {
  const klass = this.peek(argCount);
  if (!isObj(klass) ||
      klass.type !== 'class') return ...;
  this.stack[this.sp - argCount - 1] =
    this.heap.newInstance(klass);
  const init =
    klass.methods.get(this.initString);
  if (init !== undefined)
    return this.call(init as ObjClosure,
                     argCount);
  if (argCount !== 0) { ... }
}
```

(The two `...` are the error reports.) It checks that the value below
the arguments is a class, makes an empty instance, and writes it *over
the class*, in the callee's slot. That slot is about to become the new
frame's slot 0, so when `init` runs, `self` and the parameters are
already in place, and nothing had to move. `initString` is the interned
string `"init"`, made once when the VM starts, so this lookup never
builds a string. Step through it:

What does `init` give back? The compiler makes sure it is always the
instance: a function's implicit return normally pushes `none`, but in an
initialiser it pushes slot 0:

```ts
function emitReturn() {
  if (fc().type === 'initializer')
    emit(Op.LoadLocal, 0);
  else emit(Op.None);
  emit(Op.Return);
}
```

(The first `if` is one line in the file.) A bare `return;` inside
`init` also goes through `emitReturn`, so it too returns the instance,
and `return value;` in `init` is a compile error.

<Examples of="initializer">

```text
class E {}
print new E();   # E {}
```

```text
class P {
  init(x) {
    if x < 0 { return; }
    self.x = x;
  }
}
print new P(-1);   # P {}
print new P(2);    # P { x: 2 }
```

```text
class Point {}
let p = new Point(1, 2);
# runtime error: Point has no init, so
#   it takes no arguments, but got 2
```

<Run id="init-calls" />

</Examples>

The first is the simplest instance there is: `E` has no `init`, so `new`
makes an empty instance and, with no arguments to complain about, is
done. In the second, `new P(-1)` takes the early, bare `return;`, which
still returns `self`, so you get an instance with no fields, while
`new P(2)` runs to the end. The third is the mistake to watch for: with
no `init` there is nothing to receive arguments, so `newInstance`
reports exactly that. The runnable one is the realistic shape: an
`init` that stores its argument, makes a list field, and then calls a
method of its own (`self.fill()`), which works because `self` is a
complete instance from the first line of `init`.

Two more errors are worth knowing by sight. Writing `return self;` (or
any value) in `init` is the compile error `'init' cannot return a
value`; and calling a class without `new`, as in `P(1)`, is the runtime
error `cannot call a class: use 'new P(...)'`.

<Callout kind="definition">
An **initialiser** is the method named `init`. `new C(args)` allocates
an instance of `C`, stores it in the callee's stack slot (which becomes
the frame's slot 0, `self`), and calls `init` with the arguments, if
`C` has one; with no `init`, it must have no arguments. The compiler
makes every return from `init` return slot 0, so `new` always produces
the instance, and `return value;` in `init` is a compile error.
</Callout>

<Formal title="What new evaluates to">

```text
new C(v1, …, vn) ⇓ o
  where o = a fresh instance of C,
  and, if C has init, init runs with
  self = o, params = v1, …, vn
```

<span slot="read">Evaluating new C applied to values v1 to vn gives o,
where o is a new instance of class C; if C has an init method, it runs
first, with self bound to o and its parameters to the values. Whatever
init does, the result is o.</span>
</Formal>

<Prompts ids={['new-slot', 'init-returns', 'no-init-args', 'bare-return']} />

<Callout kind="engine" label="Under the hood">
JavaScript's `new` is close to Drip's: for an ordinary class without a
superclass, `new` creates the object first and binds it as `this`
before the constructor body runs. Unlike Drip, a JavaScript constructor
*may* return a different object, and if it does, that object is the
result of `new`<Cite id="ecma262" />. Drip forbids that at compile time,
which is why its VM can always take slot 0 as the answer.
</Callout>

## What you learned

- A class is a name and a **method table**, built by `class`, then
  `closure` and `method` per method; an instance is a class pointer, a
  **field table** and the field order.
- `self` is slot 0 of every method. `get.prop` checks fields, then
  methods; `set.prop` records a field's place the first time it is set.
- `new` writes a fresh instance over the class in the callee's slot and
  calls the **initialiser**, `init`, whose every return gives back slot
  0, the instance.

## A call that makes garbage

In the chapter "Objects and method calls in the VM", `get.prop` on a
method made a **bound method**, a small heap object holding the
instance and the method together, because Drip says that `o.m` on its
own is a value you can store and call later. So the plain reading of
`c.m(2)` is "read `c.m` (make a bound method), then call it". The
compiler does not do that, as the disassembler shows (the method is
called `m` here only so that the lines fit the page):

```text
0030    6 load.global         9 'c'
0033    | const              11 '2'
0036    | invoke             10 'm' (1 args)
0040    | pop
0041    7 load.global        12 'c'
0044    | get.prop           13 'm'
0047    | const              14 '3'
0050    | call                1
```

Line 6 is `c.m(2);` and line 7 is `(c.m)(3);`, which means exactly the
same thing; the brackets stop
the compiler seeing a call straight after the property, so it falls
back to the literal reading: `get.prop` allocates a bound method, and
`call` unpacks it again at once. That bound method is garbage as soon as
`call` has unpacked it, which in a loop of a million calls is a million
objects for the collector.

<Analogy title="calling an extension directly">
To reach a colleague you could ask reception to print you a card with
their name and extension, read the card, dial, and throw the card away;
or, since you already know both, you could dial the extension directly.
The second way reaches the same person and leaves no card in the bin.
<span slot="breaks">Sometimes you do want the card, to give to someone
else; that is `let f = c.add;`, and then the VM really does make the
bound method, because the value has to exist.</span>
</Analogy>

<Analogy extra title="a keyboard shortcut">
Ctrl+S saves a document without opening the File menu, finding Save and
clicking it; the effect is exactly the menu's, minus the steps in

<span slot="breaks">A shortcut always does the same thing; `invoke` has

## One instruction: invoke

When `dot` in the compiler has parsed `.name` and the next token is
`(`, it compiles the arguments and emits one instruction carrying both
the name and the argument count:

```ts
} else if (match('(')) {
  const argc = argumentList();
  emitConstantOp(name.line, Op.Invoke, k);
  emitAt(name.line, argc);
}
```

The receiver is pushed first and the arguments above it, so when
`invoke` runs, the receiver is already in the slot that will become the
method's slot 0, `self`. Here is `invoke` in `vm.ts`, shortened where
marked:

```ts
const receiver = this.peek(argCount);
// (an error unless it is an instance)
const field = receiver.fields.get(name);
if (field !== undefined) {
  this.stack[this.sp - argCount - 1] =
    field;
  return this.callValue(field, argCount);
}
const method =
  receiver.klass.methods.get(name);
if (method === undefined) return ...;
this.call(method as ObjClosure, argCount);
```

It looks in the instance's fields first; a field holding a function
shadows a method of the same name, so the field replaces the receiver
in the callee's slot and is called like any value. Otherwise it finds
the method in the class's table and calls it straight away: no bound
method, nothing to unpack, and the frame is the same one `call` would
have built. Step through both routes:

Did it pay off? In runs I did for this book, I built a copy of the
companion whose compiler never emits `invoke` (so every `o.m()` becomes
`get.prop` and `call`) and timed the `method_calls` benchmark against
the real one, alternating the two, nine runs each. The best run with
`invoke` took 704 ms and the best without it 932 ms; and where the real
VM never needed a single collection, the copy ran 48 of them and freed
1,570,728 bound methods. The chapter "Measuring and speeding up the VM"
puts this next to the other changes measured the same way.

<Callout kind="definition">
**Method invocation**, in the VM, is the single instruction `invoke
name argc`, emitted when a property access is immediately called. It
looks the name up in the receiver's fields, then in its class's
methods, and calls what it finds with the receiver already in slot 0.
It means exactly what `get.prop` followed by `call` means, without
allocating a bound method.
</Callout>

<Formal title="Invoke means read, then call">

```text
o.m(a1, …, an)  ≡  (o.m)(a1, …, an)
  invoke m n    ≡  get.prop m; call n
```

<span slot="read">Calling o.m with arguments a1 to an gives the same
result as first reading o.m and then calling that with the same
arguments. In bytecode: one invoke of m with n arguments does what a
get.prop of m followed by a call with n arguments does; the only
difference is the bound method the second one allocates.</span>
</Formal>

<Run id="field-wins" />

That program is why the field check exists: after `a.m = f;`, the
instance has a field named `m`, so `a.m()` must call `f`, exactly as
`(a.m)()` would, and it prints `field`.

## Inheritance by copying

The tree-walker found an inherited method by walking up the chain of
superclasses on every lookup. The VM does that walk once, when the
subclass is made: `inherit` copies the superclass's whole method table
into the new class.

```ts
// Copy-down inheritance: the methods are
// copied once, now.
(this.peek(0) as ObjClass).methods.addAll(
  (superclass as ObjClass).methods);
this.sp--;
```

(From the `inherit` case, wrapped; before it, the instruction checks
that the superclass really is a class.) It runs before the subclass's
own `method` instructions, so an overriding method simply overwrites
the copied entry, and every later lookup is a single probe in one
table.

<Figure caption="B extends A: inherit copies A's table into B, then B's own methods are added on top." takeaway="After the copy, finding any method of B is one table lookup, however deep the chain.">
  <CopyDownFigure />
</Figure>

This is only correct because a Drip class can never gain or lose
methods after its declaration; if it could, the copies would go stale.

`super` needs one more piece. When a class extends another, the
compiler opens a scope around the class body and declares a local named
`super` holding the superclass; methods that say `super` capture it as
an upvalue (the chapter "Capturing variables: upvalues"), and it is
closed when the class declaration ends. Here is
`class B extends A { m() { return super.m() + "B"; } }`:

```text
== <script> ==
0022    | load.global         7 'A'
0025    | load.global         8 'B'
0028    | inherit
0029    | load.global         9 'B'
0032    5 closure            11 fn m
0035    |   local 1
0037    | method             10 'm'
0040    6 pop
0041    | close.upvalue
== m ==
0000    5 load.local          0
0002    | load.upvalue        0
0004    | invoke.super        0 'm' (0 args)
```

`load.global 'A'` leaves the superclass in slot 1, the hidden `super`
local; `inherit` copies its methods into `B` and pops `B`; `B`'s
method `m` captures slot 1 (`local 1`); and after the class body, the `pop`
drops `B` and `close.upvalue` closes `super` into the upvalue. Inside
it, `super.m()` pushes `self`, then the superclass through the
upvalue, and `invoke.super 'm'` looks `m` up in *that* class's table
and calls it, with `self` already in place, allocating nothing. (Reading
`super.m` without calling it compiles to `get.super`, which makes a
bound method, as `get.prop` does.)

<Examples of="method-invocation">

```text
t.flip().value();
# invoke 'flip', then invoke 'value'
```

```text
let f = c.add;   # get.prop: a bound method
f(4);            # call: unpacked
```

```text
super.init(on);
# load.local 0, load.local 1,
# load.upvalue 0, invoke.super 'init'
```

</Examples>

The first is from the `method_calls` benchmark: `flip` returns `self`,
and the chained call becomes two `invoke` instructions, the second one
finding its receiver where the first left its result. The second is the
case `invoke` cannot cover: the method is stored as a value, so the
bound method really has to exist, and `call` unpacks it later. The
third is a subclass's `init` calling its parent's: `self`, the argument
and the superclass go on the stack, and `invoke.super` calls the
parent's `init` on the same instance.

## What you learned

- `o.m(args)` compiles to **`invoke m n`**, which calls the method with
  the receiver already in slot 0 and allocates no bound method;
  `(o.m)(args)` and `let f = o.m;` still take the long way.
- `invoke` checks fields before methods, so it means exactly what
  reading and then calling would.
- `inherit` copies the superclass's methods down once; overrides are
  added after, so they win, and every lookup is one probe.
- `super` is a hidden local captured as an upvalue; `invoke.super` and
  `get.super` start the lookup at that class.
