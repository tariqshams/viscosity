## A class, compiled

The tree-walker ran classes in *Classes, methods and inheritance in
Drip*; here is a small one on the VM, and the bytecode that builds the
class before any instance exists:

```text
class P {
  init(x) { self.x = x; }
  get() { return self.x; }
}
let p = new P(3);
print p.get();   # 3
```

```text
class               0 'P'
define.global       1 'P'
load.global         2 'P'
closure             4 fn init
method              3 'init'
closure             6 fn get
method              5 'get'
pop
```

`class 'P'` pushes an empty class and `define.global` stores it; then
each `closure` and `method` pair puts one method in the class's method
table. Both kinds of object are small: a class is a
name and a method table, and an instance is a pointer to its class, a
field table and the order its fields were first set (which is how
`print` lists them).

<Figure caption="An instance of P, and its class." takeaway="A class is a table of methods; an instance is its class plus a table of fields.">
  <ClassTablesFigure />
</Figure>

Both are hash tables keyed by interned strings (*Hash tables*). Inside
a method, `self` is not special at run time: the compiler names slot 0
of every method `self`, so `self.x` compiles to `load.local 0` then
`get.prop 'x'`, and the VM must put the instance in slot 0.

## Making an instance

<Analogy title="a new starter’s first day">
On someone's first day, the office first sets up an empty desk with
their name on it, and then runs the onboarding checklist, which fills
the drawers; whatever the checklist says, at the end of the day what
the company has gained is the person at the desk, not the checklist.
<span slot="breaks">An office can skip the checklist and still have a
working employee; a class with no `init` gives you an instance with no
fields, and Drip then refuses any arguments, because there is nothing
to give them to.</span>
</Analogy>

`new P(3)` compiles to `load.global 'P'`, `const 3` and `new 1`, so the
class sits exactly where a function would sit for an ordinary call, with
its arguments above it. The VM's `newInstance` checks that value is a
class, makes an empty instance and writes it *over the class*, in the
callee's slot; then, if the class has a method named `init` (looked up
with the interned `"init"` the VM made at start-up), it calls it. That
slot is about to become the new frame's slot 0, so `self` and the
parameters are already in place and nothing has to move:

<NewSteps client:visible />

And what does `init` give back? The compiler makes sure it is always
the instance: a function's implicit return normally pushes `none`, but
in an initialiser it pushes slot 0:

```ts
function emitReturn() {
  if (fc().type === 'initializer')
    emit(Op.LoadLocal, 0);
  else emit(Op.None);
  emit(Op.Return);
}
```

<Callout kind="definition">
An **initialiser** is the method named `init`. `new C(args)` allocates
an instance of `C`, stores it in the callee's stack slot (which becomes
the frame's slot 0, `self`), and calls `init` with the arguments, if
`C` has one; with no `init`, it must have no arguments. The compiler
makes every return from `init` return slot 0, so `new` always produces
the instance, and `return value;` in `init` is a compile error.
</Callout>

<Examples of="initializer">

```text
class P {
  init(x) {
    if x < 0 { return; }
    self.x = x;
  }
}
print new P(-1);   # P {}
print new P(2);    # P { x: 2 }
```

</Examples>

`new P(-1)` takes the early, bare `return;`, which goes through
`emitReturn` like any other return and so still returns `self`: you get
an instance with no fields. `new P(2)` runs to the end and stores `x`.
Writing `return self;` instead would be the compile error `'init'
cannot return a value`, and if `P` had no `init` at all, `new P(1, 2)`
would be the runtime error `P has no init, so it takes no arguments, but
got 2`.

<More title="More: an init that calls a method, a field that beats a method, and JavaScript's new">

<Run id="field-wins" />


`self` is a complete instance from the first line of `init`, so `init`
may call the instance's own methods:

<Run id="init-calls" />

JavaScript's `new` is close to Drip's: for an ordinary class without a
superclass, it creates the object and binds it as `this` before the
constructor body runs. Unlike Drip, a JavaScript constructor *may*
return a different object, which then becomes the result of
`new`<Cite id="ecma262" />; Drip forbids that at compile time, which is
why its VM can always take slot 0 as the answer.

</More>

## A call that makes no garbage

Reading `o.m` on its own makes a **bound method** (*Classes, methods
and inheritance in Drip*), a small heap object holding the instance and
the method, because Drip lets you store `o.m` and call it later. So the
plain reading of `c.m(2)` is "read `c.m` (allocate a bound method),
then call it"; the bound method is garbage the moment `call` has
unpacked it, and in a loop of a million calls that is a million objects
for the collector.

So when the compiler has parsed `.name` and the next token is `(`, it
emits one instruction carrying the name and the argument count,
`invoke m 1`, with the receiver pushed first, in the slot that will
become the method's slot 0. Here is `invoke` in `vm.ts`, shortened:

```ts
const receiver = this.peek(argCount);
const field = receiver.fields.get(name);
if (field !== undefined) {
  this.stack[this.sp - argCount - 1] =
    field;
  return this.callValue(field, argCount);
}
const method =
  receiver.klass.methods.get(name);
this.call(method as ObjClosure, argCount);
```

It looks in the fields first, because a field holding a function
shadows a method of the same name; otherwise it calls the class's
method straight away, with no bound method:

<InvokeSteps client:visible />

Did it pay off? On the `method_calls` benchmark, in runs I did, the
best of nine runs took 704 ms with `invoke` and 932 ms in a copy whose
compiler never emits it, and the copy needed 48 collections where the
real VM needed none.

<Callout kind="definition">
**Method invocation**, in the VM, is the single instruction `invoke
name argc`, emitted when a property access is immediately called. It
looks the name up in the receiver's fields, then in its class's
methods, and calls what it finds with the receiver already in slot 0.
It means exactly what `get.prop` followed by `call` means, without
allocating a bound method.
</Callout>

<Examples of="method-invocation">

```text
class A { m() { print "method"; } }
fn f() { print "field"; }
let a = new A();
a.m();      # invoke 'm': method
a.m = f;
a.m();      # invoke 'm': field
```

</Examples>

The first `a.m()` finds no field `m`, so it calls the method. Then
`a.m = f;` gives the instance a field named `m`, and the same `invoke`
finds the field first and prints `field`, exactly as `(a.m)()` would.
(`let g = a.m;` is the case `invoke` cannot cover: the value has to
exist, so `get.prop` makes the bound method.)

## Inheritance by copying

The tree-walker found an inherited method by walking up the chain of
superclasses on every lookup; the VM does that walk once, when the
subclass is made. The `inherit` instruction copies the superclass's
whole method table into the new class, before the subclass's own
`method` instructions run, so an override simply overwrites the copied
entry and every later lookup is one probe in one table:

<Figure caption="B extends A: inherit copies A's table into B, then B's own methods are added on top." takeaway="After the copy, finding any method of B is one table lookup, however deep the chain.">
  <CopyDownFigure />
</Figure>

This is only correct because a Drip class can never gain or lose
methods after its declaration; if it could, the copies would go stale.
`super` needs one more piece: around a subclass's body the compiler
declares a hidden local named `super` holding the superclass, methods
that say `super` capture it as an upvalue (*Upvalues: capturing and
closing*), and `super.m(x)` compiles to `self`, the arguments, the
superclass through the upvalue, and `invoke.super 'm'`, which looks `m`
up in *that* class's table and calls it on the same instance.

<More title="More: the bytecode of super">

For `class B extends A { m() { return super.m() + "B"; } }`:

```text
== <script> ==
load.global         7 'A'
load.global         8 'B'
inherit
load.global         9 'B'
closure            11 fn m
  local 1
method             10 'm'
pop
close.upvalue
== m ==
load.local          0
load.upvalue        0
invoke.super        0 'm' (0 args)
```

`load.global 'A'` leaves the superclass in slot 1, the hidden `super`
local; `inherit` copies its methods into `B`; `m` captures slot 1; and
after the class body `close.upvalue` closes `super` into the upvalue.
Reading `super.m` without calling it compiles to `get.super`, which
makes a bound method, as `get.prop` does. JavaScript engines go further
than copy-down tables, with shapes and inline caches that remember where
a property was found at each access<Cite id="bynensmeurer2018" />; that
is the subject of *Shapes, inline caches and elements kinds*.

</More>
