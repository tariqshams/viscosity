## One loop is not a program

In the committed benchmark run, summing one field of 100,000 particles
was 8.5× faster in columns than in objects. That is a fact about one
loop. A program does more: it builds its data one `push` at a time
through the generated container, runs some loops that love columns and
some that do not care, and keeps bounds checks wherever Viscosity could
not prove an index safe. Whether all of that adds up to a faster program
is a separate question, and it needs a separate measurement; and whether
the faster program is still *right* needs many more programs than one.

<Analogy title="an engine on a test bench, and the drive to work">
A car's engine on a test bench gives one number; your drive to work
gives another, with traffic lights, hills and a cold start. Both are
real, but only the second tells you how long the drive takes.
<span slot="breaks">A commute changes every day; a benchmark program
does exactly the same work on every run, so what changes between runs is
only the machine, which is what the harness has to control.</span>
</Analogy>

<Callout kind="definition">
An **end-to-end benchmark** measures a whole program, compiled the way a
user would compile it, rather than a single loop written for the
benchmark. It answers "does my program get faster?" and includes
everything the compiler changed, good and bad.
</Callout>

## Five programs, and a harness

The programs live in `packages/bench/e2e/`, each ordinary JavaScript with
no annotations: **particles** (200,000 particles with 8 fields, moved for
200 frames), **ledger** (500,000 transactions, summed and filtered),
**heat** (diffusion on a 512 × 512 grid), **boids** (20,000 boids, each
averaging the next 64) and **n-body** (gravity between every pair of
1,500 bodies). Every program times its own hot section with
`performance.now()` and ends by printing one line of JSON with the time
and a checksum of its results; the checksum makes the work observable,
so no engine can delete it as dead code (*Benchmarking honestly*), and
lets the harness check that the compiled program computed the same
thing. The harness, `packages/bench/src/matrix.ts`, runs each program on
Node and on Bun; its core, simplified:

```ts
runOnce(orig); runOnce(comp); // warm-up
for (let i = 0; i < RUNS; i++) {
  a.push(runOnce(orig));
  b.push(runOnce(comp));
}
const checks = new Set(
  [...a, ...b].map((x) => x.check));
if (checks.size !== 1) throw new Error(
  `${f} on ${rt.name}: checksums differ`);
speedupBest = min(am) / min(bm);
```

`runOnce` starts a fresh process, so neither version inherits the other's
type feedback or garbage. The first line throws one run of each away; the
loop then alternates original and compiled, `RUNS` times (9 for the
committed results), so a noisy minute on the machine hits both; and a
fast wrong answer is not a result, because a single differing checksum
throws. Step through one program's measurement:

These are two rows of `results/matrix-2026-10-31.md`: the best of nine
runs of the original and of the compiled `heat`, on each engine. On Node,
columns made `heat` four times faster; on Bun they made no difference,
because Bun ran the *original* more than three and a half times faster
than Node did (the repository's notes suggest, without engine traces to
confirm it, that V8 boxes a double held in an object field while
JavaScriptCore does not, so columns fix more on V8). Across all five
programs the geometric mean was 2.54× on Node and 1.74× on Bun.

The first time this benchmark ran, n-body and boids were *slower* with
Viscosity. The bounds proofs of *Proving it safe* did not yet cover an
outer loop's counter used in an inner loop (n-body's `b[i].x` inside the
`j` loop), a start of `i + 1`, or a `j < b.length` that is one side of an
`&&` (boids' window loop), so every such access paid for a call to
`__vsc_bc`, 1,500 × 1,500 times per step. The fix was a more general
proof, not dropping the checks; today `viscosity explain` reports
`12 of 12 element accesses proven in bounds` for n-body. Benchmarking
only the programs where your compiler shines tells you nothing; the slow
results are the useful ones. Even so, a speed-up of 1.2× (n-body today)
is within what the matrix's own note calls noise on this VM (differences
under about 10%, and up to 2× between runs), so the honest summary is the
coarse one: particles, ledger and heat are several times faster on Node,
and boids and n-body a little.

<More title="More: whole-process time, the earlier run, Python, and warm-up">

The whole-process wall time, start-up and data building included, is
what a user waiting for the program sees: for particles on Node, the
median went from 527.4 to 182.7 ms, still almost three times faster.

An earlier run is committed too (`e2e-node-2026-10-31`, 3 runs per
version, medians, measured before a later fix to how checked writes store
their values). It said ledger 5.11× and boids 1.18×; the matrix says
ledger 3.75× best (4.08× median) and boids 1.31× (1.21×): same programs,
same machine type, hours apart.

The same question was asked of Python. In CPython, an update loop over
100,000 elements took 26.66 ns per element with objects, 43.31 with list
columns and 72.7 with `array('d')` columns (the committed `python-layouts`
results, a loop benchmark rather than a whole program): columns were
*slower*, because CPython makes a new float object for every
`array('d')` element it reads. However, the typed columns used about
4.9× less memory. So the Python plugin keeps objects unless you opt in.

Each program times its hot section once per process, so the time
includes the engine getting warm: V8 starts in its interpreter and moves
hot functions up to optimising compilers as it gathers
feedback<Cite id="v8-maglev" />. A microbenchmark harness waits for that
to finish; an end-to-end benchmark keeps it in, because a user's program
pays for it too.

</More>

## A folder of programs

*Testing compilers: differential, round-trip, fuzzing and shrinking* gave
the method: compile a program, run both versions, and let the original be
the oracle. One program checks one thing; however, Viscosity has to be
right about escapes, aliases, `try`, `NaN`, strings in number fields,
Python's integers, two parsers and a second implementation in Rust. That
takes many programs, and a way of using each one many times.

<Callout kind="definition">
A **test corpus** is a large, curated collection of programs used as test
inputs. Each program is chosen to exercise one case, and the tests are
generated from the collection, so adding a case means adding a file, not
writing test code.
</Callout>

The JavaScript corpus has 40 files, and the Python corpus 20, each
probing one decision:

<Examples of="test-corpus">

```js
// viscosity: ps=soa
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
let s = 0;
try {
  for (let i = 0; i < ps.length; i++)
    s += ps[i].x;
  ps[1000].x = 1;
} catch (e) {
  console.log('caught',
    e.constructor.name, e.message);
}
console.log(s);
```

</Examples>

This is `try_catch.js` (long lines wrapped), and it follows the rules
every corpus file follows. **One idea:** it asks a single question,
whether an out-of-bounds write inside `try` throws the same error after
compiling, and its name says so. **A header** on line 1 gives the
expected decision for every collection (`ps=soa`), so a compiler that
quietly stops optimising fails too. **Observable:** lines 11 and 12 print
the error's class and message, and the last line the sum, because a
difference that is not printed cannot be caught. **Small and
deterministic:** no timing and no randomness, so two correct runs always
print the same thing.

<Prompts ids={['corpus-what', 'corpus-observable']} />

Each file is then used by several tests, for different questions: the
differential test (and the header check), the test that both parsers
give byte-identical code and reports, and the Rust port's parity test.

## The reference as an oracle, and the fuzzer

How do you know the Rust version decides and emits exactly what the
TypeScript one does? By differential testing again, with the TypeScript
compiler as the oracle: `engine/rust/scripts/gen_expected.mjs` runs it on
every corpus file, every benchmark program and the extra programs written
for the port, in both bounds modes, and stores the compiled code and the
explain report each time (402 files in `engine/rust/tests/expected/`,
with the `--frames` reports and a few profiled builds). The parity test
recompiles every source in Rust and compares byte for byte; along the
way it found bugs in the TypeScript reference too.

A corpus has one limit: every file was written by someone who thought of
the case, so it keeps found bugs found but cannot find the case nobody
imagined. For that you need programs nobody wrote. Viscosity's fuzzer,
`engine/rust/scripts/fuzz.mjs`, generates seeded random programs and
checks both behaviour and parity; its first 8,000 programs turned up five
bugs in both engines (one: `ps[i].x = rhs` checked the index *before*
evaluating `rhs`, while the original evaluates `rhs` first, so out of
bounds the two threw different errors). Each bug was fixed and got a
corpus file, so the fuzzer finds and the corpus remembers:

<More title="More: what the corpus checks in Python, and corpora elsewhere">

The Python test cannot use Node's VM contexts, so it writes both programs
to a temporary folder, runs each with the real `python3`, and compares
standard output and, for a crash, the last line of standard error, where
Python prints the exception. The corpus file `ints_stay_ints.py` is a
typical trap: a careless `array('d')` column would turn the integer 6
into `6.0`; Viscosity gives `count` a list column, and it stays `int`.
The Rust fixtures are generated in both bounds modes so that the
unchecked code paths are covered too.

Language implementations live by their corpora. Test262, the conformance
suite for JavaScript itself, is a corpus of tens of thousands of test
files covering the language specification<Cite id="test262" />. Csmith is
the opposite strategy: a generator of random C programs that finds
compiler bugs by differential testing<Cite id="csmith" />. Real compilers
use both.

<Analogy extra title="a driving-test route">
A driving examiner does not invent a new route for every learner. There
is a route, chosen to include the hard junction, the hill start and the
school crossing, and every learner drives it; when someone finds a new
way to fail, a new turn is added to the route.
<span slot="breaks">A learner drives the route once; every version of the
compiler drives the whole route, every time, and has to pass every turn
exactly.</span>
</Analogy>

</More>

## What you learned

- An **end-to-end benchmark** measures whole programs as a user would
  compile them; the harness runs fresh, alternating processes and refuses
  a speed-up when checksums differ.
- On Node, particles, ledger and heat got several times faster; bounds
  checks in hot loops once made two programs slower, fixed by a more
  general proof.
- A **test corpus** is a folder of small programs, each probing one idea,
  stating its expected decisions and printing what could differ.
- The TypeScript compiler is the oracle for the Rust port; a fuzzer finds
  the unimagined cases, and each find becomes a corpus file.
