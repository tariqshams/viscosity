## Version 0.0.1, everywhere

Ask the Rust CLI and the TypeScript CLI their version and both say
`viscosity 0.0.1`. So does every package in the repository that could
ever be published. When this chapter was written, none of them was.
The repository had no git tags and no changelog either: as far as any
registry knew, Viscosity didn't exist. (All of them are published
now; the end of the chapter says how.)

Chapter 232 packed the TypeScript CLI for npm and found three bugs on
the way. Track B adds two more things to ship: the Rust crates, which
would go to crates.io, and `@viscosity/wasm`, the Rust engine as an npm
package (chapter 338). This chapter is about the work between "it
passes its tests" and "a stranger can install it", and about which
parts of that work exist.

<Callout kind="intuition">
A release is a ferry leaving. Up to the moment it sails you can fix
anything on board. Once it has sailed, whatever was on it is on the
other shore for good, and the only remedy is the next ferry. So the
crew walks a checklist on the quay, the same one every time.
</Callout>

<Callout kind="definition">
A **release process** is the repeatable set of steps that turns one
commit into published, versioned packages: choose the version number,
record what changed (a **changelog**), build each package, check it as a
user would get it, then **publish** it to its registry. Publishing is
the step that can't be undone: a crates.io version "can never be
overwritten, and the code cannot be deleted"<Cite id="cargo-publishing-guide" />,
and an npm name and version can never be used again, even after
`npm unpublish`<Cite id="npm-publish-docs" />.
</Callout>

## Where the numbers live

A release would change three version numbers by hand:

- `engine/rust/Cargo.toml`, `[workspace.package] version`. All six
  crates say `version.workspace = true`, so they inherit
  it<Cite id="cargo-workspaces" />, and the Rust CLI's `--version`
  is compiled from it (chapter 345).
- `engine/ts/packages/cli/package.json`, for `@viscosity/cli`.
- `engine/rust/packages/wasm/package.json`, for `@viscosity/wasm`.

CI checks one thing: that the packed TypeScript CLI's `--version`
matches its own `package.json`. The release script (below) checks the
rest, and stops unless both `package.json` files say what the crates
say. The two npm packages are the same compiler, promised
byte-identical, so one number for both says so plainly.

What the next number should be follows Semantic Versioning: a major
change for an incompatible API change, minor for a compatible feature,
patch for a compatible fix, and "anything MAY change" while the major
number is 0<Cite id="semver2" />. Cargo makes that last part precise.
A requirement accepts versions whose left-most non-zero part is the
same, so `"0.1"` accepts 0.1.9 but not 0.2.0. For a 0.0.z version the
left-most non-zero part is z itself: `"0.0.3"` means `>=0.0.3, <0.0.4`,
so a caret requirement treats every patch release as
incompatible<Cite id="cargo-specifying-deps" />.
So for a 0.y.z crate, a change in y counts as major and a change in z
as minor, and every 0.0.z release is a major change<Cite id="cargo-semver-guide" />.

That is why Viscosity's first version is 0.0.1, not 0.1.0. The number
says "experimental": someone who depends on `"0.0.1"` never gets 0.0.2
without asking for it. Moving to 0.1.0 would be the first promise that
fixes arrive compatibly.

What is the API, for Viscosity? The functions, yes, but also every
`explain` line (the parity fixtures already treat it as exact), the CLI's
flags, messages and exit statuses, and the compiled code itself, which
users run.

## The crates

The workspace `Cargo.toml` holds the shared metadata: version, edition,
`authors = ["Tariq Shams"]`, `license = "MIT"`, the repository URL,
`homepage = "https://viscosity.dev"`, a readme, keywords and a
`rust-version`. Each crate adds its own one-line
`description`, its categories and a `documentation` link (docs.rs for
the libraries). That covers what the Cargo book asks a crate to fill
in before publishing: a licence, a description, a homepage, a
repository and a readme<Cite id="cargo-publishing-guide" />.

`cargo package` (which `cargo publish --dry-run` also runs) is the real
test, and packaging found two problems, both fixed now. When this
chapter was first written, on `viscosity-core` it stopped at once:

```
error: failed to verify manifest at
  `crates/core/Cargo.toml`

Caused by:
  all dependencies must have a version
  requirement specified when packaging.
  dependency `viscosity-vir` does not
  specify a version
```

(cargo 1.97, wrapped.) The workspace referred to its own crates by path
only, as in `viscosity-vir = { path = "crates/vir" }`, and crates.io
doesn't accept dependencies on code outside crates.io. The fix the
Cargo book gives is to add a version next to the path, which is used
when the crate is published<Cite id="cargo-specifying-deps" />, and
every internal entry now carries `version = "0.0.1"`. The crates would
go up in order, `viscosity-vir` first, since each needs the one below
it on crates.io already. `core`'s dev-dependency on `frontend-js`
stays path-only: cargo leaves it out of the packaged manifest, which
breaks the cycle.

The second problem: `viscosity-vir` packaged, but its file list, from
`cargo package --list`, held `Cargo.toml`, `Cargo.lock` and `src/`,
and no licence text, because `crates/vir` had no LICENSE file. The MIT
licence asks for its notice to be "included in all copies or
substantial portions of the Software". Each crate has a LICENSE now,
and `cargo package --workspace` packages and verifies all six.

## The two npm packages

`@viscosity/cli` is built by `packages/cli/build.mjs`, which npm runs as
`prepack`. It uses esbuild to bundle the CLI, the engine, acorn,
acorn-walk and sucrase into one `dist/viscosity.mjs` for Node 18 or
later, so the package has no runtime dependencies at all. Then it
copies the repository's `LICENSE` and writes `THIRD_PARTY_LICENSES.txt`
with the full licence text of each of the three bundled packages, read
from `node_modules`. A dry run of `npm pack` lists five files: those
two, the bundle, a five-line `bin/viscosity.mjs`, and `package.json`.

`@viscosity/wasm` is built by its own `build.mjs` (chapter 337). Its
licence file is bigger, because the `.wasm` statically links 71
third-party crates. The script reads each crate's licence files from
cargo's sources and stops if one has none. oxc's crates are published
without a licence file, so it uses committed copies of oxc's own.

Both packages are scoped, under `@viscosity`. Scoped packages are
private by default on npm, so a first publish would need
`--access public`, and publishing under an organization's scope needs
that organization<Cite id="npm-publish-docs" />. Both `package.json`
files now set `"publishConfig": { "access": "public" }`, and the
engine's other workspace packages say `"private": true`, so npm
refuses to publish them by accident.

## What CI already checks

`.github/workflows/ci.yml` runs on every push and pull request, in five
jobs (chapter 344). Two matter most for a release. The TypeScript job
type-checks, runs every vitest test, then packs the CLI, installs the
tarball in an empty folder and runs `viscosity --version` and
`viscosity explain` from there. The Rust job installs the TypeScript
engine (the parity reference), checks formatting, runs
`cargo test --workspace` (parity, differential, multi-file, and a
fixed-seed run of the fuzzer) and clippy with warnings as errors,
builds the wasm crate in debug, and runs `cargo package --workspace`
(without the verifying build, to save time).

What CI doesn't run: wasm-bindgen and the `@viscosity/wasm` smoke test,
a long fuzzing campaign, or the benchmarks.

## A checklist from real scripts

Every command below exists in the repository today:

1. Choose the version by Cargo's rules, and set it in all three files.
2. In `engine/ts`: `npm ci`, `npm run typecheck`, `npm test`.
3. In `engine/rust`: `cargo fmt --all --check`, the clippy command,
   `cargo test --workspace`, `cargo package --workspace`.
4. A long fuzzing campaign: `cargo build -p viscosity-cli`, then
   `node scripts/fuzz.mjs --count 20000 --seed 7`.
5. `node packages/wasm/build.mjs`, then `node packages/wasm/smoke.mjs`,
   which packs `@viscosity/wasm`, installs it, and compares every corpus
   program it compiles with the TypeScript CLI's output.
6. `npm pack` in `engine/ts/packages/cli`, and install the tarball in an
   empty folder, as CI does.
7. If the release quotes numbers, re-run `packages/bench/src/matrix.ts`
   from `engine/ts`.
8. In `book`: `node scripts/check_chapters.mjs`.

9. `scripts/release.sh --dry-run`: the tests again, then
   `cargo publish --dry-run` and `npm publish --dry-run`. It needs no
   tokens.

One step has no script yet: writing a changelog. The commit history is
the only record of changes so far.

<Callout kind="engine" label="Under the hood">
The last step is `scripts/release.sh` without `--dry-run`. It stops
unless `NPM_TOKEN` and `CARGO_REGISTRY_TOKEN` are set and the git tree
is clean, runs the tests, then publishes the crates one at a time,
`viscosity-vir` first, skipping any version crates.io already has and
waiting for each to reach the index. Before the first publish, the dry
run couldn't check one crate at a time: `cargo package -p viscosity-core`
failed to verify, because `viscosity-vir` wasn't on crates.io yet.
`--workspace` verifies each crate against the ones packed before it.
Publishing is the only step that can't be undone, and it claims names: crates.io names are first
come, first served<Cite id="cargo-publishing-guide" />, and chapter 232
found that the plain `viscosity` name on npm belongs to someone else.
So the tokens were Tariq's to add (after creating the npm organization
`viscosity`), and running the script his decision.
</Callout>

That is how it went. On 2026-11-02 `scripts/release.sh --npm-only`
published both npm packages, then `--crates-only` published the crates
in dependency order, each waiting for the one below it to reach the
sparse index. Five went out. The sixth, `viscosity-wasm`, got HTTP 429:
"published too many new crates in a short period". crates.io limits
how fast an account creates *new* names, and a first release creates
them all at once. Ten minutes later a re-run skipped the five and
published the last, which is why a release script must be safe to
repeat. `cargo install viscosity-cli` now works too.

## What you learned

- A **release process** is the same steps every time: version,
  changelog, build, check as a user would, publish. Publishing is
  permanent on both crates.io and npm.
- Viscosity's version lives in **three files**, set by hand and checked
  by the release script. It is **0.0.1**: under Cargo's caret rule
  every 0.0.z release is incompatible with the next.
  (At 0.1.0, a breaking change would be **0.2.0**.)
- Packaging the crates found two problems, now fixed: **path
  dependencies** without versions, and no licence text in a crate.
- `@viscosity/cli` is one **esbuild bundle** with no runtime
  dependencies; `@viscosity/wasm` ships notices for 71 crates. Both
  set `publishConfig.access` to public.
- CI packs and installs the CLI and packages the crates on every push;
  the wasm smoke test, long fuzzing and benchmarks are run by hand.
  `scripts/release.sh` publishes; running it is Tariq's call. crates.io's
  **rate limit on new crates** stopped the sixth crate; a re-run finished.
