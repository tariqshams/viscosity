## Two bugs nobody's tests saw

While this Part was being written, two differences between the engines
turned up by hand. The chapter *Sizes and thresholds in Rust* noticed
that, given a profile, the Rust planner wrote "about 25 (measured)
elements" where the TypeScript one wrote "about 25 elements
(measured)". And *Reading a profile in Rust* fed both CLIs a
hand-edited profile:

```json
{ "ps": { "maxLength": "20" } }
```

The Rust CLI skipped the entry, since `"20"` is a string, and
transformed `ps`; the TypeScript CLI compared `"20" < 64` the
JavaScript way (which turns the string into a number), got `true`, and
kept `ps` as objects. Same program, different decisions, and yet at the
time `cargo test` passed everything. That is not a contradiction:
every test compares against *something*, on *some* inputs, and neither
bug was in any test's inputs. (Both are fixed now.)

<Analogy title="smoke alarms and gas detectors">
A smoke alarm does not smell gas, and a gas detector does not see
smoke. You do not fix that by buying a better smoke alarm; you put a
few different detectors in the house, and you know which one covers
which danger in which room.
<span slot="breaks">A detector either works or it does not; a test
layer also has *inputs*, so even the right kind of detector misses a
danger that never happens in the rooms it is placed in.</span>
</Analogy>

## Five oracles

An **oracle** is whatever a test trusts to give the right answer.
Here there are two: the original program (run it and see what it
prints) and the TypeScript engine (the reference, whose output is
saved as fixtures). Every layer compares an engine with one of them:

<Figure takeaway="Each test compares two of three things; a bug both engines share is invisible to the edge between them." caption="Parity, the wasm check and part of the fuzzer compare the two engines. The differentials and the rest of the fuzzer compare a compiled program with the original.">
  <OracleMap />
</Figure>

```text
layer         oracle         inputs
parity        TS fixtures    95 programs
node diff     the original   68 JS
python3 diff  the original   27 Python
wasm          TS fixtures    95 programs
fuzzer        TS + original  random JS
```

Read the table one row at a time, asking two questions of each layer:
what does it trust, and what does it feed in?

**Parity** (`parity.rs`, from the chapter *Round-trip tests across
engines*) compares code and explain text with the TypeScript output,
byte for byte, for every program in both bounds modes, plus 14
`--frames` fixtures and 4 `--profile` fixtures. Its oracle is the
reference, so it catches **divergence** (the two engines disagreeing),
and nothing else: if both engines are wrong in the same way, parity
passes, because it has nothing outside the two engines to compare with.

**The node differential** (`differential.rs`) runs each original and
compiled JavaScript program in an isolated context and compares
everything printed and thrown. Its oracle is the source program
itself, so it catches **miscompiles** (a compiled program that behaves
differently), even ones both engines share; however, it sees only its
68 programs, it compiles them only with bounds checks on, and a
difference in explain text never changes what a program prints, so
explain is invisible to it. **The python3 differential** does the same
for the 27 Python programs, comparing standard output and the last
line of standard error (the exception), so a difference earlier in
standard error, such as a warning, would pass.

**The wasm check** runs the same fixtures through the WebAssembly
build. I loaded the module this book serves in Node and ran all six
suites through `compileLanguage`: 190 of 190. It is the parity oracle on
a different target, so it catches whatever changes with the target;
its API takes no profile and returns no frames, so it cannot check
either.

**The fuzzer** (`scripts/fuzz.mjs`) generates random programs in the
part of JavaScript Viscosity cares about and checks each against both
oracles: the TypeScript output against the original under node, and
the Rust output against the TypeScript output (code, explain, frames,
and explain with a random profile). My run of its default, 300 programs
with seed 1, took 5.9 seconds: 134 of them were transformed, and 20 had
an early error inserted, which both engines must reject.

<Callout kind="definition">
**Engine parity** is two engines making identical decisions, held in
place by tests against different **oracles**: the reference engine's
output (for divergence), the source program's own behaviour (for
miscompiles), and both at once on generated inputs. A test catches
only what differs from its oracle, on its inputs, under its options.
</Callout>

<Formal title="What one test checks">

```text
pass(x)  ⇔  obs(E(x))  ≈  obs(O(x))
blind:   E(x) = O(x) ≠ right(x)
```

<span slot="read">A test with engine E, oracle O, an observation obs
(the text, or what the program prints) and an equality ≈ (bytes, or
"both have an error") passes on input x when what it observes of E's
answer equals what it observes of the oracle's. It is blind whenever E
and O give the same wrong answer, and to every x it never tries.</span>
</Formal>

Put the two hand-found bugs through that rule. For parity, E is the
Rust engine, O the TypeScript fixtures, obs the explain text and ≈
"the same bytes"; the wording bug made the two texts differ, so parity
*could* have failed, but only on an input x compiled with a profile, and
no x in its set had one. For the node differential, obs is what the
program prints, and a change of wording prints nothing different, so
it could never fail, whatever its inputs. Two different reasons for
silence: the wrong inputs, and the wrong observation.

The first two are opposites. The line deleted from the Rust builder

## Inputs, options, and what counts as equal

Both hand-found bugs needed `--profile`, and at the time no fixture was
compiled with one, the fuzzer never passed one, and the wasm API still
cannot take one: an option no layer sets is untested in every layer,
however good the layers are. The second bug needed more, a profile no
profiling run would ever write, because `viscosity profile` always
writes numbers. The profile file is an input too, and every profile a
test could have used came from the profiler, so the string `"20"` was
outside every layer's reach: a layer finds only what its inputs can
produce, which is why the fix added hand-written odd profiles rather
than more profiled runs.

Then there is what counts as equal.
Parity says bytes; the differential says printed output and the error
message; the python3 test says standard output and the last line of
standard error; the fuzzer says bytes for output and presence for
errors. Each looser rule hides something, and each stricter one would
fail on differences nobody cares about.

<Prompts ids={['ep-option', 'ep-input', 'ep-equal']} />

The fixes followed from the map, and the engines have them now: four
profile fixtures and a random profile in every fuzzer batch;
`profile_cli.rs`, which feeds odd profiles to both CLIs; and
`early_errors.rs`, which checks that both engines reject 108 invalid
programs and accept 77 valid ones close to them. One gap is left: the
fuzzer generates JavaScript only. The Python plugin had one ad hoc run
of 800 random programs when it was ported (its commit message says
so), but there is no committed Python fuzzer.

<Callout kind="engine" label="Under the hood">
The fuzzer is cheap because two of its three engines run in the same
process: the TypeScript compiler and Node's `vm` module are both
JavaScript. The Rust engine is reached through its CLI, one
`viscosity build a.js b.js ... -o dir/` call per batch of 250 files, so
the cost is a few process starts per batch rather than per program.
The README puts the campaign at about 50,000 programs: the five bugs
turned up in roughly the first 8,000, and 42,000 more after the fixes
found nothing. The chapter *Fuzzing the Rust engine* goes further.
</Callout>

## Five bugs past every test

When the fuzzer of this chapter was written, `cargo test` was green,
and random programs still found five bugs that every test had missed.
Here is one, as the fuzzer's reducer left it (reformatted):

```js
function local1(m) {
  const ls = [];
  for (let i = 0; i < 64; i++)
    ls.push({ a: i, b: i });
  let t = 0;
  for (let i = 0; i < ls.length; i++) {
    ls[i].b += m;
    t += ls[i].b;
  }
  ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
  t += ls[1].a;
  return t;
}
console.log(local1(0), local1(1));
```

The function builds 64 records, adds `m` to every `b` while summing
them, and then does something odd on purpose: it stores `7` into
`ls[1].a`, where the right-hand side first pushes a 65th record (the
comma operator runs `ls.push(...)`, throws its answer away, and gives
`7`). Under node it prints `2023 2087`. Compiled by the TypeScript
engine from just before the fix (I ran it here), it printed `2017
2081`: the `7` was lost. The old engine had written the store like
this (the compiled `push` takes the field values in order; wrapped):

```js
ls.a[__vsc_bc(ls, 1, 'a', true)] =
  (ls.push(0, 0), 7);
```

JavaScript works out *where* to store (here `ls.a`, the column of `a`
values) before it runs the right-hand side<Cite id="ecma262-assignment-order" />.
The 65th push overflows the column's capacity of 64, so `grow()`
installs a new, larger column, and the `7` goes into the old one, which
nothing reads any more (*Growing collections* explained the growing).
Today both engines write this instead, which checks the index first
and stores last, into whatever column exists by then (wrapped):

```js
__vsc_set(ls, 'a', __vsc_bk(ls, 1),
  (ls.push(0, 0), 7), 'a');
```

Compiled by today's Rust CLI (release build, rustc 1.97), the program
prints `2023 2087`, as the original does. Nobody writes a test like
`local1`, because nobody thinks of it; that is the reason to let a
machine write tests.

**Fuzzing** (*Testing compilers*) means running a program on huge
numbers of machine-made inputs and checking each run against an
**oracle**, something that says whether the run was right. This chapter
is about the two ways of making those inputs.

## Two ways to search

<Analogy title="exploring a cave with chalk">
You explore a cave by chalking a mark at every junction you reach.
Each morning you go back to the deepest spot where you found an
unmarked junction yesterday and wander a little further from there;
wanders that only pass old marks are forgotten. You never know where
the treasure is, yet you are pulled steadily into parts of the cave
nobody has seen.
<span slot="breaks">A cave stays the same between visits; a program's
paths depend on the input in ways the chalk marks do not show, so two
inputs that reach the same junctions can still behave very
differently.</span>
</Analogy>

<Analogy extra title="a driving examiner">
An examiner who knows the rules of the road plans a fresh route for
every test drive: a roundabout here, a hill start there, a reversing
bay at the end. Every route is a legal drive, and over hundreds of
tests every kind of manoeuvre comes up, in every combination.
<span slot="breaks">A real examiner learns from experience which
routes catch people out; the generator in this chapter learns nothing
from its runs, and gets new kinds of route only when a person edits
it.</span>
</Analogy>

## Coverage: counting edges

To know what a run reached, a coverage-guided fuzzer compiles its
target with a few extra instructions at every branch (that is
**instrumentation**, from *Profile-guided optimization*). AFL, the
fuzzer that made this style famous, gives every basic block a random
number and adds, in effect, these three lines at the start of each
one<Cite id="afl-technical-details" />:

```c
cur = <random number for this block>;
shared_mem[cur ^ prev]++;
prev = cur >> 1;
```

`shared_mem` is a 64 kB array of counters shared with the fuzzer. The
index `cur ^ prev` (`^` is exclusive or, which mixes two numbers into
one) depends on *both* the block we are in and the block we came from,
so each counter stands for an **edge**: a step from one block to
another. The shift on the last line makes A→B and B→A land on
different counters. Why edges and not blocks? Two runs can visit
exactly the same blocks along different edges:

<Figure caption="Both runs visit A, B, C and D. A block counter sees nothing new in run 2; an edge counter sees three new edges." takeaway="Edges tell paths apart that blocks cannot.">
  <EdgeFigure />
</Figure>

An input whose run reaches a new edge (or a much larger hit count on an
old one; AFL sorts counts into buckets such as 1, 2, 3, 4 to 7) is kept
and changed further, and every other input is thrown away. In Rust,
`cargo fuzz` drives libFuzzer the same way; you write a target that
takes raw bytes, and it needs a nightly compiler for its sanitizer
flags<Cite id="cargo-fuzz-book" />.

<Callout kind="definition">
A **coverage-guided fuzzer** changes (**mutates**) inputs it has kept,
runs the instrumented target on each one, and keeps an input only if
its run reached **new coverage**, such as a branch edge no earlier
input reached. The kept inputs (the **corpus**) grow towards code no
input has reached. A **generation-based** fuzzer writes every input
from a grammar or model instead, and nothing a run reached feeds back.
</Callout>

<Formal title="The keep rule">

```text
E(x) = { (a, b) : the run on x steps
         from block a to block b }
keep x  ⟺  E(x) ⊄ Seen
Seen := Seen ∪ E(x)
```

<span slot="read">E of x is the set of edges the run on input x took. The
fuzzer keeps x exactly when E of x is not contained in Seen, the edges
every earlier run took (the symbol ⊄ reads "is not a subset of"). Then
it adds the new edges to Seen, so the same edge never counts as new
twice.</span>
</Formal>

## Why Viscosity generates programs

For Viscosity, mutated bytes are a poor input. Almost every byte string
is a syntax error, which the engine refuses while parsing, so the
analyses this Part ported never run; and the most useful oracles need a
program that *runs*, because they compare the original program with the
compiled one under node. As such, `engine/rust/scripts/fuzz.mjs` is
generation-based, like Csmith, a random generator of C programs built
to test C compilers<Cite id="csmith" />. It knows
the slice of JavaScript Viscosity cares about (arrays of records pushed
in loops, field reads and writes, escapes, out-of-bounds reads inside
`try`, annotations) and writes valid programs in it.

Every program comes from a seed, and one small function ties the
pieces together:

```js
function programAt(seed, k) {
  const s = programSeed(seed, k);
  return withEarlyError(generate(s), s);
}
```

`programSeed` mixes the campaign seed with the program's number `k`
into a new 32-bit seed (by multiplying and shifting, so that nearby
`k`s give unrelated seeds); `generate(s)` builds a program from a
random-number generator started at `s`; and `withEarlyError` gives about
one program in 20 an error that JavaScript must reject before running
(a redeclared `let`, a stray `break`, and so on), which both engines
must then refuse. Because program `k` depends only on `(seed, k)`, any
program can be made again on its own (the next chapter, *Shrinking a
failing program*, runs it and follows what it finds).

## What you learned

- **Fuzzing** checks machine-made inputs against an **oracle**.
- A **coverage-guided** fuzzer keeps a mutated input only when its run
  reaches new coverage; AFL counts branch **edges**, which tell apart
  paths that visit the same blocks.
- A **generation-based** fuzzer such as `fuzz.mjs` writes valid
  programs from a seed, with no feedback; Viscosity needs that because
  its oracles run the programs.
- A per-program **seed** makes every generated program replayable on
  its own.

## Running it

*Fuzzing the Rust engine* built up to `scripts/fuzz.mjs`, a
generator that writes a valid program from a seed. Here is a run I did
for this chapter, on the current engine (release build, rustc 1.97,
node 22, on a shared cloud VM; wrapped):

```
$ node scripts/fuzz.mjs --count 300 --seed 5
  250/300 programs, 0 failing
  300/300 programs, 0 failing
fuzz: seed 5, 300 programs (138
  transformed, 178 may go out of bounds,
  11 with an early error), 0 failing,
  4.6 s
```

"Transformed" means the engine rewrote at least one collection, so the
compiled program really differs from the original; programs that "may
go out of bounds" are checked only with `--bounds check`, since
`--bounds assume` trusts a program not to.

Every program meets three **oracles**. **Behaviour**: the original and
the compiled program run in a fresh `vm` context of node (a separate set
of globals, so one program cannot disturb the next)<Cite id="node-vm" />,
and must print the same lines and throw the same error. **Parity**: the
TypeScript and Rust engines must give the same compiled code, explain
text and code frames, byte for byte (*TypeScript vs Rust: differential
tests*). **Early errors**: both must reject the programs that were
given one. The TypeScript engine runs inside the script; the Rust one is
reached through its CLI, one `viscosity build a.js b.js ... -o dir/`
per batch of 250 programs, so a process start is paid per batch, not
per program.

Each program's seed depends only on the campaign seed and its number,
which is why `--seed 5 --only 3` can rebuild program 3 alone. Here is
the mixing function from `fuzz.mjs` (rewrapped); the program it prints

## Delete, ask, keep or undo

<Analogy title="a string of fairy lights">
One dead bulb has put out a whole string of fairy lights. Rather than
test the fifty bulbs one at a time, you swap in good bulbs for half of
them: if the string lights up, the fault was in that half. Halve again,
and in a handful of tries you hold the bad bulb.
<span slot="breaks">A string of lights has one bad bulb; a program can
need two lines at once (a push and the store it spoils), which is why
the reducer does not stop at halves but keeps trying smaller and
smaller chunks.</span>
</Analogy>

<Analogy extra title="leaving ingredients out of a recipe">
A cake keeps upsetting your stomach, so you bake it again with half the
ingredients left out, and then with the other half, until you know which
one is to blame.
<span slot="breaks">Leave out the flour and you no longer have a cake at
all, so "it did not upset me" tells you nothing; a program with half its
lines deleted is often not a program either, which is why the reducer
throws away any try that does not parse.</span>
</Analogy>

The reducer is **line-based delta debugging**. It starts with chunks
of half the lines and tries deleting each chunk in turn; it keeps a
deletion if the program still fails in the same way, and otherwise puts
the lines back and moves on by one chunk. When a whole pass changes
nothing, it halves the chunk, down to single lines. Step through it on
an eight-line program whose failure needs lines 2 and 5:

"Fails in the same way" is a function inside `reduce` (trimmed):

```js
const stillFails = (lines) => {
  const code = lines.join('\n') + '\n';
  if (!prog.early && !parses(code))
    return false;
  // ... compile it, and run it ...
  return failuresOf(p, rust)
    .some((x) => x.kind === kind);
};
```

It joins the remaining lines back into a program; a try that acorn
cannot parse counts as "passes" (unless the program was *meant* to
contain an early error), which is the missing-flour rule; and the try
is a failure only if one of its failures has the same **kind** as the
original, such as `behaviour-check` or `ts-crash`. Each call costs a
compile and two runs, which is why big chunks come first.

<Callout kind="definition">
**Delta debugging** shrinks a failing input by deleting parts of it
while a test still reports the failure. The result is **1-minimal**
when deleting any single remaining part makes the failure go away.
`fuzz.mjs --reduce` deletes chunks of lines, halving the chunk size to
1, and counts a try as failing only if it parses and shows the **same
kind** of failure.
</Callout>

<Formal title="1-minimal">

```text
fails(P) ∧ ∀ l ∈ P : ¬ fails(P ∖ {l})
```

<span slot="read">The reduced program P still fails, and for every line
l in P, the program with l removed (P minus l) does not fail. It says
nothing about removing two lines at once, or about whether some other,
smaller program would fail too.</span>
</Formal>

## Same kind, not same meaning

The reducer keeps the *kind* of failure, not what the program meant,
and the two can drift apart. Here are three of the five, as the reducer
left them (wrapped; the first is shortened, since the last chapter showed
it whole):

<Examples of="fuzzing">

```js
function local1(m) { const ls = [];
  /* 64 pushes, a loop over b */
  ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
  t += ls[1].a; return t; }
console.log(local1(0), local1(1));
```

```js
let cells = [];
for (let i = 0; i < 64; i++)
  cells.push({ a: Math.sin(i) });
for (let i = 0; i < 5; i++)
  cells.push({ a: cells[i % cells.length]
    .a * cells[i % cells.length].a });
```

```js
const cells = [];
for (let i = 0; i < 70; i++)
  cells.push({ b: (i * 37) % 11 });
for (let i = 0; i < cells.length; i++) {
  const p = cells[(k++, i)]; s0 += p.b; }
```

</Examples>

The first is program 90, the lost store, intact; the reducer only
removed lines that had nothing to do with it. The second is program 31:
a push whose new record reads two other elements, and the old engine
crashed on it with `internal error: overlapping rewrites at 741-801`,
because it rewrote the whole object literal as one piece while also
rewriting the reads inside it. The third is program 12, and it is a
trap. Its `let k` and `s0` declarations were deleted, so the *original*
now throws `ReferenceError: k is not defined`. The compiled program
still differed, though: the old emitter copied the index `(k++, i)`
without its brackets and wrote `const p = k++, i;`, which is a
`SyntaxError` (`Missing initializer in const declaration`). A
ReferenceError against a SyntaxError is still a `behaviour-check`
failure, so the reduction was accepted. The bug survived the
shrinking; the program around it stopped making sense. Read a reduced
program before you trust it.

## What the five were

The engine's README lists them as bugs 11 to 15, each now with a
program of its own in the test corpus:

```
bug                     found as
rhs ran after the check behaviour
store into old column   behaviour
rewrite in push/array   ts-crash
rewrite in an index     ts-crash
(k++, 7) as an index    behaviour
```

All five were in both engines, because the port mirrors the reference
line for line, so the parity oracle, which compares the engines with
each other, was blind to every one of them; the behaviour oracle and
the TypeScript crash found them. After the fixes, the README records a
further 42,000 programs (seeds 5 to 7 and 101 to 103, with the
generator extended to the constructs that found the bugs) that found
nothing.

## Did coverage plateau?

When this chapter was first written, I measured the line coverage of

The fuzzer covered *fewer* lines than the hand-written programs, yet
found what they missed, and ten times the programs added three lines.
Each of the five bugs needed a combination: a write whose right-hand
side pushes, an access inside a push. Line coverage says a line ran,
not what it ran with; that is one reason AFL counts edges and hit
counts, and a generator like this one finds new combinations only when
someone teaches it new constructs, as happened after the first finds.

## What you learned

- `fuzz.mjs` checks every program against three **oracles**:
  behaviour, parity and early errors.
- **Delta debugging** deletes chunks while the failure stays, halving
  the chunk to 1, which leaves a **1-minimal** program.
- The reducer keeps the failure's **kind**, not the program's meaning,
  so read the result before you trust it.
- Bugs that live in both engines are invisible to **parity**.
- **Line coverage** flattened out while the bugs hid in
  **combinations** of features.
