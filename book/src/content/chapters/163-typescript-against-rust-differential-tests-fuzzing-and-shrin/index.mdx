## Two bugs nobody's tests saw

While the Rust chapters were being written, two differences between the
engines turned up by hand. Given a profile, the Rust planner wrote "about
25 (measured) elements" where the TypeScript one wrote "about 25 elements
(measured)"; and fed a hand-edited profile, `{ "ps": { "maxLength": "20"
} }`, the Rust CLI skipped the entry and transformed `ps`, while the
TypeScript CLI compared `"20" < 64` the JavaScript way and kept it. Same
program, different decisions, and at the time `cargo test` passed
everything. That is not a contradiction: every test compares against
*something*, on *some* inputs, and neither bug was in any test's inputs
(both are fixed now, as *Profiles in Rust: writing and reading them*
told).

<Analogy title="smoke alarms and gas detectors">
A smoke alarm does not smell gas, and a gas detector does not see smoke.
You do not fix that by buying a better smoke alarm; you put a few
different detectors in the house, and you know which one covers which
danger in which room.
<span slot="breaks">A detector either works or it does not; a test layer
also has *inputs*, so even the right kind of detector misses a danger
that never happens in the rooms it is placed in.</span>
</Analogy>

## Five oracles

An **oracle** is whatever a test trusts to give the right answer. Here
there are two: the original program (run it and see what it prints) and
the TypeScript engine (the reference, whose output is saved as
fixtures). Every layer compares an engine with one of them:

<Figure takeaway="Each test compares two of three things; a bug both engines share is invisible to the edge between them." caption="Parity, the wasm check and part of the fuzzer compare the two engines. The differentials and the rest of the fuzzer compare a compiled program with the original.">
  <OracleMap />
</Figure>

```text
layer         oracle         inputs
parity        TS fixtures    95 programs
node diff     the original   68 JS
wasm          TS fixtures    95 programs
fuzzer        TS + original  random JS
```

**Parity** (`parity.rs`) compares code and explain text with the
TypeScript output, byte for byte, for every program in both bounds
modes, plus 14 `--frames` and 4 `--profile` fixtures. It catches
**divergence** and nothing else: if both engines are wrong in the same
way, parity passes. **The node differential** (`differential.rs`) runs
each original and compiled JavaScript program in an isolated context and
compares everything printed and thrown, so it catches **miscompiles**,
even shared ones, but only on its 68 programs, and explain text never
changes what a program prints. **The wasm check** runs the parity fixtures
through the WebAssembly build. And **the fuzzer** (`scripts/fuzz.mjs`)
generates random programs and checks each against both oracles; its
default run, 300 programs with seed 1, took a few seconds here (134 of
them transformed, 20 with an inserted early error that both engines must
reject).

```text

```

```text
TS:   about 20 elements (measured)
Rust: about 20 (measured) elements
```

The first is what `cargo test` reports today: all 190 fixture pairs
agree (54 of them belong to the Python plugin, which has a deep dive of
its own, *The Python plugin in Rust*). The second is the smallest kind of divergence,
a change of wording with the same decision, which only a layer that
compares text *and* runs with a profile can see; at the time no layer
did both, which is why it passed.

<Callout kind="definition">
**Engine parity** is two engines making identical decisions, held in
place by tests against different **oracles**: the reference engine's
output (for divergence), the source program's own behaviour (for
miscompiles), and both at once on generated inputs. A test catches only
what differs from its oracle, on its inputs, under its options.
</Callout>

The fuzzer's five finds were all in *both* engines, because the port
mirrors the reference line for line; parity cannot see a bug both share,
so every one was found by an oracle outside the two engines, the
behaviour check or the rule that the TypeScript engine must not crash on
a valid program. The fixes that followed came from the map: profile
fixtures, a random profile in every fuzzer batch, odd hand-written
profiles in `profile_cli.rs`, and `early_errors.rs`.

<Prompts ids={['ep-shared']} />

<More title="What counts as equal, and the gaps left">

<Formal title="What one test checks">

```text
pass(x)  ⇔  obs(E(x))  ≈  obs(O(x))
blind:   E(x) = O(x) ≠ right(x)
```

<span slot="read">A test with engine E, oracle O, an observation obs
(the text, or what the program prints) and an equality ≈ (bytes, or
"both have an error") passes on input x when what it observes of E's
answer equals what it observes of the oracle's. It is blind whenever E
and O give the same wrong answer, and to every x it never tries.</span>
</Formal>

Parity says bytes; the differential says printed output and the error
message (its Python half, for the 27 Python programs, says standard
output and the last line of standard error); the fuzzer says bytes for output and *presence* for
errors, because oxc and acorn word their messages differently. Each
looser rule hides something, and each stricter one would fail on
differences nobody cares about. The string `"20"` was outside every
layer's reach for another reason: every profile a test could use came
from the profiler, which always writes numbers. One gap is left: the
fuzzer generates JavaScript only, and there is no committed Python
fuzzer.

<Analogy extra title="checking a translation">
Two people translate the same letter; comparing their translations
catches a slip either one made alone, but if both misread the same
smudged word, they agree perfectly and are both wrong. To catch that, you
have to ask the person who wrote the letter.
<span slot="breaks">The letter writer can always be asked; a program's
behaviour is only observed on the inputs and options a test actually
runs.</span>
</Analogy>
</More>

## Five bugs past every test

Here is the heart of one of the five, as the fuzzer's reducer left it
(shortened; `ls` holds 64 records `{ a, b }`, and a loop over them adds
`m` to every `b` and sums them into `t`):

```js
ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
t += ls[1].a;
```

The store into `ls[1].a` pushes a 65th record before it gives `7` (the
comma operator). Called with 0 and 1, the whole program prints `2023 2087` under node;
compiled by the TypeScript engine from just before the fix, it printed
`2017 2081`. The
old engine wrote `ls.a[...] = (ls.push(0, 0), 7)`, and JavaScript works
out *where* to store (the column `ls.a`) before it runs the right-hand
side<Cite id="ecma262-assignment-order" />; the push overflowed the
column's capacity of 64, `grow()` installed a new column, and the `7`
went into the old one. Today both engines store last, through
`__vsc_set`. Nobody writes a test like this, which is the reason to let a
machine write tests.

<More title="The whole program">

```js
function local1(m) {
  const ls = [];
  for (let i = 0; i < 64; i++)
    ls.push({ a: i, b: i });
  let t = 0;
  for (let i = 0; i < ls.length; i++) {
    ls[i].b += m;
    t += ls[i].b;
  }
  ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
  t += ls[1].a;
  return t;
}
console.log(local1(0), local1(1));
```

Compiled by today's Rust CLI (release build, rustc 1.97), it prints
`2023 2087`, as the original does; the store became `__vsc_set(ls, 'a',
__vsc_bk(ls, 1), (ls.push(0, 0), 7), 'a')`, which decides the bounds
check first and stores last, into whatever column exists by then.
</More>

## Two ways to search

<FuzzLoopSteps client:visible />

A **coverage-guided** fuzzer such as AFL mutates inputs it has kept, and
keeps a new one only if its run reached something no earlier run did.
To know what a run reached, the target is compiled with a few extra
instructions in every basic block (**instrumentation**): AFL gives each
block a random number and adds, in effect, these three
lines<Cite id="afl-technical-details" />:

```c
cur = <random number for this block>;
shared_mem[cur ^ prev]++;
prev = cur >> 1;
```

The index `cur ^ prev` depends on *both* the block we are in and the one
we came from, so each counter stands for an **edge**, a step from one
block to another, and the shift makes A→B and B→A land on different
counters. Edges matter because two runs can visit the same blocks along
different paths:

<Figure caption="Both runs visit A, B, C and D. A block counter sees nothing new in run 2; an edge counter sees three new edges." takeaway="Edges tell paths apart that blocks cannot.">
  <EdgeFigure />
</Figure>

<Callout kind="definition">
A **coverage-guided fuzzer** changes (**mutates**) inputs it has kept,
runs the instrumented target on each one, and keeps an input only if its
run reached **new coverage**, such as a branch edge no earlier input
reached. The kept inputs (the **corpus**) grow towards code no input has
reached. A **generation-based** fuzzer writes every input from a grammar
or model instead, and nothing a run reached feeds back.
</Callout>

<Examples of="coverage-guided-fuzzing">

```rust
// a sketch, not in the repository
fuzz_target!(|data: &[u8]| {
    if let Ok(s) = from_utf8(data) {
        let o = CompileOptions::default();
        let _ = compile(s, &JsPlugin, o);
    }
});
```

</Examples>

This is what a `cargo fuzz` target for the Rust engine would look like:
libFuzzer calls the closure over and over with bytes it has mutated
towards new edges, the closure compiles them if they are valid UTF-8,
and any panic counts as a crash<Cite id="cargo-fuzz-book" />. Yet almost
every byte string is a syntax error, so such a target would mostly test
oxc's parser, and Viscosity's best oracles need a program that *runs*.
That is why `fuzz.mjs` is generation-based, like Csmith for C
compilers<Cite id="csmith" />: it knows the slice of JavaScript Viscosity
cares about and writes valid programs in it, each from a seed mixed from
the campaign seed and its number, so `--seed 5 --only 90` rebuilds
program 90 alone.

<Prompts ids={['fz-coverage', 'fz-blocks', 'fz-valid']} />

<More title="Guided against blind, run; and the keep rule">
The toy "bug" needs the three bytes `FUZ`. The blind search guesses three
letters at a time; the guided one changes one byte of an input it kept,
and keeps the result only when it passed a check no earlier input
passed. With this seed the guided search found `FUZ` at try 360; the
blind one needed 11,524 tries (one chance in 17,576 on each).

<Run id="guided-vs-blind" />

<Formal title="The keep rule">

```text
E(x) = { (a, b) : the run on x steps
         from block a to block b }
keep x  ⟺  E(x) ⊄ Seen
Seen := Seen ∪ E(x)
```

<span slot="read">E of x is the set of edges the run on input x took. The
fuzzer keeps x exactly when E of x is not contained in Seen, the edges
every earlier run took; then it adds the new edges to Seen.</span>
</Formal>

<Run id="program-seeds" />

That is the seed mixing of `fuzz.mjs`. `crates/cli/tests/fuzz.rs` runs
200 programs with seed 1 on every `cargo test`, and the README's
campaign was about 50,000 programs: the five bugs turned up in roughly
the first 8,000, and 42,000 more after the fixes found nothing.

<Analogy extra title="exploring a cave with chalk">
You chalk a mark at every junction you reach, and each morning go back
to the spot where you last found an unmarked junction and wander a
little further.
<span slot="breaks">A cave stays the same between visits; two inputs
that reach the same junctions can still behave very differently.</span>
</Analogy>
</More>

## Shrinking a failing program

A failing random program is twenty lines, and a person wants the two
that matter. `fuzz.mjs --reduce` finds them by **line-based delta
debugging**: it tries deleting chunks of half the lines, keeps a
deletion if the program still fails *in the same way* (the same kind of
failure, such as `behaviour-check`, and it must still parse), puts the
lines back otherwise, and halves the chunk size when a pass changes
nothing, down to single lines. The result is **1-minimal**: deleting any
one remaining line makes the failure go away.

<ReduceSteps client:visible />

<Prompts ids={['fz-reduce']} />

<More title="Same kind, not same meaning; and coverage that plateaued">
The reducer keeps the *kind* of failure, not what the program meant. One
of the five, as reduced, lost its `let k` and `s0` declarations, so the
*original* threw `ReferenceError: k is not defined`; the compiled one
threw a `SyntaxError`, because the old emitter copied the index `(k++,
i)` without its brackets into `const p = k++, i;`. Both are a
`behaviour-check` failure, so the reduction was accepted: the bug
survived the shrinking, and the program around it stopped making sense.
Read a reduced program before you trust it.

<Figure caption="Lines of the engine run, out of 2,614. The fuzzer ran fewer lines than the hand-written programs, and ten times as many fuzz programs ran three more." takeaway="Line coverage flattened out early; the bugs were in combinations.">
  <CoverageBars />
</Figure>

Measured at commit `c68daec` with c8, the fuzzer covered *fewer* lines
of the TypeScript engine than the hand-written programs, yet found what
they missed: each bug needed a combination, such as a write whose
right-hand side pushes. Line coverage says a line ran, not what it ran
with, which is one reason AFL counts edges and hit counts.
</More>

## What you learned

- Each test layer has an **oracle**: the TypeScript fixtures (parity,
  wasm), the original program (the differentials), or both (the fuzzer).
- **Parity** catches divergence and is blind to shared bugs; a bug hides
  where no layer feeds its input or option.
- A **coverage-guided** fuzzer keeps inputs that reach new **edges**;
  Viscosity's fuzzer **generates** valid programs from seeds instead.
- **Delta debugging** shrinks a failure to a **1-minimal** program,
  which still needs reading.
