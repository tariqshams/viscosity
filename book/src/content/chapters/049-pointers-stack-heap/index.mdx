## What is an arrow made of?

In the chapter on references you drew a variable as a box with an arrow
coming out of it, pointing at an object somewhere else, and you saw the
surprising thing that arrow does:

```js
const p = { x: 1 };
const q = p;
q.x = 5;
console.log(p.x); // 5
```

Changing `q.x` changed `p.x`, because there is only one object and both
names lead to it. However, memory is only a long row of numbered bytes,
with nowhere to draw an arrow; so what is actually stored in `p`, and
what does the engine do with it when you write `p.x`?

## Arrows are addresses

The answer is that `p` holds a number: the address where the object's
bytes begin. An "arrow" is that number, and following the arrow means
going to that address.

<Analogy title="an address written on a card">
You write a friend's home address on a card and give a copy of the card
to someone else. Now two people can find the same house; if one of them
paints the front door, the other sees a painted door when they visit.
Copying the card did not build a second house.
<span slot="breaks">A written address is words you can read; JavaScript
never lets you see or change the number in a pointer, only follow it.
And a house stays put even when every card is lost, while an object
nobody can reach any more is cleared away by the engine.</span>
</Analogy>

<Analogy extra title="a catalogue entry in a library">
A library's catalogue does not hold the books; each entry says which
shelf a book is on. Two entries (say, one under the author and one
under the subject) can lead to the same copy, and a note written in its
margin is seen by whoever fetches it next.
<span slot="breaks">A catalogue entry also carries the title and the
author; a pointer carries nothing but the address. The engine has to go
there and look to find out anything about the object.</span>
</Analogy>

<PointerSteps client:visible />

<Callout kind="definition">
A **pointer** is a stored address: a number, kept in memory, that says
where something else is. A JavaScript reference is a pointer the engine
manages for you: you can follow it (`p.x`) and copy it (`q = p`), but
you can never see or change the number inside. Running `p.x` means:
read the address in `p`, add the position of `x` inside the object, and
read the bytes found there.
</Callout>

<Formal title="Following a pointer">

```text
p.x      ≡  mem[ p + off(x) ]
q = p    ⇒  q and p hold the same address
```

<span slot="read">Reading p.x means the same as (that is what ≡ says)
reading memory at the address stored in p plus the offset of x, the
number of bytes from the start of the object to x. Copying p into q
means (⇒) that both hold the same address, so both lead to the same
bytes.</span>
</Formal>

How big is a pointer? On a 64-bit machine an address is 64 bits, so a
full pointer takes 8 bytes. V8, the engine in Chrome and Node, can
squeeze them into 4 bytes by storing a 32-bit offset from a base
address instead, a trick called pointer compression<Cite id="v8-pointer-compression" />.
Either way, an arrow costs real bytes, and following one costs a trip
to memory.

<Examples of="pointer">

```js
const p = { x: 1 };
const q = p;
q.x = 5;
p.x; // 5
```

```js
const p = { x: 1 };
const ps = [p, p];
ps[1].x = 9;
p.x; // 9
```

<Run id="mem-list" />

</Examples>

The first is the puzzle again, now with an explanation: `q = p` copies
an address, so the write through `q` lands in the one object. The
second shows that array slots hold pointers too: `ps` has two slots,
both holding `p`'s address, so `ps[1].x = 9` changes the object `p`
leads to. The runnable one builds pointers by hand, with an ordinary
array `mem` playing memory and its indexes playing addresses. Each list
node takes two slots, a value and then the address of the next node,
and address `0` means "no next node", the way `null` does. Start at
address 2, read the value, then follow the pointer stored next to it;
run it, then change the pointers to reorder the list without moving a
single value.

The common slip is expecting `=` to copy the object. Compare:

```js
const p = { x: 1 };
const q = p;           // same address
const r = { ...p };    // a new object
q.x = 5;
console.log(p.x, r.x); // 5 1
```

`q` holds `p`'s address, so it sees the change; the spread `{ ...p }`
from the chapter on copies builds a new object at a new address and
copies the *values* across, so `r.x` keeps its old value.

## Two neighbourhoods: the stack and the heap

Memory is one row, but a running program divides it into regions with
different jobs, and two matter to us. You met the first in *Recursion
and the call stack*: the **call stack**, where each active call keeps a
frame for its parameters and local variables. The second is the
**heap**: a large region where objects are put as they are
created<Cite id="mdn-execution-model" />.

<Analogy extra title="a notepad and a filing cabinet">
At your desk you keep a notepad. When a phone call starts you take a
fresh page for it, and when the call ends you tear that page off; if a
call is interrupted by another one, the new page goes on top. Anything
you need to keep after the call goes into the filing cabinet, and on the
page you only write which drawer it is in.
<span slot="breaks">You empty a filing cabinet yourself; the heap is
tidied by the engine, which reuses an object's bytes once nothing can
reach it any more. And notepad pages are all one size, while frames are
as big as their variables need.</span>
</Analogy>

<Analogy extra title="a pile of trays in a canteen">
Trays go onto a spring-loaded pile and come off in reverse order: the
last one put on is the first one taken off. A call's frame is a tray;
the call that is running right now is always the one on top.
<span slot="breaks">Trays sit there unused until someone takes them; a
frame exists only while its call runs, and is gone the moment the call
returns.</span>
</Analogy>

<HeapSteps client:visible />

<Callout kind="definition">
The **call stack** holds one frame per active call, with its parameters
and local variables, and a frame's memory is released when its call
returns. The **heap** holds objects, which stay as long as something can
still reach them, however many calls come and go. Together these are
the **stack and heap**: the two regions where a JavaScript program's
data lives<Cite id="mdn-execution-model" />.
</Callout>

<Examples of="stack-and-heap">

```js
function twice(v) {
  const n = v * 2;
  return n;
}
twice(3); // 6, and n is gone
```

```js
function make() {
  return { x: 6 };
}
const a = make();
a.x; // 6: the object outlived make
```

```js
function down(n) {
  return down(n + 1);
}
down(0);
// RangeError: Maximum call stack
// size exceeded
```

</Examples>

In the first, `v` and `n` live in `twice`'s frame, which is released
when the call returns; only the value 6 comes back. In the
second, the object is made on the heap, and `return` hands back its
address, so it survives the call that created it and `a` can still use
it. The third is the realistic warning: the stack has a limited size, and
a recursion that never stops pushes frame after frame until there is
no room left, which is the stack overflow
from the chapter on recursion.

## Two ways to store a thousand numbers

Now look at a frame holding both kinds of collection:

<Figure takeaway="Frames on the stack hold arrows into the heap." caption="Inside main’s frame, n holds a number; ps and xs hold pointers. The array ps is a row of pointers, and each points at a particle object somewhere else in the heap. The Float64Array’s three numbers sit in one contiguous block. Positions are illustrative: you never choose where things go.">
  <StackHeap />
</Figure>

The two collections hold the same kind of data in very different shapes.
`ps`, an array of objects, is really a row of **pointers**, each leading
somewhere else; to read every `x`, the machine reads a pointer, jumps to
an object, reads `x` there, and repeats. `xs`, a `Float64Array`, *is*
the numbers, packed side by side<Cite id="mdn-typed-arrays" />; to read
them all, the machine walks straight along one block.

<OtherLanguages>

```js
const xs = [1.5, 2.5];
const p = xs; // a reference
p[0] = 9;
console.log(xs[0]); // 9
```

```python
xs = [1.5, 2.5]
p = xs  # a reference, as in JavaScript
p[0] = 9
print(xs[0])  # 9
```

```java
double[] xs = {1.5, 2.5};
double[] p = xs; // a reference
p[0] = 9;
System.out.println(xs[0]); // 9.0
```

```c
double xs[] = {1.5, 2.5};
double *p = &xs[0]; /* an address */
*p = 9;             /* write there */
p = p + 1;          /* next double */
printf("%f\n", *p); /* 2.500000 */
```

</OtherLanguages>

JavaScript, Python and Java behave the same way: the variable holds a
reference, and the language keeps the address hidden. C makes it
visible: `&xs[0]` is the address of the first element, `double *p`
declares a variable that holds an address, `*p` means "the value at that
address", and `p + 1` moves on by one whole `double` (8 bytes), which is
the address arithmetic of the last chapter done by the language itself.

<Callout kind="engine" label="Under the hood">
The toy memory in the runnable example is closer to the truth than it
looks: in V8, JavaScript values live on the V8 heap and are referred to
by pointers<Cite id="v8-pointer-compression" />, and an object's fields
sit at known offsets from its start. Viscosity's job, in these terms,
is to take a heap full of small objects connected by pointers and
rewrite it into a few long, contiguous typed arrays; the next chapter
shows why the machine cares so much.
</Callout>

## What you learned

- A **pointer** is a stored address. JavaScript references are pointers
  that the engine manages for you; a full one is 8 bytes on a 64-bit
  machine, and copying one shares the object rather than copying it.
- `p.x` means: read the address in `p`, add the offset of `x`, read
  there.
- The **stack and heap**: call frames on the stack, released when the
  call returns; objects on the heap, kept while something can reach
  them.
- An array of objects is a row of pointers to objects that may be
  anywhere; a typed array is one contiguous block of numbers.
