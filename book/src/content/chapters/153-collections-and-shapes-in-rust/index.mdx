## Same pass, new home

*Finding collections, and inferring shapes* read the first steps of
`analysis.ts`: find the **candidate** bindings, then follow every load
of each through its uses, recording a **bailout** for any use Viscosity
cannot rewrite, all as closures sharing the locals of one big
`analyze`. The Rust
port, `analysis.rs`, produces the same collections and messages in the
same order; what changes is where the state lives, and how one thing
refers to another.

## The Analyzer struct

The TypeScript closures become methods of one struct, trimmed:

```rust
struct Analyzer<'m> {
    m: &'m Module,
    uses: Uses,
    loads: HashMap<BindingId,
        Vec<ValueId>>,
    collections: Vec<Collection>,
    collection_of_load:
        HashMap<ValueId, usize>,
    // ...stores, call sites, facts
}
```

`m` borrows the module for the lifetime `'m` (the analyser reads VIR and
never changes it); `uses` lists every use of every value; `loads` files
each load by binding. `HashMap` is `FxHashMap`, renamed on
import<Cite id="rustc-hash-readme" />; its order is arbitrary, which is
fine, because the analyser only *looks things up* in these maps, and
anything whose order reaches `explain` is a `Vec` or an
`IndexMap`<Cite id="indexmap-docs" />. One more detail matters later:

```rust
fn inst(&self, v: ValueId) -> &'m Inst {
    self.m.inst(v)
}
```

The instruction lives in the module, so the reference lasts for `'m`,
not for the borrow of `self`.

## Collections by number

<Analogy title="drawer numbers in a shared office">
In an office where several people share one cabinet, nobody may walk off
with a drawer, so they pass around drawer *numbers* instead: anyone with
"drawer 3" can open it, look inside and add a file, and the cabinet stays
where it is.
<span slot="breaks">If someone took a drawer out and the others slid
down, every number written on a note would be wrong. The analyser only
ever adds collections to the end and never removes one, so the numbers
stay right.</span>
</Analogy>

TypeScript's `collectionOfLoad` maps a value to the `Collection`
*object*; Rust's maps it to a `usize`, the collection's position in
`self.collections`. A `&mut Collection` in the map would keep the whole
`Vec` borrowed for as long as the map exists, while the pass keeps
changing it; a number borrows nothing.

## The worklist and the borrow checker

The second step, from `shapes_and_uses`, trimmed and rewrapped:

```rust
let mut work: Vec<ValueId> = self.loads
    .get(&self.collections[ci].binding)
    .cloned().unwrap_or_default();
while let Some(l) = work.pop() {
    for u in self.uses_of(l) {
        if let Some(follow) = self
            .use_of_collection(ci, l, u,
                &mut seen_param)
        {
            work.push(follow);
        }
    }
}
```

`work` starts as a copy of the loads of collection `ci`'s binding. Each
`pop` takes a value off the end; each of its
uses goes to `use_of_collection`, which accepts it (`.length`, a `push` of
a fresh record, an index), records a bailout, or, for a call to a
**known function** (declared once, only ever called directly) that
every caller passes this collection to, returns that function's
parameter, which goes on the stack so that the uses *inside* are checked
too. (The TypeScript closure pushes it itself; the method *returns* it,
because the stack is a local of its caller.)

And `uses_of(l)` returns a *copy* of the use list. Write
`self.uses.of(l)` in the `for` instead, and the loop holds a shared
borrow of `self` while its body calls a `&mut self` method; rustc 1.97,
on a small copy, says `error[E0502]: cannot borrow `*self` as mutable
because it is also borrowed as immutable`. The copy costs a few words
per use. `work.pop()` takes the *last* load first, as the TypeScript
does, and that order decides the order of the explain messages; step
through it on real VIR:

<Callout kind="definition">
**The collection pass in Rust** is steps 1 and 2 of `analysis.rs`.
`find_collections` files every load and store by binding, finds the known
functions, and makes a `Collection` for each `const` or `let` whose first
array store is `array.empty` or `array.new`. `shapes_and_uses` then runs a
stack-ordered worklist over each collection's loads, accepting `.length`,
`push` of a fresh record, indexing, and known calls (followed into the
parameter), and records a bailout, with its source site, for anything
else.
</Callout>

property `.sort` is one, and handing the array to the method call as its
receiver is another.

<More title="More: finding candidates with let-else, and the Formal rule">

Finding candidates is otherwise a line-for-line port. Where the
TypeScript filters every store and checks the length, Rust stops at the
first store of an array, with `let`-`else` (rewrapped):

```rust
let st = self.stores_of(binding.id);
let Some(&first_array_store) =
    st.iter().find(|&&x| matches!(
        self.inst(self.inst(x).args[0]).op,
        Op::ArrayEmpty | Op::ArrayNew))
else {
    continue;
};
```

A function that passes its parameter on to itself, `walk(qs, k + 1)`, is
not followed, and both engines report "passed to walk(), which is also
called with other values": safe, only less precise than it could be.

<Formal title="What the pass computes">

```text
refs(c) = loads(c) ∪ { param(f, k) |
  every call of f passes c at k }
ok(c) ⟺ ∀ r ∈ refs(c), ∀ u ∈ uses(r):
  u ∈ {.length, push(fresh), [i],
       known call}
```

<span slot="read">The values that refer to collection c are the loads of
its name, plus the k-th parameter of any known function f that every
caller passes c to as its k-th argument. The collection survives this
pass only if every use of every one of those values is a length read, a
push of a fresh record, an index, or such a known call; any other use is
a bailout.</span>
</Formal>

</More>

## One field or two?

A **shape** is the list of a record's field names, in order, plus what
each field may hold. The corpus program `comma_field_name.js` pushes `{
'a,b': i }` and then `{ a: i, b: 2 }`: one field whose name holds a
comma, then two fields, so two shapes, and both engines now refuse it
(`records with different fields or field order ({a,b} vs {a, b})`). The
reference used to compare shapes by joining the names into one string,
and `["a,b"]` and `["a", "b"]` both join to `a,b`; the port found it.

<Figure caption="The same two records, compared the old way and the way set_shape does it." takeaway="Compare lists, not joined text.">

</Figure>

Here is the Rust version, trimmed (the two messages are shortened to
comments):

```rust
fn set_shape(&mut self, ci: usize,
        r: ValueId, location: &str) {
    let Op::RecordNew { fields } =
        &self.inst(r).op
    else { unreachable!() };
    let aliased =
        self.uses.of(r).len() != 1;
    let c = &mut self.collections[ci];
    if c.fields.is_empty() {
        c.fields = fields.clone();
    } else if c.fields != *fields {
        // bail: "records with different
        // fields or field order (...)"
    }
    if aliased {
        // bail: "...could be aliased"
    }
}
```

<Examples of="rust-shape-pass">

```
ps (line 1) {x, tag} → struct of arrays
  · typed Float64Array columns for x;
    plain array columns for tag (may
    hold non-numbers)
```

</Examples>

The `let`-`else` takes the field list out of the record instruction
`r`; `aliased` is true if the record has a use besides the push; `c`
borrows collection `ci` mutably. The first record fixes the fields, and
every later one is compared with `!=`, which for two `Vec<String>`s
means the same name at each position, so no name can run into
another. A record with a
second use, such as `r.x = 500` after the push, is refused as possibly
**aliased**. The output is for a program that pushes `{ x: i, tag: 'a'
}` and updates `x` in a loop (real Rust CLI output, trimmed): one shape,
so struct of arrays; `x` is typed because the numeric fixpoint proved
every value stored there a number, while `tag` gets a plain array.

`fields` stays borrowed from an instruction while `c` borrows
`self.collections` mutably; that compiles only because `inst` returns
`&'m Inst` (with the default lifetime, rustc 1.97 says E0502 again).

<Callout kind="definition">
**The shape pass in Rust** is `set_shape` plus the numeric facts. The
first record a collection receives fixes its field list; every later
record must have exactly the same `Vec<String>` and exactly one use. Each
field is then typed by the fixpoint: numeric (a `Float64Array` column) if
every value stored there is provably a number.
</Callout>

## What you learned

- **The collection pass in Rust** keeps the TypeScript closures' state in
  `Analyzer<'m>`, with `inst` returning `&'m Inst`, so instructions do
  not borrow the analyser.
- Collections are referred to by **index**, and `uses_of` copies the
  use list so that the loop body can call `&mut self` methods.
- **The shape pass in Rust** compares field lists as `Vec<String>`s,
  exactly; comparing joined names let `{'a,b'}` pass for `{a, b}`.
