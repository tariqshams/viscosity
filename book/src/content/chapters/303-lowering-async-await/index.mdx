## A function that cannot wait

Here is the kind of async function you wrote in chapter 41:

```js
async function total(get) {
  const a = await get('a');
  const b = await get('b');
  return a + b;
}
```

It reads like three plain steps; however, `get('a')` might take a
second, and JavaScript runs on one thread, so if `total` really waited,
the whole program would freeze with it.
Instead, `await` gives control back: `total` returns a promise at once,
other code runs, and when the value arrives the function carries on
after the `await`<Cite id="mdn-await" />. The machine has only calls and
returns, so the compiler must build "carry on from here" out of those,
with chapter 302's trick of a `switch` on a state number.

## The rest of the work, as a value

Once the value of `get('a')` is known, what is left to do? Store it in
`a`, fetch `b`, add, return. That leftover work is the **continuation**
of the expression, and every async compiler writes it down as a function
that takes the missing value.

<Analogy title="a note on a half-built cupboard">
You are assembling a cupboard when you find a screw is missing, so you
order one and leave a note on the parts: "when the screw comes, fix the
left door, then hang both doors". Anyone can pick up the job later,
because the note says exactly what is left.
<span slot="breaks">A note is read by a person who can improvise; a
continuation is code, fixed in advance, and it gets the missing value
(the screw) handed to it as an argument.</span>
</Analogy>

<Analogy extra title="a stamped, addressed envelope">
When you write off for a brochure you enclose an envelope with your
address on it, so the company does not need to remember you; the answer
goes wherever the envelope says.
<span slot="breaks">The envelope only says where the answer goes; a
continuation also says what to do with it once it arrives, and it can
carry values with it (the variables it captured as a closure).</span>
</Analogy>

<Callout kind="definition">
The **continuation** of an expression is the rest of the computation
that is waiting for its value. Written as a function of that value, it
is a first-class value like any other: it can be stored, passed to
someone else, and called later.
</Callout>

<Examples of="continuation">

```js
// in: 1 + f(x)
// the continuation of f(x):
(v) => 1 + v
```

```js
// in: console.log(f(x) * 2)
(v) => console.log(v * 2)
```

```js
get('a').then((a) => {
  console.log('got', a);
});
```

</Examples>

In the first, once `f(x)` has a value `v`, all that is left is to add 1.
In the second the rest of the work doubles the value and prints it. In
the third, the callback given to `then` is the continuation of
`get('a')` written by hand; the promise calls it with the value when it
is ready<Cite id="mdn-promise" />.

<Formal title="Continuations as holes">

```text
E ::= □ | E + e | v + E | f(E) | ...
in E[e], the continuation of e is
  λv. E[v]
```

<span slot="read">An evaluation context E is a program with one hole
(the box) where work happens next: in the left operand of a plus, in the
right one once the left is a value, or in a call's argument. If e sits
in the hole of E, the continuation of e takes a value v and puts it in
the hole.</span>
</Formal>

## Continuation-passing style

Now push the idea all the way: suppose every function takes one extra
parameter, `k`, its continuation, and instead of returning its answer it
calls `k` with it. Nothing ever returns a value; every call says, as it
goes, what to do next. This way of writing programs is called
**continuation-passing style**, or **CPS**.

<Callout kind="definition">
In **continuation-passing style** every function takes its continuation
as an extra argument and passes its result to it rather than returning
it. Every call is then the last thing its caller does, and the order of
evaluation is spelled out in the program.
</Callout>

<Examples of="cps">

```js
function addK(a, b, k) { k(a + b); }
addK(2, 3, console.log); // 5
```

```js
function sumK(xs, i, k) {
  if (i === xs.length) return k(0);
  sumK(xs, i + 1, (s) => k(xs[i] + s));
}
sumK([1, 2, 3], 0, console.log); // 6
```

```js
readFile('a.txt', 'utf8',
  (err, s) => console.log(s));
```

</Examples>

The first adds, then hands the sum on to `k` (here `console.log`). The
second is recursive: to sum from `i`, sum the rest first, with a
continuation that adds `xs[i]` to that sum and passes the total to the
original `k`, so each continuation wraps the last. The third is Node's
older file API, CPS by design: `readFile` never returns the contents; it
passes them to the callback.

<Formal title="The call-by-value CPS translation">

```text
⟦x⟧    = λk. k x
⟦λx.e⟧ = λk. k (λx. ⟦e⟧)
⟦f a⟧  = λk. ⟦f⟧ (λg. ⟦a⟧ (λv. g v k))
```

<span slot="read">The translated form of a variable takes a continuation
k and passes the variable to it. A function becomes a function that
passes a translated function to k. A call f a works out f first and
names it g, then works out a and names it v, and then calls g with v and
with k, so the callee carries on with the caller's continuation. This is
the translation Plotkin studied in 1975<Cite id="plotkin1975" />.</span>
</Formal>

## Lowering await: cut, save, resume

To lower `total`, cut it at each `await`: the code after an `await`, up
to the next one, is that `await`'s continuation. Each piece ends by
asking a promise to call the next piece when it settles, and returns to
the event loop.

  <SplitFigure />
</Figure>

Three separate callbacks would work, but `a` must survive from piece 1
into piece 2, and loops or `try` blocks around an `await` would tangle
them; so compilers reuse chapter 302's machinery: one `step` function
with a `switch` on a state number, and the variables that live across an
`await` moved into a record on the heap (here, a closure's captured
variables, as in chapter 298).

<Run id="hand-lowered" />

`total` makes its promise and calls `step` once. Case 0 sets the next
state, starts `get('a')` and registers `step` itself as the continuation
(`rej` for failure), then returns, so "total() returned" prints before
state 1. When `get('a')` settles, the microtask queue calls
`step(value)`, which jumps to case 1, and so on, until case 2 resolves
the promise with `a + b`. Step through it:

<Callout kind="definition">
**Async lowering** compiles an async function into a resumable state
machine: a state number, a record holding every variable that lives
across an `await`, and a `step` function that runs one piece and then
registers itself (the continuation) with the awaited promise. The
function returns a promise at once, which the last piece resolves, or
rejects if a piece throws.
</Callout>

<Examples of="async-lowering">

```js
async function one() { return 1; }
// lowers to:
function one() {
  return Promise.resolve(1);
}
```

```js
// tsc --target es2015:
function total(get) {
  return __awaiter(this, void 0, void 0,
    function* () {
      const a = yield get('a');
      // ...
```

```js
// tsc --target es5, re-indented:
return __generator(this, function (_a) {
  switch (_a.label) {
    case 0: return [4, get('a')];
    case 1:
      a = _a.sent();
      return [4, get('b')];
    case 2:
      b = _a.sent();
      return [2, a + b];
  }
});
```

</Examples>

The first has no `await`, so it has one piece and needs no states: it
returns an already-resolved promise. The second and third are real
output of TypeScript 5.9.3 for our `total`, re-indented. For a modern
target, `tsc` turns each `await` into a `yield` and passes the generator
to a helper, `__awaiter`, that drives it (you will write one below).
For old browsers, which lack generators, it builds the state machine
itself: `_a.label` is the state number, and each
case returns an instruction to a helper, where `4` means "yield this
value and resume at the next label" and `2` means
"return"<Cite id="ts-emit-helpers" />; `_a.sent()` reads the value the
promise delivered.

## How real languages do it

**V8.** Node 22's bytecode for an async function is a generator's
(`node --print-bytecode`, trimmed):

```text
SwitchOnGeneratorState r0, [0], [1]
CallUndefinedReceiver1 a0, r4, [0]
SuspendGenerator r0, r0-r2, [0]
ResumeGenerator r0, r0-r2
```

The first instruction is the `switch` on the saved state; after the call
to `get`, `SuspendGenerator` saves the live registers and returns, and
`ResumeGenerator` is where the continuation starts.

**Python.** `dis` on `a = await get('a')` shows the same
shape<Cite id="cpython-dis" />: `RETURN_GENERATOR`, then `SEND`,
`YIELD_VALUE` (pause) and `RESUME` before `STORE_FAST (a)`.

**Rust.** Calling an `async fn` returns a **future**, a value holding
its saved state; `.await` polls the inner future and suspends, returning
`Pending`, until it is ready<Cite id="rustref-await-expr" />. The saved
variables show in its size (rustc 1.97, `std::mem::size_of_val`):

```rust
async fn get() -> u64 { 1 }
async fn small() -> u64 { get().await }
async fn big() -> u64 {
    let buf = [0u8; 100];
    get().await + buf[3] as u64
}
// size_of_val(&small()) is 2
// size_of_val(&big())   is 102
```

`small`'s future is two bytes, as only state numbers need saving; `big`
keeps `buf` alive across its `.await`, so its future carries it.

## What you learned

- A **continuation** is the rest of the work waiting for a value.
- In **CPS** functions never return; they pass results to `k`.
- **Async lowering** cuts a function at each `await`, saves live
  variables and a state number, and registers `step` as each promise's
  continuation.
