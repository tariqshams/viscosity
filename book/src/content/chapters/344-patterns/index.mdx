## More than a variant name

Every arm in the last chapter named one variant, perhaps with a payload.
Real code wants more. A scanner asks "is this byte a digit, a letter or
a space?", which is a question about ranges of numbers. Drip's `+` asks
"are *both* operands numbers?", a question about two values at once.
And Drip's truthiness asks "is this `none` *or* `false`?". All three are
written on the left of an arm, as a **pattern**.

<Analogy title="a coin-sorting tray">
A coin sorter is a tray of slots, each shaped for one coin. You drop a
coin in at the top; it slides past the slots in order and falls through
the first one it fits. The last slot is wide enough for anything, so no
coin is ever left on the tray.
<span slot="breaks">A coin only has a size; a pattern can look inside a
value (the payload of a variant, the fields of a struct, both halves of
a pair) and can also hand you the pieces it found, by name.</span>
</Analogy>

<Analogy title="a stencil">
Lay a stencil with a cut-out shape over a sheet of paper, and you see
only the parts that show through the holes. A pattern is a stencil laid
over a value: the solid parts say what must be there (`Number`, the
byte `b'('`), and the labelled holes (`x`, `n`) are the parts you get to
use.
<span slot="breaks">A stencil fits or it does not; a pattern may add a
condition of its own (a guard, `if n < 0.0`), so it can refuse a value
that matches its shape perfectly.</span>
</Analogy>

## The kinds of pattern

Here is a scanner's question, answered with three kinds of pattern at
once. Step a few bytes through it:

<ByteSteps client:visible />

`b'0'..=b'9'` is a **range pattern**: it fits any byte from `b'0'` to
`b'9'`, both ends included (ranges work for numbers and characters).
`p | q` is an **or-pattern**, which fits when any of its alternatives
fits. And `_` is the **wildcard**, which fits anything and binds
nothing. Here is the whole family:

  <PatternKinds />
</Figure>

<Callout kind="definition">
A **pattern** describes a shape a value can have, and may **bind**
names to parts of it<Cite id="rustref-patterns" />: literals, ranges
`a..=b`, names (which fit anything and bind it), the wildcard `_`,
alternatives `p | q`, tuples, enum variants and structs, nested inside
one another. A binding is a new variable that exists only in its arm. A
**match guard**, `pattern if condition =>`, adds a test the arm must
also pass.
</Callout>

<Examples of="pattern">

```rust
fn is_falsey(v: Value) -> bool {
    match v {
        Value::None
        | Value::Bool(false) => true,
        _ => false,
    }
}
```

```rust
match (a, b) {
    (Value::Number(x), Value::Number(y))
        => Value::Number(x + y),
    _ => Value::None, // the VM: an error
}
```

```rust
match v {
    Value::Number(n) if n < 0.0 => "neg",
    Value::Number(_) => "not neg",
    _ => "not a number",
}
```

</Examples>

The first is Drip's truthiness: `none` and `false` are false, and the
or-pattern says so in one arm, while `_` answers "everything else" (the
companion writes the same thing with the `matches!` macro:
`matches!(self, Value::None | Value::Bool(false))`). The second matches
a **tuple**, `(a, b)`, two values grouped in brackets, so that one arm
can ask "are both numbers?" and bind both payloads; any other pair falls
to `_`. The third uses a guard: `Value::Number(n)` fits every number,
and `if n < 0.0` then keeps only the negative ones, so `-1` gives
`"neg"`, `2` falls to the second arm, and `true` to the third. Run
them, and try a byte or a number of your own:

## Patterns outside match

Patterns are not only for `match`. Every `let` is a pattern, which is
why you can take a struct or a tuple apart in one line:

```rust
let (x, y) = (3.0, 4.0);
let Particle { vx, vy, .. } = p;
```

The first binds `x` and `y` at once. The second pulls the fields `vx`
and `vy` out of `p` (field shorthand again), and `..` means "ignore the
other fields". These patterns can never fail: every pair has two halves,
and every `Particle` has a `vx`. Such patterns are called
**irrefutable**; patterns that might not fit, like `Value::Number(n)`,
are **refutable**, and a plain `let` refuses them:

```text
error[E0005]: refutable pattern in local
  binding
8 |     let Value::Number(n) = v;
  |         ^^^^^^^^^^^^^^^^ patterns
  |   `Value::None` and `Value::Bool(_)`
  |   not covered
help: you might want to use `let...else`
8 |     let Value::Number(n) = v
  |         else { todo!() };
```

The help names the fix. When you want one pattern and nothing else, use
**`if let`**, a `match` with one arm, or **`let ... else`**, which binds
the names for the rest of the function and must leave (with `return`)
when the pattern does not fit<Cite id="rust-book-if-let" />:

```rust
if let Value::Number(n) = v {
    println!("a number: {n}");
}
let Value::Number(n) = v else {
    return Err(/* ... */);
};
```

The Rust Drip VM's `pop_numbers` (in `companion/rust/src/vm.rs`) starts
with exactly that second shape: `let (Value::Number(a), Value::Number(b))
= (self.peek(1), self.peek(0)) else { ... }`, a tuple pattern that
either hands it two numbers or reports Drip's runtime error, such as
`cannot use '-' on a number and a string`.

<Formal title="What a match does">

```text
match v { p₁ => e₁, …, pₙ => eₙ }
  runs eᵢ for the smallest i with v ∈ ⟦pᵢ⟧
exhaustive: ⟦p₁⟧ ∪ … ∪ ⟦pₙ⟧ = values(T)
```

<span slot="read">Write ⟦p⟧ for the set of values that pattern p fits.
A match on v runs the arm whose pattern is the first to fit v. It is
exhaustive when the sets of all its patterns, put together, include
every value of v's type T, written values(T). A pattern is irrefutable when its set alone
is every value of T.</span>
</Formal>

## Two traps

The first is the wildcard. `_` covers every case you have not written,
*including ones added later*. Add a variant to `Op`, and a `match` that
ends in `_ => {}` keeps compiling, quietly doing nothing for it; list the
variants instead whenever each one deserves a thought, and keep `_` for
when "everything else" really has one answer, as in `is_falsey`.

The second catches everyone once. A plain name in a pattern always
**binds**: it makes a new variable. It never compares with a variable
of the same name<Cite id="rust-book-patterns" />:

```rust
let limit = 3;
match n {
    limit => println!("hit"),  // ✗
    _ => println!("miss"),
}
match n {
    x if x == limit => println!("hit"),
    _ => println!("miss"),     // ✓
}
```

With `n = 7` the first prints `hit`, because `limit` in the pattern is
a brand-new name that fits anything. rustc warns you:

```text
warning: unreachable pattern
5 |         limit => println!("hit"),
  |         ----- matches any value
6 |         _ => println!("miss"),
  |         ^ no value can reach this
note: there is a binding of the same name
```

The guard in the second `match` does the comparison you meant.

<OtherLanguages title="Are both operands numbers?">

```rust
match (a, b) {
    (Value::Number(x), Value::Number(y))
        => Value::Number(x + y),
    _ => Value::None,
}
```

```ts
if (typeof a === 'number' &&
    typeof b === 'number') {
  return a + b;
}
return null;
```

</OtherLanguages>

TypeScript can take objects and arrays apart (`const { x, y } = p`), but
it has no patterns that *test*: the question "are both numbers?" is an
`if` with two checks, and narrowing (*TypeScript II: unions and
narrowing*) works out the types inside it. In Rust the test, the
narrowing and the naming of the payloads are one pattern, and the
compiler can check the whole `match` for missing cases.

## What you learned

- A **pattern** is a shape: literals, ranges `a..=b`, names that bind,
  the wildcard `_`, alternatives `p | q`, tuples, variants and structs,
  nested freely, with an optional guard `if ...`.
- `let` takes patterns too. Irrefutable ones (tuples, structs) always
  fit; refutable ones need `match`, `if let` or `let ... else`.
- `_` hides cases added later, and a plain name in a pattern binds a new
  variable instead of comparing.
