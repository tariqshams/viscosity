## Once by hand, then every time

In chapter 221 you ran two commands, `cargo build` for the
`wasm32-unknown-unknown` target and `wasm-bindgen --target nodejs`,
and the Rust engine compiled JavaScript from inside Node. That was
enough to check parity. It isn't enough to ship. A browser needs
different glue from Node. The file should be as small as it can be,
because readers download it. And the wasm-bindgen command-line tool
must be the exact version the crate was built with (chapter 257), or
it refuses the file.

The Rust ecosystem has a standard tool for all of this: **wasm-pack**.
`wasm-pack build` "creates the files necessary for JavaScript
interoperability and for publishing a package to npm": it compiles the
crate, runs wasm-bindgen, and writes a `pkg` folder holding the
`.wasm`, the JavaScript wrapper, your README and a
`package.json`<Cite id="wasm-pack-book" />. For release builds it also
runs wasm-opt, an optimizer from the Binaryen
project<Cite id="wasm-pack-book" /><Cite id="binaryen-readme" />.

<Callout kind="intuition">
A flat-pack wardrobe comes with a kit: screws, a key and a sheet of
pictures. Most people use the kit. If your wall is odd, you buy your own
screws, but you still do the same steps in the same order.
</Callout>

<Callout kind="definition">
**wasm-pack** builds an npm package from a Rust crate. `wasm-pack build`
compiles to WebAssembly, runs **wasm-bindgen** for one `--target`
(`bundler` by default, or `nodejs`, `web`, `no-modules`, `deno`),
optimizes with **wasm-opt** in release builds, and writes `pkg/` with a
generated `package.json`<Cite id="wasm-pack-book" />.
</Callout>

## Why Viscosity builds by hand

Viscosity doesn't use wasm-pack. Its package is built by
`engine/rust/packages/wasm/build.mjs`, 140 lines of Node. The odd wall
is the one-target rule. `@viscosity/wasm` wants both a `nodejs` build
and a `web` build in a single package, and lets each environment pick
its own (that is chapter 278). The script also writes the licence
texts, and with `--book` copies the web build into this book. Its
steps, trimmed:

```js
// 1. cargo
cargo build --release
  --target wasm32-unknown-unknown
  -p viscosity-wasm
// 2. wasm-bindgen, at the locked version
for (const t of ['nodejs', 'web'])
  wasm-bindgen --target t
    --out-dir dist/... viscosity_wasm.wasm
// 3. wasm-opt, if it can be found
wasm-opt -O3 <features> f -o f
// 4. LICENSE, THIRD_PARTY_LICENSES.txt
// 5. --book: copy dist/web into the book
```

(The real code calls `execFileSync` for each command.) Step 3 is
optional. With no wasm-opt the build carries on and says so, and the
result works, just larger. The wasm-opt it finds first is an npm
devDependency, so `npm install` is all a contributor needs.

## What each step does to the file

I rebuilt commit `c68daec` from an empty target directory in `/tmp`,
with cargo 1.97, wasm-bindgen 0.2.106 and wasm-opt 132, running the
script's commands one at a time. Cargo took 38 seconds on the shared
VM, and each wasm-opt run about 25. Between steps I walked the

The engine has grown since. At commit `288e497`, which adds oxc's
semantic checks (chapter 260), the same three steps give 1,844,560,
1,759,791 and 1,373,390 bytes: about 1.4 MB, 486 KiB gzipped.

A WebAssembly file is a list of numbered **sections**: types,
functions, exports, code, data, and "custom" sections that engines may
ignore. The run below walks a 52-byte module the same way, reading
each section's id and its size (a variable-length LEB128 number):

<Run id="sections" />

The second step explains a mystery from chapter 221: how does a
command-line tool know that `compile` takes a string and returns an
`Output`? The `#[wasm_bindgen]` macro can't write that down as data,
because it runs before the compiler has resolved the types. So it
emits code instead: one `__wbindgen_describe_` function per export,
which reports the types when run. The CLI contains "a tiny and
incomplete Wasm interpreter" for exactly this. It runs every describe
function, then deletes them all<Cite id="wasm-bindgen-cli-descriptors" />.

## Two kinds of glue

The two wasm-bindgen runs produce the same `.wasm` (64 bytes apart)
and different JavaScript. The `nodejs` target writes CommonJS that can
be `require`d like any Node module<Cite id="wasm-bindgen-guide" />. Its
last lines, trimmed:

```js
const wasmBytes = require('fs')
  .readFileSync(wasmPath);
const wasmModule =
  new WebAssembly.Module(wasmBytes);
const wasm = new WebAssembly.Instance(
  wasmModule, imports).exports;
```

That is synchronous: `compile` works the moment `require` returns. A
browser can't read files, so the `web` target writes an ES module with
an `init()` that you `await`. It fetches the `.wasm` (by default, from
next to the glue) and instantiates it, streaming if it
can<Cite id="wasm-bindgen-guide" />:

```js
import init, { compile }
  from '@viscosity/wasm/web';
await init();
const { code, explain } = compile(src);
```

## Checking the tools

Step 2 begins with the check you'll write below. It reads the
`wasm-bindgen` version from `Cargo.lock`, asks the CLI for its own,
and stops with the exact `cargo install` command if they differ. One
more check is worth having for a committed binary. The web `.wasm`
from my rebuild was byte-identical to the one `book/public/wasm` held
then, and a rebuild at `288e497` matches today's file, so the file this
book serves really is the engine at that commit.

<Callout kind="engine" label="Under the hood">
The final module has 15 exports: `compile`, `compileWith`,
`compileLanguage`, the getters, setters and `free` of `Output`, the
memory, and wasm-bindgen's allocator, table and start functions. It
imports just three functions from JavaScript: one throws an error, one
makes an `Error` object, and one sets up the table of JavaScript
values. Everything else, oxc's parser included, is Rust compiled into
the code section: 1,040,082 of the 1,145,498 bytes at `c68daec`, and
1,248,736 of 1,373,390 at `288e497`. `build.mjs` also
passes wasm-opt the WebAssembly features rustc enables by default for
this target (bulk memory, sign extension, reference types and three
more)<Cite id="rustc-wasm32-unknown-unknown" />.
Out of curiosity I ran wasm-opt without them: the same bytes came out.
The module lists its features in a 157-byte custom section,
`target_features`, which survives every step.
</Callout>

## What you learned

- **wasm-pack** compiles, binds, optimizes and packages a crate for
  npm, for one target at a time. `build.mjs` does the same steps by
  hand, for two targets.
- cargo's file carries **describe functions** and a custom section for
  the CLI. wasm-bindgen runs them, writes the glue and removes them.
- wasm-opt `-O3` shrank the code by about 8% and dropped about 200 KB
  of **names**. Gzipped, the whole saving was under 5%.
- The **nodejs** glue loads synchronously with `readFileSync`. The
  **web** glue needs `await init()`.
- The CLI must match `Cargo.lock` exactly, and the committed `.wasm`
  rebuilds byte for byte.
