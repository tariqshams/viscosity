## Between guessing and being told

Chapter 128's inference needs no annotations at all; however, it leans
entirely on unification, and unification answers one question only,
"are these two types *equal*?". The moment a language has subtyping
(the last chapter), the question at a call becomes "is the argument's
type a subtype of the parameter's?", and the neat equations of
algorithm W no longer settle everything. At the other extreme, the
checker of chapter 124 needs a type written on everything. TypeScript
does neither: it makes you annotate some places and works out the
rest. Here is the line it draws, in strict mode:

```ts
const f = (x) => x + 1;
// error TS7006: Parameter 'x' implicitly
//   has an 'any' type.
const g: (x: number) => number =
  (x) => x + 1;                // fine
[1, 2].map((x) => x.toFixed(1)); // fine
```

Line 1 is rejected: nothing says what `x` is. Yet line 5 has exactly
the same unannotated arrow, and it is fine, because the declared type
of `g` says what the arrow must be, so `x` must be a `number`. Line 6
too: `map` on an array of numbers will call its argument with numbers,
so `x` is a `number` and `x.toFixed(1)` checks. TypeScript calls this
**contextual typing**: "the type of an expression is implied by its
location"<Cite id="ts-type-inference" /><Cite id="ts-everyday-types" />.
Under `noImplicitAny` (part of `strict`), a parameter with no type and
no context is an error rather than a silent `any`<Cite id="ts-option-noimplicitany" />.

<Analogy title="naming a bird, or confirming one">
"What bird is that?" is a hard question: you have to know every bird.
"Is that a robin?" is much easier, because you know what to look for: a
red breast, a certain size. A type checker has the same two questions,
and the second is often answerable when the first is not.
<span slot="breaks">A birdwatcher's "yes, a robin" can be a judgement
call; checking a term against a type is exact, and it ends either in a
precise yes or in an error that says what was expected and what was
found.</span>
</Analogy>

<Analogy extra title="marking an exam">
A teacher marking "work out 17 × 3" has to do the sum; one marking
"show that 17 × 3 = 51" is handed the answer and only checks the
working. Questions of the first kind are synthesis; the second kind
are checking.
<span slot="breaks">A teacher can always fall back on doing the sum;
a checker cannot always synthesise (an unannotated λ has no type it can
find on its own), which is why some places need the type written
down.</span>
</Analogy>

## Two modes

<Callout kind="definition">
**Bidirectional type checking** splits the typing judgement in two.
**Synthesis**, `Γ ⊢ e ⇒ T`, finds a type for e with no help (read "e
synthesises T"). **Checking**, `Γ ⊢ e ⇐ T`, is given a type and confirms
that e has it (read "e checks against T"). Each kind of term gets rules
in one mode or both, and the rules say where the checker switches
between them<Cite id="dunfield-krishnaswami2021" />.
</Callout>

<Formal title="The rules for a small language">

```text
 x : T in Γ
──────────── (Var⇒)
 Γ ⊢ x ⇒ T

    Γ ⊢ e ⇐ T
───────────────── (Anno⇒)
 Γ ⊢ (e : T) ⇒ T

Γ ⊢ f ⇒ A → B    Γ ⊢ a ⇐ A
─────────────────────────── (App⇒)
       Γ ⊢ f a ⇒ B

   Γ, x : A ⊢ e ⇐ B
────────────────────── (Lam⇐)
 Γ ⊢ λx. e ⇐ A → B

 Γ ⊢ e ⇒ A     A = B
───────────────────── (Sub⇐)
     Γ ⊢ e ⇐ B
```

<span slot="read">Var: a variable synthesises the type the environment
gives it. Anno: an annotated term synthesises its annotation, after
checking the term against it. App: an application synthesises the
function's type, which must be an arrow from A to B, checks the
argument against A, and synthesises B. Lam: a λ checks against an arrow
A to B by checking its body against B with x bound to A. Sub: any term
that synthesises A checks against B when A equals B (with subtyping,
when A is a subtype of B).</span>
</Formal>

Read the rules for *where the information comes from*. A variable's type
comes from the environment, and an annotation's from what is written,
so both can synthesise. An application learns its argument's expected
type from the function, so the argument is *checked*: that is
TypeScript's contextual typing of the arrow passed to `map`. A λ can
only be checked, because only an expected arrow tells it its
parameter's type. And Sub⇐ is the bridge: whenever there is no special
checking rule, synthesise and compare. Step through it:

<Examples of="bidirectional-typing">

```text
(λx. x : bool → bool) true    ⇒ bool
```

```text
λx. x + 1      ⇒ ?   error: cannot
               synthesise a type for λ
(λx. x + 1 : number → number)
                ⇒ number → number
```

```text
(λf. f 1 : (number → number) → number)
  (λx. x + 1)                ⇒ number
```

</Examples>

The first is the smallest annotated call: Anno⇒ gives the function
`bool → bool`, the argument `true` is checked against `bool`, and the
call synthesises `bool`. The second is a spot the difference: with no
annotation, a λ has no synthesis rule, so the checker stops and asks for
one; with the annotation, it checks. The third is the realistic one, and
it is what `map` does in TypeScript: the outer function is annotated,
so App⇒ checks the argument `λx. x + 1` against `number → number`, and
that λ needs no annotation of its own.

Pierce and Turner called this way of working **local type inference**:
types travel only between neighbouring parts of the program, with no
unification variables spread across it, and the parameter types of
anonymous functions come from their context<Cite id="pierce-turner2000" />.
The price is a few annotations, usually one per named function; in
return, it copes with subtyping, and with features for which full
inference is known to be impossible<Cite id="dunfield-krishnaswami2021" />.

## What you learned

- **Bidirectional typing** has two judgements: **synthesis** (`⇒`,
  find a type) and **checking** (`⇐`, confirm a given one).
- Variables, annotations and applications synthesise; λs check; the
  argument of an application is checked against the function's
  parameter type; Sub⇐ falls back to synthesise-and-compare.
- Annotations are needed exactly where a λ has no expected type to be
  checked against; TypeScript's contextual typing is this idea.
