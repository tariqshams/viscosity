## What is the loop counting?

When Viscosity turns an array of objects `ps` into a struct of arrays,
the read `ps[i].x` becomes `ps.x[i]`, and the two behave differently at
the edges: past the end, `ps[i]` is `undefined` and `.x` on it throws a
`TypeError`, while a typed array quietly returns `undefined`. So every
rewritten access gets a check that throws the original error, unless
Viscosity can prove the check never fires. To prove that, it needs to
know what `i` *is* on every trip around the loop; the last chapter found
the loops, and this one looks at the values inside them.

## Values that climb in steps

<Analogy title="climbing a staircase">
Each step you take adds one to your step count, so after `k` steps the
count is `k`; your height above the floor is not counted separately, it
is always 17 centimetres times the step count. The step count is the
thing that drives the climb; the height follows it in lockstep.
<span slot="breaks">Real staircases end where the builder put the top;
how many trips a loop makes is decided by its test while it runs, and
is often unknown to the compiler.</span>
</Analogy>

<Analogy extra title="page numbers in a book">
Turn a page and the page number goes up by one; the line number at the
top of page `p`, in a book with 40 lines a page, is `40 × (p - 1) + 1`,
another number that climbs in steps, just bigger ones.
<span slot="breaks">You can flip back and forth in a book; an induction
variable only ever moves forwards by its fixed step, once per trip.</span>
</Analogy>

In SSA (chapter 191) a loop counter is a phi in the header. Here is
`for (let i = 0; i < n; i++)` with `const j = 2 * i + 1` in its body,
as Viscosity's IR:

```text
b1:  ; preds b0 b3
  %4 = phi %3, %17      ; i
  %6 = binop < %4, %1   ; i < n
b2:
  %8 = binop * %7, %4   ; 2 * i
  %10 = binop + %8, %9  ; 2 * i + 1
b3:
  %15 = unop + %4
  %17 = binop + %15, %16 ; + 1
```

`%4` takes `%3` (the starting `0`) when it arrives from before the loop,
and `%17` when it comes round from the latch `b3`; `%17` is `%4` plus
one (the unary `+` is how `i++` first turns `i` into a number). `%8` and
`%10` are built from `%4` with a constant multiply and a constant add.
Step through four trips and watch them move together:

<Callout kind="definition">
An **induction variable** is a value that changes by a fixed amount on
every trip around a loop. A **basic** induction variable is a phi in the
loop header whose inputs are a start value from outside the loop and
`phi + step` from inside it, where the step is the same every trip. A
**derived** induction variable is `c × i + d` for a basic one `i` and
values `c` and `d` that do not change in the loop.
</Callout>

<Formal title="Induction variables, trip by trip">

```text
basic:    i₀ = start,   iₖ₊₁ = iₖ + s
          so  iₖ = start + k·s
derived:  jₖ = c·iₖ + d
          so  jₖ₊₁ = jₖ + c·s
```

<span slot="read">On trip zero the basic variable i holds its start; on
each later trip it is the last value plus the step s, so on trip k it is
start plus k times s. A derived variable j is c times i plus d, so it
too climbs by a fixed step, c times s, each trip.</span>
</Formal>

<Examples of="induction-variable">

```js
for (let i = 0; i < n; i++)  // step 1
```

```js
for (let i = 10; i > 0; i -= 2)
// step -2: still an induction variable
```

```js
const i = y * W + x; // heat.js
c[i - 1].h + c[i + 1].h  // derived
```

</Examples>

The first is the everyday counter, step 1. The second steps by minus
two, which is still a fixed step, so it is still an induction variable.
The third is from the `heat` benchmark in this repository, which walks a
grid stored row by row: inside the `x` loop, `y` and `W` do not change,
so `i` is a derived induction variable of `x` (step 1), and so are
`i - 1` and `i + 1`.

Viscosity's own test is deliberately narrower. Its `isCountingPhi`, in
`analysis.ts`, accepts only a phi whose step is exactly `+ 1` and whose
start is provably a whole number that is zero or more:

```ts
const [x, y] = step.args.map(inst);
const base = x.op === 'unop' &&
  x.operator === '+'
  ? inst(x.args[0]) : x;
if (base.id !== phi.id || y.op !== 'const'
    || y.value !== 1) continue;
```

The first line fetches the two operands of the step's `+`; the next
three look through a unary `+` if there is one; the last two reject the
phi unless the step adds the constant `1` to the phi itself. When the
header then tests such a phi from `0` against a constant, `i < 100`,
Viscosity knows the **trip count** (100), which it uses to estimate
sizes: pushes inside loops of 10 and 20 trips give `about 200
elements` in `explain`, while a bound read from the command line gives
`size unknown statically`.

## Proving `ps[i]` is in bounds

For an access `ps[idx]`, Viscosity drops the check when all three of
these hold:

1. `idx` is a counting phi, so on every trip it is a whole number, zero
   or more.
2. A loop containing the access has `idx`'s block as its header, and the
   header's test (or one part of an `&&`) is `idx < ps.length`.
3. The test's "true" successor dominates the access, so the access can
   only run straight after the test has passed.

Here are loops over `ps`, each followed by one `console.log(ps[0].x)`
outside any loop (never proven), with the last line of `explain`, all
run for this chapter:

```text
loop                         proven
i < ps.length                2 of 3
i < n   (const n = 1000)     0 of 3
i < ps.length && go          2 of 3
i <= ps.length               0 of 3
i < ps.length; i += 2        0 of 3
ps[i] in an inner k loop     2 of 3
ps[i - 1], i from 1          1 of 3
```

Each failure breaks one condition: `n` is not `ps.length`, `<=` lets `i`
equal the length, `i += 2` is not a step of one, and `i - 1` is not a
phi at all. The inner `k` loop still works because condition 2 searches
*every* loop around the access, not just the innermost. On the
programs in `bench/e2e`, `viscosity explain` reports 12 of 12 accesses
proven for `nbody` and 11 of 11 for `boids`, but 3 of 12 for `heat`,
whose `c[i - 1]` and `c[i + W]` are derived, not counting, variables.

## Values that never change

Back in the last chapter's `sum`, the inner loop's header contains
`%9 = const 3`, and the inner body reads `g[i]` with `%14 = index.get
%0, %3`. Neither operand of that read is touched by the `k` loop, so
every trip asks the same question again.

<Analogy extra title="running laps of a track">
While you run laps, your lap count goes up, but the length of the track
is the same on every lap, so you could measure it once before you
start, rather than on every lap.
<span slot="breaks">Unless someone moves the cones while you run: a
value read from memory (an array's length, a field) stays the same only
if nothing in the loop writes to it, and proving that is a separate,
harder question.</span>
</Analogy>

<Callout kind="definition">
An instruction is **loop-invariant** in a loop if it computes the same
value on every trip: it has no side effects, and each of its operands is
either defined outside the loop or is itself loop-invariant. A phi in
the header is never invariant (it merges a value from the latch), and a
read from memory is invariant only if nothing in the loop may write
the memory it reads.
</Callout>

<Formal title="Loop-invariant, as a rule">

```text
inv(x)  ⟺  pure(x) ∧ ∀ o ∈ args(x):
             def(o) ∉ L  ∨  inv(o)
```

<span slot="read">x is invariant in loop L exactly when x is pure (no
effects, not a phi, not a memory read), and every operand o of x is
either defined outside L or is itself invariant. The rule refers to
itself, so it is solved like chapter 195's dataflow: guess, sweep,
repeat until nothing changes.</span>
</Formal>

<InvariantSteps client:visible />

<Examples of="loop-invariant">

```text
b5:                ; inner loop header
  %9 = const 3     ; invariant
```

```text
b6:                ; inner x loop body
  %32 = binop * %23, %21  ; y * W
```

```js
for (let i = 0; i < g.length; i++)
  g.push(0); // g.length: not invariant
```

</Examples>

The first is the simplest case: a constant has no operands, so it is
the same on every trip of `sum`'s `k` loop. The second is from the grid
loop: `y` (`%23`) and `W` (`%21`) are both defined outside the inner `x`
loop, so `y * W` is invariant there, though not in the outer `y` loop,
where `%23` is its counter. The third is the memory trap: `g` itself
never changes, but every `push` makes `g.length` bigger, so the read of
`g.length` in the header gives a new answer each trip (and this loop
never ends). LLVM's loop-invariant code motion pass uses alias analysis
for exactly this question before it moves a memory read<Cite id="llvm-passes" />.

<Callout kind="engine" label="Under the hood">
Viscosity uses invariance once, quietly, in its bounds proof: the outer
counter `%3` never changes inside the `k` loop, so the outer test
`i < g.length` still holds when `g[i]` is read in there. It never moves
an invariant instruction out of a loop; the next chapter shows how a
compiler that does would go about it, and why "before the loop" needs a
block of its own<Cite id="llvm-loop-terminology" />.
</Callout>

## What you learned

- A **basic induction variable** is a header phi fed by a start value
  and `phi + step`; a **derived** one is `c × i + d`. Both climb by a
  fixed step each trip.
- Viscosity's bounds proof needs a counting phi (start ≥ 0, step 1), a
  header test `i < ps.length` (perhaps inside `&&`), and a true branch
  that dominates the access.
- A **loop-invariant** instruction is pure and built only from values
  defined outside the loop or themselves invariant; find them all with
  a fixpoint.
- Memory reads are invariant only if nothing in the loop writes there.
