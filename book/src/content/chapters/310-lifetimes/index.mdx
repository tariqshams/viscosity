## The tick you skipped

Chapter 303 showed you drip-rs's token type and asked you to ignore one
piece of it:

```rust
pub struct Token<'src> {
    pub kind: TokenKind,
    pub lexeme: &'src str,
    pub line: usize,
}
```

A token's `lexeme` is a `&str`, a borrowed slice of the program's source
text. It isn't a copy. So what happens if you delete the `'src` and write
the struct the way you'd write a TypeScript interface? Rust 1.97 on this
machine (trimmed):

```
error[E0106]: missing lifetime specifier
2 |     lexeme: &str,
  |             ^ expected named lifetime
  |               parameter
help: consider introducing a named
  lifetime parameter
1 ~ struct Token<'a> {
2 ~     lexeme: &'a str,
```

Your chapter 68 scanner gave each token `source.slice(start, current)`,
a new string kept alive by the garbage collector. A Rust token holds a
*pointer into someone else's text*, which nobody keeps alive for it. So
the compiler asks: whose text, and for how long?

<Callout kind="intuition">
A reference is a cloakroom ticket, worth something only while the
cloakroom is open. A lifetime is the opening hours printed on it. Keep
the ticket as long as you like, but don't try to collect your coat after
closing: the compiler checks every ticket against the hours before the
program runs.
</Callout>

```
error[E0597]: `src` does not live long
  enough

   |                  ^^^^ borrowed value
   |                  does not live long
   |                  enough
53 | }
   | - `src` dropped here while still
   |   borrowed
54 | println!("{}", t.lexeme);
   |                -------- borrow later
   |                         used here
```

Chapter 302's three points again: where the borrow started, where the
owner died, where the borrow was still needed. And note what is *not*
an error: `sc` dies at the same brace, but `t` borrows the source, not
the scanner.

<Callout kind="definition">
A **lifetime** is the stretch of a program during which a reference
must stay valid. The borrow checker gives every reference one, and
checks that it fits inside the life of the value it points at (from
creation to drop). A reference that could outlive its value would
**dangle**; preventing that is the main job of lifetimes<Cite id="klabnik2026" />.
</Callout>

## Naming lifetimes

Inside a function body the compiler works lifetimes out by itself. It
needs your help at the *boundaries*: a struct that holds a reference,
and a signature that returns one. `'src` is a **lifetime parameter**, a
name for "however long the borrowed source is valid", declared in angle
brackets like a type parameter (chapter 309):

```rust
struct Scanner<'src> {
    src: &'src str,
    pos: usize,
}

impl<'src> Scanner<'src> {
    fn next(&mut self) -> Token<'src> {
        // ... skip spaces, find the word
        let s = &self.src[at..self.pos];
        Token { lexeme: s, line: 1 }
    }
}
```

Read `next`'s signature aloud: "borrow the scanner mutably for a moment,
and hand back a token that is valid as long as the *source* is". Same
name, same span.

A plain function with two inputs, `longer`, returns whichever string is
longer. Without annotations, Rust 1.97 asks which input the answer
borrows from (trimmed):

```
error[E0106]: missing lifetime specifier
1 | fn longer(a: &str, b: &str) -> &str {
  |              ----     ----     ^
  = help: this function's return type
    contains a borrowed value, but the
    signature does not say whether it is
    borrowed from `a` or `b`
```

The fix it suggests is `fn longer<'a>(a: &'a str, b: &'a str) -> &'a str`:
the result is valid only while *both* inputs are.

<Callout kind="definition">
A **lifetime annotation** names a lifetime with an apostrophe, such as
`'a` or `'src`. It is declared as a parameter (`struct Token<'src>`,
`impl<'src>`, `fn f<'a>`) and attached to references (`&'a str`) or to
types holding them (`Token<'a>`). Annotations never make anything live
longer; they state how lifetimes relate, so callers can be checked.
</Callout>

## The rules that let you leave them out

Chapter 303's exercise was `fn take_ident(src: &str) -> &str`, with no
ticks at all. That works because of three **elision rules**, which fill in
lifetimes when the answer is obvious<Cite id="rustref-lifetime-elision" />:

1. Each reference parameter gets its own lifetime.
2. If there is exactly one input lifetime, every output reference gets
   it.
3. In a method, if one input is `&self` or `&mut self`, every output
   reference gets *self's* lifetime.

If an output is still unnamed after that, you get E0106, as `longer`
did. The compiler never looks at the body to decide<Cite id="klabnik2026" />.

Rule 3 is where drip-rs has to be explicit. Take a word splitter shaped
like the scanner, and write its method the short way:
`fn next_word(&mut self) -> Option<&str>`. Rule 3 ties the result to
the *borrow of the splitter*. Then holding two words at once, which the
compiler does with `previous` and `current` all the time, is refused
(from a test program, trimmed):

```rust
let a = w.next_word();
let b = w.next_word();
println!("{:?} {:?}", a, b);
```

```
error[E0499]: cannot borrow `w` as mutable
  more than once at a time
35 | let a = w.next_word();
   |         - first mutable borrow
36 | let b = w.next_word();
   |         ^ second mutable borrow
```

While `a` is alive, the splitter counts as mutably borrowed, so there
can't be a second call. drip-rs's `-> Token<'src>` says the token
borrows the source instead, so the scanner is free again as soon as the
call returns.

## The longest lifetime: 'static

One lifetime is built in. `'static` means "valid for the whole run of
the program". String literals have it, because their text is stored in
the program's binary, and a `&'static str` can be used wherever a
shorter lifetime is wanted. drip-rs's error tokens rely on that:

```rust
fn error(&self, message: &'static str)
    -> Token<'src> {
    Token {
        kind: TokenKind::Error,
        lexeme: message,
        line: self.line,
    }
}
```

The message outlives any source, so it fits in a `Token<'src>`. If a
compiler hint suggests `'static` to silence a borrow error, the Rust
book advises asking first whether the reference really should live that
long<Cite id="klabnik2026" />.

<Callout kind="engine" label="Under the hood">
Follow `'src` through drip-rs. The compiler is
`struct Compiler<'src, 'a>`, with two lifetimes for two different
loans: `'src` for the source text, and `'a` for the heap, the GC roots
and the error list it borrows from its caller. It keeps `current` and
`previous` as `Token<'src>`, and each local variable's name is a
`&'src str` pointing into the source, so neither a token nor a local
copies any text; the TypeScript VM calls `slice` for every lexeme.
Lifetimes exist only for the checker: at run time a `&'src str` is
still a pointer and a length (chapter 303). engine/rust meets lifetimes
from a library: oxc builds the
JavaScript AST inside an `Allocator`, so its nodes have types such as
`Program<'a>`. That allocator is a local variable of the JS plugin's
`lower`, so nothing that borrows the AST can be returned from it, and
the port records what the emitter needs in a side table instead (its
README: "No live AST after lowering").
</Callout>

## What you learned

- A **lifetime** is the span during which a reference must stay valid.
  The borrow checker makes it fit inside the life of the value
  borrowed, or reports E0597.
- **Lifetime annotations** like `'src` name lifetimes on structs,
  impls and signatures. They describe relationships; they never extend
  a value's life.
- Three **elision rules** fill in the obvious cases. When they can't,
  E0106 asks you which input an output borrows from.
- Rule 3 ties a method's result to `self`; drip-rs's `Token<'src>`
  ties it to the source instead.
- `'static` lasts the whole run; string literals have it.
