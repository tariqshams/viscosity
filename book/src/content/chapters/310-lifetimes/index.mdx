## A reference with nothing behind it

In TypeScript you never ask how long an object will last: if `word`
still points at a string, the garbage collector (from *Reclaiming
memory: mark and sweep*) keeps that string alive. Rust has no garbage collector, so it
cannot keep anything alive on your behalf; when an owner goes out of
scope its value is dropped at once (as *Ownership* showed), and any
reference still pointing at it would point at freed memory. Such a
reference is called **dangling**, and reading through one is how C
programs crash, or worse, quietly read somebody else's data.

Rust's answer is to check, while compiling, that every reference is
used only while its value is still there. Here is the smallest program
that breaks the rule:

```rust
fn main() {
    let r;
    {
        let text = String::from("let x");
        r = &text[0..3];
    }
    println!("r is {r}");
}
```

Line 2 declares `r` and fills it in later. Inside the inner block,
`text` owns a string on the heap, and `r` becomes a slice of its first
three characters (a borrow, as in *Slices and strings*). The block ends
on line 6, so `text` is dropped and its memory freed; then line 7 reads
`r`, which would point into memory that is gone. rustc 1.97 refuses:

```text
error[E0597]: `text` does not live long
  enough
4 | let text = String::from("let x");
  |     ---- binding `text` declared here
5 | r = &text[0..3];
  |      ^^^^ borrowed value does not
  |           live long enough
6 | }
  | - `text` dropped here while still
  |   borrowed
7 | println!("r is {r}");
  |                 - borrow later used
  |                   here
```

(Long lines are wrapped to fit a phone; the words are rustc's.) Read
it as three places: where the borrow was **made** (line 5), where the owner **died**
(line 6), and where the borrow was **still needed** (line 7). Every
lifetime error you meet is some arrangement of those three.

<Analogy title="a cloakroom ticket">
You leave your coat at a theatre's cloakroom and get a numbered ticket.
The ticket is small and you can carry it anywhere, but it is only worth
something while the cloakroom is open; turn up after closing and there
is no coat to collect. A reference is the ticket, the value is the coat,
and the owner's scope is the opening hours. Rust checks every ticket
against the opening hours before the show starts.
<span slot="breaks">A real cloakroom might stay open late, or you might
get lucky; Rust never guesses, so it rejects the program if there is
any path on which the ticket could be used after closing.</span>
</Analogy>

<Analogy title="a library loan">
A library book borrowed for three weeks has a due date stamped inside.
You can read it, lend it on to a friend, or photocopy a page, but every
one of those things has to happen before the due date, because after
that the book is gone from your shelf. A lifetime is the stretch between
the day you borrowed it and the last day you need it, and it has to end
on or before the due date.
<span slot="breaks">A library can renew a loan; Rust cannot stretch a
value's life to suit a reference. If the reference needs longer, you
must change the code so that the owner lives longer.</span>
</Analogy>

<Callout kind="definition">
A **lifetime** is the stretch of a program during which a reference
must stay valid: from where the reference is made to the last place it
is used. The **borrow checker** (the compiler pass from *Borrowing*)
gives every reference a lifetime and checks that it fits inside the life
of the value it points at, from that value's creation to its drop. A
reference that could outlive its value would **dangle**; preventing that
is the main job of lifetimes<Cite id="rust-book-lifetimes" />.
</Callout>

<Formal title="The outlives check">

```text
L(x)  = the code where x is alive
'r    = the code where r is used
r = &x  is accepted  ⟺  'r ⊆ L(x)
```

<span slot="read">L of x is the part of the program where the value x
exists. Tick r (written 'r) is the part where the reference r is still
needed. Borrowing x into r is allowed exactly when tick r is a subset
of L of x: every place that uses r is a place where x is still
alive.</span>
</Formal>

<Examples of="lifetime">

```rust
let r;
{
    let x = 5;
    r = &x; // E0597: x dies first
}
println!("{r}");
```

```rust
fn make() -> &String {
    let s = String::from("hi");
    &s // s is dropped right here
}
```

<Run id="lifetime-play" />

</Examples>

The first is the smallest dangling reference: `x` lives only inside the
braces, `r` is used after them, and the error is E0597. The second is
the same mistake across a call: `s` is dropped when `make` returns, so
the reference handed back would point at nothing. rustc stops at the signature with E0106,
"missing lifetime specifier", and its help line says what you almost
certainly want: "return an owned value", that is
`fn make() -> String` with `s` as the last line. (If a function takes
a reference and returns a borrow of a local, the error is E0515,
"cannot return reference to local variable `s`".) The runnable one is
the opening program fixed, with `text` outside the block; move it back
inside and run it to see E0597 for yourself.

## A borrow ends at its last use

Lifetimes are about *uses*, not braces. Recall the rule from
*Borrowing*: many shared borrows or one mutable borrow, never both. Both of these programs borrow `v` and then push onto it; only one
compiles.

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4); // E0502
println!("{first}");
```

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{first}"); // last use
v.push(4); // fine: the borrow is over
```

In the first, `first` is still needed on line 4, so its borrow is alive
when `push` asks for a mutable one, and rustc reports E0502 ("cannot
borrow `v` as mutable because it is also borrowed as immutable"; push
may move the vector's contents to a bigger buffer, which would leave
`first` dangling). In the second, `first` is never used after line 3,
so its lifetime ends there, and `push` is fine, even though `first` is
still in scope until the closing brace. This is the idea from
*Non-lexical lifetimes and region inference*: a lifetime is the set of
program points where the reference is still live, as in *A borrow
checker in miniature*.

<OtherLanguages title="Returning a reference to a local">

```rust
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap_or("")
}
fn greeting() -> String {
    let g = String::from("hi");
    g // move it out: no borrow
}
```

```ts
function firstWord(s: string): string {
  return s.split(' ')[0] ?? '';
}
function greeting(): { text: string } {
  const g = { text: 'hi' };
  return g; // the GC keeps g alive
}
```

```c
const char *greeting(void) {
    char g[] = "hi";
    return g; /* dangling! g is on
                 the stack, gone now */
}
```

</OtherLanguages>

TypeScript never thinks about lifetimes, because the collector keeps
`g` alive for as long as the caller holds it. The C version compiles
(most compilers only warn) and returns a pointer into a stack frame
that no longer exists, the very bug Rust's check rules out. Rust gives you
two honest choices: borrow from something the *caller* owns, as
`first_word` does (its result is a slice of `s`, so it lives as long as
`s` does), or hand back an owned value, as `greeting` does, moving the
`String` out to the caller.

<Callout kind="engine" label="Under the hood">
Lifetimes exist only while compiling. Once the borrow checker is
satisfied they are thrown away, so a `&str` in the running program is
still only an address and a length, exactly as *Slices and strings*
drew it, with no counter and no check<Cite id="klabnik2026" />. That is
why drip-rs can let every token and every local-variable name point
straight into the source text: the TypeScript VM calls `slice` and
makes a new string for each lexeme, while the Rust scanner allocates
nothing at all, and the compiler has proved that no token outlives the
source it points into.
</Callout>

## What you learned

- A **lifetime** is the stretch of code where a reference must stay
  valid, from where it is made to where it is last used.
- The borrow checker makes every lifetime fit inside the life of the
  value borrowed; otherwise you get E0597 ("does not live long
  enough"), or E0106 and E0515 when a function would return a borrow of
  its own local.
- The fixes: make the owner live longer, return an owned value, or end
  the borrow sooner, because a borrow ends at its **last use**, not at
  the closing brace.
- TypeScript's collector keeps values alive; C lets pointers dangle;
  Rust proves they never do, at no run-time cost.
