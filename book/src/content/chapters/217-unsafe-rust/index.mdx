## One byte, two ways

Every instruction the Drip VM runs starts by reading a byte. clox, the C
VM from *Crafting Interpreters*, does it with `*ip++`: read through a
pointer, move it along, and trust that it is still inside the chunk.
drip-rs does this (from `vm.rs`):

```rust
fn read_byte(&mut self) -> u8 {
    let byte = self.chunk.code[self.ip];
    self.ip += 1;
    byte
}
```

`code[self.ip]` compares `ip` with the length first, every time, and
panics if it's past the end. Could Rust read the C way? Yes, with one
keyword. drip-rs chose not to, and an attribute at the top of its
`lib.rs`, just after the doc comment, makes that choice permanent: `#![forbid(unsafe_code)]`.

<Callout kind="intuition">
Safe Rust is a building where every door checks your badge. `unsafe` is
a staff-only door: behind it, a few extra rooms open, and in those rooms
nobody checks badges for you. You sign the logbook on the way in, and
whatever happens in there is on you.
</Callout>

## Raw pointers

A reference, `&T`, is a pointer with promises attached: it is never null,
it points at a live `T`, and the borrowing rules hold. A **raw pointer**
is the same address with the promises removed. You make one with
`&raw const x` or `&raw mut x`, or from a slice with `xs.as_ptr()`:

```rust
let x = 5;
let p: *const i32 = &raw const x;
println!("{}", *p);
```

Making `p` is fine. Reading through it is not, outside `unsafe` (Rust
1.97, trimmed):

```
error[E0133]: dereference of raw pointer
  is unsafe and requires unsafe function
  or block
= note: raw pointers may be null,
  dangling or unaligned; they can violate
  aliasing rules and cause data races
```

<Callout kind="definition">
A **raw pointer** is `*const T` (read through it) or `*mut T` (read and
write through it). It may be null, dangling or misaligned, it has no
lifetime, and copying or dropping it does nothing to the value it points
at<Cite id="rustref-raw-pointer" />. Creating, copying and comparing raw
pointers is safe; **dereferencing** one is an unsafe operation.
</Callout>

## What unsafe unlocks, and what it doesn't

The Rust book lists five operations that need an `unsafe` block or
function: dereferencing a raw pointer, calling an `unsafe` function
(such as `p.add(i)` or `xs.get_unchecked(i)`), using a `static mut`,
implementing an `unsafe` trait, and reading a `union`
field<Cite id="klabnik2026" />. The Reference's list adds a few rarer
ones, such as declaring `extern` blocks for C code<Cite id="rustref-unsafety" />.

What `unsafe` does **not** do is switch anything off. Types are still
checked, and so are borrows. Take a reference into a `Vec`, push, then
use the reference, all inside `unsafe`, and Rust 1.97 still says
(trimmed):

```
error[E0502]: cannot borrow `v` as
  mutable because it is also borrowed
  as immutable
```

It adds a warning that the `unsafe` block is unnecessary.

So the promise is narrow. In the extra rooms, *you* must make sure that
every raw pointer you read is valid and every `unsafe` function's rules
are kept. Break that, and the result is **undefined behaviour**. Not a
panic: the compiler optimizes on the assumption that it never happens,
so anything may follow<Cite id="rustref-ub" />.

<UncheckedSteps client:visible />

<Callout kind="definition">
An **`unsafe`** block marks code where you uphold rules the compiler
can't check. Inside it you may use the unsafe operations; everything else
is checked as usual. An **`unsafe fn`** is one whose callers must keep a
promise, so calling it needs `unsafe` too. A `// SAFETY:` comment above
the block says what the promise is and why it holds.
</Callout>

## Safe on the outside

You rarely want `unsafe` scattered through a program. The usual shape is
a small, safe function with the check inside it and one unchecked step:

```rust
if i >= xs.len() {
    return None;
}
// SAFETY: i < xs.len()
Some(unsafe { *xs.get_unchecked(i) })
```

No caller can make this misbehave, whatever `i` they pass. That is how
`Vec`, slices and `String` are built: safe methods over a little audited
`unsafe` code inside `std`<Cite id="klabnik2026" />. You will write one in
the exercise.

## Forbidding it: drip-rs

`#![forbid(unsafe_code)]` turns the `unsafe_code` lint up to its
strictest level for the whole crate. Any `unsafe` block is an error, and
unlike `deny`, a `#[allow(unsafe_code)]` lower down can't undo it: Rust
1.97 answers `error[E0453]: allow(unsafe_code) incompatible with previous
forbid`.

What did that cost? Not pointers between heap objects: chapter 214's
arenas and `Gc<T>` handles replaced them. The run-time cost is the
checks. `read_byte` checks `ip`, and every `heap[handle]` checks the
index *and* that the slot is still `Some`, because freed slots become
`None`. To put a number on it, I copied drip-rs, deleted the `forbid`,
and replaced five checked reads with `unsafe` unchecked ones:
`read_byte`, `read_constant`, `peek`, and the arena's two index methods.
Then I timed both builds, alternating, seven runs per program, on the
book's shared 4-vCPU cloud VM (release builds, rustc 1.97). Minimum
times in ms, checked / unchecked:

| program | round 1 | round 2 |
|---|---:|---:|
| fib | 1400 / 1288 | 1404 / 1237 |
| method_call | 280 / 276 | 314 / 265 |
| properties | 730 / 655 | 706 / 654 |
| zoo | 520 / 503 | 506 / 493 |
| instantiation | 558 / 518 | 557 / 502 |

The unchecked build was 1 to 16 percent faster on minimums; the medians
of round 1 went both ways. A third round, rebuilt with plain `rustc -C
opt-level=3` while this chapter was checked, gave 4 to 12 percent. Checks that never fail are cheap: the branch
predictor learns that the index is always in bounds (chapter 27).

<Callout kind="engine" label="Under the hood">
What the checks saved is harder to time but easy to point at. The
collector of chapter 85 frees objects, so a missed root leaves a handle
to a freed slot. In C that is a use-after-free that reads whatever moved
in. In drip-rs, the stress and debug modes never reuse freed slots, so
the next `heap[handle]` finds `None` and panics with a message. The 95
stress-GC programs run with a collection before every allocation, and a
missed root fails loudly. The `forbid` only covers drip-rs's own source:
`Vec` and `HashMap` are `unsafe` inside `std`. engine/rust has no
`unsafe` blocks in its crates either, but no `forbid`, and its
dependencies use it: in oxc's arena allocator, 376 source lines contain
the word.
</Callout>

## What you learned

- A **raw pointer**, `*const T` or `*mut T`, is an address without a
  reference's promises. Making one is safe; dereferencing it is not.
- **`unsafe`** unlocks a few operations, chiefly raw-pointer
  dereferences and calls to `unsafe fn`s. It switches no checks off.
- Breaking an unsafe promise is **undefined behaviour**, not a panic.
- Keep `unsafe` small and wrap it in a safe function whose own checks
  make the promise true, with a `// SAFETY:` comment.
- drip-rs's **`#![forbid(unsafe_code)]`** cost it a few percent of run
  time and bought collector bugs that panic instead of corrupting memory.
