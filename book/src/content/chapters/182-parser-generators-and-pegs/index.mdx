## A table nobody should write by hand

Over the last three chapters a grammar of six rules turned into twelve
states, a table with nine columns, and a careful reckoning of
lookaheads; doing that by hand once is how you learn it, and doing it
for a real language, with hundreds of rules and states, would be a job
for a very patient person with a great deal of paper. It is also
exactly the kind of mechanical work a program does better. "Minimal DFAs and
scanner generators" met programs that write scanners from regular
expressions; their
partners write parsers from grammars.

<Analogy title="a knitting machine and its pattern card">
A knitter who wants the same jumper a hundred times does not knit each
stitch by hand: they punch the pattern into a card once, and the machine
follows the card. Change the pattern, punch a new card, and the machine
knits the new jumper without complaint.
<span slot="breaks">A knitting machine knits whatever the card says;
a parser generator checks the pattern first, and refuses (or warns) when
the grammar has conflicts it cannot settle.</span>
</Analogy>

<Figure takeaway="A parser generator runs once, when the compiler is built; the parser it writes runs on every program." caption="The first row happens when the compiler is built: the generator reads the grammar and writes the parser's source code. <Callout kind="definition">
A **parser generator** is a program that reads a grammar (usually with
a piece of code, an *action*, attached to each rule) and writes the
source code of a parser for it. The generated parser runs each rule's
action when it recognises that rule, and that is how it builds a tree
or computes a value.
</Callout>

<Examples of="parser-generator">

```text
exp: exp '+' exp  { $$ = $1 + $3; }
   | NUM
   ;
```

```text
%left '+'
%left '*'
```

```js
prec.left(2,
  seq($.expression, '*', $.expression)),
prec.left(1,
  seq($.expression, '+', $.expression)),
```

</Examples>

The first is a rule in yacc's notation, which Bison kept (its manual
uses this very rule): an `exp` is
`exp + exp` or a number, and the action in braces says that the value of
the whole (`$$`) is the value of the first part (`$1`) plus the third
(`$3`). Stephen Johnson's yacc, written at Bell Labs in the 1970s, took
such rules for LALR(1) grammars, with extra rules for settling
ambiguity, and wrote a parser in C<Cite id="johnson1975yacc" />. The
second is that extra help, in Bison's form: the last chapter's precedence
declarations, which let the short, ambiguous grammar above build a
conflict-free table<Cite id="bison-manual" />. The third is from
tree-sitter, a newer generator whose grammars are written in JavaScript:
`prec.left` gives each rule a precedence and an associativity, which is
how its documentation fixes the conflicts its generator
reports<Cite id="tree-sitter-docs" />.

Not every generator builds LR tables. ANTLR builds top-down parsers,
in the family of the LL parsers of "LL(1) tables and rewriting grammars". Its method, ALL(*), decides between a rule's alternatives by
looking ahead as far as it needs to, and does that analysis while
parsing rather than in advance; its authors report that it handles any
grammar without left recursion, and runs in linear time on the grammars
they measured<Cite id="parr2014allstar" />.

## Parsing expression grammars

A grammar like those of "Grammars" is a *description*: `A → x | y` says
an `A` may be an `x` or a `y`, and leaves it to the parser to find out
which, which is where ambiguity and conflicts come from. A **parsing
expression grammar** (PEG) is written as a *procedure* instead: `A ← x / y`
says "try `x`; if, and only if, it fails, try `y`".

<Analogy extra title="a ring of keys">
You try the keys on a ring in order, and the first one that turns is the
one you use, even if a key further along would also have opened the
door.
<span slot="breaks">At a door, it does not matter which key turned; in
a PEG it can matter a great deal, because the first alternative that
succeeds is final, and if the rest of the parse then fails, the other
alternatives are never tried.</span>
</Analogy>

<Callout kind="definition">
A **parsing expression grammar** (PEG) has rules `A ← e`, where `e` is
built from terminals, nonterminals, sequence (`e₁ e₂`), **ordered
choice** (`e₁ / e₂`: try `e₁`; only if it fails, try `e₂` at the same
place), greedy repetition (`e*`, `e+`, `e?`: match as many as possible,
and never give any back), and the predicates `&e` and `!e`, which
succeed if `e` would or would not match, without using up any input.
Parsing a rule at a position either fails or succeeds in exactly one
way, so a PEG is never ambiguous.
</Callout>

<Formal title="Ordered choice">

```text
e₁ at i matches up to j
──────────────────────────
e₁ / e₂ at i matches up to j

e₁ at i fails,  e₂ at i matches up to j
───────────────────────────────────────
     e₁ / e₂ at i matches up to j
```

<span slot="read">If e1 matches at position i, reaching position j,
then the choice of e1 or e2 matches at i, reaching j, and e2 is never
looked at. If e1 fails at i and e2 matches at i, reaching j, then the
choice reaches j. If both fail, so does the choice.</span>
</Formal>

<Examples of="peg">

```text
A ← "a" / "ab"
on "ab": A matches "a" only;
"ab" is never tried
```

```text
IF   ← "if" ![a-z]
on "if x":  matches "if"
on "iffy":  fails (a letter follows)
```

<Run id="peg-keyword" />

</Examples>

The first is the trap every PEG author meets once: the shorter
alternative comes first and succeeds, so the longer one is dead, and a
rule `B ← A "c"` would fail on `abc`. Put the longer alternative first
and both work. The second shows a predicate doing a scanner's job: the
keyword `if` is only a keyword when no letter follows it, and `!` checks
that without consuming the letter (this is maximal munch, from "Lookahead and
maximal munch", written into the grammar). The runnable one builds these pieces as small
JavaScript functions, each taking the input and a position and returning
where it stopped, or `-1`; try `'ifx'`, `'if('` and `'i'`.

A PEG cannot have left recursion, for the same reason recursive descent
cannot: to parse an `E`, the rule's first step is to parse an `E` at
the same position, and it never stops.

```js
// broken: E starts by calling E
const E = (s, i) =>
  choice(seq(E, lit('+'), T), T)(s, i);
E('n+n', 0);
// RangeError: Maximum call stack
// size exceeded

// working: repetition instead
const E2 = seq(T, many(seq(lit('+'), T)));
```

## Packrat: remembering every answer

Ordered choice means backtracking: when an alternative fails, the parser
goes back to where the choice began and tries the next one, and the
next alternative may well start by parsing the same rule at the same
place all over again. In the worst case that repeats a great deal of
work. The cure is to remember: the result of a rule at a position never
changes, so keep a table from (rule, position) to the result, and look
it up before parsing anything.

<PegSteps client:visible />

Bryan Ford introduced this as **packrat parsing** in 2002: with the
table, each rule runs at most once at each position, so the whole parse
takes time in proportion to the length of the input, at the price of
memory for the table<Cite id="ford2002packrat" />. Two years later he
set out PEGs themselves as a formal kind of grammar, recognition-based
rather than generative, and showed that every PEG can be parsed in
linear time this way<Cite id="ford2004peg" />. Whether a PEG is the
right tool is a matter of taste: it is never ambiguous, and it can do a
scanner's work in the same grammar (as the `IF` rule shows), but when
two alternatives overlap, ordered choice
settles the question silently, where an LR generator would have
reported a conflict.

## What you learned

- A **parser generator** reads a grammar with actions and writes a
  parser: yacc and Bison write LALR(1) parsers, ANTLR writes top-down
  ALL(*) parsers, tree-sitter's grammars are written in JavaScript.
- A **PEG** uses **ordered choice**: the first alternative that
  succeeds wins, so a PEG is never ambiguous; it also has greedy
  repetition and the predicates `&` and `!`, and it cannot be left
  recursive.
- **Packrat parsing** memoises each (rule, position), which makes a
  backtracking PEG parser run in linear time, at a cost in memory.
