## Every name costs a search

Every use of a global is an instruction like `load.global 2 'total'`,
and at run time the VM looks the name up in a hash table. However, most
of the variables a program touches are **locals** (the loop counter, the
running total), used far more often, and the compiler can already see
which `let` each use refers to; so it should settle that once, at
compile time, and give the running program something cheaper than a
name.

Look at the order in which the locals of a nested block are created
and destroyed:

```drip
{
  let a = 1;
  {
    let b = 2;
  }
  let c = 3;
}
```

`a` is born on line 2; `b` is born on line 4 and dies at the brace on
line 5; `c` is born on line 6; and at the last brace `c` and `a` die,
`c` first. Because blocks nest, the local created **last** is always
the first destroyed, which is the rule of a stack.

<Analogy title="a pile of plates by the sink">
After a dinner party, plates pile up by the sink: each new plate goes
on top, and when you wash up you take from the top, so the last plate
put down is the first one washed. If you counted the plates from the
bottom as they went down (0, 1, 2), you could say "plate 1" and anyone
would know which one you meant, without writing names on the plates.
<span slot="breaks">With a real pile you can only reach the top plate;
the VM can read or change any slot by its number, whenever it likes.
The stack order only decides which slots exist at a given moment, not
which one you may touch.</span>

## Locals in stack slots

The VM already has a stack, so each local lives **in a slot of that
same stack**, and a second piece of luck makes this almost free: when
the VM runs `let a = 1;`, the initialiser leaves `1` on top of the
stack, and if `a` lives in *that* slot, no instruction is needed to
define `a` at all.

<Callout kind="definition">
A **stack slot** is a fixed position in the VM's value stack, counted
from where the current function's part of the stack begins. Each
local variable lives in one slot, from its `let` to the end of its
block, and instructions name the local by its slot number only:
`load.local 2` means "push a copy of slot 2". No variable name
survives into the running program.
</Callout>

<Examples of="stack-slot">

```text
{ let a = 1; print a; }

0000    2 const               0 '1'
0003    3 load.local          1
0005    | print
0006    4 pop
```

</Examples>

This is the companion disassembler's listing for that block, written
one statement per line. Offset 0 pushes `1`, which lands in slot 1
(slot 0 holds the running script, as *Frames: calling and returning*
explains), and slot 1 is `a` from now on, with nothing emitted for the
`let`. At offset 3, `load.local 1` pushes a copy of slot 1 for `print`;
at offset 6, the closing brace's `pop` gives the slot back. The VM's
side is two cases of `vm.ts`:

```ts
case Op.LoadLocal:
  this.push(stack[frame.slots +
    readByte()]); break;
case Op.StoreLocal:
  stack[frame.slots + readByte()] =
    this.peek(0); break;
```

`frame.slots` is where the current function's slots begin (0 for the
script). `store.local` only peeks, because an assignment is an
expression whose value is the value assigned; when it is a statement on
its own, the compiler adds a `pop`. Used outside its block, a name is
no longer a local, so `{ let a = 1; } print a;` compiles to
`load.global` and stops with `undefined variable 'a'`.

## The compiler's model of the stack

Somebody had to decide that `a` meant slot 1, and that somebody is the
compiler, which reads the source once, emitting bytes as it goes. So at
every name it must already know what the VM's stack *will* hold, and
it keeps a small model of that stack: each function being compiled has
a `locals` array of entries `{ name, depth, isCaptured }` and a
`scopeDepth` counter (how many blocks deep it is). The rule that makes
it work is that **a local's index in the array is its stack slot**;
entry 0 is added when a function starts, for slot 0. Leaving a block:

```ts
function endScope() {
  const c = fc();
  c.scopeDepth--;
  while (c.locals.length > 0 &&
      c.locals[c.locals.length - 1]
        .depth > c.scopeDepth) {
    emit(c.locals[c.locals.length - 1]
      .isCaptured ? Op.CloseUpvalue
      : Op.Pop);
    c.locals.pop();
  }
}
```

`beginScope` only adds 1 to the counter, so entering a block costs
nothing at run time. `endScope` lowers it, then, while the last entry
is deeper than the depth we are going back to, emits a `pop` (or
`close.upvalue`, for a captured local, as *Upvalues: capturing and
closing* explains) and removes the entry: those are the pops at every
closing brace, keeping the array and the real stack the same size.

<SlotSteps client:visible />

When the compiler meets a name, `resolveLocal` searches the array
**backwards**, from the most recent declaration, and returns the index
of the first entry with that name, which becomes the operand of
`load.local` or `store.local`; with no match it returns `-1`, and the
name is looked for in enclosing functions and finally treated as a
global. Searching from the end is all that **shadowing** takes.

<Figure takeaway="Searching from the end finds the innermost declaration first." caption="For print x inside the inner block, the search starts at index 3, finds the inner x at once and stops, so the outer x in slot 1 is shadowed.">
  <ResolveFigure />
</Figure>

Declaring a local happens in two steps around its initialiser:
`declareVariable` appends the entry with depth `-1`, "not ready yet",
and after the initialiser `defineVariable` sets the real depth,
emitting nothing (at depth 0 it emits `define.global` instead). So in
`{ let x = 1; { let x = x + 1; } }` the search for `x` finds the
unready inner one first, and the compiler stops with `line 4: cannot
read 'x' in its own initialiser` rather than reading a slot that holds
nothing yet.

<Callout kind="definition">
**Compile-time scope** is the compiler's own record of which locals
exist at each point in the code: the `locals` array, each entry with
the block depth it was declared at, plus the current `scopeDepth`. It
mirrors, instruction by instruction, what the VM's stack will hold at
run time, which is how a name becomes a slot number.
</Callout>

<Examples of="compile-time-scope">

```text
{ let x = 1;
  { let y = 2; let x = 3; print x; }
  print x; }

0009    6 load.local          3
0011    | print
0012    7 pop
0013    | pop
0014    8 load.local          1
```

</Examples>

(The real program has one statement per line.) At the inner `print x`
the array holds the script (0), the outer `x` (1), `y` (2) and the inner
`x` (3), and the backwards search stops at 3: `load.local 3`. The inner
brace emits two pops, removing `y` and the inner `x`, so the outer
`print x` finds index 1. The program prints `3`, then `1`.

Real VMs split names from numbers in the same way. CPython's
`LOAD_GLOBAL` finds a global through a table of names, while its
`LOAD_FAST` pushes a local chosen by a plain index<Cite id="cpython-dis" />.
V8's Ignition interpreter is a register machine, whose instructions
name their inputs and outputs as numbered registers<Cite id="v8-ignition" />,
which play much the role that Drip's slots do. And where *The
resolver* worked out a distance for each local and kept an environment
per block, the VM's compiler does that job in the pass that emits the
bytecode, and the environments disappear.

</More>

## What you learned

- Locals live and die in stack order, so each lives in a **stack
  slot**; `load.local` and `store.local` name it by number.
- **Compile-time scope** is the compiler's `locals` array plus
  `scopeDepth`: an index is a slot, `endScope` pops, and searching from
  the end gives shadowing.
