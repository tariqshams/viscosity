## Can I install it?

Somebody reads this book, likes Viscosity, and types
`npm install viscosity`. What do they get? A library at version 0.3.0,
described as "a sass library for fluid containers that handle aspect
ratios across device sizes": the name `viscosity` on npm belongs to
someone else. What they want is this:

```text
$ npm install -g @viscosity/cli
$ viscosity --version
viscosity 0.0.1
```

That works today, because version 0.0.1 of the compiler was published
on 2026-11-02, to npm and to crates.io. This chapter is about that last
step, from "works on my machine" to "works on yours"; the next one is
about what the number 0.0.1 promises.

## What a package is

<Analogy title="a sealed box with a label">
A package is a sealed box on a warehouse shelf, with a label that says
exactly what is inside: a name and a version. Once a labelled box is on
the shelf it never changes. A fix goes into a new box with a new label,
and the numbers on the label tell the customer how different the new
box is.
<span slot="breaks">A warehouse box is the same for every customer. A
package can also say which other boxes it needs (its dependencies), and
those are fetched fresh for each customer, so two people installing the
"same" package can end up with different contents unless every
dependency is pinned; Viscosity's CLI avoids that by needing none.</span>
</Analogy>

Here is the CLI's `package.json` as it is published (some fields left
out):

```json
{
  "name": "@viscosity/cli",
  "version": "0.0.1",
  "type": "module",
  "bin": {
    "viscosity": "bin/viscosity.mjs"
  },
  "files": ["bin", "dist", "LICENSE",
    "THIRD_PARTY_LICENSES.txt"],
  "engines": { "node": ">=18" },
  "scripts": {
    "prepack": "node build.mjs"
  }
}
```

The name and version are the only fields npm requires, and together
they identify the package. `@viscosity/` is a **scope**, a namespace
that belongs to one user or organization, where only they can add
packages<Cite id="npm-publish-docs" />. `bin` asks npm to install a
`viscosity` command that runs `bin/viscosity.mjs`<Cite id="npm-package-json" />;
`files` limits the tarball to those paths; `engines` says which Node
versions it supports; and `prepack` runs the build before every pack,
so the tarball always holds a fresh build. `npm pack` makes the tarball
that `npm publish` would upload, and `npm pack --dry-run` lists what
would go in it without writing anything<Cite id="npm-publish-docs" />.

<Callout kind="definition">
An **npm package** is a folder described by a `package.json`, packed
into a tarball and published to a **registry**. Its **name** (possibly
scoped, `@scope/name`) and **version** identify it. `bin` installs
commands, `files` limits what is packed, `dependencies` lists other
packages it needs with version ranges, and `engines` says which Node
versions it supports.
</Callout>

<Examples of="npm-package">

```json
{ "name": "tiny", "version": "1.0.0" }
```

```text
$ npm view @viscosity/cli dist.fileCount
5
```

```json
"exports": { ".": {
  "node": "./dist/node/viscosity_wasm.js",
  "browser": "./dist/web/viscosity_wasm.js"
} }
```

</Examples>

The first is the smallest valid `package.json`: a name and a version,
nothing else. The second asks the public registry about the real CLI:
its tarball holds five files (the bin file, the bundle, `package.json`
and the two licence files). The third is a trimmed piece of
`@viscosity/wasm`'s `package.json`, the Rust engine compiled to
WebAssembly from the previous chapter: an `exports` map lets one package
name hand Node one build and a browser bundler another.

## Three bugs nobody could see

The CLI did not start like that. Before publishing anything, the author
packed the CLI as it first was and installed the tarball into an empty
folder, the way a stranger would. Step through what happened:

<ShipSteps client:visible />

<Analogy title="moving out of a flat">
When you move out, you find out which things were yours and which came
with the flat: the kettle you used every day turns out to belong to the
landlord, and the new place has no curtains. A package leaving its
repository finds out the same way what the repository was quietly
providing.
<span slot="breaks">You notice a missing kettle the first morning. A
package's missing pieces may show up only on a stranger's machine, with
a different Node version or folder layout, which is why the test is to
install the tarball somewhere empty, the way a stranger would.</span>
</Analogy>

None of the three bugs was visible from inside the repository, because
there everything works:

1. **No dependencies.** `cli.ts` imports the core with a relative path,
   `'../../core/src/index.ts'`, which exists only in the repository's
   folder layout, and its `package.json` declared no dependencies, so
   npm installed one package and nothing else.
2. **TypeScript in `node_modules`.** Node 22.18 and later strip
   TypeScript types by default, which is why the repository runs `.ts`
   files directly; however, Node deliberately refuses to do it under
   `node_modules`, to discourage publishing TypeScript
   sources<Cite id="node-typescript-docs" />.
3. **The silent main check.** `cli.ts` ended with a check, so that
   importing it in a test does not run it, which compared
   `import.meta.url` with `process.argv[1]`. Run through npm's link in
   `node_modules/.bin`, `argv[1]` is the link's path, not the file's,
   so the check was false and the command exited with status 0 having
   done nothing.

The fixes were a build step and one small file. `build.mjs` runs
esbuild, which compiles the TypeScript and pulls the core, the front
ends and their parsers (acorn, acorn-walk, sucrase) into one file,
`dist/viscosity.mjs`, so the package has no runtime dependencies; and
because a bundle contains other people's code, the build also writes
`LICENSE` and `THIRD_PARTY_LICENSES.txt`. A separate entry file calls
`main` without any check:

```js
#!/usr/bin/env node
import { main } from
  '../dist/viscosity.mjs';
process.exit(main(process.argv.slice(2)));
```

The `#!` line matters: npm's documentation asks that every `bin` file
start with it, or the script is not run by Node<Cite id="npm-package-json" />.
(The check in `cli.ts` now compares real paths, so running the source
through a link works too.)

<Prompts ids={['pkg-ts', 'pkg-deps', 'pkg-main']} />

<Callout kind="engine" label="Under the hood">
Node's type stripping replaces type annotations with whitespace and
checks nothing. By default it runs only TypeScript whose features need
no code generation (an `enum` does), so it needs no source maps: line
numbers stay the same<Cite id="node-typescript-docs" />. That is why the
repository can run its `.ts` sources directly on Node 22.18 or later,
the version its own `engines` field asks for, and also why that
convenience stops at the edge of `node_modules`: the published CLI is
plain JavaScript, and asks only for Node 18.
</Callout>


## Out into the world

On 2026-11-02, `scripts/release.sh` published everything at version
0.0.1: `@viscosity/cli` (the TypeScript engine's command) and
`@viscosity/wasm` to npm, and the Rust port's six crates to crates.io.

<Figure takeaway="Crates go up in dependency order; a re-run skips what is already there." caption="What was published, and in what order. Each crate needs the ones above it to be on crates.io before it can be uploaded.">
  <ReleaseOrder />
</Figure>

Crates go up in dependency order, because cargo will not publish a
crate whose dependencies are not on crates.io yet: `viscosity-vir` (the
IR) first,
then `viscosity-core`, the two front ends, `viscosity-cli` and, last,
`viscosity-wasm`. The first run published five of them; crates.io then
answered the sixth with HTTP 429, "published too many new crates in a
short period" (a limit on how many *new* crates one account may create
at once), and a re-run about ten minutes later skipped the five already
there and published the sixth. Both registries were then checked the
way a stranger would use them: `npm install -g @viscosity/cli` and
`cargo install viscosity-cli` each give a `viscosity` command whose
`--version` prints `viscosity 0.0.1`. (Whether the book and docs move
to the viscosity.dev domain is still the author's decision.)

## What you learned

- An **npm package** is a tarball described by `package.json`,
  identified by **name** and **version**, with `bin`, `files`,
  `dependencies` and `engines`. The name `viscosity` is taken, so the
  CLI is `@viscosity/cli`.
- Packing and installing the CLI found three bugs (undeclared
  dependencies, TypeScript under `node_modules`, a main check that
  failed through npm's link); a bundle and a bin entry fixed them.
- On 2026-11-02, version 0.0.1 went to npm (`@viscosity/cli`,
  `@viscosity/wasm`) and crates.io (six crates, in dependency order,
  one of them a day's lesson in rate limits).
