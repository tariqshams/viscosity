## A tree that contains itself

*Syntax trees* built expressions out of nodes, where an addition node
holds two smaller expressions. Write that the obvious way as a Rust
enum (from *Enums and match*):

```rust
enum Expr {
    Num(f64),
    Add(Expr, Expr),
}
```

rustc 1.97 refuses, and says why (trimmed):

```text
error[E0072]: recursive type `Expr` has
  infinite size
3 |     Add(Expr, Expr),
  |         ---- recursive without
  |              indirection
help: insert some indirection (e.g., a
  `Box`, `Rc`, or `&`) to break the cycle
```

Rust stores an enum's fields *inside* it, so it must know the size of
every type before the program runs (the stack and the heap of *Pointers,
the stack and the heap* need it). An `Expr` that holds two `Expr`s
would contain itself, which contains itself again, forever, so it has
no size at all. In TypeScript this never comes up, because an object's
fields hold *references* to other objects, never the objects
themselves. The help line says what Rust needs: some **indirection**, a
field that holds a pointer to the child instead of the child.

<Analogy title="nesting dolls versus a note">
A set of nesting dolls has each doll inside the next; ask for a doll
that contains a doll *of its own size* and no set could ever be made.
Now let each doll hold a slip of paper saying which shelf the next doll
is on. Every doll is the same small size, and the chain can be as long
as you like.
<span slot="breaks">A slip of paper can point at any doll, even one
already pointed at; a `Box` is the *only* pointer to its doll, so two
nodes can never share a child.</span>
</Analogy>

## Box: one owner, on the heap

A **`Box<T>`** is that slip of paper: a pointer to a `T` stored on the
heap. `Box::new(v)` moves `v` to the heap and gives you the box. The
box is the value's only owner, so all of *Ownership* still holds: moving
the box moves the value's ownership, and dropping the box drops the
value and frees its memory. A box costs one heap allocation and
nothing else; there is no counting and no check when you use
it<Cite id="rust-book-smart-pointers" />.

```rust
enum Expr {
    Num(f64),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
}
```

Now an `Expr` holds at most two pointers, 8 bytes each on this machine,
plus a tag saying which variant it is, so its size is fixed
(`size_of::<Expr>()` is 24 here), and the children live
on the heap:

  <BoxTree />
</Figure>

<Callout kind="definition">
A **`Box<T>`** is a pointer to a `T` on the heap that **owns** it: there
is exactly one box per value, moving the box moves ownership, and
dropping the box drops the `T` and frees its memory. A `Box` has a
fixed size whatever `T` is, which makes recursive types possible, and
it lets you use a trait object (`Box<dyn Trait>`) as an owned
value<Cite id="rust-book-smart-pointers" />.
</Callout>

<Examples of="box">

```rust
let b = Box::new(5);
println!("{}", *b + 1); // 6
```

```rust
let e = Expr::Mul(
    Box::new(Expr::Num(2.0)),
    Box::new(Expr::Num(3.0)),
);
```

```rust
// drip-rs's object.rs
pub struct ObjString {
    pub chars: Box<str>,
    pub hash: u32,
}
```

</Examples>

The first boxes a single number: the `5` now lives on the heap, `*b`
follows the pointer (as `*` does for references in *Borrowing*), and
the program prints `6`; when `b` goes out of scope the heap memory is
freed. The second builds the tree for `2 * 3`, each child boxed. The
third is real: a Drip string's characters are a `Box<str>`, text on
the heap owned by exactly one string object. It is like a `String`
that can never grow, so it needs no spare room and is one word smaller,
which suits interned strings that never change.

## Rc: several owners, counted

A tree is the perfect case for `Box`: each node has one parent, which
owns it. Bytecode is not like that. In drip-rs, one compiled function's
`Chunk` is needed by the function object, by every call frame running
that function (a recursive function has many), and by the VM's own
"current chunk" register. Which of them owns it? All of them, and the
chunk must live exactly as long as the last one needs it.

<Analogy title="a shared flat's sign-in sheet">
A shared flat keeps a sheet by the door. Each new tenant signs in; each
one who moves out crosses their name off. Nobody "owns" the flat more
than the others, and whoever crosses off the last name turns off the
lights and hands back the keys.
<span slot="breaks">Flatmates can move out in any order and the flat
does not care; an `Rc` is the same, but it cannot notice two flats that
each list the other as a tenant, which is the next chapter's
problem.</span>
</Analogy>

That is **`Rc<T>`**, short for *reference counted*: the idea from
*Reference counting*, as a library type. `Rc::new(v)` puts `v` on the
heap next to a **strong count** of 1. `Rc::clone(&r)` does not copy
`v`; it copies the pointer and adds 1. Dropping an `Rc` subtracts 1,
and when the count reaches 0 the value is dropped<Cite id="rust-std-rc" />.
Step through it:

<RcSteps client:visible />

<Analogy title="a group chat">
A group chat stays alive while anyone is still in it. People join and
leave, and when the last person leaves, the chat is deleted. Each
member holds the same chat, not a copy of it.
<span slot="breaks">Anyone in a group chat can post; an `Rc` gives its
owners only shared, read-only access to the value, as the next part
shows.</span>
</Analogy>

There is a catch. Try to change a value through one of its owners:

```rust
let up = Rc::new(Upvalue { value: 0.0 });
let a = Rc::clone(&up);
a.value += 1.0; // E0594
```

```text
error[E0594]: cannot assign to data in
  an `Rc`
= help: trait `DerefMut` is required to
  modify through a dereference, but it is
  not implemented for `Rc<Upvalue>`
```

Of course: `a` and `up` point at the same value, and *Borrowing*'s rule
is many readers *or* one writer. With several owners alive at once, an
`Rc` can only ever hand out shared access. (The next chapter shows the
tool that adds mutation back, and what it costs.)

<Callout kind="definition">
An **`Rc<T>`** ("reference counted") is a pointer to a heap value with
several owners. The value carries a **strong count**: `Rc::clone` adds
1, dropping an `Rc` subtracts 1, and the value is dropped when the
count reaches 0. Through an `Rc` you can only read. `Rc` is for one
thread only (its count is not updated atomically)<Cite id="rust-std-rc" />.
</Callout>

<Formal title="The strong count">

```text
strong(v) = number of live Rc<T> to v
Rc::clone:   strong(v) ← strong(v) + 1
drop an Rc:  strong(v) ← strong(v) − 1
strong(v) = 0  ⟹  v is dropped
```

<span slot="read">The strong count of a value v is how many Rc pointers
to it are still alive. Cloning an Rc adds one to it (the arrow ← reads
"becomes"), dropping one subtracts one, and when the count reaches zero
the value itself is dropped.</span>
</Formal>

<Examples of="rc">

```rust
let a = Rc::new(String::from("hi"));
let b = Rc::clone(&a);
Rc::strong_count(&a); // 2
```

<Run id="rc-counts" />

```rust
// drip-rs's vm.rs, starting a call:
let chunk = Rc::clone(
    &self.heap[function].chunk);
self.frames.push(CallFrame {
    closure,
    chunk: Rc::clone(&chunk),
    ip: 0, slots });
self.chunk = chunk;
```

</Examples>

The first shares one string between `a` and `b`: two owners, one
`String`, count 2. The runnable one prints the count after each step
of the diagram (1, then 3, then 2) and checks with `Rc::ptr_eq` that
two owners really point at the same value. The third is real: when the
VM calls a function, it clones the function's `Rc<Chunk>` once for the
new call frame and keeps the original in its `chunk` register, so the
bytecode is shared three ways and copied never. A chunk is frozen once
compiled, so read-only access is all anyone needs.

<OtherLanguages title="Two names for one heap value">

```rust
let a = Rc::new(vec![1, 2, 3]);
let b = Rc::clone(&a);
println!("{}", Rc::strong_count(&a));
// 2; freed when a and b are both gone
```

```ts
const a = [1, 2, 3];
const b = a; // same array, no count
// freed some time after nothing
// can reach it, by the collector
```

</OtherLanguages>

In TypeScript every object is shared like this by default, as
*References: two names, one object* showed, and the garbage collector
decides when to free it, at a moment you cannot predict. Rust makes
sharing something you ask for (`Rc`), and frees the value at an exact
point, the moment the last owner goes, which is *Reference counting*
built into the type rather than into the engine.

## What you learned

- A **`Box<T>`** puts a value on the heap with exactly one owner, and
  costs only the allocation. Its fixed size makes recursive types,
  such as syntax trees, possible.
- An **`Rc<T>`** shares one heap value among several owners, keeping a
  **strong count**; `Rc::clone` adds 1, dropping subtracts 1, and the
  value is dropped at 0.
- Through an `Rc` you can only read (E0594 otherwise), because other
  owners may be reading too.
- drip-rs uses `Box<str>` for a string's characters and `Rc<Chunk>`
  for bytecode shared by call frames.

Next: `RefCell`, which brings mutation back by checking borrows while
the program runs, and the one shape `Rc` can never free.
