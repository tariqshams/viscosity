## The port is done

Part XII set itself one goal in *Planning drip-rs*: a Rust VM that
behaves exactly like the TypeScript VM, the same output, the same error
messages on the same lines and the same exit codes, on every program.
drip-rs meets it: all 334 corpus tests pass, so do the 165 stress-GC
programs that collect before every allocation, and on 2026-11-02
`compare_with_ts.mjs` found its output identical to the TypeScript VM's
on 343 corpus programs and 2,000 mangled ones. It runs the ten
benchmarks about four times as fast. Was it worth it? That depends on
what you count, so this chapter counts everything it can, the costs as
carefully as the gains.

## What ownership forced

Some of drip-rs's designs exist because of Rust's ownership rules (from
*Ownership* and *Borrowing*), not because a VM needs them:

- **Arenas and handles.** Objects that point at each other in any
  pattern, cycles included, cannot be Rust references, so each kind
  lives in its own `Arena<T>` (there are nine, from strings to bound
  methods) owned by the `Heap`, and links between objects are `Gc<T>`
  handles, typed indices (from *Arenas and typed indices* and *Heap
  objects in an arena*).
- **Roots passed in.** The heap cannot borrow the VM that owns it, so
  the VM hands its roots to `Heap::collect` as `&dyn Trace` values (from
  *A garbage collector in Rust*).
- **Read first, then write.** Holding a reference into the heap while
  changing it is E0502, so code reads what it needs into locals first:
  the one `clone()` of a table in the whole VM is the `inherit`
  instruction's, from *extends and super in Rust*.

The TypeScript VM could skip all three; a JavaScript object can point at
any other, and V8 frees them. None of the three is strange (arenas with
indices are an old technique in any language), but Rust made them
compulsory, and the code is longer for it.

## What it caught, and what it could not

Each Rust chapter of this Part met the compiler's refusals: two mutable
borrows of the compiler at once (E0499), a reference into a heap that
was about to change (E0502), and the two below.

<Examples of="rust-tradeoffs">

```text
error[E0004]: non-exhaustive patterns:
  `Op::Print` not covered
4 |     match op {
  |           ^^ pattern `Op::Print`
  |              not covered
```

```text
error[E0308]: mismatched types
7 |     fields(c);
  |            ^ expected
  |   `Gc<ObjInstance>`,
  |   found `Gc<ObjClass>`
```

<Run id="stale-handle" />

</Examples>

The first is rustc 1.97 on a three-variant enum whose `match` forgets
one (trimmed and wrapped): drip-rs's `Vm::run` matches on all 53
`OpCode` variants, and adding a 54th opcode without an arm for it is a
compile error, not a silent fall-through. The second is a toy with
drip-rs's `Gc<T>` shape: a handle to a class passed where a handle to
an instance is wanted. The TypeScript VM has types too, but its
casts, such as `this.peek(0) as ObjClass`, switch them off wherever a
value comes off the stack; drip-rs opens such values with a `match`. Each of these was found in
seconds, by the compiler, before any test ran; in C the borrowing
mistakes could have been a dangling pointer or two writers to one
object, found only when something broke. At run time, every index is
checked, and `#![forbid(unsafe_code)]` means no line of drip-rs can turn
the checks off.

The third, which you can run, is what Rust cannot see. A `Gc<T>` is a
number. If the VM forgets to pass a root, the program compiles, and the
collector frees an object that is still in use; in normal mode the
arena reuses the slot, the next object moves in, and the stale handle
reads *it*. No crash and no undefined behaviour, just the wrong answer:
the example prints `zoo` where it meant `fib`. That is why drip-rs's
debug and stress modes never reuse a slot (a stale read then panics) and
why the 165 stress-GC programs exist. Rust made the bug **safe**;
making it **impossible** took tests.

<Formal title="Safe is not the same as correct">

```text
safe(P)    ⇒ no undefined behaviour in P
safe(P)    ⇏ correct(P)
passes(P, C) ⇒ correct on the programs in C
```

<span slot="read">If a program P is written in safe Rust, it has no
undefined behaviour; but being safe does not make it correct. Passing
the corpus C shows it is correct on the programs in C, and nothing
more.</span>
</Formal>

## What it cost

I counted code lines in both VMs on 2026-11-02: not blank, not
comments, and for Rust nothing from a module's `#[cfg(test)]` onwards.

<LocBars />

drip-rs is 3,328 lines against the TypeScript VM's 1,714, 1.94 times as
many. Not all of the extra is about ownership. `value.rs` reimplements
JavaScript's way of printing numbers, which the TypeScript VM gets from
`String(n)`; the scanner works on bytes and spells out each case; and
`main.rs` is a 50-line command line with no twin inside `ts/src/vm`.
Seven `unreachable!` calls mark facts the types cannot express ("the
compiler always puts a class here"). The rest is the price of arenas,
handles and passed-in roots, and of a `Result` on every path that can
fail. There is also the build: a clean release build with `lto` took
about 7.5 seconds here, where the TypeScript VM runs straight from
source.

## What it bought

Speed, on the committed run of 2026-11-02: from 1.26 to 4.94 times the
TypeScript VM's speed on the ten programs, geometric mean 3.94, and 3.98
against the tree-walker, with the caveats of *Benchmarks: three
implementations* attached (best of three on a shared machine, start-up
and compiling included). Where did it come from? Not from skipping
checks: *Optimizing the Rust VM* measured an unchecked `read_byte` and
found 8% fewer instructions and no measurable time. It came from the
same design running as compiled machine code, and from keeping the hot
state in fields of the `Vm`: removing just the chunk register made fib
about 2.1 times slower. And it bought a single 594 KB executable that
needs nothing installed, with no dependencies at all (its `Cargo.lock`
lists only drip-rs itself).

<Callout kind="definition">
The **Rust trade-offs**, as drip-rs paid them: memory safety without a
garbage-collected runtime, mistakes in types, borrows and exhaustiveness
caught at compile time, and about four times the speed of the
TypeScript VM; in exchange, nearly twice the code, a design shaped by
ownership (arenas, handles, roots passed in), a build step, and logic
bugs in safe code that only tests can find.
</Callout>

<Callout kind="engine" label="Under the hood">
The Rust book describes the borrow checker's job as preventing data
races and dangling references at compile time<Cite id="klabnik2026" />,
and drip-rs shows both the reach and the limit of that: no reference in
drip-rs can dangle, because objects are reached through handles, but a
handle can still name a slot whose object has gone, which is the same
mistake one level up. Part XIII builds a much larger Rust program, the
Viscosity engine, on the same habits: arenas, typed indices, and a
shared test suite to check what the types cannot.
</Callout>

## What you learned

- Ownership **forced** arenas with typed handles, roots passed in to the
  collector, and reading before writing.
- The compiler **caught** missing match arms, wrong handle types and
  borrow conflicts; it **cannot** catch a forgotten root: safe, not
  correct.
- The port **cost** 1.94× the lines and a build step, and **bought**
  3.94× the TypeScript VM's speed and one dependency-free binary.
