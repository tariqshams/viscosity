## Counting with names

Viscosity's analysis wants to know which fields a loop touches, and how
often: `x` three times, `vx` once, `y` once. In TypeScript you reached
for a `Map` (*Map and Set*); in Rust it is `HashMap<K, V>`, a map from
keys of type `K` to values of type `V`, built on the hash table you
wrote in *Finding things fast: hash tables*. It is not imported
automatically, so a file that uses it starts with
`use std::collections::HashMap;`.

<Analogy title="a cloakroom">
At a cloakroom you hand over your coat and get a tag; later the tag
gets you your coat back. The cloakroom now holds the coat (you do not
have it any more), and asking with a tag nobody issued gets you a polite
"no coat here", not someone else's coat.
<span slot="breaks">A cloakroom hangs coats in the order they arrive,
and you could walk along the rail; a `HashMap` puts each entry wherever
its key's hash says, so walking through it gives an order that can change
from one run of the program to the next.</span>
</Analogy>

<Analogy extra title="pigeonholes in a staff room">
A staff room has a wall of pigeonholes. Instead of searching every hole
for a teacher's post, there is a rule that turns a name into a hole
number at once (say, from the first letters), so finding the post takes
the same short time however many teachers there are.
<span slot="breaks">Two names can share a hole under that rule, and
then someone has to look a little further; the hash table handles such
collisions for you, and its rule (the hash function) is deliberately
unpredictable, to stop an attacker filling one hole on purpose.</span>
</Analogy>

## Insert, get, entry

```rust
let mut ages: HashMap<String, u32> =
    HashMap::new();
ages.insert(String::from("ada"), 36);
println!("{:?}", ages.get("ada"));
// Some(36)
println!("{:?}", ages.get("alan"));
// None
```

`insert` adds a key and its value, or replaces the value if the key is
already there (and returns the old one, as an `Option`). `get` returns
an `Option<&V>`, because the key may be missing: you get a borrowed look
at the value, which the map keeps. `contains_key`, `remove` and `len`
do what their names say. Counting, however, needs something more:
"if the key is new, start at zero; either way, add one". That is the
**entry API**; step through it:

<EntrySteps client:visible />

`entry(f)` finds the slot for `f`; `or_insert(0)` puts in `0` only if
the slot was empty, and either way returns a mutable reference to the
value, which `*... += 1` follows and changes<Cite id="rust-book-hashmaps" />.

<Callout kind="definition">
A **`HashMap<K, V>`** is Rust's hash table. It owns its keys and its
values. `insert` adds or replaces, `get` returns `Option<&V>`, and
`entry(k).or_insert(v)` returns a mutable reference to the value for
`k`, inserting `v` first if there was none. Its iteration order is
arbitrary, and can change from run to run<Cite id="rust-std-hashmap" />.
</Callout>

<Formal title="A map is a partial function">

```text
m : K ⇀ V
get(m, k) = Some(m(k))  if k ∈ dom(m)
          = None        otherwise
insert(m, k, v) = m[k ↦ v]
```

<span slot="read">A map m from K to V is a partial function: it gives a
value for some keys (its domain, dom(m)) and none for the rest. get of k
is Some of the value when k is in the domain, and None otherwise.
Inserting v under k gives the same map, except that k now leads to v
(the arrow ↦ reads "maps to").</span>
</Formal>

<Examples of="hashmap">

```rust
let mut m = HashMap::new();
m.insert("x", 1);
m.insert("x", 2);   // replaces: Some(1)
m.len();            // 1
```

```rust
let used = ["x", "vx", "x", "y", "x"];
let mut n = HashMap::new();
for f in used {
    *n.entry(f).or_insert(0) += 1;
}
n.get("x");  // Some(3)
```

```rust

```

</Examples>

The first shows that a key appears at most once: the second `insert`
replaces the value and hands back the old one, so the map still has one
entry. The second is the field count, with the counting line from the
diagram. The third is real: the Rust port of Viscosity builds SSA form
(Part VI), and for each block it keeps a map from each variable to the
value that currently defines it, a map of maps.

## The map owns its keys

Insert a `String` key and it moves into the map, exactly as passing it
to a function would. Spot the difference:

```rust
let k = String::from("x");
m.insert(k, 1);
println!("{}", k);          // ✗
m.insert(k.clone(), 1);     // ✓ a copy
```

```text
error[E0382]: borrow of moved value: `k`
5 |     m.insert(k, 1);
  |              - value moved here
6 |     println!("{}", k);
  |                    ^ value borrowed here
  |                      after move
help: consider cloning the value if the
  performance cost is acceptable
```

Inserting a `&str` key instead stores only the borrow, which is fine as
long as the strings outlive the map (the chapter *Lifetimes* is about
exactly that). Reading a missing key with `m["mass"]` panics with `no
entry found for key`, so prefer `get` unless absence is a bug.

<OtherLanguages title="Counting with a map">

```rust
let mut n: HashMap<&str, i32> =
    HashMap::new();
for f in ["x", "vx", "x"] {
    *n.entry(f).or_insert(0) += 1;
}
println!("{:?}", n.get("x")); // Some(2)
```

```ts
const n = new Map<string, number>();
for (const f of ['x', 'vx', 'x']) {
  n.set(f, (n.get(f) ?? 0) + 1);
}
console.log(n.get('x')); // 2
```

</OtherLanguages>

The two read alike, with three real differences. A JavaScript `Map`
iterates in insertion order<Cite id="mdn-map" />; a `HashMap` promises
nothing. TypeScript's `get` returns `number | undefined`, where Rust's
returns `Option<&i32>`. And the TypeScript version looks the key up
twice (`get`, then `set`), while `entry` looks it up once.

The order matters for this book. The Rust port of Viscosity must make
the same decisions as the TypeScript one, message for message, so where
order reaches the output it uses `IndexMap`, from the `indexmap` crate,
a hash map that remembers insertion order. A comment in
`engine/rust/crates/core/src/builder.rs` says why: the incomplete phis
of SSA construction are filled in insertion order, which "decides value
numbering and the order of instructions, exactly as in the TS
reference".

<Prompts ids={['map-order', 'map-indexmap']} />

<Callout kind="engine" label="Under the hood">
std's `HashMap` is a Rust port of Google's SwissTable, using quadratic
probing and SIMD lookups, and by default it hashes keys with SipHash
1-3, randomly seeded, to resist attackers who choose keys that
collide<Cite id="rust-std-hashmap" />. drip-rs does not use it for
Drip's globals and fields: its `table.rs` is the table of *Finding
things fast: hash tables* ported, with linear probing, tombstones, and
storage as a struct of arrays, `keys: Vec<Option<StrRef>>` beside
`values: Vec<Value>`. Its keys are interned strings (*String
interning*) whose handle carries the hash, so the table never runs a
hash function during a lookup at all.
</Callout>

## What you learned

- A **`HashMap<K, V>`** owns its keys and values; `insert` adds or
  replaces, and `get` returns `Option<&V>`.
- `*m.entry(k).or_insert(0) += 1` is the counting idiom: one lookup,
  and a mutable reference to the value.
- Inserting a `String` key moves it into the map.
- Iteration order is arbitrary and changes between runs; use `IndexMap`
  (or sort) when order reaches the output.
