## Numbers only

Every Playground in this book has a small **TS / Rust** switch, and
choosing Rust compiles your code with this function from
`engine/rust/crates/wasm/src/lib.rs`, in your browser:

```rust
pub fn compile(source: &str)
    -> Result<Output, JsError>
```

A string goes in; a struct of two strings, or an error, comes out. But
it runs in the browser's second virtual machine, WebAssembly, whose
functions pass only numbers, so something must translate on both sides
of every call.

<Analogy title="a hatch in a wall">
WebAssembly is a hatch in a wall, just big enough for a few numbers at a
time. wasm-bindgen is a pair of clerks, one on each side. Yours puts your
letter in a locker on the far side and passes the locker number through
the hatch; the other clerk opens the locker and reads it.
<span slot="breaks">Real clerks hand over the original letter; the
JavaScript clerk writes out a *copy* in a different alphabet (UTF-8
rather than UTF-16), and a letter with a malformed character arrives
slightly changed.</span>
</Analogy>

<Analogy extra title="a shipping container">
A shipper does not care which port, crane or lorry handles the box,
because every one of them is built for the same standard size.
<span slot="breaks">A port does not open the box to check what is
inside. A WebAssembly engine does: it *validates* every module before
running a single instruction of it.</span>
</Analogy>

## A module, byte by byte

*A tiny JIT* already borrowed WebAssembly as a door to machine code; here
is a refresher, a whole module of 41 bytes that exports `add`, adding two
32-bit integers. Step through the bytes:

<ModuleBytes client:visible />

A module is the magic number `\0asm`, the version, then **sections**,
each an id, a length and the contents<Cite id="wasm-spec-core" />. The
body of `add`, `20 00 20 01 6a 0b`, is stack-machine bytecode, like
Drip's: push local 0, push local 1, add, end. Before it runs, an engine
**validates** the module, type-checking every function, which fixes the
stack height at every point, so engines compile modules to machine code
with the slots as registers<Cite id="wasm-spec-core" />.

<Callout kind="definition">
**WebAssembly** (Wasm) is a standardised, portable, low-level binary
format for code. A **module** is a preamble (`\0asm`, version 1) followed
by **sections**: types, functions, memories, exports, code and others.
Function bodies are bytecode for a typed **stack machine**; engines
**validate** a module before running it, and usually compile it to
machine code.
</Callout>

<More title="Running the 41 bytes, and reading LEB128">
The program loads the module with the synchronous `new
WebAssembly.Module` (a real page uses `await
WebAssembly.instantiate(bytes)`, which compiles without freezing the
page<Cite id="wasm-spec-jsapi" />) and prints `add(2, 3)` and
`add(2147483647, 1)`, which is `-2147483648`, because `i32` arithmetic
wraps around at 2³².

<Run id="wasm-add" />

<Formal title="Reading an unsigned LEB128 number">

```text
bytes b₀ b₁ … bₘ, where only bₘ < 0x80
n = Σₖ (bₖ & 0x7f) × 2^(7k)
e.g. 0x80 0x01 → 0 + 1 × 128 = 128
```

<span slot="read">A number is a run of bytes, and every byte except the
last has its top bit set (it is at least 0x80, "more follows"). Take the
low 7 bits of each byte, multiply the k-th group by 2 to the power 7k,
and add them up. The bytes 0x80 then 0x01 give 128.</span>
</Formal>
</More>

## One flat memory

Real programs need memory, and in the classic design WebAssembly has no
objects, no shapes and no garbage-collected heap: there is one long
array of bytes, the **linear memory**, and instructions such as
`f64.load` and `f64.store` read and write 8 bytes at a numeric
address<Cite id="wasm-spec-core" />. It grows in **pages** of 65,536
bytes, stores numbers little-endian, and an access past the end does not
corrupt anything: it **traps**, which JavaScript sees as a thrown
`WebAssembly.RuntimeError`. JavaScript reaches the same bytes through
`memory.buffer`, so struct-of-arrays columns map onto it as one start
address per column:

<Figure caption="A design for two columns, x and vx, with capacity 4. Each f64 is 8 bytes, so the vx column starts at byte 32. WebAssembly loads from the addresses; JavaScript views each column as a Float64Array over the same memory." takeaway="SoA in linear memory is a list of start addresses, one per column.">
  <ColumnsInMemory />
</Figure>

<Callout kind="definition">
**Linear memory** is a WebAssembly module's contiguous, mutable array of
raw bytes, addressed by integers from 0. Its size is a whole number of
64 KiB **pages**, and it can grow. Loads and stores are little-endian,
and an out-of-bounds access **traps**. JavaScript reaches it as
`memory.buffer`, an `ArrayBuffer` that typed arrays can view.
</Callout>

<Examples of="webassembly linear-memory">

```js
const mem = new WebAssembly.Memory(
  { initial: 1 });
const xs = new Float64Array(mem.buffer);
mem.grow(1);
xs.length; // 0: the old buffer is gone
const ys = new Float64Array(mem.buffer);
ys.length; // 16384: two pages of f64s
```

</Examples>

The memory starts at one page, so the first view sees 8,192 doubles.
Growing by one page **detaches** the old `ArrayBuffer` and makes a new
one<Cite id="wasm-spec-jsapi" />, so the old view suddenly has length 0,
while a new view sees both pages. Make views again after every grow.

<Prompts ids={['lm-detach']} />

<More title="Columns in linear memory, run, and what Viscosity has not built">
With capacity `cap`, column `k` starts at byte `k * cap * 8`, and element
`i` is `i * 8` bytes further on. This program exports a memory and a
`get(i)` doing `f64.load` at `i * 8`; JavaScript writes four numbers and
WebAssembly reads them back, then it shows the bytes of `1.5`, the trap
past the page, and the grow.

<Run id="wasm-columns" />

A loop over `x` and `vx` in linear memory would walk two contiguous runs
of bytes, and WebAssembly's SIMD instructions such as `f64x2.add` handle
two lanes at once<Cite id="wasm-simd" />. But neither Viscosity engine
has a WebAssembly back end: both rewrite source code, and WebAssembly
runs *the compiler*, not its output. Emitting hot loops as WebAssembly is
a design, not code (strings and objects have no place in linear memory,
and every call crosses a boundary), and whether it would pay is
unmeasured. WebAssembly 3.0 added garbage collection, multiple memories
and 64-bit memories<Cite id="wasm-finished-proposals" />, so such a back
end would face this whole track's question again: which layout, decided
by whom.
</More>

## The real crate

`crates/wasm/src/lib.rs` is the whole wrapper, 117 lines with its tests.
Its core, simplified:

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen(getter_with_clone)]
pub struct Output {
    pub code: String,
    pub explain: String,
}

#[wasm_bindgen]
pub fn compile(source: &str)
    -> Result<Output, JsError> {
    run(source, CompileOptions::default())
}
```

`#[wasm_bindgen]` marks what JavaScript should see: `Output` becomes a
JavaScript class, and `compile` an exported function, and
`getter_with_clone` lets JavaScript read the `String` fields by cloning
them<Cite id="wasm-bindgen-guide" />. `run` calls the core compiler and
turns its error into a `JsError`; `compileWith` and `compileLanguage`
take options, and Python.

<Callout kind="definition">
**wasm-bindgen** generates the bindings between Rust compiled to
WebAssembly and JavaScript. The `#[wasm_bindgen]` attribute marks
exported functions and structs; the `wasm-bindgen` command-line tool then
reads the `.wasm` file and writes the JavaScript glue and `.d.ts` types
that turn strings, structs and `Result`s into the numbers WebAssembly
actually passes, and back<Cite id="wasm-bindgen-guide" />.
</Callout>

<Examples of="wasm-bindgen">

```ts
// what wasm-bindgen wrote for the crate
export class Output {
  free(): void;
  [Symbol.dispose](): void;
  code: string;
  explain: string;
}
export function compile(
  source: string): Output;
```

</Examples>

This is the declaration file wasm-bindgen generated for the real crate
(trimmed). The `Err` side has vanished from the type, because it becomes
an exception, and `Output` has a `free()`, because the struct lives in
Rust's memory.

## Crossing the boundary

The generated `compile` calls `passStringToWasm0`, which asks the
module's own allocator for room in linear memory and writes the string
there as UTF-8; then the real call, `wasm.compile(ptr0, len0)`, is two
numbers in, and three numbers out (an address, an error slot and an "is
it an error?" flag). If the flag is set the glue throws; otherwise it
wraps the address in a JavaScript `Output`. Step through one call:

<BoundarySteps client:visible />

The string is *copied* and re-encoded on the way in, and an `Err`
becomes a thrown exception<Cite id="wasm-bindgen-guide" />: the published
package's `compile("let = ;")` throws an `Error` whose message is
`Unexpected token (1:6)`. The returned `Output` stays in linear memory
behind an address; every `r.code` copies the string out, and since
JavaScript's collector cannot see inside linear memory, a caller who is
done calls `r.free()`.

<Prompts ids={['str-copy', 'result-throw']} />

<More title="The generated glue, and a model of the copy">

```js
function compile(source) {
  const ptr0 = passStringToWasm0(source,
    wasm.__wbindgen_malloc,
    wasm.__wbindgen_realloc);
  const len0 = WASM_VECTOR_LEN;
  const ret = wasm.compile(ptr0, len0);
  if (ret[2]) {
    throw takeFromExternrefTable0(ret[1]);
  }
  return Output.__wrap(ret[0]);
}
```

Before each copy the glue checks its `Uint8Array` view of memory and makes
a new one if its `byteLength` is 0, because a `malloc` inside Rust may
have grown the memory, which detaches the old buffer. And a Rust panic in
WebAssembly aborts the instance rather than unwinding<Cite id="wasm-pack-book" />,
so when the Playground's worker sees a `WebAssembly.RuntimeError` it asks
for a fresh worker.

The runnable model uses a `Vec<u8>` as linear memory: it copies a string
in as UTF-8, hands over a start and a length, and rebuilds a `&str`; note
its two lengths, 23 UTF-8 bytes against a JavaScript length of 22.

## From crate to npm, and to this page

Building takes three tools, run in order by
`engine/rust/packages/wasm/build.mjs`:

<Figure takeaway="One Rust crate, three tools, two destinations: the npm package and this book's Playground." caption="What build.mjs does, with the sizes recorded in the committed build's sizes.json.">
  <WasmPipeline />
</Figure>

Cargo compiles for `wasm32-unknown-unknown`, WebAssembly with no
operating system underneath<Cite id="rustc-wasm32-unknown-unknown" />.
The `wasm-bindgen` tool, pinned at 0.2.106 like the crate in
`Cargo.lock`, writes glue twice: `--target nodejs` (CommonJS that reads
the file synchronously) and `--target web` (an ES module whose `init()`
you `await`). Then `wasm-opt -O3`<Cite id="binaryen-readme" /> shrinks
each module from about 1.76 MB to 1.37 MB (0.5 MB gzipped). The result is
the npm package `@viscosity/wasm`.

The Rust world has a standard tool for these steps, **wasm-pack**. Its
`wasm-pack build` compiles the crate, runs wasm-bindgen for one
`--target`, runs wasm-opt for release builds, and writes a `pkg` folder
with a generated `package.json`<Cite id="wasm-pack-book" />. Viscosity
writes its own script because it wants two targets in one package, plus
licence texts and the copy into the book.

<Callout kind="definition">
**wasm-pack** builds an npm package from a Rust crate. `wasm-pack build`
compiles to WebAssembly, runs **wasm-bindgen** for one `--target`
(`bundler` by default, or `nodejs`, `web`, `no-modules`, `deno`),
optimises with **wasm-opt** in release builds, and writes `pkg/` with a
generated `package.json`<Cite id="wasm-pack-book" />.
</Callout>

<Examples of="wasm-pack">

```sh
wasm-pack build --target nodejs
```

```sh
node packages/wasm/build.mjs --book
```

</Examples>

The first asks wasm-pack for CommonJS that Node can `require`, one
target per run. The second is what Viscosity runs (in `engine/rust`):
both targets, the licences, and the copy into the book.

How does a command-line tool know that `compile` takes a string and
returns an `Output`? The `#[wasm_bindgen]` macro runs before the
compiler has worked out the types, so it emits one `__wbindgen_describe_`

"a tiny and incomplete Wasm interpreter" that runs them, writes the glue,
then deletes them<Cite id="wasm-bindgen-cli-descriptors" />. wasm-opt
then drops the **name section** (function names for stack traces) and
shrinks the code. This program walks a 52-byte module's sections the

## What you learned

- **WebAssembly** is a portable binary format: a preamble and
  **sections**, with bodies for a **stack machine** that engines
  **validate** and then compile.
- **Linear memory** is one flat, growable array of bytes, in 64 KiB
  **pages**, **trapping** out of bounds; a grow detaches JavaScript's
  views.
- **wasm-bindgen** is an attribute plus a tool: a `&str` is copied in as
  UTF-8, a returned struct stays in Rust's memory until `free()`, and an
  `Err` becomes a thrown `Error`.
- **wasm-pack** packages one target per run; Viscosity's `build.mjs`
  does the same steps for two, and ships `@viscosity/wasm`.
