## Something a function cannot do

Suppose you want a statement `unless`, an `if` that runs its body when
the condition is false, and you try to add it as a function:

```js
function unless(c, body) {
  if (!c) return body;
}
const xs = null;
unless(xs === null, xs.length);
// TypeError: Cannot read properties
//   of null (reading 'length')
```

The guard was meant to protect `xs.length`, but a function's arguments
are all worked out *before* the call starts, so `xs.length` runs (and
fails) while `unless` is still waiting to be called. The same wall
stops an `assert(x > 0)` that prints the text `x > 0` when it fails: by
the time `assert` runs, all it has is `false`. What we need is
something that receives the *code* `xs.length`, unevaluated, and
decides where it goes. That is a macro.

## Expansion: code in, code out

A **macro** is a rule, run inside the compiler, that takes pieces of
the program and returns new program text or a new tree in their place.
The part of the compiler that runs the rules is the **expander**, and
it runs early: after parsing (or, in C, before it) and before the
resolver and type checker, which only ever see the expanded program.

syntax:

<Analogy title="text replacement on a phone">
Type "omw" and the phone writes "On my way!" before the message is
sent; the person reading it never sees "omw". A macro call is the
shorthand and its expansion is what the compiler reads.
<span slot="breaks">A phone replaces letters without knowing any
grammar, which is exactly how C's macros behave and why they go wrong;
the better kind of macro works on the parsed tree and never splits a
piece of code in the wrong place.</span>
</Analogy>

<Analogy extra title="standard parts on a building plan">
An architect writes "bathroom type B" in a box on the plan; before
building starts, the drawing office redraws every box as the full
detailed drawing, and redraws again if a detail contains another box.
The builders only ever see complete drawings.
<span slot="breaks">A standard drawing is the same every time; a macro
can look at its arguments and choose different code for different
cases (Rust's `macro_rules!` picks the first rule whose pattern
matches), so it behaves more like a small program that writes
drawings.</span>
</Analogy>

<Callout kind="definition">
**Macro expansion** replaces each macro call in a program with the
code its macro produces from the call's arguments (passed as code, not
as values), and repeats on the result until no macro call is left. It
runs before name resolution, type checking and code generation. A
**text macro** (C's preprocessor) works on tokens; a **tree macro**
(Rust, Lisp, Scheme) works on syntax trees.
</Callout>

<Formal title="One step of expansion">

```text
expand(m!(a₁, …, aₙ))
  = expand(Tₘ[x₁ := a₁, …, xₙ := aₙ])
expand(k(e₁, …, eⱼ))
  = k(expand(e₁), …, expand(eⱼ))
```

<span slot="read">A call of macro m with argument code a₁ to aₙ is
replaced by m's template Tₘ, with each hole xᵢ filled by the argument
aᵢ, and the result is expanded again. Any other node, of kind k, stays
as it is, with each of its children expanded.</span>
</Formal>

The difference between text and trees is not a detail: it decides
whether a macro respects the grammar. Here is the same squaring macro,
written in C and in Rust, used as `sq(n + 1)`:

<Examples of="macro-expansion">

```c
#define SQ(x) x * x
SQ(n + 1)
// gcc -E:  n + 1 * n + 1
#define SQ2(x) ((x) * (x))
SQ2(n + 1)
// gcc -E:  ((n + 1) * (n + 1))
```

```rust
macro_rules! sq {
    ($x:expr) => { $x * $x };
}
let n = 2;
println!("{}", sq!(n + 1)); // 9
// rustc -Zunpretty=expanded:
//   (n + 1) * (n + 1)
```

```text
// println! is a macro too (wrapped):
{ ::std::io::_print(format_args!(
    "{0}\n", (n + 1) * (n + 1))); };
```

</Examples>

The first is real `gcc -E` output (the flag stops after the
preprocessor). `SQ` pastes the tokens `n + 1` into both holes, the
parser then reads `n + 1 * n + 1` as `n + (1 * n) + 1`, and for `n = 2`
that is 5, not 9. The GCC manual's cure is the second definition,
parentheses round every use of an argument and round the whole
body<Cite id="gcc-cpp-macros" />. The second is Rust: `$x:expr` says
the hole takes one whole expression, so the argument arrives as a
single tree and the program prints 9; rustc's expanded output (on
stable rustc, `RUSTC_BOOTSTRAP=1` unlocks this option) prints the
parentheses only to show the grouping it already had. The third is the
rest of that expansion, trimmed: `println!` is itself a macro, which
expands into a call of a hidden printing function and another macro,
`format_args!`, which the compiler handles itself. Rust's reference
describes these "macros by example" as rules, each a *matcher* for
the syntax it accepts and a *transcriber* for the syntax that replaces
it<Cite id="rustref-macros-by-example" />.

<Run id="expander" />

Here a program is a tree of arrays, and each macro is a JavaScript
function from argument trees to a result tree. `expand` leaves strings
and numbers alone; if a node's head names a macro, it calls the macro
on the node's other elements (as code, unevaluated) and expands what
comes back, which is how the `twice` inside `unless` gets its turn;
any other node is expanded part by part. It prints the `if`, `not`
and `do` tree that the diagram above arrived at.

## Quasiquote: a template with holes

Writing the expansion of `unless` by hand as a tree is unpleasant
(`['if', ['not', c], body]`, as the runnable example did), and for a
macro of twenty lines it is unreadable. The fix is to write the result
as ordinary code with holes in it, and have the language fill the
holes. Lisp's **backquote** does exactly this: inside a backquoted
list, a comma marks a hole to evaluate, and `,@` splices a list's
elements in:

<Analogy extra title="a sign stencil">
A sign-writer's stencil has the fixed letters cut out and blank
patches left for the details; each sign uses the same stencil with
different details painted in.
<span slot="breaks">A blank patch on a stencil has a fixed size; a
hole in a quasiquote can take a tree of any size, and a splicing hole
can even take several pieces at once.</span>
</Analogy>

<Analogy extra title="a printed form with boxes">
A tax form is mostly fixed text, with labelled boxes; the result of
filling it in is still a tax form, in the same layout, whatever went
into the boxes.
<span slot="breaks">A box holds text; a quasiquote's holes are filled
with code, so what comes out is a program, which is then expanded and
compiled like any other.</span>
</Analogy>

<Callout kind="definition">
A **quasiquote** is a template of code with holes: everything in it
stands for itself (is *quoted*), except the holes (*unquotes*), which
are filled with values computed when the template is used; a
**splicing** unquote inserts the elements of a list in place of one
hole. Macro templates (Rust's `$x`, Lisp's backquote) are quasiquotes.
</Callout>

<Formal title="Filling a quasiquote">

```text
`(a ,x ,@ys)   with x = 1, ys = (2 3)
  ⇒ (a 1 2 3)
`(if (not ,c) ,b)
  with c = (> n 0), b = (log n)
  ⇒ (if (not (> n 0)) (log n))
```

<span slot="read">The backquote quotes a list; a comma before x makes
x a hole, filled with x's value; comma-at before ys splices the
elements of the list ys in, side by side. The second line builds the
expansion of unless: the condition and the body are slotted into a
fixed if-not shape.</span>
</Formal>

<Examples of="quasiquote">

```text
; Emacs Lisp
`(a list of ,(+ 2 3) elements)
  ⇒ (a list of 5 elements)
(setq some-list '(2 3))
`(1 ,@some-list 4 ,@some-list)
  ⇒ (1 2 3 4 2 3)
```

```js
// @babel/template 7.29: holes are %%x%%
const build = template.statement(
  'if (!(%%cond%%)) throw %%msg%%;');
build({ cond: t.identifier('ok'),
        msg: t.stringLiteral('failed') });
// generates: if (!ok) throw "failed";
```

```js
// JavaScript's own template literals
// are quasiquotes of strings, not trees:
const c = 'n > 0';
`if (!(${c})) { ... }`;
```

</Examples>

The first is quoted from the Emacs Lisp manual's examples of backquote
and splicing<Cite id="elisp-backquote" />: the comma evaluates
`(+ 2 3)` inside an otherwise quoted list, and each `,@` spreads the two
elements of `some-list` into the result. The second is Babel, the
JavaScript compiler, whose documentation says its `@babel/template`
package "is known as an implementation of
quasiquotes"<Cite id="babel-template" />: the run here (Babel 7.29,
trimmed) filled two holes
with trees and printed `if (!ok)`, dropping the brackets around
`ok` because the hole held one tree that needs none. The third is the
template literal of chapter 22: its holes are filled with *strings*,
so it builds text, with all of C's troubles, and a careful code
generator builds trees instead.

## What you learned

- A **macro** is handed code and returns code; **expansion** replaces
  every call and repeats until none are left, before the compiler
  proper runs. That is how a macro can add a new statement or quote
  its own argument's text, which no function can.
- **Text macros** (C) paste tokens and need defensive brackets; **tree
  macros** (Rust, Lisp) paste whole trees and keep the grammar.
- A **quasiquote** writes the output as a template with holes; macro
  templates and `@babel/template` are quasiquotes.
