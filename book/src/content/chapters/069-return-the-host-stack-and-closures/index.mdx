## A way out from deep inside

So far a Drip function can only print its answer. Here is one that
needs `return`:

```text
fn indexOf(xs, v) {
  for i in 0..len(xs) {
    if xs[i] == v { return i; }
  }
  return -1;
}
print indexOf([4, 8, 15], 8); # 1
```

At `return i;` the interpreter is five TypeScript methods deep (the
call, the body, the loop, the loop body, the `if`), and it must abandon
all of them at once, carrying the 1. The same pile of methods raises two
more questions: who remembers paused calls, and what happens to a call's
variables if a function made inside it is still around?

<Analogy title="a note passed down a line">
From the back of a long queue you hand a note forward; each person
reads it, stops whatever they were doing for you, and passes it on,
until it reaches the front.
<span slot="breaks">In the interpreter, every method that runs
statements must be written to check the note and pass it on; one that
forgets breaks `return` for everything inside it.</span>
</Analogy>

## Completion codes

One well-known design throws a small exception holding the value and
catches it at the edge of the call. Drip's interpreter uses the other,
the note: every `execute` returns a **completion code**, `NORMAL`,
`BREAK`, `CONTINUE` or `RETURN`, and every method that runs statements
checks it. One mechanism then serves `break` and `continue` too, and a
thrown exception always means a real error.

```ts
case 'return':
  this.returnValue = s.value
    ? this.evaluate(s.value) : null;
  return RETURN;
```

The `return` case parks its value in a field (`null` is Drip's `none`)
and reports `RETURN`. `executeBlock` stops at the first statement that
does not finish normally and hands its code up; an `if` returns its
branch's code; a loop stops on `BREAK` but passes `RETURN` straight up.
At the edge, `callFunction` turns the code back into a value:

```ts
const c = this.executeBlock(
  f.decl.body, env);
if (c === RETURN) {
  const v = this.returnValue;
  this.returnValue = null;
  return v;
}
return null;
```

Clearing the field stops a stale value leaking into a later call. In a
recursive function each code travels only as far as its *own* call's
`callFunction`:

<Callout kind="definition">
**Return unwinding** is leaving every statement between a `return` and
the start of its function call in one move. With **completion codes**,
each statement reports how it finished, every enclosing statement passes
`RETURN` up unchanged, and the code that runs the call takes the parked
value. In Drip, a body with no `return`, or a bare `return;`, gives
`none`.
</Callout>

<Examples of="return-unwinding">

```text
fn quiet() {
  print "a";
  return;
  print "b";
}
print quiet(); # a, then none
```

</Examples>

The bare `return;` parks `none` and reports `RETURN`, so `executeBlock`
stops before `print "b"`.

## Riding on TypeScript's stack

While `fib(3)` waits for `fib(2)`, the interpreter keeps no list of
paused Drip calls: each Drip call *is* a handful of TypeScript method
calls (six per level of `fib`), and TypeScript keeps a call
stack<Cite id="mdn-call-stack" /> for those, so "`fib(3)` is waiting"
is the plain fact that its `evaluate` has not returned yet. The
variables are not on that stack; `Environment`s live on the heap.

<Figure caption="Inside area, called from report, called from the script. Each Drip call is four or five TypeScript methods on the host stack; the interpreter's own frames array holds one small entry per call." takeaway="The host stack does the work; Drip keeps only a list of names and lines.">
  <HostFrames />
</Figure>

<Callout kind="definition">
The **host stack** is the call stack of the language an interpreter is
written in (its *host language*). An interpreter that runs each call as
ordinary host-language calls reuses it: one interpreted call becomes
several host frames, and a paused call is a host method that has not
returned yet.
</Callout>

For error messages the interpreter keeps a small shadow list, `frames`,
with a place and a line per active call: `callFunction` pushes an entry
and pops it after. A runtime error is thrown straight past the `pop`, so
the list still holds every active call when `drip.ts` prints the stack
trace, innermost first:

<Examples of="host-stack">

```text
fn area(w, h) { return w * h; }
fn report(w) {
  print area(w, "x");
}
report(3);
# runtime error: cannot use '*'
#   on a number and a string
#   at line 1 in fn area
#   at line 3 in fn report
#   at line 5 in script
```

</Examples>

Each line further out is where that call was waiting. `callFunction`
also caps the depth at 256 active calls, and one more is `stack
overflow`; if the host stack runs out first, JavaScript's
`RangeError`<Cite id="mdn-too-much-recursion" /> is reported the same
way. Step through a trace being built:

<TraceSteps client:visible />

<Analogy extra title="boxes in a friend's garage">
You are moving house, and a friend lets you keep your boxes in their
garage; you keep only a short list on your phone of what is in there.
<span slot="breaks">You could empty the garage and take your boxes
somewhere else; Drip's calls cannot be taken out of TypeScript's stack,
so a Drip program cannot be paused half-way and resumed.</span>
</Analogy>

<More title="How frames is kept, and what borrowing costs">

```ts
if (this.frames.length === FRAMES_MAX)
  throw new RuntimeError(at,
    'stack overflow');
this.frames[this.frames.length - 1]
  .line = at.line;
this.frames.push({
  place: f.decl.name
    ? `fn ${f.decl.name.lexeme}`
    : 'anonymous fn',
  line: 0 });
// ... run the body ...
this.frames.pop();
```

Before the body runs, the line of the call is written into the caller's
entry (where the caller is waiting), and an entry for the new call is
pushed. Borrowing the host stack costs **depth** (several host frames
per Drip call), **visibility** (the real record of a paused call is
TypeScript's, so a Drip program cannot be paused and resumed, which a
debugger needs) and **speed**. The bytecode VM pays all three back with
its own array of call frames, in *Frames: calling and returning*.

## Closures: which parent?

Here is a counter in Drip, as in *Closures: functions that remember*:

```text
fn makeCounter() {
  let n = 0;
  return fn () { n += 1; return n; };
}
let a = makeCounter();
print a(); # 1
print a(); # 2
```

The anonymous function uses `n`, a local of a call that has returned.
A call's fresh environment needs a parent: the globals (then `n` is
invisible), the caller's environment (*dynamic scope*), or the
environment the function was made in. Drip, like
JavaScript<Cite id="mdn-closures" />, takes the third, lexical scope; so
`DripFunction`'s `closure` field is set to `this.env` when the value is
made, and every call hangs off it:

```ts
const env = new Environment(f.closure);
```

<KeptEnvSteps client:visible />

<Analogy extra title="a letter written in a particular house">
A note says "the spare key is under the blue pot"; whoever reads it,
wherever, it means the blue pot at the house where it was written.
<span slot="breaks">A note is a frozen description; a Drip function
reads the *current* contents of the place it was written.</span>
</Analogy>

<Callout kind="definition">
A **captured environment** is the environment a function value stores
when it is made (the one current when its `fn` ran). Every call makes a
new environment whose parent is the captured one, so the body sees the
names around where it was *written*. The function plus its captured
environment is a **closure**, and it holds the variables themselves, not
copies of their values.
</Callout>

<Examples of="captured-environment">

```text
fn makeAdder(n) {
  return fn (x) { return x + n; };
}
let add2 = makeAdder(2);
let add10 = makeAdder(10);
print add2(5);  # 7
print add10(5); # 15
```

</Examples>

Each call of `makeAdder` makes its own environment holding its own `n`,
and the function made during that call captures it, so the same body
gives 7 and 15.

<More title="Closures in a loop: for against while">

Each pass of a Drip `for` loop makes a brand-new environment for the
loop variable, so functions made in the body capture different
variables; a `while` loop's counter is one variable declared before the
loop, so every function made in it shares that one.

<Figure caption="Left: each pass of a for loop has its own environment for i, so each function sees its own pass's value. Right: a while loop's counter lives outside the loop, so every function made in it sees the one j, which has reached 3 by the time they run." takeaway="A fresh environment per pass gives each closure its own variable.">
  <SharedLoopEnv />
</Figure>

```text
let gs = [];
let j = 1;
while j < 4 {
  push(gs, fn () { print j; });
  j += 1;
}
gs[0](); # 4
```

The fix, if you need a `while`, is `let mine = j;` inside the body
(which gets a fresh environment every pass), and to capture `mine`.

## Environments that outlive their call

By the time `a()` runs, every TypeScript frame of `makeCounter`'s call
is gone, yet `n` keeps its value from one call of `a` to the next,
because `n` was never in those frames: its environment is on the heap
(*Bytes, floats and memory*), and the closure still refers to it.
JavaScript keeps an object alive while the program can reach it by
following references; once nothing does, the garbage collector may
reclaim it.

<LifetimeSteps client:visible />

<Callout kind="definition">
**Environment lifetime** is how long an environment exists. When
environments are ordinary heap objects, one lives as long as anything
reaches it: a running call, a child environment (through its parent
link), or a function that captured it. It can therefore **outlive** the
call that made it, and is reclaimed once nothing reaches it.
</Callout>

<Examples of="environment-lifetime">

```text
fn makeBox(v) {
  let get = fn () { return v; };
  let set = fn (x) { v = x; };
  return [get, set];
}
let box = makeBox("old");
box[1]("new");
print box[0](); # new
```

</Examples>

The call ends, but its environment lives on through both functions, so
`get` sees what `set` wrote; once `box` is gone, it can be reclaimed.

<Figure caption="get and set were made in the same call, so both closure fields point at one environment. A change through set is seen by get; the environment lives as long as either function is reachable." takeaway="Closures made together share one environment.">
  <SharedBox />
</Figure>

The price is a heap `Environment` with a `Map` on every call, captured
or not; the VM keeps locals on a stack and moves only captured ones to
the heap, in *Upvalues: capturing and closing*.

## What you learned

- **Return unwinding**: `RETURN` is passed up until `callFunction`
  turns it into a value.
- Drip calls ride on the **host stack**; `frames` is only for traces.
- A function's **captured environment** is where it was made; an
  environment **outlives** its call while a closure reaches it.
