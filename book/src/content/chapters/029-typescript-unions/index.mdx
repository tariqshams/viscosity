## This or that

Some values honestly come in more than one kind. A customer id might be
a number (`42`) in one system and a string (`'ada'`) in another; a search
might find a thing or find nothing. Labelling such a value `number` would
be a lie, and so would `string`; TypeScript lets you say “either”, with a
bar between the two types:

```ts
function show(id: number | string) {
  return id.toUpperCase();
}
// error: Property 'toUpperCase' does not
// exist on type 'string | number'.
```

The label `number | string` reads “a number or a string”. The checker is
right to complain: if `id` turns out to be `42`, there is no
`toUpperCase` to call, and the program would crash. Until we know which kind we have, we may only do what is safe for
both.

<Analogy title="a parcel marked “a book or a mug”">
You are handed a parcel whose label says it holds a book or a mug. You
can carry it, weigh it and put it on a shelf, because those work for
either; you cannot start reading it, because it might be a mug. To read
it you first open it and look, and opening the parcel is an `if`.
<span slot="breaks">A real parcel can be shaken to guess what is inside;
the checker never guesses, so until your code checks, it assumes either
could be there, every time.</span>
</Analogy>

<Analogy extra title="a call from an unknown number">
Your phone rings and the caller could be a friend or a salesperson.
“Hello?” is safe whoever it is, however you would not read out your bank
details until you have found out who is speaking.
<span slot="breaks">On the phone you work it out from a voice, slowly and
sometimes wrongly; in code you ask once, exactly, with a check such as
`typeof id === 'string'`, and the answer is never wrong.</span>
</Analogy>

<Callout kind="definition">
A **union type**, written `A | B`, labels a value that may be an `A` or a
`B` (and `A | B | C` allows three kinds, and so on). Until your code
checks which, the checker allows only operations that are safe for
**every** member of the union<Cite id="ts-everyday-types" />.
</Callout>

<Formal title="What a union holds, and what it allows">

```text
values(A | B) = values(A) ∪ values(B)
x.m allowed on A | B  ⟺
    m allowed on A  and  m allowed on B
```

<span slot="read">The values a union can hold are the values of A
together with the values of B (the symbol ∪ reads “joined with”). Using
a method m on a value of the union is allowed exactly when it would be
allowed on an A and also on a B.</span>
</Formal>

<Examples of="union-type">

```ts
let id: number | string = 42;
id = 'ada'; // fine: a string is allowed
```

```ts
function len(v: string | string[]) {
  return v.length; // both have length
}
len('abc');      // 3
len(['a', 'b']); // 2
```

```ts
const ages = new Map<string, number>();
const a = ages.get('ada');
// a: number | undefined
```

</Examples>

In the first, `id` is labelled “number or string”, so it may start as
`42` and later hold `'ada'`; assigning `true` would be an error. In the
second, no check is needed, because strings and arrays both have a
`length` (a string's is its count of characters, an array's its count of
slots), so `v.length` is safe for every member. The third is the union
you will meet most: `Map`'s `get` (from the Map and Set chapter) may find nothing, so its
result is honestly labelled `number | undefined`, and the checker will
not let you do arithmetic on `a` until you have ruled out `undefined`.
(That check needs `strictNullChecks`, part of TypeScript's `strict`
setting, which the toolchain chapter covers.)
(The `<string, number>` part names the key and value types; generics,
two chapters on, explain it.)

<OtherLanguages>

```ts
function show(id: number | string) {
  if (typeof id === 'string') {
    return id.toUpperCase();
  }
  return id.toFixed(2);
}
```

```js

```

```python
def show(id: int | str) -> str:
    if isinstance(id, str):
        return id.upper()
    return f"{id:.2f}"
```

```java
static String show(Object id) {
    if (id instanceof String s) {
        return s.toUpperCase();
    }
    double n = ((Number) id).doubleValue();
    return String.format("%.2f", n);
}
```

```c
/* a C union stores either one, but
   does not remember which: you keep
   a tag of your own beside it */
struct Id {
    int is_text;
    union { double n; char *s; } v;
};
```

</OtherLanguages>

Python writes the same `int | str`, but nothing enforces it unless you
run a separate checker, and `isinstance` does the asking. Java has no
union of two types, so the usual trick is the catch-all `Object` plus an
`instanceof` check. C's keyword `union` means something else: the same
bytes read as either kind, with nothing recording which kind was stored,
so you keep a tag by hand (an idea the next chapter makes official).

## Following the if

The fix is to check, at run time, which kind of value arrived. You
already know the check, `typeof` from the last chapter; watch what the checker
does with it, line by line:

<NarrowSteps client:visible />

```ts
function show(id: number | string) {
  if (typeof id === 'string') {
    return id.toUpperCase(); // string
  }
  return id.toFixed(2);      // number
}
show('ada'); // 'ADA'
show(42);    // '42.00'
```

Line 2 is ordinary JavaScript that really runs: it asks the value what
kind it is. The checker reads the same test and reasons about it, so on
line 3, which only strings can reach, it treats `id` as a `string` and
allows `toUpperCase`. Line 3 also returns, so any value that reaches
line 5 cannot be a string; there the checker treats `id` as a `number`,
and `toFixed(2)` (which writes a number as text with two decimal places)
is allowed. The two calls print `'ADA'` and `'42.00'`.

<Analogy extra title="a coin-sorting machine">
Pour mixed coins into a sorting machine and they roll down a track past
a row of holes, each just big enough for one size of coin. Once the
coins pass the smallest hole, every coin of that size has dropped out,
so everything further along is something larger.
<span slot="breaks">The machine moves coins; narrowing moves nothing.
The values stay where they were, and only the checker's knowledge of
them gets more exact, line by line.</span>
</Analogy>

<Analogy extra title="a game of Guess Who">
In Guess Who you ask yes-or-no questions and flip down every face the
answer rules out: “Does your person wear glasses?” “No.” Down go all the
faces with glasses, and you never consider them again.
<span slot="breaks">A player can misremember or bluff; the checker
learns only from checks it can see in your code, such as `typeof`, `===`
and `Array.isArray`, and the answers it learns are always right.</span>
</Analogy>

<Callout kind="definition">
**Narrowing** is the checker working out a more exact type for a value
from a check in your code. It follows every `if`, `else` and `return`,
so in each stretch of code it knows which members of the union can still
be there<Cite id="ts-narrowing" />. The check runs; the narrowing is
erased with the other types.
</Callout>

<Formal title="Narrowing with a test">

```text
Γ ⊢ x : A | B    test(x) means x is an A
───────────────────────────────────────
then-branch:  x : A
else-branch:  x : B
```

<span slot="read">If, where we are (Γ, “the types known here”), x is an
A or a B, and the test passes only when x is an A, then inside the
then-branch x is an A, and inside the else-branch (or after a then-branch
that returned) x is a B.</span>
</Formal>

<Examples of="narrowing">

```ts
function twice(v: number | string) {
  if (typeof v === 'number') return v * 2;
  return v + v;
}
twice(4);    // 8
twice('ab'); // 'abab'
```

```ts
function hello(name: string | undefined) {
  if (name === undefined) {
    return 'Hello, stranger';
  }
  return 'Hello, ' + name.toUpperCase();
}
```

```ts
function asList(v: string | string[]) {
  if (Array.isArray(v)) return v;
  return [v];
}
asList('a.js');   // ['a.js']
asList(['a.js']); // ['a.js']
```

</Examples>

In the first, `typeof` splits numbers from strings: a number is doubled
with `*`, and a string is joined to itself with `+`. The second narrows
with `===`: after the early return for `undefined`, only a real string
is left, so `toUpperCase` is allowed. The third is what a build tool does
when a setting may be one file name or a list of them: the checker
narrows on `Array.isArray(v)` (which asks whether `v` is an array), so
the function always returns a list.

A common slip is checking, but not leaving, so the narrowing ends at the
closing brace:

```ts
if (typeof id === 'string') {
  console.log(id.toUpperCase());
}
return id.toFixed(2);
// error: Property 'toFixed' does not
// exist on type 'string | number'.
```

Strings went into the `if` and came out again (nothing returned), so on
the last line `id` may still be either. Adding `return` inside the `if`,
or putting the number case in an `else`, fixes it.

A second slip is ruling out `undefined` with a bare `if (v)`. The
checker does narrow on it, however `if` also treats `0` and the empty
string `''` as false (they are called **falsy** values), so a real zero
would be handled as if it were missing; `v !== undefined` says exactly
what you mean.

<Callout kind="engine" label="Under the hood">
None of this reaches the engine. `tsc` erases the union labels and the
narrowing alike, so `show(id: number | string)` becomes plain
`show(id)`, and the `typeof` check you wrote is the only part that runs.
The checker's line-by-line reasoning is called **control-flow
analysis**<Cite id="ts-narrowing" />, and it is a small version of the
dataflow analyses that *Dataflow, fixpoints and constant propagation*
builds for optimising compilers: work
out, for every point in a program, what must be true there.
</Callout>

## What you learned

- A **union type** `A | B` holds a value of either kind; before any
  check, only operations safe for every member are allowed.
- **Narrowing**: the checker follows your `typeof`, `===` and
  `Array.isArray` checks, and your `return`s, to know the exact type on
  each line. The checks run; the narrowing is erased.
- A bare `if (v)` also rules out `0` and `''`; to rule out `undefined`,
  say `v !== undefined`.
