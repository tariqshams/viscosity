## Same keys, different objects

Here are four objects with the same two properties, and a V8 internal
that asks whether two objects have the same layout (Node allows these `%`
helpers under `--allow-natives-syntax`):

```js
const a = { x: 1, y: 2 };
const b = { x: 5, y: 6 };
const c = { y: 2, x: 1 };
const d = {}; d.x = 1; d.y = 2;
%HaveSameMap(a, b); // true
%HaveSameMap(a, c); // false
%HaveSameMap(a, d); // false
```

(Node v22.23.4, V8 12.4.) `c` differs from `a` only in order, and `d` not
even in that, yet neither matches. The question behind this is one your
Drip VM answered with a hash lookup per instance (*Classes and method
calls in the VM*): where does `p.x` live?

## A shape is a shared description

<Analogy title="a printed form">
A school prints one form for every pupil: name in box 1, class in box 2.
Each sheet holds only answers, and to find a class you go straight to box
2; thousands of sheets share one description of the layout.
<span slot="breaks">A printed form never changes; a JavaScript object can
gain a property at any moment, and then it has to move to a different
"form", which is what the transition tree is for.</span>
</Analogy>

Every V8 object starts with a pointer to its hidden class (*How
JavaScript stores numbers, objects and fields*), which V8 calls a
**map**<Cite id="v8-slack-tracking" />; the map holds the property names,
their order and where each value is stored, and the object holds only
values<Cite id="v8-fast-properties" />.

<Figure caption="Particles made the same way share one map. Each object is a map pointer plus its own values; the names x and vx are stored once, in the map." takeaway="The shape holds the names and the layout; the object holds the values.">
  <ShapeShare />
</Figure>

Since any object can gain a property at any time, each addition moves it
to a new shape, and V8 links the shapes into a
tree<Cite id="v8-fast-properties" />:

<TransitionSteps client:visible />

<Callout kind="definition">
A **shape** (in V8, a **map**; also a hidden class) describes an object's
layout: its named properties, their order, and where each value and its
representation live<Cite id="v8-fast-properties" />. Shapes form a
**transition tree**: the root is an empty shape, each edge says "add this
property", and adding a property follows an existing edge or creates a new
shape. The same properties added in the same order, from the same root,
lead to the same shape.
</Callout>

<Examples of="shape transition-tree">

```
// %DebugPrint(a), trimmed
 - map: <Map[40]…> [FastProperties]
    #x: 1 (const data field 0), in-object
 - inobject properties: 2
// %DebugPrint(d), trimmed
 - inobject properties: 4
 - unused property fields: 2
```

</Examples>

`a`'s map stores `x` as field 0, inside the object (**in-object**), with
room for exactly two properties; `b` shares it, and `c` walked the `y`
edge first, onto another branch. `d` took `a`'s edges from a different
root: V8 gave the empty `{}` room for four properties, two still unused,
so the layouts differ.

<More title="More: the tree as a formula, and more runs">

<Formal title="A shape is a path from the root">

```text
shape({})             = S₀
shape(o after o.k=v)  = T(shape(o), k)
keys k₁…kₙ, in order  ⇒
  shape = T(…T(T(S₀,k₁),k₂)…,kₙ)
```

<span slot="read">An empty object has the root shape S₀. Adding a new
property k to o moves it to T(shape of o, k), the child along the edge
labelled k, made the first time it is needed. So an object's shape is
found by following its keys from the root in the order they were added;
T(T(S₀, x), y) and T(T(S₀, y), x) are different paths, so order
matters.</span>
</Formal>

A thousand particles built by one line share one map, and building half
of them with the keys in the other order gives two:

```js
const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
ps.every((p) => %HaveSameMap(p, ps[0]));
// true: a thousand objects, one map
const qs = ps.map((p, i) => i % 2
  ? { x: p.x, vx: 1 }
  : { vx: 1, x: p.x });
qs.every((q) => %HaveSameMap(q, qs[0]));
// false: two branches, two maps
```

Each map also keeps a **back pointer** to the map it came
from<Cite id="v8-src-map-12-4" />. Code can see property order too, which
is why an engine must remember it:

## Every access remembers what it found

Here is the smallest function that reads a property, and its bytecode
(`node --print-bytecode`, trimmed):

```
// function getX(o) { return o.x; }
GetNamedProperty a0, [0], [0]
Return
```

The first `[0]` is the name `"x"`; the second is a **feedback slot**,
where this bytecode "calls the LoadIC"<Cite id="v8-src-interpreter-12-4" />,
an **inline cache**. Rather than search the shape's names on every call,
the access keeps the shapes it has seen, each with a **handler** ("map M:
load field 0"): a known map costs one comparison and one load, and an
unknown one gets the full lookup, whose answer is
added<Cite id="v8-src-ic-12-4" />.

<ICSteps client:visible />

<Callout kind="definition">
An **inline cache** (IC) is a small memory, at one property access in the
code, of the shapes seen there, each with a handler saying how to do the
access for that shape; in V8 it lives in a feedback slot. It is
**monomorphic** when it has seen one shape, **polymorphic** when it has
seen a few (in V8 12.4, up to four, the default of
`--max-valid-polymorphic-map-count`<Cite id="v8-src-tiering-12-4" />), and
**megamorphic** past that, when it stops keeping its own list and looks
up the pair (shape, name) in the **stub cache**, one table shared by all
megamorphic accesses<Cite id="v8-src-ic-12-4" />.
</Callout>

<Examples of="inline-cache monomorphic polymorphic megamorphic">

```
// --log-ic: getX, ten calls each with
// {x}, {x,a}, {x,b}, {x,c}, {x,d}
LoadIC 1:29 0 1 x
LoadIC 1:29 1 P x
LoadIC 1:29 P P x
LoadIC 1:29 P P x
LoadIC 1:29 P N x
```

</Examples>

Each line is one change of state of the `x` in `o.x`: `0` is
uninitialised, `1` monomorphic, `P` polymorphic, `N`
megamorphic<Cite id="v8-src-ic-12-4" />. The first shape made the site
monomorphic, and its other nine calls changed nothing; the next three
joined the list; the fifth sent it to `N`, for good.

<Figure caption="A polymorphic site keeps its own short list; megamorphic sites share one table keyed by map and name." takeaway="Past four shapes, a site stops remembering and starts asking.">
  <StubTable />
</Figure>

This matters to V8's optimising compilers: for a monomorphic `o.x`,
Maglev emits one shape check and a load at a fixed
offset<Cite id="v8-maglev" />, a polymorphic site still gives a short list
of cases<Cite id="holzle1991" />, and a megamorphic one (such as a
tree-walker's `n.type`, one shape per node class) gives nothing.

<More title="More: an interpreter's node.type, mixins, and one shape against twenty">

```js
class Num { constructor(v) {
  this.type = 'num'; this.v = v; } }
class Add { constructor(l, r) {
  this.type = 'add'; this.l = l;
  this.r = r; } }
// ...and Mul, Neg and Var, alike
const kindOf = (n) => n.type;
// --log-ic, ten calls per class:
// 0 1, 1 P, P P, P P, P N
```

Different classes give different maps even with the same fields, so
`kindOf`'s one load goes megamorphic. The V8 team's 2021 post on `super`
shows another case: a `super.m()` call inside a mixin, where each use of
the mixin creates a new class<Cite id="v8-fast-super" />. Do not reshape a
whole program around this, though: two or three shapes is polymorphic,
which is fine, and what matters is the hot loop. The deep dive *Stub
caches and feedback vectors* looks inside the stub cache and the feedback
vector. (The runs use ten calls per shape because in Node 22 a function
gets its feedback vector only after about eight calls, and shapes seen
before that are never recorded.) Try one shape against twenty on your
device:

## Arrays have kinds

`typeof` says `'number'` for every element of `[1, 2, 3]` and of
`[1, 2, 3.5]`, but V8 keeps small integers as Smis and other numbers as
doubles, and an array known to hold only Smis can be optimised for
exactly that<Cite id="v8-elements-kinds" />. So V8 labels each array's
**elements** (its values at integer indices) with what they can hold, and
each write can only make the label more general:

<LatticeSteps client:visible />

<Callout kind="definition">
An array's **elements kind** records what its indexed elements can hold:
**SMI** (small integers), **DOUBLE** (any number, stored as raw 64-bit
doubles<Cite id="v8-src-elements-kind" />) or **ELEMENTS** (any value).
The kinds are ordered from specific to general, and an array only ever
moves towards a more general kind<Cite id="v8-elements-kinds" />. V8
records the kind in the array's map, so a change of kind is a map
transition.
</Callout>

<Examples of="elements-kind">

```js
// %DebugPrint shows, for each array:
[1, 2, 3]          // PACKED_SMI
const t = [1.5, 2];  // PACKED_DOUBLE
t[0] = 1;            // still DOUBLE
[1, 2].push(-0)      // now DOUBLE
[1, 2].push(2 ** 31) // now DOUBLE
```

</Examples>

(Read `[1, 2].push(v)` as the array after the push.) `t` starts at
DOUBLE because of `1.5`, and an integer written over it changes nothing.
The last two are the traps: `-0`, `NaN` and `Infinity` are doubles, not
Smis<Cite id="v8-elements-kinds" />, and so is any integer from
2<sup>31</sup> up in this build, so one `-0` from `0 * -1` moves an array
of counters to DOUBLE.

<More title="More: the lattice as a formula, element loads, and which numbers are Smis">

<Formal title="The lattice, and a write">

```text
SMI ⊑ DOUBLE ⊑ ELEMENTS
after a[i] = v :  kind ← kind ⊔ kindOf(v)
```

<span slot="read">⊑ reads "is at least as specific as". After writing v,
the array's kind becomes the join (⊔, "the more general of the two") of
its old kind and the most specific kind v fits; a join never moves back
up the list.</span>
</Formal>

An element load such as `xs[i]` has an inline cache that remembers the
array's map, kind included, so a helper called with arrays of several
kinds has to be ready for the most general one<Cite id="v8-elements-kinds" />.
The 2017 post counts 21 kinds in all, including the HOLEY versions for
arrays with missing slots (the deep dive *Stub caches and feedback
vectors*) and fixed kinds for typed arrays: `%DebugPrint` reports
`FLOAT64ELEMENTS` for a `Float64Array`, whose kind can never change.
