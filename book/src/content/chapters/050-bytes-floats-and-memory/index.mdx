## Where does a value actually go?

Two small programs, and one question about each:

```js
const xs = new Float64Array(1000000);
xs[999999] = 1;   // how is the slot found?

const p = { x: 1 };
const q = p;
q.x = 5;          // why does p.x become 5?
```

The first writes the last of a million slots without searching or
counting; the second changes `p` through `q`. Both answers come from the
same place, the machine's memory, and Viscosity's whole job is to
rearrange data in it; so the Core starts there.

## Bytes and floats, in one paragraph

You met the raw material in the Prelude. A **byte** is 8 bits, so it
holds a whole number from 0 to 255 (*Bits and bytes*). Every JavaScript
number is a **float64**, which takes 8 bytes, and a typed array is a
view of numbers laid over a raw `ArrayBuffer` of bytes (*Floats and
typed arrays: numbers as bytes*). Two views of the same buffer show the
bytes of one number:

```js
const f = new Float64Array([1]);
new Uint8Array(f.buffer);
// [0, 0, 0, 0, 0, 0, 240, 63]
```

The number 1 is 8 bytes, and these are the bytes as Node 22 prints them
(how a float64 is laid out bit by bit waits for *How JavaScript stores
numbers, objects and fields*). Hold on to the idea: a value is a run of
bytes, and so is everything else.

## One long row of bytes

<Analogy title="a street of numbered mailboxes">
Picture an endless street of tiny mailboxes, each holding exactly one
small thing, each with a number painted on it: 0, 1, 2, and on into the
billions. To fetch something you do not need its name, only its
mailbox number.
<span slot="breaks">On a street, mailbox 9,000 is a long walk from
mailbox 1; in memory any number is reached directly (*Caches, lines and
locality* adds an important "but"). And each of these mailboxes holds
exactly one byte.</span>
</Analogy>

<MemoryRow client:visible />

<Callout kind="definition">
**Memory** (RAM) is one enormous array of bytes. A byte's index in it
is its **address**, a plain whole number. A value bigger than a byte
sits in several neighbouring bytes and is found by the address of the
first one.
</Callout>

<Examples of="memory address">

```js
const mem = new Uint8Array(65536);
mem[0x10] = 42;
mem[0x10];  // 42
mem[1] = 300;
mem[1];     // 44
```

</Examples>

A `Uint8Array` behaves like a small memory of your own, with its indexes
playing addresses; 65,536 bytes is exactly what 16-bit addresses can
reach (an old 8-bit computer's whole memory), and `0x10` is 16 written
in hexadecimal, the usual way to write addresses. The last two lines are
the byte limit: 300 does not fit in 8 bits, so only the low 8 bits are
kept, 300 − 256 = 44.

## Side by side, with no gaps

A `Float64Array` stores its numbers one after another, 8 bytes each,
with nothing in between<Cite id="mdn-typed-arrays" />. That is the whole
answer to the first puzzle.

<Callout kind="definition">
Values are **contiguous** when they sit side by side in memory with no
gaps. If a typed array with elements of `s` bytes starts at address `b`,
element `i` starts at `b + i × s`: one multiply and one add, whatever
the length.
</Callout>

<Formal title="Where element i lives">

```text
addr(a[i]) = base(a) + i × s
contiguous ⟺ addr(a[i+1]) = addr(a[i]) + s
```

<span slot="read">The address of element i is where the array starts
plus i times the size of one element; the array is contiguous exactly
when (⟺) each element starts one element-size after the one before
it.</span>
</Formal>

<Examples of="contiguous">

```js
// a Float64Array starting at 1000:
1000 + 3 * 8;   // element 3 at 1024
// an Int32Array starting at 100:
100 + 5 * 4;    // element 5 at 120
```

</Examples>

The element size is the step: 8 bytes for a float64, 4 for an int32, so
the same index lands at different places. Finding element 999,999 is the
same two operations as finding element 0, which is why the first puzzle
needs no search.

first. A typed array's `byteOffset` says where it starts inside its
buffer, the nearest thing to an address JavaScript shows you; run it and

## Arrows are addresses

Now the second puzzle. Memory is a row of numbered bytes, with nowhere
to draw an arrow; so a reference is stored as a number, the address
where the object's bytes begin.

<PointerSteps client:visible />

<Callout kind="definition">
A **pointer** is a stored address: a number, kept in memory, that says
where something else is. A JavaScript reference is a pointer the engine
manages: you can copy it (`q = p`) and follow it (`p.x`), but never see
or change the number. For an object that keeps `x` at a fixed position,
`p.x` means: read the address in `p`, add the offset of `x`, and read
the bytes there.
</Callout>

<Examples of="pointer">

```js
const p = { x: 1 };
const ps = [p, p];
ps[1].x = 9;
p.x;  // 9
```

</Examples>

Array slots hold pointers too: `ps` has two slots holding the same
address, so writing through `ps[1]` changes the one object `p` leads
to, while `{ ...p }` would build a new object at a new address and copy
the values across (*Copies: an object of your own*). A full pointer on
a 64-bit machine is 8 bytes; V8 (the engine in Chrome and Node) can
store many of them in 4, as a 32-bit offset from a base, a trick called
pointer compression<Cite id="v8-pointer-compression" />. Either way an
arrow costs bytes, and following one costs a trip to memory.

<More title="A linked list in a toy memory">

Pointers by hand: an ordinary array `mem` plays memory, each node takes
two slots (a value, then the address of the next node), and address 0
means "no next node", the way `null` does.

## The stack and the heap

A running program divides memory into regions, and two matter here. The
**call stack** (*Recursion and the call stack*) keeps one frame per
active call, with its parameters and local variables; the **heap**
holds objects as they are created<Cite id="mdn-execution-model" />.

<Callout kind="definition">
The **stack and heap**: frames on the call stack are released when
their call returns; objects on the heap stay as long as something can
still reach them, however many calls come and go.
</Callout>

<Examples of="stack-and-heap">

```js
function make(v) {
  const n = v * 2;
  return { x: n };
}
const a = make(3);
a.x;  // 6: the object outlived make
```

</Examples>

`v` and `n` live in `make`'s frame, which is gone once the call
returns; the object was made on the heap, and `return` hands back its
address, so `a` can still use it.

<Figure takeaway="Frames on the stack hold arrows into the heap." caption="Inside main’s frame, n holds a number; ps and xs hold pointers. That picture is the argument of the next few chapters. To read every
`x` of `ps`, the machine reads a pointer, jumps to an object, reads `x`
there, and repeats; to read every number of `xs`, it walks straight
along one block. Viscosity rewrites the first shape into the second.

## What you learned

- **Memory** is one array of bytes; an **address** is an index into it.
- **Contiguous** elements put element `i` at `base + i × size`.
- A **pointer** is a stored address; a JavaScript reference is one, and
  `p.x` follows it.
- **Stack and heap**: frames go when their call returns; objects stay
  while reachable. An array of objects is a row of pointers.
