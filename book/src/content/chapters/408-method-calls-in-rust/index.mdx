## The cake, one more time

```drip
class Cake {
  init(f) { self.f = f; }
  taste() { print "Mmm, " + self.f; }
}
let c = new Cake("lemon");
c.taste();
let t = c.taste;
t();
print t; # fn taste
```

It prints `Mmm, lemon` twice, then `fn taste`, exactly like the
TypeScript VM. `drip-rs --disassemble` shows the split from the chapter
*Invoking methods, and inheritance in the VM*: `c.taste()` is one
`invoke 'taste' (0 args)`, while `let t = c.taste;` is
`get.prop 'taste'`, which has to build a **bound method**, a value that
remembers both the method and the instance it was read from, so that a
later `t()` knows what `self` is. That object, and the `init` behind
`new Cake("lemon")`, are this chapter.

## A bound method is two handles

<Analogy title="a remote already paired with one television">
Pressing a button (calling the method) works on that set (the
receiver), whoever holds the remote and wherever they carry it.
<span slot="breaks">Pairing a remote is done once; drip-rs makes a new
bound method every time a method is read from an instance, so
`c.taste == c.taste` is `false`: two reads, two objects.</span>
</Analogy>

<Analogy title="a letter in a stamped, addressed envelope">
The letter is the method, the address on the envelope is the receiver;
whoever posts it, it reaches the same house.
<span slot="breaks">A posted letter is used up; a bound method can be
called any number of times, and each call gets the same receiver.</span>
</Analogy>

The TypeScript object is `{ type: 'bound', receiver, method }`. The Rust
one, from `object.rs`:

```rust
/// A method together with the instance it
/// was looked up on.
pub struct ObjBoundMethod {
    pub receiver: Value,
    pub method: Gc<ObjClosure>,
}
```

It lives in its own arena, `heap.bound_methods`, and a value refers to
it as `Value::BoundMethod(Gc<ObjBoundMethod>)`. The receiver is kept as
a `Value`, which is exactly what a call will write back onto the stack,
and the collector traces both fields. `get.prop` makes one when the
instance has no field of that name (the chapter *Objects in Rust*), from
`vm.rs` (rewrapped):

```rust
let class = self.heap[instance].class;
let Some(method) =
    self.heap[class].methods.get(name)
else { return Err(self.no_property(...)); };
let receiver = self.peek(0);
let bound = self.alloc(ObjBoundMethod {
    receiver,
    method: as_closure(method),
});
self.set_peek(0, Value::BoundMethod(bound));
```

Two details. The method table stores `Value`s, so `as_closure` opens the
`Value::Closure` with a `match` and calls `unreachable!` on anything
else, where TypeScript wrote `method as ObjClosure`, a promise the type
checker takes on trust. And the order matters: `alloc` may collect, so
the receiver stays on the stack, a root, until the bound method exists,
and only then does `set_peek` overwrite it with the handle.

## Calling it: copy two fields out

`call_value`'s arm for a bound method, from `vm.rs` (rewrapped):

```rust
Value::BoundMethod(bound) => {
    let ObjBoundMethod { receiver, method }
        = self.heap[bound];
    // The receiver goes in slot 0, where
    // the method finds `self`.
    self.set_peek(arg_count, receiver);
    self.call(method, arg_count)
}
```

Here is the spot the difference. The tempting line is
`let b = self.heap[bound];`, and on a toy with a `Vec<Bound>` rustc
1.97 says (trimmed):

```text
error[E0507]: cannot move out of index
  of `Vec<Bound>`
4 |     let b = bounds[0];
  |             ^^^^^^^^^ move occurs
  value has type `Bound`, which does not
  implement the `Copy` trait
```

Indexing gives a *place* (a location, not a value), and `let b = place`
would move the object out of the arena and leave a
hole<Cite id="rust-std-ops-index" />. The destructuring pattern instead
binds each field by value: `Value` and `Gc<T>` are both `Copy`, so each
field is copied and the object stays put (the chapter *Ownership*
explains moves and copies). TypeScript's `callee.receiver` is a plain
reference read, so the question never comes up there. Then
`set_peek(arg_count, receiver)` overwrites the callee's own slot, which
`call` turns into the new frame's slot 0; inside the method, `self`
compiles to `load.local 0`, so it is the receiver.

<Callout kind="definition">
A **bound method in drip-rs** is an `ObjBoundMethod`, holding a
`receiver: Value` and a `method: Gc<ObjClosure>`, in the heap's
`bound_methods` arena, with a `Value::BoundMethod` handle to it.
`get.prop` makes one when a property read finds a method: it allocates
while the receiver is still on the stack, then overwrites the receiver
with the handle. Calling one copies both fields out with a destructuring
pattern, puts the receiver in the callee's slot, and calls the closure.
</Callout>

<Formal title="What a bound method and new mean">

```text
bound(r, m)(a₁, …, aₙ)
  = m(a₁, …, aₙ)   with slot 0 = r
new C(a₁, …, aₙ)
  = o              after C.init(a₁, …, aₙ)
                   runs with slot 0 = o
```

<span slot="read">Calling a bound method made from the receiver r and
the method m is calling m with the same arguments, except that slot 0,
where self lives, holds r. And new C with some arguments makes a fresh
instance o, runs C's init with those arguments and o in slot 0 (if C has
an init), and produces o.</span>
</Formal>

## Initialisers

`new` is `Vm::new_instance`. The chapter *Objects in Rust* showed its
first half: allocate the instance while the class is still in its slot,
then overwrite that slot with it. The second half (rewrapped):

```rust
match self.heap[class].methods
    .get(self.init_string) {
    Some(init) => self.call(
        as_closure(init), arg_count),
    None if arg_count != 0 => {
        // "Cake has no init, so it takes no
        // arguments, but got 2"
    }
    None => Ok(()),
}
```

`init_string` is `"init"`, interned once in `Vm::new` and listed in
`VmRoots`, so the lookup allocates nothing and the string cannot be
collected. `get` returns a copied `Option<Value>`, so the borrow of the
class ends before `call` needs `&mut self`. TypeScript's two `if`s
become one `match` with a guard, which says in one place what happens
in all three cases. The compiler's half: `method()` picks
`FunctionKind::Initializer` when the name is the keyword `init` (an
enum variant where TypeScript compared the string `'initializer'`), and
then `emit_return` ends every initialiser with `load.local 0` and
`return`, so `new` always produces the instance (rewrapped):

```rust
if self.state().kind
    == FunctionKind::Initializer {
    // An initializer returns `self`, which
    // is in slot 0.
    let line = self.previous.line;
    self.emit_op_byte_at(line,
        OpCode::LoadLocal, 0);
} else {
    self.emit_op(OpCode::None);
}
```

<Callout kind="engine" label="Under the hood">
`c.taste()` skips the bound method entirely: `invoke` opens the receiver
with `let Value::Instance(instance) = self.peek(arg_count) else { ... }`,
checks the fields (a field holding a function wins), and otherwise calls
the class's method with the receiver already in slot 0, so a normal
method call allocates nothing. A bound method, when one is made, is 24
bytes in an arena slot, a 16-byte `Value` and a 4-byte handle, padded
(printed with `size_of` on rustc 1.97). In this book's benchmark run
(`drip-rs-bench-2026-11-02.md`), `method_calls` took 167 ms on drip-rs
and 704 ms on the TypeScript VM.
</Callout>

## What you learned

- A **bound method** in drip-rs is `ObjBoundMethod { receiver, method }`
  in an arena, reached through `Value::BoundMethod`.
- `get.prop` **allocates before it overwrites** the receiver, so the
  receiver is a root if a collection runs.
- Indexing the heap gives a place: **destructure** it to copy the `Copy`
  fields out; `let b = self.heap[bound];` would be a move (E0507).
- Calling a bound method or running `init` **uses the callee's slot** as
  slot 0, `self`; `FunctionKind::Initializer` makes every `init` return
  slot 0.
