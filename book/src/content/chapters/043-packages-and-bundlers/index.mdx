## What the code does not say

Your Drip project now has a `tsconfig.json`, and it runs `tsc`. But
which `tsc`? Your computer might have TypeScript 6 installed, a
teammate's 5.4, and the test server none at all; and each version checks
a little differently. A project has to say which tools it needs, at
which versions, and how to run them; and when it is finished, a browser
wants its dozens of modules packed into one file. This chapter covers
both jobs.

## package.json and npm

<Analogy title="a recipe's shopping list, and the receipt">
A good recipe's list says "flour, type 00, any brand from 2024 on",
leaving you some room; the receipt in your bag records the exact packet
you bought, so you can buy the very same one next time.
<span slot="breaks">A shop might swap in a different flour when one runs
out. npm never installs a version outside the range you wrote, and
with the receipt (the lock file) it installs exactly what is written
there, every time.</span>
</Analogy>

<Analogy title="the label on a box of flat-pack furniture">
The label says what is inside and which version of the design it is,
lists the extra tools you will need, and points to the steps for
putting it together.
<span slot="breaks">A label is printed once. A `package.json` is edited
for the whole life of the project, often by npm itself, which adds a
line every time you install something.</span>
</Analogy>

**npm** is the command-line tool that installs JavaScript packages
from the npm registry, a public collection of published packages. A
project describes itself to npm in a file called `package.json`, at its
top level:

</Figure>

Here is how such a file comes about, in an empty folder:

```text
$ npm init -y
$ npm install --save-dev typescript@5.9.3
added 1 package, and audited 2 packages...
$ npm run check
> drip@1.0.0 check
> tsc --noEmit
```

`npm init -y` writes a starting `package.json` (named after the folder,
at version `1.0.0`). The install downloads TypeScript 5.9.3 into a
folder called `node_modules` (without `@5.9.3`, npm picks the newest
version), adds `"typescript": "^5.9.3"` to `devDependencies`, and writes
a second file, `package-lock.json`. Once you have added a `check` script by hand,
`npm run check` runs it, printing the package's name and version and
then the command. The script uses the project's *own* copy of `tsc`,
from `node_modules`, because npm puts that folder's tools first in line
while a script runs<Cite id="npm-scripts" />: on the machine this was
written on, `tsc` typed on its own was version 6.0.2, while
`npm run` used the project's 5.9.3. (`npx tsc` finds the project's copy
in the same way.)

<Callout kind="definition">
A **`package.json`** describes a package (a project, or a library to
publish): its **`name`** and **`version`** (both required only to
publish), its **`scripts`** (named commands, run with `npm run name`),
and its **dependencies**: `dependencies` for what the code needs when it
runs, and `devDependencies` for tools needed only to develop it, such as
TypeScript or a test runner<Cite id="npm-package-json" />. `"type":
"module"` tells Node that the package's `.js` files are ES modules (the
`import` kind)<Cite id="node-packages-type" />. **`npm install`** reads
it, installs the dependencies into `node_modules/`, and records the exact
versions it chose in **`package-lock.json`**, which you commit, so that
everyone who installs gets the identical set<Cite id="npm-install" /><Cite id="npm-package-lock" />.
</Callout>

Versions are written **major.minor.patch**: the patch number goes up
for bug fixes, the minor number for new features that break nothing,
and the major number for changes that may break code that used
it<Cite id="semver2" />. The `^` in front means "this version or any
later one with the same major number"<Cite id="node-semver-ranges" />:

<Formal title="The caret range">

```text
^M.m.p  accepts  v  when
  v ≥ M.m.p   and   v < (M+1).0.0
(for M ≥ 1)
```

<span slot="read">A caret range, caret M dot m dot p, accepts a version
v when v is at least M.m.p and below the next major version, M plus
one, dot zero, dot zero. So ^5.9.3 accepts 5.9.3, 5.9.10 and 5.12.0, but
not 5.9.2 or 6.0.0. (A range whose major number is 0 is narrower, since
the next number along counts as the major one.)</span>
</Formal>

```json

npm error   npm run

```

Python's `pyproject.toml` plays the same part as `package.json`, and
`pip` the part of npm. Java's Maven names a package by a group (usually
a web address written backwards) and an artifact, and keeps dependencies
in the same file, in XML. C has no standard package manager at all: a
`Makefile` says how to build, and libraries are installed by hand or by
the operating system, which is one reason a C project's setup
instructions are often long.

## Bundlers

A browser loading the interpreter as forty separate modules has to fetch
forty files, one import at a time, and they are still TypeScript; and
every function in them comes along, used or not. Before shipping, we
want one file of plain JavaScript holding only what the program uses.

<Analogy title="packing from a checklist">
You pack for a trip by starting with what you will do (a wedding, a
hike), adding what each thing needs (the suit needs its shoes, the camera
its charger), and leaving everything else at home; it all goes in one
bag.
<span slot="breaks">You pack each item whole. A bundler can leave behind
*part* of a module, one unused function, and it never makes a judgment
call: anything the code can reach is packed.</span>
</Analogy>

<BundleSteps client:visible />

<Callout kind="definition">
A **bundler** starts from an entry module, follows every import to find
all the modules the program needs (and only those), and writes them into
one file, or a few, with each module after the ones it imports. Most
also strip TypeScript's types, remove code nothing uses (**tree
shaking**), and **minify** the result (shorten names and remove spaces
to make the file smaller). esbuild, which this book's repository uses,
does all of these<Cite id="esbuild-readme" />.
</Callout>

<Examples of="bundler">

```text
$ npx esbuild src/main.ts --bundle
    --format=esm --outfile=dist/app.js
$ cat dist/app.js
// src/math.ts
function double(n) {
  return n * 2;
}
// src/main.ts
var x = double(21);
console.log(x);
```

```text
$ npx esbuild src/main.ts --bundle
    --format=esm --minify
function r(e){return e*2}var n=r(21);
console.log(n);
```

```js
// engine/ts/packages/playground/build.mjs
await build({
  entryPoints: [join(here, 'entry.ts')],
  bundle: true,
  format: 'esm',
  platform: 'browser',
  minify: true,
  outfile: '…/book/src/vendor/viscosity.js',
});
```

</Examples>

The first bundles two modules, `main.ts`, which imports `double` from
`math.ts`, which also exports a function nobody imports: the output has
`math.ts` first, its types gone, the imports and exports gone, and no
trace of the unused function. The second is the same with `--minify`:
the same program, renamed and squeezed onto one line (shown here on
two). The third is real (trimmed): it is how this book's playground packs
the whole Viscosity engine into one file that runs in your browser.

What a bundler does *not* do is check types. Add
`const oops: string = 5;` to `main.ts` and esbuild bundles it without a
word (and, since nothing uses `oops`, drops it). So a project's build
script checks first, and bundles only if the check passed (`&&` runs the
second command only if the first succeeded):

```json
"scripts": {
  "build": "tsc --noEmit && esbuild ..."
}
```

## What you learned

- **`package.json`** names a package and lists its **scripts** and
  **dependencies**; `devDependencies` are tools for developing it.
- **npm install** fills `node_modules/` and records exact versions in
  **`package-lock.json`** (commit it); `^5.9.3` accepts any 5.x from
  5.9.3 on; `npm run` and `npx` use the project's own tools.
- A **bundler** follows imports from an entry module and writes one
  file of what the program uses, with **tree shaking** and
  **minifying**; it erases types but never checks them.
