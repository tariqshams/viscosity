## Which file first?

In C, the files of a program can be compiled in any order, because each
one only reads declarations from headers, which are plain text. Many
newer languages do better than headers: a Go package or a Rust crate
imports another by name, and the compiler reads what it needs (the types
and functions the other one exports) from that package's own compiled
output. That is more reliable, since nobody can
write a declaration that lies, but it adds a rule: a module can only be
compiled after every module it imports. JavaScript has the same rule
for *running* modules: a module's top-level code runs only after the
code of the modules it imports<Cite id="mdn-modules" />. So a build
tool has to answer "in what order?", and the answer comes from a
picture.

## The import graph

Draw every module as a dot and every import as an arrow, from the
module that imports to the module it imports. The result is the
program's **module graph**. In the program below, `main` imports `a`
and `b`, `a` imports `c`, and `b` imports `c` and `d`; walk it, and
watch where each module lands in the order:

<OrderSteps client:visible />

The walk is **depth-first**: from a module, go down its first import
as far as you can before trying the next one, and remember which
modules are *in progress* (still on the walk's stack) and which are
*finished*. A module is finished only when all its imports are, so the
order in which modules finish (c, a, d, b, main) puts every module
after everything it imports. Such an order is a **topological order**.

<Analogy title="getting dressed">
Socks before shoes, a shirt before a jacket: each item has a few things
that must go on first, and any order that respects all of them gets you
out of the door dressed. There are usually several right orders, and
socks-then-shirt is as good as shirt-then-socks.
<span slot="breaks">A wardrobe never asks for shoes before socks
*and* socks before shoes; a program can do exactly that, with two
modules that import each other, and languages disagree about what to
do then.</span>
</Analogy>

<Analogy extra title="a recipe with sub-recipes">
A pie needs pastry and a filling, and the filling needs stewed apples;
the cook makes the apples, then the filling, then the pastry, then the
pie. A sub-recipe used twice (custard in two desserts) is made once.
<span slot="breaks">A kitchen can make the pastry and the apples at the
same time with two cooks; the graph allows that too (modules with no
path between them can be compiled in parallel), but the simple walk
here produces one line, not a schedule.</span>
</Analogy>

<Callout kind="definition">
A program's **module graph** has one node per module and an edge from
`m` to `n` whenever `m` imports `n`. A **topological order** of it
lists every module after all the modules it imports; a depth-first
walk that adds each module when it finishes produces one. An edge back
to a module that is still in progress means the graph has a
**cycle**, and then no topological order exists.
</Callout>

<Formal title="A build order">

```text
order is a build order  ⇔
  ∀ m → n in the graph :
      pos(n) < pos(m)
```

<span slot="read">An order is a build order exactly when, for every
arrow from a module m to a module n it imports, n's position in the
order is earlier than m's. If the graph has a cycle, say a imports c
and c imports a, the rule would need pos(a) &lt; pos(c) and pos(c)
&lt; pos(a) at once, which is impossible.</span>
</Formal>

```text
$ go list -deps . | grep app
app/c

app
```

```text
// main.mjs → a.mjs → b.mjs → c.mjs,
```

```text
$ go build .
package cyc
  imports cyc/a from main.go
  imports cyc/b from a.go
  imports cyc/a from b.go:
    import cycle not allowed
```

</Examples>

The first is real Go 1.24 output for a program shaped like `main`, `a`,
`b` and `c` above (with `grep` keeping only its own packages, since the
standard library's are listed too). `go list -deps` "visits them in a
depth-first post-order traversal, so that a package is listed only after
all its dependencies"<Cite id="go-list-deps" />, which is the walk you
just stepped through, and `go build` compiles in such an order. The
second is Node 22 running four JavaScript modules in a chain: each
module's top-level code runs after the code of the module it imports,
so the deepest one, `c`, prints first. The ECMAScript specification
defines this with a depth-first walk of its own, which also finds the
groups of modules that form a cycle (a *strongly connected component*)
and moves each group from one state to the next
together<Cite id="ecma262-module-evaluation" />. The third is Go
refusing a cycle (`a` imports `b`, which imports `a`): the language
says "it is illegal for a package to import itself, directly or
indirectly"<Cite id="go-spec-imports" />, and the error lists the whole
loop.

JavaScript allows the cycle, and the spot-the-difference shows the
price:

```js
// a2.mjs
import { b } from './b2.mjs';
export const a = 'A';
console.log(b);
// b2.mjs
import { a } from './a2.mjs';
export const b = 'B';
console.log(a);
// $ node a2.mjs
// ReferenceError: Cannot access 'a'
//   before initialization
```

Starting at `a2`, the walk reaches `b2`, whose import of `a2` points
back at a module still in progress; so `b2` runs first, and reads `a`
before `a2`'s `const a = 'A'` has run. Make the imports go one way
(move what both need into a third module) and the error disappears. (Node prints the file name and a stack too; the
message is quoted exactly.)

## What to rebuild

The same graph answers the build tool's other question. When a module's
interface changes, every module that imports it may have been compiled
against the old one, and so may every module that imports *those*:
exactly the modules that can reach the changed one by following arrows.

<Run id="rebuild-set" />

`importers` flips every arrow, so that `back.c` is `['a', 'b']`, the
modules that import `c`. `rebuild` then walks the flipped arrows from
the changed module with a to-do list, adding each module it reaches to
a set once; it prints `[ 'a', 'b', 'c', 'main' ]` for `c`,
`[ 'b', 'd', 'main' ]` for `d`, and only `[ 'main' ]` for `main`,
which nobody imports. (When
only a function's *body* changes and its interface does not, the
importers' compiled code is still right; this is what separate
compilation bought us in the last chapter, and why build tools try hard
to tell the two kinds of edit apart.)

## What you learned

- Imports make a **module graph**, with an arrow from each module to
  every module it imports.
- A **depth-first walk** that records each module when it finishes
  gives a **build order**: every module after its imports. Go compiles,
  and JavaScript runs, modules in such an order.
- An arrow back to a module still in progress is a **cycle**: Go
  rejects it, JavaScript runs it and may read a variable too early.
- After an interface change, everything that can reach the changed
  module is rebuilt.
