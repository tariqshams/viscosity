## Two facts nobody wrote down

To give a field a `Float64Array` column, Viscosity needs two facts that
no JavaScript program states:

1. every element has **the same fields**, so there is one set of columns;
2. a field only ever holds **numbers**, so a typed array can store it.

A `Float64Array` silently turns a string like `'far'` into `NaN`, so getting the
second one wrong changes what the program prints. Viscosity can't ask,
and it doesn't trust TypeScript annotations either: it strips them before
analysis, and they never change what runs<Cite id="ts-basics" />. It has
to deduce both facts from the code itself.

<Callout kind="intuition">
A detective has no confession, only evidence. “The butler did it” is a
guess; the work is checking every clue against it. If one clue
contradicts the guess, it goes. If none do, it stands.
</Callout>

<Callout kind="definition">
**Type inference** deduces the types of values from how they are made
and used, with no annotations. Viscosity's version answers one question
per value: is it provably a number? **Shape inference** deduces an
object's layout, its fields and their order, statically, from the code
that creates the objects.
</Callout>

## Rules for one value

Each IR value gets a fact from a small rule. Simplified, from
`packages/core/src/analysis.ts`:

```ts
switch (i.op) {
  case 'const':
    return typeof i.value === 'number';
  case 'binop':
    return ARITH.has(i.operator)
      && n(i.args[0]) && n(i.args[1]);
  case 'phi':
    return i.args.every(n);
  case 'loadBinding':
    return bindingNumeric.get(i.binding);
  case 'param': // every caller passes one
    return sites.every((s) =>
      n(s.args[i.index + 1]));
  case 'field.get':
    return colNumeric.get(column(i));
  default:
    return false;
}
```

`n(v)` reads the current fact for `v`. Notice that `+` counts only when
both sides are numbers, since `1 + '1'` is `'11'`. The `param` rule only
works for the known functions of the last chapter, whose every call site
is visible. Anything unfamiliar falls to `default`: not a number.

## The loop problem

The rules refer to each other. A loop counter's phi depends on the
addition at the bottom of the loop, which depends on the phi. Where do
you start? Step through both answers:

<LatticeSteps client:visible />

This is the lattice and fixpoint machinery from chapter 79, with a
two-level lattice: *number* above *maybe not*. Viscosity starts the
values that can sit on cycles (phis, variable loads, field reads and
parameters) at the optimistic top, then recomputes every value, variable
and column until a whole round changes nothing:

```ts
for (const v of m.values)
  num.set(v.id, cyclic(v) || compute(v));
for (let changed = true; changed; ) {
  changed = false;
  for (const v of m.values) {
    const nv = compute(v);
    if (num.get(v.id) !== nv) {
      num.set(v.id, nv);
      changed = true;
    }
  }
  // then variables and columns
}
```

A fact can only fall, from *number* to *maybe not*, and there are
finitely many facts, so the loop must end. As a guard, the real code
also stops after 1000 rounds, and if it hasn't settled by then it gives
up on every guess (fails closed) rather than keep an unproven one.

<Callout kind="definition">
An **optimistic** analysis starts from the best possible answer and
removes what the program contradicts. A **pessimistic** one starts from
the worst and adds only what it can prove. On a cycle, a pessimistic
analysis never gets started: each value waits for the other. Optimism
finds the largest set of facts that is consistent with every rule.
</Callout>

## Watching facts spread

Here is `viscosity explain` on three versions of one program. Records are
pushed as `add(i, 0)` in a loop, then once more as `add(5, 'far')`:

```
// the loop does ps[i].x *= 2
· typed Float64Array columns for x;
  plain array columns for y
  (may hold non-numbers)

// the loop does ps[i].x += ps[i].y
· no field is provably numeric, so
  there are no typed columns to gain

// the call is add(5, 0) instead
· typed Float64Array columns for all
  2 fields
```

The second one is the interesting one. Only `y` ever receives a string,
but `x += y` stores `x + y` back into `x`, and that might be a string,
so `x` falls too. One string poisoned two columns. A field that may hold
non-numbers is not a reason to give up, though: it gets a plain array
column, while the numeric fields still get typed ones. Try it:

## Shapes from object literals

The other fact is the shape. Viscosity only accepts records made by
object literals, in `push({...})` or in an array literal. Each becomes a
`record.new` instruction carrying its field list, and every list must
match the first, order included:

```ts
if (c.fields.length === 0)
  c.fields = [...r.fields];
else if (c.fields.join(',')
         !== r.fields.join(','))
  c.bailouts.push('records with ' +
    'different fields or field order');
```

That is the simplest possible way to unify shapes: they must be equal.
Two corpus programs show both ways to fail:

```
· unsafe: line 3: records with different
  fields or field order
  ({x, y} vs {x, y, z})

· unsafe: line 4: records with different
  fields or field order
  ({x, y} vs {y, x})
```

Why should order matter, when `{x, y}` and `{y, x}` hold the same data?
Partly for Viscosity itself: it reads the value for column `x` from a
fixed position in each `record.new`. And partly because order is part of
JavaScript. You saw in chapter 63 that shapes grow one property at a
time, and the language itself can tell the two apart:

<Callout kind="engine" label="Under the hood">
V8 learns the same two facts by watching. Its type feedback records which
shapes and number representations each operation has seen, and its
optimizing tiers specialize on that, with deoptimization as the way
back<Cite id="v8-maglev" />. Viscosity runs before the program and has
no way back, so a guess has to become a proof. That is why it uses an
optimistic fixpoint, which keeps only the guesses that every rule
confirms, and why one string or one reordered literal is enough to make
it change its decision.
</Callout>

## What you learned

- **Type inference** deduces types from how values are made and used.
  Viscosity asks one question per value: provably a number?
- Rules combine facts: constants, arithmetic on two numbers, phis whose
  inputs all agree, variables, columns, and parameters of known functions.
- Loops make the rules circular. An **optimistic** fixpoint starts at
  “number” and knocks guesses down. A pessimistic one can't prove a loop.
- Facts spread: one string in `y` can make `x` non-numeric through
  `x += y`. Such fields get plain array columns.
- **Shape inference** takes the field lists of the object literals. In
  Viscosity they must match exactly, order included.
