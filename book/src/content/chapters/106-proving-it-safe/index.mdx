## The promise

Viscosity is a source-to-source compiler, and it makes one promise:
the program it writes prints exactly what yours printed. The struct of
arrays it builds stores the same numbers; however, a JavaScript program
can notice much more than numbers. It can notice how its data is
*stored*:

```js
ps[1] === ps[2];    // one object?
console.log(ps[3]); // print the object
const keep = ps[0]; // a second name
ps.sort(byX);       // move the objects
for (const k in ps[0]) {} // its keys
```

After the rewrite there are no element objects, only columns, so if
any such line survived, the program could tell.

<Analogy title="a scene change behind the curtain">
A theatre crew changes the set during the interval, with the curtain
down. That is fine as long as nobody in the audience can see behind
it, so before anything moves, the stage manager walks the hall and
checks every gap in the curtain.
<span slot="breaks">A stage manager who misses a gap may get away with
it if nobody happens to look; a program that can observe the change
will, on every run, so Viscosity has to find every gap, not most of
them.</span>
</Analogy>

<Analogy extra title="renumbering the rooms of a hotel">
A hotel can renumber its rooms overnight, but only if no guest has
written "room 12" anywhere: on a note, in a letter, in a friend's
phone. A number kept somewhere else would now lead to the wrong door.
<span slot="breaks">A hotel can ring every guest in the morning and
tell them the new numbers; once Viscosity's output is running, there
is nobody left to fix a stale reference, so it has to prove that none
exists before it starts.</span>
</Analogy>

<Callout kind="definition">
**Safety analysis** proves that no code can observe a layout change.
In Viscosity it is an **allow-list**: every use of the collection, and
of every element it hands out, must be one that Viscosity knows how to
rewrite. Any other use adds a **reason** to the collection's bailout
list, and an empty list means safe.
</Callout>

The proof is two analyses you have met before, aimed at one question.
It is an **escape analysis** (as in *Escape analysis across
functions*): no reference to the array or to an element may reach code
Viscosity does not rewrite. And it is an **alias analysis** (as in
*Alias analysis and points-to*): no
value may be a second name for an element, and a function's parameter
may point to only one collection.

## What the array and its elements may do

The array's own uses are the short list you met in *Finding
collections, and inferring shapes*: the worklist from every load
accepts `.length`, a `push` of one fresh literal (whose shape it
checks), `ps[i]`, and a call of a known function, and sends anything
else to `bail(c, 'the array is ' + describeUse(u))`, which names what
happened. What discovery left for later is the element that `ps[i]`
hands out; each one is remembered, and its uses get an even shorter
list: read a field of the shape, or write one (the uses that fill
*Access patterns*' table). Anything else, such as passing the element
to a function or comparing it with `===`, is a reason.

<Formal title="The safety condition">

```text
safe(c) ⇔
  ∀ v ∈ Refs(c), u ∈ uses(v):
    u ∈ {length, push, index, known call}
  ∀ e ∈ Elems(c), u ∈ uses(e):
    u ∈ {e.f read, e.f written | f ∈ shape}
  ∀ ps[k] of c:  k is a number
```

<span slot="read">A collection c is safe exactly when three things all
hold. Every use of every value that refers to c (Refs, the set from
*Finding collections, and inferring shapes*) is one of the four
rewritable kinds. Every use
of every element of c is a read or a write of a field in its shape.
And every index used on c is provably a number. Fail any one of them
anywhere, and c gets a bailout reason.</span>
</Formal>

<Examples of="safety-analysis">

```text
step(ps); step(ps); console.log(ps[3].x);
ps (line 1) {x, vx} → struct of arrays
```

```text
ps.reverse();
· unsafe: line 10: uses .reverse on the
  array (only .length and .push are
  supported)
· unsafe: the array is passed to a
  method call at line 10
```

```text
console.log(ps[3]);
· unsafe: line 10: an element is passed
  to a method call
```

</Examples>

All three are the playground program at the end of this chapter,
with one line changed. The first is accepted: `ps` is only pushed,
measured, indexed and passed to `step`, whose every call passes `ps`.
The second gives two reasons for one line: `ps.reverse()` reads a
property other than `length`, and passes `ps` to a method call. The
third prints the element object itself, keys and all, and a struct of
arrays has no such object.

## Following a collection into a function

Most real code does not loop over an array where it was made; it
passes the array to a function. A call is normally an escape, because
the callee could do anything. However, if Viscosity can see *every*
call of the function, the parameter is only another name for the
collection, which is interprocedural analysis on a small scale.
Viscosity first finds its **known functions**: a function counts as
known if its name is given a value exactly once and every reference to
it is a direct call (not stored, not passed along, not called as a
method), so the call sites it can see are all of them. When `ps` is passed to a known function at
position `k`, Viscosity checks that **all** its call sites pass `ps` at
`k`; if they do, the parameter joins the worklist, and if some call
passes something else, it bails out. Two corpus files show both
outcomes:

```text
// interproc_ok.js: drift(bodies, …) ×2
bodies (line 2) {x, y, m} → struct of
  arrays
// interproc_mixed.js: total(a), total(b)
· unsafe: line 10: passed to total(),
  which is also called with other values
```

This is points-to analysis on a small scale (*Alias analysis and
points-to* showed the general kind): the parameter must point to
exactly one collection. Two collections would need two
copies of `total`, one per layout, and Viscosity does not copy
functions. An `export`ed function is never known either, since code in
another module could call it with anything; passing `ps` to one gives
"the array is passed to a function call".

## Every index must be a number

`ps[i]` is only an element if `i` is a number. Bracket access with a
string asks for a property, and some strings happen to name elements
(the dropdown below runs it).

After the rewrite, `ps[k]` becomes `ps.x[k]` and friends, which would
answer `ps['length']` completely differently, so Viscosity requires
every index to be provably a number. "Provably a number" is a fact from
the numeric fixpoint of *Finding collections, and inferring shapes*, so
this check waits until the fixpoint has finished:

```ts
for (const { c, i } of indexChecks)
  if (!isNumber(i.args[1]))
    bail(c, 'indexes the array with ' +
      'something that may not be a number');
```

The fixpoint follows parameters of known functions too: with
`function get(k) { return ps[k].x; }`, the calls `get(3)` and `get(4)`
are fine, while one call `get('4')` makes `k` "maybe not a number",
and the whole collection bails out ("indexes the array with
something that may not be a number").

## From reasons to explain

Viscosity never stops at the first problem: all the reasons are kept,
duplicates removed, and handed to the planner, which makes this the
very first question it asks: in `plan.ts`, a collection with any
reason is kept as an array of objects, each reason printed after
`unsafe:`, and no cost is ever weighed for it. Try it on the program below, which is accepted as it
stands; then make one change at a time and watch the reasons appear:
add `ps.reverse();` before the last line, print `ps[3]` instead of
`ps[3].x`, add a call `step([{ x: 0, vx: 1 }]);`, or index with
`const k = '3';`.

<More title="Under the hood: doing it at run time instead">
Makor and colleagues transform arrays of JavaScript objects into
columnar storage *while the program runs*<Cite id="makor2022" />; a
run-time system is there as each operation happens. A source-to-source
compiler gets no such second look: once its output runs, nothing of
Viscosity is left to notice a surprise. That is why it works with an
allow-list, and why even `ps[1] === ps[2]`, which only asks whether
two references name the same object<Cite id="mdn-equality" />, is
enough to stop it.
</More>

## What you learned

- **Safety analysis** proves that no code can observe the layout
  change. It is an **escape analysis** (no reference leaves the
  rewritable uses) plus an **alias analysis** (no second names), run
  as an **allow-list**.
- The array may be used for `.length`, `push` of one fresh literal,
  `ps[i]`, and as an argument to a **known function**; elements may
  only have fields of the shape read or written.
- A known function is declared once and only called directly. Its
  parameter is followed if **every** call passes the same collection;
  exported functions are never known.
- Every index must be **provably a number**, checked after the numeric
  fixpoint. Any reason makes the planner keep the array of objects and
  print it after `unsafe:`.
