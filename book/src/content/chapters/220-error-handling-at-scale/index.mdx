## Many ways to fail

The `drip-rs` binary can fail in four ways, and it says which with its
exit code: 64 if you call it wrongly, 74 if it can't read the file, 65
for a compile error, 70 for a runtime error. These are the `sysexits.h`
codes that clox uses too. A test runner, a shell script or chapter 15's
differential tests can tell the failures apart without reading a word
of the message.

Inside a program, the same question comes up at every layer. In
chapter 205 one function returned `Result<f64, String>`. That works
until a caller needs to *do* something different for different
failures. Then a `String` is a dead end: you'd have to parse the
message to find out what happened.

<Callout kind="intuition">
A `String` error is a note that says what went wrong. An error enum is
a form with tick boxes. Anyone can read the note, but only the form can
be sorted into piles without reading it.
</Callout>

## One enum for the crate

Say a command-line tool reads a minimum size from a file. Two things can
fail: reading the file (`std::io::Error`) and parsing the number
(`ParseIntError`). Give each one a variant, holding the original error:

```rust
#[derive(Debug)]
enum CliError {
    Io(io::Error),
    Num(ParseIntError),
}
```

A caller can now `match` on the kind and still see the details inside.
That is chapter 204's enum doing one more job.

<Callout kind="definition">
An **error enum** is a single enum that lists every way a crate's (or a
module's) operations can fail, one variant per kind, each holding the
details. Functions return `Result<T, ThatEnum>`, so callers handle one
error type and can match on its variants.
</Callout>

## From, and what ? does with it

The function wants to write both steps with `?`:

```rust
fn min_size(path: &Path)
    -> Result<u32, CliError> {
    let s = fs::read_to_string(path)?;
    let n = s.trim().parse::<u32>()?;
    Ok(n)
}
```

But `read_to_string` fails with an `io::Error`, not a `CliError`. This
is the detail chapter 205 mentioned in passing: on an `Err`, `?` first
passes the error through `From::from`, converting it into the
function's error type, and *then* returns it<Cite id="klabnik2026" />.
So you tell Rust how to convert:

```rust
impl From<io::Error> for CliError {
    fn from(e: io::Error) -> Self {
        CliError::Io(e)
    }
}
```

and the same for `ParseIntError`. Step through it:

<Callout kind="definition">
**`From<T>`** is the standard trait for converting a `T` into
`Self`, through `fn from(value: T) -> Self`. The **`?` operator** calls
it on every error it returns early, so one `impl From<SourceError> for
MyError` per source lets `?` work on all of them. Implementing `From`
also gives you the matching `Into` for free<Cite id="rust-std-from" />.
</Callout>

## Two real designs

Neither of this book's Rust projects has an error enum for its
library, and looking at why is the most useful part of the chapter.

**drip-rs** splits errors by when they're reported. The compiler pushes
each message, `[line 3] Error at 'x': ...`, into a `Vec<String>` as it
goes, recovering in panic mode to find more (chapter 45). The VM's
runtime error is this, from `vm.rs`:

```rust
/// Its message and stack trace are
/// already on stderr by the time one
/// of these exists, so it carries
/// nothing.
struct RuntimeError;

type Run<T = ()> = Result<T, RuntimeError>;
```

`runtime_error` writes the message and the trace into the VM's stderr
lines and returns a `RuntimeError`, and every `?` in the run loop passes
it up. `interpret` then returns an `Outcome` with the output, the errors
and `exit_code`, 65 or 70, and `main` turns that into a process exit
code. A unit struct is enough because nobody upstream needs more than
“stop”.

**engine/rust** has one error type for compiling, a newtype from
`core/src/plugin.rs`:

```rust
pub struct CompileError(pub String);

impl std::error::Error for CompileError {}
```

It also implements `Display`. A syntax error from oxc, an
AoSoA field that isn't numeric, an internal overlap check: all are one
message. The CLI has the smallest possible error enum, two variants
that both hold a `String`, because `main` treats them differently: a
`Usage` error is followed by the help text, any `Other` is not
(`cli/src/main.rs`, trimmed):

```rust
enum CliError {
    Usage(String),
    Other(String),
}

impl From<String> for CliError {
    fn from(e: String) -> Self {
        CliError::Other(e)
    }
}
```

Its helpers return plain `String` errors, and that `From` lets `?`
lift them into `CliError::Other`. Where no `From` exists, it converts by
hand:

```rust
let io = |e: std::io::Error| {
    CliError::Other(e.to_string())
};
fs::write(&a.out, text).map_err(io)?;
```

That is `map_err` doing what a `From<io::Error>` impl would do for
`?`. And in `read_profile` `?` converts on its own: `.ok_or("the
profile must be a JSON object: …")?` works in a function returning a
`String` error because the standard library has `impl From<&str> for
String`.
The WebAssembly crate of chapter 219 makes the last conversion,
`CompileError` into `JsError`, with `map_err` too.

<Callout kind="engine" label="Under the hood">
Both choices fit what the callers do. Every caller of engine/rust's
`compile` prints the message and gives up, so a `String` loses nothing;
the CLI's two variants exist only because its `main` does one thing
differently.
drip-rs's callers need the *kind*, compile or runtime, and get it as
an exit code. An error enum earns its keep when one crate's callers want
different things: a test that expects a runtime error and must not
accept a compile error, an editor that underlines compile errors at
their line, a server that retries an I/O error. The exercise sketches
that design for drip, as `DripError`; it is a design, not code drip-rs
has. Crates such as `thiserror` generate the `Display` and `From`
impls for an error enum<Cite id="thiserror-readme" />, but drip-rs
uses only `std`.
</Callout>

## What you learned

- An **error enum** gives a crate one error type with a variant per
  kind of failure, so callers can match instead of parsing messages.
- **`From`** says how to convert one error into another. `?` calls it on
  every early return, so one impl per source error is all the plumbing.
- Without a `From` impl, `?` is error E0277; `map_err` converts by hand.
- drip-rs reports errors as they happen and keeps only the kind: exit
  codes 65 and 70. engine/rust's `CompileError` is one `String`.
- Choose by what callers need to tell apart.
