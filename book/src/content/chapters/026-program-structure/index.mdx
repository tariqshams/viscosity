## Something has to run first

Last chapter split the interpreter into files. Now picture what happens
when you start it: `main.js` imports `parser.js`, which imports
`scanner.js` and `errors.js`, and every one of them has top-level code
that creates functions and classes. If `parser.js` ran before
`errors.js`, the line `class ParseError` would not have run yet, and the
parser would reach for a class that does not exist. So JavaScript needs
a rule for the order, and you need to know it, because it explains a
whole family of strange bugs.

## Who runs first?

<Analogy title="stock, then sauce, then the dish">
A recipe for the dish needs a sauce, and the sauce needs a stock; so you
make the stock first, then the sauce, and only then the dish. If two
sauces both need the stock, you make the stock once and use it twice.
<span slot="breaks">A kitchen with two cooks can make the stock and the
sauce at the same time; modules run one at a time, in one fixed
order.</span>
</Analogy>

The rule is the recipe's rule. Before running a module, JavaScript makes
sure that everything it imports has run, taking the imports in the
order they are written; and each module runs **once**, however many
files import it<Cite id="mdn-modules" />. Step through it:

<LoadOrderSteps client:visible />

That is recursion again, from chapter 19: "get this module ready" means
"get each of its imports ready, then run it", and a module with no
imports, such as `errors.js`, is the base case. The order this walk
produces (every module after everything it depends on) has a name you
will meet again in compilers: a **post-order**, because each module is
listed *after* its imports.

<Formal title="The load-order rule">

```text
A imports B   ⇒   B runs before A
every module runs exactly once
```

<span slot="read">If module A imports module B, then B finishes running
before A starts. And no module runs twice, so a shared module like
errors.js runs before the first module that needs it, and then never
again.</span>
</Formal>

<Examples of="program-structure">

```js
// b.js
console.log('b runs');
// a.js
import './b.js';
console.log('a runs');
// running a.js prints b runs, a runs
```

```js
// main.js
import './parser.js'; // imports errors
import './errors.js'; // already ran
// errors.js runs once, before parser.js
```

<Run id="wiring" />

</Examples>

The first is the smallest case: `import './b.js'` (an import that brings
in no names, only makes sure the file has run) puts `b.js` first, so its
line prints before `a.js`'s. In the second, `main.js` imports
`parser.js`, which itself imports `errors.js`, so `errors.js` runs
during the walk into `parser.js`; by the time `main.js`'s own second
import is reached, it has already run, and it is skipped. The runnable
one imitates a whole interpreter with the module pattern from the last
chapter: each "module" is a function that receives what it depends on,
and `main` has to build them bottom-up (errors, then scanner, then
parser), which is exactly the order JavaScript would run real files in.
It prints `6` (the digits of `'123'` added up) and then
`true bad digit x`: the `ParseError` thrown inside the scanner travels
out through the parser's `sum` and is caught in `main`, which checks
that it is the scanner's own kind of error. Try building the parser
before the scanner, and read the error you get.

## When two modules need each other

What if `scanner.js` imports `parser.js` and `parser.js` imports
`scanner.js`? That is a **cycle**, and the rule above cannot be obeyed:
one of them has to run first, while the other's names do not exist yet.
Code that reads such a name too early fails:

```js
// a.js
import './b.js';
export const x = 1;
// b.js
import { x } from './a.js';
console.log(x);
// ReferenceError: Cannot access 'x'
// before initialization
```

```js
// shared.js
export const x = 1;
// a.js and b.js both:
import { x } from './shared.js';
console.log(x); // 1
```

Running `a.js` starts the walk at `a`, which needs `b`, which needs `a`;
`a` has already been started, so it is not run again, and `b` runs with
`a`'s `const x` declared but not yet given its value, which is why the
message says *before initialization*. The usual fix is the second
version: move whatever both files need into a third module that both
import, so the imports point one way again<Cite id="mdn-modules" />.

## One job per module

<Analogy title="a kitchen brigade">
A good restaurant kitchen has stations with one job each (sauces, grill,
pastry), and orders flow one way, from the head chef down to the
stations. If the grill waits for the sauce station while the sauce
station waits for the grill, nothing gets cooked.
<span slot="breaks">Cooks who are stuck can talk it over and sort it
out; modules cannot, and the one that happens to run first finds
the other's names missing.</span>
</Analogy>

Splitting a program is a design decision, and good splits follow two
rules of thumb. Each module has **one clear job** that you can say in a
sentence; and the imports **point one way**, from the big picture down
to the details, so there are no cycles. Your interpreter will be split
like this:

<Figure takeaway="Every import points down, so nothing waits on itself." caption="Left: the interpreter's modules in layers. Each file imports only files below it, and errors.js, at the bottom, imports nothing. Right: two modules that import each other, which the left-hand layout makes impossible.">
  <Layers />
</Figure>

Each file imports only from files below it, so if you change how the
scanner reads numbers, only `scanner.js` changes; the error classes,
which everything uses, depend on nothing at all; and because no arrow
ever points up, a cycle cannot happen.

<Callout kind="definition">
**Program structure** is how a program is divided into modules. Aim for
modules with one job each, small exports that hide the details, and
imports that point one way, from high-level modules down to low-level
ones; then the load order is the layers from the bottom up.
</Callout>

<OtherLanguages>

```js
// errors.js
console.log('errors loaded');
// main.js
import './errors.js';
import './errors.js';
// prints once
```

```python
# errors.py
print('errors loaded')
# main.py
import errors
import errors
# prints once
```

```java
class Errors {
    static {
        System.out.println("loaded");
    }
}
// runs once, when Errors is
// first used
```

```c
/* errors.h */
#ifndef ERRORS_H
#define ERRORS_H
/* ... declarations ... */
#endif
```

</OtherLanguages>

All four make sure shared code is loaded once, but in different ways.
JavaScript and Python run a module's top-level code the first time it
is imported and remember that it has run (Python keeps it in
`sys.modules`, and a Python import cycle can fail with an
`ImportError` rather than a `ReferenceError`). Java has no top-level code in a file;
a class's `static` block runs once, the first time the class is used,
so the order follows the program's behaviour rather than its import
lines. C has no modules that run at all: `#include` pastes a header's
text in, so including it twice would paste it twice, and the
`#ifndef` "include guard" lines are the hand-made way to make the
second paste empty.

<Callout kind="engine" label="Under the hood">
Because imports name their files with plain strings at the top level,
tools can work out this whole order without running anything, and
bundlers rely on it to find code that nothing imports and leave it
out<Cite id="mdn-modules" />. The walk you just did, visiting what each
node depends on first and listing the node afterwards, is a
**depth-first post-order**, and it returns in Part VI, where a compiler
walks the graph of a function's blocks in exactly this way.
</Callout>

## What you learned

- A module runs after everything it imports, depth-first and in import
  order, and each module runs **once**; the result is a **post-order**.
- Two modules that import each other form a **cycle**, which can fail
  with `ReferenceError: Cannot access ... before initialization`; move
  the shared code into a third module.
- Good **program structure**: one job per module, small exports, and
  imports that point one way, from high-level layers down to low-level
  ones.
