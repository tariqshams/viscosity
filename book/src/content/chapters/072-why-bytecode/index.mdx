## How fast is Drip?

"Fast" only means something next to something else, so the companion
has a second Drip implementation: the bytecode VM this part builds,
also in TypeScript, which turns the tree into a flat list of small
instructions first. Both run the same ten benchmark programs, each in a
fresh Node process, best of three, timing everything from scanning on
(this book's run, committed in `companion/ts/results`: Node 22.23.4 on
a shared cloud machine, so a careful first look rather than a verdict):

<BenchChart />

The VM is faster on six programs and never by much (1.3 times at
best), and *slower* on four, the ones that make many objects or read
many fields. Both engines run on V8: the tree-walker's `Map`s and
objects are V8's own, tuned for years, while the VM rebuilds its stack,
tables and objects in TypeScript (*Measuring and speeding up the VM*
tests that explanation). None of this makes the tree-walker fast; its
costs are spread around, and to see them we look at one line.

## What one subtraction costs

Take one piece of `fib`, `n - 2`, which a CPU does in one instruction.
Here is everything the tree-walker does for it:

<OverheadSteps client:visible />

Seven method calls, four switches, two hash-map lookups and five checks,
for one subtraction; and `fib(32)` asks the same questions about the
same node millions of times, though the answers never change.

<Analogy title="a cook who rereads the recipe">
A cook making a hundred pancakes who, for every pancake, fetches the
recipe card, finds the line "add one egg", reads it, works out what an
egg is, and only then cracks one. The cracking is the real work; the
rereading is overhead, and it happens a hundred times.
<span slot="breaks">A cook would learn the recipe by heart after a few
pancakes; a tree-walker never learns, which is exactly what a bytecode
compiler adds: work done once so it need not be redone.</span>
</Analogy>

The overhead has three big sources. **Dispatch**: every node costs a
method call and a `switch` to find out what it is, every time.
**Pointer chasing**: the tree and the environment chain are webs of
separate objects, and each step must wait for the previous load, which
is far slower than walking an array in order<Cite id="slotin-amh-latency" />.
**Maps and allocation**: every local read is two hash
lookups<Cite id="mdn-map" />, nothing like a read at a known position,
and every call and loop pass allocates environments.

<Callout kind="definition">
**Interpreter overhead** is the work an interpreter does that the
program did not ask for: dispatching on node kinds, following pointers
between nodes and environments, looking names up in tables, allocating
environments and checking types. In a tree-walker it often costs far
more than the operations themselves.
</Callout>

<Examples of="interpreter-overhead">

```text
let sum = 0;
for i in 0..3 {
  sum += i;
}
# per pass: 2 new environments,
# a define, 7 more Map operations
```

</Examples>

One addition per pass costs two environments and a handful of `Map`
operations.

## Flatten the tree into a list

None of that finding-out changes between runs, so we can work it out
**once**, before the program starts, and write it down in a form that is
quick to follow. Before `*` in `2 * 3` can do anything, both operands
must be ready, so the rule is: visit a node's children *before* the
node, and write one step for each node as you finish it.

<TreeToBytes client:visible />

The list can be followed top to bottom without the tree, and the next
step is at the next index, not behind a pointer.

<Callout kind="definition">
**Bytecode** is a program written as a compact, flat list of simple
instructions, stored as small numbers in an array. A compiler produces
it once, before the program runs, and each instruction does one small
thing, such as "push this value" or "add the two newest values".
</Callout>

<Examples of="bytecode">

```text
print 1 + 2 * 3;

0000    1 const               0 '1'
0003    | const               1 '2'
0006    | const               2 '3'
0009    | mul
0010    | add
0011    | print
```

</Examples>

Drip's real compiler prints this for the tree in the diagram (the next
chapter explains the columns): three `const`s, then `mul`, `add` and
`print`, children first.

## Opcodes and operands

To store a step in an array of numbers, each kind of step gets a
number. Drip's VM keeps the numbering in `vm/chunk.ts`:

```ts
export const Op = {
  Const: 0,        // k     push constant k
  None: 1,         //       push none
  // ...
  Add: 20,
  // ...
  Print: 33,
```

There are 53 kinds, and a byte holds 0 to 255. Some need more than
their number: "push a constant" must say *which*, so two more
bytes follow the `0`, holding the constant's number, high byte first;
`add` needs nothing, because it always works on the two newest values.
The comments label the operand shapes: `k` is two bytes naming a
constant, `s` one byte (a slot or a count), `j` two bytes of jump
distance.

<Figure takeaway="An instruction is an opcode, then its operands." caption="Three real Drip instructions, one for each size of operand: none for add, one byte for load.local's slot, and two bytes for const's constant number, the high byte first.">
  <InstrBytes />
</Figure>

<Callout kind="definition">
An **opcode** is the number that says which instruction this is. An
instruction is its opcode followed by zero or more **operand** bytes,
which give it the details it needs, such as which constant to push; as
such, different instructions take different numbers of bytes.
</Callout>

<Examples of="opcode">

```text
add       →  20
const 2   →  0, 0, 2
const 300 →  0, 1, 44
```

</Examples>

`add` is one byte; constant 300 needs a high byte of 1, because
1 × 256 + 44 is 300.

<Formal title="The bytes of an instruction">

```text
instruction = opcode operand*
const k     = 0, hi, lo
              where k = hi × 256 + lo
```

<span slot="read">An instruction is an opcode followed by any number of
operands (the star reads "zero or more"). The const instruction is
three bytes: the opcode 0, then the constant's number k split over two
bytes, the high part first, so k is the first byte times 256 plus the
second.</span>
</Formal>

## A machine made of software

A list of numbers does nothing on its own; something has to read the
numbers one after another and carry each out, and it needs to be no
more than a loop. Here is a complete one for three made-up opcodes
(it stores each value straight after its `PUSH`, rather than in a side
table as Drip's VM does):

`code` is `1 + 2 * 3` flattened, children first. `st` is the machine's
pile of waiting values (its stack, the subject of *A stack machine and
its dispatch loop*), and `ip` says where in `code` it has got to.
`code[ip++]` reads the opcode and moves `ip` on; a `PUSH` reads one more
byte, its operand, and pushes it; `ADD` and `MUL` pop the newest value
into `b`, the one under it into `a`, and push the result. When `ip` runs
off the end, `7` is the only value left:

<TinyVmSteps client:visible />

No recursion, no `kind` to switch on, no `Map`: a real processor does
the same with machine code, which is why this is a *virtual* machine.

<Callout kind="definition">
A **virtual machine** (VM) is a program that runs bytecode. It
repeatedly **fetches** the next instruction, **decodes** it (works out
from its opcode which instruction it is and how many operand bytes
follow), and **executes** it, keeping its working values in its own
data structures. Its instruction set is designed for one language, not
for any real chip.
</Callout>

<Analogy extra title="a player piano">
A player piano reads a paper roll row by row and presses the keys each
row says; the same mechanism plays any roll, knowing nothing about the
tune.
<span slot="breaks">A roll only moves forward; a VM can jump back (that
is how loops work) and can stop with an error.</span>
</Analogy>

<More title="The top of Drip’s real loop, and two more runnable examples">

```ts
for (;;) {
  this.instructionsExecuted++;
  const instruction = code[frame.ip++];
  switch (instruction) {
    // ...
    case Op.True: this.push(true); break;
    case Op.Pop: this.sp--; break;
```

The same shape: read the opcode at `ip`, move on, one `case` per
opcode; `for (;;)` never stops by itself, and the `return` instruction
ends it. The first example below adds `SUB` to the tiny machine, which
shows why the right operand is popped first; the second runs `fib` on
the real VM. Even a well-built interpreter keeps the costs of decoding
operands and jumping to the next instruction's code, which V8's
Sparkplug removes by compiling bytecode to machine code in one quick
pass<Cite id="v8-sparkplug" />; this book's VM stays an interpreter.

## What you learned

- In this book's run the VM was at most 1.3 times faster, and slower on
  four object-heavy programs: a better design is not faster at
  everything, and only measuring tells you.
- **Interpreter overhead** is the work the program did not ask for:
  dispatch, pointer chasing, `Map`s and allocation.
- **Bytecode** is the tree flattened once, children first, into numbered
  **opcodes** with operand bytes; a **virtual machine** is the loop that
  fetches, decodes and executes them.
