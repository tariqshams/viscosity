## Same pass, new home

The chapter "Finding collections" read the first two steps of
`analysis.ts`: find the **candidate** bindings (variables first given an
empty array or an array literal), then follow every load of each one
through its uses, accepting the few uses Viscosity can rewrite and
recording a **bailout** (a reason to leave the array alone) for anything
else. The TypeScript keeps all of this in local variables of one big
`analyze` function, and the steps are closures that share them. The Rust
port, `analysis.rs`, produces the same collections, the same bailouts and
the same messages in the same order; what changes is where the state
lives, and how one thing refers to another.

## The Analyzer struct

The TypeScript closures become methods of one struct, trimmed:

```rust
struct Analyzer<'m> {
    m: &'m Module,
    uses: Uses,
    stores: HashMap<BindingId,
        Vec<ValueId>>,
    loads: HashMap<BindingId,
        Vec<ValueId>>,
    call_sites: HashMap<FuncId,
        Vec<ValueId>>,
    collections: Vec<Collection>,
    collection_of_load:
        HashMap<ValueId, usize>,
    element_of: HashMap<ValueId, usize>,
    // ...numeric facts, a cfg cache
}
```

`m` borrows the module for the lifetime `'m` (the analyzer reads VIR and
never changes it); `uses` lists every use of every value; `stores` and
`loads` file each store and load by binding; `call_sites` lists the call
instructions of each **known function** (declared once and only ever
called directly, so every caller is visible); and the last three are the
collections and two maps into them. `HashMap` here is `FxHashMap` from the
`rustc-hash` crate, renamed on import: a faster hasher for small
keys<Cite id="rustc-hash-readme" />. Its iteration order is arbitrary,
which is fine, because the analyzer only *looks things up* in these maps;
anything whose order reaches `explain` is a `Vec` or an
`IndexMap`<Cite id="indexmap-docs" />. One more detail matters later:

```rust
fn inst(&self, v: ValueId) -> &'m Inst {
    self.m.inst(v)
}
```

The instruction lives in the module, so the reference handed out lasts
for `'m`, not for the borrow of `self`; you can hold an instruction and
still change `self.collections` (the next chapter shows the error you get
without this).

## Collections by number

<Analogy title="drawer numbers in a shared office">
In an office where several people share one cabinet, nobody may walk off
with a drawer, so they pass around drawer *numbers* instead: anyone with
"drawer 3" can open it, look inside and add a file, and the cabinet stays
where it is.
<span slot="breaks">If someone took a drawer out and the others slid
down, every number written on a note would be wrong. The analyzer only
ever adds collections to the end and never removes one, so the numbers
stay right.</span>
</Analogy>

In TypeScript, `collectionOfLoad` maps a value to the `Collection`
*object*. Rust's `collection_of_load` maps a value to a `usize`: the
collection's position in `self.collections`. A `&mut Collection` kept in
the map would keep the whole `Vec` borrowed for as long as the map exists,
and the pass pushes to that `Vec` and changes its entries all the time; a
number borrows nothing.

</Figure>

Finding candidates is otherwise a line-for-line port. Where the
TypeScript filters every store and checks the length, Rust stops at the
first store of an array, with `let`-`else` (rewrapped):

```rust
let st = self.stores_of(binding.id);
let Some(&first_array_store) =
    st.iter().find(|&&x| matches!(
        self.inst(self.inst(x).args[0]).op,
        Op::ArrayEmpty | Op::ArrayNew))
else {
    continue;
};
```

`stores_of` gives the binding's stores; `find` walks them and stops at the
first whose stored value (`args[0]`) is `array.empty` or `array.new`; and
if there is none, the `else` branch skips this binding. Every bailout then
goes through one helper, `Collection::bail`, which also remembers the
*first* source position seen for each message, for `explain --frames`.

## The worklist and the borrow checker

The second step, from `shapes_and_uses`, trimmed and rewrapped:

```rust
let mut work: Vec<ValueId> = self.loads
    .get(&self.collections[ci].binding)
    .cloned().unwrap_or_default();
while let Some(l) = work.pop() {
    for u in self.uses_of(l) {
        if let Some(follow) = self
            .use_of_collection(ci, l, u,
                &mut seen_param)
        {
            work.push(follow);
        }
    }
}
```

`work` starts as a copy of every load of collection `ci`'s binding (or
empty, if it has none). Each `pop` takes a value off the end; each of its
uses goes to `use_of_collection`, which accepts it (`.length`, a `push` of
a fresh record, an index), records a bailout, or, for a call to a known
function that every caller passes this collection to, returns that
function's parameter, which goes on the stack so that the uses *inside*
the function are checked too.

Two things differ from the TypeScript. The TypeScript closure pushes the
parameter itself, while `use_of_collection` *returns* it, because it takes
`&mut self` and the stack is a local variable of its caller. And
`uses_of(l)` returns a *copy* of the use list. Write `self.uses.of(l)` in
the `for` instead, and the loop holds a shared borrow of `self` while its
body calls a `&mut self` method; rustc 1.97, on a small copy:

```
error[E0502]: cannot borrow `*self` as
  mutable because it is also borrowed
  as immutable
```

The copy costs a few words per use, and it is the simplest thing that lets
the method change `self` freely. Try both versions:

## Order is output

<Analogy title="a pile of letters">
Letters arrive and you drop each on a pile; when you sit down to answer
them, you take the top one, which is the last to arrive. The order of your
replies is the reverse of the order the letters came in.
<span slot="breaks">With letters the order of replies rarely matters.
Here it is printed: it decides the order of the explain messages and even
which record's fields come first.</span>
</Analogy>

<Callout kind="definition">
**The collection pass in Rust** is steps 1 and 2 of `analysis.rs`.
`find_collections` files every load and store by binding, finds the known
functions, and makes a `Collection` for each `const` or `let` whose first
array store is `array.empty` or `array.new`. `shapes_and_uses` then runs a
stack-ordered worklist over each collection's loads, accepting `.length`,
`push` of a fresh record, indexing, and known calls (followed into the
parameter), and records a bailout, with its source site, for anything
else.
</Callout>

<Formal title="What the pass computes">

```text
refs(c) = loads(c) ∪ { param(f, k) |
  every call of f passes c at k }
ok(c) ⟺ ∀ r ∈ refs(c), ∀ u ∈ uses(r):
  u ∈ {.length, push(fresh), [i],
       known call}
```

<span slot="read">The values that refer to collection c are the loads of
its name, plus the k-th parameter of any known function f that every
caller passes c to as its k-th argument. The collection survives this
pass only if every use of every one of those values is a length read, a
push of a fresh record, an index, or such a known call; any other use is
a bailout.</span>
</Formal>

All three are real Rust CLI output, wrapped. The first is the simplest:
`const ps = []` and a loop of `ps.push({ x: i })`, nothing else; the pass
accepts every use and the collection is found, and only the cost model,
later, says no. The second adds `ps.sort()`, and one line gives two
bailouts, because the pass checks *every* use: the read of `.sort` is one,
and passing the array to the method call (as its receiver) is another.
The third is the `step` program of the diagram, trimmed: `ps` is followed
into `step`'s parameter, and the loop there is what pays off.

<Callout kind="engine" label="Under the hood">
Why a stack, when a queue would find the same collections and the same
bailouts? Because the parity test compares the order too: 190 of 190
fixture pairs match byte for byte, and the fuzzer compares both engines'
`explain` and `explain --frames` text on random programs. `seen_param`
stops a parameter being followed twice when two call sites pass the
collection; however, a function that passes its parameter on to itself,
`walk(qs, k + 1)`, is not followed, and both engines report "passed to
walk(), which is also called with other values". That refusal is safe,
only less precise than it could be.
</Callout>

## What you learned

- **The collection pass in Rust** keeps the TypeScript closures' state in
  `Analyzer<'m>`, with `inst` returning `&'m Inst`, so instructions do
  not borrow the analyzer.
- Collections are referred to by **index** (`usize`), never by reference,
  so the `Vec` of collections can keep changing.
- `uses_of` copies the use list so that the loop body can call `&mut self`
  methods (E0502 otherwise).
- The worklist is a stack, as in the reference: the last load first.
  Known functions are followed by returning the parameter.
