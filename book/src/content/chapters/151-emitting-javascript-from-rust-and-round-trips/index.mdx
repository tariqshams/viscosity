## Change only what you must

*Emitting JavaScript, and round-trip testing* faced a choice: print the
whole program again from the IR, or edit the original text. Viscosity
edits. Here is the corpus program `sequence_value.js` before and after,
as the Rust CLI built it here (the container class above it is left out,
and the loop header is wrapped to fit):

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, y: (i, i + 1) });
```

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 100; i++)
  ps.push(i, (i, i + 1));
```

The array became a container of columns and the pushed object its
values; everything else is copied byte for byte, comments and odd
formatting included, which is what lets a test demand byte-identical
output from two engines, the second half of this chapter.

## A list of edits

`emit.rs` walks the plan as `emit.ts` does, and each step records an
**edit** without changing anything yet: a `struct Edit` holding a byte
range `start..end` of the original source (an insertion when the two are
equal), the `text` to put there, and a `rank` that orders insertions at
one position. Then it applies them all, and the order is the whole
trick:

<EditSteps client:visible />

<Analogy title="correction tape, from the bottom up">
Correcting a printed page with correction tape, you start at the bottom:
a correction near the bottom can make that line longer or shorter, but
every line above it is still exactly where your list of corrections
says it is.
<span slot="breaks">On paper two corrections can overlap and you
tape over both; the emitter treats an overlap as a bug in itself and
stops with an internal error.</span>
</Analogy>

Here is the real loop, from the end of `emit_js` (rewrapped, the error
message shortened to `overlap(e)`):

```rust
edits.sort_by_key(|e| {
    let back = Reverse(e.start);
    (back, Reverse(e.end), e.rank)
});
let mut out = source.to_string();
let mut last_start = u32::MAX;
for e in &edits {
    if e.end > last_start {
        return Err(overlap(e));
    }
    out.replace_range(
        e.start as usize..e.end as usize,
        &e.text);
    last_start = e.start;
}
```

The sort puts the largest `start` first (`Reverse` flips the order);
`last_start` remembers where the previously applied edit began, starting
from the largest `u32`; an edit that ends past that point would cut into
text already replaced, so it is an error; otherwise `replace_range`
swaps the bytes in place, moving only the text after them. The sort is
**stable**, so edits with equal keys keep the order they were added in,
as `Array.prototype.sort` does in the TypeScript
engine<Cite id="rust-std-slice-sort-by-key" /><Cite id="ecma262-sort-stable" />;
and a bad byte offset cannot quietly corrupt the text, because
`replace_range` panics off a character
boundary<Cite id="rust-std-string-replace-range" />.

<Formal title="Why back to front is safe">

```text
s₁ ≥ s₂ ≥ … ≥ sₙ     eᵢ₊₁ ≤ sᵢ
apply(i) changes only bytes ≥ sᵢ
⇒ edit i+1's range is still original
```

<span slot="read">Sort the edits so their starts go down, and require
each edit to end no later than the previous one started. Applying edit
i only changes text from its own start onwards, so the next edit, which
lies wholly before that start, still finds the original text at the
offsets it was given.</span>
</Formal>

## Writing text

The edits' texts and the container classes are built with `format!` and
`join`, like the TypeScript template literals. `format!` is itself a
writer: it makes a `String` and calls `write_fmt` on
it<Cite id="rust-std-fmt-write" />, and `write!` and `writeln!` call
that machinery on a `String` of your own.

<Callout kind="definition">
**`std::fmt::Write`** is the trait for anything that accepts formatted
UTF-8 text. Its one required method is `write_str(&mut self, s: &str)
-> fmt::Result`; `write_char` and `write_fmt` have defaults.
**`write!(w, ...)`** and **`writeln!`** format into any `w` with a
`write_fmt` method. `String` implements `fmt::Write`, and `format!` is
`write!` into a fresh `String`. The trait must be in scope (`use
std::fmt::Write;`). Byte streams such as files use the different trait
`std::io::Write`.
</Callout>

<Examples of="rust-codegen">

```rust
let mut s = String::new();
writeln!(s, "class {cls} {{").unwrap();
// error[E0599]: cannot write into
//   `String` ... help: trait `Write`
//   ... is implemented but not in scope
use std::fmt::Write; // the fix
```

</Examples>

`writeln!` into a `String` fails with E0599 (rustc 1.97's message,
trimmed) until the trait is imported, because `write_fmt` is a trait
method, and a trait's methods can only be called while the trait is in
scope. With the `use` in place, `{cls}` takes the variable `cls` into
the text, `{{` writes a literal `{` (braces are doubled to escape them),
and `writeln!` adds the line break. The `.unwrap()` is safe, because
`String`'s implementation calls `push_str` and returns
`Ok(())`<Cite id="rust-std-fmt-write" />; `write!` still returns a
`Result` because other writers, such as a file on a full disk, can fail.

## Writing the answer key

Now the promise those byte-for-byte edits make possible: for every test
program, the Rust port produces **the same bytes** as the TypeScript
engine, code and `explain` text alike. `scripts/gen_expected.mjs` runs
the TypeScript compiler (with Node) over every test program, once with
the default options and once with `bounds: 'assume'` (no bounds checks,
a path the default never reaches), and writes the code and explain text
of each run into `tests/expected`; those **fixtures** (stored, expected
outputs) are committed.

<Figure caption="What gen_expected.mjs writes for one program, and the totals in tests/expected." takeaway="One program, two variants, two files each.">
  <FixtureFan />
</Figure>

When the TypeScript engine changes on purpose, someone runs the script
again and reads the diff before committing it, so every change to the
expected output is seen by a person.

<Analogy extra title="tracing paper over a master drawing">
An art student copies a drawing by laying tracing paper over it; to
check the copy, you put it back over the original and hold both up to a
window, and any line that does not sit exactly on its twin shows at
once.
<span slot="breaks">Lining up perfectly says nothing about whether the
original was a good drawing; two compilers can agree on a wrong answer,
which is why a second test runs the programs.</span>
</Analogy>

## Marking the Rust engine

`crates/cli/tests/parity.rs` is a Cargo **integration test** (a file in
`tests/` that uses the crates from outside, as a user would). Its main
test, trimmed and rewrapped:

```rust
for p in programs() {
    for (suffix, bounds) in VARIANTS {
        let name =
            format!("{}{suffix}", p.name);
        let (want_code, want_explain) =
            expected(&p, &name);
        let r = p.compile(bounds);
        if r.code != want_code {
            failures.push(/* where */);
        }
        if r.explain != want_explain {
            failures.push(/* where */);
        }
    }
}
```

For each program and bounds variant, `expected` reads the two fixture
files, `p.compile` runs the Rust engine, and each `!=` compares two
`String`s byte for byte. A mismatch is pushed onto `failures` with the
first line that differs (*The Rust workspace* wrote that helper), so one
run lists every difference, and one `assert!` after the loops fails if
the list is not empty. Other tests in the file check that no fixture is
missing or left over, and run the built binary, which Cargo locates
through `CARGO_BIN_EXE_viscosity`<Cite id="cargo-targets" />. Here, with
rustc 1.97, all ten passed, and the main one printed `parity: 190/190
(54 Python)`.

<Callout kind="definition">
A **cross-implementation test** runs two implementations of the same
specification on the same inputs and requires the same outputs. One is
the **reference**; its outputs are stored as **fixtures** by a generator
script, and the new implementation is compared with them **byte for
byte**, for every program and every option variant, with a check that no
fixture is missing or stale.
</Callout>

## Equal bytes, wrong together

Two engines can agree on a wrong answer, so `differential.rs` checks
behaviour too: it runs each original and compiled JavaScript program
with `node`, in an isolated context, and compares everything printed and
thrown. To see both tests catch a real mistake, I deleted one line from
a copy of `crates/core/src/builder.rs` (the line that rewrites a `throw`
when a trivial phi is removed, which *Dominators, SSA and dataflow in
Rust* explains):

<Examples of="cross-implementation-tests">

```
4 of 190 differ:
corpus_throw_from_loop.explain.txt:
  line 1:
  want: ps (line 3) {x} → kept as
        array of objects
  got:  ps (line 3) {x} → struct of
        arrays
```

</Examples>

This is parity's report, trimmed and wrapped: four files differ, all
from `throw_from_loop.js` (code and explain, both variants), and the
entry names the fixture, the first differing line and both versions of
it. The reference keeps `ps` as objects, because an element is thrown
out of the loop; the broken port makes columns. The differential test
says why that matters: the original prints `object 1`, the compiled
program `number undefined`, since it throws an index.

<More title="More: what parity forces, and a cross-implementation test to run">

Matching decisions is not enough, because `explain` lists reasons in
the order the analyses find them. So the port copies the reference's
*order* as well: `IndexMap` where TypeScript uses a `Map`, stable sorts,
use lists with duplicates, and `vir::js_number` for numbers in text.
This runnable example is a tiny cross-implementation test: five numbers,
how JavaScript's `String(x)` writes them (captured once, like fixtures),
and how Rust's `{}` writes them.

## What you learned

- Viscosity emits by **range edits** on the original source, sorted by
  start, last first, with a **stable** sort, and applied with
  `replace_range`; an edit that ends past the previous start is an
  internal error.
- **`fmt::Write`** (`write!`, `writeln!`) appends formatted text to a
  `String`; `format!` is the same machinery. Remember `use
  std::fmt::Write;`.
- A **cross-implementation test** holds the Rust engine to fixtures the
  TypeScript engine wrote, byte for byte, 190 pairs today; a
  **differential test** beside it checks that the programs still behave
  the same.
