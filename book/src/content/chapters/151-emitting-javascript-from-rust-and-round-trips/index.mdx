## Change only what you must

*Emitting JavaScript* faced a choice: print the whole program again
from the IR, or edit the original text. Viscosity edits. Here is the
corpus program `sequence_value.js` before and after, as the Rust CLI
built it here (the container class above it is left out, and the loop
header is wrapped to fit):

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, y: (i, i + 1) });
```

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 100; i++)
  ps.push(i, (i, i + 1));
```

The array became a container of columns, and the pushed object became
its values; everything not rewritten is copied byte for byte, comments,
spacing and odd formatting included. That makes the output easy to read
and review, and it is what lets a test demand byte-identical output from
two engines (*Round-trip tests across engines*).

## A list of edits

`emit.rs` walks the plan as `emit.ts` does (first each collection's
creation, then each `push`, then element reads, then field accesses),
and each step records an **edit** without changing anything yet (from
`emit.rs`, comments shortened):

```rust
// Replace start..end with text
// (an insertion when they are equal).
struct Edit {
    start: u32,
    end: u32,
    text: String,
    rank: u32, // orders insertions
}
```

Then it applies them all, and the order is the whole trick:

<EditSteps client:visible />

<Analogy title="correction tape, from the bottom up">
Correcting a printed page with correction tape, you start at the bottom:
a correction near the bottom can make that line longer or shorter, but
every line above it is still exactly where your list of corrections
says it is.
<span slot="breaks">On paper two corrections can overlap and you
tape over both; the emitter treats an overlap as a bug in itself and
stops with an internal error.</span>
</Analogy>

Here is the real loop, from the end of `emit_js` (rewrapped, the error
message shortened to `overlap(e)`):

```rust
edits.sort_by_key(|e| {
    let back = Reverse(e.start);
    (back, Reverse(e.end), e.rank)
});
let mut out = source.to_string();
let mut last_start = u32::MAX;
for e in &edits {
    if e.end > last_start {
        return Err(overlap(e));
    }
    out.replace_range(
        e.start as usize..e.end as usize,
        &e.text);
    last_start = e.start;
}
```

The sort puts the largest `start` first (`Reverse` flips the order);
`last_start` remembers where the previously applied edit began, starting
from the largest `u32`; an edit that ends past that point would cut
into text already replaced, so it is an error; otherwise
`replace_range` swaps the bytes in place, moving only the text after
them. The rest of the sort key matters because the real emitter does
not replace `{ x: i, y: ... }` in one piece: it deletes the text
*around* each value, so a value that itself needs rewriting gets its own
edit, and edits meet at the same byte. At one position the longer
replacement goes first, and insertions go by `rank`.

<Formal title="Why back to front is safe">

```text
s₁ ≥ s₂ ≥ … ≥ sₙ     eᵢ₊₁ ≤ sᵢ
apply(i) changes only bytes ≥ sᵢ
⇒ edit i+1's range is still original
```

<span slot="read">Sort the edits so their starts go down, and require
each edit to end no later than the previous one started. Applying edit
i only changes text from its own start onwards, so the next edit, which
lies wholly before that start, still finds the original text at the
offsets it was given.</span>
</Formal>

The TypeScript version sorts on the same three keys and rebuilds the
string for each edit, `out = out.slice(0, e.start) + e.text +
out.slice(e.end)`. Both sorts are **stable**, so edits with equal keys
keep the order they were added in: Rust documents that for
`sort_by_key`<Cite id="rust-std-slice-sort-by-key" />, and ECMAScript
has required it of `Array.prototype.sort` since
2019<Cite id="ecma262-sort-stable" />. That matters, because both
engines must apply ties in the same order.

The offsets are oxc's UTF-8 byte offsets, sliced against a Rust
`String`, while the TypeScript engine slices its UTF-16 string with
acorn's offsets; as *Parsing with oxc* showed, each engine uses its own
unit on its own string, so both cut at the same characters and the port
never converts. A wrong offset cannot quietly corrupt the text either:
`replace_range` panics if a range does not fall on character
boundaries<Cite id="rust-std-string-replace-range" />, and replacing
`1..2` of `"é"` stops with `start of range should be a character
boundary`.

## Writing text

The edits' texts, and the container classes that go above the code, are
built with `format!` and `join`, line for line like the TypeScript
template literals and `join('\n')`. `format!` is itself a writer: the
standard library makes a `String` with a capacity estimate and calls
`write_fmt` on it<Cite id="rust-std-fmt-write" />, and you can call
that machinery yourself to append to one growing `String`, through the
trait `std::fmt::Write` and the macros `write!` and `writeln!`.

<Analogy extra title="a guest book">
`format!` hands each guest a fresh card and collects the cards
afterwards; `write!` passes round one guest book, and everyone writes
on the next free line of the same book.
<span slot="breaks">A guest book can run out of pages; a `String`
grows, which is why writing into one never fails, although `write!`
still returns a result, because other writers (a file, a full disk)
can.</span>
</Analogy>

<Callout kind="definition">
**`std::fmt::Write`** is the trait for anything that accepts formatted
UTF-8 text. Its one required method is `write_str(&mut self, s: &str)
-> fmt::Result`; `write_char` and `write_fmt` have defaults.
**`write!(w, ...)`** and **`writeln!`** format into any `w` with a
`write_fmt` method. `String` implements `fmt::Write`, and `format!` is
`write!` into a fresh `String`. The trait must be in scope (`use
std::fmt::Write;`). Byte streams such as files use the different trait
`std::io::Write`.
</Callout>

<Figure takeaway="One macro, two traits: text or bytes." caption="write! calls the writer's write_fmt. For a String that method comes from std::fmt::Write; for a file or stdout it comes from std::io::Write. The CLI prints with writeln!(stdout, ...) and use std::io::Write.">
  <TwoWrites />
</Figure>

<Examples of="rust-codegen">

```rust
let c = "x";
let s = format!("this.{c} = []");
// "this.x = []"
```

```rust
let mut s = String::new();
writeln!(s, "class {cls} {{").unwrap();
// error[E0599]: cannot write into
//   `String` ... help: trait `Write`
//   ... is implemented but not in scope
use std::fmt::Write; // the fix
```

```rust
let params = (0..f)
    .map(|i| format!("v{i}"))
    .collect::<Vec<_>>()
    .join(", ");
// f = 2: "v0, v1"
```

</Examples>

The first is the simplest piece of code generation: `{c}` takes the
variable `c` straight into the text. The second is the spot the
difference: `writeln!` into a `String` fails with E0599 until the
trait is imported (rustc 1.97's message, trimmed), and then `{{` writes
a literal `{`, since braces are doubled to escape them. `.unwrap()` is
safe here, because `String`'s implementation calls `push_str` and
returns `Ok(())`<Cite id="rust-std-fmt-write" />. The third is real,
from `container_class` in `emit.rs` (rewrapped): it builds the
parameter list of the container's `push` method, one `v0`, `v1`, ... per
field, joined with commas, exactly as the TypeScript template does.

<Callout kind="engine" label="Under the hood">
The container classes go after any shebang line and leading `"use

nothing. The parity work also found a splicing bug in the reference: in
`push({ y: (a, b) })` the value was copied without its parentheses (a
sequence expression's span excludes them), so the comma split the
arguments and `y` received `a`. Both engines now put the parentheses
back, which is the program at the top of this chapter.
</Callout>

## What you learned

- Viscosity emits by **range edits** on the original source; everything
  outside them is copied byte for byte.
- Edits are **sorted by start, last first**, and applied with
  `replace_range`, so earlier offsets stay valid. An edit that ends past
  the previous start overlaps, and is an internal error.
- The sort is **stable** in both engines, so ties apply in the same
  order, and a bad byte offset panics instead of corrupting text.
- **`fmt::Write`** (`write!`, `writeln!`) appends formatted text to a
  `String`; `format!` is the same machinery. Remember `use
  std::fmt::Write;`.

## Two engines, one answer

The book's Playground can compile your program with the TypeScript engine
or with the Rust engine (built to WebAssembly), and the command line has
both as well; so imagine you paste a program in, switch engines, and the
explain text changes from "struct of arrays" to "kept as array of
objects". Which do you believe? Two compilers that *mostly* agree are
worse than one, because nobody can tell which answer is real. As such the Rust port makes
a very strong promise, which is that for every test program it produces
**the same bytes** as the TypeScript engine (the same JavaScript or Python,
and the same `explain` text, down to the last space), and this chapter is
about how that promise is checked.

<Analogy title="tracing paper over a master drawing">
An art student copies a drawing by laying tracing paper over it; to check
the copy, you put it back over the original and hold both up to a window,
and any line that does not sit exactly on its twin shows at once. The
TypeScript engine's output is the original drawing, and the Rust output is
the copy.
<span slot="breaks">Lining up perfectly says nothing about whether the
original was a good drawing; two compilers can agree on a wrong answer,
which is why a second test (below) runs the programs. And here the
original sometimes turns out to have the mistake.</span>
</Analogy>

<Analogy extra title="an answer key">
A teacher writes the answer key once and marks every new student's paper
against it, without solving each question again. The answers the
TypeScript engine gives are written down once, as files, and the Rust
engine's answers are marked against those files on every test run.
<span slot="breaks">In school, the key is always right. Here, when a
student's answer disagrees, someone checks by hand, and ten times the key
itself was wrong and was corrected.</span>
</Analogy>

## Writing the answer key

The script `engine/rust/scripts/gen_expected.mjs` imports the TypeScript
compiler (with Node, which can run TypeScript files directly) and runs it
over six groups of programs: the reference's JavaScript test programs, the
end-to-end benchmarks, extra programs written for the port, and the same
three for Python. Each program is compiled twice; here is the JavaScript
loop, trimmed (two lines that write the extra files below are left out)
and rewrapped to fit:

```js
for (const [suffix, extra] of [['', {}],
    ['.assume', { bounds: 'assume' }]]) {
  const r = compile(src, jsPlugin(), {
    ...(optIn ? { mode: 'opt-in' } : {}),
    ...extra });
  writeFileSync(join(out,
    `${base}${suffix}.js`), r.code);
  writeFileSync(join(out,
    `${base}${suffix}.explain.txt`),
    r.explain);
}
```

The first two lines loop over two **variants**: no suffix and no extra
options, then the suffix `.assume` with `bounds: 'assume'`, which tells
the code generator to skip bounds checks (a path the default never
reaches, so it needs its own test). The next three lines compile the
source `src`, switching to opt-in mode when the program's first comment
asks for it. The last two calls write the compiled code and the explain
text into `tests/expected`, under the program's name plus the suffix.
Those files are called **fixtures** (stored, expected outputs), and they
are committed to the repository.

</Figure>

Counting the folder today: 68 JavaScript programs and 27 Python ones, 95

purpose, someone runs the script again and reads the diff before
committing it, so every change to the expected output is seen by a person.

## Marking the Rust engine

`crates/cli/tests/parity.rs` is a Cargo **integration test** (a test file
in `tests/` that uses the crates from outside, as a user would). Its main
test is the same loop in Rust, trimmed and rewrapped:

```rust
for p in programs() {
    for (suffix, bounds) in VARIANTS {
        total += 1;
        let name =
            format!("{}{suffix}", p.name);
        let (want_code, want_explain) =
            expected(&p, &name);
        let r = p.compile(bounds);
        if r.code != want_code {
            failures.push(/* where */);
        }
        if r.explain != want_explain {
            failures.push(/* where */);
        }
    }
}
```

`programs()` lists the same six groups, and `VARIANTS` is the pair
`("", Bounds::Check)` and `(".assume", Bounds::Assume)`. For each program
and variant, `expected` reads the two fixture files, `p.compile` runs the
Rust engine, and each `!=` compares two `String`s byte for byte. A
mismatch is not a panic straight away: it is pushed onto `failures` with a
note of where the texts first differ (your exercise), so that one run
lists every difference. After the loops, one `assert!` fails if the list
is not empty. On my run here (rustc 1.97, `cargo test --workspace
--release`, all 77 tests passing), the test printed:

```
parity: 190/190 (54 Python)
```

The same file has nine more tests: `fixtures_match_the_programs_exactly`
checks that the fixture folder
matches the programs exactly (none missing, and none left over from a
deleted program, which nobody would check), others cover the `--frames`
and `--profile` fixtures, and one runs the built `viscosity` binary (Cargo tells a test where the binary is through the
variable `CARGO_BIN_EXE_viscosity`<Cite id="cargo-targets" />).

<ParitySteps client:visible />

<Callout kind="definition">
A **cross-implementation test** runs two implementations of the same
specification on the same inputs and requires the same outputs. One is
the **reference**; its outputs are stored as **fixtures** by a generator
script, and the new implementation is compared with them **byte for
byte**, for every program and every option variant, with a check that no
fixture is missing or stale.
</Callout>

<Formal title="What parity promises">

```text
∀ p ∈ Programs, ∀ v ∈ {check, assume}:
  rust(p, v) = fixture(p, v) = ts(p, v)
```

<span slot="read">For every program p and both bounds variants v, the Rust
engine's output for p under v equals the stored fixture, which is the
TypeScript engine's output; "equals" means the same bytes, both for the
code and for the explain text.</span>
</Formal>

## Equal bytes, wrong together

Two engines can agree on a wrong answer, so `differential.rs` checks
behaviour: it runs each original and compiled JavaScript program with
`node` (in an isolated context, using a copy of the TypeScript test
runner) and compares everything printed and thrown, and it runs the Python
ones with `python3`. *Differential testing at scale* built this
test for the TypeScript engine; here it ran 68 of 68 JavaScript and 27 of
27 Python programs identically. To see both tests catch a real mistake, I
deleted one line from a copy of `crates/core/src/builder.rs` (the line
that rewrites a `throw` when a phi is removed, which the chapter

## What parity forces

Matching decisions is not enough, because `explain` lists reasons in the
order the analyses find them, and the code generator applies its edits in
the order the plan is walked. So the port copies the reference's *order*
as well: a JavaScript `Map` iterates in insertion order, so where the
TypeScript uses one, the port uses `IndexMap` (a Rust map that remembers
insertion order; a plain `HashMap` gives an arbitrary one); sorts are
stable (equal items keep their order); and numbers in text go through
`vir::js_number`, which follows JavaScript's own algorithm, so `1e21` is
written `1e+21` rather than Rust's twenty-two digits.

## When the key was wrong

When two engines disagree, the obvious suspect is the newcomer; however,
the port's README lists ten bugs it turned up in the TypeScript engine,
each fixed in both engines and pinned by a test program. Three were
**miscompiles** (the compiled program behaved differently), including the
`throw` above; others were crashes, or quieter slips such as shapes
compared by joined names (see *Shape inference in Rust*). One shows well
what a second implementation catches: past the end of a string,
JavaScript's `src[i]` is `undefined`, and a regular-expression test turns
that into the text `"undefined"`, which contains an `e`, so a `1` at the
very end of a Python file looked like a float; Rust's `s.get(k)` gives no
character at all, and the two engines disagreed.

## What you learned

- A **cross-implementation test** holds a new engine to a reference: the
  same inputs, byte-identical outputs.
- `gen_expected.mjs` writes the reference's **fixtures** (two variants
  per program, 190 pairs today); `parity.rs` compares the Rust engine with
  them on every `cargo test`, and checks for missing or stale files.
- Equal bytes can be wrong together, so a **differential test** runs
  both programs with `node` and `python3`.
- Byte parity forces the reference's **order**: `IndexMap`, stable sorts,
  and JavaScript's number formatting.
- The disagreements found **ten bugs in the reference**, fixed in both
  engines.
