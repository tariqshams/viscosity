## The same loop, a different switch

The dispatch loop of *The dispatch loop*, as it stands in
`companion/ts/src/vm/vm.ts` (trimmed and rewrapped):

```ts
for (;;) {
  const instruction = code[frame.ip++];
  switch (instruction) {
    case Op.None: this.push(null); break;
    // ... 52 more cases
    default:
      throw new Error(
        `unknown opcode ${instruction}`);
  }
}
```

And here is the top of drip-rs's, from `run` in `src/vm.rs` (rewrapped):

```rust
loop {
    let byte = self.read_byte();
    let op = OpCode::from_byte(byte).expect(
        "the compiler emits valid opcodes");
    match op {
        // one arm per opcode: 53 in all
    }
}
```

The shape is the same: read a byte, decode it, run the code for that
instruction, repeat. Two lines differ. `from_byte` (from the chapter
*Bytecode and instructions in Rust*) turns the byte into an `OpCode`, and
gives `None` for a byte no opcode has; and the `match` has no `default`.

<Analogy title="a receptionist and an architect">
A switch with a default case is a receptionist who says "not my
department" to any visitor nobody expected. A match over an enum is a
building whose doors the architect counted before it was built: if a
door has no room behind it, the building does not open.
<span slot="breaks">A building's plans can still be wrong in ways nobody
counted; the compiler only checks that every opcode *has* an arm, not that
the arm does the right thing, which is what the corpus tests are for.</span>
</Analogy>

<Analogy title="a seating plan">
A wedding planner checks, the week before, that every guest has a seat;
on the day, the only surprise left is someone who was never on the list,
and they are stopped at the door. The exhaustive
`match` is the seating plan, and `from_byte` is the door.
<span slot="breaks">A planner can let a stranger in out of kindness;
drip-rs treats a byte that is not an opcode as a bug in its own compiler,
and `expect` stops the program loudly.</span>
</Analogy>

## No default case

The match is over `OpCode`, an enum with 53 variants, and a Rust match
must be exhaustive<Cite id="klabnik2026" />: every possible value must be
covered by some arm. Add a 54th opcode and forget its arm, and the VM no
longer compiles. In TypeScript the same slip would surface only when a
program ran the new instruction and fell into `default`.

<Callout kind="definition">
**Match-based dispatch**: the loop decodes each byte into an opcode enum
and runs one `match` over it, with one arm per instruction. Because the
match must be exhaustive, every opcode is guaranteed a handler at compile
time, and the only unchecked step left is decoding the byte.
</Callout>

<Examples of="match-dispatch">

```rust
OpCode::None => self.push(Value::None),
```

```rust
OpCode::Sub => {
    let (a, b) = self.pop_numbers("-")?;
    self.push(Value::Number(a - b));
}
```

```rust
OpCode::JumpUnless => {
    let offset = self.read_short();
    if self.pop().is_falsey() {
        self.ip += offset;
    }
}
```

```text
// with one arm left out (rustc 1.97):
error[E0004]: non-exhaustive patterns:
  `OpCode::False` not covered
```

</Examples>

The first arm (de-indented from `vm.rs`, like the others) is the simplest
there is: push `none`. The second can
fail: `pop_numbers` checks that the top two values are numbers, and the
`?` sends any error straight out of `run` (more on that next); otherwise
it pushes the difference. The third is what an `if` compiles to: it reads
a two-byte jump distance, pops the condition, and if the condition is
falsey it moves the instruction pointer forward, so the next turn of the
loop reads a different byte. The fourth is the spot-the-difference: delete
the `False` arm and this is the error, naming the arm you forgot.

<Formal title="Two arms as rules">

```text
code[ip] = True
──────────────────────────────
⟨ip, S⟩ → ⟨ip + 1, S · true⟩

code[ip] = Sub   S = S′ · a · b
      a, b numbers
──────────────────────────────
⟨ip, S⟩ → ⟨ip + 1, S′ · (a − b)⟩
```

<span slot="read">Read each rule from the top down. The first says: if
the byte at ip is True, a machine whose instruction pointer is ip and whose
stack is S steps to one whose instruction pointer is one further on and
whose stack has true pushed on top. The second says: if the byte is Sub,
and the stack is some S′ with a and then b on top, and both are numbers,
then the machine steps to the next instruction with a and b replaced by
a − b. Each arm of the match is one such rule; when no rule applies (b is
a string, say), the VM reports a runtime error.</span>
</Formal>

## Errors are returned, not thrown

The TypeScript VM's `runtimeError` throws, and `interpret` catches it.
drip-rs returns errors as values instead: `run` returns `Run`, defined as
`type Run<T = ()> = Result<T, RuntimeError>;`, and an arm that can fail
uses `?`, so the error leaves `run` at once. The heart of `pop_numbers`
(trimmed and rewrapped):

```rust
let (Value::Number(a), Value::Number(b)) =
    (self.peek(1), self.peek(0))
else {
    // ... build the message, then:
    return Err(self.runtime_error(message));
};
self.stack.truncate(self.stack.len() - 2);
Ok((a, b))
```

That is a `let ... else`: if the pattern does not match, the `else` block
runs, and it must leave the function. `RuntimeError` carries no data,
because `runtime_error` has already written the message and the stack
trace by the time it returns one; running `print "hi" - 1;` prints
`runtime error: cannot use '-' on a string and a number` and
`  at line 1 in script`, and exits with 70, exactly as the TypeScript VM
does.

## The loop cannot hold the chunk

The TypeScript loop starts by caching the running frame's code in local
variables, `frame`, `code` and `constants`, and calls `reload()` after
every call and return. Try that in Rust, on a toy VM:

```rust
fn run(&mut self) {
    let code = &self.code;
    for &b in code {
        self.push(b as f64);
    }
}
```

rustc 1.97 refuses with `error[E0502]: cannot borrow *self as mutable
because it is also borrowed as immutable`. `self.push` needs `&mut self`,
all of the VM, `code` included, and a shared borrow of a field cannot
overlap a mutable borrow of the whole (*Borrowing*). The borrow checker is
right, too: in drip-rs the chunk belongs to an `ObjFunction` in the heap's
arena, and allocating can grow that arena's `Vec` and move every object in
it, so a reference into it could dangle.

So drip-rs keeps no long-lived reference at all. It copies the running
frame's state into fields of the `Vm`, which its comments compare to a
CPU's **registers** (from `vm.rs`, comments left out):

```rust
pub struct Vm {
    pub heap: Heap,
    stack: Vec<Value>,
    frames: Vec<CallFrame>,
    ip: usize,
    chunk: Rc<Chunk>,
    slots: usize,
    // ... globals, upvalues, output
}

fn read_byte(&mut self) -> u8 {
    let byte = self.chunk.code[self.ip];
    self.ip += 1;
    byte
}
```

</Figure>

Each read borrows `self` for one expression, and the borrow is over before
`push` runs; try it on a toy VM built the same way:

<Run id="registers" />

 The chunk is behind an `Rc` (*Box, Rc and RefCell*) because
several owners need it at once, and cloning an `Rc` only bumps a count;
the compiler freezes each chunk when its function is done, so it never
changes and needs no `RefCell`. `call` saves the caller's `ip` into its
frame and loads the callee's `ip`, chunk and slots into the registers;
`pop_frame` loads the caller's back. This matters more than it looks,
because every instruction reads at least one byte, so the cost of reaching
that byte (one field read here, rather than a walk from the frame through
the heap) is paid on every turn of the loop.

price is bookkeeping: `call`, `pop_frame` and `runtime_error` must all
read or write them explicitly.

## What you learned

- **Match-based dispatch**: decode the byte with `from_byte`, then one
  exhaustive `match` with an arm per opcode. A forgotten opcode is a
  compile error (E0004), not a `default` case.
- Runtime errors are `Result` values: arms use `?`, and `let ... else`
  handles operands of the wrong type.
- The loop cannot keep `&self.chunk` across `self.push`: a shared and a
  mutable borrow would overlap, and the arena could move.
- **Registers**: `ip`, `chunk: Rc<Chunk>` and `slots` are fields of the
  `Vm`, synced with the frame on calls and returns.
