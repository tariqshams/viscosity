## The numbers, as they came out

Part IV began with a promise, in the chapter "Why bytecode?": flatten
the tree into a compact list of instructions, run them in one tight
loop, and the interpreter gets faster. The companion's benchmark script
runs ten Drip programs on both engines, each in a fresh process, and
keeps the best of three runs. Here is the most recent result:

<VmVsTreeChart />

The best the VM manages is 1.3 times faster (`method_calls`), and on
four programs (`fields`, `instantiation`, `strings` and `trees`) it is
*slower* than the tree-walker. That is not the textbook result, and it
is worth saying plainly why, because the reasons are about where the
program runs, not about bytecode being a bad idea.

## Why so little

**Both engines are JavaScript, and V8 compiles both.** In C, a
tree-walker pays for chasing pointers between scattered nodes and for
deciding what each node is, and a bytecode loop removes most of that.
Here, both engines are JavaScript programs run by V8, which watches
which functions are hot and compiles them to machine code with its
optimising tiers<Cite id="v8-maglev" />. The tree-walker's
`evaluate` methods get that treatment as well as the VM's `run` loop,
so the tree-walker is far from the slow, naive interpreter the
argument assumed. On the simplest loop there is, three million passes
of `for i in 0..3000000 { s += i; }`, the tree-walker was faster in my
runs: its best was 653 ms against the VM's 814 ms.

<Run id="time-loop" />

That is the same loop, a tenth as long, so you can time it on your own
device; `clock()` is in seconds, and your numbers will differ from mine.

**Every instruction is a trip round a loop written in JavaScript.** A
bytecode interpreter pays for decoding each instruction and jumping to
its code, every time, however simple the instruction<Cite id="v8-sparkplug" />.
That loop of three million passes runs 39,000,015 instructions in the
companion's VM (its `instructionsExecuted` counter says so), which at
814 ms is about 21 nanoseconds per instruction, around forty clock
cycles on this 2.1 GHz machine, for work like "push slot 1". Most of
that is the loop around the work, not the work: counting the
instruction, reading the opcode, choosing the `case`, and reaching the
stack and `sp` through the VM object.

**The VM rebuilds in JavaScript what the tree-walker borrows from
V8.** The tree-walker stores fields and variables in JavaScript `Map`s,
which are hash tables V8 implements in its own fast, built-in code; the
VM stores them in its own `Table`, written in JavaScript. The
tree-walker's objects are freed by V8 alone; the VM's are also tracked
on its object list and swept by its own collector, on top of V8's. That
is why the four slow programs are the ones about fields and allocation.
One measurement backs it up: a copy of the VM with instance fields in a
JavaScript `Map` ran `instantiation` 1.20 times faster than the real
one, and `fields` 1.09 times faster.

<Analogy title="a fluent reader and a phrasebook">
Suppose you hand a fluent reader a novel, and alongside it a version
you have rewritten in a compact shorthand of your own, with a key. For
a beginner, the shorthand might be quicker; for someone who already
reads fast, looking up each symbol in the key costs more than the
shorthand saves.
<span slot="breaks">Shorthand is a one-way loss of meaning; bytecode
loses nothing, and on a host without a JIT (or in C) the same VM would
beat the same tree-walker comfortably.</span>
</Analogy>

## What measurably helps

So I measured the changes themselves. Each row below is two versions
of the companion, identical except for one change, run alternately nine
times each in fresh processes, on the same shared machine; the bar is
the slower version's best time divided by the faster one's.

<ExperimentsChart />

The biggest by far is a deletion. When the heap frees an object, it can
**poison** it (the chapter "Reclaiming memory: mark and sweep"), which
deletes every property; V8 handles objects whose properties are
deleted by switching them to slower "dictionary" properties<Cite id="v8-fast-properties" />,
and doing that to every dead object is expensive. The repository's
history records that profiling first found this, when poisoning was
always on, and that the fix was to run it only in stress and debug
mode. Forcing it back on now makes `instantiation` 2.03 times slower and
`trees` 1.43 times slower. The lesson: profile before you guess, because
nobody would have guessed a safety net was the bottleneck.

Next comes `invoke` (the chapter "Invoking methods, and inheritance
in the VM"):
without it, `method_calls` is 1.32 times slower. Then `inc.local`,
which this chapter is about: 1.15 times on the plain loop, and 1.12 on
`sieve` by best times, though the medians for `sieve` were equal, so
that one is within the noise. And one change I expected to matter did
not: removing the instruction counter that `run` increments on every
instruction gave 1.03 times on `fib`, which is noise on a shared
machine.

## Superinstructions

`inc.local` and `invoke` have something in common: each does, in one
instruction, the work that would otherwise take several. Since every
instruction pays its trip round the dispatch loop, fewer, bigger
instructions mean fewer trips. Step through one pass of that loop to
see where `inc.local` sits:

<Analogy extra title="a set menu">
Ordering a starter, a main and a dessert one at a time means three
trips to the kitchen and three waits; the set menu is one order and one
trip, for the combination people choose most often.
<span slot="breaks">You can change your mind halfway through a meal;
the VM must make sure no jump ever lands in the middle of a fused
sequence, because there is no middle any more.</span>
</Analogy>

<Analogy extra title="a rubber address stamp">
A business that writes the same five-line address hundreds of times a
day buys a stamp: one press does the work of five lines of handwriting.
<span slot="breaks">A stamp prints one fixed address; a
superinstruction still takes operands (`inc.local 1` names its slot),
so it fits every use of the pattern, not one particular use.</span>
</Analogy>

<Callout kind="definition">
A **superinstruction** is a single opcode that does the work of a common
sequence of several, chosen by measuring which sequences run most
often. It saves dispatches and pushes and pops. Its costs are more
opcodes in the dispatch loop, a compiler that recognises the pattern,
and the rule that no jump may target the middle of the sequence.
</Callout>

<Formal title="What fusing saves">

```text
T ≈ N × (d + w)
fuse k instructions, run f times:
  N' = N − (k − 1) × f
```

<span slot="read">Running time T is roughly the number of instructions
run, N, times the cost of a dispatch d plus the instruction's own work
w. Fusing a sequence of k instructions that runs f times removes k
minus 1 dispatches each time, so N shrinks by (k − 1) × f, while the
work w stays about the same.</span>
</Formal>

<Examples of="superinstruction">

```text
inc.local 1
# = load.local 1, const 1, add,
#   store.local 1, pop
```

```text
invoke 'm' (1 args)
# = get.prop 'm', then call 1
```

```text
LOAD_FAST_LOAD_FAST
# CPython: two LOAD_FAST in one
```

</Examples>

The first is the companion's own: the compiler emits it for the hidden
counter of every `for` loop, replacing five instructions with one, so
k is 5 and f is the number of passes; for the three-million-pass loop
that is twelve million dispatches saved, exactly the difference between
51,000,015 and 39,000,015. The second is `invoke`, which fuses a
property read and a call and, as a bonus, skips an allocation. The
third is from CPython, whose compiler fuses two adjacent `LOAD_FAST`
instructions into one, but only inside a basic block (a straight run
of code that jumps enter only at the top) and only when both operands
are small enough to share one argument<Cite id="cpython-superinstructions" />.

## What you learned

- On this host the VM is at most **1.3×** faster than the tree-walker,
  and slower on four programs. V8 compiles both engines, each
  instruction costs about 20 ns of JavaScript, and the VM rebuilds hash
  tables and garbage collection that the tree-walker borrows from V8.
- Measured, one change at a time: poisoning off (up to 2×), `invoke`
  (1.3×), `inc.local` (small), fields in a `Map` (small), the
  instruction counter (nothing measurable).
- A **superinstruction** fuses a common sequence into one opcode,
  saving (k − 1) dispatches per use; `inc.local` and `invoke` are two.
