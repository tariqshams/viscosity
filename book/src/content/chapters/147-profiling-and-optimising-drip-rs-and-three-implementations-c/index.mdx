## Two programs, two very different speed-ups

In the committed benchmark run (`results/drip-rs-bench-2026-11-02.md`, a
shared cloud VM), drip-rs ran `fib.drip` in 406 ms against the
TypeScript VM's 1,906 ms, 4.69 times as fast, but `strings.drip` in 305
ms against 383 ms, only 1.26 times. A guess about why is wrong more
often than not, so we measure, as *Measuring and speeding up the VM* did
for the TypeScript VM, and then settle the account of the whole port.

<Analogy title="a month of bank statements">
You know you spent too much last month, but not on what. You could
guess "eating out", or you could add up the statement by category and
find it was the car. A profiler is the statement: it does not judge,
it only says where the money went.
<span slot="breaks">A statement lists every payment exactly; most time
profilers *sample*, glancing at the program a few thousand times a
second, so small costs can be missed or blurred. callgrind, used below,
is the exception that counts everything.</span>
</Analogy>

## Counting every instruction

valgrind 3.22's **callgrind** runs a program on a simulated CPU and
counts every instruction, by function and source line, with who called
whom<Cite id="valgrind-callgrind-manual" />. With
debug info added from an environment variable (paths
shortened):

```text
CARGO_PROFILE_RELEASE_DEBUG=true \
  cargo build --release
valgrind --tool=callgrind drip-rs fib.drip
callgrind_annotate --inclusive=yes \
  --tree=calling callgrind.out.*
```

The run took 29 seconds instead of 0.4, but the counts are the same on
every run, which no timing on a shared machine can promise. A function's
**self cost** is its own instructions; its **inclusive cost** adds
everything it called.

<Examples of="profiling">

```text
5,593,942,673 (100.0%)  PROGRAM TOTALS
  775,407,050 (13.86%)  > Vm::call_value
                          (7,049,155x)
```

</Examples>

Two lines of fib's call tree (names shortened): `call_value` is called
7,049,155 times, exactly the calls `fib(32)` makes, a sign the profile
is honest. `Vm::run`'s self cost is 65.2%, because with `lto = true`
small functions such as `read_byte` are inlined into it (its two lines
are 5.7% each). In `strings.drip`, `run` is only 17.9%, and the big
names are `malloc`, `free`, `fmod` and Rust's formatting machinery.

<Analogy extra title="a traffic survey">
A council that wants to know which junction to widen counts the cars at
each one, for a whole day, rather than asking drivers which road feels
slow.
<span slot="breaks">Cars are all the same size, roughly; instructions
are not. A cache miss can cost a hundred times an addition, and an
instruction count treats them the same, so a count is a strong hint
about time, not a measurement of it.</span>
</Analogy>

## Drawing it: the flame graph

In a **flame graph** each box is a function on one call path, its width
its inclusive share, sitting on its caller, so its bare top edge is its
self cost<Cite id="gregg-flamegraph" />; left-to-right order means
nothing.

<FlameSteps client:visible />

<Callout kind="definition">
**Profiling** is measuring where a program's cost goes, by function and
line: a **sampling** profiler records the stack many times a second, an
**instrumenting** one such as callgrind counts every instruction. A
**flame graph** draws each call path as stacked boxes, width for
inclusive cost, so the widest towers and bare tops are where to look.
</Callout>

<Examples of="flamegraph">

```text
main;run              3647937915
main;run;pop_numbers   578030669
main;run;call_value    204425495
```

</Examples>

This is the input of Brendan Gregg's `flamegraph.pl`: one line per call
path with its self cost, here three of fib's. fib's graph is a wide,
flat mountain, almost all the bare top of `run`, the dispatch loop
itself. `strings.drip`'s is a tall, thin tower: 60.9% inside the native
`str`, with `format_number` 48.2% on its own; drip-rs spends most of it
turning small whole numbers into text, the slow way.

## Removing checks, and what actually paid

In fib, `read_byte` reads `self.chunk.code[self.ip]`, and every such read
is **bounds-checked**: Rust compares `ip` with the length and panics if
it is too big. `get_unchecked(i)` skips the comparison; it is an
`unsafe` function, because out of range its behaviour is
**undefined**<Cite id="rust-std-slice-get-unchecked" />, which means the
language promises nothing at all and the optimiser may assume it never
happens<Cite id="rustref-ub" />.

<BoundsCheck />

<Examples of="unchecked-indexing">

```text
v[5]     // panics: index out of
         //   bounds: the len is 3
         //   but the index is 5
v.get(5) // None
unsafe { *v.get_unchecked(5) } // UB
```

</Examples>

With `let v = vec![10, 20, 30];`, the checked index panics with that
message (rustc 1.97, wrapped), `get` lets the caller decide, and the
unchecked read may read another object's bytes, crash, or appear to
work. drip-rs cannot write it, because `lib.rs` says
`#![forbid(unsafe_code)]`; in a scratch copy I deleted that line and made
only `read_byte` unchecked, on the argument that every chunk ends with
`return` (an argument about the compiler, whose bugs would then become
undefined behaviour).

<Callout kind="definition">
**Unchecked indexing** reads an element without comparing its index
with the length: in Rust, `unsafe { *v.get_unchecked(i) }`. The caller
promises that `i < v.len()`; if the promise is broken the behaviour is
undefined. The checked forms are `v[i]`, which panics when out of
range, and `v.get(i)`, which returns `None`.
</Callout>

<CheckSteps client:visible />

It removed 8.0% of fib's instructions and no time: over 15 fresh runs
each, best 398 ms (median 427) committed against 406 ms (median 439)
unchecked, within the noise, because the check is a branch the CPU
predicts right every time and runs alongside other work. What did pay:
the chunk register (a copy reaching the chunk through the heap on every
read took about 2.1 times as long), and the profile's second lead, a
five-line fast path in `format_number` for whole numbers below 2^53,
`(n as i64).to_string()`, which made `strings.drip` about 1.75 times as
fast (best 176 ms against 308), the corpus still passing. It is not in
the companion code, so the tables below leave it out.

<More title="Removing checks safely, and the profiler on the TypeScript side">

When a check does cost time, safe Rust can often remove it for you:
iterating with `for x in xs` needs no index<Cite id="rust-std-iter" />,
and reading two operand bytes at once with
`<[u8; 2]>::try_from(&code[ip..ip + 2])` turns two checks into one range
check<Cite id="rust-std-array-tryfrom-slice" />, after which the
optimiser can often prove later indexes in range. For the TypeScript
VM, V8's own sampling profiler, `node --cpu-prof src/cli.ts --vm
../corpus/benchmark/instantiation.drip`, writes a `.cpuprofile`; on
`instantiation.drip` it put the VM's own `Table.grow` (12.2% of samples)
and V8's garbage collector (13.3%) near the top.

## Three implementations, one table

The tree-walker, the TypeScript VM and drip-rs all pass the shared
corpus, so they do the same work; on 2026-11-02 the ten benchmark
programs were timed on all three, best of three fresh processes,
compiling included.

<ThreeWaySteps client:visible />

A speed-up is old time over new; the summary is the **geometric mean**,
the tenth root of the product, which treats 2× and 0.5× as equal and
opposite (their ordinary average, 1.25, would call a wash a win).
drip-rs is 1.26 to 4.94 times the TypeScript VM, geometric mean 3.94
(3.98 against the tree-walker). The surprise: the TypeScript VM wins on
six programs by at most 1.30 times, loses on `fields` (0.74),
`instantiation` (0.69), `strings` (0.95) and `trees` (0.80), and has a
geometric mean of 1.01 over the tree-walker.

<Callout kind="definition">
An **implementation comparison** runs the same programs on two or more
implementations of one language, on one machine, measured one way, and
reports each speed-up (old time over new) and their geometric mean. It
means something only when all of them pass the same tests.
</Callout>

<Examples of="implementation-comparison">

```text
fields: tree 530, TS VM 712,
        drip-rs 193 (ms)
```

</Examples>

On `fields` the TypeScript VM is 0.74 times the tree-walker, while
drip-rs, on the same bytecode, is 3.69 times the TypeScript VM. V8's profiler shows why: the tree-walker keeps fields in
a `Map` and lets V8 free everything, in V8's own C++, while the
TypeScript VM builds its own hash table and collector in TypeScript, on
top of V8's. The design pays only once compiled, which the port did.

<WhereVmTime />

<More title="What the profiles of the two TypeScript implementations say">

On `instantiation`, the VM's own table (16% of samples, much of it
`Table.grow`), its own collector (10%) and V8's collector (13%) add up to
39% of the run; on `trees`, 43%; the tree-walker's `Map`s and V8's
collector take 30 to 31%. `fields` allocates nothing, and there the cost
is per instruction: `a.x += a.vx;` is eight VM instructions, five of
them probes in the hand-written table. These are end-to-end times of
short programs, so they include start-up and V8 warming up its
compiler<Cite id="v8-launch-ignition-turbofan" />, and a 0.95 on a shared
machine is best read as "about the same".

## What Rust gave, and what it cost

The port met its goal: every corpus and stress-GC program passes, byte
for byte. Ownership *forced* arenas with typed handles, roots passed in
and reading before writing. The compiler *caught*, in seconds, missing
match arms (E0004), double mutable borrows (E0499), references into a
changing heap (E0502) and a class handle passed for an instance's
(E0308). The *cost*: 3,328 code lines against the TypeScript VM's 1,714
(1.94 times, counted without blanks, comments or tests) and a build
step. It *bought* the 3.94×, from compiled code and registers, not from
skipping checks, and one 594 KB executable with no dependencies.

<LedgerSteps client:visible />

<Callout kind="definition">
The **Rust trade-offs**, as drip-rs paid them: memory safety without a
runtime, type, borrow and exhaustiveness mistakes caught at compile
time, and about four times the TypeScript VM's speed; for nearly twice
the code, a design shaped by ownership, a build step, and logic bugs in
safe code that only tests find.
</Callout>

<Examples of="rust-tradeoffs">

```rust
let name = a.alloc("fib");
a.free(name); // a root was forgotten
let other = a.alloc("zoo"); // reuses
println!("{}", a.get(name)); // zoo
```

</Examples>

What Rust cannot see, from the runnable example below, a tiny arena
that reuses freed slots as drip-rs does in normal mode: forget a root
and the program compiles, the object is freed while in use, the slot is
reused, and the stale handle reads the newcomer. No crash, no undefined
behaviour, just the wrong answer; so drip-rs's debug and stress modes
never reuse a slot. Rust made the bug **safe**; making it impossible
took tests.

Not all the extra lines are ownership: `value.rs` reimplements
JavaScript's number printing, the scanner spells out each byte case, and
`main.rs` is a 50-line command line; seven `unreachable!` calls mark
facts the types cannot express. A clean release build with `lto` took
about 7.5 seconds here. The Rust book describes the borrow checker as
preventing dangling references at compile time<Cite id="klabnik2026" />;
in drip-rs no reference can dangle, but a handle can still name a slot
whose object has gone, the same mistake one level up.
