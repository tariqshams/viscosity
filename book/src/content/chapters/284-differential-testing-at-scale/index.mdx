## From one test to a folder

*Testing compilers* gave you the method: compile a program, run both
versions, and let the original be the oracle. One program checks one
thing; however, Viscosity has to be right about escapes, aliases, `try`,
`NaN`, strings in number fields, Python's integers, two parsers and a
second implementation in Rust. That takes many programs, and a way of
using each one many times. Here is the whole TypeScript test suite, run
for this chapter (paths shortened, timings left out):

```text
$ cd engine/ts && npx vitest run
 ✓ frontend-js/.../differential.test.ts
     (42 tests)
 ✓ frontend-js/.../mini-parser.test.ts
     (47 tests)
 ✓ bench/test/layouts.test.ts (8 tests)
 ✓ core/test/core.test.ts (15 tests)
 ✓ frontend-python/.../differential...
     (21 tests)
 ✓ cli/test/cli.test.ts (14 tests)
 Test Files  6 passed (6)
      Tests  147 passed (147)
```

105 of those 147 tests were never written one by one: they are
generated, one per program, from folders of programs.

<Analogy title="a driving-test route">
A driving examiner does not invent a new route for every learner. There
is a route, chosen to include the hard junction, the hill start and the
school crossing, and every learner drives it; when someone finds a new
way to fail, a new turn is added to the route.
<span slot="breaks">A learner drives the route once; every version of
the compiler drives the whole route, every time, and has to pass every
turn exactly.</span>
</Analogy>

<Analogy title="a pilot's checklist">
Airline checklists grow from experience: after an incident, the step
that would have prevented it is written onto the list, and every crew
runs it before every flight from then on.
<span slot="breaks">A checklist is read by people who can skip a line;
the corpus is run by a program that never skips one, and a new line
costs nothing to run.</span>
</Analogy>

<Callout kind="definition">
A **test corpus** is a large, curated collection of programs used as
test inputs. Each program is chosen to exercise one case, and the tests
are generated from the collection, so adding a case means adding a file,
not writing test code.
</Callout>

## What goes in a corpus file

The JavaScript corpus has 40 files, each probing one decision. Here is
`try_catch.js` (long lines wrapped):

```js
// viscosity: ps=soa
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
let s = 0;
try {
  for (let i = 0; i < ps.length; i++)
    s += ps[i].x;
  ps[1000].x = 1;
} catch (e) {
  console.log('caught',
    e.constructor.name, e.message);
}
console.log(s);
```

It follows the rules every corpus file follows. **One idea:** this file
asks a single question, whether an out-of-bounds write inside `try`
throws the same error after compiling, and its name says so. **A
header** gives the expected decision for every collection
(`ps=soa`), so a compiler that quietly stops optimizing fails too.
**Observable:** it prints the error's class and message, and the sum,
because a difference that is not printed cannot be caught. **Small and
deterministic:** no timing and no randomness, so two correct runs always
print the same thing.

The first is the start of `aosoa_bad_block.js`, eight lines in all: its

`count` a list column, and it stays `int`. The third is the top of
`write_rhs_first.js`, a file nobody imagined until a fuzzer found the
bug it guards against, as we will see below.

## One file, many checks

The trick that makes the corpus scale is that each program is used by
several tests, for different questions. Step through the matrix:

<MatrixSteps client:visible />

All of these tests share one shape; here is the real loop in
`differential.test.ts`:

```ts
for (const f of readdirSync(dir)
    .filter((f) => f.endsWith('.js'))
    .sort()) {
  it(f, () => { /* compile, check the
    header, run both versions */ });
}
```

It lists the folder, keeps the `.js` files, sorts them so the order is
the same on every machine, and makes one named test per file. The tests
are written once, per *kind* of check; the cases are data. The Python
test cannot use Node's VM contexts, so it writes both programs to a
temporary folder, runs each with the real `python3`, and compares
standard output and, for a crash, the last line of standard error,
where Python prints the exception. The oracle is still the original
program; only the way of running it changed.

## The TypeScript compiler as an oracle

Part XIII rebuilds Viscosity in Rust. How do you know the Rust version
decides and emits exactly what the TypeScript one does? By differential
testing again, with the TypeScript compiler as the oracle.
`engine/rust/scripts/gen_expected.mjs` runs the TypeScript compiler on
every JavaScript and Python corpus file, every benchmark program and 29
extra programs written for the port (95 in all), twice: once with the
default `bounds: 'check'` and once with `bounds: 'assume'`, so the
unchecked code paths are covered too. It stores the compiled code and
the explain report each time (190 pairs), plus 14 `--frames` reports and
4 programs compiled with a profile: 402 files in
`engine/rust/tests/expected/`. The parity test recompiles every source
in Rust and compares byte for byte; run for this chapter, it printed
`parity: 190/190 (54 Python)`. The parity work paid the reference back,
too: it found bugs in the TypeScript compiler, among them a soundness
bug where an element thrown from inside a loop was not seen as
escaping (now guarded by the corpus file `throw_from_loop.js`).

## What a corpus cannot find

Every file in the corpus was written by someone who thought of the
case. The corpus is very good at keeping found bugs found, and at
checking that a new feature did not break an old one; it cannot find
the case nobody imagined. For that you need programs nobody wrote, the
random programs of *Fuzzing and test-case reduction*. Viscosity's
fuzzer, `engine/rust/scripts/fuzz.mjs`, run for this chapter on its
default campaign, printed:

```text
fuzz: seed 1, 300 programs (134
  transformed, 174 may go out of bounds,
  20 with an early error), 0 failing
```

When it was first run, about 8,000 random programs turned up five bugs
in both engines, the first of which `write_rhs_first.js` now guards:
`ps[i].x = rhs` checked the index *before* evaluating `rhs`, while the
original evaluates `rhs` first, so out of bounds the two threw different
errors. Each bug was fixed, and each got a corpus program, so the
corpus and the fuzzer feed each other:

<Callout kind="engine" label="Under the hood">
Language implementations live by their corpora. Test262, the
conformance suite for JavaScript itself, is a corpus of tens of
thousands of test files covering the language
specification<Cite id="test262" />. Csmith is the opposite strategy: a
generator of random C programs that finds compiler bugs by differential
testing, rather than from hand-written cases<Cite id="csmith" />. Real
compilers use both: a growing corpus of known cases, and a generator
that keeps adding the unknown ones.
</Callout>

## What you learned

- A **test corpus** is a curated collection of programs; the tests are
  generated from it, so a new case is a new file.
- A good corpus file probes one idea, states the expected decisions,
  prints what could differ, and is deterministic.
- Each program feeds several checks: 65 programs give 105 generated
  tests, and the TypeScript engine is the oracle for the Rust port's 402
  fixture files.
- A corpus keeps known bugs found; random programs find unknown ones,
  and each find becomes a corpus file.
