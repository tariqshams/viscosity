## One name for many values, one name for one job

A thousand particles should not need a thousand variable names, and a
piece of work should not have to be written out again wherever it is
used. Drip needs the two cures every language has, a **list** and a
**function**; both are small to add on top of environments and a Pratt
parser, and the interesting part is deciding what counts as an error.

<Analogy title="a row of numbered pigeonholes">
A post room has a row of pigeonholes labelled 0, 1, 2 and so on; the
whole row has one name, and you reach one hole by its number.
<span slot="breaks">A row of pigeonholes is built with a fixed number of
holes; a Drip list grows by one every time you `push`, and shrinks with
`pop`.</span>
</Analogy>

## Lists, xs[i] and for x in xs

`[` at the start of an expression is a prefix rule that reads
expressions up to `]`; evaluating the node evaluates each element, left
to right, into a `DripList`, a small class whose one field, `items`, is
a JavaScript array. A variable holds a reference to the list, as with JavaScript
arrays<Cite id="mdn-array" />, so `let ys = xs;` gives one list two
names, and `==` compares lists by identity. `[` *after* an expression is
an infix rule with call-level binding power, so `ps[0][1]` reads element
1 of element 0, and reading and writing share one check that asks four
questions in order, each with its own message: is it a list, is the
index a number, is it whole, and is it from `0` to `len(xs) - 1`.
Writing never adds an element; `push(xs, v)` grows a list and `pop(xs)`
shrinks it.

<Callout kind="definition">
A **Drip list** is an ordered, growable collection of values, written
`[a, b, c]`, shared by reference; two lists are `==` only if they are
the same list. An **index expression** `xs[i]` reads element `i`, and
`xs[i] = v` overwrites it; the index must be a whole number from `0` to
`len(xs) - 1`, and anything else is a runtime error that names the
problem.
</Callout>

<Examples of="drip-list index-expression">

```text
let xs = [10, 20];
let ys = xs;        # one list, two names
push(ys, 30);
print xs;           # [10, 20, 30]
print xs[len(xs) - 1];  # 30
print xs[3];
# index 3 is out of range for a
# list of length 3
```

</Examples>

`ys = xs` copies the reference, so the `push` through `ys` shows up in
`xs`; the last element is at `len(xs) - 1`, and `xs[3]` is an error
rather than JavaScript's `undefined`.

`for x in xs` is the list branch of the `for` loop that runs ranges;
step through one whose body grows its own list:

<ListSteps client:visible />

<Callout kind="definition">
A **for-in loop**, `for x in xs { ... }`, evaluates `xs` once (it must
be a list), then runs the body once per element in order, with `x` a
fresh variable each time; the length is checked before every round, so
elements pushed during the loop are visited too (as with JavaScript's
`for...of` over an array<Cite id="mdn-array-values" />).
</Callout>

<Examples of="for-in-loop">

```text
let xs = [10, 20];
for x in xs { x = 0; }
print xs;     # [10, 20]
```

</Examples>

`x = 0` overwrites the loop variable, not the element, so the list is
untouched; to change elements, loop over `0..len(xs)`.

<More title="Lists of records, and the shape Viscosity cares about">

A list of small lists, `[[0, 1], [5, -1]]`, is a list of records (an x
and a vx per particle); two lists, `xs` and `vxs`, hold the same numbers
one list per field. The first is the natural way to write it and the
second is often the faster way to run it, because a list of lists is an
array of references to other arrays, and reading every `x` chases a
pointer per particle. Records become classes in *Classes, methods and
inheritance in Drip*, and Viscosity's whole job is to take the first
shape and run it as the second.

## Functions are values, and only some values are callable

Running `fn area(w, h) { ... }` does not run the body; it makes a
`DripFunction` holding the declaration node and the environment current
at that moment (its `closure`, which the next chapter explains), and
defines `area` to hold it, a value like any other (`print area;` shows
`fn area`); `fn (x) { ... }` makes the same kind of value with no name.

A call evaluates the callee (whatever sits left of `(`), then the
arguments left to right, and only then asks what kind of value it has:

```ts
if (callee instanceof DripFunction)
  return this.callFunction(
    callee, args, e.paren);
if (callee instanceof NativeFunction) {
  // check the arity, then run it
}
throw new RuntimeError(e.paren,
  `cannot call ${describe(callee)}`);
```

`e.paren` is the `(` token, kept so an error can name the line. (The
real code also has a branch for classes, whose message says to use
`new`, and one for method calls.)

<Figure caption="After evaluating the callee and the arguments, a call looks at what kind of value the callee is. Two kinds run; the rest stop the program with a runtime error that says what went wrong." takeaway="Only Drip functions and natives can be called.">
  <CallDispatch />
</Figure>

<Callout kind="definition">
A **callable** is a runtime value that a call expression can run. In
Drip there are two kinds: a **Drip function** (made by `fn`, named or
anonymous) and a **native function** (written in TypeScript). Calling
any other value is a runtime error, and a class is made with `new`,
never with a bare call.
</Callout>

<Examples of="callable">

```text
let twice = fn (f) { f(); f(); };
twice(fn () { print "drip"; });
# drip
# drip
```

</Examples>

`twice` holds an anonymous function whose parameter `f` receives
another anonymous function, so each `f()` finds a `DripFunction` and
runs its body, printing `drip`.

## Counting the arguments, then running the body

Here is `callFunction`, leaving out the handling of `return` and a
record kept for error messages (both in the next chapter):

```ts
if (args.length !== f.arity)
  throw new RuntimeError(at,
    `${f.label} takes ` +
    plural(f.arity, 'argument') +
    ` but got ${args.length}`);
const env = new Environment(f.closure);
const ps = f.decl.params;
for (let i = 0; i < ps.length; i++)
  env.define(ps[i].lexeme, args[i]);
this.executeBlock(f.decl.body, env);
```

The first statement checks the **arity**, before anything else. Then
the call makes a fresh environment whose parent is the function's
stored `closure`, defines the parameters there and runs the body. Every
call has its own environment, so a recursive call keeps its own
parameters; and the parent is where the function was *written*, not
where it is called from, which is lexical scope. Step through two
calls:

<CallSteps client:visible />

<Callout kind="definition">
A function's **arity** is the number of arguments it takes; for a Drip
function it is the number of parameters in its declaration, and each
native function has a fixed arity of its own. Drip checks arity on every
call, before the body runs, and a mismatch is a runtime error.
</Callout>

<Examples of="arity">

```text
fn area(w, h) { print w * h; }
area(3);
# runtime error: area() takes
#   2 arguments but got 1
#   at line 2 in script
```

</Examples>

The error names both counts and the line of the call that forgot.
JavaScript reports a function's parameter count as
`f.length`<Cite id="mdn-function-length" /> but never checks it, so a
missing argument is `undefined` and misbehaves far from the slip:

## Native functions: help from the host

Nothing in Drip can ask the outside world anything, not even the time,
so the interpreter writes a few functions in TypeScript and defines them
as globals before the program starts:

```ts
native('clock', 0, () =>
  (performance.now() - this.start) / 1000);
```

`native` wraps a name, an arity and a TypeScript function in a
`NativeFunction` (`performance.now()` counts
milliseconds<Cite id="mdn-performance-now" />). Calling a native checks
the arity, then hands the arguments straight to the TypeScript function:
no environment and no Drip statement.

<Callout kind="definition">
A **native function** is a callable written in the host language (here
TypeScript) rather than in the language being run. Natives are how a
language reaches anything outside itself, such as the clock, files or
the screen, and how it offers operations that would be slow or
impossible to write in the language itself. Drip has five: `clock`,
`len`, `push`, `pop` and `str`.
</Callout>

<Examples of="native-function">

```text
print len("drip");  # 4
print len;          # native fn len
print len(7);
# runtime error: len() needs a
#   list or a string, not a number
```

</Examples>

Printing `len` does not call it; given a number, its TypeScript code
throws an error in Drip's own words.

<Prompts ids={['native-what']} />

<More title="How len is written, and two runnable examples">

```ts
native('len', 1, ([x], at) => {
  if (x instanceof DripList)
    return x.items.length;
  if (typeof x === 'string')
    return [...x].length;
  throw new RuntimeError(at,
    `len() needs a list or a string, ` +
    `not ${describe(x)}`);
});
```

`[...x]` counts whole Unicode characters rather than UTF-16 units.
`push`, `pop` and `str` are built the same way. The first example below
calls each function in a list and then tries to call a number; the
second times a loop with `clock` (your number will vary from run to
run, which *Benchmarking honestly* had a lot to say about).

## What you learned

- A **list** is shared by reference; **`xs[i]`** checks four things;
  **`for x in xs`** rereads the length each round.
- A **callable** is a Drip function or a native; a call checks
  **arity**, then runs the body in a fresh environment.
- A **native function** is host code behind a Drip name.
