## The same loop, two speeds

Here’s a loop you have written many times, run over the particles from
chapter 5. It adds up every `mass`:

```js
let s = 0;
for (let i = 0; i < ps.length; i++) {
  s += ps[i].mass;
}
```

This book’s benchmark ran exactly this loop on a thousand particles and
on a million. The work per particle is identical: one read, one add.

## The CPU: a very fast, very simple worker

<Callout kind="intuition">
Think of the processor as a worker at a desk who can only follow one
tiny instruction at a time: “pick up the number at mailbox 16”, “add
these two”, “add 8 to that address”. They are astonishingly quick at
it. But they can only hold a handful of numbers in their hands at
once.
</Callout>

Step through one turn of the loop. The instructions here are made up
and simplified, but the shape is real.

<CpuSteps client:visible />

<Callout kind="definition">
The **CPU** (central processing unit, or processor) runs a program by
repeating three steps for each instruction: **fetch** it from memory,
**decode** what it asks for, and **execute** it<Cite id="slotin-amh-pipelining" />.
As it goes, it reads and changes **registers** and memory<Cite id="apple-wwdc25-cpu" />.
**Registers** are a few tiny storage slots inside the CPU itself, where
it keeps the values it is working on right now. Using them costs almost
nothing<Cite id="slotin-amh-hierarchy" />.
</Callout>

## The warehouse problem

Adding two registers takes the CPU almost no time. Fetching a number
from main memory takes a very long time by comparison. On the CPUs
Apple describes, a read that has to go all the way to main memory is
about fifty times slower than the fast path<Cite id="apple-wwdc25-cpu" />.
A rough 2021 table for ordinary hardware tells the same story: about 2
nanoseconds for the fastest cache, about 100 for main memory<Cite id="slotin-amh-hierarchy" />.
Exact figures differ from chip to chip. The gap of one to two orders of
magnitude is what matters.

<Callout kind="intuition">
Imagine all your stock is in a warehouse across town. A trip there takes
an hour, so you keep a desk drawer for things you’re using right now, a
shelf in your office for this week’s work, and a storeroom down the hall.
Each place is bigger and further away than the last. Every time you need
something, you look in the drawer first.
</Callout>

<Callout kind="definition">
A **CPU cache** is a small, fast memory between the CPU and main memory
that keeps copies of recently used data. Modern CPUs have several, in a
**cache hierarchy**: **L1** is the smallest and fastest and sits inside
each core; **L2** and then **L3** are bigger and slower; **main memory**
(RAM) is far bigger and slower still<Cite id="slotin-amh-hierarchy" />.
**Latency** is how long one access takes, from asking to receiving.
</Callout>

## Hits and misses

Now follow one read through the ladder, then a second read of the same
thing, then a read of something new.

<CacheTrip client:visible />

<Callout kind="definition">
When the data the CPU needs is already in a cache, that is a **hit**.
When it isn’t, that is a **cache miss**, and the CPU must look further
down the hierarchy, perhaps all the way to main memory. Misses cost far
more than hits, so a few of them can dominate a loop’s running time.
</Callout>

You can do the arithmetic yourself. Say a hit costs 2 nanoseconds and a
miss 100. If 1 read in 10 misses, what does an average read cost?

```js
// 9 hits at 2 ns, 1 miss at 100 ns
const avg = (9 * 2 + 1 * 100) / 10;
console.log(avg); // 11.8
```

Even a 90% hit rate leaves reads several times slower than all hits.
That is why the million-particle loop slowed down. A thousand particles
fit in the caches, so once the loop has run, nearly every read hits. For
a million particles, the six 8-byte numbers alone come to 48 megabytes,
far more than the caches hold, so the loop keeps missing.

## What you learned

- The **CPU** fetches, decodes and executes one instruction after
  another, working on values held in **registers**.
- Main memory is far slower than the CPU, so a **cache hierarchy**
  (L1, L2, L3) keeps recently used data close by.
- **Latency** is how long one access takes. A hit in L1 takes a few
  nanoseconds; a trip to main memory takes around a hundred.
- A **cache miss** sends the CPU further down the hierarchy. A handful
  of misses can dominate a loop.
- When data outgrows the caches, the same loop gets slower per element.
