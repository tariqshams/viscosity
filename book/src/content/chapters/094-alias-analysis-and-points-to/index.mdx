## One read the compiler would love to skip

```js
function f(a, b) {
  a.x = 1;
  b.x = 2;
  return a.x;
}
```

It is tempting to replace the last read with `1`, which we wrote a
moment ago, since a read from memory is far slower than a number we
already have; however, that is only right if `a` and `b` are different
objects. Call `f(o, o)` and line 3 overwrites the
`1`, so the true answer is `2`:

<Run id="twoWays" />

Two names for one object is **aliasing** (*References: two names, one
object* in the Prelude). A compiler has to settle it for every pair of
names before the program runs, and never get it wrong in the dangerous
direction.

<Analogy title="two names on one letterbox">
A house has one letterbox with two names on it, "A. Shah" and "the Shah
family"; a letter to either lands in the same box, so if you post a
parcel to one and ask the other "has anything arrived?", the answer is
yes. From the envelopes alone, however, you cannot tell whether two
names share a box; you need to know where the people live.
<span slot="breaks">Names on a letterbox are fixed; in a program, which
object a name leads to can change from one run to the next, and even
from one moment to the next.</span>
</Analogy>

## Must, may and no

<Figure takeaway="Must and no are facts a compiler can act on; may means keep both possibilities." caption="Must: p and q always reach o1. May: q reaches o1 on some runs and o2 on others. No: p and q never share an object.">
  <MayMustNo />
</Figure>

<Callout kind="definition">
**Alias analysis** decides, for two references, whether they **must**
refer to the same object on every run, **may** refer to the same object
on some run, or **never** do. LLVM's interface returns exactly these
answers, `MustAlias`, `MayAlias` and `NoAlias` (plus `PartialAlias`,
for memory that overlaps only in part)<Cite id="llvm-alias-analysis" />.
</Callout>

<Examples of="alias-analysis">

```js
const a = { x: 1 };
const b = { x: 2 };
const c = flag ? a : b;
// c may alias a, may alias b;
// a and b: no alias
```

</Examples>

`a` and `b` are two separate `{ ... }` expressions, each of which makes
a brand-new object, so on no run can they be the same object; `c` takes
one or the other depending on `flag` (which the compiler cannot
predict), so it may alias either. Had we written `const b = a`, `b`
would copy the arrow in `a`, and they would alias on every run.

The answers are not equally dangerous. A wrong "may" (when the truth is
"no") only skips an optimisation; a wrong "no" makes `f` return `1`
when the program should return `2`, a wrong answer, the one thing a
compiler must never give. So a **sound** analysis says "may" whenever it
is unsure, and the whole craft is turning as many "may" answers as
possible into "must" or "no" without ever lying.

<More title="More: the cheap answers, and why JavaScript has fewer of them">

Real compilers start with facts that need no searching: LLVM's basic
alias analysis knows that distinct globals, stack allocations and heap
allocations never alias, and that different fields of a structure do
not<Cite id="llvm-alias-analysis" />, and its `licm` pass uses alias
analysis to decide whether a load can be hoisted out of a
loop<Cite id="llvm-passes" />. In Java or C a reference to a `Point` and
one to a `String` can never meet, because no object is both; this is
**type-based alias analysis** (TBAA)<Cite id="diwan1998" />, which LLVM
gets from metadata that front ends attach to
memory<Cite id="llvm-langref-tbaa" />. JavaScript takes this away:
`f(a, b)` can receive any two objects, or one twice, and a TypeScript
annotation is erased before the program runs (and the type system is
not sound, so the program need not obey it). A JIT checks its guesses at
run time and deoptimises; Viscosity compiles ahead of time, so it has to
prove its answers.

<Formal title="The three answers">

```text
must(p, q) ⇔ ∀ run : p = q
may(p, q)  ⇔ ∃ run : p = q
no(p, q)   ⇔ ¬ may(p, q)
```

<span slot="read">p and q must alias when, for every run (the
upside-down A), they refer to the same object at that point; they may
alias when there exists (the backwards E) a run where they do; they do
not alias when it is not true (¬) that they may.</span>
</Formal>

</More>

## Viscosity's version of the question

Viscosity asks one big question: can it turn an array of objects into a
struct of arrays without anybody noticing? There an element is a
position in some columns, so every reference to an element must become
an index, which works only for references Viscosity can see. The program below fills
`ps`, writes `42` through `p = ps[3]`, pushes `p` into a second array
`keep`, writes `7` through `keep[0]` and prints `ps[3].x` (`8`, because
`keep[0]` and `ps[3]` must alias); Viscosity refuses with `an element is
used by push at line 8`:

<AliasSteps client:visible />

Without `keep`, `p` is an SSA value that must alias element 3 and
nothing else, so `const p = ps[3]` becomes `const p = 3`. So Viscosity
asks something stricter than "may these two alias?": is every reference
to this array, and to each element it hands out, one I can follow?
Storing an element in a variable a closure captures, putting it inside
another object, or comparing it with `===` (which asks about identity,
and so needs a real object) each makes a name Viscosity cannot follow;
each counts as a "may", and the whole array keeps its layout.

<More title="More: three refusals, try it, and a run-time alternative">

Each of these lines, added after a particle loop, gets a "no":

```text
const keep = ps[0];
const peek = () => keep.x;
  an element is stored in another
  variable (keep)
const box = { p: ps[0] };
  an element is put inside another object
console.log(ps[0] === ps[1]);
  an element is compared or combined
  with "==="
```

The closure captures `keep`, so `keep` lives in memory rather than as an
SSA value, and can be read at any time.

Delete the `peek` line and print `keep.x` directly instead: `keep`
becomes an index, and `ps` becomes a struct of arrays. Research systems
that switch JavaScript arrays to columnar storage face the same
requirement, and make the switch at run time instead<Cite id="makor2022" />.

## Every name, a list of suspects

An optimiser asks about many pairs, so it pays to compute, once, the
**set of objects each name might point at**, and compare two sets per
pair. There is a snag: a loop like
`for (...) ps.push({ x: i })` can make billions of objects, so an
analysis names each object by the place in the code that creates it,
its **allocation site**; every object made there is one abstract object
`o1`, and every set stays small and finite.

<Callout kind="definition">
A **points-to set**, written pts(v), is the set of abstract objects
(usually allocation sites) that a variable, or a field of an abstract
object, may point at. Two references may alias when their sets
intersect, and cannot alias when they are disjoint; equal sets do not
prove "must", because one site can make many objects. A **points-to
analysis** computes these sets for a whole program without running it.
</Callout>

Four kinds of statement move arrows (an allocation, a copy, a field
store and a field load), and each gives one rule; Andersen's 1994 thesis
built its analysis for C on rules like these<Cite id="andersen1994" />.

<Examples of="points-to">

```js
const a = {};        // o1
const b = { n: 2 };  // o2
a.f = b;
const c = a.f;
// pts(o1.f) = {o2}, pts(c) = {o2}
```

</Examples>

The first two lines give `pts(a) = {o1}` and `pts(b) = {o2}`;
`a.f = b` puts o2 into the cell `o1.f`, which is just another place that
holds arrows; and `c = a.f` reads it back out, so `c` may point at o2:
an alias created through the heap, which no look at `c` and `b` alone
would reveal.

**Andersen's analysis** treats each copy as an inclusion, one way only.
The rules mention no order (the analysis is *flow-insensitive*: one set
per name, true everywhere), so a set may grow after a rule that reads it
has been used; the analysis goes round again and again until a round
adds nothing, a fixpoint as in *Dataflow, fixpoints and constant
propagation*, and it must stop because sets only grow and there are
finitely many sites:

<AndersenSteps client:visible />

<More title="More: Steensgaard's analysis, merge rather than copy">

Andersen's sets can grow large, and in the worst case its time grows
with the cube of the program's size<Cite id="steensgaard1996" />.
**Steensgaard's analysis** makes each variable point at one box and
treats `a = b` as "a and b point at the same box", merging two boxes
with union-find when they differ; it runs in almost linear
time<Cite id="steensgaard1996" />, but after `c = a; c = b` it says `a`
and `b` may alias, which no run can make true:

<SteensSteps client:visible />

LLVM documents a variant as "unification-based, flow-insensitive,
context-insensitive, and field-insensitive" and "very scalable
(effectively linear time)"<Cite id="llvm-alias-analysis" />: Andersen for
precision, Steensgaard when the program is enormous.

</More>
