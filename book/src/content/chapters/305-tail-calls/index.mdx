## A loop that runs out of stack

Here is a Drip function that adds up `1 + 2 + ... + n`, carrying the
running total in `acc`:

```drip
fn sum(n, acc) {
  if n == 0 { return acc; }
  return sum(n - 1, acc + n);
}
print sum(100, 0);   # 5050
print sum(300, 0);
# runtime error: stack overflow
```

Drip allows calls to nest 256 deep, so the second call fails; the same
function in Node 22 dies before `sum(10000, 0)` (at about 9,000
calls on this book's machine) with
`RangeError: Maximum call stack size exceeded`<Cite id="mdn-too-much-recursion" />.
Yet it is really a loop: each call hands over a smaller `n` and a bigger
`acc`, and once the inner call returns, the outer one passes the answer
straight on. Every waiting frame (chapter 19) is kept alive to do
nothing. This chapter shows how compilers notice that, and what to do
when yours does not.

## Tail calls

<Analogy title="transferring a phone call">
You ring a shop, and the person who answers says "that is accounts, let
me put you through" and connects you; they do not stay on the line to
repeat everything accounts says, they hang up.
<span slot="breaks">You notice being transferred; a program cannot tell
whether a tail call kept the frame or not, except by how deep it can go
(and in a debugger's list of frames).</span>
</Analogy>

<Analogy extra title="forwarding a parcel">
A parcel arrives for someone who has moved, so you write the new address
on it and post it on; the reply will go to the sender, not to you, so
you have no reason to wait for it.
<span slot="breaks">You might still want to know it arrived; a function
that makes a tail call has given up all interest in the result, because
it has nothing left to do with it.</span>
</Analogy>

<Callout kind="definition">
A **tail call** is a call whose result the caller returns straight
away, with nothing left to do afterwards. Its position in the function
is called a **tail position**.
</Callout>

<Examples of="tail-call">

```js
function f(x) { return g(x + 1); }
// g(x + 1) is a tail call
```

```js
function first(xs) {
  return xs.length ? use(xs[0])
                   : none();
}
// both branches are tail calls
```

```js
function fact(n) {
  if (n <= 1) return 1;
  return n * fact(n - 1); // not tail
}
function factT(n, acc) {
  if (n <= 1) return acc;
  return factT(n - 1, acc * n); // tail
}
```

</Examples>

In the first, `f`'s answer is whatever `g` returns. In the second the
conditional picks one branch, and its value is returned as it is, so
both calls are in tail position. The third is a spot the difference:
`fact` must still multiply by `n` after the recursive call, so the call
is not in tail position and each frame really is needed; `factT` does
the multiplying before the call, in the extra `acc` parameter, so the
call is the last thing it does. Moving pending work into an extra
argument like this is the usual way to make a function tail-recursive.
(In `return a() || b()` only `b()` is a tail call: `a()`'s value must be
tested first. The ECMAScript specification lists exactly these
cases<Cite id="ecma262" />.)

<Formal title="Tail contexts">

```text
T ::= □
    | c ? T : T
    | e || T   |   e && T
    | { s; ... ; return T; }
```

<span slot="read">A tail context T is a function body with a hole, the
box, where the final answer is produced: the hole itself; either branch
of a conditional whose branches are tail contexts; the right-hand side
of an or or an and; or the returned expression after some statements.
A call is a tail call when it fills the hole of the body's tail
context.</span>
</Formal>

In continuation-passing style (chapter 303) every call is a tail
call.

## Tail-call optimisation

If the caller has nothing left to do, its frame is dead the moment the
tail call starts. So instead of pushing a new frame, the compiler can
write the new arguments over the old ones and **jump** to the callee,
leaving the return address alone: when the callee returns, it returns
straight to the caller's caller. Step through both versions:

<FrameSteps client:visible />

Here is clang 18 compiling `long f(long x) { return g(x + 1); }` for
RISC-V (the architecture of chapters 230 to 255), with the
bookkeeping lines removed:

```text
# clang -O0
f:  addi  sp, sp, -32
    sd    ra, 24(sp)
    ...
    addi  a0, a0, 1
    call  g
    ld    ra, 24(sp)
    ...
    addi  sp, sp, 32
    ret
# clang -O1
f:  addi  a0, a0, 1
    tail  g
```

At `-O0`, `f` saves its return address `ra`, calls `g`, then restores
`ra` and returns: a full frame, kept only to pass `g`'s answer on. At
`-O1`, `f` adds 1 to its argument and does `tail g`, which the RISC-V
assembler expands to a jump that does not write a return address
(`jalr x0, ...`)<Cite id="riscv-asm-manual" />, so `g` returns directly
to whoever called `f`. For a function that tail-calls *itself*, such as
our `sum`, clang at `-O1` goes further and the call disappears into a
loop that branches back with `bnez`.

<Callout kind="definition">
**Tail-call optimisation** (TCO) compiles a tail call as a jump: the
caller's frame is released or reused for the callee's arguments, and the
return address is left pointing at the caller's caller. A chain of tail
calls then runs in constant stack space; a self tail call becomes a
loop.
</Callout>

<Examples of="tail-call-optimization">

```c
long sum(long n, long acc) {
  if (n == 0) return acc;
  return sum(n - 1, acc + n);
}
// clang -O1: a loop, no call at all
```

```c
long f(long x) {
  [[clang::musttail]] return g(x + 1);
}
```

```js
'use strict';
function sum(n, acc) {
  if (n === 0) return acc;
  return sum(n - 1, acc + n);
}
sum(1e5, 0); // RangeError in Node 22
```

</Examples>

The first is the self tail call above, which clang turns into a loop
when optimising. The second asks clang for a guarantee: `musttail`
makes a tail call compulsory "even when optimizations are disabled", so
recursion through it cannot grow the stack<Cite id="clang-musttail" />.
The third is JavaScript: since 2015 the specification says a tail call
in strict-mode code "must either release any transient internal
resources ... or reuse those resources"<Cite id="ecma262" />, yet Node
22, built on V8, still overflowed when we ran it. A rule in the
specification is not the same as what engines ship. Python 3.13
behaves the same, stopping at its default limit of 1,000 frames.

The idea is old: in 1977 Guy Steele argued that procedure calls were
thought expensive mostly because of poor implementations, in a memo
whose other title is "Lambda: The Ultimate GOTO"<Cite id="steele1977" />.

## Trampolines

When the compiler will not do it (JavaScript in V8, or your Drip VM),
you can still run deep tail recursion. Instead of *making* the tail
call, a function returns a description of it, a small function with no
parameters (a **thunk**) that makes the call when invoked. A loop, the
**trampoline**, calls thunks until it gets something that is not one.
Each call returns to the loop before the next is made, so the stack
never holds more than one or two frames<Cite id="ganz1999" />.

<Analogy extra title="a government office counter">
Each office stamps your form and hands it back with a slip saying "now
go to counter 7", rather than walking it to counter 7 itself; you, in
the queue, are the loop, going wherever the last slip says until a form
comes back marked "done".
<span slot="breaks">You can see the slips; a program pays for each
bounce with a small allocation (the thunk) and an extra call, which is
why a trampoline is slower than a real jump.</span>
</Analogy>

<Callout kind="definition">
A **trampoline** is a loop that runs a computation in which every tail
call has been replaced by returning a thunk for it: while the value in
hand is a thunk, call it; the first value that is not a thunk is the
answer. The stack depth stays constant however long the chain of calls.
</Callout>

<Examples of="trampoline">

```js
function run(r) {
  while (typeof r === 'function') r = r();
  return r;
}
run(() => () => 42); // 42
```

```js
const even = (n) => n === 0 ? true
  : () => odd(n - 1);
const odd = (n) => n === 0 ? false
  : () => even(n - 1);
run(even(100001)); // false
```

<Run id="drip-trampoline" />

</Examples>

The first is the whole trampoline: it calls thunks until something else
comes back, here two thunks and then 42. The second is a classic pair of
functions that call each other in tail position; returning thunks lets
them alternate 100,001 times without overflowing. The runnable third is
Drip, which has no way to ask "is this a function?", so `sumT` returns a
list instead: `[true, thunk]` for "call this next", or `[false,
answer]`. The `while` loop is the trampoline, and `sum(1000, 0)`, four
times deeper than Drip allows, now prints `500500`.

## What you learned

- A **tail call** is a call whose result is returned as it is.
- **Tail-call optimisation** compiles it as a jump that reuses the
  frame (`tail g` on RISC-V); JavaScript's specification asks for it in
  strict mode, but V8 does not do it.
- A **trampoline** returns thunks to a loop, giving constant stack depth
  without help from the compiler.
