## From text to bytes, with holes

The back end's work is done: instructions chosen, registers given out,
the order tuned, the little wastes swept away. What it has produced is
still text, though, and a processor reads bytes. Worse, real programs
come in pieces: our function lives in one file, the code that calls it
in another, and the data it reads in a third place, and nobody knows
yet at which addresses they will end up in memory. Three programs turn
the pieces into something that runs: the **assembler**, the **linker**
and the **loader**. This chapter covers the first, and the file it
writes; the next covers the other two.

(As chapter 225 said, Viscosity has no native back end; it hands
JavaScript to an engine. Every native compiler, however, from clang to
rustc, ends with exactly these steps, and we can watch them here with
LLVM's own tools.)

## The assembler

For most lines an **assembler** looks up the instruction in the encoding
tables of chapter 225 and writes its four bytes. Here is LLVM's
assembler, `llvm-mc`, doing one line (`-show-encoding` prints the
bytes, lowest first):

```text
$ echo "addi a0, a0, 8" | llvm-mc
    -triple=riscv64 -show-encoding
addi a0, a0, 8  # encoding:
                # [0x13,0x05,0x85,0x00]
```

It also expands **pseudoinstructions**, the convenient names that are
not real instructions: `li a1, 4` becomes `addi a1, zero, 4`, and
`call sumsq` becomes two real instructions, `auipc` and `jalr`, so it
takes 8 bytes rather than 4<Cite id="riscv-asm-manual" />. And it obeys
**directives**, lines starting with a dot that are not instructions at
all: `.text` and `.data` say whether what follows is code or data,
`.globl sumsq` says the name may be used from other files, and
`.dword 1, 2, 3, 4` lays down four 8-byte numbers.

The interesting part is labels. A branch stores the *distance* to its
target, so `blez a1, done` near the top of a function cannot be encoded
until the assembler knows where `done` is, and `done` comes later. The
classic answer is two passes over the text: the first only counts bytes
and writes down every label's address, the second encodes. Step through
it on a small version of our list sum that counts down from `n`:

<Analogy title="a table of contents">
You cannot write "Chapter 5 ........ page 112" at the front of a book
until the book has been laid out, and the contents page comes first. So
you lay out everything once to learn where each chapter falls, then go

<span slot="breaks">A book's page numbers are final once printed. Some
of the assembler's "page numbers" are not: addresses in other files are
not known at all yet, so those are left blank for someone else to
fill.</span>
</Analogy>

<Analogy extra title="a telegraph operator">
An operator turns each letter into dots and dashes from a code table,
one letter at a time, without needing to understand the message.
<span slot="breaks">The operator never has to point to a later part of
the same message; an assembler does, constantly, which is why it needs
labels, two passes and a list of holes.</span>
</Analogy>

LLVM's assembler does not literally read the text twice. Like the
**backpatching** of chapter 81, it encodes what it can at once, keeps a
list of **fixups** for the places it could not finish, and patches them
when the labels are known; with `-show-encoding` you can see one
waiting:

```text
blez a1, done  # [0x63'A',0x50'A',0xb0'A',A]
  # fixup A - offset: 0, value: done,
  #   kind: fixup_riscv_branch
```

The `A`s mark bits not yet known. In the finished file the instruction
is `63 5e b0 00`, a branch 28 bytes forward.

<Callout kind="definition">
An **assembler** translates assembly language into machine code: it
encodes each instruction, expands pseudoinstructions, follows
directives, and resolves labels, either with two passes (one to assign
addresses, one to encode) or with a single pass and a list of fixups
patched at the end.
</Callout>

<Examples of="assembler">

```text
addi a0, a0, 8   →  13 05 85 00
li   a1, 4       →  addi a1, zero, 4
                 →  93 05 40 00
```

```text
call sumsq       →  auipc ra, 0
                    jalr  ra, 0(ra)
(8 bytes, not 4)
```

```text
bnez a1, loop    at 0x1c, loop at 0x08
offset = 0x08 - 0x1c = -20
                 →  e3 96 05 fe
```

</Examples>

The first is a plain instruction and a pseudoinstruction that is really
`addi` from the zero register. The second shows why pass 1 must know each line's *size*,
not only count lines: `call` turns into two instructions. The third is a
backward branch from the listing above; its target was already known
when the assembler reached it, so only forward references need the
second pass or a fixup.

## The object file: what the assembler knows

Now a second file, which calls `sumsq` and passes it the address of a
little table of numbers:

```text
    .text
    .globl _start
_start:
    lui  a0, %hi(table)
    addi a0, a0, %lo(table)
    li   a1, 4
    call sumsq
stop:
    j    stop
    .data
table:
    .dword 1, 2, 3, 4
```

`%hi(table)` and `%lo(table)` ask for the top 20 and bottom 12 bits of
`table`'s address, split exactly as `li` splits a big constant into a
`lui` and an `addi`. But
the assembler does not know `table`'s final address (that depends on
where the linker puts this file's data), and it knows nothing at all
about `sumsq`, which is in the other file. So it writes zeros where the
answers should go, and a note for each one. The result is an **object
file**; on Linux and most Unix systems it uses the **ELF** format, and
`llvm-objdump -d -r` shows its code with the notes:

```text
0: 37 05 00 00  lui   a0, 0x0
     R_RISCV_HI20      table
4: 13 05 05 00  addi  a0, a0, 0
     R_RISCV_LO12_I    table
8: 93 05 40 00  li    a1, 0x4
c: 97 00 00 00  auipc ra, 0x0
     R_RISCV_CALL_PLT  sumsq
10: e7 80 00 00 jalr  ra
```

(trimmed to fit, and `addi a0, a0, 0` is what objdump prints as `mv`).
Each note is a **relocation**. The rest of the file is laid out like
this:

The symbol table is worth reading closely (`llvm-readelf -s main.o`,
trimmed): `table` and `stop` are LOCAL (private to this file), `_start`
is GLOBAL and defined in section 2 (`.text`), and `sumsq` is GLOBAL but
`UND`, undefined: used here, defined somewhere else. (Two extra symbols,
`$x` and `$d`, only mark where code and data start, for
disassemblers<Cite id="riscv-psabi" />.)

<Analogy extra title="a flat-pack kit">
A flat-pack wardrobe comes as bags of parts (sections), a sheet naming
every part (the symbol table), and instructions like "screw panel C to
the side marked D", which you can only follow once D is in front of you
(relocations).
<span slot="breaks">A kit contains every part it needs. An object file
names parts that are in other boxes entirely, like `sumsq`, and trusts
that somebody will bring them.</span>
</Analogy>

<Callout kind="definition">
An **object file** holds machine code and data in named **sections**,
a **symbol table** naming what it defines and what it uses but does
not define, and **relocations**. The ELF standard calls it a
*relocatable file*: code and data "suitable for linking with other
object files to create an executable or a shared object
file"<Cite id="elf-gabi" />. A **relocation** is an entry saying: at
this offset, in this way, write a value computed from this symbol's
final address (plus an addend)<Cite id="elf-gabi" />.
</Callout>

## What a relocation asks for

Each RISC-V relocation type says which bits to patch and how to compute
them. The psABI defines them with a few letters: S is the symbol's
final address, A the addend, and P the address of the place being
patched<Cite id="riscv-psabi" />.

<Formal title="Three RISC-V relocations">

```text
R_RISCV_HI20      (S + A + 0x800) >> 12
R_RISCV_LO12_I    (S + A), low 12 bits
R_RISCV_CALL_PLT  S + A − P
                  (split over auipc + jalr)
```

<span slot="read">HI20 fills a lui with the top 20 bits of the
address, after adding 0x800 so that the low part, read as a signed
number, comes out right. LO12_I fills an addi or a load with the bottom
12 bits. CALL_PLT fills an auipc and jalr pair with the distance from
the call to the function: the function's address, plus the addend,
minus the call's own address.</span>
</Formal>

<Examples of="object-file relocation">

```text
Type    Name
REL     main.o   (a relocatable file)
EXEC    prog     (an executable)
DYN     libx.so  (a shared object)
```

```text
Offset  Type              Symbol
0x0     R_RISCV_HI20      table + 0
0x4     R_RISCV_LO12_I    table + 0
0xc     R_RISCV_CALL_PLT  sumsq + 0
```

</Examples>

The first lists the three kinds of ELF file, by the type in their
header<Cite id="elf-gabi" />; an object file is the first kind. The
second is `llvm-readelf -r main.o`, trimmed: each relocation has an
offset into `.text`, a type and a symbol with an addend (all zero here).
The runnable one does the arithmetic the linker will do, once it has
decided that `table` lives at 0x12198, `sumsq` at 0x11170 and the call
at 0x11164; change the addresses and see how the 0x800 rounding moves
the high part.

One last wrinkle: with *linker relaxation* turned on (`llvm-mc
-mattr=+relax`), even a branch to a local label gets a relocation,
`R_RISCV_BRANCH`, because the linker may later shrink a `call` into a
single `jal` when the target is within a megabyte, which moves
everything after it<Cite id="riscv-psabi" />.

## What you learned

- An **assembler** encodes instructions, expands pseudoinstructions,
  follows directives and resolves labels, in two passes or with fixups.
- What it cannot resolve, it writes into an **object file**: sections,
  a symbol table (local, global, undefined) and relocations.
- A **relocation** names a place, a way to patch it and a symbol; the
  RISC-V psABI gives each type a formula in S, A and P.

Next: the linker, which joins object files and fills every hole, and the
loader, which puts the result in memory and starts it.
