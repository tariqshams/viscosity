## The counter, on the VM

Here is the counter closure from *Return, the host stack and closures*:

```text
fn counter() {
  let n = 0;
  fn count() { n += 1; return n; }
  return count;
}
let a = counter();
print a();   # 1
```

The tree-walker kept `n` in a heap environment. In the VM `n` is a
stack slot, and `return` cuts the stack back to the frame's start, so
the next call writes over it; by the time `a()` runs, `n`'s slot is
someone else's. `count` needs a small object of its own that knows
where `n` is now, and can take the value with it when the slot goes.

<Analogy title="a cloakroom ticket that outlives the cloakroom">
At a party you hand in your coat and get a numbered ticket; you carry
the small ticket, not the coat, and the ticket leads to the coat on its
rail. At midnight the cloakroom shuts, and any coat still there is
moved to a locker, with the locker number written on the same ticket;
you still hold one ticket, and it still finds your coat.
<span slot="breaks">A cloakroom gives each guest their own ticket; two
closures that need one variable hold the *same* ticket, so a change made
through one is seen through the other. And a coat is moved, where a
value is copied, leaving the old slot behind to be written over.</span>
</Analogy>

## Upvalues

That object is an **upvalue** (a value from "up there", in an enclosing
function); each closure carries one per outside variable it uses. The
compiler finds them while compiling: when a name is not a local of the
current function, `resolveUpvalue` looks in the function directly
around it; if the name is a local there, the upvalue captures that slot
(`isLocal` true) and marks the local `isCaptured`. Otherwise it asks one
level further out, by calling itself, and copies the enclosing
function's own upvalue (`isLocal` false). The list is written as byte
pairs after `closure`:

```text
== counter ==
0000    2 const               0 '0'
0003    3 closure             1 fn count
0006    |   local 1
== count ==
0000    3 load.upvalue        0
0002    | const               0 '1'
0005    | add
0006    | store.upvalue       0
```

`local 1` means "capture slot 1 of the running frame", which is `n`;
inside `count`, `n += 1` takes the four steps a local would, with
"upvalue 0" in place of a slot number.

<UpvalueSteps client:visible />

<Callout kind="definition">
An **upvalue** is a closure's handle on a variable declared in an
enclosing function. The compiler resolves upvalues while compiling and
emits one `(isLocal, index)` pair per upvalue after `closure`: when
`isLocal` is true, capture slot `index` of the running frame; when it is
false, reuse upvalue `index` of the running closure. The body reaches
them with `load.upvalue` and `store.upvalue`.
</Callout>

<Examples of="upvalue">

```text
fn outer() {
  let x = 1;
  fn middle() {
    fn inner() { return x; }
    return inner;
  }
  return middle;
}

== outer ==
0003    6 closure             1 fn middle
0006    |   local 1
== middle ==
0000    4 closure             0 fn inner
0003    |   upvalue 0
```

</Examples>

Only `inner` uses `x`, but `inner` is made when `middle` runs, perhaps
long after `outer` has returned, so `middle` must carry `x` for it. `x`
is `outer`'s local 1, hence the pair `local 1` after `closure fn
middle`; then `inner` gets `upvalue 0`, "copy my maker's upvalue 0",
although `middle` never mentions `x`. `print outer()()();` prints `1`.

## Open, then closed

At run time `closure` reads the pairs: a `local` pair calls
`captureUpvalue(frame.slots + index)`, and an `upvalue` pair copies the
running closure's upvalue. An `ObjUpvalue` has three fields, `slot`,
`closed` and `nextOpen`. While `counter` runs, `n` is in its slot, so
the upvalue records the slot's index and `load.upvalue` reads
`stack[u.slot]`: the upvalue is **open**. Two closures made in one call
must share `n`, so the VM keeps open upvalues on one list,
`openUpvalues`, sorted by slot, highest first, and `captureUpvalue`
returns the one already there or links a new one in at its place.

<CaptureSteps client:visible />

<Callout kind="definition">
An **open upvalue** is an upvalue whose variable is still on the stack:
its `slot` is the variable's stack index, and reads and writes go
straight to `stack[slot]`. The VM keeps open upvalues on one list,
sorted by slot, highest first, and a second capture of the same slot
reuses the open upvalue, so closures share one variable.
</Callout>

<Examples of="open-upvalue">

```text
fn outer() {
  let x = 1;
  fn show() { print x; }
  x = 2;
  show();   # 2
}
```

</Examples>

`show` is made while `outer` runs, so its upvalue for `x` is open.
`x = 2` is a plain `store.local 1`, and `show`'s `load.upvalue 0` reads
the same slot and prints `2`, not the `1` there when `show` was made:
the upvalue holds a place, not a copy.

Then `counter` returns, and the slot is about to go. Before it drops
the frame, `return` runs `closeUpvalues(frame.slots)`, which **closes**
every open upvalue pointing into the leaving frame:

```ts
private closeUpvalues(last: number) {
  while (this.openUpvalues &&
         this.openUpvalues.slot >= last) {
    const u = this.openUpvalues;
    u.closed = this.stack[u.slot];
    u.slot = -1;
    this.openUpvalues = u.nextOpen;
  }
}
```

The list is sorted highest first, so the leaving frame's upvalues are
the first ones on it, and the loop stops at the first lower one. Each
gets the value copied into its `closed` field, `slot` set to `-1` ("not
on the stack any more"), and is unlinked. `load.upvalue` and
`store.upvalue` use `u.closed` when `slot` is `-1`, so the closure never
notices: it holds the same object, which now holds the value.

<Callout kind="definition">
A **closed upvalue** holds its variable's value in its own `closed`
field, on the heap, and no longer refers to the stack (its `slot` is
`-1`). The VM closes upvalues just before their slots are given away:
at `return`, every open upvalue at or above the frame's start, and at
`close.upvalue`, the one for the local about to be popped. Closures that
shared an open upvalue share the closed one too.
</Callout>

<Examples of="closed-upvalue">

```text
let a = counter();
print a();   # 1
print a();   # 2
```

</Examples>

`counter()` made `count` with an open upvalue for `n`, and its `return`
closed it, copying `0` into `closed`. The first `a()` sees `slot` is
`-1`, reads `0` from `closed`, and stores `1` back there; the second
finds `1` and leaves `2`. The count lives on long after its slot was
reused.

## A fresh variable every pass

A local declared in a block dies at the block's `}`, so `endScope`
emits `close.upvalue` instead of `pop` for a local marked `isCaptured`
(the VM runs it as `closeUpvalues(this.sp - 1)`, then drops the slot).
That matters most for closures made in a loop. Drip's specification says a `for` loop's
variable is a fresh variable on every pass, and the compiler gets this
from pieces you already have: the loop variable is a local in a scope of
its own *inside* the loop, so its `close.upvalue` sits at the bottom of
the body and runs every pass.

<ClosePassSteps client:visible />

A `while` loop has no such variable. If `i` is a local declared before
the loop, every closure made inside captures the same slot, gets the
same upvalue, and sees the last value:

The body of `for i in 0..3`, pushing a closure that returns `i`:

```text
0020    | load.local          1
0022    3 load.global         3 'push'
0025    | load.global         4 'fs'
0028    | closure             5 fn
0031    |   local 3
0033    | call                2
0035    | pop
0036    4 close.upvalue
0037    2 inc.local           1
0039    4 loop               39 -> 12
```

`load.local 1` copies the hidden counter into slot 3, which is `i`; the
closure captures slot 3; `close.upvalue` closes that pass's upvalue and
frees the slot; and `inc.local 1` adds one to the *counter*, not to `i`,
so assigning to `i` inside the body changes only that pass's `i`.
`break` and `continue` leave the body early, so they emit the same `pop`
or `close.upvalue` for each local they leave, before the jump.

Lua uses the same plan: `luaF_findupval` walks a list of open upvalues
kept in stack order and makes a new one only if there is no match, and
`luaF_closeupval` copies each value into the upvalue itself and unlinks
it<Cite id="lua-lfunc" />. In C an upvalue holds a real pointer into the
stack; TypeScript cannot point into an array, so the companion stores
the slot's index. JavaScript made the same choice as Drip for loop
variables: the specification copies a `for` loop's `let` variables into
a new environment for each pass, so closures made in
`for (let i = 0; i < 3; i++)` see 0, 1 and 2, where `var` gives one

## What you learned

- An **upvalue** is a closure's handle on an outer variable; the
  compiler writes a `local` or `upvalue` pair for each after `closure`.
- An **open upvalue** points at a live slot, on one sorted, shared
  list; closing it makes a **closed upvalue** holding the value itself,
  at `return` and at `close.upvalue`, every pass of a `for` loop.
