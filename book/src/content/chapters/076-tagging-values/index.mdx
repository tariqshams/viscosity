## One stack, many kinds of thing

The stack machine in the chapter "A machine with a stack" only ever
pushed numbers, which made `neg` easy: take the top value, flip its sign,
put it back. Real Drip programs push far more than numbers:

```text
print -(1 + 2) == none;
print !none;
print "tea" + "pot";
```

All of these land in the same stack array, and each instruction has to
treat them differently: `neg` must refuse a string, `add` must add two numbers but join two
strings, and `eq` must say that `1 == "1"` is false rather than true. An
instruction can only do that if every value on the stack can answer one
question the moment it is asked: *what kind of thing are you?* Drip is
dynamically typed (the chapter "Dynamic typing and the language spec"),
so the compiler never works out the answer ahead of time, and the value
itself has to carry it.

<Analogy title="labelled jars in a pantry">
Every jar on the shelf is the same size, and every jar has a label:
"sugar", "salt", "empty". You read the label before you spoon anything
into a cake, because sugar and salt look the same and behave very
differently.
<span slot="breaks">A pantry label can peel off or be wrong; the VM
writes the tag itself, at the moment it makes the value, so the tag is
always right. And an empty jar is still a jar, where Drip's `none`
needs no contents at all, only its label.</span>
</Analogy>

<Analogy extra title="a payment slip with one box ticked">
A paying-in slip has boxes for "cash", "cheque" and "card", and you tick
exactly one; the number written underneath means a cheque number if
"cheque" is ticked and a card number if "card" is, so the clerk reads
the ticked box first and the number second.
<span slot="breaks">A paper slip has room for every kind of number at
once; a tagged value has room for one payload, and which kind it is
depends entirely on the tag.</span>
</Analogy>

## Tagged values

<Figure takeaway="A value is a tag plus a payload." caption="The kinds of Drip value. none needs no payload at all. A boolean or a number fits in the slot. An object (a string, a list, a function) is too big for any fixed slot, so its payload is an address: an arrow to the object on the heap.">
  <ValueBoxes />
</Figure>

You can write that picture down directly in TypeScript, where a tagged
union (the chapter "Tagged unions: the shape of every syntax tree") is
exactly a tag plus a payload:

```ts
type Tagged =
  | { tag: 'none' }
  | { tag: 'bool'; as: boolean }
  | { tag: 'num'; as: number }
  | { tag: 'obj'; as: object };
```

Each line is one kind of value: `tag` names the kind and `as` holds the
payload, and the `none` line has no `as` at all. An instruction checks
the tag first, and TypeScript narrows the payload for it: inside
`if (v.tag === 'num') { ... }` it knows that `v.as` is a number.

<Callout kind="definition">
A **tagged value** is a runtime value stored together with a **tag**
that says what kind of value it is, and a **payload** that holds the
data itself. Every instruction that cares about kinds reads the tag
before it touches the payload. Drip's tags are none, boolean, number and
object, and an object's payload is a **reference** to memory on the
heap.
</Callout>

<Formal title="What a Drip value is">

```text
v ::= none
    | (bool, b)    b ∈ {true, false}
    | (num, x)     x a 64-bit float
    | (obj, a)     a a heap address
```

<span slot="read">A value v is exactly one of four things (the bar
reads "or"): none on its own; the tag bool paired with true or false;
the tag num paired with a 64-bit floating-point number; or the tag obj
paired with an address on the heap.</span>
</Formal>

<Examples of="tagged-value">

```text
print 1 == "1";  # false
```

```text
print !0;        # false
print !none;     # true
```

<Run id="drip-values" />

</Examples>

The first compares a number with a string: the tags differ, so the
answer is `false` (JavaScript's loose `==` would say `true`). The second is truthiness, which
Drip also decides by tag: only `none` and `false` are false, so `!0` is
`false` (the tag of `0` is num, not none or bool) and `!none` is `true`.
The runnable one prints a value of several kinds, then stops on its last
line, the mistake everyone makes once; here it is beside the working
version:

```text
print -3;     # -3
print -"tea";
# runtime error: cannot negate a string
#   at line 2 in script
```

## The tags at work

Here is the first line of the chapter, `print -(1 + 2) == none;`,
compiled by the companion compiler and run on the real stack; the
listing is what the companion's disassembler prints for it. Watch the
tags rather than the numbers.

<StackTagSteps client:visible />

Three rules fell out of that run, and the VM keeps them everywhere:

- **Arithmetic checks tags, and can fail.** `neg` on a string stops
  with `cannot negate a string`; `1 + none` stops with `cannot add a
  number and none`.
- **Equality never fails.** Values with different tags are unequal, so
  `1 == "1"` and `none == false` are both `false`.
- **Truthiness looks at the tag** (and, for a boolean, its payload).

## How the companion VM stores a value

The `Tagged` union works, but in a VM written in JavaScript every
`{ tag, as }` is a fresh object, so `1 + 2` would allocate an object
just to hold `3`, and every read would follow a reference. That is the
HeapNumber problem from the chapter "How JavaScript stores numbers and
objects", rebuilt by hand for every value in the program.

So the companion VM writes no tag at all. Here is its whole value type,
from `vm/object.ts`:

```ts
export type Value =
  null | boolean | number | Obj;
```

`null` stands for Drip's `none`, booleans and numbers are plain
JavaScript values, and `Obj` is a heap object (the next chapter's
subject). The tag is still there, because every JavaScript value already
knows its own type and the engine keeps track of it; reading the tag is
asking JavaScript, with `typeof`. This is the real `neg` case from
`vm/vm.ts` (long lines wrapped to fit the page):

```ts
case Op.Neg: {
  const v = this.peek(0);
  if (typeof v !== 'number')
    this.runtimeError(
      `cannot negate ${describe(v)}`);
  stack[this.sp - 1] = -(v as number);
  break;
}
```

It peeks at the top value without popping it and checks the tag with
`typeof`; on anything but a number it reports an error built by
`describe(v)`, which turns a tag into words (`none`, `a boolean`, `a
string`, `a list`) for every runtime error. Otherwise it overwrites the
top slot with the negated number.

Equality and truthiness each take a single line:

```ts
export const valuesEqual =
  (a: Value, b: Value): boolean => a === b;
export const isFalsey =
  (v: Value): boolean =>
    v === null || v === false;
```

JavaScript's `===` already compares type first and contents second for
numbers, booleans and `null`, which is exactly Drip's rule (including
`nan == nan` being false and `0 == -0` being true, as IEEE 754 says).
For objects it compares identity, which is right for lists and functions
and, once the chapter "String interning" makes equal strings share one
object, for strings too.

<Figure takeaway="The same value can be laid out in different ways." caption="Boxed, every value is an object reached through a reference. The companion VM keeps the JavaScript number in the slot and lets the engine remember its type. The companion's Rust VM uses an enum, with the tag and the payload side by side.">
  <ThreeLayouts />
</Figure>

<Callout kind="definition">
A **value representation** is the layout a runtime chooses for its
values in memory: where the tag lives, where the payload lives, and how
big a slot is. A **boxed** layout puts each value in its own object
behind a reference; an **unboxed** (or **immediate**) layout keeps the
value right in the slot. The companion VM keeps none, booleans and
numbers unboxed, as far as it is concerned, and only heap objects sit
behind a reference.
</Callout>

<Examples of="value-representation">

```ts
// boxed: one object per value
const three = { tag: 'num', as: 3 };
```

```ts
// the companion VM: a plain number
const v: Value = 3;
typeof v; // 'number'
```

```rust
// the companion VM in Rust (Track B)
pub enum Value {
    None,
    Bool(bool),
    Number(f64),
    String(StrRef),
    List(Gc<ObjList>),
    // ...functions, classes, instances
}
```

</Examples>

The first is boxed, a whole object for the number 3. The second is the
companion's: the slot holds `3` itself, and `typeof` reads the tag the
engine keeps. The third is the companion's Rust VM, which you build in
Track B: Rust has no `typeof`, so the tag is written out as an **enum**,
a type whose values are exactly one of the listed variants, each with
its own payload (the `Formal` box above, as code).

One small trap hides in printing: `String(-0)` gives `"0"`, but Drip
prints negative zero as `-0` (and NaN as `nan`), so the shared
`formatNumber` in `runtime.ts` checks for those before handing the rest
to JavaScript.

<Callout kind="engine" label="Under the hood">
"Unboxed as far as the VM is concerned" hides a layer. V8 tags every
slot it stores: small integers are Smis, kept in the slot with a tag
bit<Cite id="v8-pointer-compression" />, and other numbers, such as
`3.5`, can become HeapNumbers on V8's own heap, behind a
pointer<Cite id="v8-react-cliff" />. So the companion VM's values are
tagged twice over, once by meaning (its `Value` type) and once by the
engine underneath. (The disassembler hides tags too:
`print 1 == "1";` lists as `const 0 '1'` and `const 1 '1'`, which look
identical, though the VM never mixes them up.) The chapter "NaN-boxing
and generational collection" squeezes tag and payload into one 64-bit double.
</Callout>

## What you learned

- A dynamically typed VM needs **tagged values**: a **tag** saying the
  kind, and a **payload** holding the data; instructions read the tag
  first.
- Drip's tags are none, boolean, number and object, and an object's
  payload is a reference to the heap.
- Arithmetic checks tags and can fail with an exact message; equality
  compares tags first and never fails; truthiness is decided by tag.
- A **value representation** is the layout of values in memory. The
  companion VM's `Value` is `null | boolean | number | Obj`, so it reads
  JavaScript's own tags with `typeof`, and `valuesEqual` is `===`.

Next: the object tag. Strings and lists cannot fit in a slot, so they
move out to the heap.
