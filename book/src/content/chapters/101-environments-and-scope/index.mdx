## Two variables, one name

At the end of the last chapter every Drip variable lived in one table,
the globals, and that works until someone writes a block:

```text
let a = "global";
{
  let a = "block";
  print a;
}
print a;
```

Drip, like JavaScript<Cite id="mdn-block" />, has block scope, so this
should print `block` and then `global`: the inner `a` is a *different
variable* that happens to share a name, and it should vanish at the
closing `}`. With one table, however, the second `let` overwrites the
first, the program prints `block` twice, and the outer `a` is lost for
good. One table per program is not enough; we need one table per
*block*, and a way for the tables to find each other.

## Environments

<Analogy title="sticky notes on nested folders">
Each folder in a filing cabinet has a sticky note on its cover listing a
few names and numbers, and every folder sits inside a bigger folder. To
add a name you write on the note in your hand; to find one, you read
that note first, and if it is not there you look at the note on the
folder around it, and so on outwards.
<span slot="breaks">You can open any folder in the cabinet; the
interpreter only ever looks outwards from where it is, never into a
folder nested deeper or beside it.</span>
</Analogy>

That picture is a small class. The companion's `runtime.ts` keeps
exactly this data in its `Environment`:

```ts
class Environment {
  values = new Map<string, Value>();
  enclosing: Environment | null;
  constructor(enclosing:
      Environment | null = null) {
    this.enclosing = enclosing;
  }
  define(name: string, value: Value) {
    this.values.set(name, value);
  }
}
```

The `Map` holds this block's names and their runtime values;
`enclosing` is a reference to the parent environment, or `null` for the
globals, which have no parent. `define` only ever touches *this* table,
and it is what `let` calls.

<Callout kind="definition">
An **environment** is a table from names to values, plus a reference to
an **enclosing** (parent) environment. The interpreter always has one
**current** environment, and `let` **defines** a name in the current
environment without looking anywhere else.
</Callout>

## Looking a name up

Reading a variable is where the parent arrow earns its keep. Here is a
lookup that walks the chain (we will meet the companion's faster
version in a moment):

```ts
get(name: string): Value {
  if (this.values.has(name))
    return this.values.get(name)!;
  if (this.enclosing)
    return this.enclosing.get(name);
  throw new RuntimeError(/* token */,
    `undefined variable '${name}'`);
}
```

Check here; on a miss, ask the parent, which checks *its* table and asks
*its* parent, a recursive walk along a chain of references. Only when
the walk falls off the end, past the globals, is the name truly
undefined. `assign` walks the same way and overwrites the first table
that has the name, so it never creates a variable. Step through the
program and watch where each `let` writes and which boxes each lookup
checks:

<EnvSteps client:visible />

<Formal title="Looking a name up">

```text
look(E, x) = E.values(x)    if x in E
look(E, x) = look(P, x)     if not, and
                            E's parent is P
look(E, x) = error          otherwise
```

<span slot="read">To look up the name x starting at environment E: if E
has x, the answer is its value there; if not, and E has a parent P, the
answer is whatever looking x up from P gives; and if E has no parent,
x is undefined, which is an error.</span>
</Formal>

<Callout kind="definition">
The **scope chain** is the line of environments from the current one,
through each parent, to the globals. A lookup walks it and stops at the
**first** environment that has the name; if none does, it is a runtime
error. When an inner environment defines a name that an outer one also
has, the inner variable **shadows** the outer one: inside that block,
the outer variable cannot be reached by name at all.
</Callout>

At home your family calls you "Bee", and anyone saying "Bee" there means

<Examples of="environment scope-chain shadowing">

```text
let n = 1;
{ print n; }   # 1: found one level up
```

```text
let n = 1;
{ n = 2; }     # assign walks out
{ let n = 3; } # a new n, gone at }
print n;       # 2
```

<Run id="shadow" />

</Examples>

In the first, the block's own table is empty, so the lookup walks one
step out and finds the global `n`. The second shows that `let` and `=`
do opposite things to the chain: `n = 2;` walks outwards and changes the
global, while `let n = 3;` makes a new `n` that shadows it and vanishes
at the `}`, so the last line prints `2`. The runnable one has three
levels and an assignment that lands in the middle one.

A common slip is to use the outer value to start the inner one:

```text
let a = 1;
{ let a = a + 1; }
# line 2: cannot read 'a' in its own
# initialiser
{ let b = a + 1; print b; }   # 2
```

Drip refuses the first block before anything runs (a compile error, so
exit code 65), because the inner `a` already exists, unset, while its
own initialiser runs; giving it a different name works. Declaring the
same name twice in one block (`{ let x = 1; let x = 2; }`) is refused
the same way, with `'x' is already declared in this scope`, while at the
top level a second `let` replaces a global. A pass called the resolver
checks these rules, and has its own chapter.

## Entering and leaving a block

The interpreter keeps the current environment in a field, `this.env`. A
block statement makes a fresh environment whose parent is the current
one, and runs its statements inside it:

```ts
case 'block':
  return this.executeBlock(s.statements,
    new Environment(this.env));
```

```ts
executeBlock(statements: Stmt[],
             env: Environment) {
  const previous = this.env;
  this.env = env;
  try {
    for (const s of statements) { /*...*/ }
  } finally {
    this.env = previous;
  }
}
```

Leaving the block means switching back to `previous`; nobody destroys
the block's environment by hand, because once nothing refers to it, it
is garbage like any other unreachable object. The `finally` is there
because a block does not always end at its `}`: a runtime error halfway
through throws straight out, and without the `finally` the interpreter
would be left inside the dead block's environment.

<Callout kind="engine" label="Under the hood">
The walking `get` costs one `Map` lookup per environment on the way up,
every time the line runs. The companion does better: its `Environment`
has `getAt(distance, name)` and `assignAt` instead of `get` and
`assign`, because the resolver works out *before* running how many hops
up each local variable lives, and the interpreter jumps straight there.
It finds the same variable as the walk, only faster. JavaScript's own
scopes form the same chain of outer scopes that inner code can
see<Cite id="mdn-closures" />.
</Callout>

## What you learned

- An **environment** is a table from names to values with a reference
  to its **enclosing** environment; the globals have no parent, and
  `let` defines in the current one only.
- Lookups and assignments walk the **scope chain** outwards and stop at
  the first match; falling off the end is a runtime error.
- An inner variable **shadows** an outer one with the same name until
  its block ends.
- Each block runs in a fresh environment, and `executeBlock` puts the
  old one back in `finally`.
