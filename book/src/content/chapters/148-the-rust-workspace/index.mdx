## The same compiler, twice

In *Core 5: building Viscosity* you built the compiler in TypeScript, in
`engine/ts/packages`: it reads a program, lowers it to VIR, decides which
arrays of objects to turn into columns, and rewrites the source. This
part walks through `engine/rust`, the same compiler written again in
Rust, the way the part before it walked through drip-rs. Two copies of
one compiler raise an obvious worry, however: how would you ever know
they still agree? The port answers with one rule above all the others.
Run both engines on the same program with the same options, and the
rewritten code and the `explain` text must be **equal, byte for byte**;
not "equivalent", not "the same decisions in other words", but equal.

<Analogy title="a translation checked by translating it back">
Picture a translator who knows that every page will be translated back
into the original language and compared word for word. They cannot
paraphrase, drop a hard sentence or quietly fix a mistake in the
original; if the original is wrong, they have to report it and get it
fixed first, so both versions stay identical.
<span slot="breaks">A back-translation is judged by people, who forgive
a synonym; the parity test is a string comparison, which forgives
nothing, not even a missing line break at the end.</span>
</Analogy>

<Analogy extra title="a spare key laid on the original">
A locksmith checks a cut key by laying it on the original, tooth by
tooth, rather than by trying one door: a key that opens today's lock
but differs by a hair may fail next year.
<span slot="breaks">A key is checked once; the port is checked again
after every change to either engine, against 190 pairs of
outputs.</span>
</Analogy>

The rule paid off: of the first ten bugs that porting turned up in the
TypeScript engine, three were soundness bugs (the compiled program
printed something the original did not), and all are now fixed in both
engines.

## Six crates

A **crate** is Rust's unit of compiling (a library or a program), and a
**workspace** is a set of crates built together, as *Modules,
visibility and workspaces* showed. Step through the TypeScript packages
next to the crates that port them:

<WorkspaceSteps client:visible />

Each Rust module ports one TypeScript file: `vir.ts` becomes the `vir`
crate, `plan.ts` becomes `core::plan`, `lower.ts` becomes
`frontend_js::lower`, so every later chapter can hold its Rust up
against a file you already know. (The `frontend-python` crate ports the
Python plugin, which the deep dive *The Python plugin in Rust* covers;
the core chapters stay with JavaScript.)

<Callout kind="definition">
**viscosity-rs** is the Rust implementation of Viscosity, in
`engine/rust`: a cargo workspace of six crates (`vir`, `core`,
`frontend-js`, `frontend-python`, `cli` and `wasm`) that ports the
TypeScript engine module by module. Its contract is **parity**: for
every test program, the same code and the same `explain` text as the
TypeScript engine.
</Callout>

<Examples of="viscosity-rs">

```
$ cargo run --release \
    -p viscosity-cli -- explain p.js
ps (line 1) {x, vx} → struct of arrays
  · loop at line 3 in <module>()
    touches 2 of 2 fields (vx, x)
  · typed Float64Array columns for all
    2 fields
  · about 100 elements
  · 2 of 2 element accesses proven in
    bounds
```

</Examples>

This runs the `viscosity` binary, from the `cli` crate, on a three-line
program that pushes 100 records `{ x, vx }` and then adds `vx` to `x` in
a loop. `-p viscosity-cli` picks the crate, `--release` builds with
optimisations, and everything after `--` goes to the program, not to
cargo. I ran it here with cargo 1.97 (the lines are rewrapped to fit),
and the TypeScript CLI printed the same five lines: the same collection,
the same loop with the fields in the same odd order, the same columns,
size and bounds proofs.

<More title="More: the port as a library">

```rust
use viscosity_core::{compile,
    CompileOptions};
use viscosity_frontend_js::JsPlugin;

let r = compile(src, &JsPlugin,
    CompileOptions::default())?;
println!("{}", r.explain);
```

`compile` from `core`, handed the JavaScript plugin from `frontend-js`,
returns a result whose `explain` field holds the same text, and the `?`

## The root manifest

The root `Cargo.toml` holds no code, only settings the members share.
Trimmed, with long lines rewrapped:

```toml
[workspace.package]
version = "0.0.2"
edition = "2021"
rust-version = "1.97"

[workspace.dependencies]
viscosity-vir = { path = "crates/vir",
    version = "0.0.2" }
oxc_parser = "0.156"
wasm-bindgen = "=0.2.106"
indexmap = "2"

[profile.release]
lto = "thin"
codegen-units = 1
```

A member opts in key by key: `crates/core/Cargo.toml` writes
`version.workspace = true` and `indexmap.workspace = true`, and gets the
root's value<Cite id="cargo-workspaces" />. Inheritance is never
automatic, which is why every member also writes
`rust-version.workspace = true` (oxc 0.156 itself needs Rust 1.97). The
`viscosity-vir` entry carries a `path` and a `version`: cargo uses the
path inside the workspace and the version once the crate is published
(the crates on crates.io are at 0.0.1; the workspace has moved on to
0.0.2)<Cite id="cargo-specifying-deps" />.

A plain requirement such as `"0.156"` accepts later releases only while
the leftmost number that is not zero stays the same, so it means 0.156.x
and nothing newer; that matters because oxc's syntax tree changes
between such releases. The `=` in `"=0.2.106"` accepts one version and
nothing else: the `wasm-bindgen` command-line tool refuses a `.wasm`
file built with a library whose "schema version" differs from its
own<Cite id="wasm-bindgen-schema" />, so the library is pinned to the
tool it is built with.

<Formal title="What a version requirement accepts">

```text
"2"         ≡  ≥ 2.0.0,   < 3.0.0
"0.156"     ≡  ≥ 0.156.0, < 0.157.0
"0.0.2"     ≡  ≥ 0.0.2,   < 0.0.3
"=0.2.106"  ≡  exactly 0.2.106
```

<span slot="read">A plain requirement is a caret requirement: any later
version is accepted as long as the leftmost number that is not zero
stays the same. So "2" takes any 2.x, "0.156" takes only 0.156.x, and
"0.0.2" takes only 0.0.2 itself. An equals sign accepts one version and
nothing else.</span>
</Formal>

Profiles live only in the root manifest; cargo ignores them in
members<Cite id="cargo-workspaces" />. The release profile asks for
"thin" link-time optimisation, which optimises across crates but runs
much faster than the full kind<Cite id="cargo-profiles-debug-lto" />,
and for one codegen unit, since splitting a crate into more units may
produce slower code<Cite id="cargo-profiles" />.

<More title="More: .cargo/config.toml">

One more file changes how the workspace builds, quoted whole:

```toml
# Debug info off: the build is much
# smaller and faster to link.
[profile.dev]
debug = 0

[profile.test]
debug = 0
```

This is not a manifest but cargo's configuration, which cargo looks for
in the directory you run it from and in each parent
directory<Cite id="cargo-config" />, and its `[profile]` tables
override the manifest's. `debug = 0` means no debug information, where
the dev profile's default is full debug
information<Cite id="cargo-profiles-debug-lto" />, which keeps
`target/` several times smaller (the price: backtraces lose file and
line). Run cargo from outside `engine/rust`, with `--manifest-path`,
and this file is not read at all.

</More>

## What the crates pull in

`core` adds two dependencies, both about one TypeScript habit. A
JavaScript `Map` visits its keys in the order they were inserted, the
analyses loop over maps and sets, and that order decides the order of
the lines in `viscosity explain`. Rust's `HashMap` visits keys "in
arbitrary order"<Cite id="rust-std-hashmap" />, and it is seeded
randomly, so the order can change from one run to the next. So wherever
order can be seen, the port uses `IndexMap` and `IndexSet`, which keep
insertion order as `Map` does<Cite id="indexmap-docs" />. Where it
cannot be seen, the port wants speed: `rustc-hash` is the hash that
`rustc` itself uses, faster because it gives up std's resistance to
denial-of-service attacks, which a compiler does not
face<Cite id="rustc-hash-readme" />. Files import it under std's names,
so the code reads as if it were std's (from `lower.rs`, rewrapped):

```rust
use rustc_hash::{FxHashMap as HashMap,
    FxHashSet as HashSet};
```

## The parity test

Here is how "byte for byte" is checked:

<Figure takeaway="The TypeScript engine writes the answers; the Rust engine is marked against them." caption="scripts/gen_expected.mjs runs the TypeScript engine over every program and writes tests/expected; crates/cli/tests/parity.rs compiles the same programs with the Rust engine and compares the strings.">
  <ParityLoop />
</Figure>

Each test program is compiled with the default options and with
`--bounds assume`, and each result is two files, the code and the
explain text, so `basic_soa.js` from the corpus gives
`corpus_basic_soa.js`, `corpus_basic_soa.explain.txt` and the same two
with `.assume` in the name. Nobody writes those files by hand: the
TypeScript engine *is* the expectation, so after every change to it you
run `node scripts/gen_expected.mjs`, then `cargo test`, and the parity
test shows where the port must follow. *Emitting JavaScript from Rust,
and round trips* reads the test itself; on my run here it printed
`parity: 190/190 (54 Python)`.

## What you learned

- **viscosity-rs** is `engine/rust`: six crates that port the
  TypeScript engine module by module, held to byte-for-byte **parity**.
- The root `Cargo.toml` shares settings with `key.workspace = true`, key
  by key. `"0.156"` means 0.156.x only, and `"=0.2.106"` means exactly
  that version.
- Order is visible in `explain`, so the port uses insertion-ordered
  **IndexMap** where TypeScript used `Map`, and fast **FxHashMap**
  elsewhere.
- The fixtures are the TypeScript engine's own output; `parity.rs`
  compares, and reports the first differing line.
