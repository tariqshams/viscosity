## Same data, three ways

For several chapters you have heard that layout matters; now we
measure it. This book's repository has a benchmark harness that stores the same
particles (`x`, `y`, `vx`, `vy`, `mass`, `health`) in several ways and
runs the same loops over each; here are the three that matter most, each
reading particle `i`'s `x`:

```js
// aos: an array of objects
ps[i].x
// aos-packed: one Float64Array, 6 per item
f[i * 6 + 0]
// soa: one Float64Array per field
x[i]
```

All three hold identical numbers; only where they sit in memory
changes. The first is how everyone writes it. The second keeps record
order but packs each particle's six fields into one long
`Float64Array`, so field 0 of particle `i` is at slot `i * 6`. The
third is the struct of arrays from the chapter on arrays of
objects: six separate columns, so `x[i]` is the `x` of particle `i`.

## What each loop actually loads

<Analogy title="meal kits and supermarket aisles">
A meal-kit box holds everything for one dinner: the pasta, the sauce
and the cheese, together. A supermarket keeps all the pasta in one
aisle and all the cheese in another. To cook one dinner, the box wins:
everything is in one place. To buy cheese for fifty dinners, the aisle
wins: you walk down one aisle and fill the basket.
<span slot="breaks">You can pick one item off a shelf; memory always
arrives a whole cache line (64 bytes) at a time, so reading one field
from a record also brings in its neighbours, used or not.</span>
</Analogy>

<Analogy extra title="a class register">
A teacher taking the register goes down one column, "present today",
for the whole class, without opening any pupil's file; at a parents'
evening, the same teacher opens one pupil's file and reads every page.
<span slot="breaks">A register's columns line up because they are
printed on one sheet; in a struct of arrays the columns are separate
arrays, and nothing but your own code keeps entry i of one column
matching entry i of another.</span>
</Analogy>

The loop we care about most is `update-xy`: `x += vx * dt` and
`y += vy * dt` for every particle, which needs four of the six fields.
Step through what each layout drags into the cache to get them:

<Callout kind="definition">
**AoS vs SoA** is the trade-off between keeping each record's fields
together (an array of structs) and keeping each field's values together
(a struct of arrays). AoS suits code that uses whole records; SoA suits
code that uses a few fields of many records. **Packed AoS** is AoS with
raw numbers in one typed array instead of objects.
</Callout>

<Formal title="Where a field lives, and what a loop fetches">

```text
packed AoS:  slot(i, f) = i × F + f
SoA:         slot(i, f) = column f, i
lines(AoS) ≈ n × F × 8 ÷ 64
lines(SoA) ≈ k × n × 8 ÷ 64
```

<span slot="read">With F fields per record, field f of record i is at
slot i times F plus f in packed AoS, and at slot i of column f in SoA.
A loop over n records that reads k of the F fields brings in about
n times F times 8 bytes in AoS, divided by 64 bytes per cache line,
because every field arrives whether it is read or not; in SoA it brings
in only the k columns it reads. For update-xy, F is 6 and k is 4, so SoA
fetches two thirds of the lines that packed AoS does.</span>
</Formal>

<Figure takeaway="SoA only brings in the bytes it uses." caption="Bytes reaching the cache per particle, worked out from the layouts (not measured). Packed AoS brings all 48 bytes of a record whatever the loop reads; SoA brings only the columns it reads.">

</Figure>

<Examples of="aos-vs-soa">

```js
// sum one field: SoA reads one column
let s = 0;
for (let i = 0; i < n; i++) s += mass[i];
```

```js
// one whole record: AoS has it ready
console.log(ps[7]);
// SoA must collect it from six columns
```

```js
// update-xy over columns
for (let i = 0; i < n; i++) {
  x[i] += vx[i] * dt;
  y[i] += vy[i] * dt;
}
```

</Examples>

The first is the best case for SoA: the loop reads one field out of six,
so the `mass` column is all it touches, and every byte it loads is a
mass. The second is the best case for AoS: printing particle 7 wants all
six fields, which an object already has together, while SoA would have
to visit six columns and build something to print. The third is the
loop this book measures most: four columns read, two written, nothing
else touched, each column a contiguous stream the prefetcher can follow.

<OtherLanguages>

```js
// AoS
const ps = [{ x: 0, vx: 1 }];
// SoA
const x = new Float64Array(n);
const vx = new Float64Array(n);
```

```python
# AoS: a list of objects
ps = [P(x=0.0, vx=1.0)]
# SoA: one array per field
x = array('d', [0.0] * n)
vx = array('d', [1.0] * n)
```

```java
// AoS: an array of references
P[] ps = new P[n];
// SoA: one primitive array per field
double[] x = new double[n];
double[] vx = new double[n];
```

```c
/* AoS: structs packed back to back */
struct P { double x, vx; } ps[N];
/* SoA: one array per field */
double x[N], vx[N];
```

</OtherLanguages>

Here the languages genuinely differ. In C, an array of structs is
already *packed AoS*: the structs sit back to back with no headers and
no pointers, so the only difference SoA makes is locality. In Java and
JavaScript, an array of objects is an array of references to separate
objects, each with a header, so moving to primitive arrays (`double[]`,
`Float64Array`) changes the storage as well as the order. In CPython the
`array('d')` columns save a great deal of memory, but this repository's
Python benchmark found them *slower* to loop over, because reading an
element creates a new float object each time; the layout question has a
different answer in a different engine.

## The wins

Here is `update-xy` with 100,000 particles, from this book's committed
benchmark run:

<BenchBars suite="update-xy" n={100000} title="Moving particles: x += vx, y += vy" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa']} caption="SoA is fastest; packed AoS lands in between." />

In that run SoA was about 3.8 times faster than the array of objects, and
packed AoS about 2.1 times. Reading a single field shows the effect more
strongly, because SoA reads exactly one column and nothing else (about
8.5 times faster in the same run):

<BenchBars suite="sum-one-field" n={100000} title="Summing one field (mass)" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa']} caption="One field out of six: SoA loads only what it uses." />

Notice that **packed AoS** already captures a big part of the win. It
keeps the record order, but drops the object headers, the pointer to
each object and the boxed numbers of the last two chapters; so part of
SoA's advantage is *typed storage* (raw doubles in one block), and part
is *locality* (not loading the unused fields), and only the second part
needs SoA. Random order separates them again: the `random-x` suite reads
`x` and `vx` at shuffled indexes, so the prefetcher cannot help, and
with objects every visit is a pointer to chase:

<BenchBars suite="random-x" n={1000000} title="Reading x and vx in shuffled order" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa']} caption="Without a predictable order, the hop to each object dominates; both typed layouts avoid it." />

Here packed AoS and SoA come out almost level, because the big cost was
the pointer chase, and both of them remove it.

## Small collections

With only 1,000 particles, everything fits in cache, and the picture
shrinks:

<BenchBars suite="update-xy" n={1000} title="Moving 1,000 particles" highlight={['soa']} layouts={['aos', 'aos-packed', 'soa']} caption="Small data already fits in cache, so a better layout has fewer misses to remove." />

In this run SoA was still ahead (about 1.7 times), but packed AoS was no
faster than objects at all. A layout change removes cache misses, and a
collection that fits in the cache has few misses to remove; so any
honest rule for choosing a layout has to look at the size of the data,
not only at the loop.

## Hot/cold splitting

You do not have to move every field. If a game's main loop touches `x`,
`y`, `vx` and `vy` every frame, but reads `name` and `health` only on a
menu screen, move only the busy fields into columns.

<Analogy extra title="a desk and a filing cabinet">
The things you use all day (a pen, a notebook, today's papers) live on
your desk, within reach; everything else is in the filing cabinet
across the room. The desk stays small and clear, so the daily work is
fast, and the occasional trip to the cabinet costs little because it is
occasional.
<span slot="breaks">You can carry a file from the cabinet to the desk
whenever you like; a program's split is decided in its code (or, in
Viscosity's case, by the compiler), so if a "cold" field turns out to be
read in a hot loop, the split costs time until it is changed.</span>
</Analogy>

<Callout kind="definition">
A **hot/cold split** separates fields that are used often (hot) from
fields that are used rarely (cold), so that hot loops only stream
through hot data. The hot fields become columns; the cold fields stay
together, at the same index, wherever is convenient.
</Callout>

<Examples of="hot-cold-split">

```js
const hot = {
  x: new Float64Array(n),
  vx: new Float64Array(n),
};
const cold = [{ name: 'a', health: 100 }];
```

```js
// hot loop: columns only
for (let i = 0; i < n; i++) {
  hot.x[i] += hot.vx[i];
}
```

<Run id="hot-cold" />

</Examples>

The first sets up the split: two `Float64Array` columns for the hot
fields, and an ordinary array of objects for the cold ones, where
`cold[i]` belongs to the same particle as `hot.x[i]`. The second is the
loop that runs every frame; it never touches `cold`, so names and health
never pass through the cache. The third puts it together and runs: after
moving every particle, the "menu screen" reads one particle's name from
`cold[i]` and its position from `hot.x[i]`, matched by index, and
prints `cy 9` (three frames of `+3`).

<Callout kind="engine" label="Under the hood">
Choosing a layout means weighing everything in this chapter: how many
elements there are, which fields each loop touches, and whether access
is in order. Mike Acton's 2014 talk on data-oriented design puts the
principle plainly: "If you have different data, you have a different
problem"<Cite id="acton2014" />. Viscosity makes that choice as a
compiler pass, with a cost model fed by exactly these measurements, and
it generates `Float64Array` columns<Cite id="mdn-typed-arrays" /> for
the fields it decides are hot. (Contiguous columns also happen to be
what SIMD code needs<Cite id="ispc-perfguide" />, a door the SIMD
chapter left open.) The next chapter looks at the cases where SoA
*loses*, which the cost model has to spot too.
</Callout>

## What you learned

- **AoS vs SoA** is a trade-off: AoS for whole records, SoA for a few
  fields of many records. In this book's run, SoA won clearly on loops
  that read a few fields, and on shuffled access.
- **Packed AoS** captures part of the win by dropping headers, pointers
  and boxed numbers; SoA adds locality on top, by not loading unused
  fields.
- Small collections barely benefit: data that fits in the cache has few
  misses to remove.
- A **hot/cold split** moves only the busy fields into columns, and
  leaves the rest where they are.
