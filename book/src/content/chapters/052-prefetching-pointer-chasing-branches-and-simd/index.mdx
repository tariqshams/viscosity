## The prefetcher

<Analogy title="a clerk who reads ahead">
A good warehouse clerk notices that you asked for box 10, then 11, then
12, and without being asked puts 13, 14 and 15 on the next van, so they
are on your desk by the time you want them.
<span slot="breaks">You could tell a clerk your plans; the prefetcher
cannot be told anything (in ordinary code), sees only the addresses read
so far, and spots only simple patterns.</span>
</Analogy>

<PrefetchSteps client:visible />

<Callout kind="definition">
The **prefetcher** is hardware that watches which memory a program reads
and fetches the lines it predicts come next, before they are asked for.
It follows simple patterns: forwards or backwards, through several
arrays at once, with small or medium
strides<Cite id="slotin-amh-prefetching" />. The trips to memory still
happen, but they overlap with useful work instead of stalling it.
</Callout>

<Examples of="prefetcher">

```js
for (let i = n - 1; i >= 0; i--)
  x[i] += vx[i];  // two arrays, step -8
s += x[idx[i]];   // shuffled: no pattern
```

</Examples>

The first loop walks two arrays backwards, two steady patterns with a
step of −8 bytes, well within what prefetchers follow; the second reads
in an order no pattern describes, so nothing is fetched ahead.

<More title="Try it: the same sum, in order and shuffled">

The program sums one big `Float64Array` through two index arrays,
`inOrder` (0, 1, 2, …) and `shuffled` (the same numbers mixed up by the
standard fair shuffle); on most machines the shuffled sum is several
times slower.

<Run id="order-matters" />

</More>

<Formal title="What the prefetcher looks for">

```text
a[k+1] − a[k] = d  for the last few reads
⇒ fetch a[k] + d, a[k] + 2d, …
```

<span slot="read">If the last few addresses read each differ from the
one before by the same step d, then fetch the next few addresses in that
pattern ahead of time; d may be negative, for a loop that walks
backwards.</span>
</Formal>

## Pointer chasing

Shuffling hurts objects far more than typed arrays. For `x[j]` the CPU
computes the address from `j` at once, so it can send several reads off
together<Cite id="slotin-amh-mlp" />; for `ps[j].x` the object's address
is *stored in memory*, and must be loaded first.

<ChaseSteps client:visible />

<Callout kind="definition">
**Pointer chasing** is following a chain of pointers, where each load
needs the address produced by the load before it. The prefetcher cannot
predict the addresses and the CPU cannot start the next load early, so
every step waits out the full latency; it is common in structures built
from many small heap objects<Cite id="slotin-amh-latency" />.
</Callout>

<Examples of="pointer-chasing">

```js
s += x[idx[i]];     // address from idx[i]
s += ps[idx[i]].x;  // load ps[j], then .x
// a linked list:
for (let p = head; p !== null; p = p.next)
  s += p.v;
```

</Examples>

The first line can overlap its misses, since every address follows from
`idx`; the second waits for the pointer in `ps[j]` before it can ask for
`x`. A linked list is the purest chase, and walking any tree of objects
(every syntax tree this book builds) is one too.

<More title="A treasure hunt, and the cost of a chase">

<Analogy extra title="a treasure hunt">
Each clue tells you where the next one is hidden; however many friends
you bring, nobody can set off for clue 5 until someone has read clue 4.
<span slot="breaks">Two linked nodes may happen to share a line or still
be cached, and then a step of the chase is cheap.</span>
</Analogy>

<Formal title="Overlapped reads against a chase">

```text
chase:       time ≈ n × t_mem
overlapped:  time ≈ n × t_mem / k
```

<span slot="read">A chain of n reads that each miss takes about n trips
to memory; if the addresses are known up front and the CPU keeps k reads
in flight, the same reads take about k times less.</span>
</Formal>

</More>

## The pipeline

A CPU does not finish one instruction before starting the next. It
splits each into stages and moves every instruction one stage along on
each **tick** of its clock, like a car factory where one car gets its
wheels while the next gets its doors:

<PipelineSteps client:visible />

<Callout kind="definition">
A **pipeline** splits running an instruction into stages (fetch, decode,
execute, write back, and on real chips many more) and works on several
instructions at once, each at a different
stage<Cite id="slotin-amh-pipelining" />. Once it is full, one
instruction can finish on nearly every tick; an instruction that needs
the result of one still in the line has to wait, leaving a gap.
</Callout>

<Examples of="pipeline">

```text
a = b + c
d = e + f    ; independent: no gap
a = b + c
d = a + 1    ; needs a: waits for it
```

</Examples>

The second pair waits because `d = a + 1` cannot execute until `a`
exists; a running sum `s += v` is a chain of such waits, while the work
around it (reading the next `v`, moving the loop on) flows past.

<Formal title="Ticks for n instructions through S stages">

```text
no pipeline:  n × S
pipeline:     S + (n − 1)
```

<span slot="read">Without a pipeline each of n instructions takes all S
ticks; with one, the first takes S ticks and one more finishes every
tick after that. With 4 stages, 100 instructions take 400 ticks or
103.</span>
</Formal>

## Guessing the way of an if

Sum the elements of an array of random numbers from 0 to 99 that are
below 50, then sort the array and do it again. The work is identical,
yet in a well-known experiment in compiled C++ the sorted version ran
several times faster<Cite id="slotin-amh-branching" />. The comparison
is only worked out several stages into the pipeline, and by then the CPU
wants to have fetched the next instructions; it cannot know which side
of the `if` they come from, so it guesses.

<BranchSteps client:visible />

<Callout kind="definition">
**Branch prediction** is the CPU predicting which way a branch will go
and carrying on along that path before it knows. On a wrong guess, the
work done on the wrong path is thrown away and the pipeline refills from
the right one<Cite id="apple-wwdc25-cpu" />. Predictors learn from how
each branch went before, so branches that nearly always go one way cost
almost nothing, and branches with no pattern are where they go wrong.
</Callout>

<Examples of="branch-prediction">

```js
for (const v of xs) {
  if (v < 50) s += v;
}
```

</Examples>

Over random data the guess is wrong about half the time; over sorted
data the `if` is true for a long run and then false, one switch in all.
A loop's own test `i < n` is wrong once, at the end, and an error check
that never fires is nearly free. (In JavaScript the effect depends on
the machine code the engine generates, which may not branch at all, so
measure.)

## SIMD: one instruction, several numbers

The particle update `x[i] = x[i] + vx[i]` is a million independent
additions, and most CPUs can do several with one instruction, using
**wide registers** that hold several numbers at once.

<LaneSteps client:visible />

<Callout kind="definition">
**SIMD** (*single instruction, multiple data*) is one instruction
applying the same operation to several values at once. The values sit in
a wide **vector register**, and each slot of it is a **lane**; a SIMD add
adds lane 0 to lane 0, lane 1 to lane 1, and so on, and lanes never mix.
The lane count is the register's width divided by the element's size.
</Callout>

<Examples of="simd lane">

```text
128 ÷ 64 = 2 lanes of float64
128 ÷ 32 = 4 lanes of float32
f64x2.add   two float64 adds at once
```

</Examples>

JavaScript numbers are 64-bit doubles, so a 128-bit register holds two
of them; WebAssembly (the low-level code format browsers and Node run
beside JavaScript) spells the shape in its instruction names, lane type
before the `x` and lane count after it<Cite id="wasm-simd" />. Some x86
chips have 256- and 512-bit registers as well<Cite id="ispcdocs" />.

## Vectorisation, and why it wants columns

You rarely write SIMD by hand; instead, an optimising compiler rewrites
an ordinary loop to handle several turns per step (LLVM's loop
vectoriser is on by default<Cite id="llvm-vectorizers" />), but only
when that cannot change the answer.

<LaneSumSteps client:visible />

<Callout kind="definition">
**Vectorisation** is rewriting a loop so that each step processes
several elements with SIMD instructions, one per lane, plus a **tail**
for the leftovers. A compiler does it only when the result is unchanged,
or when you have allowed it to change<Cite id="llvm-vectorizers" />.
</Callout>

<Examples of="vectorization">

```js
for (let i = 0; i < n; i++)  // safe
  c[i] = a[i] + b[i];
for (let i = 1; i < n; i++)  // not safe
  x[i] = x[i - 1] + 1;
(0.1 + 0.2) + 0.3; // 0.6000000000000001
0.1 + (0.2 + 0.3); // 0.6
```

</Examples>

In the first loop element `i` depends only on element `i`, so four at a
time gives the same answer; in the second, `x[1]` needs the new `x[0]`.
The last two lines are why a floating-point sum is not vectorised
freely: lanes regroup the additions, each addition rounds, so LLVM does
it only when you allow reordering (it also checks at run time that the
arrays do not overlap).

A vector load copies one **contiguous** run of memory into a register,
which an array of structs does not have:

<Figure takeaway="SIMD needs the values for its lanes side by side." caption="In an array of structs (top), each x is 6 slots from the next, so filling four lanes takes a gather of four separate reads. In a struct of arrays (bottom), the x column is contiguous, and one vector load fills the register.">

</Figure>

An array of structs needs gathers and runs
slower<Cite id="ispc-perfguide" />; the struct of arrays is the layout
the prefetcher, the pipeline and SIMD lanes all want.

## What you learned

- The **prefetcher** fetches lines ahead along simple patterns; reads
  whose addresses are known up front can overlap even when shuffled.
- **Pointer chasing** defeats both, since each address arrives only with
  the previous load.
- A **pipeline** overlaps instructions; **branch prediction** keeps it
  full by guessing, and pays when data has no pattern.
- **SIMD** works on several **lanes** at once; **vectorisation** needs
  independent turns and **contiguous** columns.
