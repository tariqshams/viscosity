## The silent optimiser

You run Viscosity on your program, and it gets no faster. Was there
nothing to do? Did it try and give up? Did it transform the wrong array?
An optimiser that only hands back code leaves you reading generated
code to find out. So Viscosity has a second output; here is a corpus
program, `escapes_log.js`, and what `viscosity explain` says about it:

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, y: i });
for (let i = 0; i < ps.length; i++)
  ps[i].x += 1;
console.log(ps[3]);
```

```text
ps (line 2) {x, y} → kept as array of
  objects
  · unsafe: line 5: an element is passed
    to a method call
```

(The real file has a test header on line 1 and each loop on one line;
every report in this chapter is real CLI output, with long lines
wrapped.) One line, and you know what to change: `console.log` receives
a real element object, so the object has to exist.

<Analogy title="an itemised garage bill">
A mechanic who says "fixed it" is less use than one who hands you an
itemised bill: what they replaced, what they checked and left alone, and
why. You can check the list, and next time you know what to ask for.
<span slot="breaks">A mechanic writes the bill after the work and could
leave something out; Viscosity's report is not written afterwards at
all, as we will see, which is the whole point.</span>
</Analogy>

## Anatomy of a report

A transformed collection has a longer report. This one is for
`mixed_columns.js`, which keeps strings, numbers, `null` and objects in
its fields:

```text
es (line 2) {id, hp, x, tag} → struct of
  arrays
  · loop at line 5 in <module>() touches
    3 of 4 fields (hp, tag, x)
  · loop at line 12 in <module>() touches
    2 of 4 fields (hp, x)
  · typed Float64Array columns for hp, x;
    plain array columns for id, tag (may
    hold non-numbers)
  · about 300 elements
  · 4 of 9 element accesses proven in
    bounds
```

## The planner writes the reasons

Here is `explain()` from `core/src/plan.ts`, simplified (the real one
can also print code frames, below):

```ts
function explain(p) {
  const lines = [];
  for (const cp of p.collections) {
    const c = cp.collection;
    const fs = c.fields.join(', ');
    lines.push(`${c.name} (line ` +
      `${c.line}) {${fs}} → ` +
      verdict(cp));
    for (const r of cp.reasons)
      lines.push(`  · ${r}`);
  }
  return lines.join('\n');
}
```

It analyses nothing. It prints `cp.reasons`, a list of strings the
planner filled in at the moment it decided: every place `plan()` keeps a
collection goes through `keep(...)`, which takes the reason, so a kept
collection always says why.

```ts
if (c.numericFields.size === 0) {
  out.push(keep('no field is provably ' +
    'numeric, so there are no typed ' +
    'columns to gain'));
  continue;
}
```

A report computed afterwards, by a separate function guessing what the
planner probably did, could go out of date the first time someone
changed the planner; one built from the decision itself cannot.

<Analogy extra title="marks written in the margin">
A teacher who writes "missing units, minus one" beside the answer at the
moment of taking the mark off leaves a record that cannot disagree with
the mark; a teacher who tries to remember the reasons a week later may
well get them wrong.
<span slot="breaks">A teacher can still make a slip of the pen; the
planner's reason is the very value it acted on, so there is nothing to
copy wrongly.</span>
</Analogy>

<Callout kind="definition">
An **optimisation report** is a compiler output, alongside the code,
that explains every decision it made: what it changed, what it left
alone, and the evidence for each. It is most trustworthy when the
decision procedure records its own reasons as it runs.
</Callout>

<Formal title="The shape of a report">

```text
report  → entry*
entry   → header reason+
header  → NAME "(line" N ")" "{" fields "}"
          "→" verdict
reason  → "  · " TEXT frame?
```

<span slot="read">A report is any number (the star) of entries, one per
collection. Each entry is a header followed by one or more (the plus)
reasons. A header is the name, its line, its fields in braces, an arrow
and the verdict. A reason is two spaces, a dot, a space and the text,
optionally (the question mark) followed by a code frame.</span>
</Formal>

## Why it was kept

The planner tries its checks in a fixed order, and a kept collection's
report names the check that stopped it. Safety comes first and lists
every unsafe use found, so you can fix them all at once; after that the
first failing check is the reason: a bad `aosoa` request, an
`@viscosity aos` annotation, opt-in mode, Python without opting in, no
numeric field, no loop over the fields, and finally the size threshold.
`viscosity explain --frames` adds, under each unsafe use, the source
line with carets under the code it is about:

## A report is a contract

Because the report is text, it can be tested like code, and three places
in the repository do. The **differential test** from *Testing
compilers* passes `r.explain` as the failure message when a decision is
wrong, so a failing test says why Viscosity decided what it did. The
**mini-parser test** compiles every corpus and benchmark program with
both parsers and requires byte-identical reports, not only code. And for
the **Rust port**, the reference's report and compiled code are stored
for every test program in both bounds modes, plus fourteen `--frames`
reports; run for this chapter, the parity test printed
`parity: 190/190 (54 Python)`, and its frames test passed. Changing a
word in a reason is therefore a visible diff in a review, which is
deliberate: if people read the reports, the reports are part of the
interface.

## What you learned

- An **optimisation report** explains every decision: what changed,
  what was kept, and the evidence; `viscosity explain` prints a verdict
  line per collection, then one `·` line per reason (`--frames` adds the
  code).
- The planner records the reasons as it decides, and `explain()` only
  prints them, so the report cannot drift from the decision.
- The report is tested byte for byte, as part of Viscosity's interface.
