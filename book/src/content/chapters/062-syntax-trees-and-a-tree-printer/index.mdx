## A flat line of tokens

The scanner turns `-2 * (3 + 4)` into a flat row of eight tokens. That
is not how you read it: you see a multiplication whose left side is
"minus 2" and whose right side is a whole addition. The meaning is
nested, and before Drip can run it the nesting must be written down as
a tree the interpreter can walk. The parse tree from *Grammars and parse
trees* is one such tree, but it is cluttered, with a node for every
helper rule and every token, including the `;`.

<Analogy title="a train map">
An underground train map shows the stations and which lines join them,
and nothing else: no streets, no true distances, no bends in the
tunnels. It is less faithful than a photograph from above, and far more
useful for getting from one station to another.
<span slot="breaks">A train map bends the truth about distances to look
tidy; an abstract syntax tree drops details, but never changes what the
program means.</span>
</Analogy>

<Callout kind="definition">
An **abstract syntax tree** (**AST**) is a program stored as nested
nodes, keeping only what affects its meaning. Each **AST node** is one
construct of the language: a **kind** (such as binary, literal or
print) plus its **children**, the smaller nodes it is made of, and any
tokens or values it needs to remember.
</Callout>

<Examples of="ast ast-node">

```js
// print 1 + 2;
{ kind: 'print', expression: {
  kind: 'binary', operator: '+',
  left: { kind: 'literal', value: 1 },
  right: { kind: 'literal', value: 2 } } }
```

</Examples>

Four nodes, each a plain object with a `kind`. The print node's
`expression` field holds a binary node, which remembers its operator
and holds two literal nodes, leaves with no children, in `left` and
`right`. Nothing is left of the `;`, and of `print` only the node's
kind. (In the companion, operators are whole tokens rather than strings,
so that a later error can say which line they came from.) Step through
how the tokens of a print statement become nodes, a kind, a remembered
value, or nothing at all:

## Expr: a discriminated union

You built a tree type like this in *Tagged unions: the shape of every
syntax tree*. Drip's has more kinds; here are the first few, from
`companion/ts/src/ast.ts`:

```ts
type Expr =
  | { kind: 'literal';
      value: number | string
           | boolean | null }
  | { kind: 'grouping'; expression: Expr }
  | { kind: 'unary';
      operator: Token; right: Expr }
  | { kind: 'binary'; left: Expr;
      operator: Token; right: Expr }
  | { kind: 'variable'; name: Token };
  // ...and twelve more kinds
```

Checking `e.kind === 'binary'` narrows `e` to that variant, so the
type checker knows it has a `left`. The keywords `true`, `false` and
`none` become literals holding `true`, `false` and `null`; and
`grouping`, for brackets, is not needed for the meaning (the tree's
shape already says that `3 + 4` happens first), but it lets a printed
tree show where the brackets were.

<Formal title="The abstract grammar of Drip’s simplest expressions">

```text
Expr ::= Literal(value)
       | Grouping(Expr)
       | Unary(op, Expr)
       | Binary(Expr, op, Expr)
       | Variable(name)
```

<span slot="read">An expression tree is one of five kinds of node: a
Literal holding a value, a Grouping holding one expression, a Unary
holding an operator and one expression, a Binary holding an expression,
an operator and another expression, or a Variable holding a name. It is
a grammar for trees rather than for token rows: it says what shapes of
node are allowed, not which tokens come in which order.</span>
</Formal>

</More>

## Expressions and statements

An expression *produces a value*: `1 + 2`, `x`, `"hi"`. A statement
*does something*: prints, declares a variable, loops. Statements get a
union of their own, `Stmt`, with kinds such as `print`, `let`, `block`
and `if`; statements contain expressions, some contain other statements
(a block holds a list), and a whole program parses to an array of them,
`Stmt[]`.

<Figure takeaway="Statements hold expressions; expressions never hold statements." caption="The tree of if x > 1 { print x * 2; } The if node, its block and the print node are statements (square corners). Everything that has a value, from the comparison down to the literal 2, is an expression (round corners).">
  <StmtExprTree />
</Figure>

<Callout kind="definition">
An **expression** is code that produces a value. A **statement** is
code that is run for its effect, such as printing or declaring a
variable. An **expression statement** is an expression followed by `;`,
run for its effect with its value thrown away.
</Callout>

<Examples of="expression-vs-statement">

```
f(1)    # expression: the call's value
f(1);   # expression statement
let x = print 1;
# line 1: expected an expression,
#   found 'print'
```

</Examples>

A call produces a value, so `f(1)` is an expression; on a line of its
own with a `;` it is an expression statement, run for what the call
does. The last line puts a statement where an expression is expected:
a `let` needs something with a value after `=`, and `print 1` is a
statement, so the parser stops at `print`.

<More title="Drip's Stmt type">

```ts
type Stmt =
  | { kind: 'expression'; expression: Expr }
  | { kind: 'print'; expression: Expr }
  | { kind: 'let'; name: Token;
      initializer: Expr | null }
  | { kind: 'block'; statements: Stmt[] }
  | { kind: 'if'; condition: Expr;
      then: Stmt; else: Stmt | null }
  // ...while, for, break, continue,
  // fn, return, class
```

`null` means "not there": a `let` with no `= ...` has a `null`
initialiser, and an `if` with no `else` a `null` else.

</More>

## A printer you can read

A tree lives in memory as objects pointing at objects; `JSON.stringify`
prints the tree of `1 + 2` as over a hundred characters of braces and
field names, and the shape is lost. We want a printer that shows shape
and nothing else.

<Analogy extra title="a waiter reading your order back">
A good waiter repeats your order before going to the kitchen, in a
fixed, short form, so that a mistake jumps out while it is still cheap
to fix.
<span slot="breaks">A waiter reads the order back to *you*; a tree
printer is for whoever wrote the parser, checking that the program
understood the source the way they meant.</span>
</Analogy>

```ts
function printExpr(e: Expr): string {
  switch (e.kind) {
    case 'literal':
      return e.value === null
        ? 'none' : String(e.value);
    case 'grouping':
      return '(group ' +
        printExpr(e.expression) + ')';
    case 'binary':
      return '(' + e.operator.lexeme +
        ' ' + printExpr(e.left) +
        ' ' + printExpr(e.right) + ')';
    // ...a case for every kind
  }
}
```

The literal case is the base case: `String(2)` is `'2'`, and `none`,
stored as `null`, prints as `none`. The binary case glues together a
bracket, the operator's lexeme, the left child's string, the right
child's string and a closing bracket; the children's strings come from
calling `printExpr` on them, because each child is a whole tree. Step
through it on `-2 * (3 + 4)`, watching the calls wait on the stack:

<Callout kind="definition">
A **tree printer** turns a tree back into text so a person can check
it. Drip's prints every node as `(operator children...)`: the brackets
show the tree's shape exactly, with no precedence rules to remember.
</Callout>

<Examples of="tree-printer">

```text
-x * 3       prints  (* (- x) 3)
(1 + 2) * 3  prints  (* (group (+ 1 2)) 3)
```

</Examples>

In `-x * 3` the minus binds to `x` alone, so the `*` node is the root
with `(- x)` as its left child (a variable prints as its name); in the
second, the brackets survive as a `group`. Why not print `1 + 2 * 3` as
it was written? Because then two different trees would print as the
same text, which is the ambiguity from *Grammars and parse trees*:

<Figure takeaway="Operator-first brackets never print two trees the same way." caption="Two trees for the tokens 1 + 2 * 3. Printed plainly, from left to right, both give the same text, so the printout cannot tell you which tree the parser built. Printed Drip's way, every node is one pair of brackets with its operator first, and the two trees cannot be confused.">
  <TwoPrints />
</Figure>

With the printer, a parser test is one line:
`expect(show('1 + 2 * 3')).toBe('(+ 1 (* 2 3))')`.

<More title="Every kind or the checker complains, and the printer at work">

The real `printExpr` has a case for all seventeen kinds of `Expr` and
no `default`, on purpose: if someone adds a kind and forgets its case,
TypeScript notices that the `switch` can finish without returning a
string (*error TS2366: Function lacks ending return statement*). A
`default:` that returned `'?'` would silence that check. The printer is
not meant to give back the source: `x += 1` prints as `(+= x 1)`, and
`f(a, 1 + 2)` as `(call f a (+ 1 2))`.

<Run id="showTrees" />

Printing a tree back as text is called *pretty printing*, and a code
formatter can work by parsing a program and printing it again in a
fixed style. ESTree, the tree format many JavaScript tools share, tags
every node with a string `type` field, the same idea as Drip's
`kind`<Cite id="estree" />.

</More>

## What you learned

- An **AST** stores a program as nested nodes, each a **kind** plus
  children, keeping what affects its meaning.
- Drip's `Expr` and `Stmt` are discriminated unions tagged by `kind`.
- **Expressions** produce values; **statements** do things; an
  expression with a `;` is an expression statement.
- A **tree printer** writes each node as `(operator children...)`, so
  two different trees never print the same way.
