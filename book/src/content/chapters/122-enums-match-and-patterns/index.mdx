## One of several things

Your TypeScript Drip VM spelled "this is one of several things" three
ways: the dispatch loop switched on opcode numbers, a Drip value was
`null | boolean | number | Obj` told apart with `typeof`, and a syntax
tree node was an object with a `tag` field (*Tagged unions: the shape of
every syntax tree*). Rust has one feature for all three, and the
compiler checks every use of it.

<Analogy title="a parcel form with tick boxes">
A courier's form has tick boxes: *letter*, *parcel*, *registered*. You
tick exactly one. Some boxes come with a blank to fill in ("registered:
tracking number ____"), and that blank only exists if you ticked its
box; nobody can read a tracking number off a plain letter.
<span slot="breaks">On paper you can tick two boxes or none, and the
courier has to sort it out; a Rust value is always exactly one variant,
and the compiler will not build one that is two or none.</span>
</Analogy>

## Enums

<Examples of="enum">

```rust
enum Value {
    None,
    Bool(bool),
    Number(f64),
}
enum Shape {
    Circle(f64),
    Rect { w: f64, h: f64 },
}
let v = Value::Number(2.5);
let s = Shape::Rect { w: 2.0, h: 3.0 };
```

</Examples>

`Value` is cut down from the Rust Drip VM's (`companion/rust/src/value.rs`
adds strings, lists, functions and other heap objects). A `Value` is
exactly one of three variants, and two carry data: `Bool` holds a
`bool`, `Number` an `f64`. A variant's data may also be named fields, as
`Rect` has. You name a variant with the enum, two colons and the variant
(`Value::None` is Drip's `none`, unrelated to Rust's own `None`, which
is the next chapter). In memory, a value is a tag saying which variant,
then room for the largest payload, so every `Value` has one size:

<Figure takeaway="An enum value is a tag plus room for the largest payload." caption="Drawn in the classic tag-and-payload layout. The default layout leaves the exact arrangement to the compiler, but rustc 1.97 reports 16 bytes for this Value: room for an 8-byte f64 and a tag.">
  <EnumLayout />
</Figure>

Enums are best at making a wrong state impossible to build. The VM's
`enum ObjUpvalue { Open(usize), Closed(Value) }` is a captured variable
either still in a stack slot or closed over its value, and a closed
upvalue that still has a slot cannot exist, because no variant has both.

<Callout kind="definition">
An **enum** is a type whose every value is exactly one of a fixed list of
**variants**. A variant may carry data: values in brackets, like
`Number(f64)`, or named fields, like a struct, `Move { dx: f64 }`. An
enum with data is Rust's discriminated union: the variant is the tag and
its data is the payload<Cite id="rust-book-enums" />.
</Callout>

## match

To use an enum value you ask which variant it is and take its data out,
with `match`. Each **arm** is a pattern, `=>` and the code to run;
`Value::Number(x)` fits any `Number` and names its payload `x` for that
arm. Step through two values:

<MatchSteps client:visible />

Arms are tried top to bottom and the first that fits wins, with no
falling through, so no `break` to forget. A `match` is an expression,
like `if`, so every arm must produce the same type (or E0308, "`match`
arms have incompatible types"). Above all, it must cover **every**
possible value; leave out `Value::Bool(false)` and rustc 1.97 says
(trimmed):

```text
error[E0004]: non-exhaustive patterns:
  `Value::Bool(false)` not covered
help: ensure that all possible cases are
  being handled by adding a match arm ...
12 ~         Value::Bool(false) => todo!(),
```

The `help` even writes the missing arm. In TypeScript, the check that
every case of a union is handled is something you set up with a `never`
default (*TypeScript II: unions and narrowing*); in Rust it is always a
hard error<Cite id="rust-book-match" />. That is why the Rust Drip VM's
dispatch loop, one `match op` with an arm per opcode and no catch-all,
stops compiling the moment someone adds an opcode the VM does not yet
handle.

`show` turns each variant into text, binding the payload as `b` or `n`;
`truthy` is Drip's truthiness, with `Value::Number(_)` fitting any
number without naming it. Both `match`es are the last expression of
their function, so their value is returned. Delete an arm and read what

<Callout kind="definition">
A **`match`** expression compares a value with the patterns of its
**arms**, in order, and runs the first arm that fits<Cite id="rustref-match" />.
Its value is that arm's value, so all arms have the same type. It must
be **exhaustive**: every possible value has to fit some arm, or the
program does not compile.
</Callout>

## Patterns

The left of an arm can say far more than a variant name. A scanner asks
whether a byte is a digit, a letter or a space; step a few bytes through
one `match`:

<ByteSteps client:visible />

`b'0'..=b'9'` is a **range pattern** (both ends included), `p | q` an
**or-pattern**, and `_` the **wildcard**, which fits anything and binds
nothing. Patterns nest, so one can test a tuple of two variants at once:

<Figure takeaway="A pattern says what must be there, and names the parts you want." caption="The kinds of pattern used in this book. Patterns nest: a tuple of variants, a variant holding a struct, and so on.">
  <PatternKinds />
</Figure>

<Examples of="pattern">

```rust
match (a, b) {
    (Value::Number(x), Value::Number(y))
        => Value::Number(x + y),
    _ => Value::None, // the VM: an error
}
match v {
    Value::None
    | Value::Bool(false) => "falsey",
    Value::Number(n) if n < 0.0 => "neg",
    _ => "other",
}
```

</Examples>

The first is Drip's `+`: matching the tuple `(a, b)` asks "are both
numbers?" and binds both payloads in one arm, where TypeScript needs an
`if` with two `typeof` checks. In the second, an or-pattern makes
`none` and `false` one arm, and `if n < 0.0` is a **match guard**, a test
the arm must also pass. `let` takes patterns too, as in
`let (x, y) = (3.0, 4.0);`, but only **irrefutable** ones, which always
fit; `let Value::Number(n) = v;` is **refutable**, so rustc refuses it
(E0005) and suggests `let ... else`. To test one pattern, use
`if let Value::Number(n) = v { ... }`, a one-arm `match`, or
`let Value::Number(n) = v else { return ... };`, which binds `n` for the
rest of the function<Cite id="rust-book-if-let" />.

Two traps. The wildcard covers every case you have not written,
*including variants added later*, so prefer listing variants when each
deserves a thought. And a plain name in a pattern always **binds** a new
variable; it never compares<Cite id="rust-book-patterns" />. With
`let limit = 3;`, the arm `limit => ...` fits anything (rustc warns
"unreachable pattern" for the arms after it, with "there is a binding of
the same name"); write `x if x == limit` instead.

<Callout kind="definition">
A **pattern** describes a shape a value can have, and may **bind**
names to parts of it<Cite id="rustref-patterns" />: literals, ranges
`a..=b`, names (which fit anything and bind it), the wildcard `_`,
alternatives `p | q`, tuples, enum variants and structs, nested inside
one another. A **match guard**, `pattern if condition =>`, adds a test
the arm must also pass.
</Callout>

<More title="More: patterns in a runnable scanner, sums, and discriminants">

<Run id="patterns" />

An enum is a **sum** of its variants, as a struct is a product of its
fields: `enum V { A, B(bool), C(u8) }` has 1 + 2 + 256 = 259 possible
values. Underneath, every enum value has a **discriminant**, an integer
saying which variant it holds, which the compiler may store in a smaller
type or encode some other way<Cite id="rustref-enum" />; the VM's
`OpCode` is marked `#[repr(u8)]`, so each variant is exactly the byte
that encodes it. How rustc turns arms into a tree of tests and proves
nothing is missed is the deep dive *Compiling pattern matching*, and the
layouts are *Sum types in memory*. The VM's `pop_numbers` starts with
`let (Value::Number(a), Value::Number(b)) = (self.peek(1),
self.peek(0)) else { ... }`, which either hands it two numbers or
reports Drip's runtime error.

</More>

<Analogy extra title="a coin-sorting tray">
A coin sorter is a tray of slots, each shaped for one coin. You drop a
coin in at the top; it slides past the slots in order and falls through
the first one it fits. The last slot is wide enough for anything, so no
coin is ever left on the tray.
<span slot="breaks">A coin only has a size; a pattern can look inside a
value (the payload of a variant, the fields of a struct, both halves of
a pair) and can also hand you the pieces it found, by name.</span>
</Analogy>

## What you learned

- An **enum** is exactly one of its **variants**, which may carry data.
- **`match`** runs the first arm that fits, is an expression, and must
  be exhaustive; **patterns** test and bind in one go.
