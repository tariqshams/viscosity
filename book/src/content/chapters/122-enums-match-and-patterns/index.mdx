## One of several things

Your TypeScript Drip VM needed "this is one of several things" in three
places, and spelled it three ways. The dispatch loop switched on opcode
numbers (`case Op.None: this.push(null); break;`); a Drip value was
`null | boolean | number | Obj`, told apart with `typeof`; and a syntax
tree node was a tagged union, an object with a `tag` field naming its
kind (*Tagged unions: the shape of every syntax tree*). Rust has a
single feature for all three, and the compiler checks every use of it.

<Analogy title="a parcel form with tick boxes">
A courier's form has tick boxes: *letter*, *parcel*, *registered*. You
tick exactly one. Some boxes come with a blank to fill in ("registered:
tracking number ____"), and that blank only exists if you ticked its
box; nobody can read a tracking number off a plain letter.
<span slot="breaks">On paper you can tick two boxes or none, and the
courier has to sort it out; a Rust value is always exactly one variant,
and the compiler will not build one that is two or none.</span>
</Analogy>

<Analogy extra title="a traffic light">
A traffic light is red, amber or green, never two at once, and every
driver must know what to do for each colour. A driving test that only
covered red and green would be refused, because amber happens.
<span slot="breaks">A traffic light carries no extra information, while
an enum's variants can carry data (a number, a string, a whole struct),
different for each variant.</span>
</Analogy>

## Enums

```rust
enum Op {
    Const,
    Add,
    Neg,
    Return,
}

enum Value {
    None,
    Bool(bool),
    Number(f64),
}

let op = Op::Add;
let v = Value::Number(2.5);
```

These are cut down from the Rust Drip VM: its `OpCode` (in
`companion/rust/src/chunk.rs`) has 53 variants, and its `Value` (in
`value.rs`) adds variants for strings, lists, functions, classes and
other heap objects. An `Op` is exactly one of four things. A `Value` is
one of three, and two of those carry data: `Bool` holds a `bool`,
`Number` holds an `f64`. You name a variant with the enum's name, two
colons and the variant: `Value::Number(2.5)`. (`Value::None` is Drip's
`none`, unrelated to Rust's own `None`, which comes two chapters on.)

<Callout kind="definition">
An **enum** is a type whose every value is exactly one of a fixed list of
**variants**. A variant may carry data: values in brackets, like
`Number(f64)`, or named fields, like a struct, `Move { dx: f64 }`. An
enum with data is Rust's discriminated union: the variant is the tag and
its data is the payload<Cite id="rust-book-enums" />.
</Callout>

<Examples of="enum">

```rust
enum Dir { North, East, South, West }
let d = Dir::East;
```

```rust
enum Shape {
    Circle(f64),
    Rect { w: f64, h: f64 },
}
let s = Shape::Rect { w: 2.0, h: 3.0 };
```

```rust
// from companion/rust/src/object.rs
pub enum ObjUpvalue {
    Open(usize),
    Closed(Value),
}
```

</Examples>

The first is the plainest enum: four variants and no data. The second
gives each variant its own data: a circle needs a radius, a rectangle a
width and a height (named, like a struct's fields). The third
is real, and shows what enums are best at: making a wrong state
impossible to build. A captured variable (an upvalue, from *Capturing
variables: upvalues*) is either still on the stack, in slot `usize`, or
closed, holding the value itself; a closed upvalue that still has a slot
cannot exist, because no variant has both.

In memory, an enum value is what the chapter *Sum types in memory* drew:
a tag saying which variant, then room for the largest payload, so every
`Value` is the same size whichever variant it holds.

</Figure>

<Formal title="An enum is a sum of its variants">

```text
enum V { A, B(bool), C(u8) }
V  ≅  1 + bool + u8
|V| = 1 + 2 + 256 = 259
```

<span slot="read">A value of V is an A, or a B holding a bool, or a C
holding a u8, which mathematicians write as a sum, 1 + bool + u8 (A
counts as 1, since it carries nothing). So V has 1 + 2 + 256 possible
values. A struct multiplies the counts of its fields; an enum adds the
counts of its variants.</span>
</Formal>

## match

To do anything with an enum value you ask which variant it is, and take
its data out. That is `match`:

```rust
let n = match v {
    Value::None => 0.0,
    Value::Bool(true) => 1.0,
    Value::Bool(false) => 0.0,
    Value::Number(x) => x,
};
```

Each line inside is an **arm**: a pattern, `=>`, and the code to run.
`Value::Number(x)` fits any `Number` and names its payload `x` for that
arm. Step through two different values:

<MatchSteps client:visible />

Arms are tried top to bottom, and the first one that fits wins; there is
no falling through to the next arm, so there is no `break` to forget.
`match` is an expression, like `if` in *Blocks, if and the tail
expression*, so the whole `match` has a value, and every arm must produce the same type.
(Give one arm a different type, say a `bool` where the others give
`&str`, and rustc says E0308, "`match` arms have incompatible types".)
Most important of all, a `match` must cover **every** possible value.
Leave out `Value::Bool(false)` and rustc 1.97 says (trimmed):

```text
error[E0004]: non-exhaustive patterns:
  `Value::Bool(false)` not covered
 8 |     match v {
   |           ^ pattern
   |   `Value::Bool(false)` not covered
help: ensure that all possible cases are
  being handled by adding a match arm ...
12 ~         Value::Bool(false) => todo!(),
```

The `help` even writes the missing arm for you, with a `todo!()`
body.

<Callout kind="definition">
A **`match`** expression compares a value with the patterns of its
**arms**, in order, and runs the first arm that fits<Cite id="rustref-match" />.
Its value is that arm's value, so all arms have the same type. It must
be **exhaustive**: every possible value has to fit some arm, or the
program does not compile.
</Callout>

<Examples of="match">

```rust
fn name(op: Op) -> &'static str {
    match op {
        Op::Const => "const",
        Op::Add => "add",
        Op::Neg => "neg",
        Op::Return => "return",
    }
}
```

```rust
fn area(s: Shape) -> f64 {
    match s {
        Shape::Circle(r) => 3.14 * r * r,
        Shape::Rect { w, h } => w * h,
    }
}
```

<Run id="values" />

</Examples>

The first turns each opcode into its name, one arm per variant
(`&'static str` is the type of a string literal, text that lives for the
whole program); the `match` is the last expression of the function, so
its value is returned. The second takes the payload out: `r` is the
circle's radius, and `Rect { w, h }` names the rectangle's two fields,
so `area` of a 2 by 3 rectangle is `6`. The runnable one prints Drip
values and adds two of them; change it, delete an arm, and read what
rustc says.

<OtherLanguages title="One of several shapes">

```rust
enum Shape {
    Circle(f64),
    Rect { w: f64, h: f64 },
}
fn area(s: Shape) -> f64 {
    match s {
        Shape::Circle(r) => 3.14 * r * r,
        Shape::Rect { w, h } => w * h,
    }

```

```ts
type Shape =
  | { kind: 'circle'; r: number }
  | { kind: 'rect'; w: number; h: number };
function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return 3.14 * s.r ** 2;
    case 'rect': return s.w * s.h;
  }
}
```

</OtherLanguages>

The TypeScript union needs a `kind` field that you write by hand, and
the check that every case is handled is something you set up (with a
`never` default, as in *TypeScript II: unions and narrowing*). In Rust
the tag is the variant, and a missing case is always a hard
error<Cite id="rust-book-match" />.

<Callout kind="engine" label="Under the hood">
The heart of the Rust Drip VM is one `match` in `run`, in
`companion/rust/src/vm.rs`, and it reads like your TypeScript `switch`:

```rust
match op {
    OpCode::None => self.push(Value::None),
    OpCode::Add => self.add()?,
    OpCode::Sub => { /* pop two, push */ }
    // ...one arm per opcode
}
```

The real one lists all 53 opcodes and has no catch-all arm, so adding an
opcode breaks the build until the VM handles it. `OpCode` is marked
`#[repr(u8)]`, which makes each variant exactly the byte that encodes
it, numbered as in the TypeScript VM. Underneath, every enum value has a
**discriminant**, an integer that says which variant it holds; the
compiler may store it in a smaller type, or tell variants apart some
other way<Cite id="rustref-enum" />. How rustc turns arms into a tree of
tests, and proves that nothing is missed, was the subject of *Compiling
pattern matching*.
</Callout>

## What you learned

- An **enum** is exactly one of a fixed set of **variants**, which can
  carry data: a discriminated union built into the language, and a sum
  of its variants.
- **`match`** tries its arms in order and runs the first that fits,
  binding names to the payload. It is an expression, so every arm has
  the same type, and it must be **exhaustive**.
- The Rust VM's dispatch loop is one exhaustive `match` on `OpCode`.

Next: patterns, the shapes on the left of each arm, which can do far
more than name a variant.

## More than a variant name

Every arm in the last chapter named one variant, perhaps with a payload.
Real code wants more. A scanner asks "is this byte a digit, a letter or
a space?", which is a question about ranges of numbers. Drip's `+` asks
"are *both* operands numbers?", a question about two values at once.
And Drip's truthiness asks "is this `none` *or* `false`?". All three are
written on the left of an arm, as a **pattern**.

<Analogy title="a coin-sorting tray">
A coin sorter is a tray of slots, each shaped for one coin. You drop a
coin in at the top; it slides past the slots in order and falls through
the first one it fits. The last slot is wide enough for anything, so no
coin is ever left on the tray.
<span slot="breaks">A coin only has a size; a pattern can look inside a
value (the payload of a variant, the fields of a struct, both halves of
a pair) and can also hand you the pieces it found, by name.</span>
</Analogy>

<Analogy extra title="a stencil">
Lay a stencil with a cut-out shape over a sheet of paper, and you see
only the parts that show through the holes. A pattern is a stencil laid
over a value: the solid parts say what must be there (`Number`, the
byte `b'('`), and the labelled holes (`x`, `n`) are the parts you get to
use.
<span slot="breaks">A stencil fits or it does not; a pattern may add a
condition of its own (a guard, `if n < 0.0`), so it can refuse a value
that matches its shape perfectly.</span>
</Analogy>

## The kinds of pattern

Here is a scanner's question, answered with three kinds of pattern at
once. Step a few bytes through it:

<ByteSteps client:visible />

`b'0'..=b'9'` is a **range pattern**: it fits any byte from `b'0'` to
`b'9'`, both ends included (ranges work for numbers and characters).
`p | q` is an **or-pattern**, which fits when any of its alternatives
fits. And `_` is the **wildcard**, which fits anything and binds
nothing. Here is the whole family:

<Figure takeaway="A pattern says what must be there, and names the parts you want." caption="The kinds of pattern used in this book. Patterns nest: a tuple of variants, a variant holding a struct, and so on.">
  <PatternKinds />
</Figure>

<Callout kind="definition">
A **pattern** describes a shape a value can have, and may **bind**
names to parts of it<Cite id="rustref-patterns" />: literals, ranges
`a..=b`, names (which fit anything and bind it), the wildcard `_`,
alternatives `p | q`, tuples, enum variants and structs, nested inside
one another. A binding is a new variable that exists only in its arm. A
**match guard**, `pattern if condition =>`, adds a test the arm must
also pass.
</Callout>

<Examples of="pattern">

```rust
fn is_falsey(v: Value) -> bool {
    match v {
        Value::None
        | Value::Bool(false) => true,
        _ => false,
    }
}
```

```rust
match (a, b) {
    (Value::Number(x), Value::Number(y))
        => Value::Number(x + y),
    _ => Value::None, // the VM: an error
}
```

```rust
match v {
    Value::Number(n) if n < 0.0 => "neg",
    Value::Number(_) => "not neg",
    _ => "not a number",
}
```

</Examples>

The first is Drip's truthiness: `none` and `false` are false, and the
or-pattern says so in one arm, while `_` answers "everything else" (the
companion writes the same thing with the `matches!` macro:
`matches!(self, Value::None | Value::Bool(false))`). The second matches
a **tuple**, `(a, b)`, two values grouped in brackets, so that one arm
can ask "are both numbers?" and bind both payloads; any other pair falls
to `_`. The third uses a guard: `Value::Number(n)` fits every number,
and `if n < 0.0` then keeps only the negative ones, so `-1` gives
`"neg"`, `2` falls to the second arm, and `true` to the third. Run
them, and try a byte or a number of your own:

## Patterns outside match

Patterns are not only for `match`. Every `let` is a pattern, which is
why you can take a struct or a tuple apart in one line:

```rust
let (x, y) = (3.0, 4.0);
let Particle { vx, vy, .. } = p;
```

The first binds `x` and `y` at once. The second pulls the fields `vx`
and `vy` out of `p` (field shorthand again), and `..` means "ignore the
other fields". These patterns can never fail: every pair has two halves,
and every `Particle` has a `vx`. Such patterns are called
**irrefutable**; patterns that might not fit, like `Value::Number(n)`,
are **refutable**, and a plain `let` refuses them:

```text
error[E0005]: refutable pattern in local
  binding
8 |     let Value::Number(n) = v;
  |         ^^^^^^^^^^^^^^^^ patterns
  |   `Value::None` and `Value::Bool(_)`
  |   not covered
help: you might want to use `let...else`
8 |     let Value::Number(n) = v
  |         else { todo!() };
```

The help names the fix. When you want one pattern and nothing else, use
**`if let`**, a `match` with one arm, or **`let ... else`**, which binds
the names for the rest of the function and must leave (with `return`)
when the pattern does not fit<Cite id="rust-book-if-let" />:

```rust
if let Value::Number(n) = v {
    println!("a number: {n}");
}
let Value::Number(n) = v else {
    return Err(/* ... */);
};
```

The Rust Drip VM's `pop_numbers` (in `companion/rust/src/vm.rs`) starts
with exactly that second shape: `let (Value::Number(a), Value::Number(b))
= (self.peek(1), self.peek(0)) else { ... }`, a tuple pattern that
either hands it two numbers or reports Drip's runtime error, such as
`cannot use '-' on a number and a string`.

<Formal title="What a match does">

```text
match v { p₁ => e₁, …, pₙ => eₙ }
  runs eᵢ for the smallest i with v ∈ ⟦pᵢ⟧
exhaustive: ⟦p₁⟧ ∪ … ∪ ⟦pₙ⟧ = values(T)
```

<span slot="read">Write ⟦p⟧ for the set of values that pattern p fits.
A match on v runs the arm whose pattern is the first to fit v. It is
exhaustive when the sets of all its patterns, put together, include
every value of v's type T, written values(T). A pattern is irrefutable when its set alone
is every value of T.</span>
</Formal>

## Two traps

The first is the wildcard. `_` covers every case you have not written,
*including ones added later*. Add a variant to `Op`, and a `match` that
ends in `_ => {}` keeps compiling, quietly doing nothing for it; list the
variants instead whenever each one deserves a thought, and keep `_` for
when "everything else" really has one answer, as in `is_falsey`.

The second catches everyone once. A plain name in a pattern always
**binds**: it makes a new variable. It never compares with a variable
of the same name<Cite id="rust-book-patterns" />:

```rust
let limit = 3;
match n {
    limit => println!("hit"),  // ✗
    _ => println!("miss"),
}
match n {
    x if x == limit => println!("hit"),
    _ => println!("miss"),     // ✓
}
```

With `n = 7` the first prints `hit`, because `limit` in the pattern is
a brand-new name that fits anything. rustc warns you:

```text
warning: unreachable pattern
5 |         limit => println!("hit"),
  |         ----- matches any value
6 |         _ => println!("miss"),
  |         ^ no value can reach this
note: there is a binding of the same name
```

The guard in the second `match` does the comparison you meant.

<OtherLanguages title="Are both operands numbers?">

```rust
match (a, b) {
    (Value::Number(x), Value::Number(y))
        => Value::Number(x + y),
    _ => Value::None,
}
```

```ts
if (typeof a === 'number' &&
    typeof b === 'number') {
  return a + b;
}
return null;
```

</OtherLanguages>

TypeScript can take objects and arrays apart (`const { x, y } = p`), but
it has no patterns that *test*: the question "are both numbers?" is an
`if` with two checks, and narrowing (*TypeScript II: unions and
narrowing*) works out the types inside it. In Rust the test, the
narrowing and the naming of the payloads are one pattern, and the
compiler can check the whole `match` for missing cases.

## What you learned

- A **pattern** is a shape: literals, ranges `a..=b`, names that bind,
  the wildcard `_`, alternatives `p | q`, tuples, variants and structs,
  nested freely, with an optional guard `if ...`.
- `let` takes patterns too. Irrefutable ones (tuples, structs) always
  fit; refutable ones need `match`, `if let` or `let ... else`.
- `_` hides cases added later, and a plain name in a pattern binds a new
  variable instead of comparing.
