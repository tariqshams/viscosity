## Most of the code is never called

Drip's compiler, from the chapter "One pass from source to bytecode"
onwards, works
on a whole program in one go: every function is parsed and turned into
bytecode before anything runs, which is fine for a test script. A web page
is different. It might ship a framework, a date library and the code for a
settings dialog nobody opens today, and it has to start fast. In 2019 the
V8 team listed what compiling such code eagerly costs: CPU time that
delays the code that *is* needed, memory for the bytecode, and space in
the cache; parsing and compiling sit right on the critical path of a
page starting up<Cite id="v8-preparser" />. So the cheapest parse is the
one you never do.

## Lazy parsing

<Analogy title="the appendices of a report">
When someone hands you a thick report, you do not read every appendix;
you flick through to check each one is there and roughly what it covers,
and you read one properly only when somebody asks about it. Flicking is
not free, though: you still have to turn every page to find where each
appendix ends.
<span slot="breaks">You can skim an appendix by its headings; the
preparser cannot skip a single character, because only the full grammar
says where a body really ends, and it must also spot any mistake inside
it.</span>
</Analogy>

<Analogy title="a librarian checking returns">
A librarian checking a returned book riffles through it to make sure no
pages are torn out and notes anything the catalogue needs, but does not
read the story; reading happens later, if someone borrows it.
<span slot="breaks">A librarian who later reads the book does not have to
riffle through it again first; V8 does pay twice, once to skim and once
to parse properly, for every skimmed function that turns out to be
called.</span>
</Analogy>

All major browsers parse JavaScript lazily<Cite id="v8-preparser" />.
When V8's parser reaches a function body, it can hand it to the
**preparser**, a stripped-down copy of the parser that reads the body
without building a syntax tree; when the function is called for the first
time, V8 parses it properly and compiles it then. Step through a small
file:

<LazySteps client:visible />

<Callout kind="definition">
**Lazy parsing** means skimming a function body with a **preparser**
instead of parsing it fully, and doing the full parse and compile only
when the function is first called. The preparser still checks the body's
syntax and records what the enclosing code needs to know about
it<Cite id="v8-preparser" />.
</Callout>

<Formal title="What lazy parsing saves, and what it costs">

```text
eager = Σ (all f)    parse(f)
lazy  = Σ (all f)    preparse(f)
      + Σ (called f) parse(f)
```

<span slot="read">Eager parsing costs one full parse of every function f
(Σ means "add up over"). Lazy parsing costs a cheap preparse of every
function, plus a full parse of only the functions that are called. Lazy
wins when few functions are called; when nearly all are, it costs more,
because those pay for both.</span>
</Formal>

V8 can log these events as they happen, which turns the stepper into a
real trace:

<Examples of="lazy-parsing">

```js
// lazy.js
function used() { return 1; }
function unused() { return 2; }
const eager = (function () {
  return 3;
});
used();
```

```
// node --log-function-events
//   --logfile=fe.log lazy.js
// event, start, end, name
preparse-resolution  13  29 used
preparse-resolution  45  61 unused
full-parse           86 104
interpreter          86 104 eager
full-parse           13  29 used
parse-function       13  29 used
interpreter          13  29 used
first-execution      13  29 used
```

```
// the same log, for the whole file
interpreter          0 115
first-execution      0 115
// ...and no first-execution for eager
```

</Examples>

The first is the file: two ordinary functions and one written in
parentheses. The second is V8's log of it (Node v22.23.4, V8 12.4, with
lines about Node's own code removed), where the numbers are character
positions in the file: `used` and `unused` were preparsed; the function
in parentheses was fully parsed and compiled to bytecode (the
`interpreter` event) at once; and only when `used()` ran did `used` get
its full parse, its bytecode and its first run. `unused` never got past
the preparser. The third is a detail worth noticing: the whole file (0 to
115) is compiled and run, but `eager` has no `first-execution` line,
because nothing calls it. Its full parse and bytecode were spent for
nothing, which is the other way a guess can go wrong.

## Skimming is harder than it looks

Why not jump to the matching `}`? Because finding it needs the syntax: a
brace can sit inside a string, a comment, a regular expression or a
template literal, and in 2025 the V8 team put it bluntly: there is no
shortcut of counting curly braces, because the grammar is too
complex<Cite id="v8-explicit-compile-hints" />. Try a brace counter on a
body with a `"}"` inside a string:

<Run id="brace-trap" />

The preparser also has to keep *some* information. Remember closures and
upvalues: a variable that an inner function captures must outlive its
call, so V8 stores it in a heap-allocated **context** instead of on the
stack, and whether a variable needs that depends on the functions nested
inside; so the preparser tracks the variables each skipped body declares
and refers to<Cite id="v8-preparser" />. And because the language demands
it, a syntax error in a function nobody calls still stops the whole
script. Spot the difference:

```js
function never() {
  return 1 +;
}
console.log('ran');
// SyntaxError: Unexpected token ';'
```

```js
function never() {
  return 1 + 2;
}
console.log('ran'); // ran
```

`never` is never called in either file, yet the first prints nothing but
the error, because the preparser checks every body as it skims.

## Guessing what will be called

A function that is preparsed and then called gets parsed twice; since V8
6.3 (Chrome 63, 2017) at most twice, however deeply it is
nested<Cite id="v8-preparser" />. So V8 guesses. A function written in
parentheses, `(function () {…})`, is usually called at once, so V8 parses
and compiles it eagerly as soon as it sees `(function`; the team calls
these PIFEs, *possibly*-invoked function expressions<Cite id="v8-preparser" />,
which is why `eager` was compiled before anything ran. Developers can
give hints too: in 2025 the team wrote that Chrome 136 compiles every
function in a file eagerly if the file starts with the comment
`//# allFunctionsCalledOnLoad`, and warned to use it sparingly, since
compiling too much costs time and memory<Cite id="v8-explicit-compile-hints" />.

## What you learned

- **Lazy parsing** skims function bodies with a **preparser** and parses
  and compiles them fully only when they are first called.
- The preparser cannot just count braces; it must still check syntax and
  track the variables that closures capture.
- A called lazy function is parsed twice, so V8 parses likely-called
  functions (`(function`) eagerly, and a wrong eager guess wastes work.
