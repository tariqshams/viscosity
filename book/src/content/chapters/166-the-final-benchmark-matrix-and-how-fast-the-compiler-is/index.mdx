## The other stopwatch

Since *AoS vs SoA, measured*, every benchmark has timed the programs
Viscosity *writes*. Now turn the stopwatch on Viscosity itself. When you
type `viscosity build app.js`, how long until you get your prompt back?
And when this book's Playground recompiles as you type, how long does
each compile take? Those are two different questions, with two
different answers.

<Analogy title="how fast is a taxi?">
The speed on the motorway is one answer; the time from phoning for a
taxi to arriving is another, and for a short trip it is mostly the wait
for the car to turn up. A faster engine does not help much if the car is
parked across town.
<span slot="breaks">A taxi's wait changes with traffic and the time of
day; a program's start-up is much the same every time on a quiet
machine, which is what lets us measure it and subtract it.</span>
</Analogy>

<Analogy extra title="a school report card">
A report card lists every subject in one grid, marked in the same week
by the same rules, so the rows can be compared with each other.
<span slot="breaks">A school grades every pupil on the same scale; the
matrix's machine is a noisy shared computer, so it also has to record
how much its own marks wobble.</span>
</Analogy>

<Callout kind="definition">
**Compile-time performance** is the speed of the compiler itself, from
source in to code out. Measure it as a **whole process** per compile
(what a command-line user waits for, start-up included) or **in
process**: `compile()` called again and again in one long-lived process,
after warm-up (what an editor, a build tool or a playground sees).
Neither says anything about how fast the compiled program runs.
</Callout>

<Examples of="compile-time-performance">

```sh
viscosity build basic_soa.js
# medians of 21: Rust 3.6 ms, TS 94 ms
```

```js
for (let k = 0; k < 200; k++)
  compile(src); // after 50 warm-ups
```

</Examples>

The first is one whole process per compile, the way a user runs it; the
comment holds medians of 21 alternating runs I made on the shared
machine, start-up and all, for one corpus program. The second is the
in-process question: call `compile()` 50 times to let the JIT warm up
(*Benchmarking honestly* explains why), then time 200 calls and take the
median.

## Where the time goes

A warm `compile()` is under 1% of a TypeScript CLI run, for every
program. So what is the rest? I timed the pieces, 21 fresh processes
each, alternating (load average about 1 to 2):

```text
node -e 0              32 ms
TS CLI --version       75 ms
TS CLI build (1 file)  94 ms
Rust CLI --version     3.3 ms
Rust CLI build         3.6 ms
```

<Figure takeaway="A TypeScript CLI run is mostly starting Node and loading code; a Rust CLI run is mostly starting a process." caption="An earlier round's medians on the same machine, split by subtraction: starting Node is node -e 0, loading the bundle is --version minus that, compiling is build minus --version. The Rust bar's compile slice is about 0.2 ms.">
  <WhereTimeGoes />
</Figure>

Starting Node is about a third of the TypeScript run, and loading the 1
MB bundle costs more again before a line is compiled (`--version`
compiles nothing). The compile itself adds about 20 ms, far more than
the warm figure, because in a fresh process the code is cold:
`engine/rust/results/compile-speed-2026-10-31.md` measured the first
`compile()` of `boids` at 22 ms, about 25 times its warm time. The Rust
CLI spends almost all of its few milliseconds starting a process, which
is why the CLI ratio is about twice the engine ratio: it mostly compares
Node's start-up with a native binary's. And a ratio of milliseconds is
fragile: the matrix's Rust medians were 7 to 15 ms per program, on a
busier machine, so read "<Num k="cli" />" as "about ten times, or more".

<Prompts ids={['why-bigger', 'first-call']} />

<More title="Many files in one process, and where Rust's time goes">
Both CLIs accept many files, `viscosity build a.js b.js … -o out/`, so
start-up is paid once. When this chapter was first written I timed 1, 40
and 400 files in one process with `--jobs 1`: the Rust CLI took 4.4–5.7,
11.3–11.4 and 50–62 ms, the TypeScript CLI 120–141, 205–264 and 825–899
ms, so each extra file cost Rust about 0.12 ms and TypeScript about 1.8.

<Formal title="Start-up, amortised">

```text
T(n) = S + n · c
R(n) = (S_ts + n·c_ts) / (S_rs + n·c_rs)
R(1) ≈ S_ts / S_rs,  R(∞) = c_ts / c_rs
```

<span slot="read">A run of n files costs its start-up S plus n times the
cost per file c. The ratio between the two CLIs, R, is about the ratio of
their start-ups when n is 1, and tends to the ratio of their per-file
costs as n grows large.</span>
</Formal>

<Run id="amortize" />

The model prints the two times and their ratio for 1, 10, 100 and 10,000
files, closing in on 1.8 / 0.12 = 15. With hundreds of files threads can
share the per-file cost: `results/parallel-build-2026-10-31.md` built 396
files 2.95 times faster with four threads than one into a memory-backed
folder, but only 1.24 times writing to disk, where creating the files
took about 65 ms whatever the thread count (the deep dive *Compiling in
parallel* follows those threads).

The compile-speed file also reports a callgrind profile of `nbody.js` in
the native engine: parsing with oxc about 10–17 µs, scope resolution and
lowering about 80, analysis about 35, plan and emit about 25. No phase
dominates; small heap allocations and hashing do, and the port stopped
there on purpose, a faithful translation rather than a rewrite for speed.
</More>

## One grid, one method

Three comparisons had each been measured on a different day, in a
different way: the compiled programs against their originals, the
TypeScript engine against the Rust one, and the three Drips. Numbers
taken on different days by different methods cannot honestly sit in one
table, because you cannot tell whether a difference comes from the code
or from the day; so `matrix.ts` runs them from one script, on one
machine, in one sitting, and generates its `.md` from the JSON.

<Figure caption="The matrix's three sections, their axes and how many cells each holds. Each section asks a different question; within a section, every cell was measured the same way." takeaway="A benchmark matrix is every combination of a few axes, measured by one method.">
  <MatrixAxes />
</Figure>

<Callout kind="definition">
A **benchmark matrix** measures every combination along a few axes (here:
program × JavaScript engine × original or compiled; compiler × corpus
program × way of running it; Drip implementation × program) with one
method, so that any two cells can be compared. It records the machine,
the versions and the noise alongside the numbers.
</Callout>

The machine is a shared 4-vCPU VM, and the file itself warns that
timings vary by up to about 2× between runs and that differences under
about 10% are noise. Against that, the end-to-end section runs each
program in <Num k="runs" /> fresh processes per version per engine,
original and compiled interleaved, after one discarded run of each, and
reports the **best** time, the most stable figure because noise only
ever adds time, with the median beside it. Every compiled program
printed the same checksum as its original, on both engines. The second
engine is Bun <Num k="bun" />, which runs JavaScriptCore.

<Prompts ids={['matrix-what', 'matrix-why', 'best-of']} />

<Examples of="benchmark-matrix">

```js
// one cell: heat on Node
const r = m.e2e.rows
  .find((r) => r.program === 'heat');
r.node.originalMs.best
  / r.node.viscosityMs.best;
```

</Examples>

The example reads the results file, `m`, finds heat's row, and divides
its original time on Node, <Num k="heatNodeOrig" />, by its compiled
time, <Num k="heatNodeComp" />, giving the <Num k="heatNode" /> in the
table. Reading the same row along the engine axis, on Bun the original
takes <Num k="heatBunOrig" /> and the compiled program
<Num k="heatBunComp" />, a speed-up of <Num k="heatBun" />. A whole
column is summarised by its **geometric mean**, the n-th root of the
product of the speed-ups, so that a 2× gain and a 2× loss cancel to
exactly 1.

<MatrixSteps client:visible />

On Node, Viscosity speeds up every program, with a geometric mean of
<Num k="nodeGeo" />; on Bun the mean is <Num k="bunGeo" />, and `heat`
gains nothing. The difference lies in the originals: Bun runs the
unchanged array-of-objects programs <Num k="bunOrig" /> faster than Node,
and the compiled ones only <Num k="bunComp" /> faster. JavaScriptCore was
already fast on the objects; V8 was not.

## A likely cause, not yet confirmed

`FINDINGS.md` in the bench package offers an explanation and labels it
"not yet confirmed with engine traces". The facts it rests on are
documented: in V8, a field that holds doubles keeps each value in a
separate box on the heap<Cite id="v8-react-cliff" />, while
JavaScriptCore stores a double inside the value itself<Cite id="jsc-jsvalue" />,
and a `Float64Array` holds raw doubles on both. If every `c[i].h` on V8
is one more pointer to follow, the rewrite fixes storage and locality on
V8 but only locality on JavaScriptCore, and heat, which reads four
neighbours of every cell in every step, would feel the pointer most.
Nobody has yet taken the trace of V8 that would confirm it.

The lesson for the cost model holds either way: its rules predict
*whether* a layout helps on these programs, but not *how much*, because
that depends on an engine the compiler never sees; which is why
`explain` says why a collection was transformed and never promises a
speed-up.

<Prompts ids={['explain-claim']} />

<More title="Two honest notes, and reading the Drip column">
The in-process figure carries a note added afterwards: when it was
measured, the WebAssembly side's timed region did not copy the output
strings out of linear memory, which the TypeScript side never has to do.
`matrix.ts` now does, but the timing has not been re-run, so treat
<Num k="inproc" /> as an upper bound.

The Drip section was not timed by the matrix: its <Num k="dripPrograms" />
rows are copied from the redesigned Drip's committed results of
2026-11-02, the files *Profiling and optimising drip-rs, and three
implementations compared* reads. The TypeScript VM is about level with
the tree-walker (<Num k="vmVsTree" />), and drip-rs is <Num k="rustVsVm" />
faster than it and <Num k="rustVsTree" /> faster than the tree-walker.
`matrix.ts` takes each mean over ratios rounded to two places; taken from
the times, drip-rs against the tree-walker is <Num k="rustVsTreeTimes" />.
Only the mean from the times keeps an exact rule: the third mean is the
first two multiplied.

```js
// a column, from the raw times
const xs = m.drip.rows
  .map((r) => r.vmMs / r.rustMs);
Math.exp(xs.reduce((a, x) =>
  a + Math.log(x), 0) / xs.length);
```

<Formal title="Speed-up and geometric mean">

```text
speedup(p) = t_original(p) / t_compiled(p)
geomean    = (s₁ × s₂ × ... × sₙ)^(1/n)
           = exp((ln s₁ + ... + ln sₙ) / n)
```

<span slot="read">The speed-up of a program is its original time divided
by its compiled time. The geometric mean of n speed-ups multiplies them
together and takes the n-th root; the second line computes the same
thing by averaging their logarithms, which never overflows.</span>
</Formal>

An earlier end-to-end run, `results/e2e-node-2026-10-31.json` (Node
only, a median of three, made before the fuzzer fixes changed heat's
compiled code), used a different method; compare its shape with the
matrix, never its cells.
</More>

## What you learned

- **Compile-time performance** is the compiler's own speed: per process
  for a command line, in process for editors and playgrounds; a CLI run
  is mostly **start-up**, and ratios of milliseconds are fragile.
- A **benchmark matrix** runs every comparison with one method on one
  machine, recording versions and noise; each end-to-end cell is the
  **best of fresh processes**, interleaved.
- Viscosity gains on **V8** across the board and much less on
  **JavaScriptCore**; the heap-number explanation is a **hypothesis**.
