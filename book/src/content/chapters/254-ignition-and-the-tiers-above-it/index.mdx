## A function that is called once

You met Ignition and the three compilers above it in *Tiers, speculation
and deoptimisation*: a register machine with an accumulator at the
bottom, then Sparkplug, Maglev and TurboFan, with a function moving up
as its hotness budget runs out. This chapter goes further, and it starts
with a function that the picture of "move up when hot" does not obviously
cover:

```js
function longSum(n) {
  let s = 0;
  for (let i = 0; i < n; i++) s += i % 7;
  return s;
}
longSum(1e7); // called once
```

A tier chosen at the start of a call would leave `longSum` in slow code
for all ten million trips; yet on Node v22.23.4 the call took about 19
ms, and 80 to 130 ms with `--no-use-osr` (three runs each), so something
moved it into faster code in the *middle* of the call. To see how, we
need to read Ignition's bytecode more closely, and the frame it runs
in.

## Why an interpreter at the bottom

V8 did not always start in an interpreter. Until 2017 its first tier,
Full-codegen, compiled every function straight to machine code, with
Crankshaft as the optimising compiler above it; Ignition was built
mainly to save memory, because its bytecode is a quarter to a half the
size of the machine code that compiler made<Cite id="v8-ignition" />.
Since V8 5.9 (Chrome 59, 2017) every function starts in Ignition, and
TurboFan compiles from Ignition's bytecode rather than from the source
text, so the bytecode is the one form every tier above shares<Cite id="v8-launch-ignition-turbofan" />.

<More title="More: the top tier keeps changing">

In 2025 the team wrote that TurboFan's back end had moved to a new IR,
Turboshaft<Cite id="v8-leaving-sea-of-nodes" />, and `node --v8-options`
shows `--turboshaft` already on by default in Node 22. The tiers are an
engineering choice of one period, not a fixed design.

</More>

## Reading a whole listing

Here is a function that sums an array, and the start of its listing
(`node --print-bytecode --print-bytecode-filter=sum`, trimmed of
addresses):

```
Parameter count 2
Register count 3
Frame size 24
29 S> @ 0 : 0c        LdaZero
      @ 1 : c9        Star0
47 S> @ 2 : 0c        LdaZero
      @ 3 : c8        Star1
57 S> @ 4 : 2f 03 00 00
            GetNamedProperty a0, [0], [0]
```

The header first. **Parameter count 2** is one more than `sum` declares,
because the receiver (`this`) is passed as a hidden first parameter;
`add(a, b)` reports 3. **Register count 3** says the bytecode generator
needed three registers, `r0` to `r2`, and **Frame size 24** is those
three registers at 8 bytes each. On the left, `29 S>` and `57 E>` are
source positions: the character offset in the file where a statement
(`S`) or an expression (`E`) begins, which is how a stack trace or a
debugger maps a bytecode back to your code. `Star0` is a one-byte short
form of `Star r0` ("store the accumulator into r0"); Ignition has these
for its first sixteen registers, because storing the accumulator is one
of the commonest things it does<Cite id="v8-src-interpreter-12-4" />.

<Analogy title="a recipe with numbered bowls">
A recipe written for a busy kitchen says, at the top, "you will need two
ingredients and three bowls", then gives each step with the bowl it uses
and a note in the margin of which line of the original cookbook it came
from. The cook keeps one thing in hand at a time (the accumulator) and
puts it down in a numbered bowl when the next step needs both hands.
<span slot="breaks">A cook may decide to use a fourth bowl; Ignition's
registers are fixed when the bytecode is made, and every one of them is
a slot in the call's stack frame, so the "Frame size" line is exactly
how much stack the call takes for them.</span>
</Analogy>

Now step through the loop itself, with `xs = [5, 7]`:

<LoopSteps client:visible />

<Examples of="ignition">

```
@30 : 8e 1a 00 07
      JumpLoop [26], [0], [7]
```

</Examples>

`8e` is the opcode of `JumpLoop`, and its three operands are the bytes
that follow. `[26]` (`1a`) is how far back to jump: 30 − 26 = 4, the loop
test. `[0]` is the **loop depth**, 0 for an outermost loop and one more
for each loop it sits inside. `[7]` is a feedback slot of its own; and
`JumpLoop` is the only way back to the top of a loop, which makes it the
natural place for V8 to charge the hotness budget on every trip (the
budget is spent on returns and on backward jumps<Cite id="v8-src-tiering-12-4" />)
and, as we will see, to check whether faster code is waiting.

<More title="More: the rest of the loop, opcode by opcode">

Each feedback-carrying instruction has its own slot, numbered in the
order the bytecode generator met them: the `xs.length` load is `[0]`,
the comparison `[2]`, the addition `[3]`, the element load `[4]`, the
increment `[6]` and the `JumpLoop` `[7]` (the gaps belong to slots that
take two entries). `GetKeyedProperty a0, [4]` takes the key from the
accumulator and leaves `xs[i]` there; its slot is the element access's
inline cache, which remembers the array's map, elements kind included
(*Shapes, inline caches and elements kinds*). `Mov r0, r2` copies the old
`s` into `r2`, a register nothing in this listing reads again: the
bytecode generator is simple and fast, and leaves tidying of this kind to
the compilers above it. The same listing for `longSum` puts its
`JumpLoop` at offset 28, which is worth remembering for the last section.

</More>

## Why Sparkplug is so cheap

Sparkplug turns bytecode into machine code in one pass; the V8 team
describe its core as "a switch inside a for loop", with no intermediate
representation at all, because the bytecode generator has already done
the hard work, such as resolving which variable is which<Cite id="v8-sparkplug" />.
Its code calls the interpreter's own helpers for most of the work, so
it is, in effect, the interpreter with the decoding and dispatching
taken out<Cite id="v8-sparkplug" />. The other half of the trick is the
frame:

<Figure caption="The interpreter frame of sum(xs), read off the header of its bytecode listing. The parameters sit above the frame, the registers are ordinary stack slots, and the fixed slots include the bytecode array and the current bytecode offset." takeaway="Sparkplug keeps the interpreter's frame layout, so a call can switch between the two tiers with almost no work.">
  <FrameFigure />
</Figure>

An interpreter frame keeps a pointer to the bytecode array and the
offset of the current bytecode<Cite id="v8-sparkplug" />, and Sparkplug
code uses the same layout, register slots and all<Cite id="v8-sparkplug" />.
So a running call can move from Ignition into Sparkplug without
translating anything: the values are already where Ignition put them.

Sparkplug also compiles in **batches**: in Node 22, warm functions are
queued, and the whole batch is compiled at once, on the main thread, when
their estimated size passes 4096 (the default of
`--baseline-batch-compilation-threshold`).

<More title="More: watching a batch fill up">

`--trace-baseline-batch-compilation` shows each function queued with an
estimated size and a running budget:

```
Enqueued SFI isPosixPathSeparator with
  estimated size 56 (current budget:
  3017/4096)
Enqueued SFI normalizeString with
  estimated size 3101 (current budget:
  6118/4096)
Compiling current batch of 7 functions
```

(These are Node's own start-up functions; your code is queued the same
way.)

</More>

Maglev sits between Sparkplug and TurboFan in V8, and in 2023 the
team reported it compiling about ten times slower than Sparkplug and ten
times faster than TurboFan<Cite id="v8-maglev" />; however, in this Node
22 build its flag defaults to `--no-maglev`, and even with `--maglev`,
`%OptimizeMaglevOnNextCall` prints "Maglev is not enabled.", which is why
the runs in this part go from Sparkplug straight to TurboFan.

## Getting into faster code mid-loop

Back to `longSum`. Its single call spends the hotness budget on every
`JumpLoop`, so V8 marks it for TurboFan well before the loop ends; but
the frame on the stack belongs to the interpreter (or Sparkplug), and
the new code would normally be used only from the *next* call. Instead,
V8 compiles a special version of the function whose entry is the loop
itself, and the next time the running loop reaches `JumpLoop`, it jumps
into that code with the current values of `s` and `i`. Here is
`node --trace-osr --trace-opt`, trimmed:

```
[marking … longSum … for optimization
  to TURBOFAN, …, reason: hot and stable]
[OSR - compilation started. function:
  longSum, osr offset: 28, …]
[compiling method … longSum …
  (target TURBOFAN) OSR, …]
[OSR - entry. function: longSum,
  osr offset: 28]
```

<Callout kind="definition">
**On-stack replacement** (OSR) switches a call that is already running
from one tier's code to another's, at a loop back edge, by building the
new code's frame from the current one and jumping into the new code in
the middle of the function. In V8 the entry point is named by the
bytecode offset of a `JumpLoop`.
</Callout>

`osr offset: 28` is exactly the offset of `longSum`'s `JumpLoop`. Deoptimisation, which
you met in *Tiers, speculation and deoptimisation*, is the same move in
the other direction: optimised code hands a running call back to the
interpreter at a known bytecode; OSR hands a running call *up*, at a
loop.

You can see the effect without any flags: time each block of trips
inside one call.

<Run id="osr-chunks" />

On Node v22.23.4 the first two blocks of 200,000 trips took 2.4 and 5.4
ms, and every block after that 0.6 to 0.9 ms, once the loop was running
in TurboFan's OSR code.

<More title="More: a concurrent compile, without OSR, and after the call">

The OSR compile ran on another thread (`kConcurrent`, the default of
`--concurrent-osr`), so the loop kept running in the slower tier until
the code was ready, and entered it at a later trip.

With `--no-use-osr`, the blocks after the first two stayed near 4 ms, in
Sparkplug. And asked after the call, `%ActiveTierIsTurbofan(longSum)`
(under `--allow-natives-syntax`) is false, and
`%ActiveTierIsSparkplug(longSum)` true: OSR code belongs to that one
loop entry, and is not installed as the function's code for its next
call.

</More>

## What you learned

- Ignition was built to save memory, and since 2017 its bytecode is the
  one form every tier above it compiles from.
- A listing's header gives the parameter count (with the receiver),
  the register count and the frame size; short forms such as `Star0`
  and source positions fill the rest; `JumpLoop` carries the jump
  distance, the loop depth and a feedback slot.
- Sparkplug is one pass with no IR, calling the interpreter's helpers in
  the interpreter's own frame layout, and compiles in batches.
- **On-stack replacement** moves a running call into optimised code at a
  `JumpLoop`, which is how a function called once still gets fast.
