## A red job, step by step

*Keeping it healthy* ended with the book job red. Here is how GitHub
showed that run of 2 November, step by step (from `gh run view`,
trimmed):

```
X book in 2m30s
  ✓ Install
  X Check chapters
  - Test
  - Merge new references
  - Build
  - Check site links
  - Smoke test
```

Steps in a job run in order, and the first that fails ends the job:
the later ones are shown with a dash, skipped. Each step that can fail
the job is a **gate**, and every gate exists because of a particular
kind of mistake. This chapter goes through them, job by job, with what
they actually print when they catch something. The same rule at toy
size, so you can see the order of events:

<Run id="ci-job" />

`job` walks the steps with a flag `ok`. While `ok` is true, a passing
step prints `✓` and a failing one prints `X` and clears the flag; once
the flag is false, every later step is only listed with a dash. The
book job here has one failing step, so it prints one tick, one cross,
five dashes, and "the job is red".

<Analogy title="security at an airport">
Before a flight you pass several checks: a person compares your face
with your passport, a scanner looks inside your bag, an arch looks for
metal. Each catches things the others cannot, and you board only after
all of them.
<span slot="breaks">Security staff notice odd behaviour nobody wrote a
rule for; a gate is a program that catches only what it was written to
look for, so a mistake of a new kind walks through every one (the five
fuzz bugs passed every test until a fuzzer was added).</span>
</Analogy>

<Analogy extra title="a car's yearly inspection">
A garage tests a car's brakes, lights, tyres and exhaust against a
printed list, and a pass certificate means those things were within
limits on that day.
<span slot="breaks">A car is inspected once a year; a repository is
inspected on every push, so a gate that fails points at the one change
just made rather than at a year of wear.</span>
</Analogy>

## The Rust engine's gates

The `engine-rust` job installs a stable Rust toolchain with Clippy,
rustfmt and the WebAssembly target (and Node, Python and the TypeScript
reference, which the tests run), then runs five gates in
`engine/rust`.

**Format.** `cargo fmt --all --check` exits with 0 if rustfmt would
change nothing and with 1 if it would change a file, printing the
difference<Cite id="rustfmt-readme" />. It comes first because it is
the fastest, so an unformatted file costs seconds, not minutes.

**Test.** `cargo test --workspace` is most of the job, and most of this
Part hangs off it. When I ran it here (rustc 1.97, debug build), it
passed 77 tests in 14 test binaries:

```
binary        tests  what it holds
parity          10   190 pairs, 14 frames,
                     4 profiles, the CLI
differential     2   node and python3
early_errors     6   108 invalid programs,
                     77 valid ones
multi_file       8   several files, --jobs
profile_cli      4   profiles, cleanup
os_args          2   non-UTF-8 file names
fuzz             1   200 programs, seed 1
unit tests      44   SSA, CFG, plugins ...
```

Parity holds the two engines together (*TypeScript vs Rust: differential
tests*): it printed `parity: 190/190 (54 Python)` for me, 95 programs in
two bounds modes each, plus 14 code-frame fixtures, 4 profiles and the
CLI itself. The differential test holds the compiled programs to the
originals, running both under node and CPython. `early_errors` holds
both engines to the same verdict on 108 programs JavaScript must reject
and 77 it must accept. `multi_file` holds the parallel CLI of *Compiling
in parallel* to its order, and `fuzz` runs the generator of *Shrinking a
failing program*.

**Clippy.** `cargo clippy --workspace --all-targets -- -D warnings`
turns every lint warning into an error (it passed when I ran it). Here
is what that looks like, on a small file I wrote to trip it (trimmed):

```
error: length comparison to zero
 --> src/main.rs:3:8
  |
3 |     if v.len() == 0 {
  |        ^^^^^^^^^^^^ help: using
     `is_empty` is clearer and more
     explicit: `v.is_empty()`
  = note: `-D clippy::len-zero` implied
    by `-D warnings`
```

It is a diagnostic in the full sense of *Diagnostics*: a level, a
message, a file, line and column, the code, and a label. Clippy's
README now prefers setting `CARGO_BUILD_WARNINGS=deny` (from Cargo 1.97),
which "has the benefit of not invalidating build caches"<Cite id="clippy-readme" />,
a good fit for a cached CI job; the workflow still uses `-D warnings`.

**WebAssembly and packages.** `cargo build --target
wasm32-unknown-unknown -p viscosity-wasm` proves the engine still
compiles for the browser (*Compiling the engine to WebAssembly*), and
`cargo package --workspace --no-verify --allow-dirty` proves every crate
can still be packaged for crates.io, where all six were published at
version 0.0.1 on 2 November (the comment above that step in `ci.yml`
says so: "Published on crates.io (0.0.1), and kept publishable").

## Fixtures that keep up

The parity fixtures in `tests/expected/` are the TypeScript engine's
output, committed (402 files when I counted). That is why the Rust half
of parity needs no TypeScript to run: it compares bytes with bytes. The
price is a rule. After changing the reference engine, run `node
scripts/gen_expected.mjs`, then `cargo test`, and commit both. Forget
the first step, or delete a program without its fixtures, and
`fixtures_match_the_programs_exactly` compares the folder with the
program list and fails with the message above, naming the files that are
missing and the files that are stale (left behind by a program that no
longer exists). A stale file would otherwise sit there for ever, since
no test reads it.

## The book's gates

The `book` job protects the thing you are reading. **Check chapters**
runs `scripts/check_chapters.mjs` over every chapter: the frontmatter
and the order of concepts, every citation against the bibliography,
code lines that fit a phone, the number of prompts and quiz questions,
the 12 to 18 minute budget (it told me "estimated 19.8 minutes (want
12–18)" while I was writing *Fuzzing the Rust engine*), the teaching
rules, and every exercise, whose solution must pass its tests while its
starter and wrong attempts must fail, in Node, in the Drip VM or with
`rustc`. Then `vitest` runs the book's own unit tests, **Merge new
references** folds the writers' new reference files into the
bibliography, **Build** builds the site with Astro, **Check site links**
follows every internal link and anchor, and the **Smoke test** opens the
built site in Chromium at 440 by 956 pixels and uses it: the runner, a
quiz, a stepper, the review deck, and the Playground on both engines,
which must give identical code and decisions. On 1 November it caught
two pages that did not fit a phone:

```
✗ /bibliography/: no horizontal overflow
  at 440px
✗ /chapters/191-the-browser-playground/:
  no horizontal overflow at 440px
2 smoke check(s) failed
```

The other jobs are smaller. `engine-ts` type-checks and tests the
TypeScript engine, then packs `@viscosity/cli` the way npm publishes it,
installs the tarball in an empty folder and runs it, so it tests what a
user would download rather than what the repository holds. `drip` tests
the book's companion interpreters, TypeScript and Rust, and `website`
builds the documentation site and checks its links.

<Callout kind="definition">
A **gate** is a step in CI that fails the run when it finds a problem.
A mistake reaches the main branch unnoticed only if **every** gate
misses it, which is why gates check different things, fast ones run
first, and a new kind of mistake gets a new gate.
</Callout>

<Formal title="How a mistake gets through">

```text
escapes(m) ⟺ ∀ g ∈ Gates : ¬ catches(g, m)
```

<span slot="read">A mistake m escapes exactly when, for every gate g,
g does not catch m (the symbol ¬ reads "not"). Adding a gate can only
shrink the set of mistakes that escape; it never lets one through that
was caught before.</span>
</Formal>

## What you learned

- A job's steps run in order, and the first failing **gate** skips the
  rest; the other jobs carry on.
- `engine-rust`: **format**, **77 tests in 14 binaries** (parity,
  differential, early errors, multi-file, fuzz, units), **Clippy** with
  `-D warnings`, a **wasm** build and **cargo package**.
- Committed **fixtures** must be regenerated with the reference, and a
  check finds the **missing** and the **stale**.
- `book`: the chapter checker, unit tests, references, the build, links
  and a **smoke test** at phone size on both engines.
