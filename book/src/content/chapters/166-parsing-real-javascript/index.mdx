## A bigger language

Drip's grammar fits on a page. JavaScript's specification is hundreds of
pages long<Cite id="ecma262" />, and it grows every year. Writing a
complete JavaScript parser is a project in itself, and it isn't the
project Viscosity is about. What Viscosity needs is a syntax tree it can
lower to VIR.

<Callout kind="intuition">
A shipping container has a standard size. Ships, cranes, trains and
lorries were all built around it, so any of them can carry any
container. ESTree is the standard container for JavaScript syntax trees:
many parsers fill it, many tools unload it, and none of them need to
know who packed it.
</Callout>

## ESTree

ESTree began as the documented output of the parser built into Firefox's
SpiderMonkey engine, and caught on as the common format for tools that
work on JavaScript source<Cite id="estree-readme" />. Every node is a
plain object whose `type` field says which kind of node it is, a
discriminated union, as chapter 27 showed<Cite id="estree" />. Here is
the real tree acorn builds for `p.x += p.vx;`, without its positions
and `optional` flags:

```
ExpressionStatement
  expression: AssignmentExpression
    operator: "+="
    left: MemberExpression
      object: Identifier "p"
      property: Identifier "x"
      computed: false
    right: MemberExpression
      object: Identifier "p"
      property: Identifier "vx"
      computed: false
```

`computed: false` is how ESTree tells `p.x` from `p[x]`. Each node also
has `start` and `end` offsets into the source, and, when asked for, a
`loc` with line numbers. Those offsets are what VIR's source references
point at, and what emit replaces.

<Callout kind="definition">
**ESTree** is the standard format for JavaScript syntax trees, shared by
parsers such as acorn and by tools that read their output. Each node is
an object with a string `type` (`Identifier`, `MemberExpression`, …)
plus fields specific to that type, and usually `start`/`end` source
offsets and a `loc` with lines and columns.
</Callout>

## The acorn adapter

By default the JavaScript plugin uses acorn, a small, fast parser
written in JavaScript that returns ESTree<Cite id="acorn" />. Inside
`lower`, trimmed:

```ts
const js = opts.typescript
  ? stripTypes(source) : source;
const program = acorn.parse(js, {
  ecmaVersion: 'latest',
  sourceType: 'module',
  locations: true,
  onComment: (_b, value, _s, _e,
      start, end) =>
    comments.push({ value,
      line: end?.line ?? start?.line }),
});
```

Three jobs hide in those lines. TypeScript is first turned into
JavaScript by sucrase, which removes types and leaves everything else
alone<Cite id="sucrase" />. `locations: true` asks for line numbers, for
explain. And `onComment` collects comments, which acorn reports through
that callback rather than in the tree, and `// @viscosity soa` lives in
one. After parsing,
the plugin matches each annotation to the declaration on the next line.

<Callout kind="definition">
A **parser adapter** wraps a third-party parser behind your own
interface. It calls the library with the options you need, collects
what the library reports separately (here, comments), and hands the
rest of the system the one format it expects (here, ESTree). Nothing
outside the adapter depends on the library itself.
</Callout>

## A parser you can read

The rest of the plugin only depends on ESTree: `estree.ts` describes
"the small slice of ESTree types the front-end touches". So any parser
that produces that slice, with offsets and lines, can replace acorn.
`jsPlugin({ parser: 'mini' })`, or `--parser mini` on the command line,
selects the book's own: `mini-parser.ts`, 448 lines. Statements are
recursive descent, as in Drip, one case per keyword:

```ts
case 'if': {
  p++; expect('(');
  const test = expression();
  expect(')');
  const consequent = statement();
  const alternate =
    eat('else') ? statement() : null;
  return node('IfStatement', t,
    { test, consequent, alternate });
}
```

Expressions use Pratt parsing with a table of binding powers. Here is
part of the table, and the loop at the heart of `binary`, trimmed:

```ts
const BIN = { '??': 1, '||': 2,
  '&&': 3, '+': 10, '-': 10,
  '*': 11, '/': 11, '**': 12, … };

let left = unary();
for (;;) {
  const op = peek().value;
  const bp = BIN[op];
  if (bp === undefined || bp <= minBp)
    break;
  p++;
  // ** is right-associative
  const right = binary(
    op === '**' ? bp - 1 : bp);
  left = node('BinaryExpression', t,
    { operator: op, left, right });
}
```

## Small, and honest about it

The mini parser covers what numeric, data-heavy code uses:
declarations, functions and arrows, loops including `for-of`, objects,
arrays, calls, members and every operator. Outside that, it stops
instead of guessing:

```
let y = a?.b;
→ optional chaining is not supported
  by the mini parser at line 1 near '?.'
```

<Callout kind="pitfall">
"Stops" isn't always "explains". `class A {}` isn't in the subset
either, but the mini parser reads `class` as a plain name and then
reports `expected ';' at line 1 near 'A'`. The error is safe but
confusing. A parser's error messages are only as good as the cases its
author thought of.
</Callout>

How do you know it is right on what it does accept? Chapter 146's answer:
compare. `mini-parser.test.ts` compiles every program in the
differential corpus (36 files) and the five end-to-end benchmark
programs with both parsers, and requires the compiled code and the
explanation to be byte-identical. The trees themselves needn't be: the
mini parser writes `operator` before `left`, and gives every node a
`loc` with column 0 and no end, details the plugin never reads. What matters is that the plugin can't
tell them apart.

<Prompts ids={['mp-test', 'mp-why']} />

<Callout kind="engine" label="Under the hood">
Why keep two parsers? acorn handles all of modern JavaScript, so it is
the default, and the Playground uses it too. The mini parser is for
learning: it is this book's parsing chapters applied to the real
language, and you can read all of it. Keeping it working forces the
plugin to depend on ESTree alone, never on acorn's quirks, and that is
what lets a different parser be dropped in later.
</Callout>

## What you learned

- **ESTree** is the shared tree format for JavaScript: objects tagged by
  `type`, with `start`/`end` offsets and `loc` lines.
- The **acorn adapter** calls acorn with the options Viscosity needs,
  collects comments for `@viscosity` annotations, and strips TypeScript
  first with sucrase.
- The hand-written **mini parser** uses recursive descent for statements
  and Pratt binding powers for expressions, and produces the same ESTree
  slice.
- Everything after parsing depends only on ESTree, so the parser is
  pluggable. A differential test checks that both parsers give
  byte-identical compiler output.
