## Two programs, two very different speed-ups

In this book's benchmark run (`drip-rs-bench-2026-11-02.md`), drip-rs
ran `fib.drip` in 406 ms against the TypeScript VM's 1,906 ms, 4.69
times as fast, but `strings.drip` in 305 ms against 383 ms, only 1.26
times. The same VM, the same machine, the same day: something about
`strings.drip` makes drip-rs's advantage almost vanish. You could guess
(the hash table? the garbage collector?), but a guess about where a
program spends its time is wrong more often than not, and changing code
on a wrong guess makes it more complicated and no faster. So we measure.

**Profiling** means measuring where a program's time (or instructions,
or memory) goes, function by function or line by line, rather than
timing the program as a whole. A **profiler** is the tool that does it.

<Analogy title="a month of bank statements">
You know you spent too much last month, but not on what. You could
guess "eating out", or you could add up the statement by category and
find it was the car. A profiler is the statement: it does not judge,
it only says where the money went.
<span slot="breaks">A statement lists every payment exactly; most time
profilers *sample*, glancing at the program a few thousand times a
second, so small costs can be missed or blurred. callgrind, used below,
is the exception that counts everything.</span>
</Analogy>

<Analogy extra title="a traffic survey">
A council that wants to know which junction to widen counts the cars at
each one, for a whole day, rather than asking drivers which road feels
slow.
<span slot="breaks">Cars are all the same size, roughly; instructions
are not. A cache miss can cost a hundred times an addition, and an
instruction count treats them the same, so a count is a strong hint
about time, not a measurement of it.</span>
</Analogy>

## What I ran

This machine has no `perf` (the usual Linux sampling profiler), but it
has valgrind 3.22, and valgrind's **callgrind** tool runs a program on a
simulated CPU and counts every instruction it executes (the event `Ir`),
attributed to the function and source line it came from, together with
who called whom and how many times<Cite id="valgrind-callgrind-manual" />.
To get function and line names, the release build needs debug info,
which Cargo can add from an environment variable without touching
`Cargo.toml`; I built into a scratch directory, from
`book/companion/rust`:

```text
CARGO_PROFILE_RELEASE_DEBUG=true \
CARGO_TARGET_DIR=$SCRATCH/target \
  cargo build --release
valgrind --tool=callgrind \
  --callgrind-out-file=fib.cg \
  $SCRATCH/target/release/drip-rs \
  ../corpus/benchmark/fib.drip
callgrind_annotate --auto=no fib.cg
callgrind_annotate --inclusive=yes \
  --tree=calling fib.cg
```

The run took 29 seconds instead of drip-rs's usual 0.4, about seventy
times slower, which is the price of simulating every instruction; the
counts, however, are the instructions the program really runs, and they
come out the same on every run, which no timing on a shared cloud
machine can promise. The first `callgrind_annotate` lists each
function's **self cost**, the instructions in its own body; the second
adds the **inclusive cost**, self plus everything it called, and the
call counts.

The first is the crudest profiler there is, a stopwatch round one call,
which tells you how long but not where. The second is two lines of
callgrind's call tree for fib (names shortened): 5.6 billion
instructions in all, and `call_value` called 7,049,155 times, which is
a good sign the profile is honest, because `fib(32)` makes exactly
7,049,155 calls (2 × fib(33) − 1, which you can check by hand). The
third, which you can run, times two loops with `clock()` and shows that
even the stopwatch can point you somewhere: the loop that calls `str`
is the slow one.

<SelfBars />

For fib, `Vm::run` alone is 65.2% of all instructions. That is not the
`match` statement on its own: the release build is compiled with link
time optimisation (`lto = true`), so small functions such as `push`,
`pop` and `read_byte` are **inlined** into `run`, and their
instructions count as `run`'s. With debug info, callgrind can still
split them out by source line, and two lines stand out: `read_byte`'s
`let byte = self.chunk.code[self.ip];` and `self.ip += 1;` are 5.7% of
the whole program each. The rest is `pop_numbers` (10.3%), the
bookkeeping of a call (10.2%), and `Table::get` (6.0%), which is the
global lookup of `fib` itself, made 7,049,155 times.

`strings.drip` looks nothing like that. `run`'s self cost is only
17.9%, and the big names are not drip-rs's at all: libc's `free` and
`malloc`, `fmod` (the `%` operator), and Rust's formatting machinery.

## Drawing it: the flame graph

A list of numbers hides the shape of the calls; a **flame graph** shows
it. Each box is a function on a particular call path, its width is the
share of the cost spent there (inclusive), and a box sits on top of the
function that called it, so the bare top edge of a box is its self
cost<Cite id="gregg-flamegraph" />. The left-to-right order means
nothing; boxes are only arranged so that identical paths merge.

<FlameSteps client:visible />

fib's graph is a wide, flat mountain: almost everything is the bare top
of `run`, so its time is the dispatch loop itself, which is exactly what
a bytecode VM in Rust should be good at. (It is only three boxes tall
even though fib recurses thirty levels deep, because a Drip call is a
frame on the VM's own stack, not a Rust call.) `strings.drip`'s graph is
a tall, thin tower: 60.9% of the program is inside `call_value`
running the native `str`, and climbing the tower, `format_number` is
48.2% on its own, with `format!` inside it (called 2,138,403 times, about
three times per number) at 35.3%. drip-rs spends most of `strings.drip`
turning small whole numbers like `42` into text, the slow way; that is
why its lead shrinks there, and the next chapter acts on it.

<Callout kind="definition">
**Profiling** is measuring where a program's cost goes, by function and
by line. A **sampling** profiler records the call stack many times a
second; an **instrumenting** one such as callgrind counts every
instruction. A function's **self** cost is in its own code; its
**inclusive** cost adds everything it calls. A **flame graph** draws
each call path as a stack of boxes, width for inclusive cost, so the
widest towers and the widest bare tops are where to look first.
</Callout>

<Formal title="Self and inclusive cost">

```text
incl(f) = self(f) + Σ incl(g)
          for each call f → g
share(f) = incl(f) / incl(main)
```

<span slot="read">The inclusive cost of f is its self cost plus the
inclusive costs of everything f calls; its share, which is a flame
graph box's width, is that divided by the whole program's cost. (For
recursive functions callgrind has to count each instruction once, which
is why its tree, not a simple sum, is the thing to trust.)</span>
</Formal>

<Examples of="flamegraph">

```text
main;run              3647937915
main;run;pop_numbers   578030669
main;run;call_value    204425495
```

```text
fib:     run ▇▇▇▇▇▇▇▇▇▇▇▇▇ (flat)
strings: run ▇ str ▇ format ▇ fmt!
             (a tall tower)
```

```text
node --cpu-prof src/cli.ts --vm \
  ../corpus/benchmark/instantiation.drip
```

</Examples>

The first is the input format of Brendan Gregg's `flamegraph.pl`: one
line per distinct call path, frames joined by `;`, then a count, here
three of fib's paths with their self costs; the script adds up the
widths of every prefix. The second is the shape to remember: a flat
graph says "the loop itself", a tower says "one call path". The third is
a sampling profiler for the other side, V8's own, run on the TypeScript
VM; it writes a `.cpuprofile` file, and on `instantiation.drip` I found
the VM's own hash table resizing (`Table.grow`, 12.2% of samples) and
V8's garbage collector (13.3%) near the top. *Benchmarks: three
implementations* uses that.

<Callout kind="engine" label="Under the hood">
callgrind's counts are deterministic: two runs of the same program give
the same count, give or take a few dozen instructions of start-up, so a
change that saves 1% of instructions shows up as 1%, where a 1% change
in time is lost in this shared machine's noise of tens of percent. The
catch, as the traffic survey said, is that instructions are not time;
the next chapter has a change that removed 8% of fib's instructions and
did not make it measurably faster.
</Callout>

## What you learned

- **Profiling** measures where cost goes; callgrind **counts every
  instruction**, a sampling profiler **glances** at the stack.
- **Self** cost is a function's own; **inclusive** adds its callees.
  Inlining moves small functions' cost into their caller.
- A **flame graph**: width is inclusive cost, the bare top is self cost,
  and left-to-right order means nothing.
- fib is the dispatch loop (`run` 65.2%); `strings.drip` is number
  formatting (`format_number` 48.2%), which is why drip-rs's lead
  shrinks there.
