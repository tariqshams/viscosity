## A VM you did not have to write

In Part IV you wrote a bytecode VM for Drip. Your compiler and your VM
agreed on a private format (which byte means "add", how a constant is
stored), and nobody else in the world could run your bytecode. *A tiny
JIT* then borrowed a format that every browser and Node already
understand, specified so precisely that independent engines run it the
same way: **WebAssembly**. There it was a door to machine code; here it
is the last target this track looks at, together with the one part that
JIT never needed, its memory.

<Analogy title="a shipping container">
A shipper does not care which port, crane or lorry handles the box,
because every one of them is built for the same standard size. Pack
your goods into the standard box once, and the whole world's equipment
can move it.
<span slot="breaks">A port does not open the box to check what is
inside. A WebAssembly engine does: it *validates* every module (checks
that each instruction gets the kinds of values it expects) before
running a single instruction of it.</span>
</Analogy>

## Forty-one bytes

Here is a whole WebAssembly program, written by hand as 41 bytes (a
cousin of the JIT's `sq` module, so this is a quick refresher). It
exports one function, `add`, that adds two 32-bit integers; step
through the bytes:

<ModuleBytes client:visible />

The format begins with the 4-byte magic number `\0asm` and the version,
1, and then comes a list of **sections**. Each section is a one-byte
id, the length of its contents, and the contents. The ids used here are
1 (types), 3 (functions), 7 (exports) and 10 (code), and those sections
must appear in that order<Cite id="wasm-spec-core" />. Lengths and
other integers are written in **LEB128**, a variable-length encoding in
which small numbers take a single byte, which is why each length here
is one byte.

<Formal title="Reading an unsigned LEB128 number">

```text
bytes b₀ b₁ … bₘ, where only bₘ < 0x80
n = Σₖ (bₖ & 0x7f) × 2^(7k)
e.g. 0x80 0x01 → 0 + 1 × 128 = 128
```

<span slot="read">A number is a run of bytes, and every byte except the
last has its top bit set (it is at least 0x80, "more follows"). Take the
low 7 bits of each byte, multiply the k-th group by 2 to the power 7k
(1, 128, 16,384, and so on), and add them up. The bytes 0x80 then 0x01
give 0 from the first and 1 times 128 from the second, so 128.</span>
</Formal>

The body of `add`, `20 00 20 01 6a 0b`, is bytecode for a stack
machine, like Drip's: push local 0, push local 1, add, end. The
difference is what happens before it runs. An engine first
**validates** the module, type-checking every function so that, for
example, `i32.add` can never find a missing value on the stack. The
specification notes that engines need no real operand stack at all:
because validation fixes the stack height at every point, the slots can
be treated as registers<Cite id="wasm-spec-core" />, and engines compile
modules to machine code.

<Callout kind="definition">
**WebAssembly** (Wasm) is a standardised, portable, low-level binary
format for code. A **module** is a preamble (`\0asm`, version 1)
followed by **sections**: types, functions, memories, exports, code and
others. Function bodies are bytecode for a typed **stack machine**.
Engines **validate** a module before running it, and usually compile it
to machine code.
</Callout>

<Examples of="webassembly">

```js
WebAssembly.validate(new Uint8Array([
  0x00, 0x61, 0x73, 0x6d,
  0x01, 0x00, 0x00, 0x00,
])); // true: no sections at all
```

<Run id="wasm-add" />

```js
import { compile } from '@viscosity/wasm';
const { code, explain } = compile(src);
// explain: ps (line 1) {x, vx} →
//   struct of arrays ...
```

</Examples>

The first is the smallest module there is, the preamble alone, which
`WebAssembly.validate` accepts (with version byte `0x02` it says
`false`). The second runs the 41-byte module: it prints its length,
`add(2, 3)`, and `add(2147483647, 1)`, which is `-2147483648`, because
`i32` arithmetic wraps around at 2³². (It uses the synchronous
`new WebAssembly.Module` because the book's runner stops when your code
returns; a real page uses `await WebAssembly.instantiate(bytes)`, which
compiles without freezing the page<Cite id="wasm-spec-jsapi" />.) The
third is realistic: `@viscosity/wasm` is the Rust port of Viscosity
compiled to WebAssembly and published to npm; its `compile` gives the
same `code` and `explain` as the TypeScript engine, and its 1.3 MB
`.wasm` file starts with the same eight bytes as the first example.

## One flat memory

The `add` function touched only its parameters. Real programs need
memory, and here WebAssembly is very different from JavaScript: in the
classic design there are no objects, no shapes and no garbage-collected
heap. There is one long array of bytes, the **linear memory**, and
instructions such as `f64.load` and `f64.store` read and write 8 bytes
at a numeric address<Cite id="wasm-spec-core" />. It is the picture
from *Memory is one long array*, made literal. The memory grows in
**pages** of 65,536 bytes; numbers are stored little-endian, smallest
byte first; and an access past the end does not corrupt anything: it
**traps**, which JavaScript sees as a thrown `WebAssembly.RuntimeError`.

<Analogy extra title="a street of numbered lockers">
A JavaScript heap is a city: objects live at addresses you never see,
and the garbage collector moves them around. Linear memory is one very
long street of numbered lockers, eight bytes wide each if you like. You
decide which locker holds what, and if you ask for locker 70,000 on a
street of 65,536, a guard stops you.
<span slot="breaks">Real lockers hold anything. These hold only bytes:
a string or an object has to be turned into bytes, and given an
address, by your own code, because the memory has no idea what a string
is.</span>
</Analogy>

<Callout kind="definition">
**Linear memory** is a WebAssembly module's contiguous, mutable array
of raw bytes, addressed by integers from 0. Its size is a whole number
of 64 KiB **pages**, and it can grow. Loads and stores are
little-endian, and an out-of-bounds access **traps**. JavaScript reaches
it as `memory.buffer`, an `ArrayBuffer` that typed arrays can view.
</Callout>

JavaScript and WebAssembly can look at the very same bytes: put a
`Float64Array` over `memory.buffer`, and what JavaScript writes,
WebAssembly reads.

<Examples of="linear-memory">

```js
// column k, element i, capacity cap
const addr = k * cap * 8 + i * 8;
// vx is column 1, cap 4, element 2:
// 1 * 4 * 8 + 2 * 8 = 48
```

<Run id="wasm-columns" />

```js
const xs = new Float64Array(mem.buffer);
mem.grow(1);
xs.length; // 0: the old buffer is gone
const ys = new Float64Array(mem.buffer);
ys.length; // 16384: two pages of f64s
```

</Examples>

The first is the whole layout of a struct of arrays in linear memory:
with capacity `cap`, column number `k` starts at byte `k * cap * 8`, and
element `i` is `i * 8` bytes further on, so `vx[2]` is at byte 48. The
second runs it: the module exports its memory and a `get(i)` doing
`f64.load` at `i * 8`; JavaScript writes four numbers and WebAssembly
reads `get(2)` as `3.5`, then 99 after JavaScript changes it. It also
prints the bytes of `1.5`, smallest first (ending `248 63`, which is
`0x3ff8...` backwards), shows the trap past the page, and grows the
memory. The third is the spot the difference that last line
hints at: growing the memory **detaches** the old `ArrayBuffer` and
makes a new one<Cite id="wasm-spec-jsapi" />, so a view made before the
grow suddenly has length 0, while a view made afterwards sees both
pages (131,072 bytes, 16,384 doubles). Make views again after every
grow, as *Growing collections* replaced its columns.

## Columns in linear memory

Viscosity's SoA containers already hold their numeric fields in
`Float64Array` columns; in linear memory, those columns become regions
of one memory:

  <ColumnsInMemory />
</Figure>

A loop over `x` and `vx` walks two contiguous runs of bytes, the
pattern Part II measured as fast, and WebAssembly's SIMD instructions
(from *SIMD: one instruction, many numbers*), such as `f64x2.add`, can
handle two lanes per instruction<Cite id="wasm-simd" />. So is this
what Viscosity does? Not yet, and the honest answer has three parts:

- **Neither engine has a WebAssembly back end.** Both plugins rewrite
  source code: JavaScript in, JavaScript out, and Python in, Python
  out.
- **WebAssembly runs the compiler, not its output.** The Rust port's
  `viscosity-wasm` crate wraps the whole compiler; it reproduces every
  parity fixture, is published as `@viscosity/wasm`, and is what the
  book's Playground runs when you switch it to **Rust** (Track B's
  *Compiling the engine to WebAssembly* builds it). Its output is still
  JavaScript or Python.
- **Emitting loops as WebAssembly is a design, not code.** Strings and
  objects have no place in linear memory, columns would move when it
  grows, and every call crosses a boundary; whether a hot loop gains
  enough to pay for that is unmeasured.

<Callout kind="engine" label="Under the hood">
WebAssembly keeps growing through proposals. Fixed-width SIMD became
part of version 2.0; version 3.0 added, among others, garbage
collection, multiple memories and 64-bit memories
(Memory64)<Cite id="wasm-finished-proposals" />. With garbage
collection a compiler can ask the engine for managed structs and arrays
instead of managing linear memory by hand, so a future Viscosity back
end would face the same choice this whole track has been about: which
layout, decided by whom.
</Callout>

## What you learned

- **WebAssembly** is a standardised, portable binary format for code:
  a preamble (`\0asm`, version 1) and **sections** with ids, lengths
  and contents, with lengths in LEB128. Bodies are bytecode for a
  **stack machine** that engines **validate** and then compile.
- JavaScript loads modules through the `WebAssembly` object and calls
  their **exports**; `i32` arithmetic wraps around.
- **Linear memory** is one flat, growable array of bytes, in 64 KiB
  **pages**, little-endian, **trapping** on out-of-bounds access, seen
  from JavaScript through `memory.buffer`, which a grow detaches.
- SoA columns map onto linear memory as one start address per column.
  Viscosity does not emit WebAssembly; the Rust port compiles *the
  compiler* to WebAssembly, which is a different job.
