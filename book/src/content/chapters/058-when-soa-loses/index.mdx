## The code that wants its objects back

The last chapter measured struct of arrays winning: a loop that reads a
few fields of many particles streams through a few columns and nothing
else. However, real programs do not only run tight loops; sometimes the
code really does want an object, because it pushes particles into a
list, hands them to a library, or returns one to its caller:

```js
const near = [];
for (let i = 0; i < n; i++) {
  if (x[i] < 10) near.push(get(s, i));
}
```

With columns there *is* no particle object to push, so `get(s, i)` has
to make one. This chapter is about what that costs, when it costs
nothing at all, and the blocked layout that sits between the two
extremes.

## Materialization

<Analogy title="flat-pack furniture">
A furniture warehouse stores chairs flat-packed, every leg with the
legs and every seat with the seats; it is compact, and counting the
legs is easy. But each time a customer wants a chair to take home,
someone has to assemble a new one from the parts, and two customers
asking for "chair 12" get two different chairs.
<span slot="breaks">A warehouse always pays to assemble; an engine that
can see the object is used briefly and thrown away may skip building it
altogether, as the second benchmark below shows.</span>
</Analogy>

<Analogy title="a photocopy of a record">
Ask the records office for your file and you get a photocopy. Writing
on the copy changes nothing in the office's file, and if you ask twice
you hold two separate sheets, even though they say the same thing.
<span slot="breaks">Photocopies cost paper whether or not you read
them; a materialized object only costs something if it is kept, or
passed somewhere the engine cannot follow.</span>
</Analogy>

Here is the smallest version of `get`, building an object from two
columns, and what it means for identity (the "same object?" question
from the chapter on references):

<MaterializeSteps client:visible />

<Callout kind="definition">
**Materialization** is rebuilding a whole object from its columns. It
costs an allocation per object, and each new object has a new identity,
so two materializations of the same element are never `===`, and
writing to one does not change the columns.
</Callout>

<Examples of="materialization">

```js
function get(s, i) {
  return { x: s.x[i], y: s.y[i] };
}
```

<Run id="materialize" />

```js
// kept: one real object per element
const all = [];
for (let i = 0; i < n; i++) {
  all.push(get(s, i));
}
```

</Examples>

The first is the simplest materialization: read slot `i` of each column
and put the values in a fresh object literal; every call allocates. The
second you can run: it is the code from the diagram, so it prints the two
equal-looking objects, then `false` for `a === b`, then `1`, because
`a.x = 99` changed only the copy. The third is the expensive pattern: it
keeps every materialized object, so the program ends up holding an
array of real objects, one allocation per element, which is exactly what
the array of objects had for free.

## What it costs, and when it costs nothing

The `materialize` suite in this book's benchmark does the third example:
it builds an array holding one real object per element.

<BenchBars suite="materialize" n={100000} title="Building one real object per element" highlight={['soa']} layouts={['aos', 'soa']} caption="AoS copies references to objects it already has; SoA must allocate every object." />

In this book's run SoA was about 20 to 35 times *slower* than the array
of objects, at 100,000 and 1,000,000 elements. The array of objects only
copies references to objects that already exist, while SoA allocates a
new object for every element; materializing objects that are *kept* can
wipe out every gain the columns made.

The `get-objects` suite looks similar but is different in one way that
matters. It hands each element to a small function that wants an object
and reads its six fields, but does not keep it (simplified from the
harness):

```js
function consume(p) {
  return p.x + p.y + p.vx +
    p.vy + p.mass + p.health;
}
for (let i = 0; i < n; i++) {
  sum += consume(get(s, i));
}
```

<BenchBars suite="get-objects" n={100000} title="Passing each element to a function that wants an object" highlight={['soa']} layouts={['aos', 'soa']} caption="The temporary object never escapes, so V8 removes it, and SoA keeps its lead." />

Here, in this book's run, SoA did **not** lose; it was about 3 times
faster. V8 inlined `consume` (copied its body into the loop) and then saw
that the temporary object was never stored anywhere, never returned and
never compared, so it removed the object altogether and read the columns
directly. An object that is only used inside the code that made it is
said not to **escape**; whether materializing costs anything depends
entirely on whether the object escapes, which is the question
Viscosity's escape analysis must answer. A TypeScript experiment by Zap
found the same shape: SoA wins on reading a few fields, and loses when
whole objects must be rebuilt<Cite id="ziap2025" />.

## AoSoA: blocks of columns

Between "every field of a record together" and "every value of a field
together" there is a middle layout: cut the particles into blocks of a
fixed size, and store each block as a little struct of arrays.

<Analogy title="a weekly pill organiser">
A pill organiser has one row per kind of pill and one column per day;
each box covers one week, and the next week is the next box. To take
all the morning pills for a week, you run your finger along one row of
one box; to find Wednesday of week three, you pick the box, then the
column.
<span slot="breaks">A pill box is as wide as a week because weeks have
seven days; a block of 8 doubles is chosen to fill exactly one 64-byte
cache line (and, on some hardware, one SIMD register), a fit the pill
box has no reason to care about.</span>
</Analogy>

<Figure takeaway="Inside a block it is SoA; blocks follow one another." caption="AoSoA with blocks of 8 and six fields: each block is 48 slots, a row of 8 x values, then 8 y values, and so on. Particle 10 is lane 2 of block 1, so its vx is at slot 48 + 16 + 2 = 66.">
  <AosoaBlocks />
</Figure>

<Callout kind="definition">
**AoSoA** (array of structs of arrays) is the hybrid layout: the records
are cut into fixed-size blocks, and inside each block the fields are
stored as columns. With blocks of 8 doubles, each field's run inside a
block is exactly one cache line.
</Callout>

<Formal title="Finding a field in AoSoA">

```text
block = ⌊i ÷ B⌋      lane = i mod B
slot(i, f) = block × B × F + f × B + lane
B = 8, F = 6:  slot(10, 2) = 48 + 16 + 2
```

<span slot="read">With blocks of B records and F fields, record i lives
in block "i divided by B, rounded down", at lane "the remainder of i
divided by B". Field f of that record is at the start of its block
(block times B times F), plus f rows of B, plus the lane. For blocks of
8 and six fields, particle 10's field 2 is in block 1, lane 2: slot 66.</span>
</Formal>

<Examples of="aosoa">

```js
// particle 0, field 1 (y)
0 * 48 + 1 * 8 + 0; // slot 8
```

```js
// particle 10, field 2 (vx)
Math.floor(10 / 8) * 48 + 2 * 8 + 10 % 8;
// 66
```

```js
// in order: blocks, then lanes
for (let b = 0; b < n / 8; b++) {
  const o = b * 48;
  for (let l = 0; l < 8; l++) {
    f[o + l] += f[o + 16 + l]; // x += vx
  }
}
```

</Examples>

The first shows that inside block 0, field 1 starts right after the 8
`x` values, at slot 8. The second is the general case, with the
division (`Math.floor(10 / 8)` is 1) and the remainder (`10 % 8` is 2)
that every random access has to do. The third is how a sequential loop
avoids that arithmetic: walk block by block (`o` is the block's first
slot), and inside a block walk the lanes, so `x` is at `o + l` and `vx`
two rows later at `o + 16 + l`. (This simple version assumes `n` is a
multiple of 8.) ISPC builds this layout into the language as `soa<8>`,
keeping ordinary `pts[i].x` syntax while storing blocks<Cite id="ispcdocs" /><Cite id="pharrmark2012" />,
and its performance guide recommends the blocked layout when vector
loads matter<Cite id="ispc-perfguide" />.

## AoSoA, measured

In order, over a million particles, AoSoA does well:

<BenchBars suite="update-xy" n={1000000} title="Moving 1,000,000 particles, in order" highlight={['aosoa8']} layouts={['aos', 'soa', 'aosoa8']} caption="Walking block by block, AoSoA streams almost as well as SoA." />

In this book's run it was about 3.2 times faster than the array of
objects, close to SoA's 3.3. In shuffled order it is a different story:

<BenchBars suite="random-x" n={1000000} title="Reading x and vx in shuffled order" highlight={['aosoa8']} layouts={['aos', 'soa', 'aosoa8']} caption="Every random access pays for a division and a remainder." />

There AoSoA was only about 1.8 times faster than objects, against
SoA's 7.5; and with 1,000 particles it was slower than the array of
objects even in order. Every random access must work out a block and a
lane, and in plain JavaScript, without SIMD to pay that back, the
arithmetic is pure cost.

<Prompts ids={['aosoa-random', 'aosoa-small']} />

<Callout kind="engine" label="Under the hood">
So no layout always wins: SoA for a few fields of many records,
objects when real objects must be kept, and AoSoA when blocks match the
hardware and the access is in order. Research on JavaScript engines
makes this choice while the program runs: a JIT watches an array of
objects and switches it to columnar storage automatically<Cite id="makor2022" />,
then generates specialized code paths for the transformed
arrays<Cite id="kloibhofer2023" />. Viscosity makes the same decision
ahead of time, as a compiler pass, and its escape analysis is what tells
the cheap materializations (the object never escapes) from the
expensive ones (it is kept).
</Callout>

## What you learned

- **Materialization** rebuilds an object from columns: one allocation
  each, a new identity each time, and writes that never reach the
  columns.
- When the objects are *kept*, it can be far slower than an array of
  objects (about 20 to 35 times in this book's run); when they do not
  **escape**, V8 may remove them entirely.
- **AoSoA** stores fixed-size blocks, SoA inside each block; with blocks
  of 8 doubles, each field's run is one cache line.
- In order it streams nearly as well as SoA; at random, every access
  pays for a division and a remainder.
