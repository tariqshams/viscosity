## A library needs a front door

The Rust port is a library, `compile(source, &JsPlugin, opts)`, but what
people type is `viscosity explain particles.js`. The program that answers
is the crate `engine/rust/crates/cli`, a binary called `viscosity`. Most
of its `main.rs` is plumbing between the shell and the compiler,
following conventions much older than Rust, plus one rule of Viscosity's
own: the Rust CLI must behave exactly like the TypeScript one.

<Analogy title="a post office counter">
You slide a form under the glass (the words you typed). The clerk hands
the receipt back through one slot and any complaint through another, so
you can file the receipts in a drawer and still read the complaints; and
as you leave, a light over the door turns green or red, so the next
person in the queue knows how it went without reading anything.
<span slot="breaks">A clerk can ask you a question halfway through; a CLI
like this one never does. Everything it needs is in the words you typed,
and everything it says goes out through the two slots and the light.</span>
</Analogy>

<Callout kind="definition">
A **command-line interface** (**CLI**) is a program driven from a
terminal. It receives a list of strings, its **arguments**, from the
shell. It writes its results to **standard output** (**stdout**) and its
messages to **standard error** (**stderr**), so that a user can send the
results to a file and still see the errors. When it ends it hands an
**exit status**, a small number, back to whoever started it: 0 for
success and, by convention, anything else for
failure<Cite id="rust-book-ch12-cli" />.
</Callout>

<Examples of="cli">

```
$ viscosity --version; echo "exit $?"
viscosity 0.0.2
exit 0
```

```
$ viscosity explain p.js > out.txt
$ echo $?; wc -c out.txt
0
229 out.txt
```

```
$ viscosity explain gone.js; echo $?
viscosity: cannot read gone.js: No such
  file or directory (os error 2)
1
```

</Examples>

I ran all three with the release build of the current tree (the long
line is wrapped). In the first, `$?`, the shell's name for the last exit
status, is `0`; the number is baked in from `Cargo.toml` by
`env!("CARGO_PKG_VERSION")`, so the binary from crates.io, still at
0.0.1, says `viscosity 0.0.1`. In the second, `>` sends stdout into `out.txt`,
so nothing reaches the screen and the file holds the 229-byte report. In
the third the file does not exist, so stdout stays empty, the message
goes to stderr (which `>` would not have caught) and the status is `1`.
In Rust the arguments come from `std::env::args_os()`<Cite id="rust-std-env-args" />,
and `main` returns an `ExitCode`<Cite id="rust-std-exitcode" />.

## Two kinds of error

Some failures are about the command line itself (an unknown flag, a
missing value, no files at all), and then the help text is useful. A
missing file or a syntax error is different: the command was fine, and
27 lines of help would bury the one line that matters. So the CLI's
error type keeps the two apart, and everything ends in one `match` in
`main` (from `main.rs`, rewrapped):

```rust
enum CliError {
    Usage(String),
    Other(String),
}

match run(&argv, &mut stdout, &mut stderr) {
    Ok(true) => ExitCode::SUCCESS,
    Ok(false) => ExitCode::FAILURE,
    Err(CliError::Usage(e)) => {
        let _ = write!(stderr,
            "viscosity: {e}\n\n{HELP}");
        ExitCode::FAILURE
    }
    Err(CliError::Other(e)) => {
        let _ = writeln!(stderr,
            "viscosity: {e}");
        ExitCode::FAILURE
    }
}
```

`impl From<String> for CliError` turns any plain `String` error into
`Other`, so `?` passes errors from reading and compiling straight up.
`run` returns `Ok(true)` when everything compiled, `Ok(false)` when the
run went fine but one of several files failed (that file is reported as
`viscosity: bad.js: Unexpected token (1:12)` while the others still
compile), and an `Err` otherwise. The two `Err` arms differ only in what
they write: the help after a blank line, or one line. (`let _ =` throws
away the result of writing: if stderr itself is broken, there is nobody
left to tell.) Every failure exits with `1`. Step through six real
command lines:

## Reading the words

The shell hands the program a list of strings, such as `["build",
"a.js", "-o", "out/", "--frames", "b.js"]`, and every word means
something different: `build` is what to do, `a.js` and `b.js` are files,
`--frames` switches a feature on, and `-o` says "the next word is where
the output goes", so `out/` is not a file to compile at all.

<Figure caption="The four kinds of word on one command line. An option and its value are read together, so out/ is never mistaken for a file." takeaway="Each word is a command, a file, a flag or an option, and an option takes the next word with it.">
  <WordKinds />
</Figure>

<Callout kind="definition">
**Argument parsing** turns a CLI's list of words into typed options; in
Viscosity, an `Args` struct with the command, the files, the output path
and a `CompileOptions`. A **flag** such as `--frames` is a switch, on if
present. An **option** such as `-o out/` takes the next word as its
**value**. The other words are **positional** arguments: here, the
command and then the files.
</Callout>

`parse_args` in `main.rs` is a `while` loop over the words, with an
index `i`. For each word it builds a closure, `next_os`, which moves `i`
on by one and returns that word, or, past the end, a usage error such as
"-o needs a value" (`argv.get(i)` gives `None`, and `ok_or_else` turns it
into the `Err`). The closure borrows `i` mutably, which the borrow
checker allows because the borrow ends when the `match` last uses the
closure, before the loop's own `i += 1`. Then the `match` (an excerpt,
rewrapped):

```rust
match a {
    "-o" | "--out" =>
        args.out = next_os()?,
    "--explain" => args.explain = true,
    "--frames" => args.frames = true,
    // ... --jobs, --mode, --bounds, ...
    _ if !a.starts_with('-') =>
        args.files.push(PathBuf::from(a)),
    _ => return Err(CliError::Usage(
        format!("unknown option {a}"))),
}
```

An option's arm calls `next_os()?`, so a missing value returns at once.
A flag's arm sets a boolean. The last two arms catch everything else in
a deliberate order: any word *without* a dash is a file (the `_ if ...`
is a **match guard**), and anything left is an unknown option; `match`
tries its arms from top to bottom, so the real flags come first. Step
through a real command line:

<Examples of="argument-parsing">

```
$ viscosity build a.js -o out/ b.js --frames
  files [a.js, b.js], out "out/",
  frames on
```

```
$ viscosity explain a.js --min-size 0x10
  files [a.js], min_size 16
```

</Examples>

The first shows that order is free: `b.js` after `-o out/` is still a
file, because `out/` was taken by `-o`. In the second, `--min-size` is
read with `js_to_number`, a copy of JavaScript's `Number()` as the
TypeScript CLI uses, so `0x10` is 16; Rust's `str::parse` would refuse
it, and would accept `inf`, which both real CLIs refuse.

<Prompts ids={['flag-vs-option', 'next-closure', 'arm-order', 'js-number']} />

<More title="The loop itself, and how the two number parsers disagree">

```rust
let mut i = 1; // argv[0] is the command
while i < argv.len() {
    let raw = &argv[i];
    let Some(a) = raw.to_str() else {
        // ... not UTF-8: a file name
    };
    let mut next_os = || {
        i += 1;
        argv.get(i).cloned().ok_or_else(
            || CliError::Usage(format!(
                "{a} needs a value")))
    };
    let mut next = || next_os()
        .map(|v| v.to_string_lossy()
            .into_owned());
    match a { /* as above */ }
    i += 1;
}
```

`raw.to_str()` asks whether the word is valid UTF-8; every option is
plain ASCII, so a word that is not text can only be a file name. That is
why the CLI collects `args_os()`, not `args()`, which panics on such a
word<Cite id="rust-std-env-args" /> (Linux allows any bytes in a file
name); it once did, and `tests/os_args.rs` now checks it. `next` is
`next_os` for values that must be text.

<Run id="numbers" />

Each line shows the input, what JavaScript's rules give and what Rust's
`parse` gives (`None` when it refuses): a padded `" 12 "`, an empty
string and `"0x10"` are numbers to JavaScript and errors to Rust, while
`"inf"` is the other way round.

<Formal title="The grammar of a Viscosity command line">

```text
line   ::= command word*
word   ::= flag | option value | file
flag   ::= "--frames" | "--explain" | ...
option ::= "-o" | "--mode" | "--jobs" | ...
file   ::= any word not starting with "-"
```

<span slot="read">A line is a command followed by any number of words.
Each word is a flag, or an option followed by its value, or a file.
Nothing nests inside anything else, so one loop that looks at one word at
a time can read all of it, with no recursion and no stack.</span>
</Formal>
</More>

<More title="What clap would change">
clap is the "Command Line Argument Parser for Rust"<Cite id="clap-readme" />,
and most Rust CLIs use it. Here is part of Viscosity's CLI in its
declarative style; a design, not code from the repository (I built it
against clap 4.6.7 to see what it does):

```rust
// Design: not in the repository.
#[derive(Parser)]
#[command(version)]
struct Cli {
    #[command(subcommand)]
    cmd: Cmd,
}

#[derive(Subcommand)]
enum Cmd {
    /// Show every decision and why
    Explain {
        files: Vec<String>,
        #[arg(long)]
        frames: bool,
        #[arg(long, default_value_t = 64.0)]
        min_size: f64,
    },
}
```

It is shorter, but it is a different CLI. On `--bogus` it printed
`error: unexpected argument '--bogus' found` rather than `viscosity:
unknown option --bogus`, and exited with status 2, clap's code for usage
errors<Cite id="clap-readme" />, where both real CLIs exit with 1. It
refused `--min-size 0x10` and accepted `--min-size inf`. The repository
does not say why the port skipped clap, but the code points one way:
`tests/multi_file.rs` runs both CLIs and compares their output and, for
bad `--min-size` values, their messages and exit statuses. With clap,
those would be clap's to choose.

<Analogy extra title="taking a coffee order">
"Flat white, oat milk, extra shot, to go." The barista hears it in
order: "flat white" is the drink, "to go" is a switch, and "milk" only
makes sense with the word after it, so "oat" is not a second drink.
<span slot="breaks">A barista who hears "oat mlik" guesses what you
meant; the parser does not guess, and an unknown word that starts with a
dash stops everything with "unknown option".</span>
</Analogy>
</More>

## What you learned

- A **CLI** receives **arguments** and gives back results on **stdout**,
  messages on **stderr**, and an **exit status**, 0 for success and 1 for
  every failure in Viscosity.
- `CliError` separates **usage errors**, which print the help, from
  everything else, which prints one line.
- **Argument parsing** sorts words into a command, **files**, **flags**
  and **options** with a **value**; the Rust CLI does it with one loop, a
  closure and a `match` whose arm order matters.
- Parsing by hand keeps the messages, number parsing and exit status
  identical to the TypeScript CLI's.
