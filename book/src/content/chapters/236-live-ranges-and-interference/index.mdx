## Who can share a register?

After instruction selection and leaving SSA, `sumsq` is RISC-V code
with **virtual registers**: names like `s1` and `t` that the
instruction selector invented freely, as many as it liked.

```text
b0: li   s0, 0
    li   i0, 0
    mv   s1, s0
    mv   i1, i0
b1: bge  i1, n, b4
b2: mul  t, i1, i1
    add  s2, s1, t
    addi i2, i1, 1
    mv   s1, s2
    mv   i1, i2
    j    b1
b4: mv   a0, s1
    ret
```

(`mv` is RISC-V's copy, a pseudoinstruction for `addi rd, rs, 0`; `n`
is the parameter, which arrives in a register.) There are eight
virtual registers here, and RISC-V has 31 usable integer registers,
so this one would fit anyway; however, a real function can have
thousands, and the question is the same at any size: which virtual
registers can share one real register? Two values can live in the
same register if they are never both needed at the same moment,
because then one is always finished with before the other begins.

An office has fewer desks than staff, because not everyone is in on

<span slot="breaks">People's diaries are a guess; a compiler must be

</Analogy>

A hotel gives the same room to two guests whose stays do not overlap:

whose stays overlap by even a night need different rooms.
<span slot="breaks">A hotel stay is one unbroken span of days; a

## Live ranges

Chapter 210 gave us exactly the tool: a variable is **live** at a
point if some path from there reads it before it is overwritten, and
the live sets come from a backward dataflow analysis, iterated to a
fixpoint. For `sumsq` the analysis gives these sets on entry to each
block:

```text
in(b0) = {n}
in(b1) = {i1, n, s1}
in(b2) = {i1, n, s1}
in(b4) = {s1}
```

Inside a block we walk backwards from its live-out set, one
instruction at a time, with the rule of chapter 210: above an
instruction, remove what it defines, then add what it reads. The set
of all the points where a value is live is its **live range**. `n`
is live everywhere from the entry to the loop test, round and round
the loop; `t` lives only between the `mul` that makes it and the `add`
that uses it, a single instruction gap.

<Callout kind="definition">
The **live range** of a value (a virtual register) is the set of
program points at which it is live: every point from which some path
reaches a use of it without passing a new definition. It can stretch
across blocks and round loops, and it need not be one unbroken
stretch of code.
</Callout>

<Examples of="live-range">

```text
a = p + 1      ; a live: here ...
b = a * 2      ; ... to here
return b       ; b live from line 2
```

```text
b1: bge i1, n, b4    ; n read here,
b2: ...              ; so n is live in
    j   b1           ; all of the loop
```

```text
if c { x = 1; f(x) }
else { g() }
h(); x = 2; f(x)     ; x: two pieces
```

</Examples>

The first is the simplest case: `a` is live from its definition to
the line that reads it, and `b` from its definition to the return, so
the two ranges touch but do not overlap. The second is `sumsq`'s `n`:
it is read only in the loop test, but every trip comes back to that
test, so it is live throughout the body as well. The third is varied:
`x` is live inside the `if` branch and again after `x = 2`, with a
gap between, where nothing will read the old value (in SSA the two
pieces had different names, which is why splitting them is natural).

## Interference

Two values **interfere** if they are live at the same moment, so they
cannot share a register. A simple way to find every such pair comes
from Chaitin: at each instruction that defines a value `d`, look at
what is live just *after* it; every other value there is still needed
while `d` is being written, so `d` interferes with each of them
<Cite id="chaitin1982" />. There is one exception, for copies: after
`mv d, s`, the values `d` and `s` are equal, so they do not need
different registers, and we add no edge between them. Step through

Doing the same for b0 and b4 and collecting all the edges gives the
**interference graph**: one node per value, and an edge between every

<Callout kind="definition">
Two values **interfere** if one is defined at a point where the other
is live (and the definition is not a copy of the other). The
**interference graph** has a node for each value and an edge between
each pair that interferes. Values joined by an edge must go in
different registers; values with no edge between them may share one.
</Callout>

<Formal title="Building the interference graph">

```text
for each instruction I, defining d:
  for each x ∈ liveOut(I), x ≠ d:
    if I is not the copy d ← x:
      add the edge {d, x}
```

<span slot="read">Go through every instruction I that defines a value
d. For each value x in the set of values live just after I, other
than d itself, add an edge between d and x, unless I is a copy that
sets d from x, because then the two hold the same value and may share
a register.</span>
</Formal>

<Examples of="interference-graph">

```text
a = p + 1
b = a * 2    ; a dead after: no a–b edge
```

```text
b = a        ; a copy: no a–b edge
f(a, b)      ; a and b still equal
```

```text
mul t, i1, i1   ; live after: i1 n s1 t
                ; edges t–i1, t–n, t–s1
```

</Examples>

In the first, `a` dies at the very instruction that defines `b`, so
`b` is defined when `a` is no longer live; they get no edge, and
`b = a * 2` can even write its result over `a` in the same register.
In the second, `b` is a copy of `a`, both are used later, and neither
changes in between; the copy rule leaves them unjoined, so one
register holds both. The third is from the stepper: three edges at
once, because `i1`, `n` and `s1` are all still needed while `t` is

<Callout kind="engine" label="Under the hood">
LLVM's register allocators work from **live intervals**, "the ranges
(intervals) where a variable is live", and use them "to determine if
two or more virtual registers which require the same physical
register are live at the same point in the program"
<Cite id="llvm-codegen" />, which is interference by another name.
regalloc2 starts the same way, with live-in and live-out sets per
block from "a standard backward iterative dataflow analysis", and its
authors note that keeping them exact rather than approximate "turns
out to be important for performance"<Cite id="regalloc2" />. The
graph itself can be big (a function with thousands of values can
have a great many edges), which is why textbook allocators store it
twice, as a bit matrix for "do these two interfere?" and as lists for
"who are this value's neighbours?"<Cite id="coopertorczon2022" />.
Viscosity builds no interference graph, since it allocates no
registers.
</Callout>

## What you learned

- A value's **live range** is every point where it is live; it can
  run round loops and come in pieces.
- Two values **interfere** if one is defined while the other is live;
  a copy does not make its source and destination interfere.
- The **interference graph** has an edge for every interfering pair;
  values joined by an edge need different registers.
- In `sumsq`, `n`, `s1`, `i1` and `t` all touch, so the loop needs
  four registers, and the four copies are pairs that could share.
