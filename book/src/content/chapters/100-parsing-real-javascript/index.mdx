## A bigger language

Drip's grammar fits on a page; JavaScript's specification is hundreds of
pages long<Cite id="ecma262" />, and it grows every year. Writing a
complete JavaScript parser is a project in itself, and not the one
Viscosity is about: what it needs is a syntax tree (*Syntax trees and a
tree printer*) that its plugin can lower to VIR. So the real question is
not "how do we parse?" but "what shape should the tree be?", because if
we pick a shape other parsers already produce, we can use theirs.

<Analogy title="a shipping container">
A shipping container has a standard size, and ships, cranes, trains and
lorries were all built around it, so any of them can carry any container
and none needs to know who packed it. ESTree is the standard container
for JavaScript syntax trees: many parsers fill it, and many tools unload
it.
<span slot="breaks">A container's contents are hidden and anything fits
inside; an ESTree node's contents are the whole point, and each kind of
node has exactly the fields its type promises.</span>
</Analogy>

## ESTree

ESTree began as the documented output of the parser in Firefox's
SpiderMonkey engine, and caught on as the common format for tools that
work on JavaScript source<Cite id="estree-readme" />. Every node is a
plain object whose `type` field says which kind of node it is (a tagged
union, as in *Tagged unions: the shape of every syntax tree*), plus the
fields that type promises<Cite id="estree" />.

<Callout kind="definition">
**ESTree** is the standard format for JavaScript syntax trees, shared by
parsers such as acorn and by the tools that read their output. Each node
is an object with a string `type` (`Identifier`, `MemberExpression`, …)
plus fields specific to that type, and usually `start`/`end` source
offsets and a `loc` with lines and columns.
</Callout>

<Examples of="estree">

```text
p.x += p.vx;     (acorn, no positions)
ExpressionStatement
  expression: AssignmentExpression
    operator: "+="
    left: MemberExpression
      object: Identifier "p"
      property: Identifier "x"
      computed: false
    right: MemberExpression
      object: Identifier "p"
      property: Identifier "vx"
      computed: false
```

</Examples>

The whole line is an *expression statement* (an expression used as a
statement), whose expression is an assignment with operator `+=`. Its
left side, `p.x`, is a `MemberExpression` (a property read) whose object
is the name `p` and whose property is the name `x`, and the right side
has the same shape for `p.vx`. `computed: false` is how ESTree tells
`p.x` from `p[x]`, the flag that matters most to Viscosity: in the
first, `x` is a field's name it might turn into a column, and in the
second, `x` is a variable whose *value* picks the field. An element
access `ps[i].x` is therefore two nested `MemberExpression`s, an outer
non-computed one (`.x`) around an inner computed one (`ps[i]`):

## Every node knows its characters

Each node also has `start` and `end`, offsets into the source text
counted in characters from the start of the file, with `end` one past
the last character; children nest inside their parent's range. Those
offsets are what VIR's source references point at and what emit
replaces, so they matter to Viscosity as much as the tree itself. In
`p.x += p.vx;`, the right side covers 7 to 11, and `source.slice(7, 11)`
is exactly `p.vx`:

<More title="More: the nesting rule, and slicing by hand">

<Formal title="Nodes cover ranges, and children nest">

```text
text(n) = source[n.start .. n.end)
c a child of n  ⟹
  n.start ≤ c.start ≤ c.end ≤ n.end
```

<span slot="read">The text of a node n is the slice of the source from
n.start up to, but not including, n.end. If c is a child of n, then c's
range lies inside n's.</span>
</Formal>

The runnable example walks a hand-made tree and prints each node's text;
add a node with a wrong range and see the slice come out wrong. Ask
acorn for `locations: true`, and each node also gets a `loc` with line
and column numbers.

Every file in Viscosity's JavaScript plugin after the parser reads only
ESTree: `estree.ts` describes "the small slice of ESTree types the
front-end touches", a `Node` with a `type`, `start`, `end` and an
optional `loc`, and nothing there mentions acorn. That one decision makes
the parser replaceable, and it means the plugin's shapes (an
`ArrowFunctionExpression`, a `ForOfStatement`) are the ones every linter
and bundler uses too.

## The acorn adapter

The plugin calls acorn, a small, fast parser written in JavaScript that
returns ESTree<Cite id="acorn" />; however, a bare call is not quite
enough. The plugin also needs the comments (where `// @viscosity soa`
lives), line numbers (for explain), and a way to read TypeScript, which
acorn does not parse. Here is the parsing step inside `lower`, from
`frontend-js/src/index.ts`, trimmed:

<Examples of="parser-adapter">

```ts
const js = opts.typescript
  ? stripTypes(source) : source;
const program = acorn.parse(js, {
  ecmaVersion: 'latest',
  sourceType: 'module',
  locations: true,
  onComment: (_b, value, _s, _e,
      start, end) =>
    comments.push({ value,
      line: end?.line ?? start?.line }),
});
```

</Examples>

Line 1 strips TypeScript first, with a library called sucrase that
removes types and leaves everything else alone<Cite id="sucrase" />; an
`interface` disappears but leaves an empty line, so every later line
keeps its number. `ecmaVersion: 'latest'` accepts all of modern
JavaScript, `sourceType: 'module'` allows `import` and `export`, and
`locations: true` adds line numbers to every node. `onComment` is a
callback acorn calls for each comment, because acorn reports comments
that way rather than in the tree; after parsing, the plugin matches each
`@viscosity` comment to a declaration (one on a line of its own
annotates the next line, one after code annotates its own line).

<Callout kind="definition">
A **parser adapter** wraps a third-party parser behind your own
interface. It calls the library with the options you need, collects
what the library reports separately (here, comments), prepares the input
the library cannot handle (here, TypeScript), and hands the rest of the
system the one format it expects (here, ESTree); nothing outside the
adapter depends on the library itself.
</Callout>

## A second parser, checked against the first

The payoff is one option, `jsPlugin({ parser: 'mini' })` (or
`viscosity explain --parser mini`), which swaps acorn for the book's own
`mini-parser.ts`, 451 lines that parse the subset of JavaScript numeric,
data-heavy code uses: recursive descent for statements (*Recursive
descent, precedence and associativity*) and Pratt binding powers for
expressions (*Pratt parsing*):

<MiniParseSteps client:visible />

Outside its subset it stops rather than guessing: `let y = a?.b;` gives
`optional chaining is not supported by the mini parser at line 1 near
'?.'`. To know it is right on what it does accept, the repository
compares: `mini-parser.test.ts` compiles every program in the
differential corpus (40 files) and the five end-to-end benchmark
programs with both parsers, and requires byte-identical code and
explanations. The trees themselves differ in details the plugin never
reads (the mini parser gives every `loc` column 0 and no end).

<More title="More: inside the mini parser">

An `if` statement, one case per keyword:

```ts
case 'if': {
  p++; expect('(');
  const test = expression();
  expect(')');
  const consequent = statement();
  const alternate =
    eat('else') ? statement() : null;
  return node('IfStatement', t,
    { test, consequent, alternate });
}
```

The heart of `binary`, with a table where `'+': 10`, `'*': 11` and
`'**': 12`:

```ts
let left = unary();
for (;;) {
  const op = peek().value;
  const bp = BIN[op];
  if (bp === undefined || bp <= minBp)
    break;
  p++;
  const right = binary(
    op === '**' ? bp - 1 : bp);
  left = node('BinaryExpression', t,
    { operator: op, left, right });
}
```

`**` parses its right side one power lower, so `2 ** 3 ** 2` groups to
the right. Messages are only as good as the cases thought of: `class A
{}` gives `expected ';' at line 1 near 'A'`, safe but confusing. acorn
stays the default in the command line and the Playground; the Rust port
uses a different parser, oxc, behind the same kind of boundary, and an
engine's own parser is the subject of the deep dive *Parsing JavaScript
for real*.
