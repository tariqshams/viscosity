## One small function in the way

Here is a particle update written the way most people would write it,
with the work for one particle in a function of its own:

```js
const ps = [];
for (let i = 0; i < 100; i++) {
  ps.push({ x: i, vx: 1 });
}
function move(p) { p.x += p.vx; }
for (let i = 0; i < ps.length; i++) {
  move(ps[i]);
}
console.log(ps[9].x);
```

`viscosity explain` refuses to change the layout of `ps` (`unsafe:
line 7: an element is passed to a function call`); paste the body of
`move` into the loop by hand (`const p = ps[i]; p.x += p.vx;`) and the
same tool answers `ps (line 1) {x, vx} → struct of arrays`, with
`Float64Array` columns, and `1 of 2 element accesses proven in bounds`.
Nothing about the work changed; what changed is what the analysis could
*see*, inside loops and across calls.

<Analogy title="a recipe that says &quot;see page 40&quot;">
A recipe says "make the sauce (see page 40)". You can flip to page 40
every time, or copy page 40 into the recipe; copying saves the flipping,
but the bigger win is that the whole dish is now on one page, and you
notice that half the sauce steps are pointless for this dish.
<span slot="breaks">Copying a page into every recipe that uses it makes
the book thicker each time; a compiler pays for every copy in code size
and compile time, which is why it cannot copy everything.</span>
</Analogy>

## Values that climb in steps

In SSA (*SSA and phi nodes, built on the fly*) a loop counter is a phi
in the loop header. Here is `for (let i = 0; i < n; i++)` with
`const j = 2 * i + 1` in its body, in Viscosity's IR:

<Examples of="induction-variable">

```text
b1:  ; preds b0 b3
  %4 = phi %3, %17      ; i
  %6 = binop < %4, %1   ; i < n
b2:
  %8 = binop * %7, %4   ; 2 * i
  %10 = binop + %8, %9  ; 2 * i + 1
b3:
  %17 = binop + %15, %16 ; i + 1
```

</Examples>

`%4` takes `%3` (the starting `0`) when control arrives from before the
loop, and `%17` when it comes round from the latch `b3`, where `%17` is
`i` plus one (`%15` is `i` passed through a unary `+`, which is how
`i++` first turns `i` into a number); `%8` and `%10` are built from `%4`
with a constant multiply and a constant add, so they move in lockstep
with it:

<IvSteps client:visible />

<Callout kind="definition">
An **induction variable** is a value that changes by a fixed amount on
every trip around a loop. A **basic** induction variable is a phi in the
loop header whose inputs are a start value from outside the loop and
`phi + step` from inside it; a **derived** one is `c × i + d` for a
basic one `i` and values `c` and `d` that do not change in the loop, so
it steps by `c` times `i`'s step.
</Callout>

Viscosity uses this to drop the bounds check on `ps[i]` (needed because
`ps[i].x` past the end throws, while a typed array quietly returns
`undefined`). It proves the access in bounds when `i` is a *counting*
phi (start a whole number of zero or more, step exactly `+ 1`), a loop
around the access has `i`'s block as its header and tests
`i < ps.length` (perhaps as one side of an `&&`), and the test's true
successor dominates the access (*Dominators and natural loops*), so the
access can only run straight after the test has passed.

<More title="More: which loops the bounds proof accepts">

Each loop below ran over `ps` and was followed by one
`console.log(ps[0].x)` outside any loop (never proven); the column is
the last line of `explain`:

```text
loop                         proven
i < ps.length                2 of 3
i < n   (const n = 1000)     0 of 3
i < ps.length && go          2 of 3
i < ps.length; i += 2        0 of 3
ps[i - 1], i from 1          1 of 3
```

Each failure breaks one condition: `n` is not `ps.length`, `i += 2` is
not a step of one, and `i - 1` is a derived variable, not a phi. The test
lives in `isCountingPhi` in `analysis.ts`; anything it does not recognise
keeps its check, which is always safe. When such a phi from `0` is tested
against a constant (`i < 100`), Viscosity also knows the **trip count**,
which it uses to estimate sizes.

<Formal title="Induction variables, trip by trip">

```text
basic:    i₀ = start,   iₖ₊₁ = iₖ + s
derived:  jₖ = c·iₖ + d
          so  jₖ₊₁ = jₖ + c·s
```

<span slot="read">On trip zero the basic variable i holds its start, and
on each later trip the last value plus the step s. A derived variable j
is c times i plus d, so it climbs by c times s each trip.</span>
</Formal>

</More>

## Values that never change

<Callout kind="definition">
An instruction is **loop-invariant** in a loop if it computes the same
value on every trip: it has no side effects, and each operand is either
defined outside the loop or itself loop-invariant. A header phi never is
(it merges a value from the latch), and a read from memory is invariant
only if nothing in the loop may write the memory it reads.
</Callout>

<Examples of="loop-invariant">

```js
for (let i = 0; i < g.length; i++) {
  const t = n * 2; // invariant
  g.push(t);  // g.length is not
}
```

</Examples>

`n * 2` is pure and its only operand comes from outside, so it is the
same every trip; `g` itself never changes either, yet `g.length` is not invariant: every
`push` makes it bigger, so the header's read gives a new answer each
trip (and this loop never ends). Because the definition refers to
itself, the invariant set is found the way *Dataflow, fixpoints and
constant propagation* finds facts: mark, sweep, repeat until nothing
changes:

<InvariantSteps client:visible />

Viscosity never moves an invariant instruction (it uses invariance only
in the bounds proof); the deep dive *Loop-invariant code motion* shows
the transformation, and why a memory read needs alias analysis first.

## Who calls whom

Deciding *which* calls to paste in needs a map of the program: inline
`clamp` into `move`, and `move` grows, which changes whether `move` is
worth inlining into its own callers.

<Figure takeaway="Recursion is a cycle; an unknown callee is an edge to anywhere." caption="A small program's call graph. main calls step, step calls move and clamp, move calls clamp. even and odd call each other, a cycle, so both are recursive. run(xs, g) calls whatever function g holds, so its edge goes to unknown.">
  <CallGraphPic />
</Figure>

<Callout kind="definition">
A **call graph** has one node per function and an edge `f → g` when `f`
contains a call that may reach `g`. A cycle in it is recursion (direct,
`f → f`, or mutual, `f → g → f`); a call whose target cannot be pinned
down gets an edge to "unknown", which must be treated as possibly any
function.
</Callout>

<Examples of="call-graph">

```js
sq(3);                   // → sq
const f = c ? sq : cube;
f(3);                    // → sq, → cube
xs.map(g);               // map → g
o.area();                // → unknown
```

</Examples>

In JavaScript a call names a *value*: `sq(3)` is the easy case, a
declared function called by name; `f(3)` calls whichever function `c` chose; the
callback `g` is called from inside `map`, code the caller never sees;
and `o.area()` reaches whatever the prototype chain of `o` finds at run
time. A JIT copes by *watching*: type feedback says which function a
site has called so far, so it inlines that one behind a guard and
deoptimises if the guess fails. Viscosity compiles ahead of time, so it
*proves* a small, exact part instead: a **known function** is declared
once and its name is used only for direct calls (never passed,
reassigned or called as a method), so every call site is listed.

<More title="More: deciding what to inline, bottom-up">

The usual heuristics: small callees are inlined almost always; a
function called once (and not visible outside the program) is inlined
and then deleted; a growth budget caps how much bigger a function or the
program may get; hot call sites count for more; and recursive calls are
inlined a few levels at most, much like unrolling a loop. Inliners work
**bottom-up**, leaves first, so each callee is already as optimised as
it will get when its callers look at it:

<BottomUpSteps client:visible />

The order is a postorder of the call graph; the cycle `even`, `odd` has
no true "callees first" order, which is why inliners treat cycles
separately:

<Run id="order" />

GCC's inliner, `ipa-inline.cc`, describes exactly these heuristics,
including a special recursive inliner "with results similar to loop
unrolling"<Cite id="gcc-ipa-inline" />, and LLVM documents its `inline`
pass as bottom-up<Cite id="llvm-passes" />. V8's team has written about
the price of a wrong budget: heuristics tuned to the Octane benchmark
caused regressions in real code through compile time and memory
use<Cite id="v8-retiring-octane" />.

</More>

## Pasting a function in

Doing it mechanically has two traps, both about names:

<InlineSteps client:visible />

The first is a callee local with the same name as a caller variable,
which a fresh name avoids; the second is that the parameters must all be
replaced **at once**. Inline `sub(b, a)`, where `sub(a, b)` returns
`a - b`, one parameter at a time, and `a → b` gives `b - b`, then
`b → a` gives `a - a`, which is wrong; replaced together in the original
body, it is `b - a`.

<Callout kind="definition">
**Inlining** replaces a call with a copy of the callee's body in which
every parameter is replaced by its argument, all at once; every local of
the callee gets a fresh name the caller does not use; and each
`return v` hands `v` to the code after the call. Each argument is
evaluated once, before the body (into a fresh temporary when it has
effects or is used twice), exactly as the call would have done.
</Callout>

<Examples of="inlining">

```js
function sq(v) { return v * v; }
const k = sq(3);
// inlined:  const k = 3 * 3;
// folded:   const k = 9;
```

</Examples>

Once the body is in the caller, the argument `3` meets the
multiplication and constant folding finishes the job at compile time:
no call and no multiplication, just `9`. That is the real reason to
inline; the call's own overhead is small, but the passes of the last few
chapters work inside one function, and inlining gives them a bigger
one (dead code elimination, too, can now see that a callee's result is
unused *here*). The price is size: inlining a 50-line function at 20
call sites compiles 1,000 lines.

<More title="More: inlining on a CFG, and trying it yourself">

In an IR, the call's block is cut in two at the call; the callee's
blocks are copied in with fresh ids for every block and SSA value; each
`return v` becomes a jump to the second half, where a phi picks whichever
value was returned:

<Figure takeaway="Split at the call, copy the body, join the returns with a phi." caption="Left: block b4 calls abs. Right: b4 is cut at the call; abs's three blocks are copied in with new names (c0′, c1′, c2′); each return jumps to the second half, b4', where a phi picks whichever value was returned.">
  <InlineCfg />
</Figure>

V8's TurboFan inlines (since V8 6.1, even
`Array.prototype.forEach`<Cite id="v8-release-61" />), and textbooks list
inlining among the transformations whose value lies mostly in what it
enables afterwards<Cite id="coopertorczon2022" />. When V8's team rewrote `Array.prototype.sort`, they noted that the old
JavaScript version had let the optimising compiler inline the comparison
function you passed in<Cite id="v8-array-sort" />. Viscosity itself does
**not** inline: it is a source-to-source tool, and pasting bodies all
over your program would rewrite far more than the collection code it
means to touch. Inline `move` by hand below and watch its decision flip:
