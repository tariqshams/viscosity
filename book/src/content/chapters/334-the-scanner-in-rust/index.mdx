## One character, please

The on-demand scanner of *One pass from source to bytecode* reads its
source one character at a time: `advance()` returns
`this.source[this.current++]`, and `peek()` returns
`this.source[this.current]`, or `'\0'` at the end. Each gives a
one-character string, which the scanner compares with `'('` or tests with
`isDigit`. Write `source[i]` in Rust, however, and rustc 1.97 refuses:
`error[E0277]: the type str cannot be indexed by {integer}`, with the
note `string indices are ranges of usize`.

A Rust `str` is UTF-8, where a character takes one to four bytes, so "the
character at index 5" would mean walking from the start and counting, and
Rust refuses to dress that walk up as a cheap lookup<Cite id="klabnik2026" />.
You may slice a `str` with a range of byte positions, or you may look at
its bytes; drip-rs does both.

<Analogy title="looking for punctuation in a book you cannot read">
Hand someone a novel in a script they have never seen and ask them to
circle every full stop and quotation mark: they can do it without reading
a word, because the punctuation looks nothing like the letters around it.
Byte scanning is that: drip-rs only needs to recognise Drip's ASCII
punctuation, digits and letters, and it never has to understand what an
`é` means.
<span slot="breaks">In real scripts some marks do look alike (the Greek
question mark is drawn like a semicolon); UTF-8 makes a promise no
printed page can, that no byte of a non-ASCII character is ever equal to
an ASCII byte.</span>
</Analogy>

## Two views of one text

The scanner keeps both views (from `scanner.rs`, comments trimmed):

```rust
pub struct Scanner<'src> {
    source: &'src str,
    bytes: &'src [u8],
    start: usize,
    current: usize,
    line: usize,
    last_line: usize,
}
```

`Scanner::new` fills `bytes` with `source.as_bytes()`, which copies
nothing; it is the same memory, typed as a slice of `u8`<Cite id="rust-std-str" />.
The scanner reads `bytes` to decide what each token is, and slices
`source` to make its lexeme, `&self.source[self.start..self.current]`
(`last_line` remembers where `end of file` should be reported). The
helpers become (rewrapped):

```rust
fn advance(&mut self) -> u8 {
    self.current += 1;
    self.bytes[self.current - 1]
}

/// The next byte, or NUL at the end of
/// the source.
fn peek(&self) -> u8 {
    self.bytes.get(self.current)
        .copied().unwrap_or(b'\0')
}
```

`get` returns `None` past the end, so `peek` needs no separate end test:
`copied` turns the `Option<&u8>` into an `Option<u8>`, and `unwrap_or`
turns `None` into the NUL byte, as the TypeScript version did with
`'\0'`. A **byte literal** such as `b'('` is the `u8` 40, so the big
`match` in `scan_token` reads almost like the TypeScript `switch`:

```rust
match c {
    b'(' => self.make(T::LeftParen),
    b'+' => self.make_if(
        b'=', T::PlusEqual, T::Plus),
    b'&' if self.peek() == b'&' => {
        self.current += 1;
        self.make(T::AndAnd)
    }
    b'"' => self.string(),
    // ...
}
```

`make_if` makes the long token if the next byte is the one named
(`+=`), or the short one otherwise (`+`). The `&` arm has a **guard**,
`if self.peek() == b'&'`: it only applies when a second `&` follows, so a
lone `&` falls through to the catch-all arm and is reported as
`unexpected character '&'`, exactly the message the specification asks
for.

<Callout kind="definition">
**Byte scanning** means reading source text as a `&[u8]` and comparing
bytes with byte literals like `b'('`, rather than reading characters. A
`&str`'s `as_bytes()` gives that view for free. Lexemes are still made by
slicing the `&str` with byte ranges, `&source[start..current]`.
</Callout>

<Examples of="byte-scanning">

```rust
assert_eq!(b'(', 40);
assert_eq!(b'\n', 10);
```

```rust
let s = "é!";
s.len()           // 3 bytes
s.chars().count() // 2 characters
s.as_bytes()      // [195, 169, 33]
```

```rust
// does not compile (E0277):
let c = source[i];
// compiles: one byte, a u8
let c = source.as_bytes()[i];
```

</Examples>

The first shows that a byte literal is only a number (the ASCII codes of
`(` and of a newline). The second is why Rust will not index a `str` by
character: `é!` is two characters but three bytes, and `len` counts
bytes. The third is the spot-the-difference every newcomer meets:
indexing the `str` is the error above, while indexing its bytes gives a
`u8`.

## Why bytes are safe

Scanning bytes would be a disaster if a byte of `é` could look like a
quote, and UTF-8 was designed so that it cannot:

<Figure takeaway="Every byte of a non-ASCII character is 128 or more." caption="An ASCII byte starts with 0. A longer character starts with a lead byte (110, 1110 or 11110, saying how many bytes follow), and every byte after it starts with 10.">
  <Utf8Shapes />
</Figure>

<Analogy title="a train with labelled carriages">
A one-carriage train is plain ASCII. A longer train has an engine whose
sign says how many carriages follow, and every carriage is stamped
"carriage". Nobody on the platform can mistake a carriage for an engine,
or for a train of its own.
<span slot="breaks">A real train can lose a carriage and still run;
a UTF-8 string with a missing continuation byte is simply invalid, and a
Rust `&str` is never allowed to hold one.</span>
</Analogy>

<Formal title="UTF-8 byte classes">

```text
ASCII byte:        0xxxxxxx   (0–127)
continuation byte: 10xxxxxx   (128–191)
lead byte:         110xxxxx, 1110xxxx,
                   11110xxx   (192–247)
```

<span slot="read">Every byte of UTF-8 text is one of three kinds. An
ASCII byte has a 0 as its top bit, so it is between 0 and 127. A
continuation byte starts with the bits 1 and 0, so it is between 128 and
191. A lead byte starts with two, three or four 1s and then a 0. So any
byte that belongs to a non-ASCII character is at least 128, and can never
equal an ASCII byte such as a quote or a newline.</span>
</Formal>

That is why a comparison like `c == b'"'` can only match a real quote,
and why `&self.source[self.start..self.current]` never panics: a token
starts and ends only just after an ASCII byte, after a whole character
the scanner skipped (next section), or at the very end, and all three are
character boundaries. Inside a string, `current` does pass through the
middle of `é`, however nothing is sliced until the closing quote. Step
through the scanner on `s="é";é`:

## The one non-ASCII case

Outside a string, Drip has no use for `é`, so the catch-all arm of the
match reports it (from `scanner.rs`, rewrapped):

```rust
_ => {
    // Take the whole UTF-8 character, so
    // the error names it and the next
    // token starts on a character boundary.
    while is_continuation(self.peek()) {
        self.current += 1;
    }
    self.make(T::Error(
        ScanError::UnexpectedCharacter))
}
```

and the test is a single mask, `c & 0b1100_0000 == 0b1000_0000`: keep the
top two bits and ask whether they are `10`. The loop is not decoration. I
removed it from a copy of drip-rs and ran it on `let c = é;`: rather than
an error, the scanner panicked with `end byte index 9 is not a char
boundary; it is inside 'é'`, because `make` sliced the source after only
the first byte of `é`. With the loop, the lexeme is the whole `é` and the
error reads `unexpected character 'é'`, exactly as the TypeScript VM
prints it (that scanner asks JavaScript for the whole code point, so even
an emoji is named in one piece by both). The string scanner uses the same
skip after a backslash, so `"a\é"` reports `unknown escape '\é' in a
string`.

## The rest of the scanner

Everything else is the TypeScript logic with `u8`s. Numbers, for
example: `number` steps over digits, then takes a fraction only when a
digit follows the dot (from `scanner.rs`, rewrapped):

```rust
// A fractional part needs a digit
// after the dot: `1.` is `1` `.`.
if self.peek() == b'.'
    && self.peek_next().is_ascii_digit()
{
    self.current += 1;
    while self.peek().is_ascii_digit() {
        self.current += 1;
    }
}
```

Running the real scanner on `1.5 1. 12.x` gives `Number "1.5"`, then
`Number "1"` and `Dot`, then `Number "12"`, `Dot` and `Identifier "x"`.
Strings loop to the closing `b'"'`, counting `b'\n'`s as they go;
comments run from `#` to the next newline; identifiers continue while
bytes are ASCII letters, digits or `_`, and then go through the keyword
`match` of the chapter *Tokens as enums*. Here is a cut-down scanner you

<Callout kind="engine" label="Under the hood">
The standard library uses the same rule. `str::is_char_boundary(i)` is
true when byte `i` starts a character or is the end of the string, and
the helper behind it is commented "equivalent to: b &lt; 128 || b &gt;=
192"<Cite id="rust-std-str" />: not a continuation byte. The TypeScript
scanner counts UTF-16 code units while drip-rs counts bytes, and the two
agree because everything Drip's grammar cares about is ASCII.
</Callout>

## What you learned

- Rust will not index a `str` by integer, so drip-rs **scans bytes**: it
  keeps `bytes: &[u8]` (from `as_bytes()`, free) beside `source: &str`.
- `peek` is `get(..).copied().unwrap_or(b'\0')`, and the match is on
  **byte literals** like `b'('`, with a guard for `&&` and `||`.
- In UTF-8 every byte of a non-ASCII character is at least 128, and
  **continuation bytes** look like `10xxxxxx`; so ASCII comparisons are
  safe, and lexeme slices land on character boundaries.
- For a stray non-ASCII character the scanner skips its continuation
  bytes, which names the whole character and avoids a panic.
- Numbers, strings, comments and identifiers are the TypeScript logic on
  `u8`s.
