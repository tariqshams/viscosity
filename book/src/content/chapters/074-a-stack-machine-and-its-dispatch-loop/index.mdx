## Where do the half-finished answers go?

The tree-walker kept half-finished answers on the host's call stack, as
return values waiting for the `+`. Bytecode has no recursion to lean
on: in `const 1, const 2, const 3, mul, add`, the `1` has to wait
*somewhere* while `2 * 3` is worked out. The answer is a stack the VM
keeps for itself, newest value on top, and a number saying where in the
code it has got to.

<Analogy title="a pile of plates">
In a canteen, clean plates are stacked in a pile, and you only ever
touch the top one. An instruction like `mul` is a cook who takes the top
two plates, combines what is on them, and puts one plate back; nobody
needs to know *where* any plate is, only that the one they want is on
top.
<span slot="breaks">A real pile only lets you see the top plate; the VM
can look at the second or third value down without moving anything (and
later, in *Locals as stack slots*, reach a value directly by its
position).</span>
</Analogy>

## The stack is one array

Drip's stack is one array made at full size, plus `sp`, the **stack
pointer**, the index of the next free slot (from `vm/vm.ts`, rewrapped):

```ts
readonly stack: Value[] =
  new Array(STACK_MAX).fill(null);
sp = 0;

push(v: Value) {
  this.stack[this.sp++] = v;
}
pop(): Value {
  return this.stack[--this.sp];
}
peek(distance: number): Value {
  return this.stack[this.sp - 1 - distance];
}
```

`STACK_MAX` is 65,536 (256 slots for each of 256 nested calls). `push`
writes slot `sp` and *then* moves `sp` up; `pop` moves it down *first*
and reads the top; `peek(1)` reads the value under the top without
moving anything. Nothing is allocated per value: only `sp` moves.

<Callout kind="definition">
A **stack machine** is a VM whose instructions take their inputs from
the top of a value stack and push their results back onto it. Because
the inputs are always "the top few values", most instructions do not
need to say where their inputs are, so most need no operands at all.
</Callout>

<Examples of="stack-machine">

```text
print (1 + 2) * 3;
const '1'  →  [1]
const '2'  →  [1, 2]
add        →  [3]
const '3'  →  [3, 3]
mul        →  [9]
print      →  []
```

</Examples>

Each line shows the stack after one instruction, top on the right. The
sum is finished before the `3` is pushed, so the stack never holds more
than two values (`1 + 2 * 3` needs three); `print` leaves it as it
found it, as every statement does.

<Formal title="Stack effects">

```text

add     : a b  → a + b
print   : v    →
```

<span slot="read">Each line says what an instruction needs on top of the

## The instruction pointer

Where the VM is in the code is one number too, read and moved by three
helpers inside `run`:

```ts
const readByte = () => code[frame.ip++];
const readShort = () => {
  frame.ip += 2;
  return (code[frame.ip - 2] << 8)
    | code[frame.ip - 1];
};
const readConstant = () =>
  constants[readShort()];
```

`ip` always holds the index of the *next* byte, and every read moves it
on, so reading an instruction's operands also steps over them: after a
`const` (an opcode and a two-byte constant number), `ip` has moved by
three and lands on the next opcode. (`ip` lives in `frame` because each
running function will get its own, in *Frames: calling and returning*.)
Step through `print 1 + 2 * 3;`, watching `ip` and the stack together:

<VmSteps client:visible />

<Callout kind="definition">
The **instruction pointer** (`ip`) is the position in the bytecode of
the next byte to run. Reading an opcode or an operand moves it on, so an
instruction finishes with `ip` pointing at the instruction after it.
Jump instructions change it on purpose.
</Callout>

<Examples of="instruction-pointer">

```text
0013    | jump.unless        13 -> 20
ip after reading it: 16
if the condition is false: 16 + 4 = 20
```

</Examples>

After reading `jump.unless` and its two-byte distance, `ip` is 16; if
the condition is false the instruction adds the distance, 4, so the next
instruction run is at 20. That is all a jump is.

## The dispatch loop

What remains is the part that does the work: look at each opcode in
turn and run the right code for it, for fifty-three kinds of
instruction. In Drip that is one method, `run`, and almost all of it is
one loop around one `switch`:

```ts
let frame =
  this.frames[this.frames.length - 1];
let code = frame.closure.fn.chunk.code;
// constants, stack, the helpers ...
for (;;) {
  this.instructionsExecuted++;
  const instruction = code[frame.ip++];
  switch (instruction) {
```

The first lines copy what the loop needs most into locals (reloaded
only when a call or return changes the running function). `for (;;)`
runs until a `case` leaves it (the final
`return`, or a runtime error); each turn counts the instruction,
**fetches** the opcode at `ip` while moving past it, and the `switch`
**dispatches** to its `case`. Here is the real one for `sub`, rewrapped:

```ts
case Op.Sub: {
  this.numbers('-');
  const b = this.pop() as number;
  stack[this.sp - 1] =
    (stack[this.sp - 1] as number) - b;
  break;
}
```

`numbers('-')` checks, with `peek`, that the top two values are numbers,
so a failing check leaves the stack as it was. Then `b`, the right
operand, is popped (it was pushed last), and the left operand's slot is
overwritten with the result: the same effect as popping both and
pushing, with one less change to `sp`. Step through `sub` dispatched
twice, once with numbers and once without:

<DispatchSteps client:visible />

<Callout kind="definition">
The **dispatch loop** is the VM's main loop: fetch the opcode at `ip`,
**dispatch** on it (here with a `switch`) to the code for that
instruction, run that code, and repeat. The work of fetching and
choosing is paid on every instruction, on top of the instruction's own
work, so it is the interpreter's overhead in its purest form.
</Callout>

<Examples of="dispatch-loop">

```text
print 10 - "a";
# runtime error: cannot use '-' on a
#   number and a string
#   at line 1 in script
```

</Examples>

After two `const`s, `sub`'s check peeks, finds a string, and stops the
program before anything is popped.

## What dispatch costs

Every turn pays for the same steps whatever the instruction does (count
it, read a byte, move `ip`, jump through a fifty-three-way `switch`),
and for `add` the real work is one addition, so dispatch can cost as
much as the work. The V8 team describe decoding operands and
dispatching as overheads an interpreter cannot get rid of, fast only
while the processor's branch prediction keeps guessing where the
dispatch jump lands<Cite id="v8-sparkplug" />. For Drip there is a
twist: `run` is TypeScript, so how fast our dispatch is depends on how
well V8 compiles one large function with one big `switch`, and V8
compiles the tree-walker's `switch` on node kinds just as well. That is
part of why the VM in *Why bytecode* won by so little;
*Measuring and speeding up the VM* tries the classic fix of
superinstructions, single instructions that do the work of several.

V8's Ignition is a register machine instead: its bytecodes name
registers, with an accumulator as the unwritten input and output of
many<Cite id="v8-ignition" />, so fewer, larger instructions mean fewer
turns of the loop, at the price of a compiler that decides where each
value lives. Drip keeps the stack, and a much simpler compiler.

<Analogy extra title="a sorting office">
A sorter takes the next letter, reads the postcode and drops it into
the right pigeonhole, all day; reading and choosing is the dispatch.
<span slot="breaks">A sorter can grab a handful of letters for one
pigeonhole at once; the loop handles exactly one instruction per
turn.</span>
</Analogy>

## What you learned

- A **stack machine** keeps in-between values on a stack, so most
  instructions need no operands; Drip's is one array and `sp`.
- The **instruction pointer** is the index of the next byte; reading
  operands moves it past them, and jumps move it on purpose.
- The **dispatch loop** is `for (;;)` around a `switch`; fetch and
  dispatch are paid on every instruction.
