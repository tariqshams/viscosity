## Fifty-two names

In `companion/ts/src/token.ts` the token types of *Tokens and a scanner*
are fifty-two string literals, `'('`, `'>='`, `'while'`, `'eof'` and the
rest, and it is the union type that turns a typo like `'identifer'` into
a compile error. Rust has no string literal types; it has something
better suited to the job, the enum of *Enums, match and patterns*.

<Analogy title="coat-check tickets">
A TypeScript token type is a name tag with a word written on it, and the
type checker reads every tag to make sure the word is on the approved
list. A Rust enum is a numbered coat-check ticket: the list is printed on
the counter, there is nothing to misspell, and the ticket is tiny.
<span slot="breaks">A cloakroom hands out tickets until it runs out;
there are exactly fifty-two kinds of token, fixed when drip-rs is
compiled, and a program can make as many tokens of each as it likes.</span>
</Analogy>

<Analogy extra title="a form with tick boxes">
A paper form that asks "how did you hear about us?" with five tick boxes
cannot be answered "by carrier pigeon", while a free-text box can. An
enum is the tick-box form: the answers are fixed, and the compiler knows
every one of them.
<span slot="breaks">A form usually allows an "other: ______" box; an enum
can carry extra data too, but only in the variants that ask for it, and
only of the type they name, as `Error` does below.</span>
</Analogy>

## TokenKind

Here is drip-rs's version, from `scanner.rs` (trimmed):

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum TokenKind {
    LeftParen,
    // ... 49 more plain kinds
    Error(ScanError),
    Eof,
}
```

The same fifty-two kinds, in the same order as the TypeScript union, with
two changes forced on the port. A variant must be an identifier, so `'('`
becomes `LeftParen` and `'>='` becomes `GreaterEqual` (and the keyword
`self` becomes `SelfKw`, because Rust reserves `Self`). And `Error` is
not a bare name: it carries a `ScanError`, a second enum whose three
variants, `UnexpectedCharacter`, `UnknownEscape` and
`UnterminatedString`, say what went wrong.

The `derive` line (*Traits, trait objects and derive*) makes a kind
copyable like an integer, comparable with `==` (the compiler's `check`
is `self.current.kind == kind`) and printable by name.

<Callout kind="definition">
A **token enum** is an enum with one variant per kind of token. In
drip-rs it is `TokenKind`: fifty-one variants that carry nothing, and
`Error(ScanError)`, which carries the reason for a scanning error. Every
payload is small and `Copy`, so the whole enum is `Copy`, compares with
`==`, and takes **1 byte**<Cite id="rustref-enum" />.
</Callout>

<Formal title="Counting the values of TokenKind">

```text
TokenKind = LeftParen | … | Eof
          | Error(ScanError)
|TokenKind| = 51 + 3 = 54 ≤ 256
```

<span slot="read">A TokenKind is either one of the fifty-one kinds that
carry nothing, or Error together with one of the three ScanErrors. That
makes fifty-four different values in all, which is fewer than the 256 a
single byte can tell apart, so one byte is enough (I measured
size_of::&lt;TokenKind&gt;() as 1 with rustc 1.97).</span>
</Formal>

<Examples of="token-enum">

```rust
let k = TokenKind::Semicolon;
k == TokenKind::Semicolon // true
k == TokenKind::Comma     // false

// does not compile:
kind == TokenKind::Error
// error[E0308]: mismatched types
// compiles:
matches!(kind, TokenKind::Error(_))
```

</Examples>

The first three lines compare kinds the way `check` does: the derived
`==` asks whether two values are the same variant. The rest is the slip
everyone makes once. On its own, `TokenKind::Error` is not a kind but a
*constructor*, a function waiting for its `ScanError`, so rustc 1.97
refuses with `expected TokenKind, found enum constructor`; `matches!` is
true when the value fits the pattern, and `_` fits any `ScanError`, so it
asks the question you meant.

<More title="Reading the error out, and keywords as a match">

The compiler's `advance` (rewrapped) pulls the `ScanError` out of an
error token with `let ... else`, which leaves the loop when the token is
not one:

```rust
let TokenKind::Error(error) =
    self.current.kind else { break };
let message = error
    .message(self.current.lexeme);
```

Where the TypeScript scanner looks words up in a `Map`, `KEYWORDS`,
drip-rs uses a `match` on the text (trimmed):

```rust
fn keyword(text: &str)
    -> Option<TokenKind> {
    use TokenKind as T;
    Some(match text {
        "break" => T::Break,
        // ... 18 more
        "while" => T::While,
        _ => return None,
    })
}
```

The `_` arm leaves the function, so every arm that finishes yields a
`TokenKind` for the one `Some` to wrap, and the scanner turns "not a
keyword" into a name with `keyword(text).unwrap_or(TokenKind::Identifier)`.
There is no table to build at start-up, and the patterns are exact, so
`classy` and `Class` both fall through to `_`.

Could each token carry its value, `Number(f64)` or a decoded string, as
the tree-walker's `literal` field did? It could; drip-rs chooses not to,
so that every kind stays one byte and compares with `==`. The compiler
parses a number when it emits it, with `token.lexeme.parse()`, and
decodes a string's escapes then too, where the TypeScript VM's scanner
decodes them as it scans. Try the kinds, the keyword lookup and the
sizes, and change the source string:

## Tokens that point into the source

When the TypeScript scanner meets `@`, its error token's lexeme is the
finished message. In drip-rs the lexeme is always source text (here the
`@`), and the compiler builds the message from it and the `ScanError`
when it reports the error, so both VMs print the same words.

<Figure takeaway="Same message, made at a different moment." caption="Scanning `@` on line 2. The TypeScript token carries the finished message; the Rust token carries the offending text and a ScanError, and the compiler turns the pair into the same message.">
  <ErrorTokens />
</Figure>

The token itself (from `scanner.rs`):

```rust
#[derive(Clone, Copy, Debug)]
pub struct Token<'src> {
    pub kind: TokenKind,
    pub lexeme: &'src str,
    pub line: usize,
}
```

The TypeScript lexeme is a new string from `source.slice`; here it is a
`&str`, a pointer and a length into the source, and *Lifetimes* showed
how `'src` stops a token outliving it. The token is 32 bytes:
a 1-byte kind, a 16-byte slice and an 8-byte line, padded to a multiple
of 8 (*Memory layout in Rust*). Because it is `Copy`, the compiler's
`previous` and `current` are plain copies, not borrows of the scanner.

## One byte at a time

The TypeScript scanner's `advance()` returns
`this.source[this.current++]`, a one-character string. Write `source[i]`
in Rust and rustc 1.97 refuses: `error[E0277]: the type str cannot be
indexed by {integer}`. A `str` is UTF-8, where a character takes one to
four bytes, so "the character at index 5" would mean counting from the
start, and Rust will not dress that up as a cheap
lookup<Cite id="klabnik2026" />. You may slice a `str` by byte ranges,
or look at its bytes, and the scanner does both (from `scanner.rs`,
trimmed and rewrapped):

```rust
pub struct Scanner<'src> {
    source: &'src str,
    bytes: &'src [u8],
    // ... start, current, line
}

fn peek(&self) -> u8 {
    self.bytes.get(self.current)
        .copied().unwrap_or(b'\0')
}
```

`bytes` is `source.as_bytes()`, the same memory typed as a slice of
`u8`<Cite id="rust-std-str" />, so it costs nothing. The scanner reads
`bytes` to decide what each token is, and slices `source` for the
lexeme, `&self.source[self.start..self.current]`. `get` is `None` past
the end, so `peek` needs no end test: `unwrap_or` turns `None` into the
NUL byte, as the TypeScript version did with `'\0'`. The big `match` in
`scan_token` then reads like the TypeScript `switch`, on **byte
literals** such as `b'('`, which is just the `u8` 40.

<Callout kind="definition">
**Byte scanning** means reading source text as a `&[u8]` and comparing
bytes with byte literals like `b'('`, rather than reading characters. A
`&str`'s `as_bytes()` gives that view for free. Lexemes are still made by
slicing the `&str` with byte ranges, `&source[start..current]`.
</Callout>

<Examples of="byte-scanning">

```rust
let s = "é!";
s.len()           // 3 bytes
s.chars().count() // 2 characters
s.as_bytes()      // [195, 169, 33]
s.as_bytes()[2] == b'!' // true
```

</Examples>

`é!` is two characters but three bytes, and `len` counts bytes; that is
why Rust will not index a `str` by character. `as_bytes` shows them,
195 and 169 for `é` and 33 for `!`, and the last line is the scanner's
kind of question: is the byte at this position a `!`?

## Why bytes are safe

Scanning bytes would be a disaster if a byte of `é` could look like a
quote, and UTF-8 was designed so that it cannot:

<Figure takeaway="Every byte of a non-ASCII character is 128 or more." caption="An ASCII byte starts with 0. A longer character starts with a lead byte (110, 1110 or 11110, saying how many bytes follow), and every byte after it starts with 10.">
  <Utf8Shapes />
</Figure>

<Formal title="UTF-8 byte classes">

```text
ASCII byte:        0xxxxxxx   (0–127)
continuation byte: 10xxxxxx   (128–191)
lead byte:         110xxxxx, 1110xxxx,
                   11110xxx   (192–247)
```

<span slot="read">Every byte of UTF-8 text is one of three kinds. An
ASCII byte has a 0 as its top bit, so it is between 0 and 127. A
continuation byte starts with the bits 1 and 0, so it is between 128 and
191. A lead byte starts with two, three or four 1s and then a 0. So any
byte that belongs to a non-ASCII character is at least 128, and can never
equal an ASCII byte such as a quote or a newline.</span>
</Formal>

So `c == b'"'` can only match a real quote. Inside a string, `current`
passes through the middle of `é`, but nothing is sliced until the
closing quote. Outside a string Drip has no use for `é`, and the
catch-all arm of the match reports it (rewrapped):

```rust
_ => {
    while is_continuation(self.peek()) {
        self.current += 1;
    }
    self.make(T::Error(
        ScanError::UnexpectedCharacter))
}
```

`is_continuation` is one mask, `c & 0b1100_0000 == 0b1000_0000`: keep
the top two bits and ask whether they are `10`. The loop is not
decoration. I removed it from a copy of drip-rs and ran it on
`let c = é;`: the scanner panicked with `end byte index 9 is not a char
boundary; it is inside 'é'`, because `make` sliced the source after only
the first byte of `é`. With the loop, the lexeme is the whole character,
the next token starts on a boundary, and drip-rs reports
`unexpected character 'é'`, as the TypeScript VM does. Step through the scanner on `s="é";é`:

<Analogy extra title="looking for punctuation in a book you cannot read">
Hand someone a novel in a script they have never seen and ask them to
circle every full stop and quotation mark: they can do it without reading
a word, because the punctuation looks nothing like the letters around it.
Byte scanning is that: drip-rs only needs to recognise Drip's ASCII
punctuation, digits and letters, and it never has to understand what an
`é` means.
<span slot="breaks">In real scripts some marks do look alike (the Greek
question mark is drawn like a semicolon); UTF-8 makes a promise no
printed page can, that no byte of a non-ASCII character is ever equal to
an ASCII byte.</span>
</Analogy>

<Analogy extra title="a train with labelled carriages">
A one-carriage train is plain ASCII. A longer train has an engine whose
sign says how many carriages follow, and every carriage is stamped
"carriage". Nobody on the platform can mistake a carriage for an engine,
or for a train of its own.
<span slot="breaks">A real train can lose a carriage and still run;
a UTF-8 string with a missing continuation byte is simply invalid, and a
Rust `&str` is never allowed to hold one.</span>
</Analogy>

<More title="The rest of the scanner, and the standard library's rule">

Everything else is the TypeScript logic with `u8`s. `make_if` makes the
long token if the next byte is the one named (`+=`), or the short one
(`+`); the `b'&'` arm has a guard, `if self.peek() == b'&'`, so a lone
`&` falls through to the catch-all arm and is reported as `unexpected
character '&'`. Numbers take a fraction only when a digit follows the
dot (rewrapped):

```rust
if self.peek() == b'.'
    && self.peek_next().is_ascii_digit()
{
    self.current += 1;
    while self.peek().is_ascii_digit() {
        self.current += 1;
    }
}
```

so `1.5 1. 12.x` scans as `Number "1.5"`, then `Number "1"` and `Dot`,
then `Number "12"`, `Dot` and `Identifier "x"`. Strings loop to the
closing `b'"'`, counting `b'\n'`s; the string scanner uses the same
continuation skip after a backslash, so `"a\é"` reports `unknown escape
'\é' in a string`. Here is a cut-down scanner you can run, with the
skip in it:

The standard library uses the same rule: `str::is_char_boundary(i)` is
true when byte `i` starts a character or is the end of the string, and
the helper behind it is commented "equivalent to: b &lt; 128 || b &gt;=
192"<Cite id="rust-std-str" />, that is, not a continuation byte. The
TypeScript scanner counts UTF-16 code units while drip-rs counts bytes,
and the two agree because everything Drip's grammar cares about is
ASCII.

</More>
