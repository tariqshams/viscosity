## A throw, three calls down

You met `throw` and `try`/`catch` in chapter 23; here is a small program
that uses both, with a `finally` in the middle:

```js
function parse(s) {
  if (s === '') throw new Error('empty');
  return s.length;
}
function load(s) {
  try { return parse(s) + 1; }
  finally { console.log('close'); }
}
try { load(''); }
catch (e) { console.log('caught'); }
```

It prints `close` and then `caught`. When `parse` threw, three calls
were on the stack (the script, `load` and `parse`); the error had to
skip the rest of `parse` and the `+ 1` in `load`, run `load`'s
`finally` on the way past, and arrive in a catch block two frames
down, with the stack pointer put back where that frame expects it.
None of that is ordinary returning, yet a compiler must produce code
for it.

Your Drip VM already does half of the job. When a runtime error happens,
it walks its frames from the top down to print where each one had got
to:

```text
runtime error: cannot use '/' on a number
  and none
  at line 2 in fn parse
  at line 5 in fn load
  at line 7 in script
```

(The first line is wrapped to fit.) Drip has no `catch`, so after the
walk the program stops; a language with exceptions does the same walk,
but stops at the first frame willing to handle the error.

<Callout kind="definition">
**Unwinding** is what happens after a throw: the frames above the
nearest frame with a matching handler are removed from the call stack,
from the top down, and any cleanup code that belongs to them (a
`finally`, or a C++ destructor) runs as its frame is removed. When no
frame has a handler, the error is **uncaught** and the program stops.
</Callout>

<Formal title="Unwinding, as a rule">

```text
unwind(e, f₁ … fₙ)            fₙ is the top
  = jump to h,    if h = handler(fₙ, e)
  = cleanup(fₙ); unwind(e, f₁ … fₙ₋₁)
                  otherwise
unwind(e, empty) = uncaught e
```

<span slot="read">To unwind error e through frames f1 up to fn: if the
top frame has a handler h for e, jump to h and stop. Otherwise run the
top frame's cleanup, drop it, and unwind e through the frames below.
With no frames left, e is uncaught.</span>
</Formal>

C++ on Linux follows the Itanium C++ ABI, which splits this into **two
phases**: a search phase that only
reads, walking the frames until it finds a handler without changing
anything, and then a cleanup phase that walks again and actually runs
the cleanups and removes the frames<Cite id="itanium-cxx-abi-eh" />. If
the search finds no handler, C++ calls `terminate()` without running a
single cleanup, so the stack is left exactly as it was at the throw. Step through it:

## The landing pad

Where, exactly, does the unwinder jump? It needs an address in the
compiled code, not a line of source. The compiler makes one: for each
call that might throw inside a `try` or a cleanup, it emits a small
block of code called a **landing pad** and records the call's range
together with the pad's address. Here is that in LLVM IR, from clang 18
compiling a C++ `load` whose local `File f` must be destroyed on every
exit (real output, with names shortened and
lifetime markers removed):

```text
  %r = invoke i32 @parse(i32 %n)
         to label %ok unwind label %pad
ok:
  %s = add nsw i32 %r, 1
  call void @File_dtor(ptr %f)
  ret i32 %s
pad:
  %e = landingpad { ptr, i32 } cleanup
  call void @File_dtor(ptr %f)
  resume { ptr, i32 } %e
```

A call that might throw is an `invoke`, with two places to continue: `%ok` when `parse` returns normally, and
`%pad` when it throws<Cite id="llvm-exception-handling" />. The pad runs
the destructor, the same cleanup as the normal path, and then `resume`
hands the error back to the unwinder, because this frame cleans up but
does not catch. A catch clause would instead be `landingpad ... catch`,
followed by a test of the error's type and a branch into the catch
block's code.

<Callout kind="definition">
A **landing pad** is a block of compiled code that the unwinder jumps to
when an exception passes through a call site. It runs the cleanups of
that frame and then either **resumes** unwinding (a cleanup) or
continues as normal code (a catch that matched). A landing pad is like a
second return address for a call, used only when the call throws.
</Callout>

## Zero cost, until you throw

There are two ways to tell the unwinder where the pads are. The old way
pays as it goes: on entering each `try`, the program saves its registers
in a record and pushes the record on a list, and on leaving the `try` it
pops the record (C's `setjmp` and `longjmp` can be used this way, and
LLVM still offers it as "SJLJ" exception handling, in which each
function registers itself on a global list<Cite id="llvm-exception-handling" />). That costs something on every
`try`, even when nothing is thrown. The other way pays nothing on the
normal path: the compiler writes a table, beside the code, that maps
ranges of instruction addresses to landing pads, and the unwinder reads
it only when something is thrown.

A building's fire-exit map costs nothing on an ordinary day: nobody

<Callout kind="definition">
**Zero-cost exceptions** (table-driven exceptions) add no instructions
to the normal path of a function: the compiler records, in a table kept
beside the code, which range of instruction addresses is covered by
which landing pad, and the runtime searches that table only when an
exception is thrown. Throwing becomes slower; not throwing becomes
free.
</Callout>

Here are four real tables, each trimmed:

<Examples of="landing-pad zero-cost-exceptions">

```text
# clang 18, RISC-V, load (.s file)
Call between .Ltmp0 and .Ltmp1
  jumps to .Ltmp2   On action: cleanup
```

```text
# javap -c, Java 21: safe(String)
Exception table:
   from  to target type
     0    4     5  NumberFormatException
```

```text
# python3.13 -m dis: safe(s)
ExceptionTable:
  L1 to L2 -> L3 [0]
```

```text
# node --print-bytecode: safe(s)
Handler Table (size = 16)
   from   to       hdlr
  (   3,  11)  ->    11
```

</Examples>

All four say the same thing: instructions from here to there are
covered, and a throw among them lands at this address. The
first is clang's own comment on its `.gcc_except_table` section (see the
figure). The second is HotSpot's class file: bytecodes 0 to 4 call
`parse` and return, and a `NumberFormatException` there lands at 5; a
Java exception table is searched in order, and the first matching entry
wins<Cite id="openjdk-exceptioncatch" />. The third is CPython, whose compiler turns its
`SETUP_FINALLY` pseudo-instructions into table rows, so that the cost
of a `try` with no error is "zero (or close to zero)"<Cite id="cpython-exception-handling" />. The fourth is V8's
bytecode for a JavaScript `try`, whose handler table holds one entry
per handler and the range it covers<Cite id="v8-handler-table" />.

<Callout kind="engine" label="Under the hood">
Zero cost is not quite free: the tables make files bigger, and to
remove a frame the runtime must also restore the caller's stack pointer
and saved registers without the function's help (on Linux that plan is
the `.eh_frame` section, described by the `.cfi_` lines in clang's
assembly). Your Drip tree-walker made the opposite choice for `return`
(chapter 106): it passes a signal back through every statement, which
costs a little everywhere and needs no tables.
</Callout>

## What you learned

- **Unwinding** removes frames from the top down until one has a
  handler, running each frame's cleanups on the way; C++ first searches
  without changing anything, then cleans up.
- A **landing pad** is compiled code the unwinder jumps to: it cleans up
  and then resumes unwinding, or continues as a matched catch.
- **Zero-cost exceptions** keep the plan in a table of address ranges,
  read only when something is thrown; clang, HotSpot, CPython and V8 all
  do it.
