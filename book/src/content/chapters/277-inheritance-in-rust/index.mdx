## Two classes, one copy

```
class A {
  hi() { print "A.hi"; }
  me() { print "A.me"; }
}
class B < A {
  hi() {
    print "B.hi";
    super.hi();
  }
}
B().hi();
B().me();
```

drip-rs prints `B.hi`, `A.hi`, `A.me`. The part of the listing that
declares `B`, from `drip-rs --disassemble`:

```
0015    5 OP_CLASS            6 'B'
0017    | OP_DEFINE_GLOBAL    6 'B'
0019    | OP_GET_GLOBAL       7 'A'
0021    | OP_GET_GLOBAL       8 'B'
0023    | OP_INHERIT
0024    | OP_GET_GLOBAL       9 'B'
0026    9 OP_CLOSURE         11 <fn hi>
0028    |                     local 1
0030    | OP_METHOD          10 'hi'
0032   10 OP_POP
0033    | OP_CLOSE_UPVALUE
```

And `super.hi();` inside `B.hi` is `OP_GET_LOCAL 0`, `OP_GET_UPVALUE 0`,
`OP_SUPER_INVOKE (0 args) 1 'hi'`. All of it is chapter 115's design. I
disassembled the same file with the TypeScript VM's `disassembleChunk`,
and the two listings were identical. The Rust differs in one
line of the VM and in how the compiler remembers which class it is in.

## The line that won't compile

<Callout kind="intuition">
A child starting a recipe binder photocopies every page of the parent's
binder first, then writes their own versions over some of them. Later,
nobody has to walk to the parent's house to read a recipe.
</Callout>

`OP_INHERIT` in TypeScript:

```ts
(this.peek(0) as ObjClass).methods
  .addAll(superclass.methods);
```

The same shape in Rust reads one class from the heap while writing
another. On a toy heap with `Index` and `IndexMut` impls (chapter 268),
rustc 1.97 says (trimmed):

```
error[E0502]: cannot borrow `*h` as
  mutable because it is also borrowed
  as immutable
33 | let from = &h[sup].methods;
   |             - immutable borrow
34 | h[sub].methods.extend(
   | ^ mutable borrow occurs here
35 |     from.iter().map(...));
   |     ---- immutable borrow later used
```

`h[sub]` is `*h.index_mut(sub)`: it borrows the whole heap, not one
slot<Cite id="rust-std-ops-index" />. The borrow checker can't know that
`sub` and `sup` are different handles, so it can't allow a write to one
while a reference into the other is alive. drip-rs's arm, from
`src/vm.rs`:

```rust
OpCode::Inherit => {
    let Value::Class(superclass) =
        self.peek(1)
    else {
        return Err(self.runtime_error(
            "Superclass must be a class."));
    };
    let subclass = as_class(self.peek(0));
    // Copy-down inheritance: methods are
    // copied once, now.
    let methods = self.heap[superclass]
        .methods.clone();
    self.heap[subclass].methods
        .add_all(&methods);
    self.pop();
}
```

`Table` derives `Clone`, so `clone()` copies its count and its two
`Vec`s of keys and values. The shared borrow ends at the semicolon, and
then the mutable one is free to start.

## What the clone costs

The clone is Rust memory, not a Drip object. It never goes through
`Heap::alloc`, so it can't start a collection halfway through, and
nothing on the stack needs protecting. It is dropped at the end of the
arm. And it happens once per class declaration that has a superclass,
not once per method call.

The superclass is checked with a `let ... else`, because the name
after `<` can hold anything at run time. For `let s = "x";` on line 1
and `class C < s {}` on line 2, both VMs print
`Superclass must be a class.` and `[line 2] in script`, and exit with 70. The
subclass is opened with `as_class`, which calls `unreachable!` on
anything else: the compiler always puts the class it just made there.

Order does the rest. `OP_INHERIT` runs before any of `B`'s
`OP_METHOD`s, so an override simply overwrites the copied entry.

<Callout kind="definition">
**Copy-down inheritance** copies every entry of the superclass's methods
table into the subclass's table once, when the class is declared, before
the subclass's own methods are added, so overrides win. After that a
method lookup on the subclass is one probe in its own table. In drip-rs
both tables live in the class arena, so `OP_INHERIT` clones the
superclass's `Table` first and then adds it to the subclass. This is
correct only because a Drip class can't gain methods after its
declaration.
</Callout>

## super in the compiler

The TypeScript compiler keeps nested classes in a linked list,
`{ enclosing, hasSuperclass }`, and holds the current one in `cc` while
it compiles the superclass clause, setting `cc.hasSuperclass = true`
later. drip-rs uses a stack, `classes: Vec<ClassState>`, like its stack
of `FunctionState`s (chapter 267). Holding `&mut ClassState` while
calling `self.variable(..)` would be the E0499 of chapter 270, so it
reaches in again when it needs to:

```rust
self.begin_scope();
self.add_local("super");
self.define_variable(0);
self.named_variable(class_name, false);
self.emit_op(OpCode::Inherit);
self.classes.last_mut()
    .expect("in a class")
    .has_superclass = true;
```

`add_local("super")` stores a `&'static str` where a `&'src str` goes.
That is allowed, because `'static` outlives `'src`. The same goes for
`Token::synthetic("this", line)` and `Token::synthetic("super", line)`,
which `super_` passes to `named_variable`, just as TypeScript's
`synthetic('super')` does. Its checks come first:

```rust
match self.classes.last() {
    None => self.error("Can't use \
        'super' outside of a class."),
    Some(class)
        if !class.has_superclass =>
    {
        self.error("Can't use 'super' in \
            a class with no superclass.");
    }
    Some(_) => {}
}
```

Calling `self.error` inside the arm is fine: `class` is last used in the
guard, so the borrow of `self.classes` has ended.

At run time, `OP_GET_SUPER` pops the superclass and calls chapter 276's
`bind_method`, with `this` on top of the stack as the receiver.
`OP_SUPER_INVOKE` pops it and calls `invoke_from_class`. Both open it
with `as_class`.

Copy-down trades memory for lookups: every subclass carries its own copy
of everything it inherits, and in return no lookup walks a chain. clox
makes the same trade, and depends on the same fact, that classes are
closed once declared<Cite id="nystrom2021" />. The corpus checks it from
the outside: `inheritance/` and `super/` hold 27 programs, and drip-rs
passes all of them, under the stress collector too.
</Callout>

## What you learned

- `OP_INHERIT` **copies the superclass's methods down** into the
  subclass, once, before the subclass's own `OP_METHOD`s run.
- Reading `heap[sup]` while writing `heap[sub]` is **E0502**: indexing
  borrows the whole heap. drip-rs **clones the table first**.
- The clone is Rust memory, so it **can't start a collection**.
- The compiler keeps a **`Vec<ClassState>`** and reaches back in with
  `last_mut()`, instead of holding a reference as TypeScript holds `cc`.
- `"super"` and `"this"` are `&'static str`s, accepted wherever a
  `&'src str` is expected.
