## From IR to RISC-V

The last chapter left `sumsq` as optimised LLVM IR. The part of LLVM
that turns IR into machine code is its **code generator**, run by the
tool `llc` (or from inside clang). Its documentation lists seven
stages: instruction selection, scheduling, optimisations on machine
code in SSA form, register allocation, prologue and epilogue
insertion, late optimisations, and code emission; until register
allocation, the code uses "virtual registers in SSA form"<Cite id="llvm-codegen" />.
That is our compiler from chapter 255, stage for stage, with much
more inside each stage.

To see the loop, we ask clang to keep it (`-mllvm -replexitval=never`
stops `indvars` replacing it with the formula) and stop `llc` after
chosen passes with `-stop-after=`. Step through the loop body:

The middle form is **Machine IR** (MIR): RISC-V's own instructions,
over virtual registers such as `%10:gpr` (a general-purpose register,
not yet chosen), with physical ones such as `$x10` only where the ABI
demands them. PHI elimination and the coalescer are chapters 239 and
243, the machine scheduler is chapter 246, and the result is the same
four-instruction loop clang gave us at the end of chapter 256.

## Two instruction selectors

LLVM has two ways to do the first stage. **SelectionDAG**, the older
one, builds a graph (a DAG) of each basic block's operations, then
runs a fixed sequence: build, optimise, legalise types (remove the
ones the target lacks), optimise, legalise operations, optimise,
select instructions by matching patterns, and schedule them into a
list<Cite id="llvm-codegen" />, which is chapter 237's tree tiling on
a DAG, one block at a time. **GlobalISel** is "intended to be a
replacement for SelectionDAG and FastISel", working on the whole
function and directly on MIR, through four passes: IRTranslator,
Legalizer, RegBankSelect and InstructionSelect<Cite id="llvm-globalisel" />.
Its first form is *generic* MIR, with types instead of register
classes:

```text
%5:_(s64) = nsw G_MUL %3, %3
%6:_(s64) = nuw nsw G_ADD %5, %4
%8:_(s64) = nuw nsw G_ADD %3, %7
```

(`llc -global-isel -stop-after=irtranslator`; `s64` is "a 64-bit
scalar"). With `-global-isel -global-isel-abort=1`, which fails rather
than quietly fall back to SelectionDAG, LLVM 18 compiles `sumsq` for
RISC-V to exactly the same assembly.

<Analogy title="two translators">
One translator works sentence by sentence, polishing each before
moving on; another reads the whole chapter first and translates it in
a few sweeps. Both produce the same book; they differ in how much they
see at once and how fast they work.
<span slot="breaks">Human translators may phrase things differently;
two instruction selectors must produce code with exactly the same
meaning, and here, for this loop, the very same instructions.</span>
</Analogy>

## Register allocators

LLVM ships several allocators, chosen with `llc -regalloc=`: **fast**,
"the default for debug builds", which works one block at a time;
**basic**; **greedy**, "the default allocator", which adds "global live
range splitting" and "works hard to minimize the cost of spill code";
and **pbqp**, which solves the problem as a mathematical
optimisation<Cite id="llvm-codegen" />. The difference shows at once on
our loop. Here is its body under `-regalloc=fast`:

```text
.LBB0_2:
  ld   a1, 8(sp)   # 8-byte Folded Reload
  ld   a3, 16(sp)  # 8-byte Folded Reload
  mul  a2, a1, a1
  addi a1, a1, 1
  sd   a1, 8(sp)   # 8-byte Folded Spill
  add  a2, a2, a3
  sd   a2, 16(sp)  # 8-byte Folded Spill
  bne  a0, a1, .LBB0_2
```

Values that live across blocks go back to memory at every block's
end, much as with our two-register example in chapter 256; greedy
keeps everything in registers. (Two honest footnotes. The same
documentation still shows `-regalloc=linearscan` in an example, but
LLVM 18's `llc` answers "Cannot find option named 'linearscan'", so
that line of the documentation is out of date. And on RISC-V, the pass list shows
the greedy allocator twice, because LLVM 18 allocates the vector
registers in a separate run first<Cite id="llvm-riscv-split-regalloc" />.)

## How clang and rustc are put together

  <ArchFigure />
</Figure>

**clang.** The driver decides which tools to run; ask it, and it
prints the plan:

```text
$ clang --target=riscv64 \
    -ccc-print-phases sumsq.c
0: input, "sumsq.c", c
1: preprocessor, {0}, cpp-output
2: compiler, {1}, ir
3: backend, {2}, assembler
4: assembler, {3}, object
5: linker, {4}, image
```

(trimmed of its tree-drawing characters). Inside the compiler, a
lexer and preprocessor feed "a recursive-descent parser", which hands
each construct to **Sema**, the semantic analysis library that checks
it and, "for valid programs", builds the AST; **CodeGen** then "takes
an AST as input and produces LLVM IR code from it"<Cite id="clang-internals" />.
That is Part III's front end, scanner, parser, resolver and type
checker, at industrial size.

**rustc.** Rust's compiler lowers the program more times. The AST is
lowered to **HIR**, "a more compiler-friendly representation of the
AST", where loops and `async fn` are desugared and types are inferred
and checked; then to **THIR**, fully typed and used for pattern
checking; then to **MIR**, "basically a Control-Flow Graph", where
borrow checking and many optimisations happen while the code is still
generic; and only then to LLVM IR, which is where generic code is
monomorphised (copied once per concrete type)<Cite id="rustc-dev-guide-overview" />.
Here is part of the MIR for the same `sumsq` written in Rust
(`rustc --emit=mir`, a debug build, wrapped to fit):

```text
bb2: {
  _7 = copy _3;
  _8 = copy _3;
  _9 = MulWithOverflow(copy _7,
                       copy _8);
  assert(!move (_9.1: bool),
    "attempt to compute `{} * {}`,
     which would overflow", ...)
    -> [success: bb3, ...];
}
```

It is a CFG of basic blocks, like our VIR, with one thing ours never
had: every `*` and `+` checks for overflow, because Rust's integer
operators panic on overflow in debug builds<Cite id="rustref-int-overflow" />.
In an optimised build those checks are gone from the MIR, and rustc
1.97 (whose LLVM is version 22), compiling for this machine's x86-64,
produces the same closed formula for the loop that clang did. For code generation, "usually, rustc uses
LLVM ..., but there is also support for Cranelift and GCC"; rustc does
not implement codegen itself<Cite id="rustc-dev-guide-codegen" />. The
Cranelift back end exists because it "has the potential to improve
compilation times in debug mode", and is installed from nightly as
`rustc-codegen-cranelift-preview`<Cite id="rustc-codegen-cranelift" />
(it is not part of the stable toolchain this chapter was written with,
so no Cranelift output is shown).

<Analogy extra title="publishers and a printing house">
Two publishers edit and typeset in their own ways, one in a single
pass, the other through several drafts, and then send their pages to
the same printing house, which owns the presses.
<span slot="breaks">A printing house prints what it is sent; LLVM also
rewrites what it is given, and a front end must tell it, through types
and flags such as nsw, exactly what it may assume.</span>
</Analogy>

<Callout kind="definition">
A **compiler architecture tour** is a reading of how a production
compiler divides its work: which stages it has, which intermediate
representation each stage works on, and where the front end hands
over to the back end. clang goes from tokens through an AST checked by
Sema to LLVM IR; rustc goes from an AST through HIR, THIR and MIR to
LLVM IR (or to Cranelift or GCC); LLVM goes from IR through MIR to
machine code.
</Callout>

<Examples of="compiler-architecture-tour">

```text
$ clang -S -emit-llvm sumsq.c
$ opt -passes='default<O2>' ...
$ llc -mtriple=riscv64 sumsq.ll
```

```text
$ rustc --emit=mir sumsq.rs
$ rustc --emit=llvm-ir -O sumsq.rs
```

```text
$ llc -stop-after=finalize-isel ...
$ llc -global-isel ...
$ llc -regalloc=fast ...
```

</Examples>

## What you learned

- LLVM's **code generator** runs instruction selection, scheduling,
  register allocation, prologue and epilogue insertion and emission, on
  **Machine IR** that starts in SSA form with virtual registers.
- **SelectionDAG** selects one block at a time through a DAG;
  **GlobalISel** works on whole functions in MIR. The **greedy**
  allocator is the default, **fast** is for debug builds.
- **clang**: lexer, recursive-descent parser, Sema, AST, CodeGen to
  LLVM IR. **rustc**: AST, HIR, THIR, MIR, then LLVM IR (or Cranelift
  or GCC).

That closes Part VII: from an IR to running machine code, by hand, in
a toy compiler, and in the real ones. Part VIII returns to Viscosity.
