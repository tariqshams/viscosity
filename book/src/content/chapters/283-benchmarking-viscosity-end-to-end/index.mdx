## One loop is not a program

Part II measured layouts one loop at a time; in this book's benchmark
run, summing one field of 100,000 particles was 8.5× faster in columns
than in objects. That is a fact about one loop. A program does more: it
builds its data one `push` at a time through the generated container,
runs some loops that love columns and some that do not care, and keeps
bounds checks wherever Viscosity could not prove an index safe. Whether
all of that adds up to a faster program is a separate question, and it
needs a separate measurement.

<Analogy title="an engine on a test bench, and the drive to work">
A car's engine on a test bench gives one number; your drive to work
gives another, with traffic lights, hills and a cold start. Both are
real, but only the second tells you how long the drive takes.
<span slot="breaks">A commute changes every day; a benchmark program
does exactly the same work on every run, so what changes between runs
is only the machine, which is what the harness has to control.</span>
</Analogy>

<Analogy title="a recipe's cooking time, and dinner on the table">
A recipe says "bake for 20 minutes"; dinner still takes an hour,
because of the chopping, the oven warming up and the washing-up you did
while waiting.
<span slot="breaks">In a kitchen the steps are separate; in a program
the same layout change speeds up one loop and slows down another, so
the parts cannot be timed apart and added up.</span>
</Analogy>

<Callout kind="definition">
An **end-to-end benchmark** measures a whole program, compiled the way a
user would compile it, rather than a single loop written for the
benchmark. It answers "does my program get faster?" and includes
everything the compiler changed, good and bad.
</Callout>

## Five programs, and a harness

The programs live in `packages/bench/e2e/`, each ordinary JavaScript
with no annotations: **particles** (200,000 particles with 8 fields;
each frame updates `x` and `y` from `vx` and `vy`), **ledger** (500,000
transactions; queries sum one field, or filter on one and sum another),
**heat** (diffusion on a 512 × 512 grid, reading each cell's four
neighbours), **boids** (20,000 boids, each averaging the velocity of the
next 64) and **n-body** (gravity between every pair of 1,500 bodies).
Every program times its own hot section and ends by printing one line of
JSON. Here is the end of `particles.js`, reformatted:

```js
const t0 = performance.now();
for (let f = 0; f < 200; f++)
  step(ps, 0.016);
const ms = performance.now() - t0;
let s = 0;
for (const p of ps) s += p.x + p.y;
console.log(JSON.stringify(
  { check: s.toFixed(3), ms }));
```

Lines 1 and 4 bracket the 200 frames with `performance.now()`, so the
time covers the frames and nothing else; lines 5 and 6 add up every
final position; and the last line prints both. The checksum does two
jobs (*Benchmarking honestly*): it makes the work's result observable,
so no engine can delete the work as dead code, and it lets the harness
check that the compiled program computed the same thing.

The committed results come from `packages/bench/src/matrix.ts`, which
runs each program on Node and on Bun. Its core, simplified:

```ts
runOnce(orig); runOnce(comp); // warm-up
for (let i = 0; i < RUNS; i++) {
  a.push(runOnce(orig));
  b.push(runOnce(comp));
}
const checks = new Set(
  [...a, ...b].map((x) => x.check));
if (checks.size !== 1) throw new Error(
  `${f} on ${rt.name}: checksums differ`);
speedupBest = min(am) / min(bm);
speedupMedian = median(am) / median(bm);
```

`runOnce` starts a fresh process (as in *Noisy numbers: the median, p95
and a fresh process*), so neither version inherits the other's type
feedback or garbage, and reads the JSON line it prints. The first line
throws one run of each away, to warm the file cache; the loop then
alternates original and compiled, `RUNS` times (9 for the committed
results), so a noisy minute on the machine hits both; and a fast wrong
answer is not a result, because a single differing checksum throws.

The first is one row of the matrix: the best of nine runs for each
version of `particles` on Node. The second is the same program on two
engines: on Node, columns made `heat` four times faster; on Bun they
made no difference, because Bun ran the *original* more than three and
a half times faster than Node did. The repository's findings suggest a cause, not yet
confirmed with engine traces: V8 keeps a double held in an object field
as a separate heap number, so columns fix both the storage and the
locality there, while JavaScriptCore stores the double in the object and
gains only the locality. The third is the whole-process wall time, start
up and data building included, which a user waiting for the program
would see: still almost three times faster.

The three big wins are the programs that look like Part II's
microbenchmarks: many elements, and hot loops that touch only some of
the fields. `n-body` gained least; it has only 1,500 bodies, and each
pair does a square root and a division, so memory layout is a smaller
share of its time (our reading of the program, not a measurement).

## The two programs that got slower

The first time this benchmark ran, n-body and boids were *slower* with
Viscosity than without. The commit that fixed it says why: the bounds
proofs from *Proving it safe* did not cover outer-loop indexes,
non-negative starts or `&&` guards, so checks sat inside the hot loops.
In n-body the inner loop reads `b[i]`, where `i` belongs to the *outer*
loop:

```js
for (let i = 0; i < b.length; i++) {
  for (let j = 0; j < b.length; j++) {
    const dx = b[j].x - b[i].x;
```

The old proof trusted only the innermost loop's own counter, so every
`b[i].x` became a call to `__vsc_bc` with two comparisons, 1,500 × 1,500
times per step. Boids' window loop,
`for (let j = i + 1; j < i + 64 && j < b.length; j++)`, failed for the
other two reasons. The fix was to make the proof more general, not to
drop the checks: an outer loop's counter is just as bounded inside the
inner loop, provided the inner loop does not change it; a start of
`i + 1` is non-negative when `i` is; and `j < b.length` still holds when
it is one side of an `&&`. Today `viscosity explain` reports
`12 of 12 element accesses proven in bounds` for n-body, and `11 of 11`
for boids.

<Callout kind="pitfall">
Benchmarking only the programs where your compiler shines is easy and
tells you nothing. The slow results are the useful ones: n-body and
boids are the reason the bounds proofs improved.
</Callout>

## How much to believe

An earlier run is committed too (`e2e-node-2026-10-31`, 3 runs per
version, medians, measured before a later fix to how checked writes
store their values). It said ledger 5.11× and boids 1.18×; the matrix
says ledger 3.75× best (4.08× median) and boids 1.31× (1.21×). Same
programs, same machine type, hours apart. The matrix's own note says
timings on this VM vary by up to about 2× between runs, and to treat
differences under about 10% as noise. So the honest summary is the
coarse one: on Node, particles, ledger and heat are several times
faster, while boids and n-body are a little faster, by an amount noise
could hide; a 1.2× is not a claim worth defending to two decimal places.

## A different language, a different verdict

The same question was asked of Python. In CPython, an update loop over
100,000 elements took 26.66 ns per element with dataclass objects, 43.31
with list columns and 72.7 with `array('d')` columns (the committed
`python-layouts` results, a loop benchmark rather than a whole program):
columns were *slower*, because CPython is an interpreter that makes a
new float object for every `array('d')` element it reads. However, the
typed columns used about 4.9× less memory (3.3 MB against 16.0 MB). So
the Python plugin keeps objects unless you opt in, and its report says
why; the analyses are the same for both languages, and only the cost
model's verdict differs, because measurement decided it.

<Callout kind="engine" label="Under the hood">
Each program times its hot section once per process, so the time
includes the engine getting warm. V8 starts running code in its
interpreter and moves hot functions up to optimizing compilers as it
gathers feedback<Cite id="v8-maglev" /> (*The V8 pipeline*). A
microbenchmark harness waits for that to finish; an end-to-end benchmark
keeps it in, because a user's program pays for it too.
</Callout>

## What you learned

- An **end-to-end benchmark** measures whole programs, compiled as a
  user would, including construction, checks and loops that do not
  benefit.
- The harness runs each version in fresh processes, alternating, after a
  discarded warm-up; it refuses to report a speed-up when checksums
  differ.
- On Node the committed gains were 4.37× (particles), 4.11× (heat),
  3.75× (ledger), 1.31× (boids) and 1.2× (n-body); on Bun they were
  smaller, and the small ones are within the noise.
- Bounds checks in a hot loop once made two programs slower; the fix was
  a more general proof. In CPython, columns cost time and save memory.
