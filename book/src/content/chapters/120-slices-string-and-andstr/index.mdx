## A token is a piece of the source

In *Writing a scanner*, your scanner made a token for every word of a
Drip program, and each token carried its lexeme, the exact text it came
from. The TypeScript scanner gets that text with

```ts
lexeme: source.slice(start, current)
```

which hands you a new string value. Yet the text already exists: it is
sitting right there in `source`, between `start` and `current`, and all
a token really needs is a way to say "those bytes, over there". A
struct-of-arrays loop has the same need for numbers: "elements 1000 to
1999 of the `x` column, please, without copying them".

Rust has a type for exactly that, and it builds on the last two
chapters: it is a borrow of *part* of a value.

<Analogy title="a highlighter pen">
You do not photocopy the sentence you care about in a printed book; you
run a highlighter over it. The mark says where the sentence starts and
how far it goes, and the page stays where it is, owned by whoever
bought the book.
<span slot="breaks">A highlight stays on the page for good; a slice is
a borrow, so it ends at its last use, and while it lasts the owner may
not change the page.</span>
</Analogy>

## Slices of arrays

Write a range in square brackets after a `&`:

```rust
let a = [10, 20, 30, 40, 50, 60];
let mid = &a[1..4];   // 20, 30, 40
let head = &a[..2];   // 10, 20
let tail = &a[3..];   // 40, 50, 60
let all = &a[..];     // the whole array
```

The range `1..4` starts at 1 and stops *before* 4 (write `1..=3` to
include the end); leave out a side and it runs to the start or the end.

<Callout kind="definition">
A **slice** is a borrowed view of a contiguous run of elements owned by
something else. The type `&[T]` is a shared slice of `T`s and
`&mut [T]` a mutable one. A slice value holds a pointer to its first
element and a **length**, so it is twice the size of a plain
reference<Cite id="rustref-dst" />, and every access through it is
bounds-checked<Cite id="rustref-slice" />.
</Callout>

<Formal title="When a slice is valid, and what it holds">

```text
&a[i..j]  is allowed when  i ≤ j ≤ len(a)
len(&a[i..j]) = j − i
(&a[i..j])[k] = a[i + k]
              for 0 ≤ k < j − i
```

<span slot="read">You may slice from i to j when i is at most j and j
is at most the length of a. The slice then has j minus i elements, and
its element number k is element i plus k of the original. Ask for a j
past the end, or an i past j, and the program stops.</span>
</Formal>

## Functions that take any slice

The real payoff is in function parameters. A function that takes
`&[i32]` does not care how long the array is, or whether it is getting
all of it, and a borrow of a whole array or `Vec` turns into a slice for
you<Cite id="rust-book-slices" />:

<Examples of="slice">

```rust
fn sum(xs: &[i32]) -> i32 {
    let mut total = 0;
    let mut i = 0;
    while i < xs.len() {
        total += xs[i];
        i += 1;
    }
    total
}
```

```rust
fn zero(xs: &mut [i32]) {
    let mut i = 0;
    while i < xs.len() {
        xs[i] = 0;
        i += 1;
    }
}
let mut a = [1, 2, 3, 4];
zero(&mut a[1..3]); // a is [1, 0, 0, 4]
```

<Run id="slice-sum" />

</Examples>

The first walks any slice with an index from 0 to `xs.len()` and adds
the elements up; `sum(&a)`, `sum(&a[1..4])` and `sum(&v)` for a `Vec`
all work, and none copies a number. The second takes a *mutable* slice
and writes zeros through it: lending only `&mut a[1..3]` lets the
function change elements 1 and 2 and nothing else, so `a` becomes
`[1, 0, 0, 4]`. The runnable one sums three different windows of one
array; change the ranges and run it.

Ask for a range that is not there, like `&a[2..9]` on six elements, and
the program stops while running with a **panic** (the Rust word for
"stop now, with a message"):

```text
range end index 9 out of range for
slice of length 6
```

A backwards range, `&a[2..1]`, panics with "slice index starts at 2 but
ends at 1". And forgetting the `&` does not even compile, because a
slice on its own has no size known in advance; it can only be reached
through a reference:

```rust
let s = a[0..2];  // broken
let s = &a[0..2]; // fixed
```

```text
error[E0277]: the size for values of type
  `[{integer}]` cannot be known at
  compilation time
help: consider borrowing here
```

<Prompts ids={['slice-param', 'slice-mut', 'slice-bounds', 'slice-amp']} />

<OtherLanguages title="Part of a list, passed to a function">

```rust
let xs = [10, 20, 30, 40, 50, 60];
let mid = &xs[1..4];  // a view
println!("{}", sum(mid)); // 90
```

```ts
const xs = [10, 20, 30, 40, 50, 60];
const mid = xs.slice(1, 4); // a copy
console.log(sum(mid)); // 90
```

```c
int xs[] = {10, 20, 30, 40, 50, 60};
/* pointer to xs[1], plus a length */
printf("%d\n", sum(xs + 1, 3)); /* 90 */
```

```python
xs = [10, 20, 30, 40, 50, 60]
mid = xs[1:4]  # a copy
print(sum(mid))  # 90
```

</OtherLanguages>

All four use the same half-open range, start included and end left
out. The genuine differences: TypeScript's `slice` and Python's `[1:4]`
copy the elements into a new list; C passes a pointer and a length
separately, as two arguments, and nothing stops `sum(xs + 1, 30)` from
reading far past the end; Rust keeps the pointer and the length together
in one value and checks every access against that length.

## Slices keep their owner borrowed

A slice is a borrow, so the rule of *The borrowing rules* applies. This
does not compile:

```rust
let mut v = vec![1, 2, 3];
let part = &v[..2];
v.push(9);
println!("{:?}", part);
```

```text
error[E0502]: cannot borrow `v` as
  mutable because it is also borrowed
  as immutable
```

`push` needs to change `v`, and might move its elements to a bigger
buffer, while `part` still points into the old one. (`{:?}` prints a
whole slice, like `[1, 2]`.) In TypeScript the copied slice would be its
own array and the question would never come up; in Rust a slice is
cheaper, and the price is that the owner has to stay put while you look.
For a scanner, and for a loop over a column, that is exactly right.

<Prompts ids={['slice-borrow']} />

<Callout kind="engine" label="Under the hood">
The Rust Drip VM hands its garbage collector slices. In
`companion/rust/src/vm.rs`, the roots of a collection are a `VmRoots`
value whose fields include `stack: &'a [Value]` and
`frames: &'a [CallFrame]`: views of the VM's own value stack and call
frames, borrowed for the length of one collection, with nothing copied
(the `'a` is a lifetime, the subject of *Lifetimes*). Slices matter for
Viscosity too: in a struct-of-arrays layout every `x` is in one array,
and `&xs[from..to]` hands a chunk of that column to any function that
takes `&[f64]`. *Struct of arrays in Rust by hand* leans on exactly
that.
</Callout>

## What you learned

- A **slice** `&[T]` is a borrowed window on a run of elements: a
  **pointer and a length**, 16 bytes. `&a[1..4]` leaves out its end,
  `..=` includes it, and every access is bounds-checked.
- Functions that take `&[T]` work on whole arrays, `Vec`s and parts of
  them; `&mut [T]` lets a function change just that part.
- A range out of bounds panics while running; a missing `&` does not
  compile.
- A slice keeps its owner borrowed, so the owner cannot change or grow
  while the slice is in use.

## Two kinds of text

You have used both already without being told: `String::from("fib")`
made a `String`, and the literal `"fib"` inside it was something else.
Here is the difference in four lines:

```rust
let mut own = String::from("let");
own.push_str(" x");   // own is "let x"
let kw = &own[0..3];  // "let", borrowed
let lit = "print";    // a literal
```

`own` is a **`String`**: it owns its text on the heap and can grow, so
`push_str` appends to it. `kw` is a **string slice**, written `&str`: a
view of some text that somebody else owns, here three bytes of `own`.
And `lit` is a `&str` too: a string literal's bytes are stored inside the
compiled program itself, and `lit` borrows them, which is why a literal
can never be changed<Cite id="rust-book-slices" />.

<Analogy title="your notebook and a quotation">
A `String` is your own notebook: you can write more pages into it, tear
pages out, and throw it away when you are done. A `&str` is a quotation
with a page reference: it points at words in somebody's book (your
notebook, or a printed one) without owning them, and you cannot write
into the book through it.
<span slot="breaks">A quotation can outlive the book it quotes from;
Rust's borrow checker makes sure a `&str` never outlives the text it
points at.</span>
</Analogy>

## Converting, and choosing

Going from `String` to `&str` is free: it is only a borrow. Going the
other way, with `String::from(x)` or `x.to_string()`, copies the bytes
into a fresh heap buffer<Cite id="rust-book-strings" />. So which should
a function take? Prefer `&str`. A `&str` parameter accepts literals and
slices, and when you pass `&own` for a `String`, Rust converts the
`&String` to a `&str` for you<Cite id="rust-book-slices" />.

<Examples of="string-vs-str">

```rust
fn shout(s: &str) -> usize {
    s.len()
}
shout("print");     // a literal: 5
shout(&own);        // a whole String
shout(&own[1..]);   // part of one
```

```rust
fn label(n: i32) -> String {
    let mut s = String::from("n = ");
    s.push_str(&n.to_string());
    s
}
// label(7) is "n = 7"
```

<Run id="lexemes" />

</Examples>

The first is the reason to take `&str`: one function, three kinds of
caller, and none of them copies a byte. The second has to *return* an
owned `String`, because it builds new text that did not exist before the
call (`n.to_string()` turns the number into text, and `&` lends that to
`push_str`); a `&str` would have nothing to point at once the function
ended. The runnable one cuts lexemes out of a line of Drip, the way the
scanner does, then makes an owned copy and grows it.

The three mistakes everyone makes, each broken line next to its fix:

```rust
shout(own);   // broken
shout(&own);  // fixed

// broken:
fn name() -> String { "drip" }
// fixed:
fn name() -> String { "drip".to_string() }

let both = "tea" + "pot"; // broken
let both = String::from("tea") + "pot";
```

```text
error[E0308]: mismatched types
  |     shout(own);
  |           ^^^ expected `&str`,
  |               found `String`
help: consider borrowing here
  |     shout(&own);
error[E0308]: mismatched types
  |     "drip"
  |     ^^^^^^ expected `String`,
  |            found `&str`
help: try using a conversion method
error[E0369]: cannot add `&str` to `&str`
```

The first passes an owned `String` where a borrow is wanted (and would
move it); add the `&`. The second returns a borrowed literal where an
owned `String` was promised; convert it. The third tries to join two
borrowed pieces of text, which would have to make new text with no
owner; start from an owned `String`, which `+` then grows by the borrowed
piece on the right (`format!("{}{}", a, b)` is the other common way).

<Callout kind="definition">
**`String` vs `&str`**: a `String` is an **owned**, growable buffer of
UTF-8 text on the heap. A `&str` is a **borrowed** string slice: a
pointer and a length into UTF-8 text owned by something else, such as a
`String` or the program itself. Take `&str` in parameters; return or
store a `String` when you need to own or grow text.
</Callout>

## Lengths count bytes

Both types hold **UTF-8**, the encoding in which a character takes one
to four bytes (ASCII letters one, `é` two, `€` three, `🙂`
four)<Cite id="rfc3629" />. Lengths and indices are counted in bytes,
not characters:

<Analogy extra title="a shelf of books measured with a ruler">
A ruler tells you how many centimetres of shelf a row of books takes
up, not how many books there are, because books come in different
thicknesses; and if you cut the row at the 10 cm mark you may slice a
book in half. A string's `len` is the ruler (bytes), the characters are
the books, and a slice index is a cut.
<span slot="breaks">Books can be any thickness; a UTF-8 character is
always one to four bytes, and Rust refuses to make a cut through the
middle of one, stopping the program instead.</span>
</Analogy>

```rust
let h = "héllo";
println!("{}", h.len());           // 6
println!("{}", h.chars().count()); // 5
let bad = &h[0..2]; // panics
```

```text
end byte index 2 is not a char boundary;
it is inside 'é' (bytes 1..3 of string)
```

`len` is 6 because `é` takes two bytes; `chars().count()` walks the text
and counts the characters, 5. Slicing in the middle of `é` stops the
program, because the result would not be valid UTF-8. And `h[0]` (one
number as an index) does not compile at all: "the type `str` cannot be
indexed by `{integer}`", because a byte index would not reliably give
you a character<Cite id="rust-book-strings" />.

<OtherLanguages title="How long is héllo?">

```rust
"héllo".len()            // 6 bytes
"héllo".chars().count()  // 5 chars
```

```ts
'héllo'.length   // 5 UTF-16 code units
'🙂'.length      // 2
```

```c
strlen("héllo")  /* 6 bytes, in UTF-8 */
```

```python
len("héllo")  # 5 code points
```

</OtherLanguages>

Each language counts something different. Rust and C count bytes; the
difference is that Rust guarantees the bytes are valid UTF-8 and refuses
to cut a character in half, while C knows nothing about characters at
all. TypeScript counts UTF-16 code units (as *Strings up close* showed),
so an emoji has length 2; Python counts code points. None of them counts
what a reader would call characters, which is the subject of *Strings and
Unicode*.

## The scanner, without a single copy

Here is the token type from the Rust Drip scanner,
`companion/rust/src/scanner.rs`, lightly trimmed:

```rust
pub struct Token<'src> {
    pub kind: TokenKind,
    pub lexeme: &'src str,
    pub line: usize,
}
```

and the line that makes one:

```rust
Token { kind, lexeme:
    &self.source[self.start..self.current],
    line }
```

Ignore the `'src` for now (it is a lifetime, the subject of
*Lifetimes*, and it tells the compiler a token cannot outlive the source
it points into). Step through it cutting the tokens of one line:

The file's own comment says what this buys: a token borrows its lexeme
straight out of the source text, so scanning never allocates. The
scanner also keeps `bytes: &'src [u8]`, a byte view of the same text,
because every character that matters to Drip is ASCII. Only when the
compiler turns a string literal into a Drip value does it make an owned
`String`: `unescape(lexeme: &str) -> String` reads the borrowed lexeme
and builds new text, with escapes like `\n` turned into the characters
they stand for.

## What you learned

- **`String`** owns growable UTF-8 text; **`&str`** borrows text that
  lives elsewhere, including string literals, which live in the program.
- `&String` to `&str` is free; `to_string()` and `String::from` copy.
  Take `&str` in parameters, return a `String` when you make new text.
- Lengths and indices are in **bytes**; slicing inside a character
  panics, and a string cannot be indexed by a single number.
- The Rust Drip scanner's tokens are `&str` slices of the source, so
  scanning allocates nothing.
