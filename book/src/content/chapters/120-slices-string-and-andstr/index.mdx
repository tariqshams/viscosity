## A token is a piece of the source

Your TypeScript scanner gets each token's lexeme with
`source.slice(start, current)`, which makes a new string; yet the text
already exists in `source`, and all a token needs is a way to say "those
bytes, over there". A struct-of-arrays loop wants the same for numbers:
"elements 1000 to 1999 of the `x` column, without copying them". Rust
has a type for exactly that: a borrow of *part* of a value.

<Analogy title="a highlighter pen">
You do not photocopy the sentence you care about in a printed book; you
run a highlighter over it. The mark says where the sentence starts and
how far it goes, and the page stays where it is, owned by whoever
bought the book.
<span slot="breaks">A highlight stays on the page for good; a slice is
a borrow, so it ends at its last use, and while it lasts the owner may
not change the page.</span>
</Analogy>

## Slices

Write a range in square brackets after a `&`: `&a[1..4]` covers indices
1, 2 and 3 (the end is left out; `1..=3` includes it), and `&a[..2]`,
`&a[3..]` and `&a[..]` run from the start, to the end, or over
everything. Step through what each points at:

The payoff is in parameters: a function that takes `&[i32]` does not
care how long the array is, or whether it gets all of it, and a borrow
of a whole array or `Vec` turns into a slice for
you<Cite id="rust-book-slices" />.

</Examples>

`sum` walks any slice with an index up to `xs.len()`. `main` passes it a
middle window, the whole array, a tail and a `Vec`, and none of these
copies a number (`mid` has length 3, so `sum(mid)` is 90). Ask for a
range that is not there, like `&a[2..9]` on six elements, and the
program **panics** while running: "range end index 9 out of range for
slice of length 6". A `&mut [i32]` lets a function change just that
window and nothing else. And since a slice is a borrow, the rules of
*Borrowing and the borrowing rules* apply: you cannot `push` onto a
`Vec` while a slice of it is still in use (E0502).

<Callout kind="definition">
A **slice** is a borrowed view of a contiguous run of elements owned by
something else. The type `&[T]` is a shared slice of `T`s and
`&mut [T]` a mutable one. A slice value holds a pointer to its first
element and a **length**, so it is twice the size of a plain
reference<Cite id="rustref-dst" />, and every access through it is
bounds-checked<Cite id="rustref-slice" />.
</Callout>

## Two kinds of text

You have used both kinds already: `String::from("fib")` made a
**`String`**, which owns its text on the heap and can grow, and the
literal `"fib"` inside it is a **string slice**, `&str`, a view of text
that somebody else owns. A literal's bytes are stored inside the
compiled program, and the `&str` borrows them, which is why a literal
can never change<Cite id="rust-book-slices" />.

<Figure takeaway="A String owns and can grow its bytes; a &str only points at bytes that live somewhere else." caption="A String s holding a line of Drip, a &str name borrowing one byte of it, and a literal lit borrowing bytes stored in the program. The sizes are 24 bytes for a String and 16 for a &str, from std::mem::size_of with rustc 1.97.">
  <StringLayout />
</Figure>

Going from `String` to `&str` is free, a borrow; going the other way,
with `String::from(x)` or `x.to_string()`, copies the bytes into a new
heap buffer<Cite id="rust-book-strings" />. So take `&str` in
parameters, and return a `String` when you make new text:

<Examples of="string-vs-str">

```rust
fn shout(s: &str) -> usize {
    s.len()
}
fn label(n: i32) -> String {
    let mut s = String::from("n = ");
    s.push_str(&n.to_string());
    s
}
let own = label(7);   // "n = 7"
shout("print");       // a literal: 5
shout(&own);          // a whole String
shout(&own[4..]);     // part of one
```

</Examples>

`shout` takes `&str`, so it accepts a literal, a borrowed `String`
(Rust turns the `&String` into a `&str` for you) and a slice of one, and
none of them copies a byte. `label` must *return* an owned `String`,
because it builds text that did not exist before the call; a `&str`
would have nothing to point at once the function ended. The mistakes
everyone makes are all type errors with a helpful `help:` line:
`shout(own)` is "expected `&str`, found `String`", with "consider
borrowing here"; `fn name() -> String { "drip" }` is "expected `String`,
found `&str`", fixed with `"drip".to_string()`; and `"tea" + "pot"` is
E0369, "cannot add `&str` to `&str`", because new text needs an owner
(`String::from("tea") + "pot"` gives it one).

Both types hold **UTF-8**, where a character takes one to four
bytes<Cite id="rfc3629" />, and lengths and indices count bytes:
`"héllo".len()` is 6, because `é` takes two, while
`"héllo".chars().count()` is 5. Slicing through the middle of `é`
panics ("end byte index 2 is not a char boundary"), and `h[0]` does not
compile at all, because a byte index would not reliably give a
character<Cite id="rust-book-strings" />. (TypeScript's `length` counts
UTF-16 code units instead, as *Strings up close* showed.)

<Callout kind="definition">
**`String` vs `&str`**: a `String` is an **owned**, growable buffer of
UTF-8 text on the heap. A `&str` is a **borrowed** string slice: a
pointer and a length into UTF-8 text owned by something else, such as a
`String` or the program itself. Take `&str` in parameters; return or
store a `String` when you need to own or grow text.
</Callout>

## The scanner, without a single copy

The Rust Drip scanner's tokens (`companion/rust/src/scanner.rs`, lightly
trimmed) hold their lexeme as a `&str` cut out of the source:

```rust
pub struct Token<'src> {
    pub kind: TokenKind,
    pub lexeme: &'src str,
    pub line: usize,
}
```

Ignore the `'src` for now (it is a lifetime, the subject of
*Lifetimes*: a token cannot outlive the source it points into). Each
token is made with `&self.source[self.start..self.current]`; step
through it cutting the tokens of one line:

As the file's own comment says, scanning never allocates. Only when the
compiler turns a string literal into a Drip value does it make an owned
`String`, with `unescape(lexeme: &str) -> String`, because turning `\n`
into a newline is new text.

<More title="More: cutting lexemes by hand, and four languages counting héllo">

<Run id="lexemes" />

`lexeme` returns a `&str` borrowed from `src`; the last lines make an
owned copy with `String::from` and grow it, which a `&str` could never
do.

```ts
'héllo'.length   // 5 UTF-16 code units
'🙂'.length      // 2
```

Rust and C count bytes (but only Rust guarantees valid UTF-8 and refuses
to cut a character in half); TypeScript counts UTF-16 code units, so an
emoji has length 2; Python counts code points. None counts what a reader
would call characters, which is the deep dive *Strings and Unicode*.
TypeScript's `slice` and Python's `xs[1:4]` copy; C passes a pointer and
a length as two separate arguments, with nothing stopping a read past
the end; Rust keeps them together and checks every access.

</More>

<Analogy extra title="your notebook and a quotation">
A `String` is your own notebook: you can write more pages into it, tear
pages out, and throw it away when you are done. A `&str` is a quotation
with a page reference: it points at words in somebody's book (your
notebook, or a printed one) without owning them, and you cannot write
into the book through it.
<span slot="breaks">A quotation can outlive the book it quotes from;
Rust's borrow checker makes sure a `&str` never outlives the text it
points at.</span>
</Analogy>

## What you learned

- A **slice** `&[T]` is a pointer and a length into someone else's
  elements; every access is bounds-checked.
- **`String`** owns growable UTF-8 text; **`&str`** borrows it. Take
  `&str`, return `String`; lengths count bytes.
