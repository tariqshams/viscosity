## A value that will not fit

Every slot on the VM's stack is the same size, which is how the VM finds
slot 7 without measuring slots 0 to 6; a number fits, because it is
always 64 bits. A string, however, may be `""` or a million characters
built by a loop, and a list may hold three values now and thousands
after some calls to `push`. No slot size fits all of them, so strings
and lists live somewhere else, and the slot holds the way to find them.

<Analogy title="a cloakroom ticket">
The hooks in a cloakroom only take small things, so a big suitcase goes
to the back room, and you get a numbered ticket instead. The ticket is
always the same size, whatever it stands for, and showing it gets you
the suitcase.
<span slot="breaks">A cloakroom gives each suitcase one ticket; a heap
object can have any number of references to it at once (two variables,
a list and a stack slot), and none of them is the "real" one.</span>
</Analogy>

## Heap objects

<Figure takeaway="The slot holds a reference; the object lives on the heap." caption="A string value is the obj tag plus an address. The object itself starts with a header that every object shares, then its type, then its own fields.">
  <ObjLayout />
</Figure>

The object tag from *Tagging values at run time* is that ticket: its
payload is a reference to an **object** the VM allocates on the heap.
Here is the shared header, with the string and list objects, from the
companion's `vm/object.ts` (lines wrapped):

```ts
interface ObjHeader {
  isMarked: boolean;
  next: Obj | null;
}
interface ObjString extends ObjHeader {
  type: 'string'; chars: string;
  hash: number }
interface ObjList extends ObjHeader {
  type: 'list'; items: Value[] }
```

`isMarked` is a flag for the garbage collector, and `next` links the
object into the object list. Then `type` names the kind of object, and
the rest is its own: a string's characters and a `hash` made from them
(for *Hash tables*), a list's elements in `items`. Functions, classes
and instances extend the same header, and `Obj` is a tagged union of
all nine kinds on `type`.

<Callout kind="definition">
A **heap object** is a value too big, or too changeable in size, to sit
in a stack slot, so it lives on the heap and values refer to it by
**reference**. Every heap object starts with the same **header** (in the
companion VM, `isMarked` for the garbage collector and `next` for the
object list), then a `type` tag naming the kind of object, then its own
fields.
</Callout>

<Examples of="heap-object">

```text
let s = "tea";
let t = s + "pot";
let u = t;
```

</Examples>

The first line pushes an object that already exists: the compiler made
`"tea"` with `heap.copyString` when it met the literal, and put it in
the constant pool. The second makes a new object at run time, because
`add`, given two strings, joins them into a fresh `"teapot"`. The third
copies a reference, not the characters, so `t` and `u` name one object
(*References: two names, one object*), which is safe because nothing in
Drip can change a string. Here is the join, from `vm/vm.ts`:

```ts
} else if (isString(a) && isString(b)) {
  const s = this.heap.copyString(
    a.chars + b.chars);
  this.sp--;
  stack[this.sp - 1] = s;
}
```

`a` and `b` were only *peeked* at, so they are still on the stack while
the new string is made; making an object may start the garbage
collector, which treats whatever is on the stack as in use, and popping
first would leave `a` and `b` reachable from nowhere just as it looks.

## The object list

Every object is made by one method, `allocate`, in `vm/heap.ts`:

```ts
private allocate<T extends Obj>(o: T): T {
  this.bytesAllocated += SIZE[o.type];
  // ...collect if past the threshold
  o.next = this.objects;
  this.objects = o;
  return o;
}
```

`SIZE` is a rough byte count per kind of object, so the VM can tell when
a collection is worth it. The last lines are the point: `heap.objects`
refers to the newest object, its `next` to the one before, and so on
back to the first, and adding at the front costs the same however long
the list is.

<HeapListSteps client:visible />

`"xa"` and `"xaa"` are garbage, which nothing can reach; in a VM written
in C, memory nobody can reach is memory nobody can free (a **leak**),
and the list is the VM's promise that it can always find every object
it made.

<Callout kind="definition">
The **object list** is a linked list through the `next` field of every
heap object, starting at `heap.objects`. `allocate` adds each new object
at the head, in a fixed amount of work. Walking the list visits every
allocation, reachable or not, which is what a garbage collector needs in
order to find the unreachable ones.
</Callout>

<Examples of="object-list">

```ts
const vm = new VM();
vm.heap.liveObjects(); // 11
vm.interpret('print "a" + "b";');
vm.heap.liveObjects(); // 16
```

</Examples>

`liveObjects()` follows `next` from the head, counting. A fresh VM
holds 11 objects (`"init"`, and five natives with their names); one
line adds five: the script's function, `"a"`, `"b"`, the closure that
runs the script, and the joined `"ab"`.

<More title="Under the hood: freeing in a VM written in JavaScript">

JavaScript has its own garbage collector, so the companion VM cannot
really free anything: its sweep unlinks a dead object and, in debug
mode, **poisons** it (deletes every property and installs a getter that
throws), so a bug that uses a freed object fails loudly. That is off by
default, because deleting properties can move an object into V8's
slower dictionary properties<Cite id="v8-fast-properties" />; the
comment in `heap.ts` records that profiling found poisoning was over
half the runtime.

</More>

## The list object

<Figure takeaway="A list is a heap object whose items are references and plain values." caption="The stack slot holds a reference to an ObjList. After the header come its type and items, a JavaScript array of Drip values. A number or none sits right in its cell; a string is one more reference.">
  <ListLayout />
</Figure>

A list is one more heap object, with instructions to build, read and
write it. For a literal the compiler leaves each element's value on the
stack in source order, then emits `list` with the count as a one-byte
operand. The VM's half:

```ts
case Op.List: {
  const n = readByte();
  const list = this.heap.newList(
    stack.slice(this.sp - n, this.sp));
  this.sp -= n;
  this.push(list);
  break;
}
```

`stack.slice` copies the top `n` values into a new array and `newList`
wraps the object around it; only then are the elements dropped, for the
same reason `add` peeks.

<BuildSteps client:visible />

`index.get` pops the index, checks it against the list still on the
stack, and replaces the list with the element; `index.set` does the
same with a value on top, stores it, and leaves the value on the stack
(an assignment in Drip is an expression). Both call `checkIndex`, which
tests four things in order, each with its own error: is it a list
(`"abc"[0]` says `cannot index a string`), is the index a number
(`a list index must be a number, not a string`), is it whole (`index
1.5 is not a whole number`), and is it in range (`index 3 is out of
range for a list of length 3`)? The order decides the message, so
`"abc"[1.5]` says `cannot index a string`. Writing can only replace an
element: `xs[len(xs)] = 4` is out of range, and `push` is how a list
grows.

<Callout kind="definition">
A **VM list** is a growable list object on the VM's heap: the shared
object header, then `items`, an array of values in order. The VM builds
one with `list n`, reads an element with `index.get`, writes one with
`index.set` and measures one with `list.len`; `index.get` and
`index.set` check the index first and stop with a runtime error naming
what is wrong.
</Callout>

<Examples of="vm-list">

```text
0000    1 const          0 '10'
0003    | const          1 '20'
0006    | list           2
0008    | define.global  2 'xs'
0011    2 load.global    3 'xs'
0014    | const          4 '1'
0017    | index.get
0018    | print
```

</Examples>

This is the companion disassembler's listing (spacing trimmed) for
`let xs = [10, 20]; print xs[1];`. Offsets 0 to 6 push two elements
and gather them with `list 2` into one reference, which `define.global`
stores as `xs`. Line 2 pushes the list and the index 1, and `index.get`
replaces both with `20` for `print`. (`xs[0] = 7;` would push the list,
the index and the value, then run `index.set` and `pop`.)

<More title="Growing, tracing and looping over a list">

`push` is a native function whose body, after checking it was given a
list, is `xs.items.push(v)`: JavaScript's own array does the growing,
which hides the part a VM in C or Rust must do itself. Such a list
keeps a **length** (how many elements it has) and a **capacity** (how
many slots it has room for); a push into spare room is one store, and a
push into a full list first copies everything into a bigger block.

<GrowSteps client:visible />

Doubling makes the copying cost a small, fixed amount per push on
average: from capacity 1, n pushes copy 1 + 2 + 4 + … + 2ᵏ elements, and
that sum is less than 2n. Real systems pick their own factor: V8 grows
an array to the old capacity plus half, plus 16<Cite id="v8-src-js-objects-h" />;
Python grows lists by about an eighth<Cite id="cpython-listobject" />;
and Rust's `Vec` promises only that `push` is cheap on average<Cite id="rust-std-vec" />.

A list refers to its elements, so when the collector (*Reclaiming
memory: mark and sweep*) reaches one it marks every value in `items`;
a list that contains itself cannot trap it, because an object already
marked is skipped (printing has its own guard: `let xs = []; push(xs,
xs); print xs;` prints `[[...]]`).

A for-in loop compiles to ordinary instructions, keeping the list and a
counter in two hidden locals (stack slots the compiler reserves under
names no Drip program can write); *Locals as stack slots* and *Jumps:
branches, loops and backpatching* explain the instructions it uses.
