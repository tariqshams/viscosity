## A hundred lines

The last chapter described tokens; now for the program that makes them.
In the companion code it is a single function, `scan`, in
`companion/ts/src/scanner.ts`: about a hundred lines that take a
string and return an array of tokens.

```ts
function scan(source: string): Token[]
```

It takes nothing else, not even somewhere to send error messages: a
character it cannot use becomes a token too, as you will see below, and
everything else happens inside. You wrote a smaller relative of this function for JSON
in *Checkpoint: JSON and its scanner*, and the question it answers is
the same one: given a long row of characters, where does each word
start, where does it end, and what kind of word is it?

<Analogy title="two fingers on a line of text">
Run two fingers along a line of print. Your left finger marks where the
current word began; your right finger slides forward, letter by letter,
until the word ends. Everything between your fingers is the word: write
it down, move your left finger up to your right one, and start again.
<span slot="breaks">Fingers can jump back to reread. Drip's scanner
never moves backwards: once a character is behind the right finger, it
is never looked at again.</span>
</Analogy>

<Analogy extra title="a cashier at a till">
Shopping comes down the belt in order. The cashier takes the next
item, decides what it is, and rings it up as one line on the receipt;
the plastic dividers between customers' shopping are not rung up at
all, they only separate.
<span slot="breaks">A cashier sees each item whole. A scanner sees one
character at a time, so for most tokens its real work is finding where
the item *ends*.</span>
</Analogy>

## The state and the helpers

The two fingers are two numbers, and there is a line counter for the
source location:

```ts
let start = 0;   // where this token began
let current = 0; // the next char to read
let line = 1;
```

`start` is the left finger, the index of the first character of the
token being built; `current` is the right finger, the index of the next
character to read. Around them sit a few tiny helper functions. They are
closures, from *Closures: functions that remember*: arrow functions
declared inside `scan`, so they can all see `source`, `start` and
`current` without being passed them. Here are the first three:

```ts
const atEnd = () =>
  current >= source.length;
const advance = () => source[current++];
const peek = () =>
  atEnd() ? '\0' : source[current];
```

`atEnd` is true once `current` has gone past the last character.
`advance` reads the character at `current` *and* moves `current` past it
(`current++` gives the old value, then adds one). `peek` only looks,
without moving; at the end of the source it returns `'\0'`, a stand-in
character that none of the scanner's checks will match, so callers
never have to deal with `undefined`. When a token is complete, `add`
cuts its lexeme out of the source with `slice`, from `start` up to (not
including) `current`:

```ts
const add = (type, literal = null) => {
  tokens.push({
    type,
    lexeme: source.slice(start, current),
    literal,
    line,
  });
};
```

(The real `add` also has type annotations. Here and below, the code is
simplified from `scanner.ts` to fit your screen.)

<Callout kind="definition">
A **scanner** (also called a *lexer*) is the first stage of a front
end. It reads source text character by character and produces a list of
tokens, skipping the characters that only separate them. Drip's keeps
two indexes into the text: `start`, the first character of the token
being built, and `current`, the next character to read.
</Callout>

<Formal title="What a scanner promises">

```text
scan : string → Token[]
lexeme(t) = source[start .. current)
lexemes, in order, with the skipped
characters put back  =  source
```

<span slot="read">A scanner is a function from a string to an array of
tokens. Each token's lexeme is the slice from start up to, not
including, current at the moment the token was added. And nothing is
lost or reordered: if you laid the lexemes end to end and put the
skipped spaces, newlines and comments back where they were, you would
get the source again, character for character.</span>
</Formal>

## The loop

Every round of the loop makes at most one token. It moves `start` up to
`current`, reads one character, and lets a `switch` decide what that
character begins. Step through it on a short line:

<ScanLoopSteps client:visible />

The real loop has the same shape, with a case for every kind of
character:

```ts
while (!atEnd()) {
  start = current;
  const c = advance();
  switch (c) {
    case '(': case ')': case '{':
    // … the other one-character tokens
      add(c);
      break;
    case ' ': case '\r': case '\t':
      break;
    case '\n':
      line++;
      break;
    // … more cases
    default:
      error(`unexpected character '${c}'`);
  }
}
tokens.push({ type: 'eof', lexeme: '',
  literal: null, line });
```

Line 1 keeps going until every character has been read. Line 2 starts a
new token: the left finger jumps up to the right one. Line 3 reads one
character into `c` and moves past it. The `switch` then picks a case by
that character. For a one-character token, `add(c)` is enough: because
a punctuation token's type is its own spelling (from the last chapter),
the character `c` *is* the type. The whitespace cases (space, carriage
return `'\r'` and tab `'\t'`) do nothing at all, so they make no token,
and a newline only adds one to `line`. The `default` case catches any
character no other case wanted, such as `@`, and `error` pushes a token
of type `error` whose lexeme is the message. After the loop, one `eof`
token is pushed, with an empty lexeme and the last line.

The first is the plainest round trip: two one-character tokens, the
space between them skipped, then `eof`. The second shows the line
counter at work: the newline makes no token, but it bumps `line`, so
the closing brace is recorded on line 2. The third is a scanner small
enough to read in one go, written for this page with the same loop: it
knows brackets, braces and semicolons, skips spaces, counts lines, and
reports anything else; change the input strings at the bottom and run
it again.

When the `default` case finds a character it does not know, it does
not stop and it prints nothing: it adds an `error` token, with the
message `unexpected character '@'` as its lexeme and the current line,
and *carries on*. The parser reports that token when it reaches it, so
every error, from the scanner or the parser, comes out in source order;
spot the difference between Drip's output for a program with one stray
character and for the fixed one:

```
print 1 @ 2;
# line 1: unexpected character '@'
print 1 + 2;  # 3
```

The parser reports only the first error in each statement and then
skips to the next one, so the leftover `1 2` draws no second complaint.
Nothing runs, because the pipeline stops before the interpreter if
anything was reported.

<Callout kind="engine" label="Under the hood">
Drip's scanner makes the whole list of tokens before the parser starts.
Drip's VM in Part IV makes a different choice: its scanner hands out one
token at a time, whenever the compiler asks for the next one, so the
full list is never built (see `companion/ts/src/vm/scanner.ts`). Both
use the same two pointers. Handing out tokens one by one saves memory
for a long program, while a list is easier to inspect and test; either
way the scanner is the part a compiler textbook calls the *lexical
analyser*<Cite id="coopertorczon2022" />.
</Callout>

## What you learned

- A **scanner** turns characters into tokens. Drip's keeps two
  pointers: `start`, where the token began, and `current`, the next
  character to read; each lexeme is `source.slice(start, current)`.
- `advance` reads a character and moves on; `peek` only looks, and
  returns `'\0'` at the end.
- The main loop reads one character, and a `switch` decides what it
  begins. Whitespace makes no token, `'\n'` bumps the line count, and an
  unknown character becomes an `error` token while scanning carries on.
- After the loop, one `eof` token marks the end.
