## Where you started

This was the first program in the book:

```js
function double(n) {
  return n * 2;
}
```

That chapter promised that everything later would be built from that
one idea: name a piece of work, then build bigger work out of named
pieces. Since then, those pieces have become scanners, parsers,
an interpreter, a compiler, a virtual machine, a garbage collector, an
SSA intermediate representation, a stack of analyses, and an optimizer
that changes how a program’s data sits in memory, for two languages.

At the top of a long climb you turn around. The path you took is laid
out below you, and you can see how each stretch led to the next: the
steep bit that felt pointless was the one that got you over the ridge.
</Callout>

Here is a particle simulation. Run it through the real compiler, then
read the report with the whole book in mind:

<Playground client:visible title="The whole pipeline" initial={`const ps = [];

The CLI says the same thing about it:

```
ps (line 1) {x, y, vx, vy, m} → struct
  of arrays
  · loop at line 7 in <module>() touches
    4 of 5 fields (vy, y, vx, x)
  · loop at line 13 in <module>() touches
    1 of 5 fields (x)
  · typed Float64Array columns for all 5
    fields
  · about 10000 elements
  · 5 of 5 element accesses proven in
    bounds
```

To get there, acorn parsed the source into an ESTree (chapter 92). The
front-end lowered it to VIR, in SSA form (chapters 93, 77–78).
Collection discovery found `ps` (96), the shape analysis saw five fields
in a stable order (97), and the access patterns found two hot loops
(98). The safety analysis found no escape (99), the cost model liked
10,000 elements (101), and the code generator replaced the objects with
a container of five `Float64Array`s that doubles its capacity as it
grows (103–105). Every line of the report was written by the planner
as it decided (110). Behind all of it, the differential tests run every
corpus program both ways and compare the output (112).

## What it measured

Two numbers summarize Track A: how much the bytecode VM beat the
tree-walker, and how much Viscosity sped up whole programs. Both come
from the committed result files, from one run each on a shared cloud
machine:

<TrackAResults caption="The VM won on most programs, and lost on equality and instantiation. Viscosity won big where a hot loop reads a few fields of a large array, and little on nbody and boids." />

Read the losses as carefully as the wins. The VM was slower than the
tree-walker on two programs. Part IV named the suspects: the VM runs
its own heap and garbage collector on top of V8’s, and its own hash
tables where the tree-walker borrows V8’s `Map`. One benchmark, `string_equality`,
doesn’t run on the VM at all: it fails with “Too many constants in one
chunk”, because a chunk’s constant index is one byte, so 256 constants
is the limit. And Viscosity’s smallest wins came on `nbody`, where
every body reads every field of the others, and on `boids`. The cost
model chose struct of arrays for those just as it did for the big
wins: it can’t yet tell them apart.

## What isn’t done

An honest capstone lists the unfinished parts:

- **Not on npm.** Chapter 119 found and fixed three bugs between the
  repository and `npm install`, but when this chapter was written
  nothing was published, and the name `viscosity` belongs to someone
  else. (The CLI went to npm as `@viscosity/cli` on 2026-11-02; see
  chapter 198.)
- **No WebAssembly back end** (chapter 117). Every version of
  Viscosity emits JavaScript.
- **Many ordinary programs are refused** (chapter 118): sorting,
  classes, destructuring, varying shapes, exported arrays. Some of
  those are chores; some are research.
- **The cost model is a heuristic**, with a 64-element threshold and
  measurements from one machine.

</Callout>

## Track B: the same machine, in Rust

Track B, chapters 121 to 200, rebuilds the two biggest things you made
in a language where memory layout is yours to control. First the Rust
language itself, through ownership, borrowing, arenas and
struct-of-arrays by hand (Part IX). Then Drip’s VM again, as `drip-rs`
(Part X), which already exists in `book/companion/rust` and has
benchmark results committed beside it. Then Viscosity in Rust, parsing
with oxc and producing the same decisions as the TypeScript engine
(Part XI), and finally a command-line tool, release engineering and a
final benchmark matrix (Part XII).

“The same decisions” is checkable, because Track A left a contract
behind. For every corpus and benchmark program, in both bounds modes,
the TypeScript engine’s compiled code and explain report are stored as
files in `engine/rust/tests/expected`, and the Rust port has to
reproduce them byte for byte.

<Callout kind="engine" label="Under the hood">
The Rust port is complete. Its workspace has five crates: `vir`,
`core`, `frontend-js`, a `cli` that builds a `viscosity` binary, and
`wasm`, which wraps the compiler for the browser. Its parity test
matches every stored fixture byte for byte, and the WebAssembly build
reproduces them too. Warm and in-process, it compiles the benchmark
programs about 5 to 8 times faster than the TypeScript engine
(`engine/rust/results/compile-speed-2026-10-31.md`). Track B is the
story of how it got there, one chapter at a time. Building a language twice, a
tree-walker and then a bytecode VM, and rebuilding it in a lower-level
language, is the shape this book borrowed from *Crafting
Interpreters*<Cite id="nystrom2021" />. Track B takes the same idea one
level further, to the optimizer.
</Callout>

## What you learned

- Track A built two implementations of **Drip**, read **real engines**,
  and built **Viscosity**: parse, lower to **VIR**, analyze, decide,
  generate columns, **explain**, and test differentially.
- One program passes through a dozen chapters on its way to SoA, and
  every step can be named.
- The **measurements** include losses: the VM on two programs, a
  256-constant limit, small wins where every field is read.
- What’s unfinished is known: npm, WebAssembly, refused programs, and
  the cost model.
- **Track B** rebuilds the VM and the compiler in Rust, checked byte
  for byte against Track A’s stored outputs.
