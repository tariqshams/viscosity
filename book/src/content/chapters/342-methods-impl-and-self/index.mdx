## Functions that belong to a type

The last chapter wrote `speed(&p)` as a free function, which works, but
leaves `speed` lying about with every other function in the file, and
the reader has to guess that it is about particles. TypeScript keeps
such functions inside the class, as methods. Rust has methods too, with
a twist that is the whole point of this chapter: every method says, in
its first parameter, what it will do to the value it is called on.

## impl blocks

A TypeScript class (*Classes: a blueprint for objects*) puts the fields
and the methods in one block. Rust splits them: the `struct` holds the
data, and a separate **`impl` block** attaches functions to the type.

<Analogy title="an appliance and its manual">
A washing machine comes with a manual. The machine is the struct: its
parts (drum, door, dial) are its fields. One page of the manual says how
to order a new machine from the maker (you need no machine in hand for
that); the others say what to do with the machine you have ("start a
wash", "read the timer"). The `impl` block is the manual, kept separate
from the machine.
<span slot="breaks">A manual only describes; the functions in an `impl`
block are the behaviour itself, and the compiler checks each against the
struct's fields. A type may also have several `impl` blocks, like a
manual in several booklets.</span>
</Analogy>

```rust
impl Particle {
    fn new(vx: f64, vy: f64) -> Self {
        Particle { x: 0.0, y: 0.0, vx, vy }
    }

    fn speed(&self) -> f64 {
        (self.vx * self.vx
            + self.vy * self.vy).sqrt()
    }
}
```

Every function inside an `impl` block is an **associated function** of
the type. `new` has no `self` parameter, so it is called on the type
itself, with two colons: `Particle::new(3.0, 4.0)` builds a particle at
the origin. Rust has no `new` keyword and no constructors; `new` is only
the usual name for a function that builds a value<Cite id="rust-book-methods" />.
Inside the block, **`Self`** is another name for the type, `Particle`.

`speed` has `self` as its first parameter, the value the function is
called on, so it is also a **method**, called with a dot: `p.speed()`.
It is last chapter's `speed(&p)`, moved inside.

<Callout kind="definition">
An **`impl` block**, `impl Type { ... }`, attaches functions to a type.
All of them are **associated functions**; those whose first parameter is
`self` are also **methods**, called as `value.method(...)`, and the
others are called as `Type::function(...)`. Inside the block, **`Self`**
names the type being implemented.
</Callout>

<Examples of="impl">

```rust
impl Point {
    fn origin() -> Self {
        Point { x: 0.0, y: 0.0 }
    }
}
let o = Point::origin();
```

```rust
let p = Particle::new(3.0, 4.0);
println!("{}", p.speed()); // 5
```

```rust
// from companion/rust/src/chunk.rs
impl Chunk {
    pub fn add_constant(&mut self,
        value: Value) -> usize {
        self.constants.push(value);
        self.constants.len() - 1
    }
}
```

</Examples>

The first is an associated function with no parameters at all: it hands
back the point at the origin, and is called on the type. In the second,
`Particle::new` builds a particle moving 3 across and 4 up, and
`p.speed()` works out the length of that velocity, `5`. The third is
the Rust Drip compiler's constant pool: `add_constant` appends a value
to the chunk's list of constants and returns its index, the number the
bytecode will use to find it (`pub` makes it callable from other files,
which the chapter *Modules, crates and visibility* explains).

Mixing up the two call styles is the usual first slip, and rustc's
message for it is unusually kind:

```rust
let o = p.origin();       // ✗
let o = Point::origin();  // ✓
```

```text
error[E0599]: no method named `origin`
  found for struct `Point` in the
  current scope
14 |     let o = p.origin();
   |               ^^^^^^ this is an
   |     associated function, not a method
help: use associated function syntax
```

## Three kinds of self

JavaScript's `this` is whatever object you called the method on, and the
method may read it, change it or keep it. Rust's `self` is an ordinary
parameter, so its type says exactly which of those the method does, and
there are three choices.

<Analogy title="handing over your car">
A friend who borrows your car for a ride can look but not change
anything; a mechanic borrows it to work on it, and gives it back changed;
a buyer takes it for good, and you never drive it again. That is `&self`,
`&mut self` and `self`, in that order.
<span slot="breaks">A real mechanic might keep the car for a week while
you take the bus; a `&mut self` borrow lasts only for the one call, and
the value is yours again the moment the method returns.</span>
</Analogy>

<ReceiverSteps client:visible />

- **`&self`** borrows the value to read it. Most methods are like this.
- **`&mut self`** borrows it to change it, so the caller's variable needs
  `let mut`.
- **`self`** takes ownership: the value moves into the method, and the
  caller cannot use it afterwards. It is rare, and used when a method
  turns the value into something else<Cite id="rust-book-methods" />.

<Callout kind="definition">
The **self receiver** is a method's first parameter. **`&self`** (short
for `self: &Self`) borrows the value shared, **`&mut self`** borrows it
mutably, and **`self`** takes ownership of it. The rules of the chapter
*The borrowing rules* then apply to every method call.
</Callout>

<Examples of="self-receiver">

```rust
fn speed(&self) -> f64 { /* reads */ }
```

```rust
fn step(&mut self, dt: f64) {
    self.x += self.vx * dt;
    self.y += self.vy * dt;
}
```

```rust
// from companion/rust/src/vm.rs
fn push(&mut self, value: Value)
fn pop(&mut self) -> Value
fn peek(&self, distance: usize) -> Value
```

</Examples>

`speed` only reads, so `&self` is enough. `step` moves the particle
along by its velocity, writing two fields, so it needs `&mut self`. The
third is the Rust Drip VM's stack: `push` and `pop` change the stack, so
they borrow it mutably, while `peek`, which reads the value `distance`
slots below the top, only needs to look. A reader can tell which methods
change the VM from their first line alone.

Each receiver has its own mistake, and rustc names it exactly. Calling a
changing method on a plain `let`:

```text
error[E0596]: cannot borrow `p` as
  mutable, as it is not declared as mutable
21 |     p.step(1.0);
   |     ^ cannot borrow as mutable
help: consider changing this to be mutable
```

writing a field inside a method that took `&self`:

```text
error[E0594]: cannot assign to `self.x`,
  which is behind a `&` reference
help: consider changing this to be a
  mutable reference
14 |     fn reset(&mut self) {
   |               +++
```

and using `p` after a method that took `self`:

```text
error[E0382]: borrow of moved value: `p`
21 |     let q = p.stopped();
   |               --------- `p` moved due
   |               to this method call
note: `Particle::stopped` takes ownership
  of the receiver `self`, which moves `p`
```

## A method call is a function call

You never write the borrow at the call. When Rust looks up a method, it
may borrow the receiver automatically to match the method's
`self`<Cite id="rustref-method-call" />, so `p.step(1.0)` means
`Particle::step(&mut p, 1.0)`:

<Figure takeaway="A method call is an ordinary call with the borrow filled in." caption="Rust adds &, &mut or nothing to match the method's receiver, which is why the borrowing rules apply to method calls although no & is written.">
  <CallSugar />
</Figure>

<Formal title="Method calls, spelled out">

```text
&self:     v.m(a) ≡ T::m(&v, a)
&mut self: v.m(a) ≡ T::m(&mut v, a)
self:      v.m(a) ≡ T::m(v, a)
```

<span slot="read">For a value v of type T: if the method m takes
&self, then v.m(a) means calling T's function m with a shared borrow of
v and the argument a; if it takes &mut self, the call lends v mutably;
and if it takes self, v itself is passed, so it moves. (The sign ≡
reads "means the same as".)</span>
</Formal>

<Run id="particle" />

<OtherLanguages title="A constructor and a method">

```rust
impl Particle {
    fn new(vx: f64, vy: f64) -> Self {
        Particle { x: 0.0, y: 0.0, vx, vy }
    }
    fn step(&mut self, dt: f64) {
        self.x += self.vx * dt;
    }
}
let mut p = Particle::new(3.0, 4.0);
p.step(1.0);
```

```ts
class Particle {
  x = 0; y = 0;
  constructor(
    public vx: number,
    public vy: number,
  ) {}
  step(dt: number) {
    this.x += this.vx * dt;
  }
}
const p = new Particle(3, 4);
p.step(1);
```

</OtherLanguages>

TypeScript keeps fields and methods together and builds values with
`new` and a `constructor`; Rust keeps them apart, and building is an
ordinary function. `this` is there without being asked for, and any
method may change it; Rust's `self` is written as the first parameter,
and `step` must ask for `&mut`, which in turn makes the caller write
`let mut p`. The `const` in the TypeScript only fixes the name; nothing
there says that `step` changes the particle.

## What you learned

- An **`impl`** block attaches associated functions to a type. Those
  with `self` are methods, called with a dot; the rest, like `new`, are
  called with `Type::`. `Self` names the type.
- The **self receiver** says what a method does to the value: `&self`
  reads, `&mut self` changes (and needs a `let mut` caller), `self` takes
  it.
- `p.step(1.0)` is `Particle::step(&mut p, 1.0)`: Rust adds the borrow,
  so every method call obeys the borrowing rules.
