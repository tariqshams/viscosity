## Code for someone else to call

Here is a function that works, compiles cleanly, and is unpleasant to
use:

```rust
pub fn greet(name: &String, loud: bool)
    -> String
```

A caller holding the literal `"Ada"` cannot pass it, because `"Ada"`
is a `&str`, not a `&String`, so they must write
`greet(&"Ada".to_string(), true)`; and anyone reading that line must
look up what `true` means. Nothing is *wrong*, so the compiler is
happy. An **API** (application programming interface: the names,
types and promises a library shows its users) is judged by the people
who call it, and Rust's community has written its taste down as the **Rust API Guidelines**, a checklist with codes like
C-CONV and C-GETTER<Cite id="api-guidelines" />.

<Analogy title="labelled kitchen drawers">
In a kitchen where cutlery is always in the top drawer by the sink,
you can cook in a friend's house without asking. The guidelines are
that habit for libraries: `as_` and `to_` and `into_` mean the same
cost in every crate, so you can guess the method before reading the
docs.
<span slot="breaks">A friend's odd kitchen only costs you a minute.
An API's odd choice is copied into every program that uses it, and
cannot be changed later without breaking them all, which is why it is
worth getting right before release.</span>
</Analogy>

<Analogy title="a door that shows how it opens">
A flat plate says "push", a handle says "pull"; good doors need no
sign. A good signature is the same: `greet("Ada", Volume::Loud)`
cannot be misread, where `greet("Ada", true)` needs a sign.
<span slot="breaks">A badly designed door still opens with some
fumbling. A Rust type can make the wrong use refuse to *compile*,
which no door can do for the person standing in front of it.</span>
</Analogy>

## The guidelines in practice

Step through `greet` being improved, one guideline at a time:

<ApiSteps client:visible />

<Examples of="api-design">

```rust
// C-CONV: the prefix says the cost
s.as_bytes()    // free view: &str → &[u8]
s.to_string()   // copies: &str → String
s.into_bytes()  // consumes: String → Vec
```

```rust
// C-GETTER: no get_ prefix
impl Celsius {
    pub fn degrees(&self) -> f64 {
        self.0
    }
}
```

```rust
// C-COMMON-TRAITS, C-CUSTOM-TYPE
#[non_exhaustive]
#[derive(Debug, Clone, Copy,
         PartialEq, Eq, Hash)]
pub enum Volume { Quiet, Loud }
```

<Run id="greet" />

</Examples>

The first is naming conversions (C-CONV): **`as_`** is free and
borrowed to borrowed, **`to_`** is expensive (it usually allocates),
and **`into_`** consumes its owner and gives back another owned
value<Cite id="api-guidelines" />. These three methods on `str` and
`String` follow it exactly. The second is a getter (C-GETTER): it is
called `degrees`, not `get_degrees`, because "the `get_` prefix is not
used for getters in Rust code", with exceptions such as `Cell::get`
where there is one obvious thing to get<Cite id="api-guidelines" />.
The third is an argument type with meaning (C-CUSTOM-TYPE: an enum,
not a `bool`) that eagerly derives the common traits (C-COMMON-TRAITS),
and the runnable one puts it to work in the finished `greet`, with the
three conversions on a real `String`.
That one matters more than it looks: Rust's *orphan rule* says an
`impl` must live in the crate of the trait or of the type, so if your
crate does not implement `Debug` or `Hash` for `Volume`, nobody else
can<Cite id="api-guidelines" />.

The guidelines also say how to leave room to change. Fields should be
private (C-STRUCT-PRIVATE), since a public field "prevents the type
from providing any validation or maintaining any
invariants"<Cite id="api-guidelines" />. And **`#[non_exhaustive]`**
on an enum tells other crates that variants may be added later, so
their `match` must have a `_` arm<Cite id="rustref-non-exhaustive" />.
In a scratch crate, a `match` on `Volume` from another crate without
one failed with rustc 1.97's error E0004, "non-exhaustive patterns:
`_` not covered", noting that "`Volume` is marked as non-exhaustive,
so a wildcard `_` is necessary". That error is the point: adding
`Whisper` in version 1.1 will not break anyone, because nobody could
write a `match` that assumed there were only two.

```python
    ...
```

</OtherLanguages>

TypeScript reaches the same goal with a union of string literals, which
costs nothing at run time and reads well at the call site; Python's
type hints are only advice unless a checker runs. Rust's enum is
checked by the compiler, matched exhaustively, and (thanks to
`non_exhaustive`) can grow without breaking callers.

<Callout kind="definition">
**API design** is choosing the names, types and promises a crate
exposes so that it is easy to use correctly, hard to misuse and possible
to change. The **Rust API Guidelines** record the community's
conventions: conversions named `as_`, `to_`, `into_`; getters without
`get_`; the common traits implemented eagerly; meaningful argument
types; private fields; and docs with examples<Cite id="api-guidelines" />.
</Callout>

## Cargo features

A crate often has parts not every user wants: support for a file
format, an optional dependency, a `std`-free mode. Cargo **features**
let users switch them on. A feature is a name in `Cargo.toml`, and code
can be compiled only when it is on, with `#[cfg(feature = "...")]`.
A scratch crate, `temps`:

<Examples of="cargo-features">

```toml
[features]
default = ["fahrenheit"]
fahrenheit = []
kelvin = []
```

```rust
#[cfg(feature = "kelvin")]
pub fn to_k(self) -> f64 {
    self.0 + 273.15
}
```

```toml
[dependencies]
serde = { version = "1",
          optional = true }
[features]
serde = ["dep:serde"]
```

</Examples>

The first declares two features, each enabling nothing else (`[]`),
and `default` lists the ones that are on unless a user says otherwise.
The second compiles `to_k` only when `kelvin` is on; otherwise the
method does not exist at all, so a user's `Celsius(20.0).to_k()` gets
rustc 1.97's error E0599, "no method named `to_k` found for struct
`Celsius`". With `cargo run --features kelvin` the same program
printed `293.15`. The third, in the style of the Cargo book, makes a
dependency optional: it is not even downloaded unless the `serde`
feature is on, and `dep:serde` names the dependency rather than a
feature<Cite id="cargo-features" />. `--no-default-features` turns
`default` off, and `--features a,b` turns features on.

<Figure takeaway="A dependency is built once, with the union of every feature anyone asked for." caption="Two crates in one build ask for different features of temps; Cargo compiles a single temps with both.">
  <FeatureUnion />
</Figure>

The figure shows the rule that shapes everything else: when several
packages in one build depend on the same crate, "Cargo will use the
union of all features enabled on that dependency"<Cite id="cargo-features" />,
so there is one copy of it. A feature therefore cannot *remove*
anything, because some other crate in the build may be relying on it:
features must be **additive**, and "it should usually be safe to enable
any combination of features"<Cite id="cargo-features" />. That is why
the Cargo book advises a feature named `std`, which adds the standard
library, rather than one named `no_std`, which would take it
away<Cite id="cargo-features" />.

<Formal title="Feature unification">

```text
enabled(d)  =  ⋃  requested(p, d)
             p ∈ dependents(d)
```

<span slot="read">The features a dependency d is built with are the
union, over every package p in the build that depends on d, of the
features p requested for d.</span>
</Formal>

<Callout kind="definition">
A **Cargo feature** is a named, optional part of a crate, declared in
the `[features]` table of `Cargo.toml`. It can enable other features
and optional dependencies (`dep:name`), and code can test it with
`cfg(feature = "name")`. The `default` feature lists what is on unless
a user passes `--no-default-features`. Because Cargo builds each
dependency once with the union of all requested features, features
should be additive<Cite id="cargo-features" />.
</Callout>

## What you learned

- **API design** in Rust follows the API Guidelines: `as_`, `to_`,
  `into_` say what a conversion costs; getters drop `get_`; types
  derive the common traits, because nobody else can add them later.
- Enums say what `bool`s cannot, private fields keep invariants, and
  `#[non_exhaustive]` leaves room to add variants.
- **Cargo features** switch optional code and dependencies on; one
  build unifies them, so they must only ever add.
