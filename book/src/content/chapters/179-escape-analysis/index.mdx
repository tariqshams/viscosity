## Escaping

Picture a value as having an inside and an outside. Inside is the code the
compiler is looking at and can rewrite. A value **escapes** when a
reference to it reaches somewhere outside: a function the compiler can't
see into, a variable or property that someone else reads, the caller.

```js
function f(ps) {
  const p = ps[0];
  let s = p.x + p.vx; // stays inside
  log(p);             // escapes: a call
  return p;           // escapes: a return
}
```

<Callout kind="definition">
**Escape analysis** decides whether a reference can leave a region of
code. If it can't, the compiler controls every use of the object and may
change how it is stored, or not store it at all. The places where a value
can leave are its **escape sites**: passing it to a call, storing it into
a variable, property or array, and returning it. The analysis is
conservative: “might escape” counts as “escapes”.
</Callout>

## Tracing the uses

Viscosity works on its SSA IR, where every value has a list of the
instructions that use it. To check a collection it starts from every load
of the array and walks those lists. Some uses are fine because Viscosity
knows how to rewrite them: `push` of a fresh object literal, `.length`,
and `ps[i]`. But `ps[i]` produces a new value, the element, so its uses
must be walked too. Step through it:

<EscapeSteps client:visible />

This is a worklist again, like the dataflow chapters: values to check go
in, and checking one can add more. Here is the element part, from
`packages/core/src/analysis.ts`, simplified:

```ts
for (const u of usesOf(el)) {
  const i = u.inst;
  const onEl = i && i.args[0] === el;
  if (onEl && i.op === 'field.get') {
    accesses.push(read(i));
    continue;
  }
  if (onEl && i.op === 'field.set') {
    accesses.push(write(i));
    continue;
  }
  bailouts.push(
    'an element is ' + describeUse(u));
}
```

Notice `onEl`. `ps[i].x = 5` and `box.last = ps[i]` are both `field.set`.
In the first, the element is the object being written to, which is fine.
In the second, it is the *value* being stored, so it escapes into `box`.

## Naming the escape site

A bailout that only said "unsafe" would be useless. `describeUse` turns
each escaping use into a reason a person can act on. Simplified, with the
line numbers left out:

```ts
switch (i.op) {
  case 'call':
    return 'passed to a function call';
  case 'storeBinding':
    return 'stored in another variable';
  case 'field.set':
    return 'stored into an object property';
  case 'index.set':
    return 'stored into an array';
  case 'record.new':
    return 'put inside another object';
  case 'binop':
    return 'compared or combined';
  case 'opaque':
    return 'used by code Viscosity ' +
      "doesn't model";
  case 'phi':
    return 'merged with other values';
}
```

Returns don't appear here, because a return is a block terminator rather
than an instruction; it gets its own message, "returned or branched on".
Here is what `viscosity explain` really prints for three small changes to
the program in the diagram:

```
// return ps[0] from a function
· unsafe: line 5: an element is
  returned or branched on in first()

// box.last = ps[99];
· unsafe: line 7: an element is stored
  into an object property

// console.log(ps[1] === ps[2]);
· unsafe: line 6: an element is compared
  or combined with "==="
```

The comparison is the subtle one. Nothing is stored anywhere, but `===`
asks about identity, and after the rewrite there are no element objects
to be identical. Two more sites are there for safety. `opaque` is the IR's
name for anything Viscosity doesn't model, so every argument must be
assumed to escape. A `phi` merges an element with other values, as in
`best = ps[i]` inside an `if`. Viscosity doesn't track what flows out of
a merge, so it counts the merge itself as an escape.

## Calls that aren't escapes

A call is usually an escape, but not always. If `step(qs)` is a function
declared once and only ever called directly, Viscosity knows every call
site. When all of them pass `ps`, the parameter `qs` *is* `ps`, so it
joins the worklist and its uses are checked inside `step`:

```
ps (line 1) {x, vx} → struct of arrays
  · loop at line 5 in step() touches
    2 of 2 fields (x, vx)
```

That is points-to reasoning from chapter 177 on a small scale: `qs` points
to exactly one collection. Passing an *element* to a function, as in
`move(ps[i])`, is still reported as an escape today. Try it, and then try
removing the escape:

<Callout kind="engine" label="Under the hood">
V8 and Viscosity ask the same question at different times. V8 compiles
optimized code while the program runs, specialized for what it has seen,
and can deoptimize if a guess turns out wrong<Cite id="v8-maglev" />. In
this book's run it inlined `consume(p)`, after which `p` was used only by
field reads, and the temporary object was removed. That is why
`get-objects` didn't lose. Nothing can do the same for `materialize`,
because its objects really are stored and kept. Viscosity runs before the
program does, has no deoptimization to fall back on, and doesn't inline.
So it must prove safety on the code as written, which makes it stricter
than V8: `move(ps[i])` keeps the array of objects.
</Callout>

## What you learned

- **Escape analysis** decides whether a reference can leave a region of
  code. If it can't, the compiler may change how the object is stored.
- The **escape sites** are calls, stores into variables, properties,
  arrays or other objects, and returns. Viscosity also counts identity
  comparisons, unmodelled (`opaque`) operations and phis.
- Checking is a worklist over def-use lists: an element produced by
  `ps[i]` adds its own uses to the list.
- Position matters: an element being *written to* is safe; an element
  being *stored* escapes.
- A known function whose every call passes the same collection is
  followed, not counted as an escape.
- V8 escapes less because it inlines first and can deoptimize. Viscosity
  must prove safety ahead of time, so it is more conservative.
