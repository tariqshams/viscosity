## A frame you can't hold

Chapter 83 gave the TypeScript VM call frames. Each one is a small
object, and the loop keeps the running one in a local variable:

```ts
interface CallFrame {
  closure: ObjClosure;
  ip: number; slots: number;
}
// in run(): hold the top frame
let frame =
  this.frames[this.frames.length - 1];
case OP.CALL: // ...
  this.callValue(
    this.peek(argCount), argCount);
  reload(); // frame = the new top
```

`frame` is a reference to an object in the array, so `frame.ip++`
updates the frame itself. Here is the same shape on a toy Rust VM:

```rust
let frame = self.frames.last_mut()
    .unwrap();
frame.ip += 1;
self.call(0);
frame.ip += 1;
```

rustc 1.97 (trimmed):

```
error[E0499]: cannot borrow `*self` as
  mutable more than once at a time
13 | let frame = self.frames.last_mut()...
   |             ----------- first mutable
   |                borrow occurs here
15 | self.call(0);
   | ^^^^ second mutable borrow occurs here
16 | frame.ip += 1;
   | ------------- first borrow later used
```

`call` pushes onto `self.frames`, the very `Vec` that `frame` points
into. A push can reallocate the `Vec` and move every frame in it
<Cite id="rust-std-vec" />, so the borrow checker is right to refuse.
Chapter 236 showed drip-rs's answer: the running frame's `ip`, chunk and
stack base live in fields of the `Vm`, the registers. This chapter is
about the frames behind them.

## The frames are a Vec

Adapted from `src/vm.rs`:

```rust
struct CallFrame {
    closure: Gc<ObjClosure>,
    chunk: Rc<Chunk>,
    ip: usize,
    slots: usize,
}

```

Three differences from TypeScript. The closure is a handle, not a
reference. The frame carries its function's chunk, an `Rc` clone: this
is where the README's one `Rc` gets used. When `fib` has called itself
20 deep, 20 frames hold clones of one chunk, and each clone only bumps a
count
<Cite id="rust-std-rc" />. And `ip` in a frame is meaningful only while
the frame is paused. `Vm::new` reserves room with
`Vec::with_capacity(FRAMES_MAX)`, so the frame `Vec` never reallocates.
`self.stack.len()` plays the part of TypeScript's `sp`.

## Call: save, push, load

Adapted from `call`, after its two checks: a wrong argument count, and
`frames.len() == FRAMES_MAX` (64), which is `"Stack overflow."`.

```rust
fn call(&mut self, closure: Gc<ObjClosure>,
        argc: usize) -> Run {
    // ...checks. Save the caller's ip:
    let caller = self.frames.last_mut();
    if let Some(caller) = caller {
        caller.ip = self.ip;
    }
    // Push the callee, then load it.
    let func = self.heap[closure].function;
    let chunk = Rc::clone(
        &self.heap[func].chunk);
    let slots = self.stack.len() - argc - 1;
    self.frames.push(CallFrame {
        closure, ip: 0, slots,
        chunk: Rc::clone(&chunk) });
    self.ip = 0;
    self.chunk = chunk;
    self.slots = slots;
    Ok(())
}
```

`caller` borrows `self.frames` while `self.ip` is read. They are
different fields, so that's allowed. `slots` points at the callee
itself: slot 0 of every frame holds the closure being called, and the
arguments follow it. Because `call` loads the registers itself, the
`Call` arm is one line, `self.call_value(self.peek(argc), argc)?`, with
no `reload`.

<Callout kind="definition">
drip-rs's **frame stack** is `frames: Vec<CallFrame>`, one entry per
call in progress, innermost last. A frame holds its closure's handle,
an `Rc` clone of its chunk, a saved `ip`, and `slots`, the stack index
of its slot 0. The running frame is `frames.last()`, but its live `ip`,
chunk and base are in the VM's registers. `call` saves the caller's `ip`
and loads the callee; `pop_frame` loads the caller back.
</Callout>

## Return: pop, restore, truncate

The `Return` arm, adapted:

```rust
OpCode::Return => {
    let result = self.pop();
    self.close_upvalues(self.slots);
    let Some(frame) = self.pop_frame()
    else {
        self.pop(); // the script's closure
        return Ok(());
    };
    self.stack.truncate(frame.slots);
    self.push(result);
}
```

`pop_frame` takes the top frame out of the `Vec` by value, copies the
caller's `ip`, chunk and slots into the registers, and returns
`Some(frame)`. With no caller it returns `None`, and that is how `run`
knows the script has finished, where TypeScript checks
`frames.length === 0`. `truncate(frame.slots)` drops the callee and its
arguments and locals in one step. When `frame` goes out of scope, its
`Rc<Chunk>` clone is dropped with it. `close_upvalues` is chapter 244.

## Natives and stack traces

`call_value` matches on the callee's `Value`. A closure goes to `call`.
Classes and bound methods come in chapters 246 and 247. A native is
called right there:

```rust
Value::Native(native) => {
    let ObjNative { arity, function } =
        self.heap[native]; // ...check arity
    let start = self.stack.len() - argc;
    let result =
        function(&self.stack[start..]);
    self.stack.truncate(start - 1);
    self.push(result);
    Ok(())
}
```

`function` is a `NativeFn`, a plain function pointer,
`fn(&[Value]) -> Value` <Cite id="rustref-fn-pointer" />. It gets the
arguments as a slice of the stack, borrowed, where TypeScript's
`this.stack.slice(...)` copies them into a new array.

The stack trace is where the stale `ip` matters. `runtime_error` walks
the frames innermost first, and for the top frame it must read the
register:

```rust
let top = self.frames.len()
    .saturating_sub(1);
for (depth, frame) in
    self.frames.iter().enumerate().rev()
{
    let ip = if depth == top { self.ip }
             else { frame.ip };
    let line = frame.chunk.lines[ip - 1];
    // "[line {line}] in f()" or "script"
}
```

On `fn f() { return -nil; } fn g() { f(); } g();`, spread over five
lines, drip-rs prints `Operand must be a number.`, then
`[line 2] in f()`, `[line 4] in g()`, `[line 5] in script`, as the
TypeScript VM does.

<Callout kind="engine" label="Under the hood">
The frames are also garbage collection roots. `VmRoots` traces each
frame's `closure` handle, which keeps the function and its constants
alive. The `Rc<Chunk>` needs no tracing: Rust frees the chunk's bytes
when its last clone goes, and the function object, the chunk's other
owner, stays alive as long as any frame runs it. In the committed
benchmark run, `fib.drip`, which is almost nothing but calls and
returns, took 1460 ms on drip-rs and 5685 ms on the TypeScript VM.
Chapter 253 compares all the programs.

## What you learned

- drip-rs keeps **a `Vec` of call frames**. Each `CallFrame` has a
  closure handle, an `Rc<Chunk>` clone, a saved `ip` and `slots`.
- The loop can't hold `&mut CallFrame` across a call, so the running
  frame's state lives in **registers**. `call` saves the caller's `ip`,
  pushes the callee and loads it; `pop_frame` loads the caller back.
- A running frame's own `ip` field is **stale**. The stack trace reads
  the register for the top frame.
- `pop_frame` returns **`Option<CallFrame>`**: `None` means the script
  ended. `truncate(frame.slots)` drops the callee's slots.
- Natives get their arguments as a **borrowed slice** of the stack.
