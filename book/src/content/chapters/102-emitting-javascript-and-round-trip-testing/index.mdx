## Back to JavaScript

You have VIR, the analyses have run, and the plan says: store `ps` as a
struct of arrays. The program still has to *run*, so the plugin must
produce JavaScript again, and that last step of every compiler has a
name.

<Callout kind="definition">
**Code generation** (codegen) turns the compiler's internal form back
into output text: machine code for a native compiler, bytecode for a
virtual machine, or source code for a source-to-source compiler like
Viscosity.
</Callout>

The obvious way is to *print* text for every node of a tree, as in the
chapter *Syntax trees and a tree printer*; however, the tree does not
remember the line breaks, the spacing or where the comments sat, so a
printer must decide all of that again.

<Callout kind="definition">
**Pretty-printing** is emitting code from a tree in a readable,
consistently formatted style: chosen indentation, line breaks and
brackets. It is how code formatters work, and it throws away the
original layout. **Splicing** instead replaces only the changed ranges
of the original text and copies everything else.
</Callout>

<Analogy title="retyping a letter, or correction fluid">
To fix one word in a typed letter you can retype the whole page, which
changes every line break and probably a few spaces too, or you can dab
correction fluid on that one word and type over it, and the rest of the
page stays exactly as it was. A pretty-printer retypes; Viscosity uses
correction fluid.
<span slot="breaks">Correction fluid only works if the new word fits in
the old space; a splice can replace two characters with twenty, because
text in a computer moves aside to make room.</span>
</Analogy>

<Analogy extra title="restoring a painting">
A restorer repairs a damaged corner of an old painting and leaves every
other brushstroke alone, rather than repainting the whole canvas in her
own style, because the owner wants *their* painting back, with only the
damage fixed.
<span slot="breaks">A restorer's job is to make the repair invisible;
Viscosity's edits are meant to be read, and each changed line looks
plainly different (`ps.x[p]` rather than `p.x`).</span>
</Analogy>

</Figure>

Viscosity splices, so your comments, blank lines and odd spacing survive
because nothing ever re-prints them (even the generated container class
at the top is built from template strings, one method per line).

<Examples of="codegen pretty-printing">

```js
let x=1+2   // as typed
let x = 1 + 2; // pretty-printed
ps.push({ x: i, vx: 1 }) // as typed
ps.push(i, 1) // spliced by Viscosity
```

</Examples>

The first two lines are pretty-printing as a formatter does it: the tree
is the same either way, and the printer chooses its own spaces and adds
a semicolon. The last two are Viscosity's code generation, from its real
output: only the object literal was rewritten (its values became
arguments of the generated `push`), while `ps.push(` and the closing
bracket are your own characters, untouched.

## Edits, applied back to front

An edit is a range of the original text and the text to put there
instead, `{ start, end, text }`. The offsets come from lowering, where
every instruction got a `src` (the ESTree node, with its `start` and
`end`), so the emitter can go from each instruction it needs to change
straight back to the exact characters. Here is a real program and its real output from
`viscosity build`, without the generated class (the last line is one
line in the real output):

```js
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i, vx: 1 });
for (const p of ps) p.x += p.vx;
```

```js
const ps = new __Vsc_ps();
for (let i = 0; i < 100; i++)
  ps.push(i, 1);
for (let p = 0; p < ps.length; p++)
  ps.x[p] += ps.vx[p];
```

Notice the trick with elements: the for-of header now counts, so `p`
holds an *index* instead of an object, and `p.x` becomes `ps.x[p]`.
Applying the edits is a short loop at the end of `emitJs` (trimmed):

```ts
edits.sort((x, y) => y.start - x.start
  || y.end - x.end || …);
let out = source;
let lastStart = Infinity;
for (const e of edits) {
  if (e.end > lastStart) throw new Error(
    `internal error: overlapping ` +
    `rewrites at ${e.start}-${e.end}`);
  out = out.slice(0, e.start) + e.text
    + out.slice(e.end);
  lastStart = e.start;
}
```

Edits are sorted by start offset, **last first**. Replacing `[]` with
`new __Vsc_ps()` adds 12 characters and would push every later offset
out of place; working from the end, each edit only shifts text that has
already been handled. Step through the seven real edits for the program
above (the push is rewritten in three small edits around its values):

Two edits that overlap would mean two parts of the emitter want to
rewrite the same characters; no order of applying them can be right, so
the emitter refuses with an internal error rather than produce broken
code.

<Formal title="Splicing disjoint edits">

```text
edits e₁ … eₙ sorted by start, with
  eₖ.end ≤ eₖ₊₁.start   (no overlap)
out = s[0, e₁.start) + e₁.text
    + s[e₁.end, e₂.start) + e₂.text
    + … + eₙ.text + s[eₙ.end, |s|)
```

<span slot="read">Sort the edits from first to last in the source; no
edit may end after the next one starts. Then the output is the source up
to the first edit, the first edit's text, the source between the first
and second edits, the second edit's text, and so on, ending with the
source after the last edit (|s| is the length of s). Applying them back
to front builds exactly this.</span>
</Formal>

<More title="The full edit table, one member with two edits, and the prelude">

For a collection planned as SoA, `emit.ts` makes these edits:

```
const ps = []    →  new __Vsc_ps()
ps.push({x:a,y:b})  →  ps.push(a, b)
ps[i].x          →  ps.x[i]
const p = ps[i]  →  const p = i
p.x              →  ps.x[p]
for (const p of ps)
  → for (let p = 0; p < ps.length; p++)
```

`p.x += p.vx` both reads and writes `p.x`: lowering made a `field.get`
*and* a `field.set` for it, and both point at the same source range. So
field edits are collected in a map keyed by range, and one survives:

```ts
const fieldEdit = (e, kind) => {
  const k = `${e.start}:${e.end}`;
  const prev = fieldEdits.get(k);
  const rank = kind === 'write' ? 0
    : kind === 'read' ? 1 : 2;
  if (!prev || rank > prev.kind)
    fieldEdits.set(k, { ...e, kind: rank });
};
```

A read beats a write, because JavaScript reads `p.x` before it writes
it, so out of bounds, `ps[k].x += 1` must throw "Cannot read properties
of undefined (reading 'x')", in the original and the compiled code alike.
The third kind, `late`, is for a write whose right side may run code,
such as `p.x = Math.sqrt(f(p.vx))`, where calling `f` could even grow the
columns. The real output is
`__vsc_set(ps, 'x', p, Math.sqrt(f(ps.vx[p])), 'x')`: a helper that
stores only after the right side has run, into the column as it is by
then, just as the original assigns after evaluating its right side; it
covers the read too, so it wins over both.

The rewritten code needs the container class, so the class goes in
front, followed by a bounds-check helper if any element access is not
proven in bounds (it throws the same `TypeError` message the original
would have). It does not always go at offset 0: a `"use strict"`
directive only counts if it comes first in the
script<Cite id="mdn-strict-mode" />, so putting a class above it would
quietly turn strict mode off. The emitter matches an optional shebang
line and an optional directive with a regular expression, and inserts
the prelude after them.

The runnable version applies the push's three real edits back to front;
try sorting them front to back instead and see the text come out
garbled.

Splicing depends on the parser recording offsets: acorn stores the start
and end character offsets of every node in `start` and
`end`<Cite id="acorn" />, and those flow into VIR's `src`. The same idea,
keeping the original text wherever nothing changed, is what Recast calls
a nondestructive pretty-printer: it reprints only the parts of the tree
you modify<Cite id="recast" />. Viscosity goes further, since it never
builds new tree nodes at all, only text edits.

</More>

## Nothing to do

Most of the code in a real project has no arrays of same-shaped objects
in it at all, yet Viscosity still runs over every one of those files on
every build, and for them the only correct output is the file itself,
unchanged (not reformatted, and not with a comment moved or a stray
blank line added); a compiler that quietly smudges the easy files is a
compiler nobody will leave switched on.

<Analogy extra title="a proofreader and a clean page">
Hand a good proofreader a page with no mistakes on it, and it comes
back untouched. If it came back with one comma moved, you would stop
trusting them, even on the pages that really did need fixing, because
you could no longer tell their corrections from their accidents.
<span slot="breaks">A proofreader may fairly improve a clumsy sentence
that has no mistake in it; Viscosity is not allowed to "improve"
anything, not even the spacing, because its job is layout, not
style.</span>
</Analogy>

<Callout kind="definition">
An **identity transform** is a compile that must change nothing: for
an input with nothing to transform, the output equals the input. For a
source-to-source compiler that splices its edits into the original
text, "equals" can mean **byte for byte**. It is the simplest
round-trip test there is, because the input is its own expected
output.
</Callout>

The chapter *Testing compilers: differential, round-trip, fuzzing and
shrinking* showed the round trip for a printer: parse, print, parse
again, and compare the two trees. The trees may match while the text
differs, because the tree does not keep everything (comments, blank
lines, which quotes you used). A splicer with an empty edit list has
nothing to splice, so it can promise more:

<Figure takeaway="A printer can only promise the same tree; a splicer with no edits can promise the same bytes." caption="The same three lines through two round trips. The printer rebuilds the text from the tree, so the comment, the blank line and the single quotes are gone; Viscosity, with no edits, hands back its input.">

</Figure>

<Formal title="Two round trips">

```text
printer:  parse(print(parse(s))) = parse(s)
splicer:  plan(s) = ∅  ⇒  compile(s) = s
```

<span slot="read">For a printer, the promise is about trees: parsing
the printed text gives back the tree you started from. For Viscosity it
is about text: whenever the plan for s is empty (it decides to change
nothing), compiling s gives exactly s, character for character. The
second promise is stronger, since equal text always parses to equal
trees, but equal trees can come from different text.</span>
</Formal>

<Examples of="identity-transform">

```ts
it('leaves programs with nothing to ' +
   'transform byte-identical', () => {
  const src =
    'const a = [1, 2, 3];\n' +
    '// a comment\n' +
    'console.log(a.length);\n';
  expect(compile(src, jsPlugin()).code)
    .toBe(src);
});
```

</Examples>

This is the identity test in
`packages/frontend-js/test/differential.test.ts` (its name is one string
there, split here to fit). `src` is a 57-byte program, and `toBe`
compares the compiled code with it as two strings, so every byte has to
match. It looks almost too small to matter; however, `compile` runs the
whole pipeline on it, from parsing to the analyses (which look at `a`
and reject it, since its elements are numbers, not object literals) to
an emitter with no edits and no prelude. The array makes the collection
analysis really run, and the comment and the final newline are exactly
what a printer would lose.

<More title="Two more identity cases, and 515 files of other people's code">

A TypeScript file is the one exception: it goes through the plugin's
type stripper before it is parsed, so with nothing to transform it comes
back as the same code with its types removed (`const n: number = 3; //
keep me` becomes `const n = 3; // keep me`). The realistic case is
`no_loops.js` from the differential corpus: `ps` really is an array of
records, so it gets analysed in full, but no loop ever touches its
fields, so the planner keeps it as it is and the whole file round-trips.
Of the 40 corpus files, 16 keep every collection as an array of objects,
and all 16 come back byte-identical, although nothing in that suite
checks it.

The identity check needs no expected output, so it scales for nothing:
any JavaScript file at all is a test case, and its own text is the
answer. Run over every `.js` and `.mjs` file of the 59 third-party
packages in the engine's `node_modules` folder, 515 files, all 515 come
back byte-identical. That clean result is the second run: the first
time, 17 of those files crashed the compiler, every one containing
`export default class`:

```js
export class A {}         // fine
export default class A {} // crashed:
// TypeError: Cannot read properties of
// undefined (reading 'owner')
```

The resolver declared the names in `export` declarations, but not in
`export default` ones, so the lowering asked for the binding of `A` and
got `undefined`. The corpus is about arrays and loops, and none of its
files had a default export, so no existing test could see it; the fix
was one condition in `resolve.ts` (look inside an `export default`
statement for its declaration too), and a round-trip test for it joined
the suite. Finding the bug took a test with no expected output and a
pile of code nobody on the project had written, which is the corpus
idea behind *End to end: benchmarks and differential testing at scale*,
and the reason random program generators like Csmith exist: to produce
inputs no test author would think of<Cite id="csmith" />.

</More>

## Three checks, one front-end

The front-end package has three kinds of test: the round trip guards "do not touch what
you do not change", the differential test guards "change it without
changing what it does", and parser equivalence guards "the tree is the
tree, whichever parser built it". Step through them:

<FrontEndSteps client:visible />

The differential test runs the original and the compiled program each
in a brand-new `vm` context, whose global object is a fresh one with its
own built-ins<Cite id="node-vm" />, so neither run can see what the other
left behind (Node's documentation warns that `vm` is not a security
mechanism; here it only keeps two runs apart). The outcome it records is
the list of printed lines **and** the uncaught error, if any, because a
compiled program that prints the same lines but no longer throws has
still changed what it does.

```text
$ npx vitest run packages/frontend-js

 ✓ differential.test.ts (42 tests)
      Tests  89 passed (89)
```

The 42 are the 40 corpus files plus two round-trip tests (the snippet
above, and the `export default` cases); the 47 are those 40 files and
the 5 benchmark programs through both parsers, plus 2 tests of the
hand-written parser on its own.

## What you learned

- **Code generation** turns the IR back into output; for a
  source-to-source compiler, that output is source code.
- **Pretty-printing** writes code from a tree in a chosen style and
  loses the original layout; Viscosity **splices** range edits into the
  original text instead, **back to front**, and treats overlapping edits
  as an internal error.
- An **identity transform** must change nothing; Viscosity checks it
  **byte for byte**, which only a splicing emitter can promise.
- The front-end has three checks: the round trip, the differential
  corpus (fresh `vm` contexts, printed lines and errors), and acorn
  against the hand-written parser.
