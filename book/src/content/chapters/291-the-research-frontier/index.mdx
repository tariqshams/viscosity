## Where the edge is

Take a perfectly ordinary program: make 1,000 particles, sort them by
`x`, then update them in a loop. Ask Viscosity about it:

```text
ps (line 1) {x, y} → kept as array of
  objects
  · unsafe: line 4: uses .sort on the
    array (only .length and .push are
    supported)
  · unsafe: the array is passed to a
    method call at line 4
```

No speed-up. Swap two elements by hand instead of sorting, and it
refuses again; use a class instead of object literals, export the
array, or give half the records an extra field, and you get the same
answer. Viscosity is careful, and careful means it says no a lot. Every
one of those refusals marks an edge of what it can do; however, they
are not all the same kind of edge.

<Analogy title="gaps on a library shelf">
A library's catalogue lists some books it does not have. Some are
missing because nobody has ordered them yet: they exist, and money and
time will fill the gap. Others are missing because nobody has written
them: no amount of ordering will help until somebody does the writing.
From the empty shelf, both look exactly the same.
<span slot="breaks">A library knows which books exist. In compilers you
often cannot tell which kind of gap you are looking at until you try,
and a new engine version or language feature can move a case from one
kind to the other.</span>
</Analogy>

<Analogy title="a doctor's list of untreated conditions">
Some conditions on the list have a known treatment that this clinic
does not offer yet; it needs equipment and training, not a
discovery. Others have no known cure anywhere, and what they need is
research.
<span slot="breaks">Medicine has agreed ways to test a new treatment.
For a compiler question, part of the work is often inventing the test
itself: a corpus of programs, or a benchmark nobody had thought to
measure.</span>
</Analogy>

## Gaps and open problems

The class case is a **gap**. Recognising that `new P(i)` builds an
object with fields `x` and `vx`, in that order, is known technique;
someone has to write the lowering, the shape inference and the tests.
The others need more than work. Sorting needs every column permuted in
step, plus a comparator that receives objects that no longer exist.
Varying shapes need either many layouts or a way to say "this field is
sometimes missing" in a column. Exported arrays need an analysis of
code in other files, some of which may never be shown to the compiler.

<Callout kind="definition">
An **open problem** is a question in a field that nobody has a
satisfying general answer to yet, as opposed to an **engineering gap**,
where the technique is known and only the work is missing. Telling them
apart matters: a gap needs time, an open problem needs an idea, and
often a new kind of evidence.
</Callout>

<Examples of="open-problems">

```js
for (const { x } of ps) s += x;
// unsafe: line 5: an element is used by
//   code Viscosity doesn't model
//   (destructuring)
```

```js
const t = ps[0];
ps[0] = ps[1];
ps[1] = t;
// unsafe: the array is written with an
//   index store at line 6 (+ 3 more)
```

```js
ps.push({ pos: { x: i, y: 0 }, m: 1 });
// → struct of arrays
// · typed Float64Array columns for m;
//   plain array columns for pos
```

</Examples>

Sort each one. The first is a gap: `for (const { x } of ps)` reads one
field, exactly like `p.x`, and teaching the lowering to see that is a
known kind of rewrite. The second, a hand-written swap, looks just as
small, but it is the reordering problem in miniature: an element is
read out, a slot is overwritten, and the record is stored somewhere
else, so to keep columns Viscosity would have to move every column's
slot together and prove that no other name still expects the old
object. The third is the nested record from the stepper, transformed
but only half won: making `pos` a column of its own is what the
run-time research did with nested objects, and doing it ahead of time,
with proof, is open.

Try one edge yourself. This program is refused because half its
records have a `tag`. Give every record a `tag` (an empty string will
do) and watch the verdict change:

## Problem one: proof or speculation

Viscosity runs before the program, so it must *prove* that nobody can
tell the difference; a JIT runs during the program, so it can *guess*,
check its guess, and recover.

<Figure takeaway="Ahead of time you must be right; at run time you only need a way back." caption="The two ways to change a layout. The open question is the bottom-right box for the top lane: a cheap way back for an ahead-of-time tool.">
  <ProofOrGuess />
</Figure>

That is exactly the split in the research this book started from. As
*Columnar arrays at run time: the research* describes (from the papers'
abstracts, since the full texts could not be reached; that honesty
still applies here), Makor and colleagues turned arrays of objects into
columns at run time inside GraalJS, paying for the conversion and
earning it back on later accesses<Cite id="makor2022" />, and the
follow-up duplicated loops so that each copy could assume one layout,
and transformed nested objects into columns of their
own<Cite id="kloibhofer2023" />. So a run-time system can try layouts
that Viscosity cannot prove safe, while Viscosity can explain its
choices before you ship and needs no special engine. Getting both is
the open question: emitting both versions of a loop and choosing at run
time is the obvious idea, and it costs code size and a check on every
entry.

<Formal title="What each side must establish">

```text
ahead of time:
  ∀ runs r.  out(P', r) = out(P, r)
at run time:
  check(layout)  ⇒ fast path
  ¬check(layout) ⇒ deoptimize
```

<span slot="read">Ahead of time, the rewritten program P prime must
give the same output as the original program P for every possible run
r, so the claim has to be proved once, for all inputs. At run time it
is enough that whenever the layout check passes the fast path runs,
and whenever it fails the engine falls back; each run only has to be
right for the data it actually has.</span>
</Formal>

## Problem two: knowing when it pays

The cost model is the least proven part of Viscosity: it skips
collections under 64 elements and otherwise trusts that a loop over a
few fields will win. This book's own measurements show how rough that
is. In the microbenchmarks, the gains shrank to about 1.3–2.3× at 1,000
elements, and AoSoA was often *slower* than plain objects there
(`FINDINGS.md`, section 3). In the benchmark matrix
(`matrix-2026-10-31.md`, section (a)), `nbody` gained 1.2× on Node
and 0.97× on Bun, and `heat` gained 4.11× on Node but 1.02× on Bun:
the same output, the same layout, a different engine, a different
verdict. In CPython the same layout lost on time and won on memory
(section 6). And SoA loses badly whenever whole objects must be
rebuilt<Cite id="ziap2025" />. Viscosity has no model that predicts all
of that for any program on any machine, and this book knows of none.

## Problem three: who decides

Some languages hand the choice to you. In Odin, `#soa[N]Vector3` stores
an array as columns while you keep writing `v[0].x`<Cite id="odin-overview-soa" />,
and ISPC's `soa<N>` types do the same for blocked
layouts<Cite id="ispcdocs" />. Viscosity's `@viscosity soa` annotation
(from *Opting in with @viscosity*) sits in between: you ask, and it
still checks safety. Whether an automatic tool can match an expert's
choice, and how it should explain itself when it disagrees with one, is
open.

<Prompts ids={['op-proof', 'op-cost', 'op-who']} />

<Callout kind="engine" label="Under the hood">
Sometimes the engine closes an edge for you. In this book's
microbenchmarks, a SoA loop that built a small object per element and
passed it to a function did **not** lose to objects: V8 inlined the
function and removed the temporary object by escape analysis
(`FINDINGS.md`, section 2). A static tool cannot count on that, because
V8 decides it while the program runs. Even the reports had rough edges:
for `ps[0] = ps[1]`, explain used to say "the array is stored into an
array at line 5", when the array was really the *target* of the store;
the decision was right and the sentence was wrong, and the reason now
reads "the array is written with an index store at line 5".
</Callout>

## Measuring the frontier

How do you choose which edge to work on? The same way Part VIII chose
its optimizations: measure. Run `viscosity explain` over a corpus of
real programs and count the reasons; the refusal that blocks the most
programs is the one worth an idea. (Over the engine's own 40-program
JavaScript test corpus, 27 collections become struct of arrays, 2
AoSoA and 19 are kept; but that corpus was written to exercise the
refusals, so its counts say nothing about real code. A useful tally
needs programs nobody wrote for the purpose.) That is what the exercise
builds.

## What you learned

- Viscosity's refusals mark the edge of what it can prove, and its
  explain report names each one.
- An **engineering gap** (classes, destructuring) needs work; an
  **open problem** (reordering, varying shapes, whole programs, nested
  records, unknown sizes) needs an idea.
- **Proof or speculation:** run-time systems can guess and recover;
  ahead-of-time ones must prove. Combining the two is open.
- The **cost model** is a heuristic; the book's own benchmarks, across
  sizes, engines and languages, show how far "when does it pay" is from
  solved.
- To choose a problem, **measure** which refusals are common, on code
  nobody wrote for the purpose.
