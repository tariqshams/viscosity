## When "the same type" is too strict

The type checker of chapter 124 asks, at every call, whether the
argument's type *equals* the parameter's. Here is a call it would
reject:

```ts
interface Point { x: number; y: number }
function norm(p: Point) {
  return p.x + p.y;
}
const px = { x: 1, y: 2, colour: 'red' };
norm(px); // 3
```

Lines 1 to 4 say that `norm` wants a `Point`, an object with number
fields `x` and `y`, and adds them. Line 5 makes an object with those two
fields and a third, `colour`; its type is
`{ x: number; y: number; colour: string }`, which is not the same type
as `Point`. Yet `norm` only ever reads `x` and `y`, both are there, and
the call runs and returns `3`; TypeScript accepts it. What we need is a
rule that says when a value of one type is safe to use where another
type is expected.

<Analogy title="a job advert">
An advert says "must hold a driving licence". An applicant who has a
licence *and* speaks three languages qualifies; the employer
never asks about the languages. An applicant with no licence does not
qualify, however many languages they speak.
<span slot="breaks">A real employer sees the whole person and may
decide the extra skills matter after all; a function that wants a
`Point` can only ever read what `Point` lists, so the extra fields are
invisible to it (though they are still there, and a loop over the
object's keys would find them).</span>
</Analogy>

<Callout kind="definition">
**S is a subtype of T**, written `S <: T`, when a value of type S can be
used safely anywhere a value of type T is expected. The rule that lets
a type checker do so is called **subsumption**: if an expression has
type S, and `S <: T`, then it also has type T<Cite id="pierce2002" />.
Every type is a subtype of itself, and if `S <: U` and `U <: T` then
`S <: T`.
</Callout>

<Formal title="Subsumption">

```text
 Γ ⊢ e : S        S <: T
───────────────────────── (Sub)
       Γ ⊢ e : T
```

<span slot="read">If, in environment gamma, e has type S, and S is a
subtype of T, then e also has type T. So a call whose parameter wants a
T accepts an argument of type S.</span>
</Formal>

## Records: width and depth

For record types (objects with named fields), the rule follows from
what a reader of the record can do: read the fields its type lists.
Step through the check:

<SubtypeSteps client:visible />

<Formal title="Subtyping for records">

```text
{ l₁: T₁ … lₙ: Tₙ, more fields }
  <: { l₁: T₁ … lₙ: Tₙ }          (Width)

  S₁ <: T₁   …   Sₙ <: Tₙ
───────────────────────────────  (Depth)
{ l₁: S₁ … lₙ: Sₙ }
  <: { l₁: T₁ … lₙ: Tₙ }
```

<span slot="read">Width: a record with the fields l1 to ln, plus some
more, is a subtype of the record with only l1 to ln. Depth: if each
field's type S-i is a subtype of T-i, then the record with fields of
types S is a subtype of the record with the same fields of types T.
The order of the fields does not matter.</span>
</Formal>

Putting the two rules together arranges record types from the most
general (no fields at all, which every record satisfies) down to the
most specific:

<Figure takeaway="More fields means a more specific type; a subtype sits below everything it can stand in for." caption="Record types ordered by subtyping, with each arrow pointing from a subtype to a supertype. {x} and {y} are not subtypes of each other: neither has the other's field.">
  <RecordOrder />
</Figure>

<Examples of="subtyping">

```text
{ x: number, y: number, colour: string }
  <: { x: number, y: number }     (Width)
```

```text
{ pos: { x: number, y: number, z: number } }
  <: { pos: { x: number, y: number } }
                                   (Depth)
```

```ts
function show(v: number | string) {
  return String(v);
}
show(42); // number <: number | string
```

</Examples>

The first is the Pixel and Point check from the stepper. The second
is depth: the outer records have the same single field `pos`, and the
types of `pos` are related by width, so the outer records are related
too. The third is a subtype you already know from chapter 29: a value
of type `number` can go wherever `number | string` is expected, since
it is one of the two allowed kinds. (Depth is safe as written only when
fields are read and never written; the next chapter shows why
writing breaks it.)

## By shape or by name

So far "a subtype" has meant "has the right fields". That is
**structural** subtyping, and it is TypeScript's rule: the handbook says
type compatibility "is based on structural subtyping", relating types
"based solely on their members"<Cite id="ts-type-compatibility" />. Java
works differently: a class is a subtype of another only if it says so,
by `extends` or `implements`, even when the two have exactly the same
fields. That is **nominal** subtyping (from the Latin for "name").

<Analogy title="a guest list and a height bar">
At a private party, the door checks a guest list: you get in if your
*name* is on it, however well you are dressed (nominal). At a
fairground ride, a bar checks your *height*: anyone tall enough rides,
whoever they are (structural).
<span slot="breaks">A bouncer can be talked round, and a child can
stand on tiptoe; a type checker applies its rule the same way every
time, and in a nominal language even a class that is identical in
every field is turned away without the declared name.</span>
</Analogy>

<Callout kind="definition">
In **structural** subtyping, `S <: T` is decided by the types'
structure: their fields and their fields' types. In **nominal**
subtyping, it is decided by declared names: S is a subtype of T only
if S is T, or S was declared to extend or implement T (directly or
through others). TypeScript is structural; Java and C# are
nominal<Cite id="ts-type-compatibility" />.
</Callout>

<Examples of="structural-vs-nominal">

```ts
class Pixel { x = 1; y = 2; colour = 'r'; }
norm(new Pixel()); // TypeScript: fine, 3
```

```java
class Point { int x, y; }
class Pixel { int x, y; }
Point p = new Pixel();
// error: incompatible types:
// Pixel cannot be converted to Point
```

```ts
norm({ x: 1, y: 2, colour: 'red' });
// error TS2353: Object literal may only
// specify known properties, and 'colour'
// does not exist in type 'Point'.
const px = { x: 1, y: 2, colour: 'red' };
norm(px); // fine
```

</Examples>

In the first, `Pixel` never mentions `Point`, yet a `Pixel` has number
fields `x` and `y`, so TypeScript accepts it (and the call returns 3).
In the second, Java's `Pixel` has exactly `Point`'s fields, but javac
refuses with the message shown, because nothing declares `Pixel` to be
a `Point`; writing `class Pixel extends Point {}` is how you would say
so. The third is a spot the difference worth knowing: TypeScript
accepts extra fields by width, *except* in an object literal written
straight into the call, where an extra field is more likely a typo than
a plan, so it reports error TS2353; the same object stored in a
variable first is accepted. (These were checked with tsc 5.9 and
OpenJDK 21's javac.)

## What you learned

- `S <: T` means an S can be used wherever a T is expected;
  **subsumption** lets the checker do that.
- Records: **width** allows extra fields, **depth** allows fields
  whose types are subtypes.
- **Structural** subtyping (TypeScript) goes by shape; **nominal**
  subtyping (Java) goes by declared names.
