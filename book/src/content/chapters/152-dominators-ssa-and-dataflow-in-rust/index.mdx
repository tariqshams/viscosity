## Same algorithms, new containers

*Dominators and natural loops* and *SSA and phi nodes, built on the
fly* taught these ideas; `crates/core/src/cfg.rs` and `builder.rs` port
`cfg.ts` and `builder.ts` almost line for line, Cooper, Harvey and
Kennedy's dominance algorithm and Braun et al.'s SSA
construction<Cite id="braun2013" /> included. What changes is *where
things live*.
The TypeScript keeps `Map`s keyed by block numbers; in Rust, blocks and
values sit in the module's arenas (*VIR and the plugin trait in Rust*),
so a map from blocks becomes a `Vec` indexed by `BlockId`, and "no
entry" becomes `None`.

<Analogy extra title="numbered lockers at a pool">
At a swimming pool, the desk does not write down where each locker
stands, only its number; a list of who has locker 7 is a row of slots,
one per locker, and a free locker is a slot marked "nobody".
<span slot="breaks">A pool reuses a locker for the next swimmer; the
arena never does, so a removed value keeps its slot, and an old key
still opens it: the id still "works", and quietly hands you the wrong
thing.</span>
</Analogy>

## Dominators, and a closure that borrows

`cfg.rs` first lists the blocks in reverse postorder (where the
TypeScript recurses, the port keeps an explicit stack, which visits
successors in the same order and cannot overflow on a long chain of
blocks), and then runs the dominator loop, adapted:

```rust
let intersect =
    |idom: &[Option<BlockId>], a, b| {
        // climb a and b by rpo index
    };
// ...then, for each block b in rpo:
let mut d = first;
for &p in rest {
    d = intersect(&idom, p, d);
}
if idom[b.index()] != Some(d) {
    idom[b.index()] = Some(d);
    changed = true;
}
```

`idom` is a `Vec<Option<BlockId>>`, with only the entry filled in at
first; `first` and `rest` are the block's predecessors that already have
one, and `intersect` climbs from two blocks towards the entry until they
meet. Why does the closure take `idom` as a parameter? A closure that
*captures* a variable borrows it for as long as the closure is in use,
and the loop assigns to `idom` between calls: rustc 1.97 on a small copy
says `error[E0502]: cannot borrow `idom` as mutable because it is also
borrowed as immutable`. Passing `&idom` at each call makes each borrow
last one call.

## The SSA builder

`FunctionBuilder<K>` is generic over `K`, the front-end's name for a
variable. It does not own the `Module`: every method takes `&mut
Module`, because lowering a nested function keeps two builders alive
(outer and inner) writing into one module, and two builders each
holding a `&mut Module` would be rejected by the borrow checker.

<More title="More: reading a variable across blocks">

Reading a variable that the current block does not define, trimmed from
`read_variable_recursive`:

```rust
let val = if !self.sealed.contains(&block) {
    let phi = self.new_phi(m, block);
    self.incomplete.entry(block)
        .or_default()
        .insert(v.clone(), phi);
    phi
} else if preds.len() == 1 {
    self.read_variable(m, v, preds[0])
} else {
    let phi = self.new_phi(m, block);
    self.write_variable(
        v.clone(), block, phi);
    self.add_phi_operands(m, v, phi)
};
```

A block is **sealed** once all its predecessors are known (a loop header
is not, until its back edge exists). So the first branch makes an
*incomplete* phi, filled in at sealing time, in the order of the
`IndexMap` called `incomplete`, which decides the value numbers. The
second asks the one predecessor. The third records a new phi as the
variable's value *first* (so a loop leading back here finds it rather
than asking forever), then reads each predecessor. (A fourth case, with
no predecessors, makes an `undefined` constant.)

</More>

<Callout kind="definition">
**SSA construction over arena IR** builds SSA by editing the module's
arenas through typed ids: values are `ValueId`s into `module.values`,
blocks list their instructions as `Vec<ValueId>`, and replacing a value
means rewriting every place that holds its id (instruction operands,
terminators, and the builder's own tables). Nothing points at anything,
so nothing can dangle; but an id that is missed still names the old
value.
</Callout>

A phi is **trivial** if, ignoring itself, it merges only one value; then
`try_remove_trivial_phi` replaces it with that value. For instructions
that is a loop over operands; terminators need their own `match` (`T`
is `Terminator`):

<Examples of="rust-ssa">

```rust
match &mut blocks[bi].term {
    T::CondBr { cond, .. }
        if *cond == phi => *cond = same,
    T::Return { value: Some(v), .. }
        if *v == phi => *v = same,
    T::Throw { value, .. }
        if *value == phi => *value = same,
    _ => {}
}
```

</Examples>

`&mut blocks[bi].term` borrows the block's terminator mutably, so each
arm can write through the binding it matches: a branch condition, a
returned value or a thrown value that is the removed phi now names
`same`, its replacement, and `_ => {}` leaves the rest alone. The
TypeScript version had only the first two arms. In `throw_from_loop.js`,
an element `e` is thrown from inside a loop, so the loop header got a
phi for `e` that, once sealed, merged the element with itself: trivial.
Without the `Throw` arm the throw still names the removed phi, the
escape analysis never sees the element leave, and the compiled program
throws a number where the original throws the object.

## The framework that is not there

*Dataflow, fixpoints and constant propagation* described one framework
with many instances: a lattice of facts, a rule per instruction, a meet
and a worklist<Cite id="coopertorczon2022" />. Search
`engine/rust/crates` for `trait`, however, and you find exactly one,
`LanguagePlugin`; the port has one fixpoint, `numeric_inference` in
`analysis.rs`, written directly over its own state, because one instance
does not pay for a framework. So this half **designs** one (this book's
design, not code in the repository) and lines it up against the real
loop.

<Analogy title="a tax form">
A tax form works for every household because it never asks what a
household *is*; it asks for a few numbers and says how to combine them.
A generic solver is the form: it never looks inside a fact, it only asks
for the most hopeful fact, the safe one, and how two facts merge.
<span slot="breaks">You fill in a form once. A solver applies the rules
again and again, until a whole pass changes nothing.</span>
</Analogy>

A lattice here is a set of facts ordered from hopeful to safe, with a
top (the optimistic start), a bottom (claims nothing) and a **meet**
(the best fact no more hopeful than either of two). A **problem** says
how many nodes there are, which nodes each one reads, and its rule, the
**transfer function**:

```rust
pub trait Lattice: Clone + PartialEq {
    fn top() -> Self;
    fn bottom() -> Self;
    fn meet(&self, o: &Self) -> Self;
}
pub trait Problem {
    type Fact: Lattice;
    fn len(&self) -> usize;
    fn deps(&self, n: usize)
        -> Vec<usize>;
    fn transfer(&self, n: usize,
        f: &[Self::Fact]) -> Self::Fact;
}
```

`Clone + PartialEq` lets the solver copy facts and notice "nothing
changed". `type Fact: Lattice` is an **associated type**: each problem
has exactly one kind of fact, as each plugin has exactly one `Extra`.

<Examples of="generic-dataflow">

```rust
impl Lattice for bool {
    fn top() -> Self { true }
    fn bottom() -> Self { false }
    fn meet(&self, o: &Self) -> Self {
        *self && *o
    }
}
```

</Examples>

This is the lattice Viscosity uses for JavaScript: `top` is `true`,
"provably a number", the hopeful start; `bottom` is `false`, which
claims nothing and so is always safe; and the meet is `&&`, since a
value built from two others is a number only if both are. (Implementing
our trait for std's `bool` is allowed, because the trait is ours.)

<Callout kind="definition">
A **generic dataflow framework** is a solver written once and generic
over the lattice: any analysis that supplies a fact type with `top`,
`bottom` and `meet`, and a **transfer function** per node, gets a
fixpoint from the same code. In Rust the lattice and the problem are
traits, the fact is an associated type, and the solver is a generic
function bounded by `P: Problem`.
</Callout>

The design's solver starts every fact at top and every node on a stack;
it pops a node, runs its rule, **meets the result with the old fact**
(so a fact can only move down), and if it changed, pushes the node's
users. With a lattice of finite height the stack must empty. It is
generic, `solve<P: Problem>`, so each problem gets its own monomorphized
copy with direct calls<Cite id="klabnik2026" />.

## Viscosity’s loop, as an instance

The real `numeric_inference` has values, bindings and fields as nodes,
`bool` facts and rules such as `compute`, but a different strategy:
whole rounds, every value in id order, each new fact written in place,
until a round changes nothing. Value facts are recomputed from their rules every round, not
clamped, so the loop cannot lean on the height argument to stop; it caps
the rounds at `MAX_ROUNDS` (1000) instead. And if the last round still
changed something, it **fails closed**: every fact is reset to `false`,
so no column is typed and no index is trusted. Step through the same
small problem both ways:

<SolverSteps client:visible />

<More title="More: the real loop, and the three outcomes">

Trimmed from `numeric_inference` and rewrapped (the comment stands for
three more loops):

```rust
let mut converged = false;
for _round in 0..self.max_rounds {
    let mut changed = false;
    for v in &m.values {
        let nv = self.compute(v);
        if self.num[v.id.index()] != nv {
            self.num[v.id.index()] = nv;
            changed = true;
        }
    }
    // ...bindings, then fields
    if !changed { converged = true; break; }
}
```

A unit test in `analysis.rs` pins failing closed with a budget of zero
rounds: with no rounds, no quiet round is ever seen, so even `1 + 2` is
not proven a number. The runnable example has the same three outcomes:
a budget of 1000 is quiet in round 3; a budget of 2 reaches the right
facts but never sees a quiet round, so it fails closed; and a budget of
0 proves nothing. (For Python the fact is a pair, "is a float" and "is
an int", the product lattice on the right of the figure; the deep dive
*The Python plugin in Rust* explains why.)

## What you learned

- `cfg.rs` and `builder.rs` are the TypeScript algorithms with Rust
  containers; `intersect` takes `&idom` per call, because a closure that
  captures a variable borrows it (E0502).
- **SSA over arena IR** means rewriting ids in place, terminators
  included; missing `throw` there was a soundness bug.
- The **generic dataflow** design: `Lattice` and `Problem` traits, an
  associated `Fact`, and a clamped worklist solver generic over `P:
  Problem`. engine/rust has none: one fixpoint in rounds, capped at
  1000, that **fails closed**.
