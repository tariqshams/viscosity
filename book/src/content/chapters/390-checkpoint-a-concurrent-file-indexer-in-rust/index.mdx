## The program

You have a folder of text files and a question: which files mention
both "borrow" and "checker"? A search tool answers it from an
**inverted index**, a map from each word to the set of files that
contain it, built once and then queried instantly. Building one is a
good last exercise for this part, because it needs nearly everything
in it: strings and iterators to split words, `BTreeMap` and
`BTreeSet` to store them, `std::fs` and `?` to walk folders, and
threads, `Arc<Mutex<_>>` and channels to do it on every core.

<Analogy title="a library's card catalogue">
Before computers, a library kept a drawer of cards for every subject,
each card listing the books on it. To find books on both "rivers" and
"Roman", you pulled both cards and kept the books on both. That drawer
is the index; pulling two cards and keeping the overlap is the search.
<span slot="breaks">A librarian writes each card once, by hand, as
books arrive. Our index is rebuilt from scratch every run, which is
fine for hundreds of files and wasteful for millions (real search
engines update theirs).</span>
</Analogy>

<Analogy title="a sorting office">
Post comes in one door into a single tray; several sorters each take
the next letter from the tray, sort it, and drop the result on a
conveyor that one clerk empties into the pigeonholes. The tray is the
job channel, the sorters are worker threads, the conveyor is the
results channel, and the clerk merges.
<span slot="breaks">Sorters can chat and swap letters. Our workers
share nothing but the tray (behind a lock) and the conveyor, which is
what lets Rust prove the program has no data races.</span>
</Analogy>

The whole design is one type and five small functions:

```rust
type Files = BTreeSet<String>;
type Index = BTreeMap<String, Files>;

fn words(text: &str) -> Vec<String>
fn index_text(name: &str, text: &str)
    -> Index
fn merge(to: &mut Index, from: Index)
fn find_files(dir: &Path)
    -> io::Result<Vec<PathBuf>>
fn index_parallel(paths: Vec<PathBuf>,
    workers: usize) -> Index
```

`BTree` collections keep their keys sorted, so the output is the same
on every run, and tests can compare whole indexes with `assert_eq!`.

## The one tricky line

The workers share a single job receiver, so it lives in an
`Arc<Mutex<Receiver<PathBuf>>>`, exactly the pool of the Rust book's
web-server chapter<Cite id="klabnik2026" />. How you take the next job
matters:

```rust
// holds the lock for the whole body:
while let Ok(p) =
    rx.lock().unwrap().recv()
{
    index_file(p); // others wait
}
// releases it at the end of the `let`:
let next = rx.lock().unwrap().recv();
```

Both compile and give the same answer, which is what makes the first
dangerous. A `let` statement drops its temporaries (here the lock
guard) when the statement ends, while `while let` keeps them until the
end of the loop body, so the first version holds the lock while it
reads and indexes the file, and the workers take turns instead of
working at once<Cite id="klabnik2026" />.

The compiler checks the sharing for you, too. Write `Rc` where `Arc`
belongs, and rustc 1.97 refuses (type names shortened, wrapped):

```text
error[E0277]: `Rc<Mutex<Receiver<u32>>>`
  cannot be sent between threads safely
```

`Rc` counts its owners without atomic operations, so it is not `Send`,
and `thread::spawn` demands `Send` for everything the closure takes
(*Threads, Send and Sync*). The data race you might have written is a
type error instead.

Node's `worker_threads` follow the same plan, a worker per job and
messages back, but every value sent is *copied* (cloned) into the
other thread, because JavaScript threads share no ordinary
objects<Cite id="node-worker-threads" />. Rust moves the partial index
through the channel without copying it, and its types prove that no
two threads touch the same data unguarded.

The first is the smallest piece, and the place to start: the warm-up
exercise. The second is the finished indexer, timed for this chapter
on the book's own 382 chapter files (release build, rustc 1.97, a
4-core cloud machine, median of five runs). Four workers were 2.4
times faster than one, not four, and timing the merge loop showed why:
with four workers the main thread spent about 250 ms merging, nearly
the whole run, so the single clerk was the bottleneck. Letting each
worker merge into its own index and send one result at the end cut it
to 152 ms. The runnable one is the pool pattern on its own, squaring
numbers; on a fast machine one worker may grab every job, because each
takes nanoseconds.

## What you learned

- A real program is a few plain functions around one data type, each
  tested alone before they are joined.
- A **worker pool** is a job channel whose receiver is shared through
  `Arc<Mutex<_>>`, plus a results channel; dropping the senders is how
  everyone learns the work is over.
- Measure before guessing: here the single merging thread, not the
  workers, set the speed.
