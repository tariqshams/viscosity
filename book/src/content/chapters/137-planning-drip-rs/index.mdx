## A working VM, and a blank file

You built a bytecode VM for Drip in TypeScript (*A stack machine and its
dispatch loop* onwards); it lives in `companion/ts/src/vm`, about 2,000
lines across nine files, and it runs every program in the book's test
corpus. This part rebuilds it in Rust. The result already exists (it is
called **drip-rs**, and it lives in `companion/rust`), so rather than
invent it from nothing, these chapters walk through it file by file, next
to the TypeScript you already know.

The goal is easiest to state as a test: for every corpus program, drip-rs
must print the same output, the same error messages, the same stack
traces and the same exit code as the TypeScript VM. Not "close"; the same
bytes. Most of the port is translation; one part is not, and it shapes
everything else.

<Analogy title="moving house to another country">
Most of your things go straight into boxes and come out the same at the
other end; a few need a plug adapter; and one thing, the wiring you ran
through every wall yourself, has to be redone to the new country's rules.
For drip-rs, the boxes are the scanner and the compiler, and the wiring is
the web of references between heap objects.
<span slot="breaks">A house move is done once and then forgotten; here
the old house keeps standing next door, and every program must behave
identically in both, for as long as the book exists.</span>
</Analogy>

These are real runs of the release binary (rustc 1.97). `hello.drip`
holds `print "hello, " + "drip";`, and its one line comes out on stdout.
`broken.drip` opens an `if` block that never closes; the message (wrapped
here to fit) goes to stderr, nothing runs, and the exit code is 65, the
code both VMs use for a compile error (70 is a runtime error). The last
command compiles without running and prints the bytecode, and it is,
character for character, the listing the TypeScript disassembler prints
for the same program.

<Callout kind="definition">
**drip-rs** is the Rust implementation of Drip's bytecode VM, in
`book/companion/rust`. It is a library crate, `drip`, plus a binary,
`drip-rs`. It ports the TypeScript VM module by module, uses only `std`
and no `unsafe` code, and is tested against the same corpus, which it
must match byte for byte.
</Callout>

## Objects that point at each other

In TypeScript, a closure holds its function, an instance its class, and a
class a table of closures; cycles are normal, and JavaScript's collector
sorts it out. *Box, Rc and RefCell* showed why `Rc<RefCell<T>>` is wrong
for a VM: reference counting would decide when objects die, leaving the
collector of *Reclaiming memory: mark and sweep* nothing to do; a cycle
of `Rc`s leaks<Cite id="klabnik2026" />; and every `borrow_mut()` is a
run-time check on the interpreter's hottest paths. So drip-rs uses the
design of *Arenas and typed indices*: each kind of object lives in its
own `Arena<T>` owned by the `Heap` (nine arenas), a reference is a
`Gc<T>`, a typed `u32` slot number, and `heap[handle]` reads the object.

## Roots are passed in

The TypeScript heap starts a collection by itself, inside `allocate`, and
finds the roots by calling back into the VM, which registered itself with
`this.heap.vm = this`. In Rust the VM owns the heap, so a heap method that
also reached the whole VM would need the VM borrowed while the heap
inside it is already borrowed mutably, which *Borrowing and the borrowing
rules* forbids. So drip-rs turns it round: allocating never collects. The
VM asks `heap.should_collect()`, and if the answer is yes, it borrows the
fields that hold roots one by one and hands them over (from `vm.rs`):

```rust
pub fn collect_garbage(&mut self) {
    let roots = VmRoots {
        stack: &self.stack,
        frames: &self.frames,
        globals: &self.globals,
        open_upvalues: &self.open_upvalues,
        init_string: self.init_string,
    };
    self.heap.collect(&[&roots]);
}
```

Borrowing `self.stack` for reading and `self.heap` mutably at once is
fine, because they are different fields and the borrow checker tracks
each separately. `collect` takes `&[&dyn Trace]`, a list of things that
can mark what they reach, so the compiler can pass in its half-built
functions the same way.

## The one Rc

drip-rs puts exactly one kind of thing in an `Rc`: the chunk, in the
field `pub chunk: Rc<Chunk>` of `ObjFunction`. When the compiler finishes
a function it freezes the chunk with `Rc::new`, and nothing changes it
again. The VM keeps the running function's chunk in a field of its own
(the README calls such fields **registers**) and reads bytes with
`self.chunk.code[self.ip]`. A plain `&Chunk` would point into the heap
and keep the heap borrowed while the VM pushes values and allocates; an
`Rc` clone is the VM's own pointer to the same chunk, so the heap stays
free, and because the chunk never changes it needs no `RefCell`.

## The same bytes

How do you know the port is right? The answer from *End to end:
benchmarks and differential testing at scale* is to run one corpus
through both and compare. drip-rs's `tests/corpus.rs` runs the 334 corpus
programs that are not benchmarks and checks each against the expectations
written in its comments, with a Rust port of `check()` from the
TypeScript runner. Two real lines:

```drip
print (1 + 2) * (3 + 4); # expect: 21
print "count: " + count;
```

The first, from `operators/grouping.drip`, wants `21` on stdout; the
second, from `strings/add_a_number.drip`, carries the comment `# expect
runtime error: cannot add a string and a number`, so the checker wants
that message, a stack
trace pointing at its line, and exit code 70. `cargo test` also runs 165
of the programs with a collection before every allocation
(`tests/stress_gc.rs`), which makes a forgotten root fail at once, and
`scripts/compare_with_ts.mjs` runs both VMs on every corpus program,
benchmarks included, and on thousands of randomly broken ones, comparing
stdout, stderr and exit codes. When I ran it (2026-11-02) it printed
`corpus: 343 programs compared, 0 differ` (one program reads the clock,
so it is skipped) and `mangled: 2000 programs, 0 skipped (slow), 0
differ`.

<Formal title="What “the same bytes” means">

```text
∀ p ∈ Corpus:
  run_rs(p) = run_ts(p)
run(p) = (stdout, stderr, exit code)
```

<span slot="read">For every program p in the corpus, running p on drip-rs
gives exactly the same result as running it on the TypeScript VM, where a
result is three things together: everything printed to standard output,
everything printed to standard error, and the exit code.</span>
</Formal>

## What you learned

- **drip-rs** is a module-by-module port of the TypeScript VM: `std`
  only, `#![forbid(unsafe_code)]`, tested against the same corpus.
- Heap objects live in arenas owned by the heap, referred to by `Gc<T>`
  handles; the collector decides when they die, and **roots are passed
  in** because the heap cannot reach the VM that owns it.
- Frozen chunks are the crate's only `Rc`; "correct" means the same
  stdout, stderr and exit code as the TypeScript VM.
