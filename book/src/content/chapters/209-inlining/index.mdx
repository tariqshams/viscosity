## One small function

Here is a particle update, written the way most people would write it,
with the work for one particle in its own function:

```js
const ps = [];
for (let i = 0; i < 100; i++) {
  ps.push({ x: i, vx: 1 });
}
function move(p) {
  p.x += p.vx;
}
for (let i = 0; i < ps.length; i++) {
  move(ps[i]);
}
console.log(ps[9].x);
```

Ask Viscosity what it makes of this, and it refuses to change the layout
(its real explanation, wrapped to fit):

```text
ps (line 1) {x, vx}
  → kept as array of objects
  · unsafe: line 9: an element is passed
    to a function call
```

Now paste the body of `move` into the loop yourself:

```js
for (let i = 0; i < ps.length; i++) {
  const p = ps[i];
  p.x += p.vx;
}
```

Same program, same output, and this time Viscosity says
`ps (line 1) {x, vx} → struct of arrays`, with typed `Float64Array`
columns for both fields. Nothing about the work changed. What changed
is what the analysis could *see*: inside one function every use of the
element is in view; across a call, the element disappears into code the
analysis does not follow. Pasting a function's body in place of a call
is called **inlining**, and this is its real purpose.

<Analogy title="a recipe that says &quot;see page 40&quot;">
A recipe says "make the sauce (see page 40)". You can flip to page 40
every time, or copy page 40 into the recipe. Copying saves the flipping,
but the bigger win is that the whole dish is now on one page, and you
notice that half the sauce steps are pointless for this dish.
<span slot="breaks">Copying a page into every recipe that uses it makes
the book thicker each time; a compiler pays for every copy in code size
and compile time, which is why it cannot copy everything.</span>
</Analogy>

<Analogy title="quoting instead of citing">
An essay can say "as Smith argues (2001, p. 12)" and send the reader
off to find the book, or quote the paragraph right there. Quoted, the
reader can weigh every word against the rest of the argument.
<span slot="breaks">A quotation is read as it is; an inlined body is
adapted to its new place: its parameters become the caller's arguments
and its local names are changed so they cannot collide with the
caller's.</span>
</Analogy>

## Pasting a function in

Doing it by hand looks easy. Doing it mechanically, for every call, has
two traps, both about names. Step through it:

<InlineSteps client:visible />

The first trap is a callee local with the same name as a caller
variable, which the fresh name (`s1`) avoids. The second is subtler:
the parameters must all be replaced **at once**. Here is the slip, with
`sub(a, b)` returning `a - b`, inlined at the call `sub(b, a)`:

```text
body:          a - b
a → b, then:   b - b
b → a, then:   a - a     ; wrong
at once:       b - a     ; right
```

One at a time, the second replacement rewrites a `b` that the first one
had just put in. Done simultaneously, every parameter is replaced in the
*original* body, and the call `sub(b, a)` becomes `b - a`, as it must.

<Callout kind="definition">
**Inlining** replaces a call with a copy of the callee's body, in which
every parameter is replaced by its argument, all at once; every local
of the callee gets a fresh name that the caller does not use; and each
`return v` hands `v` to the code after the call. Each argument is
evaluated once, before the body, exactly as the call would have done.
</Callout>

<Formal title="Simultaneous substitution">

```text
call f(e1, …, en),  f(x1, …, xn) = body
───────────────────────────────────────
body[x1 := e1, …, xn := en]
```

<span slot="read">If f has parameters x1 to xn and the given body, then
a call f(e1, …, en) can be replaced by the body with x1 replaced by e1,
x2 by e2, and so on, all in one step (the square brackets mean "with
these replacements made together"). When an argument has side effects
or is used twice, it is first stored in a fresh temporary, and the
temporary is substituted instead.</span>
</Formal>

## Inlining in a control-flow graph

In an IR, the callee is a whole CFG, not one expression. The caller's
block is cut in two at the call; the callee's blocks are copied in, with
fresh ids for every block and every SSA value; the copy's entry is
jumped to from the first half; each `return v` becomes a jump to the
second half; and the call's result becomes a phi of the returned
values, one per return:

## What it unlocks

The call overhead it removes is small. What matters is that the passes
of the last few chapters work inside one function, and inlining gives
them a bigger one:

<Examples of="inlining">

```js
function sq(v) { return v * v; }
const y = sq(x) + 1;
// inlined: const y = x * x + 1;
```

```js
const k = sq(3);
// inlined:  const k = 3 * 3;
// folded:   const k = 9;
```

```js
for (const p of ps) move(p);
// inlined: for (const p of ps) {
//            p.x += p.vx; }
// Viscosity now sees every field use
```

</Examples>

The first is the plain case: the call disappears and its body takes its
place, with `v` replaced by `x`. The second is where inlining pays off:
once the body is in the caller, the argument `3` meets the
multiplication, and constant folding finishes the job at compile time;
no call, no multiplication, just `9`. The same happens with dead code:
an inlined function often computes things this caller never uses, and
DCE now sees that they are unused here. Value numbering gains too, since
a value computed in the caller and again in the callee is now in one
function. The third is the chapter's opening example, where what
inlining unlocks is an analysis rather than an optimisation.

The price is size: every inlined call copies the whole body, so
inlining a 50-line function at 20 call sites compiles 1,000 lines, and
a JIT compiler pays for that in compile time and memory while the
program runs. The next chapter is about deciding which calls are worth
it.

<Callout kind="engine" label="Under the hood">
V8's optimising compiler inlines. Its release notes for V8 6.1 say
TurboFan began inlining `Array.prototype.forEach`<Cite id="v8-release-61" />,
and when V8's team rewrote `Array.prototype.sort`, they noted that the
old version, written in JavaScript, had let the optimising compiler
inline the comparison function you passed in<Cite id="v8-array-sort" />.
This book's own benchmark findings show the effect: in the
`get-objects` case, which hands each SoA element to a small function
that wants an object, SoA did not lose, because V8 inlined the function
and then removed the temporary object altogether. Textbooks list
inlining among the transformations whose value lies mostly in the
optimisations it enables afterwards<Cite id="coopertorczon2022" />.

Viscosity itself does **not** inline: it is a source-to-source tool,
and pasting function bodies all over your program would rewrite far
more than the collection code it means to touch. Try the opening
example: inline `move` by hand below and watch the decision flip.
</Callout>

## What you learned

- **Inlining** replaces a call with the callee's body: parameters
  replaced by arguments all at once, callee locals renamed, and each
  `return` turned into the call's value.
- On a CFG, the call's block is split, the callee's blocks are copied
  with fresh names, and returns jump to a join where a phi picks the
  result.
- Its main benefit is visibility: folding, DCE, value numbering and
  Viscosity's layout analysis all see caller and callee together.
- Its cost is code size and compile time, so it cannot be applied
  everywhere.
