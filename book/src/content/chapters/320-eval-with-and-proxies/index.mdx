## Code that arrives as a string

Here are two functions that differ by one line:

```js
function plain(s) {
  let x = 1;
  return x + 1;
}
function withEval(s) {
  let x = 1;
  eval(s);
  return x + 1;
}
withEval('x = 5'); // 6
```

`eval` takes a string and runs it as JavaScript, and when it is called
directly, the code runs *inside the caller's scope*: `withEval('x = 5')`
returns 6, because the string assigned to the caller's local `x`. For
`plain`, the resolver (chapter 110) knows before the program runs that
`x` is local slot 0, and nothing else can touch it. For `withEval`, the
string is only known at run time, and it might read `x`, assign it, or
(outside strict mode) declare a new `var` that shadows a global. The
compiler can no longer say what any name means.

<Analogy title="a stranger at the planning meeting">
A team plans a project with a fixed list of who does what. If anyone
may walk in at any moment with a note that reassigns jobs, nobody can
print the plan in advance; every task must be checked against the
latest notes when it starts.
<span slot="breaks">A real meeting can turn the stranger away. In
non-strict JavaScript the language guarantees that a direct eval may
reach every local name in scope, so the engine must keep them all
reachable by name.</span>
</Analogy>

<Analogy title="a theatre with no script">
In a scripted play the lighting crew can plan every cue in advance. In
improvised theatre they must watch and react, because any actor may
say anything.
<span slot="breaks">Improvisers still use the same stage; the eval'd
code also uses the same engine, only with less of the planning done
ahead of time.</span>
</Analogy>

The specification makes the line precise. A call is a **direct eval**
only if it is written as a plain call through the name `eval` and that
name finds the real built-in `eval`; then the string runs in the
caller's environment<Cite id="ecma262-eval-proxy" />. Anything else,
such as `(0, eval)(s)` or `globalThis.eval(s)`, is an **indirect** eval,
which runs in the global scope and cannot see local
variables<Cite id="mdn-eval" />. A direct eval in strict mode may still
read and assign locals, but its own declarations go into a new scope of
their own.

In `plain`, `x` is register `r0` and the addition is one instruction.
In `withEval`, V8 creates a function context on the heap, stores `x`
in slot 6 of it, asks the runtime to resolve a possibly direct eval
(`ResolvePossiblyDirectEval`), and reads `x` back from the context
after the call. MDN states the general rule: with a direct eval, engines
and build tools must give up optimisations such as inlining, and
minifiers stop renaming, "because the eval() source can depend on any
variable name in its surrounding scope"<Cite id="mdn-eval" />.

`with (o) { ... }` causes the same problem without any string. It
places an object in front of the scope chain, so that a name inside the
block refers to `o`'s property if there is one and to the outer
variable otherwise<Cite id="ecma262-eval-proxy" />, and that can differ
on every run. V8 compiles it to `CreateWithContext` and then
`LdaLookupSlot` for `x`, a lookup by name; MDN says plainly that `with`
"makes optimization impossible", and strict mode forbids it
(`SyntaxError: Strict mode code may not include a with
statement`)<Cite id="mdn-with" />.

<Callout kind="definition">
**Eval semantics** are the rules for running code given as data. A
**direct eval** runs its string in the caller's scope and may read and
assign, and outside strict mode declare, local names, so a compiler
cannot resolve names, keep locals in registers or inline across it in
that scope; an **indirect eval** (and `new Function`) runs in the global
scope and leaves locals alone. `with` adds an object to the front of the
scope chain, which has the same effect on name resolution.
</Callout>

<Examples of="eval-semantics">

```js
function f() {
  let x = 1;
  eval('x = 5');      // direct
  (0, eval)('x = 7'); // indirect
  return x;           // 5
}
```

```js
eval('var z = 1');
typeof z;   // 'number'
// with 'use strict' at the top:
// typeof z is 'undefined'
```

```js
function f(o) {
  let x = 1;
  with (o) { return x + 1; }
}
f({});        // 2
f({ x: 10 }); // 11
```

</Examples>

In the first, the direct call changes the local `x`; the indirect one
runs in the global scope, cannot see it, and creates a global `x`
instead, so `f()` returns 5. In the second (run in Node
22), a non-strict direct eval declares `z` in the surrounding scope;
with `'use strict'` the declaration stays inside the eval's own scope,
which is why strict code is easier to compile. In the third, the same
`x` means the local variable on one call and `o.x` on the next.

## Proxies: objects that decide for themselves

Reflection in the last chapter only *looked* at objects. A **proxy**
goes further: it is an object whose basic operations, such as reading a
property, writing one, `in`, `delete` or calling it, are handed to
functions you write, called **traps**. Every operation on an object is
one of a small set of *internal methods* ([[Get]], [[Set]],
[[HasProperty]], [[Delete]], [[Call]] and others), and a proxy lets you
supply your own for any of them; a missing trap forwards to the target,
and `Reflect` offers the default behaviour of each, ready to
forward<Cite id="mdn-proxy" /><Cite id="mdn-reflect" />.

<Run id="proxies" />

The first proxy logs each read and forwards it with `Reflect.get`, so
`logged.x + logged.y` prints two reads and then 7. The second turns a
negative index into one counted from the end, so `[-1]` reads the last
element. The third shows the limit: the target is frozen, so its `id`
can never change, and a trap that reports a different value makes the
read throw a `TypeError`. The specification lists the steps:

<ProxySteps client:visible />

<Callout kind="definition">
A **proxy** is an object that wraps a target and a handler; each basic
operation on the proxy calls the handler's trap for it, or is forwarded
to the target if there is none. After a trap returns, the engine checks
**invariants**, rules the target's own promises impose (such as a
frozen property's value), and throws a TypeError if the trap broke one.
</Callout>

<Examples of="proxy">

```js
const p = new Proxy({}, {
  has: (t, k) => k.startsWith('a'),
});
'apple' in p;  // true
```

```java
Greeter g = (Greeter) Proxy
  .newProxyInstance(loader,
    new Class<?>[] { Greeter.class },
    (proxy, m, args) ->
      "intercepted " + m.getName());
g.greet("Ada"); // intercepted greet
```

```python
class Config:
    def __getattr__(self, name):
        return f"<no {name}>"
Config().colour  # '<no colour>'
```

</Examples>

The first traps `in` instead of reads, so `'apple' in p` is true for an
empty object. The second is Java's `java.lang.reflect.Proxy`, which
creates a class at run time implementing the interfaces you list and
sends every method call to one `InvocationHandler`; run here with Java
21 it printed `intercepted greet(Ada)` and the generated class's name,
`$Proxy0`<Cite id="openjdk-class-reflection" />. The third is Python's
`__getattr__`, called only when ordinary attribute lookup fails, so
`debug` (a real attribute) reads normally while `colour` comes from the
hook<Cite id="python-getattr" />.

For an engine, a proxy is the same kind of obstacle as `eval`: a
property read, which an inline cache (chapter 170) normally turns into
one load at a fixed offset, becomes a call to arbitrary code followed
by the invariant check, since the trap may answer differently every
time.

## What you learned

- A **direct eval** runs a string in the caller's scope, so locals move
  to a heap context and names are looked up at run time; `with` does
  the same to every name in its block.
- A **proxy** sends each basic operation to a trap, forwards when there
  is none, and checks **invariants** afterwards.
- Java has dynamic proxies for interfaces and Python has
  `__getattr__`; in each, interception costs the optimiser its
  certainty.
