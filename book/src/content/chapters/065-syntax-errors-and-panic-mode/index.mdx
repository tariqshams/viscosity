## Three typos, one run

Say twenty lines of Drip have three typos. One parser stops at the
first; you fix it, run again, meet the second, and so on. Another tells
you all three at once. A third tells you the three and a dozen more that
are not really there, because it got lost after the first. You want the
second parser.

## What a syntax error is

At every step the grammar tells the parser what may come next: after
`let`, a name; after `print` and a value, a `;`. A syntax error is the
moment that promise is broken. In the Drip parser, every place where the
grammar *requires* a token goes through `consume`:

```ts
function consume(t, what) {
  if (check(t)) advance();
  else expected(what, t === ';'
    ? previous : current);
}
```

A `print` statement ends with `consume(';', "';' after the value")`. If
the next token has that type, `advance()` takes it; if not, `expected`
builds `expected <what>, found <token>` and hands it to the
**reporter**, an object that collects messages in a list. It does not
throw, so parsing carries on. Step through a `let` that is missing its
`;`:

The `t === ';' ? previous : current` part picks the line: usually the
line where the parser noticed, but a missing `;` belongs at the end of
the line before, so it gets the line of the token before it.

<Callout kind="definition">
A **syntax error** is source code that breaks the grammar: at some
point the parser needs a certain kind of token and finds another. Drip
reports it as `line N: expected <what>, found <token>`. Syntax errors
are found before the program starts, so if any is reported, Drip runs
nothing at all and exits with code 65.
</Callout>

<Examples of="syntax-error">

```text
let n = 3;
while n > 0 {
  print n
  n -= 1;
}
# line 3: expected ';' after the
#   value, found 'n'
```

</Examples>

The slip everyone makes. `print n` is a complete statement waiting for
its `;`; the parser notices at the `n` on line 4, the earliest token
that cannot fit, and names it, but reports line 3, where the `;`
belongs. (Drip prints each message on one line.) For any other missing
token the line is the one where the parser noticed: leave the operand
off `print 1 +` and the error is on the next line, at whatever token
arrived instead.

## Don't stop at the first

Reporting one error is easy: throw, and let the whole parse fail.
Reporting *several* is harder, because after an error the parser is in
the middle of something it no longer understands. Here is what Drip
would print if it complained about everything that looked wrong after an
error (I tried it, by deleting the one line in a copy of the companion
that keeps it quiet):

```text
print (1 + ;
print 2;
# line 1: expected an expression,
#   found ';'
# line 2: expected ')' after the
#   expression, found 'print'
# line 1: expected ';' after the
#   value, found 'print'
```

One mistake, three messages; the second and third exist only because
the first left the parser confused (the line numbers even run
backwards). The real Drip prints the first message alone.

<Callout kind="definition">
**Error recovery** is what a parser does after a syntax error so that it
can keep parsing and report later errors too. It has two goals that pull
against each other: report as many **real** errors as possible in one
run, and report no **cascading** errors, messages that are only echoes
of an earlier one.
</Callout>

<Examples of="error-recovery">

```text
print 1 +;
print 2;
print (3;
# line 1: expected an expression,
#   found ';'
# line 3: expected ')' after the
#   expression, found ';'
```

</Examples>

Two separate mistakes with a good line between them, and both are
reported from one run, with nothing invented; `print 2;` in between is
checked as usual. How the parser finds its feet again after line 1 is
panic mode.

## Panic mode: keep quiet, then skip

<Analogy title="a pianist who loses their place">
A pianist who loses their place in a piece does not keep playing wrong
notes and hope; they skip to the start of the next bar, where they know
exactly where they are, and carry on from there.
<span slot="breaks">The audience hears the gap; nobody hears what a
parser skips, which is the danger: a second mistake inside the skipped
part goes unreported until the next run.</span>
</Analogy>

Every error goes through one function, and it starts by checking a flag:

```ts
function errorAt(token, message) {
  if (panicMode) return; // an echo
  panicMode = true;
  reporter.error(token.line, message);
}
```

The first error in a statement finds `panicMode` false, so it sets the
flag and reports; any further error before the statement ends returns
without a word, because it is probably an echo. (That `if` is the line I
deleted above.) When `declaration()`, the function that parses one
statement, has finished, it checks the flag and calls `synchronize()`,
which clears it and throws tokens away until it reaches a safe place:
just after a `;`, just before a keyword that begins a statement (`let`,
`if`, `while`, `print`, `fn`, `return` and the rest), or at a `}` that
closes the block the parser is in. Braces opened *while skipping* are
skipped whole, and the end of the file stops it too.

</Figure>

<Callout kind="definition">
**Panic mode** is error recovery by skipping. On an error the parser
reports it, keeps quiet about any more errors in the same statement, and
then discards tokens until it reaches a **synchronisation point** (a
token after which the grammar is likely to make sense again), where it
resumes normal parsing.
</Callout>

<Examples of="panic-mode">

```text
let x = 1
x = 2;
print x +;
# line 1: expected ';' after the
#   variable declaration, found 'x'
# line 3: expected an expression,
#   found ';'
```

</Examples>

The `let` wanted a `;` and found `x`, which is not a statement keyword,
so `synchronize` throws away `x`, `=` and `2` and stops just after the
`;`; then `print x +;` is parsed normally, and its own mistake is
reported. That is the price, too: `x = 2;` was skipped unchecked, so a
mistake there would wait for the next run. Panic mode accepts it,
because a missed error costs one more run, while a made-up one costs
confusion.

<More title="synchronize in full, and errors that cost almost nothing">

```ts
function synchronize() {
  panicMode = false;
  let depth = 0;
  while (current.type !== 'eof') {
    if (depth === 0) {
      if (previous.type === ';') return;
      if (STATEMENT_STARTS.has(
          current.type)) return;
      if (current.type === '}' &&
          blockDepth > 0) return;
    }
    if (current.type === '{') depth++;
    else if (current.type === '}' &&
             depth > 0) depth--;
    advance();
  }
}
```

`blockDepth` counts how many blocks the parser is inside, and the `}`
itself is left for the block to take, so the parser does not lose track
of where a function body ends. A missing `{` is handled the other way
round: for `if x > 1 print x;` the parser reports `expected '{' after
the condition`, parses no body at all, and checks `print x;` as a
statement of its own. And some errors cost almost nothing: for `a + b =
3;` the parser reports `cannot assign to this expression` and skips only
the `3` and the `;`, the rest of the same statement.

## What you learned

- A **syntax error** is a token the grammar did not allow; Drip reports
  `line N: expected <what>, found <token>` and then runs nothing.
- **Error recovery** aims to report every real error in one run, and no
  **cascading** errors.
- **Panic mode** reports the first error of a statement, drops the rest,
  and skips to a **synchronisation point**; skipped tokens go
  unchecked.
