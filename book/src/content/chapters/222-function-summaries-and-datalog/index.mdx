## Read it once, use it everywhere

Context sensitivity keeps callers apart by analysing a function again
for each context, and in a big program the number of contexts can be
enormous: every chain of k call sites that can reach a function is one
more copy of its facts. There is another way, and it was the second of
Sharir and Pnueli's two approaches, the "functional approach": analyse
each function once, and record not an answer but a *rule* that turns
what comes in into what goes out<Cite id="sharirpnueli1981" />. Then
each call applies the rule to its own arguments.

For `id`, the rule is a single sentence: "the result points at whatever
the parameter points at". At `a = id(o1)` that gives `{o1}`, at
`b = id(o2)` it gives `{o2}`: the precision of a context-sensitive
analysis, while `id` was read only once.

<Analogy title="the allergy label on a recipe">
A recipe card can carry a label like "contains whatever nuts you put
in the filling". The cook reads the label instead of the whole recipe,
and the label gives the right answer for every filling, because it
says how the answer depends on the input.
<span slot="breaks">A cook can always check the recipe if the label is
unclear; an analysis that uses a summary has thrown the body away, so
the summary must be safe for every possible input, and when it cannot
be precise, it has to say the worst.</span>
</Analogy>

<Callout kind="definition">
A **function summary** records, once per function, what the function
does with what flows into it: which parameters may be returned, stored
somewhere lasting, or passed on, and which fields it reads and writes.
At every call site the analysis applies the summary to that call's own
arguments, instead of re-reading the body.
</Callout>

<Formal title="Applying a summary">

```text
S_f : facts about the parameters
        → facts about the result
r = f(x):  facts(r) = S_f(facts(x))
```

<span slot="read">The summary of f, written S_f, is a function from
facts about f's parameters to facts about its result (and effects). At
a call where r is assigned f of x, the facts about r are what you get
by applying the summary to the facts about x at that call.</span>
</Formal>

<Examples of="function-summary">

```js
function id(p) { return p; }
// summary: result ⊇ pts(p)
```

```js
function setX(o, v) { o.x = v; }
// summary: for each obj in pts(o),
//   pts(obj.x) ⊇ pts(v); returns none
```

```text
$ go build -gcflags='-m -l' .
./main.go:23:11: p does not escape
./main.go:28:33: &P{...} does not escape
```

</Examples>

The first is `id` again: its summary needs no context at all, because
it is a rule about the parameter. The second records a side effect: a
call `setX(a, b)` means "a's objects get b's objects in their field
x", which is the store rule from two chapters back, applied at the
call. The third is real: Go's compiler (go1.24.7, with `-l` turning
inlining off) analyses `func read(p *P) float64 { return p.x }` once,
concludes "p does not escape", and at the call `read(&P{7, 8})` uses
that summary to decide the new `P` can live on the stack. Go's own
source calls these summaries "parameter tags", "used at static call
sites to improve escape analysis of function arguments"<Cite id="go-escape" />.

Recursion needs one more step: to summarise `f`, you may need `f`'s
own summary. The answer is the usual one: start every summary at
"does nothing", recompute them all, and repeat until none changes, a
fixpoint over summaries instead of over sets.

## An analysis as a page of rules

By now every analysis in this part has the same shape: some facts read
off the program, some rules of the form "if this and that, then this
other thing", and a loop that applies the rules until nothing new
appears. Real points-to analyses have dozens of such rules (fields,
arrays, casts, calls, contexts), and the hand-written loops become the
hardest part to get right. **Datalog** is a small logic language whose
whole job is exactly that loop: you write the facts and the rules, and
an engine finds the fixpoint.

<Analogy extra title="a family tree and the word “ancestor”">
Write down who is whose parent, then two rules: a parent is an
ancestor, and a parent of an ancestor is an ancestor. Anyone can now
find every ancestor by applying the rules again and again until no new
names turn up; nobody needs to write a search procedure.
<span slot="breaks">A family tree only goes back in time, so it never
loops; program facts often form cycles (a = b, b = a), and the rules
still stop because no rule ever invents a new name, so there are only
so many facts to find.</span>
</Analogy>

A **fact** is a row in a table, such as `New(a, o1)` ("a is assigned a
new object from site o1") or `Assign(a, c)` ("c = a"). A **rule** has
a head, `:-` (read "if"), and a body; variables shared between body
parts must match, which joins the tables. Here are the two rules that

That is Andersen's analysis from two chapters back, in two lines. Doop,
a points-to framework for Java by Bravenboer and Smaragdakis, is
written this way from end to end, including context sensitivity and
building the call graph on the fly<Cite id="bravenboer2009" />. Here is
its copy rule, quoted from its source<Cite id="doop-micro" />:

```text
VarPointsTo(?heap, ?to) :-
   Assign(?from, ?to),
   VarPointsTo(?heap, ?from).
```

It reads: the variable `?to` may point at `?heap` if there is an
assignment from `?from` to `?to` and `?from` may point at `?heap`.
Doop's other rules add a `Reachable(?method)` condition, so that only
methods the call graph has reached contribute facts, and a rule that
derives `Reachable` and `CallGraphEdge` from the points-to sets of
receivers: the call graph and the sets grow together, as the last
chapter said they must.

<Callout kind="definition">
In a **Datalog analysis**, the program is turned into facts (rows of
relations such as `Assign` and `New`), the analysis is written as
rules `head :- body`, and an engine derives every fact the rules allow,
repeating until a round adds nothing (the least fixpoint). Because
rules never invent new values, there are finitely many possible facts,
so evaluation always stops.
</Callout>

<Formal title="Reading a rule">

```text
H(x, z) :- A(x, y), B(y, z).
∀ x, y, z :  A(x, y) ∧ B(y, z) ⇒ H(x, z)
```

<span slot="read">The rule says: for all x, y and z, if A holds for x
and y, and (the wedge ∧) B holds for y and z, then H holds for x and z.
The shared y is the join: an A row and a B row combine only when they
agree on y.</span>
</Formal>

<Examples of="datalog-analysis">

```text
Path(x, y) :- Edge(x, y).
Path(x, z) :- Edge(x, y), Path(y, z).
```

```text
Pts(v, h)  :- New(v, h).
Pts(t, h)  :- Assign(f, t), Pts(f, h).
```

```text
Pts(c, t, h) :- Assign(f, t, c),
                Pts(c, f, h).
```

</Examples>

The first is a version of the warm-up in Doop's own Datalog
tutorial<Cite id="doop-micro" />: paths in a graph, from edges. The second is the analysis in the stepper. The third
shows how context sensitivity looks in Datalog: one more column, `c`,
the context, carried through each rule, so facts from different
contexts never join. Engines then make it fast: Soufflé, which is
"frequently used as a domain-specific language for analysis problems",
compiles the rules to parallel C++<Cite id="souffle-readme" />, and
Whaley and Lam's bddbddb compiled Datalog to binary decision diagrams
to handle huge numbers of contexts<Cite id="whaleylam2004" />. Run the

## What you learned

- A **function summary** is computed once per function and applied at
  every call to that call's own arguments, which gives context-sensitive
  precision without re-reading the body (Sharir and Pnueli's functional
  approach; Go's "parameter tags").
- Recursive functions are summarised by iterating all summaries to a
  fixpoint.
- A **Datalog analysis** writes facts as table rows and the analysis as
  rules; shared variables join tables, and evaluation repeats until a
  round adds nothing. It always stops, since rules invent no new values.
- Doop writes a whole context-sensitive points-to analysis for Java this
  way, and engines like Soufflé compile the rules to fast code.
