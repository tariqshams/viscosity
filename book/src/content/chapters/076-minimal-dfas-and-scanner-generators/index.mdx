## Two states that do the same job

Build the DFA for `a|b` the way the last chapter did, and it comes out
with three states: the start, the state after reading `a` and the state
after reading `b`. The last two are both accepting, and neither has any
arrows leaving it; whatever comes next, they react in exactly the same
way, so a machine with one of them in place of both accepts the same
strings with less to store. On a real scanner the subset construction
often leaves many such twins behind, and a smaller table means a
smaller, faster scanner (it fits better in the CPU's cache, the fast
memory of chapter 50).

<Analogy title="two routes that meet">
You can reach the motorway from the north car park or the south car
park, and once you are on it, every junction and every exit is the
same; from the motorway's point of view, which car park you came from
no longer matters, so a map that only cares about where you can still
go may draw the two as one.
<span slot="breaks">Real routes differ in ways a map ignores, such as
traffic; two DFA states only count as the same if *every* possible rest
of the input, of every length, gives the same verdict from both.</span>
</Analogy>

<Analogy title="identical twins at a quiz">
If two people give the same answer to every question you could ever
ask, then for the purposes of the quiz you only need one of them on the
team.
<span slot="breaks">You can never ask every question of real people;
for a DFA you do not need to, because a finite machine can be checked
by the splitting method below, which always finishes.</span>
</Analogy>

<Callout kind="definition">
Two states of a DFA are **equivalent** if, for every string `w`, running
`w` from one ends in an accepting state exactly when running it from the
other does. **DFA minimisation** merges each group of equivalent states
into one state; the result accepts the same language with the fewest
states possible. For a scanner, states that accept *different token
types* are never treated as equivalent.
</Callout>

<Formal title="Equivalent states">

```text
p ≡ q  ⟺  for all w:
  δ*(p, w) ∈ F  ⟺  δ*(q, w) ∈ F
```

<span slot="read">p is equivalent to q exactly when, for every string w,
running w from p ends in an accepting state if and only if running w
from q does. (δ star is the "run a whole string" function from the
chapter on finite automata, and F the set of accepting states.)</span>
</Formal>

## Splitting groups until nothing splits

Checking every string is impossible, but there is a way round it: start
by assuming as much as possible is equivalent, and split groups apart
only when there is evidence. Begin with two groups, accepting and not
(the empty string already tells those apart). Then, for each group and
each character, look at where its members go: if two members go to
*different* groups, they can be told apart, so split them. Repeat until
a whole round splits nothing; each group left is one state of the
minimal DFA. Step through it on the DFA that recognised "keyword `if`
or a name":

<MinimiseSteps client:visible />

The two runs end differently, and the difference is the most important
point of this chapter for scanners. As a *language*, "`if` or a name"
is just "a name", since `if` is spelled like one, so the minimal DFA has
two states and has forgotten the keyword entirely. A scanner must
report *which* token it found, so it starts with one group per token
type, and then the keyword state can never merge with a name state.

<Examples of="dfa-minimization">

```text
a|b DFA: S -a-> P, S -b-> Q, P and Q
accepting with no arrows: P ≡ Q,
2 states after merging
```

```text
if-or-name, language only: {A} {B,C,D}
nothing splits: 2 states
```

```text
if-or-name, as a scanner:
{A} {B,C} {D}, then B and C split on f:
4 states, already minimal
```

</Examples>

The first is the twins from the start of the chapter: P and Q are in the
same starting group and have no arrows to disagree about, so they merge.
The second and third are the stepper's two runs. This simple method
repeats rounds of splitting; John Hopcroft published a cleverer way of
choosing which groups to split next, which finishes in time
proportional to n log n for a DFA with n states<Cite id="hopcroft1971" />.

## Programs that write scanners

You now have every stage, so a program can run them all for you. You
write a file listing each token's pattern; the program builds a Thompson
NFA for each, joins them with ε-moves from one new start state (as in
the "`if` or a name" machine), runs the subset construction, minimises,
and prints out a scanner.

</Figure>

The best known early tool of this kind is **lex**, written at Bell Labs
by Mike Lesk and Eric Schmidt in 1975<Cite id="lesk1975" />; **flex** (the
"fast lexical analyser generator") is its free successor, still in use
today<Cite id="flex-manual" />. Here is part of Drip's scanner as a flex
rules file, with the pattern on the left and, in braces, the C code to
run when it matches:

```text
"let"                   { return LET; }
"fn"                    { return FN; }
[0-9]+("."[0-9]+)?      { return NUMBER; }
[A-Za-z_][A-Za-z_0-9]*  { return IDENT; }
"=="                    { return EQ_EQ; }
"="                     { return EQ; }
".."                    { return DOT_DOT; }
"."                     { return DOT; }
"#"[^\n]*               { /* comment */ }
[ \t\r\n]+              { /* skip */ }
```

When more than one rule could match, flex follows two rules of its own:
take the rule that matches the **most text**, and if two match the same
amount, take the one **listed first**<Cite id="flex-manual" />. So
`letter` is an `IDENT`, because the name rule matches six characters and
the `let` rule only three, while `let` on its own is `LET`, because both
match three characters and `let` comes first. A range such as `1..5`
comes out as `NUMBER`, `DOT_DOT`, `NUMBER`: the number rule cannot take
a dot with no digit after it, and `..` is longer than `.`. That is
maximal munch and
the reserved-word table of chapter 70, now expressed as the order of
lines in a file. Inside the DFA, it means each accepting state is
labelled with the earliest rule among its NFA states; state D in the
stepper holds both the keyword's and the name's accepting states, and
gets the keyword.

<Analogy title="a recipe book and a kitchen robot">
Writing the scanner by hand is cooking from scratch; a scanner generator
is a robot that reads your list of dishes and cooks them for you, the
same way every time.
<span slot="breaks">A robot cook cannot taste; a generated scanner
cannot do things the patterns cannot say, which is why real rules files
also allow code (to count lines, say, or to check a string's escapes) to
run when a pattern matches.</span>
</Analogy>

<Callout kind="definition">
A **scanner generator** (or *lexer generator*) is a program that takes a
list of token rules, each a regular expression with an action, and
writes the source code of a scanner for them; it builds a DFA through
the Thompson, subset and minimisation steps and resolves overlaps by
longest match, then by rule order. lex, flex and re2c are scanner
generators<Cite id="aho2006" />.
</Callout>

There are two common ways to print out the DFA. A **table-driven**
scanner stores the transition table as data and runs one small loop,
exactly like `run` in the finite automata chapter. A **direct-coded**
scanner turns each state into a block of code with comparisons and
jumps, so there is no table to look up at all; re2c works this
way<Cite id="re2c" />, and Cooper and Torczon compare the two
approaches with a hand-coded scanner like Drip's<Cite id="coopertorczon2022" />.

<Examples of="scanner-generator">

```text
"if"  { return IF; }
[a-z]+ { return IDENT; }
"if" -> IF   "ifs" -> IDENT   "i" -> IDENT
```

```text
"="  { return EQ; }
"==" { return EQ_EQ; }
"===" -> EQ_EQ, then EQ  (longest first)
```

<Run id="mini-lex" />

</Examples>

The first shows both of flex's rules at once: `if` is matched by both
rules with the same length, so the earlier rule wins; `ifs` is longer
for `[a-z]+`, so it is a name. The second shows that the order of lines
does not beat length: even with `=` listed first, `==` is one token
because it is longer. The runnable one is a tiny generator, written with
JavaScript's own regexes, that follows the same two rules: for one
position in the input it tries every rule and keeps the longest match.
(Each regex has the `y` flag, *sticky*, which makes it match only
starting exactly at the position stored in its `lastIndex` property,
rather than anywhere later in the string<Cite id="mdn-regexp-guide" />.) The exercise turns it into a
whole scanner.

JavaScript's regexes do not follow those rules on their own, and the
difference catches people out:

```js
/^(if|iffy)/.exec('iffy')[0]; // 'if'
/^(iffy|if)/.exec('iffy')[0]; // 'iffy'
```

A JavaScript alternation takes the first alternative that works, not
the longest<Cite id="ecma262" />, so a scanner built on one big
regex quietly depends on the order of its alternatives; a generator
that tries every rule and keeps the longest match does not.

<Callout kind="engine" label="Under the hood">
Drip's scanner is written by hand rather than generated: for a small
language, a page of loops is easy to read and gives full control over error
messages. Generated scanners shine when the token rules are many, change
often or must be exactly right, and the theory of the last three
chapters is what lets you trust them: every rule you write becomes one
fast, small, correct machine.
</Callout>

## What you learned

- Two DFA states are **equivalent** if every rest of the input gets the
  same verdict from both; **DFA minimisation** merges them, by
  splitting groups (accepting and not, or one group per token type)
  until no group splits.
- A **scanner generator** such as lex, flex or re2c turns a list of
  token rules into a scanner through Thompson, subset construction and
  minimisation, choosing the longest match and then the earliest rule.
- Generated scanners are table-driven or direct-coded; hand-written ones,
  like Drip's, trade that automation for control.
