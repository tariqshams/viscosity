## One shape, two loops

*AoS vs SoA, measured* showed that struct of arrays wins most when a
loop reads only some of the fields. Here are two suites from this
book's benchmark run; both use the same six-field records, but one
loop reads every field and the other reads one:

<BenchBars suite="read-all" n={100000} title="read-all: read all 6 fields" highlight={['soa']} layouts={['aos', 'soa']} caption="SoA still wins, but every column must be streamed through the cache." />

<BenchBars suite="sum-one-field" n={100000} title="sum-one-field: read 1 of 6 fields" highlight={['soa']} layouts={['aos', 'soa']} caption="With one field, SoA reads only the bytes the loop needs." />

The collection is the same; what differs is the loop. So before it can
decide anything, Viscosity needs to know, for every loop, what that
loop does to the collection's fields.

<Analogy title="a warehouse picker's clipboard">
A picker carries a clipboard with one line per aisle, and in each
aisle ticks which shelves they took from and which they restocked. At
the end of the day the clipboard says how the warehouse is really
used, and whether it is laid out well.
<span slot="breaks">The clipboard counts every visit, so a busy aisle
shows up as busy; Viscosity's table records *which* fields a loop
touches, not how often, so a loop that runs twice and one that runs a
million times look much alike.</span>
</Analogy>

<Callout kind="definition">
A loop's **access pattern** says what it does to a collection's
elements: which fields it **reads**, which it **writes**, how deeply
it is **nested** inside other loops, and how many **trips**
(iterations) it makes each time it runs, if that can be known.
</Callout>

In Viscosity it is one record per loop, from
`packages/core/src/analysis.ts`:

```ts
interface LoopAccess {
  func: string;   // the enclosing function
  line: number;   // the loop's header line
  depth: number;  // 0 = not in a loop
  reads: Set<string>;
  writes: Set<string>;
  trips: number | null; // per run
}
```

## Filing every access under a loop

By this point the safety pass has already collected every element
access: each `field.get` and `field.set` whose object is an element
`ps[i]`. (Note that `ps[i].x += 1` is two accesses, a read and a
write.) Building the table is a matter of filing each one under the
innermost **natural loop** around it, using the loops that *Loops*
found from back edges and dominators. Step through it:

<AccessSteps client:visible />

The real code is short. Simplified:

```ts
for (const a of c.accesses) {
  const f = funcOf.get(a.inst);
  const l = loopOf(loops(f), a.inst.block);
  const key = l ? f.id + ':' + l.header
                : f.id + ':none';
  let la = byLoop.get(key);
  if (!la) {
    la = newRow(f, l);
    byLoop.set(key, la);
  }
  const set = a.kind === 'read'
    ? la.reads : la.writes;
  set.add(a.field);
}
```

For each access, `f` is the function it is in; `loopOf` picks the
smallest loop whose body contains the access's basic block (or `null`
outside every loop); the key is that function plus the loop's header
block, so two accesses in the same loop always share a row; a row is
made the first time a key is seen (with its depth and trip count);
and the field is added to the row's reads or writes. Because rows hold
sets, reading `x` twice in one loop counts once.

<Formal title="One row of the table">

```text
Reads(L)  = { f | e.f is read,
                  innermost(e.f) = L }
Writes(L) = { f | e.f is written,
                  innermost(e.f) = L }
depth(L)  = 1 + #{ L' | L ⊊ L' }
```

<span slot="read">The reads of loop L are the fields f such that some
element's field f is read at a place whose innermost loop is L; the
writes are the same for writes. The depth of L is one more than the
number of loops L' that strictly contain it (in the code, a loop
contains L when its body holds L's header and is bigger). A depth of
0 means no loop at all.</span>
</Formal>

<Examples of="access-pattern">

```text
for (…10…) s += ps[i].x;
<module> line 11 depth 1 trips 10
  reads x
```

```text
ps[i].x += ps[i].vx; ps[i].y += ps[i].vy;
<module> line 5 depth 2 trips null
  reads vy, y, vx, x  writes y, x
```

```text
interproc_ok.js:
· loop at line 7 in centerOfMass()
  touches 2 of 3 fields (x, m)
· loop at line 11 in drift() touches 1
  of 3 fields (x)
```

</Examples>

The first two are real rows from the program in the diagram, printed
for this chapter. The first loop only reads `x`, and runs exactly ten
times. The second is the inner loop of the `t` loop, so its depth is
2; each `+=` is a read and a write, so `x` and `y` are in both sets,
in whatever order the analysis happened to meet them. The third is
`explain` on the corpus file `interproc_ok.js`, where `bodies` is
passed to two functions: because the key includes the function, each
gets its own row, and `explain` reports "touches k of F fields",
counting reads and writes together.

## Counting trips

**Depth** comes straight from the loop nest. **Trips** is harder, and
Viscosity only tries the easiest case, which *Induction variables and
loop invariants* would call a basic induction variable: the loop's
condition is `i < c` or `i <= c` for a constant `c`, where `i` is a
phi that starts at the constant `0` and steps by `1` each time round.
Here are two real loop headers in VIR:

<Figure takeaway="A trip count needs a counter from 0 by 1, and a constant bound." caption="The loop on line 11 compares its counter with the constant 10, so it runs 10 times. The loop on line 5 compares with ps.length, a field read, so its trip count is unknown.">
  <TripCount />
</Figure>

The check, simplified:

```ts
const tripCount = (f, l) => {
  const t = f.blocks[l.header].term;
  if (t.kind !== 'condbr') return null;
  const cond = inst(t.cond);
  if (cond.operator !== '<' &&
      cond.operator !== '<=') return null;
  const [iv, bound] = cond.args.map(inst);
  if (!isCountingPhi(iv, true) ||
      bound.op !== 'const') return null;
  return cond.operator === '<'
    ? bound.value : bound.value + 1;
};
```

It finds the branch that ends the loop's header; the condition must
be `<` or `<=`; its left side must be a counting phi from zero
(`isCountingPhi(iv, true)`) and its right side a constant; then the
answer is the constant, or one more for `<=`. So `i < 10` gives 10 and
`i <= 9` gives 10 as well; `i < ps.length` gives nothing, since a
length is not a constant in the code, and nor does a loop that starts
at 1 or steps by 2. Today the trip counts feed one line of `explain`:
a `push` inside loops with known trip counts adds their product to the
size estimate, which the cost model then reads.

## Hot loops

<Analogy extra title="a restaurant kitchen">
In a restaurant, the layout of the stove matters far more than the
layout of the storeroom, because the stove is where the cooks spend
their whole evening; a good kitchen is arranged around the busy
places.
<span slot="breaks">A chef knows where the evening goes from years of
watching; Viscosity has to decide before the program has ever run, so
it can only guess where the time will go, from the shape of the
code.</span>
</Analogy>

<Callout kind="definition">
A **hot loop** is a loop in which a program spends most of its time.
Those are the only loops whose memory layout is worth optimising.
</Callout>

Before the program runs, nobody knows for sure which loops are hot.
Viscosity uses the weakest sign that can be checked from the code: an
access counts only if it is inside a loop at all. The planner, in
`plan.ts`, throws away the depth-0 rows:

```ts
const fieldLoops =
  c.loops.filter((l) => l.depth > 0);
if (fieldLoops.length === 0)
  keep('no loop reads or writes its ' +
    'fields, so a new layout cannot ' +
    'pay off');
```

<Examples of="hot-loop">

```text
ps[3].x += 1;   (no loop)
· no loop reads or writes its fields,
  so a new layout cannot pay off
```

```text
for (let k = 0; k < 2; k++) ps[k].x += 1;
ps (line 1) {x, y} → struct of arrays
  · loop at line 4 … touches 1 of 2
```

```text
no_loops.js: fills ps in a loop, then
  only reads ps.length
· no loop reads or writes its fields,
  so a new layout cannot pay off
```

</Examples>

The first touches a field, but outside any loop, so it can never be
hot. The second shows the weakness of the stand-in: a loop that runs
**twice** counts just as much as one nested three deep, and the
collection is transformed (its 100 elements clear the size threshold).
The third is the corpus file `no_loops.js`: its only loop pushes, and
pushing is not a field access, so no row has depth above 0. Depth and
trip counts are recorded, but the planner does not yet weigh one loop
against another with them; *Profile-guided optimization* replaces the
guess with measurements from a real run.

<Prompts ids={['hl-what', 'hl-proxy']} />

<Callout kind="engine" label="Under the hood">
V8 finds its hot code by watching: functions start in the interpreter,
and the ones that run often move up to the optimising tiers, which use
the type feedback collected along the way<Cite id="v8-maglev" />.
Viscosity works before the program has run, so it cannot watch; it has
to read hotness off the code, and "inside a loop" is the part of that
it can be sure of.
</Callout>

## What you learned

- A loop's **access pattern** is its read set, write set, nesting
  depth and trip count for one collection.
- Viscosity files every element access under the **innermost** natural
  loop around it, one row per loop per function; accesses outside any
  loop get a depth-0 row. `x += 1` is a read and a write, and rows
  hold **sets** of fields.
- Trip counts are known only for loops like `i < 10` counting from 0
  by 1 against a constant; today they only feed the size estimate.
- A **hot loop** is where the time goes. Before the program runs,
  Viscosity's stand-in is "in a loop": with no field access in any
  loop, it keeps the array of objects.
