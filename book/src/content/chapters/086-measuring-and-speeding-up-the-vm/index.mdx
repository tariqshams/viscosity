## The numbers, as they came out

*Why bytecode* made a promise: flatten the tree into a compact list of
instructions, run them in one tight loop, and the interpreter gets
faster. The companion's benchmark script runs ten Drip programs on both
engines, each in a fresh process, and keeps the best of three runs:

<VmVsTreeChart />

The best the VM manages is 1.3 times faster (`method_calls`), and on
four programs (`fields`, `instantiation`, `strings` and `trees`) it is
*slower*. That is not the textbook result, and it is worth saying
plainly why, because the reasons are about where the program runs, not
about bytecode being a bad idea.

<Analogy title="a fluent reader and a phrasebook">
Suppose you hand a fluent reader a novel, and alongside it a version
rewritten in a compact shorthand of your own, with a key. For a
beginner the shorthand might be quicker; for someone who already reads
fast, looking up each symbol costs more than the shorthand saves.
<span slot="breaks">Shorthand loses meaning; bytecode loses nothing,
and on a host without a JIT (or in C) the same VM would beat the same
tree-walker comfortably.</span>
</Analogy>

There are three reasons. First, **V8 compiles both engines**: its
optimising tiers turn the tree-walker's hot `evaluate` methods into
machine code just as they do the VM's `run` loop<Cite id="v8-maglev" />,
so the tree-walker is far from the slow interpreter the argument
assumed (on a plain counting loop it was faster in my runs, 653 ms against
814 ms). Second, **every instruction is a trip round a
loop written in JavaScript**<Cite id="v8-sparkplug" />, about 21
nanoseconds each, most of it spent reading the opcode and choosing the
`case`, not doing the work. Third, **the VM rebuilds in JavaScript what
the tree-walker borrows from V8**: its own hash `Table` instead of V8's
built-in `Map`, and its own collector on top of V8's, which is why the
four slow programs are the ones about fields and allocation.

<More title="More: time the loop yourself">

<Run id="time-loop" />

That is the same loop, a tenth as long; `clock()` is in seconds, and
your numbers will differ from mine. A copy of the VM with instance
fields in a JavaScript `Map` ran `instantiation` 1.20 times faster than
the real one, and `fields` 1.09 times faster, which backs up the third
reason.

</More>

## Superinstructions

`inc.local` and `invoke` have something in common: each does, in one
instruction, the work that would otherwise take several. Since every
instruction pays its trip round the dispatch loop, fewer, bigger
instructions mean fewer trips:

<DispatchSteps client:visible />

<Callout kind="definition">
A **superinstruction** is a single opcode that does the work of a common
sequence of several, chosen by measuring which sequences run most
often. It saves dispatches and pushes and pops. Its costs are more
opcodes in the dispatch loop, a compiler that recognises the pattern,
and the rule that no jump may target the middle of the sequence.
</Callout>

<Examples of="superinstruction">

```text
inc.local 1
# = load.local 1, const 1, add,
#   store.local 1, pop
```

</Examples>

The compiler emits `inc.local` for the hidden counter of every `for`
loop, replacing five instructions with one, so each pass saves four
dispatches; for the three-million-pass loop that is twelve million,
exactly the difference between 51,000,015 and 39,000,015 instructions.

<More title="More: what fusing saves, as a formula, and CPython's superinstructions">

<Formal title="What fusing saves">

```text
T ≈ N × (d + w)
fuse k instructions, run f times:
  N' = N − (k − 1) × f
```

<span slot="read">Running time T is roughly the number of instructions
run, N, times the cost of a dispatch d plus the instruction's own work
w. Fusing a sequence of k instructions that runs f times removes k
minus 1 dispatches each time, while the work w stays about the
same.</span>
</Formal>

`invoke` is a superinstruction too: it fuses `get.prop` and `call`, and
as a bonus skips the bound method. CPython's compiler fuses two
adjacent `LOAD_FAST` instructions into `LOAD_FAST_LOAD_FAST`, but only
inside a straight run of code that jumps enter only at the top, and
only when both operands are small enough to share one
argument<Cite id="cpython-superinstructions" />.

</More>

## Every value in eight bytes

Real VMs use two ideas the companion does not: a smaller value and a
smarter collector. A VM written in C must lay out its own values, and
the tagged value of *Tagging values at run time* (a tag plus an 8-byte
payload) usually pads to 16 bytes per slot. **NaN-boxing** fits every value into one 8-byte
double instead. In IEEE 754, a double whose eleven exponent bits are all
ones and whose fraction is not zero is a NaN, and that is about 2⁵³ bit
patterns, of which arithmetic only ever produces one or two; so a VM can
pick a NaN pattern arithmetic never makes (here, the quiet-NaN bits plus
one extra "box" bit) and read any double with those bits set as a tag
and a payload instead of a number.

<NanBoxSteps client:visible />

<Callout kind="definition">
**NaN-boxing** represents every value as one 64-bit IEEE 754 double.
Numbers are stored as themselves; every other value is stored as a NaN
bit pattern that arithmetic never produces, with a tag (none, boolean,
object and so on) and a payload (a pointer or an index) in its fraction
bits. Telling a number from anything else is one mask and compare, and
every real NaN must be stored in one **canonical** form, so that no
real NaN ever looks boxed.
</Callout>

<Examples of="nan-boxing">

```text
1.5      hi 3ff80000  lo 00000000
none     hi 7ffc0001  lo 00000000
obj #7   hi 7ffc0004  lo 00000007
NaN      hi 7ff80000  lo 00000000
```

</Examples>

Each value is shown as its two 32-bit words. `1.5` is an ordinary
double. `none` and object number 7 both have the box pattern `7ffc` at
the top, with tags 1 and 4 at the bottom of the high word, and the
object's payload, the index 7, in the low word (in C it would be the
pointer itself). The canonical NaN has an all-ones exponent and the
quiet bit, but the box bit is clear, so the test `(hi & 0x7ffc0000) !==
0x7ffc0000` still reads it as a number. (In JavaScript, writing a NaN
into a typed array lets the engine choose its bit
pattern<Cite id="ecma262" />, so the canonical form matters there too.)

## Most objects die young

The collector of *Reclaiming memory: mark and sweep* marks every live
object on every collection. I counted how many of the objects present
at each collection survived it:

```text
program        collections  survived
instantiation           27      0.1%
closures                 4      0.1%
sort                     4      8.5%
trees                   10       54%
```

In three of the four nearly everything was already dead: the
**generational hypothesis**, that most objects die young, on which
production collectors are built<Cite id="v8-trash-talk" /> (`trees`,
keeping big trees alive, is the honest exception). So split the heap in two: new
objects start in the **young** generation, a *minor* collection looks
only at the young generation, which is small and mostly garbage, and
objects that survive a few minor collections are promoted to the
**old** generation, which is collected rarely.

<Figure caption="A generational heap: a minor collection traces only the young side, starting from the roots and the remembered set." takeaway="An old object pointing at a young one must be remembered, or the minor collection would free a live object.">
  <GenerationsFigure />
</Figure>

The catch is an old object pointing at a young one: a minor collection
does not trace the old generation, so a young object kept alive *only*
by an old one would look dead. The fix is a **write barrier**, a check
on every store of a reference, which records such old objects in a
**remembered set** that joins the next minor collection's roots.

<Callout kind="definition">
A **generational garbage collector** divides the heap by age. It
collects the young generation often and cheaply, promotes the objects
that survive, and collects the old generation rarely. Because a minor
collection skips the old generation, it needs a write barrier that
records old-to-young references in a remembered set, which serves as
extra roots.
</Callout>

<Examples of="generational-gc">

```text
let ps = [];       # survives, gets old
for i in 0..1000 {
  let s = [i, i];  # dies young
  push(ps, [i]);   # old -> young: barrier
}
```

</Examples>

Each `s` is garbage by the next pass, so a minor collection finds almost
nothing to keep among them, exactly the 0.1% above. `ps` lives for the
whole loop and would be promoted, and pushing a new list into it creates
an old-to-young reference that the barrier must record, or the next
minor collection would free `[i]` while `ps` still holds it. (Storing a
number, as in `o.f = 3`, creates no reference, so the barrier does
nothing.)

<Prompts ids={['gen-hypothesis', 'write-barrier']} />
