## A stopwatch is not enough

Every chart in this part came from a benchmark, and you have been asked
to trust it. Here is the benchmark almost everyone writes first:

```js
const t0 = performance.now();
sumAll(xs);
console.log(performance.now() - t0, 'ms');
```

`performance.now()` returns milliseconds with a
fraction<Cite id="mdn-performance-now" />, so this looks reasonable; yet
it is wrong in four ways. It times the function's first run, before the
engine has optimised it; it throws the result away, so a compiler may
skip the work; it trusts one measurement on a busy machine; and it may
run straight after another benchmark that left the engine in an odd
state. This chapter fixes all four.

## Warm-up: time the code that really runs

V8 first compiles a function to **bytecode** and interprets it, while
recording **feedback** (the object shapes and value types it sees at
each place in the code). Functions that get **hot** are compiled again
by faster **tiers**, Sparkplug and then the optimising compilers Maglev
and TurboFan, which use the feedback to build machine code specialised
for what they saw<Cite id="v8-maglev" />.

<Figure takeaway="Code climbs the tiers as it gets hot, and can fall back." caption="V8's tiers, as the V8 team describes them. Every function starts as bytecode in the Ignition interpreter; hot functions move up; the optimising tiers build on feedback, and drop back down (deoptimise) when one of their guesses turns out wrong.">
  <TierLadder />
</Figure>

That code is *speculative*: if a guess such as "`p` always has this
shape" breaks, V8 throws it away and falls back to a lower tier, which
is **deoptimisation**<Cite id="v8-maglev" />.

<WarmupSteps client:visible />

<Analogy title="a runner's first lap">
Timing a runner on their first lap of the morning, still stiff and
tying a shoelace, tells you little about how fast they run; a coach
lets them warm up, then times the laps that follow.
<span slot="breaks">A runner warms up the same way every morning; an
engine's warm-up depends on what the code has seen, so code that later
meets different data can lose its speed again, in a way no runner
does.</span>
</Analogy>

<Callout kind="definition">
**JIT warm-up** is the period in which code gets faster as the engine
observes it and recompiles it with better tiers (a **JIT**, "just in
time", compiler compiles while the program runs). A benchmark that
wants steady-state speed runs the code until it is warm, and only then
measures. **Deoptimisation** is throwing away optimised code whose
guesses broke, and falling back to slower code.
</Callout>

<Examples of="jit-warmup">

```js
for (let i = 0; i < 1e6; i++)
  add(i, 1);  // warm: numbers only
add('a', 'b'); // a string: deoptimise
```

</Examples>

A million calls with numbers make `add` hot, and the optimised code is
built on the guess "both arguments are numbers"; the first strings break
it, and `add` is slow again until it warms up anew. This book's harness
runs the work for at least 300 milliseconds and five times before
recording anything.

<More title="Try it: eight rounds of the same sum">

Each round sums a million-element `Float64Array`; on most machines the
first round or two are noticeably slower (a browser rounds the timer, so
very fast rounds may show 0).

## Dead code: make the result matter

Compilers delete work whose result nobody uses: **dead-code
elimination** is a standard optimisation, and LLVM ships several passes
that do it<Cite id="llvm-passes" />. A benchmark loop whose answer is
thrown away is a perfect candidate, and would report a near-zero time
for a loop that never ran.

<Callout kind="definition">
**Dead-code elimination** is a compiler deleting computations whose
results are never used and that have no other effect (no printing, no
storing, no throwing); it is legal because the program's output cannot
change. A **sink** is a variable that collects every measured result and
is used at the end, so the measured work stays observable.
</Callout>

<Examples of="dead-code-elimination">

```js
sumAll(xs);          // result goes nowhere
sink += sumAll(xs);  // result is kept
// ... and at the end:
console.log(sink);   // now it is live
```

</Examples>

The bare `sumAll(xs)` builds a value nothing reads, so an optimiser that
can prove the function has no other effect may remove the call
altogether. Adding the result into `sink`, which is printed, makes the
sum live, so the loop that produced it is live and the work has to
happen. Neither version throws an error, which is what makes the trap
dangerous: the broken one quietly reports a number.

<Formal title="What makes a computation dead">

```text
live(v) ⇐ v is printed, stored or returned
live(v) ⇐ v is used to compute a live w
dead(v) ⇔ not live(v)
```

<span slot="read">A value is live if it is printed, stored where the
outside world can see it, or returned, or if it helps compute another
live value; every other value is dead, and the work producing it may be
removed, provided that work has no other effect.</span>
</Formal>

## The median and p95

Suppose seven warm, sunk runs take these times, in milliseconds:
`2.1, 2.0, 2.2, 2.0, 30, 2.1, 2.3`. Six agree, and one is fifteen times
slower, perhaps because the garbage collector paused the program or
another program grabbed the CPU. Their mean is about 6.1, slower than
six of the seven; it describes no run at all.

<Analogy extra title="your commute">
Asked how long your commute takes, you say "about 25 minutes", not the
average with the day of the motorway crash in it; someone catching a
train also wants "how bad is a bad day?", say 40.
<span slot="breaks">A benchmark's slow samples can come from the program
itself (a pause its own allocations caused), so a long tail is sometimes
the real cost, not noise.</span>
</Analogy>

This book's harness takes 30 samples, sorts them, and reports the
**median** (what a typical run costs) and the **p95** (how bad the slow
end gets). Each sample lasts at least 10 milliseconds, repeating the
work and dividing, because browsers round `performance.now()` to 100
microseconds<Cite id="mdn-performance-now" />.

<MeasureSteps client:visible />

<Callout kind="definition">
The **median** of a set of timings is the middle one once they are
sorted (or halfway between the two middle ones); the **p95** (95th
percentile) is the value that 95% of the timings are at or below. Both
ignore a few wild outliers that drag the **mean** around. From n sorted
samples, the quantile q sits at position (n − 1) × q, interpolating
between the two slots either side.
</Callout>

<Examples of="median-p95">

```js
const s = [1, 2, 3, 4];
// median: pos = (4 - 1) * 0.5 = 1.5
s[1] + (s[2] - s[1]) * 0.5; // 2.5
```

</Examples>

Four samples have no single middle: the position 1.5 falls halfway
between slot 1 (`2`) and slot 2 (`3`), giving `2.5`. With 21 samples
the p95 sits at slot (21 − 1) × 0.95 = 19 exactly. (Sort timings with
`sort((a, b) => a - b)`: plain `sort()` compares as strings, so `30`
would come before `4`.)

<More title="Try it, and the quantile rule written out">

<Run id="mean-vs-median" />

<Formal title="A quantile from sorted samples">

```text
pos = (n − 1) × q
lo = ⌊pos⌋   hi = ⌈pos⌉
Q(q) = s_lo + (s_hi − s_lo) × (pos − lo)
```

<span slot="read">For a fraction q (0.5 for the median, 0.95 for p95)
the position is n minus 1, times q; the answer starts at the sample in
slot lo, rounded down, and moves towards slot hi, rounded up, by the
fraction left over.</span>
</Formal>

</More>

## One fresh process per case

V8's optimised code is specialised for the shapes it has
seen<Cite id="v8-maglev" />. If every layout of the `get-objects` suite
ran in one process, the shared `consume(p)` would see object literals,
then instances of one class, then another: mixed feedback, more general
and slower code, and each layout's time decided by which ran before it.

<Figure takeaway="Isolation keeps one layout's history out of another's timing." caption="If every layout ran in one process (left), consume would see three shapes, and the measurements would depend on the order. One fresh process per case (right) gives each layout a clean engine.">
  <IsolationPicture />
</Figure>

<Callout kind="definition">
**Benchmark isolation** means running each measurement in a fresh
process (or worker), so that the type feedback, compiled code and heap
state left by one case cannot affect another.
</Callout>

<Examples of="benchmark-isolation">

```js
for (const layout of LAYOUTS) {
  const out = execFileSync(
    process.execPath,  // Node itself
    ['case.ts', suite, layout, n]);
  rows.push(JSON.parse(out));
}
```

</Examples>

The harness's driver (simplified) starts a brand-new Node process for
each layout, which runs one case and prints its result as JSON. A fresh
process also has a fresh heap, so garbage left by one layout cannot
trigger a collection during the next; in the browser, `LiveBench` does
the same with a new Web Worker per layout.

Finally, this book's results came from a shared cloud machine, so
compare **ratios, not absolute times**: "SoA was about 3.8 times faster"
survives a busier machine, while "1.72 nanoseconds per element" does
not. A wide gap between median and p95 means the run was noisy; run it
again.

## What you learned

- **JIT warm-up**: measure only once the optimised tiers are running;
  **deoptimisation** can make code slow again.
- **Dead-code elimination** may delete unused work; a **sink** keeps it.
- Report the **median and p95** of many samples, never one run or the
  mean.
- **Benchmark isolation**: one fresh process per case; trust ratios.
