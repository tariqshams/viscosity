## A stopwatch is not enough

Every chart in this part of the book came from a benchmark, and you have
been asked to trust it. Here is the benchmark almost everyone writes
first:

```js
const t0 = performance.now();
sumAll(xs);
const t1 = performance.now();
console.log(t1 - t0, 'ms');
```

`performance.now()` returns the time in milliseconds, with a fraction<Cite id="mdn-performance-now" />,
so `t1 - t0` is how long `sumAll` took. It looks reasonable, yet it is
wrong in four separate ways. It times the function the very first time
it runs, before the engine has optimised it. It throws the result away,
so a clever compiler is allowed to skip the work. It trusts a single
measurement on a machine doing a hundred other things. And it may run
straight after some *other* benchmark that left the engine in an odd
state. This chapter fixes the first two, which are both about the
engine changing your code while you time it; the next chapter fixes the
other two.

## Warm-up: time the code that really runs

A JavaScript engine does not run your function the same way every time.
V8 first compiles everything to **bytecode** (a compact list of simple
instructions) and runs it in an interpreter, and while it runs, it
records how the program behaves, including the shapes of the objects
and the types of the values it sees; this record is called
**feedback**. Functions that get **hot** (called often, or looping a
lot) are compiled again by faster **tiers**: first Sparkplug, then the
optimising compilers Maglev and TurboFan, which use the feedback to
generate machine code specialised for what they saw<Cite id="v8-maglev" />.

<Figure takeaway="Code climbs the tiers as it gets hot, and can fall back." caption="V8's tiers, as the V8 team describes them. Every function starts as bytecode in the Ignition interpreter; hot functions move up; the optimising tiers build on feedback, and drop back down (deoptimise) when one of their guesses turns out wrong.">
  <TierLadder />
</Figure>

That optimised code is *speculative*: it is built on guesses such as
"`p` always has this shape". If a guess turns out wrong, V8 throws the
optimised code away and falls back to a lower tier, which is called
**deoptimisation**<Cite id="v8-maglev" />. Step through one function
warming up, and then deoptimising:

<Analogy title="a runner's first lap">
Timing a runner on their first lap of the morning, still stiff and
tying a shoelace, tells you little about how fast they run. A coach lets
them warm up first, then times the laps that follow.
<span slot="breaks">A runner warms up the same way every morning; an
engine's warm-up depends on what the code has seen, so code that later
meets different data can lose its speed again (a deoptimisation) in a
way no runner does.</span>
</Analogy>

<Analogy extra title="a new barista">
On a new barista's first morning, every order means reading the menu
and checking the recipe card, so it is slow. After a week they know
that the regular at nine wants a flat white and start it as she walks
in; when one day she asks for tea instead, the guess is wrong, the milk
goes down the sink, and they go back to the card.
<span slot="breaks">A barista remembers people; V8's feedback is about
the shapes and types of values at particular places in the code, and it
can be thrown away and relearned at any moment, without anyone being
told.</span>
</Analogy>

<Callout kind="definition">
**JIT warm-up** is the period in which code gets faster as the engine
observes it and recompiles it with better tiers (a **JIT**, "just in
time", compiler is one that compiles while the program runs). A
benchmark that wants steady-state speed must run the code until it is
warm, and only then start measuring. **Deoptimisation** is throwing
away optimised code whose guesses broke, and falling back to slower
code.
</Callout>

<Examples of="jit-warmup">

```js
sumAll(xs); // 1st call: bytecode, slow
sumAll(xs); // ...
sumAll(xs); // 500th: optimized, fast
```

```js
// only numbers seen so far...
for (let i = 0; i < 1e6; i++) add(i, 1);
add('a', 'b'); // a string: deopt
```

<Run id="warmup" />

</Examples>

The first shows the problem in three lines: the same call, on the same
data, takes different times depending on how many times it has run
before, because the engine has moved it up the tiers in between. The
second shows the fall back down: after a million calls with numbers, the
optimised `add` is built on the guess "both arguments are numbers", and
the first string breaks it. The third you can run: it times eight
rounds of summing a million-element `Float64Array`, and prints each
round's time and, at the end, the total. On most machines the first
round or two are noticeably slower than the rest, though the exact
numbers depend on your device (and a browser rounds the timer, so very
fast rounds may show as 0). This book's harness handles warm-up by
running the work for 300 milliseconds, and at least five times, before
recording anything.

## Dead code: make the result matter

The second trap is subtler, because the code it breaks looks fine.
Compilers delete work whose result nobody uses: it is a standard
optimisation called **dead-code elimination**, and LLVM, for example,
ships several passes that do it<Cite id="llvm-passes" />. A benchmark
loop whose answer is thrown away is a perfect candidate, and an
optimising compiler that removes it would make your benchmark report a
near-zero time for a loop that never ran.

<Analogy extra title="homework nobody marks">
A student notices that the teacher never collects question 4, so they
stop doing it; every mark they get is exactly the same as before, and
they finish sooner.
<span slot="breaks">The student is cutting a corner the teacher would
object to; a compiler that removes dead code is doing nothing wrong,
because the program's output cannot differ, and the only "victim" is a
benchmark that was timing work nobody needed.</span>
</Analogy>

<Callout kind="definition">
**Dead-code elimination** is a compiler deleting computations whose
results are never used and that have no other effect (no printing, no
storing, no throwing). A **sink** is a variable that collects every
measured result and is used at the end, so the measured work stays
observable.
</Callout>

<Formal title="What makes a computation dead">

```text
live(v) ⇐ v is printed, stored or returned
live(v) ⇐ v is used to compute a live w
dead(v) ⇔ not live(v)
```

<span slot="read">A value is live if it is printed, stored somewhere the
outside world can see, or returned; it is also live if it helps compute
some other live value. Every value that cannot be reached by those two
rules is dead, and a compiler may remove the work that produces it
(provided that work has no other effect, such as throwing an
error).</span>
</Formal>

<Examples of="dead-code-elimination">

```js
const area = w * h; // never used:
// a compiler may delete this line
```

```js
let s = 0;
for (const x of xs) s += x;
// s is never used: the loop is dead
```

```js
let sink = 0;
sink += sumAll(xs); // keep the result
console.log(sink);  // now it is live
```

</Examples>

The first is the simplest case: `area` is computed and then never read,
so by the rules above it is dead, and so is the multiplication. The
second is the benchmark case: the loop builds `s`, but nothing reads `s`
afterwards, so the whole loop is dead, and an optimiser that can prove
it may remove the loop. The third is the fix this book's harness uses:
every result is added into `sink`, and `sink` is printed, so the sum is
live, the loop that produced it is live, and the work has to happen.
Spot the difference between the two:

```js
// broken: the result goes nowhere
const t0 = performance.now();
sumAll(xs);
const ms = performance.now() - t0;
```

```js
// working: the result is kept
const t0 = performance.now();
sink += sumAll(xs);
const ms = performance.now() - t0;
```

Neither throws an error, which is what makes this trap dangerous: the
broken version quietly reports a number, and you have no way to tell
from the number alone whether the work happened.

## What you learned

- **JIT warm-up:** V8 interprets bytecode first and recompiles hot code
  with faster tiers that rely on feedback, so a benchmark must warm up
  before it measures.
- **Deoptimisation** throws optimised code away when one of its guesses
  breaks, and the code is slow again for a while.
- **Dead-code elimination** may delete work whose result is never used;
  it is legal because the program's output cannot change.
- A **sink** keeps every measured result observable, so the work cannot
  be deleted.

## Which number do you report?

The last chapter fixed two traps: the benchmark now warms up, so it
times optimised code, and it sinks every result, so the work cannot be
deleted. Suppose you run the warm loop seven times and get these
times, in milliseconds:

```js
[2.1, 2.0, 2.2, 2.0, 30, 2.1, 2.3]
```

Six of them agree, and one is fifteen times slower: maybe the garbage
collector (the part of the engine that frees memory nobody uses any
more) paused the program, or another program grabbed the CPU for a
moment. Which number describes your loop? And there is a second, quieter
question: if this benchmark had run straight after a different one, in
the same process, would you even have got these seven? This chapter
answers both, with the two remaining habits of an honest benchmark.

## The median and p95

<Analogy title="your commute">
Asked how long your commute takes, you say "about 25 minutes", even
though once, after a crash on the motorway, it took two hours; you
would not average the two hours in. But if someone needs to be sure of
catching a train, they also want to know "how bad is a bad day?", and
you might say "on a bad day, 40".
<span slot="breaks">A commute's bad days come from the outside world;
a benchmark's slow samples can also come from the program itself (a
garbage-collection pause the loop's own allocations caused), so a long
slow tail is sometimes the real cost, not noise.</span>
</Analogy>

<Analogy extra title="house prices on one street">
Ten houses on a street sell for about the same price, and then a
footballer's mansion sells for twenty times as much. The *average* price
on the street jumps, though no ordinary house got dearer; the price of
the middle house, the one with as many dearer houses as cheaper ones,
barely moves.
<span slot="breaks">House prices are a fixed list; benchmark samples
are drawn fresh every run, so the median itself wobbles a little from
run to run, which is one more reason to take many samples.</span>
</Analogy>

This book's harness takes 30 samples, sorts them, and reports two
numbers. The **median** (the 50% point) says what a typical run costs;
the **p95** (95% of samples were at most this slow) says how bad the
slow end gets. Step through the harness's `measure()` function, warm-up
and sink included:

<MeasureSteps client:visible />

Each sample also lasts at least 10 milliseconds, because one call of a
fast loop is too short to time: browsers deliberately round
`performance.now()` to 100 microseconds, or 5 in specially isolated
pages<Cite id="mdn-performance-now" />, so the harness repeats the
kernel until a sample is long enough and divides by the number of runs.

<Callout kind="definition">
The **median** of a set of timings is the middle one once they are
sorted (or halfway between the two middle ones). The **p95** (95th
percentile) is the value that 95% of the timings are at or below. Both
ignore a few wild outliers that would drag the **mean** (the average)
around.
</Callout>

<Formal title="A quantile from sorted samples">

```text
s₀ ≤ s₁ ≤ … ≤ sₙ₋₁   (sorted)
pos = (n − 1) × q
lo = ⌊pos⌋   hi = ⌈pos⌉
Q(q) = s_lo + (s_hi − s_lo) × (pos − lo)
```

<span slot="read">Sort the n samples from fastest to slowest. For a
fraction q (0.5 for the median, 0.95 for p95), the position is n minus
1, times q; usually it falls between two slots, lo (rounded down) and hi
(rounded up). The answer starts at the sample in slot lo and moves
towards the one in slot hi by the fraction left over. This is exactly
the harness's quantile function.</span>
</Formal>

<Examples of="median-p95">

```js
// odd count: the middle one
[1, 2, 9]; // median 2
```

```js
// even count: halfway between
[1, 2, 3, 4]; // pos 1.5, median 2.5
```

<Run id="mean-vs-median" />

</Examples>

The first is the simplest case: three sorted samples, position
(3 − 1) × 0.5 = 1, so the median is the sample in slot 1, `2`, whatever
the 9 might have been. The second has no single middle sample: the
position is (4 − 1) × 0.5 = 1.5, halfway between slot 1 (`2`) and slot
2 (`3`), which gives `2.5`. The third you can run: it takes the seven
timings from the start of the chapter, prints their mean (about 6.1,
higher than six of the seven samples) and then sorts a copy and prints
the middle one, `2.1`, which is what a typical run really costs. Notice
`sort((a, b) => a - b)`: plain `sort()` compares as strings, so `30`
would sort before `4`.

## One fresh process per case

The last trap is the sneakiest, because each benchmark on its own is
fine. V8's optimised code is specialised for the shapes and types it has
seen<Cite id="v8-maglev" />. Suppose the `get-objects` suite ran every
layout in one process: the shared `consume(p)` function would see
object literals, then instances of one class, then of another, three
different shapes. Its feedback becomes mixed, so the code optimised for
it is more general and slower, and each layout's time would depend on
which layouts ran before it.

<Analogy extra title="tasting with a clean glass">
At a wine tasting, you rinse your glass (and your mouth) between wines;
otherwise the second wine tastes partly of the first, and the order you
tasted them in decides your verdict.
<span slot="breaks">A rinse leaves a little behind and you can still
taste fine; with an engine, the leftover feedback can change which
machine code runs at all, so the only reliable rinse is a completely
new engine.</span>
</Analogy>

<Figure takeaway="Isolation keeps one layout's history out of another's timing." caption="If every layout ran in one process (left), consume would see three shapes, and the measurements would depend on the order. One fresh process per case (right) gives each layout a clean engine.">
  <IsolationPicture />
</Figure>

<Callout kind="definition">
**Benchmark isolation** means running each measurement in a fresh
process (or worker), so that the type feedback, compiled code and heap
state left by one case cannot affect another.
</Callout>

<Examples of="benchmark-isolation">

```js
// one process per case
for (const layout of LAYOUTS) {
  const out = execFileSync(
    process.execPath,
    ['case.ts', suite, layout, n],
  );
  rows.push(JSON.parse(out));
}
```

```js
// not isolated: consume sees all three
timeLayout('aos', consume);
timeLayout('aos-class', consume);
timeLayout('aos-ctor', consume);
```

```js
// in the browser: a fresh Worker
const w = new Worker(url, {
  type: 'module',
});
```

</Examples>

The first is the driver from this book's harness (simplified): for
every layout, `execFileSync` starts a brand-new Node process
(`process.execPath` is the path to Node itself) that runs one case and
prints its result as JSON, which the driver collects. A fresh process
also starts with a fresh heap, so garbage left by one layout cannot
trigger a collection during the next. The second is the version to
avoid: three layouts timed one after another in the same process,
sharing one `consume`, so the third is measured with feedback from the
first two. The third is how the in-browser `LiveBench` from the AoS vs
SoA chapter does the same thing: a new Web Worker (a separate
JavaScript engine running beside the page) for each layout.

## Noise is normal

This book's results came from a shared cloud machine, and the results
file says so: expect noise, and compare **ratios, not absolute times**.
A ratio like "SoA was about 3.8 times faster on `update-xy`" survives a
slower or busier machine; "1.72 nanoseconds per element" does not. When
a result surprises you, run it again, and look at the p95 next to the
median: a wide gap means the run was noisy.

<Callout kind="engine" label="Under the hood">
This harness is more than a teaching aid. The hand-written layouts it
measures are the baselines that Viscosity's *generated* code will be
compared against, and when the compiler claims "this program should be
SoA", the claim is checked by exactly these rules: warm, sunk,
summarised by median and p95, one process per case. An optimiser is
only as honest as the benchmark that judges it.
</Callout>

## What you learned

- Summarise many samples with the **median** (a typical run) and the
  **p95** (the slow end), not with one run or the mean.
- A quantile comes from sorted samples, interpolating between the two
  slots either side of its position.
- **Benchmark isolation:** one fresh process (or worker) per case, so
  feedback, compiled code and heap state cannot leak between layouts.
- On shared machines, trust **ratios**, and read the gap between the
  median and the p95 as a measure of noise.
