## Fourteen bytes and two questions

Here is the two-line program `print 1.5 + 2;` and `print "hi";` as the
bytes Drip's compiler makes for it:

```text
0, 0, 0, 0, 0, 1, 20, 33,
0, 0, 2, 33, 1, 49
```

With the opcode table from *Why bytecode* you can start decoding: `0` is
`const`, and `0, 0` says "constant number 0". However, the bytes do not
contain `1.5` anywhere; and if the program stopped with an error, which
source line should the message name? The bytes need company: a table of
the values they refer to, and a note of where each byte came from.

<Analogy title="a parcel and its delivery note">
A parcel arrives with the small items inside and an envelope taped to
the top, holding a numbered list of the bulky items coming separately
("item 2: one garden bench") and a note of which order each item belongs
to. The box is the code, the numbered list is the table of constants,
and the note is the line numbers.
<span slot="breaks">A delivery note is read once; the VM reads the
constants every time an instruction refers to one, and reads the line
numbers only when something goes wrong.</span>
</Analogy>

## A chunk: three arrays side by side

Drip's VM keeps bytecode in a `Chunk`, from `vm/chunk.ts`:

```ts
export class Chunk {
  code: number[] = [];
  /** the source line of each byte */
  lines: number[] = [];
  constants: Value[] = [];

  write(byte: number, line: number): void {
    this.code.push(byte);
    this.lines.push(line);
  }

  addConstant(v: Value): number {
    this.constants.push(v);
    return this.constants.length - 1;
  }
}
```

`code` holds the bytes, `lines` one source line per byte, and
`constants` the values the code refers to (`Value` is any Drip value).
`write` is the only way a byte gets into `code`, and it pushes the
byte's line in the same breath, so `lines[i]` is always the line of
`code[i]`; `addConstant` appends a value and returns its index, the
number the code will use to name it. Step through the compiler filling
the chunk for the two-line program:

<ChunkSteps client:visible />

<Callout kind="definition">
A **chunk** is a unit of compiled bytecode: an array of instruction
bytes (`code`), a parallel array giving the source line of each byte
(`lines`), and the constants the instructions refer to. In Drip's VM
every function has its own chunk, and the script itself is compiled as
a function too, so a program is a tree of chunks, one per function.
</Callout>

<Examples of="chunk">

```text
print 7;

code:      0, 0, 0, 33, 1, 49
lines:     1, 1, 1, 1, 1, 1
constants: [7]
```

</Examples>

`const 0` is three bytes, `print` is 33, and the `none` and `return`
that end every script are 1 and 49; all six bytes come from line 1, and
the pool holds the one value. A function's instructions are not in the
script's chunk at all: the script's pool holds the compiled function,
with its own chunk inside, starting again at offset 0.

## The constant pool

A byte holds 0 to 255; `1.5` is an eight-byte float, and a string can
be any length. So the compiler puts each value in `constants` and
writes only its index into `code`: `const 2` means "push
`constants[2]`". The index is two bytes, so it can name constants 0 to
65,535, and indexes past that are the compile error `too many constants
in one function` (per function, since each has its own pool).

<Figure takeaway="Instructions name constants by index." caption="The real instructions for let x = 1.5; print x + 2;. Each one's last two bytes are an index into the pool; the name x is there twice, once for each mention.">
  <PoolLookup />
</Figure>

<Callout kind="definition">
A **constant pool** is a table of the literal values a chunk uses
(numbers, strings, and the functions defined inside it). Instructions
refer to a constant by its index in the pool rather than containing it.
In Drip the index is a two-byte operand, so one function can hold up to
65,536 constants.
</Callout>

<Examples of="constant-pool">

```text
let x = 7;
print x;
print x;

0000    1 const               0 '7'
0003    | define.global       1 'x'
0006    2 load.global         2 'x'
0009    | print
0010    3 load.global         3 'x'
```

</Examples>

The disassembler prints each operand followed, in quotes, by the
constant it names. A global is looked up by its name, and the name `x`
is added three times, at indexes 1, 2 and 3: `addConstant` never looks
for an existing copy. That is wasteful but simple, and with 65,536
entries to spend it does no harm in practice.

<Analogy extra title="a cloakroom ticket">
You hand your big coat over the counter and get a small numbered ticket
that fits in your pocket; the ticket says exactly which hook the coat
is on.
<span slot="breaks">A cloakroom hands each coat back once; a constant
stays in the pool, fetched again every time the instruction runs.</span>
</Analogy>

<More title="makeConstant, and how V8 keeps instructions small">

```ts
function makeConstant(v: Value): number {
  const c = chunk().addConstant(v);
  if (c > 0xffff) {
    // reports: too many constants in
    // one function
    return 0;
  }
  return c;
}
```

`0xffff` is 65,535, the largest number two bytes hold; returning 0 lets
compiling carry on and find other errors. V8's Ignition takes the same
attitude to size: it is a register machine whose special *accumulator*
register is an unwritten input and output of many bytecodes, which the
V8 team explain keeps the bytecodes smaller<Cite id="v8-ignition" />.

</More>

## Reading bytecode back

Reading bytes by hand with the opcode table open is slow and easy to
get wrong, so the companion has a **disassembler**, `vm/debug.ts`, which
prints the listings you have been reading:

```text
== <script> ==
0000    1 const               0 '1.5'
0003    | const               1 '2'
0006    | add
0007    | print
0008    2 const               2 'hi'
```

Each line is one instruction: its **offset** (the index of its opcode in
`code`), its source line (or `|` when it is the same as the byte
before), its name, and its operands. The offsets go 0, 3, 6, 7 because
a `const` is three bytes and an `add` one. And that is the one tricky
thing: nothing in a byte says whether it is an opcode or an operand, so
the disassembler must decode one instruction to learn its length before
it knows where the next starts:

```ts
for (let offset = 0;
     offset < chunk.code.length; ) {
  const [text, next] =
    disassembleInstruction(chunk, offset);
  lines.push(text);
  offset = next;
}
```

There is no `offset++`; the loop moves by whatever the instruction
says. The length comes from the opcode's operand shape, a `switch` with
one group of cases per shape:

<Callout kind="definition">
A **disassembler** prints bytecode as readable text, one instruction
per line, usually with its offset, its source line, its name and its
operands. It must decode instructions in order from the start, because
only the opcode says how many operand bytes follow.
</Callout>

<Examples of="disassembler">

```text
let n = 3;
if n > 2 {
  print "big";
}

0012    | gt
0013    | jump.unless        13 -> 20
0016    3 const               4 'big'
0019    | print
0020    4 none
```

</Examples>

`jump.unless` has a two-byte jump operand (here the bytes `0, 4`), and
the disassembler prints the jump's own offset and, after the arrow, the
offset it lands on: 13 + 3 + 4 = 20, just past the `print`, which is
where the program goes when `n > 2` is false. *Jumps: branches, loops
and backpatching* builds jumps.

<Analogy extra title="a sentence with no spaces">
"itisnotable" says "it is not able" split one way and "it is notable"
split another; you read it right only from the start, knowing where
each word ends.
<span slot="breaks">A person can guess the split from meaning; a
disassembler never guesses, it starts at offset 0 and steps by each
instruction's length.</span>
</Analogy>

## The lines array at work

When an instruction fails, the VM knows only its offset; `lines` turns
that into a source line. `print 1;`, then `print 2 +` with `-"a";` on
the next line, prints `1` and stops with `cannot negate a string at
line 3`:

<Figure takeaway="The failing byte's offset finds its line." caption="The neg instruction at offset 10 fails. The VM has already moved ip on to 11, so it reads lines[ip - 1], which is 3.">

The VM reads `lines[ip - 1]` because the instruction pointer has already
moved past the failing opcode. V8's Sparkplug makes a similar bargain
for its machine code, keeping a mapping back to bytecode offsets that
it consults only when a stack trace or the debugger asks<Cite id="v8-sparkplug" />.

## What you learned

- A **chunk** is three arrays: `code`, `lines` (one per byte) and
  `constants`; every function has its own.
- The **constant pool** holds what does not fit in a byte; a two-byte
  index allows 65,536 constants per function.
- A **disassembler** decodes from offset 0, stepping by each
  instruction's length, and prints offset, line, name and operands.
