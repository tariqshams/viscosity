## No processor has a phi

The IR of `sumsq` is still in SSA form, and its loop header begins
with two phis:

```text
b1:  ; preds b0 b2
  s1 = φ(s0, s2)
  i1 = φ(i0, i2)
```

(You met phis in *SSA and phi nodes, built on the fly*; these are the
phis `%6` and `%3` of the IR in *Machine code and assembly*, renamed so
that `s0`, `s1`, `s2` are the versions of `s`, and `i0`, `i1`, `i2`
those of `i`.) A phi means "take `s0` if we arrived from b0, and `s2`
if we arrived from b2"; however, RISC-V has no instruction that looks
back to see which way control came in, so before register allocation
the back end must say the same thing with ordinary copies. That step
is called leaving SSA, or **SSA destruction**.

The idea is to choose *before* the join instead of at it: put the
copy `s1 = s0` at the end of b0 and `s1 = s2` at the end of b2, and
whichever way control arrives, `s1` already holds the right value, so
the phi can be deleted.

<Analogy title="packing your bag before you leave">
You go to the gym from home on some days and from the office on
others. Rather than working out at the gym where your towel might be,
you put it in the same pocket of your bag before you set off,
wherever you set off from; at the gym, it is always in that pocket.
<span slot="breaks">This only works if leaving the office always
means going to the gym; if you sometimes leave it for the cinema, you

below.</span>
</Analogy>

<Analogy extra title="a relay handover">
In a relay, the baton changes hands in a zone at the end of the
outgoing runner's leg; the next runner does not have to know who ran

<span slot="breaks">A relay leg has one runner before it; a join

</Analogy>

LLVM does this too: "the most traditional PHI deconstruction algorithm
replaces PHI instructions with copy instructions. That is the strategy
adopted by LLVM"<Cite id="llvm-codegen" />. Here is its output for
`sumsq` (run with `llc -O2` and printed after its phi-elimination
pass; kill flags and branches left out):

```text
bb.0.entry:
  %4:gpr = COPY $x10
  %6:gpr = COPY $x0
  %5:gpr = COPY %6:gpr
  %8:gpr = COPY %5:gpr
  %9:gpr = COPY %5:gpr
bb.1.head:
  %1:gpr = COPY %9:gpr
  %0:gpr = COPY %8:gpr
  BGE %1:gpr, %4:gpr, %bb.3
bb.2.body:
  %7:gpr = MUL %1:gpr, %1:gpr
  %2:gpr = ADD %0:gpr, %7:gpr
  %3:gpr = ADDI %1:gpr, 1
  %8:gpr = COPY %2:gpr
  %9:gpr = COPY %3:gpr
```

`%4` is `n`, arriving in `$x10` (that is `a0`), and `%5` is the
zero, copied (via `%6`) from `$x0`; `%1` is
`i` and `%0` is `s`. The copies into `%8` and `%9` at the ends of
bb.0 and bb.2 are our copies, made into fresh names, which bb.1 then
copies into `%1` and `%0`. That is a lot of copies for a three-line
loop; coalescing (*Coalescing*, after graph colouring) removes every one
of them.

<Callout kind="definition">
**SSA destruction** (leaving SSA) replaces every phi
`x = φ(a1, ..., an)` in a block B by copies: for each predecessor
`Pk` of B, the copy `x = ak` is placed at the end of `Pk`, after its
last ordinary instruction and before its branch. The phi is then
deleted. The result is no longer in SSA form, because `x` is assigned
once per predecessor.
</Callout>

<Formal title="Out of SSA, one phi at a time">

```text
B: x = φ(a1, …, an),  preds P1 … Pn
⟹  append  x := ak  to Pk   (k = 1 … n)
    delete the phi
```

<span slot="read">Take a phi in block B that defines x from operands
a1 up to an, one per predecessor P1 up to Pn. Leaving SSA appends the
copy "x gets ak" to the end of the k-th predecessor, for every k, and
deletes the phi. It is only safe when Pk leads nowhere but B.</span>
</Formal>

## A copy needs a road of its own

A copy at the end of a predecessor that can also branch somewhere
else runs on the other path too. The edge from such a block to a
join is a **critical edge** (you met them in *Partial redundancy
elimination*): its source has several successors and its target
several predecessors, so there is no block that runs exactly when that
edge is taken. The cure is the same as there: **split** the edge, by putting a new, empty block on it,
and place the copy there.

Loops make this common. Here is a loop tested at the bottom (the
rotated shape of *Code shape: lowering control flow and data*), where `x` counts up and `y` keeps its
value from the trip before:

```text
x = 1
loop:
  y = x
  x = x + 1
  if x < 3 goto loop
return y
```

In SSA, `x` has a phi at the top of the loop, and `y1 = x2` is a copy.
The middle end's **copy propagation** (replacing every use of a name
that is only a copy of another by the other, a close cousin of
the constant propagation of *Dataflow, fixpoints and constant
propagation*) rewrites `return y1` as
`return x2` and lets dead-code elimination delete the copy:

```text
b0: x1 = 1
b1: x2 = φ(x1, x3)       ; preds b0 b1
    x3 = x2 + 1
    if x3 < 3 goto b1 else b2
b2: return x2
```

It should return 2: the first trip sets `y` to 1, the second to 2,
and then `x` is 3 and the loop stops. The back edge b1 → b1 is
critical (b1 has two successors and two predecessors); put the copy
`x2 = x3` at the end of b1 anyway, and watch:

<LostCopySteps client:visible />

The naive version returns 3: on the last trip the copy runs although
control is leaving the loop, overwriting the `x2` that the code after
the loop still needed. This is the **lost-copy problem**, named by Briggs, Cooper, Harvey and Simpson, who showed
that naive phi removal stops being safe once SSA-based optimisations
have moved things around<Cite id="briggs1998" />: before copy
propagation `x2` died inside the loop, and afterwards it is live out
of b1 at the same time as `x3`.

<Callout kind="definition">
The **lost-copy problem** is the wrong result naive SSA destruction
gives when a phi operand's copy is placed on a path where the phi's
old value is still live: the copy overwrites it too early. It happens
on critical edges, typically back edges, once optimisations such as
copy propagation have stretched a phi's value past the loop.
</Callout>

<Examples of="ssa-destruction">

```text
b3: x = φ(a, b)   ; preds b1 b2
→ b1: ...; x = a; j b3
  b2: ...; x = b; j b3
```

```text
b1: k = φ(0, k2)  ; preds b0 b2
→ b0: ...; li k, 0
  b2: ...; k = k2; j b1
```

```text
sumsq:
  b0: s1 = s0; i1 = i0
  b2: s1 = s2; i1 = i2; j b1
```

</Examples>

The first is the simplest case, an `if` and an `else` joining at b3:
each arm ends with its own copy into `x`, and no edge is critical,
since each arm has one successor. In the second, a constant operand's
copy becomes `li k, 0`. The third is `sumsq`: both edges into b1
leave blocks with one successor, so the copies go at the ends of b0
and b2.

<Examples of="lost-copy-problem">

```text
b1: x3 = x2 + 1
    x2 = x3            ; naive copy
    if x3 < 3 goto b1
b2: return x2          ; gives 3
```

```text
b1: x3 = x2 + 1
    if x3 < 3 goto b5
b2: return x2          ; gives 2
b5: x2 = x3
    goto b1
```

<Run id="lost-copy" />

</Examples>

The first is the bug: the copy sits in b1, so it also runs on the
way out to b2. The second is the cure: the back edge runs through the
new block b5, the only place the copy executes. The third runs the
original loop and both translations as JavaScript and prints `2 3 2`;
change the `3` in all three loop conditions to `5`, and the naive one
is still one too high.

## Correct first, tidy later

Another cure needs no new blocks: copy each operand into a fresh
name at the end of its predecessor, and the phi's result out of a
fresh name at the top of its block, so the names a phi joins never
overlap. That is always correct, and it is the shape of LLVM's output
above (the `%8` and `%9` copies); it also makes far too many copies,
so the second half of the job is removing them. Boissinot and
colleagues made this the recipe, correctness by inserting copies and
then quality by coalescing them away, and report it as simpler and
faster than earlier methods<Cite id="boissinot2009" />.

<Callout kind="engine" label="Under the hood">
Not every back end has phis to remove. Cranelift's register
allocator, regalloc2, takes **block parameters** instead: a branch
passes values to its target the way a call passes arguments, and the
allocator inserts the moves on each edge, because it is "much closer
to the truth to actually put those uses *in* the predecessor, on the
branch"<Cite id="regalloc2" />. Viscosity never leaves SSA at all: its
VIR is only analysed, and its output is made by editing the original
JavaScript source, so there are no phis to turn into copies.
Textbooks treat out-of-SSA translation in the same two steps as this
chapter<Cite id="coopertorczon2022" />.
</Callout>

## What you learned

- **SSA destruction** replaces each phi `x = φ(a1, ..., an)` by a copy
  `x = ak` at the end of each predecessor `Pk`, then deletes it.
- A copy cannot go at the end of a block that can also branch
  elsewhere: on a **critical edge**, split the edge with a new block
  and put the copy there.
- The **lost-copy problem** is what goes wrong if you do not: after
  copy propagation, a phi's value can still be needed after the loop,
  and a naive copy on the back edge overwrites it.
- Compilers insert copies freely for correctness, then coalesce.
