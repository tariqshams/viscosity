## The language under the language

Drip, the language the Core builds, is written in TypeScript, so every
value a Drip program makes is a JavaScript value underneath, and every
Drip rule is enforced by JavaScript code. When that code surprises you,
it is nearly always one of a handful of run-time facts: what `=`
copies, what a `Map` compares its keys by, what a closure keeps, where
a method lives, how an error travels, when a generator runs, and what
the event loop does while your interpreter runs (nothing). This chapter
gives each one in a few lines, with the Prelude chapter that teaches it
in full.

<Analogy title="a cloakroom ticket">

<span slot="breaks">A ticket shows its number; a JavaScript reference

## References, and what a Map compares

A variable that holds an object holds a reference to it, so `=` copies
the reference and both names reach one object (*References: two names,
one object*). `Map` and `Set` compare keys the same way `===` mostly
does: numbers and strings by value, objects by
identity<Cite id="mdn-equality" /><Cite id="mdn-map" />, and they find
a key by hashing it rather than by searching (*Hashing: finding without
searching*).

<Examples of="identity map">

```js
const a = { x: 1 };
const b = a;
const c = { x: 1 };
const m = new Map([[a, 'A']]);
m.get(b);         // 'A'
m.get(c);         // undefined
const t = new Map([['1,2', 'A']]);
t.get(`${1},${2}`); // 'A'
```

</Examples>

`b = a` copies the reference, so `m.get(b)` finds the key; `c` is a
lookalike with the same contents in a different place, so `m.get(c)`
misses. When an engine wants to look things up by contents (a pair of
numbers, say), it builds a string or number key from them, as the last
two lines do. Step through it:

## Closures and classes

A function remembers the variables around the place it was written, and
keeps them alive as long as the function itself is reachable (*Closures:
functions that remember*)<Cite id="mdn-closures" />. A class puts its
methods on one shared prototype object, and reading `t.is` walks the
prototype chain from the instance to find it (*Overriding and the
prototype chain*)<Cite id="mdn-prototype-chain" />.

<Examples of="closure prototype-chain">

```js
function counter() {
  let n = 0;
  return () => ++n;
}
const next = counter();
next(); next(); // 2

class Tok {
  constructor(k) { this.k = k; }
  is(k) { return this.k === k; }
}
const t = new Tok('num');
Object.hasOwn(t, 'k');  // true
Object.hasOwn(t, 'is'); // false
```

</Examples>

`counter` has returned, yet `n` lives on inside the arrow function,
which is why the second call gives 2: a closure captures the variable
itself, not a copy of its value. In `Tok`, the field `k` is the
instance's own, while `is` lives once on `Tok.prototype` and every
instance finds it there, so a million tokens share one copy of each
method.

## Errors that carry data

`throw` unwinds the call stack, frame by frame, until a `try` with a
`catch` takes it (*Error objects and how errors travel*); a class that
`extends Error` can carry what the catcher needs<Cite id="mdn-error" />.
The book's interpreter reports run-time errors this way:

```js
class RuntimeError extends Error {
  constructor(line, msg) {
    super(msg);
    this.line = line;
  }
}
try { throw new RuntimeError(3, 'bad'); }
catch (e) {
  if (e instanceof RuntimeError)
    console.log(e.line, e.message); // 3 bad
}
```

The `instanceof` test matters: a `catch` catches everything, including
your own bugs, so it should handle the errors it expects and throw the
rest on.

## Generators, and the event loop

A `function*` returns an iterator without running its body; each
`next()` runs it up to the next `yield` and pauses there, which makes it
a natural shape for a stream of tokens produced only when asked for
(*Iterators and generators*)<Cite id="mdn-iteration-protocols" />.

```js
function* digits(s) {
  for (const ch of s)
    if (ch >= '0' && ch <= '9') yield ch;
}
[...digits('a1b2')]; // ['1', '2']
```

Finally, the event loop, only as far as an engine needs it.
JavaScript runs one job at a time, to the end; promise callbacks wait as
microtasks until the current job finishes, and timers wait for a later
turn (*Asynchronous code: promises and the event loop*)<Cite id="mdn-microtask-guide" />.

```js
setTimeout(() => console.log('timer'));
Promise.resolve()
  .then(() => console.log('micro'));
console.log('sync');
// sync, micro, timer
```

So an interpreter's main loop, which is ordinary synchronous code, is
never interrupted by a timer or a promise; nothing else on the page or
in the process runs until it returns.

## What you learned

- `Map` and `Set` find objects by **identity** and strings by value.
- A **closure** keeps its variables alive; methods live once on the
  **prototype**.
- A thrown error unwinds frames to the nearest `catch`; an error class
  can carry data.
- A generator runs only when asked; a job runs to the end before any
  microtask or timer.
