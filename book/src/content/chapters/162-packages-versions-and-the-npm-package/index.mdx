## Can I install it?

Somebody likes Viscosity and types `npm install viscosity`. What they
get is a library at version 0.3.0, "a sass library for fluid containers
that handle aspect ratios across device sizes": the name `viscosity` on
npm belongs to someone else. What they want is `npm install -g
@viscosity/cli`, after which `viscosity --version` prints `viscosity
0.0.2` (in November 2026). Getting there meant three questions: what a
package is, what its number promises, and how to ship Rust to machines
you have never seen.

<Analogy title="a sealed box with a label">
A package is a sealed box on a warehouse shelf, with a label that says
exactly what is inside: a name and a version. Once a labelled box is on
the shelf it never changes. A fix goes into a new box with a new label,
and the numbers on the label tell the customer how different the new box
is.
<span slot="breaks">A box is the same for every customer; a package's
dependencies are fetched fresh for each one, so two installs of the
"same" package can differ unless every dependency is pinned.</span>
</Analogy>

## What a package is

Here is the CLI's `package.json` (some fields left out):

```json
{
  "name": "@viscosity/cli",
  "version": "0.0.2",
  "bin": {
    "viscosity": "bin/viscosity.mjs"
  },
  "files": ["bin", "dist", "LICENSE",
    "THIRD_PARTY_LICENSES.txt"],
  "engines": { "node": ">=18" }
}
```

`@viscosity/` is a **scope**, a namespace owned by one
organisation<Cite id="npm-publish-docs" />. `bin` installs a `viscosity`
command<Cite id="npm-package-json" />, `files` limits the tarball to those
paths (npm always adds `package.json` and the README), and `engines` says
which Node versions it supports.

<Callout kind="definition">
An **npm package** is a folder described by a `package.json`, packed into
a tarball and published to a **registry**, identified by its **name**
(possibly scoped, `@scope/name`) and **version**; `dependencies` lists the
packages it needs, with version ranges.
</Callout>

<Examples of="npm-package">

```text
$ npm view @viscosity/cli@0.0.2 \
    dist.fileCount
6
```

</Examples>

The registry's answer for the real CLI: six files (the bin file, the
bundle, `package.json`, the README and two licence files).

<Prompts ids={['pkg-what']} />

Packed as it first was and installed into an empty folder, the way a
stranger would, the CLI showed three bugs no test in the repository
could see:

<ShipSteps client:visible />

The one that matters most for any TypeScript package: Node 22.18 and
later strip TypeScript types, but deliberately refuse to under
`node_modules`<Cite id="node-typescript-docs" />. The fix was a build
step that bundles everything into one plain `dist/viscosity.mjs`.

<Prompts ids={['pkg-ts']} />

<More title="The other two bugs, the bin file, and what bundling costs">
The core was imported by a relative path that exists only in the
repository's layout, with no declared dependencies; and a "run only when
executed directly" check compared `import.meta.url` with
`process.argv[1]`, which through npm's link in `node_modules/.bin` is the
link's path, so the command exited quietly having done nothing. The
bundle has no runtime dependencies, and a two-line bin file calls `main`:


```js
#!/usr/bin/env node
import { main } from
  '../dist/viscosity.mjs';
process.exit(main(process.argv.slice(2)));
```

npm asks that every `bin` file start with the `#!` line, or the script is
not run by Node<Cite id="npm-package-json" />. Because a bundle contains
other people's code (acorn, acorn-walk, sucrase), the build also writes
`LICENSE` and `THIRD_PARTY_LICENSES.txt`.

<Analogy extra title="moving out of a flat">
When you move out, you find out which things were yours and which came
with the flat: the kettle you used every day belongs to the landlord.
A package leaving its repository finds out the same way what the
repository was quietly providing.
<span slot="breaks">You notice a missing kettle the first morning; a
package's missing pieces may show up only on a stranger's machine, which
is why the test is to install the tarball somewhere empty.</span>
</Analogy>
</More>

## What a version promises

npm works in **semantic versioning**<Cite id="npm-package-json" />: given
MAJOR.MINOR.PATCH, bump MAJOR for incompatible API changes, MINOR for
compatible features and PATCH for compatible fixes, resetting the numbers
to the right<Cite id="semver2" />.

<Figure takeaway="Bump one part; reset everything to its right." caption="The three ways out of version 1.9.3.">
  <BumpTree />
</Figure>

The parts compare as **numbers**, so `1.10.0` is newer than `1.9.0`; a
published name and version can never be reused<Cite id="npm-publish-docs" />;
and major version zero is for initial development, where "anything MAY
change at any time"<Cite id="semver2" />.

<Callout kind="definition">
**Semantic versioning** (semver) numbers releases MAJOR.MINOR.PATCH,
bumped for a break in the **public API**, a compatible feature or a
compatible fix, with the parts to the right reset to 0. Versions compare
as numbers, and 0.y.z promises nothing.
</Callout>

A dependency names a *range*, and npm installs the newest release in it.
The usual caret range, `^`, stops at the next change in the leftmost
non-zero part<Cite id="node-semver-ranges" />:

<CaretSteps client:visible />

<Examples of="semantic-versioning">

```text
1.9.3 + a bug fix     → 1.9.4
1.9.4 + a new option  → 1.10.0
1.10.0 + a removed
  option              → 2.0.0
```

```text
"dependencies": {
  "@viscosity/cli": "^0.0.1"
}   # accepts 0.0.1 and nothing else
```

</Examples>

The first walks three releases: a fix bumps the patch, a new option the
minor (9 + 1 is 10, not "91"), a removal the major. The second is
Viscosity's own choice: everything was first published at 0.0.1, which
Cargo reads the same way, so no dependent picks up a newer release
without asking. The same evening the npm packages went out again as
0.0.2 (a README for the CLI, a corrected dataclass message), and a
project asking for `^0.0.1` still gets 0.0.1; the crates on crates.io
are still at 0.0.1.

<Prompts ids={['sv-rules', 'sv-numeric', 'sv-caret', 'sv-cargo']} />

<More title="Comparing versions, run; and what Viscosity's public API is">

<Run id="semver-compare" />

Line 4 prints `false`, because `'1.10.0' > '1.9.0'` compares character by
character and `'1'` sorts before `'9'`; `parse` splits each version at
the dots and turns the pieces into numbers, and the last line prints
`true`.

<Formal title="Ordering versions, and a caret range">

```text
(a,b,c) < (x,y,z)  iff  a < x
   or (a = x and b < y)
   or (a = x and b = y and c < z)
^1.2.3 = [1.2.3, 2.0.0)
^0.1.0 = [0.1.0, 0.2.0)
^0.0.1 = [0.0.1, 0.0.2)
```

<span slot="read">Version a.b.c comes before x.y.z if the first part
that differs is smaller, compared as numbers. A caret range accepts
everything from the given version up to, but not including, the next
version that changes the leftmost non-zero part.</span>
</Formal>

Semver starts with a demand: declare your public API, because the numbers
only mean something relative to it<Cite id="semver2" />. For Viscosity
that is the CLI's commands and options, the plugin API, the explain text
(scripts will search it), and arguably the decisions themselves: a
release that keeps a collection it used to transform has identical
output, so by semver's letter it is a fix, but a user who measured a
speed-up may disagree. Deciding, and writing the decision down, is part
of shipping.

<Analogy extra title="editions of a book">
A reprint that fixes typos is a patch; a new edition that adds a chapter
but keeps every page number is a minor release; a revised edition that
renumbers the chapters is a major release.
<span slot="breaks">Publishers decide by habit; semver only means
something against a *declared* public API.</span>
</Analogy>
</More>

## Two ways to ship Rust

A compiled Rust program is not the same everywhere: `cargo build
--release` gives me an ELF executable for x86-64 Linux, which a Mac
cannot run. One answer is esbuild's: version 0.27.7 lists 26
`optionalDependencies`, each declaring the `os` and `cpu` it runs on, so
npm installs only the one that matches<Cite id="npm-package-json-platform" />.
The other is to compile once to WebAssembly and let the JavaScript engine
run it<Cite id="wasm-bindgen-guide" />.

<Figure takeaway="Native means one build per platform, chosen at install time; WebAssembly means one build for all of them." caption="On the left, npm installs the one esbuild package whose os and cpu match the machine. On the right, every platform, and a browser tab, runs the same .wasm.">
  <ShipTwoWays />
</Figure>

<Callout kind="definition">
**Native binaries vs WebAssembly**: a native build is compiled for one
operating system and CPU, fastest and free to use threads and files, but
one per platform. A `.wasm` is one file for every platform, run by the
host's JavaScript engine: slower, and on `wasm32-unknown-unknown`
`std::fs` returns errors and `std::thread::spawn`
panics<Cite id="rustc-wasm32-unknown-unknown" />.
</Callout>

<Examples of="native-vs-wasm">

```json
"os": ["linux"], "cpu": ["x64"]
```

```js
const { compile } =
  require('@viscosity/wasm');
```

</Examples>

The first is from `@esbuild/linux-x64/package.json`. The second is
`@viscosity/wasm`: one package for every machine, whose `exports` map
hands Node one glue and a browser bundler the other.

<Prompts ids={['native-vs-wasm-what']} />

<More title="The exports map, and what is in the box">
Each key inside an `exports` entry is a **condition**. Node sets
`"node"` and either `"import"` or `"require"`; a bundler building for the
web uses `"browser"`. The first key whose condition is active wins,
`"default"` always matches and so comes last, and a nested object that
matches nothing falls back to its parent's next
key<Cite id="node-packages-exports" />. TypeScript reads the same map and
always matches `"types"`<Cite id="ts-modules-reference" />. Step through
five importers on the real map:

<ExportsSteps client:visible />

Packed, `@viscosity/wasm` 0.0.2 is 13 files, 997 KiB (2,840 KiB
unpacked), most of it two copies of the 1.4 MB module, because each glue
file loads the module sitting next to it. The third big file is
`THIRD_PARTY_LICENSES.txt`: the `.wasm` *statically links* 71
third-party Rust crates (oxc's parser, `indexmap`, the ICU4X Unicode
crates, wasm-bindgen itself), so their notices must travel with it.
`build.mjs` asks `cargo tree` which crates are linked for the target,
finds their licence files through `cargo metadata`, and writes each
distinct text once (oxc's crates are published without their licence
file, so the package carries copies of oxc's own).

`smoke.mjs` installs the package the way a stranger would: `npm pack`,
install into a fresh directory, compile 60 corpus programs (40
JavaScript, 20 Python) through it three ways, compare with the
TypeScript CLI, and type-check a small consumer. When this chapter was
first written it reported four mismatches, all in Python explain text,
and the package was not at fault: the oracle, the TypeScript CLI's
committed bundle, had been built before a change of wording. That
corrected wording is what 0.0.2 carries. Run on the 0.0.2 tree, it
prints `✓` for all three ways, with 0 mismatches.

The npm `binaryen` package that `build.mjs` uses for `wasm-opt` is
itself WebAssembly, "a port of `wasm-opt` to JavaScript+WebAssembly … on
any platform that Node.js runs on"<Cite id="binaryen-readme" />.

<Run id="pick-native" />

That program does what npm does with esbuild's list, for whatever machine
compiles it: it asks Rust for `std::env::consts::OS` and `ARCH`,
translates Rust's names into Node's (`macos` is `darwin`, `x86_64` is
`x64`), and picks the one matching package of 26.
</More>

## What you learned

- An **npm package** is a tarball described by `package.json`, identified
  by **name** and **version**.
- **Semantic versioning** bumps MAJOR, MINOR or PATCH and compares as
  **numbers**; `^0.0.1` is 0.0.1 alone.
- **Native** builds are fastest but per platform; one **.wasm** serves
  every platform.
