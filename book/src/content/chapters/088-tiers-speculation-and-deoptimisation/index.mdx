## The same function, three ways

Your Drip VM runs a function the same way on every call; V8 does not,
as this program shows by printing, whenever it changes, which kind of
code is running `add`.

```js
// node --allow-natives-syntax tiers.js
function add(a, b) { return a + b; }
function tier(f) {
  return %ActiveTierIsTurbofan(f) ? 'TF'
    : %ActiveTierIsSparkplug(f) ? 'SP'
    : 'Ignition';
}
let last = '', s = 0;
for (let i = 1; i <= 1e5; i++) {
  s = add(s, i);
  const t = tier(add);
  if (t !== last) console.log(i, t);
  last = t;
}
```

One run on Node v22.23.4 printed `1 Ignition`, `10 SP`, `11668 TF`,
`65537 SP` and `81791 TF` (Sparkplug, then TurboFan; the numbers move
between runs): one line of code, three ways of running it, and a fall
*back* just after call 65,536.

## Start cheap, spend on what is hot

<Analogy title="a chalkboard menu">
A new café writes its dishes on a chalkboard, which is quick and easy to
change, and only a dish that keeps selling earns a place on the printed
menu; effort goes where the demand turned out to be.
<span slot="breaks">The café decides once; V8 keeps watching, and takes a
function off its "printed menu" the moment the reason for promoting it
stops being true.</span>
</Analogy>

Most code runs a handful of times, so compiling it all to the best
machine code first would waste time and memory; V8 starts each function
in the cheapest tier and spends more only once it is **hot** (in V8 12.4,
once it has run enough bytecode<Cite id="v8-src-tiering-12-4" />),
compiling *during* the run:

<TierSteps client:visible />

<Callout kind="definition">
**Tiering** is running each function in one of several **tiers** (ways
of executing the same code, from cheap to start and slow, to costly to
start and fast) and moving it up as it gets hot<Cite id="v8-ignition" />.
A **JIT compiler** (just in time) compiles while the program runs, so it
can use what has happened so far, and its compile time is part of the
running time.
</Callout>

<Examples of="tiering jit-compiler">

```
// node --trace-opt tiers.js, trimmed
[marking … add … for optimization
  to TURBOFAN, ConcurrencyMode::
  kConcurrent, reason: hot and stable]
```

</Examples>

V8 judged `add` "hot and stable" and compiled it on another thread
(`kConcurrent`) while the loop carried on, which is also why a function's
first calls are its slowest (the warm-up of *Benchmarking honestly*).

<More title="More: the hotness budget, --jitless, and warm-up you can time">

<Formal title="When a function is hot enough for TurboFan (V8 12.4)">

```text
budget(f) = length(f) × 3000
spent(f)  = Σ bytes of bytecode f ran
spent(f) ≥ budget(f)  ⇒  optimize f
```

<span slot="read">The budget of f is its bytecode length times 3000; what
f has spent is the sum (Σ) of the bytecode it has run, charged on every
return and every backward jump of a loop. Once spent reaches budget, V8
marks f for optimisation (⇒, "implies"). The 3000 is a tuning knob of one
version (`--invocation-count-for-turbofan`), not a law.</span>
</Formal>

So a function with a thousand-step loop inside gets hot in a few calls,
and one that runs once is never optimised at all. Ten million
calls of `add` took 11 ms normally and 326 ms under `node --jitless`,
which turns every compiler to machine code off (one run, Node v22.23.4).
When a hot loop is still running, V8 can swap optimised code in mid-loop:
**on-stack replacement** (OSR)<Cite id="v8-sparkplug" />.

## Ignition, and three compilers above it

Every function starts in **Ignition**, V8's interpreter since V8 5.9
(2017)<Cite id="v8-launch-ignition-turbofan" />. Drip's VM is a stack
machine; Ignition is a register machine with an **accumulator**, one
register most instructions use without naming it<Cite id="v8-ignition" />.
Above it sit three compilers to machine code:

<Figure caption="V8's tiers, as the V8 team described them between 2016 and 2023, and which of them the Node 22 build used in this book has switched on." takeaway="Each tier up costs more to compile and runs faster.">
  <TierLadder />
</Figure>

<Callout kind="definition">
**Ignition** is V8's bytecode interpreter, a register machine with an
implicit accumulator, whose instructions carry **feedback slots**. Above
it are the **optimising tiers**: **Sparkplug**, one fast pass with no
optimisations, which removes the interpreter's decode and dispatch
cost<Cite id="v8-sparkplug" />; **Maglev**, a quick optimising compiler;
and **TurboFan**, slow to compile and the fastest
code<Cite id="v8-maglev" />. Maglev and TurboFan specialise the code for
what the feedback slots recorded.
</Callout>

<Examples of="ignition optimizing-tiers">

```
// node --print-bytecode: add
@ 0 : 0b 04     Ldar a1
@ 2 : 3b 03 00  Add a0, [0]
@ 5 : ae        Return
```

</Examples>

`Ldar a1` loads `b` into the accumulator, `Add a0, [0]` adds `a` to it,
and `Return` returns it; the `[0]` is a feedback slot, where this `+`
records what kinds of value it saw<Cite id="v8-src-interpreter-12-4" />,
which Drip never did. (This Node build has Maglev switched off, so the
opening run skipped it; the deep dive *Ignition and the tiers above it*
goes further.)

## Feedback, and a bet on it

`+` adds numbers, joins strings and calls `valueOf` on objects, so a
generic `Add` must find out which case it is in on every call; yet `add`
is nearly always called the same way, and the feedback slot notices:

<FeedbackSteps client:visible />

The optimising compiler does not prove that record will stay true; it
*speculates*, and puts a check (a **guard**) in front of each guess: for
`o.x` with one shape seen, a map check and then a load at a fixed
offset<Cite id="v8-maglev" />; for `a + b` with small integers seen, a Smi
check on each operand and an add that checks for
overflow<Cite id="v8-leaving-sea-of-nodes" />.

<Figure caption="The shape of speculative code for a + b when feedback says SignedSmall. Each check on a guess has a side exit; the labels are the reasons --trace-deopt prints when one fails." takeaway="Past the guards, the code can ignore every other case.">
  <GuardFigure />
</Figure>

<Callout kind="definition">
**Type feedback** is what unoptimised code records about the values it
sees (operand kinds at an `Add`, shapes at a property access, the
function called at a call site), kept in each function's feedback
vector<Cite id="v8-maglev" />; it only ever widens. **Speculation** is
compiling code that is correct only while that feedback stays true, each
assumption protected by a guard or by a **dependency** that invalidates
the code when the assumption breaks.
</Callout>

<Examples of="type-feedback speculation">

```
// %DebugPrint(add): ints, 1.5, strings
 - slot #0 BinaryOp BinaryOp:SignedSmall
 - slot #0 BinaryOp BinaryOp:Number
 - slot #0 BinaryOp BinaryOp:Any
```

</Examples>

Each state is a fact about the past, not a promise: the opening run's
TurboFan code bet on `SignedSmall`, and the running sum passed
2<sup>31</sup> − 1, the largest Smi in this build, at call 65,536.

<More title="More: the feedback lattice, two more kinds of feedback, and a guard in plain JavaScript">

<Formal title="Feedback for +, as a lattice">

```text
None ⊑ SignedSmall ⊑ Number ⊑ Any
after a call a + b :  fb ← fb ⊔ kindOf(a, b)
```

<span slot="read">The states are ordered from narrowest to widest (⊑).
After each call the slot becomes the join (⊔, "the wider of the two") of
what it said before and what this call saw, so, like an array's elements
kind, it only moves one way. V8 has a few more states, such as one for
strings.</span>
</Formal>

A property load's feedback is its inline cache (`LoadProperty
MONOMORPHIC` with the map and a field handler), and a call site's
feedback records which function was called, which a compiler needs before
it can inline it. A global that has never changed needs no check at all:
Maglev builds it in as a constant and registers a dependency
instead<Cite id="v8-maglev" />.

## When a guess fails

A guard fails in the *middle* of a call; the call cannot start again (it
may have changed something) or fail (the program did nothing wrong), so
it must continue in code that handles every case:

<DeoptSteps client:visible />

So at every point that can deoptimise, the optimised code carries a map
of where each interpreter register's value lives, the **frame
state**<Cite id="v8-maglev" />:

<Figure caption="The frame the deoptimiser built for add('a', 'b'), read off --trace-deopt-verbose, next to add's bytecode." takeaway="Ignition resumes at the very instruction the optimised code could not finish.">
  <FrameRebuild />
</Figure>

<Callout kind="definition">
**Deoptimisation** leaves optimised code when an assumption fails and
continues the same call in unoptimised code, rebuilding the interpreter
frame from the saved frame state and resuming at the same bytecode, so
the result is the same as if nothing had been optimised. **Engine
tracing** means running with flags such as `--print-bytecode`,
`--trace-opt` and `--trace-deopt` so that the engine reports its
decisions; they are V8-internal, and their names and output can change in
any release<Cite id="v8-flag-definitions" />.
</Callout>

<Examples of="deoptimization engine-tracing">

```
// --trace-opt --trace-deopt, trimmed
[bailout (kind: deopt-eager,
  reason: not a Smi): … add …,
  bytecode offset 2, …]
ab
```

</Examples>

After 100,000 integer calls, `add('a', 'b')` failed the Smi guard, and
`ab` is the program's own output: the call still gave the right answer, because Ignition resumed at offset 2, the `Add`, with `b` already
in the accumulator. The optimised code is unlinked<Cite id="v8-lazy-unlinking" />,
and the failed call widened the feedback, so when `add` is optimised
again a second string call passes with no bailout; repeating the failed
guess would be a **deoptimisation loop**<Cite id="v8-leaving-sea-of-nodes" />.

<More title="More: reading a bailout line, and two surprising deopts">

<DeoptLineSteps client:visible />

The kind is *eager* when a check inside the optimised code failed, as
here; V8 12.4 defines a lazy kind too<Cite id="v8-deopt-kinds" />. Integer
code can deoptimise as well: `function sq(x) { return x * x; }`, called
with 0 up to 99,999, bails out with `reason: overflow`, because
46341 × 46341 is the first square past the largest Smi; and `sq('3')`
afterwards gives `not a Number or Oddball`. A loop over two
`Float64Array`s, by contrast, prints no bailouts at all, which is the
answer you want for your own hot loops. The deep dive *Watching the
engine work* covers the rest of the flags, `--trace-gc` included.
