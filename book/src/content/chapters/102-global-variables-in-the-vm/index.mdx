## A VM with no memory

By the end of chapter 101 the VM is a good calculator. It compiles
`print (1 + 2) * 3;` to bytecode and runs it. But try this:

```js
let total = 10;
total = total + 5;
print total;
```

The compiler has no idea what `let` means, and the VM has nowhere to
put `total`. In chapter 74 the tree-walker solved this with a `Map`
from names to values. The VM will do the same thing, with one change:
the table is the hash table you built in chapter 100, and its keys are
the interned strings of chapter 101.

<Callout kind="intuition">
A cloakroom. You hand over your coat, and it goes on a hook. To get it
back you say your name, and the attendant looks it up. Globals work
exactly like that: the name is the ticket, and every visit means a
look-up at the counter.
</Callout>

## A name becomes a constant

A bytecode instruction can't carry a string inside it: its operands
are single bytes. So the compiler puts the variable's *name* into the
chunk's constant pool, as a string, and the instruction refers to it by
index. Here is the helper in `compiler.ts`:

```ts
const identifierConstant =
  (name: VmToken) =>
    makeConstant(
      heap.copyString(name.lexeme));
```

`copyString` interns the name, so every mention of `total` in the
program becomes a pointer to the *same* string object. And here is how
a `let` is compiled, slightly simplified:

```ts
function letDeclaration() {
  const global = parseVariable(
    'Expect variable name.');
  if (match('=')) expression();
  else emit(OP.NIL);
  consume(';', ...);
  emit(OP.DEFINE_GLOBAL, global);
}
```

`parseVariable` consumes the name and returns its constant index.
Then the initializer is compiled, which leaves its value on top of the
stack at run time. No initializer? Push `nil`. Finally, one
instruction says "store the top of the stack under this name".

Reading and assigning go through `namedVariable`. When a name isn't a
local (the next chapter), it becomes a global:

```ts
arg = identifierConstant(name);
if (canAssign && match('=')) {
  expression();
  emit(OP.SET_GLOBAL, arg);
} else {
  emit(OP.GET_GLOBAL, arg);
}
```

Here is the real disassembly of a four-line program:

```js
let a = 1;
print a;
a = a + 2;
print a;
```

```text
== script ==
0000    1 OP_CONSTANT         1 '1'
0002    | OP_DEFINE_GLOBAL    0 'a'
0004    2 OP_GET_GLOBAL       2 'a'
0006    | OP_PRINT
0007    3 OP_GET_GLOBAL       4 'a'
0009    | OP_CONSTANT         5 '2'
0011    | OP_ADD
0012    | OP_SET_GLOBAL       3 'a'
0014    | OP_POP
0015    4 OP_GET_GLOBAL       6 'a'
0017    | OP_PRINT
0018    5 OP_NIL
0019    | OP_RETURN
```

Look at the constant numbers after the global instructions: 0, 2, 4, 3,
6. Each mention of `a` added a new entry to the pool. They are all the
same interned string, though, so the waste is a few slots of the pool,
not a few copies of the text. (Constant 0 comes before constant 1
because the name is read before the initializer.) And `a = a + 2`
ends in `POP`: an assignment produces a value, and an expression
statement throws it away.

## Three instructions

Now the VM side, from the dispatch loop in `vm.ts`:

```ts
case OP.DEFINE_GLOBAL:
  this.globals.set(readString(),
    this.peek(0));
  this.pop();
  break;
case OP.GET_GLOBAL: {
  const name = readString();
  const v = this.globals.get(name);
  if (v === undefined)
    this.runtimeError(`Undefined ` +
      `variable '${name.chars}'.`);
  this.push(v);
  break;
}
```

`readString` reads the operand byte and fetches that constant.
`DEFINE_GLOBAL` *peeks* at the value, stores it, and only then pops.
That order looks fussy, but it keeps the value on the stack, where the
garbage collector of chapter 107 can see it, until it is safely in the
table. `DEFINE_GLOBAL` never complains about an existing name: like
the tree-walker, Drip lets a second `let` at the top level simply
replace the first.

<Callout kind="definition">
The VM's **global table** is one hash table (`vm.globals`, a `Table`)
mapping interned name strings to values. `DEFINE_GLOBAL` stores and
pops the value on top of the stack. `GET_GLOBAL` pushes the value
stored under a name, or reports `Undefined variable`. `SET_GLOBAL`
overwrites an existing name and leaves the value on the stack. Each
takes one operand: the constant-pool index of the name.
</Callout>

## The SET_GLOBAL trick

Assigning to a name that was never defined must be an error. The
obvious code looks the name up, checks it is there, and then stores:
two hash look-ups. The VM does it in one:

```ts
case OP.SET_GLOBAL: {
  const name = readString();
  if (this.globals.set(name,
      this.peek(0))) {
    this.globals.delete(name);
    this.runtimeError(`Undefined ` +
      `variable '${name.chars}'.`);
  }
  break;
}
```

`Table.set` returns `true` when the key was *new*. For a correct
program that never happens, so the common case costs a single `set`.
For a mistaken one, the VM has just created a variable that shouldn't
exist, so it deletes it again before reporting the error. A program
that is about to stop anyway can afford the extra work. Notice also
that there is no `pop`: the value stays, because `print a = 3;` needs
it.

## Found late, on purpose

A global is looked up by name *when the instruction runs*, not when it
is compiled. That has a useful consequence. A function body can mention
a global that doesn't exist yet, as long as it exists by the time the
function is called:

<Run id="late-global" />

When `show` is compiled, `greeting` is just a string in its constant
pool. By the time `show()` runs `GET_GLOBAL`, the `let` has run and the
name is in the table. That is what lets two top-level functions call
each other, whichever comes first in the file.

<Callout kind="engine" label="Under the hood">
Every global access hashes into a table at run time. Interning makes
this cheaper than it sounds: each string object carries its hash, so
nothing is rehashed while the program runs, and keys are compared by
identity, not character by character. CPython does the same
kind of thing: its `LOAD_GLOBAL` instruction names a global by an index
into a table of names<Cite id="cpython-dis" />, while local variables
use a different instruction that takes a plain index. Drip is about to
make the same split. The three global instructions, and the
set-then-undo trick, follow clox from *Crafting
Interpreters*<Cite id="nystrom2021" />.
</Callout>

## What you learned

- The compiler stores a global's **name** in the constant pool, and the
  global instructions take its index as their operand.
- The VM's **global table** is a hash table keyed by interned strings.
- `DEFINE_GLOBAL` stores then pops. `GET_GLOBAL` pushes or reports
  `Undefined variable`. `SET_GLOBAL` stores and leaves the value on the
  stack.
- `SET_GLOBAL` sets first and deletes again if the key was new: one
  look-up for correct programs.
- Globals are found by name at run time, so a function can use a
  global defined after it.
