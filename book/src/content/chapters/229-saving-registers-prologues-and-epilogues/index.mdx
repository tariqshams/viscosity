## What survives a call?

In the last chapter `sumsq` called `sq` once per trip round its loop.
While `sq` runs, `sumsq` still needs three values: `n`, the running sum
`s` and the counter `i`. There is only one set of registers, and `sq`,
compiled separately, uses registers too. If `sumsq` kept `i` in `t0`
and `sq` happened to use `t0` as scratch space, `i` would come back
changed and the loop would go wrong, with no error anywhere. Someone
has to protect values that live across a call, and the convention
decides who, register by register.

<Analogy title="a shared office with lockers">
In an office where nobody owns a desk, anything left on a desk top may
be cleared away by the next person, so if you want to keep it you put
it in your bag before you get up. The lockers are different: you may
borrow one, but you must put back whatever was in it before you leave.
<span slot="breaks">People can see what is on a desk; a function
cannot tell which registers its caller still cares about, which is why
the rule has to be fixed per register in advance rather than worked
out each time.</span>
</Analogy>

<Analogy extra title="borrowing a friend's car">
You may drive it anywhere, but you bring it back with the seat, the
mirrors and the radio station as you found them; your friend never
needs to check, because that is the deal.
<span slot="breaks">A borrowed car is returned once; a function
restores every register it promised to keep on every path out of it,
including early returns.</span>
</Analogy>

The RISC-V psABI splits the registers into the two kinds<Cite id="riscv-psabi" />:

</Figure>

<Callout kind="definition">
A **caller-saved** register (RISC-V: `ra`, `t0` to `t6`, `a0` to
`a7`) may be changed by any call, so a caller that needs its value
afterwards must save it first. A **callee-saved** register (RISC-V:
`sp` and `s0` to `s11`) must hold the same value when a function
returns as when it was called, so a callee that wants to use one must
save the old value and restore it<Cite id="riscv-psabi" />.
</Callout>

<Formal title="What a call promises">

```text
for r in {sp, s0, …, s11}:
  r after the call = r before the call
for r in {ra, t0–t6, a0–a7}:
  r after the call = anything
  (a0, a1: the result)
```

<span slot="read">For every callee-saved register r, its value after a
call returns equals its value just before the call. For every
caller-saved register, nothing is promised after the call, except that
a0 (and a1) hold the result.</span>
</Formal>

Why have both kinds rather than one? Each choice suits a different
kind of value. A short-lived value that never crosses a call (a loop
temporary, `i * i`) is cheapest in a caller-saved register: nobody has
to save anything, and a **leaf** function (one that calls nobody) can
use all fifteen `t` and `a` registers freely. A value that must cross
many calls is cheapest in a callee-saved register: the callee that
borrows it saves it once, and the caller never has to. With only one
kind, one of those two common cases would always pay.

<Examples of="caller-callee-saved">

```text
sq:                    # a leaf
    mul  a0, a0, a0    # uses only a0
    ret                # saves nothing
```

```text
    mv   s0, a0        # n, kept for later
    li   s2, 0         # i
    li   s1, 0         # s
loop:
    mv   a0, s2        # i crosses the call
    call sq
    addi s2, s2, 1
    add  s1, a0, s1
    bne  s0, s2, loop
```

```text
    mv   a0, s2
    call sq
    add  s1, a0, s1    # right: s1 kept

    mv   a0, t1
    call sq
    add  t0, a0, t0    # wrong: t0, t1 may
                       # have been changed
```

</Examples>

The first is a leaf: `sq` touches only `a0`, a caller-saved register,
so it saves nothing at all. The second is the heart of clang's
`sumsq` (labels renamed): `n`, `s` and `i` all cross `call sq`, so the
register allocator put them in `s0`, `s1` and `s2`. Notice that `n`
arrived in `a0` and was moved to `s0` at once, because `a0` is about
to be reused for every call's argument and result. The third is a spot
the difference with no error message, which is what makes it
dangerous: the top half is clang's choice; the bottom half keeps `s`
and `i` in `t0` and `t1`, which is legal assembly and happens to work
with today's `sq` (it touches neither), and breaks silently the day
`sq` is recompiled and uses `t0`.

## Prologues and epilogues

Using `s0` to `s2` has a price: `sumsq` must hand its own caller back
whatever was in them. And there is a second debt: `call sq` writes a
new address into `ra`, destroying the address `sumsq` itself needs to
return to. Both are paid for in a few instructions at the very start of
the function and the very end:

<PrologueSteps client:visible />

<Callout kind="definition">
A function's **prologue** is the code at its entry that builds its
stack frame: it moves `sp` down to claim the frame and saves there the
callee-saved registers the function will use, and `ra` if the function
makes calls. Its **epilogue** is the code before each return that
undoes this: it reloads the saved registers, moves `sp` back to its
value on entry and returns. A frame size is a multiple of 16, to keep
`sp` aligned<Cite id="riscv-psabi" />.
</Callout>

<Examples of="prologue-epilogue">

```text
sq:                 # leaf, no s registers
    mul  a0, a0, a0
    ret             # no frame at all
```

```text
use9:               # calls nine, keeps
    addi sp, sp, -16    # nothing across it
    sd   ra, 8(sp)
    ...
    call nine
    ld   ra, 8(sp)
    addi sp, sp, 16
    ret
```

```text
sumsq:
    addi sp, sp, -32
    sd   ra, 24(sp)
    sd   s0, 16(sp)
    sd   s1, 8(sp)
    sd   s2, 0(sp)
    ...
    ld   ra, 24(sp)
    ld   s0, 16(sp)
    ld   s1, 8(sp)
    ld   s2, 0(sp)
    addi sp, sp, 32
    ret
```

</Examples>

All three are clang's `-O2` output (bodies elided). The leaf `sq`
needs no prologue or epilogue: it calls nothing, so `ra` survives, and
it uses no `s` register. `use9` from the last chapter makes a call, so
it must save `ra`; its 16 bytes hold `ra` at `8(sp)` and the ninth
argument at `0(sp)` (had it needed only the 8 for `ra`, it would still
claim 16, to keep `sp` aligned). `sumsq` saves `ra` and the three `s` registers, 32 bytes in
all. (Unoptimised code also sets `s0` to the old `sp` as a frame
pointer, as the `-O0` `sumsq` did two chapters ago; the psABI makes a
frame pointer optional and, when there is one, puts it in
`s0`<Cite id="riscv-psabi" />.) Every one of these instructions is
pure overhead, which is why compilers inline small callees (chapter
93) and why a register allocator that prefers `t` registers for
values that never cross a call pays off.

## What you learned

- **Caller-saved** registers (`ra`, `t0`–`t6`, `a0`–`a7`) may be
  changed by any call; **callee-saved** ones (`sp`, `s0`–`s11`) must be
  restored before returning.
- Values that cross calls go in `s` registers; short-lived ones in `t`
  and `a` registers, where leaf functions use them for free.
- The **prologue** claims a 16-byte-aligned frame and saves `ra` (if
  the function calls anything) and the `s` registers it uses; the
  **epilogue** restores them, releases the frame and returns.
