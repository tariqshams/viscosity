## Two numbers that must never meet

Here are two lines from Viscosity's engine, in
`engine/ts/packages/core/src/vir.ts`, and one variant of the
`Terminator` union from the last chapter:

```ts
export type ValueId = number;
export type BlockId = number;

// one variant of Terminator:
  | { kind: 'br'; target: BlockId }
```

A `ValueId` names one computed value and a `BlockId` names one block of
instructions; both are numbers counted from 0, so `7` is a perfectly good
value *and* a perfectly good block. A jump (`'br'`) must name a block.
Now watch:

```ts
const v: ValueId = 7;
const t: Terminator =
  { kind: 'br', target: v }; // no error
```

The checker accepts it, and the program jumps to block 7 when the code
meant "value 7": a bug with no error message anywhere. The reason is
spelled out in the TypeScript handbook: "aliases are *only* aliases",
and using one "is exactly as if you had written the aliased
type"<Cite id="ts-everyday-types" />. As far as the checker is concerned,
both lines say `number`.

<Analogy title="grams and ounces">
A recipe says "100" and the kitchen scale shows "100"; both are just
numbers, and nothing in the number says whether it means grams or
ounces. Write the unit next to every number and a mix-up becomes
visible on paper, before the cake is ruined.
<span slot="breaks">A unit changes the meaning of the number (100 grams
is not 100 ounces); a brand changes nothing at all about the value,
which is still exactly the same number while the program runs.</span>
</Analogy>

This is **structural typing**: TypeScript compares types by their
*structure* (their shape and members), never by their names, so two
types with the same structure are the same type<Cite id="ts-type-compatibility" />.
Usually that is a gift, since any object with the right properties
fits an interface, however it was made; for ids, though, it means the
checker cannot help.

## Stamping a brand

The fix is to give the two types different structures, even though both
are still numbers underneath:

```ts
type BlockId = number &
  { readonly __brand: 'BlockId' };
type ValueId = number &
  { readonly __brand: 'ValueId' };
```

The `&` builds an **intersection type**: a value of type `A & B` must be
an `A` *and* a `B` at once<Cite id="ts-object-types" />. So a `BlockId`
is a number that also has a property `__brand` holding the literal
`'BlockId'`. No real number has such a property, which is the whole
trick: no plain number, and no `ValueId` (whose brand holds a different
literal), fits a `BlockId` by accident. The property is never actually
created; it only exists in the checker's mind, and the double underscore
is a habit that says "not a real field, do not read it".

How does a real `BlockId` ever get made, then? With a **type
assertion**, `value as Type`, which tells the checker "treat this value
as that type; I vouch for it". An assertion checks nothing, and like
every type it is erased, so it cannot fail while the program
runs<Cite id="ts-everyday-types" />. That makes it dangerous anywhere and
useful in exactly one place: a small function that is the only way to
make the branded type.

```ts
function blockId(n: number): BlockId {
  return n as BlockId;
}
const b = blockId(7); // b: BlockId
```

<Callout kind="definition">
A **branded type** is a plain type intersected with a made-up property
that no real value has, such as `number & { readonly __brand: 'BlockId' }`.
It behaves as a number everywhere, but the checker refuses to treat a
plain number, or a value with another brand, as one. The only way to
make one is a **type assertion** (`as`), kept inside one small function.
TypeScript's own compiler brands its file paths this
way<Cite id="ts-path-brand" />.
</Callout>

<Formal title="Which way the door opens">

```text
BlockId <: number    ✓
number  <: BlockId   ✗
ValueId <: BlockId   ✗
```

<span slot="read">The symbol `<:` reads "can be used wherever this is
expected". A BlockId can be used wherever a number is expected (it is a
number, with something extra): true. A plain number can be used where a
BlockId is expected: false, marked ✗. A ValueId can be used where a
BlockId is expected: also false, because its brand holds a different
literal.</span>
</Formal>

<Examples of="branded-type">

```ts
type Meters = number &
  { readonly __brand: 'Meters' };
const m = 3 as Meters;
const area = m * m; // a plain number
```

```ts
const v = 3 as ValueId;
const b: BlockId = v;
// error: Type 'ValueId' is not assignable
// to type 'BlockId'. ... Type '"ValueId"'
// is not assignable to type '"BlockId"'.
const ok: BlockId = blockId(3); // fine
```

```ts
// TypeScript 5.9, src/compiler/types.ts:
// branded string type used to store
// absolute, normalized and canonicalized
// paths
export type Path =
  string & { __pathBrand: any; };
```

<Run id="brand-erased" />

</Examples>

The first is the smallest brand: `as` stamps 3 as `Meters`, and since a
`Meters` is still a number, `m * m` works; however, the result is a plain
`number`, because the checker cannot know that metres times metres is
still metres (it is not: it is square metres), so arithmetic always drops
the brand. The second is the bug from the start of the chapter, now
caught: `tsc` reports that a `ValueId` is not a `BlockId` (the `...`
stands for two lines of detail), and names the two literals that differ,
while a `BlockId` made by `blockId` is accepted.

The third is real code from the TypeScript compiler, comment and all
(reflowed to fit the page). Its `Path` is a string that has been turned
into one standard, absolute form, made in one place, a function called
`toPath`; any function that asks for a `Path` knows that work was
already done. (The compiler writes `any` for the brand's type, where we
used a literal; the effect is the same.) The runnable one shows the
honest bottom line: after erasure there is nothing left, `typeof` says
`'number'`, and the id works as an array index like any number.

## A brand as a receipt

A brand can say more than "this is a block, not a value"; it can say "this
value has been checked". Make the checking function the only door in, and
holding a branded value becomes proof that the check happened.

<Analogy extra title="a wristband at a festival">
At the gate, someone checks your ticket once and puts a wristband on you;
after that, every stage and bar looks only at the wristband, and nobody
asks for the ticket again.
<span slot="breaks">A wristband can be cut off and passed to a friend; a
brand can be forged with `as` anywhere in your code, which is why `as`
belongs in the one checking function and nowhere else.</span>
</Analogy>

program on a computer receives network traffic), from untrusted text to

The pattern has a shape worth remembering: one function at the border
turns a loose type (`number`, or `string`) into a precise one (`Port`),
refusing bad values with a `throw`; everything after it takes the
precise type, and never checks again. It is the same move as the last
chapter's `fromFlags`, and the same move as a parser, which turns loose
text into a precise structure; you write one of those in the next two
chapters.

<OtherLanguages>

```js
// no types to brand: an id is a number
const target = 7; // block? value?
```

```python
from typing import NewType
BlockId = NewType('BlockId', int)
b = BlockId(7)  # an int at run time
# mypy: plain int where BlockId wanted
# is an error
```

```java
record BlockId(int n) {}
record ValueId(int n) {}
BlockId b = new BlockId(7);
// b = new ValueId(7); does not compile
```

```c
typedef int block_id; /* only a name */
typedef struct { int n; } value_id;
value_id v = { 7 };
/* block_id b = v; error: incompatible
   types */
```

</OtherLanguages>

Python's `NewType` is the closest relative of a TypeScript brand: a
checker such as mypy treats `BlockId` as different from `int`, while at
run time `BlockId(7)` is the plain integer 7. Java's types are
**nominal** (compared by name, not structure), so two record classes are
always different types; the price is that a `BlockId` really is a small
object wrapping the number, not the number itself. C shows both sides:
`typedef` only gives a new name, exactly like a TypeScript alias, while
wrapping the number in a `struct` makes a genuinely different type, as
Java does. (Rust, in Part XI, calls the wrapping trick a *newtype*.)

<Callout kind="engine" label="Under the hood">
Viscosity's engine uses plain aliases for its four kinds of id
(`ValueId`, `BlockId`, `FuncId` and `BindingId`), and each id is the
position of its item in an array, so `m.values[v]` finds a value by its
id. Branding them would keep that working (a branded id is still a
number, and still an index) and would make a call such as
`builder.br(v)` with a value id fail to compile; the price is one `as` in
each of the few places that hand out new ids. It is a choice the engine
has not made, and a reasonable change to make.
</Callout>

## What you learned

- **Structural typing** compares types by shape, so `type BlockId =
  number` is only another name for `number`: aliases cannot tell ids
  apart.
- A **branded type**, `number & { readonly __brand: 'BlockId' }`, is
  an **intersection** with a property no real value has; plain numbers
  and other brands are refused, while the branded value still works as a
  number.
- **`as`** is a type assertion that checks nothing; keep it in one
  checking function, and a branded value becomes a receipt for that
  check.
- Brands are erased (no run-time cost, and no run-time protection),
  arithmetic drops them, and data from outside arrives without them, so
  it still goes through the checking function.
