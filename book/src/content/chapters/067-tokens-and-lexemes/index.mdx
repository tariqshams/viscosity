## Characters are too small

Here is a line of Drip:

```
let speed = 10.5;
```

The parser's job (a few chapters on) is to
recognise the shape of this line: "a `let`, then a name, then `=`, then
a value, then `;`". Now imagine it had to do that one character at a
time. Is `l` the start of `let`, or of a name like `lemon`? Is `1` a
whole number, or the start of `10.5`? Every rule of the grammar would
have to worry about spelling as well as shape. So the pipeline splits
the work: the scanner deals with spelling once, and hands the parser a
list of whole words, called **tokens**. You met the idea in *Checkpoint: JSON
and its scanner*; this chapter pins it down.

<Analogy title="a sentence marked up by a teacher">
A teacher marks up a sentence by underlining each word and writing a
label under it: *noun*, *verb*, *number*. The word as written, say
"cats", is its exact spelling; the label is its category; and a note in
the margin ("line 3") says where it was, so they can talk about it
later. A token is those three things together.
<span slot="breaks">A teacher's label depends on meaning: "run" can be
a noun or a verb. A scanner decides a token's category from its spelling
alone, without knowing what the program means.</span>
</Analogy>

## Cutting a line into tokens

Step through two lines being cut up, and watch the card: every token
has the same four parts.

<TokenSteps client:visible />

In the companion code a token is a plain object; this is the interface
from `companion/ts/src/token.ts`, with its comments removed:

```ts
interface Token {
  type: TokenType;
  lexeme: string;
  literal: string | number | null;
  line: number;
}
```

<Analogy title="a price tag">
A price tag shows the text "£4.25" in print; the till reads the actual
amount, four pounds twenty-five, which it can add up; and the tag also
says which shelf the item came from. The printed text is the lexeme,
the amount is the literal, and the shelf is the location.
<span slot="breaks">The text on a price tag was chosen by someone who
knew what the item was. A token's lexeme is simply whatever characters
were in the source, and its literal is worked out from them.</span>
</Analogy>

<Callout kind="definition">
A **token** is one meaningful word of source code. Its **lexeme** is
the exact characters it was made from, such as `"10.5"`. Its **token
type** is its category: a number, an identifier, a keyword, the `+`
operator. For numbers and strings, the scanner also stores the
**literal**: the actual value the characters stand for, such as the
number `10.5`. (Compiler textbooks often call the token type the
token's *syntactic category*<Cite id="coopertorczon2022" />.)
</Callout>

<Formal title="A token, and where its lexeme comes from">

```text
token  = (type, lexeme, literal, line)
lexeme = source[start .. end)
```

<span slot="read">A token is four values kept together, in that order.
Its lexeme is the slice of the source from position start up to, but
not including, position end; the round bracket on the right means "end
itself is left out", exactly like JavaScript's slice.</span>
</Formal>

<Examples of="token lexeme">

```text
print x;  →  print   x   ;   eof
```

```text
"fast"    lexeme  "fast"  (6 chars)
          literal fast    (4 chars)
```

```text
10.5   type     number
       lexeme   '10.5'  (text)
       literal  10.5    (a number)
       line     1
```

</Examples>

The first is the smallest case: three words make three tokens, the
space makes none, and the scanner always adds `eof` (end of file), so
the parser can keep asking "what is next?" and get a clear answer when
the program has run out. The second shows lexeme and
literal coming apart most clearly: the lexeme of a string includes its
quote marks, while the literal is the text inside them, which is what
`print` will show. The third is the full card for the number in our
`let` line: the lexeme is the four characters `10.5`, while the literal
is a JavaScript number the interpreter can do arithmetic with.

## The list of token types

Why bother with a type at all, if the lexeme already says everything?
Because the parser thinks in categories. Its rule is "a `let` is
followed by *any* name", not "followed by `speed`, or `x`, or
`total`…"; thousands of different lexemes share the one type
`identifier`. Here is every token type Drip has, from `token.ts`,
rewrapped to fit:

```ts
type TokenType =
  // single-character tokens
  | '(' | ')' | '{' | '}' | ',' | '.'
  | '-' | '+' | ';' | '/' | '*'
  // one or two character tokens
  | '!' | '!=' | '=' | '=='
  | '>' | '>=' | '<' | '<='
  // literals
  | 'identifier' | 'string' | 'number'
  // keywords
  | 'and' | 'class' | 'else' | 'false'
  | 'fn' | 'for' | 'if' | 'nil' | 'or'
  | 'print' | 'return' | 'super'
  | 'this' | 'true' | 'let' | 'while'
  | 'eof';
```

It is a union of string literal types, from *TypeScript II: unions and
narrowing*. For punctuation and keywords the type *is* the spelling
(the token for `<=` has type `'<='`); only for names, numbers and
strings do type and lexeme differ. And TypeScript rejects a misspelt
type before the scanner ever runs:

```ts
const t: TokenType = 'eqaul';
// Type '"eqaul"' is not assignable
// to type 'TokenType'.
const ok: TokenType = '==';
```

<Callout kind="definition">
A **token type** is the category of a token. Drip has 39: one for each
punctuation mark or pair, three for literals (`identifier`, `string`,
`number`), one for each of its 16 keywords, and `eof`. Spaces, newlines
and comments separate tokens but never become tokens.
</Callout>

<Examples of="token-type">

```text
+        →  '+'
<=       →  '<='
```

```text
speed  total  x  →  identifier
```

```text
while (n <= 10)  →  'while' '('
  identifier '<=' number ')'
```

</Examples>

In the first, each operator is its own type, and `<=` is one token,
not `<` then `=` (the next chapter shows how the scanner makes sure of
that). In the second, three names share one type: the parser only cares
that it is a name. In the third, the start of a real loop, the keyword
`while` has the type `'while'` and `n` and `10` get the shared types
`identifier` and `number`.

## Where did it come from?

A token also remembers where it was found, because when something goes
wrong much later (say in the parser, which never sees the characters)
that is the only way to tell you *where*:

<Run id="error-lines" />

The parser reports line 3, read from the `;` token where it expected a
value; and `one` is never printed, because the front end checks the
whole program before any of it runs.

<Analogy title="a grid reference on a map">
A map is divided into squares, so "row 3, square 9" finds one spot on
the sheet; a line and column do the same for a point in a file.
<span slot="breaks">Every square on a map is the same size. In source
text, a tab or some emoji take one or two places in the string but a
different width on screen, so "column 9" can mean slightly different
things to a program and to your eyes.</span>
</Analogy>

A scanner walks the source by **offset**: the index of a character in
the whole string, counting newlines as characters too. People want a
line and a column instead, and one turns into the other by counting:

<Figure takeaway="Count the newlines you pass." caption="The source let x;, an empty line, then print x +;. Every character, newlines included, has one offset in the whole string. The + at offset 16 comes after two newlines, so it is on line 3, and it is the ninth character of that line.">
  <OffsetGrid />
</Figure>

<Callout kind="definition">
A token's **source location** says where in the source it came from:
its line, and often its column (its position within the line, counting
from 1). Error messages use it to point at the problem. Drip's tokens
record only the line, because Drip's error messages name only the
line.
</Callout>

<Formal title="From an offset to a line">

```text
line(o) = 1 + (newlines in source[0 .. o))
col(o)  = o − (offset after the last
               of those newlines) + 1
```

<span slot="read">The line of the character at offset o is one more
than the number of newline characters before it. Its column is how far
it is past the start of its line, plus one, because columns are counted
from 1. For the + in the figure: two newlines come before offset 16, so
it is on line 3; line 3 starts at offset 8, so its column is 16 − 8 + 1,
which is 9.</span>
</Formal>

<Examples of="source-location">

```text
[line 3] Error at ';':
Expect expression.
```

```text
print x +;
         ^
```

```text
print 1;
print 2;
bytes: CONSTANT 0 PRINT CONSTANT 1 …
lines: 1        1 1     2        2 …
```

</Examples>

The first is Drip's real message for the program above: the line comes
from the token, and the quoted `';'` is the token's lexeme. The second
is what many compilers print instead, the offending line with a caret
`^` under the exact spot, which needs the column too; the exercises
build it. The third is how far the line number travels: when Drip's VM
in Part IV compiles these two lines to bytecode, it keeps a line number
beside every byte (`CONSTANT 0` is two bytes, so it has two), and an
error deep inside the VM can still name your source line.

<Callout kind="engine" label="Under the hood">
Viscosity takes the same care. Every instruction in its IR, VIR,
carries a `SourceRef` with the start and end offsets and the line it
came from (`engine/ts/packages/core/src/vir.ts`), so the back end can
rewrite exactly the right characters, and its explanations can point at
the line *you* wrote.
</Callout>

## What you learned

- A **token** is one meaningful word of source. Its **lexeme** is the
  exact characters, its **token type** is its category, and numbers and
  strings also carry a **literal** value.
- Drip's `TokenType` is a union of 39 string literal types; for
  punctuation and keywords the type is the spelling itself, and the list
  always ends with `eof`.
- Whitespace and comments separate tokens but never become tokens.
- A **source location** (line, and often column) lets later stages
  report errors in the right place; Drip records the line.
