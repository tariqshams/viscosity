## Five bugs past every test

When the fuzzer of this chapter was written, `cargo test` was green,
and random programs still found five bugs that every test had missed.
Here is one, as the fuzzer's reducer left it (reformatted):

```js
function local1(m) {
  const ls = [];
  for (let i = 0; i < 64; i++)
    ls.push({ a: i, b: i });
  let t = 0;
  for (let i = 0; i < ls.length; i++) {
    ls[i].b += m;
    t += ls[i].b;
  }
  ls[1].a = (ls.push({ a: 0, b: 0 }), 7);
  t += ls[1].a;
  return t;
}
console.log(local1(0), local1(1));
```

The function builds 64 records, adds `m` to every `b` while summing
them, and then does something odd on purpose: it stores `7` into
`ls[1].a`, where the right-hand side first pushes a 65th record (the
comma operator runs `ls.push(...)`, throws its answer away, and gives
`7`). Under node it prints `2023 2087`. Compiled by the TypeScript
engine from just before the fix (I ran it here), it printed `2017
2081`: the `7` was lost. The old engine had written the store like
this (the compiled `push` takes the field values in order; wrapped):

```js
ls.a[__vsc_bc(ls, 1, 'a', true)] =
  (ls.push(0, 0), 7);
```

JavaScript works out *where* to store (here `ls.a`, the column of `a`
values) before it runs the right-hand side<Cite id="ecma262-assignment-order" />.
The 65th push overflows the column's capacity of 64, so `grow()`
installs a new, larger column, and the `7` goes into the old one, which
nothing reads any more (*Growing collections* explained the growing).
Today both engines write this instead, which checks the index first
and stores last, into whatever column exists by then (wrapped):

```js
__vsc_set(ls, 'a', __vsc_bk(ls, 1),
  (ls.push(0, 0), 7), 'a');
```

Compiled by today's Rust CLI (release build, rustc 1.97), the program
prints `2023 2087`, as the original does. Nobody writes a test like
`local1`, because nobody thinks of it; that is the reason to let a
machine write tests.

**Fuzzing** (*Testing compilers*) means running a program on huge
numbers of machine-made inputs and checking each run against an
**oracle**, something that says whether the run was right. This chapter
is about the two ways of making those inputs.

## Two ways to search

<Analogy title="exploring a cave with chalk">
You explore a cave by chalking a mark at every junction you reach.
Each morning you go back to the deepest spot where you found an
unmarked junction yesterday and wander a little further from there;
wanders that only pass old marks are forgotten. You never know where
the treasure is, yet you are pulled steadily into parts of the cave
nobody has seen.
<span slot="breaks">A cave stays the same between visits; a program's
paths depend on the input in ways the chalk marks do not show, so two
inputs that reach the same junctions can still behave very
differently.</span>
</Analogy>

<Analogy title="a driving examiner">
An examiner who knows the rules of the road plans a fresh route for
every test drive: a roundabout here, a hill start there, a reversing
bay at the end. Every route is a legal drive, and over hundreds of
tests every kind of manoeuvre comes up, in every combination.
<span slot="breaks">A real examiner learns from experience which
routes catch people out; the generator in this chapter learns nothing
from its runs, and gets new kinds of route only when a person edits
it.</span>
</Analogy>

The cave explorer is a **coverage-guided** fuzzer, and the examiner is

## Coverage: counting edges

To know what a run reached, a coverage-guided fuzzer compiles its
target with a few extra instructions at every branch (that is
**instrumentation**, from *Profile-guided optimization*). AFL, the
fuzzer that made this style famous, gives every basic block a random
number and adds, in effect, these three lines at the start of each
one<Cite id="afl-technical-details" />:

```c
cur = <random number for this block>;
shared_mem[cur ^ prev]++;
prev = cur >> 1;
```

`shared_mem` is a 64 kB array of counters shared with the fuzzer. The
index `cur ^ prev` (`^` is exclusive or, which mixes two numbers into
one) depends on *both* the block we are in and the block we came from,
so each counter stands for an **edge**: a step from one block to
another. The shift on the last line makes A→B and B→A land on
different counters. Why edges and not blocks? Two runs can visit
exactly the same blocks along different edges:

  <EdgeFigure />
</Figure>

An input whose run reaches a new edge (or a much larger hit count on an
old one; AFL sorts counts into buckets such as 1, 2, 3, 4 to 7) is kept
and changed further, and every other input is thrown away. In Rust,
`cargo fuzz` drives libFuzzer the same way; you write a target that
takes raw bytes, and it needs a nightly compiler for its sanitizer
flags<Cite id="cargo-fuzz-book" />.

<Callout kind="definition">
A **coverage-guided fuzzer** changes (**mutates**) inputs it has kept,
runs the instrumented target on each one, and keeps an input only if
its run reached **new coverage**, such as a branch edge no earlier
input reached. The kept inputs (the **corpus**) grow towards code no
input has reached. A **generation-based** fuzzer writes every input
from a grammar or model instead, and nothing a run reached feeds back.
</Callout>

<Formal title="The keep rule">

```text
E(x) = { (a, b) : the run on x steps
         from block a to block b }
keep x  ⟺  E(x) ⊄ Seen
Seen := Seen ∪ E(x)
```

<span slot="read">E of x is the set of edges the run on input x took. The
fuzzer keeps x exactly when E of x is not contained in Seen, the edges
every earlier run took (the symbol ⊄ reads "is not a subset of"). Then
it adds the new edges to Seen, so the same edge never counts as new
twice.</span>
</Formal>

passed. With this seed the guided search kept `FAA` at try 27 and `FUA`
at try 114, and found `FUZ` at try 360; the blind one needed 11,524

kept input is a foothold; the blind search never has one.

## Why Viscosity generates programs

For Viscosity, mutated bytes are a poor input. Almost every byte string
is a syntax error, which the engine refuses while parsing, so the
analyses this Part ported never run; and the most useful oracles need a
program that *runs*, because they compare the original program with the
compiled one under node. As such, `engine/rust/scripts/fuzz.mjs` is
generation-based, like Csmith, a random generator of C programs built
to test C compilers<Cite id="csmith" />. It knows
the slice of JavaScript Viscosity cares about (arrays of records pushed
in loops, field reads and writes, escapes, out-of-bounds reads inside
`try`, annotations) and writes valid programs in it.

Every program comes from a seed, and one small function ties the
pieces together:

```js
function programAt(seed, k) {
  const s = programSeed(seed, k);
  return withEarlyError(generate(s), s);
}
```

`programSeed` mixes the campaign seed with the program's number `k`
into a new 32-bit seed (by multiplying and shifting, so that nearby
`k`s give unrelated seeds); `generate(s)` builds a program from a
random-number generator started at `s`; and `withEarlyError` gives about
one program in 20 an error that JavaScript must reject before running
(a redeclared `let`, a stray `break`, and so on), which both engines
must then refuse. Because program `k` depends only on `(seed, k)`, any
program can be made again on its own (the next chapter, *Shrinking a
failing program*, runs it and follows what it finds).

## What you learned

- **Fuzzing** checks machine-made inputs against an **oracle**.
- A **coverage-guided** fuzzer keeps a mutated input only when its run
  reaches new coverage; AFL counts branch **edges**, which tell apart
  paths that visit the same blocks.
- A **generation-based** fuzzer such as `fuzz.mjs` writes valid
  programs from a seed, with no feedback; Viscosity needs that because
  its oracles run the programs.
- A per-program **seed** makes every generated program replayable on
  its own.
