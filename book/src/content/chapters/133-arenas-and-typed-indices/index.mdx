## Pointers become numbers

*Box, Rc and RefCell* ended with three problems for a VM built from
`Rc<RefCell<..>>`: it leaks every cycle a program makes, it panics when a
program aliases the wrong objects, and it hands "when does this object
die?" to reference counting instead of to the collector of *Reclaiming
memory: mark and sweep*. drip-rs's answer is the first of its design
notes: no object owns another. One owner, the **heap**, holds every
object, in one `Vec` per kind of object, and a reference from one object
to another stops being a pointer and becomes a number, the object's
position in that `Vec`.

<Analogy title="a car park with numbered bays">
A multi-storey car park owns every bay; your ticket only says "bay 17".
You can photocopy the ticket as often as you like without creating a
second car, and two drivers can leave notes on each other's windscreens
saying "I'm the blue car in bay 9". When a car leaves, its bay is free
for the next one.
<span slot="breaks">A real car park would notice if your old ticket
pointed at someone else's car; a slot number does not, so keeping a
number after its object is freed reads whatever moved in.</span>
</Analogy>

## An arena is a Vec of slots

<Examples of="arena">

```rust
// adapted from drip-rs, src/object.rs
pub struct Arena<T> {
    slots: Vec<Option<T>>,
    free: Vec<u32>,
}

impl<T> Arena<T> {
    pub fn insert(&mut self, o: T)
        -> Gc<T> {
        if let Some(i) = self.free.pop() {
            let i = i as usize;
            self.slots[i] = Some(o);
            return Gc::new(i);
        }
        self.slots.push(Some(o));
        Gc::new(self.slots.len() - 1)
    }
}
```

</Examples>

Each slot is an `Option<T>`: `Some(object)` while it is live, `None` once
the collector frees it. `free` lists the empty slots, so `insert` first
pops the free list and refills a hole, and only when nothing is free does
it push a new slot onto the end. `Gc<T>` is the handle it returns; for
now, read it as "slot number `i`". `remove(index, reuse)` calls `take()`
on the slot, which leaves `None` behind and hands back the object, and
puts the index on the free list only if `reuse` is true (drip-rs's debug
and stress modes never reuse, so a stale handle panics with "use after
free" instead of reading a stranger). drip-rs's `Heap` has nine of these,
`strings`, `lists`, `functions` and so on up to `bound_methods`, and the
collector sweeps by walking each arena's slots, with no linked list of
objects needed.

<Callout kind="definition">
An **arena** is one collection, here a `Vec`, that owns many objects of
one type. Objects are added and removed through the arena, and everything
else refers to them by **index** instead of by pointer, so no object owns
another and cycles are only numbers. A **free list** of empty slots lets
new objects reuse old space; a **stale** index, kept after its object
was freed, reads whatever moved in: wrong, but never undefined
behaviour<Cite id="rust-std-vec" />.
</Callout>

In TypeScript, `a.other = b; b.other = a` links two objects directly, and
the tracing collector frees them when nothing can reach them. The arena
version links them by number; neither owns the other, and deciding when
they die is up to whoever owns the arena, which in drip-rs is the
collector. engine/rust is built on arenas too: VIR's `Module` keeps every
instruction in one `Vec`, and oxc builds the JavaScript syntax tree in its
`Allocator`, "a bump-based memory arena for faster AST
allocations"<Cite id="oxc-allocator" />.

</More>

## Borrowing one arena

The borrow checker still applies. `insts[i]` borrows the whole `Vec`, so
`let src = &insts[1]; let dst = &mut insts[0];` is rejected by rustc 1.97
with E0502, `cannot borrow insts as mutable because it is also borrowed
as immutable`, even though the two elements differ. Compare it with the
`RefCell` panic of *Box, Rc and RefCell*: this is a *compile* error, and
the fix is always the same, copy what you need out first, let that
borrow end, then write:

```rust
let hp = insts[1].hp; // copy a number
insts[0].hp += hp / 2.0;
```

Handles and drip-rs's `Value`s are `Copy`, so copying is cheap, and
`a.heal(a)` now simply works. drip-rs's property lookup does exactly
this, reading `let class = self.heap[instance].class;` (a copy of a
handle, so the borrow ends at the semicolon) before calling a method
that needs `&mut self`.

## Two numbers that look alike

One hole is left. With nine arenas, a slot number for one looks exactly
like a slot number for another, and with bare `usize`s nothing stops a
class's slot being used to read the instances arena, which quietly
returns some unrelated object. The fix is to wrap each kind of number in
a type of its own, a **newtype**: a struct with one unnamed field, as
engine/rust's VIR does for its instructions.

<Examples of="typed-index">

```rust
#[derive(Copy, Clone, PartialEq, Eq)]
pub struct ValueId(pub u32);

let id = ValueId(7);
let i = id.0 as usize; // 7
```

</Examples>

`ValueId(7)` builds one, and `.0` reads the number back out. VIR names
everything this way, with `ValueId`, `BlockId`, `FuncId` and `BindingId`,
each a `u32` in its own newtype; a function that wants a `ValueId` will
not take a `BlockId` holding the same number (rustc reports E0308,
mismatched types), so mixing them up is found while compiling. At run
time the wrapper is gone: it has exactly the size and layout of the
number inside.

<Analogy extra title="colour-coded tickets">
A venue gives out green tickets for the cloakroom and blue tickets for
the car park, both numbered from 1. Hand a green 17 to the car park
attendant and they refuse it at a glance; the colour says which counter
the number belongs to.
<span slot="breaks">An attendant checks the colour every time; Rust
checks it once, while compiling, and the running program carries no
colour at all, only the number.</span>
</Analogy>

</Figure>

drip-rs has nine kinds of object, so it writes the wrapper *once*, as a
generic:

```rust
pub struct Gc<T> {
    index: u32,
    marker: PhantomData<fn() -> T>,
}
```

A struct must use every type parameter it declares, or rustc 1.97 refuses
with E0392, `type parameter T is never used`, and suggests "a marker such
as `PhantomData`". **`PhantomData`** is that marker: a standard type that
takes no space and tells the compiler to act as though the struct held a
`T`<Cite id="rust-std-phantomdata" /> (the `fn() -> T` form, drip-rs's
comment says, keeps the handle `Copy`, `Send` and `Sync` whatever `T`
is). So a `Gc<ObjClass>` is 4 bytes yet a different type from a
`Gc<ObjClosure>`, and the arena implements `Index` (the trait behind
`x[i]`, from *Traits, trait objects and derive*) only for handles of its
own element type, `impl<T> Index<Gc<T>> for Arena<T>`. Step through two
arenas and two handles that hold the same number:

<HandleSteps client:visible />

One wrinkle: drip-rs writes `impl<T> Copy for Gc<T> {}` by hand rather
than deriving it, because `#[derive(Clone, Copy)]` adds the bounds `T:
Clone` and `T: Copy` to its impls, and an `ObjClass` is neither, so a
derived handle to a class would not be `Copy`.

<Callout kind="definition">
A **typed index** is a number wrapped in its own type, a newtype such as
`struct NodeId(u32)`. It costs nothing at run time (the same size and
layout as the number), but the compiler treats each wrapper as a
different type, so indices into different collections cannot be mixed
up. A generic handle like drip-rs's `Gc<T>` gives every element type its
own index type from one definition.
</Callout>

TypeScript's types are structural, so two `number` aliases are
interchangeable; *Branded types: same shape, different meaning* gets the
effect by intersecting `number` with a made-up property. Rust's structs
are nominal (a type is its name), so a one-field struct is already a
distinct type, and, as with a brand, the wrapper disappears when the
program is compiled.

</More>

## What you learned

- An **arena** is a `Vec` of slots that owns every object of one kind;
  objects refer to each other by index, so a cycle is only numbers. Copy
  numbers out of it before writing back.
- A **typed index** such as `struct NodeId(u32)` is the same bytes as the
  number but a different type; drip-rs's `Gc<T>` makes one per kind of
  object with `PhantomData`.
