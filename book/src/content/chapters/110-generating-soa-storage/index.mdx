## Where do the columns live?

The planner has said `soa` for this program, and now the compiler has
to make it true:

```js
const ps = [];
for (let i = 0; i < 1000; i++)
  ps.push({ x: i, vx: 1 });
```

Nothing in JavaScript is a "struct of arrays"; there are objects, plain
arrays and typed arrays, and the compiler has to build the new layout out
of those. This is code generation in the sense of *Emitting JavaScript,
and round-trip testing*: the plan is a decision, and now somebody has to
write the code that carries it out. Viscosity's answer is to write a
small class at the top of your file and to replace the empty array with
one of its objects, `const ps = new __Vsc_ps();`; everything about the
new layout lives inside that class.

## One array per field

Start with what the class holds: one array per field, instead of one
object per element.

<Analogy title="a register and a spreadsheet">
A paper visitors' book has one row per visitor, with their name, time and
reason written across it. A spreadsheet of the same visits keeps one
column per question, every name in column A and every arrival time in
column B, and visitor 7 is row 7 of every column; to add a visitor you
write one cell in each column, on the same row.
<span slot="breaks">A spreadsheet will happily let you sort one column on
its own; do that to Viscosity's columns and every record is scrambled,
because the shared row number is the only thing holding a record
together.</span>
</Analogy>

<Figure caption="The same three records, as objects and as columns. Element i is index i of every column, and nothing else ties a record together." takeaway="A record stops being an object and becomes an index.">
  <Columns />
</Figure>

<Callout kind="definition">
**Column storage** keeps one array per field: every `x` together, every
`vx` together, with element `i`'s fields at index `i` of each column.
Viscosity uses a `Float64Array` column for a field it has proved is
always a number, and a plain JavaScript array for any other field.
</Callout>

Why two kinds of column? A `Float64Array` stores raw 64-bit doubles side
by side, with no object per value<Cite id="mdn-typed-arrays" />, which is
the whole point; however, it stores only numbers, and anything else you
write into it is converted (the string `'7'` comes back as `7`, and
`'abc'` as `NaN`). So a typed column is correct only for a field the
numeric analysis of *Record shapes* has proved is always a number, and
every other field gets a plain array, which takes anything.

<Examples of="column-storage">

```js
es.push({ id: 'e' + i, hp: 100, x: i,
  tag: i % 3 ? null : { boss: true } });
// hp, x: Float64Array; id, tag: plain
```

</Examples>

This is the push from the corpus file `mixed_columns.js`, run 300 times.
`hp` is always `100` and `x` is the loop counter, so both are provably
numbers; `id` is a string, and `tag` is either `null` or an object. So
explain reports `typed Float64Array columns for hp, x; plain array
columns for id, tag (may hold non-numbers)`, and the generated
constructor makes two typed columns and two plain ones:

```js
this.hp = new Float64Array(cap);
this.x = new Float64Array(cap);
this.id = []; this.tag = [];
```

(The real constructor is one line; it is split here to fit.) Awkward
doubles survive too: a `Float64Array` holds any IEEE 754 double exactly,
so a stored `-0` or `NaN` comes back as itself.

<Prompts ids={['col-what', 'col-typed-why']} />

<More title="More: what a Float64Array does with values that are not numbers">

Line by line, this writes a few values into a typed column and a plain
one: `2.5` and `-0` are stored exactly (`Object.is` tells `-0` from
`0`); the string `'7'` comes back as the number `7`, and `'abc'` as
`NaN`; a write past the end is silently dropped; and a plain array takes
anything and grows.

## The container class

The columns need somewhere to live, along with the count of elements and
the one method most programs call, `push`. Here is the class Viscosity
emits for `ps`, with records `{ x, vx }` (the compiler writes each member
on one long line; the stepper reflows it to fit, with nothing else
changed):

<ContainerSteps client:visible />

<Callout kind="definition">
An **SoA container** is the object that holds a collection's columns,
with `length` (elements in use), `cap` (slots per column) and the methods
the program still needs: `push`, which takes one value per field and
returns the new length, `grow`, and `of` for array literals. Viscosity
generates one container class per transformed collection, named `__Vsc_`
plus the collection's name.
</Callout>

<Examples of="soa-container">

```js
const ps = [];
n = ps.push({ x: i, vx: 2 });
// → const ps = new __Vsc_ps();
//   n = ps.push(i, 2);
```

</Examples>

The first line is creation, the one edit every transformed collection
gets: the empty array becomes a new container. The second is a push whose
result the program keeps; the object literal is taken apart into one
argument per field, in field order, and the generated `push` writes slot
`length` of every column and returns `this.length`, exactly as
`Array.prototype.push` returns the new length, so after 100 pushes both
versions leave `n` at `100`. An array literal such as
`[{ x: 1, y: 2 }, { x: 3, y: 4 }]` becomes `__Vsc_pts.of(1, 2, 3, 4)`,
the values flattened and pushed in groups.

One awkward case: the container already has members called `length`,
`cap` and `push`, so a field with one of those names would overwrite
them, and a field like `'a-b'` cannot be written after a dot at all. The
emitter therefore renames any field that is reserved (`length`, `push`,
`grow`, `of`, `constructor`, `prototype`, `get`, `cap`, `data`) or is not
a plain identifier to `f`, its position and `_`: records
`{ length: i, cap: 1, 'a-b': 2 }` get columns `ps.f0_`, `ps.f1_` and
`ps.f2_`, and `ps[i].length` becomes `ps.f0_[i]`, while `ps.length` stays
the element count.

The check `n === this.cap` runs on every push and is almost always false;

and only for typed columns, since a plain array lengthens by itself.

<More title="More: name clashes, and ISPC's generated containers">

If a real field is already called `f0_` (records `{ length: i, f0_: 2 }`,
the corpus file `renamed_column_clash.js`), the renamed column takes one
more `_`, `f0__`, until the name is free.

ISPC does the same job inside a compiler for C-like code. Declaring
`soa<8> Point pts[...]`, for `struct Point { float x, y, z; }`, stores the
array as if each block were `struct { uniform float x[8], y[8], z[8]; }`
<Cite id="ispcdocs" />: a generated container, as here, but with the
columns cut into blocks of eight (Viscosity's blocked version is in
*AoSoA and hot/cold splitting*). One difference matters for JavaScript:
Viscosity can use a typed column only when it has proved the field is a
number, because a JavaScript field has no declared type.

<Analogy extra title="a chest of drawers">
You can pack each day's outfit in its own bag, or keep all the socks in
one drawer and all the shirts in another; Monday's outfit is then "the
first sock, the first shirt". If all you want this morning is socks, you
open one drawer and never touch the shirts.
<span slot="breaks">Socks in a drawer are in no particular order, and any
pair will do; column `x` must keep element 7's `x` in slot 7, exactly,
and slot 8 belongs to element 8.</span>
</Analogy>

</More>

## What you learned

- **Column storage** keeps one array per field; element `i` is index `i`
  of every column. Provably numeric fields get a `Float64Array`, the
  rest a plain array.
- The **SoA container** is a generated class: `length`, `cap`, one
  column per field, `push` (one value per field, returns the new
  length), `grow` and `of`.
- Fields whose names clash with the container's own members, or are not
  plain identifiers, are renamed `f0_`, `f1_`, and so on.
