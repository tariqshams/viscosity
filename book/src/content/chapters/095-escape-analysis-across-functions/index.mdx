## The analysis that stops at the door

Last chapter's points-to analysis looked at one function's statements.
Real programs are mostly calls, and an analysis that looks at one
function at a time (an **intraprocedural** analysis, "inside one
procedure") has to treat each call as a closed door: whatever goes in
might be stored anywhere, and whatever comes out might be anything.
Take the smallest function there is:

```js
function id(p) { return p; }
const a = id({ n: 1 });  // call site s1
const b = id({ n: 2 });  // call site s2
```

Behind a closed door, `a` and `b` each point at "something unknown",
so every question about them is answered "may alias", and every object
passed in counts as lost. An **interprocedural** analysis opens the
door: it follows the argument into `id`, sees that `id` hands it
straight back, and concludes that `a` is the first object and `b` the
second.

<Analogy title="tracing a pipe through the walls">
A plumber who stops at every wall has to assume the pipe behind it
could go anywhere, and so cannot promise that the kitchen tap is safe
to turn on. One who opens the panels and follows the pipe through each
room can say exactly which taps it feeds.
<span slot="breaks">A pipe goes through a wall once; a function is
entered from many places, and the hard part (the rest of this chapter)
is remembering which entrance you came in by.</span>
</Analogy>

The trick is to see a call as nothing more than copies. Calling
`r = f(x)` copies the argument into the parameter and, on the way out,
the return value into `r`, so the same inclusion rules from the last
chapter apply:

<Formal title="A call as two copies">

```text
r = f(x)  at site s:
  pts(x) ⊆ pts(param of f)
  pts(return of f) ⊆ pts(r)
```

<span slot="read">At a call site s where r is assigned f of x: the set
of things x may point at is included in the set of f's parameter, and
the set of things f may return is included in the set of r.</span>
</Formal>

<Callout kind="definition">
**Interprocedural analysis** follows facts across function boundaries:
from arguments into parameters, and from return values back to the
callers, along the edges of the call graph (chapter 93). It sees more
than an intraprocedural analysis, which must assume the worst at every
call, without copying function bodies the way inlining does.
</Callout>

In JavaScript there is a twist. Which function a call reaches depends
on which function *value* the callee holds, and that is itself a
points-to question: in `g(x)`, the targets are whatever function objects
`pts(g)` contains. So the call graph and the points-to sets have to be
built together, each new edge adding facts and each new fact perhaps
adding edges. Doop, which the next chapter meets, computes exactly this,
"on the fly"<Cite id="bravenboer2009" />.

## The price of a single shelf

Follow the copies for `id` and something goes wrong. Both calls copy
into the same parameter `p`, so `pts(p) = {o1, o2}`; the return copies
all of `p` to both callers, so `a` and `b` both end up with
`{o1, o2}`, and the analysis says they may alias. They never do.

<Figure takeaway="Merging all callers lets facts enter at one call and leave at another, which no real run can do." caption="Real paths (green) return to the call site they came from. A context-insensitive analysis also follows the red one: in at s2, out to a.">
  <PathsPic />
</Figure>

The analysis has followed a path that enters `id` at `s2` and leaves to
`s1`'s result, which no run can take: a call always returns to the
place it came from. This kind of analysis, which keeps one set of facts
per function whatever the caller, is called **context-insensitive**,
and its false answers come from these impossible paths.

<Analogy extra title="one lost-property shelf for a whole hotel">
A small hotel keeps everything guests leave behind on one shelf. When
the guest from room 4 asks for her umbrella, the desk can only say
"one of these", because nobody wrote down which room each thing came
from. A shelf per room fixes it.
<span slot="breaks">A hotel has a fixed number of rooms; the number of
ways a function can be reached (chains of callers, recursion) can grow
without limit, so the analysis has to decide how many "rooms" it can
afford.</span>
</Analogy>

## Remembering who called

A **context** is a label that tells calls to the same function apart.
The best-known choice comes from Sharir and Pnueli's "call-string
approach": label each fact with the chain of call sites that led
there<Cite id="sharirpnueli1981" />. Since recursion makes those chains
endless, analyses keep only the last **k** sites (a "k-call-site"
analysis); with `k = 1`, `id` is analysed once for `s1` and
once for `s2`. Step through both versions:

<ContextSteps client:visible />

<Analogy extra title="a translator who notes the sender">
A translator works for two clients. If replies are handed back without
noting who asked, the answers get mixed up; writing the sender's name
on each message keeps every reply going to the person who asked. The
name on the message is the context.
<span slot="breaks">A name identifies a person forever; a call string
cut to k sites can make two different chains of callers look the
same, and then their facts mix again.</span>
</Analogy>

<Callout kind="definition">
**Context sensitivity** analyses a function separately for each kind of
caller, so facts from one caller never flow back to another. The
context is usually the last k call sites (**call-string** sensitivity)
or, for methods, the allocation site of the receiver object (**object
sensitivity**). A **context-insensitive** analysis keeps one set of
facts per function.
</Callout>

<Formal title="k-limited call strings">

```text
pts(v, c)       v's set in context c
call at site s in context c:
  callee context = first k of (s · c)
```

<span slot="read">Every variable now has one set per context c. When a
function running in context c makes a call at site s, the callee runs
in the context made by putting s in front of c and keeping only the
first k sites.</span>
</Formal>

<Examples of="interprocedural-analysis context-sensitivity">

```js
id({ n: 1 });  // s1: id in context [s1]
id({ n: 2 });  // s2: id in context [s2]
```

```js
function wrap(q) { return id(q); } // s3
wrap({ n: 1 });  // id in [s3, s1]
wrap({ n: 2 });  // id in [s3, s2]
// k = 1: both are [s3]: merged again
```

```js
function put(b, v) { b.set(v); } // s4
put(box1, o1);
put(box2, o2);
// call sites: set is always [s4];
// objects: set runs for box1, box2
```

</Examples>

The first is the case from the stepper: one site of context separates
the two calls. The second shows the limit of k: `id` is now always
called from the same site, `s3` inside `wrap`, so with `k = 1` both
calls look alike and the false alias returns; `k = 2` separates them,
at the price of more contexts. The third is why object-oriented code
uses **object sensitivity**, from Milanova, Rountev and Ryder: it
analyses a method separately for each receiver object (`box1`, `box2`)
rather than each call site<Cite id="milanova2005" />. The same idea
can be pictured as **cloning**: make a copy of the function for every
context and run a plain context-insensitive analysis on the bigger
program; Whaley and Lam made that practical for large Java programs by
storing the facts compactly in binary decision diagrams<Cite id="whaleylam2004" />.

## What you learned

- **Interprocedural analysis** follows facts across calls by treating a
  call as copies: argument to parameter, return value to result.
- In JavaScript the call graph needs points-to sets (callees are
  values), so the two are built together.
- A **context-insensitive** analysis merges every caller and follows
  impossible paths (in at one call, out at another), producing false
  aliases.
- **Context sensitivity** keeps facts apart per caller: by the last k
  call sites (**call strings**), by receiver object (**object
  sensitivity**), or, equivalently, by cloning functions per context.
- More context is more precise and more expensive; when k is too small,
  a wrapper merges the callers again.

## Read it once, use it everywhere

Context sensitivity keeps callers apart by analysing a function again
for each context, and in a big program the number of contexts can be
enormous: every chain of k call sites that can reach a function is one
more copy of its facts. There is another way, and it was the second of
Sharir and Pnueli's two approaches, the "functional approach": analyse
each function once, and record not an answer but a *rule* that turns
what comes in into what goes out<Cite id="sharirpnueli1981" />. Then
each call applies the rule to its own arguments.

For `id`, the rule is a single sentence: "the result points at whatever
the parameter points at". At `a = id(o1)` that gives `{o1}`, at
`b = id(o2)` it gives `{o2}`: the precision of a context-sensitive
analysis, while `id` was read only once.

<Analogy title="the allergy label on a recipe">
A recipe card can carry a label like "contains whatever nuts you put
in the filling". The cook reads the label instead of the whole recipe,
and the label gives the right answer for every filling, because it
says how the answer depends on the input.
<span slot="breaks">A cook can always check the recipe if the label is
unclear; an analysis that uses a summary has thrown the body away, so
the summary must be safe for every possible input, and when it cannot
be precise, it has to say the worst.</span>
</Analogy>

<Figure takeaway="A summary is computed once per function and read at every call." caption="Each function's body is analysed once and boiled down to what happens to its parameter; callers use only the summary.">
  <SummaryPic />
</Figure>

<Callout kind="definition">
A **function summary** records, once per function, what the function
does with what flows into it: which parameters may be returned, stored
somewhere lasting, or passed on, and which fields it reads and writes.
At every call site the analysis applies the summary to that call's own
arguments, instead of re-reading the body.
</Callout>

<Formal title="Applying a summary">

```text
S_f : facts about the parameters
        → facts about the result
r = f(x):  facts(r) = S_f(facts(x))
```

<span slot="read">The summary of f, written S_f, is a function from
facts about f's parameters to facts about its result (and effects). At
a call where r is assigned f of x, the facts about r are what you get
by applying the summary to the facts about x at that call.</span>
</Formal>

<Examples of="function-summary">

```js
function id(p) { return p; }
// summary: result ⊇ pts(p)
```

```js
function setX(o, v) { o.x = v; }
// summary: for each obj in pts(o),
//   pts(obj.x) ⊇ pts(v); returns none
```

```text
$ go build -gcflags='-m -l' .
./main.go:23:11: p does not escape
./main.go:28:33: &P{...} does not escape
```

</Examples>

The first is `id` again: its summary needs no context at all, because
it is a rule about the parameter. The second records a side effect: a
call `setX(a, b)` means "a's objects get b's objects in their field
x", which is the store rule from two chapters back, applied at the
call. The third is real: Go's compiler (go1.24.7, with `-l` turning
inlining off) analyses `func read(p *P) float64 { return p.x }` once,
concludes "p does not escape", and at the call `read(&P{7, 8})` uses
that summary to decide the new `P` can live on the stack. Go's own
source calls these summaries "parameter tags", "used at static call
sites to improve escape analysis of function arguments"<Cite id="go-escape" />.

Recursion needs one more step: to summarise `f`, you may need `f`'s
own summary. The answer is the usual one: start every summary at
"does nothing", recompute them all, and repeat until none changes, a
fixpoint over summaries instead of over sets.

## An analysis as a page of rules

By now every analysis in this part has the same shape: some facts read
off the program, some rules of the form "if this and that, then this
other thing", and a loop that applies the rules until nothing new
appears. Real points-to analyses have dozens of such rules (fields,
arrays, casts, calls, contexts), and the hand-written loops become the
hardest part to get right. **Datalog** is a small logic language whose
whole job is exactly that loop: you write the facts and the rules, and
an engine finds the fixpoint.

<Analogy extra title="a family tree and the word “ancestor”">
Write down who is whose parent, then two rules: a parent is an
ancestor, and a parent of an ancestor is an ancestor. Anyone can now
find every ancestor by applying the rules again and again until no new
names turn up; nobody needs to write a search procedure.
<span slot="breaks">A family tree only goes back in time, so it never
loops; program facts often form cycles (a = b, b = a), and the rules
still stop because no rule ever invents a new name, so there are only
so many facts to find.</span>
</Analogy>

A **fact** is a row in a table, such as `New(a, o1)` ("a is assigned a
new object from site o1") or `Assign(a, c)` ("c = a"). A **rule** has
a head, `:-` (read "if"), and a body; variables shared between body
parts must match, which joins the tables. Here are the two rules that
compute points-to sets for copies, evaluated step by step:

<DatalogSteps client:visible />

That is Andersen's analysis from two chapters back, in two lines. Doop,
a points-to framework for Java by Bravenboer and Smaragdakis, is
written this way from end to end, including context sensitivity and
building the call graph on the fly<Cite id="bravenboer2009" />. Here is
its copy rule, quoted from its source<Cite id="doop-micro" />:

```text
VarPointsTo(?heap, ?to) :-
   Assign(?from, ?to),
   VarPointsTo(?heap, ?from).
```

It reads: the variable `?to` may point at `?heap` if there is an
assignment from `?from` to `?to` and `?from` may point at `?heap`.
Doop's other rules add a `Reachable(?method)` condition, so that only
methods the call graph has reached contribute facts, and a rule that
derives `Reachable` and `CallGraphEdge` from the points-to sets of
receivers: the call graph and the sets grow together, as the last
chapter said they must.

<Callout kind="definition">
In a **Datalog analysis**, the program is turned into facts (rows of
relations such as `Assign` and `New`), the analysis is written as
rules `head :- body`, and an engine derives every fact the rules allow,
repeating until a round adds nothing (the least fixpoint). Because
rules never invent new values, there are finitely many possible facts,
so evaluation always stops.
</Callout>

<Formal title="Reading a rule">

```text
H(x, z) :- A(x, y), B(y, z).
∀ x, y, z :  A(x, y) ∧ B(y, z) ⇒ H(x, z)
```

<span slot="read">The rule says: for all x, y and z, if A holds for x
and y, and (the wedge ∧) B holds for y and z, then H holds for x and z.
The shared y is the join: an A row and a B row combine only when they
agree on y.</span>
</Formal>

<Examples of="datalog-analysis">

```text
Path(x, y) :- Edge(x, y).
Path(x, z) :- Edge(x, y), Path(y, z).
```

```text
Pts(v, h)  :- New(v, h).
Pts(t, h)  :- Assign(f, t), Pts(f, h).
```

```text
Pts(c, t, h) :- Assign(f, t, c),
                Pts(c, f, h).
```

</Examples>

The first is a version of the warm-up in Doop's own Datalog
tutorial<Cite id="doop-micro" />: paths in a graph, from edges. The second is the analysis in the stepper. The third
shows how context sensitivity looks in Datalog: one more column, `c`,
the context, carried through each rule, so facts from different
contexts never join. Engines then make it fast: Soufflé, which is
"frequently used as a domain-specific language for analysis problems",
compiles the rules to parallel C++<Cite id="souffle-readme" />, and
Whaley and Lam's bddbddb compiled Datalog to binary decision diagrams
to handle huge numbers of contexts<Cite id="whaleylam2004" />. Run the

## Objects that never leave the room

Every object in Java, Go or JavaScript is, as far as the language is
concerned, made on the heap and cleaned up later by the garbage
collector (chapter 84). Many objects, however, live a very short life:

```js
function dist(x, y) {
  const p = { x, y };
  return Math.sqrt(p.x * p.x + p.y * p.y);
}
```

`p` is made, two fields are read, and the function returns; nothing
outside `dist` ever had a reference to it. Such an object could have
lived in `dist`'s stack frame (chapter 50), which disappears for free
when the call returns, or not existed at all, its two fields kept as
plain local numbers (scalar replacement, from chapter 95). Now change
one line:

```js
let last = null;
function dist(x, y) {
  const p = { x, y };
  last = p;   // p escapes
  return Math.sqrt(p.x * p.x + p.y * p.y);
}
```

Now `p` is reachable through `last` after `dist` returns, so it must
be a real object on the heap. The difference between the two programs
is whether the object **escapes**.

<Analogy title="notes on a meeting-room whiteboard">
Whatever is written on a meeting room's whiteboard can be wiped the
moment the meeting ends, as long as nobody took it with them. If
someone photographed the board, or pinned a note to it for the next
team, it has to be left alone.
<span slot="breaks">A photograph is a copy; a reference is not, so
whoever holds it sees every later change to the very same object, which
is why an escaping object cannot even be moved.</span>
</Analogy>

<Analogy extra title="reference-only books in a library">
A book marked "reference only" never leaves the building, so the
library can shelve it, move it or rebind it however it likes. A book
that has been lent out has to stay exactly as the borrower expects.
<span slot="breaks">The library knows which books are reference-only
because it decided so; a compiler has to work it out from the code,
for every object, before the program runs.</span>
</Analogy>

<Callout kind="definition">
An object **escapes** a region of code (a function, a loop, a thread)
when a reference to it can be used outside that region: after it ends,
or by code outside it. **Escape analysis** decides, for each allocation
site, whether its objects may escape, so that a compiler can treat the
ones that do not more cheaply. Like alias analysis it must be
conservative: "might escape" counts as "escapes".
</Callout>

## Drawing who can reach what

Choi, Gupta, Serrano, Sreedhar and Midkiff's "Escape Analysis for
Java" (1999) builds, for each method, a **connection graph**: a
points-to graph whose nodes are objects (one per allocation site),
local variables and the fields of objects<Cite id="choi1999" />. HotSpot's
optimising compiler, C2, still implements its flow-insensitive version,
and its source lists the edges each statement adds<Cite id="hotspot-escape" />:

```text
p = new T()   p  -P-> obj
p = q         p  -D-> q
p.f = q       obj -F-> f,  f -D-> q
p = q.f       obj -F-> f,  p -D-> f
```

A **P** (points-to) edge goes from a variable or field to an object, an
**F** (field) edge from an object to one of its fields, and a **D**
(deferred) edge from one variable or field to another, meaning "holds
whatever that holds"; once the graph is built, every deferred edge is
bypassed, so only points-to and field edges are left. These are the
same four rules as Andersen's analysis (in *Points-to analysis:
Andersen and Steensgaard*), drawn as a
graph. Step through one function:

## Three answers, decided by reachability

The graph is then coloured. C2 gives every object one of three states,
in these words<Cite id="hotspot-escape" />: **NoEscape**, an object
that "does not escape method or thread and it is not passed to call";
**ArgEscape**, one "passed as argument to call or referenced by
argument" that "does not escape during call"; and **GlobalEscape**, one
that "escapes the method or thread". A global starts as GlobalEscape,
an argument passed to a call that keeps no reference starts as
ArgEscape, and then each state spreads to everything it can reach: in C2's words, "for each node which is
GlobalEscape, anything it could point to is marked GlobalEscape", and
the same for ArgEscape. In the paper's words, this is "reachability
analysis on the connection graph"<Cite id="choi1999" />.

<Figure takeaway="The less an object escapes, the more the compiler may do with it." caption="The three escape states, from the most local to the least, and what each one allows.">
  <EscapeLadder />
</Figure>

<Formal title="Escape states as a lattice">

```text
NoEscape < ArgEscape < GlobalEscape
state(o) = max { start(n) : n ⇝ o }
```

<span slot="read">The states are ordered from least to most escaping.
The state of an object o is the largest starting state among all nodes
n from which o can be reached by following edges (the wavy arrow: "can
reach, in any number of steps"). An object nobody escaping can reach
keeps NoEscape.</span>
</Formal>

Notice the direction. `p.next = q` with `q` escaping does not make `p`
escape: `p` pointing *at* an escaping object is harmless, because
nothing outside can follow that arrow backwards. Being pointed at *from*
outside is what counts.

<Examples of="escape-analysis">

```js
function len(x, y) {
  const p = { x, y };   // NoEscape
  return p.x + p.y;
}
```

```js
function f() {
  const r = { v: 3 };   // ArgEscape
  use(r);  // use reads r, keeps nothing
}
```

```text
func make1() *P { p := P{3, 4}; return &p }
./main.go:14:2: moved to heap: p
func read(p *P) float64 { return p.x }
./main.go:23:11: p does not escape
```

</Examples>

In the first, `p` is only read through its own fields, so it never
leaves `len`: a candidate for the stack or for scalar replacement. In
the second, `r` is handed to `use`, which (we know from its summary)
only reads it: ArgEscape, so it must exist as an object for the call,
yet nobody keeps it, and no other thread can see it.
The third is real output from Go's compiler (go1.24.7, run with
`-gcflags='-m -l'`, so without inlining): returning `&p` makes `p`
outlive its frame, so Go moves it to the heap; `read` only reads its
parameter, so "p does not escape". Go's source states the two rules it
checks: "pointers to stack objects cannot be stored in the heap", and
they "cannot outlive that object"<Cite id="go-escape" />.

## What the answers buy

Each state unlocks something. A NoEscape object can live in its
method's stack frame, which costs nothing to free, and C2 marks such
objects as ones that "could be replaced with scalar"<Cite id="hotspot-escape" />;
V8's TurboFan does the same with its virtual objects, as chapter 95
showed<Cite id="v8-src-escape-analysis" />. An object that does not
escape its *thread* needs no locking, which was the paper's second use:
Java's `synchronized` on such an object can be removed<Cite id="choi1999" />.
And because calls are where most objects seem to escape, real analyses
are interprocedural: Go records per-function "parameter tags" (the
summaries of *Function summaries and analyses in Datalog*), so that
passing an object to a function
which only reads it is not counted as an escape<Cite id="go-escape" />.

## What you learned

- An object **escapes** a region when a reference to it can be used
  outside it; **escape analysis** finds the objects that cannot, and
  must say "escapes" whenever it is unsure.
- A **connection graph** has object, variable and field nodes, with
  points-to, field and deferred edges built from the four kinds of
  statement; deferred edges are then bypassed.
- **NoEscape**, **ArgEscape** and **GlobalEscape** spread from globals
  and arguments to everything they can reach; pointing out of an object
  never makes it escape.
- NoEscape objects can go on the stack or be scalar-replaced; objects
  local to a thread need no locks; summaries keep calls from counting
  as escapes when the callee only reads.

## The puzzle from AoS vs SoA, measured

Two of this book's benchmark suites rebuild one object per element from
struct-of-arrays columns. The first, `materialize`, keeps every object
in an array:

```js
for (let i = 0; i < n; i++)
  out[i] = { x: x[i], y: y[i] /* … */ };
```

The second, `get-objects`, hands each object to a small function and
then forgets it:

```js
for (let i = 0; i < n; i++)
  t += consume({ x: x[i] /* … */ });
```

Both loops build the same objects with the same fields, one per
element; the only difference is what happens to each object afterwards.
Here is what this book's benchmark run measured:

<BenchBars suite="get-objects" n={100000} title="get-objects: pass each element to consume(p)" highlight={['soa']} layouts={['aos', 'soa']} caption="The object is only read inside consume, and SoA did not lose at all." />

The repository's findings explain it in one sentence: V8 inlined the
consumer and removed the temporary object. This chapter takes that
sentence apart, piece by piece, and checks each piece on the Node this
book uses (Node v22.23.4, which runs V8 12.4).

## Does the object get out?

The whole question is whether anyone, anywhere, could ever see the
object itself, rather than only the numbers inside it.

<Analogy title="a cardboard tray for two coffees">
You order two coffees and the barista reaches for a cardboard tray. If
you are carrying them across town, you need it; if you are going to
drink both at the counter, the tray is pure waste, and you would rather
take the two cups and skip it.
<span slot="breaks">The barista can ask you; a compiler cannot ask the
program what it plans to do, so it has to read every line that touches
the object and prove the tray never leaves the counter.</span>
</Analogy>

<Analogy extra title="a sealed envelope in a meeting">
In a meeting, someone passes you an envelope with two numbers inside;
you read them, do a sum and bin the envelope. Nobody outside the room
ever learns the envelope existed, so it might as well have been two
sticky notes. If you posted the envelope to someone, however, it now
exists in the world, and it must be a real envelope.
<span slot="breaks">A real envelope is always made; the point of the
compiler's version is that, when nothing outside sees it, the envelope
is never made at all.</span>
</Analogy>

An object **escapes** when a reference to it reaches somewhere the
compiler cannot follow: it is stored into another object or an array,
returned, passed to a call that was not inlined, or used by an
operation that needs the object to really exist. Reading or writing its
own fields (`p.x`, `p.x = 1`) is not an escape, because that only
touches the values inside.

## Step one: see every use

In the loop as written, the object is passed to a call. To an
optimising compiler a call is a closed door, since whatever goes through
it might be stored anywhere; so the first move is to copy the small
function's body into the loop, which is called **inlining** (the
*Inlining* chapter builds it). After that, every use of the object is in
plain view. Here is a two-field version of `get-objects`:

```js
function len2(p) {
  return p.x * p.x + p.y * p.y;
}
function run() {
  let t = 0;
  for (let i = 0; i < n; i++)
    t += len2({ x: xs[i], y: ys[i] });
  return t;
}
```

`len2` reads two fields and returns a number; `run` builds a fresh
object on every iteration and passes it in. V8 will tell you when it
inlines (real output, with addresses shortened):

```
$ node --trace-turbo-inlining len2.js
Inlining 0x… {0x… <SharedFunctionInfo len2>}
  into 0x… {0x… <SharedFunctionInfo run>}
```

The line says that TurboFan, V8's top optimising tier, copied `len2`
into `run`; from here on, the object's only uses are two field reads.

## Step two: the object that isn't

Now TurboFan's escape analysis looks at each allocation, and its source
describes how. Each allocation becomes a **virtual object** that tracks
one variable per field; a store to a field sets that variable, a
load is replaced by the value last stored, and anything the analysis
does not understand counts as an escape<Cite id="v8-src-escape-analysis" />.
If, at the end, nothing needed the object to really exist, the
allocation is removed. Step through it, including the last step, where
one extra line changes the verdict:

<Callout kind="definition">
**Scalar replacement** replaces an object that does not escape with its
fields as separate local values (a *scalar* is a single plain value,
like one number): `p.x` becomes `p_x`. **Allocation sinking** moves an
allocation to the only places that still need a real object; in V8,
for a non-escaping temporary, that is the deoptimisation path, so the
fast code allocates nothing. In TurboFan's own words, an object has
**escaped** if it "escaped to untracked memory or … is used in an
operation that requires materialization"<Cite id="v8-src-escape-analysis" />.
</Callout>

<Formal title="When an object can be replaced">

```text
escapes(o) ⇔ ∃ u ∈ uses(o) :
               u ∉ { o.f , o.f = v }
¬escapes(o) ⇒ o.f  ↦  last v stored in f
```

<span slot="read">An object o escapes exactly when there is some use u
of o that is not a field read o.f or a field write o.f = v. If o does
not escape, every read of o.f can be replaced by the last value stored
into f, and then nothing reads o at all.</span>
</Formal>

## The proof is in the garbage

If the objects are really gone, the garbage collector should notice.
New objects go into V8's young generation<Cite id="v8-trash-talk" />,
and each time it fills up V8 empties it with a *scavenge* (the next
chapter takes it apart); so counting scavenges counts allocations. Run
the `len2` loop 50 times over a million elements, normally and then
with each step switched off:

```
$ node --trace-gc len2.js | grep -c Scav
3
$ node --trace-gc --no-turbo-escape \
    len2.js | grep -c Scav
1747
$ node --trace-gc --no-turbo-inlining \
    len2.js | grep -c Scav
2136
```

With both steps, fifty million objects cost three scavenges. Turn off
escape analysis and every temporary is real; turn off inlining and the
call hides the object again (and a little more is allocated, for
reasons this chapter does not chase). The figure puts this run next to
four other small loops, each run the same way:

<Examples of="scalar-replacement allocation-sinking">

```js
const p = { x: xs[i], y: ys[i] };
t += p.x + p.y; // 3 scavenges
```

```js
function make(i) {
  return { x: xs[i], y: ys[i] };
}
const p = make(i);
t += p.x * p.y; // 3 scavenges
```

```js
t += len2({ x: xs[i], y: ys[i] });
// 3; with --no-turbo-escape, 1747
```

</Examples>

The first is the simplest case: the object is built and only its two
fields are read, so TurboFan turns it into two local values and the
loop allocates nothing. The second looks as if it must escape, because
`make` *returns* the object; however, once `make` is inlined the return
is no longer a door, only a hand-over inside one function, and the
object vanishes again (with `--no-turbo-inlining` the same loop needed
1747 scavenges). The third is the realistic one, `get-objects` in
miniature: inlining first, then scalar replacement.

Now spot the difference. Each of these loops escapes:

```js
// stored where others can see it
sink = p;            // 1942 scavenges
// stored only on a path never taken
if (i === -1) sink = p; // 1748
```

The first stores `p` in a variable outside the loop, so the object must
really exist. The second is the surprising one: `i` is never `-1`, so the store
never happens, and yet in V8 12.4 every object was still allocated.
The analysis judges what the code *could* do, and one possible escape,
however unlikely, keeps the object real.

## When a guard fails

The optimised loop still has guards, the checks on its guesses from
*Speculation and deoptimisation*. If one fails halfway through, V8
falls back to the interpreter, whose bytecode still says `len2(p)` and
needs a real `p`.

<Analogy extra title="a spare key cut on demand">
A hotel does not cut a spare key for every guest; it keeps the pattern
on file, and on the rare night someone is locked out, it cuts one from
the pattern there and then.
<span slot="breaks">The new key opens the same door as the old one; the
rebuilt object is a brand-new object with the same field values, which
is only safe because no one ever saw the original to compare it
with.</span>
</Analogy>

So the object is not forgotten, only postponed. When TurboFan writes the
deoptimisation information, it describes each virtual object that is
still live by its fields, as an `ObjectState`<Cite id="v8-src-escape-analysis" />,
and the deoptimiser can then build the object for real; V8's post on
concurrent marking lists "materialization during deoptimization of a
function" among the operations that create objects<Cite id="v8-concurrent-marking" />.
That is the sunk allocation: it happens only on the path that needs it.

`materialize` has no such way out. `out[i] = p` stores the object where
code outside the loop can find it, read it later and compare it with
`out[i + 1]`; it escapes, so every allocation stays.

matters: an object that never escapes costs nothing, so only one that

## What you learned

- An object **escapes** when a reference to it reaches somewhere the
  compiler cannot follow; reading its own fields does not count.
- `get-objects` did not lose for SoA because V8 **inlined** the consumer
  and then removed the temporary object; `materialize` lost because its
  objects escape into an array.
- **Scalar replacement** turns a non-escaping object into one local
  value per field.
- **Allocation sinking** moves the allocation to the deopt path: the
  frame state describes the object by its fields, and the deoptimiser
  builds it only if a guard fails.
- Viscosity has no deoptimiser, so it must prove an object does not
  escape before it changes the layout.
