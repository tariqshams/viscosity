## Two loops, the same objects

Two of this book's benchmark suites rebuild one object per element
from struct-of-arrays columns. `materialize` keeps every object in an
array, `out[i] = { x: x[i], y: y[i] }`; `get-objects` hands each one
to a small function and forgets it, `t += consume({ x: x[i] })`. The
first was far slower for SoA; the second did not lose at all:

<BenchBars suite="get-objects" n={100000} title="get-objects: pass each element to consume(p)" highlight={['soa']} layouts={['aos', 'soa']} caption="The object is only read inside consume, and SoA did not lose at all." />

The repository's findings say why: V8 inlined the consumer and removed
the temporary object, because nobody could ever see the object itself,
only the numbers inside it.

<Analogy title="a cardboard tray for two coffees">
You order two coffees and the barista reaches for a cardboard tray. If
you are carrying them across town, you need it; if you are going to
drink both at the counter, the tray is pure waste, and you would rather
take the two cups and skip it.
<span slot="breaks">The barista can ask you; a compiler cannot ask the
program what it plans to do, so it has to read every line that touches
the object and prove the tray never leaves the counter.</span>
</Analogy>

## Does the object get out?

<Callout kind="definition">
An object **escapes** a region of code (a function, a loop, a thread)
when a reference to it can be used outside that region: after it ends,
or by code outside it. **Escape analysis** decides, for each allocation
site, whether its objects may escape, so that a compiler can treat the
ones that do not more cheaply. Like alias analysis it is conservative:
"might escape" counts as "escapes", because wrongly saying "stays
inside" could take apart an object someone still uses.
</Callout>

<Examples of="escape-analysis">

```js
let last = null;
function dist(x, y) {
  const p = { x, y };
  last = p;   // delete this: no escape
  return Math.sqrt(p.x * p.x + p.y * p.y);
}
```

</Examples>

Without line 4, `p` is made, two of its fields are read, and the
function returns; nothing outside `dist` ever held a reference, so `p`
could have lived in the stack frame, or not existed at all. With line
4, `p` is reachable through `last` after `dist` returns, so it must be
a real object on the heap. Storing an object into another object, an
array or a variable outside, returning it, passing it to a call the
compiler cannot see into, or using it where its identity matters
(`===`) are all escapes; reading or writing its own fields is not.

Choi and colleagues' "Escape Analysis for Java" (1999) builds, per
method, a **connection graph** whose nodes are objects (one per
allocation site), variables and fields<Cite id="choi1999" />, with the
edges of Andersen's four rules; HotSpot's C2 still implements it:

C2 then gives each object one of three states<Cite id="hotspot-escape" />:
**NoEscape**, **ArgEscape** (passed to a call that keeps no reference)
and **GlobalEscape**, each spreading to everything it can reach. Pointing
*at* an escaping object is harmless; being reachable *from* one is what
counts.

## Opening the door of a call

An analysis that looks at one function at a time must treat each call
as a closed door: whatever goes in might be stored anywhere. An **interprocedural** analysis opens
the door by seeing a call as copies: `r = f(x)` copies `x` into `f`'s
parameter and, on the way out, the return value into `r`, so the
inclusion rules of *Alias analysis and points-to* apply unchanged.

<Callout kind="definition">
**Interprocedural analysis** follows facts across function boundaries,
from arguments into parameters and from return values back to callers,
along the call graph. A **context-insensitive** one keeps one set of
facts per function whatever the caller; **context sensitivity** analyses
a function separately per kind of caller (usually the last *k* call
sites), so facts from one caller never flow back to another.
</Callout>

<Examples of="interprocedural-analysis context-sensitivity">

```js
function id(p) { return p; }
const a = id({ n: 1 });  // site s1
const b = id({ n: 2 });  // site s2
```

</Examples>

Both calls copy into the same parameter, so a context-insensitive
analysis gives `pts(p) = {o1, o2}`; the return copies all of it to both
callers, so `a` and `b` both get `{o1, o2}`, and the analysis says they
may alias, which they never do. It has followed a path that enters `id`
at `s2` and leaves to `s1`'s result, and no run can take it, since a
call always returns to where it came from:

<Figure takeaway="Merging all callers lets facts enter at one call and leave at another, which no real run can do." caption="Real paths (green) return to the call site they came from. A context-insensitive analysis also follows the red one: in at s2, out to a.">

</Figure>

Labelling each fact with the call site it came from (Sharir and Pnueli's
"call-string approach"<Cite id="sharirpnueli1981" />, cut to the last
*k* sites because recursion makes the chains endless) analyses `id` once
for `s1` and once for `s2`:

Object-oriented analyses often use **object sensitivity** instead, with
the allocation site of the receiver (the object a method is called on)
as the context<Cite id="milanova2005" />.

<More title="More: when k is too small, cloning, and Doop">

Wrap the call, `function wrap(q) { return id(q); }`, and every call to
`id` comes from the one site inside `wrap`, so with `k = 1` the callers
merge again; `k = 2` separates them, at the price of more contexts.
Whaley and Lam made per-context cloning practical for large Java
programs with binary decision diagrams<Cite id="whaleylam2004" />.

## Read it once, use it everywhere

Sharir and Pnueli's second approach, the "functional
approach", analyses each function once and records not an answer but a
*rule* from what comes in to what goes out<Cite id="sharirpnueli1981" />;
for `id` the rule is "the result points at whatever the parameter points
at", which gives `a` `{o1}` and `b` `{o2}`, though `id` was read once.

<Figure takeaway="A summary is computed once per function and read at every call." caption="Each function's body is analysed once and boiled down to what happens to its parameter; callers use only the summary.">
  <SummaryPic />
</Figure>

<Callout kind="definition">
A **function summary** records, once per function, what the function
does with what flows into it: which parameters may be returned, stored
somewhere lasting, or passed on, and which fields it reads and writes.
Each call site applies it to that call's own arguments, instead of
re-reading the body; recursive functions are summarised by iterating all
summaries to a fixpoint.
</Callout>

<Examples of="function-summary">

```js
function setX(o, v) { o.x = v; }
// summary: for each obj in pts(o),
//   pts(obj.x) ⊇ pts(v); returns none
```

</Examples>

A call `setX(a, b)` means "a's objects get b's objects in their field
`x`", and nothing passed in escapes further. Go keeps
exactly this kind of summary, which its source calls "parameter tags",
"used at static call sites to improve escape analysis of function
arguments"<Cite id="go-escape" />, so that passing an object to a
function that only reads it is not an escape.

## An analysis as a page of rules

In a **Datalog analysis**, the program becomes facts (rows of relations
such as `New(a, o1)`, "a gets a new object from site o1", and
`Assign(a, c)`, "c = a"), the analysis becomes rules `head :- body`
(read `:-` as "if"; a variable shared by two body parts joins their
tables), and an engine derives every fact the rules allow, round by
round, until a round adds nothing. Rules never invent new values, so
there are finitely many facts and evaluation always stops.

<Examples of="datalog-analysis">

```text
Pts(v, h)  :- New(v, h).
Pts(t, h)  :- Assign(f, t), Pts(f, h).
```

</Examples>

The first rule says an allocation points at its site; the second, joined
on `f`, says that `t = f` gives `t` everything `f` points at, which is
Andersen's analysis in two lines. A naive engine is one loop: apply every
rule to every fact so far, add what is new, and stop when a round adds
nothing; an escape analysis is the same with rules such as "an object
escapes if something that escapes points at it":

## The object that isn't

V8 takes a different road through the door: it removes the call. In
`get-objects` in miniature, a loop runs `t += len2({ x: xs[i], y: ys[i]
})`, where `len2(p)` returns `p.x * p.x + p.y * p.y`.
`node --trace-turbo-inlining` shows TurboFan copying `len2` into the
loop, after which the object's only uses are two field reads. Its escape analysis then turns each allocation into a
**virtual object** with one variable per field; a store sets the
variable, a load is replaced by the value last stored, and anything it
does not understand counts as an escape<Cite id="v8-src-escape-analysis" />:

<ScalarSteps client:visible />

<Callout kind="definition">
**Scalar replacement** replaces an object that does not escape with its
fields as separate local values (a *scalar* is one plain value): `p.x`
becomes `p_x`. **Allocation sinking** moves an allocation to the only
places that still need a real object; in V8, for a non-escaping
temporary, that is the deoptimisation path, so the fast code allocates
nothing.
</Callout>

<Examples of="scalar-replacement allocation-sinking">

```js
const p = { x: xs[i], y: ys[i] };
t += p.x + p.y;
// fast code: t += xs[i] + ys[i]
// deopt exit: { x: …, y: … } on demand
```

</Examples>

Only the fields are read, so the two values stay in registers and the
loop allocates nothing. If a guard fails halfway, however, the interpreter's bytecode still needs a real `p`; so
the deoptimisation information describes the virtual object by its
field values (an `ObjectState`), and the deoptimiser builds it only
then. Counting young-generation collections with
`--trace-gc`<Cite id="v8-trash-talk" /> shows the gap:

<Figure takeaway="Field reads only: the objects vanish. One escape, even an unlikely one: every object is real." caption="Scavenges for 50 million temporary objects, counted with --trace-gc on Node v22.23.4 (V8 12.4), one run each. The counts wobble a little between runs; the gap does not.">
  <EscapeCounts />
</Figure>

`materialize` stores each object into an array that outlives the loop,
so it escapes, and every allocation stays (even `if (i === -1) sink =
p`, a store that never runs, would do the same).

<BenchBars suite="materialize" n={100000} title="materialize: keep one object per element" highlight={['soa']} layouts={['aos', 'soa']} caption="Every object is stored and kept, so every allocation is real." />

V8's post on concurrent marking lists "materialization during
deoptimization of a function" among the operations that create
objects<Cite id="v8-concurrent-marking" />. Turboshaft, which has since
replaced TurboFan's back end<Cite id="v8-leaving-sea-of-nodes" />, adds a
late pass that removes allocations whose only uses are the stores that
fill them in<Cite id="v8-src-late-escape-analysis" />; Maglev has one
too, but in V8 12.4 `--maglev-escape-analysis` (and Maglev itself)
defaults to off.

</More>
