## Pointers become numbers

*RefCell and reference cycles* ended with three problems for a VM
built from `Rc<RefCell<..>>`: it leaks every cycle a program makes, it
panics when a program aliases the wrong objects, and it hands the
question "when does this object die?" to reference counting instead of
to the collector you wrote in *Reclaiming memory: mark and sweep*.

drip-rs's answer is the first of its design notes: no object owns
another. One owner, the **heap**, holds every object, in one big `Vec`
per kind of object; and a reference from one object to another stops
being a pointer and becomes a number, the object's position in that
`Vec`.

<Analogy title="a car park with numbered bays">
A multi-storey car park owns every bay; your ticket just says "bay
17". You can photocopy the ticket as often as you like without
creating a second car, and two drivers can leave notes on each other's
windscreens saying "I'm the blue car in bay 9". When a car leaves, its
bay is free for the next one.
<span slot="breaks">A real car park would notice if your old ticket
pointed at someone else's car; a slot number does not, so keeping a
number after its object is freed reads whatever moved in, as you will
see below.</span>
</Analogy>

## An arena is a Vec of slots

Here is the arena from drip-rs's `object.rs`, slightly shortened:

```rust
pub struct Arena<T> {
    slots: Vec<Option<T>>,
    free: Vec<u32>,
}

impl<T> Arena<T> {
    pub fn insert(&mut self, o: T)
        -> Gc<T> {
        if let Some(i) = self.free.pop() {
            let i = i as usize;
            self.slots[i] = Some(o);
            return Gc::new(i);
        }
        self.slots.push(Some(o));
        Gc::new(self.slots.len() - 1)
    }
}
```

Each slot is an `Option<T>`: `Some(object)` while it is live, `None`
once the collector frees it. `free` lists the empty slots, so `insert`
first pops the free list and refills a hole (`if let` runs its block
only if the pattern matches), and only when nothing is free does it
push a new slot onto the end. `Gc<T>` is the handle it returns: for
this chapter, read it as "slot number `i`" (the next chapter explains
the `<T>`). `remove(index, reuse)` calls `take()` on the slot, which
leaves `None` behind and hands back the object, and puts the index on
the free list only if `reuse` is true. Step through it:

<Analogy extra title="a hotel register">
A hotel does not chase guests around the building; it keeps one

<span slot="breaks">A hotel clerk would never give room 12's bill to the

reuse a slot.</span>
</Analogy>

<Callout kind="definition">
An **arena** is one collection, here a `Vec`, that owns many objects of
one type. Objects are added and removed through the arena, and
everything else refers to them by **index** instead of by pointer, so
no object owns another and cycles are only numbers. A **free list** of
empty slots lets new objects reuse old space. A **stale** index, kept
after its object was freed, reads whatever moved in: wrong, but never
undefined behaviour<Cite id="rust-std-vec" />.
</Callout>

<Formal title="Arena operations">

```text
arena : index → Option<T>
insert(o) = i, where arena[i] = None
              (or i is new); then
            arena[i] ← Some(o)
remove(i):  arena[i] ← None
```

<span slot="read">Think of an arena as a function from slot numbers to
"maybe an object". Inserting picks a slot that is empty (or a new one
at the end) and puts the object there, returning the slot number.
Removing sets a slot back to empty.</span>
</Formal>

```rust
let mut nodes = vec!["a", "b"];
let link = [1, 0]; // a→b, b→a
println!("{}", nodes[link[0]]); // b
```

```rust
// drip-rs's gc.rs: one arena per kind
pub struct Heap {
    pub strings: Arena<ObjString>,
    pub functions: Arena<ObjFunction>,
    pub upvalues: Arena<ObjUpvalue>,
    pub closures: Arena<ObjClosure>,
    pub instances: Arena<ObjInstance>,
    // ...four more, and the GC state
}
```

</Examples>

The first is the idea with nothing else: two names in a `Vec`, and a
cycle (`a` points at `b`, `b` at `a`) written as two numbers, so
following `a`'s link reads slot 1, `b`. The runnable one is a whole
tiny arena: two nodes that point at each other, followed by number,
then both freed (no counts, so no leak), and a new node that reuses a
freed slot; it prints `a -> b` and `slot 1: c`. The third is real:
drip-rs's heap has nine arenas, one per kind of object (strings,
lists, functions, natives, upvalues, closures, classes, instances and
bound methods), so asking the `instances` arena for slot 7 gives you an
`ObjInstance`, or a panic if slot 7 is empty.

## Borrowing one arena

The borrow checker still applies. `insts[i]` borrows the whole `Vec`,
so this is rejected even though the two elements differ:

```rust
let src = &insts[1];
let dst = &mut insts[0];
dst.hp += src.hp / 2.0;
```

```text
error[E0502]: cannot borrow `insts` as
  mutable because it is also borrowed as
  immutable
```

But compare it with the `RefCell` panic of the last chapter: this is a
*compile* error, and the fix is always the same: copy what you need out
first, let that borrow end, then write.

```rust
let hp = insts[1].hp; // copy a number
insts[0].hp += hp / 2.0;
```

Handles and drip-rs's `Value`s are `Copy`, so copying is cheap, and
`a.heal(a)` now simply works. drip-rs's property lookup does exactly
this, reading `let class = self.heap[instance].class;` (a copy of a
handle, so the borrow ends at the semicolon) before calling a method
that needs `&mut self`. The collector uses the same idea at a larger
scale: its mark bits do not live inside the objects but in a separate
`Marks` bitmap, one `Vec<bool>` per arena, so tracing can read the heap
through a shared borrow while marking writes the bits through a mutable
borrow of the bitmap.

<OtherLanguages title="Two objects that point at each other">

```rust
// slot numbers, owned by the arena
let a = insts.insert(Inst {
    other: None });
let b = insts.insert(Inst {
    other: Some(a) });
insts[a].other = Some(b);
```

```ts
// references, kept alive by the GC
const a = { other: null };
const b = { other: a };
a.other = b;
```

</OtherLanguages>

TypeScript links the two objects directly, and its tracing collector
frees them when nothing can reach them. The arena version links them by
number: `insert` returns a slot number, and setting `a`'s `other`
afterwards is an ordinary write into the arena. Neither object owns the
other, so the cycle costs nothing and leaks nothing; deciding when they
die is up to whoever owns the arena, which in drip-rs is the collector.

<Callout kind="engine" label="Under the hood">
Sweeping needs no list of every object (the `next` pointers of
*Objects that live on the heap*): an arena already holds every object
of its kind, so drip-rs's sweep walks each arena's slots and frees the
live, unmarked ones. The `Option` around each slot is often free: on
this machine `size_of::<ObjInstance>()` and
`size_of::<Option<ObjInstance>>()` are both 88 bytes, because Rust uses
a spare bit pattern inside the instance to mean `None`<Cite id="rust-std-option" />.
engine/rust is built on arenas too. VIR's `Module` keeps every
instruction in one `Vec`, and oxc builds the JavaScript syntax tree in
its `Allocator`, which its own documentation calls "a bump-based memory
arena for faster AST allocations"<Cite id="oxc-allocator" />.
</Callout>

## What you learned

- An **arena** is a `Vec` of slots that owns every object of one kind;
  objects refer to each other by index, so a cycle is only numbers and
  nothing leaks.
- A **free list** lets new objects reuse freed slots; a stale index then
  reads the wrong object, which is why drip-rs's test modes turn reuse
  off and panic instead.
- In an arena the borrow checker still applies, at compile time: copy
  numbers and handles out, then write.
- drip-rs keeps mark bits in a separate bitmap and sweeps by walking its
  arenas, where the TypeScript VM uses object headers and a linked list.
