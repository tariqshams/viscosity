## A question about every path

Here is a small TypeScript function with a bug in it, and the error
TypeScript gives with `strict` turned on:

```ts
let x: number, y: number;
x = 1;
if (c) { y = 2; } else { x = 3; }
console.log(x + y);
// error TS2454: Variable 'y' is used
// before being assigned.
```

If `c` is false, `y` is never set. The question is "on **every** path
to this line, was `y` given a value?", and listing paths is hopeless (a
loop makes infinitely many); so attach a small **fact** to the start
and end of every block (here, "the variables definitely assigned"), say
how each block changes it, and let facts travel along the edges.

<Analogy title="tour groups meeting at a museum door">
Two tour groups take different routes through a city and meet at the
museum door. Each guide carries a list of sights their group has seen.
The museum guide wants to know which sights *everyone* in front of her
has seen, so she keeps only the sights on both lists.
<span slot="breaks">A real guide could ask each visitor; the analysis
cannot, because once the groups merge it no longer knows which path
anyone came by, only the merged list.</span>
</Analogy>

<Callout kind="definition">
A **dataflow analysis** computes a fact for every point of a program
(usually `IN[B]` at the start and `OUT[B]` at the end of each block),
where each fact depends on the facts flowing into it along CFG edges. A
block's **transfer function** turns the fact at its start into the fact
at its end, and the **meet** combines the facts arriving from several
predecessors<Cite id="kildall1973" />. A **forward** analysis (has this
happened?) flows along the edges; a **backward** one (will this be
needed?) flows against them. A **must** question (on every path) meets
by intersection, a **may** question (on some path) by union.
</Callout>

The meet needs an order on the facts: for our sets a bigger set
promises more, and the meet is the biggest set both contain. Drawn with
the facts that promise most at the top:

<Figure takeaway="The meet of two facts is the highest fact that sits below both of them." caption="Left: every set of variables drawn from x and y, ordered by “contains”. The meet of {x, y} and {x} is {x}. Right: Viscosity’s two-point lattice for “is this a number?”.">
  <FactLattice />
</Figure>

<Callout kind="definition">
A **lattice**, in a dataflow analysis, is the set of possible facts
together with an order on them (higher means "promises more"), in which
any two facts have a **meet**: the highest fact below both of them. The
top promises everything, and the bottom promises nothing.
</Callout>

<Examples of="dataflow lattice">

```text
IN[b0] = { }        OUT[b0] = {x}
b1: y = 2           OUT[b1] = {x, y}
b2: x = 3           OUT[b2] = {x}
IN[b3] = {x, y} ⊓ {x} = {x}
```

</Examples>

Each block's transfer function adds what it assigns; at the join b3 the
meet (⊓, here intersection) keeps only `x`, and `y` missing from
`IN[b3]` is TypeScript's error. Viscosity asks "is this value a
number?" on a two-fact lattice, "number" above "maybe not", per SSA
value; a phi is a number only if every operand is, which is its meet.

## When the answer depends on itself

Add a loop and the equations go round in a circle: the test's `IN`
needs the body's `OUT`, which needs the test's `OUT`. So **guess** the
unknown facts, work everything out, and correct what is wrong until
nothing changes. As with the dominator sets of *Dominators and natural
loops*, start every unknown at the top, the **optimistic** guess, which
the meet leaves alone.

<LoopSteps client:visible />

<Callout kind="definition">
A **fixpoint** of a set of dataflow equations is a choice of facts that
the equations leave unchanged. Starting every unknown at the top and
lowering only what the equations contradict reaches the most precise
fixpoint; starting low may stop at a weaker answer that is still
self-consistent. A **worklist** holds the blocks (or SSA values) whose
facts may be out of date: take one off, recompute its fact, and only if
it changed, add whoever reads it (successors in a forward analysis,
predecessors in a backward one, users for an SSA value); when the
worklist is empty, the facts are a fixpoint.
</Callout>

Why must it stop? Every fact starts at the top and can only move down
(a smaller set coming in never gives a bigger set going out), and in a
lattice of finite **height** each fact can move down only so many
times, so the list must run dry, even for a program whose loop would
run for ever. That is the shape Kam and Ullman gave to Kildall's
idea<Cite id="kamullman1977" />:

<Callout kind="definition">
A **monotone framework** is a dataflow analysis made of a lattice of
facts with finite height, a meet, and a **monotone** transfer function
for each block (a lower fact in never gives a higher fact out). For any
such framework, iterating from the top stops, at the greatest fixpoint.
</Callout>

<Examples of="fixpoint worklist monotone-framework">

```ts
const MAX_ROUNDS = 1000;
let converged = false;
for (let rounds = 0; rounds < MAX_ROUNDS;
     rounds++) {
  let changed = false;
  for (const v of m.values) {
    const nv = compute(v);
    if (num.get(v.id) !== nv) {
      num.set(v.id, nv);
      changed = true;
    }
  }
  // ...then bindings and fields
  if (!changed) { converged = true; break; }
}
```

</Examples>

This is Viscosity's numeric inference, from
`packages/core/src/analysis.ts`, simplified. Every value that can sit
on a cycle (phis, parameters, loads, field reads) starts optimistic, at
"number"; `compute(v)` applies the rule for `v`'s instruction. Rather
than a worklist it reruns every rule in rounds until one changes
nothing: the same fixpoint, with more work. Its lattice has height 1
and its rules are monotone, so it settles; the cap is a safety net, and
if it is hit, every fact becomes "not proven", so Viscosity **fails
closed**, choosing the safe layout over an unfinished answer.

<Formal title="Definitely assigned, as equations">

```text
IN[entry] = ∅
IN[B]  = ⋂ OUT[P]   for P ∈ pred(B)
OUT[B] = IN[B] ∪ assigned(B)
```

<span slot="read">At the start of the entry nothing is assigned. For
any other block B, the fact at its start is the intersection, over
every predecessor P, of the facts at their ends; the fact at the end of
B adds the variables B itself assigns.</span>
</Formal>

## Folding, and constants that travel

Here is a loop header Viscosity prints for
`for (let i = 0; i < 2 * 50; i++)`:

```text
b1:  ; preds b0 b3
  %3 = phi %2, %14
  %4 = const 2
  %5 = const 50
  %6 = binop * %4, %5
  %7 = binop < %3, %6
```

Every pass, `%6` multiplies 2 by 50 and gets 100; a compiler can do that
once, while it compiles, and write `const 100` in its place. That is
**constant folding**. `%7` cannot follow, because `%3`, the loop
counter, is not a constant; and in SSA nothing has to be copied, since
every user of `%6` sees the constant at once. The answer must be the
machine's answer, quirks included: `'1' + 2` is `'12'`, `0.1 + 0.2` is
`0.30000000000000004`, `0 * -1` is `-0`. And constant operands are not
enough: a `call` such as `console.log(5)` prints, reading `xs[9]` can
throw, and `+` on an object first calls its `valueOf`, so none of those
may be folded.

<Callout kind="definition">
**Constant folding** replaces an instruction whose operands are all
constants with a single constant: the result of doing the operation at
compile time. It is allowed only when the operation has no side effects,
cannot throw, and gives exactly the value it would give at run time.
**Constant propagation** carries "this value is always the constant c"
from block to block, through phis, with a three-level lattice: **⊤**
(no information yet), one rung holding every constant side by side, and
**⊥** (varies). Merging gives way to anything from ⊤, keeps two equal
constants, and falls to ⊥ for two different ones.
</Callout>

<Figure takeaway="Facts only ever move down the ladder." caption="The constant lattice. At the top, ⊤: nothing known yet. In the middle, one rung holding every possible constant side by side. At the bottom, ⊥: varies. Merging two facts gives the highest fact below both of them.">
  <ConstLattice />
</Figure>

<Examples of="constant-folding constant-propagation">

```text
// let x = 1; let y;
// if (x > 0) y = 2; else y = 3;
// return y * 10;
b0: %3 = binop > %0, %2   ; 1 > 0
    condbr %3, b1, b2
b1: %4 = const 2
b2: %5 = const 3
b3: %6 = phi %4, %5       ; y
    %8 = binop * %6, %7   ; y * 10
```

</Examples>

Folding turns `%3` into `true`, then stops: `%6` is a phi whose operands
are different constants, and plain propagation, treating every block as
if it might run, meets 2 with 3 and gets ⊥. Yet `x > 0` is always true,
so b2 never runs and `y` is always 2. **Sparse conditional constant
propagation** (SCCP), by Wegman and Zadeck<Cite id="wegmanzadeck1991" />,
sees this by being optimistic about edges as well as values: every value
starts at ⊤ and every edge as not executable; a `condbr` on `true` makes
only its `then` edge executable, and a phi meets only operands that
arrive along executable edges. So `%6` meets just 2, `%8` folds to 20,
and b2 is dead. The same optimistic start keeps a loop phi like
`φ(7, itself)` at 7, while a counter `φ(0, i + 1)` still falls to ⊥.

<More title="More: folding traps, SCCP's two worklists, and real compilers">

<Run id="corners" />

Algebraic shortcuts need a proof that `x` is a number: `'3' * 1` is the
number `3`, `x - x` is `NaN` when `x` is `NaN`, and `-0 + 0` is `+0`.
Real SCCP keeps two worklists, one of CFG edges that just became
executable and one of SSA values whose fact just changed; facts live on
SSA values and move along def-use links, which is the "sparse". LLVM's
`sccp` pass is this algorithm<Cite id="llvm-passes" />, and TurboFan's
`ConstantFoldingReducer` replaces a node whose type allows only one
value with that constant<Cite id="v8-constant-folding-reducer" />.
Viscosity itself has no folding pass and does not propagate constants:
its numeric inference is the same machine with a smaller ladder, and it
does not track executable edges.
