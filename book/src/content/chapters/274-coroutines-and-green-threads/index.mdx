## A pause that only works at the top

In chapter 39 you wrote generators, and in chapters 272 and 273 you saw
them compiled into state machines. Try to pause from inside a callback,
though, and JavaScript refuses before the program even starts:

```js
function* each(xs) {
  xs.forEach((x) => { yield x; });
}
// SyntaxError: Unexpected identifier 'x'
```

The arrow function is not a generator, so `yield` means nothing inside
it. Python is quieter about the same limit: if a generator calls a
helper that contains `yield`, the call only makes a new generator
object, and nothing is paused. The reason is the lowering itself: a
generator becomes one state machine for **one** function, with room to
save that one function's variables; to pause from deeper down, it would
have to save every frame in between. This chapter is about what happens
when a language does save them.

## Coroutines

<Analogy title="two cooks and one hob">
Two cooks share a single hob. Each cooks for a while, then steps aside
and leaves their pans exactly as they were, half-stirred, so that when
their turn comes round again they carry on from that point rather than
starting the dish again.
<span slot="breaks">A cook can chop onions while waiting for the hob;
two coroutines never run at the same moment, since only the one holding
the turn runs at all.</span>
</Analogy>

<Analogy extra title="a paused film">
Pause a film to answer the door and it waits, frame and all, until you
press play; you do not watch it from the start.
<span slot="breaks">A film is paused from outside, by you; a coroutine
pauses itself, by calling yield, and can hand a value out and get one
back as it does.</span>
</Analogy>

<Callout kind="definition">
A **coroutine** is a function that can suspend itself part-way through
(it **yields**) and later be **resumed**, carrying on from the same
point with its local variables intact. Melvin Conway described programs
built from coroutines in 1963<Cite id="conway1963" />. When it always
yields back to whoever resumed it, as generators do, it is called
**asymmetric**<Cite id="moura2009" />.
</Callout>

<Examples of="coroutine">

```js
function* count() {
  yield 1; yield 2;
}
const c = count();
c.next().value; // 1
c.next().value; // 2
```

```python
def echo():
    while True:
        got = yield
        print('got', got)
e = echo(); next(e)
e.send('hi')  # prints: got hi
```

```lua
co = coroutine.create(function (a)
  local b = coroutine.yield(a + 1)
  return b * 2
end)
coroutine.resume(co, 1)  --> true 2
coroutine.resume(co, 5)  --> true 10
```

</Examples>

The first is a JavaScript generator used as a coroutine: each `next()`
resumes it until the next `yield`, which hands a value out. The second
sends values *in*: Python's `send` resumes the generator and makes the
paused `yield` evaluate to the value sent, and the reference says
plainly that this makes generators "quite similar to coroutines", except
that control always goes back to the caller<Cite id="python-expressions" />.
The third is Lua, where coroutines are a library: `resume` starts the
function with `a = 1`, `yield` hands out `2`, and the next `resume`
makes `yield` return `5`, so the function returns `10`; Lua's manual
documents that `resume` reports success with `true` before the
values<Cite id="lua-manual-coroutines" />.

<Formal title="Resume and yield">

```text
resume(c, v):  c paused at yield(□)
  ⟶ c runs with □ := v until yield(w)
  ⟶ resume(c, v) evaluates to w
```

<span slot="read">To resume a coroutine c with a value v, where c is
paused at a yield with a hole for its result: fill the hole with v and
run c until it next yields a value w; the call to resume then evaluates
to w.</span>
</Formal>

## Stackless or stackful

JavaScript generators, async functions, Python's generators and Rust's
futures are all **stackless**: each pausable function is lowered to its
own state machine, and all a paused one owns is that record. To pause
three calls deep, every function on the way down must be a coroutine
too, linked with `yield*` or `await`. A **stackful** coroutine instead
gets a whole stack of its own, so `yield` can be an ordinary call made
at any depth; Lua's manual says a yield works "even if the yield happens
inside nested function calls"<Cite id="lua-manual-coroutines" />.

<Figure takeaway="Stackless saves one function's state per level; stackful keeps a whole stack and saves one pointer." caption="Pausing three calls deep: three linked state objects, or one stack.">
  <TwoKinds />
</Figure>

How does a stackful coroutine switch? Its frames already live on its
own stack, so pausing needs only to save the CPU's registers, the
stack pointer among them, and load another coroutine's. Step through
two coroutines taking turns:

<SwitchSteps client:visible />

<Analogy extra title="a bookmark or a whole desk">
A stackless coroutine is a bookmark: it remembers one place in one
book. A stackful one is a desk you leave with every book still open
where you left it; you go to another desk and come back to find them all
as they were.
<span slot="breaks">A desk costs nothing while unused; a stack must be
reserved memory, which is why runtimes start stacks small and grow
them.</span>
</Analogy>

<Callout kind="definition">
A **stackless** coroutine saves only its own frame (a state number and
its live variables), so it can suspend only in its own body, and a call
chain of them must be marked at every level. A **stackful** coroutine
owns a separate stack, so it can suspend from any depth; switching saves
the registers and stack pointer of one and loads those of another.
</Callout>

<Examples of="stackful-vs-stackless">

```js
function* inner() { yield 1; }
function* outer() {
  yield* inner(); // must be marked
}
[...outer()]; // [1]
```

```python
def gen():
    def helper(): yield 1
    helper()   # only makes a generator
    yield 2
print(list(gen()))  # [2]
```

```go
func visit(c chan int) {
    <-c // blocks deep in the call chain
}
func walk(c chan int) { visit(c) }
// go walk(c): only this goroutine waits
```

</Examples>

The first is stackless done right: `outer` passes control into `inner`
with `yield*`, so both state machines take part. The second is the
mistake Python allows quietly: `helper()` makes a generator and throws
it away, so `1` is never produced (output from Python 3.13). The third is
stackful: a goroutine can block in `visit`, two calls down, with no
marking at all, because it has its own stack.

## Green threads

Give every stackful coroutine a scheduler that picks who runs next, and
you have a **green thread**: a thread the language's runtime schedules,
rather than the operating system. Go's `go f()` starts one, a
**goroutine**, which the specification calls "an independent concurrent
thread of control"<Cite id="go-spec-go-stmt" />.

<Analogy extra title="a waiter and many tables">
One waiter serves twenty tables: while one table reads the menu, the
waiter takes another's order; no table needs a waiter of its own.
<span slot="breaks">Tables wait politely for the waiter; in our simple
scheduler each task must yield of its own accord, and a task that never
yields would keep the waiter forever. Real runtimes also use several
waiters (operating-system threads) at once.</span>
</Analogy>

<Callout kind="definition">
A **green thread** is a thread of control scheduled by a language
runtime instead of the operating system: usually a stackful coroutine,
plus a scheduler that runs many of them on a few operating-system
threads, switching when one blocks or yields.
</Callout>

<Examples of="green-thread">

<Run id="round-robin" />

```go
done := make(chan bool)
for i := 0; i < 100000; i++ {
    go func() { <-done }()
}
// runtime.NumGoroutine() is 100001
```

```java
for (int i = 0; i < 100_000; i++)
  ts.add(Thread.ofVirtual().start(
    () -> sleep1s()));
// all done in about 2 seconds
```

</Examples>

The runnable first is a whole green-thread scheduler in a few lines,
built on generators: a queue of tasks, each run until its next `yield`
and then sent to the back. The second is Go 1.24 on this book's
machine: 100,000 goroutines all blocked at once (plus `main`), and
their stacks in use came to about 2,051 bytes each, close to the
2,048-byte minimum in the runtime's `stack.go`; a stack that fills up
is copied to one twice the size<Cite id="go-runtime-stack" />. The third
is Java 21: 100,000 virtual threads, each sleeping one second, finished
in about two seconds on four cores. OpenJDK's `VirtualThread.java`
describes "a thread that is scheduled by the Java virtual machine rather
than the operating system"; it runs on a carrier thread from a
`ForkJoinPool`, and when it blocks it unmounts and calls
`Continuation.yield`, a stackful coroutine
underneath<Cite id="openjdk-virtualthread" />.

## What you learned

- A **coroutine** suspends itself and is resumed later, locals intact.
- **Stackless** coroutines save one frame and pause only in their own
  body; **stackful** ones own a stack and pause at any depth.
- A **green thread** is a stackful coroutine plus a scheduler in the
  runtime: goroutines and Java's virtual threads.
