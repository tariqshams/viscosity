## The missing piece

The scanner makes a flat row of tokens, the grammar says which rows are
allowed, and the syntax tree is the shape we want at the end. Missing is
the program in the middle, which reads the tokens left to right, checks
them against the grammar, and builds the tree. You wrote a gentle one in
*Checkpoint: from tokens to JSON values*; here is the method behind it,
so that you can write one for any grammar.

<Analogy title="a post sorting office">
Letters arrive in one long stream. The sorter drops each letter into the
bag for its street, each full bag into the sack for its town, and each
sack into the van for its region: a flat stream goes in, and nested
containers come out.
<span slot="breaks">A sorter can pick up the letters in any order and
look at each one for as long as they like; a parser takes its tokens
strictly in order, and decides what to do from the next one or two.</span>
</Analogy>

<Callout kind="definition">
A **parser** turns a row of tokens into a syntax tree, following a
grammar. If the tokens do not fit the grammar, it reports a syntax
error instead.
</Callout>

## One function per rule

Here is a small piece of Drip's statements:

```text
statement → printStmt | block
printStmt → "print" expr ";"
block     → "{" statement* "}"
```

Write one function for each rule, and make it do, in order, what its
rule says: a terminal becomes a check that takes the token, a
nonterminal a call, a star a `while` loop, and the function returns the
node it built.

<Figure takeaway="Each piece of the rule becomes one piece of the function, in order." caption="The rule for block, and the function that parses it. The terminal { becomes consume('{'); statement* becomes a loop that calls statement until the next token is }; the terminal } becomes consume('}'). Last of all, the function returns the block node.">
  <RuleToFunction />
</Figure>

With `ts` the array of tokens, `peek()` returning the next one without
moving on, and `consume(t)` taking it and throwing if it is not `t`:

```js
function statement() {
  if (peek() === '{') return block();
  return printStmt();
}
function block() {
  consume('{');
  const body = [];
  while (peek() !== '}') {
    body.push(statement());
  }
  consume('}');
  return { kind: 'block', body };
}
```

`statement` is the choice: it peeks, and calls `block` if the next token
is `{`, otherwise `printStmt` (which takes `print`, calls `expr`, and
takes `;`). `block` takes `{`, loops while the next token is not `}`,
parsing one more statement each time, then takes `}` and returns a
block node. Watch the functions call each other:

<Callout kind="definition">
**Recursive descent** is a way to write a parser by hand, with one
function per grammar rule. A terminal becomes a check, a nonterminal a
call, an alternative an `if` that looks at the next token, and a `*` a
`while` loop. Parsing starts at the top rule and *descends* through the
calls; because rules mention each other (and themselves), so do the
functions.
</Callout>

<Examples of="parser recursive-descent">

```text
{ print 1 ; { print x ; } }
→ (block (print 1)
     (block (print x)))
```

</Examples>

The outer `block`'s second statement is a block of its own, so `block`
runs twice at once, one call inside the other, each with its own `body`
on the call stack. `statement` could choose by looking at a single token
because its two alternatives start with different tokens (`print` and
`{`); the deep dive *FIRST and FOLLOW* works out, for any grammar, when
one token is enough. Choosing with `next()` instead of `peek()` is the
mistake that bites everyone once: it *takes* the `{` while asking about
it, so `block`'s own `consume('{')` then finds `print` and throws on good
input.

From `companion/ts/src/parser.ts`, Drip's `ifStmt → "if" expression
block ( "else" ( ifStmt | block ) )?`. `match` takes a token only if it
is there, which is how the optional `else` becomes code, and
`ifStatement` calling itself is how `else if` works:

```ts
function ifStatement(): Stmt {
  const condition = expression();
  const then = bracedBody(
    "'{' after the condition");
  let otherwise: Stmt | null = null;
  if (match('else')) {
    otherwise = match('if')
      ? ifStatement()
      : bracedBody("'{' or 'if'...");
  }
  return { kind: 'if', condition,
           then, else: otherwise };
}
```

<Formal title="From rule to code">

```text
rule  A → …        function A() { … }
nonterminal  B     B()
terminal  "x"      consume('x')
( … )*             while (peek() starts it)
( … )?             if (peek() starts it)
α | β              if (peek() starts α) α
                   else β
```

<span slot="read">A rule for A becomes a function called A; a
nonterminal B in its body becomes a call to B; a terminal x becomes
consume of x. A starred group becomes a while loop that runs as long as
the next token can start the group, a group with a question mark an if
with the same test, and a choice between α and β an if that looks at
the next token to decide which to parse.</span>
</Formal>

## Precedence: one level per rule

What is `1 + 2 * 3`? Seven, because multiplication happens first; but
the tokens alone do not say that, and the ambiguous grammar from
*Grammars and parse trees* allows both trees:

<Figure takeaway="Multiplication must end up deeper in the tree than addition." caption="Two ways to group the tokens 1 + 2 * 3. In a tree, deeper operations happen first. Drip, like JavaScript and school arithmetic, builds the left one.">
  <TwoTrees which="prec" />
</Figure>

<Analogy extra title="packing for a move">
You pack small things into boxes first, and only then load the boxes
into the van. Multiplication is the boxes and addition is the van: each
product is packed and sealed before the sum loads it.
<span slot="breaks">Packing is a choice you could make differently;
precedence is a fixed rule of the language, and brackets are the only
way to ask for another order.</span>
</Analogy>

<Callout kind="definition">
**Precedence** says which operators bind tighter. In Drip, as in
arithmetic, `*`, `/` and `%` bind tighter than `+` and `-`, which bind
tighter than the comparisons, which bind tighter than `==` and `!=`; an
operator that binds tighter ends up deeper in the tree, so it is worked
out first.
</Callout>

To build it into the grammar, give each level its own rule, loosest
first, and let each rule build its operands from the next, tighter one:

```text
term    → factor ( ( "+" | "-" ) factor )*
factor  → unary ( ( "*" | "/" ) unary )*
unary   → ( "!" | "-" ) unary | primary
primary → NUMBER | "(" expression ")"
```

So `term` can only join *finished* factors, and there is no way to build
the other tree. `primary` is the base case, and a bracketed group starts
again from the loosest level, which is why brackets can override
precedence. Each level becomes one function of the same shape: get an
operand from the level below, then loop while the next token is one of
this level's operators.

```js
function term() {
  let left = factor();
  while (at('+', '-')) {
    const op = next();
    const right = factor();
    left = bin(left, op, right);
  }
  return left;
}
```

<Examples of="precedence">

```text
1 + 2 * 3   →   (+ 1 (* 2 3))
```

</Examples>

`term` calls `factor`, which gets `1` and sees `+`; that is not one of
its operators, so it returns `1`. `term` takes the `+` and calls
`factor` again, which gets `2`, sees `*`, takes it, gets `3`, and
returns the finished node `(* 2 3)`. Nobody compared the priorities of
`+` and `*`: `factor` simply never returns while a `*` is waiting.

## Associativity: which way a chain leans

Precedence does not settle `1 - 2 - 3`: both operators are on the same
level, and the two groupings give different answers.

<Figure takeaway="Same-level operators group to the left." caption="1 - 2 - 3 grouped two ways. Drip, like arithmetic, groups to the left, so the first subtraction is deeper and happens first.">
  <TwoTrees which="assoc" />
</Figure>

The loop in `term` already decides it. After `1 - 2`, `left` holds the
node `(- 1 2)`; the loop goes round again, sees the second `-`, and
builds a new node with that *whole* subtraction on its left. Each pass
wraps the tree so far, so the chain leans left.

<Callout kind="definition">
**Associativity** says how a chain of operators on the same precedence
level groups. Drip's binary operators are **left-associative**: `a - b
- c` means `(a - b) - c`. Assignment is **right-associative**: `a = b =
1` means `a = (b = 1)`.
</Callout>

<Examples of="associativity">

```text
1 - 2 - 3  →  (- (- 1 2) 3)    is -4
a = b = 1  →  (= a (= b 1))
```

</Examples>

The left grouping gives `-1 - 3`, which is `-4` (the other would give
`2`). Assignment leans right, because `1` must be stored in `b` before
that value can be stored in `a`.

Why a loop, when the grammar of *Grammars and parse trees* wrote `expr →
expr "+" item`, which says "left-associative" so clearly? Because coded
directly, the first thing `term()` would do is call `term()`, with the
same token still next, for ever, until JavaScript throws `RangeError:
Maximum call stack size exceeded`. A rule whose body starts with its own
name is *left-recursive*, and cannot be coded directly in recursive
descent; the star and the loop give the same left-leaning trees.
Recursing on the *right* instead, `return bin(left, op, term())`, does
stop, but leans the chain right: correct for assignment, wrong for `-`.

<Analogy extra title="wrapping a parcel in layers">
Wrap a present in one sheet of paper, then wrap that whole parcel in a
second sheet, then the result in a third. The first sheet ends up
innermost, and each new sheet goes round everything so far.
<span slot="breaks">A parcel is unwrapped from the outside in; a tree is
worked out from the inside out, so the innermost (first) subtraction is
done first.</span>
</Analogy>

## What you learned

- A **parser** builds a tree from tokens; **recursive descent** writes
  one function per rule, choosing with `peek()`.
- **Precedence**: one rule per level, loosest first; tighter operators
  end up deeper, and brackets restart at the top.
- **Associativity**: the loop wraps the tree so far, so `a - b - c`
  leans left; a left-recursive rule would call itself for ever.
