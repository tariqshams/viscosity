## The same answer, fifteen hundred times

Here is the heart of the `nbody` benchmark in this repository, which
works out the pull of gravity between 1,500 bodies:

```js
for (let i = 0; i < b.length; i++) {
  for (let j = 0; j < b.length; j++) {
    const dx = b[j].x - b[i].x;
    const dy = b[j].y - b[i].y;
    // ...four more lines
  }
}
```

The inner loop runs 1,500 times for every `i`, and on every one of those
trips it reads `b[i].x` and `b[i].y` again, although `i` does not change
inside the `j` loop and nothing in that loop writes to `b`. The last
chapter called such values **loop-invariant**. This chapter moves them
out of the loop, so they are worked out once per `i` rather than once per
`j`; the technique is called loop-invariant code motion, and before we
can do it we need somewhere to move them to.

## A block of its own: the preheader

"Before the loop" sounds obvious, but in a CFG it is not. The header has
at least two predecessors: the block that enters the loop, and the
latch that comes back round. Code placed in the header runs on every
trip, which is what we are trying to avoid; code placed in "the block
before" only works if there is exactly one such block and it leads only
to the header.

<Analogy title="the waiting room of a clinic">
A patient with five appointments in a row checks in at the waiting room
once, when they arrive; they do not go back out to reception between
appointments. Anything that only needs doing once per visit (showing an
ID card, filling in a form) belongs in the waiting room, not in each
appointment.
<span slot="breaks">A clinic might have two doors into the waiting room;
a preheader is built so that every way into the loop goes through this
one block, and it leads nowhere except the header.</span>
</Analogy>

<Callout kind="definition">
A **loop preheader** is a block outside a loop whose only successor is
the loop's header, and through which every edge from outside the loop
into the header passes. It dominates the whole loop without being part
of it, and it runs once each time the loop is entered, however many
trips the loop then makes<Cite id="llvm-loop-terminology" />.
</Callout>

If a loop has no preheader, the compiler makes one: add a new, empty
block `P`, point every edge that enters the header from outside the
loop at `P` instead, and give `P` a single edge to the header. The
header's phis change with it: their inputs from outside the loop now
arrive from `P` (and if several outside blocks used to enter, `P` gets a
phi of its own to merge them). LLVM's `loop-simplify` pass does exactly
this, and its documentation names LICM as the transformation it makes
simpler<Cite id="llvm-passes" />.

</Figure>

```text
b0 → b1, b3 → b1    b0 is already a

```

```text

                    loop's preheader
```

</Examples>

In the first, the loop headed by `b1` is entered only from `b0`, and
`b0`'s only edge goes to `b1` (as in last chapter's `sum`), so `b0`
already is a preheader and nothing needs adding. In the second, two
blocks enter the header, so a new block `P` is placed in front of it,
as in the figure. The third is the inner loop of `sum`: `b2` (which sets
`k = 0`) sits between the outer loop's test and the inner header `b5`,
is outside the inner loop, and leads only to `b5`, so it is the inner
loop's preheader; it runs once per trip of the *outer* loop.

## Hoisting

<Analogy extra title="making tea for a table of ten">
You do not boil the kettle ten times, once for each cup; you boil it
once, then pour ten cups. Boiling is the same whichever cup it is for,
so it moves out of the "for each cup" part of the job.
<span slot="breaks">If nobody at the table wants tea, boiling the kettle
first was wasted work; worse, if the kettle is broken you have caused a
problem that would never have happened. A compiler has to rule out the
second case exactly, as the next section shows.</span>
</Analogy>

Hoisting is then three steps: find the loop's invariant instructions
with last chapter's sweep, check that each is safe to move, and move
each safe one to the end of the preheader, keeping the order in which
they were found, so that every operand is computed before the
instruction that uses it. Step through it on the inner loop of the grid
walk from last chapter, `c[y * W + x] = 0`:

<Callout kind="definition">
**Loop-invariant code motion** (LICM) moves loop-invariant instructions
out of a loop into its preheader, so they run once each time the loop is
entered instead of once per trip. It may only move an instruction when
doing so cannot change what the program does.
</Callout>

You can see the difference in work with a counter. `mul` counts how
many times it is called; `before` multiplies inside the loop, `after`
has the multiply hoisted:

calls it once. (Here *we* did the hoisting by hand, which is fine
because `mul`'s only effect is our counter; a compiler would have to
prove a call like this has no effects before it could move it.)

## When moving it would be wrong

Being invariant is not enough. Here is a loop whose body may run zero
times, and the same loop with its invariant read hoisted:

```js
// g = [], i = 0, n = 0
for (let k = 0; k < n; k++)
  s += g[i].x;       // never runs: fine

const t = g[i].x;    // hoisted
// TypeError: Cannot read properties
// of undefined (reading 'x')
```

The original never reads `g[i].x`, because `n` is 0; the hoisted version
reads it before the loop and stops with that exact error. Two other
traps are close by: an instruction with an effect (a call, a store, a
`console.log`) would happen once instead of `n` times, and a memory read
is only invariant if nothing in the loop writes the memory it reads.

<Callout kind="definition">
In SSA form, an invariant instruction may be hoisted to the preheader
when, in addition to being loop-invariant:

1. **It cannot fail and has no effect** (it is safe to run even if the
   loop would not have run it), *or* it would certainly have run: its
   block dominates every exit of the loop, and the loop is known to run
   at least once.
2. **If it reads memory, no write in the loop may change that memory**:
   a question for alias analysis.
</Callout>

<Formal title="The hoisting rule">

```text
hoist(x) ⇐ inv(x)
  ∧ (safe(x) ∨ (∀ exit e: blk(x) dom e
                ∧ trips ≥ 1))
  ∧ (reads(x) ⇒ ¬ mayWrite(L, x))
```

<span slot="read">We may hoist x if it is invariant, and either it is
safe to run speculatively or its block dominates every exit and the loop
runs at least once, and, if x reads memory, nothing in loop L may write
what x reads.</span>
</Formal>

The usual fix for the zero-trip problem is a **guard**: wrap the loop in
`if (n > 0)` and put the preheader inside it, so the hoisted read runs
only when the loop would have run at least once. LLVM's loop rotation
does this, and its documentation walks through exactly this case, a
hoisted load that would fault when the loop does not run<Cite id="llvm-loop-terminology" />.
LLVM's `licm` pass also uses alias analysis to decide whether a load
or a call in the loop can be moved<Cite id="llvm-passes" />.

<Examples of="licm">

```js
for (let x = 0; x < n; x++)
  s += y * W + x;   // y * W: hoist
```

```js
// nbody: inside the j loop
const bx = b[i].x; // a read: only if
// nothing in the loop writes b[i].x
```

```js
if (n > 0) {          // guard
  const t = g[i].x;   // preheader
  for (let k = 0; k < n; k++) s += t;
}
```

</Examples>

The first is the easy case: `y * W` is pure arithmetic on two values
from outside the loop, it cannot throw (JavaScript's `*` on numbers
never does), so it can be hoisted however many times the loop runs. The
second is `nbody`'s read: it is invariant only because the `j` loop
writes nothing but the local variables `ax` and `ay`, which a compiler
must prove before moving it. The third is the guarded form of the
broken example above: `t` is read only when `n > 0`, which is exactly
when the original would have read it, so the program's behaviour,
including its errors, is unchanged.

<Callout kind="engine" label="Under the hood">
Viscosity moves no code: its output keeps your loops as you wrote them,
and any hoisting is left to the engine that runs the result. Its
rewritten loops do contain invariant work an engine could hoist; after
the struct-of-arrays rewrite, `ps[i].x += ps[i].vx` becomes

Whether a given engine hoists that read is up to the engine, and this
book does not assume it does.
</Callout>

## What you learned

- A **loop preheader** is a block outside the loop, entered by every
  way into the loop, whose only edge goes to the header; if there is
  none, the compiler adds one and reroutes the entering edges.
- **LICM** moves invariant instructions into the preheader, in the order
  found, so they run once per entry instead of once per trip.
- Invariant is not enough: the instruction must be safe to run early (or
  certain to run anyway), and a memory read must not be written by the
  loop.
- A **guard** (`if (n > 0)`) around the loop makes hoisting a possibly
  failing read safe when the loop might run zero times.
