## A calculator with no memory

The evaluator from the last chapter can work out `(1 + 2) * 3`, and
then it forgets; it cannot keep a running total, it cannot give a name
to a result, and it cannot even show you an answer unless something
prints it. Real programs *do* things, one after another, and they
remember what they did. In Drip, the parts that do things are
**statements**, and this chapter teaches the interpreter to run them.

## A program is a list

The parser does not return one tree for a whole program; it returns an
array of trees, one per statement, in the order they were written.
Running the program is a loop over that array, and this is `interpret`
from `companion/ts/src/interpreter.ts` (the `locals` argument comes from
the resolver, a later chapter, so ignore it for now):

```ts
interpret(statements: Stmt[],
          locals: Locals): void {
  // ...
  for (const s of statements)
    this.execute(s);
}
```

<Analogy title="a numbered recipe">
Step 4 can use the onion you chopped in step 2, but not one you will
only chop in step 6; and if the pan catches fire at step 5, you stop
there, with steps 1 to 4 done and steps 6 and 7 never started.
<span slot="breaks">A cook can do two steps at once, or skip one that
looks pointless; the interpreter does exactly one statement at a time,
in written order, and skips nothing.</span>
</Analogy>

<Callout kind="definition">
In Drip, a **program is a list of statements**. The interpreter runs
them one at a time, top to bottom; each runs to completion before the
next starts, and a runtime error stops the list where it is, so earlier
output stays and later statements never run.
</Callout>

## Statements make things happen

Here are the three statements of this chapter, from `execute` (the real
one also reports how each statement finished, which loops will need in
a later chapter):

```ts
case 'expression':
  this.evaluate(s.expression); // dropped
  return NORMAL;
case 'print':
  this.out(stringify(
    this.evaluate(s.expression)));
  return NORMAL;
case 'let':
  this.env.define(s.name.lexeme,
    s.initializer
      ? this.evaluate(s.initializer)
      : null);
  return NORMAL;
```

`evaluate` hands back a value, but no statement does: a statement is
worth running only for what it *changes*. `print` changes the world
outside the program, by adding a line of output; `let` changes the
program's memory, by adding a variable (`none`, held as `null`, when
there is no `=`). An **expression statement** evaluates its expression
and drops the value, so `1 + 2;` is legal Drip that does nothing you can
see<Cite id="mdn-expression-statement" />. It exists for expressions
that change something while they are evaluated, like an assignment.

<Analogy title="a receipt printer and a till drawer">
Ringing up a sale works out a total, but nobody cares about the number
inside the machine; what matters is what it leaves behind, a printed
receipt and more money in the drawer. Those leftovers are the side

<span slot="breaks">A shop wants the total too; an expression statement
genuinely throws its value away, and only the leftovers survive.</span>
</Analogy>

<Callout kind="definition">
A **side effect** is a change that running code makes to the world
beyond producing a value: printing output, or creating or changing a
variable. Statements exist for their side effects, and an expression
statement keeps only the side effects of its expression.
</Callout>

<Examples of="program-as-list side-effect">

```text
print 1;
print 2;    # 1, then 2
```

```text
1 + 2;      # legal; prints nothing
```

```text
let n = 0;
n += 5;     # the change is the point
print n;    # 5
```

</Examples>

The first prints `1` and then `2`, because the list runs in order. The
second is a whole program with no visible effect: the sum is worked out
and dropped. The third is how real programs use expression statements:
`n += 5;` is an assignment whose value (`5`) is dropped, but whose side
effect, `n` changing, is what the next line prints.

## A table of globals

Where does `let` put its variable? At the top level of a program, in one
table of names and values that the whole program shares, the
interpreter's `globals`, a `Map` from name strings to runtime values.
Using a variable looks its name up there, and assigning overwrites an
entry that must already exist; simplified from `lookUp` and `assign`:

```ts
case 'variable': {
  const v = globals.values.get(name);
  if (v === undefined)
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  return v;
}
case 'assign': {
  const v = this.evaluate(e.value);
  if (!globals.values.has(name))
    throw new RuntimeError(e.name,
      `undefined variable '${name}'`);
  globals.values.set(name, v);
  return v;
}
```

(`name` is `e.name.lexeme`; `undefined` is safe as "missing", because
no Drip value is held as `undefined`.) Notice that the assignment
*returns* the value: assignment is an expression with a side effect,
which is why `print a = 3;` prints `3`. For `x += e`, the companion
reads the old value of `x` once, adds the value of `e` with the ordinary
`+` rules, and stores the sum. Step through a program and watch the
table and the output change:

<Callout kind="definition">
A **global variable** is one declared at the top level of a program,
outside any block. It lives in one table shared by the whole program,
from the moment its `let` runs until the program ends. At the top level
`let` always defines, replacing an old variable of the same name, while
reading or assigning a name needs it to exist already.
</Callout>

<Examples of="global-variable">

```text
let a = 1;
print a;    # 1
```

```text
print b;    # error: undefined variable 'b'
let b = 2;
```

<Run id="running-total" />

</Examples>

The first defines `a` and then finds it. The second is a
spot-the-difference with the first: the same two lines in the other
order stop with `runtime error: undefined variable 'b'`, because the
table is filled in as the program runs, and when the `print` runs no
`let` has added `b` yet. The runnable one keeps a total across lines,
uses `+=`, prints the value of an assignment, and then replaces `total`
with a second top-level `let`, which Drip allows for globals.

## What you learned

- A Drip **program is a list of statements**, run in order; a runtime
  error stops the list, and earlier output stays.
- Statements run for their **side effects**: `print` writes output and
  `let` creates a variable; an expression statement drops its value.
- **Global variables** live in one table: `let` defines, a name looks
  up, and assignment (`=`, `+=`, `-=`) overwrites a name that must
  exist.
