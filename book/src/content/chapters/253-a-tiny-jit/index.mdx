## The interpreter is still reading

In Part IV our virtual machine ran `sumsq`, the running example of
this part, by reading its bytecode one instruction at a time; every
trip round the loop went through the dispatch loop again, deciding
afresh that `Op.Mul` means multiply. Chapter 164 showed what real engines
do about this: they count how often each function runs, and once one
is **hot** (run often enough to be worth the effort) they compile it to
machine code, while the program is still going. That is a **JIT**
compiler, "just in time"; the next chapter builds one for Drip.

Before we can, there is a more basic question. Every compiler so far
wrote its output to a file, and the operating system's loader
(chapter 252) put it into memory before anything ran. A JIT has no
file and no loader; it makes its code in the middle of a run. How does
a program make new code and then run it?

## Writing code while the program runs

<Analogy title="a busker who learns the request">
A busker who reads every song from sheet music is slow but can play
anything. When people keep asking for the same song, the busker learns
it by heart, and from then on plays it straight out, without looking
down. Reading the music is interpreting; learning the song during the
show is compiling at run time.
<span slot="breaks">A busker who forgets a bar can improvise; compiled
code that meets a case it was not built for must notice and hand back
to the slow, careful path, which the next chapter does with a
guard.</span>
</Analogy>

<Analogy title="cutting a stencil">
A sign shop paints each order by hand. When the same word comes in
for the fifth time, someone cuts a stencil, and after that each sign
takes seconds. The stencil is made during the working day, from what
the orders turned out to be.
<span slot="breaks">A stencil and a sign are plainly different
things; in a computer the new code and the data that made it sit in
the same memory, which is exactly why the rules in the next section
exist.</span>
</Analogy>

<Callout kind="definition">
**Runtime code generation** is a program producing new executable code
while it runs and then running it. The code may be source text handed
to the language's own compiler, a portable format such as WebAssembly
handed to the engine, or raw machine code written into memory and
called directly. A **JIT compiler** is runtime code generation guided
by what the program is doing, such as which functions are hot.
</Callout>

<Examples of="runtime-code-generation">

```js
const sq = new Function('x',
  'return x * x');
sq(7); // 49
```

```js
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, /* ... */ ]);
const m = new WebAssembly.Module(bytes);
```

```c
void *p = mmap(0, 4096,
  PROT_READ | PROT_WRITE,
  MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
memcpy(p, code, sizeof code);
mprotect(p, 4096, PROT_READ | PROT_EXEC);
```

</Examples>

The first is the simplest: `new Function` takes the parameter names
and the body as strings and compiles them into a real function
there and then<Cite id="mdn-function-constructor" />. It is runtime
code generation at the level of source text, and MDN warns that
it carries the same risks as `eval`: whoever controls the string
controls the code. The second is the route this chapter takes: the
program builds the bytes of a WebAssembly module and hands them to
the engine, which checks them and compiles them to machine code
itself. The third is what a native JIT such as V8's own does, in C:
the next section walks through it.

## Executable memory, and the W^X rule

The C fragment above is most of a working JIT. Here is the whole
idea, one step at a time, with eight real bytes of RISC-V machine
code (`addi a0, a0, 1` and then `ret`, so a function that adds one):

<WxSteps client:visible />

Every page of memory carries permission bits, read, write and
execute, which the processor checks on every access, and `mprotect`
changes them; an access the bits do not allow makes the kernel stop
the program with `SIGSEGV`<Cite id="linux-mprotect" />. Careful JITs
keep each page writable or executable but never both, a rule called
**W^X** ("write xor execute"): if a bug ever let an attacker write
bytes into memory, those bytes could not then be run. V8 gives two
reasons for its mode that never makes memory executable at all: some
platforms (iOS, smart TVs, game consoles) forbid ordinary programs to
write to executable memory, and refusing such writes "reduces the
attack surface"<Cite id="v8-jitless" />.

The fourth step is easy to forget. A processor may fetch instructions
through its own cache, which the program's stores did not go through;
on RISC-V, `fence.i` is "the only standard mechanism to ensure that
stores visible to a hart will also be visible to its instruction
fetches" (a hart is one hardware thread)<Cite id="riscv-zifencei" />.
`__builtin___clear_cache` is the portable spelling: compiled for
RISC-V Linux it calls the runtime library, which asks the kernel to do
the flush, while on x86-64 it does nothing, because those processors
keep the two caches in step<Cite id="compiler-rt-clear-cache" />.
(The x86-64 version of the program, with its own two instructions in
place of the RISC-V ones, printed `42` on the machine this chapter
was written on.)

<Formal title="W^X as a rule about pages">

```text
for every page p, at every moment:
  ¬ (writable(p) ∧ executable(p))
```

<span slot="read">For every page p of memory, at every moment, it is
not the case that p is both writable and executable. The symbol ¬ is
"not" and ∧ is "and"; together they say at most one of the two
permissions is on.</span>
</Formal>

## WebAssembly: the door JavaScript can use

Our Drip VM is written in JavaScript, and JavaScript has no `mmap`;
a web page cannot ask for executable memory at all. However, it can
do the next best thing. **WebAssembly** (Wasm for short; chapter 290
uses it as a target) is a binary format for code that runs on a
stack machine, like the one our VM's bytecode ran on. Browsers and
Node accept it from JavaScript, check it (a module whose code could
reach memory it was not given is refused or stopped with a trap,
rather than run<Cite id="wasm-spec-core" />) and compile it to
machine code, doing the `mmap`, `mprotect` and flushing themselves;
the next chapter looks at how V8 does that part. Here is the whole module for
`fn sq(x) { return x * x; }`:

<Figure takeaway="A module is a short header and then sections, each an id, a size and its contents." caption="The 39 bytes, one row per section. Every section starts with its id and its size in bytes; 7c is the type f64, and the last row is the function body.">
  <ModuleFigure />
</Figure>

A module starts with the four bytes `00 61 73 6d` (a zero and then
"asm") and the version, 1. After that come **sections**, each "a
one-byte section id", then the size of its contents, then the
contents<Cite id="wasm-spec-core" />. The **type section** (id 1)
lists function signatures: `60` starts one, then the parameter types
(one, `7c`, which is f64, a 64-bit float) and the result types (one,
f64 again). The **function section** (id 3) gives each function its
type. The **export section** (id 7) names what the outside world may
call: the 2-byte name `73 71` ("sq"), the kind `00` (a function) and
its index. The **code section** (id 10) holds the body: its size,
then its extra local variables (none), then the instructions,
`local.get 0` twice (`20 00`), `f64.mul` (`a2`) and `end` (`0b`).
The body runs on an operand stack, exactly as our VM's did: two gets
push `x` twice, and the multiply pops both and pushes `x * x`.

<Run id="by-hand" />

`new WebAssembly.Module(bytes)` checks and compiles the bytes, and
`new WebAssembly.Instance(module)` makes a live copy whose `exports`
are ordinary JavaScript functions<Cite id="wasm-spec-jsapi" />, so the
example prints `49`, then `2.25`, then `39 bytes`. (The specification
notes that this synchronous pair is discouraged for big modules,
because compiling can take a while; `WebAssembly.instantiate` does the
same work in the background<Cite id="wasm-spec-jsapi" />. A JIT's
modules are tiny.) One thing to remember for the next chapter: when
JavaScript calls an export that takes an f64, the argument goes
through `ToNumber`, so `sq("7")` quietly becomes `sq(7)`.

<Prompts ids={['wasm-why', 'section-shape', 'to-number']} />

Every size and count in the module is written in **LEB128**, a
variable-length code: seven bits of the number per byte, lowest
first, with the top bit of each byte saying "another byte
follows"<Cite id="wasm-spec-core" />. Small numbers (below 128) take
one byte, which is why every size above was a single byte.

<Formal title="Unsigned LEB128">

```text
n = b₀ + 128·b₁ + 128²·b₂ + …
byte k = bₖ + 128   if more follow
byte k = bₖ         for the last one
0 ≤ bₖ < 128
```

<span slot="read">Split n into base-128 digits b-zero, b-one and so
on, lowest first. Each digit becomes one byte; every byte except the
last has 128 added, which sets its top bit to say that another byte
follows. So 128 is the digits 0 and 1, written as the bytes 0x80 and
0x01.</span>
</Formal>

## What you learned

- **Runtime code generation** is a running program making code and
  running it: from source text (`new Function`), from a portable
  format (WebAssembly), or as raw machine code in memory.
- A native JIT asks for writable memory, writes the code, flips the
  page to executable (**W^X**: never both), flushes the instruction
  cache (`fence.i` on RISC-V) and calls it.
- A **WebAssembly module** is a header and sections (type, function,
  export, code), with sizes in **LEB128**; `WebAssembly.Module` and
  `WebAssembly.Instance` turn the bytes into callable functions.
