## “It worked when I tried it”

Back in chapter 3 you wrote `max`. You probably ran it on one array, saw
the right number, and moved on. Now suppose that next month you change
`max` to make it faster. Is it still right? To find out, you would have
to remember which arrays you tried, and what the answers should be.

Nobody remembers. So write it down, as code.

<Callout kind="intuition">
Pilots run through a printed checklist before every take-off, even after
ten thousand flights. Not because they forgot how to fly, but because a
written check catches the one thing memory skips. A test is a checklist
for your code, and the computer reads it out for you every time.
</Callout>

## A test is code that checks code

The smallest possible check is an `if`:

```js
if (max([3, 7, 2]) !== 7) {
  console.log('FAIL: max([3, 7, 2])');
}
```

That gets repetitive fast, so give the two jobs names. An **assertion**
checks one fact and throws if it’s false. A **test** runs some
assertions and reports whether anything threw:

```js
function expectBe(got, want) {
  if (got !== want) {
    throw new Error(
      `expected ${want}, got ${got}`);
  }
}

function test(name, fn) {
  try {
    fn();
    console.log('pass: ' + name);
  } catch (e) {
    console.log('FAIL: ' + name);
    console.log('  ' + e.message);
  }
}

test('picks the largest', () => {
  expectBe(max([3, 7, 2]), 7);
});
```

That is nearly the whole idea, and it’s how the tests behind every
exercise in this book work: `test` runs your function, `expect(x).toBe(7)`
throws if `x` isn’t `7`, and the runner counts what threw. Node’s
built-in test runner uses the same rule: a test fails if it throws, and
passes otherwise<Cite id="node-test" />.

<Callout kind="definition">
A **test** is code that runs other code on chosen inputs and checks the
results. An **assertion** is one check that must be true, like
`expect(max([3, 7, 2])).toBe(7)`. If an assertion is false, it throws,
and the test fails with a message saying what was expected and what
actually happened.
</Callout>

## Which kind of equal?

Chapter 6 showed that `===` on objects asks “same object?”. So
`expect([1, 2]).toBe([1, 2])` **fails**: two separate arrays are never
`===`. When you want “same contents”, use `toEqual`, which compares the
insides piece by piece.

Decimals need a third kind. `0.1 + 0.2` is not exactly `0.3` in
JavaScript (try it: you get `0.30000000000000004`; the next chapter shows
why). So for computed decimals, use `toBeCloseTo(0.3)`, which allows a
tiny difference.

## Two programs that should agree

Every test so far needed you to know the right answer. What if you don’t?
What is the max of a random 500-number list? Working it out by hand is
the very thing you can’t do.

<Callout kind="intuition">
Two people add up the same long receipt separately. If they get different
totals, at least one of them made a mistake, and neither had to know the
right total in advance. Agreement doesn’t prove both are right, but every
disagreement is a bug caught.
</Callout>

So write a second version that is slow but *obviously* correct. A value is
the max if nothing in the list beats it:

```js
function maxSlow(xs) {
  for (const x of xs) {
    let beaten = false;
    for (const y of xs) {
      if (y > x) beaten = true;
    }
    if (!beaten) return x;
  }
  return -Infinity;
}
```

Then feed both versions thousands of random lists, and stop at the first
disagreement. Run this against the buggy `max` from above:

<Callout kind="definition">
**Differential testing** runs two implementations of the same thing on
the same inputs and checks that they agree. You don’t need expected
answers, so the inputs can be random and endless. Every disagreement is
a bug in one of them.
</Callout>

## Running tests outside the book

In your own projects, you don’t write `test` yourself. Node comes with one,
and you run every test file with `node --test`<Cite id="node-test" />:

```js
import test from 'node:test';
import assert from 'node:assert';

test('max picks the largest', () => {
  assert.strictEqual(max([3, 7, 2]), 7);
});
```

`assert.strictEqual` is Node’s `toBe`<Cite id="node-assert" />. The engine code in
this book’s repository uses a popular library called Vitest instead, whose
`expect(x).toBe(y)` reads just like the one you’ve been using.

<Callout kind="engine" label="Under the hood">
Differential testing is the main way this book tests itself. In this
repository, the benchmark’s test file runs every particle layout, from
plain objects to struct of arrays, and checks they all compute the same
result. Later you’ll have a tree-walking interpreter, a bytecode VM and
Viscosity’s compiled output, and they must all print the same thing for
the same program. Real compiler testers do this at scale: Csmith generates
random C programs to find compiler bugs, using differential testing to
decide what counts as wrong<Cite id="csmith" />. The other approach, a
huge suite of known right answers, also exists: Test262 is the official
conformance suite for JavaScript itself<Cite id="test262" />.
</Callout>

## What you learned

- A **test** runs code on chosen inputs and checks the results. Tests run
  every time, so they catch what memory forgets.
- An **assertion** checks one fact and throws if it’s false. `toBe` is
  `===`, `toEqual` compares contents, `toBeCloseTo` allows tiny decimal
  differences.
- **Edge cases** (empty, one, zero, negative, huge, duplicates) are where
  bugs hide. Keep every old test.
- **Differential testing** checks that two implementations agree on many
  inputs, with no expected answers needed. It is how you’ll test the
  interpreters and compilers in this book.
