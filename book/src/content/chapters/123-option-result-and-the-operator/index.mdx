## Where did the value go?

You have written this TypeScript many times:

```ts
const i = [4, 5, 6].indexOf(9);  // -1
const p = ps.find((p) => p.x > 100);
console.log(p.x); // crashes if none
```

That is two ways of saying "nothing here": `-1` and `undefined`. With
`strictNullChecks`, TypeScript flags the second, because `find` returns
`P | undefined`; however, `-1` is a perfectly good number, and nothing
stops you using it as an index. Rust takes the problem away at the
root: there is no `null` and no `undefined` at all. A value that might
be missing is an ordinary value of an enum you already know how to read.

<Analogy title="a parcel-locker slip">
When you collect a parcel from a locker bank, the machine prints a slip
first. The slip says either "box 7" or "nothing for you today". You
cannot open box 7 without reading the slip, and you cannot mistake
"nothing" for a box number, because it is not a number at all.
<span slot="breaks">A paper slip can be ignored or lost; Rust will not
let you ignore an `Option`, since it is a different type from the value
inside, and every use of it has to say what happens when it is
empty.</span>
</Analogy>

<Analogy extra title="a lost-property office">
Ask at a lost-property office about your umbrella and the clerk hands
you one of two things: the umbrella, or a card saying "not handed in".
They never hand you a random umbrella and hope you will not notice,
which is what `-1` does when it pretends to be an index.
<span slot="breaks">The clerk might add "try again tomorrow"; `None`
carries no reason at all. When you need to know *why* something is
missing, Rust uses a different enum, `Result`, which the next chapter is
about.</span>
</Analogy>

## Option: maybe a value

`Option` is an enum from the standard library, like the ones in *Enums
and match*. Simplified, its definition is:

```rust
enum Option<T> {
    None,
    Some(T),
}
```

The `<T>` says "some type, to be filled in": `Option<usize>` is maybe a
`usize`, `Option<&str>` is maybe a string slice. (The chapter *Generics
and trait bounds* is about those angle brackets; for now read them like
TypeScript's `Array<T>`.) `Option`, `Some` and `None` are so common that
every Rust file can use them without importing anything. Here is
`indexOf` done honestly (`for i in 0..xs.len()` counts `i` from 0 up to,
but not including, the length, like Drip's `for i in a..b`; the chapter
*Vec and HashMap* covers Rust's loops); step through two calls:

<FindSteps client:visible />

The return type now says "maybe an index", and the caller cannot
pretend otherwise. Spot the difference: use the answer as a number, and
rustc 1.97 refuses (trimmed):

```rust
let i = find(&[4, 5], 5);
println!("{}", i + 1);  // ✗
```

```text
error[E0369]: cannot add `{integer}`
  to `Option<usize>`
12 |     println!("{}", i + 1);
   |                    - ^ - {integer}
   |                    |
   |                    Option<usize>
```

An `Option<usize>` is not a `usize`, so you have to read the slip first,
which the next section does.

<Callout kind="definition">
**`Option<T>`** is an enum with two variants: **`Some(value)`**, holding
a `T`, and **`None`**, holding nothing. A function that might have no
answer returns `Option<T>`, and the type system stops the caller from
using the `T` until it has checked which variant it got<Cite id="rust-book-enums" />.
</Callout>

<Examples of="option">

```rust
let xs = [4, 5, 6];
xs.get(1); // Some(5)
xs.get(9); // None
```

```rust
let words: Vec<&str> = vec![];
words.last(); // None
"drip".find('i'); // Some(2)
```

```rust
// from companion/rust/src/table.rs
keys: Vec<Option<StrRef>>, // None: empty
```

</Examples>

The first shows the standard library's own habit: `xs[9]` on a
three-element array would stop the program, while `xs.get(9)` asks
politely and answers `None`. In the second, `last` on an empty list has
nothing to give (`vec![]` makes an empty growable list, the `Vec` of a
later chapter), and `find` on a string answers with the byte position of
`'i'`, `Some(2)`. The third is real: the Rust Drip VM's hash table keeps
one key slot per entry, and a slot is either `Some(key)` or `None` for
empty, so "empty" can never be confused with a real key.

## Opening the slip

There are four everyday ways to get at what is inside, from the most
careful to the most blunt.

```rust
match find(&xs, 5) {
    Some(i) => println!("at {i}"),
    None => println!("absent"),
}
if let Some(i) = find(&xs, 6) {
    println!("6 is at {i}");
}
let i = find(&xs, 9).unwrap_or(0);
let j = find(&xs, 4).unwrap();
```

A `match` must cover both variants (leave out `None` and you get the
E0004 of *Enums and match*, "`None` not covered"). `if let`, from
*Patterns: the shapes match can see*, runs its block only for `Some`,
with `i` bound. `unwrap_or(0)` gives the value, or the default `0` when
there is none. And `unwrap()` gives the value or **panics**: it stops
the whole program with a message. Here is what `find(&xs, 9).unwrap()`
prints when it runs:

```text
thread 'main' (29246) panicked at
f3.rs:11:30:
called `Option::unwrap()` on a `None`
value
```

So keep `unwrap` for places where `None` would be a bug in your own
program, such as a test, never for input a user could get wrong.

<OtherLanguages title="Maybe a particle">

```rust
fn first_fast(ps: &[f64])
    -> Option<f64> {
    for i in 0..ps.len() {
        if ps[i] > 100.0 {
            return Some(ps[i]);
        }
    }
    None
}
let v = first_fast(&[3.0, 120.0]);
if let Some(v) = v { println!("{v}"); }
```

```ts
function firstFast(ps: number[])
    : number | undefined {
  for (const v of ps) {
    if (v > 100) return v;
  }
  return undefined;
}
const v = firstFast([3, 120]);
if (v !== undefined) console.log(v);
```

</OtherLanguages>

They read almost the same, and under `strictNullChecks` TypeScript also
makes you check before using `v`. The differences: in TypeScript the
check is narrowing on a union that includes `undefined`, and it is only
as strict as your compiler settings, while in Rust `Option` is an
ordinary enum, checked everywhere; and `Option` nests, so
`Option<Option<f64>>` can tell "no answer" apart from "the answer is
nothing", which `undefined | undefined` cannot.

## What Option costs

In memory, `Option` is the tagged union of *Sum types in memory*, with
one useful exception. The standard library guarantees that for some
types, such as references and `Box`, `Option<T>` is exactly the same
size as `T`: a reference is never null, so `None` can use the null bit
pattern, which the library calls the null pointer
optimization<Cite id="rust-std-option" /> (the niche of that chapter).

<Figure takeaway="Option of a reference is free; Option of a number needs a tag." caption="Sizes in bytes that rustc 1.97 printed on this machine. bool has spare bit patterns too, so Option<bool> fits in one byte, although that case is not one of the library's guarantees.">
  <OptionSizes />
</Figure>

<Formal title="Option adds one value">

```text
Option<T>  ≅  1 + T
|Option<bool>| = 1 + 2 = 3
```

<span slot="read">An Option of T is either the single value None (that
is the 1) or a Some holding any T, so it has one more possible value than T
itself: Option of bool has three, None, Some(false) and Some(true).
Whether that extra value needs extra bytes depends on whether T has a
bit pattern to spare.</span>
</Formal>

<Callout kind="engine" label="Under the hood">
The Rust Drip VM leans on `Option` where the TypeScript VM used `null`.
Returning from a call pops the running frame and then asks for the
caller with `self.frames.last()`, which is `None` when the script itself
has just returned; `pop_frame` (in `companion/rust/src/vm.rs`) returns
`Option<CallFrame>` for the same reason. A function's name is
`Option<StrRef>`, `None` for the top-level script and for anonymous
functions, which is how a stack trace knows to print `script` or
`anonymous fn`.
</Callout>

## What you learned

- **`Option<T>`** is `Some(value)` or `None`. It replaces `null`,
  `undefined` and magic values like `-1`, and it is a different type
  from `T`, so you cannot use it by accident.
- Get the value out with `match`, `if let`, `unwrap_or(default)`, or
  `unwrap()`, which panics on `None` and belongs where `None` is a bug.
- `Option<&T>` is the same size as `&T`; `Option<i32>` needs a tag.

Next: `Result`, for when you need to know *why* there is no value, and
the one-character operator that passes failures up the call stack.

## Failing out loud

When the TypeScript Drip VM meets `1 - true`, its `runtimeError` records
the message and the stack trace, then **throws**, and `interpret`
catches it several calls further out. It works; however, nothing in the
types of the functions in between says that they might be skipped, and
a reader has to know where the `catch` is. `Option` from the last
chapter will not do either: `None` says that there is no answer, but not
*why*. Rust's answer is a second enum.

<Analogy title="a delivery card">
A courier either hands you the parcel or leaves a card: "we called at
10:40; no one was home; collect it from the depot". You get one or the
other, never both, and the card tells you what went wrong and what to
do next.
<span slot="breaks">You can bin a delivery card and forget about it;
rustc warns you when a `Result` is ignored, and you cannot reach the
parcel inside an `Ok` without first dealing with the possibility of an
`Err`.</span>
</Analogy>

## Result: it worked, or here is why not

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`Ok` carries the answer, of type `T`. `Err` carries the error, of type
`E`, which can be any type you like: a `String` message, a struct, or an
enum of error kinds (the chapter *Error handling at scale* builds those).
Like `Option`, `Result`, `Ok` and `Err` need no import.

<Callout kind="definition">
**`Result<T, E>`** is an enum with two variants: **`Ok(value)`** for
success, holding a `T`, and **`Err(error)`**, holding an `E` that
describes the failure. A function that can fail returns `Result`, so its
failure is part of its type, and callers must deal with it before they
get the `T`<Cite id="rust-book-result" />.
</Callout>

<Examples of="result">

```rust
"42".parse::<i32>() // Ok(42)
"4x".parse::<i32>()
// Err(ParseIntError { kind: InvalidDigit })
```

```rust
fn as_num(v: &Value)
    -> Result<f64, String> {
    match v {
        Value::Number(n) => Ok(*n),
        _ => Err(String::from(
            "not a number")),
    }
}
```

```rust
// from companion/rust/src/vm.rs
pub struct RuntimeError;
type Run<T = ()> = Result<T, RuntimeError>;
fn run(&mut self) -> Run { /* ... */ }
```

</Examples>

The first is the standard library's: `parse::<i32>()` turns text into a
32-bit number, and the `::<i32>` (read "turbofish") says which number
type you want. `"42"` gives `Ok(42)`; `"4x"` gives an `Err` holding a
`ParseIntError` that says why, and printed with `{}` it reads `invalid
digit found in string`. The second checks a Drip value and either hands
back the number or explains: `*n` copies the `f64` out of the borrowed
value. The third is real: drip-rs names its result type once, `Run<T>`,
whose error is a `RuntimeError` (the message itself has already been
written to the error output by then), so `run` returns `Run`, meaning
`Result<(), RuntimeError>`: nothing useful on success, an error on
failure.

Unlike a thrown exception, an `Err` is an ordinary return value, so you
can forget to look at it. rustc notices; here is the spot-the-difference:

```rust
as_num(&t);                // ⚠ ignored
let n = match as_num(&t) { // ✓ handled
    Ok(n) => n,
    Err(e) => return println!("{e}"),
};
```

```text
warning: unused `Result` that must be used
15 |     as_num(&t);
   |     ^^^^^^^^^^
   = note: this `Result` may be an `Err`
     variant, which should be handled
```

## Passing it up with ?

Subtraction needs two numbers. Written with `match`, it would check each
operand and return early on `Err`, twice. That shape is so common that
Rust gives it one character:

```rust
fn sub(a: &Value, b: &Value)
    -> Result<f64, String> {
    let x = as_num(a)?;
    let y = as_num(b)?;
    Ok(x - y)
}
```

`as_num(a)?` means: if this is `Ok(n)`, the whole expression is `n`; if
it is `Err(e)`, return `Err(e)` from `sub` right now. Step through a
failing call:

<Analogy extra title="passing a form back up the chain">
A clerk who finds a problem with a form does not fix it, and does not
run to the director; they hand it back to whoever gave it to them, with
a note. That person may handle it, or hand it back again. Each desk
decides, one desk at a time, and every desk can see the form go past.
<span slot="breaks">In an office the note travels as it is; Rust's `?`
may also convert the error into the caller's error type on the way
(with the `From` trait), so each desk can speak its own language of
errors.</span>
</Analogy>

<Callout kind="definition">
The **`?` operator**, written after a `Result`, unwraps an `Ok` and
otherwise returns the `Err` from the enclosing function at once,
converting the error into the function's error type with
`From`<Cite id="rust-std-from" />. After an `Option`, it unwraps `Some`
and returns `None`. It may only be used in a function whose return type
can hold that early return<Cite id="rustref-question-mark" />.
</Callout>

<Formal title="What ? stands for">

```text
e?  ≡  match e {
         Ok(v) => v,
         Err(x) =>
           return Err(From::from(x)),
       }
```

<span slot="read">Writing a question mark after an expression e that
gives a Result means the same as matching on e: if it is Ok holding v,
the expression's value is v; if it is Err holding x, the function
returns at once with an Err holding x, converted to the function's own
error type.</span>
</Formal>

<Examples of="question-mark">

```rust
fn doubled(s: &str)
    -> Result<i32, ParseIntError> {
    let n = s.parse::<i32>()?;
    Ok(n * 2)
}
```

```rust
// companion/rust/src/vm.rs: an Option
let caller = self.frames.last()?;
```

```rust
// companion/rust/src/vm.rs: in run
OpCode::Sub => {
    let (a, b) = self.pop_numbers("-")?;
    self.push(Value::Number(a - b));
}
```

</Examples>

The first parses a number and doubles it: `doubled("21")` is `Ok(42)`,
and for `doubled("x")` the `?` returns the `ParseIntError` at once, so
the doubling never happens (`ParseIntError` is imported with `use
std::num::ParseIntError;`). The second is from `pop_frame`, which
returns an `Option`: when there is no caller frame (the script itself
has finished), `last()` gives `None` and the `?` returns `None` at once.
The third is the VM's subtraction: `pop_numbers` either hands back two
numbers or reports Drip's error (for `1 - true` that is `cannot use '-'
on a number and a boolean`) and returns an `Err`, which the `?` passes
straight out of `run`.

The rule about where `?` may go is checked. Use it in a function that
returns a plain `f64`:

```text
error[E0277]: the `?` operator can only be
  used in a function that returns `Result`
  or `Option` (or another type that
  implements `FromResidual`)

   | ---------------------------
   |   this function should return
   |   `Result` or `Option` to accept `?`

   |                      ^ cannot use the

```

<OtherLanguages title="Two steps that can fail">

```rust
fn total(a: &str, b: &str)
    -> Result<i32, ParseIntError> {
    let x = a.parse::<i32>()?;
    let y = b.parse::<i32>()?;
    Ok(x + y)
}
match total("1", "x") {
    Ok(n) => println!("{n}"),
    Err(e) => println!("bad: {e}"),
}
```

```ts
function toInt(s: string): number {
  const n = Number(s);
  if (!Number.isInteger(n))
    throw new Error('bad: ' + s);
  return n;
}
function total(a: string, b: string) {
  return toInt(a) + toInt(b);
}
try { console.log(total('1', 'x')); }
catch (e) { console.log(String(e)); }
```

</OtherLanguages>

The TypeScript `total` has no sign of failure in its type, or in its
body: the exception passes through it unseen (the jump the chapter
*Exceptions and stack unwinding* compiled, with landing pads). The Rust
`total` says `Result` in its signature, and each place it can fail is
marked with a `?` you can see. It is the same idea as an exception, made
into a value, which is also why it costs only an ordinary return.

## What you learned

- **`Result<T, E>`** is `Ok(value)` or `Err(error)`. Failure is in the
  function's type, instead of thrown past it, and an ignored `Result`
  earns a warning.
- **`?`** unwraps `Ok` or `Some`, and otherwise returns early with the
  `Err` (converted with `From`) or the `None`. It only works in functions
  that return a matching type.
- drip-rs returns its runtime errors where the TypeScript VM throws
  them, one visible `?` at a time.
