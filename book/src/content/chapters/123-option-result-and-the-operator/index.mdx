## Nothing, and failure

TypeScript has two ways of saying "nothing here": `indexOf` returns
`-1`, which is a perfectly good number that nothing stops you using as
an index, and `find` returns `undefined`, which `strictNullChecks`
catches only if it is on. It also has one way of failing: when your
Drip VM meets `1 - true` it **throws**, and `interpret` catches it
several calls further out, although nothing in the types in between says
they might be skipped. Rust has no `null`, no `undefined` and no
exceptions; it uses two ordinary enums instead.

<Analogy title="a parcel-locker slip">
When you collect a parcel from a locker bank, the machine prints a slip
first. The slip says either "box 7" or "nothing for you today". You
cannot open box 7 without reading the slip, and you cannot mistake
"nothing" for a box number, because it is not a number at all.
<span slot="breaks">A paper slip can be ignored or lost; Rust will not
let you ignore an `Option`, since it is a different type from the value
inside, and every use of it has to say what happens when it is
empty.</span>
</Analogy>

## Option: maybe a value

```rust
enum Option<T> {
    None,
    Some(T),
}
```

That is the standard library's definition, simplified. `<T>` is a type
parameter, read like TypeScript's `Array<T>` (*Generics and
monomorphization* covers it): `Option<usize>` is maybe a `usize`.
`Option`, `Some` and `None` need no import. Here is `indexOf` done
honestly; step through two calls:

<Examples of="option">

```rust
let xs = [4, 5, 6];
xs.get(1);                  // Some(5)
xs.get(9);                  // None
let i = find(&xs, 9).unwrap_or(0);
if let Some(i) = find(&xs, 6) {
    println!("6 is at {i}"); // 2
}
// find(&xs, 5) + 1          // E0369
```

</Examples>

`xs[9]` would stop the program, while `xs.get(9)` answers `None`. An
`Option<usize>` is not a `usize`, so adding 1 to one is E0369, "cannot
add `{integer}` to `Option<usize>`": you have to read the slip first.
`unwrap_or(0)` gives the value or a default; `if let` runs only for
`Some`, with `i` bound; a `match` must cover both variants; and
`unwrap()` gives the value or **panics**, so `find(&xs, 9).unwrap()`
prints ``thread 'main' (29246) panicked at f3.rs:11:30: called
`Option::unwrap()` on a `None` value`` (the thread id changes from run
to run). Keep `unwrap` for places where `None` would be a bug in your
own program, such as a test.

`Option` costs nothing for references: a reference is never null, so
`None` can use the null bit pattern, and the standard library guarantees
`Option<&T>` is the same size as `&T`<Cite id="rust-std-option" />. An
`i32` has no spare pattern, so `Option<i32>` needs a tag:

</Figure>

<Callout kind="definition">
**`Option<T>`** is an enum with two variants: **`Some(value)`**, holding
a `T`, and **`None`**, holding nothing. A function that might have no
answer returns `Option<T>`, and the type system stops the caller from
using the `T` until it has checked which variant it got<Cite id="rust-book-enums" />.
</Callout>

## Result, and passing it up with ?

`None` says there is no answer, not *why*. For that, Rust has
`enum Result<T, E> { Ok(T), Err(E) }`: `Ok` carries the answer, and
`Err` carries an error of any type you like (a `String`, a struct, or an
enum of error kinds, as *Errors at scale* builds). Because an `Err` is an
ordinary return value, failure is part of the function's type, and
calling a function for its `Result` and ignoring it earns a warning:
"unused `Result` that must be used".

Checking each step and returning early on `Err` is so common that Rust
gives it one character. `as_num(a)?` means: if this is `Ok(n)`, the
expression is `n`; if it is `Err(e)`, return `Err(e)` from the enclosing
function right now. Step through a failing call:

`as_num` either hands back a Drip number or explains why not (`*n`
copies the `f64` out of the borrowed value). `sub` uses `?` twice, so
`sub(&one, &t)` returns the `Err` from the second `as_num`, and `x - y`
never runs. The last lines are the standard library's own `Result`:
`"42".parse::<i32>()` is `Ok(42)` (the `::<i32>` says which number type
you want), and `"4x"` gives an `Err` holding a `ParseIntError` that says
why. After an `Option`, `?` works the same way, returning `None`; the
Rust Drip VM's `pop_frame` does that with `self.frames.last()?`. And `?`
is checked: in a function that returns a plain `f64` it is E0277, "the
`?` operator can only be used in a function that returns `Result` or
`Option`", since an `f64` has nowhere to put the early return.

<Callout kind="definition">
**`Result<T, E>`** is an enum with two variants: **`Ok(value)`** for
success, holding a `T`, and **`Err(error)`**, holding an `E` that
describes the failure<Cite id="rust-book-result" />. The **`?`
operator**, written after a `Result`, unwraps an `Ok` and otherwise
returns the `Err` from the enclosing function at once, converting the
error with `From`<Cite id="rust-std-from" />; after an `Option`, it
unwraps `Some` and returns `None`. It may only be used in a function
whose return type can hold that early return<Cite id="rustref-question-mark" />.
</Callout>

## Throwing versus returning

drip-rs names its result type once, `type Run<T = ()> = Result<T,
RuntimeError>;`, and its dispatch loop subtracts with
`let (a, b) = self.pop_numbers("-")?;`: for `1 - true`, `pop_numbers`
reports Drip's error and returns an `Err`, which every frame passes
straight out:

<Figure takeaway="A throw jumps over frames; an Err is returned by each one." caption="The same runtime error in the two Drip VMs. In TypeScript the exception passes straight from the throw to the catch; in drip-rs every frame returns the Err, and every one of their signatures says Result.">
  <ThrowVsReturn />
</Figure>

It is the same idea as an exception, made into a value: the signature
says `Result`, each place a function can fail is marked with a `?` you
can see, and the cost is only an ordinary return.

<More title="More: Option by hand, nesting, and the rule for ?">

<Run id="opt-play" />

That is `find` written out, with the four ways of opening the slip.
`Option` nests, so `Option<Option<f64>>` can tell "no answer" from "the
answer is nothing", which `undefined | undefined` cannot; and it is an
ordinary enum, checked everywhere, where `T | undefined` is only as
strict as your compiler settings. `Option<T>` has exactly one more
possible value than `T`, which is why it needs extra bytes only when `T`
has no bit pattern to spare (the deep dive *Sum types in memory* says
more). `?` spelled out is:

```text
e?  ≡  match e {
         Ok(v) => v,
         Err(x) =>
           return Err(From::from(x)),
       }
```

The thrown exception, by contrast, is the jump the deep dive
*Exceptions and stack unwinding* compiles, with landing pads.

</More>

## What you learned

- **`Option<T>`** is `Some` or `None`; **`Result<T, E>`** is `Ok` or
  `Err`. Both replace values you could misuse with types you must check.
- **`?`** returns early with the `Err` or `None`, visibly, in functions
  that return a matching type.
