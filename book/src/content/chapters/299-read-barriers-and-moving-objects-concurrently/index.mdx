## Two copies of one object

*Incremental and concurrent collection* let the program run while the collector marked.
Marking only *colours* objects; nothing moves, so every pointer the
program holds stays valid. A copying or compacting collector moves
objects, and if it does that while the program runs, the program may
be holding the old address. Run this:

<Run id="stale" />

The collector has made a copy, but the program still has the old
pointer and writes 5 into the old copy; when the collector finishes and
throws from-space away, the write is gone. The write barrier cannot
help: the store itself was ordinary; what went wrong is that the
program *read* a pointer that should no longer be used.

## The to-space invariant

Henry Baker's 1978 collector fixed this for a copying collector, so
that every list operation took a bounded time, however big the
heap<Cite id="baker1978" />. It is Cheney's algorithm run incrementally:
when the program allocates, the collector scans a few more objects, so
`scan` creeps towards `free` a little at a time. And whenever the
program fetches a pointer that leads into from-space, a check on the
fetch copies the object first (or follows its forwarding pointer, if
it has been copied), so the program only ever receives to-space
addresses<Cite id="baker1978" />. Lieberman and Hewitt's generational
collector, from *Generational collection in depth*, was built as an extension of
it<Cite id="lieberman1983" />.

<Analogy title="a library moving buildings while open">
A library is moving to a new building, a shelf at a time, and stays
open. If you ask for a book that is still in the old building, the
librarian fetches it to the new one before handing it over, and
crosses its old slot out with "now in the new building". You never
hold a book from the old building, so nothing you write in a margin is
lost.
<span slot="breaks">A librarian is asked for a book now and then; a
read barrier runs on every pointer the program loads, which is very
often, so the check must be a couple of instructions on its fast
path.</span>
</Analogy>

<Analogy extra title="a ticket checked at every door">
In a building being renovated, every door has a guard who glances at
your pass: almost always it is current and you walk through, and only
an out-of-date pass sends you to the desk to get a new one.
<span slot="breaks">A guard can wave someone through by mistake; a
barrier never may, since one stale pointer is enough to lose a
write.</span>
</Analogy>

<Callout kind="definition">
A **read barrier** is code that runs when the program loads a pointer
from the heap. In a concurrent copying or compacting collector it
keeps the **to-space invariant**: the program never holds a pointer to
an object's old copy. If a loaded pointer leads to an object that is
being moved, the barrier follows its forwarding pointer, or copies the
object itself, and returns the new address. Many read barriers also
**heal** the field they loaded from, writing the new address back so
the next load takes the fast path.
</Callout>

<Formal title="The to-space invariant">

```text
∀ p held by the program : p ∉ From
load(o.f) = fwd*(o.f)
```

<span slot="read">For every pointer p that the program holds, p does
not point into from-space. Loading field f of object o gives back the
value in o.f with its forwarding followed (copied first, if need be),
which is what the star means: follow the forwarding as far as it
goes.</span>
</Formal>

## Shenandoah and ZGC

Read barriers have a reputation for cost, for a plain reason: a
program loads pointers far more often than it stores them, so a check
on every load runs far more often than one on every store. Two OpenJDK
collectors pay it anyway, because a concurrent compactor buys
something big: pauses that do not grow with the heap.

**Shenandoah** marks concurrently with a snapshot barrier (its barrier
set has an SATB queue) and then evacuates objects while the program
runs. Its **load-reference barrier** in OpenJDK 21 reads (with `_heap->`
and two setup lines dropped):

```cpp
if (has_forwarded_objects() &&
    in_collection_set(obj)) {
  oop fwd = resolve_forwarded_not_null(obj);
  if (obj == fwd &&
      is_evacuation_in_progress()) {
    return evacuate_object(obj, t);
  }
  return fwd;
}
return obj;
```

If the object is in a region being emptied (the *collection set*) and
already has a copy, return the copy; if it has none yet, the program's
own thread copies it then and there. Two threads may race to copy the
same object, so the copy is published with an atomic update of the
forwarding slot, and the loser uses the winner's copy (*Threads, memory models and atomics* covers why that needs atomic
operations)<Cite id="shenandoah-lrb" />.

**ZGC** puts the check in the pointer itself. A **coloured pointer**
carries metadata bits next to the address; OpenJDK 21's ZGC keeps two
low-order bytes of them, with *remapped*, *marked* and *remembered*
bits for its phases<Cite id="zgc-barrier" />. The load barrier tests
the loaded pointer against a "bad" mask for the current phase: a good
pointer goes straight through, with its metadata shifted off; a bad
one takes a slow path (`relocate_or_remap`, as the phase needs) and
then **self-heals** the field with a good pointer<Cite id="zgc-barrier" />.

The first two are real, from OpenJDK 21.0.12 on this book's machine,
running a loop that makes 50 million small records with a 128 MB heap
(`-Xlog:gc`, trimmed). Shenandoah evacuated objects for 2.7 ms and
fixed references for 4.8 ms with the program running, and its pauses
were hundredths of a millisecond. The second is generational ZGC
(`-XX:+ZGenerational -Xlog:gc+phases`): across that run's 67 pauses
the longest was 0.153 ms. The third is Baker's barrier in his own
terms, list operations on Lisp's pairs: taking the first element
(`car`) of a pair that is still in from-space moves it first.

<Callout kind="engine" label="Under the hood">
V8 takes the other road. Its major collector compacts only some
old-generation pages, during the final pause, with parallel
threads<Cite id="v8-trash-talk" />, so the program never runs while
objects move and ordinary loads need no check. It is a different bet: a
pause that is short because it is parallel and partial, against a
small cost on every pointer load, all the time.
</Callout>

## What you learned

- Moving objects while the program runs can leave it holding an old
  copy, so a write can be lost; a **read barrier** checks every pointer
  load to stop that.
- **Baker's** collector keeps the to-space invariant: a load that
  leads into from-space copies (or follows) the object first.
- **Shenandoah's** load-reference barrier copies on demand and
  publishes copies atomically; **ZGC** tests colour bits in the pointer
  and **self-heals** the field; both keep pauses well under a
  millisecond in this chapter's runs.
