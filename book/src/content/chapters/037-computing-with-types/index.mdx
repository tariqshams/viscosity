## Two types that must agree

This whole book is about one change of layout: a list of records (an
array of objects) turned into one array per field. Labelled
in TypeScript, the two layouts look like this:

```ts
interface Particle {
  x: number; y: number;
  vx: number; vy: number;
}
interface Columns {
  x: number[]; y: number[];
  vx: number[]; vy: number[];
}
```

The second is the first with `[]` added, by hand. Add a `mass` field to
`Particle` and forget `Columns`, and nothing complains; the two quietly
drift apart. What we want is to write `Columns`
as a rule, "for every key of `Particle`, an array of that key's type", and
let the checker work it out. That rule needs three pieces: the list of
keys, the type behind one key, and a way to build a type key by key.

## keyof: the list of names

<Analogy title="the headings of a spreadsheet">
A spreadsheet of particles has the headings x, y, vx and vy along its top
row. Asking "which columns does this sheet have?" gives you those four
names, and nothing about the numbers underneath.
<span slot="breaks">Headings have an order, left to right; `keyof` gives
a union, which has no order. Also, the sheet is real data, while `keyof`
reads only the *type*, so a property added at run time is not in it.</span>
</Analogy>

```ts
type PKey = keyof Particle;
// 'x' | 'y' | 'vx' | 'vy'
```

`keyof` takes an object type and gives back a union of its keys, each as
an exact string type (the literal types of the tagged-unions chapter). Its best use is
as a constraint, so that only real property names are accepted:

```ts
function get<T, K extends keyof T>(
  o: T, k: K): T[K] {
  return o[k];
}
get(p, 'vx'); // fine: a number
get(p, 'vX');
// error: Argument of type '"vX"' is not
// assignable to parameter of type
// 'keyof Particle'.
```

That is chapter 28's typo, now caught even when the name arrives as a
string. Notice `K extends keyof T`, a constraint (chapter 36) that uses
another blank: `K` must be one of `T`'s keys, whatever `T` turns out to be.

<Callout kind="definition">
**`keyof T`** is the union of the property names of the object type `T`,
each as a literal type. If `T` has a string index signature (any string
is a key), `keyof T` is `string | number`, because JavaScript turns a
number key into a string<Cite id="ts-keyof-types" />.
</Callout>

<Examples of="keyof">

```ts
type K = keyof { a: number; b: string };
// 'a' | 'b'
```

```ts
type F = keyof Particle;
const cols: F[] = ['x', 'vx'];
const bad: F[] = ['mass'];
// error: Type '"mass"' is not assignable
// to type 'keyof Particle'.
```

<Run id="keys-at-runtime" />

</Examples>

The first is the smallest case: two keys, a union of two names. The
second is a checked list of field names, the kind Viscosity keeps when it
chooses which fields to split into columns. The runnable one shows the limit: `keyof` is about the
type, so at run time `Object.keys` can find more keys than the type
lists, which is why TypeScript gives `Object.keys` the plain type
`string[]` rather than `(keyof T)[]`.

## T[K]: the type behind one key

The return type of `get` above was `T[K]`. Square brackets on a value
read a property (chapter 5); on a type, they read the *type* of a
property.

<Analogy title="a catalogue">
A shop catalogue lists each product code with a description of what it
is. Looking up code `vx` tells you what kind of thing you will get,
without fetching it from the shelf.
<span slot="breaks">A catalogue lookup happens when you ask; a `T[K]`
lookup is worked out by the checker before the program runs, and it never
fetches a value at all, only a type.</span>
</Analogy>

<Figure takeaway="keyof reads the column of names; T[K] goes along one row." caption="Particle drawn as a table of names and types. keyof Particle collects every name into one union. Particle['vx'] starts at the name vx and reads across to its type, number.">
  <KeyLookup />
</Figure>

<Callout kind="definition">
An **indexed access type**, `T[K]`, is the type of property `K` of type
`T`. The index must be a type: a literal such as `'x'`, a union of keys
(giving a union of their types), `keyof T` itself, or `number` for the
element type of an array<Cite id="ts-indexed-access-types" />.
</Callout>

<Examples of="indexed-access-type">

```ts
type X = Particle['x']; // number
type Bad = Particle['vX'];
// error: Property 'vX' does not exist
// on type 'Particle'.
```

```ts
type Row = { id: number; name: string };
type V = Row[keyof Row]; // number | string
type P = Particle[][number]; // Particle
```

```ts
type Kind = Expr['kind'];
// 'num' | 'add' | 'mul'
```

</Examples>

The first is a single lookup, and a misspelt key is an error, as on a
value. In the second, indexing with a union gives a union, so
`Row[keyof Row]` is "the type of any one field"; and indexing an array
type with `number` gives the type of its elements (any number index
reads one element). The third uses the `Expr` type of the tagged-unions chapter: indexing a
discriminated union by its tag gives the union of every tag, so the list
of node kinds never has to be written out a second time.

## Mapped types: a type built key by key

Now the rule from the start of the chapter can be written down:

```ts
type Columns<T> = {
  [K in keyof T]: T[K][];
};
type PC = Columns<Particle>;
```

Read `[K in keyof T]` as a loop: for each key `K` of `T`, add a property
named `K` whose type is `T[K][]`, an array of that key's type. Step
through what the checker builds:

<MapSteps client:visible />

<Analogy title="a mail merge">
A mail merge takes one letter with a gap for the name and a list of
names, and prints one copy of the letter per name, each with its own name
filled in.
<span slot="breaks">A mail merge prints many letters; a mapped type makes
one object type, with one property per key. And the merge happens on
paper, while the mapped type happens only in the checker, and is erased
before the program runs.</span>
</Analogy>

<Analogy title="a formula filled down a column">
In a spreadsheet you write one formula, say "double the cell to the
left", and fill it down; each row gets the same rule applied to its own
value.
<span slot="breaks">A spreadsheet recalculates whenever the data
changes; a mapped type is worked out once, when the program is checked,
and it describes values without ever computing one.</span>
</Analogy>

Two **modifiers** can be added to each property as it is built: `?`
makes it optional (it may be missing, in which case reading it gives
`undefined`), and `readonly` stops it being assigned. A `-` in front
removes the modifier instead<Cite id="ts-mapped-types" />.

<Callout kind="definition">
A **mapped type**, `{ [K in U]: F }`, builds an object type with one
property for each member `K` of the union `U` (usually `keyof T`), whose
type is `F`, which may mention `K`. Writing `?` or `readonly` before the
colon adds that modifier to every property; `-?` and `-readonly` remove
it<Cite id="ts-mapped-types" />.
</Callout>

<Examples of="mapped-type">

```ts
type Flags<T> = { [K in keyof T]: boolean };
// x: boolean; y: boolean; and so on
```

```ts
type Opt<T> = { [K in keyof T]?: T[K] };
const patch: Opt<Particle> = { x: 3 };
```

```ts
type Frozen<T> = {
  readonly [K in keyof T]: T[K];
};
const f: Frozen<Particle> = p;
f.x = 3;
// error: Cannot assign to 'x' because
// it is a read-only property.
```

</Examples>

The first gives every key the same type, ignoring `T[K]`: a set of
on-off switches, one per field, such as "which fields has this function
read?". The second keeps each type but adds `?`, so any subset of fields
is allowed, which is what an "update these fields" argument needs. The
third adds `readonly`, so the checker refuses any assignment; at run time
the object is still an ordinary one (the label is erased), so `readonly`
guards your code, not your data.

<Formal title="What a mapped type stands for">

```text
keyof T = k₁ | k₂ | … | kₙ
{ [K in keyof T]: F(K) }
  = { k₁: F(k₁); k₂: F(k₂); …; kₙ: F(kₙ) }
```

<span slot="read">If the keys of T are k one to k n, then the mapped type
is the object type with exactly those keys, where the type of key k i is
F with k i written in place of K. For Columns, F(K) is T[K][].</span>
</Formal>

<OtherLanguages>

```ts
function get<T, K extends keyof T>(
  o: T, k: K): T[K] {
  return o[k];
}
```

```python
print(getattr(p, "vX"))
# a wrong name fails at run time:
# AttributeError: 'Particle' object
# has no attribute 'vX'
```

```java
Field f = Particle.class.getField("x");
double x = f.getDouble(p);
// a wrong name throws at run time:
// NoSuchFieldException
```

```c
/* no field names at run time: only
   byte offsets, fixed when compiling */
size_t off = offsetof(Particle, vx);
```

</OtherLanguages>

Reading a property whose name is held in a variable is ordinary in
JavaScript and Python, but only TypeScript checks the name *before* the
program runs; Python's `getattr` and Java's reflection (asking a class
about its own fields while running) find a wrong name only when that line
runs. C keeps no field names after compiling at all, only each field's
position in bytes (chapter 34).

<Callout kind="engine" label="Under the hood">
`Columns<T>` is the shape of the layout Viscosity generates when it
splits records into columns (its real columns are `Float64Array`s, but
the rule is the same: one array per key). Computed from the record type,
the two can never drift apart.
</Callout>

## What you learned

- **`keyof T`** is the union of `T`'s keys; as a constraint,
  `K extends keyof T` accepts only real property names.
- An **indexed access type**, `T[K]`, is the type behind a key; a union
  of keys gives a union of types, and `T[number]` is an array's element
  type.
- A **mapped type**, `{ [K in keyof T]: ... }`, builds a type key by key,
  and can add or remove `?` and `readonly`. All of it is erased before
  the program runs.
