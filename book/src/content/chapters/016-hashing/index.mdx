## A million names

Here is how you would find a name in an array, with the tools you have:

```js
function find(names, x) {
  for (let i = 0; i < names.length; i++) {
    if (names[i] === x) return i;
  }
  return -1;
}
```

The loop compares the name it wants with slot 0, then slot 1, then slot
2, and returns the index as soon as one matches (or `-1`, a common way of
saying "not found", once every slot has failed). That is fine for ten
names, however for a million it can mean a million comparisons, and a
compiler asks questions like "what is this name?" millions of times. A
Map, from the last chapter, answers `has('pink')` almost directly,
however many entries it holds; this chapter is about how.

<Analogy title="pigeonholes in a post room">
A post room has a wall of pigeonholes and a rule that turns each address
into a pigeonhole number. To find a letter you do not read every letter
in the building: you work out its pigeonhole, and look only there.
<span slot="breaks">A post room's rule is often "by street", which can
crowd one hole while others sit empty; a good hash function scrambles the
key so entries spread evenly, and when two keys still land together, they
simply share the hole.</span>
</Analogy>

<Analogy title="a library shelved by surname">
Novels in a library are shelved by the author's surname, so for Orwell
you walk straight to the O shelf and search only there, never the A to N
shelves.
<span slot="breaks">Surnames are spread unevenly (many on S, few on X),
so some shelves are crowded; a hash function is chosen precisely so that
every "shelf" gets about the same number of keys, and the "shelf" it
picks is a number worked out from the whole key, not its first
letter.</span>
</Analogy>

## Buckets and a hash function

A **hash table** is an array of **buckets** (small lists), plus a
**hash function** that turns any key into a bucket number. To store an
entry, work out its key's bucket and put it there; to find a key later,
work out the same bucket and look only inside it. Step through a toy
table with four buckets, whose hash function is deliberately silly (it
counts the key's letters) so you can follow it in your head:

<HashSteps client:visible />

<Callout kind="definition">
**Hashing**, the intuition: a **hash function** turns a key into a
number, and that number picks a **bucket**. Storing and finding a key
both look only inside its bucket. Two different keys landing in the same
bucket is a **collision**; they share it, and a lookup checks each entry
there. When keys spread evenly across enough buckets, each holds only a
few entries, so a lookup stays quick however big the table grows. A table
built like this is a **hash table**.
</Callout>

<Prompts ids={['hash-function-what', 'hash-why-fast', 'hash-collision']} />

<Examples of="hash-intuition">

```js
function hash(key) {
  return key.length % 4;
}
hash('red');  // 3
hash('blue'); // 0
hash('pink'); // 0: a collision
```

```js
function hashNum(n) { return n % 8; }
hashNum(13); // 5
hashNum(21); // 5 as well
hashNum(16); // 0
```

```js
const buckets = [[], [], [], []];
buckets[hash('red')].push('red');
buckets[hash('pink')].push('pink');
// buckets: [['pink'], [], [], ['red']]
buckets[hash('red')].includes('red');
// true, after checking bucket 3 only
```

<Run id="toy-table" />

</Examples>

The first is the toy hash from the diagram: the number of letters, then
`% 4` (the remainder after dividing by 4) so the answer is always 0, 1, 2
or 3, one for each bucket; `'blue'` and `'pink'` both have four letters,
so they collide. The second hashes whole numbers the same way, by their
remainder: 13 and 21 both leave 5 when divided by 8, so they share bucket
5, while 16 leaves 0. The third is the whole idea in four lines: the
buckets are an array of arrays, an entry is pushed into the bucket its
key hashes to, and a lookup works out the same bucket and searches only
that one (`includes` asks an array whether it holds a value). The runnable
version builds the same table; add keys of your own and predict their
buckets.

The one rule a hash function must never break is that the same key
always gives the same number. Spot the difference:

```js
// broken: a random bucket every time
function bad(key) {
  return Math.floor(Math.random() * 4);
}
// fine: depends only on the key
function good(key) {
  return key.length % 4;
}
```

(`Math.random()` gives a random fraction below 1, and `Math.floor` rounds
down, so `bad` picks a bucket from 0 to 3 at random.) There is no error
message here, which is what makes it nasty: `bad` stores `'red'` in one
bucket and later looks for it in another, so a key you added is
"missing". `good` is a poor spreader, but at least it is consistent.

<Formal title="Where an entry lives, and how full a bucket is">

```text
bucket(k) = hash(k) mod B
entries per bucket ≈ n / B
```

<span slot="read">In a table with B buckets, the entry for key k lives in
bucket number hash of k, mod B, which means the remainder after dividing
by B. If n entries are spread evenly, each bucket holds about n divided
by B of them (≈ reads "is about"), so a table that adds buckets as it
grows keeps that number small, and lookups quick.</span>
</Formal>

<OtherLanguages>

```js
function hash(key) {
  return key.length % 4;
}
console.log(hash('pink')); // 0
```

```python
def h(key):
    return len(key) % 4

print(h('pink'))     # 0
print(hash('pink'))  # Python's own
```

```java
static int hash(String key) {
    return key.length() % 4;
}
// every object has its own:
int code = "pink".hashCode();
```

```c
#include <string.h>
int hash(const char *key) {
    return strlen(key) % 4;
}
```

</OtherLanguages>

The toy function looks the same in all four; the real difference is what
the language gives you. Python has a built-in `hash()` that its `dict`
and `set` use, and Java gives every object a `hashCode()` method that its
`HashMap` uses, so in both you can see (and, for your own classes, choose)
the hash. JavaScript keeps the hash that `Map` uses hidden from you. C
gives you neither the hash nor the table, so you write both, as chapter
100 does.

<Callout kind="engine" label="Under the hood">
The JavaScript standard does not say how `Map` and `Set` must be built;
it only requires that, on average, a lookup's cost grows more slowly than
the number of entries<Cite id="mdn-map" />. V8 builds `Map`, `Set`,
`WeakMap` and `WeakSet` on hash tables. For an object key, V8's hash code
is a random number, unrelated to what the object contains, so it cannot be
worked out again and has to be stored with the object<Cite id="gunasekaran2018" />,
which fits Map's rule that objects are compared by identity. V8 also
switches an ordinary object's property storage to a hash table (a
"dictionary") once it holds a great many properties<Cite id="gunasekaran2018" />,
which you will meet in chapter 112; and you will build a real hash table,
with a proper hash function, in chapter 100.
</Callout>

## What you learned

- Finding a value in an array can mean checking every slot.
- A **hash table** is an array of **buckets**; a **hash function** turns
  a key into a bucket number, and storing or finding the key looks only
  in that bucket.
- Two keys in one bucket is a **collision**; they share it.
- A hash function must give the same number for the same key every time,
  and should spread keys evenly, so buckets stay short.
