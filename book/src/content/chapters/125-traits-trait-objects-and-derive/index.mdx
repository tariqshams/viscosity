## The plug, again

In *The architecture of Viscosity and its plugin API* you met the
plugin interface in TypeScript: anything with an `id`, a list of
`extensions` and a `lower` method *is* a `LanguagePlugin`, and nobody
has to say so, because TypeScript compares shapes. Rust needs the same
idea, a set of methods that many types can provide, and calls it a
**trait**; it differs in one way you will feel at once.

<Analogy title="a membership card">
A TypeScript interface is a dress code: anyone wearing a jacket gets in.
A Rust trait is a membership card: the doorman does not care what you
are wearing; he checks for the card, and you only get one by signing up,
by writing `impl Trait for YourType`.
<span slot="breaks">A card can be lent to a friend or forged; an `impl`
belongs to exactly one type, and the compiler checks every card before
the program runs, so there is no doorman to fool.</span>
</Analogy>

## Declaring and implementing

<Examples of="trait">

```rust
trait Plugin {
    fn id(&self) -> &str;
    fn exts(&self) -> &[&str];
    fn handles(&self, f: &str) -> bool {
        for e in self.exts() {
            if f.ends_with(e) {
                return true;
            }
        }
        false
    }
}
struct Py;
impl Plugin for Py {
    fn id(&self) -> &str { "python" }
    fn exts(&self) -> &[&str] { &[".py"] }
}
```

</Examples>

A cut-down version of the trait in `engine/rust`. `id` and `exts` end with `;`:
they are **required**, and each type writes its own. `handles` has a
body, so it is a **default method**, which every implementing type gets
for free and may override. `Py`, a unit struct with no fields, writes the two required methods, so
`Py.id()` is `"python"` and `Py.handles("b.py")` is `true`. Leave out `exts` and rustc says
E0046, "not all trait items implemented, missing: `exts`". Step
through one default body running for two types:

<DefaultSteps client:visible />

<Callout kind="definition">
A **trait** names a set of methods that types can provide. A type
implements it with an **`impl Trait for Type`** block, which must define
every **required** method and may override the **default**
ones<Cite id="rust-book-traits" />. Only such a block makes a type
implement the trait: traits are **nominal** (matched by name), where
TypeScript's interfaces are structural (matched by shape).
</Callout>

Give a type `Rb` methods called `id` and `exts` in a plain `impl Rb`
block, ask for a `Plugin`, and rustc 1.97 refuses with E0277, "the
trait bound `Rb: Plugin` is not satisfied", listing `Py` and `Js` as
the types that do implement it:

<Figure takeaway="Only an impl block makes a type a Plugin." caption="Js and Py wrote id and exts in impl Plugin blocks and inherit handles. Rb has methods with the same names in a plain impl block, so as far as Rust is concerned it has nothing to do with Plugin.">
  <TraitGrid />
</Figure>

Two traits may both have an `id` with different meanings, so the impl
block is where a type says which promise it keeps. The **orphan rule**
goes with it: you may write `impl Trait for Type` only if your own
crate defined the trait or the type, so you can make your types
`Display` but you cannot make `Vec` `Display`<Cite id="rust-book-traits" />.

## One list, many types

Viscosity's command line wants a list of plugins, and asks each "do you
handle `b.py`?". In Rust a `Js` and a `Py` are different types, and a
`Vec` holds one element type, so `vec![&Js, &Py]` is refused (E0308,
"expected `&Js`, found `&Py`"). We want "a reference to *some* type
that implements `Plugin`", and that type is written `&dyn Plugin`:

<Examples of="trait-object">

```rust
let ps: Vec<Box<dyn Plugin>> =
    vec![Box::new(Js), Box::new(Py)];
for p in &ps {
    if p.handles("b.py") {
        println!("{}", p.id()); // python
    }
}
```

</Examples>

`Box::new(Js)` moves the value onto the heap and `Box<dyn Plugin>` owns
it (*Box, Rc and RefCell* is about `Box`); `&dyn Plugin` would borrow
instead. The loop is compiled once, yet `p.id()` reaches `Js`'s `id`
and then `Py`'s, because the pointer carries a second pointer:

<VtableSteps client:visible />

<Figure takeaway="A trait-object reference is two pointers: the value and its type's vtable." caption="On this machine (rustc 1.97) &Js is 8 bytes, and &dyn Plugin and Box<dyn Plugin> are 16. The vtable is built once per type by the compiler, which also keeps the value's size, alignment and drop function there.">
  <FatPointer />
</Figure>

<Callout kind="definition">
A **trait object** is a value of type `dyn Trait`, always used behind a
pointer such as `&dyn Trait` or `Box<dyn Trait>`. The pointer is two
words: one to the value, and one to a **vtable**, a table holding, for
each method of the trait, a pointer to that type's
implementation<Cite id="rust-reference-trait-object" />. A call loads
the function pointer from the table and calls it (dynamic dispatch).
</Callout>

Unlike a JavaScript method call, which V8 looks up by name and speeds
up with an inline cache, a `dyn` call reads a fixed slot that the
compiler numbered ahead of time; however, it cannot know *which* table
it will get, so the call is indirect and cannot be
inlined<Cite id="rust-book-trait-objects" />. drip-rs's collector takes
`roots: &[&dyn Trace]` for exactly this reason: the VM's stack and the
compiler's half-built functions are different types, marked by one
function. (The deep dive *Trait objects and dispatch* measures the
cost.)

## Operators are trait calls

TypeScript gives you no way to say what `+` means for your own objects,
so a TypeScript game writes `add(pos, scale(vel, dt))`. Rust lets you
write `pos + vel * dt`, because to rustc an operator is a short way of
writing a call to a trait method:

<DesugarSteps client:visible />

<Examples of="operator-traits">

```rust
use std::ops::Add;
impl Add for V2 {
    type Output = V2;
    fn add(self, o: V2) -> V2 {
        V2 { x: self.x + o.x,
             y: self.y + o.y }
    }
}
```

</Examples>

`V2` is a struct of two `f64`s, `x` and `y`. `type Output = V2;` names
the type the sum produces (a type the impl chooses, which *Closures,
iterators and associated types* returns to), and `add` takes both sides
*by value* and builds a new `V2`. From then on `a + b` is
`Add::add(a, b)`<Cite id="rust-std-ops-add" />. Without the impl, rustc
says E0369, "cannot add `V2` to `V2`", and notes that an implementation
of `Add` might be missing.

<Callout kind="definition">
The **operator traits** are the traits rustc calls for operators: `Add`,
`Sub`, `Mul`, `Div`, `Neg` and the rest of `std::ops` (with `AddAssign`
and friends for `+=`, and `Index` for `a[i]`), and `PartialEq` and
`PartialOrd` for `==` and `<`. You cannot invent new operators, or
change `+` for `i32`.
</Callout>

The deep dive *Operator traits, Drop and derive* covers the rest, from
`v * 2.0` and `+=` to drip-rs's `heap[handle]`.

## derive: the routine impls, written for you

Since `add` takes its operands by value, `a + b` would *move* `a` and
`b` away, so a small number-like type should be `Copy` (and printable,
and comparable). Those impls all say the obvious thing, field by field,
so the compiler writes them when asked:

<Examples of="derive">

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
struct V2 { x: f64, y: f64 }
let a = V2 { x: 1.0, y: 2.0 };
let b = a;  // a copy: a still usable
println!("{:?} {}", a, a == b);
// V2 { x: 1.0, y: 2.0 } true
```

</Examples>

`Debug` gives `{:?}`; `Clone` gives `.clone()`; `Copy` makes
assignment copy the value instead of moving it, so `a` is still usable
after `let b = a;`; and `PartialEq` gives `==`, true when every field
is equal (where TypeScript's `===` on two objects can only ask "the
very same object?").

<Figure takeaway="derive writes the impl you would have written: one line per field." caption="What #[derive(Clone, PartialEq, Debug)] produces for V2, written out by hand (simplified). Each method uses the same trait on every field, in order.">
  <DeriveExpand />
</Figure>

<Callout kind="definition">
**`#[derive(...)]`** on a struct or enum asks the compiler to write
impls of the named traits, using each field's own impl. It works for
`Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`,
`Hash` and `Default`, and every field must implement the
trait<Cite id="rust-book-derivable-traits" />. `Display` cannot be
derived, because only you know how a value should look to a
user<Cite id="rust-std-fmt" />.
</Callout>

The classic refusal is `Copy` on a type that owns heap memory:
`#[derive(Clone, Copy)]` on `struct Tok { text: String, line: u32 }` is
E0204, pointing at `text`: "this field does not implement `Copy`".

## What you learned

- A **trait** is a named set of methods. Types sign up with
  `impl Trait for Type`, writing the required methods and inheriting
  the default ones; matching method names are not enough (E0277), and
  you must own the trait or the type.
- A **trait object**, `&dyn Trait` or `Box<dyn Trait>`, lets one `Vec`
  hold values of different types; its pointer is data plus a vtable,
  and each call reads a fixed slot and calls indirectly.
- **Operators** are trait calls: `a + b` is `Add::add(a, b)`.
- **`#[derive]`** writes `Debug`, `Clone`, `Copy`, `PartialEq` and
  friends field by field, when every field has the trait.

Next: *Generics and monomorphization*, the other way to call a trait
method, where Rust makes a copy of the function per type instead of
passing a table.
