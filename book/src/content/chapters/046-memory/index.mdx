## Where does a value actually go?

Part I gave you two pictures of data that never quite met. In the
chapter on references, a variable held an *arrow* to an object; in
*Floats and typed arrays*, a `Float64Array` was a block of raw *bytes*,
8 to a number. Part II is about the machine underneath both pictures,
and it starts with one question: when the engine stores a value, where
does it put it?

Here is a puzzle to keep in mind while we answer it:

```js
const xs = new Float64Array(1000000);
xs[999999] = 1;
console.log(xs[999999]); // 1
```

The array has a million slots, and yet writing the very last one takes
no longer than writing the first; nothing is searched, and nothing is
counted along the way. By the end of this chapter you will be able to
do the sum the machine does to find that slot, by hand.

## One long row of bytes

<Analogy title="a street of numbered mailboxes">
Picture a street so long it never seems to end, lined with tiny
mailboxes. Every mailbox holds exactly one small thing, and every
mailbox has a number painted on it: 0, 1, 2, 3, and on into the
billions. To fetch something you do not need its name; you need its
mailbox number.
<span slot="breaks">On a real street, mailbox 9,000 is a long walk
from mailbox 1; in memory, any number can be reached directly, without
passing the ones in between (the next chapter adds an important "but"
to that). Also, a mailbox can hold a parcel of any size, while each of
these holds exactly one byte, a whole number from 0 to 255.</span>
</Analogy>

<Analogy title="page numbers in a very thick book">
A book with a billion pages would be useless if its pages were not
numbered; with numbers, "page 37" tells you exactly where to open it,
and a reference to a page is just a number you can write down.
<span slot="breaks">A page holds many words; a byte holds one small
number, so anything bigger (a float64, say) needs several bytes in a
row. And a book's pages are printed once, while every byte of memory
can be rewritten as often as you like.</span>
</Analogy>

That street, or book, is your computer's **memory** (also called
**RAM**). Step through it. The row is far too long to draw in one line,
so it wraps like text: each line of boxes carries on where the last one
stopped.

<MemoryRow client:visible />

<Callout kind="definition">
**Memory** (RAM) is one enormous array of bytes, each holding a whole
number from 0 to 255. A byte's index in that array is its **address**:
a plain whole number that says where the byte is. Anything bigger than
a byte is stored in several neighbouring bytes, and is found by the
address of its first one.
</Callout>

JavaScript never shows you real addresses, but a `Uint8Array` (a typed
array of single bytes) behaves exactly like a small memory of your own,
which makes it a good model:

<Examples of="memory address">

```js
const mem = new Uint8Array(8);
mem[3] = 200;
mem[3]; // 200
```

```js
const mem = new Uint8Array(8);
mem[1] = 300;
mem[1]; // 44
```

```js
// a toy 8-bit computer's memory
const mem = new Uint8Array(65536);
mem[0x10] = 42;
mem.length; // 65536 = 2 ** 16
```

</Examples>

The first makes eight bytes, all zero, writes 200 at index 3 and reads
it back; here the index plays the part of an address. The second is a
reminder from *Bits and bytes* that a byte cannot hold more than 255:
300 does not fit in 8 bits, so only the low 8 bits are kept, which is
300 − 256 = 44. The third is the realistic one: an old 8-bit computer
used 16-bit addresses, and 16 bits can count 2¹⁶ = 65,536 different
places, so a program that imitates such a machine can keep its entire
memory in one `Uint8Array` of that length (`0x10` is hexadecimal for
16, the usual way to write addresses).

## Side by side, with no gaps

Back to the puzzle. A `Float64Array` stores its numbers one after
another, each taking 8 bytes, with nothing in between:

```js
const xs = new Float64Array(3);
xs.BYTES_PER_ELEMENT; // 8
xs.byteLength;        // 24
```

Line 1 makes three float64s. Line 2 asks how many bytes each element
takes, which is 8; line 3 asks how many bytes the whole array takes,
which is 3 × 8 = 24, so there is no room left over for anything but the
numbers.

<Analogy title="encyclopedia volumes on a shelf">
A set of encyclopedias stands on one shelf, every volume the same
thickness, in order, with no gaps. If volume 1 starts at the left end
and each is 4 cm wide, volume 7 starts 6 × 4 = 24 cm along; you can put
your hand on it without reading a single spine.
<span slot="breaks">Real volumes differ in thickness, and then the
trick fails; the elements of one typed array are all exactly the same
size, which is the only reason the sum works. (An array of objects, in
the next chapter, is a shelf of index cards pointing at books kept
elsewhere.)</span>
</Analogy>

<ElementAddress client:visible />

<Callout kind="definition">
Values are **contiguous** when they are stored side by side in memory,
with no gaps between them. A typed array's elements are
contiguous<Cite id="mdn-typed-arrays" />, so if a `Float64Array`
starts at address `b`, element `i` starts at `b + i × 8`: one multiply
and one add, whatever the length.
</Callout>

<Formal title="Where element i lives">

```text
s = bytes per element
addr(a[i]) = base(a) + i × s
contiguous ⟺ addr(a[i+1]) = addr(a[i]) + s
```

<span slot="read">The address of element i is the address where the
array starts plus i times the size of one element. The array is
contiguous exactly when (that is what ⟺ means) each element starts one
element-size after the one before it.</span>
</Formal>

<Examples of="contiguous">

```js
// Float64Array at 1000, element 3
1000 + 3 * 8; // 1024
```

```js
const ys = new Int32Array(10);
ys.BYTES_PER_ELEMENT; // 4
// at 100, ys[5] starts at 100 + 5 * 4 = 120
```

<Run id="columns-in-one-buffer" />

</Examples>

The first is the formula with numbers in: a `Float64Array` starting at
address 1000 has element 3 at 1000 + 24 = 1024. The second changes the
element size: an `Int32Array` uses 4 bytes per element, so the step is
4, and element 5 of one starting at 100 is at 120. The runnable one is
the shape Viscosity generates: two columns of particle data, `x` and
`vx`, laid out in one `ArrayBuffer`, the second starting right after the
first. A typed array's `byteOffset` says where it starts inside its
buffer, which is the nearest JavaScript lets you get to an address; run
it, and check every printed position against the formula.

Contiguous elements also have to start on a multiple of their size
inside the buffer, and the engine checks this for you:

```js
const buf = new ArrayBuffer(32);
new Float64Array(buf, 8); // fine
new Float64Array(buf, 4);
// RangeError: start offset of
// Float64Array should be a multiple of 8
```

The second argument is the byte where the view should start. Starting
at byte 8 lines every element up on a multiple of 8; starting at byte 4
would put each float64 across two of those 8-byte steps, and JavaScript
refuses.

## Seeing addresses in other languages

JavaScript, Python and Java give you no way to work with addresses; C
shows them to you, which makes it a good place to check that the
formula is real.

<OtherLanguages>

```js
const xs = new Float64Array(3);
// no way to print an address;
// only the step is visible:
console.log(xs.BYTES_PER_ELEMENT); // 8
```

```c
double xs[3];
printf("%p\n", (void *)&xs[0]);
printf("%p\n", (void *)&xs[1]);
/* e.g. 0x7ffd5c10 then 0x7ffd5c18 */
```

</OtherLanguages>

In C, `&xs[1]` means "the address of `xs[1]`", and `%p` prints an
address in hexadecimal. The exact numbers change every run, but the two
are always 8 apart (`0x18` − `0x10` is 8), because a C array of
`double` is contiguous, just like a `Float64Array`.

<Callout kind="engine" label="Under the hood">
When an optimised engine runs `xs[i]` on a `Float64Array`, it does what
you did above: it checks that `i` is inside the array, multiplies `i` by
8, adds the address where the bytes start, and loads 8 bytes from
there. Addresses on today's 64-bit machines are 64 bits long, so even
the numbers that say *where* things are take up bytes of their own (V8
even squeezes many of them into 4 bytes to save room<Cite id="v8-pointer-compression" />,
as the next chapter explains). Viscosity's whole job, in these terms, is
to take data scattered across memory and rewrite it into a few long,
contiguous typed arrays, where finding element `i` is one sum.
</Callout>

## What you learned

- **Memory** is one long array of bytes, each holding 0 to 255.
- A byte's index in that array is its **address**; a bigger value is
  found by the address of its first byte.
- **Contiguous** values sit side by side with no gaps, so element `i` of
  a typed array starting at `b` is at `b + i × size`, which is why
  reading the millionth element is as quick as reading the first.
