## Two right answers

One of the programs written for the port,
`tests/extra/unicode_offsets.js`, starts with comments and strings full
of accented letters, emoji, and the invisible line-break characters
U+2028 and U+2029, and only then declares `const ps = [];`. I parsed it
with both parsers here. acorn, the TypeScript engine's parser, says that
statement runs from offset 266 to 280; oxc, the Rust engine's, says 286
to 300. They are twenty apart and both correct, and the parity test
checks that both engines rewrite this file identically. This chapter is
about the parser that gives the second answer, and how the port walks
its tree.

## oxc

oxc, the Oxidation Compiler, is "a collection of high-performance tools
for JavaScript and TypeScript written in Rust": a parser, a linter, a
formatter, a transformer and a minifier<Cite id="oxc-project" />. The
port uses its parser and syntax-tree crates, version 0.156.

<Callout kind="definition">
**oxc** (the Oxidation Compiler) is a JavaScript and TypeScript
toolchain written in Rust. Its parser takes an `Allocator` (a memory
arena), the source and a `SourceType`, and returns a `ParserReturn`
holding the `Program` (with its comments) and a list of syntax errors.
The tree is a set of Rust types, allocated in the arena, with spans in
UTF-8 byte offsets<Cite id="oxc-parser-docs" />.
</Callout>

<Examples of="oxc">

```rust
let options = ParseOptions {
    preserve_parens: false,
    parse_regular_expression: true,
    ..ParseOptions::default()
};
let ret = Parser::new(&allocator, source,
        SourceType::mjs())
    .with_options(options)
    .parse();
if let Some(e) =
    ret.diagnostics.errors().next() {
    return Err(syntax_error(source, e));
}
```

</Examples>

This is the real call in `crates/frontend-js/src/lib.rs` (rewrapped).
`SourceType::mjs()` is acorn's `sourceType: 'module'`; `preserve_parens:
false` matches acorn's default of not keeping parentheses as nodes;
`parse_regular_expression` checks regular expression literals, as acorn
does; and `..ParseOptions::default()` fills in the rest. Errors arrive as data in the
return value, not as an exception, so parsing `const ps = [;` still
returns, and the plugin turns its first error into a `CompileError`
written as `message (line:column)`, the shape of acorn's messages: both
CLIs print `viscosity: Unexpected token (1:12)` for that program.

The parser's list of errors "is not comprehensive", however: more
expensive checks are left to oxc's semantic
analyser<Cite id="oxc-parser-docs" />, so the port once compiled `let a
= 1; let a = 2;`, which acorn rejects. Now `SemanticBuilder::new()
.with_check_syntax_error(true)` runs right after parsing, and
`early_errors.rs` checks that both CLIs reject 108 invalid programs.

## A tree in an arena

ESTree is plain objects with a `type` string. oxc's tree is Rust types:
a `Statement` enum, an `Expression` enum with dozens of variants, and a
struct per node kind, such as `BinaryExpression(Box<'a,
BinaryExpression<'a>>)`. That `Box` is not std's: it is a pointer into
the `Allocator`, a **bump arena** that hands out memory in order and
frees it all at once. `'a` is the lifetime of *Lifetimes*, and here it
names the arena: every node borrows the allocator, so no node can
outlive it. Step through what that means for the plugin:

<OxcSteps client:visible />

Objects in the arena "are never Dropped", and memory is "released in
bulk when the allocator is dropped"<Cite id="oxc-allocator-docs" />.
The TypeScript engine keeps ESTree nodes alive inside the VIR, in
`SourceRef.node`; the Rust tree dies when `lower` returns, so the VIR
keeps spans instead (an oxc `Span` is two `u32`s, with no lifetime) and
a side table of facts, at the end of this chapter.

<Analogy extra title="a notepad">
A bump arena is a notepad: each new node is written on the next free
line, nothing is ever rubbed out on its own, and when you are done you
throw the whole pad away.
<span slot="breaks">You could tear one page out of a real notepad; an
arena never gives back a single node, so a tree with one dead branch
still holds its memory until the whole arena goes.</span>
</Analogy>

## Bytes and code units

Now the two offsets. A JavaScript string is a sequence of UTF-16
**code units** (16-bit pieces; most characters take one, emoji take
two), and acorn's offsets count those. A Rust `String` is UTF-8 bytes,
and oxc's spans count bytes:

<Figure takeaway="Two units, two numbers, one character." caption="é is 2 bytes and 1 code unit; the emoji is 4 bytes and 2 code units; x is 1 of each. So x starts at byte 6 in Rust and at code unit 3 in JavaScript.">
  <TwoRulers />
</Figure>

Each engine splices its own string with its own offsets: the TypeScript
emitter writes `out.slice(0, e.start) + e.text + out.slice(e.end)`, and
the Rust one calls `out.replace_range(start..end, &e.text)`. `slice`
counts code units and `replace_range` counts bytes, so both cut at the
same characters, and the port never converts. The danger is mixing the
two: hand acorn's `266..280` to the Rust string and you get `"9, and a
line "`, from the comment above the statement; land inside a character
and Rust panics, because a string slice must start and end on a
character boundary<Cite id="rust-std-str" />. oxc reports no line
numbers, so the plugin counts them itself (`lines::LineIndex`) at the
breaks acorn counts: `\n`, `\r\n`, a lone `\r`, U+2028 and U+2029.

## Walking every child

`lower.ts` turned anything it did not model into an `opaque` instruction
taking every variable the subtree mentions, and it found them with a
small `children(n)` that loops over `Object.keys(n)`, keeps the values
that are nodes, and sorts them by where they start. A Rust struct has no
`Object.keys`, and a `match` over hundreds of node kinds in every place
that needs "all the children" would be a lot of code. oxc solves this
once for everyone.

<Analogy title="a tour guide with a short list">
A tour guide walks every room of a building in the same order. You
hand the guide a short list ("count the kitchen chairs; skip the
cellar"), and every other room gets the standard walk-through.
<span slot="breaks">A guide who skips the cellar can still glance down
the stairs; a visitor that overrides a node and does not walk it sees
nothing at all below that node.</span>
</Analogy>

Here is the idea in a toy, shaped like oxc's `Visit` trait from the
`oxc_ast_visit` crate:

```rust
trait Visit: Sized {
    fn visit_expr(&mut self, e: &Expr) {
        walk_expr(self, e);
    }
    fn visit_name(&mut self, _: &str) {}
    fn visit_func(&mut self, b: &Expr) {
        self.visit_expr(b);
    }
}
```

Every method has a default body, and `walk_expr` is the standard
walk-through: a `match` on the node that calls `visit_*` on each child,
left to right. (`: Sized` lets the defaults pass `self` to a generic
function like `walk_expr`.) The real trait has 263 generated visit
methods in oxc 0.156<Cite id="oxc-ast-visit" />, and its walk goes in
source order, as `children()` did, which matters because the order in
which variables are found decides an opaque instruction's arguments.

<Callout kind="definition">
The **visitor pattern** separates *walking* a tree from *what you do* at
each node. A trait has one method per node kind; each default method
calls a **walk** function that visits the node's children; a visitor
**overrides** only the kinds it cares about. An override replaces the
default, so it must call the walk itself if it still wants the children.
</Callout>

<Examples of="visitor-pattern">

```rust
impl Visit for Outer {
    fn visit_name(&mut self, n: &str) {
        self.0.push(n.into());
    }
    fn visit_func(&mut self, _: &Expr) {}
}
```

</Examples>

`Outer` holds a `Vec<String>` and overrides two methods: `visit_name`
pushes every name it is shown, and `visit_func`, with an empty body,
*replaces* the default walk of function bodies. So on `a + (() => b + 1)` it collects only `a`, where a
visitor that overrode `visit_name` alone would collect `a` and `b`; and
that is exactly how `HoistCollector` in `resolve.rs` stops at nested
functions on purpose. Step through both walks:

## Names without a tree

As in TypeScript, `resolve.rs` pairs every identifier with its binding
(it implements `Visit`), and then `lower.rs` builds VIR. `resolve.ts`
keys its maps by node objects, compared by identity; the port keys them
by plain values, such as `FnKey::Func(Span)` for a function ("spans of
function nodes are unique") and a `HashMap<Span, JsBindingId>` for
references, so no table needs the tree's lifetime.

The emitter used to ask ESTree nodes questions, such as (through a
parent map) "is this `a[i]` the object of a member expression?". In the
port, `SourceRef.node` is a `NodeRef`, an index into a side table of
`JsNode` facts recorded during lowering:

<Figure takeaway="The emitter's questions are answered ahead of time, in a table." caption="Lowering ps[i].x += ps[i].vx: instruction %19, the first ps[i], points at entry 4 of the side table, which records the byte spans of ps and i and that ps[i] is the object of a member expression (direct).">
  <SideTable />
</Figure>

`direct` answers the parent question: lowering sets a flag just before
it lowers a member expression's object.

<More title="More: one Lowerer instead of closures">

In TypeScript, `lowerFunction` holds its helpers (`read`, `write`,
`expr` and the rest) as closures sharing the function builder `fb`.
Rust closures cannot share mutable state that freely, so the port has
one `Lowerer` struct with the per-function state in one field, `f`. A
nested function builds an `FnState` of its own, swaps it in with `let
outer = std::mem::replace(&mut self.f, state);`, lowers its body, and
puts the outer state back with `self.f = outer;`. `lower.rs` also names,
in comments, the ESTree case each oxc case mirrors, and lowers a `"use
strict"` directive to a string constant nothing uses, as the reference
does, so that every later value keeps its `%n`.

</More>

## What you learned

- **oxc** is a Rust toolchain for JavaScript. Its parser takes an
  arena, the source and a `SourceType`, returns errors as data, and
  leaves some early errors to a semantic pass, which the port also runs.
- Its tree lives in a bump **arena** tied to `'a`, so the port keeps
  spans and a side table of facts, not the tree.
- oxc spans count **UTF-8 bytes**, acorn's offsets **UTF-16 code
  units**; each engine slices its own string with its own offsets.
- The **visitor pattern**: one method per node kind, defaults that walk
  the children in source order, and overrides that replace the walk.
