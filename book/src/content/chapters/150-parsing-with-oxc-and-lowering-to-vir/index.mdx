## Two right answers

One of the programs written for the port,
`tests/extra/unicode_offsets.js`, starts like this (trimmed; in `sep`
each `…` stands for U+2028 or U+2029, invisible line-break characters):

```js
// Ünïcödé before the collection: …
/* U+2028 and U+2029 are line breaks … */
const label = 'héllo wörld 😀 𝒳';
const sep = 'a…b…c'; // …
const ps = [];
```

I parsed it with both parsers here. acorn, the TypeScript engine's
parser, says the statement `const ps = [];` runs from offset 266 to 280;
oxc, the Rust engine's, says 286 to 300. They are twenty apart and both
correct, and the parity test checks that both engines rewrite this file
identically. This chapter is about how both can be true, and about the
parser that gives the second answer.

## oxc

oxc, the Oxidation Compiler, is "a collection of high-performance tools
for JavaScript and TypeScript written in Rust": a parser, a linter, a
formatter, a transformer and a minifier<Cite id="oxc-project" />. The
port uses its parser and syntax-tree crates, version 0.156. The parser
has "three inputs (a memory arena, a source string, and a SourceType)
and one return struct"<Cite id="oxc-parser-docs" />.

<Callout kind="definition">
**oxc** (the Oxidation Compiler) is a JavaScript and TypeScript
toolchain written in Rust. Its parser takes an `Allocator`, the source
and a `SourceType`, and returns a `ParserReturn` holding the `Program`
(with its comments) and a list of syntax errors. The tree is a set of
Rust types, allocated in the arena, with spans in UTF-8 byte
offsets<Cite id="oxc-parser-docs" />.
</Callout>

<Examples of="oxc">

```rust
let a = Allocator::default();
let ret = Parser::new(&a, "let x = 1;",
    SourceType::mjs()).parse();
// ret.program.body.len() == 1
```

```rust
let ret = Parser::new(&a,
    "const ps = [;",
    SourceType::mjs()).parse();
let e = ret.diagnostics.errors().next();
// its message: "Unexpected token"
```

```rust
let options = ParseOptions {
    preserve_parens: false,
    parse_regular_expression: true,
    ..ParseOptions::default()
};
let ret = Parser::new(&allocator, source,
        SourceType::mjs())
    .with_options(options)
    .parse();
if let Some(e) =
    ret.diagnostics.errors().next() {
    return Err(syntax_error(source, e));
}
```

</Examples>

The first is the smallest parse: make an arena, hand it the text and
`SourceType::mjs()` (a JavaScript module, acorn's `sourceType:
'module'`), and the tree comes back with one statement in its body. The
second shows how errors arrive: as data in the return value, not as an
exception, so parsing `const ps = [;` still returns, and its first error
says `Unexpected token`. The third is the real call in
`crates/frontend-js/src/lib.rs` (rewrapped); I ran all three here with
oxc 0.156. Line it up with the acorn adapter of *Parsing real
JavaScript*: `preserve_parens: false` matches acorn's default of not
keeping parentheses as nodes, `parse_regular_expression` checks regular
expression literals as acorn does, and the plugin turns the first error
into a `CompileError` written as `message (line:column)`, the shape of
acorn's messages, so both CLIs print `Unexpected token (1:12)` for that
second program.

## A tree in an arena

ESTree is plain objects with a `type` string. oxc's tree is Rust types:
a `Statement` enum, an `Expression` enum with dozens of variants, and a
struct per node kind. One variant, from `oxc_ast`:

```rust
pub enum Expression<'a> {
    // ...
    BinaryExpression(
        Box<'a, BinaryExpression<'a>>),
    // ...
}
```

That `Box` is not std's: it is oxc's **arena** box, a pointer to a node
in the `Allocator`, and here an `Expression` is 16 bytes, a tag and that
pointer. (The kinds are split finer than ESTree's too: `ps[i].x` is a
`StaticMemberExpression` whose object is a `ComputedMemberExpression`,
where ESTree has one `MemberExpression` with a `computed` flag.)

<Analogy title="a notepad">
A bump arena is a notepad: each new node is written on the next free
line, nothing is ever rubbed out on its own, and when you are done you
throw the whole pad away.
<span slot="breaks">You could tear one page out of a real notepad; an
arena never gives back a single node, so a tree with one dead branch
still holds its memory until the whole arena goes.</span>
</Analogy>

`'a` is the **lifetime** of *Lifetimes*, and here it names the arena:
every node borrows the allocator, so no node can outlive it. Step
through what that means for the plugin:

<OxcSteps client:visible />

oxc's documentation spells out the deal: objects in the arena "are
never Dropped", and memory is "released in bulk when the allocator is
dropped". To keep that from leaking, the arena refuses, at compile time,
any type that implements `Drop`, such as std's `Vec`, which is why oxc
ships arena versions of `Box`, `Vec`, `String` and
`HashMap`<Cite id="oxc-allocator-docs" />. For the port this settles a
design question. The TypeScript engine keeps ESTree nodes alive inside
the VIR, in `SourceRef.node`; the Rust tree dies when `lower` returns,
so the VIR keeps a `NodeRef` index into a side table of facts instead
(*Lowering oxc's AST to VIR*). Spans survive, because an oxc `Span` is
two `u32`s with no lifetime.

## Bytes and code units

Now the two offsets. A JavaScript string is a sequence of UTF-16
**code units** (16-bit pieces; most characters take one, emoji take
two), and acorn's offsets count those. A Rust `String` is UTF-8 bytes,
and oxc's spans count bytes:

<Figure takeaway="Two units, two numbers, one character." caption="é is 2 bytes and 1 code unit; the emoji is 4 bytes and 2 code units; x is 1 of each. So x starts at byte 6 in Rust and at code unit 3 in JavaScript.">
  <TwoRulers />
</Figure>

<Analogy extra title="a road measured in metres and in paces">
A lamp-post can be "120 metres" or "160 paces" from the corner; the
numbers differ, and both send you to the same post, as long as you
pace with the unit you were told.
<span slot="breaks">Paces vary from person to person; bytes and code
units are exact, so a mixed-up offset never lands "about" right, it
lands somewhere else entirely.</span>
</Analogy>

Before `const ps`, the test file has accented letters (one unit, two
bytes each), 😀 and 𝒳 (two units, four bytes each), and U+2028 and
U+2029 (one unit, three bytes each), which is where the twenty comes
from. Each engine splices its own string with its own offsets: the
TypeScript emitter writes `out.slice(0, e.start) + e.text +
out.slice(e.end)`, and the Rust one calls `out.replace_range(start..end,
&e.text)`. `slice` counts code units and `replace_range` counts bytes,
so both cut at the same characters, and the fixture shows identical
output from both engines.

The danger is mixing the two. Hand acorn's `266..280` to the Rust string
and you get `"9, and a line "`, from the comment on the line above; land inside
a character and Rust panics, because a string slice must start and end
on a character boundary<Cite id="rust-std-str" />. When the port does
need a JavaScript-style offset, `lines::utf16_offset` converts.

<Run id="three-lengths" />

Line numbers need care too, because oxc reports none. The plugin counts
them itself, with a `LineIndex` (in `lines.rs`) that records where each line starts, at the same breaks acorn counts: `\n`,
`\r\n`, a lone `\r`, U+2028 and U+2029.

<Prompts ids={['oxc-units', 'oxc-same-cut', 'oxc-lines']} />

<Callout kind="pitfall">
oxc's parser does not report every syntax error: its documentation says
the list "is not comprehensive", and more expensive checks are left to
its semantic analyser<Cite id="oxc-parser-docs" />. When this chapter
was first written the port ran only the parser, so `let a = 1; let a =
2;` compiled in Rust while acorn rejected it, and no parity fixture
caught it, because every parity program is valid JavaScript. The fix is
a second pass right after parsing, `SemanticBuilder::new()
.with_check_syntax_error(true).build(&program)`, whose first error is
reported the same way; and `early_errors.rs` now runs 108 invalid
programs through both CLIs, which must both reject them. Each still
words an error its own way, and not always at the same token: for that
program Rust says ``Identifier `a` has already been declared (1:4)``
and acorn `Identifier 'a' has already been declared (1:15)`.
</Callout>

## What you learned

- **oxc** is a Rust toolchain for JavaScript. Its parser takes an
  arena, the source and a `SourceType`, and returns the tree with its
  errors as data.
- The tree lives in a bump **arena**: `'a` ties every node to the
  `Allocator`, nodes are never dropped one by one, and the whole arena is
  freed at once. So the port keeps spans and facts, not the tree.
- oxc spans count **UTF-8 bytes**, acorn's offsets **UTF-16 code
  units**. Each engine slices its own string with its own offsets, so
  both cut at the same characters.
- Line numbers are counted by the plugin at every ECMAScript line
  break.
- oxc's parser leaves some early errors to a semantic pass, so the
  port runs that pass's syntax checks too.

## All the children

In *Lowering JavaScript to VIR*, `lower.ts` turned anything it did not
model into an `opaque` instruction taking every variable the subtree
mentions. It found them with one small function from `estree.ts`
(simplified):

```ts
function children(n: Node): Node[] {
  const out: Node[] = [];
  for (const key of Object.keys(n)) {
    const v = n[key];
    if (v && typeof v.type === 'string')
      out.push(v);
    // (and arrays of nodes)
  }
  return out.sort(byStart);
}
```

An ESTree node is an ordinary object, so you can ask it for its keys,
keep the values that are nodes, and sort them by where they start. oxc's
tree (*Parsing with oxc*), however, is a set of Rust types, and a struct
has no `Object.keys`; yet the port walks "all the children" in several
places, and a `match` over hundreds of node kinds in each would be a lot
of code. oxc solves this once for everyone.

<Analogy title="a tour guide with a short list">
A tour guide walks every room of a building in the same order. You
hand the guide a short list ("count the kitchen chairs; skip the
cellar"), and every other room gets the standard walk-through.
<span slot="breaks">A guide who skips the cellar can still glance down
the stairs; a visitor that overrides a node and does not walk it sees
nothing at all below that node.</span>
</Analogy>

<Analogy extra title="a shop's checkout scanner">
A checkout scans every item the same way, and the shop adds special
rules for a few products: weigh the apples, ask for proof of age for
the wine.
<span slot="breaks">If the rule for a multipack forgot to scan the
items inside it, they would go through unscanned; an override replaces
the default walk, so it must walk the children itself if it still wants
them.</span>
</Analogy>

## One method per node kind

Here is the idea in a toy, shaped like oxc's `Visit` trait from the
`oxc_ast_visit` crate:

```rust
trait Visit: Sized {
    fn visit_expr(&mut self, e: &Expr) {
        walk_expr(self, e);
    }
    fn visit_name(&mut self, _: &str) {}
    fn visit_func(&mut self, b: &Expr) {
        self.visit_expr(b);
    }
}
```

Every method has a default body, and `walk_expr` is the standard
walk-through: a `match` on the node that calls `visit_*` on each child,
left to right. (`: Sized` lets the defaults pass `self` to a generic
function like `walk_expr`.) The real trait has 263 visit methods in oxc 0.156, all generated, and each
default calls the matching `walk_*` function, which visits that node's
children<Cite id="oxc-ast-visit" />. That walk goes in source order,
as `children()` did with its sort, which matters because the order in
which variables are found decides an opaque instruction's arguments.

<Callout kind="definition">
The **visitor pattern** separates *walking* a tree from *what you do* at
each node. A trait has one method per node kind; each default method
calls a **walk** function that visits the node's children; a visitor
**overrides** only the kinds it cares about. An override replaces the
default, so it must call the walk itself if it still wants the children.
</Callout>

<Formal title="The default walk">

```text
visit_K(v, n) = walk_K(v, n)
walk_K(v, n)  = visit c₁; …; visit cₖ
```

<span slot="read">For every node kind K, visiting a node n of that kind,
unless you override it, means walking it; and walking it means visiting
each of its children c₁ to cₖ in turn, first to last as they appear
in the source. An override changes the first line for one kind and leaves the
second alone.</span>
</Formal>

<Examples of="visitor-pattern">

```rust
impl Visit for Names {
    fn visit_name(&mut self, n: &str) {
        self.0.push(n.into());
    }
}
```

```rust
impl Visit for Outer {
    fn visit_name(&mut self, n: &str) {
        self.0.push(n.into());
    }
    fn visit_func(&mut self, _: &Expr) {}
}
```

```rust
impl<'a> Visit<'a> for Mentions {
    fn visit_identifier_reference(
        &mut self,
        it: &IdentifierReference<'a>,
    ) {
        self.found
            .push((it.span, self.inner));
    }
    // visit_binding_identifier: the same
    fn visit_arrow_function_expression(
        &mut self,
        it: &ArrowFunctionExpression<'a>,
    ) {
        let saved = std::mem::replace(
            &mut self.inner, true);
        walk_arrow_fn(self, it);
        self.inner = saved;
    }
    // visit_function: the same
}
```

</Examples>

The first overrides one method: `Names` records every name and the
defaults walk the rest, so on `a + (() => b + 1)` it collects `a` and
`b`. The second
also overrides `visit_func` with an empty body; that replaces the walk
of function bodies, so it collects only `a`, which is exactly how
`HoistCollector` in `resolve.rs` stops at nested functions on purpose.
The third is the real `Mentions` from `lower.rs` (rewrapped;
`walk_arrow_fn` stands for oxc's `walk::walk_arrow_function_expression`):
it records each identifier's span and whether it is inside a nested
function, and four overrides cover all of JavaScript. `std::mem::replace` stores
`true` in `self.inner` and hands back the old value, so leaving the
arrow restores it. Run the first two, then try your own:

## Two passes, two files each

As in TypeScript, the plugin makes two passes. `resolve.rs` pairs every
identifier with its binding (*Finding every name before running: the
resolver*), then `lower.rs` builds VIR. The resolver implements `Visit`
and overrides the node kinds that `resolve.ts` handles in its own
`switch`, such as functions, blocks, loops, `try` and declarations.

The bigger change is how things are *named*. `resolve.ts` keys its maps
by node objects, which JavaScript compares by identity for free. The
port keys everything by plain values instead. An
owner is `FnKey::Program` or `FnKey::Func(Span)` (in the words of
`resolve.rs`, "spans of function nodes are unique"), `refs` is a
`HashMap<Span, JsBindingId>`, and bindings live in a `Vec`, named by a
typed index (*VIR in Rust*). No table holds a reference into the tree,
so none needs the tree's lifetime.

## Lowering, function by function

`lower.rs` uses the same rule as `lower.ts`: a variable stays an SSA
value only if it is a simple kind (`const`, `let`, `var`, a parameter
or a `catch` variable), used in no other function, never assigned in a
`try`, and not initialised with an array; anything else is a binding.

In TypeScript, `lowerFunction` holds its helpers (`read`, `write`,
`expr` and the rest) as closures sharing the function builder `fb`.
Rust closures cannot share mutable state that freely, so the port has
one `Lowerer` struct with the per-function state in one field, `f`. A
nested function builds an `FnState` of its own, swaps it in with `let
outer = std::mem::replace(&mut self.f, state);`, lowers its body, and
puts the outer state back with `self.f = outer;` before it even looks
at whether lowering succeeded. Lowering this with
`JsPlugin.lower` and `print_func` gave the listing below for `add` (the
TypeScript engine printed the same):

```js
let n = 0;
const ps = [];
function add(v) {
  ps.push({ x: v });
  n++;
}
```

```
  b0:
    %0 = param
    %1 = load ps
    %2 = record {x} %0
    %3 = push %1, %2
    %4 = load n
    %5 = unop + %4
    %6 = const 1
    %7 = binop + %5, %6
    store n, %7
    return
```

`v` stays an SSA value (`%0`), while `ps` is array-initialised and `n`
is used inside `add`, so both are bindings. In `n++`, `unop +` turns the
old value into a number, as JavaScript does, before `1` is added.

## No AST after lowering

The TypeScript engine keeps ESTree nodes in `SourceRef.node`, and its
emitter asks them questions, such as (through a parent map) "is this
`a[i]` the object of a member expression?". oxc's tree lives in the
parse's arena, so keeping it would put a lifetime on the whole `Module`;
instead `node` is a `NodeRef`, an index into a side table of `JsNode`
facts:

<Figure takeaway="The emitter's questions are answered ahead of time, in a table." caption="Lowering ps[i].x += ps[i].vx: instruction %19, the first ps[i], points at entry 4 of the side table, which records the byte spans of ps and i and that ps[i] is the object of a member expression (direct).">
  <SideTable />
</Figure>

`direct` answers the parent question: lowering sets a flag just before
it lowers a member expression's object. The other kinds of fact record
what *Emitting JavaScript from Rust* needs.

## What you learned

- The **visitor pattern**: a trait with one method per node kind, whose
  defaults **walk** the children. You override only what you need;
  overriding replaces the walk, so call it yourself if you want the
  children.
- oxc's `Visit` walks in source order, like `children()`, so value
  numbers match the reference.
- `resolve.rs` and `lower.rs` port their TypeScript files case by case.
  Node identity becomes spans and typed ids (`FnKey`, `HashMap<Span,
  _>`), and closures sharing `fb` become one `Lowerer` whose `FnState`
  is swapped with `std::mem::replace`.
- Instructions point into a **side table** of `JsNode` facts, not into
  a live tree.
