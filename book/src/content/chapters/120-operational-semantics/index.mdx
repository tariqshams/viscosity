## What does a program mean?

Drip's specification says, in English, that "`+` adds two numbers or
joins two strings"; that is clear until someone asks which side is
worked out first, or what happens when the left side prints something
and the right side fails. The interpreter answers every such question,
but it answers them *by accident*, through however its code happens to
be written; if the interpreter were the definition, every bug in it
would be part of the language. What we want is in between: a
description as precise as code, and as short and readable as a page of
rules. The last two chapters showed one, beta-reduction: a single rule
that says exactly how a lambda term runs. Now we write rules like it
for a language with numbers and `if`.

<Analogy title="a board game's rulebook">
Two families can play the same board game differently for years, each
following what their own referee always did; the rulebook is what
settles the argument, because it was written to be read, not to be
played from habit.
<span slot="breaks">A rulebook leaves gaps, and players fill them with
judgement; these rules are complete for the language they describe, and
any gap shows up exactly, as a program that has no rule to take its next
step.</span>
</Analogy>

<Callout kind="definition">
An **operational semantics** defines what programs mean by giving rules
for how they run: which expression (or program state) each one steps
to, or which value it produces. The rules follow the grammar, one or a
few for each kind of syntax, which is why Plotkin called the style
*structural*<Cite id="plotkin1981" />.
</Callout>

<Examples of="operational-semantics">

```text
(λx. t) s  →  [x ↦ s] t
```

```text
a = b, in JavaScript's spec:
1. evaluate a (to a reference)
2. evaluate b, and get its value
3. store the value into a
```

```text
if true then e₂ else e₃  →  e₂
```

</Examples>

The first is the last chapter's beta rule: a complete operational
semantics for the lambda calculus, in one line. The second is how the
ECMAScript standard defines assignment: numbered steps, run in order,
which settle that the left side is evaluated before the right
side<Cite id="ecma262-assignment-order" />; it is an operational
semantics written as prose. The third is one of this chapter's rules:
an `if` whose condition is already `true` steps to its first branch.

## A tiny language, and how to read a rule

Our language has numbers, booleans, `+`, `<` and `if`:

```text
e ::= n | true | false | e + e
    | e < e | if e then e else e
v ::= n | true | false
```

The `v`s are **values**: finished answers, which do not step. A rule
is written with a line: above it the **premises**, facts that must
already hold; below it the **conclusion**, which the rule then lets us
claim. A rule with nothing above the line is an **axiom**: always true.
(Chapter 123 reads typing rules written in exactly this form.)

<Formal title="Small steps for +">

```text
    n is n₁ plus n₂
   ─────────────────            (Add)
     n₁ + n₂ → n

        e₁ → e₁'
   ────────────────────         (AddL)
   e₁ + e₂ → e₁' + e₂

        e₂ → e₂'
   ────────────────────         (AddR)
   v₁ + e₂ → v₁ + e₂'
```

<span slot="read">Add: when both sides are numbers, the sum steps to the
number that is their sum. AddL: if the left side e1 can take a step to
e1-prime, then the whole sum can take a step, by stepping its left side.
AddR: if the left side is already a value v1 and the right side can
step, then the sum steps its right side. Since AddR asks for a value on
the left, the left side always goes first.</span>
</Formal>

`<` has the same three rules, with an axiom that gives `true` or
`false`. And `if`:

<Formal title="Small steps for if">

```text
if true then e₂ else e₃  → e₂   (IfT)
if false then e₂ else e₃ → e₃   (IfF)

               e₁ → e₁'
   ─────────────────────────────  (If)
   if e₁ then e₂ else e₃
     → if e₁' then e₂ else e₃
```

<span slot="read">IfT: an if whose condition is true steps to its then
branch. IfF: one whose condition is false steps to its else branch. If:
if the condition can step, the whole if steps its condition, and leaves
both branches untouched.</span>
</Formal>

## One small step at a time

<Analogy title="long sums on a whiteboard">
A teacher works through `(1 + 2) + (3 + 4)` on the board by rewriting
the whole line after each change: `3 + (3 + 4)`, then `3 + 7`, then
`10`, never doing two things in one line.
<span slot="breaks">A person can do two little sums at once in their
head; the rules forbid it, and they also fix the order: left before
right, every time.</span>
</Analogy>

<SmallSteps client:visible />

Every step needs a reason, and the reason is a small tree of rules
called a **derivation**: the conclusion at the bottom, with the rules
that justify it stacked above it, up to an axiom.

<Figure takeaway="A step deep inside a term is justified by a stack of rules, one per level of nesting." caption="Stepping the innermost sum of ((1 + 2) + 3) + 4. Add justifies 1 + 2 → 3; AddL lifts that step into (1 + 2) + 3; AddL again lifts it into the whole expression.">
  <DerivationTree />
</Figure>

<Callout kind="definition">
A **small-step semantics** defines a relation `e → e'`, "e steps to e'
in one step", by rules like those above. Running a program means
stepping until no rule applies; writing `e →* e'` for "zero or more
steps", the result is the value `v` with `e →* v`. A term that is not
a value, but has no rule to step by, is **stuck**: that is a runtime
error, stated precisely<Cite id="pierce2002" />.
</Callout>

<Examples of="small-step-semantics">

```text
2 + 3  →  5                (Add)
```

```text
(1 + 2) + (3 + 4)
→ 3 + (3 + 4)              (AddL)
→ 3 + 7                    (AddR)
→ 10                       (Add)
```

```text
if 1 then 2 else 3         stuck
if 1 < 2 then 5 else true  →* 5
```

</Examples>

The first is a single axiom. The second is the stepper's first program,
with each step's rule written beside it. The third shows the two
edges: `if 1 ...` is stuck, because no rule takes a number as a
condition, while the last line runs fine and gives 5, even though its
other branch is `true`: the rules never look at a branch that is not
taken. Notice also that at most one rule ever applies to a term, so
each program has exactly one way to run (the rules are
**deterministic**). The runnable example is the `+` rules in
JavaScript, printing every step:

## What you learned

- An **operational semantics** defines a language by rules for how its
  programs run, one or a few per kind of syntax.
- A rule has premises above the line and a conclusion below; an axiom
  has no premises.
- A **small-step semantics** says how a term takes one step; running a
  program is stepping until a value, and a term that cannot step is
  stuck: a runtime error, made precise.
