## A language you can hold in your head

JavaScript is a big language, with many years of features piled on top
of each other, and starting there is a poor way to learn how a language
works inside; you would spend months on corners before you reached the
middle. So for Part III you will build a smaller one, this book's own
language, called **Drip**. It is designed to be small enough to
implement completely in a few weeks, and familiar enough that the
JavaScript you already know carries over, while still having the parts
that make real languages hard to build: closures, classes and
inheritance.

<Analogy title="a model kit of a real car">
A good model kit is much smaller than the car, and some comforts are
missing; however, the engine, the wheels and the steering are all there,
and they work the way the real ones do. Once you have built the model,
the real car stops being a mystery.
<span slot="breaks">A model is smaller in every part. Drip is small in
the *number* of features, but each one it has works at full size: its
closures are real closures, and its classes are real classes.</span>
</Analogy>

<Analogy extra title="a learner's car on quiet roads">
You learn to drive in a small car on quiet streets: the pedals, the
wheel and the mirrors are the same as on any car, so almost everything
you learn carries over, and nothing too fast can happen while you
learn.
<span slot="breaks">A learner's car leaves out nothing a driver needs;
Drip leaves things out on purpose (a big library, for a start), and a
few of those gaps change how an implementation is built.</span>
</Analogy>

## Values and variables

Drip has numbers, strings, `true` and `false`, and `none`, which means
"no value" (like JavaScript's `null`). Variables are made with `let`;
and `print` is a **statement**, a command in the language itself rather
than a function, so it needs no brackets:

<Run id="values" />

Line 1 prints `3.5`: every number is a 64-bit float, as in JavaScript,
so dividing does not round down. Line 2 joins two strings with `+`,
giving `dripdrop`. Line 3 uses `&&` exactly as JavaScript does (and
`||` for "or"), and prints `true`. Line 4 prints `false`, and line 5
prints `none`. Then `let cups = 3;` makes a variable, and
`cups += 1;` adds 1 to it (Drip has `+=` and `-=`, but no `++`), so
`print cups;` shows `4`. The last line prints `0.30000000000000004`,
the same rounding you met in *Floats and typed arrays: numbers as bytes*, because Drip's
numbers are JavaScript's numbers underneath. Comments start with `#`
and run to the end of the line.

## Deciding and repeating

`if`, `while` and `for` look nearly the way you would expect, with two
small changes: the condition needs no brackets around it, and the body
always takes braces, even when it is one statement (`if x > 1 { ... }`).
One more rule differs from JavaScript, and it is
worth stepping through slowly: which values count as true.

<TruthSteps client:visible />

<Formal title="Drip's truth rule">

```text
truthy(v) = false   if v is none or false
truthy(v) = true    otherwise
```

<span slot="read">To decide an if or a while, Drip asks whether the
value v is truthy. The answer is false in exactly two cases, when v is
none and when v is false, and true for every other value: every number,
zero included, every string, the empty one included, and every
list, function, class and instance.</span>
</Formal>

<Examples of="drip">

```
let cups = 3;
print cups + 1;
```

<Run id="control" />

<Run id="classes" />

</Examples>

The first is the smallest useful Drip program: make a variable, print
a sum, `4`. The second puts the control statements to work. The
`while` loop doubles `n` while it is below 50, so `n` goes 1, 2, 4, 8,
16, 32, 64, and `print n;` shows `64`. The `for` loop walks a
**range**: `0..3` means 0, 1, 2, stopping just before 3, so it prints
`0`, `1` and `2` (`for x in xs` walks a list the same way, one element
at a time). The last two lines test `0`:
in Drip that is true, so the program prints `0 is true`, the opposite
of what JavaScript would do, whose rules list `0` and the empty string
among the values that count as false<Cite id="ecma262" />. The third is the most realistic, a small
class hierarchy, explained in the section on classes below.

## Functions and closures

Functions are declared with `fn`, a name, parameters in brackets and a
body in braces. They are values, so a function can return another
function, and the inner one remembers the variables around the place it
was made: a **closure**, exactly as in *Closures: functions that
remember*.

<Run id="functions" />

The first four lines define `square` and print `square(4)`, which is
`16`. Then `makeCounter` makes a local `n` set to 0 and, inside it, a
function `count` that adds 1 to `n` and returns it; `makeCounter`
returns `count` itself (no brackets after it, so it is not called).
`let c = makeCounter();` keeps that function in `c`, and each `c()`
updates the same `n`, printing `1` and then `2`. The last line prints a
function as a value: `fn makeCounter`. Each call to `makeCounter`
makes a new `n`, and the `count` it returns keeps that `n` alive after
the call has finished; making that work inside the interpreter is the
job of the chapter *Closures in Drip*.

<Prompts ids={['fn-value', 'closure-drip']} />

## Classes

Drip has classes with methods, `self` (Drip's name for JavaScript's
`this`) and a constructor, which must be called `init`. You make an
instance with `new`, as in JavaScript. A class inherits from another
with `extends`, and `super.name(...)` calls the parent's version of a
method. That is what the third example above does: `Cup` has
`init(ml)`, which stores the amount on the new instance as `self.ml`,
and a method `pour(x)` that takes `x` away and returns what is left.
`Mug extends Cup` inherits both and replaces `pour` with one that first
prints a warning and then calls `super.pour(x)`. So `new Mug(300)` runs
`Cup`'s `init` with `ml` set to 300, `m.pour(50)` prints
`careful, hot` and then `250`, and printing the instance itself shows
its class and fields, `Mug { ml: 250 }`.

## What you learned

- **Drip** is this book's own small language: numbers (64-bit floats),
  strings, booleans, `none`, lists, functions, closures and classes.
- `print` is a statement; comments start with `#`; there is `+=` but no
  `++`; conditions take no brackets and bodies always take braces.
- Only `none` and `false` count as false; `0` and `""` are true.
- Classes use `init` for the constructor, `self` for the instance,
  `extends` to inherit and `super` to reach the parent; instances are
  made with `new`.

## When is a mistake found?

Here is a two-line Drip program with a mistake in it:

```
print "start";
print "a" * 2;
```

Multiplying a string by a number means nothing in Drip; the question is
*when* Drip notices. TypeScript, from *TypeScript I: types as labels*,
would refuse the whole program before running any of it. Drip does not:
it prints `start`, and only when it reaches line 2 does it stop, with
`cannot use '*' on a string and a number` and the line number. That is what it means
for a language to be dynamically typed.

<Analogy title="labels on parcels">
In a sorting office, the shelves do not care what sits on them; the
label is on each parcel, and nobody reads it until someone picks the
parcel up to deliver it. If a label turns out to be wrong, that is found
at the moment of delivery, not when the parcel was shelved.
<span slot="breaks">A sorting office could check every label on arrival
if it chose to; a dynamically typed language cannot check ahead, because
which value reaches an operation may depend on input it has not seen
yet.</span>
</Analogy>

<Analogy extra title="a recipe followed step by step">
A cook working through a recipe finds out that the "2 eggs" have run
out only on reaching the step that needs them, after the oven is
already hot; a careful editor reading the recipe beforehand would have
caught a misprint like "2 cups of salt" without cooking anything.
<span slot="breaks">An editor can only catch what is wrong in the text
itself; a type checker, like the editor, checks the program's text, while
Drip, like the cook, checks the actual values as they turn up.</span>
</Analogy>

Step through what happens when `+` meets the wrong kind of value:

<TypeTagSteps client:visible />

The picture to keep is that the type travels with the **value**, as a
small tag, while the variable is only a name that points at whichever
value it holds now. `b` held a number and then a string, and nothing
objected; the check happened inside `+`, which read both tags at the
moment it ran.

<Callout kind="definition">
**Dynamic typing** means types belong to values, not variables, and
they are checked while the program runs, at the moment an operation
needs them. In Drip, `+` accepts two numbers or two strings, and the
other arithmetic operators accept only numbers; anything else stops the
program with a **runtime error** that names the line.
</Callout>

<Formal title="The rules for + in Drip">

```text
number a + number b  →  number a + b
string s + string t  →  string st
any other pair       →  runtime error
```

<span slot="read">If both values carry the number tag, the result is
their sum, tagged number. If both carry the string tag, the result is
the two strings joined, tagged string. For any other pair of tags, such
as a number and a string, + does not produce a value at all: the program
stops with a runtime error that names both, such as "cannot add a
number and a string".</span>
</Formal>

<Examples of="dynamic-typing">

```
let x = 1;
x = "one";
print x;  # one
```

```
fn twice(v) { return v + v; }
print twice(2);     # 4
print twice("ab");  # abab
print twice(none);  # runtime error
```

<Run id="type-error" />

</Examples>

The first shows that a variable has no type of its own: `x` holds a
number, then a string, and the program prints `one` without complaint.
The second shows one function working on two kinds of value, because
the check happens inside `+` on each call: `twice(2)` adds, `twice("ab")`
joins, and `twice(none)` stops with `cannot add none and none`, after
the first two lines have already printed. The third is a mistake that
real programs make all the time, gluing a label onto a number: in Drip
`"Total: " + 3` is an error (`+` never converts; you turn the number
into a string yourself, with the built-in function `str`), so the
runnable box prints `start` and then stops. Spot the difference with
its fix, which makes both sides strings:

```
print "Total: " + 3;
# runtime error: cannot add
# a string and a number
print "Total: " + str(3);  # Total: 3
```

<Prompts ids={['dyn-when', 'types-on-values', 'var-change-type']} />

Dynamic does not mean "anything goes", and languages that check at run
time still differ in how strict they are. Here is the same mistake in
four other languages:

<OtherLanguages>

```js
console.log("a" + 1); // "a1"
```

```python
print("a" + 1)
# TypeError at run time:
# can only concatenate str
# (not "int") to str
```

```java
// static types, and + joins:
System.out.println("a" + 1); // a1
```

```c
/* a pointer, moved on by one
   character: prints nothing */
printf("%s\n", "a" + 1);
```

</OtherLanguages>

JavaScript is dynamically typed, like Drip, but its `+` quietly
converts the number and gives `"a1"`; Python is dynamically typed and
as strict as Drip, stopping with a `TypeError` when the line runs. Java
checks types before running, and its rules say that `+` with a string
on either side joins, so it also prints `a1`. C has no string type at
all: `"a"` is the address of two bytes in memory (the letter and a
zero that ends it), and `+ 1` moves that address on by one, to the
zero, so it prints an empty line. Drip's choice, to refuse and say so,
is one legitimate design among several.

## Who decides what a program means?

Here is a question with no obvious answer: what should `print 7 / 2;`
show? `3`, `3.5` or an error are all reasonable, and different
languages make different choices; Drip prints `3.5`. Something has to
write that decision down, so that every implementation of the language
makes the same one, and so that when two of them disagree there is a
way to say which is wrong.

<Analogy extra title="the rulebook in a board game box">
Players argue about whether you may build a hotel before every street
in the set has a house; the rulebook in the box settles it, and any
group that plays by the rulebook gets the same game.
<span slot="breaks">Players may agree on house rules and still have a
fine evening; an implementation that departs from the spec is simply
wrong, because programs written for the language will break on
it.</span>
</Analogy>

<Analogy extra title="an answer key">
A teacher marks an exam with an answer key: every question has one
exact expected answer, and a script either matches it or does not.
<span slot="breaks">An answer key only covers the questions on the
paper. A test suite only covers the programs someone wrote down, so
passing all of them is strong evidence that an implementation is right,
not a proof.</span>
</Analogy>

<Callout kind="definition">
A **language specification** (a **spec**) is a precise description of
what every program in a language means: which programs are valid, and
what each one does or which error it reports. An implementation is
correct when it does what the spec says, for every program.
</Callout>

JavaScript's spec is a document called ECMA-262, maintained by a
committee called TC39<Cite id="ecma262" />. Drip has no committee: its
spec is this book's description of the language (`book/DRIP.md`),
made checkable by **more than three hundred test programs** in
`companion/corpus`. Each test writes down what it should
do in its own comments, and the test runner compares:

<Figure takeaway="The tests are the spec you can run." caption="A test program carries its expected output in comments. The runner runs it on each implementation and compares the output with the comments line by line; an implementation passes only on an exact match.">
  <SpecCheck />
</Figure>

<Formal title="Passing a test, and being correct">

```text
passes(I, t)  ⟺  out(I, t) = expect(t)
correct(I)    ⟺  out(I, P) = spec(P)
                 for every program P
```

<span slot="read">An implementation I passes a test t exactly when
(the double arrow, read "if and only if") the output of running t on I
is equal to the output written in t's comments. I is correct when, for
every program P at all, its output is the one the spec gives; the tests
check the first line for a few hundred programs, which is how we gain confidence
in the second.</span>
</Formal>

<Examples of="language-spec">

```
# from truthiness/what_is_true.drip
print truth(0);   # expect: true
print truth("");  # expect: true
```

```
# from operators/add_boolean.drip
print true + 1;
# expect runtime error: cannot add
# a boolean and a number
```

```text
ECMA-262: the meaning of JavaScript,
written as a document. Test262: tests
that check engines against it.
```

</Examples>

The first two are real Drip tests, shortened to fit (in the files each
`# expect` comment sits at the end of its line). The first pins down
the truth rule from the last chapter: the test's function `truth(v)`
returns `"true"` when `if v` runs its body, and `0` and `""` must both
count as true, so the expected output is `true` twice. The second
expects an error instead of output, written as `expect runtime error:`
followed by the exact message, so an implementation that printed `2`
(as JavaScript's `+` would) fails. The third is the same arrangement for
JavaScript, at a much larger scale: a written spec, and a separate,
official collection of tests that engines run to check that they follow
it<Cite id="test262" />.

## What you learned

- **Dynamic typing**: values carry their types and variables do not;
  Drip checks the tags as each operation runs, so a wrong type is a
  runtime error, found only when its line runs.
- Languages that check at run time still differ: JavaScript converts,
  Python and Drip refuse.
- A **language spec** says precisely what every program means. Drip's
  is made runnable by hundreds of test programs whose comments give the exact
  expected output or error, and both implementations must pass them.
- Passing every test is strong evidence, not proof: tests only cover the
  programs someone wrote down.
