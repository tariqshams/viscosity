## A language you can hold in your head

JavaScript is a big language, with many years of features piled on top
of each other, and starting there is a poor way to learn how a language
works inside; you would spend months on corners before you reached the
middle. So you will build a smaller one, this book's own language,
**Drip**: small enough to implement completely in a few weeks, familiar
enough that your JavaScript carries over, and still with the parts that
make real languages hard to build, namely closures, classes and
inheritance.

<Figure takeaway="Drip is JavaScript's ideas with fewer, plainer words." caption="Each row is one idea spelled two ways. The highlighted Drip column is where the spelling differs; the last row is something Drip simply does not have.">
  <DripAtAGlance />
</Figure>

<Callout kind="definition">
**Drip** is the small, dynamically typed language this book implements
twice: as a tree-walking interpreter, then as a bytecode VM. It has
numbers (64-bit floats, as in JavaScript), strings, booleans and `none`
("no value"), lists, variables, `if`, `while` and `for`, functions and
closures, and classes with inheritance.
</Callout>

<Examples of="drip">

```
fn makeCounter() {
  let n = 0;
  fn count() { n += 1; return n; }
  return count;
}
let c = makeCounter();
print c();  # 1
print c();  # 2
class Mug extends Cup {  # Cup: init, pour
  pour(x) {
    print "careful, hot";
    return super.pour(x);
  }
}
```

</Examples>

Functions are declared with `fn`; they are values, so `makeCounter`
returns `count` itself, and `count` is a closure that keeps its `n`
alive after the call has ended (*Closures: functions that remember*),
so each `c()` updates the same `n`. `print` is a statement, not a
function, so it needs no brackets; comments start with `#`; there is
`+=` but no `++`. Classes use `init` for the constructor, `self` for
JavaScript's `this`, `extends` to inherit and `super.name(...)` to call
the parent's method, and instances are made with `new`, as in `new
Mug(300)`.

<More title="Try it: values, loops, functions and classes">

Every example runs on the interpreter you are about to write, so edit
freely. `7 / 2` prints `3.5`, and `0.1 + 0.2` prints
`0.30000000000000004`, because Drip's numbers are JavaScript's numbers
underneath.

`0..3` is a range, 0, 1 and 2; and conditions take no brackets, while
bodies always take braces.

## What counts as true

One rule differs from JavaScript, and it is worth stepping through
slowly: which values an `if` or a `while` treats as true.

<TruthSteps client:visible />

In Drip only `none` and `false` are false; every number, zero included,
and every string, the empty one included, is true. JavaScript's rules
list `0` and the empty string among the false
values<Cite id="ecma262" />, so `if 0 { ... }` does the opposite in the
two languages.

<Formal title="Drip's truth rule">

```text
truthy(v) = false   if v is none or false
truthy(v) = true    otherwise
```

<span slot="read">To decide an if or a while, Drip asks whether the
value v is truthy; the answer is false in exactly two cases, when v is
none and when v is false, and true for every other value.</span>
</Formal>

## When is a mistake found?

```
print "start";
print "a" * 2;
```

Multiplying a string by a number means nothing in Drip; the question is
*when* Drip notices. TypeScript would refuse the whole program before
running any of it; Drip prints `start`, and only on reaching line 2
stops with `cannot use '*' on a string and a number` and the line
number.

<Analogy title="labels on parcels">
In a sorting office, the shelves do not care what sits on them; the
label is on each parcel, and nobody reads it until someone picks the
parcel up to deliver it, so a wrong label is found at delivery, not when
the parcel was shelved.
<span slot="breaks">A sorting office could check every label on arrival;
a dynamically typed language cannot check ahead, because which value
reaches an operation may depend on input it has not seen yet.</span>
</Analogy>

<TypeTagSteps client:visible />

The type travels with the **value**, as a small tag, while a variable
is only a name for whichever value it holds now; the check happens
inside `+`, which reads both tags at the moment it runs.

<Callout kind="definition">
**Dynamic typing** means types belong to values, not variables, and
they are checked while the program runs, at the moment an operation
needs them. In Drip, `+` accepts two numbers or two strings, and the
other arithmetic operators accept only numbers; anything else stops the
program with a **runtime error** that names the line.
</Callout>

<Examples of="dynamic-typing">

```
fn twice(v) { return v + v; }
print twice(2);     # 4
print twice("ab");  # abab
print twice(none);  # runtime error
print "Total: " + str(3);  # Total: 3
```

</Examples>

One function works on two kinds of value, because the check happens
inside `+` on each call: `twice(2)` adds, `twice("ab")` joins, and
`twice(none)` stops with `cannot add none and none` after the first two
lines have printed. Drip's `+` never converts, so to glue a label onto
a number you make both sides strings with the built-in `str`.

<OtherLanguages>

```js
console.log("a" + 1); // "a1"
```

```python
print("a" + 1)
# TypeError at run time:
# can only concatenate str
# (not "int") to str
```

```java
// static types, and + joins:
System.out.println("a" + 1); // a1
```

```c
/* a pointer, moved on by one
   character: prints nothing */
printf("%s\n", "a" + 1);
```

JavaScript is dynamically typed but its `+` quietly converts; Python is
as strict as Drip. Java checks types before running, and its `+` joins
when either side is a string. C has no string type at all: `"a" + 1`
moves an address on by one. Refusing, and saying so, is one legitimate
design among several.

</OtherLanguages>

## Who decides what a program means?

Should `print 7 / 2;` show `3`, `3.5` or an error? All are reasonable,
and languages differ; Drip prints `3.5`. Something has to write that
decision down, so that every implementation makes the same one, and so
that when two disagree there is a way to say which is wrong.

<Callout kind="definition">
A **language specification** (a **spec**) is a precise description of
what every program in a language means: which programs are valid, and
what each one does or which error it reports. An implementation is
correct when it does what the spec says, for every program.
</Callout>

JavaScript's spec is ECMA-262, maintained by a committee called
TC39<Cite id="ecma262" />. Drip's spec is this book's description of
the language (`book/DRIP.md`), made checkable by more than three hundred
test programs in `companion/corpus`, each writing down in its comments
what it should do:

<Figure takeaway="The tests are the spec you can run." caption="A test program carries its expected output in comments. The runner runs it on each implementation and compares the output with the comments line by line; an implementation passes only on an exact match.">
  <SpecCheck />
</Figure>

<Examples of="language-spec">

```
# from operators/add_boolean.drip
print true + 1;
# expect runtime error: cannot add
# a boolean and a number
```

</Examples>

This real test (shortened to fit) expects an error, written as `expect
runtime error:` and the exact message, so an implementation that
printed `2`, as JavaScript's `+` would, fails it. JavaScript has the
same arrangement at a far larger scale: Test262, an official collection
of tests that engines run against ECMA-262<Cite id="test262" />. The
companion runs the corpus against both Drip implementations, which is
differential testing (*Edge cases and differential testing*) at the
scale of a language; passing every test is strong evidence, not proof,
since tests cover only the programs someone wrote down.

<Formal title="Passing a test, and being correct">

```text
passes(I, t)  ⟺  out(I, t) = expect(t)
correct(I)    ⟺  out(I, P) = spec(P)
                 for every program P
```

<span slot="read">An implementation I passes a test t exactly when the
output of running t on I equals the output in t's comments; I is correct
when, for every program P, its output is the one the spec gives. The
tests check the first for a few hundred programs, which is how we gain
confidence in the second.</span>
</Formal>

## What you learned

- **Drip** is this book's small language: JavaScript's ideas with plainer
  words, closures and classes included; only `none` and `false` are
  false.
- **Dynamic typing**: values carry their types and variables do not, so
  a wrong type is a runtime error, found only when its line runs.
- A **language spec** says what every program means; Drip's is made
  runnable by hundreds of test programs that both implementations must
  pass.
