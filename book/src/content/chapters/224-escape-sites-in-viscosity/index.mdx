## Not just whether, but where

The last chapter's escape analysis answers with a state per object:
NoEscape, ArgEscape or GlobalEscape. Viscosity needs something a little
different. It is not deciding where one object lives; it is deciding
whether a whole array of objects can become columns, and if it says
no, it owes the programmer a reason they can act on, such as "line 6
passes an element to `console.log`". So it does not colour a graph; it
walks every use of the array, and of every element the array hands out,
and stops at the first use it cannot rewrite, naming it.

<Analogy title="every door and window of a house">
To be sure a cat cannot get out of a house, you do not watch the cat;
you go round every door and window and check each one is shut. A list
of every opening, checked one by one, is a proof.
<span slot="breaks">A cat leaves bodily, and is then outside and not
inside; a reference can be copied, so it can be both inside and
outside at once, and one copy left anywhere is enough.</span>
</Analogy>

<Analogy title="crossings at a border">
Goods can only leave a country through its border crossings, so a
customs service that staffs every crossing knows everything that
leaves. Name the crossings, and you know where to look.
<span slot="breaks">A country's crossings are on a map; a program's
"crossings" are whatever operations Viscosity has not modelled, so
the list is defined by what is safe, and everything else counts as a
crossing.</span>
</Analogy>

<Callout kind="definition">
An **escape site** is a place in the code where a reference can leave
the region an analysis controls: passing it to a call, storing it into
a variable, a property, an array or another object, and returning it.
Viscosity adds three of its own: an identity comparison (`===`), an
operation it does not model (`opaque`), and a merge (`phi`). For each
candidate array, every use of the array and of its elements must be
one Viscosity can rewrite; any other use is an escape site, and the
array keeps its layout.
</Callout>

## Following the uses

Viscosity works on its SSA IR, VIR, where every value has a list of
the instructions that use it. It starts from every load of the array
and walks those lists. Some uses are fine because it knows how to
rewrite them: `push` of a fresh object literal, `.length`, and `ps[i]`.
But `ps[i]` produces a new value, the element, and its uses must be
walked too, so this is a worklist again:

<EscapeSteps client:visible />

Here is the element part, from `packages/core/src/analysis.ts`,
simplified (`el` is the value an `index.get` produced):

```ts
for (const u of usesOf(el)) {
  const i = u.inst;
  if (i && i.op === 'field.get' &&
      i.args[0] === el) {
    c.accesses.push(/* a read */);
    continue;
  }
  if (i && i.op === 'field.set' &&
      i.args[0] === el) {
    c.accesses.push(/* a write */);
    continue;
  }
  bail(c, 'an element is ' +
    describeUse(u, el));
}
```

Only two uses are safe: reading a field of the element and writing a
field of the element, which become `ps.x[i]` and `ps.x[i] = v`. Each is
recorded as an access, because the planner later needs to know which
fields each loop touches. Everything else goes to `bail`, which records
the reason. The check `i.args[0] === el` matters, because `field.set`
has two operands:

## Naming the escape site

`describeUse` turns each escaping use into words. Simplified, with the
line numbers left out:

```ts
switch (i.op) {
  case 'call':
    return 'passed to a function call';
  case 'storeBinding':
    return 'stored in another variable';
  case 'field.set':
    return 'stored into an object property';
  case 'index.set':
    return 'stored into an array';
  case 'record.new':
    return 'put inside another object';
  case 'array.new':
    return 'put inside another array';
  case 'binop':
    return 'compared or combined';
  case 'opaque':
    return 'used by code Viscosity ' +
      "doesn't model";
  case 'phi':
    return 'merged with other values';
}
```

A return is not an instruction in VIR but a block terminator, so it
has its own message, "returned or branched on". Here is what the
engine really prints for small changes to a particle program:

<Examples of="escape-sites">

```text
function first() { return ps[0]; }
· unsafe: line 8: an element is
  returned or branched on in first()
```

```text
const box = { p: ps[0] };
· unsafe: line 5: an element is put
  inside another object
```

```text
console.log(ps[0] === ps[1]);
· unsafe: line 7: an element is
  compared or combined with "==="
```

</Examples>

The first hands the element to the caller of `first`, where Viscosity
cannot see what happens next. The second stores a reference to it
inside a new object. The third is the subtle one: nothing is stored
anywhere, but `===` asks about identity, and after the rewrite there
are no element objects to be identical. Rebuilding an object for each
side would give two different objects, so the answer would change; run
it:

<Run id="identity" />

The other two sites are there for safety. `opaque` is VIR's name for
anything Viscosity does not model, so every argument must be assumed to
escape. A `phi` merges an element with other values, as in
`let p = ps[0]; if (c) p = ps[5];`; Viscosity does not track what flows
out of a merge, so it counts the merge itself as an escape.

## Calls that are not escapes

A call is usually an escape, but not always. If `step(qs)` is declared
once and only ever called directly, Viscosity knows every call site
(chapter 210's known functions). When every one of them passes `ps`,
the parameter `qs` points at exactly one collection, so it joins the
worklist and its uses are checked inside `step`:

```text
ps (line 1) {x, vx} → struct of arrays
  · loop at line 6 in step() touches
    2 of 2 fields (x, vx)
```

That is interprocedural analysis, but not by summary: Viscosity reads
the body of `step` again for each collection it follows into it.
Passing an *element* to a function, as in `move(ps[i])`, is still an
escape today ("an element is passed to a function call"). Try it, then
remove the escape by writing the update inline:

<Callout kind="engine" label="Under the hood">
V8 and Viscosity ask the same question at different times. V8 compiles
optimized code while the program runs, specialised for what it has
seen, and can deoptimize if a guess turns out wrong<Cite id="v8-maglev" />.
In chapter 176's `get-objects` benchmark, it inlined `consume(p)`,
after which `p` was used only by field reads, and the temporary object
was removed. Viscosity runs before the program does, has no
deoptimization to fall back on, and does not inline, so it must prove
safety on the code as written, which makes it stricter than V8:
`move(ps[i])` keeps the array of objects.
</Callout>

## What you learned

- **Escape sites** are the places a reference can leave: calls, stores
  into variables, properties, arrays or other objects, and returns.
  Viscosity also counts `===`, unmodelled (`opaque`) operations and
  phis.
- Viscosity checks with a worklist over def-use lists: an element
  produced by `ps[i]` adds its own uses to the list.
- Position matters: an element being *written to* is safe; an element
  being *stored* escapes.
- A known function whose every call passes the same collection is
  followed into, not counted as an escape.
- V8 can escape less because it inlines and can deoptimize; Viscosity
  proves safety ahead of time, so it is more conservative.
