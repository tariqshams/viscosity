## The second customer

Part VIII built a compiler for one language: its front end reads
JavaScript, and its core finds arrays of objects, proves them safe,
picks a layout and explains itself. Now somebody asks the obvious
question, which is whether it works on Python.

Python programs have exactly the same problem. A list of small records
and a loop that touches two fields of each record is the same shape of
data whichever language spells it; only the spelling differs (`append`
rather than `push`, indentation rather than braces). The question this
chapter answers is what that second language *costs*: a second
compiler, or something much smaller?

<Analogy title="translators at a meeting">
Five people meet, each speaking a different language. You could hire a
translator for every pair of them (ten translators), or you could agree
on one shared working language and hire one translator per person
(five). The shared language does not have to be anybody's favourite; it
only has to be able to say everything the meeting needs to say.
<span slot="breaks">A good human translator tells you when something
does not translate. A compiler's shared language says only what it was
designed to say, so anything it has no words for (Python's `1` against
`1.0`, say) is silently lost until someone adds the words.</span>
</Analogy>

<Analogy title="one kind of wall socket">
Imagine every appliance were made with one standard plug, and each
country needed one adapter for its sockets. A new kettle would work
everywhere the day it shipped, and a new country would need one
adapter, not one per appliance.
<span slot="breaks">Electricity is electricity: an adapter changes only
the shape of the pins. Languages differ in *meaning*, not only in
shape, so a language plugin has to translate what each line means, and
some meaning still leaks through into the shared part, as the last
section shows.</span>
</Analogy>

## Languages times analyses

Count the work. Step through the bill, first without a shared middle and
then with one:

<BillSteps client:visible />

Without a shared IR (an *intermediate representation*, the compiler's
own internal language from *What an IR is for*), each analysis is
written against one language's syntax tree, so every language needs its
own copy of every analysis. With VIR in the middle, an analysis is
written once, against VIR, and a language costs one **plugin**: a
parser, a lowering into VIR, and an emitter that writes the program
back out.

<Formal title="The two bills">

```text
no shared IR:  Σ over languages l,
               Σ over analyses a: c(l, a)
               ≈ L × A
shared IR:     L × p  +  A
```

<span slot="read">Without a shared IR you pay c(l, a), the cost of one
analysis written for one language, once for every pair of a language
and an analysis; with L languages and A analyses that is about L times
A pieces of work. With a shared IR each language pays p, the price of
its plugin, and each analysis is paid for once, so the total is L
times p plus A. For Viscosity's two languages and six analyses that is
twelve analyses against two plugins and six analyses.</span>
</Formal>

<Callout kind="definition">
A **multi-language IR** is an intermediate representation that several
source languages lower into, so that the analyses and the planning
written against it serve all of them at once. It turns the cost of
supporting L languages and A analyses from about **L × A** into about
**L + A**; the price is that the IR must be able to say what *every*
language means, not only what the first one meant.
</Callout>

## One pipeline, two plugins

The contract between a language and the core is the `LanguagePlugin`
interface from *The plugin API*. This is it, from
`core/src/plugin.ts`, wrapped to fit:

```ts
interface LanguagePlugin {
  id: string;           // 'python'
  extensions: string[]; // ['.py']
  lower(source: string,
        filename?: string): LoweredModule;
  emit(source: string,
       lowered: LoweredModule,
       plan: Plan): string;
}
```

A plugin has a name, its file extensions and two jobs: `lower` turns
source text into a VIR module, and `emit` takes the source, that module
and the core's plan, and returns the rewritten program.

Here is how the CLI chooses, from `cli/src/cli.ts`:

```ts
function pluginFor(file, parser) {
  const ext = extname(file);
  return ext === '.py'
    ? pythonPlugin()
    : jsPlugin({ parser, typescript:
        ['.ts', '.mts', '.tsx']
          .includes(ext) });
}
```

`.py` gets the Python plugin and anything else the JavaScript one
(told whether to strip TypeScript types first); this is the only place
the CLI asks which language it holds.

<Figure takeaway="The language is chosen once, at the edges; the middle is shared." caption="Each file meets its own plugin on the way in and again on the way out. Between the two, the core works on VIR and never sees a brace or an indent.">

</Figure>

And here is `compile` from `core/src/index.ts`, the function the CLI
calls for every file in every language (wrapped, with one line that
fills in default options left out):

```ts
function compile(source, plugin, opts) {
  const lowered = plugin.lower(source);
  const analysis = analyze(lowered.module);
  const p = plan(analysis, { /* opts */ });
  const code =
    plugin.emit(source, lowered, p);
  return { code, plan: p, analysis,
           explain: explain(p) };
}
```

The plugin lowers; `analyze` finds collections, shapes, loops and
safety; `plan` picks a layout; the *same* plugin writes the new program;
`explain` writes the report. Only the two plugin calls touch a
language.

## What Python got for free

The Python plugin, `packages/frontend-python`, is 1,085 lines: a
tokenizer, a parser, a lowering, an emitter and 44 lines joining them
(the next three chapters walk through it). It has no safety analysis,
no loop finder, no bounds proofs, no cost model and no report writer;
it did not need them.

<Examples of="multi-language-ir">

```text
b6:
  %20 = index.get %15, %17
  %21 = field.get %20 .x
  %22 = field.get %20 .vx
  %23 = binop + %21, %22
  field.set %20, %23 .x
```

```text
JS  ps (line 1) {x, vx} → struct of arrays
  · typed Float64Array columns ...
PY  ps (line 8) {x, vx} → struct of arrays
  · typed array('d') columns ...
```

```text
ps (line 13) {x, y, vx, vy, name}
  → struct of arrays
  · loop at line 18 in step() touches
    2 of 5 fields (x, vx)
  · 3 of 5 element accesses proven ...
```

</Examples>

The first is the body of the loop `for p of ps` in JavaScript, and of
`for p in ps:` in Python, from a small program that builds 100 records
`{x, vx}` and adds `vx` to `x`: `index.get` reads element `%17` of the
list `%15` (that is `p`), the two `field.get`s read its `x` and `vx`,
`binop +` adds them and `field.set` stores the sum in `x`. The Python
plugin produces these same five instructions (only the value numbers
are one higher), so the analyses cannot tell the languages apart.

The second is the report each language gets for that program (trimmed;
Python run with `--python-auto`, explained in the emitter chapter).
Only the line numbers and the name of the column type differ, because
one planner wrote both.

The third is real: in the corpus program `particles.py` the update
loops live inside `step(arr, dt)`, which is called with the list, and
they were still found, because the shared core follows a list into the
function it is passed to, exactly as it does for JavaScript.

Refusals come free too, and here the two languages differ in a way
worth spotting:

```py
print(ps[0])
# unsafe: line 13: an element is passed
#   to a function call
```

```js
console.log(ps[3]);
// unsafe: line 6: an element is passed
//   to a method call
```

Both hand a whole record to a printer, so the record must really
exist, and the same escape check refuses both; the one word that differs
is honest, because `print` is a plain function while `console.log` is a
method of `console`. A bug fixed in that check is fixed for both
languages at once.

## What did not come free

An honest bill has a second column. Some parts of the core had to
learn about Python, and some still have not.

**Language facts.** A handful of lines in the core read
`module.language`. In JavaScript every number is a double, so any number
fits a `Float64Array`; in Python, `1` and `1.0` are different kinds of
number, so "numeric" has to mean "provably a float", and a valid index
has to be an int. The planner reads it too: CPython measured *slower*
with columns, so Python keeps its objects unless you opt in. And a VIR
`const` grew a note saying `int` or `float`, which JavaScript never
needed.

**Wording.** The reasons in a report were first written with
JavaScript in mind. For `not_dataclass.py`, whose class is an ordinary
Python class rather than a dataclass, the first report said the program
"pushes something that is not a fresh object literal". The decision was
right, however Python has neither `push` nor object literals, so the
wording became a language fact as well:

```text
· unsafe: line 8: appends something
  that is not a fresh dataclass
  instance (...)
```

**Tools and strategies.** `viscosity profile` runs the program with
Node, so for a `.py` file it now refuses up front ("profile runs
JavaScript programs only; Python profiling is not supported yet"); and
the Python emitter throws `AoSoA is not supported for Python`, because
each layout strategy is still code inside each emitter.

None of this breaks the argument; it shows where the seam is. Anything
that depends on what a value *means* in a language belongs to that
language, even when it runs in the core, and a good multi-language IR
makes those facts explicit and few.

<Callout kind="engine" label="Under the hood">
Big compilers are built the same way. LLVM's core processes an
intermediate representation and turns it into object files, while Clang
is the front end that compiles C, C++ and Objective-C into
it<Cite id="llvm-readme" />. GraalVM's Truffle comes at the problem from
the other side: each language is written as an interpreter in one
framework, and the framework derives compiled code for all of
them<Cite id="truffle-readme" />. Viscosity is far smaller, but the
bargain is the same: put the shared work behind one representation, and
make each language pay only for its own syntax and its own meaning.
</Callout>

## What you learned

- A **multi-language IR** lets L languages share A analyses, so the
  cost is about **L + A** instead of **L × A**.
- A **plugin** has two jobs, `lower` and `emit`; the CLI picks it by
  file extension, and `compile` is one function for every language.
- The 1,085-line Python plugin reuses every analysis, the planner and
  the report writer; the same program gets the same VIR and decisions.
- Some meaning leaks into the core as **language facts**: floats against
  ints, int indexes, CPython's measured cost, the wording of a reason.
