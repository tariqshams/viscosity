## Nothing to do

Most of the code in a real project has no arrays of same-shaped
objects in it at all: it reads settings, formats strings, talks to the
network. Viscosity will still run over every one of those files on
every build, and for them the only correct output is the file itself,
unchanged; not reformatted, not with a comment moved, and not with a
stray blank line added at the top. A compiler that gets the hard files
right and quietly smudges the easy ones is a compiler nobody will
leave switched on.

<Analogy title="a proofreader and a clean page">
Hand a good proofreader a page with no mistakes on it, and it comes
back untouched. If it came back with one comma moved, you would stop
trusting them, even on the pages that really did need fixing, because
you could no longer tell their corrections from their accidents.
<span slot="breaks">A proofreader may fairly improve a clumsy sentence
that has no mistake in it; Viscosity is not allowed to "improve"
anything, not even the spacing, because its job is layout, not
style.</span>
</Analogy>

<Analogy title="a removal crew sent to move nothing">
Ask a removal crew to move only the piano, and then tell them the
piano is staying after all. When they leave, the house should be
exactly as it was, down to the book left open on the arm of the
sofa.
<span slot="breaks">In a house you only notice what you look at, so
a cushion turned over might never be spotted; the test compares every
single byte, so even an invisible change, such as a missing newline at
the very end of the file, is caught.</span>
</Analogy>

<Callout kind="definition">
An **identity transform** is a compile that must change nothing: for
an input with nothing to transform, the output equals the input. For a
source-to-source compiler that splices its edits into the original
text, "equals" can mean **byte for byte**. It is the simplest
round-trip test there is, because the input is its own expected
output.
</Callout>

The chapter *Testing compilers* showed the round trip for a printer:
parse the text, print the tree back out, parse that, and compare the
two trees. The trees may match while the text differs, because a
printer builds its output from the tree and the tree does not keep
everything (comments, blank lines, which quotes you used). Viscosity's
emitter, as *Emitting JavaScript* showed, does not print; it splices a
list of edits into your text, and with an empty list there is nothing
to splice:

The printer rebuilds the text from the tree, so the comment, the blank line and the single quotes are gone; Viscosity, with no edits, hands back its input.">

<Formal title="Two round trips">

```text
printer:  parse(print(parse(s))) = parse(s)
splicer:  plan(s) = ∅  ⇒  compile(s) = s
```

<span slot="read">For a printer, the promise is about trees: parsing
the printed text gives back the tree you started from. For Viscosity it
is about text: whenever the plan for s is empty (it decides to change
nothing), compiling s gives exactly s, character for character. The
second promise is stronger, since equal text always parses to equal
trees, but equal trees can come from different text.</span>
</Formal>

## The test in the repository

The identity test sits at the end of
`packages/frontend-js/test/differential.test.ts`:

```ts
it('leaves programs with nothing to ' +
   'transform byte-identical', () => {
  const src =
    'const a = [1, 2, 3];\n' +
    '// a comment\n' +
    'console.log(a.length);\n';
  expect(compile(src, jsPlugin()).code)
    .toBe(src);
});
```

(The real test name is one string; it is split here to fit.) `src` is
a 57-byte program, and `toBe` compares the compiled code with it as
two strings, so every byte has to match. It looks almost too small to
matter; however, `compile` runs the whole pipeline on it. Acorn parses
it, the resolver works out what every name means, the lowering builds
VIR, the analyses look at `a` and reject it (its elements are numbers,
not object literals), the planner decides nothing, and the emitter,
with no edits and no prelude, returns its input. A crash anywhere along
that line, or a single stray edit, fails the test.

The program was chosen with care, too: it has an array, so the
collection analysis really runs; a comment, which a printer would lose;
and a final newline, the classic thing to drop.

<Examples of="identity-transform">

```js
const a = [1, 2, 3];
// a comment
console.log(a.length);
```

```ts
const n: number = 3; // keep me
console.log(n * 2);
// compiled: const n = 3; // keep me
//           console.log(n * 2);
```

```js
// no_loops.js, whole file, unchanged
const ps = [];
for (let i = 0; i < 100; i++)
  ps.push({ x: i });
console.log(ps.length);
```

</Examples>

The first is the repository's snippet, which comes back as all 57 of
its bytes. The second is the one exception: a TypeScript file goes
through the plugin's type stripper before it is parsed, so with nothing
to transform it comes back as the same code with its types removed (the
`: number` is gone, the comment stays). The third is the realistic
case, the shape of `no_loops.js` from the differential corpus: `ps`
really is an array of records, so it gets analysed in full, but no loop
ever touches its fields, so the planner keeps it as it is and the whole
file round-trips. Running every corpus file for this chapter, 16 of the
40 keep every collection as an array of objects, and all 16 come back
byte-identical, although nothing in that suite checks it.

## Three checks, one front-end

The front-end package has three kinds of test, and each one catches
something the other two cannot. Step through them:

<FrontEndSteps client:visible />

The differential test runs the original and the compiled program each
in a brand-new `vm` context: inside it, the global object is a fresh
one with its own built-ins, and the outside globals stay
unchanged<Cite id="node-vm" />, so neither run can see what the other
left behind. (Node's own documentation warns that `vm` is not a
security mechanism; here it is only there to keep two runs apart.) The
outcome it records is the list of printed lines **and** the uncaught
error, if any, because a compiled program that prints the same lines
but no longer throws has still changed what it does.

Here is the whole package, run for this chapter:

```text
$ npx vitest run packages/frontend-js
 ✓ mini-parser.test.ts (47 tests)
 ✓ differential.test.ts (42 tests)
      Tests  89 passed (89)
```

The 42 are the 40 corpus files plus two round-trip tests (the snippet
above, and the `export default` cases you are about to meet). The 47
are those 40 files and the 5 benchmark programs through both parsers,
plus 2 tests of the hand-written parser on its own.

## Five hundred files of other people's code

A test with one hand-written snippet only covers what its author
thought of. The identity check, however, needs no expected output, so
it scales for nothing: any JavaScript file at all is a test case, and
its own text is the answer. For this chapter it was run over every
`.js` and `.mjs` file in the engine's `node_modules` folder, 515 files
from 59 third-party packages, and all 515 came back byte-identical.

That clean result is the second run. The first time this experiment
was done, 17 of those files crashed the compiler, every one with the
same error and every one containing `export default class`; with the
fix taken out again, the engine here still reproduces it exactly (498
the same, 0 changed, 17 crashed). Here is the smallest program that
crashed, next to one that worked:

```js
export class A {}         // fine
export default class A {} // crashed:
// TypeError: Cannot read properties of
// undefined (reading 'owner')
```

The resolver (the pass from *Lowering JavaScript to VIR* that finds
out what each name refers to) declared the names in `export`
declarations, but not in `export default` ones, so the lowering later
asked for the binding of `A` and got `undefined`. The repository's
corpus is about arrays and loops, and none of its files had a default
export, so no existing test could see it. The fix was one condition in
`resolve.ts`:

```ts
const d = (s.type ===
    'ExportNamedDeclaration' ||
  s.type === 'ExportDefaultDeclaration')
  && s.declaration ? s.declaration : s;
```

That is, look inside an `export default` statement for its declaration
too, and a round-trip test for it joined the suite. (An anonymous
`export default function () {}`, which has no name to declare at all,
crashed the resolver as well; the Rust port's parity work found that
one later, and the same round-trip test covers it now.)

The fix was small; finding the bug took a test with no expected output
and a pile of code nobody on the project had written. That is the
corpus idea that *Differential testing at scale* builds on, and the
reason random program generators like Csmith exist: to produce inputs
no test author would think of<Cite id="csmith" />.

<Callout kind="engine" label="Under the hood">
Each test guards a different promise. The round trip guards "don't
touch what you don't change". The differential test guards "change it
without changing what it does". Parser equivalence guards "the tree is
the tree, whichever parser built it". A front-end that passes only one
of them can still be badly wrong, and Viscosity needs all three because
it is a source-to-source compiler: its output is somebody's code, which
they will read, debug and commit.
</Callout>

## What you learned

- An **identity transform** must change nothing. Viscosity checks it
  **byte for byte**, which only a splicing emitter can promise; a
  printer can only promise the same tree.
- The repository's round trip runs the **whole pipeline** on a tiny
  program with an array, a comment and a final newline. TypeScript is
  the one exception: its types are stripped.
- The front-end has **three checks**: the round trip, the differential
  corpus (fresh `vm` contexts, printed lines and errors), and acorn
  against the hand-written parser. All 89 tests pass.
- The identity check needs no expected output, so it **scales to any
  code**. On 515 files of third-party code it once found a crash on
  `export default class`; with the one-line fix, all 515 come back
  byte-identical.
