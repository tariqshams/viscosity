## Which of these allocate?

You met escape analysis, scalar replacement and allocation sinking in
*Escape analysis across functions*, including V8's version: inline the
consumer, turn each allocation into a virtual object with one variable
per field, and count scavenges with `--trace-gc` to prove the objects
are gone. This chapter goes further, in two directions: which everyday
patterns TurboFan can actually see through, and what the deoptimiser
does when it has to bring a vanished object back.

Here are five loop bodies, each run 50 times over a million elements of
two `Float64Array`s. Before reading on, guess which ones allocate an
object per iteration:

```js
const { x, y } = { x: xs[i], y: ys[i] };
t += x + y;
```

```js
const [a, b] = [xs[i], ys[i]];
t += a + b;
```

```js
const p = (i & 1) ? { x: xs[i], y: ys[i] }
                  : { x: ys[i], y: xs[i] };
t += p.x + p.y;
```

```js
const p = { x: xs[i], y: ys[i] };
t += p[i & 1 ? 'x' : 'y'];
```

```js
const f = () => xs[i] + ys[i];
t += f();
```

Only the first is free. The second is mostly free, and the last three
make every object, which is more than a careful reader of the core
chapter might expect: none of them stores the object anywhere.

## A field guide, measured

Read it from the top. An object whose fields are read by fixed names is
removed, and so is a class instance whose method is called, once the
constructor and the method are inlined; destructuring an object literal
is the same thing written differently. Arrays fare less well: an array
literal read at constant indices left about 7 per cent of the reference
count, destructuring an array about 15 per cent, and `for...of` over an
array literal nearly all of it, because array destructuring and `for...of`
go through the iteration protocol, with an iterator and its result
objects to see through as well. Below the reference line are the
patterns that always escape:

- **A computed field name.** `p[c ? 'x' : 'y']` is a keyed load whose key
  is not known at compile time, so the analysis cannot replace it with
  one field's variable; with a fixed `p['x']` the same loop needed 4
  scavenges.
- **One of two objects, chosen by a branch.** Both allocations meet at a
  phi node, and in V8 12.4 a variable that may hold either of two
  allocations makes both real, even when, as here, they have the same
  shape.
- **A callee too big to inline.** A consumer of 554 bytes of bytecode is
  over the default `--max-inlined-bytecode-size` of 460, so the call stays
  a closed door; with `--max-inlined-bytecode-size=1000` the same loop
  needed 11 scavenges.
- **A closure per iteration.** A new arrow function is allocated on every
  trip, with the context it captures, and V8 12.4 did not remove it.

<More title="More: how the files were made, and two more rows">

Each file defines `xs` and `ys` as `Float64Array`s of a million
elements, a function `run()` whose loop body is the pattern, and calls
`run()` 50 times. A class `A` with a constructor setting `x` and `y`
and a method `len()` returning their sum gave 3 scavenges for
`t += new A(xs[i], ys[i]).len()`; so did a loop choosing between
`new A(xs[i]).v` and `new B(ys[i]).v` in the two arms of a conditional,
because there each object is read inside its own arm and never meets the
other at a phi. Spreading an array literal into a call,
`Math.max(...[xs[i], ys[i]])`, gave 1559, close to the reference. Counts
like these are a property of one V8 version: the late escape analysis
that Turboshaft added in 2022<Cite id="v8-src-late-escape-analysis" /> and
any future change can move a row, so measure the pattern in your own hot
loop rather than learning the table.

</More>

## Bringing a vanished object back

The core chapter said that when a guard fails, the frame state describes
the removed object by its fields and the deoptimiser builds it then; V8's
post on concurrent marking lists "materialization during deoptimization
of a function" among the operations that create objects<Cite id="v8-concurrent-marking" />.
`--trace-deopt-verbose` shows it happening. Take the `len2` loop, add a
second name for the object and a line that only runs on a later call, so
that its first run deoptimises:

```js
function run(k) {
  let t = 0;
  for (let i = 0; i < n; i++) {
    const p = { x: xs[i], y: ys[i] };
    const q = p;
    t += len2(q);
    if (k === 1 && i === 5)
      t += (p === q ? 1 : 0)
        + p.x.toFixed(1).length;
  }
  return t;
}
```

After 30 calls with `k = 0`, TurboFan has compiled `run` with `p` removed
and nothing compiled for the `k === 1` branch; the call with `k = 1`
fails a guard there ("Insufficient type feedback for compare operation"),
and the trace shows the interpreter's frame being rebuilt:

<Callout kind="definition">
In a deoptimisation trace, a **captured object** is an object that the
optimised code never allocated, described in the frame state by its map
and its field values so that the deoptimiser can allocate it;
TurboFan writes these descriptions as `ObjectState`s for every
non-escaping virtual object still live at the exit<Cite id="v8-src-escape-analysis" />.
A **duplicated object** entry refers back to a captured object already
described, so that one object reached through two names is rebuilt
once, with its identity intact.
</Callout>

Two details are worth keeping. The fields came back as HeapNumbers made
from raw doubles in `xmm` registers: in the optimised loop, `x` and `y`
never existed as heap values at all, only as two numbers in registers,
which is scalar replacement seen from the other side. And the
"duplicated object" line is what makes the rebuild correct rather than
merely plausible: `p === q` must still be `true` in the interpreter, so
the deoptimiser writes the address of one new object into both slots.

## What you learned

- In V8 12.4, objects read by fixed field names, destructured objects
  and inlined class instances vanish; array literals mostly do, and
  `for...of` over one does not.
- A computed field name, two allocations meeting at a phi, a callee over
  the inlining budget (460 bytes of bytecode by default) and a closure
  per iteration all keep every object real.
- When a guard fails, the frame state describes each removed object as a
  **captured object** (its map and field values); a **duplicated
  object** entry keeps one object rebuilt once, so identity survives.
