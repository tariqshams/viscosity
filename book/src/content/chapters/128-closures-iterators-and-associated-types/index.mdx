## Arrow functions, with bars

Summing the positions of the live particles, in TypeScript and in Rust:

```ts
ps.filter((p) => p.alive)
  .map((p) => p.x)
  .reduce((a, b) => a + b, 0);
```

```rust
ps.iter()
    .filter(|p| p.alive)
    .map(|p| p.x)
    .sum::<f64>()
```

They read almost the same, but the TypeScript chain builds two whole
arrays on the way and the Rust one builds none. And `|p| p.alive` is a
**closure**, Rust's arrow function,
with its parameters between bars, which has to follow the ownership
rules like everything else, because there is no collector to keep a
captured variable alive.

<Analogy title="packing a lunchbox">
A TypeScript closure is like being allowed back into the kitchen
whenever you are hungry: the whole kitchen stays open for you. A Rust
closure packs a lunchbox instead. It takes exactly the things its body
needs, and for each one it packs either a note saying where to find it
(a borrow) or the thing itself (a move), then leaves with the box.
<span slot="breaks">A lunchbox is packed when you leave; a closure's
box is filled when the closure is created, but a borrowed item is still
the original, so changes to it show up on both sides.</span>
</Analogy>

The Rust Reference says it plainly: a closure is a value of a unique,
unnamed type, "approximately equivalent to a struct which contains the
captured values"<Cite id="rustref-closure-types" />. For each variable
it uses, it takes a shared borrow if it only reads, a mutable borrow if
it changes it, and a move if it gives the value
away<Cite id="rust-book-closures" />:

<CaptureSteps client:visible />

<Examples of="rust-closure">

```rust
let mut count = 0;
let mut tick = || count += 1;
tick();
tick(); // count is now 2
let mut c = make_counter();
c(); c(); // 1, then 2
```

</Examples>

`tick` changes `count`, so it holds a mutable borrow of it; and calling
it changes the closure, so the binding needs `let mut` (without it,
rustc 1.97 says E0596, "calling `tick` requires mutable binding due to
mutable borrow of `count`"). `make_counter` is the counter of *Closures: functions
that remember*: it ends with `move || { n += 1; n }`, where `move` puts
`n` inside the closure value. Without `move` the closure would borrow a
local that dies when `make_counter` returns, and rustc says E0373,
"closure may outlive the current function". Its return type is
`impl FnMut() -> u32`, "some closure type callable like this", because
a closure's own type has no name you can write.

<Figure takeaway="Every Fn is an FnMut, and every FnMut is an FnOnce." caption="The traits nest. A closure that only reads can be used where any of the three is wanted; one that moves a capture out can only be called once.">
  <FnLadder />
</Figure>

<Callout kind="definition">
A **closure** is an anonymous function written `|params| body` that
can capture variables from where it is written, each by shared borrow,
mutable borrow or move, whichever the body needs (**`move`** forces
moves). Each closure has its own type, and implements the **Fn traits**
its body allows: **`Fn`** if it only reads its captures, **`FnMut`** if
it changes them, and **`FnOnce`** always (one that moves a capture out
is only `FnOnce`). Ordinary functions implement all
three<Cite id="klabnik2026" />.
</Callout>

<Prompts ids={['clo-capture', 'clo-move', 'fn-traits']} />

<More title="Closures as parameters, in drip-rs">
A function that takes a closure picks the weakest bound it can live
with. drip-rs's hash table has `retain_keys(&mut self, mut keep: impl
FnMut(StrRef) -> bool)`, which calls `keep` once per key, and its
collector passes `|s| marks.strings[s.handle.index()]`, which only
reads `marks`. Because each closure has its own type, such a parameter
is generic in disguise, so monomorphization makes a copy per closure
and the call can be inlined.
</More>

## Iterators: one method, pulled lazily

An **iterator** is any value with a `next` method that hands out items
one at a time, the iterator protocol of *Iterators and generators* with
`Option` standing in for `{ value, done }`:

```rust
trait Iterator {
    type Item;
    fn next(&mut self)
        -> Option<Self::Item>;
}
```

`next` returns `Some(item)` or, at the end, `None`, and takes
`&mut self` because handing out an item moves the iterator on. Every
other iterator method is built on it<Cite id="rust-std-iter" />, and a
`for` loop calls `into_iter` on what you give it and then `next` until
`None`.

Methods that wrap one iterator in another, such as `map`, `filter`,
`zip`, `enumerate` and `take`, are **adapters**; methods that pull
until the end, such as `sum`, `count`, `fold` and `collect` (which
builds a `Vec` or a `HashMap`), are **consumers**. The difference from
JavaScript is that adapters are **lazy**: calling one only builds a
small struct around the iterator, and work starts when a consumer calls
`next`, after which each item travels the whole chain before the next
one starts<Cite id="rust-book-iterators" />:

<LazySteps client:visible />

<Examples of="rust-iterator">

```rust
let xs = [1, 2, 3, 4];
let total: i32 = xs.iter()
    .filter(|x| *x % 2 == 0)
    .map(|x| x * 10)
    .sum(); // 60
```

</Examples>

`xs.iter()` hands out `&i32`s. `filter` keeps the even ones (its
closure gets a `&&i32`, and `*x` peels off one layer); `map` multiplies
by ten; `sum` pulls each item through and adds 20 and 40, so `total` is
`60`, and no array of `[2, 4]` or `[20, 40]` ever exists. Forget the
consumer and nothing happens at all: rustc warns "unused `Map` that
must be used", because "iterators are lazy and do nothing unless
consumed". Since each adapter is a small struct with a known closure,
the chain compiles to about the same code as a hand-written loop.

## A blank each type fills in once

`type Item;` in that trait is a blank. The trait does not know what a
particular iterator yields, so it names the answer `Self::Item` and
lets each impl fill it in:

<Examples of="associated-type">

```rust
struct Countdown(u32);
impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 { return None; }
        self.0 -= 1;
        Some(self.0 + 1)
    }
}
```

</Examples>

`type Item = u32;` fills the blank for this one type, so `next` may
say `Option<u32>`. The body ends at zero with `None`; otherwise it
steps down and hands out the number it was holding, so `Countdown(3)`
yields 3, 2, 1. From then on rustc knows that a `Countdown` yields
`u32`s, and every adapter works on it with no annotation:
`Countdown(3).sum::<u32>()` is `6`. Why not `trait Iterator<T>`, the
way TypeScript writes `Iterator<T>`? Step through the difference:

<ItemSteps client:visible />

<Callout kind="definition">
An **associated type** is a type declared inside a trait (`type Item;`)
that each implementation sets (`type Item = u32;`). Inside the trait it
is `Self::Item`; from outside, `<T as Iterator>::Item`, or `T::Item`;
and a bound can pin it: `I: Iterator<Item = u32>`. Because a type
implements a trait at most once, it has exactly one value for each
associated type, so the type follows from the implementing type
alone<Cite id="rust-book-advanced-traits" />.
</Callout>

The `type Output` of an `Add` impl is one too, and so is the
`type Extra` of engine/rust's `LanguagePlugin`, each plugin's private
data.

## The standard traits

`Iterator` is one of a handful of traits that the language and its
library are built around. Implement one for your type, and a feature
starts working:

<Figure takeaway="Implement the trait, and the language feature starts working for your type." caption="The standard traits used most, what each one unlocks, and whether #[derive] can write it.">
  <StdTraitMap />
</Figure>

<Callout kind="definition">
The **standard traits** are the traits in `std` that the language and
library lean on: `Display` (`{}` and `to_string`) and `Debug`
(`{:?}`)<Cite id="rust-std-fmt" />, `Default` (a starting value),
`Clone` and `Copy`, `PartialEq` and `PartialOrd` (`==`, `<`), `Hash`
(keys of a `HashMap`), `From` and `Into` (conversions, which `?` uses)
and `Iterator` and `IntoIterator` (`for` loops and adapters).
</Callout>

<Examples of="std-traits">

```rust
impl fmt::Display for Pt {
    fn fmt(&self, f: &mut fmt::Formatter)
        -> fmt::Result {
        write!(f, "({}, {})",
            self.x, self.y)
    }
}
```

</Examples>

`Display` has one method, `fmt`, which writes into a `Formatter` (the
`write!` macro works like `format!`, into `f`); with it,
`println!("{p}")` prints `(1, 2)` and `p.to_string()` works. Where
every TypeScript object has a `toString`, Rust gives a type nothing for
free: without the impl, rustc says E0277, "`Pt` doesn't implement
`std::fmt::Display`", and suggests the `{:?}` of a derived `Debug`. The deep dive
*Operator traits, Drop and derive* goes through the rest,
including `Drop`, the trait whose method Rust calls when a value is
dropped; *Errors at scale* puts `From` to work.

## What you learned

- A **closure** is `|params| body`, a value of its own type that
  captures each variable it uses by shared borrow, mutable borrow or
  move; `move` forces moves, which a returned closure needs. **`Fn`**
  reads, **`FnMut`** changes, **`FnOnce`** may be called once.
- An **iterator** has one required method, `next(&mut self) ->
  Option<Item>`; adapters such as `map` and `filter` are lazy, and a
  consumer such as `sum` or `collect` pulls each item through every
  stage, with no arrays in between.
- An **associated type** is a blank in a trait that each impl fills
  once, which is why `Iterator` uses one.
- The **standard traits** are how a type joins in with `println!`,
  `==`, `for` and `?`.
