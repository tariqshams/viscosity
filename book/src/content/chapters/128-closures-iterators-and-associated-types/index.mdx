## Arrow functions, with bars

In *Other ways to loop: map, filter, reduce and while* you passed small
functions to array methods, `xs.filter((p) => p.alive)`, and in
*Closures: functions that remember* you saw that such a function can
use variables from the place it was written. Rust has the same tool,
with a different spelling:

```rust
let limit = 2.0;
let fast = |vx: f64| vx > limit;
println!("{}", fast(3.5)); // true
```

`|vx: f64| vx > limit` is a **closure**: the parameters go between two
bars instead of brackets, and the body follows, here a single
expression (for several statements, use a `{ }` block whose last line
is the value). It *uses* `limit`, a variable from outside. Calling it
looks like calling any function.

How does a closure hold on to `limit`? In TypeScript the engine keeps
the whole surrounding environment alive for the closure (the
*captured environment* of *Closures in Drip*), and the garbage
collector sorts out the rest. Rust has no collector, so a closure must
follow the ownership rules like everything else: for each variable it
uses, it either **borrows** it or **moves** it in.

<Analogy title="packing a lunchbox">
A TypeScript closure is like being allowed back into the kitchen
whenever you are hungry: the whole kitchen stays open for you. A Rust
closure packs a lunchbox instead. It takes exactly the things its body
needs, and for each one it packs either a note saying where to find it
(a borrow) or the thing itself (a move), then leaves with the box.
<span slot="breaks">A lunchbox is packed when you leave; a closure's
"box" is filled when the closure is created, but a borrowed item is
still the original, so changes to it show up on both sides.</span>
</Analogy>

That lunchbox is real. The Rust Reference describes a closure as a
value of a unique, unnamed type, "approximately equivalent to a struct
which contains the captured values"<Cite id="rustref-closure-types" />.
So `fast` is roughly `struct Fast<'a> { limit: &'a f64 }` with a call
method, which is exactly the *closure conversion* of *Closure conversion
and lambda lifting*, done for you by the compiler.

## Borrow, mutably borrow, or move

A closure borrows each variable only as strongly as its body needs: a
shared borrow if it only reads, a mutable borrow if it changes the
variable, and a move if it gives the value away<Cite id="rust-book-closures" />.
Step through a counter, first borrowing and then with `move`:

<CaptureSteps client:visible />

<Analogy extra title="a library book, a shared notebook, a gift">
Lending someone a library book to read is a shared borrow: you both
know where it is and nobody writes in it. Lending them the shared
notebook to write in is a mutable borrow: nobody else may touch it
until they hand it back. Giving them the book to keep is a move.
<span slot="breaks">With `move` on a number, the closure gets a copy and
you keep the original, which no gift does; that is because small
values like `i32` are `Copy`, as *Ownership* explained.</span>
</Analogy>

<Callout kind="definition">
A **closure** in Rust is an anonymous function written
`|params| body` that can **capture** variables from where it is
written. Each closure has its own unique type, roughly a struct of its
captures. By default each capture is a shared borrow, a mutable borrow
or a move, whichever the body needs; writing **`move`** before the bars
makes every capture a move<Cite id="rust-book-closures" />.
</Callout>

<Examples of="rust-closure">

```rust
let add = |a, b| a + b;
println!("{}", add(2, 3)); // 5
```

```rust
let mut count = 0;
let mut tick = || count += 1;
tick();
tick(); // count is now 2
```

```rust
// drip-rs's collector (gc.rs):
self.interned.retain_keys(|s| {
    marks.strings[s.handle.index()]
});
```

</Examples>

The first captures nothing: the types of `a` and `b` are inferred from
the call, so `add(2, 3)` is `5`. The second changes `count`, so the
closure holds a mutable borrow, and the binding needs `let mut`
(calling it changes something). The third is real: after marking, the
collector of *Reclaiming memory: mark and sweep* removes every interned
string nobody marked. `retain_keys` calls the closure once per key,
`s`, and keeps the key when it returns `true`; the closure only *reads*
`marks`, a variable of the function around it, so it borrows it shared.

Forget the second `mut`, or try to return a borrowing closure, and the
errors say what to add (rustc 1.97, trimmed):

```text
error[E0596]: cannot borrow `tick` as
  mutable, as it is not declared as
  mutable
  calling `tick` requires mutable
  binding due to mutable borrow of `count`
help: consider changing this to be
  mutable: let mut tick
```

```rust
fn make_counter() -> impl FnMut() -> u32 {
    let mut count = 0;
    || { count += 1; count } // E0373
}
```

```text
error[E0373]: closure may outlive the
  current function, but it borrows
  `count`, which is owned by the current
  function
help: to force the closure to take
  ownership of `count` ..., use the
  `move` keyword
```

`impl FnMut() -> u32` means "some closure type that can be called like
this", since a closure's own type has no name you can write. The
closure borrows `count`, a local that dies when `make_counter` returns,
which is *Lifetimes*' dangling reference again; `move || { ... }`
fixes it by putting `count` inside the closure, the compile-time twin
of *Closing upvalues: a fresh variable every pass*.

## Fn, FnMut and FnOnce

What a closure does with its captures decides how often it may be
called, and three standard traits (from *Traits*) name the answer:

<Figure takeaway="Every Fn is an FnMut, and every FnMut is an FnOnce." caption="The traits nest. A closure that only reads can be used where any of the three is wanted; one that moves a capture out can only be called once.">
  <FnLadder />
</Figure>

- **`FnOnce`**: can be called at least once. A closure that moves a
  captured value *out* (returns it, or drops it) is only this, because
  after one call there is nothing left to give.
- **`FnMut`**: can be called many times, and may change its captures.
- **`Fn`**: can be called many times, and only reads its captures.

Call a closure that gives its capture away twice, and rustc explains
exactly why not:

```rust
let name = String::from("drip");
let take = move || name;
let a = take();
let b = take(); // E0382
```

```text
error[E0382]: use of moved value: `take`
note: closure cannot be invoked more
  than once because it moves the
  variable `name` out of its environment
```

A function that *takes* a closure picks the weakest bound it can live
with. drip-rs's corpus runner takes `select: impl Fn(&str) -> bool` and
only asks it questions; the hash table's `retain_keys` takes
`impl FnMut(StrRef) -> bool`, so callers may pass a closure that counts
as it goes; engine/rust's resolver has
`with_block_scope(..., f: impl FnOnce(...))`, which calls `f` exactly
once, between entering a scope and leaving it. Because each closure has
its own type, such a parameter is generic in disguise, so
monomorphization (from *One copy per type: monomorphization*) makes one copy per
closure and the call can be inlined.

<Callout kind="definition">
The **Fn traits** say how a closure may be called. **`FnOnce`** takes
the closure by value and may be called once; **`FnMut`** needs mutable
access and may be called repeatedly; **`Fn`** needs only shared access.
The compiler implements each one the body allows; ordinary functions
implement all three, so a function's name can be passed wherever a
closure is wanted<Cite id="klabnik2026" />.
</Callout>

<Formal title="The traits nest">

```text
Fn ⊂ FnMut ⊂ FnOnce
c : Fn     ⟹  c : FnMut  ⟹  c : FnOnce
```

<span slot="read">The set of Fn closures is inside the set of FnMut
closures, which is inside the set of FnOnce closures. Read the second
line as: if closure c is Fn, then it is also FnMut, and therefore also
FnOnce. So a parameter bounded by FnOnce accepts any closure at all,
and one bounded by Fn accepts the fewest.</span>
</Formal>

<OtherLanguages title="A counter that remembers">

```rust
fn make_counter()
    -> impl FnMut() -> u32 {
    let mut n = 0;
    move || { n += 1; n }
}
let mut c = make_counter();
c(); c(); // 1, then 2
```

```ts
function makeCounter(): () => number {
  let n = 0;
  return () => ++n;
}
const c = makeCounter();
c(); c(); // 1, then 2
```

</OtherLanguages>

They behave the same, but the machinery differs. TypeScript keeps `n`
alive in a captured environment for as long as `c` exists, and any
function may change it; Rust makes you say `move` (so `n` lives inside
the closure value), `let mut c` (calling it changes it) and `FnMut`
(the caller may call it many times).

## What you learned

- A **closure** is `|params| body`. It captures each variable it uses
  by shared borrow, mutable borrow or move, as weakly as the body

## The same chain, a different machine

With the array methods of *Other ways to loop: map, filter, reduce and
while*, summing the positions of the live particles looks like this:

```js
const total = ps
  .filter((p) => p.alive)
  .map((p) => p.x)
  .reduce((a, b) => a + b, 0);
```

`filter` builds a whole new array, `map` builds another, and `reduce`
walks the second one. Here is the same thing in Rust, with the closures
of the last chapter:

```rust
let total: f64 = ps
    .iter()
    .filter(|p| p.alive)
    .map(|p| p.x)
    .sum();
```

It reads almost the same, but it builds no arrays at all. That is the
work of **iterators**, and this chapter is about how they do it.

<Analogy title="a ticket dispenser">
At a deli counter you pull a numbered ticket from a dispenser: one per
pull, in order, until the roll runs out. Nobody prints the whole roll
in advance and hands it to you; each pull produces one ticket. An
iterator is the dispenser, `next` is the pull, and an empty roll is
`None`.
<span slot="breaks">A dispenser's roll exists before anyone pulls; an
iterator over `0..1_000_000` makes each number only when asked, and an
adapter like `map` does not even look at the roll until someone pulls
from it.</span>
</Analogy>

## One method: next

An iterator is any value with a `next` method that hands out items one
at a time until it runs out. Its trait is tiny (trimmed from the
standard library):

```rust
trait Iterator {
    type Item;
    fn next(&mut self)
        -> Option<Self::Item>;
}
```

`Item` is the type it yields (an *associated type*: each iterator
picks it, as you will see in more depth later), and `next` returns
`Some(item)` or, at the end, `None`. It takes `&mut self` because
handing out an item moves the iterator on. Every other iterator method,
dozens of them, is built on `next`<Cite id="rust-std-iter" />. This is
the iterator protocol of *Iterators and generators*, with `Option`
standing in for `{ value, done }`.

```rust
let v = vec![10, 20, 30];
let mut it = v.iter();
it.next(); // Some(&10)
it.next(); // Some(&20)
it.next(); // Some(&30)
it.next(); // None
```

`v.iter()` makes an iterator that *borrows* `v` and hands out
references, `&10` and so on; it must be `let mut it`, because each
`next` changes where it is. Run it and the four lines print exactly as
the comments say (`Some(10)` shows without the `&`, since printing a
reference prints what it points at).

## What for really does

You have used `for` since *Vec and HashMap* without seeing inside it.
It is a shorthand for this trait, and the Rust Reference spells out the expansion<Cite id="rustref-loop-expr" />:

<Formal title="A for loop, unfolded">

```text
for p in e { body }
  ≡
let mut it = IntoIterator::into_iter(e);
loop {
    match it.next() {
        Some(p) => { body }
        None => break,
    }
}
```

<span slot="read">A for loop over e is the same as: turn e into an
iterator with into_iter, then loop forever asking it for the next item;
if there is one, bind it to the pattern p and run the body; if there is
none, stop. (The symbol ≡ reads "means exactly the same as".)</span>
</Formal>

`into_iter` is where the three forms of `for` differ, because each
type decides what it hands out:

```rust
for x in &v { }     // x: &T, like v.iter()
for x in &mut v { } // x: &mut T
for x in v { }      // x: T, and v is gone
```

The last one *consumes* `v`: its `into_iter` takes `v` by value, which
is *Ownership*'s move, applied to a loop. Use `v` afterwards and rustc
1.97 says so, and suggests the fix:

```text
error[E0382]: borrow of moved value: `v`
3 | for x in v {
  |          - `v` moved due to this
  |            implicit call to
  |            `.into_iter()`
help: consider iterating over a slice
  of the `Vec<i32>`'s content to avoid
  moving into the `for` loop: &v
```

## Adapters, and laziness

Methods that take an iterator and return a new one are **adapters**.
Most of JavaScript's array methods have one, called on `xs.iter()`:

```text
JavaScript          Rust, on xs.iter()
xs.map(f)           .map(f)
xs.filter(f)        .filter(f)
xs.reduce(f, a)     .fold(a, f)
xs.find(f)          .find(f)
xs.some(f)          .any(f)
xs.every(f)         .all(f)
xs.entries()        .enumerate()
```

Rust adds some that JavaScript lacks, such as `.zip(ys)`, which walks
two sequences side by side, and `.take(n)`. Methods that pull items
until the end are **consumers**: `sum`, `count`, `fold`, `for_each`,
and `collect`, which builds a `Vec` (or a `HashMap`) from whatever comes
out, with the type written on the `let`.

The big difference is **laziness**. An adapter does nothing when you
call it; it only wraps the iterator in a new struct (a `Filter`, a
`Map`). Work starts when a consumer at the end calls `next`, and then
each item travels the whole chain before the next one
starts<Cite id="rust-book-iterators" />:

<Figure takeaway="JavaScript fills an array per stage; Rust nests small iterator structs and pulls one item at a time." caption="The same chain in both languages. Rust's Map holds a Filter, which holds the slice iterator; sum pulls items through all three.">
  <ChainShapes />
</Figure>

<LazySteps client:visible />

<Analogy extra title="an assembly line versus batch cooking">
Batch cooking is JavaScript's chain: chop *all* the onions into one
bowl, then fry the whole bowl, then plate everything. An assembly line
is Rust's: one item goes from station to station to the end before the
next one enters, so no bowl of half-done items ever exists.
<span slot="breaks">A real line keeps every station busy at once; an
iterator chain runs on one thread, one station at a time, and the
"line" only moves when the last station asks.</span>
</Analogy>

Forget the consumer and nothing happens at all. rustc warns
`unused Map that must be used`, with the note "iterators are lazy and
do nothing unless consumed"; and if you write `let ys: Vec<f64> =
xs.iter().map(...)`, the E0308 type error's help line says "consider
using `.collect()`".

<Callout kind="definition">
An **iterator** is a value whose type implements the `Iterator` trait:
an `Item` type and `fn next(&mut self) -> Option<Self::Item>`.
**Adapters** (`map`, `filter`, `zip`, `take`, ...) wrap an iterator in
another, lazily; **consumers** (`sum`, `count`, `collect`, `for`) call
`next` until `None`. Because each adapter is a small struct and its
closure is known, the chain compiles to about the same code as a
hand-written loop<Cite id="klabnik2026" />.
</Callout>

<Examples of="rust-iterator">

```rust
let n = (1..=10).filter(|x| x % 3 == 0)
    .count(); // 3: 3, 6 and 9
```

```rust
let names = ["a", "b"];
for (i, s) in names.iter().enumerate() {
    println!("{i}: {s}"); // 0: a, 1: b
}
```

```rust
// drip-rs's hash table (table.rs)
pub fn iter(&self) -> impl Iterator<
    Item = (StrRef, Value)> + '_ {
    self.keys.iter()
        .zip(&self.values)
        .filter_map(|(key, value)| {
            key.map(|k| (k, *value))
        })
}
```

</Examples>

The first counts the multiples of 3 from 1 to 10 (`1..=10` is itself
an iterator, including 10) without storing any of them. The second is
JavaScript's `entries()`: `enumerate` pairs each item with its index,
and the `for` pattern `(i, s)` unpacks the pair. The third is real. The
table of *Finding things fast: hash tables* stores its keys and values
as two columns, struct-of-arrays style; `zip` walks slot *i* of both
columns together, and `filter_map` (a filter and a map in one) skips
empty slots, whose key is `None`, while unpacking the full ones. The
`+ '_` says the returned iterator borrows the table (*Lifetime
annotations*). The collector traces a table with
`for (key, value) in self.iter()`, and `grow` re-inserts every entry
the same way.

```rust
let xs = [1, 2, 3, 4];
let total: i32 = xs.iter()
    .filter(|x| *x % 2 == 0)
```

```ts
const xs = [1, 2, 3, 4];

  .filter((x) => x % 2 === 0)
  .map((x) => x * 2)
```

Same answer, different work: TypeScript's version builds `[2, 4]` and

lazy is the default. Notice also `*x` in the filter: `iter()` hands out
`&i32`, and `filter` passes its closure a reference to *that*, a
`&&i32`; `*x` peels off one layer, and Rust's arithmetic accepts the
`&i32` that is left.

## What you learned

- An **iterator** has one required method,
  `next(&mut self) -> Option<Item>`; everything else is built on it.
- `for` calls `into_iter` and then `next` until `None`: `&v`, `&mut v`

  between.

## A blank each type fills in once

*Iterators and closures in Rust* wrote them; here is the trait they implement, as the
standard library declares it (minus its many provided methods):

```rust
trait Iterator {
    type Item;
    fn next(&mut self)
        -> Option<Self::Item>;
}
```

`type Item;` is a blank. The trait does not know what a particular
iterator yields, so it names the answer `Self::Item` and lets each impl
fill it in:

```rust
struct Countdown(u32);
impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 { return None; }
        self.0 -= 1;
        Some(self.0 + 1)
    }
}
```

`type Item = u32;` fills the blank for this one type, and `next` can
then say `Option<u32>` (writing `Option<Self::Item>` would mean the
same). The body ends the countdown with `None` at zero; otherwise it
steps down by one and hands out the number it was holding, so a
`Countdown(3)` yields 3, 2, 1. From then on rustc knows that a
`Countdown` yields `u32`s: `for x in Countdown(3)` makes `x` a `u32`,
and `Countdown(3).sum::<u32>()` is 6, with no annotation anywhere else.

<Analogy title="a franchise agreement">
A coffee chain's agreement says every shop must serve "a house blend",
without saying which; each shop picks its own and prints it on the menu.
The agreement names the blank; the shop fills it once.
<span slot="breaks">A shop can change its blend next year. An `impl`
chooses its `Item` once, when the program is compiled, and every use of
that type sees the same answer.</span>
</Analogy>

<Analogy extra title="a country's power sockets">
Know the country and you know its voltage: 230 volts in France, 120 in
Canada. Nobody asks "which voltage of France?". An associated type works
the same way: know the type, and you know its `Item`.
<span slot="breaks">Some countries have two voltages in different
buildings; a type can implement a trait only once, so it has exactly
one `Item` for it.</span>
</Analogy>

Why not write `trait Iterator<T>` instead, the way TypeScript writes
`Iterator<T>`? Step through the difference:

<ItemSteps client:visible />

With a generic parameter a type may implement the trait many times
(`Iterator<u32>` *and* `Iterator<String>` for `Countdown`), and every
call to `next` would have to say which; with an associated type there is
one impl per type, so the item type follows from the type
alone<Cite id="rust-book-advanced-traits" />. Ask for the generic form
and rustc says so:

```text
error[E0107]: trait takes 0 generic
  arguments but 1 generic argument was
  supplied
2 | impl Iterator<u32> for Countdown {
  |      ^^^^^^^^ expected 0 generic
  |               arguments
```

Forget the blank, and the message names it:

```text
error[E0046]: not all trait items
  implemented, missing: `Item`
  = help: implement the missing item:
    `type Item = /* Type */;`
```

<Callout kind="definition">
An **associated type** is a type declared inside a trait (`type Item;`)
that each implementation sets (`type Item = u32;`). Inside the trait it
is written `Self::Item`; from outside, `<T as Iterator>::Item`, or
`T::Item` when it is unambiguous. A bound can pin it:
`I: Iterator<Item = u32>`. Because a type implements a trait at most
once, it has exactly one value for each associated type.
</Callout>

<Formal title="Projecting an associated type">

```text
impl Iterator for C { type Item = U; … }
────────────────────────────────────────
      <C as Iterator>::Item = U
```

<span slot="read">If there is an impl of Iterator for C that sets Item
to U, then the projection "C's Item, as an Iterator" equals U.
Since at most one such impl exists, the projection behaves
like a function from types to types: one C in, one U out.</span>
</Formal>

<Examples of="associated-type">

```rust
fn total<I: Iterator<Item = u32>>(
    it: I,
```

## The standard traits

Some traits are so common that the whole language leans on them. Each
one, implemented for your type, unlocks something:

<Figure takeaway="Implement the trait, and the language feature starts working for your type." caption="The standard traits used most, what each one unlocks, and whether #[derive] can write it (the next chapter covers derive).">
  <StdTraitMap />
</Figure>

<Callout kind="definition">
The **standard traits** are the traits in `std` that the language and
library are built around: `Display` (`{}` and `to_string`), `Debug`
(`{:?}`, and the messages of `assert_eq!`)<Cite id="rust-std-fmt" />,
`Default` (a sensible starting value)<Cite id="rust-std-default" />,
`Clone` and `Copy`, `PartialEq` and `PartialOrd` (`==`, `<`), `Hash`
(keys of a `HashMap`), `From`/`Into` (conversions, used by
`?`)<Cite id="rust-std-from" /> and `Iterator`/`IntoIterator` (`for`
loops and adapters)<Cite id="rust-std-iter" />.
</Callout>

<Examples of="std-traits">

```rust
// engine/rust/crates/core/src/plugin.rs
impl fmt::Display for CompileError {
    fn fmt(&self,
        f: &mut fmt::Formatter<'_>)
        -> fmt::Result {
        f.write_str(&self.0)
    }
}
```

```rust
// engine/rust/crates/core/src/lib.rs
impl Default for CompileOptions {
    fn default() -> Self {
        let d = PlanOptions::default();
        CompileOptions { mode: d.mode, … }
    }
}
```

```rust
// engine/rust/crates/cli/src/main.rs
impl From<String> for CliError {
    fn from(e: String) -> Self {
        CliError::Other(e)
    }
}
```

</Examples>

All three are Viscosity's Rust engine. `Display` is what makes
`println!("{e}")` print a compile error as plain text; it gets one
method, `fmt`, which writes into a `Formatter`. `Default` gives
`CompileOptions::default()`, so callers can write
`CompileOptions { mode: Mode::OptIn, ..Default::default() }` and keep
every other option as it was. And `From<String>` lets `?`
turn a `String` error into a `CliError` as it returns, and gives you
`.into()` for free, because `std` implements `Into` for every `From`.

Leave one out and the error tells you which:

```text
error[E0277]: `Pt` doesn't implement
  `std::fmt::Display`
  = note: in format strings you may be able
    to use `{:?}` (or {:#?} for
    pretty-print) instead
```

*Ownership*'s `Noisy` example printed a line as each value was
dropped; that line came from an impl of **`Drop`**, whose one method, `drop(&mut
self)`, Rust calls for you at that moment, just before the memory is
freed<Cite id="rust-reference-destructors" />. You never call it
yourself: `b.drop()` is error E0040, "explicit use of destructor
method", because Rust would then drop `b` a second time at the end of
the scope. To drop a value early, pass it to `std::mem::drop` (in the
prelude, so plain `drop(b)`), which takes ownership and lets the value
go<Cite id="klabnik2026" />:

```rust
struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}
let _a = Guard("a");
let b = Guard("b");
drop(b);
println!("end of main");
```

Inside `main` it printed `drop b`, `end of main`, then `drop a` (rustc
1.97): `b` went when it was passed to `drop`, and `_a` at the closing
brace.

## What you learned

- An **associated type** is a blank in a trait (`type Item;`) that each
  impl fills once; it is reached as `Self::Item` or
  `<T as Iterator>::Item`, and pinned in bounds as `Iterator<Item = u32>`.
- A generic parameter allows many impls per type; an associated type
  allows one, which is why `Iterator` uses it.
- The **standard traits** (`Display`, `Debug`, `Default`, `Clone`,
  `PartialEq`, `From`, `Iterator`, ...) are how a type joins in with
  `println!`, `?`, `for` and `==`; **`Drop`** runs your code when a
  value is dropped, and `drop(x)` drops it early.
