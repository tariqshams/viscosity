## Two classes that look the same

```ts
class P {
  x: number;
  constructor(x: number) { this.x = x; }
}
class K {
  declare x: number;
  constructor(x: number) { this.x = x; }
}
```

The two classes differ by one word, `declare`; yet in this book's
benchmark, moving particles made from `P` was several times slower than
moving particles made from `K`. Explaining that takes three things:
how V8 stores a number, what an object looks like in memory, and how V8
decides to store each field.

## Every number is a double

The language says every number is a 64-bit floating-point value in the
**IEEE 754** double format<Cite id="mdn-number" />, the `float64` of
*Floats and typed arrays: numbers as bytes*; C, Java and Python doubles
use it too.

<Figure takeaway="A double is a sign, an exponent and a fraction." caption="The number 1.5 in IEEE 754 form. The sign bit is 0 (positive). The exponent bits say 1023, which means 2 to the power 0. The fraction holds the digits after an implied leading 1: binary 1.1, which is 1.5.">
  <Float64Bits />
</Figure>

<Callout kind="definition">
**IEEE 754** is the standard format for floating-point numbers. Its
**double** uses 64 bits: one **sign** bit, 11 **exponent** bits (a power
of two, stored with 1023 added) and 52 **fraction** bits (the digits
after an implied leading 1, also called the *mantissa*). Whole numbers
are exact up to 2<sup>53</sup> − 1<Cite id="mdn-number" />.
</Callout>

<Examples of="ieee754">

```js
Object.is(0, -0);  // false: two zeros
1 / -0;            // -Infinity
NaN === NaN;       // false
```

</Examples>

The format has values integers do not: `-0`, a zero with its sign bit
set, which `===` calls equal to `0` but `Object.is` and division tell
apart, and `NaN`, the one value not equal to itself. The language only
fixes how numbers *behave*, however; an engine may store them however it
likes, as long as no program can tell<Cite id="v8-react-cliff" />, and V8
does.

<Formal title="Reading a double">

```text
value = (−1)ˢ × 1.f × 2^(e − 1023)
1.5:  s = 0,  e = 1023,  f = .1 (binary)
```

<span slot="read">The value is plus or minus (by the sign bit), times
"one point f", times two to the power of the stored exponent minus 1023;
for 1.5 the sign is 0, the power is zero, and binary 1.1 is one and a
half.</span>
</Formal>

<Analogy extra title="a form with three boxes">
A form for scientific notation has a box for the sign, a small box for
the power of ten and a long box for the digits; every number fits the
same three boxes.
<span slot="breaks">IEEE 754 works in twos, never writes the leading 1
of the digits, and stores the power with 1023 added.</span>
</Analogy>

## Small integers live in the slot

Counters, indexes and lengths are small whole numbers, and giving each
its own 8-byte box on the heap would waste memory and time. So V8 uses
**pointer tagging**: a slot that would hold an address can hold a small
integer instead, and its lowest bit says which it
is<Cite id="v8-pointer-compression" />.

<TagSteps client:visible />

<Callout kind="definition">
In V8, a **Smi** (small integer) is an integer stored directly in a
pointer-sized slot, marked by a lowest bit of 0; any other slot value is
a pointer to a heap object. A **HeapNumber** is a heap object holding one
double, used for numbers that are not Smis, such as `4.2`, `-0`, `NaN` or
integers too big for a Smi. HeapNumbers are immutable, so changing the
value means allocating a new one<Cite id="v8-react-cliff" />.
</Callout>

<Examples of="smi heap-number">

```js
let i = 0;  i = i + 1;  // Smi, in the slot
let t = 4.2;            // HeapNumber
let z = -0;             // HeapNumber
t = t + 1;              // a new HeapNumber
```

</Examples>

A loop counter never touches the heap. `4.2` has a fraction and `-0`
needs its sign bit (an integer has only one zero), so each gets a box and
the variable holds its address; `t + 1` cannot change the box, so it
allocates another and the old one becomes garbage. How big a Smi can be
depends on the build: with **pointer compression** (which Chrome uses to
save memory) slots are 32 bits and a Smi has 31, so `2 ** 30` is already
a HeapNumber, while a 64-bit build without it allows 32-bit
Smis<Cite id="v8-pointer-compression" />.

<More title="Tagging by hand">

<Formal title="Tagging a small integer">

```text
slot = n × 2          (lowest bit 0: a Smi)
n    = slot ÷ 2
−2³⁰ ≤ n ≤ 2³⁰ − 1   (31 bits)
```

<span slot="read">To store n, V8 doubles it, leaving a 0 in the lowest
bit; to read it, it halves the slot. Pointers have their lowest bit set
to 1. With pointer compression, n lies between minus two to the thirty
and two to the thirty minus one.</span>
</Formal>

`tag` shifts 42 left by one, giving 84 with a lowest bit of 0; `isSmi`
checks that bit with `s & 1`; `value` shifts back. The made-up address
`4097` is odd, so it reads as a pointer (real heap addresses are even,
because objects start on aligned boundaries).

<Run id="tag" />

<Analogy extra title="pigeonholes and claim tickets">
A small letter goes straight into your pigeonhole; a parcel goes on a
shelf in the back, and your pigeonhole gets a claim ticket for it.
<span slot="breaks">A HeapNumber is never changed once made, so a new
value means a new parcel and a new ticket.</span>
</Analogy>

</More>

## What an object looks like

An object is a block of memory too. Its first word (one pointer-sized
slot) points to the object's **hidden class**, its shape: which
properties it has and where each sits. Then come pointers to a store for
extra properties and one for indexed elements, and after them the
**in-object properties**, the fastest kind<Cite id="v8-fast-properties" />.

<Figure takeaway="An object is a header, then its fields; numbers that are not Smis live elsewhere." caption="Two objects of the same shape. Each starts with a three-word header; both hidden-class words point to one shared shape that says where x and n live. n is a Smi, stored in its slot; x is a double, so its slot points to a box on the heap.">
  <ObjectLayout />
</Figure>

<Callout kind="definition">
The **object header** is the hidden bookkeeping at the start of every
object; in V8 it is a pointer to the object's hidden class, then
pointers to its properties store and its elements
store<Cite id="v8-fast-properties" />. Objects of the same shape share
one hidden class, but each has its own header.
</Callout>

<Examples of="object-header">

```js
const p = { x: 0, y: 0, vx: 1.5,
  vy: -2, mass: 1, health: 100 };
// 3 header words + 6 field slots
```

</Examples>

Our particle is three header words, six slots, and for each value that
is not a Smi (here `vx`) a pointer somewhere else again; a million
particles carry a million headers, which a struct of arrays does not.

<OtherLanguages>

```js
// JavaScript (V8): header, then slots
const p = { x: 0.5, n: 3 };
```

```python
# CPython: every object, every float,
# starts with a header of its own
p = {"x": 0.5, "n": 3}
```

```java
// a header, then fields stored inline
class P { double x; int n; }
P p = new P();
```

```c
/* no header at all: 8 + 4 bytes of
   data, plus padding */
struct P { double x; int n; };
struct P p = { 0.5, 3 };
```

A C `struct` is the data and nothing else. A Java object has a small
header, with its `double` and `int` fields inline because their types
are declared. In CPython every value has its own header, so even `0.5`
is a boxed object. V8 sits in between.

</OtherLanguages>

## A field remembers what it has held

V8 watches the values stored into each field and picks the cheapest
storage that fits all of them; when a value arrives that does not fit,
the field is widened, and in general it does not go
back<Cite id="v8-react-cliff" />.

<Analogy title="a labelled kitchen drawer">
A drawer labelled "teaspoons" lets you grab one without looking. The day
someone drops a whisk in, the label becomes "spoons and whisks"; after
the first ladle it says "utensils", and now you have to look at whatever
you pull out. Nobody ever writes the narrower label back on.
<span slot="breaks">V8's label is a promise its machine code relies on,
so when a value breaks it, that code is thrown away and rebuilt; and the
label lives in the hidden class, so one odd value changes it for every
object of that shape.</span>
</Analogy>

<Figure takeaway="A field's representation only moves up the ladder." caption="Field representations as a ladder. A field that has held only Smis stays Smi; a fraction widens it to Double; anything that is not a number (undefined, null, an object) is a heap object; a mix of numbers and heap objects widens to Tagged, the most general and, for numbers, the slowest.">
  <RepLadder />
</Figure>

<Callout kind="definition">
A **field representation** is how the engine has decided to store one
field, recorded in the hidden class. V8 has **Smi**, **Double**, **heap
object** and **tagged** (anything at all), and a field moves to a more
general one when it receives a value that does not
fit<Cite id="v8-react-cliff" />. A Double field keeps its value in a box
only its object can see, so V8 updates it in place; a Tagged field keeps
numbers as ordinary immutable HeapNumbers<Cite id="v8-react-cliff" />.
</Callout>

<Examples of="field-representation">

```js
const o = { n: 1 };   // n: Smi
o.n = 1.5;            // widens to Double
o.n = 7;              // stays Double
const t = { start: null };  // heap object
t.start = performance.now(); // Tagged
```

</Examples>

`1.5` does not fit a Smi, so `n` moves up a rung, and `7` does not move
it back. `null` is not a number, so `start` begins as a heap-object
field; then a double arrives, and the only rung above both is Tagged, so
every time stored there from now on is a fresh HeapNumber. The V8 team's
advice is exactly this: do not start numeric fields as
`null`<Cite id="v8-react-cliff" />.

<Formal title="Widening: the smallest rung that fits">

```text
Smi ⊑ Double ⊑ Tagged    HeapObject ⊑ Tagged
rep' = rep ⊔ kind(v)
```

<span slot="read">⊑ is read "is below, or equal to, on the ladder".
Storing a value v changes the representation to rep ⊔ kind(v), "rep
joined with the kind of v": the lowest rung at or above both.</span>
</Formal>

## Back to the two classes

In modern JavaScript, `x;` in a class body is a real **class field**,
added before the constructor's body runs and starting as `undefined`
when it has no value<Cite id="mdn-class-fields" />. TypeScript emits
`x: number;` as exactly that field when the target is ES2022 or
later<Cite id="ts-use-define" />, while `declare x: number;` emits
nothing<Cite id="ts-37-declare" />:

```js
class P {   // what P becomes
  x;        // starts as undefined
  constructor(x) { this.x = x; }
}
class K {   // what K becomes
  constructor(x) { this.x = x; }
}
```

In `P` the first value `x` holds is `undefined`, a heap object, and the
second is a double, so the field jumps to Tagged; in `K` the first value
is a double, so the field is Double.

<FieldSteps client:visible />

Running the benchmark with V8's `--trace-generalization` flag printed
`x:h{Any;const}->t{Any;mutable}` for `P`: field `x` went from `h` (heap
object) to `t` (Tagged). In this book's run, the class with field
declarations was about 3 times slower than the object literal and the
constructor-only class at 100,000 particles, and 5 to 7 times slower at
1,000 and 1,000,000; the other two were about equal, so the cost is not
about classes, only about the field's first value.

<Callout kind="pitfall">
Make a number field's first value a number: use `declare` for fields the
constructor always sets, or assign them only in the constructor, and
never start a numeric field as `null` or `undefined`.
</Callout>

<Callout kind="engine" label="Under the hood">
A `Float64Array` has none of this: raw doubles side by side, with no
tags, boxes, headers or field representations to
widen<Cite id="mdn-typed-arrays" />, and V8's pointer compression post
recommends them for number-crunching code<Cite id="v8-pointer-compression" />.
That is why Viscosity's columns are `Float64Array`s, whatever the source
declared.

## What you learned

- Every number behaves like an **IEEE 754** double, with values such as
  `-0` and `NaN`; V8 stores small integers as **Smis** in the slot and
  other numbers as immutable **HeapNumbers**.
- Every object starts with an **object header**: a hidden-class pointer,
  then its properties and elements stores.
- A **field representation** only widens; a number field that starts as
  `undefined` or `null` ends up Tagged, and every update allocates.
