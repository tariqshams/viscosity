## One data structure

Every analysis from here on asks how a program *runs*: which value flows
into which instruction, which loop reads which field, what could reach a
call. A syntax tree is a poor place to ask, because it is shaped like the
text, so `t = t + v` inside a loop is one node that stands for a
different value on every pass. Viscosity asks its IR, **VIR**, all of
which lives in `packages/core/src/vir.ts`, 176 lines long.

<Analogy title="a customs declaration form">
A customs form does not ask travellers to describe their luggage in
their own words; it has a box for "goods over the allowance" and a box
for "food or plants", because those are what the officers check, so a
traveller from anywhere fills in the same boxes and an officer reads
them at a glance.
<span slot="breaks">A traveller can lie on a form; a VIR instruction is
made by the plugin from the code itself, and when the plugin is unsure,
it writes "unknown" rather than guessing.</span>
</Analogy>

## Modules, functions, blocks

A `Module` holds a list of `Func`s (one per function, plus `<module>`
for the top-level code), a list of `Binding`s, and every instruction by
its id. A `Func` is a control-flow graph, as in *IR, three-address code
and control-flow graphs*: a list of `Block`s and an entry block, where
each block holds instructions, its predecessors, and exactly one
**terminator**:

```ts
type Terminator =
  | { kind: 'br'; target: BlockId }
  | { kind: 'condbr'; cond: ValueId;
      then: BlockId; else: BlockId }
  | { kind: 'return';
      value: ValueId | null }
  | { kind: 'throw'; value: ValueId }
  | { kind: 'unreachable' };
```

`br` always jumps to one block, `condbr` to `then` or `else` depending
on a value, `return` and `throw` leave the function, and `unreachable`
marks a block nothing can reach. An instruction is one record type for
every operation (a tagged union in spirit, as in *Tagged unions: the
shape of every syntax tree*): an `id` (`%7`), an `op` (`'binop'`), its
operands `args` as ids, its block, a few optional fields such as
`operator`, and `src`, the link back to your text (the plugin's syntax
node, its offsets and its line), which emit uses to know what to
replace and explain uses to say "line 4".

## SSA values and bindings

VIR is in SSA form (*SSA and phi nodes, built on the fly*): `let t = 0`
and `t = t + …` make two different values, and at the loop header a
`phi` picks the one that matches the edge control came in by. Step
through a real listing, one source line at a time:

<VirSteps client:visible />

<Callout kind="definition">
**VIR** is Viscosity's intermediate representation. It is
language-neutral: every plugin lowers to it, and every analysis reads
only it. Each function is a **CFG** of basic blocks in **SSA form**:
local variables that no closure captures become values defined once and
joined by `phi`s; other variables become **bindings**, read and written
with explicit `load` and `store` instructions.
</Callout>

<Examples of="vir">

```js
function count(xs) {
  let n = 0;
  let k = 0;
  const bump = () => { n = n + 1; };
  for (const x of xs) {
    bump(); k = k + 1;
  }
  return n + k;
}
// count:  %1 = const 0; store n, %1
//   b1:   %16 = phi %3, %18     ; k
// bump:   %4 = load n; …; store n, %6
```

</Examples>

`k` becomes phis, as always (`%16` takes `%3`, the starting `0`, from
before the loop, and `%18`, `k + 1`, from the back edge). `n`, however,
is changed inside `bump`, and a call to `bump` could happen anywhere; a
phi cannot describe "whatever the closure did", so `n` stays a binding,
and the arrow's body really is `load n`, `binop +`, `store n`. The
JavaScript plugin also makes a binding of any variable that starts out as
an array, so the analyses see every read of a candidate collection as a
`load` they can follow (*Lowering JavaScript to VIR* gives the full
rule).

<More title="More: the phi rule, by hand, and how the builder makes phis">

<Formal title="Single assignment, and the phi rule">

```text
∀ v. v has exactly one definition
B has preds p₁ … pₙ, and in B:
  %v = phi %a₁, …, %aₙ
entering B from pₖ  ⟹  %v = %aₖ
```

<span slot="read">Every value v has exactly one defining instruction. If
block B has n predecessors and starts with a phi whose arguments are in
the same order, then entering B from the k-th predecessor gives the
phi the k-th argument's value.</span>
</Formal>

<Run id="phi-by-hand" />

Plugins do not build SSA by hand: `packages/core/src/builder.ts` gives
them `readVariable` and `writeVariable` and builds SSA on the fly with
Braun and colleagues' algorithm<Cite id="braun2013" />, which is why phi
ids look out of order (a phi is created only when a read first needs
it). A phi is not run like other instructions; the deep dive *Leaving
SSA* turns phis into plain copies.

</More>

## Data operations as instructions

Most of what the layout analyses need comes down to one question:
*which fields of which collection does this code read and write?* On a
low-level IR, where `ps[i].x` has become "load the pointer at `ps` plus
8 times `i`, then the number 16 bytes past that", every analysis would
have to recognise the same patterns again. So most of VIR's operations
are the expected `const`, `binop`, `phi`, `call` and `closure`, and the
unusual ones are about data.

<Callout kind="definition">
VIR's **record and collection nodes** are its first-class data
operations: `record.new` (a record with named fields, in order),
`array.empty`, `array.new` and `push` (building a collection),
`index.get` and `index.set` (its elements), and `field.get` and
`field.set` (a **field access** on a record). Beside them, `intrinsic`
is a known built-in numeric function such as `Math.sqrt`, which returns
a number and keeps no reference to its arguments.
</Callout>

<Examples of="record-collection-nodes">

```text
const o = { x: 1, vx: 2 };
  %2 = record {x, vx} %0, %1
xs.push({ x: 3, vx: 4 });
  %8 = record {x, vx} %6, %7
  %9 = push %5, %8
xs[0].vx = Math.sqrt(o.x * o.x);
  %12 = index.get %10, %11
  %16 = Math.sqrt(%15)
  field.set %12, %16 .vx
```

</Examples>

All three come from one real listing. The object literal becomes one
`record` instruction that names its fields and takes their values;
`push` takes the array (`%5`, loaded from the binding `xs`) and the new
record; and in the last line `xs[0]` is an `index.get`, `Math.sqrt` an
`intrinsic` (printed as a call by name), and the assignment a
`field.set` on that element with the field name written last. A Python
dataclass call lowers to the same `record`, so the analyses never see
which language a record came from:

## Opaque: an honest unknown

JavaScript is enormous (getters, proxies, `with`, tagged templates,
destructuring), so the JavaScript plugin models the subset that matters
for data layout and turns everything else into **opaque**, with every
variable the code mentions as an argument. A template literal on line 4
of the particle program, `` const s = `${ps[0]}`; ``, lowers to
`%15 = index.get %13, %14` and `%16 = opaque(template) %15`, and
`viscosity explain` says `unsafe: line 4: an element is used by code
Viscosity doesn't model (template)`.

Opaque means "might do anything with these arguments": keep them, change
them, hand them on. Every analysis treats it in the worst way, so its
arguments escape (*Escape sites: how Viscosity proves a rewrite safe*)
and its result is unknown. Being unsure can only ever lead to a missed
rewrite, never a wrong one, and because the reason is printed, a missed
one can be fixed by changing the code.

<More title="More: why VIR stays high-level">

Choosing the level of an IR is a classic trade-off: a low-level IR
exposes every load and address for the back end, while a high-level one
keeps the structure analyses want<Cite id="coopertorczon2022" />. VIR
stays at the level of records and elements because its only users are
the layout analyses; it is never run, and no machine code is made from
it. `intrinsic` covers a fixed set of `Math` functions, and only when
`Math` really is the global: a local variable called `Math` could be
anything, so it is lowered as an ordinary call.

</More>
