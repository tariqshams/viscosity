## Getting around costs more than the work

At the end of Part III you counted what the tree-walker does for
`n - 2`: three recursive calls, three `switch`es on the node kind, two
Map lookups and two type checks, all to do one subtraction. The
subtraction was the cheap part. Getting to it was expensive.

None of that bookkeeping changes from one run to the next. The node
for `n - 2` is a subtraction every time `fib` is called. So why work it
out again a million times? Work it out *once*, write the answer down in
a form that is quick to follow, and then just follow it.

## Flatten the tree

<Callout kind="intuition">
A family tree tells you who is related to whom. A recipe tells you what
to do next. You can cook from a family tree of dishes ("the sauce needs
a roux, the roux needs butter…"), but you keep climbing up and down it.
A recipe has already done that climbing for you: step 1, step 2,
step 3.
</Callout>

A tree can be turned into a recipe by visiting each node's children
before the node itself, and writing down one step per node:

<TreeToBytes client:visible />

The steps come out in exactly the order the work has to happen: every
operand is ready before the operator that needs it. Each step is tiny,
and the list is a plain array, so following it means moving to the next
index, not chasing a pointer to another node.

<Callout kind="definition">
**Bytecode** is a program written as a compact, flat list of simple
instructions, stored as numbers in an array. A **compiler** produces it
once, before the program runs. Each instruction does one small thing,
like "push a constant" or "add the top two values".
</Callout>

## Opcodes: instructions as numbers

To store a step as a byte, give each kind of step a number. Drip's VM
has a table of them in `companion/ts/src/vm/chunk.ts`:

```ts
// chunk.ts (excerpt)
export const OP = {
  CONSTANT: 0, NIL: 1, TRUE: 2, FALSE: 3,
  POP: 4,
  // …
  ADD: 18, SUBTRACT: 19, MULTIPLY: 20,
  DIVIDE: 21, NOT: 22, NEGATE: 23,
  PRINT: 24,
  // …
  RETURN: 33,
} as const;
```

There are 37 of them in the finished VM, so one byte (0 to 255) has room
to spare. Some instructions need extra information. "Push a constant"
must say *which* constant, so the byte after it is an **operand**:
`0, 2` means "constant number 2". `ADD` needs nothing more, because it
always works on the two newest values.

<Callout kind="definition">
An **opcode** is the number that says which instruction this is. An
instruction is its opcode followed by zero or more **operand** bytes
that give it details, such as which constant to use. Different
instructions can therefore take different numbers of bytes.
</Callout>

## A machine made of software

Something has to read those bytes and do what they say. It is a loop:
read an opcode, do that instruction, move on, repeat. Here is a whole
one, for three opcodes, with each value stored straight after its
`PUSH` to keep it short:

<Run id="tiny-vm" />

Notice what is missing: no recursion, no `kind` field, no lookups. The
loop keeps its own small stack of values, `st`, and an index, `ip`,
saying where it is in the code. A real CPU works the same way on
machine code, which is why a loop like this is called a *virtual*
machine: it's a pretend processor, built out of software.

<Callout kind="definition">
A **virtual machine** (VM) is a program that executes bytecode. It
repeatedly fetches the next instruction, decodes its opcode, and
performs it, keeping its working values in its own data structures.
The instruction set is designed for the language, not for any real
chip.
</Callout>

## Did it pay off?

The companion code already contains the finished VM, so you can see
where this road leads before you walk it. These are the same benchmark
runs as chapter 107, this time in seconds rather than as a ratio:

<BenchPairs />

The wins are real. The programs the tree-walker found hardest, full of
calls, method lookups and field reads, are where the VM saved the most
time. That's where the tree-walker's overhead piled up.

But read the rest honestly:

- **`zoo_batch`** isn't a race. It loops until ten seconds of clock time
  have passed, then reports how much work it finished, so both engines
  take about ten seconds by design.
- **`string_equality`** has no VM time at all. The compiler gave up:
  this VM's instructions only have room for a one-byte constant
  number, so a chunk holds at most 256 constants. The script only has
  eight variables, but the compiler adds a variable's name as a new
  constant *every time* the name appears, and this script names them
  hundreds of times. Chapter 120 shows where that limit lives.
- **`instantiation` and `equality`** got *slower*. One run on a shared
  machine can't say why. There are suspects, though: every VM object is
  also tracked by the VM's own heap and garbage collector, running on
  top of V8's; and the VM's hash tables are hand-written TypeScript
  where the tree-walker borrows V8's built-in `Map`. Later chapters
  test those suspects.

<Prompts ids={['string-eq-limit', 'slower-lesson']} />

<Callout kind="engine" label="Under the hood">
V8 made this same move for JavaScript. Its interpreter, Ignition, runs
bytecode, and the V8 team reported that the bytecode is between a
quarter and half the size of the machine code their earlier baseline
compiler produced<Cite id="v8-ignition" />. Even a fast interpreter
keeps some cost it can't remove: decoding each instruction and
dispatching to the next one. V8's Sparkplug compiler exists to remove
exactly that<Cite id="v8-sparkplug" />. Drip's VM follows clox, the
bytecode VM from *Crafting Interpreters*<Cite id="nystrom2021" />, so
it can be checked against the same tests.
</Callout>

## What you learned

- **Bytecode** is a program as a flat array of small instructions,
  produced once by a compiler, in the order the work must happen.
- Visiting children before parents turns an expression tree into that
  order.
- An **opcode** is the number naming an instruction; **operands** are
  the extra bytes some instructions need.
- A **virtual machine** is a loop that fetches, decodes and performs
  instructions: a pretend CPU for your language.
- The VM beat the tree-walker on most programs, lost on two, and
  couldn't compile one. A better design is not faster at everything.
