## A multiply on every trip

Two chapters ago we met this loop, which reads every other element of
`a` starting at index 1:

```js
for (let i = 0; i < n; i++) {
  const j = 2 * i + 1;
  s += a[j];
}
```

Every trip multiplies `i` by 2 and adds 1, although we know (from the
induction variable chapter) that `j` simply goes 1, 3, 5, 7, climbing
by 2. There is a multiply hidden in almost every array access, too:
chapter 52 showed that element `i` of a `Float64Array` sits `8 × i`
bytes from its start, so the machine works out `start + 8 × i` for every
read. A multiply is never cheaper than an add, and on many processors
it is slower; in a loop that runs millions of times that adds up, so
compilers look for multiplies that could be additions (the name comes
from swapping a "strong" operation for a weaker one).

<Analogy title="saving the same amount every week">
If you put twenty pounds in a jar every Friday, you never work out
"twenty times the number of weeks" to know what is in the jar; you add
twenty to last week's total.
<span slot="breaks">A bank account that earns interest grows by a
different amount each week, and then adding a fixed amount gives the
wrong answer; strength reduction only works when the step really is the
same on every trip.</span>
</Analogy>

<Analogy extra title="planting fence posts">
To put a post every three metres, you do not measure three times the
post number from the corner of the field each time; you walk three
metres on from the post you just planted.
<span slot="breaks">Walking on from the last post lets small errors
pile up (a few centimetres off each time), while measuring from the
corner does not. Computers have exactly this problem with fractions, as
we will see; with whole numbers they do not.</span>
</Analogy>

## Turning the multiply into an add

The induction variables of two chapters ago come in **families**: a derived
variable `j = c × i + d` belongs to the family of the basic variable
`i`, with multiplier `c` and offset `d`, where `c` and `d` do not change
in the loop. Since `i` steps by `s`, `j` steps by `c × s`; so we can
give `j` a phi of its own, start it at `c × i₀ + d` in the preheader,
and add `c × s` to it in the latch. Step through it on our loop:

<SrSteps client:visible />

<Callout kind="definition">
**Strength reduction** replaces an expensive operation in a loop with a
cheaper one that gives the same results, most often a multiply of an
induction variable by an add: for each derived induction variable
`j = c × i + d`, it creates a new phi that starts at `c × i₀ + d`
(computed in the preheader) and grows by `c × s` each trip, and makes
every use of `j` use the new phi instead.
</Callout>

<Formal title="Reducing c × i + d">

```text
i₀ = start,   i ← i + s,   j = c·i + d
⟹  j₀ = c·start + d,   j ← j + c·s
```

<span slot="read">If i starts at start and grows by s each trip, and j
is c times i plus d, then j can start at c times start plus d and grow
by c times s each trip, with no multiply inside the loop (c times s is
loop-invariant, so it is worked out once).</span>
</Formal>

<Figure takeaway="Every member of a family steps by its own fixed amount." caption="The basic variable i and three members of its family, on trips 0 to 4. Each row grows by c × 1 per trip, so each can be kept up to date with one addition.">
  <FamilyFigure />
</Figure>

<Examples of="strength-reduction">

```js
// address of a[i]: start + 8 * i
// becomes p, with p += 8 each trip
```

```js
let j = 1;               // 2 * 0 + 1
for (let i = 0; i < n; i++) {
  s += a[j];
  j += 2;                // 2 * 1
}
```

```js
// heat.js, row by row: y * W + x
let row = W;             // y starts at 1
for (let y = 1; y < W - 1; y++) {
  // ... c[row + x] ...
  row += W;
}
```

</Examples>

The first is the one every compiler does: the byte address of `a[i]`
is a member of `i`'s family with `c = 8`, so it can be a pointer that
moves 8 bytes per trip. LLVM's `loop-reduce` pass is described in
exactly these terms, an array reference whose address is rewritten to
start at its first value and be incremented each trip<Cite id="llvm-passes" />.
The second is our loop by hand: `j` starts at `2 × 0 + 1 = 1` and adds
`2 × 1 = 2` per trip. The third is the grid walk from the `heat`
benchmark: in the outer loop, `y × W` is a family member of `y` with
`c = W` (invariant), so the start of each row can be kept in `row`,
which starts at `1 × W` and adds `W` per row.

Here is the trap the fence posts warned about:

```js
let a = 0;
for (let k = 0; k < 10; k++) a += 0.1;
a;         // 0.9999999999999999
10 * 0.1;  // 1
```

Ten additions of `0.1` round ten times, and the small errors pile up;
the multiply rounds once. With whole numbers there is nothing to round
(a float64 holds every whole number up to 2⁵³ exactly, as the chapter on
floats and typed arrays showed), so
compilers reduce integer induction variables, and leave floating-point
ones alone unless you have allowed them to change your answers.

## Getting rid of the old counter

After strength reduction, our loop uses `i` for only one thing: the
test `i < n`. Everything else reads `j`. But `j = 2 × i + 1`, and since
`2` is positive, `i < n` is true exactly when `2 × i + 1 < 2 × n + 1`,
which is `j < 2n + 1`. So the test can use `j` instead, with the bound
`2n + 1` worked out once in the preheader, and then nothing uses `i` at
all: its phi and its `+ 1` are dead code, which chapter 203's pass
deletes.

<Callout kind="definition">
**Induction variable elimination** removes an induction variable that
is only needed by the loop's own test (and its own update): it rewrites
the test to compare another member of the same family against a
matching bound, computed once before the loop, and then lets dead code
elimination delete the old variable. For `j = c × i + d`, the test
`i < n` becomes `j < c × n + d` when `c > 0`, and `j > c × n + d` when
`c < 0`.
</Callout>

<Examples of="induction-variable-elimination">

```js
const end = 2 * n + 1;   // preheader
for (let j = 1; j < end; j += 2)
  s += a[j];             // no i at all
```

```js
// p = address of a[i], step 8:
// i < n  becomes  p < start + 8 * n
```

```js
// c = -1: j = -i, so i < n means
// j > -n, not j < -n
```

</Examples>

The first is our loop at the end of the process: one variable, one add
per trip, one comparison, and the multiply moved out to the preheader
where it runs once. The second is the classic machine-level form: after
the address of `a[i]` has become a pointer `p`, the loop can stop when
`p` reaches the end of the array, and the counter disappears. The third
is the mistake to watch for: multiplying both sides of `i < n` by a
negative number flips the comparison, so a compiler must know the sign
of `c` before it rewrites the test. LLVM's `indvars` pass does the
related clean-up of rewriting exit tests, and of computing values the
loop leaves behind after the loop rather than inside it<Cite id="llvm-passes" />.

<Callout kind="engine" label="Under the hood">
Viscosity does neither of these things; it keeps your loops exactly as
written. Its bounds proof (two chapters ago) is one reason that is a
good choice: the proof looks for a phi that steps by exactly `+ 1` and
the test `i < ps.length`, and a loop rewritten to step a pointer by 8
would no longer match. Simple counters are easy to reason about, which
is a good reason for any compiler to reduce them only after the
analyses that want them have run.
</Callout>

## What you learned

- **Strength reduction** turns a family member `j = c × i + d` into its
  own phi: start `c × i₀ + d` in the preheader, add `c × s` each trip.
- It is exact for whole numbers; for fractions, repeated adding rounds
  differently from one multiply, so compilers leave those alone.
- **Induction variable elimination** rewrites the exit test to use a
  family member (flipping it if `c` is negative), after which the old
  counter is dead and DCE removes it.
