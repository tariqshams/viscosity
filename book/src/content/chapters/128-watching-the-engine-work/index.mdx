## Make the engine talk

Chapters 117 to 124 described V8's tiers, shapes, elements kinds,
deoptimization and garbage collector. You don't have to take any of it
on trust. V8 has flags that print what it is doing, and Node passes them
through. Every output in this chapter is real, from this book's machine,
trimmed only to fit your phone.

<Callout kind="pitfall" label="These flags are V8's, not yours">
They are defined inside V8 for its own developers, in one file per V8
version<Cite id="v8-flag-definitions" />. They are not part of
JavaScript or of Node's stable interface, and names, output formats and
defaults can change in any release. Everything below was run on
**Node v22.23.4, V8 12.4.254.21**. Addresses (`0x…`) differ on every
run. Run `node --v8-options` to see what your own version offers.
</Callout>

## Bytecode

Ignition is a register machine with an accumulator<Cite id="v8-ignition" />.
Ask for one function's bytecode, using the filter so you don't get
Node's own thousands of functions:

```text
$ node --print-bytecode \
    --print-bytecode-filter=add bc.js
```

For `function add(a, b) { return a + b; }`:

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[generated bytecode for function:
 add (0x… <SharedFunctionInfo add>)]
Bytecode length: 6
Parameter count 3
Register count 0
 @ 0 : 0b 04     Ldar a1
 @ 2 : 3b 03 00  Add a0, [0]
 @ 5 : ae        Return
```

`Ldar a1` loads the second argument into the accumulator. `Add a0, [0]`
adds the first argument to it, and `[0]` is a **feedback slot**: where
this `+` records the types it sees (chapter 122)<Cite id="v8-ignition-handlers" />.
`@ 2` is its offset. Remember it.

## Optimizing, and giving up

This program makes `add` hot with integers, then hands it a double:

```js
function add(a, b) {
  return a + b;
}
for (let i = 0; i < 1e5; i++) add(i, 1);
add(0.5, 1); // a double!
```

```text
$ node --trace-opt --trace-deopt opt.js
```

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[marking … <JSFunction add …> for
 optimization to TURBOFAN, …,
 reason: hot and stable]
[compiling method … add …
 (target TURBOFAN), mode:
 ConcurrencyMode::kConcurrent]
[compiling method … <JSFunction …>
 (target TURBOFAN) OSR, …]
[completed optimizing … add …
 (target TURBOFAN)]
[bailout (kind: deopt-eager, reason:
 Insufficient type feedback for call):
 … <JSFunction (sfi = …)>, …
 bytecode offset 41, …]
[bailout (kind: deopt-eager, reason:
 not a Smi): … <JSFunction add …>,
 … bytecode offset 2, …]
```

`add` is "hot and stable", so TurboFan compiles it, concurrently, on
another thread. The nameless function is the top-level script. Its
loop never returns, so V8 uses on-stack replacement
(OSR)<Cite id="v8-flag-definitions" />: it switches the loop to
optimized code while the loop is still running. You won't see Maglev:
in this Node build, `--v8-options` lists it as off by default.

Then two bailouts. The script's optimized code reaches the call
`add(0.5, 1)`, which had never run, so it had no feedback. And `add`
itself fails its integer check at bytecode offset 2: the `Add` above.

<Callout kind="definition">
**Engine tracing** means running a program with an engine's diagnostic
flags so that the engine reports its own decisions as it makes them.
In V8 these include `--print-bytecode` (Ignition bytecode),
`--trace-opt` (functions marked and compiled by the optimizing tiers),
`--trace-deopt` (every deoptimization, with its kind, reason and
bytecode offset), `--trace-generalization` (hidden-class fields
becoming more general) and `--trace-gc` (one line per garbage
collection)<Cite id="v8-flag-definitions" />. Their output is for
diagnosis, not for parsing in production: it varies between versions.
</Callout>

## Looking inside objects

With `--allow-natives-syntax`, V8 lets your source call some of its
internal runtime functions with a `%` prefix. Without the flag, `%` is a
syntax error. `%DebugPrint` and `%HasFastProperties` are among the
functions V8 lists for testing<Cite id="v8-runtime-h" />:

```js
const p = { x: 1, y: 2 };
console.log(%HasFastProperties(p));
delete p.x;
console.log(%HasFastProperties(p));
%DebugPrint({ x: 1.5, y: 2 });
```

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
true
false
DebugPrint: 0x…: [JS_OBJECT_TYPE]
 - map: 0x… <Map[40](HOLEY_ELEMENTS)>
   [FastProperties]
 - All own properties …: {
   #x: 0x… <HeapNumber 1.5>
     (const data field 0), in-object
   #y: 2 (const data field 1),
     in-object
 }
0x…: [Map] in OldSpace
 - instance size: 40
 - inobject properties: 2
```

Deleting `x` drops `p` into dictionary mode (chapter 119). The `map` is
the object's shape. `y` holds a Smi directly, while `1.5` lives in a
HeapNumber (chapter 55). For an array, `%DebugPrint([1, 2, 3])` shows
`PACKED_SMI_ELEMENTS`, and after `push(1.5)` it shows
`PACKED_DOUBLE_ELEMENTS` (chapter 121).

<Callout kind="definition">
**Natives syntax** is V8's `%Name(args)` syntax for calling its internal
runtime functions directly from JavaScript, enabled only by
`--allow-natives-syntax`. Functions such as `%DebugPrint` (print an
object's map, fields and elements) and `%HasFastProperties` are meant
for V8's own tests: they are not JavaScript, and they can change or
disappear between versions<Cite id="v8-runtime-h" />.
</Callout>

## A field that changes kind

FINDINGS.md section 4 used `--trace-generalization` to explain why a
TypeScript-style class was slow. You can reproduce it: a class with a
field declaration, filled with doubles. Node prints many lines for its
own code, so keep only yours:

```js
class P {
  x;
  constructor(x) { this.x = x; }
}
const ps = [];
for (let i = 0; i < 10; i++) {
  ps.push(new P(i + 0.5));
}
```

```text
$ node --trace-generalization gen.js \
    | grep gen.js
[generalizing]x:h{Any;const}->
 t{Any;mutable} (uninitialized field)
 [new ~P+16 at …/gen.js:3]
```

The field starts as a heap-object field (it holds `undefined` before
the constructor runs), and storing a number generalizes it to a generic
*tagged* field, so every double is boxed. Without the `x;` line, no
such line appears for `x`.

## Garbage collection

Keep three million small objects alive and watch the collector:

```text
# Node v22.23.4, V8 12.4.254.21 (trimmed)
[…]   24 ms: Scavenge 4.4 (5.1) ->
  3.9 (6.1) MB, … 1.03 / 0.00 ms …
  allocation failure;
[…]  214 ms: Mark-Compact 53.7 (86.2)
  -> 41.0 (74.2) MB, … 44.16 / 0.00
  ms … GC in old space requested
[…]  577 ms: Scavenge 166.9 (185.5)
  -> 166.9 (201.5) MB, … 32.16 / 0.00
  ms … allocation failure;
3000000
[…]  617 ms: Mark-Compact 205.6
  (235.1) -> 3.6 (36.9) MB, …
```

Each line gives the time since start, the collector, the size of the
objects before and after (with the heap's memory size in brackets), the
time it took, and the reason<Cite id="v8-gc-tracer" />. Scavenges are
young-generation collections, mark-compacts old-generation ones
(chapter 124). At 577 ms a scavenge freed nothing: every object was
still in `keep`. Once the script had finished, the last mark-compact
found almost everything dead.

## What you learned

- **Engine tracing**: V8's `--print-bytecode` (with a filter),
  `--trace-opt`, `--trace-deopt`, `--trace-generalization` and
  `--trace-gc` report its decisions as it makes them.
- A deopt line gives the **kind** (eager or lazy), the **reason**, the
  function, the tier, and the **bytecode offset**, which you can match
  to the `--print-bytecode` listing.
- **Natives syntax** (`--allow-natives-syntax`) gives `%DebugPrint` and
  `%HasFastProperties`: maps, fields, elements kinds and dictionary
  mode, live.
- All of it is **V8-internal** and version-specific: label your output
  with the version, and expect it to change.
